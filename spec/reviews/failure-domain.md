# SR-002: Failure-Domain Analysis — ec_distann Spec Batch

## Summary

Revision `d25ea9e0c` replaces the self-sufficient inline-vector record with a
two-object design: a lean index record (coarse `search_code` + adjacency +
neighbor codes, FR-076) plus a co-placed full-precision heap row read
node-locally for exact rerank (FR-078/FR-079, ADR-085 D11). This is the correct
`ec_diskann` split and it fixes the D1 amplification, but it opens a failure
class the atomic inline-vector layout structurally could not have: record and
vector are now two distinct physical objects, on two storage tiers, that can
diverge (one present, one absent), drift apart (record hash-owned here, heap row
elsewhere), age out independently (tombstone/vacuum), fail independently
mid-hop, and — critically — obey different mutability rules (the index record is
epoch-immutable under D10; the heap tier, being the base table under normal PG
MVCC/VACUUM, is not). FR-079's three-outcome table (present / not-owned /
owned-but-absent) classifies only the **index-record** read; the second
**heap** read it added in the same edit has no defined outcome table, no fault
class, and no coverage in NFR-020's taxonomy. Five new fault modes
(FND-012..FND-016) are enumerated below; four are genuine spec gaps and one
(co-placement drift) is build-time-asserted but runtime-undefined.

Prior-findings re-evaluation: the revision touched only FR-076/078/079,
ADR-085, and NFR-018. The identity/DML/epoch/beam findings on the untouched
requirements (FND-001..003, FND-005..011) persist unchanged. FND-004 is
**updated, not resolved**: its premise (heap tuple and graph record may live on
different nodes) is now a first-class co-placement *obligation* (FR-078-AC-4),
which mitigates the read-path split but reintroduces the same split as a runtime
drift hazard (FND-013) and does not touch the mid-delete lost-tombstone hazard
it raised. FND-008 (epoch immutability vs in-place mutation) gains a new
dimension — the heap tier — captured as FND-016. No prior finding is fully
resolved by this revision.

## Findings

| ID | Severity | Summary | Refs |
|----|----------|---------|------|
| FND-001 | high | Epoch-mismatch retry rule contradicts in-scan consistency: FR-082 says the coordinator "retries once after refreshing its epoch view", but FR-082 also requires one scan to execute entirely within one epoch. If refresh happens after k−1 hop rounds succeeded against the old epoch, continuing under the new epoch mixes epochs; restarting the whole scan is the only consistent reading but is unstated (and interacts with the NFR-019 BW×H cap — do restarted rounds count?). Specify: refresh-retry means full-scan restart under the new epoch, with counter semantics. (Now largely addressed by FR-082's restart rule + AC-2 + NFR-019 reset; retain until the SR cross-check confirms the counter semantics are drilled.) | FR-082, FR-081, NFR-019, NFR-020, EC-019, EC-022 |
| FND-002 | high | vec_id hash-collision handling exists only at build time. ADR-085 D6 fails the build on collision and EC-020/TC-038 test only the build path, but FR-083 incremental insert computes hash64(source_identity) for a new vector against a live graph; a collision with an existing vec_id would alias two logical rows into one record (or overwrite it) with no specified detection or error. Specify insert-time collision behavior (detect-and-error) and add the case to the fault taxonomy/TC-043. | FR-083, FR-076, ADR-085 D6, EC-020 |
| FND-003 | medium | Entity-identity gap for UPDATE: vec_id is stable per source_identity across epochs, so an UPDATE to an indexed row (delete + aminsert in PG AM terms) re-inserts under the same vec_id while the old record is live or tombstoned. Whether this is an overwrite, an error, or a tombstone-then-replace — and how in-flight traversals holding the old adjacency behave — is unspecified in FR-076/FR-083. | FR-076, FR-083, ADR-085 D6 |
| FND-004 | medium | Cross-node delete/tombstone path still unspecified after co-placement. The revision co-locates each record's heap row on the record's hash-owned node (FR-078-AC-4), so the read path is node-local, but the DML origin node need not be the vec_id-owning node: FR-083's ambulkdelete "SHALL tombstone the record" (and now must also account for the co-placed heap row's deletion/vacuum lifetime) implies a remote write whose transport, epoch interaction, and mid-delete failure mode remain absent — NFR-020 covers mid-insert but a lost tombstone still silently resurrects a deleted row (FR-083-AC-1), and the co-placed heap row's fate after delete is undefined (feeds FND-014). | FR-083, FR-078, FR-078-AC-4, NFR-020 |
| FND-005 | medium | Reachability is a build-time-only invariant: FR-077-CON-3 (medoid reachability) is asserted on the stitched output, but vacuum drops edges to reclaimed records "until repaired" and incremental insert re-prunes neighbor degrees — neither carries a reachability (or repair-completeness) obligation, so the published graph can silently disconnect over DML churn, degrading recall with no drill or counter that would detect it. Add a post-vacuum/post-insert reachability property or a periodic connectivity check requirement. | FR-083, FR-077-CON-3, EC-023, NFR-017 |
| FND-006 | medium | FR-079 `code_threshold` is unbounded lossy pruning with no owner or correctness constraint: neighbors "MAY be omitted" below a caller-supplied floor, but no FR states who computes the threshold, how it is bounded so pruned neighbors provably cannot enter the top-k, or how it composes with FR-081-AC-4's early-exit-equivalence guarantee. As written, a too-aggressive threshold silently degrades recall — the exact class NFR-020 bans — via a documented parameter rather than a fault. | FR-079, FR-081-AC-4, NFR-020 |
| FND-007 | medium | Result-set completeness under beam exhaustion is undefined: empty index, k greater than live (non-tombstoned) records, an all-tombstone frontier, or a beam that exhausts before H rounds with fewer than k exact results. NFR-020 demands "correct complete result or error" but no requirement defines whether returning fewer than k rows is complete-and-correct or an error, so the drills cannot classify these outcomes. | FR-081, FR-075-AC-3, NFR-020 |
| FND-008 | medium | Epoch immutability vs in-place mutation is unresolved: FR-082 treats a published epoch as a consistent, fingerprint-identified artifact, yet tombstone flag writes (FR-083 delete), delta-buffer inserts (D5), and incremental-insert back-edge read-modify-writes all mutate published-epoch state without changing the fingerprint. Specify what the fingerprint attests to (topology/roster only vs record content) and the consistency rule for readers concurrent with these in-place writes. The revision adds a second mutable surface not covered by D10 — the co-placed heap tier — see FND-016. | FR-082, FR-083, ADR-085 D5, ADR-085 D10 |
| FND-009 | low | Retired-epoch reclaim gate has no leak/failure behavior: FR-082-AC-3 waits on an in-flight query count reaching zero, but a coordinator crash or abandoned scan that never decrements the count wedges reclamation forever. FR-082 now documents an operator override, so this is partially addressed; retain until the override is given AC/drill coverage (no timeout or lease is specified for automatic recovery). | FR-082, NFR-020 |
| FND-010 | low | Head-index construction failure policy is unstated (trust-boundary strictness): FR-080 builds the in-memory head index lazily "on first use per epoch" from a persisted sample, but a missing/corrupt sample or construction failure has no defined behavior — strict (fail the scan) vs resilient (fall back to medoid entry with degraded first hops) is unchosen, and the fallback would silently change recall. | FR-080, NFR-020 |
| FND-011 | low | NFR-019's touch bound covers only "a top-k scan", but FR-083 incremental insert runs the same FR-081 beam search plus batched back-edge RMW fan-out; per-insert record-touch work is unbounded by any stated requirement, so insert cost can silently scale with corpus/degree without breaching any gate. | NFR-019, FR-083 |
| FND-012 | high | Present record with an absent co-placed heap row is undefined. FR-079's outcome table classifies the **index-record** read only: (a) present, (b) not-owned → placement error, (c) owned-but-absent → structural fault. The revision added a second, separate **heap** read (via `heap_tid`) for `exact_dist`, but no outcome is defined for "record present, heap row missing" (torn build→publish that wrote the record before the vector, a partial/failed heap write, or a heap tuple later removed). FR-082's "records never physically reclaimed within a published epoch" guarantee — which lets FR-079 declare case (c) "always corruption, never a vacuum race" — is asserted for the index record, not the heap tier (see FND-016), so a missing heap row is not even guaranteed to be corruption. Without a defined error class, `exact_dist` is at risk of being NULL/garbage and the node silently mis-reranked — the silent-wrongness class NFR-020 exists to ban. Add a fourth outcome (owned-record / heap-row-absent → structural fault, distinct from the missing-record case) to FR-079 and a `missing_heap_row` drill to NFR-020. Genuine gap. | FR-079, FR-079-AC-3, FR-076, FR-082, NFR-020 |
| FND-013 | high | Co-placement drift has no runtime detection. FR-078 places both objects by the identical `hash(vec_id)` and FR-078-AC-4 asserts they resolve to the same owning node, but that AC is build/test-time; at runtime FR-079 simply *assumes* the heap read is local ("both reads are node-local"). If a placement bug lands the record on node A and its heap row on node B (or nowhere reachable from A), the local heap read finds nothing and the expansion collapses into the same undefined heap-absent path as FND-012 — a silent miss, not the explicit `placement_drift` error NFR-020 defines for a mis-owned *record*. NFR-020's `placement_drift` case is about record ownership, not heap co-placement, so this violation is unclassified. Require a runtime co-placement check (heap_tid resolves on the owning node) that raises the placement-drift error class rather than degrading silently. Genuine gap (build-asserted, runtime-undefined). | FR-078, FR-078-AC-4, FR-079, NFR-020 |
| FND-014 | medium | Tombstone heap-row lifetime vs exact_dist is undefined. A tombstoned record stays traversable (FR-076-AC-4) and FR-079 returns it "normally with the flag set" (`is_tombstone=true`), and FR-079 unconditionally requires `exact_dist` "for each returned vec_id" against the co-placed heap row. But a tombstone is a deleted base-table row: its heap tuple is a legitimate VACUUM target, so for any tombstone whose heap row has been reclaimed the mandated heap read is a guaranteed miss — a fault the coordinator would then have to swallow for a row it excludes from results anyway. The spec neither says `exact_dist` is skipped (NULL) for tombstones nor requires the heap row to outlive the tombstone flag. Specify that tombstoned rows return with `exact_dist` absent and no heap read is attempted (or, alternatively, that the heap row is retained for the tombstone's lifetime). Genuine gap. | FR-079, FR-076, FR-076-AC-4, FR-083 |
| FND-015 | medium | Two-read partial failure mid-hop is unclassified. Expansion is now two reads per vec_id (index record, then heap row). If the record read succeeds but the local heap read fails on IO error or corruption, NFR-020's general "any single fault → error or correct" applies in spirit but the specific classification is undefined: which error class (the FR-079 structural-fault class of FND-012, or a distinct IO fault), and — decisive for the drill assertions — whether it is retriable (like the epoch-mismatch error) or fatal to the scan. NFR-020's taxonomy enumerates `missing_node_record` but no heap-read-failure case, so the fault drill cannot assert an outcome. Add the case and pin retriable-vs-fatal semantics. Genuine gap. | FR-079, NFR-020, FR-081 |
| FND-016 | high | The co-placed heap tier is outside the epoch-immutability guarantee (ADR-085 D10 / FR-082). FR-082's published-epoch mutation model scopes immutability to "graph-node records and adjacency"; it does not mention the heap tier. But the heap tier IS the base table, under ordinary PG MVCC: a concurrent UPDATE/DELETE + VACUUM can mutate or reclaim a heap tuple mid-scan, and — worse — PG recycles TIDs, so a stale `heap_tid` can resolve to a *different* tuple, silently computing `exact_dist` against the wrong vector with no fault at all. This directly undercuts FR-079's rationale that within a published epoch there are no vacuum races (true only for the index record, not the heap). Either bring the heap tier under the epoch-immutability / retention guarantee (retain heap rows for the epoch's readable lifetime, forbid TID reuse for referenced rows), or make the heap read revalidate identity (e.g. vec_id stamped on the heap row and checked) so a recycled/stale tuple errors instead of silently mis-scoring. Genuine gap, and the highest-consequence of the five (silent wrong result, not an error). | FR-082, ADR-085 D10, FR-079, FR-078, NFR-020 |
