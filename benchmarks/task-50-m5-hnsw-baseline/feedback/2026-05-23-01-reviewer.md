## --bits 4 in HNSW load: no-op, no issue

`suite-manifest.json` shows `--bits 4` on every HNSW step. This
is the `ecaz corpus load` CLI default (`[default: 4]`), expanded
by the suite runner regardless of whether the profile consumes
it. For `--profile ec_hnsw`, the bits flag is a no-op — HNSW
does not use RaBitQ quantization. Not a bug.

If the suite runner ever picks up a feature to omit
profile-irrelevant flags, that would tighten the generated
command lines, but it has no observable behavior impact today.

## Important caveat — no direct A/B against pre-burndown

The manifest correctly states the WSL2 reference at
`benchmarks/task-50-local-baseline/` is **not directly comparable**
(WSL2 i9-10900K vs. Apple M5 Pro arm64). That means this packet
**cannot empirically prove "no regression"** in the strict §Exit
Criterion 3 sense — the only available pre-burndown numbers are
on a different host.

This is acceptable because:

1. The 448 closeout's risk-attenuation argument ("no allocation-
   shape changes, no scoring-math changes, no WAL-ordering
   changes, no payload-byte changes") provides the audit-level
   evidence that the 47-slice rotation should not regress hot
   paths. The bench window's role here is **functional gate
   (HNSW still runs) + forward-baseline establishment**, not
   strict A/B regression detection.
2. Forward Task 50 / Task 33 packets that touch hot paths will
   compare against this new M5 baseline, which is what §Exit
   Criterion 3 is actually designed for going forward.

**Recommendation**: the manifest should make the gate
interpretation explicit. Suggested addition under §Scope or a
new §"Gate disposition" section:

> This packet fulfills §Exit Criterion 3 by establishing the
> M5 post-burndown HNSW baseline. The pre-burndown WSL2 numbers
> are not host-comparable; the rotation's "no observable behavior
> change" claim is audited at the diff level (per closeout 448
> §Bench gate) rather than re-measured here. Subsequent Task 50
> / Task 33 packets that touch HNSW hot paths gate against this
> file as their pre-state baseline.

Not blocking the run — just clarifies the gate semantics in the
durable record.
