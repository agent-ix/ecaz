# Review: Current AWS RaBitQ / IVF Round + New 1M Benches

- New committed work after the prior review: `quant_bits`, bits=1 NEON/LUT, default `rerank_width=50`, 50k/100k closeout, and AWS snapshot workflow changes.

## Findings

### P1: The new 1M benchmark evidence is not closure-quality yet

The 1M artifacts are still local-only in this checkout, so they are invisible to the normal review/benchmark provenance loop until committed and pushed. More importantly, the logs themselves are incomplete or failed:

- `artifacts/latency-1m-bits1.log:1-3` starts with a broken `pg_prewarm` command.
- `artifacts/latency-1m-bits1-v2.log:1-4` is only a SQL quoting error plus a header.
- `artifacts/latency-1m-bits1-v3.log:17-23` has latency, but no completed recall table; it stops after fetching corpus at `latency-1m-bits1-v3.log:25-27`.
- `artifacts/recall-1m-bits1.log:1` is empty.
- `artifacts/cloud-snapshot-1m.log` is zero bytes.

The v3 latency table is also suspicious: nprobe=32 reports p50 37.9 ms, while nprobe=64 reports p50 19.3 ms (`artifacts/latency-1m-bits1-v3.log:17-19`). That can happen if the first measured cell was still warming, but then it should not be used as a final latency curve.

Impact: do not close the round or claim scale confirmation from these 1M numbers yet. Rerun through the benchmark suite with a committed config, fail hard on prewarm/recall errors, use the same count/query set as the 50k/100k runs, and commit the packet-local manifest/results before citing the data.

### P1: The AWS workflow doc says `nlists` changes do not require rebuilding; that is wrong

`docs/aws-bench-workflow.md:71-75` lists `nprobe` and `nlists` together as "Don't rebuild" knobs because they "only affect search." `nprobe` is a scan knob; `nlists` is not. `nlists` controls centroid count, directory/list layout, and tuple assignment at build time. Reusing a snapshot after changing `nlists` silently benchmarks the old index geometry; it does not necessarily error with a posting tuple mismatch.

Impact: this can invalidate exactly the kind of AWS reuse workflow we need for the next optimization round. Move `nlists` to the rebuild-required list and make the snapshot inventory include the built nlists value. This matters because one of the highest-value next optimizations is sweeping list geometry at matched recall.

### P1: `running_top_k_for_pruning` hard-codes K=200 without knowing the query LIMIT

The new no-rerank pre-prune path creates a `CandidateTopK` even when there is no rerank frontier limit (`src/am/ec_ivf/scan.rs:1044-1048`). The helper then defaults to K=200 and explicitly notes that `LIMIT > 200` would see truncation (`src/am/ec_ivf/scan.rs:1152-1165`).

Current EXPLAIN evidence says the Cauchy-Schwarz bound is too loose to prune on this corpus, so this does not bite today. But if the next round tightens the bound, partial-sum early-exit, or score-margin pruning, this becomes a correctness bug: no-rerank scans with LIMIT > 200 can drop candidates before final ranking.

Impact: tie pruning K to the real scan limit, disable no-rerank pre-prune until the limit is available, or gate the default behind an explicit opt-in GUC. The next optimization work should not make this latent truncation real.

### P2: The bits=1 byte-LUT allocates 8KB for every prepared RaBitQ query, including bits=4

`prepare_scorer` and `prepare_estimator` always call `build_bits1_byte_lut_boxed` (`src/quant/rabitq.rs:459-460`, `src/quant/rabitq.rs:491-492`). For non-bits=1 widths, the helper still allocates a zero-filled `Box<[[f32; 8]; 256]>` and returns it (`src/quant/rabitq.rs:1270-1278`).

Impact: this optimizes bits=1 but adds an 8KB heap allocation and memset to every prepared query for the legacy/default bits=4 path. Make the field `Option<Box<...>>`, specialize the bits=1 scorer state, or otherwise avoid allocation when `bits_per_dim != 1`. Also remove the unused `sum_query_dequant` helper's 8KB stack `empty` table (`src/quant/rabitq.rs:1313-1320`) or keep it from ever becoming a hot-path fallback.

### P2: `rerank_width=50` is now a product default based on a narrow lane

The comment says the default is justified by DBpedia bits=1 + `heap_f32`, K=10, and that LIMIT > 10 should override it (`src/am/ec_ivf/mod.rs:24-31`). That may be the right benchmark setting, but as a global default it is now attached to every heap-f32 index that does not specify a width.

Impact: before treating this as landed product behavior, add evidence for 100k/1M recall at the chosen default and document the exact semantic contract. I would prefer an adaptive default such as `max(k * factor, floor)` once the executor scan limit is available, or a storage-format/quant-bits-specific default rather than a single constant.

### P2: Benchmark provenance is still lighter than the repo rules require

This top-level benchmark packet has no `manifest.md`, no `suite-manifest.json`, and no `results.jsonl` under `benchmarks/aws-round-rabitq-ivf/`. The new 1M runs also appear to be one-off command logs instead of an `ecaz bench suite` run.

Impact: the raw numbers are useful for iteration, but not yet durable enough for a comparison against vchord. The next packet should include the suite config, structured results, exact head SHA, snapshot ID, instance type, storage format, quant bits, rerank mode, nlists, nprobe sweep, and whether the run used isolated one-index-per-table surfaces.

### P3: Root-level `callgrind.out.1807567` is tracked outside the packet

`callgrind.out.1807567` is tracked at the repository root from `47e178772`. Review evidence should be packet-local under the owning benchmark/review artifacts directory.

Impact: small issue, but it weakens provenance hygiene. Move it under the benchmark packet and manifest it if it is intentional evidence; otherwise drop it from the branch.

## Further Optimization Options

The current 50k/100k progress is real, but I agree there is still enough headroom to chase another 2-3x. I would prioritize options that reduce candidate volume or avoid heap-rerank I/O before spending more time on small inner-loop wins.

1. Run paired same-host vchord vs ec_ivf with the same query IDs, same runner, same snapshot class, same warmup, and paired recall. This is the measurement gate; until then the remaining gap can be cache, runner, candidate volume, heap fetch, or storage layout.

2. Add per-cell counters for posting pages read, posting tuples visited, candidates scored, candidates pruned, duplicates removed, heap rerank rows, heap blocks fetched, and rerank time. The next 2-3x target depends on knowing whether the p50 is candidate scoring, random heap fetch, centroid routing, or page traffic.

3. Sweep `nlists` and training size at matched recall. Larger list counts may let us reach 0.99 recall with much lower nprobe and fewer candidates. This is likely one of the biggest remaining levers if vchord is winning on routing/list geometry.

4. Try adaptive nprobe from centroid score margins. If the top centroid scores separate cleanly for easy queries, stop probing early; hard queries can still use the high nprobe path. This attacks p50 without sacrificing p95 recall.

5. Prototype an inline rerank sidecar: `rabitq + source_f16`, `rabitq + pq8/residual`, or optional full-source f32 for comparison. vchord appears to buy latency with storage. We should measure that tradeoff directly rather than assuming heap_f32 can close the whole gap.

6. If keeping heap_f32, batch rerank fetches by heap block. Sort the rerank frontier by heap TID/block, fetch/pin pages in locality order, compute exact scores, then restore score order. This can recover much of the vchord advantage without storing full vectors inline.

7. Make `rerank_width` adaptive. Width 50 looks good for K=10 in the current lane, but a fixed relation default is coarse. Test 25/50/75/100 at 50k/100k/1M and choose width from K, score margin, nprobe, or a recall-target profile.

8. Add exact-rerank early stop from approximate margins. Once the current exact top-k is strong enough and remaining approximate candidates cannot overtake under a calibrated bound, stop heap fetches. This is the direct way to make high-recall rerank cheaper.

9. Tighten RaBitQ pruning beyond the current Cauchy-Schwarz bound. The EXPLAIN counters show zero bound prunes today, so the wiring is not the limiter; the bound is. Explore epsilon-bound pruning, query-dependent thresholds, or partial-sum early-exit in the NEON loop.

10. Persist per-code scale/bound metadata in a new posting format. Candidate scoring still pays scalar work around `norm`, `o_dot`, and dequant scale. Storing precomputed scale factors can replace divides and repeated decode-side arithmetic with multiplies.

11. Revisit posting layout for SIMD scan. A structure-of-arrays layout for hot RaBitQ bytes, norms, and heap TIDs could improve streaming and prefetch versus tuple-by-tuple payload decode. This is a format change, but it matches the latency target better.

12. Add software prefetch for posting pages and candidate payloads. At high nprobe the scan is streaming many posting tuples; prefetching the next block/list while scoring the current batch may help p95 and high-nprobe cells.

13. Specialize the bits=1 scorer state fully. Now that bits=1 is the target, avoid generic bits dispatch, generic LUT state, and non-bits=1 branches in the hot estimator path.

14. Consider SVE2-specific kernels if the Graviton v4 runtime exposes useful width. NEON bits=1 is already good, but SVE2 could reduce loop overhead and improve dequant/accumulate throughput if implemented cleanly with scalar fallback.

15. Compare centroid-routing quality against vchord. If vchord reaches the same recall with fewer visited candidates, the fix is not another estimator micro-optimization; it is training, list count, residual routing, or multi-probe strategy.

16. Build a storage-vs-latency Pareto table. Include compact RaBitQ heap_f32, RaBitQ + f16 sidecar, RaBitQ + PQ sidecar, and full inline source. The target may require explicitly choosing a storage budget rather than forcing the smallest index to match vchord latency.

## Summary

The bits=1 path and width=50 sweep are the right direction, but the latest 1M evidence is not usable as closure yet. The most promising next round is not another small attribution pass; it is a controlled candidate-volume/rerank-I/O investigation with same-host vchord comparison and enough counters to decide whether we should spend bytes in the index to remove heap fetches.
