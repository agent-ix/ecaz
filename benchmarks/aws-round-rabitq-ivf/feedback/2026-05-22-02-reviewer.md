## Findings

### P1: The final packet still says the numbers are `pg_prewarm`-driven, but every new measured log shows prewarm failed

`results.md:82-86` still frames the final cumulative numbers as `pg_prewarm` warm-cache evidence. The latest logs continue to show the same failed SQL before the measured tables:

- `artifacts/latency-final.log:5-7`
- `artifacts/latency-rerank-heap-f32.log:1-3`
- `artifacts/latency-rerank-off.log:14-16`
- `artifacts/latency-centroid-simd.log:5-7`

Impact: the p50 numbers may still be useful, but they are query-warmed / workload-warmed numbers, not `pg_prewarm` numbers. Please either fix the quoting and rerun the final summary cells, or relabel the packet so future readers do not treat these as controlled buffer-pool prewarm evidence.

### P1: The BF16 row says "inactive on V2", but the code still actively dispatches to BF16 on BF16-capable aarch64 hosts

`results.md:141` says the BF16 bfdot path is "kept but inactive on V2". The code path does not make it inactive: `sum_query_dequant_with_bf16` checks `is_aarch64_feature_detected!("bf16")` and returns `sum_query_dequant_neon_bf16_bits4` before the f32 NEON path (`src/quant/rabitq.rs:1303-1315`). Graviton 4 / Neoverse V2 exposes BF16 per the prep packet, so this remains the production scoring path there.

Impact: the current text understates both risk and behavior. Since the BF16 artifact is neutral/slower and we still do not have a deterministic BF16-vs-f32 score drift gate, either disable BF16 by default or document that it is active and add drift/recall tests before treating the final numbers as production-safe.

### P1: The vchord comparison is not yet strong enough to support the "3.1x structural gap" conclusion

The packet compares current ec_ivf runs on the Phase A m8g.xlarge setup against historical vchord data from `benchmarks/comparators-50k-100k-1m/manifest.md`, whose host was m8g.2xlarge (`manifest.md:25-31`). The comparator packet also has multiple vchord latency sources with different values: `artifacts/comparators/50k/vchord/rabitq/latency.log` reports p50 2.725 ms, `artifacts/sweep/50k/vchord/rabitq/default.latency.log` reports p50 16.424 ms, and the manifest Pareto row reports 90.3 ms at recall 0.9995.

Impact: the high-level architectural hypothesis may be right, but the packet should not yet claim a measured 3.1x structural gap. We need a same-host, same-runner, same-query-set vchord/ec_ivf comparison with one latency source and paired recall before closing the round on that conclusion.

### P1: The LUT-hoist + pre-prune attribution is still not supported by counters

The cumulative table still attributes the 9.35 ms -> 8.64 ms change to "LUT hoist + pre-prune" (`results.md:140`, `results.md:202-206`). The no-rerank/default RaBitQ path does not construct a `running_top`, because `pre_rerank_candidate_limit` only returns a limit for `rerank = 'heap_f32'` with positive width (`src/am/ec_ivf/scan.rs:1129-1135`). The updated rerank experiments are good, but the packet still needs EXPLAIN counters showing `stats_postings_pruned_by_bound > 0` for the exact cells used in the attribution.

Impact: keep the latency improvement, but call the cause "LUT hoist plus possible run-to-run/cache effects" until the packet includes per-cell pruning counters.

### P2: `inner_product_neon` relies on a debug-only length check before unsafe loads

The new centroid SIMD helper uses `let n = left.len()` and then loads from both slices up to `n`, but the only equality check is `debug_assert_eq!(left.len(), right.len())` (`src/am/ec_ivf/scan.rs:868-895`). The previous scalar implementation used `zip`, which could not read beyond either slice.

Impact: the current call path likely passes matching query/centroid dimensions, but this is now an unsafe precondition. Use a release `assert_eq!`, pass the expected dimension from metadata, or compute over the common length only if mismatch should be tolerated. Also add a scalar-vs-NEON differential test for the centroid inner product, including non-multiple-of-16 dimensions.

### P2: Changing the global `rerank_width` default to 200 needs a narrower contract

The latency win from capping heap rerank is real: `latency-rerank-width-sweep.log` shows 50k nprobe=64 p50 dropping from 79.4 ms uncapped to 8.93 ms at width 200 with the same reported recall. But `EC_IVF_DEFAULT_RERANK_WIDTH` is a global default (`src/am/ec_ivf/mod.rs:21-27`) and the evidence is one DBpedia 50k lane.

Impact: I would not block the experiment, but before landing this as a product default, document the semantic change and add a regression test/admin snapshot expectation for a heap_f32 index created without an explicit width. Consider whether the default should be tied to `k`, `nprobe`, or `max_candidate_rows` rather than a fixed 200 for all scales.

## Optimization Options / Next Checks

The current 8.37 ms high-recall point is still plausibly 2-3x above where it can land. I do not think we should treat the vchord gap as closed or purely structural yet; the packet has not isolated enough of the remaining time.

1. Run same-host vchord vs ec_ivf on the current m8g.xlarge or m8g.2xlarge, using the same query IDs and fresh latency/recall extraction. This is the highest-value next measurement because it validates whether the remaining gap is truly structural.

2. Add EXPLAIN-counter rows to the packet for the final no-rerank and heap_f32 runs. Specifically capture postings visited/scored/pruned, heap TIDs scored, filtered duplicates, rerank rows, and posting pages read. Right now the verification is too light to tell whether the next 2-3x is in scoring, heap fetch, dedup, centroid routing, or candidate volume.

3. Prototype an in-index rerank source variant as the direct vchord-countermeasure. The packet's storage comparison makes the tradeoff explicit: vchord pays hundreds of MB to avoid heap fetches. A controlled `rabitq+source_f32`, `rabitq+source_f16`, or `rabitq+pq8-rerank` sidecar variant would test the core tradeoff: pay index bytes to avoid 100-200 random heap tuple fetches per query. This is the most likely single path to a 2x+ win at high recall.

4. Batch and locality-optimize heap rerank before giving up on heap_f32. Today heap rerank still appears to fetch row versions candidate-by-candidate. Sort the rerank frontier by heap TID/block before fetch, batch page pins where possible, and then restore score order. If the index remains compact, this could claw back a large fraction of the vchord advantage without storing full source vectors inline.

5. Make heap rerank width adaptive. A fixed 100/200 is a good benchmark knob, but a production default could be `max(k * factor, floor)` with an upper cap, or chosen from observed candidate score margin. The width sweep suggests 100 may be as good as 200 in this lane; quantify where it breaks. Also test width 25/50/75 at nprobe 64, because at recall 0.988 the current 100 frontier may still be conservative.

6. Reduce candidate volume rather than only scoring it faster. Sweep `nlists`, training sample size, and nprobe for recall-matched points. vchord may be winning with better routing/list geometry, not just rerank storage. If `nlists=224` forces too many candidates at 0.99 recall, try larger `nlists` with lower nprobe and measure posting pages + candidates at matched recall.

7. Add source-aware rerank thresholds. If RaBitQ score margins are strong, stop rerank fetches once the remaining candidate bound cannot enter top-k after exact rerank. This needs a calibrated bound or empirical guard, but it attacks the high-recall heap fetch cost directly.

8. Store precomputed RaBitQ per-code scale metadata. Persist `scale = norm / (o_dot * x_norm)` and `bound_scale = norm / abs(o_dot)` in a new storage version so scanning replaces candidate-time divides and repeated scalar decode with multiplies. This will not fix heap rerank, but it makes high-nprobe no-rerank and pre-prune cheaper.

9. Vectorize nibble unpack/table lookup. The f32 NEON kernel still builds dequant vectors through scalar nibble expansion. A `tbl`/SVE2 lookup path for 16 or 32 nibbles at a time is the remaining pure-kernel route. It is less likely than rerank-source work to yield 2x alone, but it can stack with other wins.

10. Consider a two-level or residual rerank code. A cheap second-stage code stored inline with each posting, such as PQ8/F16 residual against centroid, could improve final ordering enough to lower heap rerank width or skip heap rerank for many queries. This is the storage/latency middle ground between today's compact RaBitQ and vchord's full-source-inline approach.

11. Keep BF16 out of the default path until it wins. If it stays in tree, gate it behind a feature/GUC or runtime env knob and add score-drift tests plus 50k/100k recall parity evidence.

12. Add centroid SIMD unit coverage. The current latency gain is plausible and useful, but the unsafe helper needs scalar parity coverage for dimensions like 1, 3, 15, 16, 31, 1536.

13. Fix the prewarm command and make the runner fail hard when warmup fails. Silent warmup failure is now repeated across several artifacts and keeps weakening otherwise-useful evidence.

## Summary

The latest round makes real progress: the 4-way f32 kernel, centroid SIMD, and bounded heap rerank results are directionally strong. The remaining review blockers are evidence quality and a few safety/contract gaps, not the basic optimization direction. The packet should be tightened before using it as the final comparison against vchord.
