# Review: AWS RaBitQ / IVF Optimization Packet

Scope reviewed:

- Branch `aws-optimization-ivf-rabitq-spire` at `efc8cb301`.
- Packet `benchmarks/aws-round-rabitq-ivf/` and prep packet `benchmarks/aws-round-prep/`.
- Committed code changes through `efc8cb301`, plus current untracked follow-up artifacts `artifacts/latency-bf16.log`, `artifacts/latency-post-hashbrown.log`, and `setup-rerank-variants.sql`.

## Findings

### P1: The packet attributes gains to Cauchy-Schwarz pre-prune, but the measured default indexes do not appear to activate it

`results.md` says the final 7-8% gain comes from "LUT-hoist + pre-prune" and says skipped candidates could not enter top-K. The code path only constructs `running_top` when `uses_score_bound_pruning()` is true **and** `pre_rerank_candidate_limit(index_options)` returns a limit:

- `src/am/ec_ivf/scan.rs:979-983`
- `src/am/ec_ivf/scan.rs:1072-1078`

That limit is only present for `rerank = 'heap_f32'` with positive `rerank_width`. The committed fixture script builds the measured RaBitQ indexes with only `WITH (storage_format = 'rabitq')`, so `rerank = auto`, and `RerankMode::Auto` resolves to `Off`.

Impact: the reported post-NEON default RaBitQ sweep may be measuring LUT hoist and cache/noise, not pre-prune. The pre-prune claim needs either a rerank-enabled rerun using `setup-rerank-variants.sql` or EXPLAIN counter evidence showing `stats_postings_pruned_by_bound > 0` for the cited cells.

### P1: The warm-cache claim is contradicted by the artifacts

`results.md:82-86` says the final numbers are `pg_prewarm`-driven. The cited warm logs show the prewarm SQL failed before the measurement:

- `artifacts/latency-warm-cycle2-xlarge.log:2-5`
- `artifacts/latency-bf16.log:1-3`
- `artifacts/latency-post-hashbrown.log:7-9`

Impact: the p50s may still be stable after query-driven warming, but the packet should not call them `pg_prewarm` evidence. Fix the SQL quoting and rerun the final comparison, or relabel these as query-warmed measurements and keep the cold-cache caveat attached.

### P1: BF16 is now a production dispatch path without a deterministic score-drift gate, and the current artifact does not show a win

`PreparedEstimator::estimate_ip` and `estimate_ip_scalar_only` now always pass BF16 mirror state into the scoring dispatcher (`src/quant/rabitq.rs:836-864`), and Graviton 4 will prefer the BF16 `bfdot` path when `bf16` is detected (`src/quant/rabitq.rs:1275-1286`). That path truncates the query and dequant LUT to BF16 (`src/quant/rabitq.rs:1196-1216`) before scoring.

The only committed SIMD equivalence test covers f32 NEON vs scalar (`src/quant/rabitq.rs:2684-2716`), not BF16 vs f32/scalar. The untracked `latency-bf16.log` also does not show a clear latency win over the prior f32 warm numbers: 50k nprobe=64 is 8.82 ms BF16 vs 8.64 ms in `results.md`, and 10k nprobe=64 is 4.16 ms BF16 vs 4.07 ms.

Impact: this changes ranking arithmetic on BF16-capable ARM hosts without a unit-level drift budget and currently looks neutral to slightly slower. I would keep the f32 NEON path as the default and gate BF16 behind explicit evidence: scalar/f32/BF16 score-drift tests, recall at 50k+ and 100k, and a latency win after the prewarm issue is fixed.

### P2: The packet has durable-evidence gaps

The packet cites `/tmp/aws-round-rabitq-ivf/...` for missing 10k recall logs (`results.md:78-80`). The checked-in packet also lacks the suite runner's normal `suite-manifest.json`, `results.jsonl`, per-step recall logs, and storage logs for the full matrix. For benchmark packets, local-only `/tmp` paths and terminal extracts should not be the durable source of truth.

Impact: the headline is plausible, but the packet is not yet strong enough as durable review evidence. Bring the missing suite artifacts into `benchmarks/aws-round-rabitq-ivf/artifacts/` or explicitly narrow the claims to the logs that are actually packet-local.

### P2: BF16 prep overhead is paid even when the runtime will not use BF16

`prepare_estimator` always builds `query_bf16` and `dequant_lut_bf16` (`src/quant/rabitq.rs:486-490`), while the field comment says the vector is empty when BF16 is not detected (`src/quant/rabitq.rs:816-820`). On x86 and non-BF16 ARM, this adds a per-query allocation and conversion with no scoring benefit.

Impact: this is probably small next to SRHT rotation, but query prep is in the measured query path. If BF16 remains, build the BF16 mirror only behind `cfg(target_arch = "aarch64") && is_aarch64_feature_detected!("bf16")`, or remove it until BF16 has a demonstrated latency/recall tradeoff.

## Optimization Options To Explore

These are the next things I would consider, in priority order.

1. Establish attribution before more code changes. Fix prewarm, run `EXPLAIN (FORMAT JSON, ecaz, ANALYZE)` for the same cells, and extract `stats_postings_scored`, `stats_postings_pruned_by_bound`, `stats_filtered_duplicates`, `stats_heap_tids_scored`, and rerank row counts. That tells us whether the remaining gap is inner scoring, candidate volume, dedup, or heap rerank.

2. Treat BF16 as experimental for now. The current BF16 kernel still does scalar nibble unpack into a stack `dq` array before `bfdot`, so it may be decode-bound rather than FMA-bound. Either disable it or try a proper vectorized nibble-unpack/table-lookup kernel before keeping it.

3. Add a deterministic BF16/f32 score-drift harness. For each dim and seed, compare scalar f32, NEON f32, and BF16 scores across random queries/codes, report max absolute error, rank correlation, and top-k overlap. This is cheap and should gate any approximate arithmetic path.

4. Store precomputed RaBitQ scale metadata in future index versions. The scan still reads `norm`, `o_dot`, and `x_norm` and computes `norm * sum / (o_dot * x_norm)` per posting. Persisting `scale = norm / (o_dot * x_norm)` and `bound_scale = norm / abs(o_dot)` would replace candidate-time divides with multiplies and make the pre-prune check cheaper. This needs a storage-format version decision.

5. Push the nibble decode harder. The f32 NEON kernel is strong, but every iteration still expands nibbles through scalar loads into temporary arrays. Candidate approaches: NEON `tbl` lookup for 16 nibbles at a time, SVE2 table lookup on Graviton 4, or a build-time expanded-code sidecar for hot benchmark profiles if the storage/latency tradeoff pencils out.

6. Try an SVE2 path on Graviton 4. ADR-039 already calls out Graviton 4 SVE2. A 256-bit SVE2 implementation could process wider chunks than 128-bit NEON, but only if nibble unpack is vectorized too; otherwise it will just move the bottleneck.

7. Measure whether dedup is worth doing during scan. The `hashbrown` swap is fine, but the bigger question is whether `stats_filtered_duplicates` is high enough to justify a hash map in the hot path. If duplicates are rare, collect candidates into a bounded vector/heap and dedup after partial selection; if duplicates are common, consider a tighter `ItemPointer` key representation or list-local dedup strategy.

8. Use rerank mode as a real tuning dimension. `setup-rerank-variants.sql` is the right direction, but the packet needs measured `rerank=heap_f32` cells. If heap rerank lets us run much lower nprobe at the same recall, it will beat micro-optimizing score kernels.

9. Tune IVF topology against vchord, not just kernels. Sweep `nlists`, `nprobe`, training sample size, and rerank width at 50k/100k/1M. If vchord is winning by candidate volume or centroid quality, SIMD alone will not close it.

10. Build the AWS bench binary for the host when doing hardware-specific claims. For the benchmark lane, try `-C target-cpu=neoverse-v2` or `native` and record it in the packet. Keep portable release artifacts separate, but let the Graviton comparison use Graviton scheduling.

11. Compare against vchord with matched recall, not just matched knobs. Report the fastest ec_ivf RaBitQ configuration that reaches the same recall/ndcg as vchord at each corpus size. If that requires a different nprobe/rerank mix, the product comparison should use the recall-matched point.

12. Consider a two-stage scorer. Use RaBitQ's compact code for broad prefiltering, then either heap f32 or a persisted higher-fidelity compressed scorer for the small frontier. This is likely more fruitful than trying to make one 4-bit estimator serve both pruning and final ordering.

## Summary

The f32 NEON work is real progress and looks like the main 3x gain. I would not yet accept the "pre-prune contributed 7-8%" or "pg_prewarm-driven final numbers" claims as written. The next pass should fix the packet evidence, explicitly measure rerank/pre-prune with counters, and either revert/gate BF16 or prove it with drift + recall + latency evidence.
