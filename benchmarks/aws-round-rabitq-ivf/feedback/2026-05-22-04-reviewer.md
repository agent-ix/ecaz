# Review: 1M Recall Update + Current Closeout Claims

## Findings

### P1: The 1M "faster than vchord" conclusion is not recall-matched or runner-matched

`results.md:465-477` now says ec_ivf is faster than vchord at every measured nprobe. The data is promising, but that conclusion is too strong:

- The vchord row is `90.3 ms @ recall 0.9995` from the comparator sweep (`benchmarks/comparators-50k-100k-1m/artifacts/sweep/1m/_pareto.tsv`).
- The best ec_ivf measured point is `67.3 ms @ recall 0.9936` (`results.md:456-460`), not the same recall band.
- The ec_ivf latency table is from the pre-resize `m8g.xlarge` run (`results.md:421-445`), while the recall run moved to `m8g.2xlarge` (`results.md:449-453`) and the vchord comparator packet was also `m8g.2xlarge`.
- The vchord comparator uses 200 queries/iterations; the ec_ivf recall uses q=500 and latency uses 500 iterations. That is better than before, but still not a paired same-query comparison.

Impact: this is not yet a direct win over vchord at matched recall. The supported statement is narrower: at 1M, ec_ivf reaches 0.9936 recall in 67.3 ms, while historical vchord reaches 0.9995 recall in 90.3 ms on a different run. To claim the vchord gap is closed or reversed, rerun vchord and ec_ivf on the same host, same query IDs, same benchmark runner, and include a point that actually targets vchord's recall ceiling.

### P1: `nlists` is still documented as a no-rebuild knob

The AWS workflow doc still says `nprobe` / `nlists` reloption changes "only affect search" and should not rebuild (`docs/aws-bench-workflow.md:71-75`). That remains wrong for `nlists`: list count determines centroid training, directory/list layout, and tuple assignment at index build.

Impact: this is now more urgent, because one of the highest-value next optimizations is sweeping `nlists` at 1M. If the workflow teaches agents to reuse a snapshot after changing `nlists`, the next benchmark round can silently measure the old geometry.

### P2: The cross-scale closeout contains a stale/wrong 50k high-recall claim

`results.md:496-498` says "At nprobe=128 we reach vchord's recall ceiling exactly (0.9991 vs vchord 0.9995 at 1m) in 7.5 ms at 50k." The final width=50 sweep directly above says:

- nprobe=128: `6.67 ms`, recall `0.9963` (`results.md:330-337`)
- nprobe=256: `11.3 ms`, recall `0.9971` (`results.md:330-337`)

The `7.5 ms / 0.9991` pair appears to come from an earlier bits=1 byte-LUT artifact, not the current final-default width=50 sweep. It also compares 50k recall against a 1M vchord recall ceiling, which is not a stable cross-scale claim.

Impact: fix this before treating `results.md` as the round summary. It currently overstates the final operating point and could misdirect target-setting.

### P2: The 1M packet still contains failed/incomplete artifacts without clear labeling

The new q=500 recall artifact is useful and complete (`artifacts/recall-1m-bits1-q500.log:7-20`). But the packet also commits:

Impact: keep these if they are intentionally historical, but mark them as failed/deferred in a manifest or replace them with clean final artifacts. Right now a reader has to infer which files are authoritative from `results.md`.

### P2: Benchmark provenance still does not satisfy the packet rules

There is still no `manifest.md`, `suite-manifest.json`, or `results.jsonl` under `benchmarks/aws-round-rabitq-ivf/`. The new 1M measurement was not driven by a checked-in `ecaz bench suite` config.

## Further Optimization Direction

The q=500 1M recall data changes the optimization picture: ec_ivf is now in the right broad band, but the next 2-3x depends on reducing candidate work, not just shaving the current NEON loop.

1. **Run a paired comparator suite first.** Same m8g.2xlarge, same q=500, same warmed state, same runner, ec_ivf + vchord + pgvectorscale. The 1M comparator packet shows pgvectorscale has a strong ~98% recall corner (`6.5 ms @ 0.980`), and vchord has the ~99.95% ceiling (`90.3 ms @ 0.9995`). We need ec_ivf plotted against both.

2. **Sweep `nlists` at 1M.** The current result likely uses the automatic list geometry from index build. Try larger list counts with lower nprobe and measure recall, posting pages read, postings visited, candidates scored, and heap rerank rows. If routing improves, this can give a real 2x by cutting visited candidates.

3. **Measure candidate counters on the 1M cells.** The latency curve from nprobe=64 to 256 is almost linear, which points at candidate volume. Add EXPLAIN/counter rows for postings visited/scored, pages read, heap fetches, rerank frontier size, and time in heap rerank.

4. **Test inline rerank sidecars.** vchord spends index bytes to avoid heap-source fetch cost. Prototype `rabitq + source_f16`, `rabitq + PQ/residual`, or full-source f32 sidecar as a Pareto experiment. We need to know how many bytes buy the next 2x.

5. **Batch heap rerank by heap block.** If we keep heap_f32, sort the rerank frontier by block/TID before exact scoring and restore score order after. This attacks random heap fetch cost without changing the index format.

6. **Make nprobe adaptive.** The p50 path should not always pay the hard-query nprobe. Use centroid score margin or candidate bound progress to stop probing early for easy queries.

7. **Make rerank_width adaptive.** Width=50 works for K=10 on this corpus, but use K and score margin to decide whether a query needs 25, 50, 100, or more.

8. **Tighten pruning after fixing the LIMIT contract.** The existing Cauchy-Schwarz bound does not prune on this corpus. Partial-sum early exit or calibrated score bounds could cut scoring, but only after pruning K is tied to the real query LIMIT.

9. **Specialize the bits=1 scorer state.** Remove generic bits dispatch and non-bits=1 allocation from the bits=1 hot path and the legacy bits=4 path. This is smaller than the rerank/candidate-volume work, but it is clean stacked speed.

10. **Consider a posting layout v2.** A structure-of-arrays layout for hot code bytes, scale metadata, and heap TIDs would make the scan more cache/prefetch friendly than tuple-by-tuple decoding. This is a bigger format change, but it is the right kind of change if the 1M counters show posting scan bandwidth is dominant.

## Summary

The new q=500 1M recall measurement is valuable and materially improves the packet. The blockers are now mostly claims and methodology: do not call the vchord comparison won until it is paired and recall-matched, fix the `nlists` workflow rule before geometry sweeps, and add counters so the next optimization round can target candidate volume or heap rerank instead of guessing.
