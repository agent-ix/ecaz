## Code review — lazy candidate (`245c2054f`)

I read the full scan-path diff plus the surrounding cursor machinery on the
branch head. Findings:

- **Window safety.** The `RemotePending` check sits *after* the
  proven-prefix/deepening guard in `custom_scan_access`, so
  `output_index < proven_prefix_len(state)` always holds and
  `pending_materialization_window(output_index, batch, proven)` can never
  return an empty or inverted range. The `remote_ids.is_empty()` internal
  error is genuinely unreachable rather than a latent panic.
- **Proven-prefix equivalence.** Eager compacts dropped rows and counts
  emitted rows with `raw_rank < effective`; lazy keeps every hit
  (`RemoteSkipped` occupies the slot) and sets
  `proven_outputs = hits.len().min(effective)`. Because lazy slot index ==
  raw rank and skipped slots are never emitted, the set of rows served
  inside the proven prefix is identical between arms. The
  011-P1 unproven-tail rule is preserved.
- **Deepening.** Rebuild starts the next window at the consumed cursor, so
  the stable consumed prefix is never re-fetched; `next_output` is not
  reset; the deepen cap (`max(initial × 64, 1024)`) is untouched and remains
  the work bound. Correct.
- **Fail-closed.** Any materialize error goes through `pgrx::error!`, so a
  later-batch owner failure aborts the query; the live outage scenario in
  packet 003 confirms this end-to-end.
- **Isolation.** Every new variant, branch, GUC, and counter is behind
  `distann-head-attribution-benchmark`; the production-build check log in
  packet 003 confirms the GUC and branch are absent from normal builds.

## Non-blocking findings (carry into Task 191)

1. **P3 — "toasted" scenario likely never leaves the heap page.**
   `payload_note = repeat(md5(id), 400)` is 12,800 bytes of a 32-char string
   repeated 400×; under default EXTENDED storage pglz will compress this to a
   few hundred bytes and keep it inline. The scenario therefore exercises
   compressed-inline varlena detoast, not out-of-line TOAST pointers. Task
   191's matrix should force genuine out-of-line storage — incompressible
   content (e.g. concatenating distinct `md5(id || n)` chunks) or
   `ALTER TABLE … ALTER COLUMN payload_note SET STORAGE EXTERNAL`.
2. **P3 — duplicate fetch of materialized-but-unconsumed rows across a
   deepen.** A rebuild reverts every remote slot to `RemotePending`,
   including slots at/above the cursor that a previous window already
   materialized but the executor had not yet consumed. Starting the window at
   the cursor protects consumed rows only; the `[cursor, old-window-end)`
   remainder is re-fetched. Bounded and correctness-neutral, but Task 191 can
   carry materialized payloads across rebuilds of the stable prefix.
3. **Note — stage double-booking.** In the lazy build path the same
   association elapsed is recorded under both `MaterializeOutputAssociate`
   and `OutputMerge` (and window materialization is added into
   `CustomScanTotal` per sample). This is deliberate for cross-arm
   comparability and the packet tables never sum the aliased stages, but any
   future consumer of `results.jsonl` stage rows should not add
   `output_merge` to `materialize_output_associate`.
4. **Note — suite runner git descriptor ordering.** The runner writes the
   tracked output manifest before capturing its git state, self-inflicting
   `-dirty`. Small suite fix (capture descriptor first) would remove a
   recurring manifest caveat.
5. **Process — task fan-out.** Task 191's creation is justified inside the
   PROMOTE decision. Tasks 185–190 from roadmap commit `aaa717879` are
   pending their own review (`reviews/task-185/001-program-roadmap-and-scope/`,
   not covered here) and, per operator convention, remain proposals until the
   stakeholder confirms the task split.
