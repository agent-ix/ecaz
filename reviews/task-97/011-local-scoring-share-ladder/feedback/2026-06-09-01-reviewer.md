## Why the kernel loses today — the parallelism is transposed

I read `src/quant/qjl32/avx2.rs` against this packet's numbers. The
inner loop vectorizes *within* one candidate across 8 dims, then
**de-vectorizes the accumulation**: `_mm256_mul_ps` → `_mm256_storeu_ps`
to a stack array → `for lane in 0..8 { sum += ... }` (avx2.rs:102-110).
Per candidate per 8 dims that is one SIMD multiply plus a store,
reload, and 8 scalar adds — more memory traffic and more scalar work
than the plain scalar loop it replaces. A 0.92–0.97× result is the
expected outcome of this shape, not a property of QJL itself.

Compare the grouped-PQ AVX2 kernel (Task 94), which cleared its gate:
it vectorizes **across candidates** — 8 candidates per `__m256`, one
vector accumulator per candidate-group, dims iterated sequentially.

## Required optimization slice (before any stop-condition call)

Transpose the qjl32 AVX2 kernel to candidate-parallel:

```text
for candidate_octet in block32 (4 octets of 8 candidates):
    mse_acc8 = zero; qjl_acc8 = zero          // one lane per candidate
    for dim in 0..original_dim:
        idx8   = per-candidate 3-bit MSE index at this dim      (i32x8)
        vals8  = gather codebook[idx8]            // 8-entry table:
                 //  _mm256_i32gather_ps, or permutevar8x32 with the
                 //  codebook held in a register
        mse_acc8 += vals8 * broadcast(rotated[dim])
        sgn8   = per-candidate QJL sign at this dim (±1.0)
        qjl_acc8 += sgn8 * broadcast(sq[dim])
    out8 = mse_acc8 + gamma8 * qjl_scale * qjl_acc8   // per-candidate FMA
```

Two properties of this shape:

1. **Per-candidate accumulation order is dim-ascending — identical to
   the scalar reference.** With mul-then-add (no fused FMA in the
   accumulate step) each lane performs literally the same float
   operations in the same order as `score_scalar_tail`, so the result
   can be bit-exact per candidate, stronger than the tolerance gate
   requires. If you use `_mm256_fmadd_ps` for throughput instead,
   the ADR-076 tolerance pair still applies and the strict anchor
   stays with the forced-scalar reference.
2. **Full vector utilization with zero stack round-trips** in the hot
   loop — accumulators live in registers; the only per-dim loads are
   the code-byte extracts and two broadcasts.

The same transpose applies to the NEON kernel (4 candidates per lane
group) ahead of the Graviton 4 run, and to the SVE inner loop.

Practical notes: the per-candidate 3-bit index extraction at a given
dim crosses byte boundaries per candidate — extract with scalar shifts
into an `[i32; 8]` then `_mm256_loadu_si256`, exactly as the current
code already does for its index vector; that part survives the
transpose unchanged. Codebook is 8 f32 = one `__m256`, so
`permutevar8x32` avoids gather latency entirely.
