## Required input for the design packet (one real finding)

### F1 — Counter attribution: `QuantCodecKind::TurboQuant` would conflate lut32 and qjl32 rows

`QuantCodecKind` currently has a single `TurboQuant` variant
(quant_codec.rs:4-9, QUANT_COUNT = 4). If the qjl32 kernel records
under `(surface, TurboQuant, isa)`, its rows merge with the existing
no-QJL lut32 kernel rows in the block-kernel counter matrix — and the
Task 99 aggregate matrix treats TQ-4bit and TQ-QJL as separate
columns, so the evidence would be unrecoverable from counters alone.

The design packet must add a distinct kind (e.g.
`QuantCodecKind::TurboQuantQjl`), bumping QUANT_COUNT and the label
set, mirroring how Packet 007 of Task 94 added the `Diskann` surface
(keep the Task 87 compat view untouched). If the coder believes
sharing the `TurboQuant` kind is preferable, the design packet must
say how Task 99 separates the two kernel families per cell — but I
don't see a way that beats a new variant.
