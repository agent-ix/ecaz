# Approved direction for the qjl32 design packet — attribution + architecture

Operator decision (2026-06-09). This fixes the open questions from
seq 01/02 for the design packet. Three parts:

## 1. Counter attribution: Option A confirmed

Add `QuantCodecKind::TurboQuantQjl` exactly as seq 02 describes —
enum + `ALL` + label `"turboquant_qjl"` + `QUANT_COUNT` 4→5 — landed
as its own commit before the first qjl32 row is recorded. Do NOT
rename the existing `"turboquant"` label (it is baked into emitted
lines, results.jsonl rows, and prior packet artifacts; Task 99's
matrix header translates).

## 2. Kernel structure: separate family, shared primitives, no unification

`qjl32` is its own ADR-076 module family at
`src/quant/qjl32/{mod,scalar,neon,sve,avx2}.rs`. Rationale, agreed
with the operator:

- The inner loops are genuinely different algorithms, not one
  algorithm at two settings. lut32 is 16-entry LUT rows with 4-bit
  nibble codes and nothing else; qjl32 at canonical 4 bits is
  8-entry LUT rows (`mse_bits = 3`) with 3-bit packed indices, PLUS a
  sign-masked accumulation over packed QJL bits, PLUS a per-candidate
  `gamma * qjl_scale` FMA combine with `CandidateMeta::Gamma` side
  data. Even the "shared" LUT stage differs in row width and index
  decode.
- Do NOT thread mode branches or const-generics through lut32 to
  unify the families. lut32 is the production flagship path
  (every 1536-dim scan); keeping qjl32 separate keeps Task 97's
  blast radius out of the most important hot loop.
- Boilerplate dedup is already handled by Task 92 infrastructure:
  ISA dispatch, shape validation, timing, counter recording, and
  block/tail splitting come from `candidate_batch.rs` helpers and the
  module skeleton. qjl32 implements only its inner loop.
- Low-level primitives may be shared as small helpers ONLY where
  byte-identical (e.g. lane-gather utilities, sign-mask expansion —
  the sign term shares structure with the Task 93/95 popcount lane).
  Sharing means extracting a helper both call, never merging kernel
  entry points.

## 3. LUT-core parameterization is a named follow-up, not Task 97

There are now three LUT-accumulation families (lut32 16-entry,
grouped_pq_block 16-entry-per-group, qjl32's 8-entry MSE stage). If a
FOURTH LUT family appears — e.g. the Task 99 profile revives the
deferred Task 96 2-bit lane (4-entry rows) — that is the trigger to
extract a width-parameterized LUT core and re-anchor the existing
families on it, with the full counter matrix as the no-regression
gate. Until that trigger, parameterization is speculative
generalization; do not build it. (This matches the deferred Task 96
task file's own "thin instantiation parameterized by LUT entry
count" note.)
