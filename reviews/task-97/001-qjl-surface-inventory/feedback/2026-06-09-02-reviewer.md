# F1 expansion — why `QuantCodecKind::TurboQuantQjl` is required, not optional

Supplement to seq 01 F1, for the design packet. One detail here is
stronger than seq 01 stated: a shared kind doesn't just blur new
evidence, it **corrupts the existing Task 87 compat format**.

## Mechanism

Scoring events record into the global matrix keyed by
`BlockKernelCounterKey { surface, quant_kind, isa }`
(candidate_batch.rs:163). The key is the event's only identity —
dimension, mode, and kernel module are not recorded. Rows sharing a
key merge at record time, unrecoverably.

## The collision is same-process, same-surface

The lut32/qjl32 split is by *dimension*, not AM or storage format: a
1536-dim IVF TurboQuant table scores via lut32 (no-QJL lane), a
1024-dim IVF TurboQuant table via qjl32 — both `surface=ivf`, both
TurboQuant storage, same ISA set. Any mixed-dimension workload merges
the two kernels' rows. The Task 99 profile is mixed-dimension by
construction (it must include a non-tiled dim to exercise QJL at
all), so the collision is guaranteed on the exact workload that needs
the evidence.

## Three consumers break

1. **Direct rows / results.jsonl** — `quant=turboquant` would mean
   "lut32 or qjl32 or both, unknowable" in every
   `[block-kernel-counters]` line and every
   `metric=block_kernel_counters` suite row. Task 97's scoring-share
   AC (the 1.5×/1.8×/2× ladder) has no evidence format left.
2. **Task 87 compat view corrupted retroactively** — the
   `[task87-counters]` snapshot accumulates `lut32_flushes` /
   `lut32_candidates` from every row where
   `quant_kind == QuantCodecKind::TurboQuant`
   (candidate_batch.rs:356-359). qjl32 kernel flushes would be
   reported as lut32 flushes in a stable, already-consumed format
   whose meaning is "the no-QJL 4-bit LUT kernel fired." Silently
   wrong, not merely ambiguous.
3. **Task 99 matrix** — TQ-4bit and TQ-QJL are separate columns by
   the task file; direct counter rows are the established per-cell
   evidence standard (Task 92 closeout). Shared kind → one evidence
   stream for two columns.

## Required fix

Add `QuantCodecKind::TurboQuantQjl`:

- extend the enum + `ALL` + label set (`"turboquant_qjl"`),
  `QUANT_COUNT` 4→5 (matrix 100→125 entries — negligible);
- the Task 87 compat filter `quant_kind == TurboQuant` then
  **automatically excludes** the new kind — correct semantics (QJL
  was never lut32) with zero compat-view changes;
- SQL snapshot iterates `QuantCodecKind::ALL` → new rows appear
  without wiring; the suite parser (Task 94 packet 008) is
  schema-less `key=value` → `quant=turboquant_qjl` flows through
  untouched;
- precedent: Task 94 packet 007 added the `Diskann` surface to this
  same matrix the same way (extend direct view, freeze compat view).

## Rejected alternatives

- **Dimension/module as a new key axis** — fourth dimension for one
  consumer; the kind enum is already the kernel-family discriminator
  (different algorithm, different payload shape: gamma + sign bytes
  vs codes-only).
- **Bench-layer tags only** — works only for dimension-homogeneous
  steps, loses unit-test and SQL-level attribution, leaves the compat
  corruption in place.
- **Post-hoc inference from fixture dims** — impossible on
  mixed-dim workloads, which is what Task 99 runs.

The design packet should land the new kind as its own commit (or
alongside the counter-helper work) before any qjl32 kernel records a
row.
