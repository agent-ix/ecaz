## Why one more slice is required — the tails are 87% addressable

The shared helper (`score_turboquant_qjl_batch_inner`,
candidate_batch.rs:736) engages SIMD only when `batch.len() >= 32`,
scores ⌊n/32⌋ full blocks, and sends everything else — whole sub-32
batches AND every remainder up to 31 candidates — through the scalar
tail. Meanwhile the transposed kernel is **already octet-structured**:
`score_block32_avx2` is four calls to `score_candidate_octet_avx2`.

The slice: lower the SIMD entry to 8-candidate granularity in the qjl
batch path — score ⌊n/8⌋ octets via the existing octet routine, scalar
only for `n mod 8`. No AM batching policy change, no new kernel code,
no block-width change; counter semantics: octet-scored candidates are
kernel rows under the dispatched ISA (they execute the AVX2 octet
routine; ADR-076's "kernel row" is about which code path scored, not
the block quantum — state this in the request so Task 99 reads the
rows correctly).

Back-of-envelope from this packet's own numbers: if ~7/8 of SPIRE's
12.7 ms tail moves to the octet path at the kernel's measured rate,
tail ≈ 4.1 ms, total scoring ≈ 7.5 ms vs 21.9 ms scalar-off ≈ **~2.9×
direct share** — clearing not just the 1.5× floor but the 2× target.
Even at half the predicted efficiency it clears 1.5×.

HNSW benefits doubly: its m=8 expansions (8–16 candidates) are 100%
scalar today *plus* batch-queue overhead — which is why it sits at
0.92×. With octet entry most expansion candidates get SIMD; if HNSW
still measures <1.0× after that, add a min-batch bypass (route
batches under 8 straight to per-candidate scoring, skipping queue
overhead) rather than carrying a regression.
