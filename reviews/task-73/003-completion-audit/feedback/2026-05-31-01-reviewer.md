## Findings worth recording

### F1 — Variant index isolation (methodology nit, not blocking)

The 100k SPIRE suite reuses prefix `task73_spire_100k` across all variants
(tg16/tg32/tg64/tg128, b0/b1/b2). Between variants the suite rebuilds the
index on the same heap rather than replicating per-variant tables. Memory
`feedback_index_isolation_rule` calls for "build per-variant tables even
when it costs a one-time index build".

The original rule's failure mode was the planner choosing the wrong index by
cost when multiple indexes coexisted; that doesn't apply here because only
one SPIRE index exists at any time (DROP+CREATE between variants). The risk
that *does* apply is shared heap/buffer-cache state across variants
producing per-variant latency that's not order-independent.

Not blocking acceptance — the recall numbers are robust to this, and the
sweep was strictly monotone in `top_graph_search_list_size`. But for any
follow-on packet that wants to re-cite p50 deltas as load-bearing, please
either replicate per variant or document the run order + cold/warm state.

### F2 — `recursive_fanout` axis not swept

Task spec says "varying ... `recursive_fanout` if Phase 1 evidence suggests
it's a knob." The packet didn't sweep it. Acceptable per the conditional,
but the closeout would be stronger if it stated explicitly that Phase 1
evidence did not flag `recursive_fanout` as a tunable axis on these
fixtures.

### F3 — Default-change recommendation surface

The closeout shelves a default change but the underlying decision —
"SPIRE's stock 100k recall@10 is 0.85, ship that or surface a quality
preset?" — is a real product question, not a no-op. Recommend filing a
follow-on note (or task stub) so this doesn't quietly drop on the floor
once Task 74's profiler gate clears.
