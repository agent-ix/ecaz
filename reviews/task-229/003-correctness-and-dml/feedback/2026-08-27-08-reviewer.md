## Item 1 — the defect

`materialize_remote_payload_pairs` previously raised on a missing row-tier
payload:

```rust
if payload.tuple_payload_missing {
    return Err(format!(
        "EC_GENERATION_MISSING: physical owner {ordinal} has no row-tier payload for vec_id {requested}"
    ));
}
```

It now reads:

```rust
if payload.tuple_payload_missing {
    // The exact row version disappeared between traversal and
    // materialization under the request snapshot. The owner
    // already probed the same row-tier TID; both payload
    // stores being invisible is the established remote skip
    // contract, not structural corruption.
    continue;
}
```

The `continue` is unguarded. `prefer_payload_sidecar` is a parameter of this
function and is not consulted here, so the new semantics apply to
`prefer_payload_sidecar == false` as well:
`materialize_remote_payloads` when the cover does not apply,
`materialize_ranked_remote_payloads` (`generation_read.rs:6381`, hardcoded
`false`), every legacy uncovered `ec_distann` index, and the no-cover control
arm of this task's own A/B.

The comment's justification does not hold for those callers. It is true only in
the sidecar path, where `materialize_sidecar_payloads` sets `missing` **only**
when the sidecar row is absent *and* the `row_tier_visible` probe under the same
snapshot came back false — that arm is correct and I have no objection to it.
On the row-tier path there is no such probe: `tuple_payload_missing` comes
straight from `heap.__ec_distann_found IS NULL`
(`remote_endpoint.rs:967`, `:1049`), which is the row-tier lookup itself. A NULL
there means a live, non-tombstoned graph record has no row-tier tuple — the
condition the previous code classified as structural corruption and refused to
serve past.

Two consequences:

- **Correctness.** An uncovered generation with genuine row-tier corruption now
  returns short results instead of erroring. Nothing else in the loop catches
  it: `is_tombstone` is checked separately and afterwards, and the
  `response.rows.len() != ids.len()` guard above only checks the batch shape,
  not per-row presence.
- **Attribution.** Packet 004's no-cover arm runs this code, so it is not the
  pre-229 control. Per the repo's A/B rule, a change that moves the control
  makes per-change attribution impossible, and this one can move recall and
  returned-row counts specifically in the direction that flatters the cover
  arm. A PROMOTE/STOP taken over these two arms would not be measuring the
  sidecar.

The fix is one line — guard the skip with `prefer_payload_sidecar` and keep the
`EC_GENERATION_MISSING` error otherwise. If the intent is genuinely to relax the
uncovered contract too, that is a separate change with its own justification and
its own before/after evidence; it does not belong inside a covering-sidecar
packet.

## Questions 1–4

**Q1 — covered read snapshot/skip/retry/fail-closed parity. Partly.** The
sidecar arm's contract is implemented as described and is correct where I can
check it statically: `materialize_sidecar_payloads` does one ordered
TID-keyed `LEFT JOIN` with `WITH ORDINALITY`, re-checks the request identity
echo per row against `node.heap_tid`/`node.vec_id`, re-checks the stored
identity echo, and splits the miss three ways — miss with invisible row tier is
a skip, miss with a *visible* row tier is
`EC_GENERATION_MISSING: visible row-tier tuple (b,o) has no payload sidecar
entry`, and a partially-NULL sidecar row is an incomplete-identity error. There
is no partial sidecar/row-tier reconstruction: `project_payload` either covers
every requested attnum or errors. Selection is fail-closed at two independent
points — `payload_sidecar_covers` at plan time and the `prefer_payload_sidecar`
re-validation inside `materialize_payloads`, which re-runs
`validate_row_schema` and `covers_projection` on the owner rather than trusting
the caller. `AllColumns` never selects the sidecar. The unresolved part is
item 1 and the missing evidence in item 2.

**Q2 — DML atomicity and version-exactness. Source is consistent; unproven.**
`append_payload_sidecar` runs inside `insert_from_prepared_slot` immediately
after `append_row_tuple` and before the graph record, in the same transaction,
under `RowExclusiveLock` on both sidecar relations taken early, so encode
failure, insert failure, or a later injected failure unwinds all three. The
sidecar key is the new row-tier TID, and the unique index is on `row_tid`, so a
same-identity replacement appends a new version without conflicting with the
retained old one. Delete is graph-tombstone-only with no sidecar delete —
correct, and consistent with the pre-existing row-tier retention rule rather
than a new leak, since the row tier already retains superseded versions the same
way. Note for packet 004: the storage arm must therefore measure post-DML
totals, not post-build totals, or it will under-report the cover's bytes.

**Q3 — runner field completeness. Not verifiable from source.** The plumbing is
present end to end: `OwnerMaterializationTelemetry` gains
`sidecar_selected`/`sidecar_lookup_ns`/`requested_rows`/`returned_rows`/
`missing_rows`/`row_tier_visibility_probes`; the profile SRF exposes
`payload_source`, `payload_fallback_reason`, and the five sidecar counters; and
the coordinator cross-checks the owner's reported source, fallback reason, and
`returned + missing == requested`. The 40-stage/52-work-row and
replacement/delete p95 expectations are runner behavior, not source facts —
they need the packet-004 audit output. One narrow point: that coordinator
cross-check is inside `#[cfg(feature = "distann-head-attribution-benchmark")]`,
so a production build does not verify the owner's row accounting. That is
defensible for a benchmark-only invariant; flagging it so it is a decision
rather than an accident.
