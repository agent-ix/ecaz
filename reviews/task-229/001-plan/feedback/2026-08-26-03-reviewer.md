## 2. B2 — closed

The local mechanism is named, sited, and separately measurable.

- **Mechanism and site.** `request.md:82-89`: eligible `Frozen` outputs become
  `FrozenPayloadPending { vec_id, row_tid }` at ranking time;
  `materialize_pending_physical_window` is generalized to gather local and
  remote pending rows in the demanded window; "at most one local SPI
  `unnest(row_tids, vec_ids) WITH ORDINALITY` lookup per snapshot attempt and
  window, never SPI per row." That is B2's batched-at-materialization branch, so
  the per-row-planner-cost justification B2 made conditional does not apply.
- **The site supports it.** `pending_materialization_window`
  (`custom_scan.rs:1422-1436`) already returns a window slice spanning local and
  remote outputs alike, so gathering local pending rows from that same slice is
  a generalization of the existing loop at `:1400-1414`, not a second pass. The
  eager single batch has a direct precedent at `:1773-1775` (log X6).
- **Endpoint confounding.** What remains is ~1-2 SPI executions replacing ~4
  direct `table_tuple_fetch_row_version` calls per lazy-10 window. That cost
  sits inside the candidate arm of §6's same-generation A/B and is gated
  two-sided (≥5.0% **and** ≥0.50 ms on both independent pairs), so it cannot
  quietly inflate the primary endpoint — it can only make the gate harder to
  pass, which is the correct direction.
- **Telemetry.** `request.md:256-259` records local batched SPI initial/retry
  work and remote owner lookup work as separate stages, with local batch count
  and rows per batch, "so per-row SPI cannot hide in the primary endpoint".
  Packet 004 will read this, not infer it.
- **The W5 `vec_id` gap is closed by construction.** `hit.vec_id` is in scope at
  both `Frozen` construction sites (`custom_scan.rs:1733` and `:1789`, with
  `hit.vec_id` used at `:1744`, `:1747`, `:1792` in the same closures), so the
  pending variant carries the identity without new plumbing and the §2 echo
