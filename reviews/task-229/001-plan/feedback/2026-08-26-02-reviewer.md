## 1. Blockers

### B1 — The local `Frozen` class has three distinct existing visibility outcomes, and §3 collapses them into one

§3 states one rule — "Existing `tuple_payload_missing -> RemoteSkipped`
semantics for a sidecar tuple not visible under the read snapshot … if the
row-tier tuple is also not visible, return the normal missing marker" — and then
converts eligible `CustomScanOutputRow::Frozen(row_tid)` local hits "preserving
the same visibility rule". The local class does not follow that rule today.

Evidence (log W3), `src/am/ec_distann/custom_scan.rs`:

- `:1246` — `Local(tid)`, not visible → **skip silently**.
- `:1256-1261` — `Frozen(tid)` fetches under `(*estate).es_snapshot`.
- `:1264-1285` — if that fails it **refetches under
  `RegisteredSnapshotGuard::latest()`**, with an in-code comment that a
  concurrent physical replacement retiring the row-TID between ranking and
  consumption is the expected case.
- `:1296-1300` — if *both* attempts fail it raises
  `EC_GENERATION_MISSING: published row-tier tuple ({},{}) disappeared`. The
  local class **errors**; it never skips.
- `:1318` — `RemoteSkipped` is the only arm that `continue`s.

So converting `Frozen` under §3 as written diverges from the control in one of
two ways, both on the covered arm and both under exactly the concurrent
same-identity replacement packet 003 checkpoint 5 must exercise:

1. If a sidecar miss returns "the normal missing marker", the candidate **skips
   a row where the control raises `EC_GENERATION_MISSING`**.
2. If the sidecar lookup runs only under `es_snapshot`, it misses inside the
   window the control recovers from at `:1269-1285`, so the candidate **loses or
   errors on a row the control returns**.

This is the same class of defect as seq-01 P1-2, in the mirror direction, and it
breaks Acceptance 2's requirement that the candidate differ from the control
only by the covered mechanism.

**Required in §3:** state the local rule separately from the remote rule, in
these terms.

- The local sidecar lookup runs under `es_snapshot`, and on a miss retries under
  `RegisteredSnapshotGuard::latest()`, matching `:1269-1285` attempt-for-attempt.
- If the sidecar entry is still not found, probe that exact row-tier TID under
  the same two snapshots. Row-tier visible → corruption ERROR (the two tuples
  share an inserting transaction). Row-tier also not visible → raise the
  **existing** `EC_GENERATION_MISSING: published row-tier tuple ({},{})
  disappeared` error verbatim, not a skip.
- Say explicitly that `RemoteSkipped` semantics apply to the **remote** class
  only, so no reader infers local rows became skippable.

### B2 — The local lookup mechanism is unstated, and the obvious reading regresses the primary endpoint

§2's "one bounded batch with ordered `unnest(row_tids, vec_ids) WITH
ORDINALITY` against the single unique index" is correct and well-precedented for
the **remote** class — it extends the owner SPI shape already at
`remote_endpoint.rs:953` and `:1036` (log W4). The local class has no batch.
`Frozen` rows are resolved one at a time inside the per-row
`custom_scan_access` loop (`custom_scan.rs:1180-1186`, arm at `:1248-1300`), and
each currently costs a single direct `table_tuple_fetch_row_version` call — no
SPI, no planner, no snapshot registration.

Replacing that with one SPI `unnest` round per row would add plan and executor
setup on roughly 40% of the production lazy-10 window (Task 239's restored 6
remote + 4 local of 10). That cost lands directly on the 100k warm-mean primary
endpoint §6's PROMOTE gate turns on, and it could invert the result of the one
authorized decision run.

**Required in §2 or §3:** name the local mechanism and where it runs.

- Whether local sidecar lookups are batched at window materialization (alongside
  the remote batch, in `materialize_pending_physical_window`) or resolved
  per row in `custom_scan_access`.
- Whether the local lookup uses SPI or a direct
  `index_beginscan` + `table_tuple_fetch_row_version` pair against the sidecar
  index and heap. If SPI-per-row is chosen, say so and state why the added
  per-row planner cost does not confound the primary endpoint.
- Fold the answer into packet 002 checkpoint 5's telemetry so the local and
  remote lookup stages are separately attributable in packet 004, not inferred.

While fixing this, close the small consequence at log W5: `Frozen` is
`Frozen(ItemPointer)` and carries **no** `vec_id` (`custom_scan.rs:616-640`), so
§2's "the returned SQL row must echo the requested `row_tid` and `vec_id`" is not
expressible locally as the enum stands. Either extend the variant to carry the
`vec_id` already known at ranking time, or scope the `vec_id` echo check to the
remote class explicitly and say what stands in for it locally. Do not leave it
implied.

## 3. What closed, and on what evidence — do not relitigate

**P1-1 — closed.** §2 keys the sidecar by the frozen row-tier `row_tid` with an
append-one-row-per-version replacement rule, `vec_id` demoted to a checked echo
and digest-order field. Retention is now *derived* from the row tier's
append-only rule rather than declared, which also closes Q5's rejected
derivation. One note recorded for accuracy, not as a finding (log W6): the
production remote path ships `vec_ids` and the owner resolves them to the
current TID itself (`remote_endpoint.rs:775`; Task 221's
`benchmark_expanded_locator` is the benchmark-only TID-shipping variant), so
version-exactness buys less remotely than locally. TID keying remains correct
there — every row-tier version has a same-transaction sidecar entry, so §3's
"visible row-tier tuple with no matching visible sidecar tuple = corruption"
stays provable on the remote class.

**P1-2 — closed for the remote class**, and B1 above is the local remainder.
The ERROR list (absent relation, cover/schema mismatch, key or `vec_id` echo
mismatch, malformed length/null shape, decode failure) and the
skip-on-not-visible split are correct and correctly derived from the same
inserting transaction.

**P1-3 — closed.** §6 preregisters the primary endpoint (100k warm mean
end-to-end), a two-sided threshold (≥5.0% **and** ≥0.50 ms on **both**
independent covered-generation pairs), an explicit no-favorable-averaging rule,
a 2.0% smaller-scale non-regression band, 5.0% p95/p99 tail ceilings, a 5.0%
per-node storage ceiling, 10.0% build-time and insert-throughput ceilings, a
15.0% replacement/delete p95 ceiling, and a named non-gating endpoint set. That
is a decision rule, not a validity gate.

**P1-4 — closed.** §6's same-generation `benchmark_covering_sidecar` Userset arm

the suite already has the isolated-pair validator to extend
(`suite.rs:5013-5037`, log W7). AB/BA is correctly retained for build, storage
and DML only, and correctly labelled separate-generation.

refusal to claim detection of a same-length value bit flip beyond page checksums
