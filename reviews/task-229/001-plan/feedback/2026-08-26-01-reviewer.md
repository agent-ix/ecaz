## 1. P1 blockers

### P1-1 — Key the sidecar by the frozen row-tier TID, not by `vec_id`

The plan makes the sidecar an **identity-latest** store
(`vec_id bigint NOT NULL` unique, one row per identity, "upserts the sole
sidecar row"). Every payload read it replaces is **version-exact**.

Evidence (log V2, V3):

- `physical_dml.rs:511-529` — a same-identity replacement *retains* the old
  graph tuple (`UPDATE ... SET is_current = false`) and appends a **new**
  row-tier tuple at a **new** TID, recorded in a new graph record with
  `record_version + 1`. The row tier is append-only and version-addressed.
- `generation_read.rs:2409-2440` — `materialize_payloads` resolves graph
  records to `node.heap_tid` and builds the payload query over those TIDs.
- `custom_scan.rs:1248-1269` — the local `Frozen(tid)` path fetches the exact
  row-tier TID under `es_snapshot`, with an in-code comment stating that a
  concurrent physical replacement retiring that TID between ranking and
  consumption is a known bounded visibility race.

Consequences of `vec_id` keying:

1. A traversal that ranked a graph record and a sidecar lookup that resolves by
   identity can straddle a committed same-identity replacement and emit the
   **new** payload at the **old** record's rank — a tuple that never existed as
   a consistent row. TID addressing cannot produce this, because the TID names
   the version.
2. The sidecar's MVCC lineage stops matching the row-tier tuple it stands in
   for. An in-place `UPDATE` creates its own version chain with its own xmin,
   independent of the row-tier tuple's.
3. It forces the plan to invent a new retention rule ("the one sidecar row is
   retained but unreachable while the current graph record is tombstoned"),
   which is why review question 5 exists at all.

**Ruling: key the sidecar by the frozen row-tier TID.** The TID is already in
hand at both ends — `append_row_tuple` returns `row_tid` before
`insert_graph_record` (`physical_dml.rs:502,527`), and the read path already
materialises `typed_tids` from `node.heap_tid`. Keep `vec_id` as a non-key
column for the digest ordering and the wrong-key echo check.

This buys, at no cost:

- Version-exactness identical to the row tier, by construction.
- **Visibility equality**: the sidecar tuple and the row-tier tuple it covers
  are inserted by the same transaction, so "sidecar entry visible" is the same
  event as "row-tier tuple visible" under any snapshot. That is what makes P1-2
  resolvable.
- Append-only replacement, so retention-until-reclaim (question 5) falls out of
  the existing row-tier rule instead of being a new special case.
- `fillfactor = 100` and no HOT-update pressure on the sidecar heap.

If the coder wants to keep `vec_id` keying, the revised plan must state the
snapshot rule explicitly and prove the two anomalies above cannot occur; a
plan that is silent on which snapshot the sidecar lookup runs under is not
reviewable.

### P1-2 — A missing covered entry must not be an error

The plan rules that "a missing covered entry for a live graph record" is
structural corruption that "errors fail-closed; it does not silently fall back."
That is a behaviour change, not a hardening.

Evidence (log V4):

- `remote_endpoint.rs:908-967` — `build_payload_sql` LEFT JOINs the locator
  list against the row tier and projects
  `heap.__ec_distann_found IS NULL AS tuple_payload_missing`.
- `custom_scan.rs:1405-1413` — a vec_id with no returned payload becomes
  `CustomScanOutputRow::RemoteSkipped`, and `custom_scan.rs:1318` drops it from
  the result.

So today a live graph record whose row-tier tuple is not visible is a
**legitimate, silent skip** — it is the documented outcome of the concurrent
replacement / visibility race that `custom_scan.rs:1264-1269` calls "a bounded
visibility race". Under the plan's rule, an ordinary concurrent DML race on a
*covered* query becomes a query ERROR while the identical race on an uncovered
query returns one fewer row. That breaks Task 229 Acceptance 2's requirement
that the candidate not diverge from the control on anything but the covered
mechanism.

**Ruling: split the rule.**

- Fail-closed ERROR — correct and required for: absent sidecar relation for a
  generation whose descriptor declares a cover, cover/schema disagreement,
  wrong-key or wrong-cover-digest echo, malformed offset/null shape, entry
  length mismatch, and any decode failure. These are format corruption and can
  never be produced by a legal concurrent write.
- Skip, matching `tuple_payload_missing → RemoteSkipped` — required for: entry
  not visible under the read snapshot.

Under P1-1's TID keying these are cleanly separable, because a missing *visible*
entry at a TID whose row-tier tuple *is* visible is provably corruption (same
inserting transaction), while both-invisible is the existing race. Under
`vec_id` keying they are not separable, which is a second independent reason to
take P1-1.

### P1-3 — The preregistered decision design has no effect-size threshold

The plan preregisters *validity* gates (semantic identity, provenance,
counterbalancing) and then says the decision is "PROMOTE or STOP only after all
scales and both positions pass semantic/provenance gates". Passing a validity
gate is not a decision rule. Task 229's own decision rule requires the evidence
to establish that the retrieval win "justifies its storage, lifecycle, and DML
cost", which is a trade, and a trade needs a stated rate.

**Required in the revised plan, before packet 004 runs:**

1. The primary endpoint: which metric, at which scale, in which arm position.
   (Task 222 closed on warm mean latency; say whether 229 uses the same.)
2. The PROMOTE threshold with sign and magnitude, plus the STOP band.
3. The tie-break when the two counterbalanced pair deltas disagree in sign, or
   when 10k and 100k disagree. "Report the envelope" is not a rule; name what
   decision an envelope that straddles zero produces.
4. The cost ceilings that turn a latency win into a STOP: per-node sidecar
   bytes as a fraction of the generation, build-time delta, and per-insert DML
   work delta.
5. The secondary endpoints that are reported but explicitly do not gate.

### P1-4 — AB/BA is the wrong primary control for the latency endpoint

The two-fresh-pair `AB/BA` design is a reasonable position/warmth control, and
it is genuinely needed for the axes that can only differ between builds (build
time, storage). It is the *weaker* option for latency, and this repository
already has the stronger one.

Evidence (log V5): Tasks 220, 221 and 222 each shipped a `Userset` bool GUC that
toggles the owner-materialization path **within one generation and one fixture
build** — `ec_distann.benchmark_packed_payload`,
`ec_distann.benchmark_expanded_locator`, `ec_distann.benchmark_payload_projection`
(`options.rs:515-541`) — and `suite.rs:4942-5037` already validates those as
isolated control/candidate pairs, requiring
`candidate.payload_projection == control.payload_projection` on every other
axis. Task 222's accepted 33.33%–40.41% warm-mean result was produced this way.

The sidecar is a build-time format, so the *build* and *storage* axes cannot be
GUC-toggled. The *read path* can: build one covered generation, then A/B
sidecar-read versus forced-row-tier-read inside it. That removes the position,
warmth, and build-to-build confounds entirely rather than bounding them, and it
isolates exactly the mechanism under test.

**Ruling on the evidence design:**

- Primary latency/recall endpoint: same-generation `benchmark_covering_sidecar`
  GUC arm, following the 220/221/222 pattern and the suite's existing isolated-
  pair validation.
- Build time, storage, per-node bytes, DML work: the two-pair AB/BA as planned.
  Keep the counterbalanced envelope and the per-cell NFR-022 provenance.
- Both arms of the GUC pair must come from the same extension binary; state the
  build profile in `manifest.md` so `allow_debug_extension` can stay false.

This also reduces the number of full 3-owner builds packet 004 needs.

## 2. P2 items to fold into the checkpoint lists

**P2-1 — The entry encoding is roughly 10× larger than it needs to be, and its
per-entry digests are largely redundant.** With a fixed-width-only allowlist and
a frozen cover, `column_count` and `end_offsets` are both fully derivable from
the cover descriptor; only the null bitmap varies. For the exact candidate the
plan preregisters (`covering_payload_attnums='1'`, `id bigint`), the proposed
record is `version | vec_id(8) | cover_digest(32) | column_count | null_bitmap |
end_offsets(4) | value(8) | entry_digest(32)` — roughly 89 bytes to carry 8
bytes of payload. The minimum canonical form is `null_bitmap | packed
fixed-width values` = 9 bytes. That ~80 bytes/row lands directly on the storage
axis Task 229 P3 must report, on the exact arm the decision turns on. Either
(a) drop `column_count` and `end_offsets`, replace the 32-byte cover digest with
an 8-byte truncated cover tag, and drop the per-entry digest — relying on the
descriptor/receipt/manifest binding, strict length validation, and page
checksums; or (b) keep them and justify the per-row overhead against the
measured storage delta in packet 002. Do not carry it unexamined into 004.
Also: `ALTER TABLE ... ALTER COLUMN payload SET STORAGE PLAIN` so the sidecar
can never re-enter the detoast machinery the task exists to avoid, and state the
fillfactor.

**P2-2 — Justify heap + unique B-tree over a covering index, on the record.**
Task 229 P1 says "Choose and document one bounded lookup representation"; the
plan chooses but does not document why. The obvious alternative is
`CREATE UNIQUE INDEX ... (key) INCLUDE (payload)`, which makes the bounded
lookup index-only for a bulk-loaded, never-updated (under P1-1) generation and
halves the page touches on the candidate arm. Pick one and state the reason.
Do not build both — the task forbids it.

**P2-3 — Do not change any existing digest domain string.** `GENERATION_DESCRIPTOR_DOMAIN`
is `b"ec_distann_generation_descriptor_v2\0"` (`generation_descriptor.rs:38`);
`EPOCH_MANIFEST_DOMAIN` is `b"ec_distann_epoch_manifest_v2\0"` and
`READY_RECEIPT_DOMAIN` is `b"ec_distann_ready_receipt_v1\0"`
(`manifest_v2.rs:43-44`). A V3 descriptor or V3 manifest must be digested under
the **unchanged** domain, with the version living inside the bytes. Changing a
domain to match a new version number silently reprints every legacy digest.
There is precedent for exactly this: `DistannBuildOptions` already encodes V2 or
V3 conditional on content and decodes V1/V2/V3, all under the containing
structure's unchanged domain (`generation_descriptor.rs:60-63,734-736,793-794`).
Follow it. Packet 002 must carry byte fixtures proving a legacy V2 descriptor,
V1 receipt, and V2 manifest each decode and re-encode byte-identically with an
identical digest.

**P2-4 — The receipt width change has call sites the plan does not name.**

`generation_catalog.rs:131` and `:703` (`Option<[u8; 303]>` and a fixed-array
parameter), `handoff.rs:1686`, **`lifecycle_wire.rs:132` and `:147` — the
cross-node Ready-receipt-set framing, which the plan never mentions** —
`src/am/mod.rs:112`, `src/am/ec_distann/mod.rs:167`, `src/lib.rs:480`, and
`src/tests/ec_distann_physical_lifecycle.rs:6116`. On the SQL side there are two

and `ec_distann_epoch_candidate.ready_receipt_set` (`sql/bootstrap.sql:562`).
Add all of these to packet 002 checkpoint 3.

## 3. Rulings on the eight review questions

**Q1 — numeric physical-attnum reloption, 16-attribute cap, fixed-width
allowlist: ACCEPT, with three additions.** A build-time string reloption is
well-precedented (`add_local_string_reloption` at `options.rs:1288`, used for
`neighbor_code_format` and `head_construction`), and treating the persisted
descriptor rather than the mutable reloption as authoritative is exactly right —
`ALTER INDEX ... SET` would otherwise silently redefine a built generation.
Additions: (i) also reject an attnum whose frozen entry has `dropped == true` or
`generated_kind != 0`; `row_schema.rs:21-29,220-247` already models both, and the
row-tier relation preserves dropped-column attnum alignment via the
`__ecdz_drop_*` placeholders at `generation_store.rs:371-376`, so the check is
cheap and must not be skipped. (ii) State the *reason* for 16: 16 attributes ×
16 bytes (`uuid`, the widest allowed) = 256 bytes worst case, which keeps every
entry far under the TOAST threshold and makes "bounded" a provable property
rather than a chosen number. Put that sentence in the plan. (iii) Confirm the
allowlist is closed over PG18 binary send stability — all ten types are
`integer_datetimes`-era fixed width on PG18, which is fine, but say so.

**Q2 — one heap plus one unique B-tree as the sole bounded representation:
ACCEPT the "exactly one representation" constraint; the specific choice needs
justification.** See P2-2. Also apply the naming convention at
`generation_store.rs:317-323` (`_ecdz_row_/_ecdz_graph_/_ecdz_dir_` + oid +
build-id suffix); `_ecdz_cover_<index_oid>_<build_uuid>` fits under NAMEDATALEN
only if the uuid suffix is truncated the same way the existing three are —
match the helper, do not hand-roll the name.

**Q3 — preserving no-cover V2/V1/V2 bytes while introducing optional versions:
ACCEPT, conditional on P2-3 and P2-4.** The scheme is sound and already has a
working precedent in this codebase. The two conditions are: unchanged digest
domains, and byte fixtures proving legacy round-trip identity. Per the project's
research-stage posture, no extension upgrade script is required — a re-bootstrap
is acceptable — but say in packet 002 that existing databases are re-bootstrapped,
because the AB/BA control arm must run on the **post-change** bootstrap and the
same binary, not on the pre-change SHA.

**Q4 — initial-build digest binding versus later Task 167 mutable DML state:
ACCEPT the principle.** Binding the build-time content into
descriptor → receipt → manifest → fingerprint, and letting Task 167 mutate
generation-local state outside that published identity, is exactly how the
existing graph and row-tier digests already behave, and the plan's analogy holds.
Two requirements: name the receipt field `initial_content_digest` (or equally
explicit) so no later reader mistakes it for a live checksum, and add an explicit
test that a post-Ready insert does **not** invalidate publication, restart, or
retained-predecessor reads. Note the binding is only sound once keying is
version-exact — see P1-1.

**Q5 — retaining tombstoned sidecar rows until generation reclaim: ACCEPT the
outcome, REJECT the derivation.** The outcome is right. It should not be a new
rule invented for the sidecar; under P1-1's TID keying it is the *same* rule the
row tier already follows — superseded versions are retained and reclaimed with
the generation, and the delete path (`physical_dml.rs:797-870`) only flips the
graph record's tombstone flag and never touches payload storage. Derive it,
don't declare it.

**Q6 — corruption/missing as an error rather than fallback: SPLIT.** Error for
format/structural corruption; existing `RemoteSkipped` semantics for a
not-visible entry. See P1-2. The plan's blanket rule is a regression.

**Q7 — applying the sidecar to local as well as remote owner hits: ACCEPT, but
strictly after P1-1 and P1-2.** Local application is the right ambition — it is
where the largest per-row saving sits, since the local path currently pays a
full frozen-row heap fetch. But the local `Frozen(tid)` fetch at
`custom_scan.rs:1248-1270` **is** the visibility check for a local hit; replacing
it with an identity-keyed lookup removes the mechanism that makes a
concurrently-replaced local row invisible. Two clarifications the plan must
carry: (i) only `CustomScanOutputRow::Frozen` is affected — `Local(tid)` fetches
from `ss_currentRelation`, the user's own table, and must be untouched; (ii)
state explicitly that the frozen row-tier ctid was never the user relation's
ctid, so converting `Frozen` hits to virtual projected tuples does not change
`ctid` / EPQ / `FOR UPDATE` behaviour — `custom_scan_recheck` already returns
true unconditionally (`custom_scan.rs:2017-2024`) on the premise that these rows
have no coordinator heap identity.

**Q8 — the two-pair AB/BA envelope as sufficient position/warmth control: NOT
SUFFICIENT as the primary latency control.** See P1-4. AB/BA bounds the
confound; the same-generation GUC arm removes it, is the established house
pattern for this exact class of change, and is already validated by the suite.
Use the GUC arm for latency/recall and AB/BA for build/storage. Separately, P1-3
applies regardless of which design is chosen: without a preregistered effect-size
threshold, neither design produces a decision.
