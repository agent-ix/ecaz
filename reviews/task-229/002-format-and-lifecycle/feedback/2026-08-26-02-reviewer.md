## 1. Review question 1 — the descriptor is canonical, bounded, and bound

**Yes on all three, under a new domain that changes no existing one.**

**Canonical (log X2).** Every field is fixed-width or u32-length-prefixed
(`put_string` -> `put_len_prefixed`, `canonical_wire.rs:114-124`), so no two
distinct field tuples share a byte string. `decode` bounds `attribute_count` to
1..=16 *before* `Vec::with_capacity` (`payload_sidecar.rs:174-180`) so a hostile
count cannot drive an allocation, then `decoder.finish` (`:194`) rejects
residue. Because `attribute_count` is the exact loop bound and `validate()` pins
`entry_format_version == 1` and `maximum_attribute_count == 16`, a successfully
decoded descriptor re-encodes byte-for-byte — the property checkpoint 3 needs
when it starts persisting these bytes.

**Bounded (log X6).** `maximum_payload_bytes()` (`:126-144`) uses `checked_add`
on both sums and gates value bytes / bitmap bytes / total against 256 / 2 / 258.
16 x 16-byte `uuid` + `16.div_ceil(8)` = 258 exactly, attained by the renamed
test.

**Bound to the schema (log X5).** `validate_row_schema` re-validates the
supplied row schema rather than trusting its provenance (`:216`), requires
fingerprint equality (`:217`), and then requires per-attribute agreement on
dropped / generated / type / typmod / collation / send / receive / width.

Two things I checked rather than assumed:

- **The collation gate is not a latent breakage.** `validate()` requires both
  collation strings to be *empty* (`:93-94`). That would be a feature-killing
  bug if any allowlist type carried a collation. It cannot:
  `resolve_relation_schema` emits `''` when `a.attcollation = 0`
  (`row_schema.rs:63-64`), and all eleven allowlist types are non-collatable
  (`typcollation = 0`). So V9 is a fail-closed gate no legitimate cover can
  trip.
- **The indexed vector cannot be smuggled into a decoded descriptor.**
  `validate_row_schema` does not know the vector attnum, but an `ecvector`
  column is not one of the eleven `pg_catalog` names, so `fixed_binary_width`
  rejects it first. Structural, not a denylist.

**Domain (log X3).** `ec_distann_payload_cover_descriptor_v1\0` is new and used
only by `digest()`. `BUILD_REGISTRATION_DOMAIN` is unchanged, and the diff adds,
removes, or edits no other `_DOMAIN` constant. Matches plan 001 §4.

## 2. Review question 2 — the entry codec is exactly the accepted layout

**Yes, and it fails closed on every malformed shape, with no per-entry
metadata.**

The payload is precisely `null_bitmap | concatenated_non_null_values`
(log X6). NULL is one bit and consumes zero value bytes. Encode and decode use
the identical bit order (`index / 8`, `1 << (index % 8)`), so the codec is
self-inverse. No per-entry cover digest, column count, offset array, or checksum
is written — plan 001 §2 "Compact canonical entry", implemented literally.

Fail-closed arms, all present and all returning `Err`:
count mismatch and per-value width mismatch on encode; truncated bitmap,
wrong-length bitmap, non-zero padding bits, `checked_add` offset overflow,
per-attnum value truncation, and trailing bytes on decode; then invalid
requested TID, row-TID echo mismatch, and `vec_id` echo mismatch on
`decode_row` (log X7), all three evaluated *before* any value is exposed.
`ItemPointer` derives `PartialEq` (`storage/page.rs:31`), so the TID comparison
is a full (block, offset) comparison, and `ItemPointer::INVALID`'s `u32::MAX`
block is caught by the `InvalidBlockNumber` arm. Validating only the *requested*
TID is sufficient because the returned TID must equal it.

`validate_null_bitmap` skipping the padding check when `attribute_count % 8 == 0`
is correct, not a hole: at 8 and at 16 attributes the bitmap has no padding bits.

1. **Test the descriptor rejection arms that guard bytes read back from disk —
   close in checkpoint 3.** Log X12 inventories what the 5 passing tests cover
   and what they do not. Untested: `maximum_attribute_count != 16`, empty
   attribute list, count > 16, `attnum == 0`, non-increasing/duplicate attnums,
   interior NUL in an identity string, empty type/send/receive identity,

   truncated descriptor input, and non-UTF-8 identity strings. Every one of
   those is reachable *only* through `decode()` of hostile or corrupt bytes —
   which is exactly the capability checkpoint 3 introduces, and exactly the
   corruption-detection story plan 001 §2 sells ("Packet 002 will corrupt keys,
   `vec_id` echoes, length/null shapes, descriptor identity, relation identity,
   and initial digest"). The code is correct on inspection; it is the evidence
   that is missing. Checkpoint 3 is already the byte-fixture checkpoint, so
   these belong in the same slice. Two smaller ones to fold in: `decode_row`'s
   invalid-requested-TID arm (log X7) and a genuine truncated-*bitmap* case for
   `decode_payload` — the existing `&payload[..len-1]` case leaves 8 bytes,
   which is >= the 1 bitmap byte, so it lands on the value-truncation arm
   instead.
2. **`validate()` allocates on every encoded and decoded row.** Log X13.
   `validate()` builds a throwaway `DistannRowSchemaAttribute` per attribute
   (`:101-113`) — six `String` clones plus `"covered".to_owned()`, roughly five
   heap allocations per attribute per call — purely to call
   `fixed_binary_width`, which reads only `type_namespace` and `type_name`. It
   runs from `encode()`, `encode_payload()`, and `decode_payload()`, so it is
   once per row in each direction: ~50 allocations per lazy-10 window at the
   preregistered `covering_payload_attnums='1'` cover, ~800 at 16 attributes.
   Not a correctness defect and not on a measured path yet, but it sits directly
   on the path whose PROMOTE gate is ">= 5.0% **and** >= 0.50 ms" at 100k
   (plan 001 §6). Fix cheaply: change the signature to
   `fixed_binary_width(type_namespace: &str, type_name: &str)`, and have the hot
   codec entry points take an already-validated descriptor rather than
   re-validating per row.
3. **`#[allow(dead_code)] mod am;` means a clean `cargo check` proves less than
   the disposition implies.** `src/lib.rs:57` suppresses `dead_code` across the
   whole access-method tree, and there is no other suppression in the

   `decode_payload` currently have no non-test caller. That is fine and expected

   point is that checkpoint 3 and 4 must not rely on `dead_code` to catch an
   unwired path. The clippy half of disposition 4 stands on its own: I read all
   three clippy logs, the four inherited failures are real, no Task 229 file is

   identical to `origin/main`. Separately, the seq-01 concern itself is moot —

4. **Thread the resolved descriptor forward; do not re-resolve from

5. **Two claims in `request.md` are slightly stronger than the code.** Neither
