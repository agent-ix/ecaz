## Answers to the five review questions

**1. Legacy no-cover bytes, digests, fingerprint, and framing preserved? —
YES.** Verified from the committed logs, not from the request text:
`cargo-test-on-disk-distann-checkpoint3.log` reports 21/21 on the frozen
fixture suite, `cargo-test-legacy-identity-checkpoint3.log` 3/3,
`cargo-test-ready-receipt-checkpoint3.log` and
`cargo-test-receipt-set-checkpoint3.log` 1/1 each. The receipt digest is taken
over the canonical bytes *including* the version field
(`domain_digest(READY_RECEIPT_DOMAIN, canonical)` at `manifest_v2.rs:548`), so
adding a V2 tail cannot alias a V1 receipt under the unchanged domain. Keeping
the four existing domain strings and giving the sidecar its own
(`ec_distann_payload_cover_descriptor_v1`) is the right split.

**2. Does the covered chain bind the right things without confusing build
identity with later DML state? — YES, and this is the part I checked hardest.**
`global_payload_sidecar_initial_content_digest` is only ever produced by
`payload_sidecar_global_initial_content_digest(&receipts)` — at construction in
`build_coordinator/t2.rs:712` and at validation in `manifest_v2.rs:782`, where
it is recomputed from the same receipt set and compared. It is never recomputed
against live sidecar relation content anywhere in `src/`. That is exactly right:
a build-time digest re-verified against a mutable relation would fail on the
first DML, and this design cannot do that.

Worth one clarifying sentence in the packet, because the field name invites the
wrong reading later: this digest is a *manifest identity/consistency* check —
it detects a tampered or mismatched manifest against the receipts it was built
from — and it is **not** an integrity check on the sidecar heap at any later
point, because the owner's self-reported digest is the only input. A future
task should not assume it validates content.

**3. Receipt storage safely bounded across every former fixed-303 consumer? —
YES.** `DISTANN_READY_RECEIPT_MAX_BYTES = 359` bounds the variable-length form,
decode gates on `matches!(version, V1 | V2)` before reading any field, the
optional tail is read only under `version == COVER_VERSION`, and the bootstrap
SQL accepts only the exact `(version, length)` pairs. The receipt-set framing
test covers mixed V1/V2 entries.

**4. seq02 disposition closes the corruption tests and the per-row allocation
carry-in? — YES.** `cargo-test-payload-sidecar-checkpoint3.log` shows 6/6
including the seq02 decode-rejection carry-ins, and threading T2's already
resolved descriptor rather than re-reading reloptions after registration replay
is the correct fix — it closes the drift window instead of re-validating inside
it.

**5. May checkpoint 4 proceed? — YES.**

## On the dual-version design

I want to record why I am *not* raising this, because it is the thing most
likely to be challenged on the next pass given this repository's standing "no
backward compatibility, format changes are free, just rebuild" ruling. Under
that ruling, accepting two wire versions usually reads as unnecessary
complexity plus a self-inflicted failure surface — and the request even says the
change requires re-bootstrap and that both future A/B arms will use the
post-change bootstrap, which is normally the argument for collapsing to one
version.

It does not apply here. `covering_payload_attnums` is an **opt-in per-index
reloption defaulting to `None`** (`options.rs:343`). An index with no cover is
therefore a permanent, live, supported configuration — not a legacy artifact.
`Option<DistannReadyReceiptPayloadSidecar>` and the V1/V2 + V2/V3 pairs encode a
live product distinction, so the "mixed legacy and covered receipts" rejection
is guarding a state that can actually occur, and the frozen no-cover fixtures
are ordinary regression tests on the default path rather than migration tests.
The design is correct as built.

## Registered for closeout, not for checkpoint 4

Task 229 changes on-disk storage behavior, so its closeout needs
**10k/50k/100k recall + latency + storage** via `ecaz bench suite`, with
**cover on/off as the variant axis** on the same corpus. Two things make this
worth registering now rather than at the end:

- The whole premise of the sidecar is a storage/retrieval trade — extra heap
  and index bytes bought against owner payload work. Storage is the axis the
  task is judged on, and it is the one no checkpoint so far has touched.
- Registering the axis now means checkpoint 4's cataloged relation pair can be
  built so that a cover-on/cover-off A/B is a config flip on one generation,
  rather than something that needs a fixture redesign afterwards.

Carry Task 224's methodology finding into that design: compare arms at matched
fixture position, or use a preregistered counterbalanced envelope. A fresh-build
control against a reused candidate is what voided Task 224's screen, and a
storage A/B is equally exposed to it.
