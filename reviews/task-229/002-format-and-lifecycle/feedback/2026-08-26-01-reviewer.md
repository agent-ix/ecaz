## 1. Review question 1 — the grammar is the accepted canonical contract

**Yes, exactly.** Packet 001 `request.md:24-28` fixed the contract as
"a canonical comma-separated list of positive physical attnums, strictly
increasing, unique, and bounded to 16". `parse_covering_payload_attnums`
(`options.rs:432-467`) enforces all five terms, in an order that makes each
rejection specific rather than incidental (log X3):

canonical spelling via `token != attnum.to_string()` (rejects `01`), positive
via the explicit `attnum == 0` arm, strictly-increasing-implies-unique via
`attnum <= previous`, the 16 bound before any parsing, and decimal-only via the
all-ASCII-digit gate *before* `parse::<u16>` — which is why `1,+2` and `1, 2`
reject on the grammar rather than on integer parsing. Ten invalid spellings
plus the 17-element case are unit-covered at `options.rs:1500-1519`, one per
rejection arm.

Registration (`options.rs:1364-1374`) is byte-for-byte the same
`add_local_string_reloption(..., ptr::null(), None, None, offset)` shape as the
three existing string reloptions, and `init_local_reloptions` already takes
`size_of::<EcDistannReloptions>()` (`options.rs:1224`), so the new
`#[repr(C)]` offset field cannot write past the blob. Absence really is `None`:
a NULL default leaves offset 0, and `read_string_reloption`
(`reloptions.rs:28-30`) returns `None` on offset 0.

`distributed_control=true` is required (`options.rs:1439-1443`), matching the
plan.

Two notes, neither a finding:

- No `validate_string_relopt` callback is registered, so the grammar is enforced
  at reloption **read**, not at catalog write. `CREATE INDEX` is transactionally
  equivalent (ambuild reads options; the statement rolls back). `ALTER INDEX
  ... SET` would commit a bad value and error on every later read. That is the
  pre-existing posture of `neighbor_code_format`, `source_identity`, and
  `head_construction` — consistent with the AM, not a new hazard.
- The `raw.is_empty()` arm is unreachable from SQL because
  `read_string_reloption` errors on `''` first (`reloptions.rs:47-49`). It is
  still directly unit-tested, which is the right call for a `pub`-adjacent
  parser.

## 2. Review question 2 — resolution fails closed, and the set is exact

**Yes on both halves.**

**Allowlist.** `fixed_binary_width` (`payload_sidecar.rs:27-39`) is
set-identical to packet 001 `request.md:36-38`: eleven types, eleven arms,
nothing added, nothing dropped. I checked each width against the PG18 binary
*send* output length rather than against `typlen`, since the plan's rationale is
binary-I/O stability: `bool` 1, `int2` 2, `int4`/`float4`/`date` 4,
`int8`/`float8`/`time`/`timestamp`/`timestamptz` 8, `uuid` 16. All eleven
match, and the two near-misses that would have been wrong — `timetz` (12) and
`interval` (16 but three fields) — are correctly absent.

The domain/array/user-defined exclusion is **structural, not a denylist**, which
is the stronger property. `resolve_relation_schema` (`row_schema.rs:58-85`)
joins `pg_type` on `a.atttypid` with no base-type recursion, so a domain records
its own `typname` in its own namespace and dies on the
`type_namespace != "pg_catalog"` gate; an array records `pg_catalog._int8`-style
`typname` and matches no arm. The one hole a bare namespace check could leave —
a user type planted in `pg_catalog` — is closed by the `typname` arms, since
those eleven names are already taken there.

**Fail-closed arms.** Log X5 tables all thirteen gates in
`resolve_payload_cover` (`payload_sidecar.rs:41-136`) against packet 001's
six-item rejection list. All six accepted exclusions are present — absent,
dropped, generated (both `s` and `v`), indexed vector, missing binary
send/receive, type outside the closed set — and the resolver adds count, order,
and `checked_add` overflow gates on top. Every arm returns
`Err(String)` with an `EC_SCHEMA_UNSUPPORTED:` prefix. There is no `unwrap`,
`expect`, panic, or silent skip in the resolver.

Two things I checked rather than assumed:

- Gate **ordering** produces the specific error, not a generic one. Because
  `DistannRowSchemaDescriptor::validate` requires contiguous attnums
  (`row_schema.rs:181-189`), a dropped attribute is still *present* as a
  canonical-empty entry — so the `dropped` gate at `:88` fires before the
  allowlist gate at `:103` would have (a dropped attribute has an empty
  `type_namespace`). Same for the binary-I/O gate at `:98`.
- The second `row_schema.validate()` call at `:49` is redundant with
  `resolve_relation_schema:166` and is **correct** to keep: the resolver takes a
  descriptor by reference and must not trust its provenance once checkpoint 2
  starts feeding it decoded descriptors.

**258-byte maximum.** Constants at `payload_sidecar.rs:5-10` and the
`div_ceil(8)` null bitmap at `:119` reproduce the plan's arithmetic exactly:
16 attributes x the widest allowed 16-byte scalar = 256 value bytes, plus a
two-byte bitmap = 258, matching `request.md:41-43` and staying under the TOAST
threshold. The sixteen-`uuid` test (`payload_sidecar.rs:185-199`) attains it
exactly and also pins `entry_format_version`, `maximum_attribute_count`, the
fingerprint binding, and `attributes.len()`.

`maximum_attribute_count` being the format cap (16) rather than the resolved
count initially read as an inconsistency next to the per-cover
`maximum_payload_bytes`. It is not: packet 001 `request.md:48-49` specifies
"entry format version 1 and the **maximum** attribute count" as a descriptor
field, with the per-cover attnums carried separately in `attributes`. The
implementation matches the accepted contract.

## 3. Review question 3 — placement is early enough, no-cover is preserved

**Yes on both.**

**Placement.** Both sites sit after `open_control_index` and
`lock_registry_revision` and before anything that captures or constructs:
T1 (`t1.rs:317-327`) precedes `replay_registration` (`:331`),
`ensure_build_slot_available` (`:348`), and `desired_participants` (`:350`);
T2 (`t2.rs:223-232`) precedes `replay_registration` (`:237`),
`capture_source_snapshot` (`:308`), `capture_physical_source_rows` (`:337`),
and `build_physical_graph_workspace` (`:344`). Both run under the retained
control relation lock **and** the registry revision row lock, so the reloption
read cannot race a concurrent registry mutation.

T2's refactor is safe rather than merely plausible: `open_control_index`
(`generation_store.rs:84-114`) opens `index_oid` itself, so `control` and the
later `index_relation` guard are the same relation. Hoisting
`relation_options(control.as_ptr())` to `:223` means
`options.validate_head_sizing_inputs()` at `:331` observes exactly the values it
observed before this commit — under a stricter lock mode
(`ShareRowExclusiveLock` rather than `AccessShareLock`), which is the safe
direction.

**No-cover.** `resolve_payload_cover` returns `Ok(None)` at
`payload_sidecar.rs:46-48` before touching the schema, and
`EcDistannOptions::DEFAULT` gains `covering_payload_attnums: None`
(asserted at `options.rs:1497`). Two computations *are* unconditional, and I
checked each for a new failure class rather than taking the request's word
(log X8):

- `relation_options(control.as_ptr())` is new as a direct call in T1, but
  `control_compatibility_digest` at `t1.rs:329` already read the same
  reloptions off the same relation in the same transaction. No new failure.
- `routine::indexed_ecvector_attnum` is genuinely new on the no-cover path. Its
  three error arms are each unreachable on an index that builds successfully
  today: `ii_NumIndexKeyAttrs != 1` is blocked by `amcanmulticolumn` being unset
  plus `ambuild.rs:1370-1372`; `ii_NumIndexAttrs > 2` is blocked by
  `ambuild.rs:1373-1387` combined with `control_compatibility_digest` requiring
  `source_identity='include'`; and the expression-key arm (`attnum <= 0`) hits
  only indexes that already fail at `physical_dml.rs:148`,
  `generation_read.rs:1243`, and `routine.rs:621` — i.e. indexes that were never
  usable, now failing earlier with the same message.

So no index that previously produced a usable no-cover generation now fails, and
no no-cover byte, descriptor, or relation changes.

## 4. Review question 4 — checkpoint 2 may proceed

**Yes.** Carry these five into it. They are implementation notes and do not
require a reply before checkpoint 2 starts; item 1 is the only one that must
actually be *closed* in checkpoint 2.

1. **Bind the resolved cover into the registration identity — required in
   checkpoint 2.** Nothing today ties T1's resolved cover to T2's.
   `replay_registration` compares `row_schema_fingerprint` and
   `compatibility_digest`, and `control_compatibility_digest`
   (`generation_store.rs:117-141`) folds in only `distributed_control` and
   `source_identity` — not `covering_payload_attnums`. An
   `ALTER INDEX ... SET (covering_payload_attnums=...)` between T1 and T2, or
   before a T1 replay, changes the resolved cover with no digest movement and no
   error. This is **not** a checkpoint-1 defect: `let _resolved_payload_cover`
   (`t1.rs:323`, `t2.rs:228`) persists and consumes nothing, so no divergence is
   observable yet. It becomes a real correctness hole the moment the descriptor
   is persisted, and packet 001 `request.md:27-28` already rules the persisted
   descriptor authoritative over the mutable reloption. Fold the cover into
   `compatibility_digest`, or into the registration row alongside
   `row_schema_fingerprint`, in the same slice that lands
   `DistannPayloadCoverDescriptorV1`.
2. **The 258-byte guard is unreachable — do not count it as tested.** With the
   parse gate and the resolver both capping at 16 attributes and the widest
   allowlist entry at 16 bytes, `value_bytes` cannot exceed 256 and the
   comparisons at `payload_sidecar.rs:123-130` cannot fire on any reachable
   input. The guard is correct defense-in-depth and should stay. But the test
   name `resolution_binds_schema_and_enforces_the_258_byte_bound` overstates
   what it proves — it proves the bound is *attained exactly*, and no negative
   case exists to write. Worth renaming so checkpoint 2 does not inherit the
   impression that overflow is covered.
3. **`indexed_ecvector_attnum` runs unconditionally.** Verified non-regressive
   above, and failing earlier is arguably the better behavior. If you would
   rather keep the no-cover path literally untouched, both it and
   `relation_options` hoist cleanly under
   `if options.covering_payload_attnums.is_some()`. Either choice is fine —
   stating it so the decision is deliberate.
4. **Run clippy before the slice that consumes the resolved fields.**
   `cargo fmt` and `cargo check --lib --no-default-features --features pg18` both
   pass with no warnings on the new module, which is appropriate under the
   no-tests-by-default policy for a preflight-only checkpoint. But
   `ResolvedPayloadCoverAttribute::{schema_attribute,binary_width}` are
   currently constructed and never read outside `#[cfg(test)]`. Run
   `cargo clippy --all-targets --no-default-features --features pg18 -- -D warnings`
   in the checkpoint that first reads them, so a dead-code or
   `--all-targets`-only lint does not surface late.
5. **Consider excluding the ADR-063 `source_identity` INCLUDE attnum.** The
   resolver rejects the indexed vector attnum (`payload_sidecar.rs:74-78`) but
   not the identity INCLUDE column. Covering it is correct, just redundant —
   those bytes already travel as `vec_id`. Optional; a wasted 16 bytes out of
   258 is a real fraction of the budget if a user does it by accident.
