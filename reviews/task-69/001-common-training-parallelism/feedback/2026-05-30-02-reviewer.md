# Reviewer follow-up — Task 69 packet 001 (kmeans partial reduction shape)

**Verdict: NOT a BLOCK on correctness (byte-equal output preserved), but
the change is a perf regression vs the prior commit and should be either
reverted or reshaped before Slice D measurement.**

Reviewing commit `dcc0d0b39 Use deterministic kmeans partial reduction`,
which lands on top of `578d8f402` and appears to address the
sequential-accumulation note in my earlier feedback
(`2026-05-30-01-reviewer.md`).

## What changed

The iteration body now:

1. Parallel-maps every sample into a `KMeansAssignmentPartial { sample_index,
   centroid_index, sum: sample.clone(), changed }`
   (`training.rs:assign_kmeans_chunks`, ~line 250).
2. Sequentially folds the `Vec<KMeansAssignmentPartial>` into the
   iteration-global `sums`/`counts`/`assignments`
   (`training.rs:reduce_kmeans_partials`, ~line 275).

## Why this isn't the intended shape

The task plan asks for *per-thread* partials, reduced once per thread at
the end of the parallel section:

> Use a per-thread `Vec<Vec<f32>>` sums buffer plus a per-thread
> `Vec<usize>` counts buffer, reduced into the iteration-global `sums`
> and `counts` after the parallel section.

`dcc0d0b39` instead produces *per-sample* partials. Each partial:

- carries a fresh `Vec<f32>` allocation (`sum: sample.clone()`) — one
  `samples * dimensions` allocation per k-means iteration, on top of
  the existing samples buffer,
- is then walked sequentially in source order to do the same
  in-place add the previous commit already did.

Net effect vs `578d8f402`:

- accumulation phase: still single-threaded, same arithmetic, same
  source-order reduction — no parallelism added,
- allocation: a fresh `Vec<f32>` of length `dimensions` per sample per
  iteration (no reuse across iterations because the `partials` vec is
  rebuilt each pass),
- indirection: an extra struct + Vec walk vs the previous direct
  `samples.iter().zip(next_assignments.iter())`.

So this commit is byte-equal in output but slower and more
allocation-heavy than the version it replaced. It does not move
accumulation onto multiple threads.

## What "per-thread partials" actually looks like

Two acceptable shapes for an actual parallel reduction:

1. **Rayon `fold` + `reduce`:** each thread folds an `nlists`-shaped
   `(sums, counts)` accumulator over its chunk, then `reduce` combines
   thread-local accumulators pairwise. Determinism requires a fixed
   chunking strategy and a fixed reduction order — `rayon::iter::ParallelIterator::fold_chunks`
   with a deterministic chunk size, or a `collect::<Vec<_>>()` of
   thread-local accumulators followed by a sequential merge in collected
   order, gives byte-equal output if the per-thread fold itself is
   deterministic.
2. **Chunked indexed reduction:** split `samples` into N fixed-size
   chunks, parallel-map each chunk to a fully-reduced
   `(nlists-sized sums, nlists-sized counts, changed)` tuple, then
   merge chunks in chunk-index order. Deterministic byte-equal as
   long as the chunk size is fixed.

Either shape gives O(threads) accumulation passes instead of
O(samples), and is what the original spec was asking for. The
property tests already in place
(`spherical_kmeans_parallel_matches_scalar_byte_for_byte`) gate the
determinism contract regardless of which shape is chosen — if those
pass, the byte-equality claim holds.

## Recommendation

Pick one of:

- **(A) Revert `dcc0d0b39`.** Keep `578d8f402`'s simpler in-place
  sequential accumulation. It is byte-equal, has no extra allocation,
  and the assignment-dominant cost model from my earlier note still
  holds. Then validate at Slice D whether the accumulation step
  actually shows up on the profile. If it doesn't, you're done.
- **(B) Replace `dcc0d0b39` with a real per-thread fold.** Use either
  of the two shapes above. Keep the existing determinism property
  tests as the contract.

I'd prefer (A) until Slice D evidence justifies (B), since the current
commit is strictly worse than its parent on perf without giving
anything in exchange. (B) is the right move only if Slice D
measurement at large `samples` shapes shows accumulation as a hot
fraction.
