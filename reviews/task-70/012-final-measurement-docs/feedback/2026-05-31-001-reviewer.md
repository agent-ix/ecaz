## Concern: unprofiled compare-step regression at L=200

Walking the cross-engine compare-step (the unprofiled signal, which
is the reviewable performance measurement) across packets:

| packet | event | ec_diskann L=200 mean |
| --- | --- | ---: |
| 003 | Phase 1 baseline (pre-Phase 2) | **0.83 ms** |
| 004 | neighbor retention slice — kept | 0.77 ms (−0.06 vs baseline ✓) |
| 008 | sub-timing instrumentation lands | **0.97 ms** (**+0.20 vs packet 004 ⚠**) |
| 009 | membership-insert merge — kept | 0.91 ms (recovered 0.06 vs packet 008) |
| 012 | final state | 0.88 ms |

**Net change vs Phase 1 baseline at L=200: +0.05 ms / +6 %.**

Packet 004's win was real and held. Packet 009's win was real and
held. But packet 008's instrumentation introduced ~0.20 ms of
overhead in the *unprofiled* compare-step path — which is supposed
to be zero-overhead. Packet 009 recovered ~0.06 ms of that;
packets 011/012 may have recovered another ~0.03 ms via inlining
hints. ~0.11 ms of packet-008-introduced overhead remains.

### Why this happened

Packet 008 unified profiled and unprofiled paths via
`vamana_scan_with_profile(.., Option<&mut FrontierProfile>)` with
~10 `if let Some(profile) = ..` runtime branches in the inner loop.
The default path passes `None`, but LLVM cannot fully dead-code-
eliminate these branches across the function boundary. At L=200
with ~5000 inner-loop iterations × ~10 conditional branches ×
~2 ns/branch ≈ 100 µs of residual instrumentation tax per query.

Contrast packet 001's `execute_diskann_scan` vs
`execute_diskann_scan_profiled` split (routine.rs) — that one
keeps two fully separate functions with no shared inner-loop
conditional checks, and pays zero overhead in the default path.

### Why I'm not blocking closeout on this

- Exit criteria do not require monotonic improvement vs Phase 1
  baseline. They require recall preservation (✓) and updated
  cross-engine evidence (✓), both met.
- The customer-facing comparison (vs `pgvectorscale`) is still
  favorable: at L=200 `ec_diskann` (0.88 ms) is 22.8 % faster
  than `pgvectorscale` (1.14 ms) at recall 0.9975 vs 1.0000.
- The L=64 lane shows no regression vs Phase 1 (0.64 vs 0.64 ms).
- The docs row's framing — "now measures X" — accurately states
  current state without overclaiming Task 70-specific attribution.

### Recommended follow-up packet (not blocking)

File a Task 70 follow-up packet (or a Task 70.1 if a new task is
preferred) with a single deliverable: split the profile/non-profile
paths the way `routine.rs` does, so the default path pays zero
runtime overhead. Concrete shape:

- Keep `greedy_descent_with` and `vamana_scan_with` as the
  non-profile entrypoints with no `Option<&mut FrontierProfile>`
  parameter and no inner conditional branches.
- Move the instrumented variants into separate functions
  (`vamana_scan_with_frontier_profile`,
  `greedy_descent_with_frontier_profile`) that have the timing
  code unconditionally compiled in.
- Acceptance gate: compare-step ec_diskann L=200 returns to
  ≤ 0.83 ms (Phase 1 baseline), and ideally ≤ 0.77 ms (post-
  packet-004 baseline) once the kept slices are accounted for.

The duplication cost is real (it's the same tradeoff packet 001
called out for `execute_diskann_scan_profiled`), but for the hot
inner loop the zero-overhead default path is worth it.
