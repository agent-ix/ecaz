# Review: Task 70 / Packet 004 — Frontier Neighbor Retention — ACCEPT with caveats

Reviewed the source diff at `dd42450f7fd0215d9c7385dd9cc1b25c0443b769`
(`src/am/ec_diskann/scan.rs`), `artifacts/phase2-frontier-summary.md`, and
the surrounding `vamana_scan_with` / `greedy_descent_with` invariants.

## What this packet does

Two structural changes to `greedy_descent_with`:

1. `neighbors_from_tuple` now consumes the `VamanaNodeTuple` and returns
   `(Vec<ItemPointer>, usize)` instead of copying live neighbors into a
   fresh `Vec`. `FrontierEntry` gains a `neighbor_count` field;
   iteration uses `into_iter().take(neighbor_count)`.
2. `insert_visited_sorted` now caps `visited_best` at `list_size` after
   every insert.

Net result: one fewer `Vec` allocation per visited node, and a bounded
visited set during traversal.

## What I verified against the source

- **No new `unsafe`.** Confirmed.
- **No anti-pattern-B violations.** The `Vec<ItemPointer>` is owned
  cleanly through `FrontierEntry`; no `&'a` lifetimes; no raw pointers.
  Compliant with `feedback_anti_pattern_b_unbounded_lifetime`.
- **`min(neighbors.len())` is a defensive hardening.** The new
  `usize::from(tuple.neighbor_count).min(tuple.neighbors.len())` caps
  the count against the actual vec length, which the old
  `.take(tuple.neighbor_count as usize)` did not guard. Quietly fixes
  a latent over-read class.
- **`visited_best.truncate(list_size)` is semantically correct.**
  `partition_point` gives an ascending-sorted position; insert + truncate
  preserves the top `list_size` by ordering. Downstream
  `filter(emittable).take(rerank_budget)` requires
  `rerank_budget ≤ list_size`, which `vamana_scan_with` already
  validates at entry. Truncation is safe.
- **Tests pass.** 18 scan module tests + full bench suite per request.

## Caveats (flagging, not blocking)

1. **The win is below typical noise (2–5% on frontier_us).** At L=64
   the reported total `mean_us` actually went UP 0.76% (rerank
   variance ate the frontier win); only L=200 shows a clean
   reduction. The summary calls this out honestly. A single-run
   measurement at this magnitude could be noise; ideally we'd see
   N=3+ suite reruns with confidence intervals before claiming the
   slice. Not blocking — the structural change is correct on its own
   merits — but the headline "−4.55%" should be read as
   indicative-not-confirmed.

2. **Behavior change worth calling out: `visited_best` is now bounded
   at `list_size`.** Previously unbounded — could grow to ~visit_count
   (758 at L=64, 1585 at L=200). On clean fixtures with no tombstones
   the cap is invisible (recall preserved at 0.9965 / 0.9975
   identically). The latent risk lives in **tombstone-heavy
   workloads**: if many of the top-`list_size` candidates are
   non-emittable (tombstoned or stripped per ADR-047 pass 1), the
   filter-take in `vamana_scan_with` could end up with fewer than
   `rerank_budget` emittable candidates. Previously the unbounded
   visited set provided extra slack; now there's none.

   This is exactly the kind of regression a clean-corpus bench will
   miss. Suggestion: run the scan tests with a corpus that has been
   vacuumed mid-test or contains tombstones (`reviews/task-29b/` may
   have relevant fixtures), or add a unit test in
   `scan::tests` that exercises a visited-best with mostly-tombstoned
   top candidates and asserts the emittable count.

3. **The `+9.48%` rerank delta at L=64** is suspicious. The slice
   doesn't touch rerank; this is pure noise. Underscores point (1):
   the measurement window is too small to distinguish the slice's
   real effect from per-run variance.

4. **My packet 003 sub-timing suggestion** ("split frontier into
   heap-ops vs visited-bitset vs neighbor iteration") was authored
   after this slice was committed. Future Phase 2 slices should land
   that sub-timing first so the next slice has a sharper target than
   "the residual." This slice happens to target allocation, which is
   defensible without sub-timing, but the next one needs the
   breakdown.

5. **Cross-engine comparison.** Post-slice `ec_diskann` matches
   pgvectorscale at L=64 (parity at 0.60 ms mean, slightly higher
   recall 0.9965 vs 0.9960) and pulls ahead at L=200 (0.77 vs 1.13 ms,
   though pgvectorscale has 1.0000 recall vs 0.9975). The competitive
   posture improved without sacrificing recall on this fixture.

## Verdict

Accept. Structural improvement is correct, the tombstone-safety
risk is documented for follow-up, the win is small but legitimate.

Before the next slice:
- Add a tombstone-heavy regression test exercising the bounded
  `visited_best`.
- Add the sub-timing instrumentation (heap-ops / visited / neighbor
  iter) from packet 003 review point 1.
- Consider rerunning the suite N=3 to confirm the L=200 win is above
  noise.
