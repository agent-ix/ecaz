## Key finding: heap ops are NOT the bottleneck

The sub-timing data answers a question that's been guiding the last
three Phase 2 slice attempts:

| field | L64 mean | L200 mean | share of `frontier_us` |
| --- | ---: | ---: | ---: |
| `frontier_candidate_heap_us` | 4.13 us | 10.96 us | **1.0 % / 1.2 %** |
| `frontier_visited_set_us` | 0.23 us | 1.06 us | 0.06 % / 0.12 % |
| `frontier_neighbor_iter_us` | 0.09 us | 0.79 us | 0.02 % / 0.09 % |
| `frontier_retained_insert_us` | 0.01 us | 0.00 us | 0 % / 0 % |
| **sum of inner sub-timers** | **4.46 us** | **12.81 us** | **~1.1 % / ~1.4 %** |
| `frontier_us` total | 401.60 us | 920.04 us | 100 % |

**98–99 % of frontier residual is NOT in any of the four wrapped
inner ops.** This is the load-bearing inference for the next slice:

- Packet 004's neighbor-retention slice (kept) and packet 005's
  binary-heap slice (reverted) both targeted the candidate-heap
  surface, which is at most ~1.2 % of frontier_us. My packet 005
  revert recommendation is confirmed retroactively — algorithmic
  heap rewrites cannot win Phase 2's 5 % gate against this
  workload, because there isn't 5 % of heap time to recover.

## Where the residual actually lives

The 98–99 % unaccounted residual is one of (combining what the
sub-timing can and can't see):

1. **Post-descent processing in `vamana_scan_with` after
   `greedy_descent_with` returns** — `filter(emittable)`,
   `take(rerank_budget)`, the heap-TID sort,
   `prefetch_tids` construction, the final distance sort. None of
   these are inside greedy_descent so the inner sub-timers cannot
   see them; they all bleed into the outer `frontier_us` residual.
2. **Closure-call overhead** — the prefilter closure is invoked
   per neighbor (5256 calls at L200). Even at ~50 ns per virtual
   call, that's 250 us — plausibly material at this scale.
3. **Cache-miss latency** during `reader.read_node(nbr)` and
   neighbor walks. Some of this is in `graph_read_decode_us`
   already, but the in-CPU stalls between graph_read returns and
   the next op are not.
4. **Instant::now() overhead from the new sub-timers themselves.**
   At L200 the sub-timing adds ~10–12 `Instant::now()` pairs per
   neighbor slot × 5256 slots × ~30 ns each ≈ 1.6 ms of wrapping
   overhead per query. That's *more* than the reported
   `frontier_us` — meaning the profile-on path inflates the
   residual significantly. The summary already notes the latency
   table difference (0.96 ms unprofiled → 1.29 ms profiled at
   L200, ~35 % overhead).

The coder's reviewer note in the request captures (1)–(3) honestly:
*"wall-clock micro-timing inside the fastest inner-loop pieces is
too fine-grained to fully allocate the residual."* Agreed.

## Operation count signal (the real Phase 2 signpost)

| metric | L64 mean | L200 mean | ratio L200/L64 |
| --- | ---: | ---: | ---: |
| `graph_read_count` | 758 | 1585 | 2.09× |
| `frontier_candidate_heap_ops` | 894 | 1990 | 2.23× |
| `frontier_visited_set_ops` | 1751 | 5257 | **3.00×** |
| `frontier_neighbor_slots` | 1751 | 5257 | **3.00×** |
| `frontier_retained_inserts` | 67 | 202 | 3.01× |

L200's super-linear scaling vs visit count comes from **visited-set
checks and neighbor-slot walks**, not heap ops. The 3.00× factor
matches `list_size` ratio (200/64 = 3.125), suggesting these are
dominated by repeated work near the bounded-frontier size — i.e.,
work that scales with the K of "top-K" rather than the visit
count.

`frontier_visited_set_ops == frontier_neighbor_slots == 5257` means
every neighbor slot at L200 generates one `in_frontier.contains`
check, and zero `INVALID` slots in this fixture. Consistent.

## What I verified against the source

- **Default path is overhead-free.** `vamana_scan_with` routes
  through `vamana_scan_with_profile(.., None)`. The `Option`
  matches as `None` and all the `if let Some(profile) = ...`
  branches are skipped. The compiler will likely inline these
  branches to dead code on the non-profile call site.
- **No new `unsafe`.** Confirmed.
- **No anti-pattern-B violations.** All `&mut FrontierProfile`
  parameters are bounded by the call frame.
- **Profile path is correct.** Every `Instant::now()` is paired
  with an `add_profile_elapsed`. Every counter increment matches a
  successful op (e.g., visited_set_ops increments on both
  contains-hit and contains-miss branches; that's the right
  semantic).
- **`heap_started`/`push_started`/etc. reuse the same `Instant`
  variable name across blocks** in the diff — each `let` rebinds
  fresh, no chance of stale `started` values. Verified.
- **Test count 19 → still 19.** No new test, but no broken
  existing ones either. Profile path doesn't have a unit test of
  its own.

## Concerns (non-blocking)

1. **No unit test exercises the profile path.** The default path is
   well-tested; the profile path is sizable and has zero direct test
   coverage. A small smoke (call
   `vamana_scan_with_frontier_profile` with a synthetic reader,
   assert all 4 counters are positive and no panic) would be cheap.
   Matches my packet 001 review's same concern; the pattern is
   recurring.

2. **Per-op Instant wrapping inflates `frontier_us` significantly.**
   At L200 the profile path measures `total_us` = 1037 us; the
   non-profile path measures ~0.96 ms = 960 us. So the wrapping adds
   ~80 us per query — about 8 % of total. Inside `frontier_us`
   specifically, the wrapping overhead is proportionally larger. The
   sub-timers are reliable for *relative* shape (heap vs visited vs
   neighbor) but not for *absolute* frontier_us attribution.

3. **Most signal is now in the operation counts, not the timers.**
   The summary already pivots to that view. For the next slice,
   reducing per-op count (e.g., dedup'd visited check, batched
   neighbor expansion) is a clearer Phase 2 target than reducing
   per-op cost.

## Verdict

Accept. This is the right shape of instrumentation, and the
finding — heap is not the bottleneck — is the answer to the
question my packets 003/004/005 reviews were asking. The coder's
reframing toward operation counts as the slice signpost is correct.

## What I'd watch for next

- **Don't pick a slice that targets a sub-1 % wall-time bucket.**
  The candidate-heap surface is now demonstrably below the 5 %
  gate; do not rewrite it again.
- **The 3× scaling of visited_set_ops / neighbor_slots from L=64 to
  L=200** is the strongest lever signal in the data. A slice that
  reduces duplicate neighbor lookups, batches the `in_frontier`
  membership check, or dedupes neighbor sets across visits could
  hit the gate.
- **Or shift attribution.** A coarser bucket pass — say, time
  inside `greedy_descent_with` vs time after it returns — would
  isolate post-descent processing as a candidate. If the
  post-descent work is the actual residual, that's a different
  slice surface than anything Phase 2 has tried.
