# Review: Task 70 / Packet 006 — Shelved Rerank Result Retention — ACCEPT (shelve confirmed)

Reviewed the measured commit `4f499e279`, the revert commit `3f3fa8bfe`,
and `artifacts/phase2-rerank-retention-summary.md`.

## What this packet does

Records a negative-result Phase 2 slice. The measured change replaced
the "materialize all `rerank_budget` exact results then sort+truncate"
pattern with a bounded top-`top_k` max-heap maintained per
exact-rerank result. At the current `rerank_budget=64` / `top_k=10`
operating point, the heap maintenance cost exceeded the savings;
exact-rerank phase regressed 13–15%, end-to-end L=200 latency
regressed ~7%. The slice was reverted.

## What I verified

- **Reverted code matches packet 005 state.** `git diff
  3f3fa8bfe^..3f3fa8bfe -- src/am/ec_diskann/scan.rs` and the
  pre-measurement test pass both confirm the tree is back to
  packet 005 semantics. `cargo-test-after-revert.log` shows 18
  tests passing post-revert.
- **Measurement is honest and unambiguous.** L=200 total +4.21%,
  exact rerank +13.90%. Recall preserved 1:1. The slice clearly
  regresses.
- **The mechanism is well-explained.** At budget=64 / top_k=10, the
  heap maintains a bounded set of size 10 across 64 inserts. The
  per-insert heap op costs more than the deferred sort-truncate
  pattern of 64 elements. Heap retention pays off when
  `rerank_budget` is much larger than `top_k`; the current operating
  point isn't in that regime.
