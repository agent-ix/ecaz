# Review: Task 70 / Packet 003 — Phase 1 Suite Config + First Run — ACCEPT

Reviewed `artifacts/suite.json`, `artifacts/phase1-profile-summary.md`,
the `vamana_scan_with` signature in `src/am/ec_diskann/scan.rs:199-291`,
and verified the phase-split arithmetic against the summary table.

## What this packet does

Lands the Task 70 Phase 1 measurement: `ecaz bench suite` config that
loads real10K DBpedia into `ec_diskann`, sweeps `list_size` 64 + 200,
captures 200 `ec_diskann_scan_profile` NOTICE rows per L via raw
`dev sql` steps, compares against pgvectorscale, and produces the
ranked P0 slice list.

## What I verified against the source and artifacts

- **Phase split is internally consistent.** At L=64 the sum of phases
  in the summary table (12.48 setup + 269.62 frontier + 80.71 rerank
  + 3.85 prefetch + 2.20 graph + 0.07 prefilter + 0.01 expand =
  368.94 us) matches the reported "profiled total" 369.68 us within
  rounding. Same check passes at L=200.
- **Prefilter accounting is honest.** `vamana_scan_with` uses the
  `prefilter` closure as the per-visit distance function (binary
  sidecar), and `prefilter_score_us` measures that closure. The
  ~70 ns per-call mean is plausible for a binary popcount-style
  prefilter; it is not under-attribution.
- **Frontier dominance is real, not a measurement artifact.** With
  prefilter, graph_read, prefetch, and rerank wrapped in their own
  closures, `frontier_us` = `vamana_scan_with` wall minus those four.
  What remains in that residual is exactly the orchestration:
  candidate-heap push/pop, visited bitset, neighbor iteration,
  bounded-frontier truncation. 270 us / 758 visits ≈ 350 ns per
  visit at L=64 — credible for a log-N heap op + ~graph_degree
  visited checks.
- **Recall floor preserved.** L=64 recall@10 0.9965 and L=200 0.9975
  both clear Task 70's "no regression" gate.
- **pgvectorscale comparison reads correctly.** At L=64 `ec_diskann`
  is 0.04 ms slower but 0.0010 higher recall (effective Pareto
  parity). At L=200 `ec_diskann` is 0.30 ms faster but 0.0025
  lower recall (different Pareto point). The summary frames this
  neutrally; my read is that `ec_diskann` is competitive on the
  comparator engine.

## P0 ranking — agreed, with sharpening

The ranked list (1: frontier, 2: exact heap rerank; shelve everything
< ~5%) follows the data. Two refinements before Phase 2:

1. **The "frontier" bucket is still composite.** It contains at least
   (a) candidate-heap push/pop, (b) visited-bitset query/insert,
   (c) inner neighbor-list iteration, (d) bounded-frontier ordering.
   The plan summary names (a)/(b)/(c) but the profile doesn't
   separate them. Before committing a Phase 2 slice, add one more
   sub-timing pass that distinguishes at minimum heap-ops vs
   visited-bitset vs neighbor iteration, otherwise the slice risks
   optimizing whichever subcomponent is *not* the bottleneck.
2. **Exact heap rerank at 21.83% (L=64) is mostly heap fetch +
   detoast.** Before committing a Phase 2 slice here, separate
   "buffer fetch wall time" (network/storage) from "in-CPU detoast +
   distance compute". If most of it is fetch, the existing batched
   prefetch is already the best lever; if detoast is material, the
   slice shape changes.

## Other notes (non-blocking)

3. **`entry_resolution_us` is captured in the NOTICE but missing from
   the summary table.** Add a row for it; the table accounts for
   total cleanly except for that field.
4. **Phase split uses mean only.** The NOTICE captures per-query so
   p95/p99 per-phase is recoverable from the log. For latency tail
   work, that view is more useful than mean alone — a phase that
   averages low but spikes can dominate p99.
5. **`bench latency --session-guc` does not surface per-query NOTICEs
   through the tokio-postgres path** (called out in the summary
   notes). For Phase 2 this matters: if you want NOTICE capture from
   the parallel latency workers (not just the serial `dev sql`
   step), the latency runner needs a NOTICE callback. Worth filing
   as Phase 0 infrastructure for any Phase 2 sweep that goes wide.
6. **`LOAD 'ecaz'` before `SET ec_diskann.scan_profile_notice` is a
   real footgun.** Without `LOAD`, PG accepts an unregistered
   custom GUC as a placeholder; the extension binds the real GUC
   later and never sees the toggle. The summary records this but
   the GUC docs in `register_gucs` (packet 001) should call it out
   too, otherwise the next operator burns 30 minutes on a silent
   no-op.

## Verdict

Accept. Phase 1 closes with a defensible P0 ranking and reviewer
approval. Before opening a Phase 2 slice, sharpen the "frontier"
sub-timings and add p95/p99 per phase — those two pieces of
follow-up measurement will keep the slice scope tight.
