# Review: Task 70 / Packet 007 — Tombstone Retention Regression — ACCEPT

Reviewed `e633b9dd05d2b8ef6fe54f1674443e11af8e6208`,
the new test `sc_018_tombstoned_top_scores_do_not_starve_emittable_frontier`,
and the packet 005 revert at `7707117f1`.

## What this packet does

Directly addresses the tombstone-safety caveat from my packet 004
feedback. In `greedy_descent_with`:

1. Adds `if picked.emittable` gate before `insert_visited_sorted` —
   non-emittable (tombstoned / ADR-047 stripped) candidates do not
   consume retained-frontier slots.
2. Keeps neighbor expansion unconditional — graph connectivity is
   preserved through tombstoned nodes (the original DiskANN
   correctness property).
3. Updates `greedy_descent_with` doc to reflect "emittable frontier"
   semantics.
4. Adds regression test `sc_018` with a star graph where 4
   tombstoned nodes have the best prefilter scores and 4 live
   nodes rank behind them; asserts the scan emits the live nodes
   not the tombstones.

The packet 005 binary-heap slice was reverted at `7707117f1` per my
prior recommendation. The retained set is back to
`Vec<ScanCandidate>` + `insert_visited_sorted` + `truncate(list_size)`
shape from packet 004.

## What I verified against the source

- **Behavior change is exactly what the packet-004 review asked for.**
  Previously a tombstone-heavy descent could fill `visited_best`
  entirely with non-emittable candidates and starve rerank to zero
  results. Now non-emittable candidates participate in traversal
  (for connectivity) but cannot displace live candidates from the
  bounded retained set.
- **The test reproduces the original bug shape.** With the old code
  on this fixture, `visited_best` would be `[node1, node2, node3,
  node4]` (the 4 tombstones, best scores), `filter(emittable)` then
  yields zero candidates, rerank returns nothing. The new test
  asserts `emitted_nodes == [5, 6, 7, 8]`, which is impossible
  without the emittable gate.
- **Test uses real `vacuum::mark_deleted`** to set tombstone flags —
  exercises the actual deletion path, not a mocked emittable=false.
  Good fidelity.
- **Cost of the new check.** One bool branch per pop, well-predicted
  on tombstone-free workloads. Zero measurable performance cost
  expected.
- **No new `unsafe`.** Confirmed.
- **No anti-pattern-B issues.** All changes inside the existing
  `pg_am_callback!` boundary.
- **Test count**: 18 → 19. `cargo-test-diskann-scan.log` confirms
  all 19 pass.

## Notes

1. **Star graph is a narrow topology**, but for the specific bug
   ("tombstones at top of the priority order starve retained set")
   it's the canonical reproducer. The retained-set gating logic is
   topology-agnostic, so this test is sufficient for the regression
   class. If you wanted a broader test, a 2-hop graph with mixed
   tombstone distribution would exercise the traversal continuation
   more thoroughly — but I do not require it.

2. **Stop-threshold interaction is correct.** The traversal stop
   check is `retained_best.len() >= list_size && next >= worst_retained`.
   With the new gate, `retained_best` fills slower under
   tombstone-heavy load, so the scan keeps walking until it either
   collects `list_size` live candidates or exhausts the frontier.
   Exactly the desired behavior.

3. **`emittable` semantics are preserved end-to-end.** The downstream
   `vamana_scan_with` already had
   `frontier.into_iter().filter(|c| c.emittable)` before this slice;
   the gate makes the retained set internally consistent with that
   filter rather than relying on the post-filter to drop tombstones.
   That's cleaner — the retained set now represents "what could be
   emitted" instead of "what was visited."

4. **Performance posture is unchanged on clean fixtures.** The
   real10K corpus has no tombstones, so the recall/latency results
   in packets 004 onward apply unchanged. This packet correctly
   excludes a benchmark run.

5. **Sub-timing instrumentation is still pending.** Packet 008
   appears to be that work (`Add DiskANN frontier sub-timing
   profile` commit visible on `main`); I'll review when its
   request.md lands.
