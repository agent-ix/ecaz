## The oracle bounds settle the question

### Score-margin rescue

| margin predicate | best-case rows recovered | best-case recall |
| --- | ---: | ---: |
| ≤ 0.001 | 3 | 0.9838 |
| ≤ 0.0025 | 6 | 0.9844 |
| ≤ 0.005 | 11 | 0.9854 |
| **≤ 0.01** | **26** | **0.9884** |
| all selected-leaf | 81 | 0.9994 |

### Rank-delta rescue

| extra blocks | best-case rows recovered | best-case recall | min added cands |
| ---: | ---: | ---: | ---: |
| 64 | 4 | 0.9840 | 4,096 |
| 128 | 7 | 0.9846 | 12,288 |
| 256 | 16 | 0.9864 | 45,056 |
| 512 | 30 | 0.9892 | 163,840 |
| **1024** | **47** | **0.9926** | **507,904** |
| 2048 | 58 | 0.9948 | 1,310,720 |

These are **oracle upper bounds** — they assume the rescue triggers
on exactly the failing queries with zero false positives. A real
predicate (e.g., score-margin-based ambiguity detection) would also
fire on non-failing queries, inflating candidates beyond these
minimums.

### Why this kills the selective rescue path

Three structural problems:

1. **Narrow predicates can't clear the 0.9925 recall floor.** Even
   the best margin-rescue (≤ 0.01 captures 26 rows) only reaches
   0.9884 oracle. That's below the Task 79/81 spec floor.

2. **The first predicate that crosses the floor (rank ≤ 1024 →
   0.9926 oracle) already adds 507,904 candidates = ~5.5%
   inflation** with zero false-positive margin. That's already
   approaching blanket-cap territory and depends on perfect
   oracle behavior.

3. **Wide predicates that recover enough recall behave like the
   rejected blanket-cap sweep.** rank ≤ 2048 (recall 0.9948
   oracle) adds 1.3M candidates = ~14% inflation, matching Task
   83's rejected cap1280-1664 controls.

So there's no bounded predicate that simultaneously: (a) clears
0.9925 recall, (b) preserves the candidate surface, and (c) has
plausible real-world trigger fidelity. The selective-rescue axis
closes correctly.

## Why Task 85 is correctly framed

The remaining moves at AWS 1M are structural, not parameter-tuning:

1. **Richer per-block summary geometry** (per ADR-074): V5 leaf
   format with different summary representation (e.g., residual
   sketches, learned codebooks, hierarchical summaries). This is
   the path the Task 81 reviews kept circling.

2. **Different leaf row geometry** (smaller blocks at 1M density):
   block_rows=8 or 4 instead of 16, multiplying summary count per
   leaf to match leaf row growth. Build cost grows but discrimination
   could keep pace with density.

3. **Routing-side changes** (different top-graph construction or
   per-level nprobe budgets): bounded by the Task 81 evidence that
   showed wider routing doesn't help and narrower hurts.

4. **Accept 0.9832 as the operational 1M ceiling** at this geometry
   and focus on tail latency / throughput at scale.

Each of these is a real ticket, not a knob-tuning slice. Task 85
treating SPIRE as a "broader product-scale Pareto program" reads as
explicit acknowledgment of this.
