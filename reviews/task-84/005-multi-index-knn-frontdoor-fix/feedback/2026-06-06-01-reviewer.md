# Task 84 packet 005 — multi-index KNN frontdoor fix + k=3 AWS result

## Decision

**Accept on two axes:**

1. **DML frontdoor fix**: clean, narrow, ADR-069-compliant. Land it.
2. **k=3 AWS result interpretation**: correctly framed as a negative.
   k=3 does not recover 1M recall at matched candidates. The k>2
   summary-count axis can close.

**One incidental finding worth recording**: at matched recall and
candidates, the k=3 row's p50 is ~30ms faster than the retained k=2
baseline. That's not the Task 84 goal and may be measurement
artifact (fresh-build disk layout, run-to-run variance), but it's
worth following up before discarding the k=3 path entirely.

## DML frontdoor fix (07974586f) — clean

### Narrowness verified

- **UPDATE/DELETE**: always fail-closed. Unchanged.
- **PK SELECT**: fail-closed via shape classification
  (`unsupported_pk_predicate` etc.).
- **Non-PK SELECT (KNN)**: passes through only when shape classifier
  returns `non_pk_select_pass_through`.

The decision branch only returns "no front-door action" when the
shape kind is *not* in the fail-closed list. Failure-reason agnostic
on the surface but bounded by shape — multi-index context load
failure can't accidentally route a write through.

### Multi-index detection is implicit but correct

`dml_frontdoor_catalog_index_and_pk()` already rejects
`ec_spire_index_count > 1` explicitly. The fix doesn't add a parallel
multi-index check; it relies on the existing rejection + shape
classification to gate the pass-through. That's the right
factoring — single source of truth for what counts as a frontdoor
candidate.

### Test coverage strong

- `test_ec_spire_multi_index_knn_select_passes_through`: creates
  table with two SPIRE indexes, runs KNN SELECT, verifies
  pass-through. New path covered.
- `test_ec_spire_dml_frontdoor_hook_fail_closed_context_error`:
  uses `WHERE id = 5` (PK predicate). Still fails closed because
  shape classifier returns unsupported PK predicate kind, which is
  NOT in the pass-through list. **Existing fail-closed contract is
  intact.**

### ADR-069 alignment confirmed

ADR-069 specifies PK/DML routing through frontdoor. Non-PK SELECTs
are out-of-scope per ADR-069 — the fix isn't carving an exception,
it's correcting overreach (the prior behavior was failing reads
ADR-069 never specified). No semantic change to write paths.

### Safety

- No new unsafe blocks.
- No panics on hot path (defensive `.unwrap_or(false)`, early-return
  on catalog errors).
- Code surface +47 LOC in `mod.rs`, +45 LOC in tests. Small and
  contained.

## k=3 AWS result — decisive negative for k>2 axis

### Results table

| cap | recall@10 | candidates | p50 | retained k=2 comparison |
| ---: | ---: | ---: | ---: | --- |
| 1024 | 0.9808 | 8,190,090 | 264.202 ms | new probe point |
| **1152** | **0.9832** | **9,213,742** | **252.186 ms** | **= k=2 recall** |
| 1280 | 0.9846 | 10,237,430 | 258.684 ms | = Task 83 cap1280 control |

### Recall is byte-identical to k=2

At cap=1152:
- k=3 recall: 0.9832
- k=2 retained: 0.9832 (Task 82/001, 83/001, 84/001 all confirm)
- Miss attribution at cap=1152: **3 routing + 81 selected-leaf** —
  identical to k=2.

**The same blocks are being selected at matched cap.** k=3 summaries
don't reorder block selection meaningfully at 1M leaf density. This
is the cleanest possible negative for the k>2 axis: not just "no
recall improvement" but "no change in which blocks rank inside cap."

This is consistent with the seq-01 prediction bucket #3 ("matches
Task 79 packet 043 + Task 84 packet 002 'richer signal didn't help'
pattern. Close k>2 axis. The recall problem is then likely a summary
*kind* problem (geometry vs density), not a *quantity* problem (more
reps)").

### The intriguing latency delta (not the gate, but worth following up)

| run | p50 | p95 | p99 | source |
| --- | ---: | ---: | ---: | --- |
| k=2 (Task 82) | 281.345 | 351.396 | 370.986 | retained |
| k=2 (Task 83/001) | 288.769 | 363.138 | 375.732 | retained |
| k=2 (Task 84/001) | 282.869 | 354.557 | 368.232 | retained |
| **k=3 (this packet)** | **252.186** | **311.879** | **324.200** | **fresh build** |

The k=3 row is ~30ms faster across all percentiles. That's not noise
in a single-percentile sense — p50/p95/p99 all move together by
similar magnitudes. Possible explanations:

a. **Fresh-build disk layout** — k=3 index is newly built, the k=2
   retained surface has accumulated reads/cache state from many
   prior runs. Plausible: 64MB extra index size + fresh page-cache
   pattern could explain it.
b. **k=3 scoring is incidentally faster** — taking `max` over 3
   representatives may give better early-cap-trigger behavior than
   over 2, allowing earlier exits. Speculative.
c. **Graviton instance/time-of-day variance** — possible but the
   30ms is consistent across multiple percentiles, which is more
   structural than noise typically shows.

**Suggested follow-up**: before discarding the k=3 path entirely, run
a fresh k=2 build on the same surface and measure its p50. If a fresh
k=2 build is also ~252ms, the latency win is "fresh build" not k=3.
If a fresh k=2 stays at ~282ms, k=3 has incidental latency value
even though it doesn't recover recall. Either outcome is useful.

### Storage delta

- k=3: 936.4 MiB, 991.9 B/row
- k=2: 872.1 MiB, 923.7 B/row
- **+7.4% size** for the third representative. Operationally minor
  but worth recording in any future preset.

### Cold-start anomaly at cap=1024

`global1024` shows p99=2902 ms (vs p95=340 ms). That's a single
catastrophic query out of 500. Worth investigating before declaring
cap=1024 a valid probe point — if it's a one-off cold-cache event
the run could be re-measured for a clean comparison. Not blocking
the k>2 closure decision.

## Recommended next direction

The packet recommends "bounded selective-rescue policy keyed by
selected-leaf ambiguity/near-cap signals." I agree:

The Task 84/001 enriched data shows:
- 26 of 81 selected-leaf misses are within 0.01 score margin of cap
  (calibration-recoverable)
- 28 of 81 are in top-8 routes
- 55 of 81 are at margin worse than −0.01

A bounded selective rescue could target the ~26 near-margin misses
with a small extra block budget (e.g., +64 blocks per query) ONLY
for leaves with high score-margin ambiguity. Estimated cost: ~1-2%
candidate inflation for a potential +0.3pp recall. That's the kind
of policy that could fit inside the Task 79/81 latency envelope.

If even that doesn't move the 1M needle, the residual 55 below-margin
misses are likely format-bound (V5 / richer geometry per ADR-074),
which is a larger ticket.

entirely — could be incidental latency value even without recall
gain.

Next slice = bounded selective rescue per packet recommendation.
