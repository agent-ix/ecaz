# Task 84 packet 007 — paired k2/k3 latency control + scope reframe

## Decision

**Accept.** The paired same-suite control is exactly the right experiment
to test my packet 005 seq-01 hypothesis that the "k3 ~30ms p50 win" was a
warm-state artifact rather than a k3 effect. Result: **confirmed
warm-state artifact**. Warmed k2 (255.571ms p50) is essentially identical
to k3 (257.047ms) — k3 doesn't beat warmed k2.

Equally important: the packet **correctly reframes Task 84's goal** under
the user's actual clarification — latency improvement at the retained
recall point, not recall recovery. That changes how the Task 80-84 work
should be interpreted going forward.

## The paired control resolves the latency question cleanly

| row | order | p50 | p95 | p99 |
| --- | --- | ---: | ---: | ---: |
| k2 first (cold) | 1 | 274.607 ms | 340.723 ms | 354.243 ms |
| k3 | 2 | 257.047 ms | 319.000 ms | 336.771 ms |
| k2 route-prior 0.10 | 3 | 254.764 ms | 317.188 ms | 332.755 ms |
| k2 repeat (warm) | 4 | **255.571 ms** | **314.469 ms** | **331.985 ms** |

The order-controlled deltas tell the story:

- **Cold → warm gap**: k2 first → k2 repeat = **19.04 ms p50** (~6.9%).
  That's the warm-up effect alone.
- **k3 vs warm k2**: 257.047 vs 255.571 = **+1.48 ms p50** (k3 is
  *slightly slower*, well within noise).
- **Route-prior 0.10 vs warm k2**: 254.764 vs 255.571 = **−0.81 ms p50**
  (within noise, but p95/p99 worse for route-prior).

Conclusion: the "k3 wins by 30ms" finding from packet 005 was the warm
state of the retained k3 index being compared against cold or older-state
k2 baselines from packets 003/004/005. Same-suite paired control
eliminates the artifact.

## My packet 005 seq-01 prediction was correct — refined

I wrote:

The actual answer is more refined than "fresh build" — it's **warm cache

This is the right way to close that thread. Good methodology.

## Scope reframe — substantive course correction

> "improve AWS 1M/q500 latency while retaining the current recall point,
> not recover additional recall."

This recasts what Tasks 80-84 should have been optimizing. Under this
goal:

- **Recall-recovery work** (Tasks 80-84 packets 001-006) was solving
  the wrong problem. Useful as negative evidence for design space
  bounding, but not what the user was asking for.
- **The current warmed k2 baseline at ~255ms p50 / ~315ms p95 / ~332ms
  p99 / 9.21M cands / 0.9832 recall** is the operational reality.
  All four rows in this paired control land near that band.
- **None of the Task 84 mechanisms beats warmed k2** at the retained
  recall point. k3 = parity. Route-prior 0.10 = parity at p50, worse
  at p95/p99.

So the corrected Task 84 outcome is also "no clean latency lever found,"
but it's a different statement than packet 006's "no bounded recall
recovery." Both are honest negatives; they're answering different
questions.

## Non-blocking notes

1. **Future latency work standardization**: the packet correctly names
   this — "Future latency work needs standardized warmup and paired-order
   controls before claiming small deltas." That's a procedural finding
   worth recording in the Task 85 spec as a method requirement, not
   just an aspirational note.
2. **Cold/warm gap (~20ms p50) is operationally meaningful** — that's
   ~7% of latency, on the order of any optimization being tested. If
   user latency targets are tight, the cold-state penalty may itself
   be the most impactful axis to address (e.g., index pre-warming on
   startup, page-cache hint strategies, prefetch).
3. **The 1.48ms k3-vs-warm-k2 gap** (in k3's slightly-slower direction)
   is too small to be confident about, but if it's directional it's
   the small cost of computing max-IP over 3 reps vs 2. Worth noting
   as an operational data point for any future preset decision.
4. **The retained k=3 index is now confirmed non-useful** for either
   recall (Task 84/005) or latency (this packet) at the retained
   surface. Worth dropping it to save the +64 MB retained storage.

## Verdict

Accept. Clean methodology, decisive result, correct interpretation. The
paired control closes the "is k3 a latency optimization" question with
"no, it was warmup." The Task 84 scope reframe to latency-at-retained-
recall is the user's actual goal and changes how the prior work should
be read.

Net Task 84 latency outcome at AWS 1M / 0.9832 recall / 9.21M cands:
**warmed k2 at ~255ms p50 / ~315ms p95 / ~332ms p99 is the operational
floor**. No mechanism in Tasks 80-84 beat it. Cold-state penalty (~20ms
p50) is the largest single discoverable axis and probably the highest-
leverage Task 85 starting point.

Task 84 should be re-closed with this packet's data as the corrected
outcome record, alongside packet 006's "no recall recovery" closeout.
The two together establish the SPIRE 1M operational state cleanly:
0.9832 recall at warmed ~255ms p50, no parameter knob moves either
axis usefully, format/structural changes required to move further.
