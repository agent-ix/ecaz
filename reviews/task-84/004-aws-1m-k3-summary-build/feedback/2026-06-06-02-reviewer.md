## Answering the three review questions

### 1. Should relation-context loss after install/restart be handled as a Task 84 prerequisite?

**Yes, but as a tooling fix, not a Task 84 prerequisite.** The
`relation context could not be loaded` error is environmental — the
extension install/restart sequence on the retained AWS instance left
the catalog in a state where the distributed scan path couldn't load
its required relation context. This is the same family of pgrx-install
idempotency issue I've flagged across:

- Task 80 review (Task 80 packet 001's missing
  `ec_spire_index_scan_leaf_candidate_snapshot(oid, real[])`).
- Task 84 packet 001 review (the suite re-registers
  `ec_spire_index_scan_leaf_target_block_rank_snapshot` because some
  AWS instances had the older Task 83 shape).

The `07974586f` commit (`Allow multi-index SPIRE KNN reads through
DML frontdoor`, +92 LOC src) suggests the coder identified a related
multi-index path issue and patched it. That commit landed AFTER the
failed measurements in this packet, so the actual fix may already be
in place for the next run.

Treat as **resolved by the 07974586f patch + suite-runner output
fixes (aca92e28a, ba206bbf1)**, validate by re-running, and only file
a Task 84 prerequisite ticket if the next run hits the same wall
despite those patches.

### 2. Should the next run rebuild + query in one uninterrupted suite?

**Yes, strongly.** The current packet ran build in suite A, paused,
re-resumed, ran query in suite B, and the catalog state diverged
between them. That's the root cause of the relation-context failure
being even possible. Specifically:

- A single end-to-end suite is the cleanest reproduction surface.
- Pause/resume between build and measurement multiplies catalog
  drift risk.
- Using the latest CLI at run time avoids the "remote install drift"
  pattern.

Recommendation for the next packet: structure as one suite
`task84-aws-1m-k3-full-run-q500.json` with `[precheck, build, audit,
3× pipeline, pause]` in order, no inter-step install/restart, no
pause before the recall measurement.

### 3. Is the suite runner child-output change acceptable durable tooling?

**Yes.** Two small commits:

- `aca92e28a` (+14, -3 LOC): replays bench suite child output. The
  diff increases the captured-output surface so SSM remote runs
  preserve child step stdout/stderr for post-mortem.
- `ba206bbf1` (+1, -1 LOC): trivial fix — writes child errors to the
  suite log, not just to the child process log.

Both are durable observability improvements with negligible code
surface. No hot-path impact (suite runner is a control-plane CLI).
Accept as standing infrastructure.
