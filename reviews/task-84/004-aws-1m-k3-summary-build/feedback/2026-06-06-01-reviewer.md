## Three predictions to record before the run

So result interpretation is bounded by what the data shows:

1. **If k=3 at cap=1152 recovers recall ≥0.9890 at matched cands**:
   richer per-block geometry at 1M density is real and additive. This
   would clear the gate decisively and become the recommended
   operational preset for 1M. Likely close Task 84 with this as the
   accepted slice.
2. **If k=3 at cap=1152 recovers recall to 0.9850-0.9890 at matched
   cands**: partial win. The mechanism works but doesn't fully close
   the gap to the recall ceiling (0.9994). Worth keeping as a
   shippable preset and following up with a calibration slice on the
   remaining selected-leaf misses.
3. **If k=3 at cap=1152 stays at 0.9832 or worse**: matches the Task
   79 packet 043 + Task 84 packet 002 "richer signal didn't help"
   pattern. Close k>2 axis. The recall problem is then likely a
   summary *kind* problem (geometry vs density), not a *quantity*
   problem (more reps).

The 100k Task 79 packet 035 result (k=3 broke recall ceiling at 100k)
makes prediction 1 my central case, but the 1M shift from "summary
density signal" to "row density signal" means it's not certain.

## Concerns / non-blocking flags

1. **`cloud_upload_padding` fields in the suite config**: 9 of them,
   each ~500 bytes of repeated characters. The comment
   "force-s3-config-upload-to-avoid-ssm-heredoc-write-path" indicates
   an SSM heredoc workaround — this is a tooling defect dragging
   real configs around. Worth filing an ecaz-cli ticket for the
   underlying upload path, then dropping the padding. Not blocking
   this run.
2. **Build time at k=3** will be noticeably higher than k=2 (O(k×n)
   farthest-first seeding). At 1M with the existing block16 geometry
   that's ~3× the seeding inner loop. Estimate something like 25-40
   min for the build vs the retained k=2 ~28 min from Task 80
   manifest. Worth recording the actual build time in the closeout.
3. **No k=4 / k=5 control** in this packet. If k=3 delivers, a
   follow-up sweep over k ∈ {2,3,4,5} would let an operator pick
   the Pareto point. Don't pre-load it into this packet; just file
   it as the next slice if k=3 wins.
4. **target-block-rank + enriched-context outputs**: confirm both are
   enabled in the suite so the post-run can do the same per-miss
   attribution as packet 001. If they're not, the packet should add
   them before the AWS run.
5. **Comparator set**: should cite packet 001 (0.9832 baseline +
   enriched context), packet 002 (route-prior negative), Task 83
   packet 002 (blanket-cap controls), and Task 79 packet 035 (the
   100k k=3 win that motivated this path).
