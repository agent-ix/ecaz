# 112/002 — Benchmark: lazy heap-f32 rerank is inert (no win), as predicted

Evidence: `benchmarks/ivf-111g-115-attribution/` (FINDINGS.md, `head-lazy-ab`),
fixed `.so` 67e1534c, 100k coarse_rerank heap_f32 index, A/B via
`ec_ivf.lazy_heap_rerank` off vs on, sweep `[8,16,32,64,128,200]`.

## Measured

| | recall np64 / np200 | p50 np64 / np200 |
|---|---|---|
| lazy off | 0.9650 / 0.9985 | 6.95 / 12.9 ms |
| lazy on  | 0.9650 / 0.9985 | 6.84 / 12.8 ms |

Recall byte-identical and latency within noise → **lazy rerank fires no skips and
delivers no win**, exactly as the 112/113 analysis concluded: `NoBound` slack=+inf
+ `min_kept == rerank_width` (no k-cap) + the loose residual bound mean the stop
never triggers. The driver/gate/counters are correct infrastructure, but the P0
heap-fetch-reduction goal is **not realized**.

## Verdict

- 112 lazy is **infrastructure-only, recall-safe, no latency win** — do not claim
  the win. The 002/003 follow-ups (exact-score floor fix + k-cap) remain
  prerequisites, and per the 113 residual-bound analysis the eventual payoff is
  likely marginal (the residual bound is loose at 1-bit).
- Broader benchmark context: exact `heap_f32` rerank already reaches recall@10
  ≈0.999 at adequate nprobe, and **1-bit RaBitQ coarse + exact rerank is the
  efficient operating point** (smallest index, fastest scan, same recall). The
  heap-fetch-reduction lever 112 targets is real but small relative to that.
