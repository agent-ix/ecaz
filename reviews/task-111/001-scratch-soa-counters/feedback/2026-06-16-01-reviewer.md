## Verdict

LGTM. This is a clean, low-risk Phase 1 instrumentation slice that does not
touch the on-disk format. It correctly serves the Phase 1 goal of producing
evidence that row-posting decode/reshaping is material before changing the
durable page layout.

## What I verified

- `record_scratch_soa_flush` is invoked exactly once per non-empty
  `IvfPostingScratchSoa` drain in `process_scratch_soa_postings`
  (`scan.rs:1478`), before the batch scorer runs, and is guarded by the
  existing `scratch.is_empty()` early return. So an empty drain does not
  inflate the flush count.
- Byte accounting is sound: `scratch.payloads.len()` is already a byte buffer,
  and `heap_tids.len().saturating_mul(ITEM_POINTER_BYTES)` converts the TID
  count to bytes. `u32::try_from(...).unwrap_or(u32::MAX)` saturates rather
  than panicking on overflow, consistent with the other counters in this file.
- The three new `ExplainProperty` entries are wired and the array width was
  bumped `15 -> 18`; the equality/property-order test was updated with a fresh
  prime-numbered fixture so the renumbering is internally consistent.

## Minor notes (non-blocking)

1. The counters are cumulative across the whole scan, which is the right
   granularity for the Phase 1 audit. When you write the Phase 1 audit packet,
   please cite `Scratch Payload Bytes Copied` / `Scratch Heap TID Bytes Copied`
   **alongside** `Postings Scored` so the per-posting copy cost is legible — a
   raw byte total without the divisor is hard to compare across cells.
2. The Phase 1 stop-condition (close if decode/copy is not material at the
   target high-recall cells) is still open. The same-host audit that exercises
   these counters at the standard `ec_ivf` sweep is the gating evidence; this
   packet correctly stops before drawing that conclusion.
