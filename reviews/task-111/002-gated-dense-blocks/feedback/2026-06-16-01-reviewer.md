# Feedback: Task 111 Packet 002 — Gated Dense Posting Blocks

**Reviewer:** Claude (Opus 4.8)
**Date:** 2026-06-16
**Checkpoint reviewed:** `a82983bcac9d`

## Verdict

Solid Phase 2/3 slice. The codec is carefully bounds-checked, the layout is
self-describing via a new tag (so old indexes stay readable), the gate defaults
off, and dedup is correctly shared with the row path. I'm **not** blocking the
checkpoint, but there is **one correctness gap that must be closed or
explicitly fenced before this gate is used under any churn**, plus a perf gap
that undercuts the task's own thesis and several test gaps that are the real
acceptance gating items. Details below.

## Must address before churn / promotion

### 1. Dense blocks have no delete/visibility handling — the gate is currently unsafe under DELETE (MAJOR)

The row path filters on `posting.deleted`
(`scan.rs:1331`, `scan.rs:1399`). The dense-block path has **no equivalent**:
`IvfDensePostingBlockTuple` carries no per-posting live/dead state and no
live/dead bitmap (the candidate layout in the task file listed one as
"if needed" — it is needed). After a gated build, a `DELETE` of a heap row
whose posting lives inside a dense block cannot be reflected: vacuum/delete
marks `POSTING_FLAG_DELETED` on row postings, and there is no path to mark a
row dead inside a frozen block. `insert.rs` correctly forces
`dense_posting_blocks: false` for the mutable path, so new tuples land in row
postings — but the **already-frozen** rows in dense blocks are the exposure.

Please confirm which of these is true and act accordingly:

- **If IVF correctness depends on the in-index `deleted` flag** (i.e. a
  returned candidate TID is trusted without a heap MVCC recheck that drops
  dead/invisible tuples), then gated dense scans return deleted rows — a
  wrong-results bug, and acceptance criterion #4 ("same candidates as the
  legacy path") fails for the delete case.
- **If correctness relies on heap visibility recheck at fetch/rerank time**,
  results are still correct, but dead rows consume candidate-budget and top-k
  slots, so this is a silent **recall dilution** under churn that your Phase 5
  benchmark (built clean, no deletes) will not catch.

Either way, this slice should not be promotable while the behavior is
undocumented. Minimum acceptable for now: state the contract explicitly in the
reloption help text and packet, and add a focused test that builds with the
gate on, deletes a row that is inside a dense block, and asserts the deleted
row is not emitted (or is provably filtered downstream). You already list this
under "Known Remaining Work" — I'm raising it from a note to a gating item
because the reloption is live and a user can hit it today with no warning.

## Should address (perf — this is the task's core thesis)

### 2. The dense scan still re-materializes `gamma[]` (and a fresh `scores`) per block

`process_dense_posting_block` calls `block.gammas()` (`scan.rs:1646`), which
allocates a `Vec<f32>` and byte-decodes every gamma per block visit, and
`let mut scores = Vec::new()` allocates per call. The whole point of Task 111
(task file lines 78-81: "pass `gamma[]` and `payloads[]` directly to the batch
scorer without first reconstructing equivalent vectors in scratch") is to
remove exactly this reshaping. `payloads` is passed through zero-copy (good),
but `gamma[]` is reconstructed — so the dense path trades the row scratch copy
for a per-block gamma alloc. On a little-endian target the stored `gamma_bytes`
are already `f32` LE and could be borrowed (e.g. a checked
`bytemuck`/`align_to` cast) and passed as `&[f32]`; `scores` could be a reused
buffer hung off the scan opaque. This won't change correctness but it directly
affects whether Phase 5 shows the latency win the task exists to produce.
Worth fixing before the benchmark gate so the measurement reflects the intended
layout, not a half-reshaped one.

## Looks correct — verified

- **Codec bounds checks.** `IvfDensePostingBlockRef::decode` validates tag,
  exact total length (`input.len() != payload_end`), and stored-vs-expected
  `payload_len`. `validate_offsets` checks every heap-tid range against
  `total_heap_tids` and decodes each rerank TID. Both scan entry paths
  (`visit_all_ivf_posting_entries_from_buffer`, pg18 read-stream and the
  non-pg18 per-block path route through it) call `validate_offsets()` before
  `heap_tids(index)` slices, so the `heap_tid_bytes[..]` slicing cannot panic
  on a malformed frozen block.
- **Old-index compatibility (acceptance #2).** New `IVF_DENSE_POSTING_BLOCK_TAG
  = 0x25` is only written when the gate is on; the scan dispatches on the tag
  byte and treats unknown tags as a no-op, so existing row-only indexes are
  untouched and still readable.
- **Dedup / mixed scan (acceptance #4, partial).** Both row and dense
  candidates funnel through the shared `best_by_heap_tid` map, so a heap TID
  appearing in both a frozen block and a row/delta posting is deduplicated.
  Mixed visitation within one block range is handled by
  `IvfPostingEntryRef::{Row,DenseBlock}`.
- **Counter design.** `record_row_posting_visited` and
  `record_dense_posting_visited` both delegate to `record_posting_visited`, so
  the legacy `Postings Visited` total is preserved (= row + dense) while the new
  breakdown counters are additive. No regression for existing EXPLAIN/bench
  consumers.
- **Build writer.** `posting_count()` was correctly repointed to
  `directory_entries[].live_count` (since `posting_tids_by_list` now holds block
  TIDs, not posting TIDs, under the gate); `live_count` is set from
  `tuple_indices.len()` independently of block packing. Page-fit is checked with
  `dense_posting_block_tuple_fits(pending.len()+1, pending.len()+1, ...)` before
  the new posting is added, so each emitted block fits a page.

## Minor / follow-up

3. **Batch-scorer `||` chaining contract.** `scored_batch` relies on each
   `score_*_batch_from_payloads` being all-or-nothing into the shared `scores`
   buffer (a false-returning scorer must push nothing). The
   `scores.len() != block.len()` guard catches gross mismatches, but the
   invariant is implicit. It mirrors the existing scratch path so it's an
   established convention — just calling it out as a sharp edge if a future
   scorer partially fills before bailing.
4. **Single-posting-too-large edge.** If one posting's encoded size alone
   exceeds a usable page, the build loop never flushes (the `!pending.is_empty()`
   fit-check guard is false on the first element) and the final `encode` ->
   `insert_raw_tuple` will error. This also fails in the row format, so it's not
   a regression, but a clearer up-front error would help debugging.
5. **Task 42 coordination.** Tag `0x25` is a new durable on-disk element. The
   task file calls for coordinating with Task 42 (on-disk-format invariants) if
   a new format version is introduced. Please confirm Task 42's invariant set /
   format-version doc is updated to know about the dense-block tag before
   promotion.
