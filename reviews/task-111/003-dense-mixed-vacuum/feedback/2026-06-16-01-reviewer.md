## Verdict

This resolves the MAJOR delete-safety finding from packet 002 and closes the
two test gaps I flagged there. The deleted-bitmap design is clean, the vacuum

requires, and the new PG18 fixtures actually exercise the scan + vacuum paths

## How this answers prior feedback

- **Delete safety (was MAJOR, packet 002 #1):** A fixed-size deleted bitmap is
  now part of the dense block (`(count+7)/8` bytes, placed between header and
  `gamma[]`), the scan skips deleted entries in both the batch and scalar
  fallback loops (`scan.rs:1685`, `scan.rs:1707`), and vacuum marks dead
  entries in place. The "scan returns deleted rows" exposure is gone.
- **Test gaps (was AC#3/#4):** PG18 fixtures now cover gated dense build scan,
  mixed dense+row-insert scan, and vacuum removal of a build-time dense
  posting — with `debug_ec_ivf_gettuple_counter_snapshot` asserting the scan
  actually traversed dense blocks (`dense_blocks_visited`/`dense_postings_visited`)
  rather than silently falling back to row postings. That counter assertion is
  exactly the right way to keep these tests honest.

## Verified correct

- **Bitmap bounds.** `dense_deleted_bitmap_get` uses `.get(...).is_some_and(...)`
  and `_set` uses `.get_mut(...)`, so an out-of-range index is a safe no-op /
  `false` rather than a panic. `encode` validates
  `deleted_bitmap.len() == dense_deleted_bitmap_len(count)`, and `Ref::decode`
  derives the bitmap slice from `count` and only constructs the struct after the
  exact-total-length check (`input.len() != payload_end`), so all sub-slices
  remain in bounds.
- **Vacuum size invariant.** The bitmap is fixed-size regardless of how many
  bits are set, so a `Rewrite` re-encodes to the same byte length; the
  `encoded.len() != tuple_bytes.len()` guard in
  `rewrite_ivf_postings_from_exclusive_buffer` therefore holds for dense blocks
  exactly as for row postings. Marking deleted does not move line pointers.
- **Vacuum dead-detection.** `bulkdelete_dense_posting_block` only marks an
  entry deleted when *all* its heap TIDs are dead, with checked
  `start/count/end` arithmetic and a bounds-checked `heap_tids.get(start..end)`.
  For the single-heap-TID build path this is exactly right, and it is
  idempotent on re-vacuum (already-deleted entries are skipped, `changed`
  stays false → `Keep`).
- **Accounting.** `removed_heap_tids` and `record_live_posting` feed the same
  `ListBulkDeleteResult` as the row path (via a `RefCell` shared between the two
  closures), and the vacuum fixture confirms `directory_live = 2`,
  `directory_dead = 1`, `tuples_removed = 1`, `num_index_tuples = 2` —
  i.e. the directory live/dead bookkeeping is consistent after a dense delete.

## Notes / follow-ups (non-blocking)

1. **Format versioning heads-up (please record).** The bitmap was inserted into
   the dense-block layout *without* bumping the tag (still
   `IVF_DENSE_POSTING_BLOCK_TAG = 0x25`). A dense index built at packet 002
   (`a82983bca`) will now fail to decode (length mismatch), since the reader
   expects the extra bitmap bytes. This is harmless because the format is
   experimental, gated, and default-off — no released or real index exists — but
   any dev/test index built during the 002 window must be rebuilt. Worth a line
   in the manifest, and worth confirming the Task 42 on-disk-format invariant
   set is updated to describe the *current* 0x25 layout before promotion.
2. **All-dead block reclamation.** When every entry in a block becomes dead, the
   block is bitmap-marked but the tuple/page is not freed. That's correct for
   "minimum lifecycle handling" and Task 114 owns repack/density, so this is
   expected — just flagging that space is not reclaimed, only logically hidden.
3. **Legacy-equivalence assertion (test strength).** The fixtures assert
   completeness (all live rows returned) and exclusion (deleted TID absent),
   which is solid. To nail AC#4 ("same candidates as the legacy path") even
   harder, consider a variant that builds the identical fixture with
   `dense_posting_blocks = 0` and diffs the output id/score set against the
   dense build. Optional, but it would convert "looks complete" into "provably
   identical."

The perf/allocation gap from packet 002 (#2, per-block `gamma[]` reconstruction)
is out of scope for this packet and is being carried forward — see packet 004 /
005. Leaving this request open.
