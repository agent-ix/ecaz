# Feedback: Task 111 Packet 005 — Dense Scan Scratch Buffers

**Reviewer:** Claude (Opus 4.8)
**Date:** 2026-06-16
**Checkpoint reviewed:** `5e9e9fecb00`

## Verdict

LGTM. This closes the per-block allocation gap I raised in packet 002 (#2): the
dense scan no longer allocates a fresh `gamma[]` and `scores` Vec for every
block. The implementation mirrors the existing `IvfPostingScratchSoa`
lifecycle, the `unsafe` is correctly scoped and documented, and the unit test
demonstrates capacity reuse. No code changes requested.

## Verified correct

- **Lifecycle parity.** `IvfDensePostingBlockScratch` is scan-opaque-owned,
  lazily allocated via `dense_posting_block_scratch()`, and freed in
  `ec_ivf_amendscan` via `free_dense_posting_block_scratch` — same
  `Box::into_raw` / `Box::from_raw` pattern as the SoA scratch, so it slots into
  the existing scan teardown without a new leak path. The `std::mem::replace`
  to null before `Box::from_raw` is the right double-free guard.
- **Buffer reuse.** `dense_posting_block_scratch()` calls `clear()` on reuse
  (length reset, capacity retained), and `load_gammas` refills gammas + clears
  scores. The new `copy_gammas_to` does `clear(); reserve(count); extend(...)`,
  so a steady-state scan reuses one allocation across all blocks. The unit test
  `dense_posting_block_scratch_reuses_gamma_and_score_capacity` proves
  capacity is preserved across a larger→smaller reload and that scores are
  cleared — exactly the regression guard this needs.
- **`unsafe` soundness.** The raw `scratch` pointer addresses a *separate heap
  Box*, disjoint from the `EcIvfScanOpaque` struct itself, so reading through
  `(*scratch)` while `record_scored_posting_candidates` reborrows
  `opaque: &mut` does not alias — the two allocations are independent and the
  candidate-recording path never re-enters `dense_posting_block_scratch` or
  touches the `dense_posting_block_scratch` field during the loop. The
  all-or-nothing `||` batch-scorer contract and the
  `score_count != block.len()` guard are preserved.
- **Behavior unchanged.** The scalar fallback now indexes
  `(*scratch).gammas[index]` instead of an owned `gammas` Vec; the
  `is_deleted`, live-tid-budget, and min-bound-prune logic are all intact.

## Note (non-blocking)

1. **Residual copy vs true zero-copy.** Gammas are still *decoded/copied* into
   the reused buffer rather than borrowed directly from the page bytes. That's a
   reasonable call — it eliminates the allocation (the dominant cost) while
   keeping the portable little-endian decode and avoiding the alignment / LE-only
   assumptions a `bytemuck`-style zero-copy `&[f32]` cast would introduce. The
   remaining O(count) decode is cheap relative to scoring. If Phase 5 numbers
   show gamma handling is still hot, a borrowed-slice fast path on aligned LE
   pages is the next lever, but I would not pursue it speculatively.
