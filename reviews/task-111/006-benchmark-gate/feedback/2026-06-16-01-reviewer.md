## Root cause — confirmed and worth stating precisely

The TQ regression is not noise; it is a structural consequence of the
one-page-per-block design interacting with payload size:

- TQ dense: **4233 blocks / 42171 postings ≈ 10 postings/block.**
- RB1 dense: **1189 blocks / 42171 postings ≈ 35 postings/block.**

`process_dense_posting_block` scores exactly one block's postings per batch
call, so the achievable SIMD width is bounded by postings-per-block. TQ's larger
payload (≈3.5× RB1's index bytes) means fewer postings fit per page, so TQ dense
batches at width ~10 (below the width-32 sweet spot) and never reaches
`width_ge32`, while RB1 dense clears 32 and wins. The row path sidesteps this
because its scratch-SoA accumulator batches *across* blocks up to
`IVF_POSTING_SCRATCH_SOA_BATCH_POSTINGS`, so it stays at width≥32 for both
formats. The packet's proposed next slice — dense-block packing / scan-side
coalescing to feed the scorer wider batches — targets exactly this mechanism.
Good diagnosis.

## Evidence-scope caveats (do not block the iterate verdict; would block a future promote)

1. **100k only, no 1M.** Phase 5 asked for "real 100k and 1M where available";
   the manifest documents that no local 1M corpus manifest was present, so this
   is 100k-only. For a *don't-promote* decision this is sufficient — a clear p50
   regression at 100k won't reverse at 1M. But any later promotion attempt must
   add 1M and the AWS lanes per the all-benches rule before the default moves.
2. **nprobe sweep [16, 32], not the registered `ec_ivf` default [8,16,24,32,48,64].**
   A bespoke config is justified here (the canonical lane configs have no
   dense-vs-row dimension), and the manifest states the cells — but it does not
   explicitly justify the *narrower nprobe grid* vs the registered default. Two
   cells suffice to establish the regression and the iterate call; just flag in
   the manifest *why* the grid is subset so a future reader doesn't read it as
   the standard sweep. If promotion is ever reconsidered, run the full
   default_sweep so the regression's nprobe-dependence is visible.
3. **Storage number labeling (minor).** The summary index sizes (TQ 87.6/78.9,
   RB1 29.7/22.5 MiB) are the ec_ivf index in isolation; the raw `storage-*`
   `indexes` field is ~2.1 MiB higher (89.7/81.0, 31.8/24.6) because it includes
   the per-table PK btree. The storage *win* is identical under both readings
   (dense ≈ −8.7 MiB TQ, −7.2 MiB RB1), but the packet should say which figure
   it's quoting so the two don't look inconsistent.
