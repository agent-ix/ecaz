## Caveat 1 — debug helpers unavailable on release build

The scaffold (packet 001) called
`tests.ec_hnsw_debug_last_build_timing()` and
`tests.ec_hnsw_debug_parallel_graph_build_workers_launched()`. The
release-installed extension doesn't expose those `pgrx-test`-only
helpers, so the executed SQL substitutes:

- wall-clock timing via `\timing on`
- `pg_stat_get_db_parallel_workers_launched(current database)`
  before/after each `CREATE INDEX`

The PG counter stayed `0` for all four builds, so launched
graph-worker count is **not proven** by this packet. The packet
notes this explicitly — good.

This is a real instrumentation gap for Task 33 Phase 1, but not a
blocker for the refresh's findings:

- Build wall time is captured directly (the load-bearing number).
- Index size is invariant across worker counts.
- The `pg_stat_get_db_parallel_workers_launched` counter not
  ticking probably means `ec_hnsw` parallel build doesn't register
  as a PG parallel workgroup in `pg_stat_database` — worth an
  audit. Likely the workers are spawned via `ec_hnsw`'s own
  `RegisterDynamicBackgroundWorker` path rather than via the
  `ParallelContext` machinery that `pg_stat_get_db_parallel_workers_launched`
  reports on. If so, the counter is genuinely the wrong probe, not
  evidence of zero workers.

**Recommendation for Phase 2** (not blocking this packet): either
publish a release-build-safe equivalent of the debug helpers (e.g.
expose a stable SQL function gated on a server GUC), or rely on
`select count(*) from pg_stat_activity where backend_type='client backend'`
sampled during the build for empirical worker-launch evidence. Don't
gate ADR-073 prototype work on closing this instrumentation gap.

## Caveat 2 — Memory HWM is `not_measured`

The packet's caveat matches my packet 001 feedback prediction:
build-time memory HWM was not captured (raw SQL step doesn't sample
backend RSS). Additionally, the `kind=latency` step's
`memory_samples=0, hwm_peak_kb=0, rss_peak_kb=0` rows show the
latency-side sampler didn't fire either.

This is a real Phase 1 gap from the plan ("memory HWM" is listed in
§Phase 1). It does not block the Phase 2 decision because:

- Build wall time scales as expected at the worker counts;
- Index size is captured (proxy for graph memory footprint);
- The Phase 2 ADR (offline/staged build) is justified by build-time
  + recall evidence, not memory HWM.

For the run packet's own narrative, record memory HWM as
`not_measured` in the summary (which the packet does in the caveats
section but not in `results.jsonl`). The recall and latency rows in
`results.jsonl` carry `hwm_peak_kb: "0"` — change those to
`"not_measured"` or strip the column to avoid a downstream consumer
publishing "0 KB" as a real claim. Same precedent as Task 32 packet
002.
