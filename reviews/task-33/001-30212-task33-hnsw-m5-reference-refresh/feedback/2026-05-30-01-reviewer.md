## Note 1 — Build-time memory HWM is not captured

The suite defaults set `sample_backend_memory: true` /
`memory_sample_interval_ms: 25`, but those only apply to first-class
`bench` step kinds (recall/latency/storage). The worker-sweep step is
`kind: raw` — `ecaz dev sql` does not sample backend RSS. So the four
build invocations will produce build wall time, phase timing, worker
launch count, and index size, but **no memory HWM**.

The Task 33 plan §Phase 1 explicitly lists memory HWM as required.
Options for the follow-up run packet:

1. Wrap each `CREATE INDEX` in a background memory sampler — e.g.
   spawn `ps -o rss,vsz -p <postmaster_pid>` once per second from a
   shell wrapper around `ecaz dev sql`, capture to a per-worker log
   under `artifacts/`. Cheapest fix.
2. Add a first-class `kind: build-sweep` step to `ecaz bench suite`
   that does the GUC/table-option matrix natively and reuses the
   bench backend-memory sampler. Larger change; this is what the
   request.md flags as the alternative.

For a Phase 1 reference refresh, option 1 is fine — Task 33 doesn't
need product-quality memory observability, just enough to compare
across worker counts. Option 2 belongs in a separate suite-runner
task if the team wants it durable.

The follow-up packet should not silently drop memory HWM from the
captured fields — record it as `not_measured` if option 1 isn't
done, mirroring the Task 32 packet 002 precedent
(`memory_hwm_kb: "not_measured"` in `results.jsonl`).

## Note 2 — Single-index selection for recall/latency/storage

The SQL renames `task33_m5_hnsw_real50k_w4_idx` to
`task33_m5_hnsw_real50k_m16_idx` and the follow-on `kind=recall` /
`kind=latency` / `kind=storage` steps run against that single index.
So recall/latency are measured only at `workers=4`, not across the
1/2/4/8 sweep.

This is the right call for a "reference refresh" — Task 26's prior
best point was at four workers, so a single-index follow-on matches
that surface — but call it out in the run packet's manifest:

> Recall, latency, and storage are measured against the `workers=4`
> build, matching Task 26's best point. The 1/2/8 builds contribute
> only build-time, phase-timing, worker-launch, and index-size
> evidence; their query-time characteristics are not measured.

If a later packet wants the four-way recall/latency comparison,
that's a separate run — but the Phase 1 requirement doesn't insist
on it.

Task 33 plan §Stop Conditions says:

Flagging now so the run packet's reviewer (which may be me again)
has the criterion pinned to packet artifacts rather than relying on

## Two minor SQL nits — not blocking

1. The load step at the top of the suite builds an index
   (`task33_m5_hnsw_real50k_m16_idx`) which the sweep SQL then
   drops immediately. That's an extra ~build wall time (one full
   `CREATE INDEX` on real50K) before the sweep starts. Could be
   avoided by passing a "no index" or "skip index" flag to the load
   step if `ecaz bench suite` `kind: load` supports it. Marginal —
   not worth blocking on.
2. The final `\echo === select best worker index ===` block does
   `DROP INDEX IF EXISTS task33_m5_hnsw_real50k_m16_idx;` then
   `ALTER INDEX ... w4_idx RENAME TO m16_idx`. If the rename ever
   fails (e.g., the w4 build silently produced no index), the
   follow-on recall/latency/storage steps will fail on a missing
   relation. Consider asserting `pg_relation_size('...w4_idx') > 0`
   before the rename to fail fast with a clearer error. Optional.
