## ADR-073 review

### Context section

Correctly cites:

- ADR-042 (native HNSW builder as production path) and ADR-048
  (concurrent DSM as default parallel build);
- packets 002 + 003 as the Task 33 evidence;
- Task 33 §Stop Conditions as the trigger to pick a Phase 2 lane.

The bullet list at lines 24–32 accurately summarises the two
packets' findings: through-`w4` gains, `w8` regression, release-build
debug-helper gap.

### Decision section

> Move HNSW follow-up from worker-threshold tuning to a
> **staged/offline bulk build lane**.

Matches Task 33 plan §Phase 2 option "Offline/staged bulk build".
Two-stage architecture (offline build → PG validate + publish) is
the right shape and consistent with ADR-046's push model.

Key clause: "The current ADR-048 concurrent DSM path remains the
in-PostgreSQL default until the staged path has a validated artifact
contract and benchmark packets. This ADR does not remove ADR-048."
This is the correct preserve-fallback discipline.

### Requirements section

The six bullets (artifact identity / row identity / validation /
publish lifecycle / fallback / quality gate) cover the surface a
staged builder needs. Specifically good:

- **Artifact identity** includes builder version + corpus hash —
  prevents stale-artifact accidents.
- **Row identity** explicitly calls out heap-TID mapping vs
  source-identity resolution at publish — the load-bearing
  correctness question for any offline build.
- **Validation** lists page-format invariants, neighbor slot bounds,
  entry point, layer metadata, duplicate handling, checksum
  coverage. This is the contract that gates any future "stage and
  publish" prototype.
- **Quality gate**: recall must be measured against the
  in-PostgreSQL builder on the same corpus. Correctly preserves the
  Task 33 plan's 0.5 pp recall-floor clause as a hard prerequisite.

### Non-Goals section

Explicitly excludes:

- live insert / vacuum repair (correct — staged build is bulk-only),
- GPU dependency in the PG backend (correct — keeps the seam),
- on-disk `ec_hnsw` page format changes (correct — separate ADR if
  needed),
- more ADR-048 worker-count tuning (correct per stop condition).

Clean Non-Goals list. Doesn't try to do too much.

### Consequences

Positive bullets accurately describe the architectural payoff.
Negative bullets honestly call out that this ADR does **not**
immediately improve `CREATE INDEX USING ec_hnsw` — that's the
realistic tradeoff for a design-lane decision, and the ADR doesn't
oversell.

### Follow-Up Work

Four items:

1. Draft staged artifact schema + publish/validation lifecycle.
2. Add a narrow CPU-only prototype that emits + validates a small
   staged artifact (no query-path change).
3. Benchmark staged vs ADR-048 on the same 50K/100K surfaces.
4. Decide on documented recommendation only after #3.

This is the right ordering — schema → prototype → benchmark →
decide. Items #1 and #2 are concrete enough to open packets against.

## One note — status field

ADR-073 frontmatter says `status: PROPOSED`. That's correct for the
content (a design lane decision, not an implementation commitment).
But the ADR's "this is the direction" stance is stronger than
typical `PROPOSED` ADRs that haven't yet had review. Two options:

1. Keep `PROPOSED` and treat this reviewer feedback as the first
   review pass; promote to `ACCEPTED` once a prototype packet (#2
   above) lands. This is the cleanest path.
2. Promote to `ACCEPTED` now, treating packets 002 + 003 + this
   review as sufficient acceptance evidence.

I'd recommend option 1 — keep `PROPOSED` until prototype evidence
exists. The ADR is *not* committing to remove ADR-048 or to ship a
staged builder; it's committing to the next design step. That
matches `PROPOSED` semantics better.
