# Review addendum — Task 123 verdict is single-INSTANCE; the contained multi-node lane is the correct efficiency instrument and was not used

Raising a material scope limitation the prior sign-offs under-weighted.
**The scan-path no-go should be treated as a single-instance result, not the
program's multi-node efficiency verdict, until it is re-measured on the contained
local multi-instance lane.**

## What was actually measured

Every recall/latency/scan-cost run behind both the Task 121 and Task 123 verdicts
ran on a **single PostgreSQL instance**:

- Task 121 Phase 1/2/3 manifests: "Isolation: local single PostgreSQL instance";
  packet 016 states outright it is "not the local multi-node Phase 0 lane."
- Task 123 Phase A/B reused those single-instance `b4/tr50/f8` surfaces.

The contained **local multi-instance lane** (coordinator + N worker PG instances
on one host) built in Task 121 **Phase 0** (packets 002-006) — whose entire
purpose was cheap pre-AWS distributed measurement — was **smoke-tested only**. It
never carried the DOE, the Phase A latency gate, or any scan-cost run.

## Why the multi-instance lane is the right instrument here (and why single-instance distorts the cost verdict)

- **Recall / route containment is topology-independent** — same vectors, same
  routing, `route-containment == final recall` regardless of leaf placement. The
  recall findings transfer; they are valid. ✅
- **The cost verdict is not transferable from single-instance.** The whole basis
  of 123's no-go ("flat exact dominates," "the binding wall is the scan/candidate
  path") is a latency/cost claim, and it was taken on the single-instance code
  path, which does not faithfully exercise SPIRE's distributed executor
  (coordinator-routed scan, remote leaf materialization, tuple transport).
- **Same-machine multi-instance has ~0 network RTT.** So it is not a
  "parallelism vs network" tradeoff — it is a *clean* efficiency substrate: it
  runs the real distributed path with the network term removed, leaving the
  per-stage engine costs (leaf-read, tuple materialize/encode, candidate-score,
  heap-append) as genuine, attributable, **improvable** work rather than artifacts
  of a degenerate local shortcut.
- One nuance, not a contradiction: same-machine still incurs the tuple
  **serialization/materialization CPU** cost across the libpq boundary (the
  hex-text vs typed `bytea[]` / projection-width issue that
  `121-spire-distributed-read-transport-efficiency` targets). That cost is real
  and is itself one of the prime optimization surfaces — so "transport latency is
  near zero" applies to the network hop, while the encode/materialize path
  remains both measurable here and a thing to improve.

Net: we can get the data we need cheaply — recall is already in hand and
topology-safe; the contained multi-instance lane yields the efficiency numbers
the program is actually about, with the residual per-stage cost being the
improvement target.
