# Review — Task 123 prune rehome + bench tooling (packets 014/015/016)

**Verdict: tooling/code is sound, but STOP before running the 017 prune A/B as
planned — the rehomed prune is structurally inert for every candidate config this
task carries. Verified in code.**

## Blocking finding: the prune never fires for boundary_replica_count > 0

The rehomed prune only engages when `dedupe_mode == NoReplicaDedupeDisabled`
(`pre_materialization_min_ip_to_keep` returns `None` otherwise). And the scan plan
sets dedupe mode by boundary replication (`src/am/ec_spire/options/mod.rs`):

```rust
dedupe_mode: if options.boundary_replica_count > 0 {
    SpireCandidateDedupeMode::VecIdDedupeEnabled      // -> prune DISABLED
} else {
    SpireCandidateDedupeMode::NoReplicaDedupeDisabled // -> prune enabled
}
```

So **any `boundary_replica_count > 0` disables the prune.** The task's carried
candidates are `n1024 b2` (boundary=2) and `n128 b4` (boundary=4) — both have
boundary > 0, so the prune is a **no-op for both**. It only does anything at
`b0`, which is not a recall candidate (b0 recall is too low).

Consequence: a `ec_spire.pre_materialization_prune` on/off A/B on `n1024 b2`
(the apparent plan for packet 017) will show **zero difference** — and on this
disk-constrained host that's a multi-hour run spent measuring a guard that
short-circuits to `None`. Do not run it as-is. (This is the engagement question I
flagged on PR #43; it's now confirmed in code, not hypothetical.)

## What's actually needed for the prune to matter

Pick one, before spending a run:

1. **Make the prune recall-safe under `VecIdDedupeEnabled`** (the real fix) so it
   engages for the b2/b4 candidates. This is the non-trivial part: under replica
   dedupe, a candidate below the current keep threshold can still be the surviving
   member of a dedupe group, so skipping its materialization on the approximate
   score must be proven not to drop a true positive. That correctness argument +
   a recall A/B is the work — and it's where a real communications win for the
   actual candidate would come from.
2. **Or scope the prune A/B to a `b0` variant explicitly**, and state plainly that
   the result does NOT transfer to the b2/b4 candidates (prune disabled there).
   Useful as a mechanism datapoint, not as a candidate win.

Either is fine — but the packet must not present a b0 prune result as if it helps
the b2/b4 candidate, and must not run prune on/off on b2 expecting signal.
