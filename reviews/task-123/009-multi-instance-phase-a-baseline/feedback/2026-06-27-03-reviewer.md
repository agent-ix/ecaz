## Gap 1 — per-node payload bytes are still `id`-only (communications unmeasured)

The per-node timeline reports, for every worker, `payload_bytes / payload_rows =
2560 / 320 = 8 bytes/row` (e.g. n1024-b2 np8: node2 320 rows/2560 B, node3 310/2480,
node4 300/2400). 8 B/row is a bare `bigint` id — the suite is still projecting
`id` only. So `payload_decode_p50 = 0.000 ms` and the "communications" column is
measuring id transport, not the real object/vector payload that dominates
distributed cost. This is exactly the gap flagged in
`reviews/task-123/010-.../feedback/2026-06-27-01`: **re-run with a realistic
projection** (the payload/vector width a production read ships) so the per-worker
byte counters report true transport cost. As-is, the headline efficiency
dimension is still unmeasured.

## Gap 2 — still 32 queries

Both cells are `--bench-queries-limit 32`. The 009 feedback (seq-01) asked for
**≥200 queries** before any multi-instance cost verdict — a result that reverses
the single-instance no-go needs at least the sample size of the verdict it
overturns. 32q recall/latency remains a directional signal, not decision-grade.
