# Coordination review — fold PR #43 `pre_materialization_prune` into the Task 123 multi-instance efficiency line

This is a cross-task handoff note for the Task 123 SPIRE owner, not feedback on
the 009 run itself (see seq-01 for that). **PR #43 contains a ready-made lever for
the latency path that this packet's own data says matters, and it was measured on
the wrong substrate — evaluate it on the multi-instance lane before building
anything equivalent from scratch.**

## What PR #43 is

PR #43 ("Draft: SPIRE materialization prune handoff from Task 122",
branch `task-122-spire-handoff`) is SPIRE work the TurboQuant (Task 122) agent
did before TQ closed out TQ-only in PR #42. The code is small and focused (49
lines in `src/am/ec_spire/`):

- new `ec_spire.pre_materialization_prune` GUC (default **on**);
- in the candidate scoring loop (`scan/candidates.rs`), after the cheap quantized
  `ip` score but **before materializing the row**, skip the candidate if `ip` is
  already below the running top-k keep threshold (`pre_materialization_min_ip_to_keep`).

Guards (sound): only when replica-dedupe is disabled
(`NoReplicaDedupeDisabled`), only with a bounded candidate limit, and skipped when
deletions are present; truncations are recorded via the observer.

## Why it belongs here, and why its own A/B undersells it

The prune attacks **materialization** — which on a single instance is a local row
read, but on the multi-instance lane is exactly what becomes a **shipped tuple
(object bytes across libpq)**, i.e. the "communications" cost the amended Task 123
targets and the dominant stage in this 009 baseline.

PR #43's A/B (packet `reviews/task-122/004-spire-prune-ab-suite`) measured it
**single-instance**:

- recall neutral: `1.0000` prune on and off;
- materialized candidates `251,555 → 8,495` (~30× fewer);
- latency ~flat: p50 `92.4` vs `93.8 ms`.

So single-instance it looks marginal (local materialization is cheap, ~1.5%).
**That is the same single-instance-substrate error we already corrected once.** A
~30× cut in materialized candidates should translate, on the multi-instance lane,
into ~30× fewer tuples serialized/shipped per worker — a large communications/
latency win that the single-instance A/B cannot show. This is likely one of the
biggest latency levers available to the route-efficient `n1024 b2` candidate.
