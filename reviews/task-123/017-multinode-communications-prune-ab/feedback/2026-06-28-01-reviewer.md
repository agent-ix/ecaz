## What the run shows (n128-b4 / n1024-b2, 200q, np96)

Matrix: `{projection id, id+source} × {prune off, on}`. From the committed
`n128-b4-200q/bench-suite/results.jsonl`:

- prune **on vs off**: 5524 vs 5509 ms (source), 5472 vs 5690 ms (id) — **no
  effect**, both candidates.
- projection **source vs id**: ~5500 ms either way — **no latency difference**,
  despite source shipping the full ~12 KB payload vs ~8 B.
- recall 1.0000 across all arms; latency ~5500 ms at np96.

## 1. The prune arm is a confirmed no-op (matches my packet-014 finding)

The prune only engages for `NoReplicaDedupeDisabled`, and dedupe mode is
`boundary_replica_count > 0 → VecIdDedupeEnabled`. Both candidates are boundary>0
(b2/b4), so the prune never fires — and the data confirms it (on==off). The
prune-on/off arms are dead weight for b2/b4. To make the prune meaningful you must
either make it recall-safe under `VecIdDedupeEnabled`, or A/B it at b0 and state
it does not transfer to the candidates. As run, half the matrix measures nothing.

## 2. Projection cap fixed — credit

You raised `ec_spire.max_remote_payload_bytes_per_row` 1024 → 16384, and the
`id,source` path now runs with **zero** `remote_payload_too_large` errors. That
closes the projection-failure blocker from packet 013. Good.

## 3. The real signal: transport bytes are NOT the latency driver

source (full ~12 KB/candidate) vs id (~8 B) is latency-flat (~5500 ms). If the
payload genuinely shipped (the raised cap implies it did — confirm via the
per-node `payload_bytes_sum` in the timeline rows, which the summary
`results.jsonl` leaves null), then **communications/transport is not where the
cost is at this scale** — it's scan / candidate-scoring / heap. That reframes the
reopened latency path: the win, if any, is in the scan/score stages, not in
shrinking shipped bytes. Make this the headline of the packet, and confirm it by
quoting per-node bytes shipped for source vs id (so "bytes actually shipped" is
proven, not inferred).

## 4. Latency still in the high/disk regime

~5500 ms at np96 is the same regime as the (disk-confounded) packet-011 numbers.
The host was 99–100% full during this lane. Re-measure latency on a
non-disk-constrained host before any latency number is decision-grade — applies to
this packet too.

## What this packet needs before it's the communications verdict

1. Confirm per-node bytes shipped (source vs id) to make #3 a proven finding, not
   an inference.
2. Drop or fix the prune arm (#1) — don't present on==off as a result.
3. Clean latency rerun off the full disk (#4).
4. Then state the verdict: communications is/ isn't the cost driver, with bytes +
   per-stage timing backing it.
