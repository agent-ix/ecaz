## The fix is correct

Removing the `dedupe_mode != NoReplicaDedupeDisabled → None` guard so
`pre_materialization_min_ip_to_keep()` delegates to `min_ip_to_keep()` for all
modes is right, and recall-safe at the exact-score level:

- The deduped threshold comes from `peek_live_worst_deduped()` bounded by
  `candidates_by_vec_id.len()` — i.e. the worst of the *unique vec-id* top-k, the
  correct dedupe-aware bound.
- `min_ip_to_keep()` returns `None` until that bounded unique set is full, so no
  pruning happens before there's a real threshold.
- The threshold is **monotonic non-decreasing** as more candidates arrive, so a
  candidate with `ip < threshold` can never later qualify — pruning it cannot drop
  a truth. A replica of an already-retained vec_id that is *above* threshold is
  not pruned (strict `<`), so dedupe still gets to keep the better copy; a replica
  *below* threshold is pruned, but its qualifying copy (if any) is retained
  independently. No exact-score recall path is lost.
- Strict `<` preserves ties / deterministic ordering. Good.

The unit test `miri_pre_materialization_prune_threshold_engages_for_bounded_dedupe`
covers the key case (replica below threshold dropped, top-2 unique correct under
`VecIdDedupeEnabled`). Scoped honestly: "code checkpoint… does not close Task 123…
next step is the b2/b4 prune A/B."

## Required before the prune is a validated lever

The exact-score safety above is necessary but not sufficient — the prune actually
decides on the **quantized/approximate** `ip`, so a true positive whose
approximate score is below threshold but whose exact score would qualify can still
be dropped. That risk is identical to the b0 case (shown recall-neutral in PR #43
single-instance), but it is **not** confirmed for the b2/b4 multi-instance
candidates. So:

1. Rerun the **prune on/off A/B on b2/b4** (now that the guard engages), reporting
   **recall** (must stay at the prune-off value) *and* the candidate-count /
   materialization / latency effect (which should now be non-zero, unlike packet
   017's inert arms).
2. Heed the Task 112/113 precedent: a recall-safe material skip is **conditional**
   — the bound is loose at low bit-depth and may need a k-cap. If recall drops at
   b2/b4, the prune needs a tighter bound or a cap, not just "on by default."
3. Keep it off the 99%-full disk for any latency number (standing issue).
