## Code review (commit a91955a27)

I read the engine diff (`dispatch.rs`, `production_transport.rs`,
`scan_output.rs`, `types.rs`, `lib.rs`):

- **Purely additive:** three counters (`payload_decode_elapsed_ms`,
  `payload_decode_row_count`, `payload_decode_bytes`) threaded through
  `SpireRemoteProductionHeapReceiveResult` → timeline rows → CLI render. No
  routing, recall, candidate-selection, or storage logic touched. The "no
  behavior change" claim is accurate.
- **Behavior-preserving refactor:** the existing inline payload-byte loop is
  extracted into `remote_heap_payload_decode_bytes()` and reused on the second
  decode path — same `typed_bytes + json_bytes` saturating logic, no semantic
  change to the existing metric.
- **Overhead is confined and cheap:** one `Instant` around the decode loop plus
  a fold over candidates already being iterated, only on the production-read
  path — not on the default local scan path. Overflow handling
  (`try_from`/`checked_add`/`saturating`) is careful. The
  `unwrap_or(u64::MAX)`-poisons-the-sum pattern is pre-existing and acceptable
  for a diagnostic counter.
- Failure/legacy paths zero the new fields explicitly (`production_transport.rs`,
  `scan_output.rs`) — no uninitialized reads. Unit tests cover the render and the
  rollup; contained smoke exercises the real path. Good.

This is exactly the kind of gated, zero-default-path-overhead instrumentation
that is safe to carry on the branch (and eventually to main).

## The gap it does and doesn't close

- **Closes:** per-worker payload decode timing + bytes plumbing now exists and
  renders per node. The "communications" dimension is now *measurable*.
- **Does not yet close:**
  1. The smoke (and the 009 baseline) still project **`id` only**, so the
     reported bytes (320 B/node) are an id payload, not the real object/vector
     transport cost. To actually measure communications you must run with a
     **realistic projection** (the payload/vector width the production read would
     ship). Right now it proves the meter works, not what it reads.
  2. Still no separation of **leaf-read vs materialize vs candidate-score** — the
     timeline gives payload-decode timing, but the scoring/traversal split the
     amended task asks for isn't there yet.
  3. Validated only on a 4-query smoke; not re-run on the 100k baseline (host
     disk ~20 GiB, acknowledged).

## Recommendation

Land it (sound, additive). Next: re-run the 009 cells at ≥200 queries **with a
realistic projection** so the new per-worker byte counters report true
communications cost, and extend the timeline to split leaf-read / materialize /
score so all four amended dimensions (scoring, traversal, planning,
communications) are attributable in one table. That table is the efficiency
deliverable.

Hygiene clean: focused unit tests listed and passing, contained smoke artifacts
committed, no corpus/shard data.
