## Checks performed

- **Production isolation (double-guarded).** All new head policies, seed
  modes, GUCs, `pg_extern`s, and builder code are `#[cfg(feature =
  "distann-head-attribution-benchmark")]`. `benchmark_seed_mode` /
  `benchmark_head_policy` GUC registration and their parsers are cfg-gated
  (`options.rs:260,269,343,352,511`), so production cannot even name the new
  values. As belt-and-suspenders, `generation_read.rs` returns
  `EC_BAD_INPUT: head_basin_diverse is unavailable in production builds` when
  the enum arm is reached in a non-benchmark build. Good.
- **Disjoint split contract — no evaluation leakage (Q2).**
  `load_benchmark_query_splits` reads rows 201–400 (training) and 401–600
  (validation) via `skip(start).take(200)`; the immutable evaluation rows
  1–200 are never loaded by the builder. Each slice is length-checked and
  SHA-256-digested into the report. Critically, `training_gateway_set_cover_
  nodes` returns **`training.selected`** — membership is a deterministic
  function of the training split only. The validation split is used solely to
  emit a held-out recall *proxy* and a selection-Jaccard; it never influences
  which 4,096 nodes are persisted. Evaluation outcomes cannot reach the
  builder. Leakage protection is sufficient.
- **Determinism (reproduced).** Set-cover uses a lazy-greedy max-heap keyed
  `(gain, Reverse(vec_id), node)` — total order, smallest vec_id breaks gain
  ties; the lazy re-push on stale gain is correct. Diversity greedy breaks
  ties on `(penalized_rank, vec_id, candidate)`. All candidate/truth sorts use
  `total_cmp().then vec_id`. `frequency`/`coverage` are `HashMap`s but every
  consumer sorts or reduces order-independently, so iteration order does not
  leak. I independently re-ran both unit tests
  (`gateway_set_cover_is_deterministic_and_uses_marginal_gain`,
  `basin_diverse_selector_reduces_same_component_overlap`) — both pass; the
  set-cover test pins `first == second` and the exact greedy pick order
  `[0,1,2]` / gains `[2,1,1]`, and the basin test pins `[10,30]` with strictly
  lower pairwise overlap than the control `[10,20]`. The five committed
  artifact logs are genuine and match.
- **Traversal semantics (Q1).** `GatewayBuildExpander` runs the real
  `distann_orchestrated_search` core: neighbor frontier ordered by
  `prepared.score_dist(code)` (RaBitQ), exact final `-source_inner_product`
  rerank, `beam_width=4`, `hop_rounds=100`, `top_k=10`. Frontier ordering,
  visited-once dedupe, and the BW×H expansion cap are the production ones, not
  a re-implementation. Truth is exact top-10 IP over the full build-graph
  vectors; coverage tokens are `query_index*10 + rank`, universe `queries*10`,
  in-bounds. This legitimately measures RaBitQ-frontier reachability under the
  production kernel. See F1 for the one semantic gap.
- **Bounded work / no exhaust (Q4).** Attribution work is
  200 queries × ≤32 candidates × ≤(BW·H=400) expansions per split × 2 splits,
  plus 2 held-out joint traversals × 200 validation queries — all bounded and
  timed (`construction_ms`). The emitted report is compact aggregates only
  (counts, means, `hard_query_regions` keyed by bounded u16 geometry region,
  marginal-gain summary, estimated peak bytes). No per-query rows, no
  corpus-sized data. Good.
- **CLI/suite wiring (Q5).** `parse_distann_multinode_rows` gains
  `physical_benchmark_gateway` / `physical_benchmark_basin` branches;
  `head_basin_diverse` and `training_gateway_set_cover` are accepted by suite
  step validation, the `--seed-strategy`/`--head-policy` guards, and
  `parse_benchmark_seed_variants`. Emission runs only when the gateway policy
  / diverse variant is actually configured. The parser test and policy-
  expansion test cover the new rows. Ready to drive the packet-003 screen.

## Findings (advisory; F1/F2 want a manifest line in 003)

1. **Single-seed attribution is an isolated-budget upper bound, not a joint
   marginal.** `analyze_gateway_split` runs each candidate as a *single* seed
   with the full BW4/H100 budget. Production traversal runs all 32 seeds
   against one **shared** BW×H beam whose early-exit is governed by the joint
   kth exact distance. So per-seed `truth_pairs_reached` and the set-cover
   objective credit each candidate with reachability it would not get when
   competing for budget alongside 31 others — an upper bound on its true joint
   marginal. This is a defensible Phase-1 attribution (relative ordering is
   what set-cover consumes) and the real arbiter is the joint-path
   `held_out_traversal_recall` proxy + the packet-003 100k screen. But the
   packet/manifest should state explicitly that the per-seed gateway
   aggregates are isolated-budget diagnostics, so a flat or negative 100k
   screen is read as "isolated reachability didn't transfer to the joint
   budget," not as an inconsistency.

2. **Tail-fill source differs between the two membership arms.** Control
   `training_landmarks` backfills unused cap slots with `fill_with_geometry`
   (`head_sample.rs:1193`); the gateway arm backfills with **frequency nodes
   only** and hard-errors if set-cover + frequency cannot reach 4,096
   (`head_sample.rs:631`). So the two persisted heads can differ in tail
   composition (geometry-spread vs query-frequency) and the gateway arm has a
   build-time failure mode the control arm does not. Because exact scoring
   returns the nearest 32 of 4,096 as seeds, the tail almost never changes the
   returned seeds — consistent with the Task 182/183 NEG results that
   landmark-tail members don't move the top-32 — so this should not confound
   the *seed-level* A/B. Still, it is a genuine head difference and a possible
   build failure unique to the gateway cell; record it in the 003 manifest so
   it is a known, not a surprise, at 100k. (If the frozen contract's
   "frequency membership fills unused slots" is intended to be the *only*
   difference from control, note that control's own fill is geometry, not
   frequency — the two arms are not tail-identical.)

3. **Keep selection off training/validation in packet 003.** The builder
   correctly makes no candidate selection here. Per the task's "Training or
   validation metrics never break an evaluation tie," packet 003 must select
   the advancing cell by held-out *evaluation* recall (rows 1–200 / the 100k
   eval identities); the `*_held_out_recall_proxy` and
   `training_validation_selection_jaccard` fields are diagnostic context only
   and must not be cited as the selection criterion.

4. **Minor, no action needed.** (a) `validation.selected` runs a full
   set-cover that is used only for the selection-Jaccard — a small,
   harmless extra build cost. (b) `truth_pairs_possible` is reported as
   `queries*10` even when a query has fewer than 10 exact-truth nodes; only
   matters at tiny corpora, a non-issue at the 10k/50k/100k screen scales.
   (c) `physical_benchmark_basin` `basin_json` is emitted via
   `.replace(' ', "")` and the aggregates are numeric, so the space-stripping
   is safe here — but keep basin/gateway JSON values numeric (no string
   fields) so the space-delimited parser stays unambiguous.
