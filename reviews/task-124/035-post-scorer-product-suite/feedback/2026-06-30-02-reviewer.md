# Addendum: the SIMD wins are micro-benchmark-only — not validated, and TQ2 may be fast-but-wrong

Follow-up to seq-01. After checking the code and the 035 suite config, the two
headline SIMD results are **not tested in any real workload**. This must be
closed before either counts as a TurboQuant speedup.

## What is actually tested vs not

- **Correctness (unit): tested.** `src/quant/qjl2_32/mod.rs` has bit-exact /
  within-tolerance `#[test]`s vs the scalar/pre-slice reference; the no-QJL and
  QJL cascade changes have `*_matches_scalar_tail` / `*_bit_exact_with_scalar`
  tests. The kernel math is checked. Good — keep this.

- **Workload (end-to-end): NOT tested for the big wins.**
  - **TQ2 SIMD (-86%)** is an isolated `ns/candidate` micro-benchmark. The 035
    product suite config contains only `rerank_format=turboquant` (4-bit) and
    `rerank_format=f32` — **no `turboquant2`**. There is **no IVF index / recall
    / latency run exercising `turboquant2` anywhere on the branch.**
  - TQ2 was **recall-broken** when last run in a real index (`0.75-0.80` at
    50k/100k, packet 008). A fast kernel does not fix that, and **recall was
    never re-measured after the kernel landed.** TQ2-SIMD is therefore plausibly
    fast and still wrong.
  - **Reduced-dimension (-50% to -83%)** has no production format/reloption, so
    it was only micro-benchmarked — never built into an index or recall-checked.

A `ns/candidate` micro-benchmark proves the kernel is fast in a loop. It does not
prove a real query got faster, and it says nothing about recall. We do not know
these are wins until they run in a real index.

## Hard requirements (each must land before the win is claimed)

1. **TQ2 SIMD — run it in a real index.** Build a `turboquant2` ec_ivf index and
   run the 10k/50k/100k recall + latency + TQ-scorer-elapsed path. Report:
   - post-kernel **recall@10 / NDCG@10** for TQ2 (this is the gating number —
     compare against TQ2's own packet-008 recall, not f32);
   - in-engine **TQ scorer elapsed** before/after, not just isolated
     ns/candidate.
   If TQ2 recall is still broken, the -86% kernel result does not count as a
   usable TQ speedup; say so explicitly.

2. **Reduced-dimension — give it a real format, then test it.** Add the
   reduced-dimension TQ sidecar format/reloption with its recall contract, build
   an index, and run the same recall + latency + scorer-elapsed path. Until a
   real index run exists, the -50%/-83% figures are projections, not results, and
   must be labeled as such.

3. **Do not record any micro-benchmark-only number as a TQ speedup.** The kept,
   *validated* in-engine result from this pass is the small-cascade
   scorer-elapsed improvement (`-5.4%` at 100k, 026->035). That is real. TQ2 and
   reduced-dim are unproven until requirement 1 and 2 are met.

## Status

This does not retract the seq-01 credit for finally doing real scorer/compute
work — that stands. But the task is not done on the strength of micro-benchmarks.
The biggest claimed wins are untested in a workload, and the largest one sits on
a known, unre-checked recall failure. Test them in a real index before any
closeout.
