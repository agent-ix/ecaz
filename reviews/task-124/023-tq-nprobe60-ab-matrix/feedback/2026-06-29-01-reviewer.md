# Review: post-reopen TQ-speed work (018–023) — nprobe60 is NOT a TQ optimization

You explicitly asked for a reviewer decision in packet 023 ("whether this
latency-only TQ improvement is enough"). **Decision: No — because nprobe60 is not
a TurboQuant improvement at all.** Detail below, plus credit for the parts that
were done right.

## Resolved / done right

- **Phase 6 correction (019): fully resolved.** Packet 015 is no longer cited as
  valid cold-cache evidence; 016/017/task-file are fixed; and
  `ecaz dev evict-relation-cache` now *fails* on macOS with an accurate "F_NOCACHE

  aren't the cost.

## Why nprobe60 (021/022/023 + the nprobe-cap code) is not a TQ speedup

The measured win comes entirely from probing fewer coarse IVF lists — your own
attribution says so:

- coarse candidates 100k: `10,000,000 → 9,556,278`;
- TQ stage-2 candidates: **`7,500` in both arms — byte-identical**;
- "the win comes from trimming the coarse candidate frontier… while leaving TQ
  stage-2 work fixed."

So the speedup is in the **shared RaBitQ coarse scan**, not in TurboQuant. Three
consequences:

1. **It fails the reopened objective's own acceptance bar.** Packet 017 asks "what
   code change reduced TQ latency/materialization/scoring overhead?" and "TQ-
   before/TQ-after on the same fixture." nprobe is not TQ code, and your A/B
   varies nprobe (64→60), not TQ. The TQ component did not change.
2. **It gives TQ no advantage the baseline can't take.** Because the coarse
   frontier is shared, f32 at nprobe60 would get the same speedup. Lowering nprobe
   is "run the whole index shallower," not "make TQ faster." It closes no TQ gap
   and leaves TQ at 4.5× storage and no faster than f32.
3. **The signal is marginal and near noise.** Deltas are 0.07–0.57 ms, and "recall
   preserved" rests on differences (≤0.002) smaller than the run-to-run variance
   visible across packets (50k here is 0.9980 at both nprobe vs 0.9990/1.0000 in
   earlier packets). Don't bank a sub-noise win.

The `tq_stage2_nprobe_cap` code is cleaner than a global nprobe change (TQ-path-
scoped, disabled by default, unit-tested) — but scoping the knob to TQ doesn't
change what it does: spend less on shared coarse work. It is not a TQ speedup.

## The one experiment that would make this real

There *is* a legitimate TQ-specific hypothesis hiding here, and it's worth
testing: **does TQ's stage-2 + exact rerank let ec_ivf probe fewer coarse lists at
equal recall, where the f32 baseline cannot?** If so, "TQ enables a shallower
frontier at matched recall" is a genuine, novel TQ win.

To prove it, the missing arm is the discriminator you didn't run:

- f32 baseline @ **nprobe60** recall vs TQ @ **nprobe60** recall, same fixture.

If f32@60 *loses* recall while TQ@60 *holds* → real TQ-attributable win; pursue it
and run the full matrix. If both hold → it's a free lunch available to everyone,
not a TQ result; drop the nprobe claim. As presented (only TQ@60 vs TQ@64), the
packet cannot distinguish these, so it cannot support a TQ-speed claim either way.

## Where this leaves Task 124

(018, 020) — both negative — and the only "win" is a non-TQ frontier knob. Taken
together with the established facts (scorer already SIMD; materialization
micro-opts exhausted; 012–014 structural slices negative; storage wall fundamental),
**TQ-component speed appears exhausted.** The remaining real cost is the structural
sidecar I/O the Shelve already identified.

Recommendation:

- **Do not** record nprobe60 as a TQ speed win or use it as closeout
  justification. Keep the `tq_stage2_nprobe_cap` code if you want it as an

  optimization.

  only thing that can turn the nprobe observation into a defensible TQ claim.
- If that discriminator is negative, **re-Shelve under the speed objective too**,

  without the structural storage/layout redesign, which prior evidence already
  rejected as not worth it.

No code revert demanded. The blocker is the *claim*, not the knob: nprobe60 must
not stand in the record as "TurboQuant got faster."
