# Correction: TQ speed-optimization space is NOT exhausted — the scorer kernel was never touched

This supersedes the framing in my seq-01 approval. Scope of this note is **TQ
internal speed only**: what was done to make TurboQuant faster, what worked, what
failed, and what was never attempted. No baseline comparison, no storage/promotion
judgment — those are out of scope for the speed objective.

## TQ speed changes that SUCCEEDED (kept)

All of these reduce memory traffic / materialization around the scorer:

- **Selected-payload loader (003):** load only the requested survivor payloads
  instead of assembling the full group slab. Measured TQ-internal effect at
  100k/nprobe64: index-side TQ segment payload bytes `2,839,027 → 1,748,632`;
  TQ payload decode time `1202 µs → 514 µs`. Real speedup.
- **Contiguous selected slab (011):** one slab per group vs per-TID `Vec`. Small
  measured TQ latency improvement, kept.
- **Final exact width 25 → 15 (005):** fewer rows in the final pass. Modest TQ
  speedup, adopted as the working config.
- **Group-width locality (004):** smaller persisted groups cut segment reads
  sharply (group-16: `1.75 MB → 147 KB` segment bytes/query). Locality lever.

## TQ speed changes that FAILED (reverted)

All micro-allocation / addressing tweaks — the materialization micro-overhead is
at its floor:

- top-k fusion (012); compact group headers (013); direct-slot addressing (014);
  vector-index vs HashMap lookup (018); borrowed score buffer (020); selected-slab
  vector lookup (025).

## TQ speed ideas NEVER ATTEMPTED — the space is not exhausted

The burndown optimized the I/O envelope **around** the scorer and then declared
the scorer itself "not the lever" because `scalar_candidates=0`. But SIMD ≠
optimized. The following TQ-speed levers were never touched:

1. **The TQ scoring kernel itself.** No change on this branch reaches the kernel
   (`src/am/common/candidate_batch/`, `src/quant/`); every edit is in
   `src/am/ec_ivf/` plumbing. Untried inside the kernel: register/accumulator
   blocking, LUT-in-register vs memory layout, batch-accumulation width, software
   prefetch, instruction-count reduction, dequant/FMA fusion. This is the center
   of "make TQ faster" and it was never profiled, let alone optimized.
2. **Per-query LUT / query-prep cost.** TQ builds a per-query lookup table; its
   build cost and layout were never measured. "query-prep overhead" is on the
   task's own lever list and was skipped (018/020/025 touched per-candidate
   materialization, not query-prep).
3. **Batch / flush width tuning.** `width_ge32=100` was *confirmed* but never
   *swept* as a throughput lever; different flush widths change SIMD utilization
   and memory traffic.
4. **Dimension / subspace reduction.** Only bit-depth was varied (4 → 2 → 1).
   Scoring TQ over fewer dimensions (projection) reduces both bytes loaded and ops
   per candidate — a distinct speed axis, never tried.
5. **TQ2 with a real SIMD kernel.** TQ2 (008) was rejected as "slow," but its own
   packet records it fell back to **scalar** (no TQ2 block kernel exists). Its
   speed was never actually measured on a SIMD path; it was killed by an
   implementation gap, not a measured kernel result.
6. **QJL TQ scoring speed.** All speed work used no-QJL 4-bit; the QJL scoring
   surface was never speed-benchmarked.
7. **Prefetch / software pipelining** of payload reads ahead of scoring to hide
   memory latency — distinct from *which* payloads are read (003 reduced the set;
   nobody pipelined the reads).

## Reviewer position

I was wrong to let seq-01 read as "TQ speed is exhausted." Accurately: the
**materialization/I/O envelope** around the TQ scorer was thoroughly explored and
yielded real, kept speedups; the **scorer kernel, query-prep, batch-width,
dimensional, TQ2-kernel, and QJL** speed paths were not attempted. The
speed-optimization space is **open**, and the single largest untouched lever is
the TQ scoring kernel itself.

If the intent is to keep optimizing TQ speed, the next slice should be a profiled
pass on the no-QJL 4-bit TQ kernel + per-query LUT build — not another scan-path
materialization tweak, which is the part that is now at its floor.
