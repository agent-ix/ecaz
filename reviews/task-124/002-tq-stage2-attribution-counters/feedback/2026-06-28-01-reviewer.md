## Non-blocking notes for the next slice

1. **Output truncation is a top-k contract, document it.** The stage-2 path
   `candidates.truncate(final_len)` and `return`s early, so
   `stage2_final_rerank_width` becomes a hard cap on emitted rows (same gotcha
   `rerank_width` already has). For the width-25 product path this is fine, but
   the A/B harness must set `stage2_final_rerank_width >= k/LIMIT` or recall is
   silently capped. Worth a one-line note in the bench config / task notes so a
   future run doesn't misattribute a recall miss to TQ quality when it's just
   truncation.

2. **`resolve_scan_stage2_final_rerank_width` is evaluated ~3× per rerank call**
   (once in `should_run_…`, once for the width, once inside `should_run_…`
   again). It's a cheap GUC read so not a perf concern, but you could thread the
   resolved width through once when you wire telemetry, to avoid the re-reads
   reading inconsistently if a GUC ever changed mid-call.

3. **Phase 0/2 still owed before closeout.** The audit (`tq-score-surface-audit.md`)
   is solid on the IVF hot path, but per the task this remains open pending: the
   10k/50k/100k width-25 `ecaz bench suite` A/B vs the RaBitQ + f32 product
   baseline, the per-query scorer telemetry (block width / scalar-tail / ISA)
   the audit's "Gaps For Phase 3" calls out, and the Phase-2 payload
   insert/delete/vacuum/rebuild invariant evidence. Do not promote on the
   current evidence — and the requests correctly don't.
