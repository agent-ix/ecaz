## Required correction: the Phase 6 evidence does not support what it's cited for

The closeout (016) and the task-file Phase 6 row cite packet 015 as a completed
"IO-sensitive validation" that came back "negative/mixed." **The 015 run is not a
valid cold-cache test**, so it cannot be cited as IO-sensitive evidence.

Root cause, in `crates/ecaz-cli/src/commands/dev/relation_cache.rs:292`
(commit `3be1ba32e`): the macOS path opens a transient fd per relation file, calls
`fcntl(fd, F_NOCACHE, 1)`, and drops the fd **without reading through it**.

- `F_NOCACHE` only changes caching behavior for I/O issued **through that fd**; it
  does **not** purge pages already resident in the unified buffer cache.
- The function never reads through the fd, so nothing is even pulled/bypassed.
- PostgreSQL reads the relation through its **own** fds, which do not carry
  `F_NOCACHE`, so the query still hits the warm page cache.

Net: the "evict" step is effectively a no-op for query latency. The latency
deltas in 015 (e.g. f32 100k/nprobe32 p99 `13.8 ms` vs ~`5.6 ms` warm in 011) are
therefore run-to-run variance, not cold reads — which is itself a tell that the
cache state was uncontrolled. The coder partially flagged this ("per-relation
`F_NOCACHE` rather than a global OS cache purge"), but the closeout still records
Phase 6 as a satisfied IO-sensitive gate. It wasn't.

   IO-avoidance thesis is structurally self-defeating in-engine.

So the Shelve is correct on the merits. I am not requiring the remote true-cold
run — it would burn effort to reach a conclusion the storage wall already forces.
