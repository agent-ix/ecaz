# 111g/004 — Benchmark confirms the index-side sidecar accounting bug (codex P1) with hard numbers

Evidence: `benchmarks/ivf-111g-115-attribution/` (FINDINGS.md Finding 3 + Finding 1),
HEAD-matrix configs `head-sidecar-index-placement` and `head-rerank-format-matrix`,
Intel host, PG18, real DBpedia dim 1536, release `.so` SHA-verified, sweep
`[8,16,32,64,128,200]`.

## Measured: index-side `rerank_placement='index'` is a severe regression, not a win

codex's P1 (the sidecar counter reports survivor bytes O(W) while the scan reads
the whole chain O(N)) is **confirmed and quantified** at 100k:

| metric | table-side f16 | index-side f16 |
|---|---|---|
| p50 @ nprobe 8 | 4.7 ms | **551 ms** (117×) |
| p50 @ nprobe 200 | 13.2 ms | **552 ms** (42×) |
| p50 vs nprobe | scales 5→13 ms | **flat ~540 ms** (O(N), nprobe-independent) |
| index size | 25.4 MiB | **416 MiB** (16×) |
| recall@10 | ✓ | ✓ (same) |

The flat ~540 ms across nprobe is the signature of `load_rerank_sidecar_payloads`
materializing the entire `0x2A` chain (~307 MB for 100k f16) into a HashMap per
query to serve ~64 survivors (~196 KB). The `stats_rerank_source_bytes_read`
"byte-win" I approved in 003b was an artifact of counting O(W), not the O(N) work.

**Do not promote `rerank_placement='index'`.** It is slower and larger at equal
recall as implemented.

## Also: f16 table-side rerank was broken (Finding 1), now fixed

Separately, `rerank_format='f16'` collapsed recall@10 to ~0.6 (subnormal binary16
decode bug in `f16_bits_to_f32`, base exponent −1 vs −14). Fixed (commit
`0c3efc611`, `bench-ivf-111g-115-attribution`); f16 now ≈ f32 (0.9975 vs 0.9985
@np200). The 003b f16 parity test only checked index-f16 == table-f16, never
f16 ≈ f32, so it passed while the path was broken — a test-the-wrong-invariant gap.

## Verdict + fix

- **111g table reps:** f16(fixed) ≈ f32 recall but no IO/size benefit at table
  placement; rabitq4 rerank loses recall (0.942 @np200). Plain f32 remains best
  for table-side.
- **111g index-side:** regression → **ADR-079** (survivor-directed bounded read
  via a sidecar directory: ~307 MB → ~196 KB/query) is the fix; re-bench
  sidecar-index after. Until then, index-side should be considered
  experimental/non-promoted.
- The byte counter must also record blocks/pages actually read so evidence
  reflects true IO (the gap that hid this).
