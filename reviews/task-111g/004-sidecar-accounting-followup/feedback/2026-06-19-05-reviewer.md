## P1 — IVF format version bump (NFR-016) — FIXED

Agreed: extending the metadata struct from 86 to 92 bytes (the new persisted
`rerank_sidecar_directory_head` field) is a width/field change and per
`NFR-016-on-disk-format-evolution-discipline.md` must move to a new current
format version, not silently widen v3. Fixed in commit `7fe38a478`
("ADR-079 (4/4): bump IVF metadata format version 3->4 for the 92-byte layout"):

- `EC_IVF_INDEX_FORMAT_VERSION` 3 → 4. `decode()` already rejects any
  `format_version != INDEX_FORMAT_VERSION`, so the genuine legacy 86-byte v3
  layout is now rejected **by version**, not by an ambiguous same-version length
  mismatch — exactly the policy you asked for.
- Fixtures: `ivf_metadata_v3.hex` restored to the genuine 86-byte/v3 bytes (now
  a rejected-by-version fixture); new `ivf_metadata_v4.hex` (92 bytes/v4,
  directory head = `INVALID`).
- Tests: `on_disk_fixtures` gains `ivf_metadata_v4_fixture_decodes` and
  `ivf_metadata_v3_is_rejected_by_version` (byteswap test moved to v4);
  `size_of_assertions` asserts `EC_IVF_INDEX_FORMAT_VERSION == 4` and
  `EC_IVF_METADATA_BYTES == 92`; `upgrade_matrix` writable-set ivf `3 → 4`.
- Docs: `docs/on-disk-format.md` and `fixtures/upgrade/matrix.csv` now describe

## ADR-079 outcome (the reason the directory was added)

The directory exists to kill the index-side O(N) full-chain sidecar read that the
attribution bench exposed (the original 004 accounting finding: the
`stats_rerank_source_bytes_read` counter measured O(W) survivor bytes while the
real work was an O(N) full-chain `HashMap` build). Measured on the Intel host,
real DBpedia 1536-dim @100k, fresh build, no inserts (release `.so` `6078da14`;
full table in `benchmarks/ivf-111g-115-attribution/FINDINGS.md` Finding 8,
artifacts under `.../artifacts/adr079-sidecar-index/`):

| index-side @100k | recall np64 / np200 | p50 np8 / np64 / np200 | vs pre-fix |
|---|---|---|---|
| rabitq4 | 0.917 / 0.942 | 7.7 / 9.6 / 16.0 ms | **fixed** (was flat ~551 ms) |
| f16     | 0.964 / 0.9975 | 146.8 / 150.2 / 159.2 ms | 3.6× faster, still slow |

- **Correctness proven:** index-side recall now matches table-side/f32 at all
  scales → the survivor-directed read returns the right payloads.
- **rabitq4 fully fixed:** compact payload → many entries/block → tiny directory
  → bounded read scales with nprobe (16 ms), ≈ table-side.
- **f16 still directory-bound:** 3072 B payload → ~2 entries/sidecar-block →
  ~50k blocks → ~74-block directory; the per-block directory read (~140 ms) now
  dominates (flat ~150 ms). Survivor reads are bounded, but the f16 directory is
  large. Follow-up lever: denser / 2-level directory or a per-relation directory
  cache.

**Net verdict (unchanged):** table-side f32 remains the best default (13 ms,
recall 0.999, 25 MiB lean index). ADR-079 removed the catastrophic regression
and makes index-side **rabitq4** a real fast+compact option (recall-capped
~0.94, rabitq4 lossy). Do not promote index-side f16. The fallback path
(directory head `INVALID`, or any index with rows inserted since the last build)
re-uses the existing full-chain read, so correctness does not depend on the
directory being present.
