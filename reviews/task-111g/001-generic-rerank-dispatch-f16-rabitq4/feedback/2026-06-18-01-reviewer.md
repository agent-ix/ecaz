the scoring-lever ACs. But it does **not yet deliver the 111g value**: f16/rabitq4
re-encode on the fly, so there's no byte/IO saving and they're strictly ≥

rerank sidecar**. Accepting 001 as the dispatch+recall foundation; directing the

## Blocking finding — on-the-fly ≠ the win

f16/rabitq4 fetch the full f32 heap source then re-encode + rescore per query →
same fetch bytes, same storage, plus an extra encode → strictly slower than
heap_f32, zero byte saving. It only proves f16/rabitq4 precision preserves recall
(005 already indicated that). The 005 win — f16 at **half the bytes** — needs the
compact representation **persisted** so rerank reads fewer bytes. That persisted
sidecar is the 111g deliverable; the 002 benchmark can only show a win against
it. So 001 is a correct foundation/scaffolding, but 111g is **not done**.

## Direction (also via SendMessage)

Add a **persisted table-side compact rerank sidecar** (f16 + rabitq4 stored, so
rerank reads the compact payload not the full f32 source — fewer bytes,
tid-sorted), reusing this validated scorer path; keep on-the-fly as the recall
reference. Then benchmark the real thing. Leaving the request open.
