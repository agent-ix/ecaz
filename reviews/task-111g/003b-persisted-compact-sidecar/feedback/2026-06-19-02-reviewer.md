# 111g/003b — Follow-up review: request changes on index-side sidecar evidence

Reviewed current `main` at `0a195764a`, plus the 003b request/manifest and
post-strip feedback. This is a code + packet review; I did not run new tests or
benchmarks.

## Findings

### P1 — Index-side rerank materializes the full sidecar chain, but the packet and counter treat it as survivor-only I/O

The 003b request says scan "loads the chain into `HashMap<heap_tid, payload>`,
sorts survivors tid-ascending, and reads only the survivor payloads (bounded by
`rerank_width`)" and records `stats_rerank_source_bytes_read`
(`request.md:58-63`). The manifest then uses that counter as the byte-win
evidence (`artifacts/manifest.md:86-93`).

The implementation does not do survivor-bounded sidecar I/O. In
`src/am/ec_ivf/scan.rs`, `rerank_probe_candidates_index_side` first calls
`load_rerank_sidecar_payloads` (`scan.rs:2500-2504`), and that helper walks the
entire `0x2A` chain, decoding/copying every live sidecar payload into a
`HashMap<ItemPointer, Vec<u8>>` (`scan.rs:2551-2581`). Only after that full-chain
materialization does the code look up the selected survivors and increment
`source_bytes_read` (`scan.rs:2507-2545`).

So for an index with `N` sidecar entries and `W = rerank_width`, the actual
index-side scan/copy work is `O(N * compact_payload_len)` per scan, while the
EXPLAIN counter reports only `O(W * compact_payload_len)`. That invalidates the
packet's byte-reduction evidence as a proxy for the real sidecar read path and
can easily erase the intended latency win before the scorer runs.

This needs either an implementation change or an explicit downgrade of the claim:

- make sidecar lookup genuinely survivor-directed, for example with a block/range
  directory, sorted-chain merge against sorted survivor TIDs, per-list sidecars,
  or another bounded lookup structure;
- or record the full sidecar chain bytes/pages materialized and treat the current
  sidecar as a correctness-only/experimental format until a real A/B benchmark
  proves it wins despite the full scan.

Until then, do not promote `rerank_placement='index'` as the 111g performance
win on the basis of `stats_rerank_source_bytes_read`.

### P2 — 003b manifest remains stale after the clean-break strip

Commit `6dbcad121` correctly strips the v1/v2 backward-compat machinery, and the
current decoder is a hard v3-only clean break (`page.rs:672-693`). The request
appendix notes this at `request.md:151-180`.

However, the durable manifest still claims:

- `EC_IVF_METADATA_BYTES_V2 == 80` was pinned (`manifest.md:43-45`);
- `ivf_metadata_v1_fixture_decodes` proves an 80-byte v1 image decodes under the
  v3 reader (`manifest.md:46-48`);
- the upgrade matrix has v1/v2 read-only rows (`manifest.md:49-50`);
- the table-placement pg_test is "the same path a v1/v2 index takes"
  (`manifest.md:64-65`).

Those statements contradict the post-strip code and the current task closeout,
which says v3 is a research-project clean break. Because `manifest.md` is the
packet-local source of truth for evidence, refresh it rather than relying on the
later approval feedback to correct it.
