# 111g/005 — Deep audit follow-up: direct TIDs are real, but prior rerank-format conclusions were over-broad

Reviewed current branch source plus the committed 111g/005 packet and benchmark
artifacts. Static/read-only review only; no new tests or benchmarks run.

## Findings

### P1 — The table-side f16/rabitq4 benchmarks are not evidence for persisted compact storage

The current `rerank_placement = 'table'` implementation does not persist a table-side
f16/rabitq4 representation. It reads the original f32 heap/source vector and changes
only how that fetched vector is scored: `src/am/ec_ivf/rerank.rs:3-18` says the
on-disk layout is untouched and the rerank payload is always the heap source vector.
For f16, each fetched source is rounded at query time (`score_source`,
`src/am/ec_ivf/rerank.rs:91-98`). For rabitq4, each fetched f32 source vector is
encoded into a payload slab during the query before scoring
(`src/am/ec_ivf/rerank.rs:214-253`).

That means the benchmark rows that show f16/rabitq4 table-side with the same
25.4 MiB index size and slightly worse latency than f32 only prove that the
query-time conversion/scoring variants are not useful. They do not prove that a
persisted table-side compact payload, a packed f16 page layout, rabitq8, or TQ
cannot win. Any review packet, ADR, or benchmark finding should name this path as
"heap f32 source + query-time compact scoring", not as table-side compact storage.
The Task 111h sweep should be treated as the first real test of persisted f16,
rabitq4/rabitq8, and TQ rerank payloads under a common architecture.

### P2 — 111g/005 supersedes the old "f16 is still 150 ms" verdict; update the benchmark narrative

The 111g/005 packet shows the direct posting-carried sidecar TID hot path is a real
fix for the f16 sidecar lookup bug: the request cites f16 index-side @100k improving
from `146.8 / 150.2 / 159.2 ms` to `2.99 / 6.02 / 13.0 ms` at nprobe
`8 / 64 / 200` (`request.md:53-67`). The scan now prefers direct sidecar block TIDs
when every survivor carries one (`src/am/ec_ivf/scan.rs:2516-2574`) and groups reads
by those block TIDs (`src/am/ec_ivf/scan.rs:2621-2680`).

However, the shared benchmark write-up still contains the older ADR-079 conclusion
that f16 is directory-bound around 150 ms (`benchmarks/ivf-111g-115-attribution/FINDINGS.md:104-131`).
That is now stale for the current direct-TID path. Please update the shared findings
or add a superseding note so future work does not continue reasoning from the
pre-111g/005 directory-only result. The remaining f16 concern is no longer query
latency in this fresh-build/direct-pointer case; it is the very large index footprint
(the 111g/005 packet still reports f16 index-side as hundreds of MiB at 100k).

### P2 — Re-run or re-cite insert/vacuum coverage after the direct-TID change

The packet's review focus explicitly asks whether more insert/vacuum coverage is
required (`request.md:69-78`). The answer is yes: at minimum, the packet should
re-run and cite the existing focused pg_tests after the direct-TID change, or add a
note explaining why their prior run covers this exact hot path.

The changed behavior is not just a fresh-build benchmark path. Insert now prepends a
single-entry sidecar block, stores that block TID directly on the posting, and updates
the metadata head (`src/am/ec_ivf/insert.rs:136-203`,
`src/am/ec_ivf/insert.rs:208-243`). Scan then uses the direct-TID loader whenever all
survivors carry valid `rerank_tid`s, independent of the directory fallback
(`src/am/ec_ivf/scan.rs:2545-2574`). Existing tests that appear relevant are
`test_ec_ivf_index_placement_insert_maintains_sidecar`
(`src/tests/ec_ivf.rs:1497-1547`) and
`test_ec_ivf_index_placement_vacuum_removes_sidecar_entry`
(`src/tests/ec_ivf.rs:1953-2003`), but 111g/005 only cites `posting_scratch_soa`,
`cargo check`, and the fresh-build suite (`request.md:34-45`). This packet should
either re-run/cite those insert/vacuum tests at the direct-TID commit or add an
equivalent direct-TID live-insert/vacuum proof.

### P3 — Internal sidecar layout comment is stale

`src/am/ec_ivf/page.rs:1872-1879` still says insert appends to the sidecar tail and
rerank reads the whole chain into a heap-TID map. Current insert prepends
single-entry blocks (`src/am/ec_ivf/insert.rs:233-243`), and current scan first uses
posting-carried direct TIDs (`src/am/ec_ivf/scan.rs:2545-2574`). Please update that
comment; stale internal layout docs already contributed to bad assumptions in this
lane.
