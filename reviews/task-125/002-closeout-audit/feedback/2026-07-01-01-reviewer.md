## Reframing the matrix: the metrics came back negative, not pending

The audit lists 126 and 127 as **Partial** — "implemented, just missing a
metric." The metrics are now committed, and they are **null/negative results**,
which is a different status than "partial":

- **Task 127 — the bounded scorer never runs.** The new counters report
  `pruned_candidates=0 kept_candidates=0` (and `lut32_pruned=0 lut32_kept=0`)
  at **all** of 10k/50k/100k. `posting_prune_cutoff` yields no cutoff for this
  IVF/nprobe=32 shape, so the entire NEON bounded-scorer path is **dead in the
  measured config** — exercised only by unit tests. This ships a
  `#[target_feature]` bounded kernel + unsafe surface that does nothing here.
  → **Drop Task 127 from the closeout**, or demonstrate a config where the
  bound activates *and* wins (higher nprobe / tighter cutoff). If it stays, add
  the `debug_assert!(centroid_ip == 0)` invariant guard (the ip-space bound is
  only exact for the non-residual lane — see packet 001 seq 01) plus an in-situ
  activation test. "Recall unchanged" is not evidence it works; it's evidence it
  never fired.

- **Task 126 — width is release-neutral; the curve is debug-only.**
  `task126-width-profile.log` is a debug microprofile (ns/candidate in the
  *thousands* — unoptimized build), which cannot rank SIMD kernels; the release
  suite showed no end-to-end delta from BLOCK_WIDTH 32→64. Worse, the curve is
  monotonically better toward 256 (32=12662, 64=11578, 128=11084, 256=10875), so
  it does not even endorse the chosen 64 as optimal. Keeping BLOCK_WIDTH=64 is
  fine (release-neutral), but label the width curve indicative/debug — it is not
  decision-grade. A real per-width number needs a release ns/candidate microbench
  or an end-to-end release sweep.

## Task 125 tiling: implemented + bit-exact, but neutral on the only host tested

The literal cross-block dimension tiling is now real
(`score_lut_no_qjl_4bit_batch_tiled` → `neon::score_batch_tiled_neon`) and has a
good bit-exactness test across dims [7,8,1536] × widths [7,8,63,64,71,128]
(this also closes my earlier tail-coverage NIT). But the `candidate-closeout-tiled`
suite vs the pre-tiling int16 suite (both Apple) shows it is **neutral-to-noise**:

| scale | int16 kernel → tiled | int16 lat → tiled |
|---|---|---|
| 10k | 23.92 → 24.35 ms (**worse**) | 0.88 → 0.91 ms (worse) |
| 50k | 41.57 → 39.53 ms (~5%) | 1.88 → 1.83 |
| 100k | 38.90 → 38.18 ms (~2%) | 2.73 → 2.70 |

This is exactly what the cache math predicts: the i16 LUT is ~49 KB and Apple's
P-core L1D is 128 KB, so the LUT already fits — there is nothing to tile away
here. **Tiling's payoff is on Graviton (64 KB L1D, where the 98 KB f32 LUT
hard-spilled and even i16 sits at 77% occupancy), which was not benchmarked.**

Decision (the audit's own option 1 vs the fallback):
- **(a)** Benchmark tiling on the Graviton lane (`aws-graviton.json`). If it wins
  there, ship it as a Graviton-motivated win. **or**
- **(b)** Do **not** ship tiling; amend Task 125 to accept the int16 compact LUT
  as the cache-traffic solution in lieu of cross-block tiling. Cleaner, and
  avoids shipping a second NEON kernel that is neutral-or-worse on the host we
  can actually measure.

I lean (b) unless Graviton shows the win — see the code smell next.

**Code-quality flag on the tiled kernel (blocks shipping tiling as-is):**
`score_batch_tiled_neon_impl` heap-allocates in the hot path — `acc =
vec![...; 2*octet_count]` per call and, worse, `cols_by_octet = vec![...;
octet_count]` **inside the per-dim-chunk loop** (reallocated every 8-dim chunk).
For a kernel whose entire purpose is reducing memory traffic, per-tile `Vec`
allocation is counterproductive and is a plausible cause of the 10k regression.
If tiling is kept, hoist these to stack arrays / reused scratch before any
Graviton A/B — otherwise the Graviton test measures allocator overhead, not
tiling.

## Still open (carried from packet 001 feedback, unaddressed because unpushed)

  **shared** no-QJL 4-bit scorer; the closeout counters themselves show

  binary sha. Given the shared-pgrx install hazard and the mid-session
  `pull --rebase` the packet-001 audit observed, stamp each suite with the
  binary sha + commit and confirm all cells (baseline / int16 / tiled) ran on
  the same binary.
