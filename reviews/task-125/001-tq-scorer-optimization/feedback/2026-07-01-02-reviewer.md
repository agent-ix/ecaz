# Task 125: Close-Out Testing Plan for the int16 LUT Win

Follow-up to seq 01. This is the concrete test set required to **land the int16
compact-LUT win** (the one lever that delivered) and to decide how far to push
it, before the remaining directions spin out into their own tasks.

## Corrected mechanism (matters for the plan)

The int16 win is a **cache-residency effect, not bandwidth volume** — proven by
the block-width null: `BLOCK_WIDTH 32→64` halves LUT *reload frequency* yet gave
nothing, while halving LUT *bytes* (f32→i16) gave ~2×. So the lever is "LUT
working set vs **L1D**."

Verified L1D sizes (this changes where the win lands):

- Apple M4/M5 P-core: **128 KB L1D**.
- Graviton 4 (Neoverse V2): **64 KB L1D**, 2 MB L2/core.
- Graviton 5 (Neoverse V3): **still 64 KB L1D**, 2 MB L2, 180 MB L3.

L2/L3 keep growing; **L1D is pinned at 64 KB across all Graviton generations**
(latency-bound). Consequence:

- f32 LUT = 1536×16×4 = **98 KB**: fits Apple's 128 KB L1D at high pressure
  (that is the win we measured locally), but **hard-spills to L2 on every
  Graviton**.
- i16 LUT = **49 KB**: comfortable on Apple, fits Graviton's 64 KB (77% occ).
- i8 LUT = **24.5 KB**: fits everywhere with headroom for codes.

So the win is host-cache-dependent and the local Apple number is likely a
**lower bound** for Graviton. This is why the close-out must be multi-host.

## Required to land (blocks closeout)

1. **Cross-AM recall spot-check.** int16 + `BLOCK_WIDTH` changes are in the
   *shared* no-QJL 4-bit scorer; SPIRE (test tol relaxed 1e-6→1e-3) and DiskANN
   (dispatch flipped 32/7→0/39) are provably affected but unmeasured. Run
   recall@10 at 10k/50k/100k for **SPIRE, HNSW, DiskANN** on the int16 build vs
   baseline. Expect byte-equal-ish recall; the gate is "no recall regression on
   any AM that shares the kernel." Latency is a bonus (they should also speed up
   for free).

2. **Multi-host A/B on Graviton 4 (and the Intel/AVX2 lane).** Re-run the IVF
   int16 A/B on `aws-graviton.json` and `intel-local.json`. The AVX2 path also
   switched to i16, so the x86 lane needs its own number. Hypothesis: the
   Graviton win ≥ the Apple win because f32 spills L1D there. Store per-host
   suites in the packet.

3. **Provenance.** Record the installed `.dylib`/`.so` sha256 + git commit in
   each `*-suite-manifest.json` (or a `manifest.md` line per host), and confirm
   all cells ran against the same binary — the audit caught a `pull --rebase`
   moving a worktree mid-session, and the shared-pgrx install hazard applies.

## The "how far does the lever go" test (agreed)

4. **i8 LUT A/B.** Same change, pushed to i8 (24.5 KB, per-query scale). Gate is
   recall: i8 is 256 levels vs i16's 65k, so the risk is accuracy, not speed.
   Run IVF recall+latency at 10k/50k/100k on **all three hosts** (the i8 payoff
   should be biggest on Graviton's 64 KB L1D; Apple may already be at the L1
   floor and show little delta). Decision rule:
   - i8 recall-neutral → adopt i8 as default (bank the extra headroom + Graviton
     win).
   - i8 loses recall but i16 is clean → ship i16, shelve i8 with the numbers.
   This single result also tells us whether we are **cache-bound (i8 helps) or at
   the L1-residency floor (i8 flat)** — which decides whether tiling is worth
   pursuing (see task spin-out).

## Not part of this closeout (spinning out to tasks)

- **Dimension tiling** — the durable L1D fix and Task 125's original unfulfilled
  scope; decision gated on test 4's cache-bound/floor answer.
- **Non-scorer profiling** — kernel −48% but latency only −30% ⇒ scorer is ~60%
  of query time; flamegraph the other ~40% (heap/top-k, page I/O, candidate
  materialization) before mining the scorer further.
- **Small-batch graph-AM scorer** — the DiskANN 0/39 finding shows graph AMs
  never hit the wide block kernel.
- Candidate-count reduction is **deprioritized** (tasks 119/121 showed minimal
  results); SPIRE remote-scan latency is already owned by **Task 131 (SPIRE
  streaming top-k)**.

Once tests 1–4 land, the int16 win is closeable across the TurboQuant family and
we have the data to size the tiling/profiling directions.
