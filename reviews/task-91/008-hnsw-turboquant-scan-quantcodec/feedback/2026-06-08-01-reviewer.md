# Reviewer feedback — Task 91 Packet 008 (HNSW TurboQuant scan QuantCodec)

## Verdict

**Approve.** First HNSW scan path is now on `QuantCodec`; polarity, scan
state ownership, and bit-exactness preserved.

## Spot checks against commit `ed5fb20e9`

- `HnswTurboQuantScanCodec<'a>` wraps `&ProdQuantizer`. Implements
  `QuantCodec` with `PreparedQuery = HnswTurboQuantPreparedQuery<'a>`
  borrowing scan-owned state for all four modes (`Exact`, `FullLut`,
  `TiledLut`, `Int8Approx`). ✓
- `prepare_ip_query` returns an explicit error
  ("`ec_hnsw TurboQuant scan codec uses scan-owned prepared query
  state; query length {}`") because scan code preallocates the query
  state outside the trait. That is the correct shape — the trait
  contract doesn't force HNSW to relinquish its scan-state ownership.
  ✓ Matches the Packet 001 dispatch contract's "AM-owned versus
  quant-owned state" split.
- `score_ip_candidate` reads gamma only for the `Exact` branch and
  ignores it for the three LUT-style branches (matching the pre-slice
  call shapes that did not take gamma). ✓
- `score_scan_element_result` is restructured so all four modes flow
  into one `-codec.score_ip_candidate(&prepared, payload)?` site,
  unifying the score-polarity negation that was previously repeated
  per-arm. The error path is `pgrx::error!("ec_hnsw scan scoring
  failed: {err}")` — matches HNSW's existing fatal-error convention.
  ✓
- `CandidateMeta::Gamma(gamma)` is the metadata used for all four
  arms. For the three LUT modes the gamma value is ignored inside
  `score_ip_candidate`, so the unconditional `Gamma` carrier is
  harmless. ✓
- Pre-slice behavior preserved:
  - `Exact` arm previously did `-quantizer.score_ip_from_parts(prepared, gamma, code_bytes)`;
    new path goes through `Exact(&PreparedQuery)` variant and ends in
    the same `score_ip_from_parts` call. ✓
  - `FullLut` arm previously did
    `-quantizer.score_ip_from_parts_lut_no_qjl_4bit(prepared, code_bytes)`;
    same end call now via `FullLut(&PreparedLutNoQjl4BitQuery)`. ✓
  - `TiledLut` and `Int8Approx` likewise. ✓
- The new focused test
  `hnsw_turboquant_scan_codec_matches_direct_exact_modes` asserts
  `to_bits()` equality between the trait path and the direct
  `score_ip_from_parts_*` calls for all four prepared variants, plus
  metadata parity for `codec_kind`, `search_codec_tag`, `payload_len`,
  and `encode_source`. ✓ That is the Phase 4 parity shape Packet 002
  established as the migration template.

## Smaller observations (non-blocking)

- The `HnswTurboQuantScanCodec` adapter currently lives inside
  `src/am/ec_hnsw/scan.rs`. That's fine for the first Phase 4 slice.
  If later HNSW slices (PqFastScan, RaBitQ) introduce their own
  per-codec adapters, please consider whether they belong alongside
  this one in a new `src/am/ec_hnsw/quant_codec.rs` (paralleling
  `src/am/ec_ivf/quantizer.rs`'s adapter layout). Not blocking.
- `payload_len()` reports `code_len(original_dim, bits)` which covers
  both `mse_packed + qjl_packed`, but only `Exact` actually consumes
  the full code. The three LUT modes take just `encoded.mse_packed`.
  Document or assert that distinction at the call site so a future
  reader does not mismatch metadata against actual code length when
  feeding through `score_ip_batch`. Not blocking for this slice
  because `score_ip_batch` is not used here.
- PqFastScan grouped search, PqFastScan binary traversal, and RaBitQ
  traversal scoring are correctly scoped out per the request.
  Track them as later Phase 4 packets.
