## Findings to lock before Phase 2

### F1 (must-fix in Phase 2): Counter attribution for mixed batches

The Task 92 counter contract (this packet's sibling) gives implementers two
choices for scalar-tail attribution after an ISA kernel block:

> - record the tail under `isa=Scalar`, preferred for exact attribution; or
> - record it under the selected ISA row's `scalar_*` fields if implementation
>   simplicity wins.

That decision affects whether Tasks 93–98 cells are comparable across hosts
and across ISA dispatch outcomes. Task 91 Phase 2 (the IVF retouch) is the
first concrete consumer and will set the de-facto convention by example.

Please pick one option in the Phase 2 IVF retouch packet and record that
choice as a binding rule for Tasks 93–98 in `dispatch-contract.md`, not as
an option list. Otherwise the per-quant tasks will drift on it.

### F2 (must-fix in Phase 2): Bit-exactness baseline for IVF retouch

`dispatch-contract.md` says "Scalar implementations must be bit-exact with
the pre-migration scorer." The Phase 2 IVF retouch covers four prepared-query
shapes (`TurboQuant`, `TurboQuantNoQjl4BitLut`, `RaBitQ`, `PqFastScan`). The
existing IVF generic TurboQuant path calls `score_ip_from_parts`, the no-QJL
4-bit path calls Task 87's LUT32 scorer, the RaBitQ path uses an estimator
with bound-aware helpers, and PqFastScan uses suffix-max LUT state. Those
are four different bit-equality baselines.

Phase 2 evidence should include one focused unit test per shape that asserts
`f32::to_bits()` equality of `score_ip_batch` output against the pre-retouch
scorer for at least one fixture per shape. The packet text currently only
calls out "focused unit tests"; making it per-shape avoids a silent shape
falling out of parity coverage. Please commit to that scope in the Phase 2
request.
