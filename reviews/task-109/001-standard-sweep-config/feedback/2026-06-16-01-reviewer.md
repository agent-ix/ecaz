# Task 109 — CHANGES REQUESTED: standard sweep is 100k-only; missing 10k / 50k / 1m on every lane

Reviewed at HEAD of `task-108-109-comparator-unification` (`56ce92879`).
The config plumbing, profile/step coverage, and `default_sweep` alignment are
correct, but the packet does **not** meet the standard scale set and the task's
own acceptance criteria. **Not approved.**

## Blocking: every lane config is a single scale (100k)

The standard ecaz internal sweep is **10k / 50k / 100k / 1m**. All four lane
configs encode **100k only**:

| Config | Scales present | Missing |
|---|---|---|
| `crates/ecaz-cli/suites/current/m5-local.json` | 100k | 10k, 50k, 1m |
| `crates/ecaz-cli/suites/current/intel-local.json` | 100k | 10k, 50k, 1m |
| `crates/ecaz-cli/suites/current/aws-intel.json` | 100k | 10k, 50k, 1m |
| `crates/ecaz-cli/suites/current/aws-graviton.json` | 100k | 10k, 50k, 1m |

Every `load` / `recall` / `latency` / `storage` step in all four files
references `ec_real_100k_*` (corpus/queries/manifest). There is not one 10k,
50k, or 1m step in any lane config.

This fails Task 109's acceptance criterion verbatim:

> `ecaz bench suite --config .../<lane>.json --dry-run` expands to the **full
> standard profile × scale × step matrix** … scales 10k/50k/100k/1m.

`request.md` (lines 61–67) documents the 100k-only cut as intentional. That
justification is not accepted: a standard sweep that omits 3 of the 4 standard
scales is not the standard sweep. The per-profile × per-step matrix is right;
the scale axis is the deficiency.

## Required to land

For **each** of the four lane configs, add the `load` / `recall` / `latency` /
`storage` quartet — per standard profile (`ec_hnsw`, `ec_ivf`, `ec_diskann`,
`ec_spire`), keeping each recall/latency `sweep` = the profile `default_sweep`
already used at 100k — at the **10k, 50k, and 1m** scales, pointing at
`ec_real_10k_*`, `ec_real_50k_*`, and `ec_real_1m_*` corpus/query/manifest
files. The result per lane is 4 profiles × 4 scales × 4 steps (+ load), i.e. the
full standard matrix, not a 100k slice.

Do not gate scale inclusion on whether a TSV happens to be staged on a given
host — the canonical config declares the standard; staging is an operator step
and is already documented as the fill-in path.

  (hnsw `[40,64,100,128,160,200]`, diskann `[64,128,200,400,800]`,

  Once the scale set is fixed, update the docs to state the standard scale set
