## Why item 1 blocks closeout

Task 235 is the write-side twin of Task 234, and it applies the same wrapper.
Every write phase now routes through `bounded_write_phase` →
`await_remote_write` → `await_remote_read`, which wraps each statement in a
`tokio::time::timeout` raced against `postgres_interrupt_signal()`'s 5 ms poll
loop. Per the task's own "Why", these transaction-control and intent statements
previously used direct synchronous paths. A single distributed insert now
carries that machinery across BEGIN, endpoint mutation, PREPARE TRANSACTION,
intent write, and COMMIT PREPARED — five wrapped round trips per row per owner,
where there were none.

When that same wrapper landed on the read path, it measured **+12.8% / +17.5%**
warm mean at 50k/100k, and the best screened fast path still cost **+7.1%** at
50k. That is why Task 234's ledger row says closeout NOT DONE. The write path
has a higher per-operation statement count than the read path, and it has zero
measurements.

I checked whether this is cheap before asking: it is.
`task167_default_insert_throughput` already exists at
`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:3777`, already emits
`physical_benchmark_insert_throughput_ab`, and is already invoked by the normal
`distann-local-multinode` step. The only reason Task 234's run produced no
numbers is that its config set `skip_single_control: true`. This is a config
flag and a suite run, not new instrumentation.

I want to address the two fair objections directly, because both appear in the
task file:

- *"Optimizing build/publish throughput" is an explicit Non-goal.* Agreed, and
  I am not asking for optimization. Not optimizing and not measuring are
  different things. The ask is a regression measurement, and the disposition it
  supports is "bounded/correct at acceptable cost", which is a claim the task
  currently makes implicitly and cannot support.
- *None of the four acceptance criteria mention a benchmark.* Also true. The
  closeout evidence rule is program-level, not per-task-AC, and this change
  mutates index contents through a restructured transport. A task's own AC list
  cannot opt out of it — that is precisely the "implemented-but-unbenched"
  shape the rule exists to catch.

If the measurement comes back neutral, this becomes an ACCEPT with a stronger
disposition than the packet can currently claim. If it comes back at +7% or
worse, that is a product decision worth having deliberately rather than
discovering after merge.

**Decision authority is genuinely coordinator-driven — verified in code, not
just in the log.** `prepared_resolution` (`remote_transport.rs:2025`) returns
`None` for both `InProgress` and `Unknown`, so neither can produce an action.
`coordinator_xid_status` maps a NULL `pg_xact_status` to `Unknown` with the
comment "CLOG may have been truncated, and recovery must not infer a decision
from age" — that is the correct reading of 2PC, and using `xid8` rather than a
32-bit xid avoids the wraparound aliasing that would make this unsound. An
`Err` from the status lookup returns a failure string rather than a decision,
so even a lookup fault cannot produce a guess.

**The lost-ack path is closed on both sides.** The reaper scans the *union* of
`pg_prepared_xacts` and nonterminal intent rows
(`prepare_requested`/`prepare_acked`/`commit_intended`), so a crash between a
successful `COMMIT PREPARED` and the intent upsert is still reconciled — the
GID is gone from `pg_prepared_xacts` but survives in the intent table. The
matrix confirms it: `after_commit_prepared_ack_loss` shows `before_prepared=0
before_nonterminal=11` converging to `source=1 owner=1`. Correspondingly, a
failed `COMMIT`/`ROLLBACK PREPARED` records
`{action}_failed:outcome_unknown:operator_retry` and does **not** write a
terminal intent state — it does not claim an outcome it could not confirm.
Foreign-coordinator GIDs are skipped with the correct justification (only the
named coordinator owns `pg_xact_status` for that xid).

final_intent=commit_local duplicate_actions=0` — unknown status stops, retains
`prepare_requested`, creates no prepared transaction, then converges to

## Not blocking

`remote_write_server_failure` matches on `sqlstate == "53200" &&
message.contains("maximum number of prepared transactions")`. The substring is
English-locale-dependent, so on a server with a non-English `lc_messages` the
operator hint silently degrades to `remote_sqlstate_53200`. The degradation is
safe — no wrong decision, just a less useful category — so this is not worth a
code change now. It is the same message-substring pattern as the
`EC_RECORD_MISSING` check I flagged for Task 237's taxonomy inventory; both
belong there.
