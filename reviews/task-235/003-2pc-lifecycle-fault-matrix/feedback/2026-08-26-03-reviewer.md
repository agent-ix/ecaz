## Item 1 — the arms are not comparable

`518ec9540` makes `mid_insert_drill` conditional on `skip_fault_drills`. The
committed suite config sets `skip_fault_drills: true` on all six steps, so:

- **control arm** (pre-10:02 binary): the mid-insert drill *ran*. I confirmed
  this — there is not one `pass=skipped` line in any of the three control
  summary logs, because the code that emits it did not exist yet.
- **candidate arm** (post-10:02 binary): the mid-insert drill would be skipped.

The mid-insert drill performs mutating inserts during the fixture run. Executing
it in one arm and not the other, in a benchmark whose measured quantity *is
insert throughput*, is a work asymmetry that lands directly on the number under
test.

`730b4945b` compounds it: it sets `ec_distann.local_node_id` on the coordinator
session before the physical benchmark. That GUC feeds
`super::roster::current_local_node_id()`, which the prepared-transaction reaper
uses to decide which GIDs are its own work — the exact path this task changed.
The control arm ran without it set; the candidate arm would run with it. That is
a behavioural difference in the code under measurement, not a harness detail.

Neither change is wrong. Both look like genuine fixes needed to make the
candidate arm run at all. But a fix that lands mid-A/B invalidates the arm that
already ran. Land both, then re-run control, then run candidate — all three
scales on one binary.

## Item 2 — `518ec9540` prints the skip and then overwrites it

The new code:

```rust
let physical_mid_insert_ok = if args.skip_fault_drills {
    ecaz_println!("... physical_mid_insert_failure pass=skipped reason=skip_fault_drills");
    true
} else {
    mid_insert_drill(psql, socket_dir, nodes[0].port, args).await
};
ecaz_println!("... physical_mid_insert_failure pass={physical_mid_insert_ok}");
```

The second `ecaz_println!` is unconditional, and `physical_mid_insert_ok` was
just set to `true`. So the summary log — which is what the suite parser reads
into `results.jsonl` — still records `pass=true` for a drill that never ran.
The `pass=skipped` line is emitted and then contradicted two lines later.

This is not hypothetical, and it is not new. The identical shape is already live
for the concurrency drill at `distann_multicluster.rs:8848-8871` and `:8956`:
skip → set `true` → unconditional `pass={ok}` into stdout *and* the summary.
Its consequence is visible in the control arm's committed evidence right now.
With `skip_fault_drills: true` and `skip_concurrency_drill: true` configured on
every step, `suite-results-control.jsonl` records at all three scales:

```
physical_serving                pass=true
physical_mid_insert_failure     pass=true
physical_concurrent_insert_query pass=true
physical_routed_delete_vacuum   pass=true
physical_topology_gate          pass=true
```

`results.jsonl` is the NFR-007 machine-readable source of truth, and it is
currently asserting five passing drills for a run configured to skip them.

This is the third appearance of this defect. The Task 224 review documented it
for `physical_routed_delete_vacuum` at `:10575-10592`, and Task 234's packet 005
(`775496af1`) claimed to fix that one. Fixing it drill-by-drill by copying the
same broken shape will keep producing it. The correct fix is to make the
outcome a tri-state — ran-and-passed / ran-and-failed / skipped — and have the
single summary emitter render `pass=skipped` rather than coercing a skip to
`true` at the call site. Do that once, in the emitter, and all four drills stop
lying at the same time.
