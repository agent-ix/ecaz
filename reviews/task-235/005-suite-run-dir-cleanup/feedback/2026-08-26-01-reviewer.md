# Task 235 packet 005 (suite run-dir cleanup) — NOT DONE: one ordering bug in the failure path

Verdict: **NOT DONE.** The path safety is genuinely thorough and I am not asking
for changes there. One item:

1. **A cleanup failure now masks the step failure that caused it.** Bail on
   `step_failure` before propagating `cleanup_result`, or attach the cleanup
   error as context to the step failure.

## Item 1 — the exact case this will hit

At `suite.rs:1424-1429`:

```rust
let cleanup_result = cleanup_distann_run_dirs(&config, &mut manifest).await;
write_manifest_if_requested(&args, &config, &manifest).await?;
cleanup_result?;                      // <-- propagates first
if let Some(step_failure) = step_failure {
    bail!("{step_failure}");          // <-- never reached
}
```

`cleanup_distann_run_dirs` bails when a `postmaster.pid` remains:

```rust
if run_dir_has_postmaster_pid(&run_dir).await? {
    ...push("run_dir_cleanup=blocked_live_postmaster");
    bail!("refusing to remove run_dir {} while a postmaster.pid remains", ...)
}
```

These two conditions are **correlated, not independent**. A step that fails
partway through is exactly the step that leaves nodes running — that is how
`task235-write-throughput-candidate-50k` sat up for an hour after its suite
stopped. So the common failure sequence is: step fails → nodes still up →
cleanup refuses → the operator sees `refusing to remove run_dir …` and never
sees why the benchmark actually failed.

The information is not lost — the manifest is written before `cleanup_result?`,
which is the right ordering and I want to credit it — but the terminal error is
the one a human reads first, and it will be the least important of the two.

Reversing the two lines fixes it. Better still, keep both: bail on the step
failure with the cleanup error attached as context, so a blocked cleanup is
still visible without displacing the cause.

Same argument applies to the threshold-failure path below it, for the same
reason.

## What I verified and accept

**Deletion target resolution is fail-closed at every layer.** I traced
`validate_distann_suite_run_dir` rather than trusting the summary:

- `Component::ParentDir` → bail, so no `..` traversal.
- `run_dir == cluster_root || !run_dir.starts_with(cluster_root)` → bail, so the
  root itself can never be the target and the path must be a strict child.
- Both paths are **canonicalized and re-checked**, so a symlinked run_dir cannot
  escape `ECAZ_CLUSTER_ROOT`.
- Canonicalization of an existing `run_dir` propagates its error with `?` rather
  than falling back to the raw path — that is the detail that closes the
  dangling-symlink hole, and it is easy to get wrong.
- A non-existent `run_dir` is reconstructed under the canonical root from the
  already-verified child relationship, rather than canonicalized loosely.
- Explicit rejection if either canonical path lands inside the repo root or
  inside `CARGO_TARGET_DIR`.

Rust's `remove_dir_all` refuses a symlinked top-level path, so the window
between validation and deletion is not exploitable in any realistic way on this
host.

**Ordering is correct.** `extract_result_rows` → `enrich_distann_result_rows` →
`write_results_jsonl` → `evaluate_thresholds_for_steps` → cleanup. Results are
durably on disk before anything is deleted, and `has_missing_artifact` refuses
to delete a fixture whose expected packet artifacts are absent. That is the
right gate: the fixture is only disposable once the evidence it produced is not.

**The retain escape hatch is right.** `retain_run_dir_reason` requires a
non-empty single-line reason and writes both the reason and
`run_dir_cleanup=retained` into the manifest, so a retained fixture is a
recorded decision rather than an accident. That matches how
`--run-dir` exceptions are supposed to be justified in the packet.

**Rejecting a repo-local `CARGO_TARGET_DIR` is the second half of the fix.**
This packet addresses the fixture half of the disk problem; that check addresses
the build half — the `target/task220-cli-{,2,3,4}` pattern that put four full
dependency graphs inside the repo for one ticket. Both root causes in one
change.

**Scope discipline is right.** No extension or index behavior, no benchmark
result, no PGDATA created for the packet, and the validation claim
(`cargo check -p ecaz-cli` plus two path-policy unit tests) is stated plainly
rather than dressed up.

## Non-blocking

The two unit tests cover path policy only — parent-directory components and a
repo-local run dir. Nothing exercises the postmaster gate, the missing-artifact
gate, or an actual removal. That is a defensible line to draw, since testing
real deletion means building real fixtures, and every gate here fails closed. If
you want cheap coverage without a cluster, the postmaster and missing-artifact
gates are both testable against a `tempfile` tree with a fake `node1/postmaster.pid`
and no `ECAZ_CLUSTER_ROOT` involvement.
