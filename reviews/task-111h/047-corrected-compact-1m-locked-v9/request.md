Immediate 1M/w64 readouts:

- Source f32 and index f16 have identical recall in this run:
  0.9770 at nprobe 64, 0.9860 at nprobe 128, 0.9880 at nprobe 200.
- Index f16 is slower than source f32 in the warm latency sweep and uses far
  more ec_ivf index storage: 3.2 GiB versus 226.8 MiB.
- No measured 1M/w64 cell reaches recall@10 >= 0.9900 by nprobe 200.
- RaBitQ-8 clip 4 is the only compact quantized cell that reaches recall@10 >=
  0.9700. It first qualifies at nprobe 64 with recall@10 0.9730.
- RaBitQ-8 estimator is slightly faster than source f32 at nprobe 64 latency
  in this run, 18.1 ms versus 18.7 ms, but its recall remains lower at nprobe
  64, 128, and 200.
- RaBitQ-8 exact-dequant did not improve recall over estimator and was worse
  at nprobe 200 latency.
- RaBitQ-4 and TurboQuant are storage-efficient relative to f16, but do not hit
  recall@10 >= 0.9700 at width 64 on this 1M slice.
- TurboQuant exact-dequant did not improve recall over default.

## Caveats

- This is a 1M/w64 local PG18 warm-cache run with 100 measured queries, not a
  full production-scale benchmark.
- The first source f32 cell includes shared table/query load time; later cells
  skip already-loaded chunks, so compare index build timing rather than total
  load step duration across cells.
- The CLI `ec_ivf` profile warning shows that
  `rabitq_rerank_least_squares`, `rabitq_rerank_clip`, and
  `rerank_exact_dequant` are not in the profile's known-reloption list yet.
  The loader passed them through verbatim, the extension accepted them, and the
  suite completed. This should be cleaned up before final closeout.
- The staged corpus manifest prefix is shared while the suite uses task prefix
  `task111h047_1m_shared`; the config intentionally used
  `--allow-manifest-mismatch`.
- The truth cache generated by the recall steps is intentionally not committed
  per packet rules.
