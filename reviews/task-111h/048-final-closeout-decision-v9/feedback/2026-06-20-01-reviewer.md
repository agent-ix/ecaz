# 111h/048 — f16 efficiency verified + corrected closeout resolves the 041 rejection

Two parts: (1) a focused re-trace of the f16 `index` path the operator asked
about — are all prior fixes in, is per-query work efficient, or is it still doing
redundant work; (2) confirmation that the corrected sweep (packets 042-047) fills
the 041 gaps.

## f16: all prior fixes landed, per-query work is efficient, remaining cost is an inherent storage floor

Deep-traced `src/am/ec_ivf/rerank.rs` + `scan.rs`. The old "f16 does a lot of
work on every query" smell is **resolved**:

1. **Subnormal decode fix — present.** `f16_bits_to_f32` (`rerank.rs:1167-1205`)
   is IEEE-correct: signed zero, the −14 subnormal base exponent (the historical
   bug used −1 and collapsed recall to ~0.6), inf/NaN. Pinned by
   `f16_round_trip_is_accurate_for_subnormal_magnitudes` (`rerank.rs:1286`).
2. **Scores directly from packed bytes — no per-candidate materialization.**
   `f16_payload_negative_inner_product` (`rerank.rs:1089-1104`) reads 2 bytes/dim
   from the persisted payload and accumulates the dot product on the fly; no
   per-candidate `Vec<f32>` decode. Pinned by
   `f16_sidecar_payload_scores_without_materializing_source_vec` (`rerank.rs:1416`).
3. **No query-time f32→f16 re-rounding.** The `index` path
   (`rerank_probe_candidates_index_side`, `scan.rs:2386`) has no heap fetch / no
   source read; the query is rounded to f16 **once** in `prepare_query`
   (`rerank.rs:209`). The bogus 111g per-candidate re-round (`score_source_diagnostic`)
   is reachable only on `source_diagnostic` placement, never `index`.
4. **Direct-TID lookup, not O(N) chain.** Survivors resolve via posting-carried
   `rerank_tid` → group-header TID, deduped per unique group
   (`load_rerank_groups_by_header_tid`, `scan.rs:2828-2856`). The old ADR-079
   O(N) full-chain / heap-map-rebuild (~150 ms) is now only a fallback for
   postings lacking direct pointers. **This was the original "lot of work per
   query"; it is gone.**
5. **Per-query work is lean.** f16 scores from **borrowed** group slices
   (`scan.rs:2984-2987`), zero per-candidate allocations; the only owned copy is
   one `payloads` clone per *unique group* at load (`scan.rs:2903`), amortized
   across that group's survivors. No `payload_slab` copy (that's batch-only).

**So: efficiently processed now, and the residual cost is an inherent floor, not
redundant work.** f16's latency is dominated (~80-90%) by reading the extra
sidecar index pages — the f16 payload is `dimensions*2` bytes per vector
(`rerank.rs:176`) persisted on top of the IVF postings, so the index is ~14× the
f32 source column (3.2 GiB vs 226.8 MiB at 1M). The "f16 is slower" claim in the
audit (line 81) is therefore **legitimate and well-founded now** — f16 is I/O-bound
on its own storage bloat, not compute-bound on leftover work.

### The one removable residue (small) + the real architectural lever
- **f16 still scores SCALAR, not SIMD-batched.** `is_batched()` is false for F16
  (`rerank.rs:822`); RaBitQ/TurboQuant go through SIMD batch scorers, f16 does a
  scalar `.map().sum()`. A missed optimization (~10-20% of f16 compute), not
  redundant work — worth doing only if f16 is revived.
- **The dominant lever is placement, not scoring.** As a sidecar that
  *duplicates* the f32 source, f16 is structurally dominated by `source/f32`:
  identical recall, strictly more storage and I/O. f16 can only win if it
  *replaces* the f32 source (store f16 instead of f32 → ~half storage, near-lossless
  recall, index-only serving). The closeout's f16 verdict captures exactly this —
  "iterate only if f32 source storage is removed/replaced or f16 scoring/layout
  materially changes" (line 96). That framing is correct.

**Verdict on the f16 decision: sound and well-rationalized.** Do-not-promote is
right; the rationale correctly attributes the loss to storage duplication, not to
a fixable per-query inefficiency.
