# 111h — STOP before abandoning compressed rerank formats: the rabitq8 ceiling is an artifact of non-residual encoding, not the format's limit

Follow-up to `2026-06-20-01-reviewer.md`. Operator review flagged the rabitq8
recall ceiling as suspiciously low and asked that we probe each format to its
true recall/latency ceiling — even at higher latency — so the space is fully
explored before any promote/iterate/abandon call. I dug into the 100k artifacts
and the rerank codec; the suspicion is correct and has a concrete code cause.
**Do not record an abandon decision for rabitq4/rabitq8/turboquant on the current
data.**

## Evidence: the ceilings collapse to a shared plateau

Recall@10 ceiling at 100k (max over all width×nprobe in
`019/artifacts/results-report.jsonl`):

| format (index placement) | recall@10 ceiling | at |
| --- | ---: | --- |
| source f32 | 0.9990 | w128 np200 |
| f16 | 0.9980 | w128 np200 |
| **rabitq8** | **0.9520** | w64 np200 |
| **turboquant** | **0.9520** | w64 np200 |
| **rabitq4** | **0.9420** | w64 np200 |

f16            np8=0.7860 np32=0.9345 np64=0.9710 np128=0.9940 np200=0.9980

Two independent tells that this is a bug, not a fidelity floor:

1. **rabitq8 (256 levels/dim) beats rabitq4 (16 levels/dim) by ~1 point.** A 16×
   resolution increase buying 0.942 → 0.952 is not what a working 8-bit quantizer
   does. An 8-bit rerank of already-survivor candidates should be near f16/f32.
2. **rabitq8 ≡ turboquant across the entire nprobe curve** (0.9000/0.9315/
   0.9490/0.9520 — bit-identical at np32/64/128/200). Two different quantizers
   landing on the same plateau means a **shared upstream lossy step** is the
   bottleneck, not either format's bit depth. More nprobe cannot lift it (flat
   from np128→np200), so it is a quantization-fidelity ceiling.

## Root cause: rerank RaBitQ is non-residual with gamma discarded / zeroed

`src/am/ec_ivf/rerank.rs`:
- **Encode (line 177):** `let (_dimensions, _gamma, code) = quantizer.encode_source(source)?;`
  — `encode_source` is the **non-residual** path (it quantizes the raw vector, not
  the residual `o − c` against the assigned centroid), and the computed **gamma is
  discarded** (`_gamma`).
- **Score (line 242):** `quantizer.score_ip_from_parts(prepared_query, 0.0, payload)`
  — gamma is **hardcoded 0.0**.
- The codec is resolved non-residual at `rerank.rs:87`
  (`resolve_with_pq_group_size_and_bits(StorageFormat::RaBitQ, …, Some(bits))`,
  `rabitq_residual` defaults false).

RaBitQ is built around the **unit-normalized residual against the assigned IVF
centroid**, with gamma carrying the per-vector scale and the centroid added back
at score time — this repo documents exactly that
(`quantizer.rs:59-65`: "encode … residual `o − c` … scan adds the exact per-list
centroid … The non-residual `encode_source` path rejects RaBitQ-residual indexes
so a centroid is never silently dropped"). Feeding RaBitQ raw vectors with no
centroid and gamma=0 strips out the structure it depends on — which is precisely
why 8 bits barely beats 4 and both pin to ~0.95. TurboQuant at least *carries*
gamma (`rerank.rs:191-199, 254-255`) yet still pins to the same plateau, so the
non-residual/no-centroid choice is the dominant error, confirmed independently.

**The high-fidelity path already exists on this branch.** Task 115 added RaBitQ
residual mode: `rabitq_residual` flag, `encode_source_residual` /
`encode_code_residual` against the centroid, real gamma
(`quantizer.rs:131-256`). The 111h rerank codec simply does not use it. The
survivor's assigned list/centroid is known at rerank time, so a residual rerank
payload (encode `o − c`, carry gamma, add centroid at score) is feasible with the
existing machinery — this is wiring, not new math.

## What this means for the decision

The warm-cache suites (017/018/019) remain methodologically sound and the
*numbers* are real — but the **interpretation** "compressed formats lose
substantial recall" measures the non-residual encoder, not the formats. The
honest current decision is:

- **f16** — promote-candidate (recall-neutral; open question is its ~14× index
  footprint, a layout problem, not a fidelity one).
- **rabitq4 / rabitq8 / turboquant** — **iterate, do NOT abandon.** Their measured
  ceiling is not their real ceiling.

## Asks for the next slice (probe each format to its true ceiling)

1. **Fix the rerank RaBitQ encoder to residual mode**: encode the survivor's
   residual against its assigned centroid via the Task 115 machinery, carry the
   real gamma in the payload (as TurboQuant already does), and score with that
   gamma + centroid add — not `encode_source` + `0.0`. Re-check whether TurboQuant
   rerank should likewise be centroid-relative.
2. **Re-bench rabitq4/rabitq8/turboquant** (the existing isolated suite is enough;
   no new corpus) and compare ceilings against f16/f32. The acceptance question is
   whether residual rabitq8 approaches f16/f32 recall at materially smaller
   storage than f16's ~14× index.
3. **Then** build the matched-recall table (the P2 from seq-1): at fixed recall
   ≈0.97 and ≈0.99, compare each surviving format's latency + total storage. Per
   operator guidance, push nprobe/width far enough to actually *reach* those recall
   targets for each format (accept the higher latency — the point is to map the
   full frontier, not stop at the standard grid's last point).

This keeps the goal the operator stated: explore the space fully so the next-step
decision is well-informed, rather than abandoning formats on a number a known
encoder choice depressed.
