Per the A/B-attribution rule, a fix that moves the bar by ≤0.005 (and makes

**8-bit RaBitQ (0.9525) barely beats 4-bit (0.9380)** — a 16× resolution increase
buying ~1.5 points. That is the tell that bit depth is not the binding constraint.

## Root cause (verified by code trace): estimator variance + fixed ±2σ clip, not encoding

1. **The index-side RaBitQ rerank scores through the asymmetric *estimator***
   `estimate_ip_scalar_only` (`quantizer.rs:385` → `rabitq.rs:~4570`), a statistical
   estimate of ⟨q, o−c⟩ whose error floor is set by estimator **variance**, not by
   the code's bit depth. A reranker's whole job is to reorder an already-close
   survivor frontier (cosines within ~1e-3); the estimator's variance can't resolve
   those near-ties, so recall plateaus ~0.95 at any bit depth. f16/f32 reach 0.998
   because they compute the **exact** inner product (`rerank.rs:907-938`) and *can*
   reorder near-ties. This single mechanism explains both "residual didn't help"
   and "8-bit ≈ 4-bit."
2. **Fixed clip = 2.0** (`RABITQ_DEFAULT_QUANT_CLIP`, `rabitq.rs:79`): the ~5% of
   N(0,1) mass beyond ±2σ is truncated identically at 4- and 8-bit, so the extra
   levels are spent inside a range whose clip-truncation (bit-independent) is a
   binding error term.

So **~0.95 is a property of the chosen estimator + clip, not a proven RaBitQ-rerank
limit.** The v7 numbers are real and the fixes are sound — but they rest on the
false premise that a finer RaBitQ *code* yields a finer *reranker*.

## Two untested levers already exist in the tree — do NOT abandon compressed rerank yet

Both are present and unused on the IVF **index** path:
- **Exact dequantized scoring.** `exact_score_mode()` exists
  (`quantizer.rs:299`). Score rabitq8 survivors via an exact dequant dot product
  instead of `estimate_ip_scalar_only`. f16 proves exact scoring resolves near-ties
  at ~0.998; an exact-dequant rabitq8 should land much closer to f16 than 0.95.
- **Wider clip.** The kernel takes an explicit clip (`with_bits_clip`,
  `rabitq.rs:330`) and the bench harness *already* defines `rabitq8c3`/`rabitq8c4`
  (clip 3.0/4.0, `crates/ecaz-cli/src/commands/bench/sidecar_rerank.rs:41-61`) —
  but those knobs are wired only into the standalone sidecar surface, and **no v7
  suite ran them against the index format** (grep of committed suites: zero hits).
  The index path is hardwired to clip=2.0.

### Ask for the next slice (cheap, high-value, before any abandon call)
Run a small index-path A/B at 100k (existing isolated suite, no new corpus):
rabitq8 with (a) exact-dequant scoring and (b) clip ∈ {2,3,4}. Decision rule:
- if either lifts the ceiling toward f16 (~0.99) → compressed rerank is **viable**
  at a fraction of f16's ~14× index footprint — that's the actual win 111h is
  chasing, and it changes the promote/abandon call;
- if both stay ~0.95 → abandon is now **evidence-backed** rather than an artifact,
  and you can close the compressed formats with confidence.

This keeps the operator's stated goal — explore the space fully so the decision is
informed — rather than abandoning on a number the estimator/clip depressed.
