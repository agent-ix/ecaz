# 111h — Packed rerank-group architecture: correctness review (slices 001–008)

Static/read-only review of the committed 111h slice stack on
`bench-ivf-111g-115-attribution` (`a3b6eda24` → `e35538066`). **Benchmarks are
explicitly out of scope for this pass** (Phase-3 matrix is env-blocked on the
review box and is the gating closeout item); this review covers code correctness
of the persisted packed-group layout only. The 008 packet's stated review focus
(direct lookup / fallback scan / deleted-slot exclusion) is answered under

stack since the slices form one architecture.

## Verdict

**No P1 correctness bugs found.** The packed rerank-group codec, build/insert/
vacuum consistency, scan-side direct-pointer lookup, codec dispatch, and the
no-query-time-source-conversion invariant for the index path all hold up under
read review. The encode path is overflow-guarded and self-validates by
decoding + `validate_offsets()` before returning; decode enforces exact-length
(`input.len() == payload_end`) with monotonic, in-bounds slice math; the v4→v5
format break is clean (fixtures + upgrade matrix + v4-rejection test updated per
NFR-016/Task 42); padding to scorer width happens only at scoring time and never
persists or scores deleted/padded slots. This is solid work — the implemented
slices are correct.

The open items below are **P2/P3**, and most map to task-111h checklist lines
the coder has **not** yet checked (benchmarks, table-owned storage, copy
elimination, decode/score timing, mixed-posting end-to-end fixtures). So this is
"correct as far as it goes, here are the next steps and a few cleanups," not a
blocking review.

## 008 review focus — confirmed correct

- **Direct posting-carried TID lookup** (`scan.rs` `rerank_group_payload_for_heap_tid`,
  ~2805): resolves a survivor's slot by scanning `0..valid_count`, skipping
  `is_deleted(index)`, matching the heap TID within the slot's
  `heap_tids[start..end]`, returning `payloads[payload_offset..+payload_len]`.
  Build (`build.rs:1054`) and insert (`insert.rs:261`) write offsets sequentially
  in posting order via `from_single_heaptid_postings`, and scan reassembles
  `payloads = header.payloads ++ segments` in chain order, so offsets index the
  reassembled buffer correctly. No payload/TID mismatch.
- **Fallback scan with INVALID direct TID**: direct pointers are used only when
  *all* candidates carry a valid `rerank_tid` (`scan.rs:2556`); otherwise the
  batch loads every group via `load_rerank_groups_full_chain`, so the fallback
  group-iteration always has the group present. Logic is sound.
- **Deleted-slot exclusion**: vacuum only flips the header deleted bitmap
  (`vacuum.rs:232`), never compacting the `valid_count`-length metadata arrays, so
  offsets stay aligned; scan skips `is_deleted` slots. A recycled heap line
  pointer cannot be matched to a stale payload. Covered by
  `rerank_group_payload_lookup_skips_deleted_group_slots`.

The packet is also correctly scoped — the Non-Claims section properly disclaims
benchmark evidence and the remaining PG18 lifecycle fixtures.

## P2 — worth addressing

### P2-1. Concurrent-insert chain-orphan window (carried forward from 111g)
`insert.rs:259-271` + `insert.rs:198-205`. `append_rerank_sidecar_entry` reads
`metadata.rerank_sidecar_head` via a plain `read_metadata_page`, freezes the new
group's `next_group_tid` to that value, then a *separate* `update_metadata_page`
sets `rerank_sidecar_head = rerank_tid` unconditionally — it does not re-link to
the head observed under the exclusive metadata lock. Two concurrent backends
inserting into the same index can both observe head `H`, both set
`next_group_tid → H`, and the last metadata writer wins; the other group becomes
unreachable from `rerank_sidecar_head`.

Hot-path scan is unaffected (each survivor resolves via its own posting-carried
direct `rerank_tid`). The orphan only hurts (a) `bulkdelete_rerank_groups`
chain-walk tombstoning and (b) the full-chain fallback loader, and defers page
reclaim to REINDEX. This same read-stale-head/prepend pattern existed in the
111g `0x2A` path and is preserved verbatim, so it is **not a regression** — but
since 111h is rebuilding this layer it is the right time to fix it by re-linking
`next_group_tid` inside the `update_metadata_page` read-modify-write closure
under the exclusive lock.

### P2-2. Index-side batched path is still the owned-copy + double-copy "legacy baseline"
`scan.rs:2592-2604` + `LoadedRerankGroup.payloads` (`header.payloads.clone()` at
`scan.rs:2753`). For batched formats (RaBitQ-4/8, TurboQuant) the path loads each
group's full payloads into an owned `Vec<u8>`, then copies each survivor slice
again into `payload_slab` before batch scoring. This is exactly the
"copy each survivor into a Vec then copy again into a batch slab" pattern the
task flags as a legacy baseline rather than the final page-local-slice layout.
It is correctly instrumented (`record_rerank_payload_slab_bytes_copied`, asserted
`== 0` for the non-batched f16 path), so it is measurable — which the task
requires — but should not be mistaken for the final compact layout. Matches the
still-unchecked checklist line "Implement or explicitly benchmark away owned
per-survivor payload copies and double-copy batch-scoring slabs." Flagging so the
benchmark narrative attributes any compact-format loss correctly.

### P2-3. EXPLAIN: `decode time` / `scoring time` not isolated (matches unchecked checklist)
`scan.rs:1730-1746`, `explain.rs:437-447`. Only two stage timers exist:
`stats_approximate_scan_elapsed_us` and `stats_exact_rerank_elapsed_us`. The
exact-rerank timer wraps the *entire* `rerank_probe_candidates` call — group page
reads + payload decode + scoring fused into one number. The task asks for
separate decode-time and scoring-time; those are the genuine gap (checklist line
still unchecked, correctly). Note: **pages-read and payload-bytes ARE wired**
(`RerankGroupReadStats`, `scan.rs:2648-2671`, with a real metadata-bytes vs
payload-bytes split computed from decoded tuples) — so only the two timing
sub-metrics are missing, not the whole counter line.

### P2-4. `payload_bytes_scored` duplicates `source_bytes_read` on the index path
`scan.rs:2622-2628`, comment `explain.rs:135-138`. On the index path both
counters are recorded with the **same** accumulated sum, so the comparison the
comment advertises ("compare scored-width with source_bytes_read") is trivially
1.0 and proves nothing; on the source path `payload_bytes_scored` stays 0. Either
make `payload_bytes_scored` reflect a genuinely distinct quantity (e.g. scored
width vs bytes physically read) or drop it and adjust the comment.

## P3 — hardening / coverage / cleanup

- **`IvfRerankGroupHeaderRef` accessors panic on bad input** (`page.rs:1660-1702`).
  `gamma()`/`heap_tids()`/`payload_offset()` etc. slice with `[start..start+N]`
  and `.expect()`, safe only if `validate_offsets()` ran and `index < valid_count`.
  `Ref::decode()` does **not** call `validate_offsets()` (only the `Tuple` path
  does). All current callers go through the validated `Tuple` path, so this is
  latent — but the zero-copy `Ref` accessors are exactly the page-local-slice
  surface the task wants scan to migrate to, and that migration would expose the
  footgun. Fold `validate_offsets()` into `Ref::decode()` or document the
  precondition.
- **No cycle/bounds guard on `next_group_tid` chain walkers** (`page.rs:1564-1567`;
  vacuum/fallback walkers). The payload-*segment* loop self-terminates via a
  byte-count ceiling (good), but the *group* chain has no length ceiling or
  visited-set; a corrupted/cyclic `next_group_tid` would loop indefinitely in any
  full-chain walker. Add a bound when the live fallback/vacuum walkers are
  exercised.
- **Coverage gap: full-chain fallback / mixed-posting path has no end-to-end test.**
  `rerank_group_payload_lookup_uses_direct_tid_and_fallback_scan` exercises the
  in-memory fallback branch, but no pg_test produces a real scan where some
  survivors carry INVALID `rerank_tid` (coalesced/multi-heaptid postings under
  index placement) forcing `load_rerank_groups_full_chain`. Insert/vacuum pg_tests
  stay on the single-heaptid direct-TID path. Aligns with the unchecked checklist
  line "cover ... mixed postings that cannot carry an unambiguous direct pointer."
- **Coverage gap: no scan-level test for a partial final group** (`valid_count <
  scorer_width`) — padding is only exercised indirectly via the
  `from_single_heaptid_postings` unit path, not end-to-end.
- **Dead `0x2A` sidecar loaders left unreferenced** (`scan.rs:2850/2909/2944`,
  plus `read/rewrite_ivf_rerank_sidecar_block*` in `page.rs`) — no live or test
  callers after the switch to packed groups. Remove or annotate
  retained-as-baseline so a future reader doesn't think `0x2A` is still a read
  path. (Per repo convention I am flagging, not deleting.)
- **O(valid_count) per-survivor linear lookup** within a group
  (`rerank_group_payload_for_heap_tid`). Correct; with scorer-width groups and
  many survivors per group the total is O(survivors × valid_count). Not
  load-bearing for correctness; a sorted/indexed in-group lookup would remove the
  quadratic factor if it shows up in the bench.
