# 111h Final Closeout — Architectural Review: NOT READY TO CLOSE

Full architectural review of the closeout claim (`537c16ca8 mark persisted rerank
sweep complete`), covering decision soundness, architecture quality, gaps,
alternate designs, pitfalls, and goal achievement. Verdict up front:

**The engineering is done and good. The *decision* is not honestly closeable —
two of the three compact-format abandons rest on a configuration the closeout
itself calls "misleadingly pessimistic." Close requires a corrected full
10/50/100/1M sweep, not just a status flip.**

## Did we reach our goals?

- **Engineering goals — YES.** Common rerank codec (f16/rabitq4/rabitq8/TQ behind
  one interface), scorer-width packed `0x2B`/`0x2C` layout, clean
  source/index/table/source_diagnostic placement model, v8 format with fixtures +
  upgrade matrix, PG18 lifecycle correctness, full warm matrix via `ecaz bench
  suite`. All genuinely met.
- **Decision goal — NO.** The task's binding bar: "not closeable until every
  format is implemented and benchmarked **or rejected by packet-local evidence
  showing a concrete correctness or layout blocker**." A decision string exists
  for every format, so the bar is met *in form*. It is **not met in substance for
  rabitq4** and is **under-substantiated for rabitq8 and TurboQuant** (below).

## The central flaw — premature abandon on the wrong config (repeats the trap the task was written to prevent)

Packet 036 proved the default `rabitq_rerank_clip=2` is "misleadingly pessimistic":
rabitq8 @ nprobe200 goes **0.9525 (clip2) → 0.9830 (clip3) → 0.9915 (clip4)** at
*identical* 183.6 MiB index size. clip4 ≈ f16 recall (0.998) at ~half f16's index
(183.6 vs 330 MiB @100k). The lever is real and decisive.

But the closeout applies that lesson **asymmetrically**:

- **rabitq4 → ABANDON is not evidence-backed.** Clip is wired for rabitq4 on the
  *same code arm* as rabitq8 (`rerank.rs` `RaBitQ4 | RaBitQ8 => new_with_clip`),
  default 2 (`options.rs EC_IVF_DEFAULT_RABITQ_RERANK_CLIP=2`). Every rabitq4 cell
  in the entire 10k/50k/100k/1M matrix ran at clip=2 (grep: zero rabitq4 cells set
  clip 3/4). rabitq4 sits at 0.938–0.946 — squarely in the band a +0.03–0.04 clip
  lift would move, and it is the *smaller* index. It was abandoned without the test
  that rescued its sibling. This is exactly the premature-abandon trap.
- **TurboQuant → ABANDON, but with NO lever ever applied.** Answering the operator
  question directly: TQ got a **good spread across scale/width/nprobe** —
  10k/50k/100k/1M × widths {32,64,128,256} × nprobe {8…200}, ceilings 0.9815 /
  0.9600 / 0.9565 / 0.9510 respectively. But TQ has **no clip or score-mode knob at
  all** (both are gated to rabitq4/8); it was only ever scored through its single
  default estimator path. So its abandon rests on one un-tuned configuration, with
  the decisive fidelity lever neither exposed nor tested.
- **Worse, the deeper lever was never run on *anything*.** The 024 finding named
  *two* levers: wider clip **and** exact-dequant scoring (`quantizer.rs:299
  exact_score_mode()`). Only clip was tested, and only on rabitq8. Exact-dequant —
  the apples-to-apples-with-f16 scorer — was never run on rabitq4, rabitq8, or TQ.
- **rabitq8 → "iterate not promote"** is the most defensible of the three, but it
  has **no matched-recall comparison vs f16** (the 029 matched-recall table predates
  clip4 and contains only clip2 rabitq8 rows). The comparison that actually decides
  promote-vs-iterate — rabitq8-clip4 vs f16, *index-only*, at recall 0.97/0.99 —
  does not exist. And the "didn't beat source/f32" rationale uses the wrong frame:
  source/f32 needs the heap f32 vector; an index-only compact payload's value
  proposition is precisely *not* paying for that. The right disqualifier is "vs
  f16," not "vs source/f32."

Net: 2 of 3 compact abandons (rabitq4, TQ) rest on un-swept levers; the iterate
verdict (rabitq8) lacks its deciding comparison. The promote of source/f32 and the
reserve of `table` are sound.

## Gaps — the missing numbers

1. **rabitq4 clip sweep** {2,3,4} — cheap, reuses the 036 harness.
2. **A TQ fidelity lever** — either expose a TQ-analogous tuning knob or run
   exact-dequant scoring for it; today TQ has none.
3. **Exact-dequant scoring** for all compact formats (the second 024 lever, never run).
4. **Matched-recall vs f16, index-only, at 0.97/0.99** for each format at its *best*

5. **clip breadth** — clip evidence is width=64, 100k (+50k cold) only; no 10k/1M,

6. **Cold/remote IO** — single-sample, local `posix_fadvise` eviction, 50k only;
   a directional probe being asked to carry a promotion axis.

## Alternate designs worth a follow-up (from the architecture pass)

- **Insert mints 1-wide groups** (`insert.rs append_rerank_group_entry` →
  `from_single_heaptid_postings` of one survivor per block). The scorer-width
  packing that justifies the whole `0x2B` layout is realized only at build time;
  every post-build insert defeats it and bloats the index. Format-independent
  latent perf/bloat bug — worth fixing regardless of which format wins.
- **f16's ~14× blowup is inherent to duplicating the heap source at half precision**,
  not to the layout. The untested f16 hypothesis is index-only-serving: store f16
  *instead of* the f32 source, not in addition. That's the only path to an f16 win.
- **Non-uniform payload framing** — gamma is in-payload for TQ, discarded for
  RaBitQ, absent for f16; the header *already* stores per-entry gammas
  (`page.rs`), so TQ's in-payload gamma is redundant. A single "code + header
  metadata + centroid correction" contract would collapse three score paths into
  one (needs the borrowed arithmetic-estimator API that packet 038 deferred).
- **clip should be a first-class quant knob**, not rerank-only — it materially
  helps recall and the main storage path can't reach it.

## Pitfalls that WERE handled well

- **ALTER footgun genuinely closed** — clip + score_mode now read from v8 metadata
  (`scan.rs:628-629` overrides reloptions), so `ALTER INDEX SET (clip=…)` without
  REINDEX can no longer silently mismatch. v8 rejects v7. Clean.
- **v8 format integrity** is fully consistent (fixture, upgrade matrix, size
  assertions, docs, version rejection tests).
- **Data integrity** — every number spot-checked across packets 024/027/028/029/036
  traces exactly to committed `results.jsonl`; no fabrication, no untraceable cell.
- **1M shared-table** is time-isolated to one index per cell with `--force-index`
  (planner-contamination risk neutralized) and disclosed — acceptable.
- **Decode/score stage timers** are wired (not stubs).

## Recommendation (per operator closeout policy)

We are near the end of the line and still missing numbers, so per the standing
rule, **close on a full corrected sweep, not a status flip:**

1. **Lock the right config at 10/50/100k first.** Sweep clip {2,3,4} (and the
   exact-dequant lever) for **rabitq4 and rabitq8**, add a fidelity lever for
   **TurboQuant** (or run exact-dequant for it), and produce the **matched-recall
   vs f16 index-only** table at 0.97/0.99. This makes every abandon/iterate/promote
   rest on each format's *best* config — which is exactly the task's no-deferral
   bar (reject only on a concrete blocker at best config).
2. **Run 1M last, once the config is locked and we're genuinely ready to close** —
   don't spend a 1M run on an intermediate config. The current 1M (clip2,
   shared-table) is fine as a directional baseline but should not be the closeout
   1M.
3. Only then flip the task to complete.

The headline outcome may well stand (source/f32 as default; compact formats not
promoted) — but right now it would be *concluded*, not *demonstrated*, for rabitq4
and TQ. One corrected sweep converts "abandoned on the wrong clip" into a real,
defensible decision.
