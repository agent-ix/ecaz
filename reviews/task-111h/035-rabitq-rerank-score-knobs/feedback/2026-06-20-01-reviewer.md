# 111h/035 — RaBitQ rerank score knobs: APPROVED for the A/B; trustworthy as long as each cell is a fresh CREATE INDEX

Fast, well-scoped response to the 024 feedback. The two index-path levers
(`rabitq_rerank_least_squares=0|1`, `rabitq_rerank_clip=1..8`, default
estimator/clip=2) are correctly wired and the A/B they enable will produce
trustworthy numbers. Deep-traced; findings below.

## Verdict: correct for the bench workflow

- **Clip encode/score consistency is GUARANTEED within a fresh build.** Clip is
  single-sourced from the persisted reloption at both ends: encode
  (`build.rs:944`, `insert.rs:256`) and score (`scan.rs:2367-2368`) both read
  `rabitq_rerank_clip` from `relation_options` and thread it into
  `new_with_clip → cached_seeded_srht_bits_clip`, so the encode levels
  (`rabitq.rs:505`), dequant LUT, and prepared-query dequant all derive from the
  same clip. The quantizer cache key now includes `quant_clip_bits`
  (`rabitq.rs:83-87,313`), so two indexes with the same dim/seed/bits but
  different clip do not alias. No corruption path in the standard
  one-CREATE-INDEX-per-variant flow.
- **Least-squares dispatch is correct.** Scalar and batch both route to
  `estimate_ip_least_squares_scalar_only` (`rerank.rs:346-349, 558-595`); the
  batch path loops scalar LS rather than silently falling back to the estimator
  kernel, and the residual centroid-IP correction (`score -= centroid_ip`) is
  preserved for the LS path (`rerank.rs:794-880`, gated on `residual:true`
  independent of score_mode). The request's "scalar LS, no LS batch kernel"
  non-claim is accurate and harmless for correctness.
- **Reloption validation is correct.** Knobs are rejected outside
  `coarse_rerank` + rabitq4/8 (`options.rs:207-216`), clip is range-checked
  1..8, LS flag is 0/1, and defaults (estimator, clip=2 ==
  prior `RABITQ_DEFAULT_QUANT_CLIP`) leave existing indexes and all prior
  benchmark cells bit-identical.
- **No format bump needed** (clip changes level values inside an unchanged byte
  layout, per-index reloption). No no-op knobs: tests prove clip=2≠clip=4 payload
  bytes and estimator≠LS scores (`rerank.rs:728-788`).

## Findings

### P2 — clip/score_mode are not baked into metadata; `ALTER INDEX` is a silent-mismatch footgun
`page.rs:636-714` (`MetadataPage`) persists `storage_format/quant_bits/
rabitq_residual` but **not** clip or score_mode; the rerank scorer reads them
from live reloptions (`scan.rs:2367-2368`). PostgreSQL accepts
`ALTER INDEX ... SET (rabitq_rerank_clip = 4)` on a clip=2-built index without a
rebuild (only the 1..8 min/max is enforced), after which scan decodes clip=2
payloads with a clip=4 LUT → **silently wrong rerank scores**. The bench is
immune (fresh CREATE INDEX per cell, never ALTER), so this does not threaten the
A/B — but it should be guarded: reject these two reloptions under ALTER (require
REINDEX), or bake clip/score_mode into metadata like `quant_bits`. At minimum,
document them as build-time-only.

### P3 — docs note missing
`docs/on-disk-format.md` doesn't record that `coarse_rerank` rabitq payload
*values* now depend on the build-time `rabitq_rerank_clip` reloption (ties to the
P2 ALTER footgun). One line would close it.

## Decision-logic caveat — what this A/B can and cannot conclude

This wires the **least-squares** scorer (a lower-variance estimator already in
the tree), not a full materialized exact dequant-dot — the request says so
honestly. That bounds the inference from the upcoming results:

- If **LS + clip{3,4}** lifts the rabitq8 ceiling toward f16 (~0.99) → the
  estimator-variance theory from 024 is confirmed and compressed rerank is
  viable at a fraction of f16's ~14× index; **promote-iterate**, run the matched
  recall/latency/storage table.
- If LS + clip falls short → that is **not yet** sufficient for abandon. The
  definitive apples-to-apples test against f16 is an **exact dequant-dot** scorer
  (f16 wins precisely because it scores the exact inner product), which the
  packet correctly scopes as a separate, not-yet-built lever. Only if exact
  dequant-dot ALSO plateaus near 0.95 is abandon evidence-backed. So if the LS
  A/B disappoints, the next slice is the exact dequant-dot lever, not a decision.

In other words: the metrics this enables are necessary, and may be sufficient if
LS wins — but if LS loses, one more lever is required before the decision. Worth
stating in the eventual decision packet so "LS didn't help" is not mis-read as
"compressed rerank can't work."
