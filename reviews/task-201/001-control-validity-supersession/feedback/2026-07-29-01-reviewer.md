# Task 201 scope challenge: the frozen control is inadmissible

**Bucket disambiguation.** This bucket is the **ec_distann** Task 201
(`plan/tasks/201-ec-distann-post-replica-latency-residual.md`). Task 201 is
double-allocated: `origin/main` carries an unrelated
`201-task38-interrupt-poll-followups.md`. Per the convention `StR-008` already
uses for the 141--146 collisions, cite by explicit branch and path.

## Finding

Task 201 cannot be executed as written. Its **Frozen control** section places the
Task 199 coordinator traversal replica inside the control:

> ":34 - Task 199 normal-build coordinator traversal replica, when an explicit
> Ready image exists, with unchanged owner fallback;"

and its scope rules forbid the questions that would expose the problem:

> ":43-44 No Task 185/186 head change, Task 188 BW8 change, graph rebuild,
> neighbor codec change, replica format/lifecycle change, or new benchmark
> selector may enter the control or candidate screen."

> ":113 (non-goals) repeating Task 199's already accepted aggregate replica A/B"

The replica holds `(vec_id, owner_ordinal, graph_record, exact_vector)` for every
vec_id from every owner — full-precision f32 plus the complete graph record,
measured at 1,659,518,976 bytes at 100k, linear in N, resident on one
coordinator (`src/am/ec_distann/traversal_replica.rs:275`; `FR-084` "for every
vec_id in the active generation").

Consequences:

1. It does not satisfy `NFR-021` (no single node holds index state growing with
   corpus cardinality), so under `NFR-022` it is inadmissible as the control
   against which a PROMOTE/STOP is recorded.
2. A latency attribution against it measures a single-node Vamana index with a
   distributed row store attached — the distributed read path is not under test.
3. The task is *structurally* unable to report this, because replica design and
   format questions are ruled out of scope in advance.

This is not a criticism of the task's author. Task 201 faithfully inherited the
control the roadmap recorded as "the current latency control" after Task 199's
promotion. The defect is upstream, in that promotion.

## Also inherited

Task 201's Why section (`:13-15`) carries forward "unchanged storage between the
owner and replica arms". That claim is not a measurement. The suite's storage
step computes its scalars **before** the arm loop
(`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:5153-5160`) and
reprints them **inside** it (`:5209-5212`), so the arms are byte-identical by
construction. The replica's 1.66 GB and ~1.94 GB of WAL reach only a log-only
metric that never enters `results.jsonl`. Task 204 fixes the runner.

## Disposition

**SUPERSEDED by Tasks 205 and 206.** The latency lane is now:

- **205** — Algorithm 1 expansion pushdown (coordinator-derived threshold `t`,
  candidate limit `l`, owner-side prune/sort/truncate), A/B at fixed BW=4/H=100.
- **206** — the traversal regime (wide beam, few rounds), blocked on 205.

Both are controlled against the **owner-traversal arm** (18.3/20.4/19.9 ms at
10k/50k/100k), which is the conforming baseline restored in the roadmap ledger.

## What should be reused, not discarded

Task 201's **Phase 1 attribution decomposition** (`:54-63`) is a good contract
and should be carried into 205/206 rather than re-authored: local traversal and
frontier/merge work; owner-side payload SQL, heap lookup, detoast, encode, and
transport wait; coordinator decode, datum ownership, copy, output association,
and executor residuals; connection/session setup and reuse; remote payload
rows/bytes, exact reads, candidate work, and tails; RSS and allocation behavior.
Its entry-gate discipline — fresh committed PG18 release, byte-identical
generation, diagnostic counters only in a separately labeled instrumentation run
— should also carry forward.

Only the control was wrong.
