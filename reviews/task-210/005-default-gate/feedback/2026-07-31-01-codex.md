## Findings

### P1 — The explicit zero-byte distribution gate is still not met

`plan/tasks/210-ec-distann-distribution-restoration.md` requires every P2a and
P2b arm to report `outstanding_distribution_gap=none` and coordinator head bytes
to reach zero. The packet's own manifest reports 53,440 bytes of
`ec_distann_generation_head` at 10k, 50k, and 100k, and leaves those empty
neighbour rows on `NFR_021_KNOWN_DISTRIBUTION_GAPS`.

This is also intentional in the implementation: `build_coordinator/t2.rs`
persists `DistannPersistedHeadGraph { entry: 0, neighbors: vec![Vec::new();
head_sample.entries.len()] }` when shard storage is enabled. Empty graph rows
are still corpus-sized coordinator state, so the measured constant is a useful
bounded-state result but cannot be reported as the task's stated zero-byte
closeout.

Please remove the graph-row persistence and update the load/manifest/state
shape to represent a membership-only coordinator head, then rerun the required
10k/50k/100k P2a and P2b recall, latency, and storage A/Bs. If the intended
acceptance has changed to allow these rows, that needs an explicit task/spec
decision rather than retaining `outstanding_distribution_gap` while declaring
the gate passed.

### P2 — Replica materialization rebuilds with the serving node's ordinal

The replica path in `generation_read.rs` calls both `owner_head_shard_key()` and
`build_owner_head_shard()` with `self.generation.owner_ordinal`. On the normal
owner path that is the shard ordinal, but on a replica path it is the serving
node's local generation ordinal, which can differ from the imported shard's
actual owner ordinal. `build_owner_head_shard()` folds that ordinal into the
graph seed, so the same replica vectors can produce a different graph topology
and cache key on different serving nodes.

The remote `DistannPhysicalHeadRequest` carries member IDs but no shard/owner
ordinal, and `replica_head_vectors()` selects the vectors without validating or
returning the stored `shard_ordinal`. Consequently the serving node has no
authoritative shard ordinal to use. This undermines the claimed replica of a
shard and is consistent with the packet's replica recall being lower at 50k and
100k (`0.9540/0.9265` versus the default `0.9545/0.9290`), even though it is
within the current CI tolerance.

Pass the actual shard ordinal through the physical request/endpoint (or derive
it from an authenticated replica record), validate imported rows against it,
and use it for the shard key and graph seed on both owner and replica paths.
Then add a focused owner-versus-replica graph/seed equivalence check and rerun
the replica A/B matrix.
