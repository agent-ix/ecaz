## 1. The storage half of head sharding is inert (acceptance criterion 1 fails)

The candidate arm's coordinator storage row at 100k is byte-identical to
control — the full-precision landmark vectors are still coordinator-resident:

    variant=candidate-sharded-head ... node=coordinator
      head_sample_bytes=25280512 head_graph_bytes=614095
      coordinator_resident_unsharded_bytes=25894607

Expected `~0` / membership-only. `ec_distann.shard_head_storage` has exactly
one reader (`build_coordinator/t2.rs:742`), and the fixture sets it via `SET`
in the session that runs `CREATE INDEX` — but the persisted head still carries
full vectors, so either the T2 stage does not run on that session (GUC not
visible where it is read) or the flag is read and not applied. This is
failure mode #2/#1 territory: the mechanism shipped, the arm ran, and only the
itemised emitter (P0) caught that nothing changed. Needs a diagnosis + an
activation check (e.g. assert the persisted head_sample row width matches the
membership-only format when the option is on) before any rerun.

## 2. Candidate latency is ~196× control: per-query owner shard rebuild

    100k control-local-head:      mean_ms=36.40  p50_ms=34.10  p95_ms=48.00
    100k candidate-sharded-head:  mean_ms=7148.30 p50_ms=6988.70 p95_ms=8020.70

`RetainedGenerationScan::head_search` calls `build_owner_head_shard(...)` on
**every RPC** — a Vamana build over the owner's ~C/owners landmarks per owner
per query. The shard is epoch-immutable and deterministically seeded from the
epoch fingerprint, so it must be built once per epoch per owner and cached
(same lifecycle as the retained-epoch cache), not rebuilt per query. Recall
is fine (0.9290 vs 0.9275 control), which confirms the search itself is
correct — only the rebuild placement is wrong.

## 3. P2b replica arm hard-fails: replica-side serving was never implemented

`sweep-head-replica2-100k` failed the suite:

    ERROR: [EC_PLACEMENT] vec_id 0x17af90eae695e82a belongs to roster ordinal 1, not 0

`head_shard_server()` redirects a shard's search to a replica node, but the
server-side `ec_distann_head_search_physical` → `validate_ownership` rejects
members the node does not own — and even without validation it would
`resolve_nodes` against its **local** directory, which does not hold them.
`ec_distann_head_shard_export` (the P2b export endpoint) has **zero callers**.
Either implement replica import/serving (replica pulls the bounded shard from
the owner via the export endpoint, caches it epoch-scoped, serves it without
ownership validation of non-owned members) or drop the
`head_replica_count=2` step from the config until serving exists.
