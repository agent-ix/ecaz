Reviewed `333c51fe4` ("spire: rerank overfetched leaf routes by leaf score").
This is the slice that makes route overfetch semantically active. The
collect→rerank→truncate logic is correct and the default α=1.0 path stays
behavior-compatible. All four review-focus points confirmed.

## Review-focus assessment

1. **α-overfetch considers up to `max_leaf_routes` unique leaves before
   trimming** — CONFIRMED. `select_leaf_routes_with_row_budget` dedups by
   `seen_leaf_pids.insert` and breaks only when `seen_leaf_pids.len() >
   max_leaf_routes` (= `ceil(α·nprobe).min(leaf_count)`). The former in-loop
   `routes.len() >= selected_leaf_routes` early break was removed, so collection
   now fills the full cushion before any trim.

2. **Final trimming uses leaf-score rerank and returns ≤ effective nprobe** —
   CONFIRMED. After the loop:
   `if routes.len() > selected_leaf_routes { routes.sort_by(leaf_route_leaf_score_cmp);
   routes.truncate(selected_leaf_routes); }`. `leaf_route_leaf_score_cmp` orders
   by `leaf_score` desc → `route_score` desc → `parent_pid` → `leaf_pid`
   (deterministic). `selected_leaf_routes == nprobe.min(leaf_count)`, so the
   returned set is exactly the top-nprobe-by-leaf-IP of the overfetched pool.
   The new `SpireRecursiveLeafRoute.leaf_score` field carries the exact leaf IP
   (`route.score`) independently of the visible `route_score`, so accumulated
   (path-score-ordered) collection can still rerank by leaf IP — the Phase-1
   mechanism, implemented faithfully.

3. **Default α=1 behavior-compatible** — CONFIRMED. At α=1.0,
   `max_leaf_routes == selected_leaf_routes == nprobe`; collection stops at
   `nprobe` unique leaves, `routes.len() (==nprobe) > selected_leaf_routes
   (==nprobe)` is false, so the rerank/truncate block is skipped entirely.
   Result set and ordering are identical to pre-333c51fe4. Verified in the 003
   10k A/B: baseline `(off,1.0)` recall matches the pre-change expectation and
   the precheck shows `route_overfetch_multiplier = 1`.

4. **Ready for the release A/B packet** — YES; consumed by packets 003/004/005.

## Correctness details checked

- **Rerank always by leaf score, both ranking modes:** `leaf_route_leaf_score_cmp`
  uses `leaf_score` regardless of `SpireLeafRouteRanking`, which is the intended
  "route-order collect, leaf-IP rerank" semantics for the accumulated-score
  overfetch variant. Correct.
- **Non-recursive / snapshot paths seed `leaf_score` sensibly:** root-object and
  quantized-probe constructions set `leaf_score = route.score` / `-distance`
  (matching `route_score`); the snapshot/`selected_leaf_routes_from_snapshot`
  paths seed `leaf_score = 0.0`. Those paths do not overfetch
  (`routes.len() > selected_leaf_routes` is not reached), so the `0.0` seed is
  never used as a rerank key. Acceptable, but a brief comment noting "unused;
  these paths never overfetch" would prevent a future footgun if overfetch is
  ever wired through them.
- **`stopped_by_max_leaf_routes` bookkeeping** is set both on the cushion-break
  and on post-loop truncation — consistent.

## Findings

### Finding (LOW) — `leaf_score = 0.0` seed on non-overfetch paths is a latent footgun
See above. Not a defect today (those paths never trigger the rerank), but if a
future change lets a snapshot/quantized path overfetch, all `leaf_score`s would
tie at 0.0 and the rerank would silently fall back to `route_score` order.
Recommend a one-line comment or debug-assert that these paths run with
`selected_leaf_routes == max_leaf_routes`.
