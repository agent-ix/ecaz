## Two metrics to get (prioritized; keep them cheap)

1. **Matched-recall baseline comparison (must-have).** Every 111e number is
   *recall-at-fixed-latency*; the closeout has no *latency-at-fixed-recall*
   comparison. So we can say "coarse_rerank gives 0.973 at ~12 ms" but not
   "coarse_rerank hits recall 0.97 at X ms vs dense-rb8 / row-f32 at Y ms." That
   second framing is the one a promote/iterate decision actually needs. Run
   coarse_rerank vs **dense-rb8** and **row-f32** (optionally dense-rb4) at
   **matched recall targets (≈0.97 and ≈0.99)**, 50k + 100k. This is the metric
   that says whether the approach is worth continuing, so it's the priority.

2. **Rerank-representation matrix extension (cheap, secondary).** Packet 005
   measured only **f32 / f16 / rabitq8**; the contract also names **rabitq2 /
   rabitq4 / turboquant**, untested. The interesting hole is **rabitq4** (smaller
   than f16, and rabitq8's 0.946 was too lossy — is there a compact rerank that
   *keeps* f32 recall?). Extend the existing 005 sidecar sweep with rabitq2,
   rabitq4 (and TQ if it fits the harness) — **50k only, candidate_k 50/100,
   recall + bytes + sidecar p50**. One run; it just picks which compact
   `rerank_format` to implement first. Note: rerank representation is **not** the
   111e blocker (the frontier is), so this is "inform the future slice," not
   "unblock" — keep it to the one cheap pass.

## What would be overboard (defer)

Full 100k × all-rerank-reps × all-nprobe × all-candidate_k; 1M; index-side
placement measurement. These wait until the compact-rerank format is actually
implemented and the frontier-quality work lands — otherwise it's optimizing a
non-bottleneck stage and re-running it all later.

## Sharpen the "next levers" framing in the closeout

My packet-006 feedback called 113/115 "frontier-quality levers"; more precisely:

- The 100k/np32 ceiling is **routing-dominated** — true neighbors sit in IVF
  cells the narrow nprobe didn't probe (centroid partitioning + high-dim boundary
  geometry), not mainly rb1 mis-ranking. Evidence: widening candidate_k did
  nothing; nprobe64 fixed it.
- **115 (residual)** = recall-*per-probe* (sharper within-list score); it lowers
  *how wide* you must probe but does **not** change routing, so it can't directly
  recover a neighbor in an unprobed cell.
- **113 (bound pruning)** = recall-*neutral efficiency*; it funds a wider nprobe
  at the same latency. Not itself a recall lever.
- **Adaptive nprobe** = the direct routing fix (probe wide only on hard queries).
- If 113 + 115 + adaptive nprobe still leave a 100k gap, the deeper lever is
  attacking routing at the source — **more centroids / better partitioning, or
  boundary replication** (SPIRE-style) — bigger change, the "cheap levers
  insufficient" fallback.

Net for the closeout: "iterate; the gate is frontier *containment* (routing), so
the next work is recall-per-probe (115) + cheaper-per-probe (113) + adaptive
nprobe to make wide-enough probing affordable — measured against the matched-
recall baseline above."
