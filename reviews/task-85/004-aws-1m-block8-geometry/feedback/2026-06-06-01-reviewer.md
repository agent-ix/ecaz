# Task 85 packet 004 — AWS 1M block8 geometry (pre-run)

## Decision

**Accept the suite shape for AWS execution.** Tests the
`leaf_block_rows=8` geometry axis I named as untested in the Task
80-84 retrospective, with the right scope (separate index, matched
routing, four caps), the right acceptance bar (warmed Task 85 floor
+ matched recall + lower cands), and packet 003 as the joint-
distribution justification.

This is the first Task 85 packet that could land a real latency
win at the retained recall point. Outcome will tell us whether the
"summary density at 1M leaf density" hypothesis from the
retrospective generalizes to leaf geometry, not just summary count.

## Suite shape correctness

- **Separate index**: `aws_spire_1m_rabitq_t85_block8_tg256_idx`.
  Preserves retained block16 surface for direct comparison. Multi-
  index DML frontdoor fix from Task 84/005 covers the query path.
- **Build GUC**: `ec_spire.leaf_block_rows=8`. Single axis change
  vs retained k=2 block16 tg256 build.
- **Cap sweep**: `1152, 1536, 2048, 2304`. Spans the joint-
  distribution evidence — 1152 is direct comparison, 1536 is the
  Task 83 control neighborhood, 2048 covers ~half the broad miss
  tail per packet 003, 2304 is the upper probe.
- **`global2048` warm repeat**: matches the Task 85/001 paired-
  warmup methodology. Good.
- **Storage step after build**: lets us see the block8 storage
  cost vs block16.
- **Audit passed**: 8 steps.

## Acceptance bar correctness

The bar — `recall@10 ≥ 0.9832`, p50/p95/p99 better than warmed
floor (246.4/304.5/321.3 ms), `candidate_sum < 9,213,846` — is
exactly right. Strong enough to weed out warmup artifacts and
recall-floor games.

**Implicit comparator**: the warmed floor was 255 ms in Task 84/007
and 246 ms here. The 9ms improvement between those packets is
itself within warmup variance, so the bar of "better than 246.4ms"
is tight. Worth at least one same-suite warm-warm comparison
within this packet so block8 vs block16 are measured under
identical warmup state.

## Three predictions to record before the run

So result interpretation is bounded:

1. **If block8 cap1152 hits recall ≥ 0.9870 at cands ≤ 9.21M with
   p50 ≤ 240ms**: clean win. Smaller blocks at the same cap admit
   a tighter row surface; discrimination improves at 1M density.
   Promote as candidate operational point. **My central case.**

2. **If block8 cap1152 hits recall ≈ 0.9832 at cands ≈ 7M with
   p50 ≤ 230ms** (lower cands, similar recall, lower latency):
   secondary win pattern. Block8 narrows the surface without
   meaningfully changing which blocks rank inside cap. Worth
   measuring also at cap=1536/2048 to find the right cap for the
   geometry.

3. **If block8 cap1152 produces ≈ same recall + ≈ same cands +
   ≈ same latency**: the geometry change is a no-op at 1M density
   under the routing/cap shape. Close block_rows axis. Move to
   V5 format work (ADR-074) or accept the 0.9832 ceiling.

A fourth degenerate case: if block8 build fails or measurement
fails like Task 84/004 did, the prerequisite is to validate the
fresh build + query path on the multi-index table works cleanly
end-to-end. The Task 85/002 SSM observability fix should help
diagnose.

## Concerns + suggestions

### 1. No same-suite block16-vs-block8 paired control

Block8 will be measured against the Task 85/001 baseline as the
comparator. That's correct in spirit, but it introduces a
between-suites comparison. A small addition — running one warm
block16 cap1152 row inside this same suite alongside the block8
rows — would let the warmup state be exactly identical for the
comparison.

**Suggestion**: add one warm block16 `global1152` row to the suite
after the block8 rows finish. Compare block8 vs block16 within the
same suite's warmup state. ~5 minutes additional AWS time, removes
all warmup-variance uncertainty from the headline comparison.

### 2. Build cost prediction

`block_rows=8` will double the number of blocks per leaf vs
block16. Expected build time impact:
- block_rows summary-building cost scales linearly with block count
  → build time ~ +X% vs block16's 28 min.
- On-disk summary bytes also double per leaf — index size will be
  larger.

The packet should record build time explicitly in the manifest so
operators see the cost picture.

### 3. Storage delta expected

If block16 was 872 MB, block8 will probably land near 1.1–1.3 GB
(rough estimate: ~2× the summary chain bytes + same row chain
bytes). Worth recording.

### 4. The cap1152 row is the headline; the cap1536/2048/2304
sweep is mostly for sensitivity. If cap1152 fails the bar, the
higher caps probably trade cands for recall and won't be a Task 85
acceptance row anyway. But they're cheap to run alongside the
build, and tell us the shape of the trade curve at block8.
