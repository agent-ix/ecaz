# Task 85 packet 004 — outcome (block8 reject; CPU-bound finding)

## Decision

**Accept the block8 rejection.** The data is clean and the verdict
is correct: block8/cap1152 hit matched recall (0.9832) with **50%
fewer candidates** (4.6M vs 9.2M), but p50 latency **regressed by
~37ms (+15%)** at p95 +52ms. The candidate-density hypothesis was
partially right — block8 does narrow the row surface — but
candidate count is not the dominant latency cost at 1M.

This packet supersedes my seq-01 pre-run review. The seq-01
central case (recall ≥0.9870, p50 ≤240ms) didn't land; the seq-01
case (3) (no-op geometry change) was wrong too — block8 isn't a
no-op, it actively makes latency worse despite candidate
reduction.

## What the result actually proves

| metric | warmed block16 floor | block8/cap1152 | delta |
|---|---:|---:|---|
| recall@10 | 0.9832 | 0.9832 | matched ✓ |
| candidates | 9,213,846 | 4,607,442 | **−50%** |
| p50 | 246.397 ms | 283.839 ms | **+37.4 ms (+15%)** |
| p95 | 304.476 ms | 357.274 ms | +52.8 ms (+17%) |
| p99 | 321.342 ms | 2,729.302 ms | catastrophic outlier |

**Key architectural finding**: halving block size doubled summary
count per leaf → doubled summary scoring CPU. Reducing the row
surface by 50% didn't compensate. This is consistent with Task 81
packet 003's 81.5% summary-CPU share at 1M — summary scoring was
already the dominant cost, and block8 made it worse.

So the structural cost picture at 1M is:
- **Summary scoring CPU dominates** (grows with block count).
- **Per-candidate decode cost** (the surface block8 was meant to
  reduce) is the smaller share.

This effectively confirms a finding the Task 81 reviews suggested
but never tested directly: **reducing candidate count alone
doesn't move latency at 1M.** The summary-side cost has to come
down too.

## The p99 spike (2729ms) is informative

A single q500 outlier at 2.7 seconds is ~10× the typical p99 in
this lane. The p95 (357ms) and p99 (2729ms) divergence tells you
this isn't a steady-state effect — it's almost certainly a
cold-cache event hitting one query.

That fits the Task 84/007 cold/warm finding (~20ms gap was the
warm-state recovery; a true cold-page-cache fault on a single
query can be much larger). The block8 index is **newly built**
and ~2× more summary pages to fault in, so the single-query worst
case is dramatically wider.

This sharpens my retrospective point: cold-state latency is the
load-bearing axis. A fresh index built mid-suite has fewer pages
warmed than the retained surface, and block8's tail at 2729ms is
the smoking gun.

## What this leaves on the design space

After this packet, the remaining unexplored axes are:

1. **Cold-state warmup work** — pre-warming, page-cache hints,
   prefetch. The p99 spike here suggests this is *higher* leverage
   than the retrospective estimated. Could be tens of ms per
   percentile, not single digits.

2. **LARGER block geometry** (block_rows=32 or 64). Direction
   opposite to what packet 004 tested. If summary CPU dominates,
   FEWER summaries (larger blocks) could help latency. Risk:
   discrimination collapses, recall drops below 0.9832.

3. **Summary scoring kernel optimization** — SIMD widening, cache
   tiling, reducing per-summary IP cost. This is where the time
   actually goes per Task 81/003's 81.5% share.

4. **V5 leaf format / ADR-074** — could include changes that
   reduce summary scoring cost (e.g., codebook quantization of
   summaries, hierarchical summaries that prune cheaper). Larger
   ticket.

5. **Routed leaf count reduction** — if summary count grows with
   routed leaves, fewer routes = fewer summaries = lower summary
   CPU. Task 81/005 said wider routing hurt; this packet implies
   *narrower* routing should help, but only if recall holds. Task
   82's 3 routing misses set the hard floor at 0.9994 with current
   routing.

6. **Accept 0.9832 / ~246ms as operational ceiling.**

## Suggested next mechanism packet

Given the summary-CPU-dominates finding, I'd order:

a. **Cold-state characterization packet** — build a fresh block16
   index in a single suite, run cold + warm-1 + warm-2 + warm-3,
   measure the warmup curve and the worst-case single-query tail.
   Cheap and definitively quantifies the cold-state lever.

b. **Larger block geometry test (block_rows=32 or 64)** — same
   suite shape as packet 004 but in the opposite direction. If
   recall holds at 0.9832 with fewer summaries, latency probably
   drops. If recall collapses, format/discrimination work is
   forced.

c. **Summary scoring kernel profiling** — measure where in summary
   scoring the time actually goes (IP per summary, max-reduction,
   chain decode, prefetch). Decide whether SIMD/cache work has
   headroom.

Order matters: (a) is cheap and structural, (b) is the natural
inverse test of this packet, (c) is more research-y.

## Verdict

Accept rejection. Block8 is the second mechanism axis Task 85 has
closed (after the joint distribution closed the cap/rescue axes).
The unexpected finding — that the 50% candidate reduction
*increased* p50 latency — is a load-bearing result. It tells us
summary scoring CPU is the dominant latency cost at 1M, not
candidate decode.

Strongly recommend the next Task 85 mechanism packet target one of:
a (cold-state characterization), b (larger blocks), or c (kernel
profiling). Avoid more single-axis sweeps inside the current
geometry — the closed-axis list now covers basically all knob-level
moves at the V4 format.

If the summary-CPU finding holds under further measurement, V5
format work (per ADR-074) becomes the credible large-ticket
direction for Task 85 closure. Otherwise, Task 85 may need to
close with "accept 0.9832 / ~246ms as the 1M operational ceiling
at the current SPIRE architecture."
