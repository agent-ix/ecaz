# Task 85 packet 006 — block32 geometry (pre-run)

## Decision

**Accept the suite shape for AWS execution.** Tests the larger-block
geometry direction I named in my packet 004 seq-02 and packet 005
seq-01 reviews — directly attacking both the summary-CPU axis
(packet 004's finding) and the leaf object-read I/O axis (packet
005's finding) with a single mechanism. Suite preserves global
allocation (per packet 005's "global allocation is doing real

This is the inverse of packet 004 and the right next mechanism

## Why this packet is the right inverse test of packet 004

| axis | block8 (packet 004) | block16 (retained) | block32 (this) |
|---|---|---|---|
| summary count per leaf | 2× more | baseline | **2× fewer** |
| summary scoring CPU | +increased | baseline | **expected decrease** |
| rows per block | 8 | 16 | **32** |
| object read segments | 2× more | baseline | **2× fewer** |
| candidates per cap unit | smaller | baseline | **larger** |

Block32 attacks both load-bearing latency axes the prior packets
identified:
- **Summary CPU** (packet 004's 81.5% share finding at 1M):
  halved by halving summary count per leaf.
- **Object read I/O** (packet 005's 69% share at warm): reduced
  proportionally to fewer selected blocks (each block now decodes
  twice the rows in one segment fetch).

So block32 directly tests: **does fewer/larger summaries reduce
cost more than larger blocks reduce discrimination?**

## Three predictions to record before the run

1. **If block32 cap576 hits recall ≥0.9832 at p50 ≤ 220ms**
   (~25-30ms better than warmed 246ms baseline): **clean Pareto
   win**. Smaller summary count + smaller selected-block read
   set both buy latency. Promote as the Task 85 product profile
   candidate. **My central case** given the cost-attribution
   evidence.

2. **If block32 cap576 hits recall 0.96-0.9832 at p50 ~230-240ms**:
   partial — discrimination weakens with bigger blocks, recall
   drops a few pp, but latency improves. Worth measuring cap768
   to see if extra budget recovers recall at still-better latency
   than retained. Could become a tunable preset.

3. **If block32 cap576 hits recall < 0.96 with any latency**:
   block geometry hits a discrimination wall at 1M density. Close
   the block-geometry axis entirely. Move to either cold-state
   warmup or V5 format. **The k>2 result from Task 84/005 would
   suggest a discrimination floor exists, but it's at *finer*
   granularity — coarser blocks may still discriminate well at
   1M.**

The central case is what my packet 005 cost picture predicts:
~25% summary CPU at warm = halving it = ~28ms saved on p50 if the
saving translates linearly. Object read side could save a similar
amount if global allocation skips even more leaves at coarser
geometry. Total potential ~30-50ms p50 if both axes contribute.

## Concerns + suggestions

### 1. The matched-budget choice (cap576)

`576 × 32 = 18,432 rows = 1152 × 16` — matched in the **row
count being admitted**, not in the **cap count itself**. Worth
clarifying in the manifest that "matched cands" means matched
row budget (and therefore matched candidate scan surface), not
matched block selection count. The block selector still operates
over a halved block universe.

### 2. Storage cost should be recorded explicitly

Block32 will have approximately **half** the summary chain bytes
of block16 (fewer blocks → fewer summaries on disk). Worth a
storage step in the suite manifest similar to packet 004's
post-build storage capture. From the block8 packet, the EBS
expansion lesson should generalize: block geometry changes are
storage-sensitive and need explicit reporting.

### 3. Build cost prediction

Block32 should build **faster** than block16 (~half the summary-
building work). The block16 retained build was ~28 min. Block32
estimate ~15-20 min. Worth recording for operational picture.

### 4. The cap1152 ceiling row

`block32 cap1152` admits 1152 × 32 = 36,864 row-equivalents per
query — **2× the retained block16 cap1152**. So this row is
really exploring "what if we double the candidate budget?" Recall
should approach 0.9890+ (per Task 83's blanket-cap controls at
similar candidate inflation), but latency will be higher. It's
the right ceiling probe, but the row is more about the recall
asymptote than a viable operational point.
