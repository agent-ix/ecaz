# Task 85 packet 001 — handoff + product baseline suite (pre-run)

## Decision

**Accept the baseline suite shape and the handoff framing for AWS
execution.** Cleanly inherits Task 84's negative evidence (packets
006 + 007), explicitly uses the warmed retained k2 row as the latency
floor per my packet 007 review, and sets a defensible acceptance bar:
"matched or improved recall + faster than the warmed retained row."

This is a baseline packet, not a mechanism claim — and that's the
right shape for Task 85's first checkpoint.

## What the suite gets right

### Warm-state floor methodology

The retained Task 79/81 surface runs **twice in order** so Task 85
uses the warmed repeat as the latency reference, not a cold first
measurement. Directly applies the packet 007 finding (~19ms p50
cold→warm gap). All future Task 85 latency comparisons should cite
the warm row as the comparator.

### Honest handoff citations

Cites packets 006 + 007 + my packet 007 feedback explicitly. Doesn't
re-litigate closed axes from Tasks 80–84. Per the spec's "Task 84
must inherit accepted/rejected policy evidence" requirement — clean.

### Comparator policy acknowledges its gap

IVF comparator cited from `benchmarks/task51-aws-ivf-rabitq-final-gate/`.
HNSW and DiskANN gaps explicitly flagged as required-or-deferred
before Task 85 closes. That's better than silently treating SPIRE
alone as the universe.

### Cap controls preserved

cap1280 + cap1536 from Task 83/002. Documents the recall-vs-cands
trade curve as a backdrop, not as a recovery path.

### Code-change-free baseline

Pure measurement packet using `ecaz bench suite`. Audit passed (6
steps). No src/ surface to scrutinize.

## What the baseline doesn't yet establish

These are gaps to fill in subsequent Task 85 packets, not blockers
for this one:

### 1. Warmup curve, not just a single warm row

Running cold + warm-1 gives you a 2-point sample. **A 3rd run
(warm-2) would let you estimate convergence** — does latency keep
dropping with more warmup, or does it stabilize after one cold
priming run? If page-cache fills monotonically over several runs,
the "warmed floor" might still be artificially high. Adding a third
identical row here would cost ~2 minutes of AWS time and would
calibrate the floor properly.

### 2. No diagnostic capture for joint miss distribution

The Task 84 retrospective flagged that margin × route_rank × rank_delta
were never cross-tabbed. If this baseline ran `--target-block-rank-output`
+ `--miss-attribution-output` at the warmed row, Task 85 would have
a single joint distribution dataset to refer back to instead of
re-deriving it later.

### 3. Cold-state characterization is implicit

Packet 007 surfaced the ~20ms cold→warm gap as **the largest single
discovered latency axis**. This baseline correctly uses the warmed
row as the floor, but the cold row is just "what to ignore" — it
isn't itself characterized as a target for optimization. Future
Task 85 mechanism packets should likely have a dedicated cold-state
packet (or pre-warming experiment) before the warm-floor work starts.

## Concerns about the acceptance bar wording

> "future work must beat the warmed retained row at matched or
> improved recall"

This is the right bar, but "beat" needs operational definition. From
my packet 007 review:

- The cold→warm gap is ~19ms (7%).
- Run-to-run variance on a single q500 measurement at AWS Graviton
  is probably 3–8ms per percentile.
- A "real win" needs to be larger than the warmup spread.

**Recommendation**: Task 85 should commit to either (a) running each
candidate mechanism in the same paired-warmup shape as packet 007
(cold + warm so the within-suite warmup state is identical to the
baseline's), or (b) running N=3+ measurements and reporting median
with range, so a 5ms claimed win isn't just noise.

The seq-01 of packet 007 already named this — "Future latency work
needs standardized warmup and paired-order controls before claiming
small deltas." This baseline packet is the right place to lock that
in as a Task 85 measurement convention.

## Non-blocking notes

1. **No code-side measurement of cold-state mechanisms**: if Task 85
   plans pre-warming work, the first mechanism packet will need to
   exercise something like `pg_prewarm` on the SPIRE leaf object
   store. Worth scoping early.
2. **Block geometry alternatives** (block_rows=4 or 8) are
   referenced in my Task 80-84 retrospective. Not part of this
   baseline; should be a named axis in a follow-on Task 85 packet
   if cold-state work doesn't deliver enough.
3. **Multi-index storage cost note**: the retained AWS table now
   has 2 SPIRE indexes (k=2 + k=3). The k=3 is confirmed non-useful
   (Task 84/005, 007). Task 85 baseline should consider dropping it
   to clean state and save retained storage, OR retain it as
   reference and document the decision. Either is defensible but
   should be deliberate.
4. **6-step audit passed**: the suite shape is mechanically
   correct. Run with confidence.

## What I want to see in packet 002+

Looking forward — the next packets should target one of:

a. **Cold-state mechanism packet**: explicit pre-warming experiment
   (page-cache hints, `pg_prewarm`, leaf object prefetch). Highest-
   leverage axis per packet 007.
b. **Block geometry packet**: build a `block_rows=8` k=2 index for
   AWS 1M and measure at matched cands/recall. Untested axis
   addressing the 1M density argument from a different angle than
   k>2.
c. **Joint miss distribution packet**: cross-tab existing Task 82/84
   evidence so any next mechanism slice can target the actual joint
   structure, not independent assumptions.

Any of these is a real Task 85 contribution. The current
single-knob frame is closed.

## Verdict

Accept. Clean handoff, correct warmup methodology, honest gap
flags. Run the AWS suite, capture the warmed floor + cold/warm
delta + cap1280/1536 controls. That dataset becomes the immovable
reference for all subsequent Task 85 mechanism work.

Suggest adding (or filing as packet 002): paired-warmup measurement
convention as an explicit Task 85 process requirement, applied to
every mechanism packet going forward.
