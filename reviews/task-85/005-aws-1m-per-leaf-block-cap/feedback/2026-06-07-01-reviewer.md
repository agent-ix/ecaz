# Task 85 packet 005 — per-leaf block cap (rejected, with useful finding)

## Decision

**Accept the rejection.** At matched candidate budget
(`perleaf12 = 96 routes × 12 blocks = 1152`), recall collapses
from 0.9832 to **0.7714** (−21pp) AND p50 nearly doubles
(249.2ms → 477.2ms). Both axes lose decisively. Per-leaf block
caps are not a Task 85 latency path at the current routing shape.

The packet's diagnostic breakdown surfaces a meaningful
architectural finding: **global block allocation has a built-in
object-read pruning side effect** that per-leaf allocation
destroys, even at matched candidate counts.

## What the data shows

### Headline matched-budget row

| metric | global1152 warm | perleaf12 | delta |
|---|---:|---:|---|
| recall@10 | 0.9832 | **0.7714** | **−20.6pp** (catastrophic) |
| candidates | 9,213,846 | 9,213,924 | matched (+78) |
| p50 | 249.160 ms | 477.209 ms | **+228 ms (+92%)** |
| p95 | 306.730 ms | 494.663 ms | +188 ms (+61%) |
| p99 | 318.763 ms | 500.243 ms | +181 ms (+57%) |

This isn't a Pareto trade — it's two-axes-lose. Even before any
latency discussion, the recall collapse alone rejects the policy.

### Recall scan across per-leaf budgets

| budget | recall | matches global control? |
|---|---:|---|
| perleaf8 (768) | 0.7108 | no — even smaller budget, deep recall loss |
| perleaf10 (960) | 0.7454 | no |
| perleaf12 (1152) | 0.7714 | matched cands; still −20.6pp vs global |
| perleaf14 (1344) | 0.7980 | larger budget, still no recovery |

Even at perleaf14 (17% more total blocks than global1152), recall
stays at 0.7980 — **18pp below global1152's 0.9832**. Equal per-
leaf allocation can't concentrate budget on the leaves where the
true winners actually live. The global scorer's information
content is doing real work — it's not just a "fancy budget."

## The architectural finding (worth recording)

The funnel timing comparison at matched candidate budget:

| stage | global1152 warm | perleaf12 | delta |
|---|---:|---:|---|
| p50 object read | 170.822 ms | 350.475 ms | **+180 ms (+105%)** |
| p50 candidate/summary score | 55.787 ms | 56.665 ms | +0.9 ms (flat) |
| total candidate sum | 9,213,846 | 9,213,924 | matched |

**Object read time doubled at matched candidate count.**
Scoring time is flat. The cost is entirely in the I/O side.

Why? Global allocation has an implicit leaf-skipping effect:
when the global scorer ranks all blocks by summary score and
caps at 1152, some routed leaves contribute zero blocks to the
cap. SPIRE doesn't need to read object segments from those
leaves at all. Per-leaf allocation forces a fixed number of
blocks per leaf, so every routed leaf must be touched — and the
leaf object reads are the expensive part.

This is a non-obvious, durable architectural property of global
allocation. Worth recording in any future SPIRE design doc:
**global block allocation is also implicit object-read pruning.**

## Connection to packet 004's CPU finding

Packet 004's block8 result said summary scoring CPU dominates at
1M. Packet 005's result adds: **object read I/O is the *other*
dominant cost** at the warm operational floor (170.8ms / 246.4ms
= 69% of p50). The split at warmed global1152 is approximately:

- Object read: ~170 ms (69%)
- Summary/candidate scoring: ~56 ms (23%)
- Other (heap rerank, candidate marshalling, return path): ~20 ms (8%)

So the warm-state latency budget is roughly **70% I/O + 25%
summary-CPU + 5% rest**. Block8 made the scoring CPU side worse;
per-leaf allocation made the I/O side worse. Neither found a
mechanism that reduces *either* without hurting the other.

This refines my packet 004 seq-02 retrospective: the next
mechanism likely needs to attack **leaf object read I/O** as the
primary axis, not summary scoring CPU. Possible directions:

1. **Cold-state warmup** (still highest leverage per Task 84/007
   and the block8 p99 spike).
2. **Object read locality** — page-cache prefetch, mmap layout
   review, hot/cold payload split per ADR-074 territory.
3. **Reducing routed leaf count** with selective routing that
   preserves recall ceiling (Task 82's 3 routing misses cap this
   at 0.9994 oracle).
4. **Larger blocks** (block_rows=32) — would reduce both
   summary count AND object segments to read. Untested.

## Verdict

Accept rejection. Per-leaf block cap closes as a latency path:
recall collapse + 92% p50 regression at matched cands.

The **architectural finding** about global allocation's implicit
object-read pruning is the durable contribution from this
packet. It explains why per-leaf is strictly worse and shapes
the next mechanism direction.

Combined with packet 004's "summary CPU dominates" finding,
Task 85 now has a clear two-axis cost picture: **~70% I/O + ~25%
summary CPU at warm steady state**. The remaining unexplored
high-leverage axes target I/O (cold-state warmup, larger blocks
that reduce both, hot/cold payload split per ADR-074) more than
they target CPU.

Strongly recommend the next mechanism packet target the I/O side
directly — cold-state characterization (cheapest, structural) or
larger block geometry (untested in this direction) before any
larger format ticket.
