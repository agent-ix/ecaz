# Task 85 packet 002 — cloud SSM observability + timeout

## Decision

**Accept.** Narrow, well-scoped tooling fix that turns silent
indefinite SSM polling waits into bounded, observable failures.
No SPIRE semantics affected. The change is in
`crates/ecaz-cloud/`, not `src/`, so it doesn't touch any of the
guarded SPIRE format/scan/storage paths.

This is the right unblocking move after the packet 001 baseline run
got stuck in opaque SSM polling (per the `4c4189d83 Record Task 85
baseline bench stall` commit). Without it, Task 85's measurement
discipline depends on the operator noticing the wedge and ctrl-Cing
manually.

## Code review (`crates/ecaz-cloud/src/ssm.rs`)

### Change set

1. New constant: `AWS_CLI_CALL_TIMEOUT = 60s`.
2. `send-command` wrapped in `tokio::time::timeout(60s, ...)`.
3. `get-command-invocation` wrapped in `tokio::time::timeout(60s, ...)`.
4. `eprintln!("ssm: instance={} command_id={} timeout_secs={}")`
   printed immediately after a successful send, before the long
   poll begins.
5. Improved error wrap messages distinguishing "timed out locally"
   from "invoke … failed."

### Correctness

- **Inner timeout is per-call**, not per-overall-operation. The
  60s bounds each AWS CLI subprocess invocation only. Good — if
  the AWS CLI is healthy but the remote SSM command genuinely
  takes a long time, the outer poll loop's existing deadline
  (`timeout_secs + 60`) is what governs.
- **No semantic change to remote scripts.** This is purely the
  local subprocess plumbing.
- **`eprintln!` to stderr**: correct channel for diagnostic output
  that shouldn't get captured into result documents. Operators see
  the command_id without it polluting bench output JSON.
- **Error wrap chain preserved**: `timeout` error → wrapped with
  context, subprocess error → wrapped with original context.
  Both paths surface usable diagnostics.

### Safety

- No new unsafe blocks.
- No new panics.
- `Result<String>` return signature unchanged — callers don't need
  to handle a new error kind explicitly.
- `tokio::time::timeout` is the standard pattern; no concurrency or
  cancellation gotchas.

### Test coverage

- `cargo fmt --check -p ecaz-cloud`: passed.
- `cargo test -p ecaz-cloud`: 10 tests pass.

The 10 tests are likely covering existing ssm.rs behavior. No new
test was added explicitly for the timeout path. That's a small
coverage gap — adding a test that exercises the timeout branch
(e.g., a mock AWS CLI that hangs) would confirm the wrap chain
under failure. **Non-blocking** because the wrap chain is small
and easy to read by inspection, but worth filing as a follow-on
TODO.

### Risk: is 60s the right value?

For healthy AWS CLI invocations, 60s is generous (typical responses
are <5s). Two considerations:

- **Backstop role**: this is a backstop against AWS CLI subprocess
  wedges (e.g., DNS hang, credential refresh stall, IMDS timeout).
  60s is appropriate for "something is structurally wrong" detection,
  not for tight latency control.
- **Could 60s mask a genuine slow response under load?** Unlikely
  for `send-command` (which is essentially an API call). For
  `get-command-invocation` polled in a loop, 60s per call means
  worst-case observable wedge before bailout is 60s, which is
  acceptable.

The constant should probably stay 60s. If operators ever hit it
spuriously, the constant is easy to bump.

## Process hygiene (clean)

- Change is narrow (one file, ~30 LOC effective change).
- fmt + tests passed.
- No scope creep into SPIRE src/ or other AWS-side code.
- Manifest cites the exact commands used.

## Non-blocking notes

1. **Add a timeout-branch test** when convenient. A mock subprocess
   that hangs would confirm the local-timeout wrap chain produces
   the expected error message. Small follow-on.
2. **Consider also adding a max-deadline log message** when the
   outer poll loop's `timeout_secs + 60` deadline fires. The new
   `eprintln!` shows the command_id at start; symmetric printing
   at terminal state (success/timeout) would close the
   observability loop. Optional, depends on how noisy operators
   want stderr.
3. **The Task 85 baseline (packet 001)** is now unblocked. Worth
   noting in the packet 001 follow-up commit that this fix
   landed before the baseline retry.

## Verdict

Accept. Clean, narrow, ADR-/format-version-irrelevant (CLI plumbing
only). Unblocks the Task 85 AWS baseline measurement without
touching SPIRE semantics. Worth merging immediately and retrying
the packet 001 baseline against the fixed CLI.

Future Task 85 mechanism packets benefit from this fix being in
place — every AWS run is now observable + bounded by design.
