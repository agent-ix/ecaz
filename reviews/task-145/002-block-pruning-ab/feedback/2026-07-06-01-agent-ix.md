# Task 145 Packet 002 (block-pruning-ab) — Review

## VERDICT: CHANGES REQUESTED

The "do not promote block pruning" *conclusion* is defensible and I do not object
to it. But I cannot accept this packet as clean evidence, for two structural
reasons that repeat and compound the packet 001 problem:

1. **Wrong path — measured entirely on the LOCAL scan path, not the remote
   coordinator path Task 145 is about.** Every pipeline cell reports
   `remote_fanout_sum = 0` and the `remote_fanout` step status is literally
   `not_applicable_local_scan`. Like 001's `remote:false`, this A/B never
   exercises the coordinator remote-rescore loop in `hierarchy_snapshots.rs`
   that the spec flags. Block pruning may cut candidates on the local path, but
   that path already works; the target path is untouched and unmeasured.

2. **The recall evidence is self-contradictory and the rejection rests on the
   weaker of the two numbers.** The pipeline `distinct_recall@k` claims a large
   loss; the canonical truth-cache recall harness (recall@k, ndcg@k, CI95, 2000
   trials) shows **zero** loss and is byte-identical between control and block.
   These cannot both be true measurements of the same pruned index.

Plus, as in 001, there is **no `src/` change** — commit `4313bf2c9` touches only
`reviews/…` artifacts, and the remote-path AC1 fix (honoring `rerank_width` in
the coordinator rescore loop) is still **not done**.

## Does block pruning engage? YES — verified from raw counters

Block pruning is a pre-existing, default-disabled mechanism
(`ec_spire.leaf_block_pruning_*` GUCs in `options/mod.rs`, ADR-074); this packet
does not add it. It is mechanically active here. From `suite-results.jsonl`
(`step=candidates`, nprobe96), control (pruning off) vs block (max_global_blocks=128):

| scale | control candidate_sum | block candidate_sum | cut |
| --- | ---: | ---: | ---: |
| 10k n128 | 1,502,699 | 396,050 | -74% |
| 50k n1024 | 986,258 | 395,052 | -60% |
| 100k n1024 | 1,874,885 | 402,835 | -79% |

`heap_rerank_sum = 10,000` (= 200 queries × 50) and `rerank_width = 50` in **both**
variants, so the only differing knob is the block-pruning GUC and the candidate
delta is correctly attributable to pruning. Engagement is real.

Caveat: the *direct* per-block prune counter dump (`leaf-block-rank-*.jsonl`) was
intentionally not committed; engagement is inferred from the candidate_sum delta.
That inference is sound here, but the explicit prune counter would have been the
cleaner proof the task asked for.

## Does it cut cost at equal recall? UNRESOLVED — recall metrics disagree

Latency (nprobe96, release, verified from jsonl):

| scale | variant | p50 | p95 | pipeline recall | truth-cache recall |
| --- | --- | ---: | ---: | ---: | ---: |
| 10k n128 | control | 9.466 | 10.238 | 1.0000 | 1.0000 |
| 10k n128 | block | 6.267 | 6.942 | 0.9920 | **1.0000** |
| 50k n1024 | control | 13.619 | 14.805 | 0.9595 | 0.9590 |
| 50k n1024 | block | 14.103 | 16.329 | 0.9085 | **0.9590** |
| 100k n1024 | control | 17.482 | 19.179 | 0.9570 | 0.9300 |
| 100k n1024 | block | 12.826 | 15.438 | **0.7755** | **0.9300** |

The manifest bases its "unacceptable recall loss (100k 0.9570→0.7755, 50k
0.9595→0.9085)" rejection on the **pipeline** column. But the truth-cache recall
rows are byte-for-byte identical between control and block — same
`distinct_recall@k`, same `recall_ci95_low/high`, same `recall_worst` (0.4000 at
100k), same `ndcg@k` — for two *different* indexes over 2000 trials. That degree
of identity is essentially impossible unless either (a) block pruning removed
zero true top-10 neighbors (recall fully preserved, and the pipeline number is
the misleading one), or (b) the truth-cache recall harness did not apply the
block-pruning scan GUCs and simply re-measured an unpruned scan for both prefixes
(in which case truth-cache is not a valid check of the pruned path and the
pipeline number is the only signal — but it is unvalidated). Note the two metrics
disagree even for **control** (100k 0.9570 vs 0.9300), confirming they are
different methodologies.

Either way, the recall cost of pruning is **not cleanly established**. The packet
cannot both cite the truth-cache table as evidence pruning "held recall" and cite
the pipeline table as evidence it "lost recall." This must be reconciled before
the negative claim is trustworthy: run the recall harness with the pruning GUCs
actually applied to the pruned prefix and show a non-identical result, or explain
why the pipeline `distinct_recall@k` diverges from the canonical harness.
