## Code correctness — sound on the default path

- **Lever 1 (dense pool)** `CandidateDedupPool::record_best` (`scan.rs:394`) is
  a 1:1 rewrite of the former `HashMap` dedup: one slot per heap tid, replaced
  only on `candidate_cmp == Less`; counter mapping (`Inserted` /
  `ReplacedWorse` / `KeptExisting`) matches the old `Entry` logic exactly.
- **Lever 2 (lazy heap)** `RankedProbeCandidates::LazyHeap` pops via
  `Reverse<CandidateHeapEntry>` whose `Ord` is `candidate_cmp`
  (`score.total_cmp → block → offset`) — a strict total order over the pool's
  distinct heap tids, so pop order equals the former `sort_by(candidate_cmp)`
  ascending order. No ties (distinct tids) → deterministic, identical output.
- **Heap lifecycle clean:** both store paths call `free_posting_candidates`
  first, so no stale heap shadows the array in `next_posting_candidate`.

## Blocking finding (now fixed) — heap_f32 + rerank_width<=0 skipped rerank

The lazy-heap routing sent the collect to `LazyHeap` whenever
`pre_rerank_candidate_limit` returned `None`, and **only the `Sorted` branch runs
the exact rerank**. But `pre_rerank_candidate_limit` returns `None` for
`heap_f32` with `effective_rerank_width <= 0` — the reachable "rerank all"
sentinel (`resolve_rerank_len(<=0) = candidate_len`, `scan.rs:2820`). In that
config the new code **silently skipped the exact rerank** where the former
unconditional call reranked the whole frontier → an off-default recall
regression. The A/B (default rerank is auto, not heap_f32) never exercised it,
and the unit test at `scan.rs:5653` actually pinned the `→None` behavior. The
in-code comment ("a `Some` pre-rerank limit is *exactly* the heap_f32
condition") was imprecise: the true condition is heap_f32 **AND** width>0.

**Fix (`c204f3905`):** split the two concerns. `pre_rerank_candidate_limit`
keeps its original bounded-limit meaning (still correct for the running-top
prune sizing at `scan.rs:1730`, where `None` must stay `None`); a new
`ranked_collect_limit(index_options, candidate_len)` owns the sorted-vs-lazy
decision — heap_f32 always takes `Sorted` (`Some(width)` when width>0, else
`Some(candidate_len)` for rerank-all), every non-heap_f32 mode takes the lazy
heap. `LazyHeap` now iff rerank is not heap_f32, so the default topk_collect win
is unchanged and heap_f32 always reranks. Added `ranked_collect_limit` unit
coverage (incl. the width<=0 rerank-all case) and corrected the comments.
`cargo check --lib` clean; pg_test deferred (macOS dyld blocker).
