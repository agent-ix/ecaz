## Is the remote rescore path actually fixed to honor rerank_width? YES — code verified

Verified against the diff (not the manifest). The review-request commit
`c13d4fe4b` is artifacts-only, but it sits on top of the real fix `4d7e927f0`
(8 files, +290/−70; 5 src, 3 test). The mechanism:

- **Coordinator-local heap rescore now truncates to top-W before rescoring.**
  New `remote_search_compact_candidate_rerank_prefix` (`hierarchy_snapshots.rs`
  :185) sorts the compact remote candidates with the existing
  `remote_search_candidate_cmp` and truncates to `rerank_width.min(len)` via
  `select_nth_unstable_by` + `truncate` + `sort_by`, *before* the exact heap
  rescore loop (`remote_search_heap_candidate_rows_from_compact_candidates`,
  :243–247). Width `0` returns the full frontier unchanged (prior behavior).
  This is precisely the spec's complaint — the loop that previously
  exact-rescored **every** candidate now rescores only the top-W.
- **The multi-node remote leg propagates the width to remote sessions.**
  `scan_output.rs` reads `scan_plan.rerank_width` and threads
  `effective_rerank_width` through the fanout executor
  (`production_transport.rs`: every `compact_candidate_receive` /
  `remote_heap_receive` signature now carries it) into the receive-request
  structs (`dispatch.rs`: `SpireRemoteProductionCandidateReceiveRequest` /
  `…HeapReceiveRequest` gain the field). Before running the remote heap-receive
  SQL, the coordinator issues
  `SELECT set_config('ec_spire.rerank_width', $1, false)` on the remote
  connection (`dispatch.rs` :1655 and :2255), so each participating node applies
  the width in its own exact heap rescore (the Task-141 local-scan substrate
  001 verified already honors it). The final coordinator merge stays at `top_k`
  — correct: each node rescores only its top-W, then results merge to top_k.

So the design is coherent and complete: width is honored at **every** node's
exact rescore (coordinator-local via the new truncation, remote nodes via the
GUC handoff), not just the local single-node path. No silent default flip:
width `0` preserves full-frontier, and the effective width comes from
`resolve_scan_rerank_width(relation_options().rerank_width)`, whose default is
unchanged.

Test coverage is real, not decorative:
- `remote_heap_rerank_prefix_keeps_full_frontier_for_zero_width` — width 0
  keeps all 3, sorted best-first (0.10, 0.20, 0.30 in `<#>` convention). ✔
- `remote_heap_rerank_prefix_limits_exact_heap_resolution_width` — width 2 of 4
  keeps the two *best* (0.05, 0.10), correctly proving `select_nth` picks the
  top-W by score, not the first W. ✔
- `production_executor_state` asserts `effective_rerank_width` (9, 1) actually
  lands in the built receive requests. ✔ (propagation is asserted, not assumed)
- Fault-path structs updated with `effective_rerank_width: 0` (mechanical, keeps
  `receive_faults.rs` compiling). All three logs: `test result: ok`.

Caveat: the test log is the **debug** `test` profile (`unoptimized +
debuginfo`) — appropriate for unit correctness, but it underscores there is no
release build and no bench here.
