## What's solid

### Mathematical correctness of the cutoff

`try_estimate_ip_scalar` (`src/quant/rabitq.rs:1055`) computes:

```
max_estimate = candidate_norm * query_norm / |candidate_o_dot|
```

…and prunes when `max_estimate < min_ip_to_keep`. By Cauchy-Schwarz on
the inner product `<q_rotated, x_dec>`:

```
|sum_q_dequant| <= query_norm * candidate_x_norm
=>  |actual| = candidate_norm * |sum_q_dequant| / (|candidate_o_dot| * candidate_x_norm)
            <= candidate_norm * query_norm / |candidate_o_dot|
            =  max_estimate
```

So `max_estimate < min_ip_to_keep` implies `|actual| < min_ip_to_keep`,
i.e. `actual < min_ip_to_keep` for top-k-by-IP semantics. Safe upper
bound; no false prunes.

### "Alignment on estimate_ip_scalar_only" is a free CPU win, not a recall change

The framing "Aligns RaBitQ scalar and batch scorer output on
`estimate_ip_scalar_only`" reads at first like a behavior change, but
`estimate_ip_scalar_only` is documented as "IVF-fast estimate that
skips the ε-concentration bound (sqrt + a few multiplies per
candidate) since the IVF scan path only uses the scalar estimate"
(`src/quant/rabitq.rs:907-913`). The previous code path was computing
`estimate_ip(...).estimate` and discarding the bound. The new path
returns the same `.estimate` value without computing the unused bound.
Numerically identical, faster. Good.

### Scan-side wiring (`scan/candidates.rs:779`)

- `min_ip_to_keep()` returns `None` while the heap is below its limit
  (no cutoff applied → score everything); returns `Some(-peek)` once
  the heap is full (negation handles the max-heap-via-min-heap
  convention).
- The bifurcated entry path (`if RaBitQ && bounded → cutoff path,
  else → original path`) leaves TurboQuant and unbounded scans
  untouched. Tight scope.
- Pruned candidates are recorded via `observe_truncated_candidate` so
  Task 75/77's funnel diagnostics still account for them — the
  truncated-candidate count goes up, candidate_score_time per pruned
  row stays low, which is exactly what the funnel should show.

## Required before this slice clears the Task 78 gate

### R1 — Packet 002 (suite evidence) must show recall preserved

Task 78 (per `plan/tasks/78-spire-latency-optimization.md`) inherits
the Task 73/75 recall-floor requirement: high-recall 100k recall@10
preserved within 0.5pp. The unit tests cover boundary cases
(NEG_INFINITY → keep all, MAX → prune all) but say nothing about
mid-range behavior at production cutoffs. End-to-end suite evidence at
`tg96/nprobe96` is the load-bearing answer.

Packet 002 has `suite-rabitq-baseline.json` and
`suite-rabitq-current.json` (configs, no run output) and no
`request.md`, so I'm not reviewing it on this turn — but the slice
shouldn't be considered Phase 2 P0 complete without it.

### R2 — p50 win >= 10% at matched-recall point

Task 78 still carries the `>=10%` p50 win gate from the inherited
Task 77/74 framing. The cutoff's expected win depends on what fraction
of candidates can be pruned. With the funnel data at tg96/nprobe96
(15.5M candidates, 5,000 retained over 200 queries — ~0.16% survival),
the headroom is real, but cutoffs only kick in *after* the heap fills.
The first 25 candidates per leaf-route get scored fully; only the
candidates after that benefit. The suite measurement should report
both p50 latency and the fraction of candidates pruned by the cutoff
(packet 002 — please surface this via the existing truncated-candidate
diagnostic so the cutoff's contribution is auditable).

## Suggested (non-blocking)

### S1 — Add a mid-range cutoff unit test

The boundary cases (NEG_INFINITY, MAX) prove the framework works. A
test with `min_ip_to_keep` set to half-way between the smallest and
largest expected score for a known fixture would lock the numerical
behavior — and would catch a future bug where `try_estimate_ip_scalar`
drifts from `estimate_ip_scalar_only` on the keep path.

### S2 — Two-path divergence risk

`append_quantized_v2_column_candidates` (original) and
`append_quantized_v2_column_candidates_with_rabitq_cutoff` (new) now
both handle the per-row scan loop. Diagnostic-timer placement and
visibility-check ordering must stay in sync between them. Worth a
comment on each function noting the other exists and what they must
agree on, so a future edit to one doesn't silently desync the timers.

## Verdict

Code is correct and ready for the suite-evidence packet. Hold the
"Phase 2 P0 slice landed" verdict until packet 002 (with request.md +
suite run) shows recall preserved and a measurable p50 win.
