# Task 78 packet 002 — RaBitQ suite evidence

## Decision

**Accept the shelve.** The packet correctly concludes that the
packet-001 cutoff slice does not clear the Task 78 `>=10%` p50 gate
at the matched-recall 100k point. The measurement is honest and the
methodology is sound. The slice should not land as a Task 78 P0.

One diagnostic gap is worth fixing before the next slice attempt — see
finding R1.

## What's solid

### Methodology

- Separate baseline-binary install from `/tmp/ecaz-task78-baseline/`
  vs current install at `c5b37ce0c`. Both backends are SHA-pinned in
  the manifest (`5a5cea5122…` baseline, `d781b7af4e4…` current). No
  binary-aliasing risk.
- Per-lane isolated databases
  (`task78_spire_rabitq_baseline` / `task78_spire_rabitq_current` /
  `task78_spire_turboquant_current`) per the project's
  index-isolation rule.
- Three settings (nprobe 64/96/128), real corpus, 200 queries.
- TurboQuant lane added as a comparison control rather than just
  baseline-vs-current.
- Recall preserved exactly across lanes: `retained=5000`,
  `returned=2000` identical at every (lane, nprobe) row. No recall
  regression risk on this fixture.

### Result interpretation

- p50 deltas are within noise: -0.4%, +1.0%, -1.6%. The cutoff
  doesn't help and doesn't materially hurt; consistent with adding a
  small per-candidate scalar read.
- Score share at 87-88% for RaBitQ on Intel matches the Task 77
  pattern (82-83% there used TurboQuant). The shift comes from RaBitQ
  scoring being faster, not from materialization changing.
- TurboQuant score-share at 95.7% and p50 at 101 ms (vs RaBitQ's
  33.8 ms) is a strong product signal — RaBitQ is ~3x faster at
  identical recall at this point.

### Decision

- Shelving with packet-local evidence is the right call. The Task 78
  spec inherits the `>=10%` p50 win gate; the data shows the slice
  doesn't clear it.
- Correctly defers TurboQuant/RaBitQ default-policy to a separate
  narrower task. That's the same boundary Task 76 enforced and is
  consistent.

## Findings

### R1 — Cutoff diagnostic doesn't separate cutoff-prunes from heap-evictions (required before next slice)

Both baseline and current report `truncated = 15,501,227` at nprobe
96. This is the existing candidate-budget truncation, not the new
cutoff path. The new
`append_quantized_v2_column_candidates_with_rabitq_cutoff` calls
`observe_truncated_candidate` for cutoff-pruned rows, which feeds
the *same* counter as heap eviction. As a result, the funnel cannot
answer the load-bearing diagnostic question: **did the cutoff ever
fire, and if so how often?**

That matters for the next iteration. The two failure modes look
identical in the current evidence:

- (a) The cutoff fires often but the savings are offset by the
  scalar-read overhead (suggests the wiring is right but the upper
  bound is too loose for this corpus).
- (b) The cutoff almost never fires because the upper bound
  `candidate_norm * query_norm / |candidate_o_dot|` is dominated by
  ~uniform candidate norms in this fixture (suggests a tighter bound
  is needed — e.g. fold in XOR-popcount as a refined upper bound).

Both diagnoses point at different next moves. Add a separate
counter (e.g. `cutoff_pruned_count` distinct from
`heap_evicted_count`) before the next cutoff variant lands.

### R2 — Score-share is unchanged, which confirms Task 77's read

Independent confirmation: even with the cutoff in place, score
remains 87-88% of measured candidate-path time. The Task 77
no-slice closeout's reasoning (object reads + materialize + heap are
together too small to clear 10%) reproduces here on RaBitQ. The
implication is the same — the dominant cost is the scoring kernel
itself, and a Task 78 follow-on should target that path (storage
format / scoring SIMD) rather than another bounded-heap trick.

### R3 — Notes on the funnel JSON shape

`funnel-attribution-summary.json` here uses a flatter row schema
(`candidates: int`, `retained: int`, plain timing percentiles) than
Task 77's nested-summary shape (`candidates.sum/min/max/mean/p50/p95`,
`score_ns.sum/...`). Both are workable, but the inconsistency makes
cross-packet jq queries annoying. Pick one shape going forward —
the Task 77 nested shape carries more info, but the Task 78 flat
shape is faster to read. Either is fine, just settle on one.

## Smaller note (non-blocking)

The `score_p50_ms` for current at nprobe 96 (33.77 ms) is 7.6% *higher*
than baseline (31.38 ms). That's larger than the p50 latency
difference (+1.0% at nprobe 96), which suggests the scoring path
itself is slightly slower under the cutoff branch — consistent with
the per-candidate scalar read added even on the keep path. Worth a
one-line note in the manifest so the next reader understands why
score time went up while overall latency was flat.

## Verdict

Packet accepted as a shelve with reviewer-acknowledged failure to
clear the gate. Before the next Task 78 slice attempt, add the
cutoff/heap-eviction counter split (R1) so the next iteration's
evidence can attribute behavior to the right cause.
