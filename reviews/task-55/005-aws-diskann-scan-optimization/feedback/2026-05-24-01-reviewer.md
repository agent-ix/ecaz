# Reviewer Feedback: DiskANN AWS Scan Optimization (packet 005)

Reviewed:

- code: `cbf037334` "Optimize DiskANN scan materialization"
- packet: `reviews/task-55/005-aws-diskann-scan-optimization/`
- bench: `benchmarks/task55-aws-diskann-lowcost-config-audit/` (before),

- code path: `src/am/ec_diskann/{reader,scan,scan_state,routine,insert}.rs`

## Bottom line

**APPROVE on merits, two hard asks before the speedup claim lands
publicly.** This is a real, well-shaped optimization with byte-
identical storage and exactly-equal recall across the sweep — strong
evidence the algorithm is unchanged. The win comes from eliminating
an unconditional O(N) per-scan materialization that the binary-
sidecar path never used.

## What changed (one paragraph)

`ec_diskann_ambeginscan` used to call
`materialize_chain_from_index`, which walked every block of the
index main fork and copied all tuples into an in-process
`DataPageChain` — paid in full on every scan regardless of
`list_size`. The new path reads only the metadata page in
`ambeginscan` and routes greedy descent through a new
`GraphReader` trait. For the default binary-sidecar prefilter path,
a `RelationGraphReader` pins/locks each visited block on demand via
`LockedBufferGuard::read_main_handle`, so a 100k-node index with
`list_size=64` reads ~100 nodes instead of ~12 000. The grouped-PQ
prefilter still materializes the chain inside `amrescan` because it
needs codebook tuples; that fallback is preserved and gated by a
clean `Option<&DataPageChain>` in `prepare_prefilter`.

Bonus: `greedy_descent_with` now uses
`entries.remove(&picked.tid)` so the neighbor `Vec` is moved out of
the map instead of cloned per expansion. Safe because `picked.tid`
is added to the visited set before lookup and cannot be picked
again.

## Strengths

1. **Recall preserved exactly.** Per the manifest, recall@10 is
   identical before and after at every `list_size` (0.9165, 0.9625,
   0.9745, 0.9855, 0.9865). That is the right test for "did the
   algorithm change" and the answer is no.
2. **Storage unchanged.** 46.1 MiB / 483.1 B per row before and
   after at 100k — no on-disk-format risk, existing indexes don't
   need rebuild (per `memory: feedback_no_recreate_corpus`).
3. **Clean trait abstraction.** `GraphReader` is a two-method
   surface (`read_node`, `first_live_tid`) implemented by both
   `PersistedGraphReader` (delegated to inherent methods, no
   behavior change for chain callers) and `RelationGraphReader`.
   Scan functions become generic over `R: GraphReader` and the
   chain-backed path is byte-equivalent.
4. **Fallback preserved correctly.** `prepare_prefilter` now takes
   `Option<&DataPageChain>` and errors cleanly when the grouped-PQ
   path is selected without a chain; `amrescan` materializes the
   chain lazily only when the prefilter actually needs it.
5. **Bonus allocation cut.** The `.clone()` removal in
   `greedy_descent_with` is a free win and the safety argument is
   sound.
6. **Measured win is dramatic and shape-consistent.** 36× at
   list_size=64 collapsing to 6.1× at list_size=800 is exactly the
   curve you'd expect from "fixed materialization cost subtracted
   from a per-visit-growing descent cost".

## Hard asks before this lands as a public claim

### H1. 1M-scale validation (StR-007 conformance)

The speedup is measured at 10k and 100k only. `StR-007` says product
benchmark claims need scale evidence at 1M+. The change *should*
scale — it eliminates O(N) per-scan work that grows with index size
— but at 1M the per-query block-read count grows (more nodes
visited per query, EBS cold-read costs reshape the curve), so the
trade is not identical to 100k.

Concrete ask: run the same before/after suite against a 1M corpus
on the same `m8g.2xlarge` shape, warm cache, and add a `kind:
latency` p50/p95/p99 row pair (before/after) to the bench manifest.
If there is no preserved 1M DiskANN snapshot, this is the
opportunity to take one (per `memory: feedback_aws_bench_sizing`
and `feedback_no_recreate_corpus`: snapshot before destroy).

### H2. Unit test for `RelationGraphReader` against a live PG index

The only validation of the new relation-backed reader is the
end-to-end recall preservation in the bench. That is necessary but
not sufficient. The reader can be wrong in ways the bench doesn't
exercise — wrong tuple at a TID that the descent never visits,
wrong overflow walk under churn, wrong behavior on a relation with
deleted nodes.

Concrete ask: add a `pgrx test pg18` test under
`src/am/ec_diskann/scan_state.rs` (or a new test module) that:

- builds a small DiskANN index against a real PG relation,
- iterates every live node TID from the in-memory chain,
- asserts `RelationGraphReader::read_node(tid)` returns a tuple
  byte-equal (or field-equal) to `PersistedGraphReader::read_node(tid)`,
- asserts `RelationGraphReader::first_live_tid()` matches
  `PersistedGraphReader::first_live_tid()` on the same index,
- exercises at least one query path through the relation reader and
  asserts the result set matches the chain-reader result set.

The `cargo test --lib ec_diskann::scan --no-run` evidence currently
in the request only proves the new code compiles — that is too thin
for a default scan path change.

## Soft asks (not blockers)

### S1. `bound_heap_tids_for_owner_relation` is O(blocks) per
overflow-bearing result

When `expand_scan_results_with_bound_heap_tids_relation` is called
for K results and any have `has_overflow_heaptids = true`, each
overflow-bearing result triggers a full main-fork block scan via
`overflow_tuple_refs_for_owner_relation`. The old chain version did
the same algorithm but against an in-memory chain; the new version
pays PG buffer-manager lookup per block.

This is correct, but at high overflow density (many backlinks
exceeding inline capacity) you can land in a regime where the
overflow scan dominates the saved materialization. The bench
fixture is `ec_real_10k` / `ec_real_100k` — bulk-loaded, low
overflow density — so the bench would not catch this.

Concrete ask: either (a) document the assumption ("overflow
density is expected to remain low; if a future workload increases
it, build a per-scan overflow index"), or (b) bench against a
corpus with explicit high-overflow churn (e.g. churned `ec_diskann`
under sustained inserts) to bound the regression. Not a release
blocker.

### S2. `R: GraphReader + ?Sized` is unusual and unnecessary today

The generic functions added in `scan.rs` use `R: GraphReader + ?Sized`.
Neither current implementor is unsized; the `?Sized` bound enables
`&dyn GraphReader` callers that don't exist. Pure style nit — drop
the bound unless dyn-dispatch is planned, to keep the API surface
honest about what it currently supports.

### S3. Bench reports mean only, missing percentiles + cache state

This is the systemic bench-harness gap I called out in
`reviews/task-51/027-sidecar-sweep-pressure-reduction/feedback/2026-05-24-01-reviewer.md`.
The before/after table here reports `mean` (`61.9 ms → 1.72 ms`)
with no p50/p95/p99 and no `cache_state` field. The win is so large
that even a p99 reading would clearly favor the change, but the
practice gap should be closed at the harness level. Not a packet
blocker; reference the prior feedback so the coder isn't refighting
this per-packet.

## On the speedup claim itself

The 36× headline number is consistent with what was actually
removed:

- 100k index, 46.1 MiB chain.
- `ambeginscan` allocated and copied that full chain on every
  scan.
- `list_size = 64` visits ~100 nodes ≈ ~0.1% of the index.
- Eliminating the 99.9% wasted copy is exactly what produced the
  win.

So the size of the win is *not* surprising — it's the size of the
mistake that was there before. That cuts both ways: it's a genuine
improvement, AND it tells you the prior bench claim that "DiskANN
is slow" was largely a measurement artifact of `ambeginscan` cost,
not an algorithmic property of Vamana. Worth carrying this insight
into how the Task 55 round closes out: the prior "DiskANN is 2.8 s
at 1M (comparator manifest)" reading included this same fixed cost
and may also collapse under the same optimization on a 1M run. That
is exactly why H1 (1M validation) is the load-bearing ask here.
