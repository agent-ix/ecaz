# Reviewer Feedback: Open RaBitQ Storage Format For ec_diskann

Follow-up to `2026-05-24-01-reviewer.md`. Not a blocker on packet 005;
this is a scoping note asking the coder to open a new task for a
follow-on feature.

## Ask

Open a new task under `plan/tasks/` (next free numeric slot, e.g.
`60-ec-diskann-rabitq-storage-format.md`) for:

> **Add `rabitq` storage format to `ec_diskann`.**

Goal: make RaBitQ-1bit codes available as a DiskANN payload, alongside
the existing `pq_fastscan`, so operators can trade DiskANN's
graph-traversal recall/latency curve against RaBitQ's much smaller
on-disk footprint.

## Motivation

The Task 55 packet 005 win restores DiskANN/Vamana as a real latency
contender on AWS (1.72 ms mean at 100k, list_size=64). The remaining
weakness is index size: `ec_diskann` is hardcoded to `pq_fastscan` at
`src/am/ec_diskann/options.rs:52`, so today there is no DiskANN
quantizer choice. Operators who want a smaller DiskANN index have no
knob.

Size extrapolation (from existing landed measurements):

| index                            | 100k        | 1M (extrapolated) | per-row |
| -------------------------------- | ----------: | ----------------: | ------: |
| `ec_diskann` + `pq_fastscan`     | 46.1 MiB    | ~461 MiB          | 483 B   |
| `ec_ivf` + `rabitq`              |  —          | 298 MiB (measured)| ~313 B  |
| `ec_diskann` + `rabitq` (target) |  —          | ~150–250 MiB      | ~160–260 B |

The DiskANN+RaBitQ target sits below `ec_ivf`+RaBitQ because the
1-bit code replaces the PQ payload while the per-node graph
neighbours (~32 × 4 B = 128 B) stay constant. This would make
DiskANN+RaBitQ the smallest competitive ANN index in the workspace.

Storage win is the headline; latency/recall is the gate. Whether the
RaBitQ-on-DiskANN graph descent maintains recall parity with the
PQ-FastScan prefilter is an open question that the task should answer
by measurement.

## Scope (for the new task to refine)

1. **Storage format enum + parse** — extend
   `src/am/ec_diskann/options.rs::StorageFormat` to add
   `RaBitQ`, wire `parse_reloption`, `as_str`, and `DEFAULT`
   policy (default stays `pq_fastscan`).
2. **Build-side encode** — emit RaBitQ payloads in the DiskANN
   build path. Reuse the existing RaBitQ encoder used by `ec_ivf`
   and `ec_spire` (`src/quant/rabitq.rs` or wherever the IVF +
   spire callers consume it). Per-node payload replaces the
   PQ-FastScan payload in `VamanaNodeTuple` (or a new tuple variant
   if mixing formats on disk is unsupported).
3. **Scan-side prefilter** — implement a RaBitQ binary-sidecar-style
   prefilter for DiskANN greedy descent. This is the path that
   already benefits from packet 005's optimization, so the new
   format should not regress the materialization-avoidance work.
4. **Backwards compatibility** — existing `pq_fastscan` indexes
   must keep loading and scanning unchanged. Tag the on-disk
   `INDEX_FORMAT_V3_DISKANN` with a storage-format discriminator if
   not already present (see metadata-page layout in
   `src/am/ec_diskann/page.rs`).
5. **Tests** — pgrx tests for build + scan against both formats,
   plus a recall parity check at 100k showing RaBitQ-on-DiskANN
   recall@10 is within an explicit acceptable delta of
   PqFastScan-on-DiskANN at matched list_size.
6. **Bench gate** — a packet under `benchmarks/<topic>/` measuring
   PqFastScan-vs-RaBitQ on DiskANN at 100k AND 1M (per StR-007),
   reporting size, recall@10, p50/p95/p99 latency, cache_state,
   and host-parity fields per the systemic harness asks from
   `reviews/task-51/027-sidecar-sweep-pressure-reduction/feedback/2026-05-24-01-reviewer.md`.

## Reusable code to lean on, not duplicate

- RaBitQ encode/decode kernel — already consumed by `ec_ivf`
  (`src/am/ec_ivf/quantizer.rs`) and `ec_spire`
  (`src/am/ec_spire/quantizer/`). New `ec_diskann` consumer should
  call the same shared crate-internal path, not re-implement.
- Binary sidecar prefilter pattern — already implemented in
  `src/am/ec_diskann/scan_query.rs` for the existing
  `PAYLOAD_FLAG_BINARY_SIDECAR` path. The RaBitQ payload should
  slot into the same prefilter shape if possible.

## Out of scope for the new task

- DiskANN turboquant variant (separate decision).
- Mixed-format indexes (one DiskANN index with mixed PQ + RaBitQ
  nodes). Pick one format per index at build time.
- Migration of existing `pq_fastscan` indexes to RaBitQ
  in-place — operators should rebuild if they want to switch.

## Reporting requirement (carry forward from prior feedback)

This is also the next opportunity to fix the systemic clarity gap:
the new task's bench rows MUST carry an explicit `storage_format`
field in `results.jsonl`, not just in the EXPLAIN row. Task 55
packet 005's `latency`/`storage` rows do not currently carry that
field, which is why a reader has to dig into the EXPLAIN log to
confirm `pq_fastscan` was the path measured. Same systemic harness
gap I called out in
`reviews/task-51/027-sidecar-sweep-pressure-reduction/feedback/2026-05-24-01-reviewer.md`
items 4 and §Gap E.

## Acceptance for "we have RaBitQ on DiskANN"

Minimum to land:

1. `CREATE INDEX ... USING ec_diskann WITH (storage_format = 'rabitq')`
   builds cleanly at 100k+ corpus.
2. Scans return correct results (recall@10 ≥ existing
   `pq_fastscan` minus an explicit, measured delta).
3. Index size at 1M is smaller than the corresponding
   `pq_fastscan` index — exact target left to the bench, but
   ≥ ~30% reduction is the qualitative bar that makes the format
   worth shipping.
4. Bench packet under `benchmarks/<topic>/` records the comparison
   per the reporting requirement above.

Not strictly required to ship but very desirable:

- A `pq_fastscan` vs `rabitq` Pareto chart at 100k AND 1M so
  operators can pick the format from the recall/latency/size axes.
