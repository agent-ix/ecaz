# Task 165 packet 021 review

No M3/phase signoff. The disjoint-shard drill is meaningful progress and proves
the fixture can operate after pruning each node to its owned heap rows, but the
closeout claim is broader than the evidence and several prior P1 blockers remain.

## Findings

### P1 - Phase closeout evidence is still below the Task 165 and repository gate

The latest evidence remains a 2k-row/50-query local fixture. Task 165 requires
drill logs plus 50k multinode distinct_recall >= single-node - 0.001 via
`ecaz bench suite` in a release build
(`plan/tasks/165-ec-distann-m3-lifecycle-faults.md:33`). The repository closeout
rule for scan/index/storage changes requires 10k/50k/100k recall, latency, and
storage evidence via `ecaz bench suite`, packet-local and traceable to
`results.jsonl`.

Packets 019/020 call `ecaz bench recall` directly on a generated 2k
`benchgate_*` copy (`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:781`)
and packet 021 adds a destructive fixture drill. There is still no suite config,
suite manifest, `results.jsonl`, 10k/50k/100k matrix, latency result, or storage
result in the Task 165 packets.

### P1 - FR-082 active epoch publication is still not wired into reads

The published epoch is stored in metadata (`src/am/ec_distann/epoch_manifest.rs:74`),
but scans continue to use the session GUC epoch (`src/am/ec_distann/roster.rs:77`)
and construct placement/fingerprints from the GUC-derived directory
(`src/am/ec_distann/roster.rs:140`). The epoch-swap-under-load drill publishes
epochs 1/2 while the scan SQL pins `ec_distann.epoch=1`
(`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:612`,
`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:654`).

This remains a metadata write/churn smoke test, not proof that queries during a
real publish consume a new epoch atomically or return wholly from one published
epoch.

### P1 - NFR-020 fault taxonomy is still incomplete

The fixture currently reports six fault drills: simulated network partition,
epoch bump no false reject, remote content divergence, missing/reindexed remote
index, remote backend termination, and placement drift. NFR-020/TC-042 also
call for cases such as remote statement timeout, hop-round failure mid-beam,
missing node record, missing heap row/co-placement drift, mid-insert failure,
and mid-delete failure (`spec/non-functional/NFR-020-distann-fault-behavior.md:31`,
`spec/tests.md:233`). Those are still not present in the latest summary.

This is not yet the "100% drill pass across the taxonomy" acceptance criterion.

### P2 - The disjoint-shard signature ignores returned rank order

The packet claims a byte-identical top-k result signature before/after pruning,
but the signature query aggregates `id` values ordered by `(qid, id)`:

```
SELECT md5(string_agg(id::text, ',' ORDER BY qid, id)) ...
```

(`crates/ecaz-cli/src/commands/dev/distann_multicluster.rs:728`)

That proves the unordered top-k id set per query stayed the same. It does not
prove byte-identical ranked output. A rank-order regression within a query would
produce the same md5. The drill should carry ordinality/rank from the lateral
subquery and aggregate by `(qid, rank)` with distance included if the claim is
"byte-identical."

### P2 - Disjoint pruning uses a diagnostic raw-tuple decoder without structural validation

`ec_distann_list_directory` reads raw node tuple bytes and slices the heap TID
and flags offsets directly (`src/am/ec_distann/remote_endpoint.rs:76`,
`src/am/ec_distann/remote_endpoint.rs:90`). `resolve_owned_rows` uses the same
raw slicing pattern for the data path (`src/am/ec_distann/remote_endpoint.rs:356`).
Neither path validates the node tuple tag/length/format before trusting those
offsets.

Because packet 021 now uses `ec_distann_list_directory` to drive destructive
heap-row pruning, this should use the typed node tuple decoder or equivalent
bounds/tag validation before it feeds DELETE ctids.

### P2 - The transport still aliases logical node identity by conninfo

The transport pool remains keyed only by conninfo
(`src/am/ec_distann/remote_transport.rs:76`). Both expand and materialize setup
apply target node identity sequentially and then launch concurrent futures using
`connections[request.conninfo]` (`src/am/ec_distann/remote_transport.rs:165`,
`src/am/ec_distann/remote_transport.rs:224`,
`src/am/ec_distann/remote_transport.rs:369`,
`src/am/ec_distann/remote_transport.rs:425`). If multiple logical remote owners
share a conninfo, both requests can run under the last-applied `local_node_id`.

The current real 3-instance fixture avoids this by giving each node a distinct
port, but the loopback/logical-shard path remains incorrect unless the pool key
includes identity or concurrent same-conninfo requests are serialized through
separate sessions.

### P3 - Packet 021 has no artifact manifest

The packet lacks `artifacts/manifest.md`; the request cites only the summary
log. For this packet especially, the manifest should pin the exact head SHA,
command, fixture parameters, pruning model, and the before/after signature lines.
