# Task 165 packet 010 review

No signoff for the row-payload endpoint yet. The architecture is the right next slice, but the endpoint currently trusts caller-supplied send functions too much.

## Findings

### P1 - Row payload shipping must derive or verify `typsend`; accepting executable function names is not safe enough

`ec_distann_materialize_row_payloads` accepts `payload_send_functions text[]` from the caller (`src/am/ec_distann/remote_endpoint.rs:340`). `build_payload_sql` only checks that each function string is an identifier and then executes it against the heap column (`src/am/ec_distann/remote_endpoint.rs:493`, `src/am/ec_distann/remote_endpoint.rs:495`, `src/am/ec_distann/remote_endpoint.rs:498`). `validate_send_function` rejects punctuation injection, but it still allows any valid unqualified or schema-qualified function name (`src/am/ec_distann/remote_endpoint.rs:537`).

That is a correctness and security boundary problem for a SQL-visible remote endpoint. A caller can supply a valid identifier that is not the column type's `pg_type.typsend`, or a user-defined function with side effects that accepts the column type and returns `bytea`. Unqualified names also resolve through the active search path, so even built-in-looking names such as `int8send` are not pinned to `pg_catalog`. The packet test covers an injection-shaped string (`src/tests/ec_distann_basic.rs:1291`), but not a valid wrong function or search-path hijack.

The endpoint should derive the send function on the owner from the heap relation metadata, or validate exact equality against the owner-side `pg_type.typsend` for each requested column and execute a schema-qualified/OID-derived function name. The existing SPIRE typed payload path is a good precedent: it looks up `attr.atttypid`, `typ.typsend`, and the send proc namespace/name on the owner (`src/lib.rs:15937`, `src/lib.rs:15945`, `src/lib.rs:15956`) and stores a quoted qualified send function (`src/lib.rs:16017`) before building payload SQL (`src/lib.rs:16617`). Distann should use the same owner-derived metadata pattern rather than trusting coordinator-provided executable names.

### P2 - The shared resolver still needs raw tuple validation

This endpoint uses `resolve_owned_rows` before fetching heap payloads (`src/am/ec_distann/remote_endpoint.rs:381`). As noted for packet 009, that helper slices raw node tuple bytes without checking tag/length/flags (`src/am/ec_distann/remote_endpoint.rs:285`). Please fix the shared resolver so both materialization endpoints return classified errors instead of panicking or decoding non-node data.

### P3 - `heap_relation_qualified_name` leaks syscache-allocated names

`heap_relation_qualified_name` calls `get_rel_name` and `get_namespace_name` (`src/am/ec_distann/remote_endpoint.rs:465`, `src/am/ec_distann/remote_endpoint.rs:474`) and converts the returned C strings, but never `pfree`s either pointer. This is small per call, but the row-payload endpoint is on the scan hot path. Mirror the existing pfree discipline used around syscache-returned names elsewhere before this becomes a repeated-query backend memory leak.

## What was done well

- Shipping owner-side column bytes is the correct architectural boundary for the eventual CustomScan; remote ctids alone cannot work on a real distributed fixture.
- Preserving request order with `WITH ORDINALITY` and asserting response cardinality are good contracts for the coordinator-side consumer.
- The tests prove byte-exact `int8send` output for the happy path and cover epoch mismatch and obvious SQL injection syntax.
