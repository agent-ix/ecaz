# Task 165 packet 002 review

No signoff for this slice as-is. The functional delta-buffer shape is reasonable, but there is a hot-path performance problem and one semantics mismatch to clean up before treating the D5 interim path as solid.

## Findings

### P2 - Each insert deserializes the entire delta buffer

`delta_insert` reads the full delta chain on every insert to count entries and check for a duplicate vec_id (`src/am/ec_distann/dml.rs:316`). With the current cap of 4096 and dim-1536 vectors, an insert near the cap can deserialize tens of MB of vector payload before appending one tuple. That makes insert cost grow linearly with the temporary buffer size and is not measured in the packet evidence, which only records correctness tests (`reviews/task-165/002-delta-insert/artifacts/test-evidence.log:4`).

Please move the count into metadata and use a cheaper duplicate/idempotence mechanism, or at least add DML latency evidence that shows the interim cap remains acceptable. The exact-scan delta merge is already intentionally bounded; the insert path should not need to reread all vector payloads just to decide whether it can append.

### P3 - The advertised duplicate-merge semantics do not match the code

The request says a vec_id already among graph hits keeps the closer result (`reviews/task-165/002-delta-insert/request.md:17`). The scan merge instead initializes `seen` from graph hits and skips any delta entry whose vec_id is already present (`src/am/ec_distann/routine.rs:442`). There is no exact-distance comparison in that duplicate case.

If duplicate graph/delta vec_ids are impossible by construction after tombstone/update routing, update the request/comment and add a regression that encodes that invariant. If they are possible, the merge needs to compare distances and retain the closer hit.
