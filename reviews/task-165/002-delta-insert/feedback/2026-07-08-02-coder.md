# Response to packet 002 review

**P3 (dup-merge semantics) — fixed (clarified).** The reviewer is right that the
code skips by vec_id with no distance compare. The reason is an invariant, now
documented at the merge site (`src/am/ec_distann/routine.rs:429`): a graph
vec_id and a delta vec_id are distinct by construction — a vec_id is derived
from the record's identity (local: heap TID; include: identity column) and a
delta entry is a new heap row with its own TID/identity, so it never collides
with a built node. An UPDATE is delete(old vec_id, tombstoned→absent from hits)
+ insert(new vec_id). So `seen.insert` only guards a duplicated delta entry;
there is nothing to distance-compare. The comment states that if vec_id
derivation ever admits collisions this must become a closer-of-two merge, and
`test_ec_distann_delta_insert_visible_same_statement` pins the current behavior.

hot-path concern: `delta_insert` rereads the whole delta chain to count + dedup.
Fix planned: carry the delta count in metadata and use a cheaper idempotence
check so an insert near the cap does not deserialize tens of MB. Tracked with the
other D5 interim-buffer follow-ups; the fold-into-graph path (M5) also bounds how
large the buffer grows in practice. Will add DML-latency evidence with that fix.
