# Task 165 packet 015 review

No signoff for "all 6 FR-082 sub-ACs covered." The packet adds useful metadata state and tests, but the read path still consumes the old GUC-based epoch view and the frozen vector tier is not implemented.

## Findings

### P1 - `ec_distann_publish_epoch` is not the read path's active epoch source

The lifecycle endpoint writes `metadata.active_epoch` (`src/am/ec_distann/epoch_manifest.rs:77`), but scans still build placement and epoch identity from `ec_distann.roster`, `ec_distann.local_node_id`, and `ec_distann.epoch` GUCs (`src/am/ec_distann/roster.rs:77`, `src/am/ec_distann/roster.rs:140`). `collect_distann_hits` computes the fingerprint from that GUC-derived placement and then separately passes `current_epoch()` to the remote session setup (`src/am/ec_distann/routine.rs:395`, `src/am/ec_distann/routine.rs:402`).

That means publishing epoch 5 changes `ec_distann_epoch_status`, but a query whose session GUC remains `ec_distann.epoch = 1` still serves/fingerprints epoch 1. The packet's AC-1 test only checks that the status table reports the written number (`src/tests/ec_distann_basic.rs:1439`); it does not prove queries during an epoch swap read the published epoch or return wholly from one epoch. The design packet explicitly said GUCs needed to become fallback/override once the manifest landed; that has not happened.

### P1 - The retention gate is not wired to live scans and can be erased by publish

`ec_distann_retire_epoch` gates on `metadata.in_flight_count` (`src/am/ec_distann/epoch_manifest.rs:95`), but the only writer in this branch is the debug setter (`src/am/ec_distann/epoch_manifest.rs:150`). No scan increments or decrements the count. Worse, `ec_distann_publish_epoch` unconditionally resets `in_flight_count = 0` (`src/am/ec_distann/epoch_manifest.rs:80`), so a publish can clear a non-zero retention count instead of preserving the old epoch until readers drain.

Until scans enter/leave an epoch through a shared in-flight mechanism and counts are retained per epoch, AC-3/AC-6 are a test-only state machine, not production lifecycle semantics.

### P1 - AC-5 frozen vec_id->vector correspondence is not implemented

FR-082 requires the exact-rerank vector bound to a vec_id to be frozen for the published epoch and protected from base-table TID reuse (`spec/functional/index/distann/FR-082-distann-epoch-lifecycle.md:34`). The current expander still exact-reranks by fetching the live heap tuple through `heap_relation`, `snapshot`, `slot`, `source_attnum`, and `heap_tid` (`src/am/ec_distann/expand.rs:152`). Remote row payload materialization likewise resolves the heap relation and fetches by ctid at read time (`src/am/ec_distann/remote_endpoint.rs:402`, `src/am/ec_distann/remote_endpoint.rs:533`).

The tombstone test proves tombstone flags are honored, not that delete+VACUUM+TID-reuse cannot make a vec_id rerank against the wrong tuple. The request itself lists the multi-node frozen-vector tier as remaining work, so AC-5 cannot be marked covered.

## What was done well

- Persisting epoch state in the metadata page is a useful foundation for a real manifest/root-control implementation.
- The restart-once helper has the right outer shape for discarding partial scan state on a retriable epoch mismatch.
