# Task 165 packet 011 fix re-review

No CustomScan signoff. Shipping qual columns fixes one concrete wrong-result
case and binding the indexed attribute is progress, but the deepening cursor is
not ordering-safe and operator eligibility remains too broad.

## Findings

### P1 - Deepening serves rows beyond the proven prefix and can skip reordered rows

When convergence early-exits, only the first `effective` hits are proven. The
ordinary AM cursor tracks that boundary and deepens before reading past it. The
CustomScan instead stores every hit in `state.outputs`
(`src/am/ec_distann/custom_scan.rs:884-920`) and deepens only after
`next_output >= outputs.len()` (`src/am/ec_distann/custom_scan.rs:759`). It can
therefore emit unproven rows beyond `effective`.

On a later deepen, the code replaces the sorted output set and deliberately
keeps `next_output` (`src/am/ec_distann/custom_scan.rs:921-924`). Only the proven
prefix is stable; rows newly discovered before that cursor can be skipped, while
unproven rows from the old attempt may already have been emitted. Selective quals
make this an ordinary wrong-ORDER-BY/LIMIT case. Expose only the proven prefix
and deepen before crossing it, with a stable-prefix/seen invariant, or disable
the CustomScan for quals until it can do so. Add a regression whose qualifying
top-k requires at least two searches.

The stated cap is also not a cap: it is recomputed from the current
`state.effective` (`effective * 64`), so `effective < cap` remains true as the
bar doubles.

### P1 - Planner eligibility still accepts the wrong ORDER BY operator

`query_expr_from_sort_expr` validates only a two-argument OpExpr shaped as
relation Var plus `real[]` (`src/am/ec_distann/custom_scan.rs:164-185`). The
selected index is now bound to the Var's attribute, but the operator/opfamily and
opclass are not checked (`src/am/ec_distann/custom_scan.rs:293-317`). The path can
advertise an arbitrary operator's pathkeys while executing EC_DISTANN inner-
product search. This is a correctness requirement, not an optimization
follow-up. Bind the exact ordering operator strategy to the selected
`IndexOptInfo`, with two-index and wrong-operator EXPLAIN/result regressions.

### P2 - The qual fix makes remote materialization an unmeasured wide-row eager path

`build_payload_metadata` now ships every non-dropped column
(`src/am/ec_distann/custom_scan.rs:635-673`), and every remote hit is materialized
before the executor asks for the next row (`src/am/ec_distann/custom_scan.rs:899-920`).
Each deepen fetches the full replacement hit set again. On the real 1536-dim
tables this can ship multiple vector-sized columns for hundreds of candidates to
satisfy a small LIMIT. Collect the union of targetlist/qual Vars, materialize in
bounded batches until LIMIT is satisfied, and cache previously fetched payloads.
The single-node Task 166 latency rows do not exercise this cost.
