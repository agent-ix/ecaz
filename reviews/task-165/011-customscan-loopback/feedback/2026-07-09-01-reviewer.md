# Task 165 packet 011 review

No signoff for the CustomScan yet. The loopback happy path proves the row-shipping/reconstruction mechanism can work for `SELECT id ... LIMIT k`, but the planner/executor path is not correct for normal SQL shapes.

## Findings

### P1 - CustomScan can return the wrong result for queries with quals

The plan stores executor quals on the CustomScan (`src/am/ec_distann/custom_scan.rs:347`), but `ensure_outputs` asks the graph search for only `state.top_k` hits and truncates before those quals are evaluated (`src/am/ec_distann/custom_scan.rs:795`, `src/am/ec_distann/custom_scan.rs:807`). `ExecScan` will then filter rows after `custom_scan_access` returns them. If a query has `WHERE category = 'x' ORDER BY embedding <#> q LIMIT 10`, this path searches the global top 10, filters them, and stops; it never deepens to find the top 10 rows satisfying the qual. That can under-return or return a non-top-k qualified result set.

The remote tuple payload has a second qual bug: payload metadata is narrowed only from the plan target list (`src/am/ec_distann/custom_scan.rs:552`), while non-shipped attributes are reconstructed as NULL (`src/am/ec_distann/custom_scan.rs:948`). A remote row whose qual references a non-projected column will have that column NULL during qual evaluation, so valid rows can be dropped or NULL-sensitive predicates can be mis-evaluated.

Until the CustomScan can over-fetch/deepen through post-scan quals and ship every Var needed by both target list and quals, restrict the path to no base restrictions or fall back to the ordinary local path.

### P1 - Planner eligibility does not prove the ORDER BY matches the selected ec_distann index

The hook accepts any sort expression shaped as `(relation Var) <op> real[]` / `real[] <op> (relation Var)` (`src/am/ec_distann/custom_scan.rs:179`) and then picks the first ec_distann index on the relation (`src/am/ec_distann/custom_scan.rs:230`). It does not verify the operator is the ec_distann distance operator, that the relation Var is the indexed column for that index, or that the opclass matches the query. On a table with two vector columns or a query ordering by an unindexed vector column, this path can search the wrong index column and still advertise the query's pathkeys.

The planner candidate needs to bind the ORDER BY Var/opfamily/opclass to the exact `IndexOptInfo` it selects. If that metadata is not available yet, only enable the CustomScan for the simplest proven shape and add a regression with two ec_distann indexes where only one matches the ORDER BY column.
