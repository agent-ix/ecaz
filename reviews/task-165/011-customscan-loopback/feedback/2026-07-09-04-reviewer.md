# Task 165 CustomScan fix re-review (`d4bd980dc`)

**Status: PARTIALLY FIXED — no signoff.**

Bounding the cursor at `effective` before deepening is the right correction for
the common case, and the real-10k observation (`qual_correctness mismatch=1 →
0`) is useful. The implementation does not yet establish the stable-prefix
invariant claimed by the commit.

## Findings

### P1 - The claimed stable sort is actually unstable and has no tie-breaker

The commit says the exact-distance stable sort makes the served prefix invariant
across deepening. Both sort sites use `sort_unstable_by` on `exact_dist` alone
(`src/am/ec_distann/scan.rs:221`, `src/am/ec_distann/routine.rs:505`). Equal
distances can reorder when the deeper result vector changes length. Because
`next_output` is retained across replacement, a prefix `[A, B]` can become
`[B, A, ...]` after serving A, causing A to be returned twice and B to be
skipped.

Use a deterministic total key such as `(exact_dist, vec_id)` and preserve the
already-served identities explicitly; a tie newly discovered before the cursor
must not shift the array under that cursor. Add a regression with duplicate/equal
distance vectors that forces at least one deepen.

### P1 - Filtering remote payload misses can pull unproven hits into the counted prefix

`run_search_and_build_outputs` first receives ranked hits, then drops remote rows
whose payload is missing. `proven_prefix_len` computes
`min(effective, outputs.len())` after that filtering. If one of the first
`effective` raw hits is missing, a raw hit beyond the proven boundary shifts into
the first `effective` output positions and is incorrectly treated as proven.
Remote materialization is also repeated on every deepen, so payload appearance
can change and reorder the output array beneath `next_output`.

Track the raw proven boundary through materialization, cache the served/payload
state, and expose only successfully materialized rows whose raw rank was proven.

### P2 - The deepening cap is still self-moving

The code still recalculates `cap = state.effective * 64` on every iteration, so
`state.effective < cap` remains true as the bar doubles. This is not the fixed
cap described by the comment. Store a cap derived once from the initial bar or a
separate bounded option.
