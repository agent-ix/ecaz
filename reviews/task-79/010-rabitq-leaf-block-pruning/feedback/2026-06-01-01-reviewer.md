# Task 79 packet 010 — RaBitQ leaf block pruning

## Decision

**Accept the implementation slice.** Build-side summary materialization
and scan-side block selector both look correct, defensively shaped, and
preserve all the right fallback paths. No latency claim is made yet —
that's packet 011's job — but the code path is in place and tests
landed for the load-bearing pieces.

## What's solid

### Two-GUC contract is clean and disabled-by-default

- Build-time `ec_spire.leaf_block_rows` (0 disabled, max 4096)
- Scan-time `ec_spire.leaf_block_pruning_max_blocks_per_leaf` (0
  disabled, max 4096)

Both default 0. Existing indexes (V2 or V3 with `block_rows=0`) and
existing scans see no behavior change. Userset context. This is the
right shape for a feature behind a measurement gate.

### Scan-side selector (`select_leaf_block_row_ranges`) fallback discipline

Returns `Ok(None)` (full-leaf scan path) for:
- disabled budget (`max_blocks_per_leaf <= 0`)
- empty summaries
- non-RaBitQ scorer (TurboQuant correctly falls back per packet
  framing)
- `max_blocks >= summaries.len()` (no-op pruning would be wasted
  summary CPU)

Errors (rather than silent fallback) for:
- payload format mismatch between summary and scorer
- row range overflow (`row_base.checked_add` overflow check)
- non-finite summary score (`!ip.is_finite()`)

That separation — *unsupported* path → silent fallback, *corrupt*
path → error — matches the error-on-corruption semantics committed
in packet 009 (per my packet 007 F4). Good consistency.

### Build path (`build_leaf_block_summaries`)

Validates:
- `block_rows > 0` (caller error if 0 but path active)
- row count matches source vector count
- all rows same payload format
- dimensions > 0

Errors are descriptive. Empty rows returns empty Vec rather than
panicking.

### Tests landed (4)

`leaf_block_summaries_cover_rabitq_row_blocks`,
`select_leaf_block_row_ranges_keeps_best_rabitq_blocks`,
`prepare_single_level_snapshot_scan_candidates_uses_top_graph_when_enabled`,
`collect_quantized_routed_probe_candidates_matches_prepared_assignment_scorer`.
Last one is the parity test — pruning path vs. assignment scorer
produces equivalent results on the same rows.

### Top-graph routing through common collector

"Routed the top-graph candidate path through the common validated
quantized leaf collector so the default high-recall top-graph lane
can actually use the pruning path." This is important — if top-graph
had its own collector that didn't call the selector, the high-recall
default lane would silently skip the optimization. Single collector =
single place where pruning happens.

## Findings

### F1 — Summary is the *mean* of source vectors; document or revisit

`build_leaf_block_summaries` averages source vectors per block and
encodes the mean with the row payload format. For RaBitQ summaries,
that gives a per-block centroid score. It's a reasonable proxy for
"the best row IP in this block" but it's not provably tight — a block
with mean IP `0.5` could contain a single row at IP `0.95` that the
mean-based ranking would miss.

The packet doesn't justify this choice. Two reasonable defenses:

1. **Empirical**: packet 011's recall measurement at varying
   `max_blocks_per_leaf` will reveal whether mean-based ranking
   preserves recall well enough. If recall holds at the Task 79
   target band, the choice stands.
2. **Theoretical**: for normalized vectors, mean has known bounds on
   max-IP deviation across the block. Worth a line in the next
   packet's manifest if the math is named.

If recall drops materially in packet 011, alternatives include:
upper-bound summary (max row IP precomputed per block) or
bounding-ball center+radius. But don't preemptively complicate.

### F2 — Build memory: source vectors must be held to compute summaries

`build_leaf_block_summaries` takes `source_vectors: &[Vec<f32>]`.
That means the build path keeps raw source vectors in RAM until
summaries are written. For 100k corpus × 768-dim × f32 = ~300MB of
extra resident memory during build at `leaf_block_rows > 0`.
Probably fine on the Intel desktop, but worth tracking against
Task 72's build-perf characterization. Not blocking — the alternative
(streaming summarization) is harder and may not be needed.

### F3 — Packet 009's R1 malformed-chain test still not addressed

My packet 009 review asked for a malformed-chain rejection test
before scanner consumption landed. The scanner now exists, but I
don't see a test that constructs a malformed V3 summary segment and
verifies the scan errors rather than silently falling back. The
selector here errors on per-row format mismatch and overflow, but the
storage-layer "broken segment chain link" case isn't exercised
end-to-end.

For packet 011 (benchmark): if any benchmark run fails with a V3
decode error, that's actually the right behavior. Worth a single
fault-injection test in this slice or the next to lock that
contract. Add it before TurboQuant comparison work begins (which
would expand the surface area).

## Verdict

Implementation accepted. The code is the right shape, fallbacks are
correct, error semantics match the design intent from packet 007.

Next is packet 011 (benchmark) — the load-bearing question is whether
mean-based summaries preserve recall at the Task 79 target band while
pruning enough rows to clear the candidate gate. F1's summary-encoding
choice will be tested empirically there.
