# Task 79 packet 039 — k=3 routing breadth sweep

## Decision

**Accept as honest negative evidence.** Lowering nprobe trades p50
for recall on a steep curve. nprobe=88 lands at 45.4ms p50 (just
0.4ms over gate) but recall drops to 0.9910 (-0.15pp under gate).
Cannot get both at any tested nprobe.

The candidate count stays flat (~4.66M) because the global block
cap saturates from whichever leaves are routed — so route reduction
doesn't reduce the scored row surface.

## The frontier curve

| nprobe | candidates | p50 | recall | gates |
| ---: | ---: | ---: | ---: | --- |
| 64 | 4.66M | 38.3 ms | 0.9815 | recall ✗ |
| 72 | 4.66M | 41.6 ms | 0.9865 | recall ✗ |
| 80 | 4.66M | 43.4 ms | 0.9895 | recall ✗ |
| 88 | 4.66M | 45.4 ms | 0.9910 | recall ✗ (close!) |
| 96 | 4.66M | 47.9 ms | 0.9925 | p50 ✗ |

Steep curve, no sweet spot. The recall-vs-nprobe relationship is
constrained by routing quality at the top-graph level — if a
winning row's leaf isn't in the routed set, no block selection
can recover it.

That's an interesting separate finding: **the routing layer is
itself dropping ~0.15pp of winners at nprobe=88**. At nprobe=96
that loss is recovered. So routing breadth and block selection
both need to be tight to hit recall.

## What this reveals

The candidate surface ceiling is set by block selection, but the
recall floor is set by routing breadth. They're coupled: reducing
routing breadth costs recall faster than it saves block scoring
CPU at the high-recall band.

This rules out routing breadth as a latency-recovery axis. The
next slice needs to attack the scoring CPU at fixed nprobe=96, or
change the index shape entirely.
