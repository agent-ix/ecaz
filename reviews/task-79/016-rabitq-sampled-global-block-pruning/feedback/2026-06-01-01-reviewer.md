## What's solid

### Honest candidate accounting

> "sampled rows are not hidden. They call the normal visible
> candidate observer and accumulator path before the final block
> scan, so benchmark `candidate_sum` includes the extra sampled row
> scoring."

This is the critical correctness property. Three implications:

1. `candidate_sum` is comparable to prior packets — no metric drift
2. A sample row that happens to be a real winner can survive into
   the heap on its own merit, even if its block doesn't make the
   final cut
3. The duplicate-row dedupe path handles the case where a finally-
   selected block includes a previously-sampled row

That last point matters: without dedupe, scoring the sample then
the full block would double-count those rows. Existing dedupe path
handles it.

### Deterministic sampling

`sample_leaf_block_row_indices` uses `(sample_index * 2 + 1) * row_count / (sample_count * 2)`
— evenly spaced midpoints. For `sample_count=2`, that's ~25% and ~75%
of the row range. No randomness, no per-query state, no caching
weirdness. Reproducible.

Edge cases handled: `checked_sub` on the range bounds, saturating
`min(row_count - 1)` on the final offset.

### Two-knob composition is clean

- `ec_spire.leaf_block_pruning_global_probe_blocks`: how many blocks
  to *probe* with samples
- `ec_spire.leaf_block_pruning_sample_rows_per_block`: how many sample
  rows per probed block
- `ec_spire.leaf_block_pruning_max_global_blocks` (existing): final
  block budget after reranking

Composition: `probe_blocks >= max_global_blocks` is enforced
(otherwise no reranking happens — selector falls back to packet 014
summary-only global). Sampling disabled → fallback to packet 014.
All defaults 0.

## Findings

### F1 — Deterministic sample placement assumes uncorrelated row order (forward-looking)

The midpoint-pattern sample selection works well if row order within
a block is uncorrelated with vector "value" (IP score). If rows are
ordered (by insert time, by cluster, by some build-time sort), the
midpoint indices could systematically miss high-IP rows.

The build path partitions leaves into deterministic subleaf blocks
(per packet 009), but I don't see a strong claim about *intra-block*
row ordering. If the benchmark in 017 shows recall recovers at high
probe_blocks but stalls at low probe_blocks, the cause might be
row-order correlation, not summary insufficiency.

Mitigation if 017 reveals this: shuffled sampling (deterministic
shuffle based on block_id) or stratified sampling. Not blocking —
the midpoint pattern is the right first try.

### F2 — Cost arithmetic for the benchmark sweep

The suggested sweep is `final 320-448, probe 768-1536, sample 1-4`.
Worst case is `probe=1536, sample=4 = 6144 extra row scores per
query`. At 200 queries, that's ~1.23M extra candidate scores added
to `candidate_sum`.

So if 015's global512 row was 6.27M candidates and the equivalent
sampled-final512 would add ~1.23M sample candidates, the new
candidate count would land ~7.5M — well past the 5.2M gate. The
benefit has to come from sampling letting `final` drop to e.g. 256
or 320 with the right blocks selected, dropping the final scan to
<5.2M and offsetting the sample overhead.

The arithmetic suggests `final<=320, probe~=768, sample=2` is the
sweet spot to test first. Worth flagging this so the benchmark
sweep doesn't get distracted by combinations that mathematically
can't clear the gate.
