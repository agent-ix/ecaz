# Task 79 packet 022 — global radius block scoring

## Decision

**Accept the implementation slice.** This is a real consistency
bug fix: the per-leaf selector uses `mean_ip + query_l2_norm × radius`
(Cauchy-Schwarz upper bound), and the global selector was using
just `mean_ip`. The new `score_leaf_block_summary_ip` helper unifies
them through one path.

Given packet 021's finding that block admission is the binding
constraint, restoring the upper-bound semantics at the global level
is exactly the right surface to attack.

## What's solid

### Bug fix is clean

```rust
fn score_leaf_block_summary_ip(...) -> Result<f32, String> {
    // ... format checks ...
    if summary_format == SpireAssignmentPayloadFormat::RaBitQ && summary.gamma < 0.0 {
        return Err("ec_spire leaf V3 RaBitQ summary radius must be non-negative".to_owned());
    }
    let mean_ip = scorer.score_payload_ip(...)?;
    let ip = if summary_format == SpireAssignmentPayloadFormat::RaBitQ {
        mean_ip + scorer.query_l2_norm() * summary.gamma
    } else {
        mean_ip
    };
    Ok(ip)
}
```

Three properties:
1. **RaBitQ-specific upper bound**: only applies for RaBitQ
   summaries (TurboQuant uses mean only — defensive)
2. **Radius validation**: errors on negative radius (corruption
   guard)
3. **Format mismatch errors**: not silent fallback

Both per-leaf (`select_leaf_block_row_ranges`) and global
(`score_global_leaf_block_ranges`) selectors now call this
helper. Single source of truth for block scoring.

### New regression test

`select_global_leaf_block_row_ranges_uses_rabitq_summary_radius`
locks the contract. 7 tests pass in `leaf_block`.

## Why this might work where per-leaf radius (packet 013) didn't

Packet 013's failure mode: at the per-leaf level, radius-adjusted
ranking favored broad blocks over good-mean blocks within the same
leaf. Each leaf got K blocks regardless of summary quality, so
giving broad blocks an edge meant tighter blocks (which often had
the actual winners) lost slots to noise.

**Global ranking changes this calculus.** Global selection ranks
blocks across leaves. A high-radius block from a leaf with poor
overall summary scores still gets to compete against lower-radius
blocks from any leaf. If the radius bound is the correct upper
bound on max-row-IP-in-block, then the global ranking gets the
right blocks regardless of intra-leaf comparisons.

The packet 013 failure was *per-leaf radius being too generous*;
the packet 022 fix is *global radius restoring the upper bound
the per-leaf path already uses*. These aren't the same change.

## Finding

### F1 — Watch for the "radius dominates" failure mode at global scale

Even at global scale, radius could over-amplify if many blocks
have substantial radius. The fix is mathematically correct (it's
an upper bound), but if the bound is too loose, you'll see:

- candidate count rises (more blocks selected than before)
- recall doesn't move (loose bound = no discriminating power)

If packet 023 shows that pattern (recall stuck at 0.9675-0.9860 at
similar candidate counts), the radius bound is too loose to be
discriminating, and the residual gap is genuinely summary
information content — which is the case for multi-rep summaries.

If packet 023 shows recall climbing toward 0.9925 at the same
candidate budget, the bug fix alone closes Task 79.

## Verdict

Implementation accepted. The bug is real, the fix is consistent
with the per-leaf path, and packet 021's attribution makes this
the right surface to attack. Packet 023's benchmark is the test.
