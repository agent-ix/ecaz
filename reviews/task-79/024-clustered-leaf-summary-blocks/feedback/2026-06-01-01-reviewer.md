# Task 79 packet 024 — clustered leaf summary blocks

## Decision

**Accept the implementation slice — and this is a genuinely clever
direction I hadn't suggested.** Instead of multi-representative
summaries (which would have required a format extension), the coder
found a third path: **cluster rows within each leaf at build time
so the existing V3 single-summary blocks become geometrically
meaningful.**

This trades multi-rep's k× storage and query CPU cost for build-
time work, with the same hypothesized benefit (better block
ranking accuracy).

## Why this is interesting

The packet 015/021/023 attribution chain proved that the block
selector drops winners because the summary score isn't
discriminating. Two ways to fix that:

1. **Multi-rep**: more bits per block (k centroids). Format bump,
   k× scoring cost. (Option B from my prior framing)
2. **Better-organized blocks**: same one summary per block, but
   the block represents a coherent geometric cluster so the
   summary IS the cluster centroid. No format change, no extra
   scoring cost. (Option D — this packet)

If clustered blocks produce meaningful centroids:
- mean-summary becomes a *real* cluster centroid, not the mean of
  random rows
- the radius bound becomes a tight cluster radius, not a noisy
  upper bound on arbitrary contiguous rows
- both mean-only and radius-bound scoring should improve

The radius-weight knob (`leaf_block_pruning_summary_radius_weight`)
lets the benchmark resolve exactly which scoring strategy works
best on clustered blocks — sweep weight=0.0/0.5/1.0 to compare
mean-only, mid-blend, and full Cauchy-Schwarz bound.

## What's solid

### Reuses existing k-means infrastructure (Task 69)

`common_training::train_spherical_kmeans` is the rayon-parallel
shared k-means from Task 69. Plus `assign_vectors_to_centroids`.
That's the right architectural reuse — no new training code,
existing parallel paths.

### Determinism preserved

`seed.wrapping_add(leaf_pid)` per-leaf seeding. Builds are
deterministic across runs (same corpus + same leaf_pid → same
clustering).

### Defensive build-time validation

- `block_rows == 0`: error
- Row count vs source vector count mismatch: error
- Empty inputs: early return preserving input
- Non-finite source values: error
- Dimension mismatch: error
- Centroid index out of range: error (defensive guard against
  k-means internal corruption)

### V3 format unchanged

`layout_leaf_rows_for_block_summaries` runs only when
`ec_spire.leaf_block_rows > 0`. V2 and no-summary V3 leaves are
unchanged. The summary chain coverage validation continues to
apply post-reorder.

### Radius-weight default 1.0 preserves prior behavior

Existing global radius behavior (packet 023) is the default at
weight=1.0. New benchmarks can sweep down to weight=0.0 (mean-
only) to compare clustered-vs-arbitrary block summaries with
the same scorer.

### Tests landed

- `leaf_block_layout_groups_rows_before_summary_chunks` — verifies
  the layout invariant (cluster-grouped before summary chunking)
- `leaf_block_summary_radius_weight_controls_rabitq_bound` —
  verifies the weight knob semantics

## Findings

### F1 — Row reordering invariant check (verified by spot read)

The diff shows `materialization_rows.rows.into_iter().zip(
materialization_rows.source_vectors).zip(centroid_indexes)` —
preserving `(row, source_vector, centroid_assignment)` tuples
through the reorder. That keeps vec_id ↔ row ↔ source_vector
correspondence intact.

Worth checking once more: the row_index used in the summary
chain (`row_base`, `row_count`) refers to the *post-reorder*
position. Since the summary chain is built after the reorder,
this is internally consistent. Downstream scan code uses
`(row_base, row_count)` ranges to skip block reads, and those
ranges are over the post-reorder layout — which is what gets
written to disk. No inconsistency.

### F2 — Build cost worth measuring at packet 025

K-means at `block_count ≈ leaf_size / 64` per leaf. For 100k
corpus at n=128: ~12 clusters × 128 leaves = ~1,540 k-means
runs at ~50 vectors per run. Rayon-parallel, but per-leaf
overhead adds up. Worth reporting build-time delta in packet
025's manifest so the build/quality tradeoff is auditable.

If clustering adds e.g. ~10-30 seconds to a 100k build, that's
acceptable for a Task 79 win. If it adds minutes, it's still
acceptable but worth noting against Task 72's parallel build
work.

### F3 — Sweep recommendation for packet 025

The radius-weight knob is the load-bearing variable. Suggest:

| final_blocks | radius_weight | what it tests |
| --- | --- | --- |
| 384 | 0.0 | clustered mean-only vs packet 015 mean-only |
| 384 | 0.25 | partial bound |
| 384 | 0.5 | mid blend |
| 384 | 0.75 | partial bound |
| 384 | 1.0 | clustered full radius vs packet 023 full radius |
| 320 | best weight from 384 sweep | smaller budget at best weight |
| 288 | best weight | smaller still |

If clustered mean-only at global384 beats packet 015's 0.9675 by
even 2pp (to 0.99+), Task 79 might close at smaller budgets
(global288 or 320 = under candidate gate with margin) without
the +2.65ms multi-rep cost.

## Verdict

Implementation accepted. This is the most evidence-informed slice
in the sequence — it's targeting the exact failure mode (block
ranking accuracy) with the minimum infrastructure cost (no
format change, reuses Task 69 k-means). The radius-weight knob
makes packet 025 a directly-comparable test to all prior packets.

Looking forward to packet 025 to see if clustered-block ranking
delivers the 2-3pp recall improvement needed to close Task 79
within the existing p50 gate.
