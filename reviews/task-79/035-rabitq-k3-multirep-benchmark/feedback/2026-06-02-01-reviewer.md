# Task 79 packet 035 — k=3 multi-representative benchmark

## Decision

**Accept as critical breakthrough — Task 79 is now within striking
distance.** k=3 at `global768` clears recall AND candidate gates
simultaneously for the first time in 35 packets: 0.9925 recall ✓,
4.86M candidates ✓. Only p50 (49.25ms) misses by 4.25ms.

**This proves the remaining failure mode is purely latency, not
recall ceiling.** That's a fundamentally different problem than
the prior 34 packets characterized.

## The breakthrough result

| k | best (recall, cands) | p50 | gate status |
| --- | --- | ---: | --- |
| k=1 (single rep, packet 015) | 0.9860 @ 6.27M | 47.5 ms | recall ✗ cands ✗ p50 ✗ |
| k=2 (packet 029) | 0.9905 @ 4.86M | 48.67 ms | recall ✗ |
| **k=3 (packet 035)** | **0.9925 @ 4.86M** ✓ ✓ | **49.25 ms** | **only p50 ✗ by 4.25ms** |

For the first time the recall gate is hit at a candidate-gate-
compliant budget. The remaining work is shaving ~4.25ms from p50.

## What this tells us empirically

The previous 30+ packets characterized a recall ceiling. **That
ceiling didn't exist** — it was an artifact of insufficient
summary information content. k=3 broke through it cleanly.

That validates the multi-representative hypothesis from packet 015
F2 (over 20 packets ago). It also validates packet 026's
diagnostic interpretation that the missing winners were "blocks
that needed better summary discrimination, not bigger budget."

## The p50 cost calibration

k=2→k=3 added ~4.4ms p50 at the same cap (640: 44.85ms → 49.91ms
in packets 029 vs 035). That cost is consistent with the
back-of-envelope estimate I did earlier: extra summary scoring CPU
scales with k. k=3 at cap768 = 2304 summary scores per query vs
k=2 at cap640 = 1280 scores.

So the question is: can we get k=3 *recall* at k=2 *latency*?

## Two viable closing paths

Coder's recommendation names both correctly:

### Path A — Per-leaf score calibration with k=2

Hypothesis: the k=3 recall improvement came from better cross-leaf
score comparability (3 centroids per block give a better summary
of the block's spread). A learned per-leaf score normalization
factor at build time could potentially deliver similar cross-leaf
comparability at k=2 cost.

- Cost: build-time only (zero scan-time CPU)
- Risk: calibration factor might not capture the same signal as
  the extra centroid
- Coder is testing this in packet 036 (leaf-contrast-calibration,
  in flight)

### Path B — Two-stage scoring (k=2 shortlist + k=3 final)

Hypothesis: use cheap k=2 score for first-pass block ranking, then
score top-N candidates with k=3 for final selection.

- Cost: k=2 cost on all probe blocks + k=3 cost on small final
  set = ~3-4ms estimated overhead total
- Risk: shortlist quality is constrained by k=2 score, might lose
  the k=3 winners that would've been recovered by k=3 ranking

If Path A delivers, Task 79 closes cleanly. If not, Path B is the
fallback.

## What's solid in the experiment

## Verdict

Task 79 is now precisely characterized as a "lower the p50 from
~49.25ms to ≤45ms while preserving k=3-level recall" problem. That's
a much smaller and clearer optimization target than "improve summary
discrimination at unknown rank distance" was.

Packet 036 (leaf-contrast-calibration) is the cleanest first try.
If calibrated k=2 can hit ~0.9920+ recall at cap640-ish budget,
Task 79 closes at the cap that already passed p50.

This is the closest result yet by every metric. Look forward to 036.
