# Task 79 packet 003 — row-budgeted routing (Phase 3)

## Decision

**Accept the slice as a proof-of-mechanism with the closeout direction
the request itself proposes** (move the budget into route generation,
not post-route). The code is correct, the GUC contract is safe, and the
measurement honestly reports both the win (mechanism works, recall
preserved) and the gap (post-route placement leaves upstream cost
on the table).

This is not a Task 79 *closing* slice — it doesn't clear both gates
simultaneously. But it's a clean step toward one.

## What's solid

### Code correctness

- **GUC contract is safe-by-default.** `ec_spire.max_routed_candidate_rows`
  defaults to `0` (disabled), bounded by `EC_SPIRE_MAX_MAX_CANDIDATE_ROWS`,
  Userset context. Existing behavior unchanged unless explicitly set.
- **`apply_leaf_route_candidate_row_budget` is well-shaped.** Iterates
  ordered leaf routes, reads header `assignment_count` per route via
  `object_store.read_object_header`, accumulates with `saturating_add`,
  stops when `selected_rows >= max_rows`. Early-return on
  `leaf_routes.len() <= 1` prevents the budget from killing single-leaf
  scans.
- **No new unsafe blocks.** All new code lives in safe Rust paths;
  the only I/O is the existing object-store header read surface.
- **Tests landed.** `test-max-routed-candidate-rows.log` and
  `test-caps-routed-candidate-rows.log` show targeted tests passed.
- **`cfg!(test)` short-circuit on the GUC reader** keeps unit tests
  deterministic by forcing the disabled value — fine, since the
  candidate-side tests pass the budget value explicitly through the
  scan-plan plumbing.

### Measurement quality

- **Funnel data is healthy and per-query.** Spot-checked the
  n256/row26k/nprobe=128 funnel: `leaf_route_count` varies query-to-query
  (72, 64, 69, 69, 68 across q1-q5) because the budget cap is reached
  at different cumulative row counts per query. `candidate_count` also
  varies (26024, 26063, 26093, 26370, 26229). Not the Task 75 invariance
  bug.
- **The route_sum vs placed_route_sum table is the load-bearing
  diagnostic.** Showing that at n256/nprobe=128/192/256 the *generated*
  route_sum scales (25600/38400/51200) while the *placed* route_sum
  stays flat at 13270 is exactly what proves the post-route placement is
  the bottleneck. Good honest measurement.

### Best Pareto row

`n256/f16/row26k/nprobe=192`:
- candidates: 5,252,750 (within 1% of the 5.2M gate)
- recall@10: 0.9975 (matches gate exactly)
- p50: 65.3 ms (6.7% *worse* than baseline)

That's the most informative point: both quality gates effectively
satisfied, but latency went the wrong direction. The cost is in
upstream route generation (51k routes at nprobe=256 vs 13k placed)
plus per-route header reads to compute assignment counts.

## Findings

### F1 — Header-read cost per route is the upstream tax (non-blocking)

The current `apply_leaf_route_candidate_row_budget` reads the header
of every candidate leaf in route order until the cap is hit. At
n256/nprobe=192, that's ~192 header reads/query before the cap fires.
The reads are small but the *I/O surface* per query expands. In the
next slice — where budget moves into route generation — the header read
should be cached or amortized:

- consider caching the routing-time assignment-count look-up per
  `(leaf_pid, object_version)` within a scan session, since the same
  leaf can be re-evaluated across rescans;
- if the next slice fetches assignment counts from the routing object
  rather than per-leaf headers (e.g. persisting `source_count` on the
  routing-child level per the task spec Phase 3 option 1), it can avoid
  per-route I/O entirely.

Not blocking this packet — the cost shows up but the slice is
correctly framed as exploratory.

### F2 — One row missing from the matrix that would tighten the closeout

The matrix has `row26k` and `row36k` budgets but not `row52k` for n256.
The funnel file `funnel-100k-rabitq-n256-f16-b0-tg256-row52k.jsonl` is
listed in the artifacts directory but doesn't show in the request's
result table. If that file has data, surface it — it would establish
whether a looser budget at n256 recovers the baseline's p50 while
holding candidate count below 10M.

### F3 — Build-vs-scan ownership of `assignment_count` (forward-looking)

The Phase 3 spec's option 1 (persist `source_count` on routing children)
is the natural next move for both correctness and performance:

- it removes the per-route header read at scan time;
- it makes the route-generation stop-condition trivially cheap;
- it does require an on-disk format consideration — please get an
  ADR or format-version note before the next slice if it touches the
  routing partition object schema.

The Phase 3 spec's option 2 (lightweight estimate from existing
headers) would avoid the format change but at the cost of accuracy.
This packet's per-route I/O is option-2-shaped. Worth deciding which
direction the next slice takes before code is written.

## Verdict

Accept. The slice is a clean proof-of-mechanism with honest measurement
of where the bottleneck moves. Next slice should:

1. Move the budget into route generation as a stop-condition (the
   request's own recommendation).
2. Decide between persisting `source_count` on routing children
   (cleaner, requires format consideration) vs lightweight header
   estimates (no format change, more I/O at scan).
3. Surface the row52k data if it's already captured.

No further code needed on this slice — it stands as Phase 3's "the
mechanism works, placement is wrong" checkpoint.
