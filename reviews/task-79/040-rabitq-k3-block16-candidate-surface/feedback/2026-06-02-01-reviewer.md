# Task 79 packet 040 — k=3 block16 candidate surface

## Decision

**Accept as interesting Pareto point but not a path to closure.**
block16 + k=3 at global1216 produces a striking result: 3.88M
candidates ✓ (clears *strong* ≤4M target with margin), 0.9940
recall ✓ (above gate by 0.15pp). But p50 jumps to 52.64ms — 7.6ms
over the gate, worse than the block32 baseline by ~4.7ms.

The candidate axis has now been pushed past the gate. The
remaining problem is purely scoring-CPU latency, and block16 makes
it worse, not better.

## The new Pareto picture

| config | candidates | p50 | recall | best metric |
| --- | ---: | ---: | ---: | --- |
| k=3 block32 g736 fast-path (035+038) | 4.66M | 47.91 ms | 0.9925 | best p50 |
| k=3 block16 g1216 (040) | **3.88M** | 52.64 ms | 0.9940 | best cands+recall |

So we have two viable "best" recipes depending on what you weight:

- **Best p50 (block32)**: 2.91ms over p50 gate, recall and cands gates barely passed
- **Best candidates+recall margin (block16)**: 7.6ms over p50 gate but recall +0.15pp and cands well under strong target

If Task 79 is interpreted strictly, block32 is closer (smaller gate miss). If interpreted operationally with margin, block16 has a more robust shipping profile (better worst-case recall, fewer candidates).

## Why block16 lost on p50

The packet's diagnosis is correct:
- block16 doubles the summary count vs block32
- Summary scoring is now the dominant work, not row scoring
- The 19,200 routed-leaf object reads are fixed per query —
  14.97 GB object bytes regardless of cap

So shrinking blocks adds CPU for summary scoring of ALL routed-leaf
summaries (not just those in the final cap), which is fixed at
nprobe=96 routed leaves. That's a fixed-cost amplification.

## What this tells us about the remaining design space

After 40 packets, the optimization budget is now clearly bounded by:

1. **Summary scoring CPU at fixed nprobe=96 routed leaves** —
   the dominant cost. Cannot reduce without cutting routing
   breadth (which 039 ruled out).
2. **Object read bytes (14.97 GB at nprobe=96)** — fixed regardless
   of selector. This is leaf payload + summary chain I/O.
3. **Block selection at the global cap** — already optimized.

The only remaining technical paths to attack (1) are:
- SIMD/cache-aware multi-rep RaBitQ inner loop (real engineering,
  uncertain payoff)
- Cheap first-stage block shortlist (coder's recommendation) —
  but packet 037 showed this is constrained because the shortlist
  must cover the recall tail
- Reduce summary scoring scope to non-routed-leaf subset (would
  require a scan-time hierarchical pre-filter — new architecture)

## My read on Task 79

After 40 packets and 5 distinct k=3 working recipes (varying block
size, cap, scoring path), the design space at the current
algorithm shape is exhausted. The recall ceiling was broken at
packet 035; the residual gap is a documented ~3-8ms latency
overhead from the k=3 scoring CPU.

The honest framings now are:

**Document the closure as a tradeoff:**
- Pick block32/g736/k=3/fast-path as the operational recipe
- Recall ≥0.9925 ✓, candidates ≤5.2M ✓ (4.66M), p50 47.91ms
  (2.91ms over 45ms target — 6.5% miss)
- Task 79 spec allows packets that "intentionally change rerank
  width and prove the full tradeoff" — by analogy, a documented
  trip-off variance closure with explicit recall/cands/p50 numbers
  is a meaningful operational artifact
- The infrastructure (V4 format, multi-rep build, fast-path
  selector) lands and ships

**Or pause:**
- Same artifact, but framed as "Task 79 remains formally open;
  best-known SPIRE recipe documented for future work"
- Useful if there's near-term plan to attack the k=3 scoring kernel

**Or commit to k=3 SIMD kernel work:**
- 2-3 more packets, uncertain outcome
- If it lands 3-4ms savings, Task 79 closes strictly

## Verdict

block16+k=3 accepted as new Pareto point. Updated best-known
recipes:
- **Strict-gate-closest**: block32/g736/k=3/fast-path (47.91ms,
  2.91ms over)
- **Best-margin**: block16/g1216/k=3 (52.64ms, but recall and
  cands have safety margin)

User-facing decision: which of the three framings above to take.
Genuinely a product/scope call now.
