# Task 79 packet 007 — subleaf block pruning design (ADR-074)

## Decision

**Accept ADR-074 as the Phase 4 design checkpoint.** This is the right
direction given the accepted Task 79 evidence: packets 001-004 bounded
the geometry, replica, and route-budget alternatives, and the remaining
failure mode is whole-leaf granularity. Query-aware block pruning
directly attacks that mode.

The ADR is structurally sound, cites the bounding evidence correctly,
and commits to the V3 reject-unknown format pattern that the
ecosystem already uses (ADR-070 Option A). Approve to start the
implementation packet.

## What's solid

- **Bounded-alternative table** cites real measured numbers from
  packets 001/002/004 — not hand-waving.
- **Query-aware vs fixed-prefix** distinction is correctly made and
  matches the empirical evidence from packet 006's apparent abandonment
  (see F1 below).
- **Reject-unknown V3 format bump** is the right pattern. Leaving V2
  decoding unchanged as fallback preserves the upgrade story.
- **Storage contract specifics:** little-endian fields, length checks,
  reject-malformed validation, summary chain reachable from leaf meta
  (not embedded in row segments). All defensible choices.
- **Acceptance criteria** match the Task 79 spec gates exactly:
  recall ≥0.9925, candidates ≤5.2M (strong ≤4.0M), p50 ≤45ms or 25%
  better, retained/returned comparable. No goalpost shifting.
- **TurboQuant deferred** until RaBitQ has a defensible row — same
  discipline as packets 003/004.

## Findings

### F1 — Stale packet directories should be cleaned up (housekeeping)

`reviews/task-79/005-rerank-budget-probe/` and
`reviews/task-79/006-leaf-prefix-row-cap/` each contain only a suite
config and an empty artifacts directory — no request.md, no run logs.
The ADR's alternatives table covers what looks like the 006 result
("Fixed Leaf Prefix or Build-Time Row Ordering — Rejected as a closing
design"), suggesting these probes were tried and abandoned in favor of
this design.

If those probes did run and produced "negative-result" data, the
packet should still have a request.md and a minimal manifest so the
evidence chain is auditable. If they were started and abandoned
without measurement, the directories should be removed. Leaving
half-built packet directories on the branch makes the dev-line state
hard to read.

### F2 — Block size choice is unconstrained (forward-looking)

> "The natural first block unit is the existing leaf V2 physical column
> segment size, or a small multiple of it if measurement shows segment
> summaries are too fine."

For a ~780-row leaf at n=128 or ~390-row leaf at n=256, block size
drives:

- summary count per leaf (build cost, storage)
- summary scoring cost per query (CPU)
- pruning granularity (recall risk)

A 64-row block on a 390-row leaf gives ~6 summaries per leaf; a
256-row block gives ~1.5 summaries (i.e. mostly degenerate). The
"small multiple of segment size" range matters a lot. The
implementation packet's design should commit to a starting block-size
range (say, 32-128 rows) and report the sweep, not pick an arbitrary
single value.

### F3 — No explicit cost model in the ADR (forward-looking)

The acceptance criteria are *outcome* gates. The ADR doesn't sketch
*where the wins come from* — i.e., how summary-scoring cost trades
against avoided row-scoring cost. A back-of-envelope at the 5.25M
candidate point would help the next slice scope itself:

- if summaries are RaBitQ-encoded with the same scoring kernel, the
  per-summary CPU is ~1/block_size of per-row CPU;
- with `block_size=64`, summary scoring is ~1.5% of full row scoring;
- to clear the strong 4.0M candidate gate from 5.25M, ~24% of row
  blocks need to be pruned per leaf;
- p50 win requires summary scoring overhead < (row blocks pruned) ×
  (per-row scoring cost).

Not blocking — the ADR is a design checkpoint, not an implementation
spec. But the implementation packet's pre-flight should include this
math so the slice has a defensible target before code lands.

### F4 — Fallback semantics on malformed summary chain (clarify before implementation)

> "reject malformed summary chains before row-segment pruning is
> enabled."

I read this as "error at scan time on malformed chains." But the
runtime control section also says:

> "a fallback mode that forces full selected-leaf scans for A/B
> validation"

The implementation packet should make the error-vs-fallback policy
explicit:

- corrupted summary chain on a V3 leaf → error (poison pill, surfaces
  index corruption) or silent fallback (resilient, but masks issues)?
- missing summary chain (old V2 leaf upgraded in-place) → fallback;
  but is the upgrade path automatic, or does it require a build-time
  step?
- diagnostics mode that disables pruning → must work without surface
  tests breaking on a V3 leaf where summaries exist.

The ADR has the right primitives (V3 format, V2 fallback, GUC
override) — just needs explicit semantic choices when the
implementation packet starts.

## Verdict

ADR-074 accepted as the Phase 4 design gate. The implementation packet
should:

1. Clean up the stale packet 005/006 directories (or backfill their
   request.md if they have data worth keeping).
2. Commit to a starting block-size range and report a sweep.
3. Include a back-of-envelope cost model in the pre-flight section so
   the slice has a defensible target.
4. Make the fallback/error policy explicit for malformed and missing
   summary chains.

No code-side blocking concerns. Approve to start implementation.
