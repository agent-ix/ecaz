# Task 79 packet 014 — RaBitQ global leaf block pruning

## Decision

**Accept the implementation slice.** This is a structurally different
approach from packets 010-013: instead of "top-N blocks per leaf,"
score all summaries across all routed leaves once and keep the top-K
globally. The implementation is well-shaped, GUC contract is
disabled-by-default, fallbacks are correct, tests landed.

Whether global allocation rescues the loose-summary ranking is
packet 015's empirical question. The hypothesis is sound — if a
leaf's summaries all rank poorly globally, that leaf probably also
contributes few winners, so spending budget elsewhere is rational.

## What's solid

### Structural shift is the right next experiment

Packets 010-013 showed per-leaf top-N selection is too coarse:
budget gets spent uniformly across leaves regardless of summary
quality. Global selection lets the budget flow toward leaves with
high-scoring summaries naturally.

This complements packet 004's earlier insight that "higher nprobe at
constant row budget gives better leaf *selection* at constant scored-
row cost" — global block pruning is the same idea extended to leaf-
internal granularity. Worth trying before the heavier multi-rep or
sketch alternatives.

### GUC contract preserves defaults

- `ec_spire.leaf_block_pruning_max_global_blocks` (new)
- Default 0 = disabled, max bounded
- When 0, per-leaf path (packet 010) runs unchanged
- Userset context

The new GUC is orthogonal to `leaf_block_pruning_max_blocks_per_leaf`
(packet 010) — when global is set, it takes precedence; when 0, per-
leaf semantics apply. Clean composition.

### Critical semantic: zero-scan for non-selected leaves

> "weak routed leaves with summaries receive an explicit empty
> selected range when none of their blocks are in the global top K,
> so they scan zero leaf rows instead of falling back to full-leaf
> scans"

This is load-bearing. Without it, leaves with summaries but no
globally-selected blocks would silently full-scan, defeating the
purpose. The HashMap-based selection (returns `Vec<Range>` per
leaf, possibly empty) makes this explicit. Good.

### Mixed V2/V3 degradation is reasonable

If global GUC is set but a leaf is V2 (no summaries), the global
selector returns None for that leaf because `summary_count == 0`.
The scan then falls back to the per-leaf or full-leaf path for that
leaf. So mixed-version indexes degrade gracefully rather than
erroring — this is the right call for a session-level GUC during
the experiment phase.

### Test coverage

- `select_global_leaf_block_row_ranges_spends_budget_across_leaves`
  — directly tests the per-leaf-vs-global distinction
- `collect_quantized_routed_probe_candidates_matches_prepared_assignment_scorer`
  — parity test continues to pass

The "spends budget across leaves" test name implies an assertion
that budget is allocated heterogeneously based on summary scores
rather than uniformly. Good targeted test.

## Findings

### F1 — Mean-only summary score, intentional per packet 013

> "global selection uses mean-only RaBitQ summary scores intentionally;
> packet 013 accepted radius-adjusted selection as negative evidence"

That's the right scoping. Even though packet 011's mean-only result
was too lossy *per-leaf*, the open question is whether mean-only
ranking is good enough when allocation is *global*. If global helps
with mean-only, you have a working slice without revisiting summary
encoding. If global doesn't help even with mean-only, the failure
attributes to the summary semantics, not the allocation strategy.

Clean experimental design.

### F2 — Delta path is preserved separately

> "delta rows still flow through the existing loaded-delta and
> accumulator path"

That matters because deltas are by-vec-id updates that haven't been
compacted into leaf rows yet, so they don't have block summaries.
Skipping pruning for deltas is the correct behavior — they're already
a small frontier.

Worth a one-line note in the next benchmark's manifest: how many
delta rows are scored vs leaf-row scored. If delta volume is high
on the fixture, the delta path could mask global-pruning wins.

### F3 — `read_quantized_v2_leaf_object_for_route` returns None path

In `collect_validated_quantized_leaf_route_candidates_with_global_block_pruning`,
when `read_quantized_v2_leaf_object_for_route` returns None for a
route, the code processes only delta candidates and continues. This
is correct (the leaf object simply isn't present), but worth
verifying in the benchmark that no routed leaves silently produce
zero candidates due to read failures masquerading as missing leaves.
The funnel diagnostic should surface `leaf_route_count` minus
`scanned_leaf_count` per query to catch this.

## Verdict

Implementation accepted. The structural change (global vs per-leaf
allocation) is the right next experiment given the failure mode in
packets 011/013. Benchmark 015 will reveal whether the allocation
strategy alone is enough to reach the Task 79 gates with the same
mean-only summary semantics.

If 015 succeeds: Task 79 closes with a working candidate-reduction
recipe and no V3 format extension needed beyond what packet 009
shipped.

If 015 fails: the failure attribution is "summary semantics are
fundamentally insufficient regardless of allocation strategy,"
which strengthens the case for either multi-representative
summaries (V3 extension or V4 bump) or pausing Task 79.
