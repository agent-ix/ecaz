# Task 79 packet 012 — RaBitQ radius-adjusted block pruning

## Decision

**Accept the implementation slice.** Code is correct, math is a sound
Cauchy-Schwarz upper bound, and the slot-reuse approach (`summary.gamma`
holding radius) avoids a V3 format bump. Tests landed for both build
(radius materialization) and selector (radius ranking).

The empirical question — whether the bound is tight enough to preserve
recall — is packet 013's job.

## What's solid

### Math is a correct upper bound

For RaBitQ summaries:
- block summary IP estimate = `encoded_mean_ip`
- max possible row IP in block ≤ `encoded_mean_ip + query_l2_norm × radius`
  by Cauchy-Schwarz on the residual `row - block_mean`

The selector now ranks by this bound rather than by `encoded_mean_ip`
alone. Mathematically, this never over-prunes (the bound is always ≥
the true max), so no row that should win gets eliminated by the
bound itself — only by the budget after ranking.

### Slot reuse avoids format bump

`summary.gamma` already exists in the V3 summary segment and row
scoring already requires `gamma == 0` for RaBitQ rows. Storing radius
in `summary.gamma` for summaries (not rows) is a clean compact reuse:

- Build path computes max L2 residual and stores in summary `gamma`
- Selector reads `gamma` as radius
- Row scoring is unaffected (uses row's own `gamma`, not summary's)

If a summary is ever misread as a row, the row scorer's "gamma must
be 0" check will error rather than silently doing the wrong thing —
that's a soft safety net.

### Build path adds `query_l2_norm`

The scorer now carries `query_l2_norm`, which is needed for the
bound computation. Added in `SpirePreparedAssignmentScorer` as a
field. No allocation churn — just one extra f32 per scan.

### Test coverage

- `leaf_block_summaries_cover_rabitq_row_blocks` extended to verify
  radius materialization
- `select_leaf_block_row_ranges` extended with radius-ranking test

Reasonable for an implementation slice; benchmark validation is
packet 013's lane.

## Finding (non-blocking)

### F1 — Slot reuse is correct but worth one explicit comment

The dual semantics of `summary.gamma` (radius for RaBitQ summaries,
unused/0 for TurboQuant summaries, and unused/0 for all row payloads
RaBitQ-side) is a real invariant. The code enforces it implicitly:
the selector reads `gamma` as radius only when scorer is RaBitQ; row
scoring errors on non-zero gamma. But a future contributor changing
either path could break the invariant silently.

A single comment on `SpireLeafBlockSummary.gamma` documenting
"RaBitQ summaries store max-L2-residual radius here; TurboQuant
summaries leave 0; row payloads must have 0" would lock the
contract.

Not blocking — the code works correctly, this is just future-proofing.

## Verdict

Implementation accepted. The bound is mathematically sound; the
storage approach is appropriately minimal. Whether the bound is tight
enough is packet 013's empirical question.
