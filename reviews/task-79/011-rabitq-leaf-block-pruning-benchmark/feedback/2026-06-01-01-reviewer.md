# Task 79 packet 011 — RaBitQ leaf block pruning benchmark

## Decision

**Accept as honest negative-result evidence.** The benchmark validates
my packet 010 F1 prediction: mean-of-source-vectors as a block summary
ranks the high-IP blocks too weakly to preserve recall. The
implementation works mechanically (V3 no-prune reproduces baseline
exactly), but the summary *semantics* need to change. The packet
correctly identifies that as the next slice rather than shipping a
broken default or hand-waving the recall gap.

## What's solid

### V3 no-prune row reproduces baseline exactly

`block64 prune0`: 15,506,227 cands / 62.9 ms / recall 0.9975. That's
within run-to-run noise of the Task 78 baseline (15,506,227 / 60.3 ms
/ 0.9975). Critical sanity check — it proves:

- the V3 format scaffold doesn't perturb scan behavior when pruning
  is disabled
- the path through the common collector (packet 010) didn't break
  top-graph routing on the high-recall lane
- summary build during load adds the right number of summaries
  without polluting the scan

### Pattern across the matrix is unambiguous

| block_rows | best recall (highest prune kept) | candidates | recall |
| ---: | --- | ---: | ---: |
| 64 | prune6 (~37% blocks kept) | 6.76M | 0.8685 |
| 32 | prune10 (~50% blocks kept) | 5.82M | 0.8820 |
| 128 | prune4 (~67% blocks kept) | 8.46M | 0.8835 |

Recall correlates with rows-kept ratio, *not* with block size. That
means the mean-summary ranking is barely better than random within
the leaf — the savings come from "keep more rows," not from "keep the
right rows." Exactly what F1 predicted.

### Honest closeout

- No goalpost shifting: gates not cleared, packet says so directly.
- No TurboQuant lane: correctly held back per packet 010's framing
  ("comparison/control target after the RaBitQ candidate-surface
  sweep finds a viable operating point"). Don't burn cycles on
  TurboQuant when the primary lane fails first.
- Names the next move precisely: "upper-bound score or
  multi-representative summary per block."

## Findings

### F1 — V3 format header may need an extension for upper-bound or multi-representative summaries

The V3 format from packet 009 stores `summary_block_rows`,
`summary_count`, `first_summary_segment_locator`, `summary_bytes_total`
and one summary per block as `(row_base, row_count, gamma, payload)`.

For the next slice's alternatives:

- **Upper-bound summary** (per-block max-IP precompute): needs to
  encode either a single bound float per block, or a (bound,
  representative-vector) pair. The bound is query-independent for
  certain forms (e.g. `max_row_norm × query_norm`) but
  query-dependent for tighter bounds. The latter doesn't fit
  precomputed summaries at all — it has to be computed at query
  time from per-block stats. So the format extension is either
  "per-block norm/range scalars" or unchanged if the bound is
  computed from existing payload.
- **Multi-representative summary** (k centroids per block): needs
  `summaries_per_block: u32` field in V3 meta and the segment to
  carry `k × payload_size` per block. That's a clean V3 extension
  if added now, or a V4 bump if the V3 format is considered frozen.

Recommend the next packet's design checkpoint decide format-bump
strategy before code lands. The V3 reject-unknown discipline from
packet 009 makes either choice safe (V3 with no representatives
counts as "old"; V4 is a fresh format).

### F2 — Summary scoring overhead bound

The matrix doesn't isolate summary-scoring CPU cost. Looking at
`block32 prune8`:
- 4.68M candidates scored
- p50 38.2 ms
- vs no-prune 15.5M cands / 62.9 ms

That's 70% fewer candidates for 39% less p50 time. The slope suggests
~25% of time is in non-row-scoring work — summary scoring,
selection, or other overhead. At `block32`, summary count is
~24 per leaf vs `block64` ~12 vs `block128` ~6. The scoring overhead
should scale with summary count, but the data here doesn't clearly
separate that.

For the next slice's benchmark, surface summary-score-time per query
in the funnel so the cost can be attributed. Otherwise a multi-rep
summary (k summaries × N blocks) might silently regress p50 even with
better recall.

### F3 — Whether to pause Task 79 vs continue

Worth flagging to the user: this packet says the simplest summary
encoding doesn't work, and the proposed next-slice directions
(upper-bound or multi-rep) are real implementation cost
(format extension, build cost, scoring cost). Two reasonable choices
for the dev line:

1. **Continue Task 79** with an upper-bound summary slice as the
   next packet. The infrastructure investment (V3, scanner, sweep
   tooling) is sunk; one more summary-encoding iteration is
   incremental.
2. **Pause Task 79** and re-prioritize. The candidate-surface
   problem has been characterized exhaustively; if the dev line has
   other work that's more important than the SPIRE/IVF latency gap
   for SPIRE-bound users, this is a reasonable place to bookmark.

Not a reviewer-side call. Flagging for the user to decide.

## Verdict

Negative-evidence packet accepted. The implementation path is
verified working but the first summary-encoding choice doesn't
preserve recall. The closeout direction (upper-bound or
multi-representative summary) is correct. Next slice will need a
short design checkpoint for the format extension before code lands.

This is the right kind of failure — fast, honest, with the gap
precisely characterized. Two reviewer notes (F1 format strategy, F2
summary-cost attribution) plus one user-facing question (F3
continue vs pause) for the next decision.
