# Task 79 packet 001 — candidate surface baseline

## Decision

**Accept.** The geometry-only sweep correctly establishes that no
`nlists`/`recursive_fanout`/`nprobe` combination tested meets both Task 79
gates simultaneously. The proposed next direction (routing-budget /
top-graph work, not another heap cutoff or scorer micro-optimization) is
sound given the data.

## What's solid

- **Baseline reproduces cleanly** at the Task 78 settings: 15,506,227
  candidates, 19,200 routes, recall@10 `0.9975`, p50 `61.234 ms`.
  Matches Task 78 numbers within noise.
- **Funnel diagnostic SQL is healthy.** Spot-checked the n512/f16/tg128
  funnel JSONL — per-query candidate counts vary naturally
  (q1=5,628, q100=7,263, q200=6,513 at nprobe=32). The Task 75
  query-invariance bug doesn't recur.
- **Methodology is reproducible.** Suite config checked in, isolated
  database, `ecaz bench suite` driven (no shell sweeper), audit + dry-run
  + run + status + report all logged.
- **Geometry-only failure mode is honest.** Every row that hits the
  candidate gate (≤5.2M) misses the recall gate (within 0.5pp of 0.9975),
  and vice versa. No cherry-picking.

## Key reading of the data

The data confirms the "routing wastes the candidate surface" hypothesis
from the task spec:

| config | candidates | recall@10 | observation |
| --- | ---: | ---: | --- |
| n128/f8 nprobe=96 | 15.5M | 0.9975 | baseline; routes 75% of corpus |
| n512/f16 nprobe=128 | 5.3M | 0.9645 | 3x fewer rows, loses 3.3pp |
| n2048/f64 nprobe=96 | 1.15M | 0.8875 | 13x fewer rows, loses 10.9pp, **also p50 jumps to 76.9 ms** |

The n2048 row is particularly informative: a 13.5x candidate reduction
*increases* p50 latency, which signals fanout/centroid cost overtakes
scoring savings at extreme nlists. That bounds the geometry-only ceiling
from above.

## Findings

### F1 — `nlists=256` is missing from the matrix (non-blocking)

The task spec lists `nlists` sweep `128, 256, 512, 1024, 2048`. The actual
matrix has `128, 512, 1024, 2048` but not 256. The 256-leaf row would
test whether there's a useful Pareto point between 128 (15.5M / 0.9975)
and 512 (4M / 0.9420). Not strictly required for the Phase 1 decision
(the trend across the sampled rows is clean), but if Phase 2 needs a
geometry comparison point for the routing-budget slice, the 256-leaf
row would be informative.

### F2 — Per-leaf row distribution not surfaced in the request (non-blocking)

The task spec requires "leaf density distribution for selected routes:
mean, p50, p95, p99, max candidates per selected leaf route". The
artifact funnel files carry `leaf_candidate_mean/p95/max` per query, but
the request summary table doesn't surface per-config leaf-density
percentiles. For Phase 2's routing-budget decision, that distribution
matters: if selected leaves have skewed row counts, fixed-leaf-count
routing wastes budget on dense leaves. Worth surfacing in the closeout
or in the Phase 2 packet's baseline comparison.

### F3 — `p50` at n2048 is the inflection signal worth naming explicitly

The request notes the candidate reductions but doesn't call out that
nlists=2048 *increases* p50 (76.9 ms vs baseline's 61.2 ms) despite
13.5x fewer scored candidates. That's a measured ceiling on geometry-only
work: somewhere between 1024 and 2048 leaves, the fanout/route-management
cost begins to dominate. If Phase 2's routing-budget slice ends up
recommending a target `nlists` in the closeout, this inflection is the
upper bound to cite.

## Forward-looking note

The proposed Phase 2 direction (top-graph route budget separate from
`scan_plan.nprobe`, honoring `nprobe_per_level` semantics, routing
diagnostics for root-exhaustion) is well-scoped against this evidence.
The task spec already names the implementation surfaces
(`scan/routing.rs`, `options/mod.rs`, `build/top_graph.rs`); the Phase 1
data supports starting there rather than at storage-format work
(Phase 4) or adaptive nprobe (Phase 5).

## Verdict

Phase 1 baseline accepted. Phase 2 routing-budget direction is the right
next move on this evidence. F1-F3 are non-blocking — address in the
Phase 2 packet's baseline-comparison surface so the routing-budget slice
has a clean Pareto frame to land against.
