# Task 79 packet 013 — radius block64 benchmark

## Decision

**Accept as honest negative evidence.** The radius-adjusted selector
doesn't improve over the mean-only baseline from packet 011 — in fact
it's slightly worse at comparable budgets. The closeout reads the
result correctly: "single-summary block selection is still the wrong
abstraction."

This narrows the next attempt cleanly. Any "one scalar (or one
scalar + correction) per block" approach is now empirically ruled
out at the high-recall band.

## What's solid

### V3 prune0 reproduces baseline

`block64 radius prune0`: 15,506,227 cands / 62.1 ms / 0.9975 recall.
Matches packet 011 prune0 within noise. The radius-storage change
doesn't perturb the no-pruning path — slot reuse works correctly.

### Direct head-to-head with packet 011

| metric | mean-only (011) | radius (013) |
| --- | --- | --- |
| prune4 candidates | 4,547,347 | 4,681,394 |
| prune4 p50 | 37.3 ms | 37.0 ms |
| prune4 recall | 0.7790 | 0.6640 |
| ~9M cands recall | 0.8835 (block128/prune4) | 0.8835 (block64/prune8) |

Same shape, ~same recall at matched candidate count, radius
materially worse at low budgets. The data clearly says: the bound is
mathematically valid but too loose to act as a discriminator at this
fixture/budget combination.

### Diagnostic interpretation matches what the math predicts

A Cauchy-Schwarz upper bound that includes `query_norm × radius` will
favor blocks with high radius. On a dense corpus, almost every block
has substantial radius, so the bound is dominated by `radius` rather
than `mean_ip`. The selector ends up preferring *broad* blocks over
*good-mean* blocks — and the broad blocks are mostly noise, not
hidden winners.

### Honest negative framing

The packet doesn't claim a partial win or wave at the radius numbers
as "directional." It says explicitly: "This should not be accepted as
a Task 79 latency improvement."

## Findings

### F1 — Two new directions in the closeout, both real

The packet's "next experiments" list names three reasonable paths:

1. **Multiple representatives per block** — store k centroids per
   block, select by best representative score. Requires V3 format
   extension (`summaries_per_block: u32` field) or V4 bump per my
   packet 011 F1.
2. **Per-block candidate sketch** — bloom-filter-shaped membership
   from training queries or row top-k. Different infrastructure
   (build needs query-aware training pass, scan needs sketch
   evaluation per block). Higher cost, potentially much better
   ranking.
3. **Tiny row-sample probe** — summary scoring as first pass, then
   sample a few rows per surviving block before committing to row
   ranges. Two-stage selection, but stays within V3 format.

Of these, option 3 is the cheapest first try and stays within V3.
Option 1 is the natural format-bump direction if option 3 doesn't
clear the gate. Option 2 is the largest implementation investment
and should be a last resort.

### F2 — The radius approach exposed a useful insight worth keeping

Even though the radius bound doesn't preserve recall as a *selector*,
the radius itself is real per-block geometry information that's now
computed and stored. A two-stage selector (e.g. mean-IP first, then
narrow by `mean_ip` (not `mean_ip + radius`) and use radius only as
a *sanity check* to reject tightly-clustered blocks with high mean)
might re-use the same storage. Don't throw the radius away.

### F3 — The continue-vs-pause decision from packet 011 F3 remains open

This packet narrows the design space but doesn't change the
fundamental question. The simplest two summary encodings (mean,
mean+radius) both fail at the high-recall band. Each next attempt
(multi-rep, sketch, two-stage probe) carries real implementation
cost.

Same user-facing question as packet 011: continue Task 79 with
option 3 (tiny row-sample probe — cheapest, stays in V3) or pause
and bookmark? My recommendation if continuing: option 3 first
because it's the lowest-risk next slice. If it works, great. If it
doesn't, the closeout has strong evidence that single-stage
summary-based selection is structurally insufficient and the next
move is multi-representative (option 1) with the format bump.

## Verdict

Negative-evidence packet accepted. Implementation works, math is
sound, but the bound is too loose for the target band. Next move is
the user's call between option 3 (tiny row-sample probe, V3-stable)
and pause.
