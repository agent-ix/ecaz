# Task 79 packet 027 — clustered block32 radius-weight benchmark

## Decision

**Accept as incremental progress, but still misses all three
gates simultaneously.** Block32 + clustered + w=0.25 reaches recall
0.9900 at 5.67M candidates / 47.6ms p50 — close on all three
axes but not closing the task gate (0.9925 / 5.2M / 45ms).

The packet 026 diagnostic verdict stands: this is geometric
refinement around the same structural ceiling, not a path through
it.

## Direct comparison to block64 (packet 025)

| setting | candidates | p50 | recall | gates |
| --- | ---: | ---: | ---: | --- |
| block64 g416/w0.25 (025) | 5.20M | 45.8 ms | 0.9835 | cands ✓ / p50 ✓ / recall ✗ |
| block32 g896/w0.25 (027) | 5.67M | 47.6 ms | 0.9900 | cands ✗ / p50 ✗ / recall ✗ |

Block32 gives +0.65pp recall but at 9% more candidates and 1.8ms
worse p50. Both fall short of all three gates. Critically:

**Neither row clears the 0.9925 recall gate.** The closeout's
"first recall-passing" framing uses a looser threshold (≥0.99);
the strict Task 79 gate is 0.9925.

## What block32 tells us about geometry

Block32 has 2× the summaries per leaf. At g896 (vs block64 g416 —
roughly the same row budget after the 2× block-count scaling),
each summary covers fewer rows so the mean+radius score should be
more discriminating per block.

The +0.65pp recall lift is consistent with finer blocks
discriminating the *short-rank-tail* misses (e.g., the 57 routed-
but-rank>cap misses from packet 026's diagnostic). But the long-
rank-tail misses (p99=588, max=1099 from 026) are spread across a
wide enough rank range that finer blocks alone can't catch them at
budgets compatible with the candidate gate.

That's exactly what packet 026's rank distribution predicted: the
misses aren't clustered at rank 384-416; they spread to 588+.
Going to block32 lifts the recall ceiling slightly but doesn't
collapse the rank tail.

## Why this still doesn't close Task 79

To clear all three gates simultaneously with block32 would
require recall to climb to 0.9925 at cap ~768-800 (under
candidate gate) at p50 ~44ms (under latency gate). Looking at the
curve from 027:

| cap | candidates | recall |
| ---: | ---: | ---: |
| 832 | 5.27M | 0.9885 |
| 896 | 5.67M | 0.9900 |
| 1024 | 6.48M | 0.9915 |

To reach 0.9925, extrapolation suggests cap ≈ 1100-1200, which
would push candidates well past the gate. The marginal recall per
added cap unit is falling, same shape as block64.

## Connection to packet 026 diagnostic

The 026 rank distribution at block64 showed:
- 57 misses ranked between 384-1099 (the addressable bucket)
- Median miss-rank around 419-588

Block32 effectively splits each block64 into 2, doubling the
rank budget at any cap. So a block64 miss at rank 500 might land
at block32 rank 1000 in the doubled scheme. That's why the
recall ceiling improves slightly but the geometric problem
persists: the long tail of low-summary-signal blocks is
fundamental to single-scalar-per-block ranking, not a function
of block size.

## Verdict

Accept. Block32 is an incremental win (+0.65pp recall) but
doesn't close the structural problem identified in packet 026.
The coder's recommendation — "add richer per-block representative
information and score against it" — is the same multi-rep
direction my packet 026 feedback aligned with.

Packet 028 (block16, in flight) will probably show the same
pattern: more granular, slightly higher recall ceiling, still
short of gate. Block size sweep is bounded at this point. The
next slice should be multi-representative summaries (or
calibrated per-leaf block score, per my 026 R2) — not further
block-size refinement.

## Note on `block32 g896 radius0.25` as "local baseline"

The packet asks whether to use this as the current local RaBitQ
baseline. My read: yes for **operational purposes** (it's the
best recall-per-cost recipe found), but **not as a Task 79
closure claim**. The packet's own framing of "0.9900 recall is
not enough for Task 79 solved" is correct.

If the dev line ships SPIRE before Task 79 closes, this would be
the SPIRE's best-practical-recipe for a single-scalar selector.
That's a useful artifact even if Task 79 stays open.
