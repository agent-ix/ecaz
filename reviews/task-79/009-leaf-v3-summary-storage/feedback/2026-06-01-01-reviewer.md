## Code-side checks

### Format bump (header.rs)

V3 added to the `format_version` allow-list in both encode and decode
paths alongside V1/V2. Reject-unknown semantics preserved — unknown
versions still error.

### V3 meta extension (leaf_v2_parts.rs)

New meta fields: `summary_block_rows`, `summary_count`,
`first_summary_segment_locator`, `summary_bytes_total`. Stored at
fixed byte offsets in the meta tail (positions 30-52). Length checks
via `try_into().expect()` on slices that are statically the right
length — safe expects, will never panic at runtime.

### Validation discipline

`validate_leaf_block_summary` checks payload format match.
`validate_leaf_block_summary_coverage` checks summary count matches
meta and that row coverage is consistent. Both invoked from the
object's `validate()` method, called before `block_summaries()`
returns.

### Test coverage

`leaf_partition_object_v3_store_round_trips_block_summaries` (round
trip), `leaf_partition_object_v2_store_segments_large_leaf` (V2
regression). 2 V3 tests + V2 regression preserved. Could use a
malformed-chain rejection test before scanner consumption lands —
see F1.

### Safety

No `unsafe { ... }` blocks added. All `.expect()` calls are on
fixed-length slice → array conversions that cannot fail at runtime.

## Findings (non-blocking, for the next packet)

### F1 — Malformed-chain rejection test would lock the F4 contract

The error-on-corruption semantics from packet 007 F4 are stated in
the request but I don't see a test for it. Before the scanner-side
consumption lands, a unit test that constructs a deliberately
malformed V3 summary segment (wrong length, bad payload format,
broken chain link, etc.) and asserts the read errors would lock that
contract against future drift. Worth adding to the next checkpoint
since the scanner will be relying on that error path.

### F2 — `SPIRE_PAYLOAD_FORMAT_RABITQ`-only test coverage

The test uses RaBitQ payload exclusively (correct per Task 79's
RaBitQ-primary scope), but the encoding path is payload-format-
agnostic. A TurboQuant round-trip test would be cheap insurance
against the V3 format diverging from V2's storage-format-neutral
contract. Not blocking — RaBitQ is the only consumer for the Task 79
implementation arc.

### F3 — Cost model is calibrated against route-time budget baseline

The request math assumes the no-format-change baseline is the 5.25M
candidate point from packet 004. That's the right anchor. Worth
adding to the manifest of the next slice (when summary scoring lands)
so reviewer can compare expected vs measured pruning rates directly.

## Verdict

Storage scaffold accepted. The format bump is clean, error semantics
are explicit, V2 fallback preserved, 2 V3 tests + V2 regression land.
