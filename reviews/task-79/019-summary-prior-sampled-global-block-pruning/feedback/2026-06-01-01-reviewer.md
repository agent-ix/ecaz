# Task 79 packet 019 — summary-prior sampled global block scoring

## Decision

**Accept the implementation slice.** This is exactly the fix
recommended in my packet 017 feedback: "preserve summary score as
prior, let samples ADJUST it instead of replacing it." The
`blend_leaf_block_summary_sample_score` function is small, clean,
and correctly upward-only.

## What's solid

### Blend math is correct

```rust
fn blend_leaf_block_summary_sample_score(
    summary_ip: f32,
    best_sample_ip: Option<f32>,
    sample_summary_prior_weight: f64,
) -> f32 {
    let Some(sample_ip) = best_sample_ip else {
        return summary_ip;
    };
    if sample_ip <= summary_ip {
        return summary_ip;
    }
    let sample_weight = (1.0 - sample_summary_prior_weight) as f32;
    summary_ip + (sample_ip - summary_ip) * sample_weight
}
```

Three properties verified:

1. **Graceful fallback**: no samples → summary score (preserves
   packet 015 behavior when sampling effectively disabled)
2. **Upward-only**: `sample_ip <= summary_ip` → summary unchanged.
   Bad samples can't demote high-summary blocks. This was the
   exact failure mode from packet 017.
3. **Bounded promotion**: at `prior_weight=0.8`, sample can lift
   block by 20% of the `sample - summary` delta. Strong samples
   still promote within the probed frontier.

### GUC contract

- `ec_spire.leaf_block_pruning_sample_summary_prior_weight`
- Default `0.8` (heavy summary weight)
- Range `[0.0, 1.0]` enforced (errors on out-of-range or non-finite)
- Composes cleanly with existing global/probe/sample GUCs

At weight=1.0: pure summary (no sample influence). At weight=0.0:
pure sample (back to packet 016/017 behavior — should not be used,
just there for the math limit).

### Test coverage

6 tests passed in `leaf_block`. The two named scenarios:
- "bad samples do not demote summary-ranked blocks"
- "strong samples can still promote a lower-summary block within
  the probed frontier"

Both are load-bearing for the correctness claim.

## Findings

### F1 — Cross-reference my packet 018 seq-02 follow-up

You may not have seen it before starting this packet, but I posted
a follow-up note on packet 018 recommending the **rerank_width
axis** as a parallel test direction. The hypothesis: RaBitQ
baseline gets 0.9975 recall with `rerank=25` only because the
massive 15.5M candidate surface gives the noisy RaBitQ score
enough redundancy. When block pruning shrinks the candidate
surface 3-4x but rerank stays at 25, the noisy score no longer
has redundancy → recall drops.

That note's recommendation:

- existing global selector (packet 014), block64, global384/512
- **`rerank_width` sweep at 25/50/100/200/500**
- no new code, just GUC tuning

This is orthogonal to packet 019's summary-prior fix:

- if **019's summary-prior** rescues recall → great, ship it
- if **wider rerank** rescues recall → that's a complete Task 79
  closure with zero new code
- if **both together** rescue recall → even better, you have a
  composable recipe

For packet 020's benchmark, consider adding a `rerank_width` axis
alongside the `prior_weight` axis. The combined matrix is small
enough (5 weights × 3 reranks × 2 final_block settings = 30 rows)
to fit one suite run.

### F2 — Default `prior_weight=0.8` is a reasonable starting point

Heavy weight on summary means the sample is a *light* upward
correction. Worth confirming this aligns with the intent — if you
expect sample signal to be strong (e.g., samples are very
representative of block winners), you'd want lower prior_weight
(more sample influence). If summary is mostly right (per packet
015 evidence), heavy prior weight is correct. Default 0.8 leans
toward "summary is mostly right" which matches the evidence.

The sweep should probably include `prior_weight=0.5` and `0.95`
to bracket the sensitivity.
