# Task 79 packet 004 — route-time row budget

## Decision

**Accept the slice.** The code correctly moves the budget into route
selection and addresses both packet 003 follow-ups (F1 cached
assignment counts, F2 row52k surfaced). The packet's own conclusion —
that the remaining gap is whole-leaf granularity, not late filtering —
is correctly drawn from the data. The proposed next direction
(subleaf or finer-partition selection) is sound.

This is not a Task 79 closing slice, but it correctly bounds where the
remaining work lives.

## What's solid

### Code correctness

- **Snapshot-time caching of leaf assignment counts** lifts F1's
  per-route header read cost to a one-shot snapshot pass. The new
  `leaf_assignment_counts_by_pid: HashMap<u64, usize>` is populated
  during the manifest walk and reused by the route-time budget closure.
- **Defensive guards:**
  - Duplicate-pid check on snapshot construction errors on duplicate
    `manifest_entry.pid` — catches a real corruption mode.
  - `usize::try_from(header.assignment_count)` overflow check.
  - The `leaf_row_count` closure errors with `"should not be read
    without a row budget"` when no budget is active — prevents
    accidental use of the closure on the no-budget happy path.
- **No new unsafe blocks.** All new code is safe Rust through the
  existing object-store and routing surfaces.
- **Disabled-by-default behavior preserved.** GUC default 0 still
  disables the cap; existing scans unchanged.
- **Tests landed:** 3 test files
  (`test-caps-routed-candidate-rows`, `test-max-routed-candidate-rows`,
  `test-routing-row-budget-diagnostics`) plus clippy clean.

### Measurement

- **Funnel data still healthy per-query.** Spot-checked
  n256/row26k/nprobe=128: q1=72 routes/26024 cands,
  q100=65 routes/26107 cands. Per-query variation natural.
- **Route-time diagnostic is the load-bearing evidence.** Showing
  `selected_child_sum=51200`, `deduped_route_sum=13270` at all nprobe

  the budget is enforced during route selection, not post-route.

## Genuinely interesting observation the packet under-states

At n256/row26k, increasing nprobe from 128 to 192 to 256:

- routes selected: identical (72/65 per query at q1/q100)
- candidates scored: identical (~5.25M total)
- recall@10: rises from `0.9910` to `0.9975` to (presumably) higher

That means **higher nprobe gives better leaf *selection* at constant
scored-row cost**. The budget caps the bottom of the route ordering;
the top end gets to choose from a larger high-quality frontier. That's
a real win mechanism worth surfacing — it suggests the next slice's
target should be "preserve this quality-frontier behavior while
shrinking the per-leaf row count," which aligns with the subleaf
direction.

## Findings

### F1 — Small p50 regression vs packet 003 at the same setting (non-blocking)

n256/f16/row26k/nprobe=192 was 65.288 ms in packet 003 and is
67.473 ms here — a 2.2 ms (3.3%) regression at the same setting and
same candidate count. With 200 queries, this is probably run-to-run
noise, but worth a note: the route-time budget should be neutral-or-
better at the matched-recall point. If it's not noise, the snapshot-time
bulk header pass may carry per-scan amortization cost worth
characterizing. Easy check: re-run the same row 3-5 times and report
p50 variance.

### F2 — Subleaf vs finer-partition decision should be data-driven (forward-looking)

The packet's "next direction" is correctly framed (subleaf pruning
OR finer global partitioning), but doesn't commit. The Phase 1
geometry data already bounded the finer-partitioning option: at
n=2048, candidates dropped to 1.15M but recall fell to 0.8875 and p50
*rose* to 76.9 ms (packet 001). That suggests global partitioning
hits a build/route cost ceiling around n=1024-2048.

The subleaf direction is more promising on this evidence — preserves
the high-quality leaf *selection* mechanism this packet revealed,
prunes inside selected leaves. Recommend the next packet leads with
a subleaf design sketch (per task spec Phase 4) rather than another
geometry sweep.

### F3 — TurboQuant skipped on this packet — correct call

The packet's explanation ("no RaBitQ winner to guard") is right.
TurboQuant comparison should land only when a RaBitQ candidate-reduction
recipe is close enough to defend. Don't burn measurement cycles on
TurboQuant until then.

## Verdict

Accept. The code is correct, the F1/F2 follow-ups from packet 003 are
addressed, and the packet honestly bounds where the remaining work
lives. Recommend the next slice lead with subleaf design rather than
more global partitioning, based on the cross-packet evidence.
