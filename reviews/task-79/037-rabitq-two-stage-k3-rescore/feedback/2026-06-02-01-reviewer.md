# Task 79 packet 037 — two-stage k=3 rescore (Path B)

## Decision

**Accept as marginal-progress negative evidence.** Two-stage scoring
(k=2 shortlist + k=3 rescore) saves only ~0.2ms p50 vs full k=3 —
much less than my packet 035 F2 estimate suggested. The
implementation is correct but the math doesn't deliver the
expected speedup at the relevant cap.

One new positive finding: **global736 also reaches 0.9925 recall**
(at 4.66M cands), slightly better than global768. So the recall-
passing surface widened by ~32 cap units.

## Why the two-stage savings were small

| approach | p50 | savings vs full k=3 |
| --- | ---: | ---: |
| full k=3 (cap736) | 48.85 ms | baseline |
| two-stage cap736 / rescore 1280 | 48.65 ms | **-0.2 ms** |
| two-stage cap768 / rescore 1280 | 49.09 ms | -0.0 ms (same cap) |

The math: at cap736 with probe=1280, the first pass already scores
1280 blocks with k=2 (cost ≈ 0.8 × full k=3). The rescore adds the
third representative on those 1280 blocks. Net cost: ~0.8 + ~0.4 =
~1.2× full k=3 cost, but they happen sequentially so wall time is
similar to full k=3.

For two-stage to save real time, the rescore set would need to be
much smaller than the probe set (e.g. rescore=512 from probe=1280).
But shrinking rescore loses the recall benefit — the late
representative needs to evaluate enough blocks to actually catch
the previously-missed winners.

The fundamental constraint: probe+rescore must cover the rank-
distribution tail of winners to maintain recall, and that tail
geometrically demands large rescore sets at the high-recall band.

## What this implies

After packets 035/036/037, the constraints are clear:
- k=3 recall recipe needs cap ≥ 736 (now confirmed)
- k=3 scoring CPU at that cap is ~49ms p50
- Two-stage doesn't help (rescore set must be near full probe)
- Per-leaf calibration doesn't help (036 ruled out simple version)

## Remaining viable paths

Same set as 036 with one update:

1. **Cheaper k=3 scoring kernel** — packet 038 (in flight, "summary-
   score fast-path") is targeting this. The k=3 score per block is
   3 × RaBitQ IP estimate; if the RaBitQ IP kernel can be reused
   across the 3 representatives with SIMD batching, the marginal
   cost per representative could drop significantly. This is the
   most technically interesting path.
2. **Different calibration baseline** (variance/quantile, not
   mean) — speculative
3. **Accept the slight p50 miss** — 3.65-3.85ms over the 45ms gate
   = 8% over. After 37 packets and the recall gate hit, this might
   be a product call worth making

## A note on Task 79 framing

The Task 79 gate is "p50 ≤ 45ms **or** ≤ 25% better than 60.256ms
baseline." 25% better = 45.19ms. Both interpretations land at the
same ~45ms target.

But the spec also allows: "packet intentionally changes rerank
width and proves the full recall/latency/candidate tradeoff."
With recall ✓, candidates ✓, and p50 9% over gate, it might be
worth proposing a Task 79 closure variant that documents the
tradeoff explicitly: "Task 79 closes with recall and candidate
gates met; p50 49ms vs 45ms target represents the floor of
RaBitQ + V4 multi-rep at this corpus shape." That's not a strict
closure but it's a meaningful operational artifact.

User call. My read: if packet 038 doesn't deliver ≥4ms savings,
proposing the tradeoff-documented closeout is reasonable.

## Verdict

Two-stage k=3 axis closed. Best k=3 recipe is global736/k=3 at
~49ms p50. Packet 038 is the last cheap technical path before
the "accept tradeoff or pause" decision becomes the user-facing
call.
