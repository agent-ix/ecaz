# Task 79 packet 015 — global block pruning benchmark

## Decision

**Accept as honest negative evidence with a strong attribution.**
Global allocation is meaningfully better than per-leaf (packets
011/013), but still doesn't clear all three gates simultaneously.
The closeout's read — "failure now points to summary semantics, not
merely budget allocation" — is now empirically well-supported by the
three-packet ladder (010→014 across allocation, 011/013/015 across
benchmark).

This is the natural place to re-surface the continue-vs-pause
decision: the simpler design-space options are exhausted; remaining
options carry materially more implementation cost.

## What's solid

### Global > per-leaf, measured directly

At comparable candidate counts:

| candidates | packet 011 (per-leaf mean) | packet 015 (global mean) | Δ recall |
| ---: | ---: | ---: | ---: |
| ~6.3-6.8M | 0.8685 (block64/prune6) | 0.9860 (global512) | **+11.75pp** |
| ~4.5-4.7M | 0.7790 (block64/prune4) | 0.9675 (global384) | **+18.85pp** |

That's a substantial improvement from the allocation strategy alone.
Global selection clearly extracts more signal from the same summary
encoding than per-leaf. The hypothesis from packet 014 — "let the
budget flow toward high-summary leaves naturally" — is validated as
*directionally* correct.

### But still misses both gates

| budget | candidates | p50 | recall | gate read |
| --- | ---: | ---: | ---: | --- |
| global384 | 4.68M | 43.2 ms | 0.9675 | cands ✓ / p50 ✓ / recall ✗ |
| global512 | 6.27M | 47.5 ms | 0.9860 | all 3 miss |
| global768 | 9.44M | 55.6 ms | 0.9925 | cands ✗ / p50 ✗ / recall=gate |
| global1024 | 12.6M | 64.0 ms | 0.9970 | back to baseline shape |

The Pareto frontier has shifted up (better than per-leaf), but no
single setting clears all three gates. The recall-vs-candidates
curve is now smooth enough that you can pick "good recall at the
candidate gate" (global384: 0.9675) or "recall at the threshold but
candidates 2x over" (global768: 0.9925) — no point hits both.

### Attribution is clean

The three-packet ladder narrows the design space precisely:

1. **Allocation matters**: global beats per-leaf by ~12-19pp recall
   at matched candidates (this packet vs 011).
2. **Single-scalar summary is the limit**: even with optimal
   allocation, single-mean summary can't push recall to 0.9925 at
   the 4.0M strong target.
3. **Therefore**: next attempt must change *what's stored per
   block*, not *how blocks are chosen*.

### F2 — User-facing continue-vs-pause decision (third time surfaced)

The original packet 011 F3 and packet 013 F3 each flagged this. With
packet 015's result, the decision is sharper because the remaining
options are heavier:

**Option A: Tiny row-sample probe (two-stage)**
- Stays in V3 format
- Build: no change beyond existing summary materialization
- Scan: after summary scoring picks top-K blocks, sample N rows
  from each surviving block, score them, and use the row scores to
  pick the actual top-M blocks before committing to full-row scan
- Cost: extra row reads per query × sample size; need to plumb a
  two-stage selector
- Risk: still relies on summary scoring as the first filter, which
  this benchmark proved is the weak link. Sampling might fix it if
  the right blocks survive the first filter, but if they don't,
  no amount of sampling helps.

**Option B: Multi-representative summaries (V3 extension or V4 bump)**
- Format change: per-block stores k centroids/representatives
  instead of 1
- Build: residual or k-means within each block
- Scan: score k summaries per block, take max
- Cost: k× summary scoring CPU, k× summary storage
- Risk: lower than Option A — multi-rep directly addresses the
  "one scalar can't rank well" problem this packet identified.
  Format bump is real cost but reject-unknown discipline (per
  packet 009) makes it safe.

**Option C: Pause Task 79**
- The candidate-surface problem is now exhaustively characterized
  across 15 packets
- Infrastructure (V3 format, summary build, global+per-leaf
  selectors, suite tooling) survives for future work
- Documentation closeout would name the design space and the
  measured frontier

My read after 5 packets of negative evidence: option B is the most
likely to actually close Task 79, but it's a real ~2-3 packet
implementation arc with a format bump. Option A is a smaller try
that might or might not work. Option C is reasonable if the
SPIRE/IVF latency gap isn't on a near-term critical path.

Still the user's call — but this is the third packet in a row where
the same decision recurs without new options narrowing it. Worth
explicit direction before the next slice.

## Verdict

Negative-evidence packet accepted. Global allocation is the right
mechanism but mean-only summaries are the binding constraint. The
next slice (whichever direction) needs to attack summary
information content, not allocation. Decision on
A/B/C is user-facing.
