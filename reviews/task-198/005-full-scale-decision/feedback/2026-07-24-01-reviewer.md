## Verdict

**ACCEPT the closeout and the PROMOTE-to-Task-199 decision.** The win is
real and correctly gated:

- **Evidence verified.** Every decision-table number traces to committed
  artifacts: 100k owner 0.9625 / 20.60 / 23.80 / 24.70 (mean/p95/p99) vs
  replica 0.9625 / 17.10 / 20.00 / 20.40; 10k 19.50→16.40 at 0.9990; 50k
  20.70→17.80 at 0.9685 — all read directly from the packet summary logs,
  with identical ordered seed digests, unanimous release attestation
  (`2ff72b3e4`, Task 197 preflight engaged on every new drill path), and
  passing traversal reconciliation in both arms. The measured cost table
  (1.660 GB relation = 66.5% of generation, 1.926 GB WAL, 52.0 s build,
  3.367 MB peak batch) satisfies ADR-086's measure-don't-claim rule; actual
  bytes came in above the 57.9% design envelope and below the 1.0× ceiling,
  exactly the outcome the ADR's discipline was built for.
- **The fixture false-positive was handled with integrity.** Packet 004
  caught packet 003's stale-counter false pass, disclosed it, fixed the
  drill in three attributed commits (bounded 64-row request, planner
  forcing, production CustomScan shape), retained the false line as audit
  history, and re-ran all scales: `mid_scan_full_restart pass=true
  fallback_count=1` at 10k/50k/100k in the corrected packet-005 runs.
  This is the reconciliation-gate culture working.
- **Production is genuinely untouched, doubly.** The entire replica surface
  is behind `#[cfg(feature = "distann-head-attribution-benchmark")]` (not in
  default features) AND the off-by-default GUC
  `ec_distann.benchmark_traversal_replica`; a normal build compiles the scan
  branch out entirely. The scan path reuses the owner path's
  `distann_orchestrated_search` — one traversal core, not a fork — and
  mid-scan failure provably discards all replica state and restarts from the
  same pinned epoch (eager search makes a partial prefix impossible by
  construction).
- **FR-084 closes my Task 190 R1 correctly on mechanism:** the Ready→Stale
  flip commits on a loopback autocommit control connection *before* the
  stable SQLSTATE 40001 is raised, cannot roll back with the failing DML,
  and fails closed (no owner write) if the side transaction cannot commit.

Deep code review (two independent passes: the new module, and the
scan/store/transport/harness diffs) found no unsoundness, no memory-safety
issue, and no path by which a replica failure can produce wrong results —
every analyzed failure degrades to the owner path or errors without owner
writes. What it did find is two P1 coherence holes and a cluster of P2s,
all masked today by the double gate, all of which land squarely in Task 199.

## P1 findings — Task 199 MUST close these before Ready-preference becomes the normal path

**F1 (P1): the mutation guard has zero engine call sites.**
`ec_distann_guard_traversal_replica_mutation` (`traversal_replica.rs:923`)
is correct in isolation (exactly-once 40001, concurrent-caller safe), but
nothing in `src/` calls it: not `dml.rs`, not
`remote_endpoint.rs::apply_record_writes`, not participant tombstoning.
FR-083 deletes are in-place tombstone flips on the published generation —
the epoch fingerprint does NOT change — so with the benchmark GUC on, a
plain `DELETE` mutates owner state while the coordinator replica stays
`Ready` and serves the deleted rows as hits indefinitely. Identity
revalidation cannot detect this by construction. FR-084's lifecycle row
("Ready | first published-generation mutation | Stale") is SHALL-level and
currently convention-only; FR-084-AC-5 was demonstrated by the drill calling
the guard directly, not by an actual mutation. Task 199 Phase 1/3 must wire
the guard into every owner-write dispatch path and re-drill AC-5 through a
real `DELETE`/insert, not the front door.

**F2 (P1): the build copy has no coherence fence.** The builder streams
~391 chunks (at 100k) via independent RPCs, each under a fresh owner
snapshot. A within-epoch tombstone flip landing mid-copy (dispatchable,
per F1) yields a replica mixing pre/post-mutation chunk states. The content
digest is computed over what was read, so a torn image self-validates;
tombstones don't change cardinality, so every count check passes; nothing
re-verifies owner digests against owner state after the copy. The committed
drills mutate only after Ready and cannot catch this. Fix options for Task
199: verify epoch-mutation counters (or owner content digests recomputed
owner-side) before the Ready flip, or make the guard wiring (F1) also block
mutations during Building.

## P2 findings

**F3: side-transaction deadlock exposure violating FR-084's own lock rule.**
`ec_distann_mark_traversal_replica_stale` takes `PgRelation` — pgrx's
`FromDatum` acquires AccessShareLock on the index inside the loopback
transaction, contradicting FR-084's "the catalog update SHALL be the only
lock". Concrete hang: outer DML holds AS on the index; a third session
queues AccessExclusive; the loopback's AS queues behind it; the AEL waits on
the outer transaction; the outer backend is blocked on the loopback socket
read — no lock cycle PostgreSQL can detect, and the 5 s timeout covers only
connect, not the query. Fail-safe for data, unbounded blocking for the DML.
Fix: pass a plain OID and do pure catalog SPI, plus a `statement_timeout`
on the control session.

**F4: `Ready → Retiring` is unreachable.** Retire's UPDATE matches
`state = 'Stale'` only, and no code writes `Retiring` from Ready or on epoch
change, though FR-084's lifecycle table requires both. After a new epoch
publishes, the old Ready replica (1.66 GB at 100k) is unselectable but
unreclaimable except by manually firing the mutation guard to force Stale.
Storage leak per epoch turnover.

**F5: "new scans observe Stale" fails under REPEATABLE READ/SERIALIZABLE.**
The replica catalog read uses the transaction snapshot and the read path
never calls `require_read_committed`. A scan inside an RR transaction begun
before the Stale commit still selects the replica after the mutation retry
has changed owner state — diverging from what the owner path (fresh remote
snapshots) would return for the same scan. Either enforce read-committed
when replica selection is on, or document RC-only in FR-084.

**F6: loopback authentication trap.** The control connection authenticates
as the invoking user with no password; under scram/md5 pg_hba, invalidation
fails permanently → every DML fails closed while a replica is Ready, with
manual stale-marking the only unblock. Also, `require_index_owner` runs
before the Ready check, so non-owner DML through the guard errors even with
no replica present. Both are availability traps Task 199's wiring hits
immediately.

**F7: replica-path errors are swallowed silently.** The scan integration is
`if let Ok(...)` at both open and search; a corrupt/truncated Ready image is
never demoted to Stale, never logged — every subsequent query pays
open-validate plus a doomed first expansion before falling back, and real
replica bugs are indistinguishable from "no replica". Only the
feature-gated `ReplicaFallbacks` counter (which also conflates no-replica
with mid-scan failure) records anything. Task 199 Phase 4 observability
must add a WARNING plus auto-demotion on validation failure.

**F8: suite variant-encoding asymmetry.** Suite validation accepts
`beam_width`/`hop_rounds` as `None==None` across an owner/replica pair, but
expansion force-fills `4`/`100` for the replica arm only; the multicluster
pair-matcher then finds no same-search pair and bails at runtime on a config
that validated. The committed packet configs dodge this by setting both
fields explicitly; the next author won't know to.

## P3 findings (record; fix opportunistically in Task 199)

1. Benchmark work counters double-count hop/frontier telemetry on fallback
   (failed replica attempt + owner rerun both record); per-scan
   `DistannScanCounters` are correct.
2. The mid-scan drill's `fallback_count` read defaults to `1` on query
   error (`unwrap_or(1)`) — the drill would "pass" if the snapshot function
   itself failed.
3. FR-084 operator-surface deviations: invoker-rights + `object_ownercheck`
   instead of SECURITY DEFINER + fixed search_path + PUBLIC revoke
   (arguably safer, but nonconforming); `retire` returns `bool` vs spec
   `void`; error token `EC_REPLICA_INVALIDATED_RETRY` vs spec
   `EC_REPLICA_INVALIDATED` (SQLSTATE 40001 is right, so retry loops work).
4. No explicit non-authoritative/multi-coordinator rejection check in
   build/retire/reclaim/status (FR-084 SHALL); rejection today is implicit
   via the control-index catalog.
5. Invalidation is index-wide (`state='Ready'`) rather than
   exact-active-identity; over-invalidation is the safe direction.
6. `try_access_share` cannot actually return the fallback branch — it
   blocks and ereports on a dropped relation, so the tiny
   catalog-read-to-lock race aborts the query instead of taking the owner
   path (never stale data).
7. Cross-ISA identity risk: the replica scores coordinator-side where the
   owner path scores owner-side; on heterogeneous hardware, FP summation
   order can diverge tie-ordering vs FR-084-AC-2. All drills are same-host.
   Related: the final sort still has no vec_id tie-break (deferred 164-P1).
8. `benchmark_exact_neighbor` has no replica-expander equivalent — enabling
   both benchmark GUCs silently compares non-identical algorithms.
9. `sql/bootstrap.sql` creates both replica catalog tables unconditionally
   even though production builds cannot write them.
