**2. Encoder/decoder-symmetric constants (10)** on byte-layout
offsets (lines 42, 75, 76, 83, 127):

This is a new equivalence class. The argument: byte-layout
constants are consumed by both encoder and decoder. If a mutation
shifts the offset by some delta, both encode AND decode shift by
the same delta — so the round-trip succeeds (data lands at the
same wrong offset, but is read from the same wrong offset).

**Conditionally valid.** This is sound IF and only IF:
- The constants are never used as absolute byte counts in
  assertions (i.e., no test checks `bytes.len() == EXPECTED`).
- The constants are never used asymmetrically (e.g., in only
  encoder OR only decoder).
- No external readers depend on the absolute byte layout.

For wire-format constants, the third condition is the worrying
one. **If `vec_id.rs`'s byte-layout constants determine the
on-disk wire format, mutations would shift the wire format —
and breaking on-disk compatibility silently with a new release
is exactly the kind of bug Task 39 should catch.**

The triage cites lines 42, 75, 76, 83, 127. Without re-reading
each line, I can't fully verify the symmetric-use claim. A
proper closeout audit should check whether any of these
constants are explicitly checked in static-assertion-style tests
(`assert_eq!(SPIRE_ASSIGNMENT_ROW_FIXED_TAIL_BYTES, N)`).

If any constants ARE wire-format offsets, the "equivalent"
verdict is wrong — the mutants would change the on-disk format
without breaking tests, which is a real on-disk-format
regression risk.

**Recommended follow-up:** add static byte-position assertions
for any wire-format constants on these lines, so future
encoder/decoder-symmetric mutations would actually break tests.
