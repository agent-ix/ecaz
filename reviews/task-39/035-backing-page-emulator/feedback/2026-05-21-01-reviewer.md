## Architecture verification

### Stable-address pattern is correct

**`BackingPage`** (lines 465-472):
```rust
pub(super) struct BackingPage {
    bytes: Box<[u8; EMULATOR_PAGE_BYTES]>,      // heap-stable bytes
    line_pointers: Vec<Box<ItemIdData>>,         // heap-stable per-item
    next_tuple_offset: usize,
    bytes_consumed: usize,
    special_size: usize,
    initialized: bool,
}
```

Two critical address-stability guarantees:
1. `Box<[u8; 8192]>` — the bytes array's address is stable even
   if `BackingPage` itself moves (the heap allocation persists).
2. `Vec<Box<ItemIdData>>` — each `ItemIdData` is in its own heap
   allocation, so its address survives `Vec` resize. Production
   code stores `*mut ItemIdData` returned by `PageGetItemId` and
   dereferences it later; this address-stability is load-bearing.

**`BufferRegistry`** (lines 558-572):
```rust
pages: HashMap<(Oid, BlockNumber), Box<BackingPage>>,
page_lookup: HashMap<usize, *mut BackingPage>,  // bytes addr → page
```

- `Box<BackingPage>` in HashMap keeps the BackingPage at a stable
  heap address even when the HashMap resizes/rehashes.
- `page_lookup` provides reverse lookup from a raw `*mut u8`
  (the bytes pointer returned by `BufferGetPage`) back to the
  owning BackingPage — needed because the production code holds
  the raw bytes pointer and passes it to `PageGetItem`/etc.

### `PageInit` / `PageAddItemExtended` semantics

`PageInit` (689): clears bytes, resets line_pointers, sets
`next_tuple_offset = PAGE_BYTES - special_size`. Matches
production `PageInit(page, page_size, special_size)`.

`PageAddItemExtended` (698):
- Computes aligned payload size via `emulator_raw_tuple_storage_bytes`
  (mirrors production `raw_tuple_storage_bytes`).
- Returns `InvalidOffsetNumber` if no space.
- Writes bytes at `next_tuple_offset - aligned_payload`,
  decrements `next_tuple_offset`, allocates a new `Box<ItemIdData>`
  with `lp_off`/`lp_flags`/`lp_len`.
- Returns 1-indexed offset.

Layout matches production: tuples grow downward from top-of-page
toward the line-pointer array growing upward from bottom.
Special area at end.

### `PageGetItem` / `PageGetItemId`

`PageGetItem` (720): dereferences `*item_id`, reads `lp_off`,
returns `bytes_ptr + lp_off`. Stable because lp_off is bounded
< PAGE_BYTES.

`PageGetItemId` (738): returns `&mut **boxed` — gets the

dereferences it; the `Box` heap-stable address makes this safe.

## Findings

### 1. The stable-address pattern is correctly implemented

Both `Box<BackingPage>` (HashMap stability) and
`Vec<Box<ItemIdData>>` (line-pointer stability) are the right
choices. A naive `Vec<ItemIdData>` (no inner Box) would break
when the Vec resizes — production code holding a `*mut ItemIdData`
would suddenly point at deallocated memory. The `Box<>` per
element prevents this.

### 2. The reverse `page_lookup` HashMap is the right shape

Production calls `BufferGetPage(buffer)` to get `*mut u8`, then
passes that pointer back to `PageGetItem(*mut u8, item_id)`.
Without the reverse lookup, `PageGetItem` couldn't find the
owning `BackingPage`. The reverse map handles this. Stable
because the `Box<BackingPage>` heap address never changes (only
the HashMap entry).

### 3. Layout matches production exactly

Verified `emulator_align_up` mirrors production `align_up` (same
formula), `emulator_raw_tuple_storage_bytes` mirrors production
`raw_tuple_storage_bytes`. Round-trip tests should produce
identical layout as the real `pg_sys::PageAddItemExtended`.

### 4. (concern) Memory-aliasing safety on `page_mut`

Lines 620-633:
```rust
fn page_mut(&self, page_ptr: Page) -> Option<&mut BackingPage> {
    // SAFETY: raw points into a Box<BackingPage> owned by self.pages.
    // ...
    // BackingPage simultaneously because each pg_sys page helper
    // ...
    unsafe { Some(&mut *raw) }
}
```

This converts `*mut BackingPage` → `&mut BackingPage` from an
`&self` method. **This is technically unsound** — taking
`&mut` from `&self` in Rust requires interior mutability (which
`BackingPage` doesn't have).

The comment claims it's safe because pg_sys helpers don't hold
multiple `&mut` simultaneously. In practice the tests are
serialized by `TEST_LOCK`, so no real aliasing happens.

**Acceptable for a test harness**, but not idiomatic Rust. A
stricter approach would use `RefCell<BackingPage>` inside the
HashMap and `borrow_mut()` per call. Cost: extra runtime check.
Worth a one-line note about the soundness shortcut for future
maintainers.

### 5. Production code path is unaffected

The 582-line addition is entirely in
`hardening/careful/src/pg_guards.rs`. The production guard
files at `src/storage/*_guard.rs` and `src/storage/wal.rs` are
imported by `#[path]` (lines 798-820) but **not modified**.
Production PG18 build sees the real `pg_sys` from pgrx; careful
build sees this fake. No risk of behavioral change in production.
