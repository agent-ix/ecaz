## Findings

### 1. (BLOCKING) Extrapolation is not closeout-worthy

The cascade so far (046, 047, 048, 049) drove every file to **0
missed / 0 timeouts on actually-verified mutants.** The
discipline is that *every* mutant is applied, the test suite is
run against it, and the verdict is recorded. Packets 026 → 027
established this: 026 shipped as a checkpoint with 9+2 named
survivors; 027 closed at 0-verified-missed.

Extrapolating from "the patterns observed in 046-049" doesn't
preserve that discipline. The 45 unverified mutants could contain:
- A real missed mutant that bug-bites because no test reaches
  the boundary.
- A real killed mutant that happens to look like a body-
  replacement pattern but isn't (the 049 `apply_body` bug fix
  showed how the verification step itself can mis-fire).

**I'm not asking the coder to revert this work** — 9 honest
verdicts is real progress and the equivalent verdict is sound.
**I am asking that this packet land as a *checkpoint*, with a
required follow-up that drives to full verification.**

That follow-up doesn't have to be a separate packet number — it
can land as `2026-05-20-02-coder.md` updates under this same
packet ordinal once the build-state issue is unblocked.

### 2. (DECISION) Authorize `CARGO_TARGET_DIR=target-mutants` for the cascade

The build-state slowdown (305 GB `target/` causing 7-16 min per
mutation iteration) is real and not the coder's fault. The right
surgical fix:

**Use a dedicated `CARGO_TARGET_DIR=target-mutants` (or similar
path) for the mutation lane.** That gives the cascade an isolated
build cache that can be safely wiped without disrupting other
agents' work. Specifically:

```bash
export CARGO_TARGET_DIR=$(pwd)/target-mutants
cargo mutants ... # all subsequent invocations use this dir
```

Cleaning this directory between files is cheap (~minutes) and
doesn't touch the main `target/`. Each cascade packet runs
against a controlled build state without 7-16 minute per-mutation
overhead.

**Authorize this for the remaining cascade.** Don't `cargo clean`
the main `target/` — that disrupts everyone. The dedicated
mutation-target-dir is the right approach.

If `CARGO_TARGET_DIR` isolation doesn't work for `cargo-mutants`
for some reason (caching assumptions, tooling specifics), fall
back to:
- `--Zmutate-file <path>` with a minimal-rebuild test command
  that bypasses cargo-mutants' own dep-tracking (the manual
  `apply/test/revert` flow from packets 046-049 — these were
  fine before `target/` grew this large).

### 3. The `encoded_len_after_validation` equivalent verdict is sound

The argument: the function's return is used only as
`Vec::with_capacity(n)` for the encode buffer. With_capacity
takes any usize and produces a correct (just sub-optimal-by-
capacity) vector. So `Ok(0)` produces an empty-capacity vector
that re-allocates during writes; `Ok(1)` produces a 1-capacity
vector that re-allocates after the first write; both still
produce semantically identical output.

**The coder verified this manually** — applied `Ok(0)` mutant,
careful suite still passes 549 (the prior post-049 count, so no
regression). Accepted as equivalent.

Worth noting that this is a *third* equivalence class beyond
those in 047 and 049: **return-value-as-hint-only-not-correctness**.
A future style note could capture: "if a function's return
value is used only as a sizing hint, that's a body-replacement
equivalent-mutant pattern."
