**5 `align_up` mutants — all killed by `align_up(17, 8) == 24`:**
- `%` → `/`: 17/8=2; result 17+(8-2)=23 ≠ 24 → fails

  ≠ 24 → fails
- `+` → `*`: 17*(8-1)=119 ≠ 24 → fails
- `-` → `+`: 17+(8+1)=26 ≠ 24 → fails
- `-` → `/`: 17+(8/1)=25 ≠ 24 → fails

**4 `aligned_tuple_bytes` mutants — killed by the two
`aligned_tuple_bytes` assertions:**
- `==` → `!=`: same condition-flip pattern; early-exit branch
  returns the unaligned tuple_len.
- `+` → `-` / `-` → `+` / `-` → `/`: change tuple_len base or
  alignment offset; produces different aligned values.

Test inputs (payload=8 and payload=9) are well-chosen: 8 already
aligns (testing the `remainder==0` early-exit branch) and 9
forces the round-up branch. Both arithmetic branches covered.

## Findings

### 1. The 4-assertion test is information-dense

One test, 4 assertions, kills 9 mutants. **Efficient
discrimination** — same shape as the cascade-era one-test-per-
guard pattern that came later (027, 047, 049).

### 2. (cross-reference) Boundary-value test design pattern

The (17, 8) and (9, payload) choices use **non-aligned values**
that the arithmetic mutations alter visibly. A test using
already-aligned values (e.g., `align_up(16, 8)` alone) would
hit the early-exit branch and miss the round-up arithmetic. The
test correctly includes BOTH the early-exit AND round-up
branches — covering both behaviors of the conditional.

This is the prototype for the cascade's later "one-twist-on-
known-good" pattern. Good foundational work.
