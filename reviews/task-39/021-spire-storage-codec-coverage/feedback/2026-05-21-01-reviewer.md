## Architecture verification

### `include!` chain pattern

The new `spire.rs` mounts SPIRE storage children via `include!`
inside a `storage` module:

```rust
pub mod storage {
    use super::meta::{...};
    use super::page;
    use crate::careful_pg_guards::pg_sys;
    use crate::storage::page::{...};

    include!(concat!(env!("CARGO_MANIFEST_DIR"),
                     "/../../src/am/ec_spire/storage/vec_id.rs"));
    include!(concat!(..., "/relation_plan.rs"));
    include!(concat!(..., "/header.rs"));
    include!(concat!(..., "/assignment.rs"));
    include!(concat!(..., "/leaf_v1.rs"));
    // ... and more storage children
}
```

This works for **llvm-cov** (which tracks include sites as part
of the parent file's line counts) — that's why coverage gains
from 0% to 41-97% across 11 storage files.

### Important note on cargo-mutants discovery (carried forward)

`include!` is opaque to cargo-mutants' AST walker. This is what
the 046 packet later discovered when running mutation on
storage children — the prescribed `cargo mutants --file ...`
returned 0 mutants because the children weren't mounted via
`mod` declarations. The cascade then used `--Zmutate-file
<absolute path>` + manual apply/test/revert to work around.

The 021 packet itself is **coverage-only**; the mutation
problem only surfaced when 046 tried to use cargo-mutants on
the same files. 021's design choice (include! vs mod) was the
right call for coverage but created the mutation-tooling
discovery in 046.

### Imports + dependencies wired correctly

```rust
use super::meta::{...};                          // SPIRE meta types
use super::page;                                  // SPIRE page module
use crate::careful_pg_guards::pg_sys;             // fake pg_sys
use crate::storage::page::{...};                  // production storage::page
```

The dependency direction is: SPIRE storage codecs → meta types
+ page module + fake pg_sys + production storage::page. All
the prereqs exist in the careful crate before the include!
chain fires.

### Production source unaffected

The production source files are not modified — `include!`
literally text-substitutes them at compile time. Production
crate compiles them as `mod` children of
`src/am/ec_spire/storage/mod.rs` (the production tree); careful
crate compiles them via `include!`. Same source, two compile
contexts. **No behavior change in production.**

## Findings

### 1. The choice of include! over mod was structural

SPIRE storage children rely on `super::` paths that resolve
differently between production tree position
(`am/ec_spire/storage/...`) and careful tree position
(`careful_storage::...`). Using `include!` text-substitutes
them into the careful's `storage` namespace where the same
`super::` paths resolve correctly.

A `mod` declaration alternative would have required modifying
every child's `super::` paths (like 019 did for `scan.rs`),
which the cascade later sidestepped with the manual
`--Zmutate-file` workflow.

### 2. 22 baseline rows lifted from 0 → 41-97%

The biggest single SPIRE coverage-gain packet. 11 storage
codec files (assignment, header, helpers, leaf_v1, leaf_v2,
leaf_v2_parts, local_store, local_store_set, routing_delta,
top_graph, vec_id) all moved from 0% to measured.

### 3. (cross-reference) Sets up the cascade's substantive work

Once these files were under coverage, the cascade (046-058)
could run mutation campaigns on each. Without 021's include!
chain, the cascade would have started from 0% on every file.

## Disposition

**Code-level verified.** 240-line spire.rs is pure routing
(use imports + include! chain). Production code untouched.
11 storage files from 0% to measured. Foundational for the
cascade.
