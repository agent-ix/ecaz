## Findings

### 1. (IMPORTANT) Bug fix in `run-spire-mutations.py` may invalidate prior `KILLED` body-replacement verdicts

The `apply_body` bug searched forward from the reported `line:col`
for the opening `{` of the function body. For one-line implicit-
return bodies (e.g., `fn is_visible(...) -> bool { flag & MASK !=
0 }`), the forward search jumped past the closing `}` to the NEXT
function's `{`, and mutated *that* function's body. The original
function was unchanged; the test suite ran against an unmodified
helper plus a corrupted unrelated function, which typically caused
*some* test to fail — wrongly reporting the mutant as KILLED.

This is a real tooling defect that affected packets 046, 047, 048.
Recommended follow-up: **re-run the body-replacement subsets** of
those packets with the fixed script, and confirm or update the
killed verdicts. The risk: a body-replacement mutant in
`leaf_v2.rs` / `leaf_v2_parts.rs` / `header.rs` may have been
falsely-killed and is actually a missed survivor.

Concretely:
- 046 (leaf_v2): 14 mutants — the body-replacement ones (likely
  `column_segments → Ok(empty)`, `assignment_rows → Ok(vec![])`
  per the triage) should re-verify.
- 047 (leaf_v2_parts): 67 killed + 1 equivalent — body-replacements
  in `Meta::validate`, `Segment::decode`, `Segment::validate_against_meta`
  should re-verify.
- 048 (header): 35 killed — same audit.

Not blocking 049's acceptance. Track as a separate re-verification
packet (or as a note that the next packet runs in the fixed script
and back-validates the prior three). The bug-fix discovery is
honest and reported clearly — good work; better to find this in
packet 4 than packet 13.

### 2. Equivalent-mutant class 1: disjoint-bit `|→^` (11 mutants)

For non-overlapping single-bit flags, `a | b == a ^ b` by truth
table (`a & b == 0 ⟹ a | b == a ^ b`). Standard pattern from
047 ("DELTA_INSERT | DELTA_DELETE" case). Verified by inspection
that each named flag pair (BOUNDARY^TOMBSTONE, TOMBSTONE^DELTA_DELETE,
etc.) is structurally disjoint.

All 11 equivalent verdicts accepted.

### 3. Equivalent-mutant class 2: reachability-restricted `||→&&` (1 mutant)

`stride < 2 || stride > MAX` mutated to `stride < 2 && stride > MAX`.
The argument: callers reach `leaf_v2_assignment_vec_id_layout` only
after `SpireVecId::from_bytes` has already validated `2 ≤ stride ≤
MAX`, so `stride < 2` is never true for any input that reaches this
function. The `&&` mutant errors only on the impossible joint case;
both expressions return `false` for every reachable input.

**Accepted, with one caveat.** Reachability-based equivalence is
weaker than structural equivalence — it depends on an upstream
invariant. If a future refactor weakens `SpireVecId::from_bytes`'s
validation, the mutant becomes non-equivalent. Worth a
`debug_assert!(stride >= 2, "upstream invariant")` at the call site
to pin the invariant — that's not in this packet's scope, but a
worthwhile follow-up. Not blocking.

### 4. Equivalent-mutant class 3: mutation-resistant loop arithmetic (4 mutants)

This is a new equivalence class not seen in prior cascade packets.
`leaf_v2_max_segment_rows` computes an initial guess and then runs
a decrement loop until `fits(rows)` is true. Arithmetic
perturbations on the initial guess (`-→+` overestimate, `/→*` huge
value) still converge to the correct answer because the decrement
loop fires. Predicate perturbations (`>→==`, `>→<`) on `rows > 0`
short-circuit but return the initial calculation which already
fits for standard inputs (page_size=8192, payload_stride=4,
vec_id_stride=16 → 253 rows).

**Conditionally accepted.** The 4 mutants are equivalent for the
input ranges currently exercised. The packet correctly flags the
caveat: "if real callers ever pass a configuration where the loop
matters, a follow-up packet should expand the test surface and
re-evaluate."

For now, BLCKSZ=8192 is hardcoded by PG18 and SPIRE strides come
from a small enumerated set, so the input range is bounded. **But
this is the weakest equivalence class yet documented — it depends
on production input constraints, not on the source code structure
itself.**

Recommended follow-up: add a test that drives `leaf_v2_max_segment_rows`
with an input where the initial calculation *would* overestimate
and the loop *would* fire (synthetic small-page or unusual
stride combinations) — if such an input is constructable in the
careful harness without breaking other invariants, it would
discriminate at least the `-→+` and `/→*` mutants. Not blocking
049; worth a follow-up note.

### 5. (lesson) Bigger files need multi-pass verification

049 ran in two rounds: initial 190-mutant enumeration → 41
survivors → 15 killing tests added → 17 survivors second pass →
15 equivalents documented + 2 found by the bug fix.

That's a more iterative shape than the smaller-file packets
(046/047/048 each closed in one or two passes). Worth noting that
the bigger SPIRE storage files (`assignment.rs`, `local_store.rs`,
`local_store_set.rs`) may show the same pattern. **The next
packet should expect 2-4 passes for a file in this size range
(~190+ mutants).**
