## What actually landed (architecture)

Task 122 is a broad 7-phase TQ performance investigation. The diff is small and
well-scoped to two concrete pieces, both reusing existing infrastructure rather
than adding parallel machinery:

1. **SPIRE pre-materialization prune** (Phase 2, in-engine, GUC-gated
   default-on): `src/am/ec_spire/scan/candidates.rs` skips row materialization
   for any scored candidate whose inner product cannot enter the running top-k.
   Gated by `ec_spire.pre_materialization_prune` (default on).
2. **Sidecar TQ stage-2 measurement harness** (Phase 3, CLI-only, not an engine
   path): `crates/ecaz-cli/.../sidecar_rerank.rs` adds a `turboquant4` sidecar
   variant and a two-stage `--final-rerank-k` exact-f32 reducer, plus suite
   plumbing.

The `src/am/common/candidate_batch/mod.rs` change is doc-only and *correct*: it
de-stales a comment — the body already routes through `score_width_cascade`
(mod.rs:196), so the old "scalar tile walk is currently the only backend"
comment was wrong; the new comment matches the code.

The closeout decision is sound: the prune is recall-neutral with a large
materialization reduction but only a *modest* latency gain and **no** product
win over RaBitQ at the measured shape; the stage-2 reducer is promising but only
demonstrated in the sidecar harness, not in-engine. Boxing the promotion into
Task 123 with the evidence boundary preserved (in-engine required, sidecar not
sufficient) is the right call. The closeout does not overclaim.

## Code review — prune correctness (the load-bearing change)

Verified the prune is recall-byte-identical to the unpruned bounded path:

- `candidate.score` is stored as `-ip` (candidates.rs:2504). The accumulator
  heap orders by `score` ascending (`scored_candidate_cmp`, types.rs:56-60), so
  the max-heap `peek()` is the worst (smallest-ip) kept candidate.
  `min_ip_to_keep()` returns `-peek.score = ip_worst`. The negation math is
  correct.
- The new `pre_materialization_min_ip_to_keep()` returns `None` (no prune)
  unless **(a)** the heap is full (`heap.len() >= limit`, candidates.rs:3287)
  and **(b)** dedupe is `NoReplicaDedupeDisabled`. The prune site additionally
  requires **(c)** `deleted_vec_ids.is_empty()`. All three guards are correct
  and conservative.
- The prune fires only on strict `ip < min_ip_to_keep`. A candidate with ip
  *equal* to the worst kept is **not** pruned, which preserves the tie-break
  winners that `append_bounded` would still admit (`scored_candidate_cmp`
  tie-breakers on epoch/role/tid/...). So no candidate that could win is ever
  dropped. This is why the diagnostics A/B is winner-identical.

Counter consistency verified: pruned candidates call
`observer.truncated_candidate(epoch, placement, columns.flags[row_offset])`, and
`columns.flags[row_offset] == row.flags` (storage/vec_id.rs:302), so the
primary/boundary-replica role split for a pruned candidate matches the normal
truncation path. The `diagnostics.rs` test exercises exactly this (limit=1, two
candidates, second pruned, asserts `truncated_primary=1`).

## Non-blocking observations (for Task 123, not gating this closeout)

1. **`pre_materialization_prune_enabled()` hardcodes `true` under
   `#[cfg(test)]`** (options/mod.rs), diverging from the sibling
   `candidate_batch_scoring_enabled()` which reads the GUC in all cfgs. Effect:
   the prune-OFF path is not unit-testable and every in-crate SPIRE test runs
   with prune forced on. The green test logs indicate nothing else broke, but a
   one-line comment explaining *why* it's pinned (deterministic prune coverage)
   would help, and Task 123's in-engine version should keep an off-path unit
   test.
2. **`candidate_row_count` semantic shift is user-visible.** Under the default-on
   GUC this diagnostic SRF counter (lib.rs) now counts *materialized survivors*,
   not all scored candidates; pruned rows move into
   `truncated_candidate_row_count`. This is intentional and is effectively the
   "materializations avoided" signal the task asked for, but it is a behavior
   change to a public diagnostic surface — anything that compared
   `candidate_row_count` across the prune boundary will see the shift.
3. **`truncated_candidate_row_count` now conflates two events** (heap eviction vs
   pre-materialization prune). The funnel JSONL (`item_sum` vs `candidate_sum`)
   does capture the distinction, so no data is lost, but Task 123 may want a
   dedicated "materializations avoided" counter rather than overloading
   truncation, since Phase 2/Phase 4 explicitly call for that counter.

None of the above block the closeout. Recommend accepting the
keep-experimental / promote-to-Task-123 outcome as written.
