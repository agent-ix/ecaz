# Reviewer Feedback: Task 118 HNSW Candidate Pool Diagnostic Fix

Reviewed commit `59858d090` plus the diagnostic code it builds on
(`a2b1654e0`, the frontier diagnostic). Scope: the frontier-containment
diagnostic in `scan_debug.rs`, `ec_hnsw_recall_helpers.rs`, and
`hnsw_frontier.rs`. The candidate-pool fix here is the decision point that
shapes the whole attribution conclusion, so the findings below are mostly
about *measurement validity*, not Rust correctness.

## What is good

- The fix is a real improvement over the prior stale visible-frontier snapshot:
  the old version genuinely under-reported containment, so switching to the
  AM-emitted candidate stream removes a false-negative source.
- The CLI/suite wiring is done the right way: `hnsw-frontier` and
  `hnsw-score-correlation` are new `SuiteStep` variants in `suite.rs`, not a
  forked bash sweeper, which is exactly what `CLAUDE.md` asks for.
- Sign/metric conventions are consistent (I checked): `frontier_approx_ranks`
  ranks the negated/distance approx score ascending and `frontier_exact_ranks`
  ranks the raw dot-product exact score descending, so rank 1 = best in both.
  No wrong-sign bug here — good, since that is exactly what Phase 4 was meant
  to catch.

## Finding 1 (HIGH, measurement validity): the "frontier" and "final emitted"
## sets are identical by construction — the diagnostic cannot separate the two
## failure modes Task 118 exists to separate

`debug_gettuple_frontier_containment_report`
(`scan_debug.rs:~2402`) consumes the **entire** gettuple stream with no
top-k LIMIT, then sets:

```
let pre_final_frontier_size = final_emitted_count;
let pre_final_frontier_candidates = final_emitted_candidates.iter().map(...);
```

So `pre_final_frontier_size`, `frontier_candidates`, and `final_emitted_*`
are derived from the same stream. The code comment is explicit about this
("Treat the full AM-emitted stream as the pre-final candidate pool").

The artifact confirms the fields are tautologically equal. From
`artifacts/frontier-10k-hnsw-turboquant-candidate-pool-smoke5.jsonl`,
query 0, ef_search=40:

```
visited_before_output                  = 40
pre_final_frontier_size                = 40
final_visited_count                    = 40
final_emitted_count                    = 40
exact_reranked_candidates              = 40
frontier_row_indices == final_emitted_row_indices set?  True
```

Every count collapses to `ef_search`, and `frontier_row_indices` is the same
set as `final_emitted_row_indices`. That means `truth_top10_in_frontier` is
literally measuring containment in the final emitted output, because there is
no truncation step between "frontier" and "emitted" in this harness.

Task 118 Phase 1 requires: *"The diagnostic must distinguish 'truth row never
entered the frontier' from 'truth row was present but final rerank/output lost
it'."* The current implementation collapses exactly those two stages into one.
It can answer "did truth make it into the ef_search-sized emitted stream"
(useful, and it shows truth@10 → 1.0 at ef=128/200), but it cannot attribute a
miss to traversal vs. rerank-ordering vs. output truncation — which is the
deliverable.

To actually separate the stages the diagnostic needs to capture the result-heap
/ beam state *before* the AM applies its final ordering+rerank, as a set
distinct from the post-rerank emitted stream. Reporting both as separate
columns when they are always equal is, at minimum, misleading evidence for a
P0 attribution packet, and `request.md` / the rendered summary table present
"frontier" and "emitted" as two measurements.

## Finding 2 (HIGH): `candidates_dropped_before_exact_rerank` is structurally
## degenerate and does not measure what Phase 2 asks for

```
let candidates_dropped_before_exact_rerank =
    (final_visited_count - exact_reranked_candidates).max(0);
```

`final_visited_count` is `visited_tids.len()` and `exact_reranked_candidates`
is `grouped_rerank_heap_score_calls`. In the artifact both are 40, so the
counter is 0. Two problems:

- Phase 2 defines this as *frontier candidates retained but dropped before
  exact rerank*. Subtracting rerank calls from **visited** conflates graph
  traversal fanout with the frontier. On a real graph scan where
  `visited_tids` >> ef (true HNSW traversal touches many more nodes than the
  beam width), this would report a huge bogus "dropped" number that is mostly
  nodes never in the frontier at all.
- In the captured run `visited == frontier == emitted == ef_search`, so the
  counter degenerates to ~0 and carries no signal. Combined with Finding 1,
  this suggests `visited_tids` in this debug path is only tracking the result
  set, not the true traversal fanout — please confirm. If true, the
  "visited count" the task asks for (distinct from frontier size) is also not
  being measured.

## Finding 3 (MEDIUM): `visited_before_output` is captured before the gettuple
## loop yet equals the final count

`visited_before_output` is read immediately after `debug_am_rescan`, before
any tuple is fetched. For a lazy graph-first scan that should be ~0 (or just
bootstrap); instead it is 40, same as `final_visited_count`. Either traversal
is eager (then this column is redundant with `final_visited_count`) or the
field is populated by something other than pre-fetch traversal. As emitted it
adds no information distinct from the final count — please confirm the intent
and whether the column should be dropped or made meaningful.

## Ask

These do not require reverting the fix — the candidate-pool stream is a
legitimate thing to measure. But before the packet 006 attribution conclusions
(graph-build vs. traversal vs. frontier-width vs. rerank-boundary) are treated
as decision-grade, the diagnostic needs to either (a) actually separate the
pre-rerank frontier from the post-rerank emitted stream, or (b) the packet
narrative must stop presenting `frontier` and `emitted` as independent
evidence and explicitly state they are the same set, and fix the
`dropped_before_exact_rerank` derivation so it is frontier-relative, not
visited-relative.
