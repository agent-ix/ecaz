# Task 80 final review — architectural + packet 001 (AWS 1M block16 pruning)

## Decision

**Accept the shelving decision.** The closeout is operationally correct:
Task 80's block-cap mechanism does not preserve the 100k candidate/latency
win at 1M scale, and the proper fix is the deeper ADR-074 leaf block-summary
format (now Task 81). However, **the closeout's reasoning under-reads the
data** in a way worth recording so Task 81's design starts from the right
diagnosis.

## Architectural review of task spec

### What the spec gets right

- **Clean Track A / Track B split** with explicit fallback contract: if
  row-budgeted routing can't reduce surface inside selected leaves, escalate
  to leaf-local pruning. This matches ADR-075's priority ordering.
- **Non-goals are sharp**: explicitly forbids the recall-by-top-graph-width
  trap (which the AWS 1M top-graph rebuild proved is candidate explosion,
  not latency) and forbids scoring-kernel work before candidate surface is
  reduced. Both correct per Task 79 evidence.
- **Gate floors are well-anchored**: 0.9925 recall, ≤5.2M cands strong /
  ≤4.0M stretch, ≤45ms p50 / ≥25% improvement vs 60.256ms baseline. These
  are the same gates Task 79 used, so cross-task comparability is preserved.
- **AWS comparison set is honest**: cites both the old tg96 row (target to
  beat) and the tg256 recall-ceiling rows (the candidate-explosion failure
  mode to avoid). No surface-swapping.
- **Required diagnostics list is comprehensive**: includes per-leaf row
  estimates, scored vs retained vs returned, object bytes, scoring timing,
  score share. Enough to attribute any failure to the right layer.

### What the spec assumes that the AWS run disproves

The spec frames the problem as "candidate-surface reduction at scale" — i.e.
the goal is to reduce the *number of candidates scored*. The packet 001
result shows this framing is incomplete: **the 100k Task 79 win didn't
reduce candidates per query much more than the existing 100k baseline
geometry already did.** See "Critical architectural finding" below.

This isn't a fault in the Task 80 spec — it's something the AWS evidence
revealed that the Task 79 100k evidence couldn't show. The Task 81 spec
should incorporate it.

### Critical architectural finding the closeout misses

Recompute candidates *per query* across the comparable rows:

| surface | cap | candidates total | queries | cands/query |
| --- | ---: | ---: | ---: | ---: |
| 100k local (Task 79 044) | 1152 | 3,673,383 | 200 | **18,367** |
| AWS 1M (this packet) | 1152 | 9,213,846 | 500 | **18,428** |
| AWS 1M (this packet) | 2048 | 16,379,614 | 500 | **32,759** |
| AWS 1M old tg96 baseline | n/a | 9,213,846 | 500 | **18,428** |

Two facts jump out:

1. **At cap 1152, candidates per query are essentially identical (18,367
   vs 18,428).** The block-cap mechanism produces the *same per-query
   candidate count at 1M as at 100k*. The cap is not binding at 1M with
   cap=1152 — it's producing the same selection as the baseline
   leaf-routing did at 1M.

2. **The cap=1152 row also matches the old tg96 candidate count EXACTLY
   (9,213,846 → 9,213,846 — same to the row).** This is not a tuning
   improvement at all at 1M; the global-cap path collapses to the prior
   tg96 selection because the cap is larger than what the geometry
   already selects.

So the "8.5× latency increase at 10× scale" (35.29ms → 301.12ms) is
**not** a candidate-surface failure. It's per-candidate I/O cost scaling
poorly because:

- the 1M SPIRE index is ~872 MB on disk vs the 100k index's much smaller
  footprint;
- per-candidate object reads pay more page-cache misses and more decode
  cost at 1M;
- the deferred-decode infrastructure from Task 79 reduces *bytes per
  selected block range*, not *cost per candidate*.

The recall gap is the other half: cap=1152 only hits 0.9832 at 1M vs
0.9940 at 100k. To match the recall floor at 1M you need cap=2048+
(0.9914-0.9918), which then DOES bind and explodes candidates 1.78x.

**Combined, this means the Task 79 win was geometry-specific to 100k, not
a general candidate-surface mechanism.** At 1M the leaf row density is
~7800/leaf vs ~780/leaf at 100k, so:

- per-leaf block-summary information is more dilute (each k=3 summary
  represents 10× more rows);
- the recall ceiling drops because summary scoring can't discriminate
  fine-grained block winners with that density;
- to recover recall you must let more blocks through, which spikes
  candidates back up.

This is the *real* reason Task 80 needs Task 81's persisted block-summary
format: it has to scale summary density with leaf row count, not just rely
on the existing fixed-k summary geometry.

### Catalog repair finding (worth flagging)

The packet records that `ec_spire_index_scan_leaf_candidate_snapshot(oid, real[])`
was missing from the retained AWS extension catalog after the new ecaz
install ran. The SSM repair (`ssm-register-candidate-snapshot.json`)
manually re-registered the pgrx function with `CREATE FUNCTION` +
`ALTER EXTENSION ... ADD FUNCTION`.

**This is a deployment idempotency bug, not a code defect.** The pgrx
install path should re-register all extension SQL functions even on a
retained catalog, or `ecaz cloud install` should rebuild the extension
SQL from the binary's `.control`/`.sql` files. Worth filing as a small
ecaz-cli or `ecaz_pg_test` install hardening ticket so the next AWS
follow-up doesn't trip the same gap.

## Hand-off to Task 81

The closeout correctly names `plan/tasks/81-spire-leaf-block-summary-format.md`
as the next owner per ADR-074. Task 81 should incorporate the diagnosis
above:

1. **Frame the problem as block-summary density, not candidate count.**
   At 100k leaf rows are ~780/leaf and existing k=3 summaries discriminate
   well; at 1M they're ~7800/leaf and k=3 doesn't. The persisted block-
   summary format needs to scale block size and summary count to leaf row
   density.
2. **The latency gap at matched candidates is I/O cost, not scoring CPU.**
   The persisted format should also reduce per-candidate object bytes
   (probably by separating hot summary from cold row payload more
   aggressively than V4 does).
3. **Recall ceiling at 1M needs explicit measurement before format work.**
   Run a control showing what recall the *theoretical* per-row brute-force
   on routed leaves achieves at 1M with different block sizes — that's the
   ceiling Task 81 has to beat, not the AWS 1M tg96 row.

## Verdict

Task 80 shelving accepted. Spec was sound; AWS evidence is honest and the
truncation at cap=2048 was correct. The closeout could be tighter on
*why* the path failed (the data shows it's per-candidate I/O + summary
density at 1M, not candidate count per query), but the operational
decision and the hand-off to Task 81 are right.

Two recorded notes for downstream:

- **Task 81 design**: incorporate the cands/query analysis above so the
  persisted summary format addresses summary density at scale, not just
  more cap tuning.
- **ecaz-cli / install hardening**: file a small ticket for the pgrx
  function re-registration gap that the packet patched manually.
