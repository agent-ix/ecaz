## Why item 1 is a real gap and not process ceremony

The candidate strictly *adds* per-call work to every read RPC: a
`futures_util::select` over the query future and a 5 ms-poll interrupt signal,
a `cancel_token()` clone plus `RemoteTlsConfig` clone per await, a second
`postgres_interrupt_pending()` check on the success path, and typed error
classification. There is no mechanism by which that makes reads faster.

The packet nevertheless measures the candidate as 3.84% / 6.37% / 4.52% faster
in warm mean, with every recorded p50/p95/p99 also lower. I verified those
deltas against `suite-results-{control,candidate}.jsonl` and they are computed
correctly (10k 7.03→6.76, 50k 8.16→7.64, 100k 8.40→8.02). The arithmetic is not
the problem — the numbers are real, and that is exactly what makes them
informative: **an impossible improvement of 4–6% is a direct measurement of this
fixture's sequential-arm drift floor.**

That floor is load-bearing. The ledger row this packet exists to clear records
the pre-TLS signal as warm mean +12.8% / +17.5% at 50k/100k, with the best
screened fast path still +7.1% at 50k. A drift band of ±6% does not resolve
+7.1%. So the current evidence cannot distinguish "the wrapper is free" from
"the wrapper still costs ~7% at 50k and drift masked it." The disposition the
task needs — no regression — is the one claim the run cannot support at the
resolution required.

The manifest is honest about this ("single-run observations and can include
order/cache noise", "do not treat these single sequential latency runs as a
general-purpose performance claim"), and I want to credit that: the packet
does not overclaim. But the correct response to a disclosed resolution limit
that sits on top of the decision threshold is to close the resolution gap, not
to record the verdict with the caveat attached. An A-B-A control repeat at 50k
either shows control drifting by 4–6% between repeats — which retires the old
+7.1% signal as unresolvable noise and lets the ACCEPT stand cleanly — or it
shows control repeating tightly, which means the sign flip is real and needs a
mechanism before anyone believes either number.

A second, smaller reason to want the repeat: the two arms were built on
**independently constructed generations**, not one shared generation.
`cluster_graph_side_bytes` differs by exactly one 8 KiB page at 50k
(410,189,824 vs 410,181,632) and 100k (831,750,144 vs 831,758,336). That is
benign for storage, and it is the honest explanation for the 100k recall
boundary move (see below), but it means arm-to-arm variance includes build
variance as well as run variance. The reuse repeat isolates the run component.

## What I verified and accept

**TLS preservation and pool-key boundary — accepted.** The claim that no
pre-Task-236 `NoTls` path is reintroduced holds. The two `NoTls` sites in
`src/am/ec_distann/remote_transport.rs` (`cancel_remote_query` at ~112,
`open_remote_connection` at ~640) are both inside `tls_config.no_tls()`
branches, and `no_tls()` is only reachable through
`RemoteTlsPolicy::DistannSecure`, which maps absent `sslmode` to `Require`
(`remote_postgres_tls.rs:281`), rejects `allow`/`prefer` outright (line 418),
and confines `disable` to explicit loopback hosts (`validate_policy`, lines
437–453). This matches the ruling already recorded in
`reviews/task-236/005-main-integration/feedback/2026-08-25-01-reviewer.md`.
Pool keys carry `security_fingerprint` alongside `work_identity`, and
`pool_entry_is_superseded` will not let a same-work-identity entry with a
different security fingerprint be reused.

**Cancellation and interrupt-race handling — accepted.** `await_remote_read`
checks `postgres_interrupt_pending()` before the await, races the query against
`postgres_interrupt_signal()`, and — the part I looked hardest at — discards an
already-successful result when an interrupt landed during the await
(`Ok(value) if postgres_interrupt_pending() => { drop(value); Interrupted }`).
That is the correct choice: returning rows that the backend is about to abort on
is the partial-result failure mode this task exists to remove. Cancel delivery
is bounded at 100 ms on both the interrupt and the timeout path, with the
timeout path's comment correctly noting that dropping a tokio-postgres future
does not prove the owner stopped, hence unconditional eviction of the ambiguous
session.

**25-cell fault matrix — accepted, all 25 verified individually.** Every line in
`artifacts/runtime/task234-read-rpc-fault-matrix.log` carries `pass=true`,
`remote_work_drained=true`, and a positive `retry_rows`, across
{physical_head_search, crown_code_export, gateway_routing_export,
head_shard_export, head_shard_import} × {remote_statement_timeout,
local_query_cancel, local_statement_timeout, remote_backend_termination,
connection_reset}. Error categories are typed per fault
(`EC_REMOTE_STATEMENT_TIMEOUT`, `canceling`, `EC_REMOTE_BACKEND_TERMINATED`,
`EC_REMOTE_TRANSPORT_RESET`) and no cell returns rows. The timing claim in
`request.md` is precise as written: slowest reset 1,223 ms, and the slowest
non-reset cell is 509 ms.

Retaining `failed-tls-restart-console.log` and its runtime logs rather than
deleting the first failed run is the right call — it is what makes the CLI
fixture bug (owner restarted without its TLS server config) checkable instead of
asserted.

**Recall and storage neutrality — accepted.** Recall is byte-equal at 10k
(0.9990) and 50k (0.9540). At 100k it moves 0.9295 → 0.9290, one hit in 2,000,
which reconciles exactly to the single top-10 boundary swap (id 73101 → 63646)
recorded in the manifest. Head membership `ids_sha256` is identical between arms
at all three scales (10k `53067d1e…`, 50k `515e5e9a…`, 100k `fd5a185f…`), so
head selection did not move. Given identical head membership, an unchanged
scoring path, and independently built generations differing by a page, treating
the boundary swap as build/tie nondeterminism rather than a read-path regression
is the correct reading, and I accept it.

**Suite discipline — accepted.** Driven by `ecaz bench suite` against a
committed `suite.json` with a preregistered audit (6 steps, 3 run / 3 skipped
per arm, zero failed/missing/stale), artifact SHA-256s recorded, corpus and
PGDATA correctly not committed, `run_dir` under `~/.ecaz/clusters/`. Per-arm
isolated one-index-per-owner fixtures, no shared-table surface.

**Bookkeeping — accepted.** The task file `Status:` header and
`plan/tasks/README.md` row 234 agree with each other and with the packet, cite
both the review packet and the benchmark packet, and correctly state that Tasks
237 and 228 stay blocked. `plan/design/ec-distann-recall-latency-roadmap.md`
row 234 was updated in `ed5ac814c` to scope the old numbers to their measured
SHAs rather than deleting them. Superseding the pre-TLS negative result for
*disposition* while retaining it as evidence is the right handling and I am
not asking for it to be reversed.
