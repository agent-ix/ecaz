# Task 234 packet 005 — NOT DONE: the drift bound refutes packet 004, it does not rescue it

Verdict: **NOT DONE.** The run is exactly the one I asked for, it was executed
honestly, and every number verifies. What is wrong is the conclusion drawn from
it. Two items:

1. **Restate the disposition as a small measured cost, not as neutrality.** The
   packet's own data shows the candidate slower at both fixture positions, on
   every statistic. "Does not resolve as a regression" is defensible about
   *magnitude* and wrong about *direction*. Fix it in `request.md`, the
   `benchmarks/.../manifest.md` results section, the Task 234 `Status:` header,
   `plan/tasks/README.md` row 234, and the roadmap row — all five currently
   carry the neutral reading.

2. **Record an explicit product ruling accepting that cost.** Follow the Task
   236 precedent, where a P0 transport property was accepted *with* its
   measured warm-mean penalty stated rather than by arguing the penalty away.
   Tasks 237 and 228 unblock on this verdict, so the number they inherit should
   be a decision, not an absence.

No rerun. No fault matrix. No 10k/100k rebuild. The measurement is done and I
am not asking for more of it.

## What the data actually says

I re-derived every figure from `suite-results-{control,candidate}-drift-v2.jsonl`
rather than from `request.md`. All four means, all percentages, and both
comparisons against the old 8.16 ms control reproduce exactly:

| | control | candidate | candidate − control |
|---|---:|---:|---:|
| seed (fresh fixture) | 8.83 | 9.43 | **+6.80%** |
| repeat (`reuse_fixture`) | 8.47 | 8.74 | **+3.19%** |
| within-arm seed→repeat | −4.08% | −7.32% | |

At the repeat position the other statistics agree: p50 +2.03%, p95 +0.96%,
p99 +1.89%. That is **two fixture positions × four statistics = eight
indicators, all signed the same way**, in the direction the mechanism predicts —
the candidate adds a `select` against a 5 ms interrupt poll, a cancel-token and
`RemoteTlsConfig` clone, and a second pending-check per read.

The drift bound itself is real and useful: three observations of the *same*
control SHA now span 8.16 / 8.47 / 8.83 ms, an 8.2% spread, and same-fixture
repeat alone moves a mean 4–7%. That band is wide enough that +3.19% is not
separable from zero at this resolution. I accept that.

But the band cuts the other way too, and this is the part the packet does not
say: **it retires packet 004's headline.** Packet 004 reported the candidate
6.37% *faster* at 50k and carried that into the task header, the README row,
and the roadmap as a neutral-or-better result. On today's matched comparison the
candidate is slower at both fixture positions. The −6.37% was drift, exactly as
the packet-004 review argued it had to be, and packet 005 is the evidence that
settles it. A packet that refutes its predecessor's headline should say so
plainly instead of carrying "reverses the historical pre-TLS negative latency
signal" forward unamended.

So the honest three-sentence disposition is: the wrapper costs something small;
this fixture cannot resolve how much, beyond bounding it well under the
historical +7.1%; the direction is consistent and matches the mechanism, so it
should be recorded as a cost rather than as parity. That is a *better* result
for Task 234 than the neutrality claim, because it is one a later reader cannot
overturn with a rerun.

## What I verified and accept

**The run is the one I registered.** `reuse_fixture: true` on the repeat step
for both arms, `--reuse-provenance-dir` pointing at that arm's own seed, same
`run_dir` per arm, 50k, 50 timed iterations after 10 warmups, 200 queries,
`persisted_head`, release profile, correct SHAs on every row
(`ed5ac814c` control, `7c42dc818` candidate). Seeding a fresh fixture first
because the originals had been removed is the right call and is disclosed.

**Result identity holds.** Recall is 0.9540 on all four runs, and head
membership `ids_sha256 = 515e5e9a480e…` is identical across all four *and*
identical to packet 004's 50k value. The fixture is genuinely the same surface;
the candidate changes no result.

**The harness changes are legitimate and were disclosed rather than buried.**
`775496af1` deletes a six-line guard that previously refused
`secure_remote_transport` combined with `reuse_fixture`. I checked what it was:
a fail-closed placeholder for functionality that did not exist, not a
correctness invariant. Implementing secure reuse and removing the guard is the
right order. The strict row-count check is untouched, as claimed. Making
`skip_fault_drills` actually skip the mutating routed DELETE/VACUUM drill it
already documented as excluded is a genuine fix, and it is the same class of
defect the Task 224 review found (a skipped drill reported as a pass).

**TLS stayed on — and I can show it, not just take it.** Both arms carry
`--secure-remote-transport` and the `pg18-ssl` toolchain on the command lines
recorded in `suite-{control,candidate}-drift-v2.log`. The empirical check
matters more here, because `validate_policy` permits `sslmode=disable` on
loopback, so a reuse path that failed to reload TLS could have silently
downgraded on a 127.0.0.1 fixture. If that had happened these runs would be
*faster* than packet 004's TLS-on control — Task 236 measured TLS at +14.6%
warm mean. Both drift controls are **slower** than 8.16, so no silent plaintext
downgrade occurred.

## Non-blocking

The drift runs do not emit a TLS preflight line the way packet 004's matrix did
(`tls=verify-full`, client-certificate auth, plaintext rejection), and no
`tls=` / `secure_remote_transport=` field appears on any normalized row in the
two `-drift-v2.jsonl` files. The command line is adequate durable evidence and
my empirical check above closes the question for this packet, so this does not
block. But with the secure+reuse guard now removed, a `tls=` field on the
provenance row would make "secure reuse stays secure" checkable from
`results.jsonl` alone, which is where NFR-007 says the machine-readable truth
lives. Worth adding the next time that emitter is touched.
