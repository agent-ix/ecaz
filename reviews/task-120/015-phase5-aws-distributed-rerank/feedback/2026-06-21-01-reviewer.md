## (b) Does the route-overfetch recall lever hold on the distributed path at AWS scale, and at what latency?

**Not demonstrated on the distributed path.** The nprobe 64→96 sweep only ran
single-node (`0.9646`→`0.9716`). On the distributed path the only sweep is the
5-query smoke at nprobe 8/16/32, which reaches recall@10 `0.7400 / 0.8800 /
0.9200` (resume3 Coordinator query-metrics table) — still climbing at nprobe 32,
5-query sample, no CI, different truth set. So the lever direction looks
*consistent* but is **not measured at the nprobe range or query count needed to
claim it holds distributed**. Latency on the distributed smoke is total_p50
`55 / 70 / 89 ms` at nprobe 8/16/32 (production-read profile, resume3) — but that
is low-nprobe and 5 queries, not comparable to the single-node 234 ms@nprobe96.

Note also the single-node 990k recall ceiling here (`0.9716`@nprobe96) is
consistent with the prior-task finding that 96 is still on the rising part of the
knee. The explicit packet-011 follow-up — **build the AWS index with a larger
`top_graph_search_list_size` so nprobe can sweep past 96** — was **not done**:
the index was built at `top_graph_search_list_size=96` (storage log reloptions,
placement plan), the same ceiling as local. So the "sweep past the knee" question
is still open at AWS scale.

## (c) Is the near-data distributed rerank hypothesis validated by measured distributed activity?

**Partially demonstrated as a functioning path; NOT validated as a
recall/latency win.** Measured distributed activity is real:
- production-read profile (`production-read-profile-smoke.log`,
  resume2/resume3): `result_source=remote_heap_candidates`,
  `local_pid_count=0`, `remote_pid_count=32`, `remote_heap_ready_dispatch=2`,
  `remote_heap_candidate=20`, `returned=10`, `status=ready`, `next_blocker=none`.
  The pipeline-smoke table confirms `local_pid_sum=0` with all candidates coming
  from remote heaps across nprobe 8/16/32.
- So workers do generate and exact-resolve candidates locally and ship compact
  exact-scored streams to the coordinator (merge_output 10, 0 duplicates) — the
  Phase-5 contract shape is exercised end-to-end.

**Caveat the next packet must resolve:** the smoke also prints a *handoff summary*
line that reports `next_blocker = requires_remote_heap_resolution` /
recommendation "add origin-node row locator resolution before returning remote
heap rows" (`smoke-customscan-read.log:22`, resume2/3). The `production_read_only`
profile right below reports `status=ready/next_blocker=none`. These are two
different exit paths: the production-read-only profile is ready, but the full
handoff that returns actual heap *rows with origin-node locator resolution* still
flags a blocker. This is exactly why the `EXPLAIN ANALYZE` returns rows of
`width=12` (id/score projection) and `nprobe: 0, rerank_width: 0` in the plan
node — it is the production-read projection path, not a full-row materialization.
The packet should state plainly whether a full distributed result (heap rows, not
just ids) is wired, because Phase 5's "end-to-end recall and latency" metric
depends on it. The required-metrics list in the task (worker-local candidates
generated/reranked, rows/bytes shipped, coordinator merge cost, end-to-end recall
+ latency, effect of worker count + fanout) is only partially present and only at
5 queries / low nprobe.
