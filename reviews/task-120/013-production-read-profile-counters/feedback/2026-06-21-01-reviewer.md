# Review: Task 120 Packet 013 — Production Read Profile Counters

## What this change does

Commit `7e86b627d` (head SHA matches `manifest.md`) touches exactly one file,
`crates/ecaz-cli/src/commands/bench/spire_pipeline.rs` (+64/-0). It widens the
existing `ProductionReadProfileAggregate` to carry 14 additional production
read-profile metrics that the `ecaz bench spire-pipeline
--include-production-read-profile` path already queries from
`ec_spire_remote_search_production_read_profile` but previously dropped on the
floor:

- `local_pid_count`, `skipped_pid_count`
- `compact_candidate_count`
- `remote_heap_ready_dispatch_count`, `remote_heap_failed_dispatch_count`
- `remote_heap_candidate_count`, `local_heap_candidate_count`
- `payload_decode_row_count`
- `merge_input_count`, `merge_duplicate_vec_id_count`, `merge_output_count`
- `strict_fail_count`

Three touch points, all parallel: the struct field list
(`spire_pipeline.rs:3758+`), the `record()` accumulator
(`spire_pipeline.rs:3796+`), and the render table header + cell rows
(`spire_pipeline.rs:4299+`, `:4348+`). A test fixture row and two new header
assertions are added (`:5175+`, `:5215+`).

## Correctness — verified against source

- **Metric names match the emitter.** Every newly aggregated key resolves to a
  real `metric!(rows, "<name>", ...)` push inside
  `ec_spire_remote_search_production_read_profile` (`src/lib.rs:13605–13728`),
  including the easy-to-miss `remote_heap_failed_dispatch_count`
  (`src/lib.rs:13622`), `merge_input_count` (`:13721`), `merge_output_count`
  (`:13727`), and `strict_fail_count` (`:13728`). No typos, no orphan columns.
  `i64_metric` (`spire_pipeline.rs:3465`) parses the string value and falls back
  to `0` on a missing/unparseable key, so a metric the SQL surface ever drops
  degrades to zero rather than panicking.
- **Aggregation is correct, no double-counting.** Each
  `ProductionReadProfileRow` is one query's key→value map
  (`spire_pipeline.rs:3445`), `record()` is invoked once per query, and each
  `+=` sums that query's already-merged value across the suite's query set. This
  is the identical idiom the pre-existing `selected_pid_count_sum` /
  `remote_pid_count_sum` / `dispatch_count_sum` fields use — the new fields just
  follow it. The CLI does **not** re-sum across leaves/workers; that rollup
  already happens server-side (`scan_output.rs` /
  `production_transport.rs` merge dispatch results into the single per-query row
  the profile function returns), so the CLI summing one merged value per query
  is the right level and avoids leaf/worker double-counting.
- **Semantics line up with the distributed read path.** These are
  coordinator-side production-read (2pc/distributed) counters — local vs remote
  vs skipped PID partitioning, remote heap dispatch readiness/failure, remote vs
  local heap candidate volume, payload decode rows, and coordinator merge
  input/dup/output — exactly the worker-stream and merge attribution Phase 5
  needs.
- **Purely additive, non-behavioral.** No scan/read execution path is touched;
  this is CLI reporting only. No SQL surface, suite config, profiles, Terraform,
  or AWS load logic changed. Confirmed by the single-file diff.
