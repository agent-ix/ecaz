## Correctness findings (verified, not asserted)

1. **The packet-002 stage 4/5/6 attribution ambiguity is genuinely resolved —
   and was resolved by the snapshot this packet now also surfaces standalone.**
   Packet 002's noted limitation (stages 4/5/6 sharing one
   `predicted_id_set.contains(truth_id)` lower-bound predicate) is gone in the
   current tree. Stage 4 `local_candidate_frontier` uses
   `target_candidate_rank_row_retained` (`spire_pipeline.rs:3003-3006`,
   helper `3215-3217`: `status == "target_candidate_ranked" &&
   approximate_rank.is_some()`); stage 5 `exact_source_rerank_frontier` uses
   `target_candidate_rank_row_in_rerank_prefix` (`3038-3041`, helper
   `3219-3225`: additionally `selected_by_rerank_prefix == Some(true)`); stage 6
   `final_top_k` still uses the returned-id set (`3069`). The per-stage
   `containment_basis` is now `"target_candidate_rank_snapshot"` for stages 4/5
   (`3001`, `3036`), not the lower-bound sentinel. So candidate-frontier drops
   (`candidate_not_retained`, `stage_missing_reason_for_candidate_frontier`,
   `3227-3243`) are now distinguishable from rerank-width drops
   (`rerank_width_cap`, `stage_missing_reason_for_rerank_frontier`,
   `3245-3260`). Packet 005 makes that same snapshot durable as its own JSONL so
   the candidate/rerank attribution is reviewable per-truth-row outside the
   aggregated stage-containment record.

2. **Field mapping is exact and complete.** The SQL `SELECT` projects 16
   columns in a fixed order (`spire_pipeline.rs:1731-1738`); `From<Row> for
   TargetCandidateRankRow` reads `row.get(0..15)` in the same order
   (`2176-2196`); `TargetCandidateRankRecord::from_row` (`2227-2249`) copies all
   16 plus the join keys. No field is dropped or transposed. `truth_rank =
   row.target_ordinal + 1` (`2237`) correctly converts the 0-based SQL ordinal
   to a 1-based rank, matching the sibling records (`LeafBlockRankRecord` at
   `2320`, MissAttribution at `2422`/`2540`).

3. **Truth-row join is correct.** The standalone path keys each row by
   `usize(target_ordinal)` and resolves `truth_id =
   query_truth_ids[truth_index]` (`spire_pipeline.rs:730-744`), with explicit
   overflow/bounds errors. Unlike the stage-containment path (which collapses
   rows into a `HashMap` keyed by ordinal, last-write-wins), this path **pushes
   every returned row**, so multiple physical-placement rows per truth neighbor
   (distinguished by `pid` / `row_index` / `node_id`) are all preserved. That is
   the right choice for a per-neighbor diagnostic and is consistent with the
   snapshot's `ORDER BY target_ordinal, approximate_rank NULLS LAST, pid NULLS
   LAST, row_index NULLS LAST` (`1738`) deterministic ordering.

4. **Query reuse is sound.** When both `--target-candidate-rank-output` and
   `--stage-containment-output` are set for the same query, the snapshot is
   queried once (`717-743`, stashed in `candidate_rank_rows_for_stage`) and the
   stage-containment block consumes it via `match ... Some(rows) => rows, None
   => query...` (`783-794`). The `None` arm preserves the standalone-disabled
   behavior. The `target_local_sequence` derivation (truth_id +
   `leaf_block_rank_local_sequence_offset`, with `checked_add` overflow guard,
   `714-728`) is identical to the stage-containment derivation, so the two
   paths submit the same `$3::bigint[]` argument — reuse is semantically safe,
   not just a coincidence.

5. **Validation gating is complete and symmetric.**
   `--target-candidate-rank-output` requires `--include-recall`
   (`977-981`) and is included in the non-negative
   `leaf_block_rank_local_sequence_offset` guard (`1006-1012`). A rejection unit
   test was added (`4520-4527`) asserting the `requires --include-recall`
   message. Output write `write_target_candidate_rank_jsonl` (`3352-3372`)
   creates parent dirs and emits one `serde_json` object per line with trailing
   `\n` — same well-formed shape as the sibling writers.

6. **Suite wiring is correct.** `SpirePipelineStep.target_candidate_rank_output`
   is `#[serde(default)]` (`suite.rs:462-463`), included in the expected-artifact
   `.chain(...)` (`2579`) so a missing JSONL surfaces as a step failure, and
   emitted via `push_opt_path("--target-candidate-rank-output", ...)`
   (`3104-3108`). Both the expansion assertion (`4768-4772`) and the
   `None`-default test (`4826`) are updated.

## Minor / non-blocking

1. **No end-to-end unit test asserts `TargetCandidateRankRecord` field values.**
   The 22 passing tests cover validation rejection and suite expansion, but
   there is no `from_row`-level assertion analogous to the funnel-record test
   (`4831-4856`) checking that the emitted JSONL fields (e.g. `truth_rank`,
   `selected_by_rerank_prefix`, `approximate_rank`) carry through correctly. The
   mapping is mechanical 1:1 and the snapshot itself is exercised by the
   stage-containment path, so this is low risk — but a small record-shape test
   would lock the column-order contract against future SQL drift. Worth adding
   when the Phase 1 matrix run lands.
2. Stage-containment's `HashMap`-by-ordinal collapse (pre-existing, not this
   packet) means its per-stage view uses one representative placement row per
   truth neighbor; this standalone JSONL is the surface that preserves all
   placements. No action needed — just noting the two outputs are intentionally
   different granularities.
