## Correctness findings (verified against source)

1. **Same approximate frontier as the existing local-scan diagnostic — confirmed.**
   The diff extracts `collect_validated_scan_plan_approx_candidates`
   (`candidates.rs:519-567`) and routes *both*
   `collect_scan_rerank_locality_diagnostics` (the pre-existing local diagnostic)
   and the new `collect_scan_target_candidate_rank_snapshot`
   (`candidates.rs:480-518`) through it. Top-graph and non-top-graph branches are
   preserved verbatim (only `&snapshot`/`&hierarchy` borrows and a `context`
   string for the error message changed). So request claim #1 holds: the
   candidate set observed by the snapshot is the same set the locality diagnostic
   observes, which is the validated scan-plan approximate frontier.

2. **Rerank-prefix membership matches the locality diagnostic's prefix rule.**
   `target_candidate_rank_rows_from_candidates` computes `rerank_prefix_len`
   with the identical `if rerank_width == 0 { len } else { width.min(len) }`
   formula (`candidates.rs:682-686`) used by `rerank_prefix_heap_locality`
   (`candidates.rs:623-627`), and sets `selected_by_rerank_prefix =
   approximate_rank <= rerank_prefix_count` with a 1-based rank
   (`candidates.rs:719`, `735`). This is consistent with `prefix =
   &candidates[..rerank_len]` and depends on the candidate vector being in
   approximate-score order — the same assumption the existing diagnostic already
   relies on. No new assumption introduced.

3. **First-occurrence (best) rank per target is recorded.** Iteration inserts
   into `found_target_ordinals` and skips repeats (`candidates.rs:713-716`), so a
   target_local_sequence that appears at multiple candidate positions (boundary
   replication / dedupe) records its lowest/best rank. Correct semantics for "did
   this truth row reach the candidate frontier, and at what rank."

4. **Missing-reason attribution is now a true stage split, not a lower bound.**
   - Candidate-frontier (`stage_missing_reason_for_candidate_frontier`,
     `spire_pipeline.rs:3094-3110`): returns `contained` iff the candidate-rank
     row is retained; otherwise it first defers to the *block*-rank snapshot for
     `routing_miss` / block-prune reasons, and only then reports
     `nprobe_zero` / `candidate_not_retained` from the candidate snapshot status.
     This correctly distinguishes routing/block loss from candidate non-retention
     — the exact gap packet 002 said "must be closed before any Phase 2/3 policy
     decision."
   - Rerank-frontier (`...for_rerank_frontier`, `spire_pipeline.rs:3112-3127`):
     `contained` iff in rerank prefix; else falls back to the candidate-frontier
     reason if not even retained, and otherwise emits `rerank_width_cap`. Sound.
   - Final (`...for_final`, `spire_pipeline.rs:3129-3145`): now cascades
     block → candidate → rerank → `not_returned_in_topk`. Sound.

5. **`containment_basis` flipped off the lower-bound sentinel.** Stages 4 and 5
   now carry `"target_candidate_rank_snapshot"` instead of
   `"final_hits_lower_bound_until_target_candidate_rank_snapshot"`
   (`spire_pipeline.rs` diff, lines around 2865/2900). This is the precise label
   correction follow-up #1 asked for, and the updated unit test asserts it
   (`candidates.containment_basis == "target_candidate_rank_snapshot"`,
   `rerank.containment_basis == "target_candidate_rank_snapshot"`).

6. **Consumer keying is consistent.** Both `query_leaf_target_block_rank_rows`
   and `query_target_candidate_rank_rows` are passed the *same*
   `target_local_sequences` slice built from `query_truth_ids` + offset, in truth
   order (`spire_pipeline.rs:764-794`), and `from_query` keys the candidate-rank
   rows by `target_ordinal` looked up by `truth_index`
   (`spire_pipeline.rs:2752-2766`), matching the established block-rank
   convention. So the per-truth-row joins across the two snapshots align.

7. **`#[pg_extern]` boundary is well-formed.** `strict` + positivity guard on
   `target_local_sequences` (rejects `<= 0`), the same
   `open_valid_ec_spire_index_guard` + `with_spire_live_index_relation!` pattern
   as the sibling snapshots, and the 21-column `TableIterator` schema matches the
   row struct field-for-field, with the CLI `SELECT` and `From<Row>` reading the
   same 16-column projection in order. The SQL `ORDER BY target_ordinal,
   approximate_rank NULLS LAST, pid, row_index` matches the in-kernel sort, so
   ordering is stable across the SQL/Rust boundary.

   run. Acceptable for a diagnostic checkpoint, but the Phase 1 closeout (packet

   follow-up #2 and the task's Required Evidence, AC1 needs the actual
   `ecaz bench suite` run emitting these rows at 10k/50k/100k (AWS 1M before any
   product claim). This packet is the plumbing that makes that run *correct*; it
   is not the evidence. Packet 007 (`007-phase1-local-containment`) appears to be
   that run — it should explicitly cite this commit as the diagnostic source.

   (`spire_pipeline.rs` ~2362) still matches only `"block_ranked"`; it is fed by
   the target *assignment* snapshot, not this candidate-rank snapshot, so it is
   not wrong today. Worth a glance if it is ever pointed at the new snapshot.
