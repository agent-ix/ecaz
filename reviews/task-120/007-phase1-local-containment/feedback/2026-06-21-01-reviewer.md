## The problem: 3 of 6 funnel stages are non-functional (AC1 gap)

AC1 requires evidence that "identifies where SPIRE loses or retains exact truth
rows," and the task explicitly enumerates the stages it wants attributed:
topology route set, selected leaves, selected leaf blocks, local candidate
frontier, exact/source rerank frontier, final top-k
(`plan/tasks/120-...md:46-55`, `:186-187`).

In `pipeline-{scale}-stage-containment.jsonl` the three *upstream* stages —
exactly the ones the Task 81-84 history says dominate the gap — are derived from
the broken target-block-rank snapshot and report **0% containment /
`routing_miss=2000` for every scale × nprobe** (`pipeline-stage-containment-summary.txt`
stage_ordinal 1-3 on every block). Per-record `containment_basis` confirms the
mechanism:

```
topology_route_set     -> target_block_rank_routed_leaf_lookup   (all 2000 not_found)
selected_leaves        -> target_block_rank_routed_leaf_lookup   (all 2000 not_found)
selected_leaf_blocks   -> target_block_rank_selected_by_global_cap(all 2000 not_found)
local_candidate_frontier -> target_candidate_rank_snapshot       (REAL)
exact_source_rerank_frontier -> target_candidate_rank_snapshot   (REAL)
final_top_k            -> query_metric_returned_ids              (REAL)
```

This is the **same** defect the request already flags for the standalone
target-block-rank snapshot (`request.md:43-48`,
`pipeline-target-block-rank-summary.txt` — all 12 cells
`not_found_in_routed_leaves 2000`). The request frames that as only a
"route-vs-block attribution" caveat. But because stages 1-3 of the *headline
stage-containment funnel* inherit that same broken basis, the funnel does not
actually attribute loss across route set vs selected leaves vs selected blocks
at all. The proof that retained truth rows DO enter the candidate frontier
(stage 4, 1841/2000 at 100k/32) directly contradicts the stage-1-3 claim that
2000/2000 are routing misses — so stages 1-3 are demonstrably wrong, not merely
coarse.

Net: this packet proves the loss happens **at or before the candidate frontier
and not in rerank**, and that retained rows rank well. It does **not** localize
the pre-frontier loss to routing vs leaf-selection vs block-pruning — which is
the specific Phase-1 question seeded by Tasks 81-84 (`:66-67`). The request's
own recommendation ("a post-frontier exact/source rerank policy alone is not
supported") is sound and supported; but its forward guidance that Phase 4
route-set work needs the block attribution fixed first understates that the
*current* stage funnel cannot even separate routing loss from leaf/block loss
today.
