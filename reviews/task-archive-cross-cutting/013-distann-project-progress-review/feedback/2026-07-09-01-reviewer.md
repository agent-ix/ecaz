# DistANN/SPIRE project progress review: architecture, optimization, and code structure

## Verdict

**Changes requested before SPIRE is treated as product-ready or promoted from
research/opt-in.** The storage/epoch/placement architecture and operational
control plane are substantially more mature than the ANN quality/economics, and
the project has done unusually good work preserving negative benchmark results.
However, the current PostgreSQL planner integration has two correctness/security
holes that are independent of the Task 146 Pareto result:

1. the vector `CustomScan` claims ORDER BY/LIMIT semantics for query shapes it
   does not execute faithfully; and
2. the transparent UPDATE/DELETE plan replacement drops row-security quals.

Those should be fixed or failed closed before further product claims. The
running Task 146 measurements remain useful for the algorithmic decision, but
cannot make these semantic issues safe.

## Scope

This is a project-level review of the full DistANN/SPIRE program, not a review
of Task 146 alone. It covers the current architecture and implementation across
build, immutable epoch publication, placement, scan/routing, remote execution,
CustomScan/DML integration, storage, maintenance, operator CLI, and benchmark
infrastructure. I used the full task index and relevant design/ADR set for orientation,
then deep-read the source and the milestone/reversal evidence across the
program, including Tasks 30, 85, 120, 121, 123, 131, 138, and 141-146. This is
intentionally not a packet-by-packet restatement of every historical review.

The review is based on committed HEAD `de99f5ec7` plus committed review and
benchmark packets. The untracked Task 146 packet 007, including the second 50k
run reported as still running, is deliberately excluded from findings and
numbers. Task 146 and its outstanding multi-instance matrix appear here only as
the current benchmark frontier, not as the owner or boundary of this review.

## Blocking findings

### P0 — transparent UPDATE/DELETE can bypass row-level security

The DML planner hook derives its primitive request from the rewritten `Query`,
runs the normal planner, and then replaces `PlannedStmt.planTree`
(`src/am/ec_spire/dml_frontdoor/mod.rs:705-724,745-763`). The replacement node
has no target list, qual, relation scan, or child plan
(`src/am/ec_spire/custom_scan/planner.rs:353-402`). The classifier rejects
joins, subqueries, RETURNING, and unsupported predicates, but it does not reject
`Query.hasRowSecurity` or non-empty target-RTE `securityQuals`
(`src/am/ec_spire/dml_frontdoor/mod.rs:323-329,1440-1455`). There are no SPIRE
RLS/security-qual guards or tests in the current tree.

PostgreSQL implements RLS by injecting policy expressions as security quals.
Those expressions are planned into the original scan tree; they are not
enforced merely because `PlannedStmt.relationOids` survives. The installed PG18
headers explicitly describe `relationOids` as plan dependencies, permission
metadata as `permInfos`, and `securityQuals` as expressions that must be tested
before returning a row (`artifacts/postgres-rls-plan-metadata-audit.log`). The
replacement therefore preserves ordinary statement metadata while discarding
the expressions that decide whether this user may update/delete this row. The
remote primitive then routes the PK mutation without executing the discarded
policy.

This also corrects the assertion in
`reviews/task-30/723-30803-spire-customscan-pivot-adrs/feedback/2026-05-11-004-reviewer.md:114-116`:
`relationOids` is dependency metadata, not an RLS execution surface. Normal ACL
permission metadata may survive the plan replacement; row-policy expressions do
not.

Required response:

- Immediately fail closed for transparent UPDATE/DELETE when
  `Query.hasRowSecurity` is true or the target RTE has security quals. Keep that
  restriction in ADR-069/FR-059 until SPIRE has an explicit distributed
  authorization model.
- Add PG18 integration coverage under a non-owner role for `ENABLE ROW LEVEL
  SECURITY` and `FORCE ROW LEVEL SECURITY`, covering allowed and denied PK
  UPDATE/DELETE. Assert both row count and remote heap contents.
- Audit SELECT and INSERT separately; do not infer their safety from the DML
  test. Remote credentials and coordinator-user identity need an explicit
  contract.

### P0 — vector CustomScan accepts ORDER/FILTER shapes it cannot preserve

Path eligibility currently checks only that global sort pathkeys exist, LIMIT
is finite, and one target-list expression is a binary `OpExpr` containing a
relation `Var` and a float4-array Const/Param
(`src/am/ec_spire/custom_scan/cost_helpers.rs:41-49,52-99,211-243`). It does not
validate the operator OID/opfamily/strategy, indexed attribute, sort direction,
NULL ordering, base restrictions, RLS quals, or whole-query join shape.

The resulting path advertises *all* of `root.sort_pathkeys` as satisfied and
carries base restrictions as plan quals
(`src/am/ec_spire/custom_scan/planner.rs:119-154,235-265,433-466`). At execution,
SPIRE requests exactly `LIMIT` outputs from the remote production scan
(`src/am/ec_spire/custom_scan/dml.rs:513-541`) and only afterward calls
PostgreSQL `ExecScan`, where plan quals are evaluated
(`src/am/ec_spire/custom_scan/begin_exec.rs:319-330,607-643`). That reverses the
required semantics for a query such as:

```sql
SELECT id
FROM items
WHERE tenant_id = 7
ORDER BY embedding <#> $1
LIMIT 10;
```

SQL requires the nearest ten *eligible* rows. This path obtains the nearest ten
unfiltered rows and then removes ineligible rows, with no refill. It can return
too few rows or a different top-k. The remote projection builder also derives
requested columns from the plan target list but not `plan.qual`
(`src/am/ec_spire/custom_scan/begin_exec.rs:160-217`), so a column used only by
a qual may be absent from a remote tuple and materialize as NULL. Separately, a
DESC or alternate binary operator can be accepted while the path still returns
SPIRE's nearest-neighbor ordering and claims the user's pathkeys.

Required response:

- Make path generation fail closed to the exact supported bare query contract:
  the correct distance operator/opclass and indexed attribute, ascending
  semantics, a supported Const/Param type, no unsupported joins, and no
  unpushed restrictions/security quals.
- If filtered ANN is to be supported, execute the filter at the data-owning
  node and define refill/termination semantics; fixed coordinator overfetch is
  not correctness-preserving for arbitrary selectivity. Include all qual Vars
  in the typed payload contract.
- Add PG18 regressions for DESC, an unrelated binary operator, a WHERE clause
  that excludes the nearest rows, a qual-only projected column, a join, and RLS.
  Assert both plan choice and exact output against a forced non-SPIRE reference.

## High-priority architecture and optimization findings

### P1 — idle pooled connections consume “active dispatch” capacity across backends

`SpireRemotePooledConnection` owns the advisory-lock governance permit
(`src/am/ec_spire/coordinator/remote_candidates/dispatch.rs:546-559`). A
successful read returns that connection to a backend-local idle pool
(`dispatch.rs:659-670,811-1001`), so the permit lives until eviction or backend
exit. The locks themselves are the global/per-node slots
(`src/am/ec_spire/coordinator/remote_candidates/governance.rs:69-91,162-218`).
Yet the GUC contract calls these maximum *concurrent dispatches across
PostgreSQL backends* (`src/am/ec_spire/options/mod.rs:1071-1088`).

With either cap enabled, backend A can warm enough idle sockets to retain all
slots. Backend B then receives `remote_executor_overload` while no dispatch is
active. Packet 142/011 explicitly makes this trade, but it changes the public
meaning from active work to retained connection capacity. Defaults are zero,
so current single-session benchmarks do not expose it.

Required response:

- Scope the permit to active candidate/heap work, or replace the SPI advisory
  lock loop with a shared-memory counter/semaphore that is cheap enough to
  acquire once per fanout operation.
- If idle connection capacity also needs a global cap, give it a separate name,
  metric, and failure mode.
- Before accepting the outstanding multi-instance/concurrency work, add a
  two-coordinator-backend test: A warms and idles its pool; B must still acquire
  an active-dispatch slot. Benchmark with caps both disabled and enabled.

### P1 — the cache still performs O(hierarchy) work per query, and planning is O(placements)

The planner eligibility check reads and decodes the complete placement
directory, then iterates every entry and builds node sets for each eligible
base-relation planning callback
(`src/am/ec_spire/custom_scan/planner.rs:1-74,77-100,433-466`). This is outside
the Task 142 execution caches and makes planning cost grow with partition count.

The execution cache has a related problem: on every hit,
`load_cached_coordinator_routing_hierarchy` clones the entire decoded hierarchy;
on a miss it clones once into the cache
(`src/am/ec_spire/scan/routing.rs:154-186`). The cloned value owns the root
object, all internal centroid objects and maps, leaf counts, and optional top
graph (`src/am/ec_spire/scan/types.rs:62-75`). The `leaf_count` timer starts
before that clone and then recursively recounts leaves
(`src/am/ec_spire/scan/routing.rs:304-354`).

The committed Task 142 release profile already shows the scaling signal:
50k/nlists=1024 has roughly 0.62-0.65 ms leaf-count p50 and 2.12-2.14 ms route
selection, versus about 0.08 ms and 0.26 ms for nlists=128
(`reviews/task-142/016-post-cache-release-ab/artifacts/manifest.md:140-159`).
Task 142 produced a large real win by removing repeated loads, but this remaining
copy/recount path will become a backend-memory and CPU limit well before the
billion-scale target.

Required response:

- Cache an immutable, epoch-keyed runtime snapshot and borrow/share it per
  query (`Rc` is sufficient inside one PostgreSQL backend; `Arc` if a future
  executor crosses threads). Store leaf count and routing summaries in it.
- Publish or cache an O(1) planner eligibility summary keyed by index OID and
  active epoch; invalidate it on relcache/epoch changes. Do not decode the full
  directory during every planning callback.
- Add a planner-time, warm-query CPU, and per-backend memory scaling lane over
  increasing nlists/top-graph sizes. Task 146 end-to-end latency alone will not
  isolate this failure mode.

### P1 — scan options are a stringly typed, nine-round-trip remote side channel

Each remote candidate query constructs eight scan GUC name/value pairs and
applies them sequentially with one `SELECT set_config` round trip apiece
(`src/am/ec_spire/coordinator/remote_candidates/dispatch.rs:382-449,1491-1531`).
The heap phase sends `rerank_width` in a ninth round trip
(`dispatch.rs:1739-1749`). This repeats per data node and query even on pooled,
prepared connections.

Besides fixed latency, this creates two execution contracts: local behavior is
read from coordinator process state, while remote behavior depends on a
hand-maintained list of string names. The Task 141-145 history repeatedly had to
distinguish “implemented locally” from “actually engaged remotely”; this
transport shape makes omissions easy and type/version validation impossible.

Required response:

- Introduce one versioned `SpireRemoteScanOptions` contract shared by local and
  remote planning. Pass it as a typed endpoint argument (preferred), or at least
  apply all values in one statement while migrating.
- Include the effective options/fingerprint in remote diagnostics and reject a
  protocol version that cannot represent a requested option.
- Add a contract test that toggles every option and proves the effective local
  and remote request objects are identical. Keep engagement counters as the
  acceptance surface.

## Code structure finding

### P2 — file separation currently hides a set of flat mega-modules

The tree looks decomposed on disk, but 106 `include!` statements flatten most
SPIRE fragments into a few Rust modules. For example, coordinator, scan,
storage, update, build, custom scan, and remote-candidate fragments all share
their parent's private namespace (`src/am/ec_spire/mod.rs:219-229`,
`scan.rs:50-57`, `storage.rs:21-33`, `custom_scan/mod.rs:215-222`, and
`coordinator/remote_candidates/mod.rs:1-24`). This provides neither real module
privacy nor dependency direction and permits fragments to reach across the
entire subsystem.

The static audit in `artifacts/source-structure-audit.log` counts about 66.4k
production SPIRE Rust lines. Individual production files are already 2k-4.2k
lines; `src/lib.rs` is 20.4k lines with 246 `#[pg_extern]` entries, while each of
the suite and SPIRE-pipeline CLI files is over 7.2k lines. This has moved away
from ADR-049's “cleanly modular internal structure” goal and raises the cost of
checking planner/executor/protocol invariants such as the P0 findings above.

Recommended response (incremental, not a rewrite):

- Convert fragments to real modules around five seams first: published epoch
  snapshot, routing selection, candidate scan, remote protocol, and PostgreSQL
  planner/executor integration.
- Make dependencies point inward toward typed domain contracts; keep SQL/pgrx
  wrappers and CLI formatting at the edges.
- Replace repeated local/remote parameter lists with typed request/response
  structs before doing cosmetic file splitting.
- Generate or centralize repetitive SQL wrapper/row-codec glue where practical.
  Preserve the current on-disk format during this work.

## Architecture and optimization assessment

The core architectural choices are sound and worth keeping:

- immutable partition objects plus active-epoch publication give the system a
  coherent read/version boundary;
- explicit placement state, endpoint identity, strict/degraded behavior,
  cancellation, typed tuple payloads, and bounded 2PC scope are good production
  primitives;
- the CustomScan pivot avoided mirroring remote rows into a coordinator heap;
  and
- the review workflow has correctly retained negative results instead of
  promoting predicted wins.

Operationally, the control plane is now credible. Task 30's AWS closeout showed
pooling eliminate repeated socket opens and reduce p50/p95 without changing
recall. Task 142 then removed substantial repeated routing/manifest/identity
work; its release A/B improved nlists=1024 p50 by roughly 39-45%. Those are real
systems wins.

Algorithmically, SPIRE is not yet on a product Pareto frontier. The accepted
Task 85 1M comparison remains decisive: SPIRE's opt-in point was 0.9876 recall
at 222.692 ms and 872.1 MiB, versus IVF/RaBitQ at 0.9864/34.6 ms/298.0 MiB or
0.9936/66.2 ms/298.0 MiB
(`reviews/task-85/033-comparator-product-policy-gate/request.md:6-25`). Task 120
localized the missed truth rows at or before routed-leaf candidate selection,
not rerank. Tasks 144 and 145 correctly declined to promote closure, ratio,
block, or bound-pruning ideas that did not win or did not engage. This argues
for continuing to spend algorithm work on route quality/selectivity and
hierarchy representation, not another round of heap/rerank micro-tuning.

The metric history also justifies the current caution. Task 138 showed old
multi-instance duplicate-tolerant recall near 1.0 could correspond to only
0.4146-0.5195 distinct recall
(`reviews/task-138/001-distinct-recall-rescore/request.md:36-55`). Only
post-fix, distinct-recall results should support a distributed quality claim.

Task 146's committed anchor packet is well formed: IVF reaches 0.9975 at 33.6
ms on 50k and 0.9980 at 37.6 ms on 100k, while the measured HNSW sweeps are
faster but below the preregistered recall gate
(`reviews/task-146/006-anchor-results/request.md:24-38`). No SPIRE S1-S6 verdict
is available yet. Completion still requires the committed single-instance and
multi-instance 10k/50k/100k matrices, including distinct recall, latency,
storage, row-instance scan fraction, and engagement counters. The running
second 50k pass is work in progress, not evidence until its packet is finalized.

One accepted but important architecture boundary should remain prominent in
product documentation: v1 remote reads use independent remote PostgreSQL
statements rather than one exported cross-shard snapshot, and remote tuples
cannot receive normal EPQ revalidation
(`spec/adr/ADR-068-spire-distributed-table-topology.md:129-147`). That is a
documented v1 consistency model, not a new defect, but it materially limits the
queries/applications for which “transparent distributed table” is accurate.

## Recommended order of work

1. Fail closed and add PG18 regressions for the two P0 planner/RLS issues.
2. Repair active-dispatch governance semantics before using multi-instance or
   concurrent-client evidence as an overload/readiness claim.
3. Consolidate scan options into a typed, versioned remote request and require
   nonzero engagement evidence for every experimental gate.
4. Finish and review Task 146's preregistered single-instance and 3-worker
   matrices; do not reinterpret incomplete/local-only rows as a verdict.
5. Replace per-query hierarchy cloning/recounting and planner directory scans,
   then add explicit nlists/memory/planning scaling evidence.
6. Modularize along the typed seams above as those fixes land, without changing
   the on-disk format.
