## P0 — correctness, new

### P0-A: Vector CustomScan is generated for base rels inside join queries; top-k truncation before the join silently drops rows

`src/am/ec_spire/custom_scan/planner.rs:433-467`,
`src/am/ec_spire/custom_scan/cost_helpers.rs:36-50`. Eligibility gates only on
`RELOPT_BASEREL`/`RTE_RELATION`, `sort_pathkeys != NULL`, `limit_tuples >= 0`,
and the ORDER BY operand shape. Nothing requires the rel to be the query's
*only* base relation. For
`SELECT ... FROM t JOIN u ON ... ORDER BY t.emb <#> $1 LIMIT 5`, rel `t`
passes every check, the path is added with `top_k = 5`
(`planner.rs:221,250-261`), and the executor fetches exactly 5 remote rows
(`custom_scan/dml.rs:513-542`) *before* the join runs. Join partners of rows
ranked 6+ are silently missing — wrong results, independent of the known
WHERE-after-LIMIT P0. Fix: require
`bms_equal(rel->relids, root->all_baserels)` (single-baserel query) before
treating `limit_tuples` as a pushable top-k.

### P0-B: PARAM_EXEC query vectors are evaluated in BeginCustomScan before InitPlans exist — SQL-reachable backend crash

`cost_helpers.rs:234-243` accepts any `T_Param` with
`paramtype == FLOAT4ARRAYOID` without checking `paramkind` (verified: the
match arm tests only `paramtype`). `begin_exec.rs:84-110` evaluates it eagerly
in `BeginCustomScan`. For
`SELECT * FROM t ORDER BY emb <#> (SELECT qv FROM q LIMIT 1) LIMIT 5`, the
sublink becomes an InitPlan whose PARAM_EXEC slot is attached to the *top*
plan node; executor init recurses into children (running `BeginCustomScan`)
before that node's initPlan list is initialized, so `ParamExecData.execPlan`
is NULL and the datum is 0 with `isnull = false`.
`Vec::<f32>::from_polymorphic_datum(0, false, ...)` (`begin_exec.rs:101`) then
dereferences a null varlena → segfault, or (if mapped) a garbage query vector
→ silently wrong results. Fix: accept only `paramkind == PARAM_EXTERN` in
`is_query_value`; better, defer Param extraction to first `ExecScan` (also
fixes P1-J and P2 rescan staleness below).

### P0-C: Epoch cleanup's three safety legs are all broken — physical deletion can destroy epochs still being read

Cleanup (`index_epoch_cleanup_run`,
`coordinator/snapshots.rs:1016-1092` + `delete_object_tuples_no_compact`) is
the only destructive path, and each of its protections fails independently:

1. **The pin counter is dead code.** `SpireEpochManifest.active_query_count`
   gates `cleanup_eligible_at` (`meta/epoch.rs:84-92`) but *no code path ever
   increments it* — every producer writes 0 (`insert.rs:247`,
   `vacuum/mod.rs:483,632`, build drafts) and
   `retired_epoch_manifest_from` (`build/publish.rs:505`) resets it. Scans run
   under AccessShareLock (no conflict with the ShareUpdateExclusive publish
   lock) with no epoch pin; protection is purely the 10-minute wall clock +
   2 retained retired epochs (`meta.rs:11,13`). Every `aminsert` publishes an
   epoch, so churn is fast. A cursor/analytics query older than the window has
   its tuples line-pointer-deleted underneath it → `"points at an unused
   slot"` errors, or decode of a *reused* slot.
2. **Chained manifest blobs of retained epochs are unprotected.**
   `collect_physical_cleanup_candidates` (`snapshots.rs:951-978`) protects
   tuple-by-tuple via the four manifest decodes; chain-meta and segment tuples
   written by `append_manifest_blob_tuple` (`page.rs:331-372`) decode as none
   of them. Only the *active* epoch's chains are protected via the
   root-control TIDs. Any retained non-active epoch whose placement directory
   or object manifest chains (normal at a few hundred leaves, i.e. 100k+ rows)
   loses its chained manifests — and since its directory never lands in
   `protected_directories`, **every object tuple it references also loses
   protection** and is deleted while the epoch is still supposed to be
   readable.
3. **"Latest manifest by max TID" is unsound after any cleanup.**
   `latest_epoch_manifests` (`snapshots.rs:838-863`, duplicated at
   `diagnostics.rs:437-460`) resolves Published-vs-Retired by picking the max
   `(block, offset)`. But `append_object_tuple` consults the FSM
   (`page.rs:286-301`) and `PageAddItemExtended` reuses LP_UNUSED slots, so
   after cleanup frees space, the retired copy of a manifest can land at a
   *lower* TID than the original Published copy → the epoch is seen as
   Published forever (storage leak, phantom published epoch, cleanup planning
   confusion).

Fix: implement real pinning (per-backend epoch pins in shared memory, or a
lock that conflicts with scans during physical deletion); protect whole blob
chains by decoding assembled payloads; and make state resolution
order-insensitive (Retired supersedes Published for the same epoch — states
only move forward) or rewrite manifests in place
(`rewrite_object_tuple_same_len` exists).

### P0-D: VACUUM does not remove boundary-replica index entries for dead heap TIDs — wrong query results after TID reuse

`vacuum/mod.rs:234-246` (`run_bulkdelete`) emits delete-deltas only for
`is_visible_primary_assignment` rows; a boundary replica of the same vec_id
lives in a *different* leaf (`storage/helpers.rs:38-52`) and gets no delta.
Scan-side filtering uses only the deltas of the *probed* leaves
(`scan/candidates.rs:3708-3740`). With `boundary_replica_count > 0` (the
standard replicated-SPIRE configuration): DELETE row X (primary in leaf A,
replica in leaf B) → vacuum records the delta on A only → heap TID pruned and
reused by unrelated row Y → a query probing B but not A returns Y ranked by
X's stale quantized vector. This violates the `ambulkdelete` contract (every
index entry for a dead TID must be removed) and there is no value recheck in
ANN order-by scans to catch it. Fix: iterate all *scored* assignments
(primary + replica) in `run_bulkdelete` and emit a delete-delta per base_pid
holding an assignment for the dead TID.

## P1 — high priority

### Distributed write path / 2PC

- **P1-A: UPDATE has no 2PC.** Insert and delete wrap the remote mutation in
  `BEGIN … PREPARE TRANSACTION` with intent rows and xact callbacks
  (`write_payload.rs:532`, `:777-835`); update runs a bare autocommit
  `client.query_one(remote_sql)` (`write_payload.rs:686-743`, verified
  `:723`) and reports `remote_update_applied`. A local abort after the remote
  update commits leaves permanent silent divergence, invisible to the reaper
  (no gid ever existed). Route update through the same prepare/intent
  machinery.
- **P1-B: COMMIT/ROLLBACK PREPARED failures are swallowed with zero logging,
  and the reaper then skips them forever.**
  `resolve.rs:361-383` — connect failure → bare `return`; commit failure →
  `let _ = client.batch_execute(...)`. The reaper classifies the orphan as
  `commit_local` and skips it with "operator must resolve manually"
  (`resolve.rs:298-302`) — but the operator was never told. A prepared xact
  left on a data node pins xmin and holds locks indefinitely. Minimum fix:
  `pgrx::warning!` with node_id/gid on every swallowed failure; better, a
  `commit_remote_pending` intent state the reaper resolves (commit_local means
  the global decision was commit).
- **P1-C: Prepared-transaction GID collision.** Gid =
  `ec_spire_insert_{index_oid}_{node_id}_{served_epoch}_{top_xid}`
  (`resolve.rs:5-20`) — no per-statement discriminator. Two writes to the same
  node in one top transaction (batch insert of ≥2 rows placed on one node;
  insert+delete at the same epoch) collide: the second PREPARE fails, and the
  intent upsert (`ON CONFLICT (gid) DO UPDATE`, `resolve.rs:111-117`) resets
  the first xact's intent state first, corrupting the reaper's record. Add a
  per-backend sequence to the gid and make the intent insert error on
  conflict.
- **P1-D: Ambiguous PREPARE failure → no-op ROLLBACK → in-doubt xact leaks
  until someone manually runs the reaper** (`dispatch.rs:2586-2627`); on a
  connection-loss-category error also attempt `ROLLBACK PREPARED <gid>` over
  a fresh connection, and wire the reaper to run periodically.

### Cancellation / timeouts (directly relevant to multi-instance testing)

- **P1-E: All sync-client remote paths are uncancellable and unbounded at
  default settings.** `remote_search_connect_timeout_ms` and
  `remote_search_statement_timeout_ms` default to 0 (`options/mod.rs:59-64`),
  and the sync `postgres::Client` paths (update/delete/select, fingerprint
  guards, reaper, and — worst — the commit/abort **xact callbacks** at
  `resolve.rs:372`) have no interrupt poll at all. A hung data node during
  `CommitTransaction` hangs the coordinator backend beyond
  `pg_cancel_backend`. Fix: interrupt-poll wrapper (or async transport) for
  sync paths + non-zero default timeouts, especially anything reachable from
  xact callbacks.
- **P1-F: `pg_terminate_backend`/fast shutdown not observed.** The 5 ms local
  cancel poll checks `InterruptPending && QueryCancelPending` only
  (`dispatch.rs:2737-2740`); `ProcDiePending` never fires it, so fast shutdown
  hangs on any in-flight remote fanout. Also read `ProcDiePending`.
- **P1-G: No interrupt checks in build/maintenance/vacuum loops.** Zero
  `CHECK_FOR_INTERRUPTS`/`vacuum_delay_point` in `ec_spire` + `am/common`
  (grep-verified by two agents independently). Post-scan build phases
  (k-means, assignment, boundary closure), `run_bulkdelete`, physical cleanup
  scans, and the split path's heap-fetch+k-means are uninterruptible for
  minutes at 100k–1m scale, and vacuum ignores cost-based delay. Plus a
  potential infinite loop: the V5 segment-chain walker
  (`relation_store.rs:642-673`, copy at `local_store.rs:608-635`) loops until
  `row_end` reaches a target; a corrupt cyclic chain never terminates — bound
  by `meta.segment_count`.

### WAL / storage

- **P1-H: Use-after-free — page image read after `GenericXLogFinish`.**
  `page.rs:614-617` (verified: `wal_txn.finish()` at :615, then
  `registered.record_current_free_space()` at :617 reads
  `PageGetFreeSpace(self.page)` on the image pointer that finish just freed),
  also `:660-661` and `:704-705`. Under `MEMORY_CONTEXT_CHECKING` the chunk is
  clobbered → garbage FSM entries; in release, stale reads today, arbitrary
  on future palloc reuse. Fix: record free space from the real buffer page
  while the lock guard is still held, or before finish. Root cause is
  `SpireRegisteredPage` escaping the typed `RegisteredBufferPage` lifetimes
  via raw `page_ptr()` (`page.rs:78-171`) — extend the typed wrapper and
  delete the escape hatch.
- **P1-I: Unvalidated on-disk counts feed `Vec::with_capacity` before any
  length check.** `leaf_v1.rs:50`, `routing_delta.rs:455`,
  `top_graph.rs:116`, `relation_store.rs:591,744`, `local_store.rs:560,703`,
  `page.rs:888`. One flipped bit in a stored count turns "decode error" into
  a multi-GB allocation → OOM/abort during a scan. The routing-object /
  placement-directory / store-config decoders already do the
  `expected_len == input.len()` check first — apply the same hardening
  (bound count by `remaining_input / min_entry_bytes`).

### Planner/executor integration (beyond the packet 013 P0s)

- **P1-J: DML plan replacement bypasses the entire ModifyTable machinery.**
  The classifier (`dml_frontdoor/mod.rs:1979-2042`) checks
  join/subquery/RETURNING/PK-shape but not `relhastriggers` (row/statement
  triggers silently never fire), inbound/outbound FKs (ON DELETE
  CASCADE/RESTRICT never enforced), `relkind` (partitioned parents match and
  get whole-plan-replaced), or inheritance. This is the missing sibling set to
  packet 013's RLS gap — extend the fail-closed classifier.
- **P1-K: Fail-closed planner ERROR fires for ordinary read-only SELECTs.**
  `dml_frontdoor/mod.rs:789-815,2012-2035`: `WHERE id > 100` or
  `WHERE id = 5 AND status = 'x'` on a distributed table errors with
  FEATURE_NOT_SUPPORTED at plan time, while `SELECT *` with no WHERE passes
  through and reads the (empty/stale) coordinator heap. Range/compound reads
  error; full-table reads silently return wrong local data. Pick one contract
  and apply it uniformly.
- **P1-L: Extension catalogs resolved via `RelnameGetRelid` (search_path).**
  `custom_scan/planner.rs:508-566`: any user can shadow
  `ec_spire_placement(_by_index_oid)` earlier in their search_path; the
  planner hook then index-scans the user's relation with a hard-coded
  oid-equality scankey — type confusion / attacker-influenced path
  eligibility, plus a physical index scan per set_rel_pathlist call. Resolve
  schema-qualified in the extension namespace and verify the index key type.
- **P1-M: Rust-heap leak on error abort.** Exec state is `palloc0` +
  `ptr::write` of a struct full of system-allocator `Vec`/`String`s;
  `ptr::drop_in_place` runs only in `EndCustomScan`
  (`begin_exec.rs:5-20,337-352`). Any elog(ERROR)/cancel mid-execution leaks
  the Rust buffers (including full remote payload rows in `state.outputs`)
  permanently. Register a `MemoryContextCallback` for the drop and make
  EndCustomScan idempotent.
- **P1-N: DML PK-select CustomPath uses startup/total cost = −1.0**
  (`planner.rs:175-177`): unconditional plan hijack ignoring `enable_*` GUCs,
  negative costs propagate into parent cost sums and EXPLAIN. Use
  `disabled_nodes`-style must-win semantics or a small positive cost.

### Coordinator control plane

- **P1-O: Same-epoch manifest rewrites race with publishers and are invisible
  to caches.** The placement-node/consistency-mode rewrite surfaces
  (`coordinator/debug.rs:43-159` — operator-facing, not test-gated) and
  active-epoch rematerialization (`materialization.rs:97-103`) run under
  RowExclusiveLock, which does not conflict with the ShareUpdateExclusive
  publish lock → lost-update on root control (can resurrect a retired epoch
  and stale allocator cursors → pid/vec_id reuse). And both thread-local
  caches (`ACTIVE_EPOCH_ANCHOR_CACHE` `snapshots.rs:214-249`,
  `COORDINATOR_FANOUT_MANIFEST_CACHE` `hierarchy_snapshots.rs:356-402`) key on
  `(relid, epoch)` and assume immutability, so a node marked unavailable/moved
  keeps receiving strict-mode dispatches from every backend with a warm cache.
  This matters directly for the planned multi-instance tests. Fix: take the
  publish lock in all root-control writers; forbid same-epoch republication or
  add a manifest_generation to root_control and cache keys.
- **P1-P: Compaction silently drops all boundary replicas from compacted
  leaves.** `publish_compacted_delta_epoch_if_needed`
  (`vacuum/mod.rs:356-497`) rebuilds leaves from
  `is_visible_primary_assignment` rows only — a plain VACUUM after a few
  inserts strips replicas from every leaf that had a delta → silent recall
  regression and broken replica-identity invariants. Collect with
  `is_visible_scored_assignment`.

### Hot-path performance (extends packet 013's cache finding; A/B bench required per closeout rules before/after any fix)

- **P1-Q: Storage-node scan prep loads and validates the full routing
  hierarchy twice per query.**
  `scan/candidates.rs:555-595` calls `count_snapshot_recursive_leaf_pids`
  (full `from_snapshot` validation + full hierarchy decode) solely for
  `leaf_count`, then candidate collection repeats both
  (`candidates.rs:494-495` / `snapshot.rs:278-279`). The diagnostics
  collectors (`candidates.rs:597-626`) already show the load-once shape.
- **P1-R: Delta discovery is an O(all objects) header-read sweep per scan**
  (`snapshot.rs:844-867`, called at `:402`), even on delta-free indexes — the
  third full-manifest header sweep per top-graph query. Record object kind in
  the manifest/epoch snapshot instead.
- **P1-S: Innermost scoring loop allocates per row.** `min_ip_to_keep` →
  `peek_live_worst_deduped` clones a full candidate including its
  `Vec<u8>` vec_id just to read `.score` (`candidates.rs:3968-3994,
  4112-4124`), per scanned row in the default dedupe config; `SpireVecId`
  itself is a heap `Vec<u8>` allocated per materialized row and re-cloned
  into heap+map on accept (`storage/vec_id.rs:336-371`,
  `candidates.rs:4063-4090`) — tens of thousands of small allocs per query.
  Add a non-cloning score peek and an inline fixed-size vec_id key.
- **P1-T: Recursive descent clones entire routing objects (full centroid
  matrices) per beam parent per level**
  (`routing.rs:628-631,1397-1401,1561-1570,1070-1073`) — several MB of memcpy
  per query at realistic fanout/dims; borrow from the loaded hierarchy
  instead.
- **P1-U: Per-row INSERT publishes an O(partitions) epoch and nothing
  reclaims automatically.** Each `aminsert` re-encodes and appends the entire
  placement directory + object manifest (+ retired copy) under the publish
  lock (`insert.rs:111-264`, `update/delta.rs:43-62`); physical reclamation
  exists only in the manual `index_epoch_cleanup_run` — insert-heavy
  workloads grow the index monotonically and serialize all writes. Hook
  cleanup into `amvacuumcleanup` (it already holds the publish lock) and move
  toward delta-manifest publication.
- **P1-V: Build memory is O(corpus × dims) with 2–3× duplication**
  (`build/types.rs:31-46`, `drafts.rs:401-402` — the code even has a
  `draft_input_clone_ms` timer for the second full clone;
  `recursive.rs:259-261,396-408`). ~9 GB+ peak at 1m×768-d. Pass
  slices/indices; consider spilling.

## P2 — moderate (condensed)

- **Rescan ignores `chgParam`** — stale query vector/PK re-used on rescan
  (`begin_exec.rs:503-536`); `FOR UPDATE`/rowMarks not excluded and EPQ
  recheck blindly returns true (`begin_exec.rs:689-701`); `BeginCustomScan`
  ignores `EXEC_FLAG_EXPLAIN_ONLY` (catalog lookups + Param eval during plain
  EXPLAIN); per-tuple varlena datums allocated in the per-query context
  instead of `ecxt_per_tuple_memory` (`tuple_payload.rs:108-138,260-294`);
  SELECT projected-column derivation maps `resno` positionally onto attnums
  (`dml_frontdoor/mod.rs:2702-2736`); UPDATE SET-expr shape validated only at
  execution (`dml.rs:384-387`).
- **Remote payload trusts remote type OIDs** — user-defined types (≥16384)
  decode against whatever the coordinator has at that OID
  (`payload_limits.rs:129-143`); reject or name-verify. **Remote write SQL is
  string-interpolated** (`quote_sql_literal` doubles quotes only — unsafe if a
  data node runs `standard_conforming_strings=off`) and executed via
  multi-statement `batch_execute` (`write_payload.rs:1-117`,
  `dispatch.rs:2527`); use parameters like the read path does.
- **Pool has no stale-connection detection or key-generation eviction** —
  first query after a remote restart fails (no single safe retry), and
  stale-key zombie entries linger holding governance permits
  (`dispatch.rs:634-670,1299-1400`) — extends packet 013's permit finding.
  **Governance permits release via SPI inside `Drop`** — during
  error-unwind that SPI call runs in an aborted transaction (panic-in-unwind
  → backend PANIC risk), and unlock failures silently leak a session advisory
  lock, permanently consuming a dispatch slot; the SPI advisory locks are also
  session-re-entrant, so the caps are effectively per-backend, not
  per-dispatch (`governance.rs:85-160`). Replace with direct
  `LockAcquire`-based locks or a shared-memory counter.
- **Vacuum materializes the entire index in memory up to 3× per cycle**
  (`vacuum/mod.rs:303-354` — every visible assignment including payload
  bytes); stream instead. **Split of an all-dead leaf wedges maintenance**
  (selection by index-side counts, then `"requires source rows"` error every
  run until vacuum catches up; `update/materialization.rs:288-365`,
  `scheduler.rs:92-110`) — defer instead of erroring. **Maintenance planning
  silently ignores non-available placements**, shifting split/merge
  thresholds with no degraded-planning signal
  (`snapshots.rs:2703-2707`). **Stale TopGraph carried across
  replacement/compaction epochs** — the two load-bearing
  `TODO(phase6)` comments (`update/leaf_rows.rs:236`, `vacuum/mod.rs:445`);
  with top graphs enabled, the first split/merge turns the index into one
  that fails closed until rebuild, with no warning in the maintenance result.
  Track as a task, and drop carried TopGraph placements when the root routing
  object is rewritten.
- **NULL vector in the indexed column errors CREATE INDEX / INSERT outright**
  (`build/drafts.rs:513`) — convention is to skip NULL keys.
- **No privilege gating on ~224 SPIRE pg_externs**, including topology
  registration with conninfo secret references, static placement publication,
  consistency-mode flips, and remote `ROLLBACK PREPARED` reaping
  (`lib.rs:2243,2347,2513,2715`) — one superuser-or-owner guard helper is
  cheap even for research.
- **Error-surface smells:** exactly one SQLSTATE in the whole subsystem
  (everything else XX000 — corruption indistinguishable from bad options);
  492 `map_err(|_| ...)` sites discard root causes; the `cfg!(test)` GUC-stub
  pattern (~40 accessors) has three bool stubs that invert production
  defaults, so unit tests can never exercise the default-off paths
  (`options/mod.rs:1229-1530`).
- **Hot-path oddments:** full top-graph structural validation
  (O(nodes×degree)) re-runs on every query
  (`routing.rs:1762-1849`) — validate at load/publish; top-graph greedy
  search scores centroids with a scalar zip/sum `inner_product`
  (`routing.rs:1980-1985`) instead of the ADR-077 SIMD kernels; RaBitQ column
  scoring shreds an already-contiguous payload slab into per-row structs and
  re-concatenates it (`quantizer/mod.rs:511-545`,
  `candidates.rs:3094-3126,3454-3467`); selected-row-range membership is
  O(rows×ranges) linear rescan (`candidates.rs:2789-2806`); the bounded
  RaBitQ filtered path materializes row+vec_id and pays a HashMap probe per
  *pruned* row (`candidates.rs:3492-3597,3850-3862`); per-row GUC read inside
  the scoring loop (`candidates.rs:3171,3361`); store-ordered leaf processing
  discards the best-first route order and weakens the prune threshold
  (`snapshot.rs:881-938`). All perf items need A/B bench per closeout rules.

## Verified-sound (for calibration)

Deterministic merge/tie-break ordering end-to-end (`total_cmp` + full
tie-break chains, no NaN-panic comparators); rescan state reset; buffer
pin/lock RAII discipline with no lock-order inversions found; atomic
root-control publication (readers never see torn manifests absent P0-C);
explicit little-endian codecs with length/magic/version validation; gated
timing instrumentation; payload row/batch/byte limits enforced before decode;
strict-mode fail-closed on `next_blocker` in the AM consumer; degenerate
k-means cases (empty clusters, nlists > rows) handled.

## Recommended triage order

1. P0-A/P0-B (planner shape + Param crash) alongside the packet 013 P0 fixes —
   they share the same fail-closed eligibility rework.
2. P0-D + P1-P (vacuum/replica correctness) — silent wrong results and silent
   recall loss in the default replicated config; both are small, testable
   fixes in `run_bulkdelete`/compaction row collection.
