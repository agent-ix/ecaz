## Blocking findings

### 1. P1 — the attribution lane's "candidate" is not the lazy-10 path; the control's GUC leaks into it

`materialization_variant_settings_sql` (`:2903-2960`) emits a
`SET ec_distann.benchmark_materialization_batch_size` **only when the variant's
batch size is not 10** (`:2908`). It assumes a variant with batch 10 can rely
on the session default (`-1`, "production fixed lazy-10 policy",
`src/am/ec_distann/options.rs:488-496`).

That assumption does not hold in this call sequence.
`compare_materialization_scenario` runs the control first and the candidate
second **on the same `coordinator` client** (`:5856-5858`), and
`materialization_result_json` (`:2873-2901`) issues each variant's settings SQL
as a session-level `SET`. There is no `RESET`, no `DISCARD`, and no second
connection anywhere in `5843-6340`. So:

1. control (`materialization_batch_size: 0`) executes
   `SET ec_distann.benchmark_materialization_batch_size = 0`;
2. candidate (`materialization_batch_size: 10`) emits **no** batch-size SET;
3. the candidate query therefore runs with the GUC still at **0 — eager**.

`run_materialization_correctness` also applies the control's settings once
before the scenario loop (`:6104-6109`), so this holds from the first scenario
onward, and the `mixed_local_remote` and `post_first_batch_remote_failure`
drills (`:6221-6226`, `:6260-6270`) re-apply the candidate's settings without
restoring the batch size either.

Consequence for this packet: `remote_requested=8, local_consumed=4,
payload_reads=12` is a measurement of the **eager** materialization path, not
of production lazy-10. Rule 1 as written would stamp that
"REPRODUCED ON EXACT CURRENT MAIN" and send packet 002 to bisect the production
bounded-read path — for a counter shape the production path may never produce.
Eager deepening over a top-10 window is a straightforward mechanism for 12
reads with correct, identical rows, and it is consistent with `fewer_than_window`
(5 rows, bound 10) passing immediately before in Task 224's control log.

This is a defect in main's harness, discoverable without any live run. It is
not a reason to widen the bound.

### 2. P1 — the production lane cannot compare eager against lazy-10 at all

`ec_distann.benchmark_materialization_batch_size` is registered only under
`#[cfg(feature = "distann-head-attribution-benchmark")]`
(`src/am/ec_distann/options.rs:486-496`). In the featureless `pg18` release
that lane 1 installs, the GUC does not exist; the harness's `SET` is accepted
as an inert placeholder (proved by Task 199's normal-release 50k run,
`reviews/task-199/003-release-matrix-and-decision/artifacts/repeat-50k/normal-release-ab-50k/distann-multinode-summary.log:76-83`
— seven rows, `attribution_available=false`, all digests identical), and
`materialization_batch_size()` returns `PRODUCTION_MATERIALIZATION_BATCH_SIZE`
unconditionally (`options.rs:838-846`).

So in lane 1 both "variants" are byte-identically the production path, and both
recall arms are the same configuration under two labels. request.md §1 says the
lane must "report eager/candidate result identity" and "complete recall for
both eager and lazy-10 variants". Identity there is true by construction and
carries no information, and the two recall rows are not an eager/lazy-10 pair.
Lane 1 is still a worthwhile production-path gate — seven scenarios, correct
rows, `attribution_available=false`, recall completes — but it must be
described as what it is.

### 4. P2 — "mismatch fails closed" on SHA and feature set is not true

request.md: "Both live suites must attest exact SHA `41392c011...`, release
profile, and their expected feature set on every node; mismatch fails closed."

`validate_extension_preflight` (`:459-519`) takes **node 1's own values as the
expectation** and then checks only: (a) non-empty SHA, (b) cross-node
unanimity of SHA/profile/features, (c) profile is `release` unless
`allow_debug_extension`, (d) the `pg-test` feature is absent. It never compares
against a pinned SHA and never compares against an expected feature list. A
unanimous three-node install of the *wrong* build passes preflight and prints
its SHA as `status=passed`.

Release profile and `pg-test` absence do fail closed. SHA and feature-set
pinning are operator discipline plus post-hoc reading of the emitted
`release_profile_preflight` line — which is fine, but the packet must say so,
because "fails closed" is what makes a reader trust an unreviewed live run.
Lane 1's stated seven-row / `attribution_available=false` gate does
incidentally catch a stale attribution build, and that is worth keeping as the
explicit backstop it is.
