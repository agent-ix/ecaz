## Why this is now sound

The new pattern at each worker entry:

```rust
let header: &EcHnswParallelBuildSharedHeader = unsafe {
    ptr::NonNull::new(shared)
        .unwrap_or_else(|| pgrx::error!("ec_hnsw parallel build shared header is null"))
        .as_ref()
};
header.validate();
// ... later in the same function:
let is_concurrent = header.is_concurrent;
HeapRelationGuard::try_open(header.heaprelid, ...)
IndexRelationGuard::try_open(header.indexrelid, ...)
```

Three differences from the blocked 401 helper:

1. **The `&` is named at a `let` binding** inside the function frame, not
   returned from a function signature. Its lifetime is the lexical scope of
   `header`, which is the worker function frame. Rust's borrow checker
   enforces this — there is no `'a` parameter for any future caller to
   choose `'static` from.
2. **The `unsafe { ... }` is at the obligation site**, not behind a safe
   facade. Anyone looking at this code sees the obligation and the SAFETY
   comment together. The 401 helper hid the obligation behind a safe
   signature.
3. **The SAFETY comment is context-specific** ("the leader inserted
   `shared` before launching workers and keeps the DSM segment alive
   until every worker exits"), not the function-level contract a helper
   would have to write generically.

The two worker entries each carry one of these blocks; the per-function
copy is acceptable because each block is the syntactic anchor for the
borrow that follows it. Trying to factor the block back out into a helper
re-creates the unbounded-`'a` problem.
