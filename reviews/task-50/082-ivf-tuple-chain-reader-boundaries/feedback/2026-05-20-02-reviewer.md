# Finding from full code-diff audit: Anti-pattern A

This packet was re-audited as part of the full code-diff review
recorded in
`reviews/task-50/132-helper-soundness-audit/feedback/2026-05-20-03-reviewer.md`.

## Finding

IVF tuple-chain readers (centroid / directory / codebook) made safe to call while accepting raw `pg_sys::Relation` (commit `9b460c2b`).

The helper(s) in this packet were converted from `unsafe fn` to safe
`pub(crate) fn` while still accepting a raw PostgreSQL pointer
(`pg_sys::Relation`, `pg_sys::IndexScanDesc`, `pg_sys::ParamListInfo`,
`*mut PlannerInfo`, `*mut CustomScan`, `*mut TupleTableSlot`,
`*mut pg_sys::varlena`, etc.) and dereferencing it internally.

This is the same shape as packets 014 (`live_index_relation`) and
100 (`current_planner_cost_constants`), which I flagged and which
were fixed by packets 017 / 141 marking them `unsafe fn`. The
SAFETY comment names the right invariant but the borrow checker
does not enforce it — a future caller has no compile-time signal.

## Required fix (per consolidated audit)

Pick one:

1. **Option A** — mark `unsafe fn`: every call site gains a one-line
   unsafe wrapper with a context-specific SAFETY comment. Minimal
   code churn; matches the 017 / 141 template.

2. **Option B** — take a guard / view reference (preferred where a
   guard type exists): change the raw `pg_sys::*` parameter to
   `&IndexRelationGuard` / `&HeapRelationGuard` /
   `&SpireLiveIndexRelation` / etc. The borrow checker then carries
   the live-resource contract.

## Status

The reduction *numbers* in this packet's request.md are real
(caller-side unsafe blocks are gone). The *safety contract* claim
is weaker than the request.md implied because the acknowledgement
moved from caller-site unsafe block to a SAFETY comment inside a
safe helper. After the fix, the architectural claim is defensible.
