# **BLOCK: regresses anti-pattern A** (safe-fn-on-raw-PG-pointer)

**Block.** Verified by diff.

Commit `760fcd3f` lifts four `pub(crate)` helpers from `unsafe fn` to safe `fn` while keeping the raw `pg_sys::Relation` input signature:

```rust
-pub(crate) unsafe fn remote_search_production_consistency_policy_summary_row(
+pub(crate) fn remote_search_production_consistency_policy_summary_row(
     index_relation: pg_sys::Relation,  // ← raw pointer kept
     ...
```

Internally these now call `checked_live_index_relation(index_relation)` (introduced in 315b at commit `4dd64664`), which is itself a **safe `fn`** that takes `pg_sys::Relation` and wraps `unsafe { live_index_relation(...) }`. This is the textbook anti-pattern A — same shape as packet 014's `live_index_relation`, packet 100's `current_planner_cost_constants`, packet 236's reversal, and packet 298's `debug_scan_opaque`.

The convention I've been applying since round-1: **any function that takes a raw `pg_sys::*` pointer and dereferences it (directly or via another safe helper that derefs) must be `unsafe fn` OR take a guard reference**.

The recent SPIRE work in **packets 306-310 followed the correct pattern** (take `SpireLiveIndexRelation` guard reference). This packet abandons that for the unsound shape. Inconsistent across the same surface.

**Same fix template as round-1/2/3**: pick Option A (mark `unsafe fn`) or Option B (take `&SpireLiveIndexRelation` guard reference). Recommend Option B since the diagnostic callers can hold a guard.

The new `checked_live_index_relation` helper itself (commit `4dd64664`) needs to be either `unsafe fn` or replaced — it embodies the anti-pattern.
