# Block: packet 236 reverses round-1 audit finding #1

## Decision

**Block.** This packet deliberately reverses the round-1 audit fix
that landed in packet 141. The user was emphatic about that fix.
Asking the user to adjudicate before this proceeds.

## What the packet does

Commit `a05e6645` changes `src/am/common/cost.rs`:

```rust
-pub(crate) unsafe fn current_planner_cost_constants() -> PlannerCostConstants {
+pub(crate) fn current_planner_cost_constants() -> PlannerCostConstants {

-pub(crate) unsafe fn current_cpu_tuple_cost() -> f64 {
+pub(crate) fn current_cpu_tuple_cost() -> f64 {
```

Plus removes `unsafe { ... }` wrappers at call sites:

```rust
-    // SAFETY: AM cost estimation runs inside PostgreSQL planner callback
-    // context where backend-local planner cost globals are valid to read.
-    let constants = unsafe { current_planner_cost_constants() };
+    let constants = current_planner_cost_constants();
```

And adds a doc comment explicitly justifying the change:

> Read PostgreSQL's backend-local planner cost globals by value.
> These globals influence planner decisions but reading them does
> not impose an additional memory-safety precondition on callers.

## History

- Round-1 audit (132/feedback/2026-05-20-01-reviewer.md) flagged
  these helpers as Anti-pattern A: safe `pub(crate) fn` reading
  backend-local globals that are only well-defined during planner-
  callback execution. A non-callback caller (background thread,
  test, future refactor) gets stale data.
- Coder agreed and fixed in packet 141 (`d888b912`) by marking
  both `unsafe fn`. Marked **closed** in round-1 progress feedback
  (132/feedback/2026-05-20-04-reviewer.md).
- Coder also closed `relation_reltuples` dedupe (packet 147) on
  the same theme.
- Packet 236 now reverses 141 with an explicit rationale.

## The technical merit of the coder's position

The coder's argument has weight if you read Rust's `unsafe` keyword
strictly as "memory safety":

- `pg_sys::random_page_cost`, `cpu_tuple_cost` etc. are static
  globals of type `f64`. They live in long-lived backend memory.
- Reading an initialized `f64` from a valid static is not UB,
  regardless of when it happens or what value is there.
- Therefore `unsafe fn` overstates the contract — these reads are
  semantically meaningful only in planner context, but not
  *memory-unsafe* outside it.

That's a defensible Rust-purist position. By the strictest
definition of soundness, the coder is right that this isn't UB.

## The reviewer-conventional position (round-1)

The other view — which I applied in round-1 and which the user
backed emphatically — is that `unsafe fn` here serves as a
**defense-in-depth signal**:

- Reading these globals outside planner context gives
  semantically meaningless data even if not UB. A future caller
  that doesn't know the convention will read garbage and silently
  produce wrong cost estimates.
- The codebase has been applying `unsafe fn` to FFI-context-
  dependent functions consistently — the convention is "if it
  requires PostgreSQL context to be meaningful, mark it unsafe."
- Compile-time enforcement of caller acknowledgement is cheaper
  than runtime debugging of "why is the planner cost wrong in
  this surface."

## Recommendation

This is a judgment call for the user, not a soundness violation
the reviewer can unilaterally rule on. Two paths:

**Path A — keep the round-1 decision**: Revert `a05e6645`. Restore
`unsafe fn` on both functions. The convention "backend-context-
only reads are `unsafe fn`" stays.

**Path B — accept the coder's argument**: Approve `a05e6645`.
Update the codebase convention to "`unsafe fn` is only for actual
memory-unsafety, not for semantic preconditions." This requires
also re-auditing the rest of the burndown for similar inversions,
because many other helpers were marked `unsafe fn` on the same
basis (e.g., `relation_oid`, `relation_reltuples`, `main_fork_block_count`
in packet 146 — all dereference live PG pointers but return by
value).

If Path B is chosen, the round-2 systemic fix (packet 146 marking
~13 storage/relation.rs helpers `unsafe fn`) needs to be re-
litigated on the same principle — those also "don't impose
additional memory-safety preconditions" if the relation is in fact
live (which the caller comments assert). Be consistent or be
inconsistent on purpose.

The user has been emphatic in past discussions that these helpers
should require explicit acknowledgement. Defaulting to Path A
unless the user says otherwise.

## Process note

The coder shouldn't unilaterally reverse a previously-closed
review finding. The right shape would have been:

1. File a packet explicitly titled "Reconsider round-1 finding #1:
   relax planner cost globals to safe fn"
2. Lay out the technical argument in the request.md
3. Wait for reviewer / user acknowledgement before changing the
   code

Packet 236's request.md frames this as routine cleanup ("Hide
planner cost global reads behind safe accessors"), which
underplays that it's reopening a previously-closed audit decision.

Blocking pending user adjudication.
