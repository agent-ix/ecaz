# Partial approve: constructor fix landed, lifetime parameters still missing

## Status

Approve the part that landed. Commit `7920c133` correctly converts
the storage guard constructors from safe `fn` to `unsafe fn`:

- `IndexScanGuard::begin` → `pub(crate) unsafe fn begin(...)`
- `HeapScanGuard::begin` → `pub(crate) unsafe fn begin(...)`
- `TupleTableSlotGuard::create` → `pub(crate) unsafe fn create(...)`
- `TupleTableSlotGuard::single_for_heap` → `pub(crate) unsafe fn single_for_heap(...)`

That closes the **constructor-contract** half of round-1 audit
findings #4 and #5. Callers now acknowledge the raw-pointer input
at construction.

## Outstanding: dependency-lifetime parameters not added

The structs themselves still look like this (post-fix):

```rust
pub(crate) struct IndexScanGuard {
    // no <'rel, 'snap> tying to &HeapRelationGuard / &ActiveSnapshotGuard
}

pub(crate) struct HeapScanGuard {
    // no <'rel, 'snap> tying to dependencies
}

pub(crate) struct TupleTableSlotGuard {
    // no <'rel> tying to the Relation
}
```

Round-1 audit findings #4 and #5 had **two** halves:

1. constructor should be `unsafe fn` — **done** ✓
2. struct should carry `<'rel, 'snap>` / `<'rel>` PhantomData
   parameters binding the guard's lifetime to its dependencies —
   **still missing**

Without the lifetime parameters, the guard correctly closes its
own resource in Drop, but nothing prevents the guard from
outliving the borrowed relation or snapshot it depends on. If a
future refactor moves the guard into a longer-lived container
while the dependency drops, that's use-after-free of the
dependency (the guard's own resource cleanup runs fine, but the
relation it scanned has already been closed by the time the scan
descriptor is touched again).

## Fix

Add PhantomData lifetime parameters:

```rust
pub(crate) struct IndexScanGuard<'rel, 'snap> {
    scan: pg_sys::IndexScanDesc,
    _rel: PhantomData<&'rel HeapRelationGuard>,
    _snap: PhantomData<&'snap ActiveSnapshotGuard>,
}

impl<'rel, 'snap> IndexScanGuard<'rel, 'snap> {
    pub(crate) unsafe fn begin(
        relation: &'rel HeapRelationGuard,
        snapshot: &'snap ActiveSnapshotGuard,
        nkeys: i32,
        norderbys: i32,
    ) -> Option<Self> { ... }
}

pub(crate) struct HeapScanGuard<'rel, 'snap> { ... }

pub(crate) struct TupleTableSlotGuard<'rel> {
    slot: *mut pg_sys::TupleTableSlot,
    _rel: PhantomData<&'rel RelationGuard>,
}
```

Each caller that today passes `pg_sys::Relation` directly should
either:
- already hold a `RelationGuard` / `HeapRelationGuard` and pass
  it by borrow; or
- have an `unsafe fn` boundary just above where it constructs the
  guard from the raw PG-provided relation pointer.

## Severity

Low-to-moderate. Today all callers hold all three guards in the
same stack frame (verified by spot-checking the diffs); the partial
fix is currently sound in practice. The architectural risk is that
the lifetime parameters are what *makes* the soundness claim
defensible by construction. Without them, the claim relies on
caller discipline at every future site that constructs one of
these guards.

This is the same incompleteness pattern as round-2's storage
facade fix — facade marked `unsafe fn`, which is right, but a
borrowed-input shape (Option B) would have been stronger. For the
storage facade I accepted the lighter Option A; for these guards
the lifetime parameters are the more important half because they
catch outliving, not just construction.

Not a blocker on this packet's approval — call it conditional
approve. Please file a follow-on packet adding the PhantomData
lifetimes before the closeout summary is written.
