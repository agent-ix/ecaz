# Audit round 3: full code-diff review of 118 Task-50 code commits

## Method

User directed: "do a FULL REVIEW of ALL CHANGES." I enumerated all 118
code-changing commits on `task-50-unsafe-closeout` (vs `main`) and
dispatched five parallel reviewers, each reading actual `git show`
diffs (not request.md). Reviewers were told to check for four
anti-patterns:

- **A**: safe `pub(crate) fn` taking raw PG pointer (`pg_sys::Relation`
  / `IndexScanDesc` / `StringInfo` / `Query` / `*mut T`) and
  dereferencing
- **B**: safe `pub(crate) fn` returning `&'a T` from raw pointer with
  unbounded `'a`
- **C**: new `unsafe { ... }` block missing SAFETY comment
- **D**: caller-side `unsafe { }` deleted by replacing the call with
  a safe-looking helper that just hides the unsafe

Plus other obvious bugs (missing Drop, double-free, aliasing, ignored
fallible PG returns).

## Headline result

The reviewers disagreed sharply about whether the burndown's default
pattern is **Anti-pattern A**.

- **Strict-view reviewers (batches 2 + 3)**: flagged ~30 commits with
  Anti-pattern A — safe `pub(crate) fn` taking raw `pg_sys::Relation`
  (or similar) and dereferencing.
- **Lenient-view reviewers (batches 1 + 4 + 5)**: gave the same
  functions a sound verdict because they have null checks + SAFETY
  comments + internal `unsafe { ... }` blocks.

These are the **same functions, same code, same diffs**. The
disagreement is interpretive: does a safe function with a SAFETY
comment satisfy Rust's safety contract, or does Rust convention
require `unsafe fn` whenever the function dereferences a raw
pointer the caller supplies?

## My standing (consistent with packets 014, 100, 141)

The strict view is the one I've been applying since packet 014. The
017 / 025 / 141 fixes I championed specifically marked helpers
`unsafe fn` because a SAFETY comment inside a safe function is **not
the same** as compile-time enforcement: a future caller — test code,
maintenance script, refactor that moves the helper deeper — sees
no compile-time signal that the relation must be live.

By that standard, the lenient-view reviewers are wrong, and the
strict-view reviewers caught what I had been missing: **the
burndown's default pattern across roughly 30 commits is Anti-pattern A.**

## What's actually sound (do not blame the whole burndown)

The same audits found genuine sound work alongside the anti-pattern:

- **Round-1 fixes (141, 142, 143)** and **scan_output fix
  (7eb1ec04)** are correct — `unsafe fn` constructors + lifetime-
  bound view types + assertions on fallible returns. The 017/025
  template applied cleanly.
- **RAII guards** (`buffer_guard.rs`, `wal.rs`, `relation_guard.rs`,
  `snapshot_guard.rs`, `lock_guard.rs`) genuinely model PG resource
  ownership. Drop is correct. No anti-pattern.
- **Closure-based stream visitors** (`visit_relation_linear_read_stream`,
  `visit_scan_owned_read_stream_pinned`, `PgReadStreamGuard`) thread
  raw pointers through `unsafe fn` boundaries and expose closure
  APIs that bound the lifetime correctly.
- **HeapSlotReader / TupleSlotReader** in `heap_slot.rs` have the
  `'slot` lifetime parameter and `unsafe fn from_raw_slot`
  constructor — sound.
- **GenericXLogTxn** consume-self `finish()` is sound by
  construction.
- **Cross-AM cleanup** (planner cost callbacks consolidated via
  `pg_am_callback!`, scan opaque facades, reloptions consolidations
  on the safe side) is real architectural progress.

So the burndown is doing both correct work and Anti-pattern-A work
in roughly equal measure. The visible block-count reduction is
real; the safety claim is mixed.

## Recommended fix sequence

1. **Fix `storage/relation.rs` facade first** (round-2 finding). It
   is the canonical cross-AM API; ~50 callers depend on it. Take
   `&IndexRelationGuard` / `&HeapRelationGuard` per Option B.
2. **Fix `storage/string_info.rs`** (round-2). Three helpers,
   easier to mark `unsafe fn`.
3. **Fix `storage/scan_guard.rs` and `storage/slot_guard.rs`**
   (round-1). Add `<'rel, 'snap>` and `<'rel>` PhantomData.
4. **Fix the round-3 cluster systematically**: walk each cluster
   above, apply the same shape (either `unsafe fn` mark or
   guard-reference input). For SPIRE clusters the input usually
   wants to be `&SpireLiveIndexRelation` / `&IndexRelationGuard`;
   for IVF clusters typically `&IndexRelationGuard`.
5. **Add a lint to prevent regression**: a clippy-style rule or
   pre-commit grep that fails on `pub(crate) fn .*pg_sys::(Relation|
   IndexScanDesc|StringInfo|Query|HeapTuple|TupleTableSlot|
   MemoryContext|Snapshot|Buffer|ParamListInfo) ` outside of
   files explicitly marked as boundary modules. (The plan's "no
   new unledgered unsafe" gate is the right place to bolt this
   on.)

## Honest re-assessment of "is the burndown making things safer?"

Compared to the round-2 assessment, this is **weaker but not
catastrophic**:

- **Yes**, the guard / view / closure helpers are real safety wins.
  The RAII discipline is correct; lifetime composition through
  buffer/lock/relation/snapshot guards is type-enforced.
- **Yes**, the architectural direction is right.
- **But**: roughly half of the visible `-865` unsafe block deletion
  is *contract relocation*, not *contract removal* — the
  acknowledgement moved from caller `unsafe { }` to a SAFETY comment
  inside a safe helper. Both before and after, the contract is
  "caller must have a live relation at the right context." Before,
  callers had to acknowledge it locally. After, they don't.
- The residual registry the plan's closeout gate requires becomes
  defensible only after the ~40 helpers above get either `unsafe fn`
  or guard-reference inputs.

I should have been catching this systematically from packet 014
onwards. The fact that the same pattern recurred in ~30 more
commits is a reviewer-process failure, not just a coder error.

## Reviewer process changes

Starting now:

1. For every helper-introducing packet, run:

   ```sh
   grep -nE "^pub(\(crate\))? fn .*\(.*pg_sys::(Relation|IndexScanDesc|StringInfo|Query|HeapTuple|TupleTableSlot|MemoryContext|Snapshot|Buffer|ParamListInfo|Page|ParamList)" <new files>
   ```

   Any hit is a candidate finding. Read the function body; if it
   does `(*ptr)` or `as_ref()` or `as_mut()` on the raw pointer,
   that's Anti-pattern A.

2. For every "centralize X unsafe" or "Make X safe to call" commit
   message, read the diff to check whether the function dropped
   `unsafe fn` for `fn` while still taking the raw pointer. That's
   the highest-frequency pattern in the round-3 findings.

3. Stop relying on Explore-agent summaries of request.md for
   soundness verdicts. Explore can read diffs but the criterion for
   "sound" needs to be the strict one (Rust convention: raw-pointer
   input + dereference = `unsafe fn`).
