## New finding: 17 helpers with the same anti-pattern

While spot-checking the round-1 fix, I grepped the broader storage
facade and found the safe-fn-on-raw-PG-pointer shape is **systemic**
across `storage/relation.rs` and parts of `storage/string_info.rs` /
`common/cost.rs`:

Every one is `pub(crate) fn` (no `unsafe`) that takes a raw
PostgreSQL pointer type (`pg_sys::Relation` = `*mut RelationData`,
`pg_sys::StringInfo` = `*mut StringInfoData`) and dereferences it
internally. Example:

```rust
pub(crate) fn relation_oid(relation: pg_sys::Relation) -> pg_sys::Oid {
    if relation.is_null() { pgrx::error!("..."); }
    // SAFETY: callers pass a live opened PostgreSQL relation descriptor; ...
    unsafe { (*relation).rd_id }
}
```

The SAFETY-comment wording ("callers pass a live opened PostgreSQL
relation descriptor") is **textually identical** to the contract that
packet 014's `live_index_relation` had — the one I flagged as anti-
pattern and packet 017 fixed by marking `unsafe fn` and threading
references.

The null check catches null but not use-after-free, not stale
pointers, not pointers to a closed/dropped relation. The contract
lives in the comment; the borrow checker does not enforce it.

## Why this matters more than the round-1 findings

`storage/relation.rs` is **the canonical cross-AM relation API**.
Packets 126/127/128/129/130 routed every AM (HNSW, IVF, SPIRE,
DiskANN) through these helpers. Every place that used to be a
caller-side `unsafe { (*rel).rd_id }` now reads
`storage::relation::relation_oid(rel)` — and the safety contract
moved from a per-call-site `unsafe { ... }` acknowledgement to a
per-helper SAFETY comment that nothing enforces.

That means the visible `−23 src/` from packet 126,  `−11` from 127,
`−9` from 128, etc. — those reductions are **partly cosmetic**.
Callers no longer wrap in `unsafe { }`, but the safety contract is
weaker because the helper itself doesn't acknowledge the raw-pointer
boundary.

This pattern recurring at scale, after I had already documented and
fixed it in 014→017 and 100→141, is a process problem as well as a
soundness problem. The 017 / 025 / 141 template should be the
default for *any* helper that takes a raw PG pointer. It wasn't
applied to the storage facade.

## Severity

Moderate, *not* catastrophic:

- Today every caller of these helpers is genuinely at a context
  where the relation is live (AM callback, build state, vacuum
  state, custom-scan entry point) — runtime UB risk is low.
- The architectural risk is that the helpers *look safe* and a
  future refactor could call them from a context where the
  precondition doesn't hold (e.g. caching a `pg_sys::Relation`
  across transactions, calling from a non-callback thread,
  test code that constructs a raw pointer for mocking).

This is the same risk pattern as the round-1 cost.rs finding: a
backend-only API exposed as safe Rust. Future-proofing requires
fixing the helper, not just trusting current call sites.

## Fix options (same as before)

For each of the 17 helpers:

**Option A — `unsafe fn`** (minimal churn):

```rust
pub(crate) unsafe fn relation_oid(relation: pg_sys::Relation) -> pg_sys::Oid {
    ...
}
```

Cost: every call site now wraps in `unsafe { ... }`. The visible
src/ unsafe count goes back up by ~100–200 blocks (the entire
deletion claim of packets 126/127/128 partially reverses). But the
SAFETY contract is acknowledged at every call site, restoring the
017 template.

**Option B — `&IndexRelationGuard` / `&HeapRelationGuard` input**
(correct fix, more work):

```rust
pub(crate) fn relation_oid(guard: &IndexRelationGuard) -> pg_sys::Oid {
    // SAFETY: guard.as_ptr() is live for the guard's lifetime
    unsafe { (*guard.as_ptr()).rd_id }
}
```

Cost: every caller has to have a `RelationGuard` in scope. Many AM
callbacks receive raw `pg_sys::Relation` directly from PG; those
sites need an `unsafe fn` to construct a guard from the raw pointer
once at the boundary, then everything downstream is safe.

This is the **right** fix because it lets the borrow checker carry
the contract and matches the rest of the architecture (which already
has `IndexRelationGuard`, `HeapRelationGuard`, etc. — they're just
not being consumed by the relation helpers).

**Recommended**: Option B for `storage/relation.rs`. The guard types
already exist; the work is mechanical (change each `pg_sys::Relation`
param to `&IndexRelationGuard` / `&HeapRelationGuard`, fix callers).
The block-count delta should be roughly net-zero after the dust
settles — same total contract acknowledgement, just at the right
boundary.

`storage/string_info.rs` is a smaller surface (3 helpers); Option A
is probably fine there.

## Honest re-assessment of "is the burndown making things safer?"

Walking back my round-1 answer somewhat:

- **The RAII guard layer is sound**: `BufferGuard`, `RelationGuard`,
  `SnapshotGuard`, `LockGuard`, `WALTxn` correctly model PG resource
  ownership and Drop. Real safety win.
- **The 017-style typed views are sound**: `IvfPageRelation<'a>`,
  `SpireLiveIndexRelation`, `HeapSlotReader<'slot>` etc. take raw
  pointers in `unsafe fn` constructors and expose lifetime-bounded
  safe methods. Real safety win.
- **The cross-AM storage facade is partly unsound**: `storage/relation.rs`
  and `storage/string_info.rs` bypass the guard layer and dereference
  raw pointers in safe signatures. This was the canonical API for
  packets 126–130; that means ~50+ caller-side `unsafe { }`
  deletions are contract-relocated rather than contract-enforced.
- **The cleanup packets 084 / 085 / 086 / 088 / 089 / 096 / 097 / 098 /
  099 / 102 / 103 / 104 / 105 / 106 / etc.** — these consumed the
  storage facade. Whether they're "sound" depends on whether the
  facade is sound. So the verdict on dozens of packets is provisional
  pending the facade fix.

The 865 unsafes-deleted number is still real in the sense that
caller-side `unsafe { ... }` blocks are gone. It's just that for
the ~100–200 of those that route through the unsound facade, the
contract isn't type-enforced — it's comment-enforced.

## Process recommendation

For helper-introducing packets going forward (and there are many
remaining — P12 SIMD newtypes, P13 tests, more P11 planner work,
HNSW Wave 3), I'll do a one-`grep`-per-packet check:

```sh
grep -nE "^pub(\(crate\))? fn .*\(.*pg_sys::(Relation|IndexScanDesc|StringInfo|Query|HeapTuple|TupleTableSlot|MemoryContext|Snapshot)" <new files>
```

Any hit is a candidate for the anti-pattern. If the function
dereferences the raw pointer in its body without an `unsafe fn`
modifier, that's the failure mode — flag in feedback before
approving.

I should have been doing this check since packet 014. Apologies for
missing it on the storage facade rollout.
