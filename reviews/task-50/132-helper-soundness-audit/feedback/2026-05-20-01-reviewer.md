# Architectural audit: are the burndown's central helpers actually safer?

## Decision

**Yes, substantially — with six concrete fixes required.**

After auditing the ten central helper modules that absorb the bulk of
caller-side unsafe in the burndown, the architectural shape is sound
and the burndown is genuinely making things safer. The pattern of
small RAII guards + lifetime-bound view types + reference-input
contracts works: where it's applied correctly, the borrow checker
now carries the safety contract instead of caller discipline.

However, **six specific soundness issues** were found in helpers that
look safe but allow safe code to trigger UB. These need fixes before
the residual registry is meaningful — otherwise hundreds of callers
inherit the gap by routing through these helpers.

## What's genuinely safer

The audit confirms the pattern works in seven of the ten helpers:

- **`callback.rs`** (`am_callback`, `pg_am_callback!`) — closure input
  forces the caller to pass a callable; no raw pointers escape; SAFETY
  comments name the AM-entry-point invariant. Sound.
- **`heap_slot.rs`** (`HeapSlotReader`, `TupleSlotReader`) — `unsafe fn
  from_raw_slot`/`from_raw` constructors take raw pointers; `'slot`
  lifetime parameter ties downstream borrowed access to the slot;
  safe methods (`clear`, `fetch_row_version`, `required_datum`) never
  expose raw pointers back to callers. Sound.
- **`stream.rs`** — `prefetch_relation_blocks` pins state on the
  stack, registers it with PG, and ends the stream before the function
  returns. `PgReadStreamGuard` Drop calls `read_stream_end` exactly
  once. Visitor closures use `PinnedBufferGuard` to enforce per-buffer
  release. Sound.
- **`buffer_guard.rs`** — three guard types (`PinnedBufferGuard`,
  `PinnedBufferLockGuard<'a>`, `LockedBufferGuard`) correctly model
  pin / lock / release pairing in Drop. PhantomData lifetime on the
  lock guard prevents outliving the pin. Sound.
- **`wal.rs`** — `GenericXLogTxn` Drop aborts if not explicitly
  finished; `finished` flag prevents double-finish; `finish(self)`
  consumes the value so it cannot be used after. Sound (one error-
  handling note below).
- **`relation_guard.rs`** — `IndexRelationGuard`, `HeapRelationGuard`,
  `RelationGuard` each pair open with the matching close in Drop; no
  borrowed lifetime is leaked; callers must hold the guard to use the
  relation pointer. Sound.
- **`snapshot_guard.rs`** — `ActiveSnapshotGuard` correctly sequences
  register → push, pop → unregister in Drop. Sound.
- **`lock_guard.rs`** — stored release function pointer is invoked
  in Drop; `unsafe fn from_acquired*` constructors document the caller
  contract. Sound.

The architectural win is real: where these helpers are consumed,
caller-side `unsafe { ... }` is genuinely *deleted*, not just
relocated. The borrow checker enforces lifetime composition between
relations, snapshots, scans, slots, and buffer pins. The 865 unsafes
removed from src/ are not theatre.

## Six concrete soundness issues

### 1. `common/cost.rs:102, 120` — backend-global reads exposed as safe fn

```rust
pub(crate) fn current_planner_cost_constants() -> PlannerCostConstants {
    // reads pg_sys::random_page_cost, pg_sys::cpu_tuple_cost, etc.
}

pub(crate) fn current_cpu_tuple_cost() -> f64 {
    // reads pg_sys::cpu_tuple_cost
}
```

These read backend-local globals (`pg_sys::random_page_cost`,
`pg_sys::cpu_tuple_cost`) that are only well-defined during planner
callback execution. The functions are **safe**, so any safe caller —
including a future maintenance thread, a test, or a non-callback
context — can call them and get garbage or trip an assertion.

**Severity**: moderate. The SAFETY comment names the invariant but
no Rust mechanism enforces it. Callers today are AM cost callbacks
so the issue is latent.

**Fix options**:
- Mark `unsafe fn` and require callers to wrap in `unsafe { ... }`
  with a context acknowledgement.
- Or, take a context-enforcing token: `fn current_planner_cost_constants(_ctx: &PlannerCallbackContext)`
  where the token is only constructible inside the callback wrapper.

**Cross-posted finding**: introduced in packet 100 (planner cost GUC
callers); reference there.

### 2. `common/scan_output.rs:5, 20, 47` — safe fns dereferencing raw IndexScanDesc

```rust
pub(crate) fn set_scan_heap_tid(scan: pg_sys::IndexScanDesc, heap_tid: ItemPointer)
pub(crate) fn set_scan_orderby_score(scan: pg_sys::IndexScanDesc, ...)
pub(crate) fn clear_scan_orderby_output(scan: pg_sys::IndexScanDesc)
```

`pg_sys::IndexScanDesc` is `*mut IndexScanDescData` — a raw pointer.
These three functions accept it in a safe signature and dereference
it. The null check is necessary but not sufficient; it doesn't
catch use-after-free or a wrong pointer.

**Severity**: moderate. Current callers are AM `amgettuple` callbacks
that hold a valid descriptor, but the helper itself has no compile-
time guarantee.

**Fix options**:
- Take an `&IndexScanGuard` or a fresh `IndexScanDescView<'a>` newtype
  whose constructor is `unsafe fn`.
- Or, mark all three `unsafe fn`.

**Cross-posted finding**: introduced in packet 042 (am-scan-output-writer).

### 3. `storage/relation.rs:86` — `relation_tuple_desc` returns unbounded raw TupleDesc

```rust
pub(crate) fn relation_tuple_desc(relation: pg_sys::Relation) -> pg_sys::TupleDesc {
    // returns raw pointer borrowed from relation
}
```

A safe function returns a `pg_sys::TupleDesc` (raw pointer borrowed
from the relation). Callers can stash it past the relation's
lifetime; nothing prevents use-after-free at the call site.

**Severity**: moderate. The function next to it (`relation_tuple_desc_copy`)
correctly returns `PgTupleDesc<'static>` — the unsound one looks
intentional for performance but isn't lifetime-bounded.

**Fix**: take a `&IndexRelationGuard` / `&HeapRelationGuard` and
return `&'a TupleDesc` so the borrow checker bounds the descriptor
lifetime to the guard's lifetime.

**Cross-posted finding**: introduced in packet 126/127/128 (cross-AM
relation helpers).

### 4. `storage/scan_guard.rs` — `IndexScanGuard`/`HeapScanGuard` missing lifetimes

Both scan guards correctly close the scan in Drop, but neither carries
a lifetime parameter binding the scan to its borrowed relation and
snapshot:

```rust
pub(crate) struct IndexScanGuard {
    // no <'a> tying to &HeapRelationGuard or &ActiveSnapshotGuard
}
```

If the scan guard outlives a borrowed relation or snapshot it depends
on, that's use-after-free of the dependency even though the scan
itself is correctly closed.

**Severity**: moderate. Today this works because callers hold all
three guards in the same stack frame. A future refactor that moves
the scan guard into a longer-lived container would silently break.

**Fix**: add `<'rel, 'snap>` parameters with `PhantomData<&'rel
HeapRelationGuard>` and `PhantomData<&'snap ActiveSnapshotGuard>`.

**Cross-posted finding**: pre-existing helper; flag for next P10
packet that touches scan guards.

### 5. `storage/slot_guard.rs` — `TupleTableSlotGuard` missing relation lifetime

```rust
pub(crate) struct TupleTableSlotGuard {
    // no <'a> tying to the Relation it was created from
}
```

`create()` and `single_for_heap()` take `pg_sys::Relation` by value
with no lifetime; the slot can outlive the relation that backs its
`TupleDesc`.

**Severity**: moderate. Same shape as #4.

**Fix**: add `<'rel>` parameter with `PhantomData<&'rel RelationGuard>`.

### 6. `storage/wal.rs::register_locked_buffer_full_image` — ignored return value

```rust
pg_sys::GenericXLogRegisterBuffer(...);  // return value not checked
```

PG documents `GenericXLogRegisterBuffer` as returning the registered
image page pointer; on failure it can return NULL. The helper
ignores this. If failure can happen at runtime, downstream mutation
operates on a stale page.

**Severity**: low — likely cannot fail in practice for the
`GENERIC_XLOG_FULL_IMAGE` flag, but the function should either check
the return or document why ignoring is safe.

**Fix**: check return, error on NULL, or add a SAFETY note citing the
PG docs.

## Architectural assessment

The big-picture answer to "are we really making things safer?" is **yes**:

1. The boundary helpers absorb FFI / PG handle / WAL / buffer / scan
   unsafe at named places. The set of files containing unsafe is
   shrinking (currently ~120 files vs 131 at Wave 0 baseline).
2. Lifetime composition through `PinnedBufferGuard<'a>`,
   `LockedBufferGuard`, `IndexRelationGuard`, `HeapSlotReader<'slot>`,
   `IvfPageRelation<'a>`, `SpireLiveIndexRelation` etc. means a
   significant fraction of removed `unsafe { ... }` callsites are
   genuinely type-checked rather than just textually deleted.
3. The 017 / 025 / 030 plan introduced consistent vocabulary: `unsafe
   fn` constructors at the boundary, safe methods with lifetime-bound
   outputs. That vocabulary is being applied across IVF, SPIRE, HNSW,
   DiskANN.
4. The Drop-based RAII pattern (`*Guard` types) is correctly modelling
   PG resource ownership in seven of eight guard files audited.

But the audit also revealed that the consistency claim is **not
universal**. Three of the central helpers (`cost.rs`, `scan_output.rs`,
parts of `relation.rs`) and two guard types (`scan_guard.rs`,
`slot_guard.rs`) leak the contract back out as `safe fn` taking raw
pointers or returning unbounded references. That's the same anti-
pattern packets 012/014/015 had, fixed by packet 017 — recurring in
new helpers that didn't go through the 017 template review.

This is what the "soundness regressed in 024" warning would have
caught at scale if I had been reading code instead of summaries.

## Recommendation

Treat this audit as the **next slice's input list**. Six fixes, all in
central helpers; each fix is small (single-file change), and fixing
them at the helper level automatically tightens the contract for the
hundreds of callers downstream:

1. `current_planner_cost_constants` / `current_cpu_tuple_cost` → `unsafe fn`
   or context-token (packet 100 / 105 follow-on).
2. `set_scan_heap_tid` / `set_scan_orderby_score` / `clear_scan_orderby_output`
   → take `&IndexScanGuard` or mark `unsafe fn` (packet 042 follow-on).
3. `relation_tuple_desc` → take `&RelationGuard`, return lifetime-bounded
   (packet 126 follow-on).
4. `IndexScanGuard` / `HeapScanGuard` → add `<'rel, 'snap>` parameters
   with PhantomData.
5. `TupleTableSlotGuard` → add `<'rel>` parameter with PhantomData.
6. `GenericXLogTxn::register_locked_buffer_full_image` → check return
   or document why ignoring is safe (packet 050 follow-on).

After those land, the residual registry the closeout requires becomes
defensible: every surviving unsafe sits in a helper that genuinely
type-enforces its invariant.

## Reviewer note on process

This audit is the kind of review that should have been happening on
each batch of helper-introducing packets. From packet ~037 onwards
I (the reviewer) was approving packets based on Explore-agent
summaries of the coder's `request.md`, not reading the actual
diffs. That meant the anti-patterns in #1 and #2 above slipped
past my review even though I had explicitly flagged the same shape
in packets 012/014/015 earlier in the project.

Going forward I'll spot-check helper-introducing packets by actually
reading the helper signature (specifically: `pub(crate) fn ... ` that
takes `*mut T` and produces `&'a T` or dereferences without an
`unsafe fn` modifier). That's a one-`grep`-per-packet check; it
should have been my baseline since the 017 template was established.
