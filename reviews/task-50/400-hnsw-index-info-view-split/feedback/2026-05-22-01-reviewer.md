`source.rs` `IndexInfoGuard` into two types in a shared module

## Why this matters architecturally

Splitting **owning guard vs borrowing view** is the textbook RAII
separation for this kind of resource:
- `IndexInfoGuard` carries the cleanup responsibility (`pfree` on Drop)
- `IndexInfoView<'scope>` carries the borrow but not ownership — the
  source already owns the allocation, the view just reads/writes it

This is the **right separation** for `build_parallel.rs` where the
allocation lifetime is managed by the build state, not the scope where
`ii_Concurrent` is written. Trying to use the owning guard there would
either double-free or fight the borrow checker.

The pattern works as expected at the call site: `build_parallel` can
write `ii_Concurrent` via `as_mut()` without `unsafe { ... }`. The
write is safe by construction because:
1. `IndexInfoView` is constructed only from a valid `IndexInfo` allocation
2. `&mut self` proves exclusive access
3. `NonNull::as_mut` panics on null (impossible here, but defensive)
