## Claim-by-claim verification

1. **`qjl_enabled` shape** — `src/quant/prod.rs:1476-1478`:
   `!(bits == 4 && rotation::tile_dim(dim).is_some())`. For
   `bits == 2` this is always true → the 2-bit lane is QJL-enabled by
   construction. ✓
2. **`mse_bits` shape** — prod.rs:1484-1490: QJL-enabled lanes get
   `bits - 1` MSE bits, so 2-bit TurboQuant is a 1-bit MSE + QJL
   residual-sign lane. That is the gamma/residual-sign kernel family
   (Task 97), not a LUT-per-dim no-QJL family. ✓
3. **No-QJL APIs hard-gated to 4-bit** — the
   `prepare_ip_query_lut_no_qjl_4bit` /
   `score_ip_from_parts_lut_no_qjl_4bit` / `mse_code_bytes_no_qjl_4bit`
   family all assert `self.bits == 4 && !qjl_enabled(...)`
   (prod.rs:303,328,355,359,451,...). ✓
4. **SQL surface cannot create a 2-bit index** —
   `DEFAULT_QUANT_BITS = 4` (lib.rs:348) and
   `validate_tqvector_bits` rejects any other value (lib.rs:367-374). ✓
5. **No 2-bit no-QJL identifier exists anywhere** — repo-wide grep for
   `NoQjl2Bit` / `no_qjl_2bit` finds nothing; the only 2-bit code is
   `pack_mse_indices_2bit`, which serves the QJL-enabled MSE lane. ✓
6. **AM consumers** — SPIRE, IVF, DiskANN, HNSW all route no-QJL batch
   scoring exclusively through `PreparedLutNoQjl4BitQuery` /
   `score_turboquant_no_qjl_4bit_batch_for`. ✓

## Why the stop condition is the right call (not a scope dodge)

Two things distinguish this from a missing-codec gap that should be
closed in-task:

- The Task 96 task file's Phase 0 explicitly mandates stopping, and
  its Out of Scope section explicitly excludes "storage format work
  for 2-bit adoption — separate concern." Building the kernel would
  require first *creating* a storage/scoring surface, which the task
  by its own text does not own.
- ADR-076 kernels are required to be registered against real AM
  scoring surfaces with recall/counter evidence. A speculative
  `lut32_2bit` with zero consumers could not satisfy its own
  acceptance criteria (per-AM registration, scoring-share, recall
  byte-equal) — every AC would be vacuous.

The forward path in the packet is correct: a future storage-surface
task decides whether 2-bit TurboQuant becomes a no-QJL surface (Task
96 resumes, likely as a thin LUT-entry-count parameterization of the
Task 87/94 LUT family) or stays QJL-enabled (the kernel belongs to
Task 97's family).
