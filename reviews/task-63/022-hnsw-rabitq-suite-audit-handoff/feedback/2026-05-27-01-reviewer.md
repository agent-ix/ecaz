## Correctness review (passed)
I specifically checked the items flagged as risky and found them sound:

- **Scoring sign.** `RaBitQScorer::score` returns an inner-product estimate
  (higher = closer); the HNSW scan negates it in
  `score_rabitq_search_code_result` (`scan.rs:2809-2811`,
  `-prepared_query.score(...)`), matching the grouped path's
  `-prepared_query.score(...)` and BeamCandidate "lower is better" ordering.
  Consistent across build/insert/scan.
- **No double query rotation.** Encoder (`encode_code`, `rabitq.rs:451`) and
  query prep (`prepare_ip_query`, `rabitq.rs:420`) each rotate exactly once via
  the same seeded SRHT rotation; the scorer consumes the already-rotated query.
  No double-application.
- **Seed consistency.** Build uses `state.seed` for both the quantizer and the
  stored `metadata.seed` (`build.rs:1646,1668`); scan rebuilds the quantizer
  from `metadata.seed`/`metadata.search_bits` (`scan.rs:2237-2241`); insert uses
  `metadata.seed` (`insert.rs:2077-2081`). All agree.
- **Code-length agreement.** `encode_code` emits exactly `code_len_for(dim,bits)`
  bytes (`rabitq.rs:401-405,451-491`). Scan derives `search_code_len` via
  `rabitq::code_len_for` (`graph.rs:228`); insert asserts the derived code
  length matches `layout.search_code_len` (`insert.rs:2084-2090`). Decode
  validates exact lengths.
- **On-disk backward compat.** New `INDEX_FORMAT_V4_RABITQ = 4` and
  `SearchCodecKind::RaBitQ = 3` are additive; `MetadataPage::decode` accepts
  V1/V2/V3/V4 (`page.rs:327-335`) and `graph_storage_format()` still maps
  V1/V3→TurboQuant, V2→PqFastScan (`page.rs:208-214`). Metadata byte layout (47
  bytes) is unchanged. Existing TurboQuant/PqFastScan indexes load unchanged.
  `from_metadata` round-trips are unit-tested in `codec.rs`.
- **Insert.** Fully implemented (`append_rabitq_tuple`,
  `bootstrap_empty_rabitq_flush_output`, shared backlink planner). The "more
  than one fresh data page" error (`insert.rs:2159`) is the same pre-existing
  limitation shared by TurboQuant (`:1586`) and PqFastScan (`:1966`) — not
  RaBitQ-specific, and it is an explicit hard error, not silent partial support.
- **Vacuum.** Fully implemented — RaBitQ is routed through the shared
  `TQ_GROUPED_HOT_TAG` grouped-hot path for dead-heaptid retention, finalize,
  connection repair, linear-repair top-up, and entry-point repair
  (`vacuum.rs:699-733, 918-939, 1411-1443`). `vacuum_cleanup` is a no-op for
  *all* formats (no page compaction); that is pre-existing behavior, not a
  RaBitQ regression. **The task file's "vacuum reportedly unimplemented" caveat
  is stale and should be removed.**
- The descriptor validates RaBitQ metadata invariants strictly (must have cold
  rerank payload, must not have binary sidecar, search_codec must be RaBitQ,
  `search_subvector_dim == search_bits`, no grouped codebook chain —
  `graph.rs:181-235`).

## Minor findings
- **`GraphStorageDescriptor::RaBitQ(PqFastScanLayout)`** reuses the
  `PqFastScanLayout` struct (also in `InsertFormatAdapter::RaBitQ` /
  `VacuumFormatAdapter::RaBitQ`). It works because RaBitQ pins
  `binary_word_count = 0`, but the type name is misleading and
  `encode_rabitq_hot_tuple` has to defensively error if `binary_word_count != 0`
  (`insert.rs:2103-2105`). A dedicated `RaBitQLayout` (or renamed shared
  `GroupedHotLayout`) would make the invariant structural rather than
  runtime-checked. Non-blocking.
- **RaBitQ requires source vectors at build time** (`build.rs:1702-1704`) and at
  insert time (`insert.rs:2076`). This is correct and consistent, but it means a
  `tqvector`-only column cannot build a RaBitQ HNSW index. Confirm the
  user-facing docs caveat (packet 012/014) states this clearly.
