# Task 60 Review: `ec_diskann` RaBitQ Storage Format

**Verdict:** The code slice is correct and well-structured. No blocker-level
correctness bugs found in the implementation. **However, Task 60 cannot be
closed**: the headline acceptance gates (recall parity, 1M storage win, real
bench rows) are entirely unmet — only dry-run scaffolding exists.

## Correctness / Code Review

### No Blockers found
The core integration is sound. Key positive findings:

- **No kernel duplication (scope §3 satisfied).** `src/am/ec_diskann/quantizer.rs:9,73,343`
  reuse `RaBitQQuantizer`, `PreparedEstimator`, `code_len_for`, `encode_code`,
  `prepare_estimator` from `src/quant/rabitq.rs`. No RaBitQ math is forked into
  the DiskANN tree.
- **Query rotation is not double-applied.** RaBitQ path passes the *raw* query
  to `prepare_estimator` (`quantizer.rs:350`) and relies on the quantizer's
  internal SRHT (`rabitq.rs:516`). This matches the IVF/spire contract
  (`src/am/ec_ivf/quantizer.rs:200`). The grouped-PQ path, by contrast,
  pre-rotates via `encode_query_srht`. Mixing these would be a silent recall
  bug; it is correctly avoided.
- **Scoring sign is consistent.** Prefilter score is "lower = better" (Hamming
  distance / `-grouped_pq_score`). RaBitQ uses
  `-prepared.estimate_ip_scalar_only(...)` (`quantizer.rs:179`), correctly
  converting IP-similarity (higher=better) to distance. Uses the same
  `estimate_ip_scalar_only` fast path IVF uses.
- **Build/scan code-length agree.** Both `BuildParams::search_code_len`
  (`build.rs:89-110`) and scan-time `metadata_search_code_len`
  (`quantizer.rs:207-218`) route through the single
  `quantizer::metadata_search_code_len` → `code_len_for`. No divergent stride
  computation. (204 bytes for 1536-D @ 1 bit, confirmed.)
- **Seed consistency.** Build (`ambuild.rs:280`), bootstrap (`insert.rs:1197`),
  and insert (`quantizer.rs:243-247` reading `metadata.seed`) all anchor the
  RaBitQ rotation to `DEFAULT_QUANT_SEED` / persisted seed. No seed drift
  between build and insert.
- **Materialization-avoidance win preserved (scope §4 satisfied).** For RaBitQ
  with default `prefilter_kind=auto`, `routine.rs:586-590` computes
  `needs_materialized_chain=false` (RaBitQ is not grouped-PQ), so
  `opaque.chain` stays `None` and the scan takes the on-demand
  `RelationGraphReader` branch (`routine.rs:660`). The packet-005 win is not
  regressed.
- **Backward compatibility (scope §5, AC §3 satisfied at code level).** The new
  `decode` validation (`page.rs:141-149`) only accepts codec kinds
  `GROUPED_PQ(2)`/`RABITQ(3)`; existing indexes wrote `GROUPED_PQ`
  (`page.rs:91`), so they still decode. `metadata_binary_word_count` keys off
  the persisted `PAYLOAD_FLAG_BINARY_SIDECAR` flag, not the format — legacy
  sidecar widths preserved. Compat test added (`page.rs`
  `decode_preserves_existing_grouped_pq_metadata`).
- **Rerank unchanged (non-goal honored).** `execute_diskann_scan`
  (`routine.rs:779-794`) reranks via `exact_heap_rerank_distance` from the heap
  `ecvector` column for both formats; nothing format-specific touches rerank.

### Minor

1. **`routine.rs:587-597` — wasteful chain materialization before a guaranteed
   error.** If an operator sets `ec_diskann.prefilter_kind='grouped_pq'` against
   a RaBitQ index, `needs_materialized_chain` is `true` (the
   `matches!(prefilter_kind, GroupedPq)` arm ignores codec), so the *entire*
   index chain is materialized into process memory (line 592) and only *then*
   does `prepare_prefilter` reject it (`quantizer.rs:337-341`). Not a
   correctness bug — it errors out — but it does a full-index allocation purely
   to throw. Suggested direction: short-circuit the grouped-PQ materialization
   when `search_codec_kind == VAMANA_SEARCH_CODEC_RABITQ` before line 591,
   mirroring the explicit reject already present in `prepare_prefilter`.

### Nit

2. **`page.rs:22-25` doc comment is now stale.** The comment still says "Vamana
   metadata page uses SRHT + grouped-PQ search codes" — true only for the
   default format. Worth a line acknowledging RaBitQ codec=3.
3. **`quantizer.rs` reuses `search_subvector_dim` as the RaBitQ bit-width
   carrier** (`build.rs:380`, `quantizer.rs:130,224`). This is a deliberate
   field overload flagged in `request.md` (001). It is internally consistent
   (`rabitq_bits_from_metadata` reads it back), but it is an undocumented
   semantic reuse of a grouped-PQ field name. The ADR-072 adapter direction
   (packet 014) is the right long-term home for this; acceptable for now but
   worth a code comment at the struct field.

## Acceptance-Criteria Gaps (the real blocker for closing the task)

The implementation is landable, but **the task's measurement gates are not
met**. `benchmarks/task60-diskann-rabitq-format/artifacts/` contains only
`suite-dry-run.log` and `suite-manifest.json` — **no `results.jsonl`, no
recall/latency/storage logs.** Every `request.md` (001–014) explicitly defers
this to "the benchmark host."

Unmet acceptance criteria:

- **AC §1** (builds at 100k+ on real corpus) — not demonstrated; only a tiny
  pgrx/SQL smoke (packet 004) exists.
- **AC §2** (recall@10 within a measured, documented delta of pq_fastscan) —
  **no recall numbers exist**; the "acceptable delta" deliverable is undefined.
- **AC §4** (1M index ≥30% smaller than pq_fastscan, or recorded "not worth
  shipping") — **no storage measurement**; the shipping decision is unmade.
- **AC §5** (bench packet records 100k AND 1M with
  `storage_format`/`cache_state`/host-parity) — suite is correctly *scaffolded*
  for this (`suite.json` covers both scales, both formats, with the required
  fields, audited at 24 steps), but **never executed**.

The suite scaffolding itself is compliant with the workflow rules (driven by
`ecaz bench suite`, no ad-hoc sweeper, fields present), so the remaining work is
purely the host run + recording the delta and shipping decision.
