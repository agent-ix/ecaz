# Task 200 — settle the Task 188 reconnect workaround by rerun, not inference

Addendum to `2026-07-28-05-reviewer.md`. The ACCEPT stands. This names the one
claim in the closeout that rests on inference, and the run that would settle it.

## The gap

Task 200's Phase 3 B item 4 says to remove the Task 188 reconnect workaround
"once the bound is in and the regression test passes." Both conditions are now
met, so on the current text the workaround is removable.

It should not be removed yet, because **nothing has demonstrated that this fix
accounts for Task 188's 52 GB.**

What is established is circumstantial, and the packets are careful to say so:
`task188-batch10-stage-counters-suite.json` sets `head_policy:
training_landmarks` and `physical_benchmark: true` and sets neither
`stage_counter_only` nor `skip_recall`, so it satisfied the gate at
`distann_multicluster.rs:4229` and *would* have issued the coverage statement.
The task file states this as "plausibly this same statement." That is the right
word, and it is not evidence.

The competing explanation has never been ruled out. Task 188's workaround was
`benchmark_backend_batch_size: 5` — reconnecting every five **queries** — and it
appeared to help. A defect confined to a single coverage statement should be
largely indifferent to reconnecting between queries, because the statement's
transaction ends either way. That the workaround seemed to work is weak evidence
for a *second*, query-scoped mechanism that Task 200 never reproduced: the
production A1 loop was flat before the fix, so if such a mechanism exists it is
not on the ordinary read path, but Task 188's arm differs from A1 in stage
counters, beam width, and the seed-variant matrix.

Most likely this is all one defect and the workaround was cargo-culted onto a
run that would have survived without it. That is a hypothesis.

## The run that settles it

Task 188's own step, on the fixed build, with the workaround **off**:

- `benchmark_backend_batch_size: 0` (one backend, no reconnect);
- otherwise `task188-batch10-stage-counters-suite.json` unchanged — stage
  counters on, `skip_recall` absent so the coverage statement runs, both
  seed variants, `benchmark_iterations` as configured;
- `--sample-backend-memory` with the series retained.

Outcomes:

- **Bounded** → this fix accounts for the 52 GB, the workaround is dead weight,
  remove it and record the series as the reason. Task 200 closes fully.
- **Grows** → there is a second mechanism, Task 200's closeout is scoped to the
  coverage statement only, and the workaround stays until that is found. This is
  the outcome that matters, because it is the one the current text would let
  slip through.

Run it on the fixed extension from a **committed** tree, so the result does not
inherit follow-up 2 from feedback 005.

Phase 3 B item 4 currently reads:

> Remove the Task 188 reconnect workaround once the bound is in and the
> regression test passes.

Both conditions are satisfied, which makes removal look authorized. Tighten it:

> Remove the Task 188 reconnect workaround once Task 188's own step has been
> rerun on the fixed build with `benchmark_backend_batch_size: 0` and shown
> bounded RSS, with the series in the packet. Do not remove it on the strength

Small edit, and it is the difference between a closeout that proves the
workaround is unnecessary and one that assumes it.
