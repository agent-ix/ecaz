## P0 — the `#[pg_test]` is very likely incapable of detecting this defect

`test_distann_physical_seed_detoast_memory_is_bounded` ran and passed
(`pg18-seed-memory-regression.log:22`,
`test tests::pg_test_distann_physical_seed_detoast_memory_is_bounded ... ok`).
That it passes on the fixed build is expected. Nothing shows it fails on the
broken one, and the arithmetic says it would not.

The defect is **one detoast copy retained per row scanned, per call**. Its
magnitude is entirely a function of rows × row size. This test's fixture is:

- a one-row physical graph — the test itself asserts
  `rows == 1, "the one-row physical graph should yield one seed"`;
- 4-dimensional vectors (`ARRAY[1.0, 0.0, 0.0, 0.0]::real[]`).

So pre-fix, each call leaked a single detoast copy of one small `graph_record`.
Across `ITERATIONS = 300` that is on the order of tens to low hundreds of KB —
against `MAX_GROWTH_BYTES = 4 * 1024 * 1024`. **The test would have passed on
`fa84ff3b0^`.**

For scale: the real defect leaked ~33,000 rows × ~6 KB **per call**. This fixture
is five orders of magnitude smaller per call.

Required, and it is the same bar the integration gate was held to: run this test
at `fa84ff3b0^` and record the result.

- If it fails there — good, record the red run and this finding closes.
- If it passes there — as expected — the test is a no-op guard and must be made
  capable: more rows in the fixture, wider vectors, or a budget derived from the
  measured per-call retention at this fixture size rather than a round 4 MB. A
  budget must be set from what the defect *would* produce, not from what looks
  comfortably large.

## P0 — the unattended test does not run under the standard command

The test is `#[cfg(feature = "distann-head-attribution-benchmark")]`, and the
recorded invocation required it explicitly:

```
PGRX_FEATURES="pg18 pg_test distann-head-attribution-benchmark"
```

`CLAUDE.md` names `cargo pgrx test pg18` as the validation command. Without that
feature the test is not compiled in, so the standard command does not run it and
neither will anyone changing `generation_read.rs` next month.

Either fold it into whatever feature set the standard command uses, or state in
the packet and in the test's doc comment the exact command required and get that
command into the repo's documented validation path. An unattended test nobody
invokes is the same problem as a manual one.

## P1 — the integration gate passed a run where RSS grew 20×

`executable-regression-run` result line:

```
coverage_invocations=300 samples=16609
rss_first_kb=19556 rss_last_kb=396632 rss_delta_kb=377076
rss_slope_kb_per_s=5.82 max_slope_kb_per_s=1024.00 pass=true
```

RSS went from 19.5 MB to 396.6 MB — **+377 MB** — and the gate reported a slope
of 5.82 KB/s and passed.

Reading the series explains it and does not excuse it. Sampling is ~27 ms
(`elapsed_ms=0, 27, 54`), 16609 samples over ~454 s, and the shape is a fast
climb to ~402 MB followed by a long plateau
(`elapsed_ms=454152 rss_kb=401968`). That plateau matches the clean manual run's
402 MB steady state, so this is very likely cold-start warm-up, not a leak.

But the least-squares slope is dominated by the plateau and is nearly blind to
the step: 5.82 KB/s × 454 s predicts a 2.6 MB rise against 377 MB observed. A
future defect shaped as *fast rise then plateau at a higher level* — an unbounded
cache filling, a per-backend structure sized by corpus — produces a small slope
and passes.

I asked for slope over peak, and that was right for a linear leak; this run shows
slope alone is not sufficient. Compute the statistic over the **post-warm-up**
segment: discard samples until RSS stabilises, then assert both slope and
absolute delta across the remainder. The clean run gives the budget directly —
828 KB peak-to-trough at steady state — so a post-warm-up delta bound of a few MB
is available and is ~100× tighter than what the gate currently enforces.

Whatever is chosen, the packet must state why a 377 MB delta is an acceptable
pass. Right now nothing does.

## P1 — the green run does not match the committed config

The committed configs now both carry
`"coverage_memory_regression_max_slope_kb_per_s": 100.0` — the tightening I asked
for, in both the positive and negative suites. Good.

But the recorded green run was executed at `max_slope_kb_per_s=1024.00`. The

is a formality the packet has to discharge: re-run at the committed threshold, or
state explicitly that the recorded run predates the tightening and why the
recorded slope is sufficient.
