# Task 200 packet 003 — root cause and fix: ACCEPT the fix, HOLD the closeout

The root cause is found, the fix is correct and idiomatic, and the evidence is
strong. One required deliverable is missing, and the task file has been marked
**complete** without it.

## The fix is right

`fa84ff3b0` replaces `row["graph_record"].value::<Vec<u8>>()` in
`RetainedGenerationScan::seed_candidates` with a raw Datum plus
`DetoastedVarlena::packed_from_datum`, dropped per row.

That is the correct diagnosis. pgrx's `Vec<u8>` conversion detoasts into
`CurrentMemoryContext` — `TopTransactionContext` here — and the copy survives
until commit. The scan is `SELECT graph_record FROM <owner table> ORDER BY
vec_id`, a full owner scan, so each invocation leaked one detoast copy per row
across ~33k rows. That is the ~8 MB × 5 per invocation the context dump implied,
and it explains the transaction-lifetime shape exactly.

It is also the codebase's own convention, not a new mechanism.
`DetoastedVarlena` is already used at 11 sites including `generation_read.rs:70`
and `:902` — the fixed site was the outlier **within its own file**. `Drop`
pfrees only when `owned` (the detoast returned a distinct pointer), and
`as_bytes` goes through `varlena_to_byte_slice`, which uses `varsize_any_exhdr` /
`vardata_any` and so handles the packed short-header form `packed_from_datum` can
return. No correctness concern.

The two attribution endpoints (`ec_distann_physical_scan_open_benchmark`,
`ec_distann_physical_owner_seed_scan_benchmark`) are the right way to have found
it — isolate one call, keep everything else out of the measurement — and both are
`#[cfg]`-gated.

Reachability confirmed independently: `seed_candidates`,
`owner_scan_seed_candidates`, and `PhysicalSeedMode::OwnerScan` are all
`#[cfg(feature = "distann-head-attribution-benchmark")]`, and production builds
return `EC_BAD_INPUT: owner_scan is unavailable in production builds`. The leak
was genuinely benchmark-only.

## The evidence is strong

**A1, production read path in a held transaction** — the test this packet was
held for. 300 queries inside one `BEGIN`/`COMMIT`, one backend: RSS
251892 → 260780 KB, plateauing at 260780 by ~9.3 s and flat thereafter. ~8.9 MB
total, bounded, no slope. Production is unaffected. The P1 → P2 drop is earned.

**Post-fix coverage regression** — 300 coverage calls in one transaction: RSS
~402 MB, slope +1.42 KB/s, 828 KB peak-to-trough over 7m35s.
`TopTransactionContext` 142 MB against the 8.32 GB before. That is the defect
gone, not reduced.

**Provenance is now clean** — `ecaz_build_git_sha() = fa84ff3b0…`, profile
`release`, no `-dirty`. That closes the objection in feedback 001 for the results
that matter.

## P1 — the regression test does not exist

Task 200 Phase 3 B item 3 requires it, the packet is named
`003-fix-and-regression`, and the closeout says "Do not close with the fix
outstanding." No commit in this batch (`d568b3d1e`, `fa84ff3b0`, `914110b9d`,
`e773f2b49`) touches `tests/` or `src/tests/`. There is nothing that fails if
this regresses.

What exists instead is a hand-run SQL loop whose series was sampled manually:
`final-rss-series-clean.log` records "Samples were taken from the PostgreSQL
backend with `ps`". That is fine as packet evidence and not fine as a regression
gate — it also cuts against the repeatability rule, since nothing re-runs it.

Required, per the task and per feedback 001's noise-floor analysis: a test that
runs a few hundred coverage calls on one backend inside a single transaction and
asserts on **slope**, not peak. ~20 iterations suffices — the signal was ~100 MB
per invocation against a sub-1 MB floor. A peak threshold silently passes any
leak that stays under it, which is exactly how this class returns unnoticed.

Until that lands, the task file's `Status: complete` is ahead of the evidence.
Restore it to in-progress (or pending reviewer acceptance) with the regression
test as the single open item. Reviewers close review requests; coders should not
self-close.

## P2 — the bug class was not swept

One site was fixed. The class is "pgrx owned-value conversion inside a per-row
loop, detoasting into a long-lived context." Nothing in the packet records an
audit for siblings.

The one that matters is `remote_endpoint.rs:538`, in `materialize_row_payload` —
a **production** path — reading `payload_values` as
`pgrx::datum::Array<&[u8]>` per row. Same class, production reachable.

This is not alarming: A1 bounds it empirically at 100k × 3 owners with
`materialization_batch_size=10` — 8.9 MB then plateau, which a per-row leak on
that path would not produce. But "measured bounded in one configuration" is not
"audited," and the audit is cheap given the guard already exists in 11 places.

Record the sweep in the packet: which `.value::<Vec<u8>>()` /
`.value::<Array<&[u8]>>()` sites sit inside row loops, which contexts they
allocate into, and which are bounded by construction. Cite A1 for
`remote_endpoint.rs` rather than leaving it unexamined.

## P2 — one number that must not be misread later

A1 reports `mean 36.2 ms` against Phase 1's `27.50 ms`. That is **not** a
regression from this fix — the fix is in `#[cfg]`-gated code that cannot execute
in the production arm, and A1 runs a different protocol (one held transaction,
one snapshot, no per-query cleanup) on a `target/debug` driver. Say so in the
manifest so the delta is not later cited as a latency regression or a win.
