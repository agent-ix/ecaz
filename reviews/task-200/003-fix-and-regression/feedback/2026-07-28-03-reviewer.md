# Task 200 packet 003 — REQUEST CHANGES: the regression gate has never run

Re-review after `ff057bf71` and `586a122cd`. Two of four findings from
`2026-07-28-02-reviewer.md` are handled. The one that blocks merge is not.

**Not approving.** This cannot merge without a test that has actually run and
actually passed.

## P0 — the gate exists on paper only

`artifacts/executable-regression-run/` contains a single file,
`suite-manifest.json`, and its one step reads:

```
coverage-held-transaction-100k -> status: "dry-run"
```

The gate has **never been executed**. It has never passed. Its assertion has
never fired in either direction. `request.md` states this plainly — "the
integration run is the remaining closeout action" — which is the correct
disclosure, and it also means the packet is not reviewable as a regression
packet yet.

Code that asserts is not a test until it runs. A gate whose exit path has never
been exercised is an untested assertion about an untested assertion.

## P0 — the gate was never validated against the pre-fix build

Even once it runs green, a regression gate that has only ever been observed
passing proves nothing about its ability to detect the defect. The negative
control is mandatory here and it is cheap, because the exact broken commit is
known:

1. run the gate at `fa84ff3b0^` (pre-fix) — it **must fail**, and the failure
   line must show a slope in the ~100,000 KB/s range;
2. run it at `fa84ff3b0` or later — it must pass at ~1 KB/s.

Both outcomes go in the packet. Without step 1 there is no evidence the gate
detects anything; it would have passed just as happily against the build that
consumed 52 GB if the threshold or the slope computation were wrong.

## P1 — the threshold is 720× looser than the measured floor

`--coverage-memory-regression-max-slope-kb-per-s` defaults to `1024.0`. The clean
post-fix measurement was **+1.42 KB/s**; the defect was ~100 MB/s
(~102,400 KB/s).

So the default sits three orders of magnitude above the floor and two below the
defect. It would catch this exact bug, and it would silently pass a leak at
500 KB/s — 30 MB/minute, 1.8 GB/hour, which is precisely the "gradual backend
bloat nobody attributes to `ec_distann`" the task was filed about.

Set the default from the measured floor, not from the defect: something in the
50–100 KB/s range keeps a 35–70× margin over observed noise and still catches
anything of consequence. If a looser value is deliberate, justify it in the
manifest against the measured floor.

## P1 — nothing runs this automatically

The repository standard is that a merge needs tests. This gate is a CLI flag on a
benchmark fixture: it needs a live three-node cluster, a staged 100k corpus, and
a manual `ecaz bench suite run`. No `cargo test`, no `cargo pgrx test pg18`, no
CI path reaches it. Nothing will run it on the next change to
`generation_read.rs`, which is the only circumstance in which a regression gate
has value.

The integration gate is worth keeping — it is the only thing that can exercise
the real three-owner path. But it does not substitute for a test that runs
unattended. Add a `cargo pgrx test pg18` case that exercises the same conversion
at whatever scale a single-node test fixture allows and asserts bounded growth
across a few hundred iterations in one transaction. Small scale is fine: the
mechanism is per-row detoast retention, so it reproduces at any row count that
makes the slope exceed noise, and it does not need three owners.

Both layers, then: unattended test for the mechanism, integration gate for the
real topology.
