# Task 200 — reuse fixtures; stop rebuilding identical data

Operator-directed. Two actions: reuse the fixture that already exists for Phase
2, and land fixture reuse in the suite runner so arms that differ only by a
runtime setting share one build.

## The waste

`distann_multicluster.rs:513-528` wipes the run directory
(`fs::remove_dir_all`) and re-`initdb`s every node on **every** invocation. There
is no reuse path and no flag to skip it.

Task 200 has therefore built the same 100k three-node fixture three times:

1. run 1, counters-off — died during the coverage query;
2. run 2, counters-off — deleted run 1's fixture, rebuilt it identically, then
   ran 8 seconds of queries;
3. run 3, counters-on — a third copy of the same corpus, same graph parameters,
   same seed, on separate ports.

The counters-off step took 1,602,595 ms end to end. The measurement inside it ran
from `elapsed_ms=0` to `elapsed_ms=8067`. **Over 99% of that run was rebuilding
data that already existed, byte-identical.**

Arm 3 is the clearest case: counters-on versus counters-off is a **GUC**. It
needs no different corpus, no different graph, no different cluster. That entire
rebuild exists only because the runner cannot say "same fixture, toggle the
setting, run the second arm."

## Action 1 — Phase 2 reuses the fixture on disk now

`/home/peter/.ecaz/clusters/task200-counters-off-100k/` — `node1`, `node2`,
`node3`, **6.8 GB**, corpus loaded, graph built, generation published. This is
the exact fixture behind the counters-off series in this packet. Its postmasters
are stopped; the data directories are intact. Restarting PostgreSQL on an
existing PGDATA takes seconds.

**Do not rebuild anything for Phase 2.** Reuse those three data directories as
they stand — corpus, graph, and published generation all intact. Start fresh
backends against them and run the diagnostics; nothing about the fixture needs to
change for any of the three checks below. Base port 42080 (nodes on
42080/42081/42082), `listen_addresses=127.0.0.1`, `unix_socket_directories`
empty, so TCP only. Start each node against its existing data directory with
`shared_preload_libraries=ecaz`, then drive it through `ecaz dev sql` per the
operator-CLI rule.

All three Phase 2 checks from feedback 002 run against that one live fixture, in
minutes:

1. `pg_log_backend_memory_contexts(<pid>)` at two or three points as RSS climbs —
   settles palloc vs. Rust-side allocation, the branch point for the whole
   investigation;
2. 200 separate `ec_distann_physical_seed_coverage_benchmark(...)` statements vs.
   one 200-way `CROSS JOIN LATERAL` — settles whether retention is
   statement-scoped;
3. RSS slope over ~20 iterations rather than a peak over several hundred, per the
   noise floor in feedback 001 (sub-1 MB drift against ~100 MB per round).

Take the index regclass and a query vector from the live fixture rather than
reconstructing them.

**Preserve that directory until Phase 2 has run against it.** It is the only
pre-built copy of the state that produced the 14.5 GB observation, and two things
would destroy it: any `distann-multicluster` invocation carrying that
`--run-dir`, and the standing guidance to remove run directories once cited
results are captured. Hold that cleanup, record the exception in
`artifacts/manifest.md`, and remove the directory once attribution is captured.

## What "reuse" means, exactly

**Reused — the built fixture.** Concretely, the three PGDATA directories under
the run directory (`node1`, `node2`, `node3`) and everything already materialized
inside them:

- the initialized PostgreSQL clusters (`initdb` output, config, the installed
  `ecaz` extension);
- the loaded corpus rows — the ~33k rows per owner recorded in
  `physical_topology`;
- the built physical graph and the head sample (`graph_bytes`, `row_bytes`,
  `directory_bytes` per node; `head_sample_bytes`, `head_graph_bytes`);
- the **published generation** — the sealed, active epoch the read path serves,
  the state `physical_topology phase=published` attests.

That is the expensive artifact. It is deterministic given corpus + build
parameters + seed, so rebuilding it produces a byte-equivalent result and buys
nothing.

**Not reused — everything downstream of the fixture.** Every measurement is
re-executed against the reused fixture, every time:

- the query loop and all its results — recall, latency, storage, coverage;
- all GUCs and session state, including `distann_stage_counters`;
- seed-variant controls, iteration counts, warmups, batch sizes, sampling
  intervals;
- backend connections — a reused fixture still gets fresh backends, which
  matters here, since backend-lifetime state is the thing under investigation.

**Never reused — anything that changes what got built.** Listed under the refusal
rule below; those force a rebuild.

The line is: reuse the *data*, re-run the *measurement*. No result is ever
carried across runs — only the corpus, graph, and generation the results are
measured against.

## Action 2 — land fixture reuse in the suite runner

Extend the runner rather than scripting around it, per the FR-038 rule. Add a
reuse option on the `distann-local-multinode` fixture step:

- **Reuse when the existing run directory already holds a published generation
  matching the requested corpus prefix, scale, graph parameters, seed, and
  extension build**; rebuild otherwise. Match on the identity the fixture already
  attests — the provenance lines carry `corpus_prefix`, `query_sha256`,
  `extension_git_sha`, and `extension_build_profile`, so the check is a
  comparison against recorded values, not a new mechanism.
- **Refuse to reuse across a build-affecting difference.** A changed corpus,
  scale, graph degree, head cap, seed, codec, or extension SHA forces a rebuild.
  Runtime-only differences — GUCs such as `distann_stage_counters`, seed-variant
  controls, iteration counts, sampling — do not.
- **Record the decision in the manifest.** Every step emits whether it built or
  reused, and on reuse, the identity it matched against. A reused fixture must be
  as traceable as a built one.
- **Keep rebuild the default.** Reuse is opt-in, so no existing packet changes
  behavior and no measurement silently inherits a stale graph.

This makes the counters-on/counters-off pair one build instead of two, and it
makes the A/B **stronger**: both arms measured against one identical index, so
any difference is attributable to the counter setting rather than to build
variance between two independent builds.

Land it as its own commit before the next packet uses it, per the suite-runner
rule.
