# Task 200 — do not rebuild the fixture for Phase 2; one already exists

Supersedes one suggestion in `2026-07-27-02-reviewer.md` and adds a preservation
request. Operator-directed.

## Retraction

I was drafting a suggestion to add a fixture-reuse option to the suite runner,
on the reasoning that `distann_multicluster.rs:513-528` wipes the run directory
(`fs::remove_dir_all`) and re-`initdb`s on **every** invocation, so an iterative
attribution loop would pay a full rebuild per iteration.

The wipe is real and unconditional. The conclusion was not. The wipe happens when
you *launch the fixture command* — nothing requires launching it again. Phase 2
needs a running database and a SQL client, not the fixture driver. **Withdraw the
reuse-flag suggestion.** If Phase 2 turns out to genuinely need many independent
rebuilds, it can be revisited then; do not build it on speculation.

## What already exists

`/home/peter/.ecaz/clusters/task200-counters-off-100k/` — `node1`, `node2`,
`node3`, **6.8 GB**, corpus loaded, graph built, generation published. This is
the exact fixture behind the counters-off series in this packet.

Its postmasters are stopped (only the in-flight counters-on run at base port
42180 is up), but the data directories are intact. Restarting PostgreSQL on an
existing PGDATA is seconds. **There is no reason to rebuild anything for Phase
2.**

## Preserve it

This is the only pre-built copy of the state that produced the 14.5 GB
observation. Two things would destroy it:

1. any `distann-multicluster` invocation with
   `--run-dir /home/peter/.ecaz/clusters/task200-counters-off-100k` — line 513
   wipes first;
2. the standing guidance to remove run directories once cited results are
   captured, which normally would apply here.

**Hold that cleanup until Phase 2 has run against it**, and record the exception
plus the reason in `artifacts/manifest.md`. Remove it immediately afterwards —
6.8 GB is not free on this host, and the counters-on fixture is a second copy of
comparable size.

## Reuse it

Base port 42080 (nodes on 42080/42081/42082), `listen_addresses=127.0.0.1`,
`unix_socket_directories` empty, so TCP only. Start each node against its
existing data directory with the same `shared_preload_libraries=ecaz`, then drive
it through `ecaz dev sql` per the operator-CLI rule.

The three Phase 2 checks from feedback 002 all run against that one live fixture:

1. `pg_log_backend_memory_contexts(<pid>)` at two or three points as RSS climbs —
   settles palloc vs. Rust-side allocation, which is the branch point for the
   whole investigation;
2. 200 separate `ec_distann_physical_seed_coverage_benchmark(...)` statements vs.
   one 200-way `CROSS JOIN LATERAL` — settles whether retention is
   statement-scoped;
3. RSS slope over ~20 iterations rather than a peak over several hundred, per the
   noise floor in feedback 001 (sub-1 MB drift against ~100 MB per round).

Minutes, on data that already exists. Take the index regclass and a query vector
from the live fixture rather than reconstructing them.

## Provenance note

Reusing a fixture across arms is normally a smell, and the wipe-and-rebuild
default is correct for measurement packets — it is what stops stale state
leaking between arms. This is not a measurement run; it is call-site attribution
on a fixture whose build provenance is already recorded in this packet. State
that distinction in `manifest.md` so the reuse is a recorded decision rather than
a silent one, and rebuild from scratch for any A/B that follows a fix.
