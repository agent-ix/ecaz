# Task 200 — attribution leads from source reading

Follow-on to `2026-07-27-01-reviewer.md`. This is source reading only; no
allocator tool was run and nothing here is proven. It is offered so Phase 2 does
not start from the task file's suggested list, two entries of which now look
wrong.

## Ruled out this pass

**`head_cache.rs` — confirmed bounded.** `CacheMap = HashMap<u32,
Arc<DistannIndexCacheEntry>>` keyed on `index_oid`; `cached_index_entry` either
returns `Arc::clone` on a fingerprint match or `insert`s, which drops the prior
`Arc`. One entry per index, replaced in place. Agrees with the task file.

**`remote_transport.rs` — confirmed bounded, contrary to the task file.** The
task names "remote transport buffers" as a suggested starting point. It should
be demoted. `DistannTransportState` is a single `thread_local` holding one
`current_thread` tokio runtime plus `connections: HashMap<String,
PooledConnection>` keyed by `lifecycle_connection_key(conninfo)` —
`ensure_pooled_connections` reuses by key, `PooledConnection::Drop` aborts its
task, and `with_transport_state` clears the whole map when an interrupt is
observed. Per-call scratch (`vec_ids_i64`, `node_id_strs`) is owned locally and
dropped. Nothing here accumulates across calls.

## The shape the curve implies

From `early-rss-observation.md`: 2.4 GB at 24 s → 14.5 GB at 145 s. That is
~100 MB/s, near-linear, inside **one** statement. The statement is 200 lateral
invocations of the coverage benchmark, so ~72–100 MB **per invocation**.

That number is too large to be any bounded Rust structure being cloned and too
regular to be fragmentation. It is the size of a per-call allocation that is
never released *within the statement*.

Which points at the thing the coverage function does that the production read
path does not: it calls `PhysicalGenerationScan::open(index_regclass.oid())` on
**every** lateral invocation (`generation_read.rs:1735`). The production
CustomScan opens once per scan. 200 opens inside one statement is a workload no
other caller generates.

`open_once` (`generation_read.rs:2189`) per call does: `open_control_index`
(relation open + `AccessShareLock`), `active_generation_identity`,
`ScanTokenGuard::register_checked`, a second `active_generation_identity`, then
either a `cached_physical_epoch` hit or `load_build_candidate`. Several of those
paths run SPI (`generation_catalog.rs` has 13 `Spi::connect*` sites).

## Why this reframes the diagnostic tool

If the retention is **palloc-side** — SPI results, relation-open detritus, or
anything allocated in a per-query rather than per-tuple context — then it is
freed at statement end and invisible across a query loop. That is exactly the
observed split: 14.5 GB inside one statement, flat 261 MB across 300 separate
statements.

And it inverts the task file's premise. Task 200 says "`pg_backend_memory_contexts`
will not show it" because the state is Rust-allocated outside PostgreSQL's
contexts. That reasoning holds for `static`/`thread_local` growth across
statements. It does not hold for intra-statement palloc growth, which
PostgreSQL's own reporting shows precisely.

**So run the cheap test before reaching for heaptrack.** Re-run the coverage
statement on one backend and, from a second session, call
`pg_log_backend_memory_contexts(<pid>)` two or three times as RSS climbs. The
dump lands in the node log.

- A context growing into the GB range names the culprit almost directly, and the
  fix is a per-call context reset or hoisting the `open()` out of the lateral.
- All contexts small while RSS is at 10 GB rules palloc out and *earns* the
  heaptrack/massif run the task anticipates.

Either outcome is decisive, it costs one run, and it is available now.

## Second, cheaper discriminator

Call the coverage function directly in a loop against one backend — no fixture,
no suite:

```sql
SELECT * FROM ec_distann_physical_seed_coverage_benchmark(:idx, :q, 32, 32);
```

200 separate statements versus one statement with 200 lateral invocations, same
backend, RSS sampled. If the loop is flat and the lateral grows, the retention is
statement-scoped and the search collapses to the per-call `open()` path. This
also tests the Task 188 hypothesis in packet 001's first finding directly.

## Standing caveat

`PhysicalGenerationScan::open` per lateral call is a *benchmark* misuse, not
necessarily a production defect. If that is where this lands, the honest closeout
is the task's second branch — bound it, document the mechanism, record why the
production path is unaffected, with the counters-off series as the evidence — and
the P1 priority on this task comes down.
