# Task 200 packet 002 — attribution: REQUEST CHANGES

The evidence collected here is good and the reuse work landed cleanly. But the
packet cites the one number from the memory-context dump that carries no
attribution, and the "separate statement" comparison did not do what it claims.
Both are fixable from artifacts you already have.

## P1 — the dump names the culprit; the packet cites the total instead

`attribution-summary.md` and `manifest.md` both quote
`Grand total: 8323959872 bytes ... 8314784136 used`. The line directly under it
in `001-reproduction/artifacts/run-latency-rerun/diagnostic-node1.log:127` is the
finding:

```
level: 2; TopTransactionContext: 8321499136 total in 1002 blocks;
          8603128 free (6895 chunks); 8312896008 used
```

**8.32 GB of the 8.32 GB grand total — 99.97% — is in `TopTransactionContext`.**
Every other context in that dump is trivial: `CacheMemoryContext` 1.07 MB,
`TopMemoryContext` 132 KB, `ExecutorState` 82 KB, `ExprContext` 8 KB.

That is the attribution Phase 2 asked for at the context level, and it settles
the question the whole task was framed around:

- The memory is **PostgreSQL-allocated, in a PostgreSQL memory context**, fully
  visible to `pg_backend_memory_contexts`. It is not Rust-side `static` /
  `thread_local` state. The task file's premise — "these subsystems hold large
  state outside PostgreSQL's memory contexts … `pg_backend_memory_contexts` will
  not show it" — is **wrong for this defect**, and the packet should say so
  explicitly. That premise is why Phase 2 was scoped to expect heaptrack/massif;
  it is not needed.
- `TopTransactionContext` is **transaction**-lifetime, not statement-lifetime. It
  is reset at commit/abort. That single fact explains both observations at once:
  the 300-query production loop runs one transaction per query, so the context is
  discarded 300 times and RSS stays at 261 MB; the coverage statement is one
  transaction, so nothing is reclaimed until it ends.

Also worth recording: 8.32 GB in **1002 blocks** is ~8.3 MB per block. PostgreSQL
gives oversized chunks their own block, so this is on the order of 1000 large
allocations — roughly 5 per lateral invocation — not millions of small ones. That
is a strong narrowing hint for call-site work.

**Action:** rewrite `attribution-summary.md` around the `TopTransactionContext`
line, not the grand total. Quote the level-2 line verbatim.

## P1 — the "separate statement" run was not separate transactions

`coverage-separate-200.log` is cited as a separate-statement comparison showing
growth from ~1.9 GB to ~3.6 GB across 14 calls, and packet 002 reads that as the
same growth pattern outside a single statement.

The node log shows how it was actually sent
(`diagnostic-node1.log:279`, one `STATEMENT:` entry):

```
SELECT 0 AS query_ordinal, ... ;\nSELECT 1 AS query_ordinal, ... ;\nSELECT 2 ...
```

All 200 statements went in **one simple-query protocol message**. PostgreSQL
executes a multi-statement simple-query string inside a **single implicit
transaction**. So `TopTransactionContext` was never reset between those 14 calls
— they were separate *statements* but one *transaction*.

The test therefore cannot distinguish the two hypotheses it was run to
distinguish, and its 1.9 → 3.6 GB figure must not be cited as evidence that
growth survives statement boundaries. Given the `TopTransactionContext` finding,
the result is exactly what transaction-scoped accumulation predicts.

**Action:** re-run with each call as its own round trip — a shell loop of
`ecaz dev sql` invocations, or `psql -c` per statement — so each commits. Sample
RSS across the whole loop. Expected result if the current picture holds: flat,
because each commit discards the context. If it is *not* flat, the defect is
larger than currently believed and the production conclusion in packet 003 does
not hold.

## P2 — attribution stops at the function, not the call site

Phase 2 asks to "attribute the allocation to a call site." Packet 002 concludes
"the benchmark-only seed-coverage implementation" — which is where packet 001
already stood. The context is now known; the call site is not.

The search space is small and the constraints are tight:

- There is **no `MemoryContextSwitchTo` anywhere in production `src/`** — only in
  `src/tests/ec_distann_basic.rs`. So nothing is deliberately allocating into
  `TopTransactionContext`; these allocations land there because
  `CurrentMemoryContext` *is* `TopTransactionContext` when they run.
- ~5 allocations of ~8 MB per invocation.
- No SPI contexts appear in the dump, so SPI result retention is not the holder.

The candidate that fits: the coverage helper calls
`PhysicalGenerationScan::open(index_regclass.oid())` on **every** lateral
invocation (`generation_read.rs:1735`), where the production CustomScan opens
once per scan.

Note packet 002 states the growth is attributable "not
`PhysicalGenerationScan::open` on the production read path." That is a true
statement about the *production read path* and not evidence about `open()`
itself — the coverage helper calls the same function, 200 times per statement.
Ruling it out requires a measurement, not the distinction between callers.

**Action:** one experiment settles it — call `PhysicalGenerationScan::open` 200
times in a loop without the surrounding coverage work (or comment the rest of the
helper body out in a scratch build) and sample RSS.
