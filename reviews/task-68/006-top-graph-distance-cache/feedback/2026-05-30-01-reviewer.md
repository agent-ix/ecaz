## Code shape

`SpireTopGraphDistances` enum with two variants:

- `Matrix { node_count, distances: Vec<f32> }` — precomputed
  `node_count²` flat matrix, used when the matrix fits the 64 MiB
  cap.
- `Direct { nodes, distance_offset }` — falls back to the original
  per-pair `inner_product` closure.

`distance(a, b)` dispatches via match. The Vamana builder still
sees the same closure-like interface (`let dist = |a: u32, b: u32|
-> f32 { distances.distance(a, b) }`) so the upstream caller is
unchanged.

What's preserved:

- The shared `spire_top_graph_direct_distance` helper is used by
  both the matrix-fill loop and the direct fallback, guaranteeing
  byte-identical pair distances regardless of which variant is
  chosen.
- IP-derived pseudo-distance expression and `(distance_offset -
  inner_product).max(0.0)` clamping are byte-identical to the
  original closure.
- `max_centroid_norm_sq(nodes)` is called exactly once for both
  variants (it was the original closure's free variable too).

What's gained:

- For `nlists * recursive_fanout = 128` nodes at 100k:
  `128² × 4 B = 64 KiB` matrix → fits comfortably.
- For the Vamana builder which calls `dist(a, b)` many times per
  iteration over the same node pairs (greedy search + robust
  prune), the matrix turns repeated `inner_product` over 1536-dim
  vectors into a single load from a hot ~64 KiB region. That's
  the cap-relevant win.

## Memory cap

`SPIRE_TOP_GRAPH_DISTANCE_MATRIX_MAX_BYTES = 64 MiB`. At 4 B/entry
that's a 4096-node ceiling — i.e. the matrix path is taken for
SPIRE top graphs up to 4096 routing nodes. Beyond that the slow
direct path is used, which is the original behaviour, so no
regression risk for very large top graphs.

The `node_count.checked_mul(node_count)` + `checked_mul(size_of)`
guards correctly avoid usize overflow at extreme sizes. Falls
through to direct on overflow, also correct.

64 MiB is a reasonable in-process build-time cap. If SPIRE moves
to top-graph sizes beyond 4096 nodes, the cap can be revisited.
For today's deployment shapes, the matrix path is always taken,
which is what the measurement should confirm.

## Determinism

Matrix fill is `for a in 0..node_count { for b in 0..node_count { ... } }`
— fixed source-order. Each cell uses the same
`spire_top_graph_direct_distance` function the fallback uses. The
new test
`top_graph_matrix_distances_match_direct_distance_function`
asserts cell-by-cell equality on a small graph. Byte-equal output
vs the pre-cache implementation is preserved.

The diagonal entries are filled (`a == b` case computes
`(offset - dot(a, a)).max(0.0)`), which is what Vamana would
compute on the fly too. No semantic difference.
