## Instrumentation correctness — concerns to flag

### Phase double-counting

`draft_ms` in the recursive path is the outer wall time of
`build_recursive_epoch_input_from_centroid_plan_with_timing`. That
function internally records `recursive_kmeans_ms` and
`recursive_assignment_ms`. So `draft_ms` ⊇
`recursive_kmeans_ms + recursive_assignment_ms`. Today the inner
times are tiny (≤ 2 ms at the measured shapes) so the overlap doesn't
distort the ranking, but the ranking text should call it out
explicitly so future packets don't sum these as if they were
disjoint.

Similarly, `object_store_ms` in the recursive top-graph path is the
outer wall time around `build_recursive_top_graph_epoch_from_leaf_inputs_with_store`,
which internally records `top_graph_ms`. At the 100k measurement
they are byte-identical (252 ms / 252 ms) — i.e. `object_store_ms`
in the top-graph-enabled path **is** the top-graph time, with no
separate object-store flush attribution. Two acceptable fixes:

- subtract inner timings from outer at notice-emit time so the
  printed phases are disjoint, or
- rename the fields to make the containment relationship explicit
  (`draft_total_ms` / `recursive_kmeans_ms`, `object_store_total_ms`
  / `top_graph_ms`).

I'd prefer the first since downstream packet authors read the notice
row and don't necessarily read this code.

### Recursive k-means call count

`recursive_kmeans_calls=1` at nlists=128, fanout=8. The recursion in
`build_recursive_routing_hierarchy_draft` should keep iterating
parent levels until target_fanout is achieved, so `ceil(log_8(128)) ≈
3` levels are expected. The measurement shows one call. This is
either:

- a real property of the current recursion termination (e.g. the
  routing draft only does one level for this shape because it bundles
  128 children into 16 then 16 into 2 in a single pass), or
- a missing instrumentation point — i.e. only the outermost call to
  `train_spherical_kmeans` is wrapped, and inner levels of the
  per-level loop bypass `timing.add_recursive_kmeans`.

Confirm before Phase 2. If it's the former, document it in the next
packet's manifest so future readers don't suspect the
instrumentation. If it's the latter, fix the wrap and re-run the
characterization.

### Sample-collect cost

`sample_collect_ms=0` at both 10k and 100k. Either the sample-collect
call is genuinely free (likely, since `training_sample_vectors` is a
clone-references walk over `self.tuples`) or the timing is below
the 1 ms `as_millis()` resolution. Worth noting either way; if
SPIRE ever moves to a real sampling pass this counter will need
sub-ms resolution.

### Resolution

All counters use `Duration::as_millis()` → `u128`. For the very
short sub-phases (recursive k-means at 2 ms, publish at 1 ms),
this gives single-digit-ms resolution that's right at the noise
floor. Phase 2 measurement packets should keep an eye on whether
any P0-targeted phase falls below ~5 ms total and needs
microsecond timing.
