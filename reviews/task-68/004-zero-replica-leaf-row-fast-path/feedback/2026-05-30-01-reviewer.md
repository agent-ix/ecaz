## Code shape

The fast path is a narrow early return in
`build_recursive_leaf_rows_by_pid` gated on
`boundary_replica_count == 0`:

```rust
if boundary_replica_count == 0 {
    // derive primary_pid directly from route_map[assignment_index]
    // build placements through build_boundary_leaf_assignment_placements_with_identity
    // drop(source_vectors); return Ok(rows_by_leaf_pid);
}
// existing per-source boundary routing path unchanged
```

What's preserved:

- The non-zero-replica path is byte-identical to before the change
  — no risk of regression for deployments that use replicas.
- The fast path goes through the same
  `build_boundary_leaf_assignment_placements_with_identity` helper
  the slow path uses, so validation and local/global vec-id
  allocation behaviour are identical.
- Source order is preserved (`assignments` and `assignment_indexes`
  iterated together via `.zip()`), so placement determinism is the
  same.

What's removed:

- The wasted call to `route_boundary_assignment_for_vector(...,
  boundary_replica_count + 1)` for every source vector when
  `boundary_replica_count = 0`. The slow path was looking up
  `replica_count + 1 = 1` nearest leaf via the route map for every
  source even though the primary leaf PID was already in
  `assignment_indexes`.

This is exactly the right shape for an early-return fast path:
config-gated, semantically equivalent, no new code path on the slow
side.

## Caveat — config scope

This fast path only fires for `boundary_replica_count == 0`. The
measured Phase 1 corpus uses exactly that, so the measurement in
packet 005 is on the right surface. For deployments that use
`boundary_replica_count > 0`, the slow path is unchanged and
`draft_leaf_rows_ms` will still be the dominant cost. That's a
separate Phase 2 slice — call it explicitly in the Task 68 closeout
so future readers don't assume "draft leaf rows is solved" without
the qualifier.
