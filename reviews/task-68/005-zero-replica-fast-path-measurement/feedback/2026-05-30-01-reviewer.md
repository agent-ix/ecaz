**Qualifier 1 — config-specific:** This fast path only fires for
`boundary_replica_count == 0`. The measured corpus uses that
config, so the measurement is on-surface, but the Task 68 closeout
should call out that `boundary_replica_count > 0` deployments will
still see the original `draft_leaf_rows_ms` cost. If that's a
target deployment, open a follow-up slice for the non-zero replica
case; if it's not, document the assumption.

`heap_scan_ms` (1252 ms = 37 %) is the new largest phase at 100k.
The original packet 002 ranking listed heap scan at rank #2, so
this is consistent with the predicted post-slice ranking. But
heap scan is PG-side `table_index_build_scan` callback work, and
the cost-per-row is largely outside this code's control. Task 68
should be explicit about whether heap scan is in scope (e.g. via
prefetch, columnar I/O) or out of scope (cap accepted) before the
next P0 slice picks a target.
