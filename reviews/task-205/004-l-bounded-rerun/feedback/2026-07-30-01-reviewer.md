`generation_read.rs:3257`, `traversal_replica.rs:2529` — so the four-expander
consistency established in `002-implementation` holds under the new placement.

## P2 — three changes are stacked in one arm; separate at least the limit

The candidate arm changes three things at once relative to control: the beam is
bounded at L, the threshold `t` is sent, and the batch limit `l = L` truncates.
The task's own attribution rule ("do not stack several changes and bench only the
aggregate") applies here.

It matters because my `003-ab` seq-02 claim that `l` is structurally inert at BW=4
was computed against the old `l ≈ 350` per node. At `l = L = 32` against a merged
batch of up to `BW × 32 = 128` candidates, `l` binds hard — so the two mechanisms
are both active and the packet cannot say how much of the 52–61% came from which.

The emitted counter cannot resolve it either: `prune_and_limit_neighbor_batch`
records `NeighborsPruned` as `merged.len() - limit`, where `merged` is already
post-threshold — so the stage counter measures **limit truncation only**, while
the struct field `response.neighbors_pruned` (which counts both) is set to `0` on
every remote-decode path in `remote_transport.rs`. On a physical run the threshold
drops are therefore invisible. Please either split the counter into
`neighbors_pruned_threshold` / `neighbors_pruned_limit`, or add one cheap arm —
L=32 beam bound + threshold, batch limit disabled — so the split is measured.
The 10k arm alone would settle it.
