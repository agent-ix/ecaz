# Task 205 / 003-ab — REQUEST CHANGES

Verdict: **REQUEST CHANGES.** The A/B was run honestly and reported honestly, and
the bottom line ("do not advance Algorithm 1") is the right call. But both of the
packet's load-bearing claims are wrong in a way that matters:

1. the A/B did not measure the pushdown, because the pushdown pruned **exactly
   zero** neighbors in all 150 scans — it is inert by construction, not merely
   ineffective; and
2. the NFR-021 inadmissibility verdict is a misapplication of the requirement,
   and taken at face value it also blocks Tasks 206–209.

The packet should not be closed with "Algorithm 1 does not help." It has not been
measured yet.

## P1 — the pushdown is inert; the A/B measured nothing

The request says "response bytes are nearly identical." They are not nearly
identical; the two arms are bit-for-bit the same run. From the retained
`distann-multinode-summary.log` files under `run-candidate-stage2/`:

| scale | arm | `remote_expand` samples | `traversal_frontier_insert` samples |
|---|---|---:|---:|
| 10k | control | 436 | 21,978 |
| 10k | candidate | 436 | 21,978 |
| 50k | control | 624 | 44,584 |
| 50k | candidate | 624 | 44,584 |
| 100k | control | 586 | 44,384 |
| 100k | candidate | 586 | 44,384 |

Identical to the unit, at every scale. `traversal_frontier_insert` counts every
neighbor the coordinator ingests. If the owner had dropped even one neighbor of
one node on one query, this number would differ. Across 150 scans and ~110,000
frontier inserts, the filter removed nothing. That is the finding, and it is
stronger and more useful than "no measured saving."

### Why it cannot fire — two independent structural reasons

**(a) `t` is derived from an unbounded frontier, not from a bounded candidate
heap.** In `src/am/ec_distann/scan.rs`, `beam` is a `BinaryHeap` that accumulates
*every* candidate ever enqueued and is never trimmed. `derive_pushdown_limits`
takes `min` over that entire heap:

```rust
beam.iter().map(|c| -c.dist).min_by(|l, r| l.total_cmp(r))
```

At 100k that heap holds roughly 890 entries per scan (44,384 inserts ÷ 50 scans),
so `t` is the score of the single worst candidate the search has ever seen. Any
real neighbor beats it. The paper's `t = peek_worst(H_C)` is the worst member of a
heap **bounded at `L`** — the bound is not incidental to Algorithm 1, it *is* the
mechanism. `L` does not exist as a parameter in this implementation, so there is
nothing to peek the worst of.

**(b) `l` can never bind.** `candidate_limit = remaining_rounds × BW`, i.e. ~396
at round 0. The run early-exits at ~12 rounds (`remote_expand` 586 samples ÷ 50
scans ÷ BW=4), so `l` never drops below ~350 for the entire scan. Graph degree is
32. A limit of 350+ applied to at most 32 neighbors truncates nothing, ever.
Separately, `l` is applied per expanded node rather than per response, so the
effective per-response bound is `BW × l` ≈ 1,584 — another factor of 4 of slack
on a bound that was already ~11× too loose.

Equation (2)'s ~6× bandwidth saving is not reachable from this derivation under
any workload. The identical byte counts are the expected result, not a surprising
one.

This also explains the `001-contract` equivalence argument: it is sound, but it is
sound *because* the mechanism never engages. See my feedback on that packet.

### What I'd want before a re-run

- Introduce `L` as a real bounded-candidate-heap parameter and derive `t` from the
  `L`-th best retained candidate, per §2.4.
- Set `l` on the order of `BW` or `L`, not the total remaining budget, and apply
  it per response rather than per node.
- Then re-run this same matrix. The current config, corpus SHAs, and control arm
  are all fine and reusable.

## P1 — the NFR-021 verdict is a misapplication, and it over-blocks

`nfr-021-growth.md` computes 277,372,928 ÷ 25,706,496 = 10.79, compares it to
NFR-021's `<= 2.0`, and concludes the owner-control surface is inadmissible,
which via NFR-022 kills the A/B.

That reading contradicts NFR-021's own Statement, which says explicitly:

> A structure that is O(N) but genuinely sharded — each node holding only its own
> partition — satisfies this requirement.

The A/B surface is exactly that. Three physical owners, disjoint partitions,
zero non-owned rows, all six topology gates passed. Per-node bytes grow ~linearly
with N because the roster is fixed at three nodes across all three scales — a 10×
corpus on a fixed roster *must* give ~10× per-node bytes. 10.79 is the correct and
healthy answer for a correctly sharded index; it is not a defect signal.

The Measurement table's row is what's wrong, not the run. As written, the gate can
only pass if the roster grows with N, which the local fixture does not do. Applied
literally it fails **every** ec_distann configuration on this fixture — including
the properly-sharded one the requirement was written to bless, and including
whatever 206–209 produce. A gate that fails both the thing it was written to catch
and the thing it was written to permit is not discriminating anything.

Note that the discriminating measurement now exists, thanks to Task 204: the
coordinator's own `physical_benchmark_storage_node` row. On the owner-control arm
it is `graph_side_bytes=0`; on the coordinator-replica arm it is
`1,659,518,976`. *That* is the NFR-021 violation NFR-021 was written to catch, and
it is visible without any cross-scale ratio at all.

Asks:

- Withdraw the NFR-021 inadmissibility verdict from this packet. Do not record an
  admissibility judgement derived from a fixed-roster growth ratio.
- Escalate the spec contradiction to the NFR-021 owner rather than resolving it
  inside Task 205. The fix is one of: scale the roster with N so the ratio
  measures distribution instead of corpus size, or restate the measurement as
  coordinator-resident / non-owned bytes (which the Task 204 emitter now supports
  directly).
- Re-state the decision on its real basis: not advanced because the implemented
  pushdown is inert, pending the `L`-bounded derivation above.

## P2 — no activation evidence

There is no counter anywhere in the run for "rounds where `t` was non-NULL" or
"neighbors pruned." I had to infer inertness from `traversal_frontier_insert`
sample counts, which happens to work but is indirect. Please add
`pushdown_rounds_with_threshold` and `neighbors_pruned` (or equivalent) to the
scan counters and emit them. Without them, a future re-run cannot distinguish
"the mechanism ran and did nothing" from "the mechanism was never wired up" —
which is the exact ambiguity Task 203 Defect 2 was raised to eliminate.

## P3 — build hygiene

The manifest notes the baseline release build "required a temporary reverted
compiler workaround in the fault-injection C source," and `002-implementation`
records the CLI check as blocked by the same `implicit declaration of function
'maybe_sleep'` error. It is correctly disclosed and unrelated to Task 205, but it
has now degraded validation in two packets and forced an ad hoc edit into a
benchmark build. Worth a small standalone fix rather than another disclosure.
