# Task 205 / 002-implementation — ACCEPT the plumbing; the derivation is wrong

The wiring in this packet is clean and complete. The defect is not here; it is in
the coordinator-side derivation of `t` and `l`, which I've written up against
`001-contract` and `003-ab`. Summary: the pushdown pruned exactly zero neighbors
across the whole A/B (`003-ab` feedback), because `t` is taken from an unbounded
frontier heap and `l` is ~11× larger than any response can be.

Reviewing this packet on its own terms:

## What is right

**Every expander honors the contract, with no path left behind.** I checked all
four implementations of `DistannNodeExpander::expand_nodes`, which is where Task
203 Defect 2 found the previous rot:

- `expand.rs` `LocalNodeExpander` — now delegates to `prune_and_limit_neighbors`
  instead of its own inline threshold loop, so the legacy and production paths
  cannot drift.
- `generation_read.rs` `GenerationExpander` — the `_code_threshold` discard at the
  old `:3146` is gone; it filters and truncates.
- `generation_read.rs` `PhysicalMultiOwnerExpander` — forwards both values on the
  local route and on the remote request.
- `traversal_replica.rs` `ReadyTraversalReplica` — the `_code_threshold` discard
  at the old `:2455` is gone.

Routing them all through one shared `prune_and_limit_neighbors` is the right call
and is what makes "keep the legacy path consistent" (Phase 3) actually hold rather
than being a promise.

**The ABI is carried end to end.** `candidate_limit` is added with a `NULL`
default to `ec_distann_expand_nodes`, `ec_distann_expand_physical_nodes`,
`_cached`, and `_profile`, and threaded through `remote_transport` /
`remote_endpoint`. Negative limits are rejected as `BadInput` at both
`i32 -> usize` conversion sites. The hardcoded `None` at the sole orchestration
call site is gone, which was the specific thing Task 203 flagged.

**The benchmark exact-neighbor re-expansion correctly passes `None, None`**
(`expand_nodes_raw(&neighbor_ids, None, None)`), so the measurement path is not
silently pruned by the feature under test. Easy thing to get wrong; it was
gotten right.

**`prune_and_limit_neighbors` ordering is correct.** Filter is `>=` so
threshold-ties survive; sort is ascending `code_dist` then `vec_id`, so the
truncation window is deterministic and best-first. The length-mismatch guard on
the two input slices is a good defensive check.

**Test evidence is real.** 13 passed / 0 failed, and the two named tests do what
they claim — `algorithm1_pushdown_is_order_identical_to_unbounded_path_with_tombstone`
compares full `DistannScanHit` equality (not just id order) against the
`pushdown=false` reference on the same fixture, with ties, a tombstone, and two
frontier regions.

## P2 — the identity tests cannot fail for the right reason

`params(2, 4, 5)` gives BW=2, H=5, so `remaining_expansion_budget` starts at 8 and
the fixture has 9 nodes with ≤3 neighbors each. As with the production
configuration, `l` cannot bind and `t` is drawn from an unbounded heap. The
identity test therefore passes whether or not the filter is correct — it would
also pass against a stub that ignored both arguments.

`owner_pushdown_keeps_threshold_ties_and_deterministic_limit_order` is the only
test that genuinely exercises the filter, and it calls `prune_and_limit_neighbors`
directly rather than going through the orchestrator.

When the `L`-bounded derivation lands, please add an orchestrated identity test
where the threshold provably prunes — assert a non-zero prune count *and* result
identity in the same test. Right now "identical results" and "nothing happened"
are indistinguishable at this layer, which is the same ambiguity that let the
inert path reach a full 3-scale benchmark.

## P3 — `l` is applied per node, not per response

Algorithm 1's `l` bounds what the host returns. Here it is applied inside
`prune_and_limit_neighbors`, i.e. once per expanded `vec_id`, so a BW-wide batch
can return up to `BW × l`. Worth either fixing or stating explicitly in FR-079,
since the contract packet describes `l` as bounding "each response."
