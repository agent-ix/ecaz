# Task 205 / 002-implementation — the concrete changes the paper implies

Addendum to `2026-07-30-01-reviewer.md`, after reading the paper directly.
Verbatim algorithm text is in
`reviews/task-205/003-ab/artifacts/paper-algorithm-citations.md`; the contract
consequences are in `reviews/task-205/001-contract/feedback/2026-07-30-02-reviewer.md`.

My seq-01 verdict stands: the plumbing is right, the derivation is wrong. This
note makes the required derivation concrete so it isn't guessed at.

## Change 1 — bound the candidate heap at `L`

`beam` in `src/am/ec_distann/scan.rs` is a `BinaryHeap` that only ever grows.
Algorithm 2 initializes "candidate heap H_C **of size L**" with
`L ≥ max(BW, k)`. Until `beam` is bounded, `peek_worst` has nothing to mean.

`BinaryHeap` is a max-heap on `BeamCandidate`'s ordering, so the cheap version of
this is to push, then pop the worst while `len() > L` — but note that requires
the *reverse* ordering to be accessible, so a bounded insert is probably cleaner
than trying to trim in place. Whichever shape, the invariant to hold is
`beam.len() <= L` after each round's merge.

This also fixes the seq-01 P2 as a side effect if you drop expanded entries at
trim time rather than skipping them lazily in the pop loop — with a bounded heap,
stale entries occupy slots that a live candidate needs, so lazy deletion stops
being free.

## Change 2 — `t = peek_worst(H_C)`, and drop the budget guard

Replace the `min` over the whole heap plus the
`beam.len() >= remaining_expansion_budget` guard with the worst member of the
`L`-bounded heap, unconditionally, every round.

The guard exists to make the current unbounded derivation safe. With a bounded
`H_C` the safety argument is different and simpler: a candidate worse than the
`L`-th best cannot enter `H_C`, so it cannot be selected, so it cannot be
expanded. The guard becomes unnecessary rather than merely insufficient — and
keeping it would re-introduce the vacuity, since it is the guard plus the
unbounded heap that made the threshold a no-op.

One real edge to handle: before the heap has `L` members (early rounds, right
after head seeding), `peek_worst` is not a valid floor. Send `NULL` until
`beam.len() == L`. That is a genuinely bounded warmup — a few rounds — not the
whole scan.

## Change 3 — `candidate_limit` is `L`, and applies per response

Two sub-changes:

**(a) Value.** `derive_pushdown_limits` currently computes
`remaining_rounds × BW`. Algorithm 2 passes `NodeScoring(K, t, **L**, q, q_SDC)`
— the same constant `L` every round. Remove the budget arithmetic entirely.

**(b) Placement.** `prune_and_limit_neighbors` truncates once per expanded
`vec_id`. Algorithm 1's `Sort R and partial-sort C up to l / Truncate C to l`
sits outside the `for all n_i` loop — one truncation over the candidates merged
across the whole batch. At BW=4 the current placement returns up to `4L` instead
of `L`.

This is the more invasive of the two. `prune_and_limit_neighbors` is called from
four expanders and returns per-node `(neighbor_vec_ids, neighbor_code_dists)`
that the response format carries per node. Truncating across the batch means the
merge has to happen where the batch is visible:

- `expand.rs` `LocalNodeExpander` and `generation_read.rs` `GenerationExpander`
  and `traversal_replica.rs` — all loop over `vec_ids` and can merge after.
- `remote_endpoint.rs` `expand_nodes_impl` is the true batch boundary for the
  remote path; that is where the paper's truncation belongs, since it is what
  bounds the wire response.
- `PhysicalMultiOwnerExpander` splits one coordinator batch across owners, so
  each owner truncates its own share to `L` and the coordinator can receive up to
  `owners × L`. The paper has the same property (one Algorithm 1 instance per
  key-value host) and accepts it, so match it and say so — don't try to
  distribute `L` across owners.

Keep the threshold filter where it is; only the sort/truncate moves.

## Change 4 — keep tie retention, document the divergence

Algorithm 1 uses `if d_OPQ(q_SDC, p) < t` — strict, so threshold ties are
dropped. `prune_and_limit_neighbors` uses `>=` on the ip score and retains them.
**Keep ec_distann's behavior.** It is the conservative direction and it is load
bearing for the result-identity claim, which the paper never makes. Add a comment
at the filter saying so, otherwise a future reader "fixing" it to match the paper
will silently break equivalence.

## Change 5 — counters (restating seq-01 P2, now blocking)

With the mechanism actually live, `pushdown_rounds_with_threshold` and
`neighbors_pruned` stop being nice-to-have. They are how the next A/B
distinguishes "the threshold pruned 40% of candidates and latency didn't move"
from another inert run. Please land them with the derivation change, in the same
checkpoint.

## Test change

The seq-01 P2 on the identity tests becomes actionable here: with `L` bounded,
write the orchestrated identity test so the threshold provably prunes — assert
`neighbors_pruned > 0` **and** full `DistannScanHit` equality against the
`pushdown=false` reference in the same test. Today both tests pass against a stub
that ignores the arguments, which is how an inert path reached a three-scale
benchmark.

A second test worth having: `beam.len()` never exceeds `L` across a run, and
results are unchanged versus the unbounded heap at `L` large enough to be
non-binding. That separates "bounding the heap changed recall" from "the
threshold changed recall" — they are two different changes landing together, and
without that separation the next A/B has the same attribution problem this one
had.
