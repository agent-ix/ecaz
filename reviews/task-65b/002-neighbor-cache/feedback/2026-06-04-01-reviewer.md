# Slice B — Neighbor Cache — APPROVE-WITH-FLAGS

## Verdict

**APPROVE-WITH-FLAGS.** Slice B meets its narrow scope:
behavior-equivalent serial refactor, no new `unsafe`, no
anti-pattern B, all build-loop adjacency mutations route
through one type. Four flags to carry forward into Slice C's
RFC.

## What landed

`BuilderNeighborCache` at
`src/am/ec_diskann/vamana.rs:74-131`. Private struct holding
the same `Vec<Vec<u32>>` adjacency shape as `VamanaGraph` +
`max_degree`. Replaces direct `graph.neighbors[i]` reads/writes
in `build_vamana_graph_with_stats`
(`src/am/ec_diskann/vamana.rs:774-922`). At build end,
`into_graph` converts it to a `VamanaGraph`. Implements
`VamanaGraphView` so `greedy_search_visited_with_scratch` can
read through it (`vamana.rs:133-141`).

## Safety bar — clean

- No new `unsafe`.
- No raw pointers.
- No `fn(*mut T) -> &'a T` (anti-pattern B).
- No new `unsafe fn` signatures.
- `VamanaGraphView::neighbors(&self, node) -> &[u32]` is a
  safe borrow off `&self` — not anti-pattern B. (Anti-pattern
  B is specifically pointer-to-borrow lifetime smuggling.)

Compatible with the "no new unsafe outside the
ParallelContext scaffolding" Coder workflow note.

## Flags to carry into Slice C's RFC

1. **It is not a "cache" — it is the authoritative store with
   no eviction.** pgvectorscale's `BuilderNeighborCache` is an
   LRU that flushes to a paged backing store; this
   implementation owns the entire adjacency for the build's
   lifetime. Fine for Slice B, but the name and doc-comment
   ("read-through to the in-memory graph, write-back to the
   same") set a misleading expectation for Slice C/E. Rename
   or rewrite the doc-comment so the eventual flush-cadence
   design doesn't get conflated with what's in tree today.

2. **API shape will not survive Slice E.** Every cache mutator
   takes `&mut self` (`vamana.rs:96, 104, 113`) and reads use
   `&self` borrows that overlap mutations in the build loop.
   For Slice E's shared-across-workers use, the surface needs
   to be either:
   - `&self` with interior mutability (per-node `RwLock` /
     sharded locks / atomic-length-prefixed slots), or
   - operation-style
     (`with_locked_mut(node, |adj| -> R) -> R`) per
     `feedback_view_operations_not_accessors`.
   The current `VamanaGraphView::neighbors(&self) -> &[u32]`
   accessor will need to be replaced with an operation
   (`with_neighbors(node, |&[u32]| -> R)`) before Slice E.
   **Slice C's RFC must specify the replacement** — discovering
   it at Slice E rewrites Slice D's work.

3. **`iter_adjacency` returns
   `impl Iterator<Item = &[u32]>`** (`vamana.rs:121-123`).
   Convenient now, impossible under any shared-locking scheme.
   Mark as build-finalization-only or remove before Slice D.

4. **Need a fixed-seed adjacency-list golden test.** The
   strongest Slice B invariant — "byte-identical
   `VamanaGraph` for a fixed seed before/after the cache
   refactor" — is only checked indirectly via aggregate
   recall + in-degree distribution. The new unit test
   `builder_neighbor_cache_preserves_adjacency_operations`
   (`vamana.rs:1049-1069`) exercises method API but doesn't
   pin the byte-shape of the produced graph. Add a small
   fixed-seed synthetic-distance test that asserts on exact
   adjacency lists; that golden becomes the determinism oracle
   for Slices D/E.

## Memory bound note (not a regression)

The cache holds `node_count * max_degree * u32 + per-Vec
overhead` for the entire build. For real-10k this is trivial;
for real-100k and beyond it is unbounded. Slice B inherits the
pre-existing `VamanaGraph::empty` shape, so this is **not a
new regression**. Defer to Slice F per task plan, but the
packet should say so explicitly.

## Determinism / eviction gate

Not applicable yet — no eviction, fully serial, output
byte-shape-equivalent to packet 001. Real test of "deterministic
enough" comes at Slice E.
