## Blocking findings

### B-1. Packet has no `request.md` and no `manifest.md`

`reviews/task-65b/004-worker-one-scaffold/` contains only
`artifacts/`. CLAUDE.md "Coder Workflow → Output" requires both
files. Per `feedback_reviews_always_to_files`, the packet is
invisible to the inbox loop without a `request.md`. Land both.

### B-2. Fallback (`requested_workers = 0`) byte-equality is unproven at corpus scale

Acceptance #6 / Validation gate #5 require byte-equal output
and ≤5% timing vs. Task 65 head when `worker_count = 0`. With
this commit:

- w=0 now goes through `build_and_persist_vamana_with_parallel_config`
  (`ambuild.rs:341`); the original
  `build_and_persist_vamana_serial` (`build.rs:254`) is
  unreachable from ambuild.
- `BuildOutput.parallel_stats` is now a populated field even
  at w=0 (`build.rs:325-334`).
- `BuildFlushTiming` adds parallel fields to the NOTICE log
  line (`ambuild.rs:467-487`) — the log surface changed.
- The test `task65b_worker_one_scaffold_matches_serial_output`
  covers w=1↔serial parity on a 48-row synthetic, not w=0
  against Task 65 head, and not at corpus scale.

No real-10k / real-100k log demonstrating byte equality or the
5% timing budget. Land that evidence — for either path
(`run-the-suite-at-w=0` or a `cargo-test` golden against Task
65 head) — before this packet closes.

### B-3. Task 71 parallel-callback lesson ignored

`src/am/ec_diskann/routine.rs:210-212` still has
`amestimateparallelscan = aminitparallelscan = amparallelrescan = None`
and line 183 keeps `amcanbuildparallel = false`. This is the
exact trap Task 71 packet 003 burned six hours on
(`reviews/task-71/003-worker-curve/feedback/2026-06-02-04-reviewer.md:23-32`
and `2026-06-03-08-reviewer.md:61-99`). HNSW and IVF both wire
those callbacks (`src/am/ec_hnsw/routine.rs:31-65`,
`src/am/ec_ivf/routine.rs:29-63`). Slice D is the natural place
to plumb them behind no-op implementations paired with the w=1
scaffold; doing it later guarantees the next slice rediscovers
the trap.

Per `feedback_dont_defer_safety_fixes` (HARD RULE): this is not
"optional follow-on" when the precedent is already in tree on
both peer AMs. Wire them now, even if they're no-ops.

### B-4. Reloption surface + coordinator choice diverge from peer AMs without an ADR

- `ec_hnsw/options.rs` and `ec_ivf/options.rs` do **not**
  expose a custom `parallel_build_workers` reloption. IVF
  reads `(*index_info).ii_ParallelWorkers`
  (`src/am/ec_ivf/build_parallel.rs:46-53`), which PG populates
  from the standard `parallel_workers` table reloption +
  `max_parallel_maintenance_workers` GUC.
- DiskANN now exposes its own `ec_diskann.parallel_build_workers`
  reloption that bypasses PG's worker accounting and creates
  two competing controls (table reloption vs. AM reloption).
- Task plan §Coder workflow notes: "Existing `ec_hnsw`
  reloption naming is the precedent."
- The runtime uses a rayon pool (`build.rs:337-341`). Task plan
  §Scope item 3 calls rayon the **second-choice fallback**,
  acceptable only as a stepping stone, because it loses
  `pg_stat_progress_create_index`, WAL/buffer accounting, and
  `pg_stat_activity` visibility.
- Packet 003 is about locking, not coordinator choice. There
  is no packet that justifies picking rayon over
  `ParallelContext`.

Either land an ADR + dedicated packet justifying rayon (with
explicit acknowledgement of the Validation gate #6 waivers),
or pivot to `ParallelContext` here. Don't split the difference.

## Substantive concerns (non-blocking)

5. **The "scaffold" is a no-op.** `pool.install(|| serial_build())`
   wraps a function with zero rayon parallel work. Single
   worker thread runs the serial path. The byte-equality test
   is tautological. No FFI surface touched, no DSM allocated,
   no `ParallelContext` established — so the commit does not
   prove "the scaffolding works" as Slice D's description
   claims.

6. **`parallel_build_batch_size = 1` default is misleading.**
   With batch=1 and w=1, no batching can happen; the default
   conveys no information. `parallel_build_flush_rate = 0` is
   "Reserved … 0 means unused" but the reloption is live and
   validated against 0..1_000_000, so users can set values the
   code silently ignores. Either wire them or reject non-zero
   in `validate_parallel_config`.

7. **No per-worker / contention / stale-read instrumentation.**
   Task §Scope item 7 explicitly requires per-worker timing,
   contention counters, stale-read fraction. The new
   `BuildParallelStats` is currently empty / pure scaffolding;
   land at minimum the field shape so Slice E can populate it.

8. **`u16::try_from` rejection message.** `validate_parallel_config`
   says "0 or 1" but should also name the reloption (or the
   table reloption + GUC pair) so an operator can find it.

9. **Test gaps**: no w=0-vs-plain-serial explicit byte test;
   no reloption out-of-range rejection test; reloption parse
   round-trip only tests defaults; no Linux/CI evidence (macOS
   `_BufferBlocks` blocker on pg_tests).
