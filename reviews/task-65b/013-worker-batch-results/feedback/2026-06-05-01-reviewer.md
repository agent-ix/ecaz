## Parallelism reality check (Task 71 lesson)

The implementation uses a **rayon thread pool**, not Postgres
`ParallelContext`. `src/am/ec_diskann/build.rs:348-380` builds a rayon pool
with `requested_workers` threads, and on line 370 sets
`effective_workers: parallel.requested_workers` — i.e. it copies the
configured count, it does not measure actual fanout. The
`parallel_rayon_scaffold=1` field confirms this. Postgres
`pg_stat_get_db_parallel_workers_launched` is not consulted, and the
session `max_parallel_maintenance_workers` override (set to 1/2/4/8 in
`pgoptions`) has no effect on the rayon path.

That said, the rayon scaffold IS demonstrably doing work in parallel:
`parallel_proposal_ms` rises with batch size (0 → 726 ms), and on real100k
w8/b32 the wall time drops from 335 s (w4) to 192 s (w8). So workers are
doing real work — they are not silent no-ops. But the "effective_workers"
field cannot be trusted as evidence of fanout; it is a tautology. The
proposal_ms / reducer_ms / total_candidate_reads triple is the actual
parallelism signal, and that data is real.

Worth noting from packet 013's own interpretation: the deterministic
**reducer phase is now the dominant cost** (reducer/total = 66–79% on
real10k, 85–89% on real100k). Adding more workers makes the reducer
**slower** (978 → 4432 ms going w1→w8) because each worker proposes more
edges per epoch that the single-threaded reducer must serialize. Scaling
is collapsing exactly where the request flags it.

The packet does not state which determinism option was taken. The shape
(equal node order, different adjacency, equal recall) reads as
non-deterministic-but-recall-stable.
