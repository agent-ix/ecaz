# Task 65b Slice C — Locking Design Review

Verdict: **REQUEST-CHANGES**.

## 1. Chosen Design Shape

- Parallel mechanism: **rayon stepping stone** for the graph core (worker
  fanout for proposals only).
- Locking primitive (Slice D/E): **none on the shared graph** — writes are
  funneled through a single leader/reducer that owns `BuilderNeighborCache`
  and applies in pivot order. Sharded `RwLock`/LWLock stripes are *reserved*
  for a hypothetical live-shared-cache follow-on.
- Cache-flush policy: epoch-bounded. Each epoch exposes an immutable snapshot;
  the leader commits at epoch end; the next epoch reads the committed cache.
  No mid-epoch flush; `parallel_build_flush_rate` is currently a no-op
  logging-only reloption.

This is determinism option 3 (deterministic reduction after parallel proposal),
explicitly with a stated path to option 2 if reducer time dominates.

## 2. Coverage Of The Two Hard Invariants

(a) **Stale neighbour reads.** Addressed in principle: workers read an immutable
epoch snapshot, so within-epoch reads are coherent. Cross-epoch
freshness is bounded by epoch size. The packet defines a
`stale_read_fraction` counter, which is good. **Gap:** the packet never
sets an upper bound on epoch size or any rule for when same-epoch
staleness violates the 0.5pp recall gate. Slice E will have nothing
quantitative to fail against.

(b) **Backlink races.** Fully avoided by single-writer reducer. This is
correct and the cleanest possible answer for v1. **Gap:** no analysis of
reducer throughput vs the ~7s graph-construction budget. With real10k
backlinks=142105 and reprunes=61593 (manifest) serialised through one
thread, the reducer is a plausible Amdahl ceiling well above the 3s goal.
The packet acknowledges this risk verbally but offers no back-of-envelope
floor; reviewer cannot tell whether Slice E can even hit the gate before
opening the sharded-lock follow-on.

## 3. Determinism + Concurrency-Test Plan

- Determinism: option 3 is named, with a stated migration toward option 2.
  Acceptable per the validation gate ("either documented nondeterminism with
  statistical recall bounds, or bit-equal output for a fixed seed + worker
  count"). The packet claims bit-equal for a fixed seed/worker count/batch
  size; that claim is testable.
- **Concurrency-test surface: MISSING.** The task plan calls out concurrency
  tests as *mandatory at Slice E* and points at `loom`/`shuttle`/HNSW's
  `concurrent_dsm_state.rs` model checking. The design says nothing about
  which surface will be model-checked, what invariants the model expresses,
  or how the leader-reducer is verified to be the only writer. Per
  `feedback_dont_defer_safety_fixes`, this cannot be deferred.

## 4. Gaps And Hand-Waving

- **Hub contention.** Correctly avoided in v1 by single-writer reducer.
  However the packet's "future sharded RwLock stripes" plan handwaves the
  exact case (medoid + p99=79, max in-degree 2881) where stripes still
  collide. No mapping function, no stripe count, no acquisition-order
  proof beyond "ascending stripe order." That is fine as a *future*
  follow-on but it should not be presented as a drop-in next step.
- **Fallback path.** `parallel_build_workers=0` is mentioned but the
  design does not state whether `workers=1, batch=1` *also* takes the
  reducer path (as the text implies) or short-circuits. The byte-equality
  claim against Task 65 head depends on this.
- **Fault recovery if a worker dies.** Not addressed at all. Rayon panics
  propagate via `JoinHandle`, but the packet doesn't say whether a worker
  panic poisons the epoch, retries, or aborts the build. HNSW's
  ParallelContext path inherits Postgres's worker-death handling; rayon
  does not.
- **Postgres integration regression.** Choosing rayon means losing
  `pg_stat_progress_create_index`, WAL/buffer accounting, and
  `pg_stat_activity` worker visibility — all of which validation gate #6
  *requires if option ParallelContext is chosen*. The packet does not say
  whether gate #6 is in force here or waived. Reviewer reads gate #6 as
  not-waivable for production; it must be explicitly addressed.
- **Reducer back-pressure.** No bound on the proposal queue between
  workers and leader. Long epochs with R=32 × batch_size proposals per
  pivot are bounded but unstated.
- **Cache coherence with packet 002.** The design says workers read an
  immutable snapshot and the leader applies through
  `BuilderNeighborCache`, but does not specify whether the snapshot is
  Arc-shared (cheap, copy-on-write at commit) or fully cloned per epoch
  (expensive). Packet 002 introduced the cache; the snapshot mechanism
  is the load-bearing integration point with it and is left to
  implementation.

## 5. Consistency With HNSW Reference

The task plan explicitly recommends Postgres `ParallelContext` "matching
HNSW's `build_parallel.rs` pattern" and lists rayon as "acceptable as a
stepping stone if `ParallelContext` integration proves too large." The
design picks rayon without arguing that ParallelContext is too large —
it picks rayon for graph-core fanout because the *write model* is
single-leader. That is a reasonable v1 call but the packet should make
the case explicitly that ParallelContext brings no benefit over rayon
when there is only one writer, and commit to a ParallelContext migration
checkpoint if/when sharded live commit lands. As written, it reads as
diverging from the recommended pattern without justification.

HNSW's `concurrent_dsm_state.rs` model and `EcHnswConcurrentDsmInsertStateCell`-style
scaffolding are not referenced for reuse, even though the task plan called
them out as directly applicable for DSM/`HeapRelationGuard`/`IndexRelationGuard`
wrappers and WAL accounting.

## 6. Verdict

**REQUEST-CHANGES.** The core design (deterministic epoch + ordered
reducer + rayon proposal fanout) is defensible and correctly avoids
both hard invariants for v1. But three items must land in this packet
before Slice D/E start, per the task plan and standing memory rules:

1. **Concurrency-test surface named.** loom/shuttle/HNSW-style — pick
   one and state what invariants get checked (single-writer-on-cache,
   epoch monotonicity, snapshot immutability). Per
   `feedback_dont_defer_safety_fixes` this is a blocker, not a
   follow-up.
2. **Reducer Amdahl floor.** Back-of-envelope: with 10k pivots,
   142105 backlinks, 61593 reprunes, what's the minimum reducer wall
   time on one thread? If it exceeds ~1.5s the 3s gate is unreachable
   on this design and the packet should say so and pre-commit to the
   sharded-commit follow-on slice.
3. **Gate #6 disposition.** State explicitly whether
   `pg_stat_progress_create_index` / WAL+buffer attribution /
   `pg_stat_activity` worker visibility is waived for the rayon
   stepping stone, and what triggers the ParallelContext migration.

Nice-to-have but not blocking: snapshot Arc-vs-clone decision; worker
panic policy; concrete reloption defaults for epoch/batch sizing
floor (Slice F will tune, but a starting point should be named).
