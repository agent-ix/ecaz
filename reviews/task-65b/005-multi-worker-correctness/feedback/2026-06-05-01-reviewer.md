# Slice E — Multi-Worker Correctness — REQUEST-CHANGES

## Verdict

**REQUEST-CHANGES.** The implementation is structurally sound
(no `unsafe`, no anti-pattern B, single-writer enforced by
`&mut`), and the deterministic-ordinal-sort reducer is the
right design choice per ADR-075 + packet 003. But three of the
gates packet 003 was approved on are not actually cashed by
this packet's evidence.

## Shape of Slice E

`build_vamana_graph_with_parallel_epochs`
(`src/am/ec_diskann/vamana.rs:959-1077`):

- **Per-epoch rayon `par_iter`** computes proposals from
  workers.
- **Deterministic single-threaded reducer** drains proposals
  sorted by `ordinal` and applies `set_neighbors` +
  backlinks + reprune on the live `BuilderNeighborCache`.
- **Per-epoch snapshot** = `BuilderNeighborCache.clone()`
  (cloning the cache itself, not the dedicated
  `BuilderNeighborSnapshot` type that exists at
  `vamana.rs:157-170`).

## Safety bar — clean

- No new `unsafe`.
- No anti-pattern B (no `fn(*mut T) -> &'a T`).
- Single-writer invariant on `BuilderNeighborCache` is
  enforced by `&mut` borrow checker on the outer reference.
- No new unsafe outside the existing build callback boundary.

## Blocking findings

### B-1. No batch=1 byte-equivalence test of actual graph adjacency

Packet 003 §"Reloptions And Slices" explicitly required
batch=1 to "match the serial cache-backed path exactly."
The test `task65b_worker_one_scaffold_matches_serial_output`
(`build.rs:697-738`) asserts only:

- `entry_point`
- `node_to_tid` (BFS-from-medoid order)
- `persistence_order` (also BFS-from-medoid)
- `medoid`
- `final_in_degree` (a `MetricSummary` — count/mean/percentiles,
  **NOT per-node values**)

A divergent adjacency can survive every one of these checks.
`persistence_order` being BFS-from-medoid means it equals the
serial side as long as the medoid is the same. The
`final_in_degree` summary is a histogram — distributions can
match while individual lists diverge.

**Add a direct
`assert_eq!(serial_graph.neighbors, worker_one_graph.neighbors)`**.
Plus the same at (worker=1, batch=4) vs (worker=4, batch=4) to
prove the ordinal-sort reducer actually serializes the
parallel path.

### B-2. Real-10k Recall@10 evidence missing from this packet

Packet 003 seq 02 explicit ask: "Slice E should enable
`parallel_build_workers = 4` ... enforce recall plus
deterministic repeat runs." Task plan §"Slice E" plan: "Recall
gate enforced on every fixture." The packet defers recall to a
later slice ("Not yet claimed by this packet: recall-gate and
scaling-curve measurement packet"). The 0.5pp recall gate **is
the load-bearing acceptance criterion for Slice E itself**;
deferring it leaves the design call un-cashed.

Either land real-10k Recall@10 inside this packet's
`artifacts/`, or rename the packet to "scaffold landing" and
explicitly hand the gate off to packet 011/013.

(Note: per the packet 013 review, real-10k recall **is**
preserved across the sweep — 0.9965/0.9970/0.9975 exactly.
Update this packet's request.md to cite that explicitly, since
the design promise was that Slice E itself would establish
recall preservation.)

### B-3. Concurrency-test surface from packet 003 not fully implemented

Packet 003 seq 02 was APPROVED on the promise that Slice E
would assert (1) single-writer cache ownership, (2) snapshot
immutability, (3) fixed output for repeated schedules via a
deterministic interleaving model. The shipped tests:

- **Determinism across 2 invocations of the same config**
  (`task65b_multi_worker_epoch_build_is_deterministic_for_fixed_config`,
  `build.rs:786`) — rayon work-steal nondeterminism is masked
  by ordinal-sort, so two runs are likely identical regardless.
  Not the adversarial-schedule test packet 003 specified.
- **No test that exercises snapshot immutability** under
  proposal load (e.g. assert snapshot equals pre-epoch cache
  state after `par_iter` returns).
- **No model test for "no proposal from epoch N can observe
  commits from epoch N"** — cross-epoch boundary unchecked.

Packet 006 partially closes this — see packet 006 seq 01
(commit b9a96ed46) for the model-test gaps that remain.

## Substantive concerns (non-blocking but worth addressing)

1. **Snapshot type is the cache itself, not `BuilderNeighborSnapshot`**
   (`vamana.rs:990` calls `neighbor_cache.clone()`).
   `BuilderNeighborSnapshot` exists specifically for the
   read-only-by-construction role. Using the cache directly
   weakens the structural separation; a future refactor could
   accidentally pass `&mut` cache to workers and clippy-pass.
   Switch the snapshot variable to `BuilderNeighborSnapshot`.

2. **Per-epoch full Vec clone cost not flagged.**
   `vamana.rs:990` clones the outer
   `Vec<Arc<[u32]>>`. At n=10k, batch=1, that's 10k clones —
   800MB–2.4GB of churn during a build targeting ≤ 3 s. The
   packet 013 reducer-dominance finding is partly downstream of
   this. Per-epoch double-buffer or in-place snapshot would
   sidestep it. Packet 009 (epoch-snapshot-cow, commit
   f64c0a36e) appears to address this — confirm in the next
   feedback round.

3. **Worker-panic semantics undocumented.** Packet 003 seq 02
   open question: rayon proposal task panics mid-epoch behavior.
   Current code uses `par_iter().map().collect()` which
   propagates panic out of `pool.install`. The reducer's
   `&mut neighbor_cache` reference is safe on panic-unwind
   because nothing committed yet — but no test or comment
   confirms the reasoning.

4. **`stale_read_fraction` not surfaced in NOTICE.**
   `ambuild.rs` logs `parallel_same_epoch_candidate_reads` and
   `parallel_total_candidate_reads` but not the ratio. Packet
   003 §"Stale-Read Accounting" lists `stale_read_fraction` as
   the headline metric. Log the ratio too.

5. **`same_epoch_candidate_reads` is a proxy, not a true
   stale-read counter** (`vamana.rs:1144-1152`). Counts
   candidate-set membership where the candidate node's ordinal
   is in `[epoch_start, ordinal)` — i.e. "happens to be earlier
   same-epoch pivot", not "read an out-edge list stale wrt
   serial." Packet 003 allows the proxy; just call it out in
   the field doc-comment.

6. **No upper bound on `requested_workers` / `batch_size`** in
   `validate_parallel_config` (`build.rs:405`). Slice F sweep
   work should clip these before someone sets
   `parallel_build_batch_size = 100_000_000`.

## Cross-reference vs packet 003 spec

| Packet 003 requirement | Status |
|---|---|
| Immutable snapshot once per epoch | YES (via clone) |
| Workers produce proposal records only | YES (`VamanaPivotProposal`) |
| Reducer is the only writer to cache | YES (structural) |
| Sorted by `(pass, epoch, pivot_ordinal)` | Partial — sorted by `ordinal` only; `pass`+`epoch` debug-asserted, not part of sort key. Single-pass build today, brittle if multi-pass lands. |
| Epoch monotonic, no epoch-N observation | YES (epoch loop outer; reducer between epochs) |
| `parallel_batch_size = 1` byte-equivalent | **Not asserted on adjacency** (B-1) |
| Stale-read metrics logged | Partial (S4 + S5) |
| Reducer wall time logged | YES (`parallel_reducer_ms`) |
| Recall ≤ 0.5pp at batch>1 | **Not measured in this packet** (B-2) |
| Repeated-schedule deterministic output | Weakly — 2 same-config runs only (B-3) |

ADR-075 stepping-stone caveats (rayon, no PG worker
accounting) correctly preserved.
