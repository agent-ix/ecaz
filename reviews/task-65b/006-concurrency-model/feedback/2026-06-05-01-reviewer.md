## Test mechanism

- Hand-rolled, synchronous, single-threaded. No `loom`, no `shuttle`,
  no `std::thread`. This is consistent with packet 003's "hand-rolled
  deterministic interleaving" direction (correctly avoiding loom over
  rayon internals).
- Runs without PostgreSQL: confirmed. The added tests touch only
  `BuilderNeighborCache`, `VamanaPivotProposal`, and
  `commit_vamana_pivot_proposal` — pure data + pure functions. They
  live in the `vamana.rs::tests` module which compiles under
  `--features pg18` but does not invoke `pgrx` machinery.
- However: there is **no interleaving** in any of the three tests. A
  "deterministic interleaving model" would enumerate proposal-arrival
  orders and assert reducer output equality. Test 2 names this but
  short-circuits by sorting both inputs identically before commit.
  This is the central gap.

## Blocking gaps

1. **No adversarial schedule sweep.** Add a test that enumerates all
   permutations of a small proposal set (or a representative shuffled
   set under a seeded PRNG) and asserts the post-reduce
   `BuilderNeighborCache` neighbors are byte-identical. Today's
   "out-of-order" test trivially passes because both inputs are
   re-sorted by `ordinal` before the loop.
2. **No cross-epoch invariant test.** Add a test that commits epoch
   N, then constructs an epoch-N proposal whose snapshot pre-dates
   the commits, and asserts the worker output (and `same_epoch_*`
   counters) match the snapshot view, while an epoch-N+1 proposal on
   a fresh snapshot observes the epoch-N commits. This is the
   invariant the parallel build actually relies on for correctness.
3. **Single-writer ownership not enforced at the type level.** The
   reducer is "the only writer" only by convention. The packet 003
   surface called for asserting "single-writer cache ownership". A
   trybuild/`compile_fail` test, or routing all worker access through
   a `&CacheSnapshot` wrapper that exposes no `&mut` methods, would
   close this. Today a worker that gained a `&mut BuilderNeighborCache`
   would compile.
4. **`request.md` overclaims.** It says the packet "closes the
   Slice E concurrency-test surface". It does not — it closes a
   subset. The Review Notes section honestly excludes scaling/recall
   gates but does not flag the model-test coverage gaps above. Per
   memory `feedback_dont_overclaim_done`, the request should state
   which packet-003 invariants are and are not covered.

## Non-blocking observations

- `task65b_parallel_epoch_batch_one_matches_serial_graph_exactly`
  is a useful byte-shape oracle but it's a property of the existing
  parallel build path, not a model-check. It belongs to Slice D's
  byte-equivalence gate; leaving it here is fine, but it shouldn't
  count toward the model surface.
- The fact that `build_vamana_graph_with_parallel_epochs` uses
  `par_iter()` over rayon while the new tests all run synchronously
  is acceptable per packet 003's "do not loom over rayon internals"
  guidance, but it means the actual concurrent surface (the rayon
  fan-out) has zero direct test coverage. The model tests substitute
  for that by testing the commit body in isolation; that is the
  intended design, but it places a higher bar on invariants 2/3/4
  than was met.
- No new `unsafe`. No anti-pattern B violations. Refactor is clean.

## Requested changes before re-review

1. Add an adversarial-permutation test for invariant #4 that does
   not re-sort by ordinal before commit, or that enumerates all
   schedules and asserts neighbor equality.
2. Add a cross-epoch invariant test for #5.
3. Either add a `compile_fail` or trait-boundary test for #2/#3, or
   document why runtime-only assertion is acceptable and reference
   the call sites that prove single-writer ownership.
4. Rewrite the `request.md` "Scope" and "Review Notes" sections to
   list each packet-003 invariant and mark coverage honestly.

The refactor and the three tests as landed are a good foundation;
they're just not a "model" yet.
