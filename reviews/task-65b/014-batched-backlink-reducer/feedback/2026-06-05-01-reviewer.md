# Slice F — Batched Backlink Reducer — APPROVE-WITH-FLAGS

## Verdict

**APPROVE-WITH-FLAGS.** Real-10k gate now meets ≤ 3 s with
preserved recall, which is a substantial win over packet 013's
4.70 s miss. The mechanical perf changes are clean. The
algorithmic change (`grow_alpha = batch_size == 1`) is honest
about its scope but introduces a real correctness boundary

## What landed

Commit `f3809bf18` (`src/am/ec_diskann/vamana.rs:598-1221`,
+49 / -16 lines):

### Mechanical perf changes (clean wins)

- **Duplicate `combined.sort()` eliminated** at two call
  sites: `robust_prune` already sorts internally, so the
  outer `combined.sort()` before passing in was wasted work
  per reprune. Touches the same hot path that previously
  dominated reducer time.
- **Adjacency replacement batched** to one
  `replace_neighbors(pivot, pruned)` per pivot. Prior shape
  was `set_neighbors(...)` + per-target writes; the new
  shape consolidates the `Arc<[u32]>` swap to once per
  proposal. Substantial allocator-churn relief.

These two are unambiguous APPROVE.

### Algorithmic policy change (the review-focus question)

`let grow_alpha = batch_size == 1;` (`vamana.rs:1022`):

- `batch_size = 1` retains growing-alpha pruning (the serial-
  equivalence path Slice D's byte-equality oracle is based on).
- `batch_size > 1` uses `robust_prune_final_alpha` directly
  (single pass at `alpha_final`), skipping the intermediate-
  alpha distance work.

This is a **real algorithmic divergence**, not just a
performance tweak. The graph produced at batch ≥ 2 is now
**not** the same graph the serial path produces. The coder is
honest about this in `request.md`: "it changes the graph
produced by multi-worker builds and should be treated as the
main correctness/design question."

Empirical evidence in this packet:

- b=64 holds recall (0.9950 ≥ 0.9925 floor).
- b=96 misses by 0.0005.
- b=128 (the `b128-after-prune` exploratory artifacts) ran
  but isn't summarized in `manifest.md`'s gate table —
  presumably trends the same way.

So the recall floor empirically binds the batch size between
b=64 and b=96 on real-10k. That's a narrow window.

## Flags

### F-1. The recall floor needs to be enforced by the code, not just observed in artifacts

`b=96` produces a graph that fails the Task 65 recall floor
by 0.0005. Nothing in the build path prevents an operator
from setting `parallel_build_batch_size = 96` and silently
shipping a sub-floor graph. Two acceptable shapes:

- **Reloption upper bound**: clip `parallel_build_batch_size`
  to a value the recall sweep has validated (e.g. 64 on
  real-10k-class fixtures), with a `NOTICE` if a higher value
  is requested. Document the empirical basis in the reloption
  doc-string.
- **Build-time post-check**: compute a recall proxy on a
  fixed-seed sample at build end; if below floor, escalate
  to `NOTICE` or fall back to `grow_alpha = true` and rebuild.

Without one of these, the recall floor is an observability
property, not a correctness property.

### F-2. Per-batch-size recall surface needs to live in the AM, not in measurement packets

This packet measures recall *after the build* via
`ecaz bench recall`. Future operators won't run the sweep.
The AM should expose at minimum:

- a `NOTICE` line at build end documenting
  `alpha_growth_disabled=true/false`,
- the `parallel_batch_size` value used,
- a one-liner in the build log explaining the recall trade-off
  for batch > 1.

`grow_alpha = batch_size == 1` is invisible to the operator
right now. Surfacing it makes future debugging tractable.

### F-3. real-100k gate is still 4.6× over budget

`139.356 s` vs `30 s` target. The reducer is still 88% of
total (122 of 139 s). Per ADR-075 migration trigger #1
("ordered leader commit is the measured Amdahl bottleneck
after Slice E/F"), this is the case where the rayon stepping
stone is reaching its ceiling and the sharded live-commit /
ParallelContext migration should be considered.

Path forward options:
- **(A) Continue iterating on the rayon path** for one more
  slice (Slice F.2?) targeting the reducer at real-100k
  scale. The fact that the same optimization halved real-10k
  reducer time suggests there's more headroom, but the
  workload at 100k is different (more backlinks per epoch).
- **(B) Invoke ADR-075 migration trigger** for the real-100k
  case. Open a Slice G packet that pivots to either sharded
  live-commit or ParallelContext-with-DSM, scoped at the
  real-100k workload.
- **(C) File a partial Stop Condition**: declare real-10k met
  and real-100k deferred to a future task. This keeps Task
  65b's primary fixture (real-10k) in scope and explicitly
  matches ADR-075's stepping-stone framing.

The coder's call. (A) is the lowest-risk next step if the
real-100k reducer shape is similar enough to real-10k. (C) is
the honest closeout if reviewer + coder + project owner all
agree real-10k was the load-bearing fixture.

### F-4. Honest packet framing

`request.md` and `manifest.md` are clear that this is
progress, not closure, and explicitly call the real-100k miss
out. Good. Matches `feedback_dont_overclaim_done`.
