## Finding 1 (HIGH) — baseline, armed, and recovery results are discarded

`run_spire_remote_socket_fault_probe` executes
`SELECT count(*) FROM ec_spire_remote_search_production_read_profile(...)`
with `batch_execute` at `spire_multicluster.rs:2487-2491`,
`:2494-2498`, and `:2528-2531`. `batch_execute` exposes only command success;
the returned count is never read or checked.

Consequences:

- the baseline can return zero or an incomplete result and still pass;
- socket-slow can return a degraded/partial result and still pass;
- after socket-reset, the "recovery" query can continue returning a clean
  degraded result with remote 1 absent and still emit `recovery=true`.

The exact provider marker proves remote 1 was faulted during the armed query,
but it does not prove that the participant rejoined afterward. Capture the
baseline, armed, and recovery counts (or stronger participant/source
identities). Require a nonempty expected baseline, equality for slow mode, and
full baseline-equivalent participation after disarm. Reset may remain either a
clean error or explicitly verified degraded result while armed.

## Finding 2 (LOW) — the manifest understates the fixture topology

`artifacts/manifest.md` describes a
"one-coordinator/two-participant" fixture. The implementation constructs one
coordinator plus `remote1`, `remote2`, and `remote3`
(`spire_multicluster.rs:1229-1262`), and the documentation correctly calls it
a three-worker fixture.

Correct the packet manifest so its topology metadata matches the code and the
lane that Linux evidence will exercise.
