## Finding 11 (Medium): the PG18 regression fixture builds a line-pointer state PostgreSQL never produces, and the assertion depends on it

`append_unused_line_pointer` (`routine.rs`) creates the "unused" slot with:

```rust
let offset_number = page.add_item(&[0xFF])?;
page.mark_item_unused(offset_number)?;
```

and `mark_item_unused` (`wal.rs`) does only `(&mut *item_id).set_lp_flags(0)`.

That zeroes `lp_flags` to `LP_UNUSED` but leaves `lp_off` and `lp_len` at the
values `PageAddItemExtended` wrote (`lp_len = 1`). Real PostgreSQL never
produces that combination: `ItemIdSetUnused` clears all three, so a vacuumed
slot has `lp_flags = LP_UNUSED`, `lp_off = 0`, `lp_len = 0`.

The difference is load-bearing for this test. `ItemIdHasStorage(itemId)` is
`lp_len != 0`, and `PageAddItemExtended`'s free-slot search only reuses a slot
when **both** `!ItemIdIsUsed` and `!ItemIdHasStorage` hold. `add_item` calls
`PageAddItemExtended(..., InvalidOffsetNumber, 0)`, so it does perform that
search. Consequences:

- With the fixture's slot (`lp_len = 1`), PostgreSQL skips it, the later
  insert appends at a higher offset, and the assertion
  `inserted_tid.offset_number > unused_tid.offset_number` holds.
- With a faithful vacuum-produced slot (`lp_len = 0`), PostgreSQL **reuses**
  offset 2, and that same assertion would fail.

So the regression currently passes because the fixture is non-canonical, and
`manifest.md`'s description of it as "a real unused line pointer" / "an
LP_UNUSED physical offset" overstates its fidelity.

The fix itself is not in question — `visit_tuple_bytes` classifies a slot as
`Unused` on `lp_flags() == 0` alone, so materialization handles both states
identically, and the offset-preservation behaviour under test is real. What is
missing is coverage of the state that actually occurs in production.

Requested:

1. make `mark_item_unused` match `ItemIdSetUnused` — clear `lp_off` and
   `lp_len` alongside `lp_flags` — so the fixture is byte-faithful to what
   VACUUM leaves behind;
2. rework the offset assertion accordingly, since PostgreSQL will then reuse
   the slot: assert the reused tuple is addressable at the *recycled* offset
   and that materialization maps it correctly; and
3. keep a persistent-gap case as well — the scenario the fix exists for — by
   constructing it the way production does (a gap on a page with no room for
   the next tuple, so the slot survives), rather than by leaving stale
   `lp_len`.

Both paths matter: (2) is what happens after a normal VACUUM, and (3) is what
breaks TID stability. Today the packet tests neither exactly.

## Nit: state why recall is bit-identical

Recall matching to four decimals at all 15 points is the expected result, but
the packet does not say why: a freshly built-and-loaded corpus index contains
no unused line pointers, so the A/B never exercises the changed branch. That
makes the suite a genuine no-regression gate and not evidence that the fix
works — which is the PG18 regression's job. Worth one sentence in
`manifest.md`, so a later reader does not mistake the identical recall for
validation of the fix.
