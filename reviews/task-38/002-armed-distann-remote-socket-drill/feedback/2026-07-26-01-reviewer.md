# Review Feedback: Task 38 packet 002 — armed DistANN remote socket drill

## Verdict

**REQUEST CHANGES.** The exact-peer/provider design is narrow and the packet
correctly declines to claim Linux runtime coverage. Two evidence gates need to
be corrected before the first live run is retained as decision-grade proof.
Live reset and slow execution on Linux remains a closeout requirement.

## Finding 1 (MEDIUM) — the runner reports recovery before it executes recovery

`run_remote_socket_fault_probe` returns a line containing
`recovery=verified-by-subsequent-owner-query`
(`distann_multicluster.rs:3460-3466`). The caller immediately prints that line
at `:3277`, but only then executes the purported recovery/materialization query
at `:3281-3287`.

If that query fails, the command correctly returns an error and never writes
the final summary, but captured stdout already contains a positive recovery
claim. A packet-local runner log can therefore say recovery was verified in a
failed run.

Move the recovery query into the probe and emit the line only after it checks
the expected `source_id`, or emit `recovery=pending` first and a distinct
verified line after `materialized_source_id == source_id`.

## Finding 2 (MEDIUM) — socket-slow does not prove a delta over its baseline

The slow gate at `distann_multicluster.rs:3437-3443` checks only
`fault_ms >= latency_ms`. If a normal remote-owner query already takes longer
than the configured delay, a run passes without proving an observable
slow-versus-baseline effect. The exact marker proves that an interposed syscall
was reached, but the retained timing claim still lacks an A/B gate.

Retain and enforce a same-run delta, preferably
`fault_ms >= baseline_ms + latency_ms` with a documented tolerance if the first
Linux measurements show scheduler variance. At minimum require
`fault_ms > baseline_ms` as packet 003 already does.
