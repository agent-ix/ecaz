## Production change: no risk, correct pattern

Six new `crate::fault::maybe_fail_palloc` sites in `ec_distann` — two in
`ambuild.rs` (including the control-relation path, which is DistANN-specific
and correctly separate) and four in `routine.rs` at `aminsert`, `ambulkdelete`,
`amvacuumcleanup`, and `ambeginscan`. That mirrors the `ec_diskann` placement
exactly, and `maybe_fail_palloc` is GUC-gated on `ecaz.fault_palloc_nth`
(default `-1`) with an early return, so the shipped cost is a static read plus a
branch. `aminsert` is per-tuple, so it is worth naming that explicitly — but
the same call already ships in four AMs on the same path, so this adds no new
class of cost. The `routine.rs` import reorder is rustfmt churn.

No objection here.

## Flag 1 (HIGH, record before citing this as coverage) — the new C has never been compiled anywhere

`crates/ecaz-fault-injection/build.rs` returns early unless
`CARGO_CFG_TARGET_OS == "linux"`, so this macOS host never invokes the C
compiler on `ldpreload_provider.c`. Repository CI is `workflow_dispatch`-only
(unchanged on this branch), so no Linux job has built it either. The 136 lines
of new C — `peer_target_matches`, `should_fault_socket`, `maybe_reset_socket`,
`maybe_sleep_socket`, the `recv`/`send` interposers — have not been compiled,
let alone executed.

`unavailable-summary.log` implies this (`provider build is target_os=linux`)
but frames it as "cannot execute". The stronger and more useful statement is
"not compiled on any host, including CI". Please say that.

What raises this above a documentation nit: the diff is **not purely
additive**. It inserts `maybe_reset_socket(...)` and `maybe_sleep_socket(...)`
at the top of the *existing* `read()` and `write()` interposers — the exact
code paths behind the EIO/ENOSPC/slow-disk lanes that packet 001 evidenced live
in May. A previously-evidenced provider now carries an uncompiled edit. The
ordering is written defensively (`should_fault_socket` short-circuits on
`enabled()` and `mode_is()` before ever calling `getpeername`, so file-fault
modes never pay the socket path), and I believe it is correct by reading — but
"correct by reading" is what this repo's rules exist to distrust.

## Flag 2 (MEDIUM) — exact-peer matching likely cannot work over Unix sockets

`peer_target_matches` builds the match key from `getpeername(fd)`. For an
accepted `AF_UNIX` connection the *server* side has an unnamed peer — the
client never binds a path — so `sun_path` is empty and the key becomes the bare
string `"unix:"`. Matching that would require setting
`ECAZ_FAULT_PROVIDER_PEER=unix:`, which then matches *every* unnamed Unix peer
in the process: precisely the opposite of the "exact peer, without faulting
unrelated PostgreSQL traffic" property the PR body claims.

TCP is unaffected, and both transports this targets are TCP
(`socket-reset-env-current-host.log` shows `PEER=tcp:127.0.0.1:39711`), so the
feature may be fine as built. But the docs and `--peer` help should say
TCP-only rather than implying general socket support, otherwise the first
person to point this at a Unix-socket PG connection gets either no faults or
indiscriminate ones. Worth a `sun_path[0] == '\0'` guard that fails loudly
instead of silently producing `"unix:"`.

## Flag 3 (MEDIUM) — the interposed syscall set may miss the transports it targets

Only `read`, `write`, `recv`, and `send` are hooked. Not `recvmsg`, `sendmsg`,
`recvfrom`, `sendto`, `readv`, or `writev`. Async Rust network stacks routinely
use the vectored and message variants — `writev` for buffered writes,
`sendmsg`/`recvmsg` under several TLS and runtime combinations — so if the
DistANN owner/payload or SPIRE remote SQL transports take those paths, the
fault never fires.

The failure mode is the bad kind: a lane that injects nothing reports no error,
which is shaped like a pass. This is unfalsifiable on the current host, so it
is a question for the first Linux run rather than a defect claim —
`strace -f -e trace=network` on one query settles it in a minute, and the
answer belongs in the packet either way.

## Flag 4 (LOW) — `FaultFixture` makes an invalid state representable

`FaultFixture::new` is a public `const fn` over `(FaultAm, Option<DistannCodec>)`,
so `FaultFixture::new(FaultAm::DistAnn, None)` is constructible and both
`slug()` and `as_str()` fall through to `_ => "invalid"`. Those strings feed
fixture identity and relation naming. The `ALL` array is correct and
`all_lanes_cover_every_distann_codec_with_distinct_fixture_ids` guards it, but
the guard is on the constant, not the constructor.

Folding the codec into the variant — `FaultAm::DistAnn(DistannCodec)` — deletes
both `_ => "invalid"` arms and makes the bad state unconstructible. Worth doing
while the type is young and has one call site pattern.

## Flag 5 (LOW) — errno and syscall hygiene in the new path

`peer_target_matches` calls `getpeername()` on every `read`/`write` while a
socket mode is active, including on regular files where it fails with
`ENOTSOCK` and leaves `errno` modified before the real call runs. Harmless as
written — `errno` is only meaningful after the real call fails, and that call
sets its own — but it is worth a comment so a future edit does not start
trusting `errno` across that boundary. Same path doubles the syscall count for
file I/O under socket modes, which is acceptable for a fault provider and worth
knowing when interpreting `socket-slow` timings.

## Review-focus response

The PR asks for acceptance of the five-AM scope and the documented Linux-host
deferrals. On scope: accepted, the DistANN fixture model is right and the

packet is honest about it — with the correction in Flag 1 that "cannot execute
here" understates it to "never compiled anywhere", and the note that a Linux
dev host, if one is reachable, converts this from a deferral into a scheduling
choice.
