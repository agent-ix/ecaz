## Finding 9 (Medium): the OOM-kill oracle lost its self-check and can no longer detect its own degradation

`run_memory_oom_kill_case` (`fault.rs:3386`) gained an unrequested change in
`147d44d05`:

```rust
let worker_task = tokio::spawn(async move {
    worker.batch_execute(&sql).await?;              // the AM workload
    worker.batch_execute("SELECT pg_sleep(10)").await  // new: hold open
});
```

The old shape ran only the workload, and the oracle
`Ok(()) => Err("{label} unexpectedly completed before SIGKILL")` was a real
guard: if the SIGKILL at `delay_ms = 25` landed after the workload finished, the
lane failed loudly and told you the timing was wrong.

With the `pg_sleep(10)` hold appended, the task can no longer return `Ok` in
either case — it is killed during the build, or it is killed while parked in
`pg_sleep`. Both paths look identical to the oracle and both pass. The guard
that made the timing meaningful has been removed, and nothing replaced it.

The comment is candid that this "does not claim that the signal lands in an AM
critical section", but the effect is stronger than the comment admits: the lane
can no longer *detect* that it degraded. On a faster host where a workload
completes inside 25ms, this reports a clean pass for killing an idle backend —
precisely the "silent cap" the repo rules forbid.

**To be fair to this run, the M5 evidence is not compromised.** I checked what
the killed backends were actually executing, via PostgreSQL's own
`DETAIL: Failed process was running:` lines in
`m5-partial-live/main-postmaster.log`:

```
[91787] LOG:  client backend (PID 93248) was terminated by signal 9: Killed: 9
[91787] DETAIL:  Failed process was running: CREATE INDEX ecaz_fault_hnsw_idx ... USING ec_hnsw ...
[91787] LOG:  client backend (PID 93278) was terminated by signal 9: Killed: 9
[91787] DETAIL:  Failed process was running: SET enable_seqscan = off; SELECT count(*) FROM generate_series(1, 400000) ...
```

Both signals verifiably landed inside the AM workload, and the log shows genuine
crash recovery (`redo starts at C0/8B04B790`, `redo done`, `ready to accept
connections`). So the `executed=49` claim stands on this host.

The defect is the loss of the guard for *future* runs — notably the designated
Intel host, which is faster and where the 25ms delay has less margin. PostgreSQL
already reports the ground truth in that DETAIL line; the runner simply no
longer checks it.

Requested: keep the hold as a safety net, but restore the guard by asserting
*where* the signal landed. Immediately before `send_sigkill`, query
`pg_stat_activity` for that pid and require `state = 'active'` with a `query`
matching the AM workload rather than `pg_sleep`; fail the case otherwise. Then
the marker can honestly report `signal_landed_in=workload` and the lane means
what its name says. If the intent really is to accept an idle kill, the case
must be renamed and the plan's expected outcome updated, because
"oom-kill during build" is what the 116-case plan advertises.

## Finding 10 (Blocking): a production DiskANN correctness fix landed inside a fault-injection review response, with no behavioral or benchmark coverage

`a35d1cd71` changes production DiskANN code — `src/storage/page.rs`,
`src/am/ec_diskann/reader.rs`, `src/am/ec_diskann/scan_state.rs` — not the fault
harness. The defect it fixes is real and serious: `materialize_chain_from_index_handle`
previously compacted tuples via `insert_raw_tuple`, dropping unused line-pointer
slots, so every physical TID after an unused slot shifted. Stored graph
neighbour TIDs then resolved to the wrong tuples. The fix preserves offsets via
`insert_existing_raw_tuple` / `insert_unused_slot` and filters sentinels in
`iter_tids`. That the fault harness surfaced this is a genuine win for Task 38.

The problem is how it landed. This path is not test-only — it is called from
`insert.rs:827`, `routine.rs:1270/1822/2173/2183`, and `diagnostics.rs:68`,
i.e. live insert, scan, and vacuum callbacks. Three specific gaps:

**10a. The invariant the fix exists to restore is checked with `debug_assert`.**

```rust
let materialized_tid = page.insert_existing_raw_tuple(tuple_bytes)?;
debug_assert_eq!(materialized_tid, tid);
```

Both `debug_assert_eq!` calls compile out in release. In the builds that ship,
a materialized-vs-physical TID divergence — exactly the bug just fixed — is
silent again. This must be a hard check returning `Err`, since the enclosing
function already returns `Result<_, String>`.

**10b. Two `.expect()` panics on a live AM callback path.** In the same
function: `.expect("materialized chain always has a first page")` and
`.expect("physical block must have a matching materialized page")`. A panic
crossing the pgrx `extern "C"` boundary is the failure mode Task 38 exists to
prevent, and the function returns `Result<_, String>`, so both are avoidable
with no design change. Per the branch's standing rule on safety regressions,
these are not "optional cleanups".

**10c. No behavioral or benchmark coverage.** The only evidence is two
page-accounting unit tests
(`data_page_materialization_preserves_unused_line_pointer_offsets`,
`data_page_materialization_uses_physical_pageadditem_accounting`). Neither
exercises a DiskANN scan. There is no regression test that reproduces the
original defect end-to-end — build an index, produce an unused line pointer
(update/vacuum), scan, and assert neighbour identity — so nothing prevents a
future compaction change from silently reintroducing it.

More importantly, `CLAUDE.md` is explicit: a change to **index, scan, or storage
behavior** must not be closed on unit tests or predicted wins, and requires A/B
recall + latency + storage at **10k / 50k / 100k** for the affected access
method. `ec_diskann` scan traversal and page materialization are squarely in
scope. The packet currently claims "the Apple-M5 scope is complete" while this
change carries none of that evidence.

Requested: split this into its own packet with its own `request.md`; convert
10a to a hard error and 10b to returned errors; add an end-to-end DiskANN
regression that fails without the fix; and run the standard `ec_diskann` A/B at
10k/50k/100k per NFR-007 before any closeout claim covers it. Task 38's M5
scope should not be described as complete while an unbenchmarked production AM
change rides inside it.

## Nit: `raw_tuple` returns the unused-slot sentinel as success

`insert_unused_slot` stores `Vec::new()`, and `raw_tuple` returns it as
`Ok(&[])` — indistinguishable from a legitimately empty tuple. Callers are
saved by downstream length checks (`tuple_tag` errors with "tuple at (b,o) is
empty", and `VamanaNodeTuple::decode` rejects a short buffer), so this is not
currently exploitable, but the sentinel deserves an explicit representation
rather than an in-band empty vector.
