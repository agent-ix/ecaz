## Finding 1 (Blocking, M5): `pg_stat_io` / `pg_stat_wal` are reported "unavailable" on a host where both work, and the aggregate never evaluates them outside `run_smoke`

`assert_pg_stat_io_non_decreasing` (`fault.rs:3704`) and
`assert_pg_stat_wal_non_decreasing` (`fault.rs:3734`) both open with:

```rust
let Some(before) = before else {
    crate::ecaz_println!("[fault] pg_stat_io unavailable; skipping io counter probe");
    return Ok(());
};
```

`before == None` means *this caller captured no baseline*. It does not mean the
view is unavailable. The printed marker asserts a host capability gap that does
not exist, and the lane still reports pass.

I measured both views on this exact host and PG18 instance:

```
SELECT count(*) FROM pg_stat_io;                          -> 79
SELECT coalesce(sum(reads + writes + writebacks + extends + fsyncs), 0)::bigint
  FROM pg_stat_io;                                        -> 113567203
SELECT wal_records::bigint, wal_bytes::bigint FROM pg_stat_wal;
                                                          -> 359065291  407713486649
```

Those are the *exact* queries in `pg_stat_io_total()` and
`pg_stat_wal_snapshot()`. Both succeed. Evidence:
`artifacts/2026-07-27-reviewer-pgstat-availability.log` and
`artifacts/2026-07-27-reviewer-pgstat-exact.log`.

I then ran a real host-independent aggregate case live at this checkpoint:

```
target/debug/ecaz --database ecaz_fault_task38 --host /Users/peter/.pgrx --port 28818 \
  dev fault mutation-control --kind cancel-unexpected-palloc --rows 16 \
```

Evidence: `artifacts/2026-07-27-reviewer-m5-mutation-live.log`. This is the same

## Finding 2 (Blocking, M5): the aggregate refuses to run its 49 host-independent cases here, so `make fault-full` has zero local authority on this host

`require_full_host` (`fault.rs:1994`) bails on any non-Linux host before a
single phase executes. But phases `local` (35) and `mutation` (14) are pure
SQL against a live PG18 — no LD_PRELOAD, no cgroup, no systemd — and packets
006/007 already executed exactly those lanes live on this M5. I re-executed one
of them above at this checkpoint to be sure.

So on this host, the "authoritative" aggregate produces a plan and nothing
else, while 49 of its 116 cases are runnable here right now. Task 38 §Exit
Criteria says "`make fault-full` is locally authoritative"; on the M5 it is
authoritative for zero cases.

The precedent for the correct shape is already in this same file:
`run_memory_rlimit_oom_probe` has a `#[cfg(not(target_os = "linux"))]` variant
that prints `memory_rlimit_oom_skipped target_os=macos … reason=linux-only` and
returns `Ok`, rather than failing the lane. The aggregate should do the same
thing at phase granularity.

Requested: run what the host supports and ledger the rest explicitly. Concretely
— execute the `local` and `mutation` phases on any host with a live PG18; skip
`provider`/`remote-socket`/`cgroup` on non-Linux with one explicit
`full_phase_skipped phase=<name> reason=linux-only cases=<n>` line per phase;
and gate the authority marker so the closing line reads
`live_authority=partial executed=49 skipped=67` on this M5 and
`live_authority=true executed=116 skipped=0` only on the designated host. Keep
`require_full_host`'s Linux checks, but scope them to the phases that need
them. Then land the M5 partial run as packet evidence.

Per `CLAUDE.md`'s no-setup-deferral rule, "the aggregate only runs on Linux" is
not an acceptable resting state for 49 cases that run here.

## Finding 3 (Non-blocking, source): `enabled()` and `fd_target_matches()` clobber `errno` on every interposed call

In `ldpreload_provider.c`, `peer_target_matches` is careful — it saves
`saved_errno`, restores it on every exit path, and the comment explains exactly
why. That discipline is missing from its two neighbours on the same hot path:

- `enabled()` now calls `access(arm_file, F_OK)` (new in this checkpoint) and
  leaves `errno == ENOENT` behind whenever the provider is disarmed, which is
  the majority state of every socket and provider case.
- `fd_target_matches()` calls `readlink("/proc/self/fd/N")` and leaves `errno`
  set whenever the descriptor has no `/proc` link (sockets, pipes, anon fds).
- `record_fault_event()` → `append_marker_line()` can fail its raw `openat`
  and leave `errno` set.

All three run *before* the real syscall is dispatched. This checkpoint widens
the exposure: `maybe_sleep_path`/`maybe_sleep_fd` now route slow-disk through
`should_fault_path`/`should_fault_fd`, so the slow-disk lane — which previously
used the errno-free `maybe_sleep()` — now inherits it.

The failure mode is narrow but real: PostgreSQL uses the
`errno = 0; … ; if (errno == 0) errno = ENOSPC;` idiom around short writes
(`XLogWrite` in `xlog.c`). Our clobber lands after PG's `errno = 0` and before
the real `pwrite`, so a genuine short write is reported with a fabricated
`ENOENT`. In a fault-injection harness specifically, an oracle keying on the
resulting SQLSTATE can accept for the wrong reason.

Requested: save and restore `errno` in `enabled()`, `fd_target_matches()`, and
around `record_fault_event()`, matching what `peer_target_matches` already does.

## Finding 4 (Non-blocking, tests): the new slow-disk regression test does not test the behavior that was broken

`ldpreload_slow_disk_marks_only_the_matched_path`
(`ecaz-fault-injection/src/lib.rs:1045`) asserts only that the marker contains
`fault=1 mode=slow-disk target=/etc/hosts` for a matched path and no `fault=1`
for an unmatched one. The sequence-1 defect was that slow disk **slept
globally**. Marker emission and sleeping are separately implemented — the test
would still pass if `sleep_millis` were deleted, or if it slept on every path.

The test also runs at `LATENCY_MS=1`, which is unmeasurable.

Requested: raise the latency to something resolvable (300–500ms) and assert
wall-clock — matched run elapsed `>= latency`, unmatched run elapsed
`< latency`. It stays Linux-gated, so it must be authored now to be picked up
by the designated host's run.

## Finding 5 (Non-blocking, oracle strength): the slow-disk timing threshold is confounded by the provider restart

`run_full_provider_case` measures `baseline_ms` via `measure_disk_workload`
*before* `run_provider_restart`, then compares the post-restart measurement
against `baseline + configured_latency`. The restart drops shared buffers, so
the cold-cache penalty alone can satisfy the threshold with the injected sleep
contributing nothing. At the default `--provider-latency-ms 25` the restart
effect is plausibly larger than the signal.

The arithmetic fix from sequence 1 is correct as far as it goes, and the
`fault=1 mode=slow-disk` marker assertion is what actually proves injection
fired. But the timing line reads like an independent proof and is not one.

Requested: either measure the baseline after a provider-off restart within the
same case so both measurements start cold, or state plainly in `manifest.md`
that the marker is the injection proof and the timing threshold is a
supporting sanity bound.

## Finding 6 (Nit): hardcoded counts in the evidence line

`run_full` computes `provider_cases` from `cases` but hardcodes
`remote_socket_cases=4 cgroup_cases=7` in the format string
(`fault.rs:1864`). If the plan changes, the emitted evidence line silently
lies while the unit test catches the drift. Compute all three from `cases`.

## Finding 7 (Nit): a single unreadable log aborts the whole PANIC audit

`capture_and_assert_full_logs` uses `fs::read_to_string(log)?` inside the loop,
so one non-UTF-8 or unreadable `.log` anywhere under the artifact root ends the
audit early and skips writing `no-panic-audit.log` — after a long live run.
Use a lossy read and accumulate failures.

## Finding 8 (Note, isolation): SPIRE sockets escape the aggregate's runtime root

`spire_multicluster.rs:1167` sets
`socket_dir = repo_root/target/spire-local-multinode-sockets-{run_id}`,
ignoring `--run-dir`. The aggregate passes an isolated `case_runtime`, but
SPIRE's sockets land outside it. Harmless for evidence integrity (it is under
`target/`), but `request.md`'s "evidence/runtime roots remain isolated" claim
has this exception and should say so.

## Verdict

Source and packet provenance for the 116-case plan are sound, and the sequence-1
threshold fix is correctly implemented and tested. Findings 1 and 2 are blocking
**for the Apple-M5 scope specifically**: both are defects this host can fix and
prove today, and both currently degrade the evidence the Intel/Linux run will
produce. Finding 1 additionally means an already-approved packet-007 artifact
carries a false capability claim.

Findings 3–5 are source/test-quality issues on the Linux path; they are not
M5-blocking but should land before the designated host runs the aggregate,
because 4 in particular is the only regression guard on the sequence-1 fix.

Task 38 correctly remains open. No AWS, remote host, Docker, CI, nightly, or
Intel command was run for this review. All commands executed here were local
Apple M5 against the pgrx PG18 instance at `/Users/peter/.pgrx` port `28818`.
