## Must fix before the Pareto / any promote call

1. **The "p50/p95 latency" table is funnel-inflated spire-pipeline timing, not a
   clean `latency` step — and it is presented as latency.** This is the same
   issue flagged on 012 and 015, and here it's worse because the request draws a
   *cost* conclusion from it ("b4/tr50 … higher fixed-nprobe latency"). The config
   has only load + storage + spire-pipeline + truth-cache — no `latency` step. The
   spire-pipeline clock runs with full per-query funnel + stage-containment
   instrumentation attached (157 ms at np4 up to 2135 ms at np96 for 50k is
   ~5–40× the Task 120 baseline), so it is a *relative* cross-cell cost signal
   only. Add the caveat wherever these numbers appear, and the finalist cells need
   a real cache-warm `latency` step (registered concurrency) before recall vs
   latency vs storage can be Pareto'd. Right now the recall/storage axes are
   decision-grade and the latency axis is not.

2. **The consolidated `…-results.jsonl` was clobbered by the `--only` resumes.**
   It currently holds only `pipeline-50k_b4_tr10_f8` rows (and those are
   `tuple_transport_capabilities` diagnostics, not recall), because each `--only`
   resume rewrote `--results-output`. The recall *does* fully trace — to the
   per-cell `pipeline-*.log` + `*-stage-containment.jsonl` — so the evidence is
   intact and I verified every cited number against it. But the artifact named as
   the packet's consolidated results no longer represents the four cells, which is
   a provenance trap for the next reader. Either regenerate a single consolidated
   results.jsonl covering all four cells, or have `manifest.md` name the per-cell
   `*-stage-containment.jsonl` as the source of truth and note the consolidated
   file is partial.
