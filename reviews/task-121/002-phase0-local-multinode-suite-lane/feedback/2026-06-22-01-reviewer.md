# Review: Task 121 Phase 0 - Local Multi-Node Suite Lane

## Verdict: changes-requested

The slice is well-structured and clean as a *suite-step wrapper*: it parses,
validates, templates artifact dirs, expands the right command, and has a passing
unit test + dry-run evidence. But it does **not** meet Phase 0 AC1 as written.
The new `spire-local-multinode` step is a thin clap shell that shells out to the
727-line hand-rolled `scripts/run_spire_phase13e_aws_harness_local_pg18.sh`
(itself shelling `scripts/spire-aws/{load,register,smoke}.sh` + a `jq`-generated
inline suite config). AC1 explicitly calls for making local multi-node
first-class **"with no bespoke harness"** and removing exactly that "phase13e
harness" churn. This wraps the harness; it does not replace it. On top of that
the lane cannot drive the reloption matrix AC1 requires, and the declared
artifact paths do not match what the harness produces.

## What is good

- Clean, idiomatic extension of the FR-038 suite runner: new `SuiteStep`
  variant threaded through name/kind/tags/validate/expand/expected_artifacts/
  input_paths/produced_paths, plus `push_opt_u16`/`push_opt_usize` helpers
  (`crates/ecaz-cli/src/commands/bench/suite.rs:211, 398-447, 2511-2540,
  3120-3176`). No new bash *sweeper* was added at the suite layer - it routes
  through `ecaz bench suite`, satisfying the literal "no new bash sweeper" rule
  for the runner itself.
- Validation is sensible: pg must be 18, tier in {correctness, representative},
  `bench_top_k`/`bench_queries_limit` reject 0
  (`suite.rs:2511-2540`).
- Unit test `spire_local_multinode_step_expands_local_four_instance_lane`
  asserts the expansion and ports (`suite.rs:4061-4133`), and
  `cargo test ... commands::bench::suite` is green (52 passed,
  `artifacts/cargo-test-ecaz-cli-suite.log:58,63`).
- Dry-run evidence traces and is reproducible
  (`artifacts/suite-phase0-local-multinode-dryrun{,.log,-manifest.json}`).
- Packet hygiene is clean: 6 files, no corpus TSVs, no tunnel-state, no SSM
  trees, head_sha recorded.

## Required changes

### 1. AC1, half A: this wraps the hand-rolled harness, it does not remove it
The CLI command `run_local_multinode_pg18` requires and executes
`scripts/run_spire_phase13e_aws_harness_local_pg18.sh`
(`crates/ecaz-cli/src/commands/dev/spire_multicluster.rs:985-1073`); if the
script is absent it bails (`:996-1001`). That 727-line script is the Task 120
"phase13e" harness (it even self-describes as "the AWS Phase 13e correctness
harness against four local PG18 instances", `scripts/...sh:32`), and it in turn
shells `scripts/spire-aws/load.sh` (711 lines), `register.sh`, `smoke.sh` and
hand-builds a `spire-pipeline` SuiteConfig with `jq`
(`scripts/...sh:313-410`). AC1's whole point (and the task "Why" / Non-Goals:
"No bespoke bench sweepers or per-packet shell glue; extend `ecaz bench suite`")
is to retire that glue. Renaming the entry point to a clap subcommand does not
make the topology first-class - the orchestration (initdb x4, port/socket
management, role/extension creation, topology JSON authoring, placement
registration, the nested suite-config generation) still lives in shell. The
node-bring-up + placement-registration belongs *inside* the suite runner (e.g.
a real multinode step that brings up the four instances, registers remotes, and
emits a normal child `ecaz bench suite` run), not behind a `Command::new("bash")`
shim. As written, the lane is a wrapper, not a first-class lane.

### 2. AC1, half B: the lane cannot drive the reloption / per-lever matrix
AC1 requires "a single SuiteConfig builds per-variant `ec_spire` indexes via
reloptions". The whole Phase 1 OFAT screen (nlists, top_graph_search_list_size,
boundary_replica_count, recursive_fanout, top_graph_degree,
training_sample_rows, storage_format) depends on this. The underlying
`load.sh` *does* support it - via env vars `SPIRE_AWS_COORD_RELOPTIONS`,
`SPIRE_AWS_REMOTE_RELOPTIONS`, `SPIRE_AWS_STORAGE_FORMAT` and `--index-name`
(`scripts/spire-aws/load.sh:42-81, 327-343, 395-416`). But the new
`LocalMultinodePg18Args` exposes **none** of these - no `--reloption`,
`--storage-format`, `--index-name`, or per-lever flags
(`spire_multicluster.rs:373-466`), and the command sets no `SPIRE_AWS_*` env
(`grep RELOPTION|STORAGE_FORMAT|index_name` over the file is empty). So a Task
121 `SuiteConfig` literally cannot vary `ec_spire` reloptions through this lane;
you would still have to set env vars on the harness by hand. The reloption
matrix half of AC1 is not delivered. The packet `request.md` and `manifest.md`
do not acknowledge this gap.

### 3. Declared expected_artifacts do not match harness output (broken evidence tracking)
After a real run the suite will report `missing_artifacts` for this step because
the declared paths are wrong (`suite.rs:2690-2699`):
- `expected_artifacts` declares `<artifact_dir>/topology.local.json`, but the
  harness writes topology to `$RUN_DIR/topology.local.json`
  (`scripts/...sh:177,251`). With `run_dir` != `artifact_dir` (exactly the
  dry-run config's layout), the file never lands under `artifact_dir`.
- `expected_artifacts` declares
  `<artifact_dir>/local-spire-pipeline-suite/suite-manifest.json` and
  `.../suite-results.jsonl`, but the harness writes the nested suite to
  `$LOG_DIR/bench-suite/suite-manifest.json` and `.../results.jsonl`
  (`scripts/...sh:314,397-398`). Triple mismatch: subdir (`bench-suite` vs
  `local-spire-pipeline-suite`) and filename (`results.jsonl` vs
  `suite-results.jsonl`).
- Worse, `expected_artifacts` declares the bench-suite manifest/results
  *unconditionally*, but the step supports `skip_bench_suite` (and the shipped
  dry-run config sets it true). A skip-bench smoke run will always report those
  two as missing.

Fix by either (a) deriving expected_artifacts from the actual harness layout and
gating the bench-suite artifacts on `!skip_bench_suite`, or (b) - preferred -
making the harness write topology + nested suite under `artifact_dir` with the
declared names. Add an integration/smoke test that actually runs the lane once
(correctness tier, tiny corpus) and asserts the declared artifacts exist, so
this class of drift is caught.

## Minor / notes

- The default smoke-log name is hardcoded to `phase13e-local-multinode.log`
  (`suite.rs:1166-1170`), perpetuating the "phase13e" naming the task wants
  gone. Cosmetic, but it signals the wrapper-not-replacement posture.
- The lane has zero coverage that a distributed query actually returns; the unit
  test only checks arg expansion. AC1 is about distributed *correctness/recall*
  being measurable; a dry-run + arg-expansion test does not demonstrate that the
  lane builds four instances and a remote-routed scan returns. Per CLAUDE.md
  "always test and measure", at least one real correctness-tier smoke run's
  `smoke.sh` + funnel/pipeline output should be captured in the packet before
  Phase 0 is called done (it need not be a full bench, just proof the lane runs
  end-to-end locally).
- No leak/teardown concern with the harness itself - it traps EXIT and stops all
  four instances (`scripts/...sh:196-202`) and refuses a pre-existing RUN_DIR
  (`:185-188`). That part is fine. Ports are caller-supplied with no collision
  check, but that is acceptable for a local lane.

## AC1 status: NOT met

AC1 ("Phase 0: local multi-node is a first-class suite lane and a single
SuiteConfig builds per-variant `ec_spire` indexes via reloptions - no
hand-rolled harness") fails on two counts: (1) the lane *wraps* the existing
727-line hand-rolled harness rather than replacing it, and (2) it provides no
reloption/storage-format/index-name surface, so a single SuiteConfig cannot
build per-variant `ec_spire` indexes through the lane. The artifact-path
mismatch (#3) additionally means the lane's own evidence tracking is wrong. This
is a good first refactor of the entry point, but Phase 0 is not complete; close
out by absorbing the orchestration into the suite runner (or at minimum exposing
the reloption matrix + fixing artifact paths + landing one real local end-to-end
smoke as evidence).
