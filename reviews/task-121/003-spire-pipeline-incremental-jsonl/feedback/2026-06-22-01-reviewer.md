## Correctness — confirmed clean

- **Truncate-and-rewrite full snapshot, not append.** All five writers
  (`write_funnel_jsonl` 3337, `write_stage_containment_jsonl` 3353,
  `write_leaf_block_rank_jsonl` 3372, `write_target_candidate_rank_jsonl` 3388,
  `write_miss_attribution_jsonl` 3409) build the full buffer from the *entire*
  `rows` slice and call `tokio::fs::write(path, output)`, which truncates the
  file each call. Because the row `Vec`s
  (`spire_pipeline.rs:341-346`) are declared once before the nprobe loop and
  only ever grow (`.push` / `.extend`), every flush re-serializes the complete
  cumulative set. Consequence: each on-disk file is always a complete,
  prefix-consistent JSONL of all records processed so far — **no duplicate
  lines, no partial/interleaved lines, no append-concatenation of stale
  records.**
- **No resume/concat hazard.** A re-run starts with empty `Vec`s and the first
  flush truncates the prior file, so a re-run cannot concatenate onto a stale
  file. (There is no resume mode in this command; the suite re-invokes the
  subprocess fresh.)
- **Flush placement is correct.** The new in-loop flush
  (`spire_pipeline.rs:836-845`) sits inside the inner
  `for (query_index, query) in queries.iter().enumerate()` loop (419), nested in
  `for nprobe in &sweep_values` (350), after the per-query funnel/containment
  rows are appended. So each completed query persists its evidence — exactly the
  recoverability the packet wants. The unchanged final flush
  (`897-905` region, refactored into the same helper at 3294-3324) is now a
  redundant-but-harmless full rewrite of the identical buffer.
- **No double-writer race.** Verified the suite runner only passes
  `--funnel-output` / `--stage-containment-output` paths to the `spire-pipeline`
  subprocess (`suite.rs:3344-3348`); it does not write these JSONL files itself.
  `spire_pipeline.rs` is the sole writer per path.
- **Borrow fix is right.** `args.log_output` was switched to `.as_ref()`
  (`spire_pipeline.rs:900`) and `tokio::fs::write(path, ...)` updated to borrow,
  which is required so `args` is no longer partially moved and can be borrowed by
  `flush_pipeline_jsonl_outputs(&args, ...)` both inside and after the loop.
  Compiles clean (build log shows only the pre-existing
  `LoadedDistributedPlacementConfig.path` dead-code warning).

## Non-blocking note — write amplification

Because each flush rewrites the *entire* cumulative buffer and fires once per
query, total bytes written grows ~O(N²) in the number of records across a sweep.
For the bounded q20/n96 smoke this is trivial. For the intended q200 ×
multi-nprobe Stage-1 runs (~800 records), the final queries each rewrite the
full ~800-record buffer, i.e. hundreds of full-file rewrites. This is acceptable
for the recoverability goal and is not a correctness issue, but if it shows up as
real overhead on the long q200 screen, consider either (a) flushing every K
queries instead of every query, or (b) true append (open once with
`OpenOptions::append`, write only the newly-pushed rows, truncate once at
start). Not required for merge.

## Optional follow-up — coverage

The 19 tests are the pre-existing record/serde/SQL tests; none exercise
`flush_pipeline_jsonl_outputs` or assert that an interrupted (partial) run leaves
a valid-JSONL prefix. The live-check artifacts demonstrate well-formed output
empirically, so this is sufficient for this change. A small unit test that calls
a writer twice with a growing slice and asserts the file equals the second
snapshot (no duplication, valid lines) would lock in the invariant cheaply.
Optional, not a merge blocker.
