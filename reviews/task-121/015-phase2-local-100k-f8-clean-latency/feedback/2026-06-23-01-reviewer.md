# Review — Task 121 Phase 2 local 100k clean-latency

**Verdict: needs-evidence — the latency numbers are not decision-grade.** Good
that a real `latency` step (the gap flagged on packet 012) was added; but the
values are implausible and must be re-measured before they enter any Pareto.

## The numbers are 30-50x the Task 120 release baseline

`latency` step, p50 per query, 100k, ec_spire recursive rabitq f8:

| cell | np24 | np32 | np48 | np64 | np96 |
| --- | ---: | ---: | ---: | ---: | ---: |
| b0_tr10_f8 (baseline) | 821.6 ms | 1102.9 | 1767.4 | 2326.1 | 3538.6 |
| b1_tr50_f8 | 1420.0 ms | 1776.2 | 2508.0 | 3129.7 | 4193.1 |

Task 120 packet 011 measured the **same** corpus / AM / scale at **p50 ~26 ms
(np32) and ~66 ms (np96)** on a release build. These are 30-53x higher. A
baseline 100k cell at np24 should be ~20 ms, not 821 ms.

## Cause is NOT a debug build — likely host contention

- `suite-...-manifest.json` records `"build_profile": "release"`, so the installed
  `.so` is release (the CLI being `target/debug/ecaz` only drives SQL and does
  not affect engine timing). So this is not the pg_test-debug-`.so` trap.
- The most probable cause is **measurement under load**: the Intel bench host is
  running many concurrent Task 121 slices/builds (50k b0-b1, 50k f8 supplement,
  100k factorial, multinode) in the same window. A `latency` step taken while the
  box is simultaneously building indexes and running other suites is invalid —
  CPU/IO contention inflates p50 by exactly this kind of factor.
- A measurement-config difference (e.g. an unintended heavy GUC, or
  `cache_state: post_pipeline_warm` inheriting pipeline diagnostic state) is the
  other candidate. Either way, untrusted.

## Required before these latencies are usable

1. **Re-measure on a quiesced host** — no concurrent builds/suites running; one
   measurement at a time.
2. **Sanity-gate against Task 120**: a baseline 100k cell must land in the
   ~20-70 ms p50 band across np24-96, or the run is rejected and investigated.
3. **Commit the precheck** for the latency run (this packet has none) — the
   config-baseline section is mandatory per the Task 121 guardrails; record
   build_profile + that the host was otherwise idle.
4. Only b0_tr10 and b1_tr50 cells are present — the Pareto needs all finalist
   cells (b0/b1/b2/b4 x tr x f) at clean latency, paired with the per-cell
   storage already captured.

## What is fine

The step *type* is right (real `latency` kind, p50/p95/p99, 100 iters,
post-warm), hygiene is clean, and the intent is correct. The problem is purely
that the measured values are not credible and lack build/host provenance.
