## Concern to resolve before the Phase-4 verdict: the win region may miss the operating point

Every pruning win here lands at **np48–96**, and at np48+ recall is *already
saturated* (1.0000) for this b4/tr50 candidate — at 50k recall is ~0.98 by np8,
~0.99 by np16, 1.0 by np48. The whole point of the routing fix (b4) is that you
can **operate at low nprobe** because routing no longer drops truth. So the
shipped operating point is np8–16 — and there sampled pruning is **neutral to
slightly worse** (019: np8 68→73 ms; 022 standalone: flat at 48, worse at 64).

So as it stands, the Phase-3 scan lever speeds up exactly the high-nprobe regime
the routing fix lets you *avoid*, and does nothing for the regime you'd actually
ship. That's a real Pareto finding, and it needs to be confronted head-on in
Phase 4: **does block pruning help the b4 config at its recall/latency operating
point, or only in a regime that's moot once routing is fixed?** If the latter,
the honest verdict is "pruning doesn't move the shipped point" — which is a
legitimate, decisive result, but it changes the promotion story. Pick the
operating nprobe (the recall/latency knee, ~np16 here) and show pruning's effect
*there*, not just at np96.

## Compute win, not I/O win — clarify the mechanism

Both 019 and 022 note object/read bytes are **unchanged** while candidate and
heap-rerank counts drop. So "block pruning" here is cutting candidate-scoring
*compute*, not block *reads* — the blocks are still read, then filtered. The
task framed Phase 3 block pruning as cutting *scan* cost. Confirm whether the
read-byte path genuinely can't be skipped on this local single-node surface (a
measurement/path limitation) or whether the pruning is structurally
post-read. If reads aren't actually avoided, the storage+I/O cost of the
block-summary index (50k: +203 MiB index, 4265 B/row) buys only a compute trim —
material for the Pareto cost accounting.
