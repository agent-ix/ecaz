# Review: Task 104 packet 007 qjl32 NEON optimization

## Findings

1. **P1 - QJL remainder batches still fall back to scalar on Apple silicon, so the packet does not satisfy the claimed `scalar_candidates=0` kernel-on coverage.**

   The new NEON implementation only accelerates full 32-candidate blocks through `score_turboquant_qjl_block32`; the remainder path still calls `score_turboquant_qjl_octet8_avx2` and breaks to scalar when that returns `None` on aarch64. See `src/am/common/candidate_batch/mod.rs:660-728` and `src/quant/qjl32/mod.rs:143-150`. There is no NEON octet/remainder entry point analogous to the AVX2 one, even though `src/quant/qjl32/neon.rs:106-231` already has an internal octet implementation.

   The packet evidence shows this is not theoretical:

   - `reviews/task-104/007-qjl32-neon-optimization/artifacts/latency-hnsw-qjl1024-kernel-on.log:8-15` records only 2,944/3,040 NEON candidates but 138,422/224,574 scalar candidates in the same kernel-on HNSW step.
   - `reviews/task-104/007-qjl32-neon-optimization/artifacts/latency-ivf-turboquant_qjl-batch-on-qjl1024.log:8-15` records 4,620/4,266 scalar candidates from sub-32 IVF remainder flushes.
   - `reviews/task-104/007-qjl32-neon-optimization/artifacts/latency-spire-qjl1024-kernel-on.log:8-15` records 21,190/43,065 scalar candidates in the SPIRE kernel-on step.

   That contradicts packet 008's acceptance summary that kernel-on cells have `isa=neon / scalar_candidates=0`, and it leaves HNSW QJL effectively one-off dominated despite the full-block kernel speedup. Please either add and route a NEON octet/remainder helper for 8-31 candidate tails, or explicitly keep this packet open as a partial optimization with packet 008 revised so it does not claim AC3 closure.
