# Review: SPIRE Registration SQL Renderer

Review target: commit `7bba11ff61fdb7e2999c5b204acb7dc20f1dac9e`
(`crates/ecaz-cli/src/commands/corpus/render_spire_registrations.rs`),
read together with packets 961 and 963.

## Findings

### P1 — Renderer rejects the real identity JSON: `active_epoch` is an unknown field

`RemoteEndpointIdentity` is declared `#[serde(deny_unknown_fields)]` and has no
`active_epoch` field. But the identity query this renderer is designed to
consume — `distributed_remote_identity_query_sql` in
`crates/ecaz-cli/src/commands/corpus/load.rs:994` — emits exactly that key:

```
'active_epoch', a.active_epoch,
'last_served_epoch', a.active_epoch,
'min_retained_epoch', a.active_epoch,
```

So when `register.sh` captures the live remote identity JSON and feeds it to
`ecaz corpus render-spire-registrations`, `serde_json::from_str` will fail with
`unknown field 'active_epoch'`, and the whole AWS register step (packet 963)
aborts before producing any coordinator SQL.

This is masked by the unit test: `identity_json()` in the renderer's test module
hand-writes a fixture that omits `active_epoch`, so `renders_descriptor_
registration_sql_from_plan_and_identity` is green against a payload the
production query never actually produces. The test fixture and the generator
have diverged.

Fix options (coder's call):
- add `active_epoch: i64` (ignored) to the struct, or
- drop `deny_unknown_fields` here, or
- remove `active_epoch` from `distributed_remote_identity_query_sql` since all
  three epoch fields are currently set from `a.active_epoch` anyway.

Whichever you pick, please replace the hand-written `identity_json()` fixture
with the actual output of `distributed_remote_identity_query_sql` (or assert the
two are byte-identical) so this class of drift can't recur. A round-trip test
"generator output parses in the renderer" would have caught this.

### P2 — `sql_string_literal` assumes `standard_conforming_strings = on`

`sql_string_literal` escapes only `'` → `''`. That is correct on PG defaults
(`standard_conforming_strings = on` since 9.1), and the inputs here
(index names, secret names, hex, extension version) are low-risk. Flagging only
so it's a conscious assumption: if any of these values can ever contain a
backslash and the coordinator session has conforming strings off, the literal
would mis-parse. The validated hex and regclass inputs make this academic today;
no change required unless you want a defensive `E''`-aware path.

## What looks good

- Fail-closed validation is thorough: empty/duplicate remotes, regclass mismatch
  vs plan, both `endpoint_status` and `tuple_transport_status` must be `ready`,
  nonempty even-length hex validated through `hex::decode`, positive epochs.
- All interpolated string values go through `sql_string_literal`; numeric
  `node_id`/epochs are typed integers. No SQL-injection surface in the generated
  registration statements.
- `\set ON_ERROR_STOP on` header plus regclass-cast-on-literal is the right shape
  for an operator-applied SQL file.

Holding this packet open pending the P1 fix.
