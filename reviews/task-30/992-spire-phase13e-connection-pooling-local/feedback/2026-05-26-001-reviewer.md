# Review: SPIRE Phase 13e Connection Pooling (local gate)

Reviewed as code (commit `402b92943`), not just logs.

## Pooling implementation matches the 974 gate

`SpireRemotePooledConnectionKey` (dispatch.rs) keys the pool by exactly the
fields the 974 acceptance requires: `descriptor_generation`,
`conninfo_secret_name`, `remote_index_identity`, `tls_mode`, `user`,
`statement_timeout_ms`. Because identity/generation are *in the key*, a
descriptor or endpoint-identity change yields a different key — stale-identity
reuse is prevented by construction, not just by a check. There is a bounded
`pool_limit()`, a `Drop` impl for `SpireRemotePooledConnection` (session
cleanup), and failure-category recording on the dispatch path.

## Empirical: no regression from pooling

`local-gates-after-pooling/phase13e-local-gates-summary.tsv`: **all 22 gates
pass** with pooling enabled — 5 core (static placement, multicluster customscan
read, insert-read helper + trigger, transport-overlap) and the full 17-case
stage-e fault matrix (epoch/version skew, fingerprint mismatch, network
partition, connection reset, cancel, local/remote timeout, remote OOM, remote
backend termination, CIC + drop/reindex lifecycle). So introducing pooling did
not regress the read or fault behavior.

## What I verified vs did not (being precise)

- Verified by code: pool keying, bounded limit, Drop cleanup, identity-in-key
  (no stale reuse by construction), and the 22-gate pass.
- NOT independently verified: the quantitative "pooled reuse reduces follow-up
  socket opens" claim — the gate summary shows pass/fail, not the socket-open
  delta. Please surface a with-vs-without-pooling `socket_open_sum` /
  `connect_count` comparison in the packet so the latency benefit is evidenced,
  not asserted. The 974 acceptance is "pooled reads reduce connect/TLS count and
  improve latency without stale-identity reuse" — the reduction number is the
  missing half.
- NOT line-audited: every invalidation branch (auth/TLS failure, schema drift,
  disconnect mid-use). The key design makes identity drift safe; please confirm
  a mid-use disconnect/auth failure drops the pooled entry rather than returning
  it to the pool.
