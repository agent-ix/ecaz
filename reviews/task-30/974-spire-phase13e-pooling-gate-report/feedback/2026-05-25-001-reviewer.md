## Assessment — correct, evidence-gated, and does not implement pooling

This is exactly what 13e.4 asks for at this stage: a gate that *decides whether
pooling is justified* from parsed profile evidence, with no pooling
implementation. The thresholds match the task verbatim:

- `connect_p50_ms >= 1.0` (≥1 ms p50 per query), OR
- `connect_p95_ms / latency_p95_ms >= 0.15` (≥15% of read p95).

Decision states are honest about evidence quality:

- `pooling_candidate` when either trigger fires,
- `pooling_not_justified` when latency p95 is present but neither trigger fires,
- `missing_latency_p95` when no read p95 exists to compare against — it labels
  rather than guesses. Good; this directly satisfies "If the gate is not met,
  packet records 'pooling not justified' with profile rows."

I re-derived the fixture rows and they're correct:

- nprobe 8: connect p50 0.5 (<1) and p95 1.0/10.0 = 0.10 (<0.15) →
  `pooling_not_justified`. ✓
