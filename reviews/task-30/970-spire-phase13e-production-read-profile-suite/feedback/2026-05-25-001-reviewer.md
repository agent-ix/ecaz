# Review: Production Read Profile Suite Capture

Review target: commit `bb0841437...` (`bench/spire_pipeline.rs` +250,
`bench/suite.rs` +319).

## Assessment

No blocking findings, and this packet does the right thing on the workflow rule
that matters most here: the production read profile is captured by adding a
first-class `kind: spire-pipeline` step to `ecaz bench suite` plus
`--include-production-read-profile` on `ecaz bench spire-pipeline` — not by a
one-off shell sweeper. That is exactly the FR-038 / "`ecaz bench suite` only"
expectation, and landing the runner extension as its own commit before using it
in configs (973) is the correct sequencing.

## Strengths

- The profile aggregation covers the fields 13e.3 asks for at the correctness
  tier: selected/remote PID counts, dispatch/socket counts, connect/candidate/
  heap/merge/total p50/p95, candidate/heap query counts, payload bytes,
  timeout/cancel counts, degraded skip count, returned candidate count.
- 18 focused `spire_pipeline` tests plus a `bench suite run --dry-run` that
  proves the step expands to `bench spire-pipeline --include-production-read-
  profile`. Unlike the extension-SQL packets, this CLI-side work has real unit
  coverage — good.

## Notes

- The dry-run proves *expansion*; there is no executed profile run here (correct
  — that's deferred to the AWS tiers). When those run, ensure the profile p50/p95
  columns are populated from real remotes, not zero-filled defaults, before any
  pooling decision (13e.4) cites them.
- Confirm `--include-production-read-profile` sources its counters from the same
  async production executor as the CustomScan path (packet 972's timeline SQL),
  not a diagnostic probe — the task is explicit that libpq diagnostic helpers
  are not performance evidence.
