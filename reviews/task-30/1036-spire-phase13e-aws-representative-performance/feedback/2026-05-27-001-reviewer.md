# Review: SPIRE Phase 13e AWS Representative Performance — real run surfaced a real format bug

This is the first *real* representative AWS run (after the 1000–1035 scaffolding
that had no actual run, per my 1009 finding). It did not produce the
representative measurement — but it earned something more valuable: a genuine
SPIRE format bug that the synthetic 10k correctness corpus never exposed.
Code-verified, not log-trusted.

## What happened (real run, real data)

The run fetched qdrant-dbpedia and prepared the **real `ec_real_100k` corpus**
(100,000 rows + 1,000 queries, sha256-checksummed — not sample/dry-run data),
then failed at index build:

```
ERROR: ec_spire populated ambuild failed:
       ec_spire object tuple payload 10832 exceeds page size 8192
  (run-representative-performance-pass-rerun-after-prepare-path-fix.log)
```

## The bug (verified in src)

`src/am/ec_spire/page.rs:577-583` (`try_append_object_tuple_to_block`) and
`:627-635` (`append_object_tuple_to_new_block`) enforce that a SPIRE **object
tuple payload must fit within a single 8 KB page**, and hard-error otherwise.
The real DBpedia corpus produced a 10,832-byte object — over the ~8 KB usable
page — so `ambuild` aborts.

Notably, SPIRE *does* have a multi-page spill mechanism — `ManifestBlobChainMeta`
/ `ManifestBlobChainSegment` + `max_manifest_blob_chain_segment_payload_bytes`
(`page.rs:651-674`) — **but only for manifest blobs**. The failing path is an
**object** tuple, which has no equivalent chain/spill. So the gap is concrete:
oversized objects can't span pages the way oversized manifests can.

This is exactly why the representative tier matters: real 1536-dim DBpedia data
produces objects the synthetic 10k corpus didn't, exposing a page-size format
limit that local correctness never hit.

## Required before the next representative AWS attempt

1. **Fix the oversized-object path locally.** Either route oversized object
   tuples through a chain/segment spill (as manifest blobs already do) or
   establish/enforce a documented max object size with a real corpus that fits.
   Prove the `ec_real_100k` build succeeds on the local 4-PG harness (989-style)
   before re-running on AWS.
2. **This is an on-disk-format change** — per CLAUDE.md memory rules, a format
   change means existing SPIRE indexes/snapshots must be rebuilt, not reused.
   Call that out in the fix's ADR/notes.
