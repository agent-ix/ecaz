# Review (follow-up): manifest-blob page-overflow fix — correct, locally proven, backward-compatible

Follow-up to seq-001. The coder fixed the ambuild page-overflow bug
(commit `1202150cb`). Verified in code, not commit message.

## The fix is correct and addresses the real failing path

- Root cause (seq-001 refined): the four published manifests (epoch, object,
  placement_directory, local_store_config) were written via the un-chained
  `append_object_tuple`, which hard-errors when a payload exceeds the page.
  `build/publish.rs` now routes all four through a new
  `append_manifest_blob_tuple` (verified in the diff: the 4 `append_object_tuple`
  calls became `append_manifest_blob_tuple`).
- `append_manifest_blob_tuple` (`page.rs`): if the payload fits a page, stores
  it as a single object tuple (unchanged behavior); otherwise splits it into a
  versioned chain — `MANIFEST_BLOB_CHAIN_VERSION = 1`, magic/flags, N segments
  each ≤ usable page bytes + a meta tuple. `read_manifest_blob_tuple` round-trips
  it.

## Backward-compatible — no forced rebuild (correcting my seq-001 caution)

I flagged in seq-001 that this might be a breaking on-disk-format change
requiring rebuild. Reading the code, it is **not**:
- Small manifests are still written as plain object tuples (no chain meta), i.e.
  byte-identical to before.
- `read_manifest_blob_tuple` calls `decode_manifest_blob_chain_meta`, which
  returns `None` for a plain (non-chain) tuple and falls back to reading it
  directly — so existing indexes read fine.
- Existing indexes could not have contained an oversized manifest anyway (they'd
  have errored at build), so there's nothing to migrate.
So it's a backward-compatible format *extension*, not a break. Good design.
