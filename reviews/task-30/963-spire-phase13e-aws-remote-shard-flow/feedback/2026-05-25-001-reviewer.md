# Review: AWS Remote Shard Load Flow

Review target: commit `300ca60fef6bac22754aa227154eb71a14cda721`
(`scripts/spire-aws/{load,register}.sh`, `register-remotes.sql`,
`infra/spire-aws/Makefile`).

## Findings

### P1 — Register flow inherits the renderer `active_epoch` bug (see packet 962)

`register.sh` captures each remote's identity JSON and then calls
`ecaz corpus render-spire-registrations`. Because the live identity query emits
`active_epoch` and the renderer struct is `deny_unknown_fields` without that
field, the render step will fail and no coordinator registration SQL is
produced. This script cannot complete end-to-end until packet 962's P1 is fixed.
Cross-ref: `reviews/task-30/962-.../feedback/2026-05-25-001-reviewer.md`.

### P2 — Identity capture mixes psql stderr into the JSON file

`register.sh` captures the remote identity result with:

```
ecaz dev sql --host "$REMOTE_HOST" ... --sql "$IDENTITY_SQL" \
  --log-output "$IDENTITY_DIR/node-${NODE_ID}-identity.json"
```

`dev sql` without `--raw` runs psql `-A -t -F '\t'`, so stdout is bare
tuples-only output — good, the JSON value is unframed. But `run_logged`
(`crates/ecaz-cli/src/commands/dev/sql.rs:178`) writes **stdout concatenated
with stderr** to the file. Any NOTICE/WARNING the remote emits during the
identity query lands in the same file, after the JSON, and the renderer's strict
`serde_json::from_str(trimmed)` will then fail.

The identity functions may be quiet today, but capturing a machine-parsed result
through a combined-stream "log" flag is fragile. Suggest either a result-only
capture path (stdout only) or, at minimum, set `client_min_messages = warning`/
`error` in `$IDENTITY_SQL` so stray notices can't corrupt the payload. Please
also confirm psql writes a trailing newline only (no extra blank from `-t`),
since the renderer trims but does not strip embedded lines.

## Quoting review (coder's explicit ask) — looks correct

- `mapfile -t remote_load_args < <(jq -r '.remote_load_args[]' ...)` then
  `"${remote_load_args[@]}"` is the right pattern; args with spaces survive.
- `set -euo pipefail` is present in both scripts, and the `exit 2` calls live
  inside `jq -c | while read` subshells — with `pipefail` the subshell's exit
  propagates and aborts the parent. Correct.
- `--argjson node_id "$NODE_ID"` is safe given `node_id` is numeric from the
  plan.

One minor: `COORD_INDEX=$(jq -r '.coordinator_index_name' "$PLAN_FILE")` is
interpolated into `--sql "...'${COORD_INDEX}'::regclass..."` unparameterized.
Low risk since the value is generator-produced, but it's the one spot in these
scripts where a SQL value is built by shell string concatenation rather than the
renderer. Fine to leave; noting for awareness.
