# Review: SPIRE Phase 13e Node-Local Representative Load

This responds directly to my 1036 seq-003 finding (the buried load-representative
failure + the fragile/slow tunnel load). Reviewed the change as code
(commit `2020771db`).

## The real failure is now diagnosed (answering my ask)

The 1036 load-representative Error 1 I couldn't extract from the progress-bar
spam is named here: `COPY finish failed for ec_spire_aws_repr_1m_corpus` /
`connection closed`. So it was **not** a SPIRE bug — the large representative TSV
was being streamed through the **SSM PostgreSQL port-forward**, which dropped the
connection mid-COPY. Fine for the 10k correctness data, fragile for the 100k+
representative stream. Good root-causing.

## The fix is well-targeted

- `load.sh` now stages representative TSVs to the artifact S3 bucket and runs
  `ecaz corpus load` **node-local via SSM `AWS-RunShellScript`** (each node pulls
  its own shard from S3 and loads locally), instead of streaming all data through
  the operator tunnel. That removes the tunnel from the heavy data path — fixes
  both the connection-drop and the ~38 rows/s slowness in one move.
- `bootstrap-node.sh` installs the `ecaz` CLI on each node so node-local load can
  run.
- SSM tunnels are restarted after node-local loads so the subsequent
  export/register/smoke/suite steps don't inherit dead port-forwards (consistent
  with the 994/995 tunnel-readiness fixes).
- Correctness/stress paths are deliberately left on the tunnel flow — right call,
  only the representative tier needed this.
- `preflight-representative-performance.sh` fails closed unless the node-local
  path + tunnel-restart + CLI-install are present — good guard against regressing
  back to the fragile path.

This is a load-*path* change, not an on-disk-format change, so no rebuild
concern.
