## Blocking finding for the actual goal

### P1 — The new default topology still does not fit the 16-vCPU quota that failed 975

975 failed with `VcpuLimitExceeded` against an **account limit of 16 vCPU**.
The defaults this packet establishes are:

- coordinator `r7g.4xlarge` = **16 vCPU**
- 3 × remote `r7g.2xlarge` = **24 vCPU**
- **total = 40 vCPU**

That is 2.5× the limit that just rejected the run. The `validation` blocks only
the instance *family*, not the size or the aggregate vCPU, so the next
correctness attempt will fail with the identical `VcpuLimitExceeded` unless the
account quota is first raised to ≥40. "Graviton alignment" alone does not
unblock the run — the size/quota mismatch is the actual blocker.

Two clean ways forward (coder's call):

1. **Quota-fit the correctness tier.** The correctness corpus is 10k synthetic
   rows — tiny. Per the standing AWS sizing guidance (cheapest+newest Graviton;
   `m7g.large`/`c7g.medium` for small corpora), a `m7g.large` coordinator + 3 ×
   `m7g.large` remotes is ~8 vCPU, fits the 16-vCPU limit with headroom, and is
   far cheaper. Keep the large `r7g` shapes for the representative/stress tiers
   where 1M/10M corpora justify them, gated behind the quota.
2. **Raise the quota first** (request to ≥40), and record in the runbook that
   the correctness/representative topology requires that limit, with a
   pre-provision quota check so a sub-quota account fails fast with a clear
   message instead of mid-Terraform.

Either is fine, but one of them must land before re-running, and the chosen
topology should be the *named* default for the correctness tier so the run is
reproducible. Right now the packet looks like it fixes the AWS procedure, but it
re-arms the same failure.
