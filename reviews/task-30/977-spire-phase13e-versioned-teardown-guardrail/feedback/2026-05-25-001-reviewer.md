# Review: SPIRE Phase 13e Versioned Teardown Guardrail

Review target: commit `48fd61fbe13684359cafbf64229b789c6d6c6aa8`.

## Assessment

`force_destroy = true` on `aws_s3_bucket.artifacts` is the correct minimal fix
for the `BucketNotEmpty` teardown failure I flagged on packet 975 (P0-1).
Terraform will now empty object versions + delete markers before `DeleteBucket`,
so a failed provisioning/install run no longer strands a billable versioned
bucket. `fmt`/`validate` pass. Good, direct response to the finding.

## Findings (non-blocking but please act)

### N1 — The bucket already leaked by 975 is not retroactively cleaned

`force_destroy` only applies to *future* destroys of a Terraform-managed
bucket. The bucket from the failed 975 run
(`ecaz-spire-aws-20260525201045387900000003`) was already orphaned and is not
under this state anymore. Please manually confirm it's gone
(`aws s3api list-buckets`, then `delete-objects` over `list-object-versions` if
needed) so it isn't billing in the background. This packet prevents recurrence;
it does not undo the existing leak.

### N2 — The other 975 teardown residue (Secrets Manager) is not addressed here

975 also failed to provision because `ecaz-spire-aws-remote-1` was "already
scheduled for deletion" — a Secrets Manager secret left in pending-deletion from
a prior run blocks recreation by the same name. `force_destroy` on the bucket
doesn't touch this. Before the next attempt, either
`delete-secret --force-delete-without-recovery` the stuck secret(s), or suffix
the secret name with a run/generation id so a pending-deletion secret never
collides with a new provision. Otherwise re-provisioning will fail again even
with the quota fixed.

## Scope (agreed)

Correctly scoped — this does not claim AWS correctness, just removes one concrete
teardown blocker found by 975. No blocking findings on the change itself.
Deferring formal accept to an outside reviewer.
