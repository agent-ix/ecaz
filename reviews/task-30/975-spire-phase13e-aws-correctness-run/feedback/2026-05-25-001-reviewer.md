# Review: SPIRE Phase 13e AWS Correctness Run

Review target: local artifacts under
`reviews/task-30/975-spire-phase13e-aws-correctness-run/artifacts/` (the whole
packet is currently **untracked** — see P0-4).

## Outcome: the AWS correctness run did NOT succeed

Both attempts ended with `COMMAND_EXIT_CODE="2"` at the provision step; no
benchmark tier ran and **none of the required 13e.3 correctness profile fields
were captured** (selected PIDs, dispatch count, connect/TLS time, candidate
time, heap time, payload bytes, merge time, timeout/cancel counts). So this is a
failed-provisioning record, not a correctness proof. AWS-scale SPIRE remains
unproven.

Root causes from `aws-correctness-run.log`:

- **`VcpuLimitExceeded`** (line ~1244/1252): the topology requested more vCPU
  than the account limit of 16 for that instance bucket. The 1-coordinator +
  3-remote topology doesn't fit a 16-vCPU quota at the chosen instance size.
- **Secrets Manager collision** (line ~1236): `ecaz-spire-aws-remote-1` "is
  already scheduled for deletion" — a leftover secret from a prior run blocked
  recreation. State from an earlier incomplete teardown is colliding with new
  provisions.

## Findings

### P0-1 — Possible leaked AWS resources (cost + the "never leave running" rule)

`aws-correctness-retry-quota-fit.log` ends with teardown **failing**:

```
Error: deleting S3 Bucket (ecaz-spire-aws-20260525201045387900000003):
... StatusCode: 409 ... BucketNotEmpty: The bucket you tried to delete is not
empty. You must delete all versions in the bucket.
make: *** [Makefile:119: teardown] Error 1
```

That bucket (and likely its versioned objects) may still exist and is billable.
Please confirm via `aws s3api list-buckets` / `list-object-versions` that it is
gone, and the Secrets Manager secret too (`force-delete-without-recovery` if it
must be reused immediately). The teardown path needs to empty versioned buckets
(`aws s3api delete-objects` over `list-object-versions`, or a force-destroy
lifecycle) before `DeleteBucket`, or these leaks recur on every failed run.

### P0-2 — Private TLS keys must not be in the packet

`artifacts/tls/ca.key` and `artifacts/tls/i-0d1bcedf2ee38ff93/server.key` are
**private keys**. Even for a throwaway, destroyed instance, private keys must
never be committed. Remove them from the packet and add a `tls/*.key` ignore
rule before anything here is committed. Keep only what review needs (the run
logs, topology, manifest) — not key material.

### P0-3 — Compiled binaries don't belong in the review packet

`ecaz-latest.tar.gz`, `ecaz-aws-tarball/lib/ecaz.so`,
`ecaz-pg18-package/.../ecaz.so`, and the per-instance tarballs are build
outputs. They bloat the repo and aren't review evidence. Record the build SHA /
`ecaz.control` version in the manifest instead and drop the binaries.

### P0-4 — Packet is incomplete and untracked

`git status` shows the entire `975-...` directory as untracked (`??`), and there
is **no `request.md` and no `artifacts/manifest.md`**. Per the workflow this
packet is invisible to other agents and is not yet a reviewable measurement
packet. A measurement packet must have `manifest.md` (head SHA, command,
timestamp, instance types/quota, whether it used isolated one-index-per-table,
the cited result lines) and a `request.md` summarizing the outcome. Right now
the "result" is a provisioning failure, which is fine to record — but record it
explicitly rather than leaving raw logs.

## What to fix before re-running

1. Fit the topology to the 16-vCPU quota (smaller instances, or request a quota
   bump) — and prefer the cheapest+newest Graviton sizing per the standing AWS
   sizing guidance.
2. Make teardown idempotent and version-aware so a failed run cleans up fully
   (no stuck secrets, no non-empty buckets) before the next attempt.
3. Reuse the existing corpus/index via snapshot rather than rebuilding on each
   attempt; snapshot before any destroy and verify the snapshot covers the
   volume.
4. Drive the actual correctness capture through `ecaz bench suite` (the 973 tier
   configs), and confirm the profile fields land.

This is a useful failure record, but it is not AWS correctness evidence and is
not yet a committed/complete packet. No formal accept; leaving open. Flagging
P0-1 (cost/leak) and P0-2 (private keys) as the urgent items.
