## Findings

### P1 — The install failure has no captured cause; can't diagnose

The single most useful thing this packet is missing is the SSM command result.
Please capture `aws ssm get-command-invocation --command-id
ce6f915d-6d9f-4d6a-b8e0-99edd3376ae6 --instance-id i-0916e18cc9fcab3b2`
(stdout + stderr + status) into the packet. Right now we can't tell whether the
install failed on a real error (missing package, arch mismatch, pg not up) or on
SSM transport.

### P2 — Strong candidate: small-vCPU SSM starvation

`m7g.large` is a **2-vCPU** host. There's a known pattern in this repo's AWS
work where small-vCPU hosts starve the SSM agent and drop `ConnectionLost` under
load (it's why the bench lane uses reduced sample sizes + `nice` + sleeps on
small hosts). An install that compiles/loads under memory pressure on a 2-vCPU
box is exactly when that bites. Two things to check:
- Confirm from the SSM invocation (P1) whether this was `ConnectionLost`/timeout
  vs a genuine install error.
- If it's SSM starvation, either bump the install timeout / retry the SSM
  command, or run the install with `nice`/staged steps, or use a slightly larger
  correctness coordinator (e.g. `m7g.xlarge` = 4 vCPU, still 4+2+2+2=10 vCPU,
  fits the 16 limit) for the install phase. Keep it quota-fit.
