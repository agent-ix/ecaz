# Review (follow-up 3): Read fails on AWS — `custom_scan_tuple_delivery` gap, and the run is churning

Correcting/extending seq-003. seq-003 reported "distributed placement works on
AWS" based on the publish succeeding. That's true but incomplete: the **read
immediately after publish failed**, and the run has since been re-cycling the
load/placement phase rather than progressing.

## The actual blocker (not a build failure)

`coordinator-placement-snapshot-after-remote-publish.log` contains:

```
ERROR:  ec_spire local heap tuple delivery requires custom_scan_tuple_delivery
        before consuming 100 remote placement(s); first remote pid 2 is on node_id 2
```

So: placement publishes fine (`1|100|3`), but when the coordinator tries to
serve a read across the 100 remote placements, the read path errors out because
`custom_scan_tuple_delivery` is not enabled in this AWS path. The distributed
read never produces results — no `EcSpireDistributedScan` EXPLAIN, no recall, no
profile fields.

This is a real **local-fixture-vs-AWS gap**: the local 969 PG18 fixture proves
the same read path green, so either (a) the fixture sets
`custom_scan_tuple_delivery` (a GUC / customscan delivery mode) that the AWS
runbook/`bench.sh` path does not, or (b) the AWS read is being driven by a
different entrypoint (e.g. ad hoc SSM `psql`) that doesn't go through the
CustomScan delivery setup that `ecaz bench suite` / the fixture uses. Either way
it's a config/wiring gap in the production AWS read path, not the extension
build.

## The run is churning, not progressing

Timeline (from log mtimes): install success 16:24 → publish `1|100|3` 18:59:02 →
**coordinator index reset (`DROP INDEX`) 18:59:50 → coordinator reload 19:00 →
remote shards dropped+reloaded 19:00–19:02** (3 load + 3 drop cycles per the log
set). So after the read error, the run tore down the coordinator index and
remote shards and is rebuilding — i.e. retrying the load/placement from scratch
rather than fixing the read-path config. As of the latest sync (19:02) it's
mid-reload of node 4, still with no read output.
