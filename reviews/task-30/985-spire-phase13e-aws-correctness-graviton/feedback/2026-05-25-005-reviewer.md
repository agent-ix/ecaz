# Review (follow-up 4): STOP AWS churn — the production read path is not proven locally

## The gate is being applied wrong

The gate for spending AWS time/money is **not** "did we fix the last bug." It is
"are we certain the full production path works end-to-end locally, so we don't
churn in AWS." That gate is **not met**, and the AWS run (985) is premature.

## Evidence that local never proved the AWS read path

The `custom_scan_tuple_delivery` error that blocks the AWS read
(`coordinator-placement-snapshot-after-remote-publish.log`, seq-004) is **not a
new AWS bug** — it is a path the local fixture never exercised:

- `custom_scan_tuple_delivery` appears **nowhere** in
  `scripts/run_spire_phase13e_static_remote_placement_pg18.sh` (the 969 local
  proof). It only appears in `src/` (tests + vocab + runtime_state).
- The local fixture reads via **raw `psql` `EXPLAIN`/`SELECT` with
  `enable_seqscan=off enable_indexscan=off`** (lines ~417–432), i.e. it forces
  the CustomScan through planner GUCs in an interactive session.
- The AWS path drives the read differently (and is supposed to go through
  `ecaz bench suite`), which is where the `custom_scan_tuple_delivery`
  requirement surfaces.

So the local 969 "read passed" and the AWS "read fails" are **two different read
entrypoints**. Local proved *a* read, not *the production* read. That's why AWS
immediately hit an error local never saw — and it's why the run is now churning
(reset index + drop/reload shards, 3 cycles) instead of converging.

## Required before any further AWS spend

1. **Reproduce the failure locally.** Extend the 969 fixture (or add a sibling)
   to drive the read through the **exact same production entrypoint AWS uses**
   — `ecaz bench suite` with the spire-pipeline step — on the local
   1-coordinator+3-remote topology. It should hit the same
   `custom_scan_tuple_delivery` error locally. If it doesn't, the local and AWS
   paths still differ and that difference must be found first.
2. **Fix it locally.** Set/enable `custom_scan_tuple_delivery` in the production
   read path (not just the test harness), and prove the distributed read green
   locally through `ecaz bench suite`: `EcSpireDistributedScan` in EXPLAIN,
   recall vs baseline, strict fail-closed + degraded partial rows, and the
   profile fields populated.
3. **Only then return to AWS.** With the production read proven locally through
   the suite, the AWS run becomes what it should be — network/perf/deployment
   evidence — instead of debugging logic on rented hardware.

## Process note

Each AWS retry is also rebuilding the corpus/index (coordinator reset + remote
drop/reload), which burns time/money and conflicts with the standing
"reuse + snapshot, don't recreate corpus" rule. Debugging a read-config error by
re-provisioning data on AWS is the most expensive possible way to find a bug
that a local suite run would surface in minutes.

**Recommendation: pause the AWS correctness run; close the local↔production read
path gap and get a green `ecaz bench suite` read locally first.**
