# Task 82 packet 001 — AWS 1M recall attribution

## Decision

**Accept as decisive 1M recall diagnosis.** The bounded attribution
result answers the question the packets 003/005/006 reviews kept
circling: at AWS 1M with cap=1152, **96% of recall misses are
selected-leaf block pruning failures**, not routing failures. The
mechanism the missed truth rows need is block selection inside selected
leaves, not wider routing.

This is the cleanest data we've had on the 1M recall problem since the
SPIRE work started, and it cleanly justifies the Task 83 successor.

## The headline result

| stage | missed truth rows | share |
| --- | ---: | ---: |
| routing_miss | 3 | **3.6%** |
| selected_leaf_block_pruning_or_candidate_cap | 81 | **96.4%** |
| assignment_missing | 0 | 0% |
| candidate_or_rerank_cap | 0 | 0% |

84 misses over 5,000 q500 truth rows = 0.9832 recall, identical to the
three prior matched-candidate AWS rows (Task 80 packet 001, Task 81
packets 003 + 005). The attribution split confirms what those packets'
identical-candidate-count evidence implied: the leaves containing the
missed winners ARE being routed to; the blocks containing those winners
are NOT being selected from those leaves at cap=1152.

## Why this is the decisive evidence

Prior reviews (especially Task 81 packets 003 + 005) argued from
indirect evidence that the 1M recall problem must be summary
discrimination at 1M leaf density, because cands/query were identical
across routing breadth changes. Packet 006 attempted to confirm this
with rank attribution but couldn't reuse the q500 truth cache against a
sliced query set, and the uncached q500 attempt streamed full corpus.

Packet 001 solves it by inverting the lookup: instead of finding the
rank of each missed winner, it asks per-truth-row "which leaf, which
block, did the selector reach?" with `target_local_sequences` passed in
explicitly. That's a bounded scan over only the 5,000 truth rows, not
a full block-rank sweep — exactly the tooling extension I named in the
packet 006 review.

The 11-minute backend cancellation of the full block-rank approach is
honestly retained as negative evidence. Good provenance.

## Non-blocking notes

1. **Latency reported is higher than packet 003's** (281.345ms vs
   265.911ms p50) because the bounded attribution adds the target
   snapshot lookup as a step. That's expected per-query overhead for
   diagnostic instrumentation, not a regression. Worth recording
   explicitly in the next packet's manifest if any latency comparison
   is made against packet 003.
2. **The 3 routing misses are worth keeping in mind** — they're a hard
   floor on what selected-leaf containment can recover. Even perfect
   block selection inside selected leaves can only get recall to
   (5000-3)/5000 = **0.9994** at this geometry. To exceed that, you
   need routing/top-graph changes that the Task 81 evidence said
   explode candidates. So Task 83's ceiling is ~0.9994 at the current
   geometry.
3. **The miss-attribution JSONL emits null fields for hit rows** —
   that's a lot of disk for 4,916 rows where most fields are null.
   Future packets might filter `hit=false` rows at the CLI layer to
   keep packet artifacts small. Not blocking; the full row stream is
   useful for cross-checking.

## Verdict

Accept. This is the diagnostic the Task 80/81 review stack was
asking for. The attribution result conclusively narrows the design
space:

- Pure routing/top-graph work is **not** the lever (3 of 84 misses).
- Selected-leaf block containment/scoring IS the lever (81 of 84
  misses) — Task 83's scope is correctly named.
- The achievable recall ceiling at the current geometry is ~0.9994 even
  with perfect block selection; if higher recall is required, routing
  has to change too.

Code change is observational only, no behavior change on the scan
hot path, no new unsafe. Cloud cost discipline preserved. Ready for
Task 83 to use this evidence as the design constraint.
