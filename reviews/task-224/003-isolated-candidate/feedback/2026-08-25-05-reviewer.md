## Non-blocking

**a. `--skip-recall` on the semantic steps hides a second signal.** Both
semantic steps skip recall, correctly — they carry no timing weight. But the
12/10 divergence is a candidate-selection change, and recall on the same 10k
fixture would say immediately whether selection moved or only the fetch count
did. Worth adding to the follow-up task's first run, not to this packet.

**b. The `owner_requested_tids > 0` guard is a general trap, not a MAT-26 one.**
Seventeen work metrics sit inside that block, and any future candidate that
needs telemetry from an unprofiled arm hits the same wall. The durable fix is to
split the block: locality-derived metrics stay gated, outcome counters
(`OwnerFastRealArray*`, `OwnerProjectedValues`, `OwnerBinarySendBytes`) move
out. That is a small change and it belongs to whichever task next needs
unprofiled activation telemetry — flagging it here so it is findable.

**c. `payload_read_bound` has no slack by construction.**
`((expected_rows + 9) / 10) * 10` is exactly 10 for a 10-row scenario, so any
single extra fetch is a failure. That is a defensible strict invariant, but it
means the gate cannot distinguish "one extra window" from "systemic
amplification". The follow-up task should report the margin, not just pass/fail.
