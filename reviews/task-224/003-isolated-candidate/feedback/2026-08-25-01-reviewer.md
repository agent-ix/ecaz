## Blockers

### P1-1. The candidate step aborts: the fail-closed zero-column guard fires on the recall child and on the materialization-correctness matrix

`generation_read.rs:2498-2503` fails the whole owner request when
`fast_real_array_send` is set and no projected attribute is `pg_catalog._float4`:

```
"Task 224 fast real[] sender requires at least one projected pg_catalog.real[] column"
```

That guard is right in spirit. The problem is that the GUC is not scoped to the
one SQL shape that has a `real[]` in its targetlist. It is set as a **session**
GUC on three surfaces, and only one of them projects `source`:

1. **The recall child** — `distann_multicluster.rs:7673-7677` appends
   `ec_distann.benchmark_fast_real_array_send=on` to `recall_args`. The recall
   child never receives `--owner-payload-shape` (that flag is added only to
   `latency_args`, `:8177-8181`), so it runs `build_knn_sql`
   (`bench/recall.rs:1254-1259`): `SELECT id FROM dm ORDER BY embedding <#> $1
   LIMIT $2`. **Id-only.**
2. **The materialization-correctness matrix** — the new
   `SET ec_distann.benchmark_fast_real_array_send = on`
   (`distann_multicluster.rs:9144-9150`) runs on the coordinator immediately
   before `run_materialization_correctness`, whose very first statement is
   `SELECT id FROM {corpus} ORDER BY embedding <#> (…) LIMIT 64`
   (`:6170-6175`). **Id-only**, and several later scenario shapes are narrow too.
3. The latency child — `SELECT id, source …` for `vector-bearing`
   (`bench/latency.rs:161`). This is the only one that satisfies the guard.

The projection mask follows the targetlist exactly, so an id-only query really
does reach the owner with one non-`_float4` attnum. **This is confirmed by
packet 002's own artifacts**, not inferred — `owner_projected_values` scales
precisely with targetlist width across the four arms, all on the same 1357
materialized rows:

| arm | targetlist | value | columns implied |
| --- | --- | --- | --- |
| id-only | `id` | 1357 | 1 |
| narrow-scalar | `id, source_id` | 2714 | 2 |
| vector-bearing | `id, source` | 2714 | 2 |

(`reviews/task-224/002-locality-attribution/artifacts/run/*/distann-multinode-summary.log`.)

Consequence: `mat26-candidate-100k` raises `DistannExpandError::BadInput` during
its **recall** step — which runs before latency in the arm loop
(`:7695` recall, `:8261` latency) — and the step dies with zero latency
evidence. If recall were skipped it would die again in the correctness matrix.
`mat26-control-100k` is unaffected because the GUC is never set there.

The `owner_fast_real_array_send=true` config as preregistered cannot produce the
A/B it preregisters.

Fix direction — pick one, but say which in `manifest.md`:

- **Degrade instead of failing** when the projection has no `real[]` column:
  fall through to the native send functions for that request and count it. This
  is the smallest change and it keeps the GUC honest as a session-wide switch.
  Keep a counter for these requests so a silent no-op cannot masquerade as
  activation (see P3-1).
- Or **keep fail-closed and scope the GUC to the latency child only**, dropping
  the recall append and the correctness-matrix `SET`. That costs you the
  prediction-identity and semantic-matrix coverage the candidate arm is supposed
  to demonstrate, so I do not recommend it — those are exactly what the packet
  needs to prove.

The first option keeps every gate in the proposed decision rule reachable.

### P1-3. "Byte-identical to `array_send`" is false for one input class, and the test does not cover it

`request.md` states the candidate "preserves PostgreSQL's binary array wire
format" and the manifest calls the pgrx test "SQL-level byte identity". That
claim does not hold in general, because the fallback trigger and `array_send`'s
flags word test different things:

- `array_send` emits `AARR_HASNULL(v) ? 1 : 0` for the flags int32
  (`/home/peter/.pgrx/18.3/src/backend/utils/adt/arrayfuncs.c:1607`).
  `ARR_HASNULL` is "is there a null bitmap", not "are there nulls".
- `fast_real_array_binary` falls back on `array_contains_nulls(array_ptr)`
  (`generation_read.rs:3220`), which *scans* the bitmap and is accurate
  (`arrayfuncs.c:3766-3771`: "This gives an accurate answer, whereas testing
  ARR_HASNULL only tells if the array *might* contain a null").
- Arrays with a bitmap and no nulls are reachable: `array_set_element` sets
  `newhasnulls = (ARR_HASNULL(array) || isNull)` (`arrayfuncs.c:2322`) and
  writes the bitmap at `:2439`. So overwriting the NULL element of
  `ARRAY[1,NULL,3]::real[]` with a non-null value yields exactly that shape.

For such a value the candidate emits flags `0` where `array_send` emits `1` —
the arrays differ in four wire bytes.

**Impact is confined to the claim, not to the data.** `array_recv` validates the
flags word only as `0 or 1` (`arrayfuncs.c:1308-1312`) and recomputes `hasnulls`
from the per-element lengths that `ReadArrayBinary` actually reads
(`:1399-1408`), so the coordinator's `ReceiveFunctionCall`
(`custom_scan.rs:2001`) reconstructs an identical `real[]` either way. Nothing
corrupts. But a packet whose candidate is justified by exact-byte equivalence
cannot leave an uncovered input class where the bytes are not equivalent.

Cheapest correct fix — make the trigger match `array_send` exactly by falling
back on the presence of the bitmap rather than on the presence of nulls, i.e.
test `header.dataoffset != 0` instead of calling `array_contains_nulls`. That is
byte-exact by construction, is strictly cheaper (no bitmap scan), and needs no
change to the encoder.

Then add the missing case to
`task224_fast_real_array_send_is_byte_identical_to_array_send`. Repro to pin:

```sql
CREATE TEMP TABLE t (a real[]);
INSERT INTO t VALUES (ARRAY[1, NULL, 3]::real[]);
UPDATE t SET a[2] = 5;
SELECT ec_distann_fast_real_array_send(a) = array_send(a) FROM t;  -- false at this HEAD
```

I confirmed this from the PG 18.3 source lines cited above rather than by
executing it, because executing it requires installing over the extension this
host currently has — see P1-2. Please run it as part of the fix.

### P1-4. Instrumentation parity is asymmetric, which is packet 002 authorization constraint 1

Packet 002 authorized the screen on "both arms in the same instrumentation
state, preferably both on unprofiled production SQL"
(`002-locality-attribution/feedback/2026-08-25-02-reviewer.md:132-135`).
`skip_owner_locality_profile=true` correctly gets both arms onto the same
*unprofiled production SQL shape*. But the candidate arm is still measured and
the control arm is not:

- `payload_send_profile_start()` / `_finish()` now run when
  `locality_profile_enabled || fast_real_array_send`
  (`generation_read.rs:2574`, `:2739`).
- `ec_distann_fast_real_array_send` calls
  `owner_buffer_usage_snapshot()` twice, `Instant::now()`/`elapsed()` twice, and
  `record_payload_send_profile` — per projected value
  (`:3274-3294`).
- The control arm calls `array_send` directly out of `build_payload_sql`
  (`remote_endpoint.rs:963`) with no shim at all.

The direction is conservative: the handicap is on the candidate, so a pass
survives it. It is also small — order 4 clock/counter reads per value against
13.57 values per scan. It is not nothing, though, and more importantly the
counters it produces exist in one arm only, which is why P3-2 below matters.

This does not need a re-architecture, but it does need one of:

- **Disclose and bound it.** State in `manifest.md` that the candidate arm
  carries a per-value timing shim the control arm does not, give the measured
  or estimated cost, and state that the delta is therefore a lower bound on the
  candidate's true effect. This is sufficient for a screen.
- Or **symmetrize**, which also buys you attribution — see the gate discussion.

## Review questions

**1. Is the exact-byte sender safe and semantically complete for the registered
`real[]` projection boundary?** Safe: yes, with one nit (P3-3). Semantically
complete: no — P1-3. Everything else in the encoder checks out:

- Wire layout matches `array_send`'s header/dims/lbounds/element framing
  (`arrayfuncs.c:1605-1614` vs `generation_read.rs:3191-3205`), including the
  per-element `4` length prefix that `float4send` produces.
- `to_bits().to_be_bytes()` preserves negative zero and NaN payloads exactly;
  `pq_sendfloat4` does not normalize either. The pgrx test covers both.
- `ARR_DATA_OFFSET` is reproduced correctly for both the bitmap
  (`header.dataoffset`) and no-bitmap (`MAXALIGN(sizeof(ArrayType) +
  2*ndim*4)`) cases (`:3238-3251`), so element data is read from the right place
  even in the fallback-eligible shape.
- Detoast is via `pg_detoast_datum` (`common/detoast.rs:29`), which handles
  compressed, on-disk external, short-header and expanded inputs, and
  `DetoastedVarlena::drop` pfrees only what it owns (`detoast.rs:83-91`).
  `values` borrows the detoasted buffer and is copied into an owned `Vec` before
  the guard drops. No leak, no use-after-free.
- Overflow arithmetic in `encode_fast_real_array_parts` is checked throughout;
  the dimension-product and capacity paths both return `Err` rather than
  wrapping, and the two negative unit tests pin the mismatch cases.
- Type discipline is layered and fails closed at every layer: substitution only
  for `pg_catalog._float4` frozen-schema attributes (`:2423-2432`), `AnyElement`
  OID check against `FLOAT4ARRAYOID` (`:3267-3269`), and an `elemtype` check
  after detoast (`:3217-3219`). The wrong-type pgrx test covers the SQL-visible
  path.
- Mutual exclusion with the locality profiler (`:2484-2489`) and with Task 220
  packed payload (`:2490-2497`) is enforced server-side, not just in the CLI.

**2. Does the explicit coordinator-to-owner flag keep the production path and
the A/B isolation honest?** The propagation is honest; the isolation is not yet.

Propagation is correct and I checked both build configurations. The flag is read
once on the coordinator (`options.rs:964-972`, GUC registered `Userset` and
default `false`), placed on the request in `PhysicalGenerationScan`
(`generation_read.rs:6756-6758`), and shipped as an explicit `$13::boolean`
parameter. Owners never read the GUC themselves, so an owner session cannot
drift from the coordinator's decision. Feature isolation is genuinely clean:
`PHYSICAL_MATERIALIZE_SQL` and the parameter vector are separately `cfg`-gated
(`remote_transport.rs:1616-1626`, `:2842-2892`), the request field is gated, and
the non-feature `cargo check` at HEAD passes — the 12-vs-13 arity mismatch that
a sloppier gating would have produced does not exist.

Isolation is not honest yet for two reasons already stated: the candidate arm
cannot complete its own recall and correctness runs (P1-1), and the two arms are
not in the same instrumentation state (P1-4). One thing the design gets exactly
right, and I want it on the record because it is easy to lose in a rewrite: the
SQL *shape* is byte-identical between arms — same `build_payload_sql`, same
`LEFT JOIN LATERAL`, same `''::bytea` NULL short-circuit, same ordinality
restore — with only the `{send}` identifier differing
(`remote_endpoint.rs:953-969`). That is the right isolation and it should
survive whatever fix P1-1 gets.

**3. Is the preregistered 5% usefulness gate appropriate?** The threshold is
reasonable; the gate is under-specified in two ways that should be fixed before
the run, because a preregistered gate amended afterwards is not preregistered.

5% of warm mean as a *usefulness* bar is defensible — below that, a bespoke
sender is not worth carrying in production, and the packet correctly bounds the
expectation by 18.258830% rather than 24.709206%. Keep it. Add:

- **A noise floor.** 200 queries × 200 iterations is a reasonable budget, but
  the gate compares two separately-launched steps against a reused fixture, so
  step-order and buffer-state effects are inside the measurement. Preregister
  what run-to-run variation you will treat as noise — a control-vs-control
  repeat is the cheap way to get it — and state it before you see the candidate
  number. As written, a 5.4% result and a 4.6% result get opposite dispositions
  with nothing establishing that the two are distinguishable.
- **An attribution condition.** The gate is currently a black box over
  end-to-end warm mean. Require that the send-region counters move by roughly
  the amount the end-to-end delta claims. A whole-scan improvement with a flat
  send bucket is not MAT-26 working, and this task has already had one candidate
  (MAT-25) die because the physical counters contradicted the summed bucket.

On attribution there is a structural problem worth naming: it is currently
**impossible** to measure the fast sender under the profiler, and correctly so.
`build_profiled_payload_sql` ignores `sends` entirely and routes every column
through `ec_distann_profile_binary_send` (`remote_endpoint.rs:960-964`), which
calls `array_send` — so a profiled candidate arm would measure the control. The
`fast_real_array_send && locality_profile_enabled` guard is right to reject it.

The clean way out is also the fix for P1-4: the candidate function already *is*
"timing shim + fast sender", and `ec_distann_profile_binary_send` already *is*
"the same timing shim + `array_send`". Running the control step with the
locality profile on and the candidate step with the fast sender on gives you two
arms behind the same shim, differing only in the inner serializer — which is
exactly the attributed A/B, with symmetric instrumentation. Keep the unprofiled
pair as the headline end-to-end number and add the profiled pair as the
attribution companion. That is two extra steps on an already-built fixture, and
it converts a threshold you have to trust into one you can explain.

**4. May the live same-generation 100k screen proceed at this HEAD?** No. P1-1
means the candidate step cannot complete, and P1-2 means whatever it did produce
would be measured on a debug `pg_test` extension. Fix P1-1 through P1-4, land
them as a code checkpoint, and reopen — packet 003 stays open; this does not
need a new packet ordinal.

## Non-blocking

**a. The activation proof cannot distinguish the fast path from the fallback.**
`distann_multicluster.rs:8461-8477` bails unless `owner_projected_values` and
`owner_binary_send_bytes` are both non-zero. Both counters are incremented by
`record_payload_send_profile`, which
`ec_distann_fast_real_array_send` calls on *both* branches — including the
`array_send` fallback (`generation_read.rs:3276-3294`). So the check proves the
wrapper ran, not that the exact encoder ran. For the DBpedia corpus that is a
distinction without a difference, but the whole point of an activation gate is
to not have to reason about that. A dedicated fallback counter, asserted zero,
would make it airtight — and it becomes necessary rather than nice if P1-1 is
fixed by the degrade-instead-of-fail route, since then a mis-scoped GUC could
produce a fully inert "candidate" arm that still passes activation.

**b. Nothing pins the emitted provenance suffix.** The new
`owner_locality_profile=` / `owner_fast_real_array_send=` fields
(`:9167-9170`) are good — they put the arm's identity on every row. No test
asserts they are emitted, so a future refactor can drop them silently and the
packet's isolation claim becomes unverifiable after the fact. Same shape as
non-blocking item (b) in the packet 002 feedback; a one-line assertion over the
composed line closes it.

**c. Zero-length slice past the end of an empty array's allocation.** For
`'{}'::real[]`, `construct_empty_array` palloc0s exactly `sizeof(ArrayType)` =
20 bytes, while `data_offset` computes `MAXALIGN(20)` = 24, so
`slice::from_raw_parts(base+24, 0)` (`generation_read.rs:3252-3253`) builds a
zero-length slice from a pointer four bytes past the object. No read occurs and
palloc's chunk rounding means the address is backed, so this is not a live
defect — the pgrx test exercises it and passes. It is UB by the letter of
`from_raw_parts`'s validity rule. An early return of the 12-byte header for
`item_count == 0` sidesteps it.

**d. Volatility and parallel-safety differ between the arms.**
`ec_distann_fast_real_array_send` is `volatile, parallel_restricted`
(`:3263`); `array_send` is immutable and parallel-safe. In this SQL the value
feeds a per-row `CASE` inside a `LEFT JOIN LATERAL`, so no folding or
parallelism is available to either arm and I do not expect any planner
difference. Direction is conservative if there is one. Worth a sentence in
`manifest.md` rather than a change — `ec_distann_profile_binary_send` carries
the same declaration, so packet 002's profiled arms had it too.
