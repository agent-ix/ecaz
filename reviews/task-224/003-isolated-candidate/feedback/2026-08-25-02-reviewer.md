## Blockers

Consequences beyond the step dying:

- The gate "both decision-bearing semantic matrices must pass"
  (`request.md:98`) is unsatisfiable as configured. Only a non-reuse step can
  run a matrix, and only step 1 is non-reuse.
- The guard is not simply mislabeled. The matrix issues no DML, but its
  `post_first_batch_remote_failure` scenario `pg_ctl -m immediate stop`s owners

  fixture, so relaxing the guard blindly is not the answer — see B2.

Fix direction, pick one and state it in `manifest.md`:

- **Preferred: take the semantic matrices out of the timing suite entirely.**
  The matrix is a correctness proof; it does not need *the* measured
  generation, it needs *a* generation. Run the control-arm and candidate-arm
  matrices as their own non-reuse steps (own `run_dir`, own build, 10k is
  fine), and leave all four timing steps free of `materialization_correctness`.
  This satisfies B1 and B2 at once and costs no timing fidelity.
- Or **land a suite/fixture change** that lets `materialization_correctness`
  combine with `reuse_fixture`, as its own commit with a test, *and* reorder so
  no decision-bearing latency step is preceded by another step's owner restart.
  Per AGENTS.md that extension lands before the packet uses it.

Whatever you choose, add a `validate_config` rule for the reuse/matrix pairing
so the next config cannot reach run time with it.

### B2. Step ordering puts an unclean owner restart between control A and the candidate

Independent of B1, the four-step order interacts badly with what the matrix
does. Within a step the order is recall → latency → … → correctness matrix
(`:7695`, `:8261`, `:9163-9182`), so control A measures its own latency before
its matrix runs. But the matrix is the *last* thing step 1 does, and it
immediate-stops and restarts owners 2 and 3. Under the current ordering the
candidate's latency (step 2) is the first measurement taken after two
crash-recovered, cold-buffer owners, while control B (step 3) inherits owners
warmed by the candidate step. That asymmetry lands precisely on the
control-A-versus-candidate comparison the headline gate depends on, and it is
not captured by `N`, which is defined from A and B.

The direction is conservative for a PASS and ambiguous for a FAIL, which is not
good enough for a screen whose only possible outcomes are "advance" and "STOP
Task 224".

Fix: ensure every decision-bearing latency step begins in the same fixture
state. The B1 preferred fix does this by construction. If you keep matrices in
the suite, run all four latency steps first and both matrices last.

### B3. The attribution gate is not executable as written

`request.md:93-96` / `manifest.md:36-38` define the gate as
"profiled-control `owner_binary_send_ns` minus candidate `owner_binary_send_ns`
… at least 50% of the end-to-end warm-mean saving". Three things are missing
before that can be computed without discretion after the fact:

1. **`owner_binary_send_ns` is not an artifact field.** It is a column of the
   owner endpoint (`remote_transport.rs:1628`). What lands in `results.jsonl`
   is `physical_benchmark_stage` with `stage=materialize_owner_binary_send_work`
   and `mean_ms` — this is the row family packet 002 used for 6.967996
   (`002-locality-attribution/artifacts/gate-calculation.md:65`). Name the row
   family, the field, and the arm selector.
2. **Normalization.** `mean_ms` is per custom-scan execution; the warm mean is
   per query. For the packet 002 vector-bearing arm these coincide
   (`elapsed_ms 3217.710518 / mean_ms 16.088553` = 200 executions for 200
   queries), but the identity has to be asserted from the emitted rows in this
   run, not assumed. State that you will assert equal execution counts across
   the compared arms and fail the gate if they differ.
3. **Summed-owner versus serial.** Packet 002 established that the summed-owner
   send bucket (6.967996 ms/scan) overstates any serial saving, which the
   endpoint critical path caps at 5.148990 ms/scan. A gate that compares a
   summed-owner delta against a serial end-to-end delta is therefore biased
   *toward* passing — the opposite of the direction the packet claims for its
   other instrumentation asymmetries. Either deflate by the observed
   endpoint-critical/summed ratio the way `gate-calculation.md:73-77` did, or
   say explicitly that 50% is a summed-work threshold and that it is a weak
   test.

## Review questions

**1. Is the exact-byte sender safe and semantically complete for the registered
`real[]` projection boundary?** Yes — this is now settled. The one input class
seq01 found is closed at the trigger rather than in the encoder, which is the
stronger fix, and the reproducer is pinned. Everything seq01 verified about the
encoder still holds at this HEAD: wire layout, `to_bits().to_be_bytes()` for
negative zero and NaN, `ARR_DATA_OFFSET` reconstruction, `pg_detoast_datum`
lifetime discipline, checked overflow arithmetic, and the three-layer type
fail-closed. The empty-array path no longer forms a slice past the allocation.
Nothing further is required of the serializer.

**2. Does the explicit coordinator-to-owner flag keep the production path and
the A/B isolation honest?** The flag and the degradation are honest. The
isolation is still not, but for scheduling reasons now (B1, B2) rather than
semantic ones. Two specifics worth recording:

- The ineligible counter is per owner *request*, and the CLI asserts it zero
  only in the vector-bearing latency arm — which is the right scope, because
  the recall child and the matrix are separate processes whose degraded
  requests must not pollute the measured arm. One gap: the `nodes.is_empty()`
  early return (`generation_read.rs:2504-2514`) builds
  `OwnerMaterializationTelemetry::default()` and drops
  `fast_real_array_ineligible_requests`. An empty request can therefore degrade
  uncounted. Not decision-bearing at 100k; fix it while you are there.
- The preflight attests a *unanimous, non-empty* SHA
  (`distann_multicluster.rs:485-506`); it does not compare it to an expected
  value, so `request.md:82-83`'s "attest … exact git SHA" is stronger than the
  code. The SHA is on every emitted row
  (`extension_git_sha={expected_sha}`), so record the required value in
  `manifest.md` and check the rows post-hoc.

**3. Is the preregistered 5% usefulness gate appropriate?** The threshold is
right and I would keep it. The surrounding structure is much better than seq01:
the tail gate is computable directly from `physical_benchmark_latency`
`p95_ms`/`p99_ms`, the activation gate is enforced in code rather than asserted
in prose, and the prediction-identity and matrix conditions are stated before
measurement. Three notes:

- **The noise floor is sound in direction but is not a pure control repeat.**
  Control B is `stage_counter_only`, so it skips recall and the single control
  (`suite.rs:4814`, `distann_multicluster.rs:7497,7598`) while control A runs
  them; and A runs two variants where B runs one. `N` therefore measures
  run-to-run noise *plus* a protocol and position difference. Because the
  candidate is measured between A and B, and the gate demands `2*N`, this
  inflates the bar rather than lowering it — acceptable for a screen, but say
  so in `manifest.md` instead of calling `N` a noise floor unqualified.
- **The profiled-control versus candidate send-region comparison is
  sufficiently comparable, and I can bound the one asymmetry.** The profiled
  arm wraps both projected values while the candidate wraps only the `real[]`,
  so the profiled send bucket carries an extra `int4send` per row that the
  candidate's does not — this inflates the apparent saving, i.e. it is
  anti-conservative for the attribution gate specifically, which the packet's
  "conservative for the candidate" framing does not cover. The magnitude is
  settled by packet 002's id-only arm, which measured exactly that quantity:
  **0.005083 ms/scan against a 6.967996 ms/scan vector-bearing send bucket, or
  0.073%** (`gate-calculation.md:63,65`). Negligible. Both regions time only
  the inner serializer and both include detoast, so the comparison is otherwise
  like-for-like. State the 0.073% bound in `manifest.md` and the objection is
  closed.
- The shim bound itself is constructed correctly: the profiled arm wraps two
  values per row to the candidate's one, so `profiled − C` genuinely
  over-estimates the candidate's handicap.
