# Task 64 Review: HNSW Quantized Codec Adapter

## Verdict

The core Task 64 deliverable is **clean, narrow, and behavior-preserving**. The
hard-stop conditions are respected: no on-disk byte changes for existing
TurboQuant/PqFastScan indexes, no forked graph topology lifecycle, and no
premature cross-AM trait. I have **no Blockers**. Findings below are
scoping/clarity notes the closeout should address.

## What I verified

**On-disk compatibility (HARD STOP) — PASS.** `src/am/ec_hnsw/page.rs` only adds
new enum variants/constants (`INDEX_FORMAT_V4_RABITQ`, `SearchCodecKind::RaBitQ`,
`GraphStorageFormat::RaBitQ`). No existing byte offset, field, or encoding
changed. `MetadataPage::graph_storage_format` still maps V1/V3→TurboQuant and
V2→PqFastScan identically; the format-version allowlist in deserialization
additively gains V4. Existing V1/V2/V3 indexes never reach any RaBitQ arm.
`codec.rs:154-177` has explicit tests asserting TurboQuant/PqFastScan metadata
identities are preserved.

**Adapter extraction is verbatim-preserving — PASS.** `BuildState::initial_metadata`
(build.rs) and the build tuple-fit check were moved into
`HnswStorageCodec::initial_metadata` / `build_tuple_fits_on_page`
(codec.rs:45-127) as exact copies of the prior inline match arms.
`GraphStorageDescriptor::matches_storage_format`/`storage_format_name` collapsed
into a single `codec()` accessor with semantically identical mapping (graph.rs).

**Graph topology lifecycle not forked (ADR-033) — PASS.** RaBitQ consumption
adds `InsertFormatAdapter::RaBitQ` / `VacuumFormatAdapter::RaBitQ` variants and
format-specific payload helpers (`append_rabitq_tuple`, `encode_rabitq_hot_tuple`,
`derive_rabitq_search_code_for_insert`, `score_rabitq_search_code_result`).
Neighbor discovery, backlink/lock ordering, level sampling, and repair ordering
remain in the shared pipeline and only call adapter hooks. Scan adds a
`RaBitQScorer` path with polarity normalization (`-prepared_query.score(...)`)
kept local; traversal is unchanged.

**No premature cross-AM trait — PASS.** `HnswStorageCodec` is a concrete
HNSW-local enum; shared quantizer math stays in `src/quant` (`Family`,
`RaBitQQuantizer`). Consistent with ADR-072.

## Findings

### Minor — closeout language re. RaBitQ vacuum should be reconciled with Task 63
This packet's closeout should not imply the adapter makes RaBitQ fully
lifecycle-complete on its own. **Correction from the Task 63 review:** RaBitQ
vacuum *is* implemented (routed through the shared `TQ_GROUPED_HOT_TAG`
grouped-hot path — `vacuum.rs:699-733, 918-939, 1411-1443`), so an earlier draft
note claiming "vacuum unimplemented" is stale. The accurate statement is: Task
64 extracts the seam; Task 63 fully implements RaBitQ build/scan/insert/vacuum
against it; the only outstanding RaBitQ gap is publishable benchmark evidence
(tracked in Task 63), not vacuum.

### Minor — `from_metadata` legacy V1 path remains reachable through the new seam
Not introduced by Task 64 (pre-existing), but the adapter now routes through
`HnswStorageCodec::from_metadata` → `graph_storage_format()`. V1_SCALAR is still
accepted and mapped to TurboQuant within `GraphStorageDescriptor::from_metadata`.
No regression, just noting the legacy V1 path remains reachable through the new
seam exactly as before. No action required unless Task 42 invariant coverage
wants it tightened.

### Nit — RaBitQ reuses `PqFastScanLayout` as its descriptor payload type
`GraphStorageDescriptor::RaBitQ(PqFastScanLayout)` (graph.rs). Functionally fine
and guarded by strict `from_metadata` validation (rejects sidecar, requires cold
rerank, requires `SearchCodecKind::RaBitQ`, validates `search_subvector_dim ==
search_bits`), but the shared struct name invites future confusion if the two
layouts diverge. Consider a type alias or dedicated `RaBitQLayout` when Task 63
finalizes. Task 64 itself is unaffected.

### Nit — `append_rabitq_tuple` carries a single-fresh-page limitation
insert.rs: `"ec_hnsw aminsert does not yet support RaBitQ tuples that require
more than one fresh data page"`. This is a Task 63 storage limitation at the
(correct) tuple-append seam, not a topology fork — and it is the same
pre-existing limitation shared by TurboQuant and PqFastScan. Flagging for Task
63 tracking only.
