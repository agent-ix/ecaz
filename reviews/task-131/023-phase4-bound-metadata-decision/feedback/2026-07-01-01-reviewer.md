# Reviewer Feedback: Packet 023 — Phase 4 Bound Metadata Decision

You correctly diagnosed the root cause — "the representative indexes do not
build leaf block summaries" — and I independently confirmed it in the code. But
the **decision drawn from it is one step premature.** The right next action is
not "shelve Phase 3 / spin up a whole new metadata subsystem"; it is "flip the
build GUC that already exists, rebuild one cell, and re-run the diagnostic you
already have." That is a single rebuild, not a design project.

## Confirmed root cause (code-traced)

`collect_quantized_selected_leaf_threshold_profile`
(`src/am/ec_spire/scan/candidates.rs:250`) counts a leaf's bound as *available*
only when the persisted leaf object carries a non-empty `summaries` vector and
the payload is RaBitQ (lines 315–324). Leaf summaries are written only when
`ec_spire.leaf_block_rows > 0` at **build time**
(`build/recursive.rs:262–284`, gated by `current_leaf_summary_block_rows()`),
and that GUC **defaults to 0 = disabled** (`options/mod.rs:36`, registered
line 829; help text: "0 disables summaries"). The b2/b4 configs are already
RaBitQ, so condition (b) holds — the only thing failing is (a), summaries never
persisted. An index built with the default therefore *must* report
`available=0`. That is precisely what packet 022 saw.

## Why the shelve is premature, not justified

The bound is not fundamentally unavailable — it is fully wired end to end and
**sound**:

- build → persist (`recursive.rs:270`) → read (`local_store.rs:557`,
  `read_leaf_object_v2`) → scored;
- the diagnostic constructs the score context with **radius_weight = 1.0**
  hardcoded (`candidates.rs:293`), i.e. the full Cauchy-Schwarz upper bound
  (`max_rep(q·rep) + ||q||·γ`), and deliberately does **not** use the unsound
  0.0 session default. So soundness is not the blocker either.

So Phase 3's early-stop was never actually exercised — it was evaluated against
indexes that structurally cannot produce the bound, and then reported as
"unavailable." You cannot conclude a mechanism doesn't work from a run in which
the mechanism was switched off at build time.

Note this is the phase that matters most: Phase 1 already established the
latency bottleneck is remote **scan/scoring**, not heap. Phase 3's early-stop is
the only phase that targets scan work. Shelving it on a GUC technicality shelves
the one idea aimed at the actual bottleneck.

## Required before any Phase 3 shelve — the run you already named

You wrote the revival path yourself ("build representative multi-instance
indexes with leaf block summaries enabled, then measure … available, selective,
storage-affordable, recall-safe"). Do that *before* closeout, at least one cell:

1. Rebuild one representative cell (10k or 50k, `n128/b4`) with
   `SET ec_spire.leaf_block_rows = 64` (or 128) before `CREATE INDEX` — the GUC
   is consumed at build time, so query-time SET does nothing to an existing
   index; the index must be rebuilt. Keep RaBitQ; default
   `leaf_block_summary_representatives=1` is fine. **Do not** touch
   `leaf_block_pruning_summary_radius_weight` — the diagnostic forces 1.0
   internally.
2. Re-run `ec_spire_remote_search_production_candidate_threshold_profile` /
   the suite boundability step against that index.
3. Read `sound_bound_available_sum`, `threshold_block_skipped_sum`,
   `threshold_row_skipped_sum`, plus index storage delta and recall.

The decision then becomes evidence-based, three ways:
- **bounds available AND a real fraction of blocks/rows skippable** → Phase 3 is
  viable; build the gated recall-safe early-stop on the packet-015 streaming
  structure and A/B query latency at 10k/50k/100k.
- **bounds available but skips trivial / not selective, or storage cost
  unaffordable** → *now* shelve, with real numbers behind it, and record the
  storage/selectivity that killed it.
- **bounds still zero with summaries on** → a real defect; investigate before
  any decision.

## Minor code note

`collect_quantized_selected_leaf_threshold_profile` folds a
`read_leaf_object_v2` *error* into the same `sound_upper_bound_missing` counter
as "no summaries" (`candidates.rs:315`). Harmless on the all-zero surface, but
once summaries exist a genuine I/O read failure would be silently miscounted as
"no bound." Consider a distinct error path/counter before relying on this
diagnostic with summaries enabled.
