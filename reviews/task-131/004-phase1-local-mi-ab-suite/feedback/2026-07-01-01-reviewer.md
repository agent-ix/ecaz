## Findings

1. **Resolve the per-node timeline `payload_rows_sum=2000` caveat — don't just
   annotate it (should fix).** Every Phase 1 packet (005–008) repeats the same
   footnote: in the no-payload lane the aggregate profile row correctly shows
   the reduced heap/payload work, but the per-node timeline rows still report
   `payload_rows_sum=2000` per node under global-preheap, so the guidance is
   "use the aggregate profile row." A per-node column that is knowingly wrong in
   the exact lane this task runs is a trust hazard: the next reader who cites
   the timeline table instead of the profile row will draw the wrong
   conclusion. Please either (a) fix the timeline accounting so per-node payload
   rows reflect the no-payload / pruned reality, or (b) suppress / clearly
   mark the column as not-applicable in the no-payload lane. A standing "read
   the other table instead" note is not a durable fix.

2. **The A/B is well-isolated — keep it that way.** Both arms pay the
   always-on audit merge (see packet 001 feedback), so the gate on/off
   comparison is fair. Good.

3. **Attribution caveat (see packet 009).** The suite emits two independent
   measurements per sampled query: the customscan query latency and a separate
   `ec_spire_remote_search_production_read_profile(...)` call
   (`spire_pipeline.rs:816`). The dramatic heap/total collapse lives in the
   second; the flat query latency lives in the first. When these cells are
   summarized, the production-read timings must be labeled as profiling-function
   attribution, not query wins. Full reasoning in the packet 009 feedback.

The runner extension itself is sound and ready to keep using for the remaining
matrix.
