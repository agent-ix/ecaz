## Notes

- **Counter semantics are the right ones.** `input_count` (pre-merge candidate
  total), `candidate_count` (post-merge survivors), `duplicate_vec_id_count`,
  and `pruned = input - candidate` (via `saturating_sub`) exactly quantify the
  heap rows a global merge could avoid, which is what Phase 1 needs to justify
  the endpoint. Answering your reviewer-focus question directly: computing the
  merge after candidate receive and before applying heap results is the correct
  low-risk diagnostic point, and the counter set is sufficient to green-light
  the subset endpoint you built in packet 002.

- **This audit merge became always-on cost.** Once packet 002 lands,
  `record_global_pre_heap_candidate_metrics` runs a full candidate merge on
  every pooled production read whether or not the feature GUC is set. That's
  acceptable (merge ≪ heap receive) and keeps the A/B fair, but it is now
  permanent per-query overhead rather than a one-off audit. Keep it in mind if
  a future decision is to ship the audit counters but not the pruning.

- **`saturating_sub` for `pruned` can mask an invariant break.** If
  `candidate_count` ever exceeded `input_count` (it never should — merge only
  removes rows), `pruned` would silently clamp to 0 rather than surface the
  bug. Not worth changing for a diagnostic counter, but if these counters
  outlive Phase 1, a debug assert that `candidate_count <= input_count` would
  be cheap insurance.

No blocking issues. Code-path correctness for the endpoint itself is covered in
the packet 002 feedback; the evidence read is in packet 009.
