# Reviewer Feedback: Task 131 Phase 1 — Cross-Cutting Evidence Read

This is the phase-level synthesis across packets 005–009 (10k/50k/100k ×
`n128/b4` and `n1024/b2`). Localized code findings are in the 001/002/004
feedback files. Head: branch `task-131-spire-streaming-global-topk`.

## Bottom line

Phase 1 is **correct, recall-safe, and does what it claims mechanically** —
remote heap rows fall from 6000 to 2000 (~66%) at matched recall in every cell.
But it **does not move end-to-end query latency at any scale or shape.** That is
not a failure: Task 131's own plan calls Phase 1 "a limited win at best" and
frames it as de-risking global-merge semantics before scan-time feedback. Read
that way, this is a clean, useful **negative result**. My recommendation is
**iterate to Phase 2, do not promote Phase 1 as a latency win** — and fix how
the evidence is headlined before it gets cited downstream.

## The numbers, honestly

Recall is matched to 4 decimals in all six cells (0.9975–1.0000, baseline ==
global-preheap). Heap rows 6000→2000 everywhere. Query latency, the actual
Task 131 objective ("materially reduce SPIRE distributed read latency at matched
recall"):

| cell | query p50 base → preheap | verdict |
| --- | --- | --- |
| 10k n128/b4 | 591.3 → 595.3 ms | flat (slightly worse) |
| 10k n1024/b2 | 535.3 → 534.4 ms | flat |
| 50k n128/b4 | 2583.0 → 2593.5 ms | flat (slightly worse) |
| 50k n1024/b2 | 663.8 → 663.3 ms | flat |
| 100k n128/b4 | 5366.1 → 5357.1 ms | flat |

Across the matrix query p50 moves by well under 1%, sometimes the wrong way.
p95/p99 are similar — mixed, small, within run-to-run noise for a single-run
cell. **On the metric the task exists to move, Phase 1 is flat.**

## The discrepancy that must be reconciled before citation

Each packet headlines a large "production-read total" and "heap" collapse — e.g.
10k: heap p50 669→7 ms, total 554→310 ms; 100k: total 5341→2668 ms. Taken at
face value a ~2.7 s production-read reduction at 100k that yields ~0 ms query
improvement is self-contradictory.

The resolution is in the harness: the suite takes **two independent
measurements per sampled query** (`spire_pipeline.rs:816`) — the normal
customscan query (which produces recall + the latency table) and a *separate*
`ec_spire_remote_search_production_read_profile(...)` call (which produces the
heap/total profile). The profiling function attributes per-phase cost in its own
serial execution; it is **not** the critical-path cost inside the real query.
So the heap/total collapse is real *for the profiling call* but does not
represent query latency, which is dominated by remote scan/scoring (candidate
production) — precisely the work Phase 1 does not touch, and precisely what
Phase 2/3 target.

This is a measurement-claim issue under REVIEWER.md, so to be explicit:

- The heap-work reduction (rows 6000→2000) **is** a genuine, well-evidenced
  win and traces to `results.jsonl` (`remote_heap_candidate_sum`,
  `payload_rows_sum`). Keep citing it.
- The "heap p50 669→7 ms / total 5341→2668 ms" figures **must be labeled as
  production-read-profile attribution, not query latency**, wherever they
  appear. As currently phrased in the packet summaries ("production-read total
  timing improved") they read as end-to-end wins to anyone skimming. Please add
  the caveat inline in the packet result summaries, or the next consumer will
  promote a win that the query-latency table flatly contradicts.

## Corroborating point

This result confirms the Task 123 finding restated in the Task 131 plan: heap /
materialization payload is not the dominant latency driver. Phase 1 now proves
that positively — you can delete two-thirds of the heap rows and the query does
not get faster. That is exactly the de-risking Phase 1 was meant to provide, and
it strengthens the case for spending Phase 2/3 effort on candidate-phase / scan-
time pruning rather than further heap-side optimization.

## Recommendation

1. **Decision: iterate, not promote.** Record Phase 1 as: mechanism correct,
   recall-safe, heap work cut ~66%, **query latency neutral at 10k/50k/100k** →
   proceed to Phase 2 (candidate-to-heap streaming / removing the candidate-
   phase barrier), which is where the flat-latency evidence says the real cost
   lives. The GUC stays `off` by default (correct — it is diagnostic).
2. **Before any closeout note:** add the profiling-vs-query-latency caveat to
   the 005–009 result summaries so the heap/total numbers aren't mis-cited.
3. **Fix the per-node timeline `payload_rows_sum=2000` accounting** (packet 004
   finding #1) rather than footnoting it.
4. **Close the unit-test gap on `assign_global_heap_candidate_subsets`**
   (packet 002 finding #1) before this path is a promotion candidate.

Nice, disciplined work overall — the honesty in each packet ("query latency was
not improved", "flat") is exactly right and made this easy to trust. The only
gap is that the headline profile numbers need the same framing the prose already
gives the query numbers.
