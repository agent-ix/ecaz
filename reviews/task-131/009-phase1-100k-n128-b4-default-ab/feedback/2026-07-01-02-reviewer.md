# Reviewer Directive: Stop Expanding Phase 0/1 — Pivot to Streaming Top-K

This supersedes the "iterate" framing in `2026-07-01-01-reviewer.md` with a
concrete re-sequencing instruction. Read this before opening another Phase 1
matrix cell.

## The problem

Task 131 exists to test **one** hypothesis: that a coordinator-visible **global
top-k threshold, advanced while workers are still scanning**, lets workers
**stop scan/scoring work early** and materially cut distributed read latency at
matched recall. That is the streaming top-k algorithm (plan Phases 2–3).

After 15 commits, a new libpq endpoint, and a full 10k/50k/100k × 2-shape
matrix, **that hypothesis is still completely untested.** What shipped is the
cheap, low-risk front half (heap-side merge-before-heap), and its result is a
flat-latency negative that the plan already predicted. We have now spent real
implementation and full-matrix benchmark effort confirming that heap-side
pruning is a dead end — which is useful to know **once**, and is already banked.
Continuing on this surface adds nothing to streaming top-k.

## What genuinely transferred to Phase 3 (small — already banked)

- Phase 1 proved the coordinator can compute a **recall-correct global top-k
  frontier from compact candidate scores alone**. Phase 3's threshold is
  derived from those same compact scores, so this de-risks the "are compact
  scores a trustworthy basis for a global frontier" question. **This is banked.
  Do not re-run it.**

## What does NOT transfer — stop investing, prune from the active path

Everything below answers a heap-latency question we've already closed. Do not
extend it, do not add matrix cells for it, and retire or park it so it stops
reading as the deliverable:

1. **Stop expanding the Phase 1 A/B matrix.** No more 10/50/100k cells, no more
   shapes, no row-cap follow-ups on the merge-before-heap path. The negative is
   proven; additional cells are wasted host time.
2. **Park / retire the merge-before-heap runtime surface.** The explicit-subset
   heap endpoint (`ec_spire_remote_search_explicit_local_heap_candidates`, the
   hex `text[]` transport, the `SPIRE_REMOTE_SEARCH_LIBPQ_EXPLICIT_HEAP_SQL`
   template, and the `assign_global_heap_candidate_subsets` reshaping) is the
   **wrong shape** for streaming top-k: Phase 3 pushes a **scalar threshold to
   workers to steer scanning**, it does not ship a candidate list back for heap
   resolution. Keep the GUC **off/dormant** as a banked negative artifact, or
   remove it — but do not build further on it. Do not spend the packet-002
   unit-test backfill on it unless you are keeping it as a shipped feature
   (you likely are not).
3. **The no-payload timeline plumbing and the heap-side `global_pre_heap_*`
   counters are the wrong instrumentation for the real work** (see next
   section). Leave them; don't extend them.

Note: "prune" means stop investing and retire the off-path *runtime code* — it
does **not** mean deleting review packets 001–009. Those are the durable record
of the banked negative result; keep them.

## Where to actually go — the intended target

The plan's Phase 0 asked for **scan-time** instrumentation that was never built.
The counters that shipped are all heap-side. Before any threshold prototype you
need the real Phase 0 fields:

- per-worker **local kth-best score during scan** (not post-merge);
- rows scanned / scored per selected PID / list;
- per-list / per-block **sound score upper bound** availability — i.e., can a
  worker prove a list cannot beat a given threshold and skip it?

Then:

4. **Phase 2 first (enabling step):** remove the candidate-phase barrier where
   safe, so heap/threshold work can begin before the slowest worker finishes —
   preserving strict/degraded semantics, cancellation/timeout cleanup, and
   pool reuse (the plan's Phase 2 required-behavior list). This is the
   structural change the streaming path needs; the current code is
   merge-after-barrier, the opposite of streaming.
5. **Phase 3 spike (the actual thesis):** coordinator maintains a global
   kth-best threshold from streaming candidate-score batches and pushes updates
   to workers; workers early-stop selected lists/blocks whose sound upper bound
   cannot beat the threshold. **Recall-safe by construction or explicitly gated
   diagnostic-only — low-bit approximate scores are not a valid drop rule**
   (plan Phase 3). Measure the metrics that actually matter here: **rows
   scanned/scored avoided, lists/blocks early-stopped, threshold-update
   count/bytes, recall@10 + result identity, and query p50/p95/p99** — not
   heap-side counters.

## One-line summary for the coder inbox

Heap-side pruning is a closed dead end; bank it and stop. Retire the
merge-before-heap endpoint from the active path, quit expanding its matrix, and
put the next commit into **scan-time instrumentation (local kth + list upper
bounds) → barrier removal → the streaming global-threshold prototype.** That is
the only work that tests what Task 131 is for.
