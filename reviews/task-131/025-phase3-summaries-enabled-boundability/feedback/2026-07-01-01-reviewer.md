# Reviewer Feedback: Packet 025 (in flight) — Summaries-Enabled Boundability

Early review of the in-flight packet 025 work: the test design, the strategy,
and — most importantly — a root-cause finding that changes what you build next.
**Your GUC plumbing works, but it is targeting the wrong build path. Bounds are
still zero because the distributed fixture's scanned leaf objects are created by
`coordinator/materialization.rs`, which never writes summaries at all.** Read
the root-cause section before running anything else.

## Root cause: why `sound_bound_available_sum` is still 0 with the GUC verified ON

I traced both lanes and the engine code:

- The `-set` lane load logs show `[loader] session_guc ec_spire.leaf_block_rows=64`
  echoed via `current_setting` read-back on the coordinator and both remote
  loaders. The GUC delivery is real and verified. Good instrumentation.
- Yet the `-set` bench results report exactly the same counters as the
  no-GUC lane: `sound_bound_available_sum=0`,
  `sound_bound_missing_sum` = 688/633/599, zero block/row skips. Identical
  missing-counts across lanes means the scan read the same summary-less
  surface both times.
- Engine trace: `current_leaf_summary_block_rows()` is consumed in exactly one
  place — `src/am/ec_spire/build/recursive.rs:251` (local `CREATE INDEX`
  build). The distributed read path does not scan those loader-built leaves.
  It scans the coordinator-owned remote leaf base created by
  `ec_spire_materialize_static_remote_leaf_assignments_with_mode(...)` in the
  rendered per-node materialization SQL
  (`remote-leaf-materialization/node-N-remote-materialize-rendered.sql`).
- `src/am/ec_spire/coordinator/materialization.rs` (327 lines) contains **zero
  references to summaries**. The leaf partition objects it builds are
  structurally incapable of carrying block summaries, regardless of any GUC,
  session SET, or PGOPTIONS delivery.

So the `-set` lane's zero is expected-by-construction, and no amount of GUC
plumbing can flip it. Per the 024 seq-3 ruling ("bounds still zero with
summaries ON → that is a defect; investigate"), this is the investigation
result: **the defect is a missing feature in the materialization path, not a
delivery bug.** Phase 3 boundability cannot be measured on the multinode
surface until materialization can write summaries.

Also for the record: the first lane (`10k-n128-b4-leaf-block-rows64`) never had
the GUC applied at all — no `session_guc` echo, no `leaf_block_rows` anywhere
in its logs. Do not cite it as a summaries-on cell. It is, however, a perfectly
good **control lane** (same config, bound source off) — relabel it as the
control in the packet manifest rather than deleting it.

## What to build next (design)

### Step 1 — teach materialization to write summaries (the actual unblock)

- Factor the summary construction out of `build/recursive.rs` (the RaBitQ
  k-representatives + covering-radius encoding, lines ~262–273 / 819–850) into
  a shared writer, and call it from `materialization.rs` when building remote
  leaf objects. Do not duplicate the encoding — the soundness of the bound
  lives in that one implementation, and two copies will drift.
- Reuse the existing leaf V3/V4/V5 summary format (`leaf_v2_parts.rs` meta:
  `row_base`, `row_count`, `gamma`, encoded representatives). Do not invent a
  new on-disk shape; the readers and their tests already exist.
- GUC delivery for materialization: the materialization SQL runs in its own
  psql session on each node, so make the rendered SQL template emit an explicit
  `SET ec_spire.leaf_block_rows = <n>;` line, parameterized by the fixture
  flag. That is auditable in the packet artifact (the rendered SQL *is* the
  evidence), unlike ambient `PGOPTIONS` inherited through the process tree.
  Keep the PGOPTIONS path if you like as belt-and-braces, but the rendered SQL
  must show the setting.
- Keep it gated: default `leaf_block_rows=0` must produce byte-identical
  materialization behavior to today.

### Step 2 — rerun the boundability profile, gate the decision on four numbers

Rerun the 10k `n128/b4` cell with summaries materialized, against the control
lane. The decision gates, per the 024 seq-3 conditions:

1. `sound_bound_available_sum > 0` — if still zero, the shared writer isn't
   reached; instrument and fix before anything else.
2. **Selectivity** — `threshold_block_skipped_sum` / `threshold_row_skipped_sum`
   as a fraction of scanned blocks/rows at the derived threshold. Bounds that
   exist but never skip are a measured shelve.
3. **Storage delta** — index/leaf storage with summaries on vs the control lane
   (the storage steps are already in your suite config; diff them).
4. **Recall parity** — summaries change leaf layout; verify recall against the
   control *before* any early-stop exists, so layout effects are not later
   confounded with pruning effects.

If available-but-not-selective or storage-unaffordable: shelve Phase 3 **with
these numbers** — that is a legitimate, accepted closeout path. Only if
available AND selective do you proceed to Step 3.

### Step 3 — only if selective: the gated early-stop on the packet-015 structure

The profile today is diagnostic-only (`collect_quantized_selected_leaf_threshold_profile`
is called for observability, never wired into the scan). The real early-stop
design, in increments:

- **Increment A — worker-local threshold seeding (no new protocol).** Pass the
  coordinator's current global kth (from the compact-score frontier packet 024
  proved trustworthy) in the existing candidate request
  (`SpireRemoteProductionCandidateReceiveRequest`). Workers use
  `max(local kth, seeded global kth)` as the skip threshold. Zero new channels,
  strictly recall-safe, measurable on its own. Measure before building more.
- **Increment B — mid-scan refresh, only if A's headroom analysis justifies
  it.** There is currently NO coordinator→worker mid-scan channel (dispatch is
  one-shot request/response). The cheapest refresh shapes are chunked candidate
  production with a threshold piggybacked per chunk, or a side channel.
  Both add real protocol complexity — the task's whole point is to decide
  whether that complexity is paid for. Do not build B speculatively; the
  instrumentation from A (how much scan work remained after the threshold
  could first have stopped it) tells you B's ceiling.
- **Recall safety by construction, always:** skip a block only when its sound
  RaBitQ upper bound (radius_weight = 1.0) is strictly worse than a
  known-lower-bound on the global kth. Missing/foreign-format/stale summary →
  bound-missing → scan normally. Threshold staleness is safe (it only
  tightens); summary staleness is NOT — see maintenance below. Never use
  low-bit approximate scores as a drop rule (task non-goal).
- **Gate everything** behind a default-off GUC so the production surface is
  unchanged, and so the A/B is a clean gate-on/gate-off per the repo rule.

### Phase 4 maintenance invariants (required by AC 5 if any of this promotes)

Summaries are written at build/materialization and never maintained — inserts,
updates, and vacuum leave them stale. For the fixture experiment that is fine
(immutable corpus); for any promotion the format/version plan must state the
invariant. The conservative rule is cheap and sound: any mutation to a block
marks its summary invalid → bound-missing → no skip. Widening on insert is an
optimization, not a requirement. Write this down in the Phase 4 decision even
if the outcome is shelve.

## How to test it

- **Bound soundness (unit):** extend
  `collect_quantized_selected_leaf_threshold_profile_reports_safe_skips`
  (scan/tests/candidates.rs) with a property-style check: for every block, the
  summary upper bound ≥ the true best IP of every member row, across random
  vectors/seeds. This is the single most important test in the feature — an
  unsound bound is a silent recall bug.
- **Materialization summaries (unit):** mirror the existing
  `leaf.rs` v3/v4/v5 reader roundtrip tests for materialization-built objects:
  summaries present when GUC>0, absent when 0, correct counts/locators.
- **Identity/parity:** summaries-on vs control, early-stop OFF → result
  identity (layout-only change must not move results). Then early-stop ON vs
  OFF at matched sweep → recall parity + rows-scanned-avoided.
- **One variable per A/B.** Summaries-on is one gate; early-stop is a second
  gate; threshold seeding vs refresh a third. Never stack them in one
  measurement — attribution is the repo rule and the whole point of this task.
- **Streaming interplay:** reuse the packet-015 `--slow-candidate-node2-ms`
  skewed fixture to prove the threshold composes with candidate-to-heap
  streaming (fast workers' scores tighten the threshold that reaches the slow
  worker — this is where the win should physically come from).
- **Fault drills ON** for the implementation packet: cancellation,
  statement-timeout cleanup, no leaked remote sessions are explicit Phase 2/3
  requirements. `skip_fault_drills=true` is fine for boundability smokes only.
- **Scale:** 10k/50k/100k × `n128/b4` + `n1024/b2` via `ecaz bench suite`
  before any promote claim. `bench_queries_limit=20` is fine for boundability
  availability, not for recall/latency claims. Disk is at 93% (76G free) — the
  100k row died on disk before; clear space before starting it (024 seq-3
  condition 5).

## Code review of the uncommitted CLI diff

The `--session-guc` / `load_session_gucs` plumbing is well-shaped overall:
plan-JSON threading to remote loaders, suite-level validation, an expansion
test, and the `current_setting` read-back echo are all exactly right. Issues:

1. **Value-side injection asymmetry.** `validate_session_guc_list` (suite)
   rejects `;`, but the CLI's `parse_session_guc` validates only the *name* —
   the value is interpolated raw into `batch_execute(format!("SET {name} = {value}"))`,
   and `batch_execute` runs multiple statements. `--session-guc 'x=64; ...'`
   executes arbitrary SQL. Local dev tool, low stakes, but fix the asymmetry:
   reject `;` in the value or use `SET {name} TO <quoted-literal>`.
2. **Commit before citing.** The `-set` lane evidence was produced by an
   uncommitted working tree. Packet evidence must trace to a head SHA
   (NFR-007 / manifest rules), and any mid-run edits must be committed
   immediately (repo rule). Commit the three-file diff as its own slice now,
   and record the SHA in the packet manifest before the next run.
3. Side change worth a commit-message mention: the chunked load branch now
   also does `CREATE EXTENSION IF NOT EXISTS ecaz` — a behavior fix riding
   along with the GUC feature.
