# Reviewer Feedback: Packet 002 — Global Pre-Heap Merge Prototype (code)

Reviewed at branch `task-131-spire-streaming-global-topk`, code commit
`34272982a` plus the follow-ups it depends on. Focus: correctness of the new
merge-before-heap path and its new remote endpoint.

## Verdict

The implementation is correct and, importantly, **recall-safe by
construction**. The GUC gating, the empty-subset skip, and the hex transport
are all sound. Main gaps are test coverage of the new coordinator-side
reshaping logic and one redundant merge. Nothing here blocks the Phase 1
evidence, but the test gap should close before this path is a promotion
candidate.

## What's correct

- **Recall-safety argument holds.** `assign_global_heap_candidate_subsets`
  merges the compact candidate batches with
  `merge_validated_remote_search_candidate_batches(requested_epoch, batches,
  Some(top_k))`, dedupes by `vec_id`, keeps the global top-k, then requests
  heap rows only for each node's surviving subset. Because the coordinator
  already merges down to `top_k` after heap receive, and heap resolution only
  attaches block/offset to an already-scored candidate (it does not change
  score or set membership), a candidate pruned from the global top-k could
  never enter the final answer. So skipping its heap fetch cannot change the
  result set. The 10k–100k A/B (recall matched to 4 decimals in every cell)
  is consistent with this.
- **Node-identity contract is preserved.**
  `remote_search_explicit_local_heap_candidate_rows` stamps
  `node_id: meta::SPIRE_LOCAL_NODE_ID` on every rebuilt candidate, exactly like
  the existing `remote_search_local_heap_candidate_rows` path
  (`remote_search_coordinator_local_candidates_result` produces local-node
  candidates). The coordinator re-stamps `node_id` per dispatch on receipt, so
  forcing LOCAL on the worker is the right contract, not an identity bug.
- **Empty-subset skip** (`dispatch.rs`, the
  `matches!(global_heap_candidates.as_ref(), Some(c) if c.is_empty())` branch)
  correctly short-circuits to a synthetic READY result with
  `reusable_connection: Some(connection)` — the connection is untouched, so
  returning it to the pool is valid.
- **Defensive decoding** in the `#[pg_extern(stable, strict)]` function is
  thorough: per-field length checks against `served_epochs.len()`, negative /
  overflow guards on every integer column, and hex-decode failure surfaced as a
  clear `pgrx::error!`. `strict` + the pre-SQL empty skip means the endpoint is
  never invoked with empty arrays.

## Findings

1. **No unit coverage on the core new logic (should fix).** The only new test
   is `explicit_heap_candidate_parameters_encode_binary_fields_as_hex`, which
   covers the *encode* direction of the parameter builder. There is no test for
   `assign_global_heap_candidate_subsets` itself — the part that actually
   changes behavior:
   - partition of merged candidates by `node_id` and assignment back to the
     matching session;
   - the empty-batch early return (`batches.is_empty()`);
   - the empty-subset → skip-heap path;
   - the "first session with `Some(session)` supplies `requested_epoch` /
     `top_k`" selection.
   This is pure, PG-free logic operating on `SpireRemoteProductionCandidate
   SessionResult` vectors and is well within reach of the existing
   `production_executor_state_tests` harness (which already builds
   `SpireRemoteProductionTransportAdapter::run_heap_receive_requests`
   fixtures). Empirical recall parity is strong evidence, but per REVIEWER.md
   the new codec/reshaping path wants per-branch coverage before promotion.
   There is also no round-trip test of the *decode* side (hex → bytes on the
   worker); a small `hex::encode`→`hex::decode` assertion would lock the
   transport contract.

2. **Redundant global merge per query (minor perf / clarity).** With the GUC
   on, the global merge is computed twice per production read:
   - once in `assign_global_heap_candidate_subsets` (`dispatch.rs`), which sets
     `metrics.global_pre_heap_*` on `result.metrics`, and
   - again in `record_global_pre_heap_candidate_metrics`
     (`production_transport.rs:1131`), which **overwrites** the same fields with
     a fresh `merge_ready_candidate_batches(Some(top_k))`.

   The `metrics.add_transport_metrics(&result.metrics)` at
   `production_transport.rs:1004` folds the dispatch-computed counters in, and
   then line 1009 discards them by reassigning with `=`. Net effect: the
   authoritative reported counters come from the audit recompute, and the
   dispatch-side computation is dead for reporting purposes. The two merges
   produce the same numbers, so this is not a correctness bug, but it is an
   extra full candidate merge on the hot path. Consider having the dispatch
   path return the merge result (or its counts) up to the executor so the
   metric is recorded once, and drop the second merge. At minimum, a comment
   noting which of the two computations is authoritative would help the next
   reader.

3. **Audit merge is now unconditional overhead on both A/B arms (note, not a
   defect).** `record_global_pre_heap_candidate_metrics` runs on every pooled
   production read regardless of the GUC. That's fine for A/B fairness (both
   arms pay it) and matches the Phase 0 audit intent, but it is permanent
   per-query merge cost that ships even with the feature off. Acceptable given
   merges are cheap relative to heap receive; flagging so it's a conscious
   choice rather than an accident.

4. **Hex `text[]` transport doubles identifier bytes over libpq (accept).**
   `vec_id` / `row_locator` go over the wire as hex text arrays. For this
   no-payload path the identifiers are small and this sidesteps `bytea[]`
   escaping, so it's a reasonable trade. Worth a one-line rationale in the code
   or ADR if this endpoint outlives the diagnostic phase, since a binary
   encoding would halve that transport.

None of the above changes the Phase 1 conclusion; see packet 009 feedback for
the cross-cutting evidence read.
