# Reviewer Feedback: Packet 027 — Duplicate IDs in Returned Top-K (New Finding)

Mid-run finding from the identity artifacts, separate from the gate question.
**The distributed production read is returning the same corpus row multiple
times inside a single top-10 result, pervasively, in both arms.** This looks
like a pre-existing result-quality defect on the distributed surface that the
new identity harness has just made visible. It does not change the packet-027
seq-2 ruling, but it must be recorded and triaged as its own finding.

## Evidence

From the committed-format identity JSONL (`spire_result_identity` records,
which are the same `predicted_ids` recall is computed from — I traced
`ResultIdentityRecord::from_query` to `execute_query_metric`'s
`SELECT id FROM <corpus> ORDER BY embedding <#> $1 LIMIT $2`):

- 10k lane: **183 of 200 queries** contain duplicate ids in their top-10 —
  identically in BOTH arms — worst case 6 duplicates (only 4 distinct
  neighbors returned for k=10).
- 50k lane (in flight): **179 of 179** completed queries so far have
  duplicates. Example, query_ordinal 1:
  `[38468,38468,38468,43507,43507,43507,49535,49535,49537,49537]` — 10 rows,
  4 distinct ids.
- `id` is the corpus primary key (`*_corpus_pkey` exists), so duplicate ids =
  the same heap row emitted repeatedly by the scan, not a data property.

## Probable mechanism (to be confirmed, not assumed)

The fixture uses `boundary_replica_count=4` across 3 remote nodes. If replica
copies of the same row carry per-node/per-leaf `vec_id`s, a merge that dedupes
by `vec_id` will not collapse copies of the same row arriving from different
nodes → duplicate TIDs in the final top-k. Top-k results are disproportionately
boundary/hub rows, which fits the very high dup rate. Confirm against
`merge_duplicate_vec_id_sum` and one hand-run exact query; do not adopt my
mechanism without checking.

## Why this matters beyond this packet

- **recall@k is being flattered.** Recall reads 0.9985–1.0 while most results
  contain only 4–8 distinct neighbors. That is only arithmetically possible if
  the recall computation counts duplicate hits (per-position membership in the
  truth set). Every "matched recall" claim on this multi-instance surface —
  Tasks 123 and 131 packets included — measures less than it appears to: a
  user issuing k=10 gets fewer than 10 distinct neighbors.
- This is a **correctness/result-quality defect on the default distributed
  read surface**, discovered by instrumentation this task added. It outranks
  latency-tuning work in priority and is NOT a task-131 item to fix — do not
  expand this branch to fix it.

## Required actions

1. **File it as its own task** (plan/tasks/) with the identity JSONL evidence,
   the suspected replica-dedupe mechanism, and a note that the recall metric
   double-counts duplicate hits. Reference this packet.
2. **State it in the packet 027 readout and the revised closeout**: identity
   comparisons between arms remain valid (same behavior both arms, and the
   structural no-op conclusion is untouched), but "recall matched" language
   must be qualified: matched-with-duplicates, k-distinct not guaranteed.
3. Do not fix it on this branch; do not re-run the A/B for it.
