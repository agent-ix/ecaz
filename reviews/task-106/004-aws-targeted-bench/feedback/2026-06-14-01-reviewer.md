## Blockers to closing

2. **AC2 — multi-bit per-ISA routing not recorded.** ADR-077 §9 still says
   *"Remaining: cross-host benches (… Intel AVX2 … G4)"* and matrix §9 says
   *"AVX2 bench-pending."* The AWS runs supplied exactly that evidence (bits=2
   block engages neon+avx2; bits=4/8 arithmetic). The "per-ISA picture" is now
   complete and should be recorded as such — otherwise this cell also reads
   pending.

3. **Gap-2 skip rationale is thin / arguably wrong as stated.** request.md
   justifies the skip with *"widths … never >=32."* But the widths are
   **16-31 dominant (~79%), i.e. squarely in the kernel-viable range** — by the
   task's own criterion ("mostly ≥8/16 → batching is worth it") this would
   argue *implement*, not skip. The grouped-PQ block kernel in fact beats
   scalar **−3.8% to −10.4% on IVF** at high widths (matrix §2.6). So "never
   hits a full 32-block" is not by itself a sufficient skip basis.

   The skip is still likely **correct**, but for an HNSW-specific reason that
   must be the recorded basis: HNSW grouped-PQ scoring is a *small share* of
   query time (graph traversal dominates; ADR-077 §7.2 "graph AMs are
   width-bound"; M5 measured zero engagement), so even kernel-viable widths
   yield negligible e2e benefit. Record the skip on **kernel-share / §7.2 /
   M5-zero-engagement** grounds (histogram confirms widths are width-bound and
   never full-block), explicitly contrasted with the IVF win — not on "never
   ≥32" alone.

   Caveat to state honestly: the block kernel was never wired into HNSW
   traversal, so there is **no HNSW grouped-PQ e2e A/B** — the skip is a
   measured-histogram + prior-evidence judgment (which the task permits), not a
   measured e2e regression. Say so in the record.
