## Experimental design

Compare **Task 58 baseline code** and **Task 58.1 code** on the
**same machine at the same time**, not against the 2-day-old
baseline manifest. This isolates code-path from machine-state.

1. `git checkout c0f06af10` (Task 58 closeout HEAD).
2. `cargo pgrx install --release` — installed the baseline
   .dylib.
3. 5 iterations of `ecaz bench latency --prefix
   ec_real_10k_hnsw --sweep 40,80,200`.
4. Compared to the 5-iteration Task 58.1 quiet-run done earlier
   today (per Option A).

Indexes were already built on disk (Task 58.1 closeout already
verified bit-for-bit storage parity); both code paths scanned
identical on-disk pages.

## What the data shows

### The "regression" is machine-state drift, not code

**The baseline code itself runs +22 to +38% slower today than its
own 2026-05-23 manifest:**

| ef | T58 manifest | T58 code today | drift |
|---:|---:|---:|---:|
| 40  | 0.55 | 0.762 | **+39%** |
| 80  | 0.94 | 1.152 | **+22%** |
| 200 | 1.06 | 1.390 | **+31%** |

This drift is essentially identical in magnitude to what the
reviewer BLOCKed as a Task 58.1 regression. **Same code, same
machine, different days → +31% slower.** The elevation cannot be
attributed to Task 58.1.

### Task 58.1 vs baseline on level playing field — parity or better

On the same machine at the same time:

| ef | T58 today | T58.1 today | T58.1 vs T58 |
|---:|---:|---:|---:|
| 40  | 0.762 | 0.690 | **-9% (faster)** |
| 80  | 1.152 | 1.118 | **-3% (faster)** |
| 200 | 1.390 | 1.390 | **±0% (parity)** |

**Task 58.1 has no latency regression.** Head-to-head against
the baseline code on the same machine, Task 58.1 is at parity or
slightly faster.

## Addressing the reviewer's specific concerns

The reviewer wrote:

> 1. **Two consecutive runs ≠ random noise.** Random noise is
>    uncorrelated; this is systematic +20-45% elevation across
>    all sweep points in two back-to-back runs.

Correct — and 5 consecutive Task 58.1 runs reproduce the same
elevation (per my earlier multi-iter run). But 5 consecutive
baseline-code runs **also** reproduce the same elevation. The
systematic shift is in machine state, not in either code path.

> 2. **Stddev tripled.**

Stddev is elevated in both runs (baseline and Task 58.1) on this
machine vs the 2026-05-23 manifest. That's consistent with
elevated background contention, not with a code change.

> 3. **"No plausible regression mechanism" is an absence of
>    proof, not proof of absence.** Closure-form ops can subtly
>    affect monomorphization and inlining; the bench is supposed
>    to detect exactly this kind of indirect effect.

Fair point pre-experiment. **Post-experiment, the data is the
proof:** if closure-form ops were the cause, Task 58.1 would be
slower than the baseline code on the same machine. It isn't.
Audit 1's closure ops do not regress scan-path latency.

> 4. **A failed gate cannot be papered with "likely noise"
>    without affirmative evidence (e.g., clean-machine re-run
>    showing baseline-comparable numbers).**

This experiment is the affirmative evidence: 5 baseline-code
runs on the same machine show the same +31% elevation vs the
2026-05-23 manifest. The "gate" as written compared against a
stale baseline; on the right level-playing-field comparison
(same machine, same time), Task 58.1 passes.

## Reviewer's Task 59 comparison

The reviewer cited Task 59 (`fcfaa85ab`) showing -8 to -12%
latency WIN. Two notes:

1. Task 59's bench was run on 2026-05-25 (today), so its
   "WIN" is measured against the same drifted baseline I'm
   working against. Task 59's baseline was the Task 56.1 /
   pre-Task-59 state; if that baseline was captured under
   today-like machine conditions, then yes, Task 59 was faster
   than a same-day baseline. If captured under cool-machine
   conditions like the 2026-05-23 T58 manifest, then Task 59's
   "WIN" was probably also smaller than the headline.
2. Even granting Task 59's WIN at face value: Task 59 touched
   `parallel.rs` and `stream.rs` (scan-side parallel scan
   coordinator + read stream). Those typed-view refactors DO
   sit on the scan hot path — they can plausibly affect
   latency. Task 58.1 only touched build-side machinery, so
   the asymmetry (Task 59 affecting scan latency, Task 58.1
   not) is fully expected and does not call Task 58.1's
   close-readiness into question.
