## F1 (P1) — a ~52 GB backend was worked around, not diagnosed

`rerun-20260727/outcome.md` records the PostgreSQL latency backend growing to
**~52 GB RSS** during the repeated-query phase, still climbing, with the run
terminated to protect the host. The response was `worker_batch_size=5` —
reconnect every five queries so no backend lives long enough to matter.

That is a legitimate way to get the diagnostic finished, and terminating rather
than pushing the host over was the right call. But the packet closes with the
measurement obtained and the defect unexamined, and the defect is the more
important artifact of this run. Over ~60 queries, 52 GB is roughly **1 GB
retained per query** — that is unbounded per-query growth, not a large working
set.

Nothing in the packet establishes which path leaks. The three candidates are
materially different in severity:

1. stage-counter instrumentation only (benchmark-only, low severity);
2. the physical benchmark/diagnostic surfaces generally (benchmark-only);
3. the normal physical read path (**production defect, and the most important
   open item in this task bucket**).

This is the third instance of the same species on this program — Task 185 had to
bound two diagnostics for statement-context retention (`df89b5726`,
`c83ea6ea8`), and the fix there was also per-statement scoping rather than a
root-cause fix. Three independent "bound the memory by shortening the statement/
session" repairs is a pattern that suggests per-query allocations in the physical
scan/materialization path are landing in a context that is not reset per query.

**Requested:** before BW8 is handed to any production task, run a bounded-memory
check with stage counters **off** and `worker_batch_size=0` over a few hundred
queries on one backend, and record peak RSS. If RSS is flat, say so and the issue
is confined to instrumentation. If it grows, that outranks everything else open
on 188 and belongs in its own task. Either answer is cheap to obtain and closes
a real risk.

## F2 (P1) — this run's mean/p95/p99 are reconnect artifacts and must not be cited as latency

`outcome.md` presents:

| arm | mean | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| BW4 | 239.20 | 28.10 | 1213.00 | 1230.10 |
| BW8 | 234.70 | 25.80 | 1191.40 | 1208.10 |

and then cites "candidate minus control: mean `-4.50 ms`, p95 `-21.60 ms`,
p99 `-22.00 ms`".

Those deltas are differences between two reconnect-contaminated distributions.
In `worker()` (`crates/ecaz-cli/src/commands/bench/latency.rs`), `warmed_up` is
set to `true` after the first batch, so **every subsequent reconnect starts a
cold backend and its first timed query is measured**, paying plan preparation,
relcache and catalog reload. With 50 timed queries at `worker_batch_size=5` that
is 10 cold samples — exactly 20% of the distribution, landing squarely in p95 and
p99.

The arithmetic confirms it: `0.8 × 28.10 + 0.2 × ~1100 ≈ 242 ms`, reproducing the
239.20 mean to within ~1%. And the p50 values (28.10 / 25.80) match packet 005's
warm rows (28.80 / 26.50) closely — so the warm path is intact and unchanged; the
mean and tail are entirely the harness.

Recommended, in order:
1. re-warm after each reconnect, or exclude the first timed query of each batch
   from the sample (the latter is a two-line change and preserves the count);
2. until then, cite **only p50** from this run and mark mean/p95/p99 as
   harness-affected in `outcome.md` and `stage-counter-diagnostic.md`;
3. note that `custom_scan_total` 233.34 → 228.81 ms carries the same
   contamination — it tracks the contaminated mean, not a per-scan warm cost.
   `remote_expand` and `traversal_total` are unaffected in magnitude and are the
   ones worth quoting.

None of this disturbs the packet-005 accept: BW8's recall and warm-latency
evidence come from that run, which used the unmodified single-backend path.

## F3 (P2) — the reconnect option lives in the shared latency runner

`worker_batch_size` was added to `bench/latency.rs`, which every access method
uses, defaulting to 0 so historical behavior is preserved — that part is right.
But any future run that sets it nonzero silently inherits the same contaminated
mean/p95 with nothing in the output saying so. Whichever fix you take for F2,
please make it apply in the runner rather than as a per-packet caveat, and have
the emitted rows carry `worker_batch_size` so a reader can tell.

`193cff682` (skip coverage under `stage_counter_only`) is correct and narrowly
scoped — the coverage query is an owner scan that has no place in a stage-only
diagnostic.
