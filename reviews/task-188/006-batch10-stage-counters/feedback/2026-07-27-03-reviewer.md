## Must fix before merge

### M1 — equivalence check for the shared latency-worker refactor (blocking)

`555fdd1bb` restructured 291 lines of `crates/ecaz-cli/src/commands/bench/latency.rs`
— the `worker()` loop that **every access method's latency benchmark runs
through**, including every suite `latency` step for HNSW, IVF, DiskANN and SPIRE.
The claim is that `worker_batch_size=0` preserves historical behavior. Reading it,
that looks right: batch size collapses to `iterations`, so one client, one
prepared statement, one pass. But it is asserted, not demonstrated, and the
existing `mod tests` at line 870 are pure-function tests — none exercise the async
worker.

If the restructure shifts results even slightly at the default, every future
latency number across every AM moves with it and there is no baseline left to
notice against. Please run one config at the pre-refactor commit and at
`193cff682`, `worker_batch_size` unset, and show the numbers agree within noise.
Any single existing lane config is fine; this does not need the standard sweep.

### M2 — re-warm after each reconnect (blocking)

In `worker()`, `warmed_up` latches `true` after the first batch, so every
subsequent reconnect starts a cold backend whose **first timed query is
measured**, paying plan preparation and relcache/catalog reload. At
`worker_batch_size=5` over 50 iterations that is 10 cold samples — 20% of the
distribution, landing squarely in p95/p99.

Fix in both implementations — `bench/latency.rs` and the distann
`benchmark_backend_batch_size` path in `dev/distann_multicluster.rs`. Either
re-run the warmup after each reconnect, or exclude each batch's first timed
sample (two lines, and it preserves the sample count semantics you already
report).

### M3 — emit the batch size on result rows (blocking, cheap)

Neither `worker_batch_size` nor `benchmark_backend_batch_size` appears in any
emitted row. A reader cannot tell a reconnect-affected run from a clean one.

The precedent is right there and it worked: `materialization_batch_size` is
emitted on every physical row, and that is exactly what let me catch the eager-0
