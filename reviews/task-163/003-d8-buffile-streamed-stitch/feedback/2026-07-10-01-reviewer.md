## Verdicts on the request's five verification asks

1. **No shard output reachable at stitch start — PASS.** `ShardSpill` holds
   only `{io, entry_count}`; `append_shard` consumes each `ShardGraph` by
   value and encodes incrementally; `stitch_shard_spool` receives spills via
   `std::mem::take`. No hidden clones or captures. (But see P2-1: the *build
   phase* still batches complete shard graphs.)
2. **Header-only lookahead, exactly-once sequential reads — PASS.**
   `ShardEntryHeader` is a `Copy { node: u32, neighbor_count: usize }` and is
   structurally incapable of holding a payload. `consume()` reads each
   adjacency exactly once, strictly sequentially, and only when its node is
   the current minimum group (cross-checked via the `entry_node != node`
   guard). The little-endian round-trip is endian-correct.
3. **Accounting completeness — PARTIAL PASS.** BufFile block buffers
   (`shard_count × BLCKSZ`), cursor and heap capacities, passthrough/union
   capacities, and the union+candidates+R prune footprint are all counted;
   output graph and source vectors are correctly excluded. Gaps: P2-2
   (`assignment.members` retained and unaccounted), and small P3 undercounts
   (BufFile struct overhead beyond BLCKSZ; the transient moment where the
   consumed `neighbors` Vec and the union are both live).
4. **Deterministic output preservation — PASS, verified line-by-line.**
   Multi-membership: the heap pops equal-node entries in ascending shard
   order; `sort_unstable` + `dedup` over the collected union reproduces the
   old `BTreeSet` ascending iteration exactly; `robust_prune` re-sorts by
   `(distance, node)` with a deterministic tie-break, so outputs are
   byte-identical. Single-membership passthrough order is preserved exactly.
   Two deliberate deviations, both strictly better: a node in zero shards is
   now a hard coverage-gap error instead of a silent empty adjacency, and
   `stitch_peak_union_len` now reflects multi-membership nodes only (see
   P3-6). Note `tc038_determinism` compares new-vs-new; the old-vs-new
   equivalence rests on this code-level argument, which this review checked
   and endorses.
5. **cfg split cannot leak the test transport — PASS.** The split is pure
   `#[cfg(test)]`/`#[cfg(not(test))]` with no feature involvement; the
   installed `.so` is built by a normal `cargo build --lib` (confirmed in
   `cargo-pgrx-test-sharded-build.log`), where `cfg(test)` is off, so the
   pg_tests exercised the real BufFile transport.

Artifact verification: all cited log lines check out verbatim (10/10 pure

## P2 findings (close before Task 163 closeout / D8 "done" claims)

- **P2-1 — Build-phase peak still holds all shard graphs at once when
  `rayon_threads >= shard_count`** (`shard_build.rs:612-632`).
  `build_shard_spool` collects a whole batch of
  `batch_width = min(threads, shard_count)` complete `ShardGraph`s before
  spilling any. Shard count is capped at 16 and the Intel bench host has ≥16
  threads, so in the realistic configuration the process high-water mark is
  unchanged — the spill only shortens the peak's duration and moves it before
  the stitch. `stitch_peak_retained_bytes` is honest for the stitch phase but
  will be misread as the build's memory high-water mark. Fix direction:
  encode each shard to bytes inside the rayon worker (pure Rust) and have the
  main thread `BufFileWrite` completions as they finish (ordered channel), or
  spill within the batch as each shard completes. At minimum, the NOTICE/
  manifest should also report the build-phase batch peak so the numbers can't
  be over-claimed.
- **P2-2 — `assignment.members` is retained across the stitch and
  unaccounted** (`shard_build.rs:485-501`). The full membership lists
  (~`duplication_factor × N × 4` bytes — several MB at 1M nodes) live until
  after `stitch_shard_spool` returns, only to serve two scalar stats. Copy
  the scalars out and drop the assignment before the stitch, or include it in
  the accounting.
- **P2-3 — The D8 memory benefit is unmeasured, and the BufFile transport is
  only exercised at 8-row scale.** No artifact captures the new NOTICE fields
  from any real build (not even the pgrx fixture), and there is no peak-RSS
  or before/after A/B at 10k/50k/100k. `tc038_d8_spill_and_cursor_bound`
  validates the accounting arithmetic against the in-memory stand-in, where
  the "spill" is itself resident, so the `retained < spill_bytes` assertion
  holds only in the model. The pg_tests drive BufFile over a spool of a few
  dozen bytes: one block, no block-boundary crossing, no short-read loop
  exercise. Required before closeout per the repo measurement rule: (a) a
  pg_test with a multi-block spool (a few hundred rows, `build_shards >= 2`),
  and (b) captured build NOTICE lines (and ideally peak-RSS A/B) at
  10k/50k/100k, plus a graph-digest or recall A/B at 10k old-vs-new to make
  the "existing Task 163 recall evidence carries forward" claim a fact
  rather than an inference. This packet is honest that closeout gates remain
  open, so these are conditions, not misrepresentations.
- **P2-4 — No interrupt checks in the stitch or shard-build loops.** Zero
  `check_for_interrupts!` hits under `ec_distann/`; a 1M-node sharded build
  is minutes of uncancellable CPU. Pre-existing gap, but the new per-group
  merge loop is the natural place for one.

## P3 findings

- **P3-1** — All five claimed spool validations (coverage gap, out-of-range
  node/neighbor, over-degree, unsorted stream, unconsumed tail) are enforced
  in code, but none has a negative-path test. With the test transport in
  place these are five cheap corrupt-spool tests.
- **P3-2** — `ShardSpoolIo::drop` calls `BufFileClose` during panic unwind
  (e.g. `temp_file_limit` ereport → pgrx panic); a nested ereport there is
  panic-in-drop → backend abort. A `std::thread::panicking()` guard (skip
  close; the resource owner cleans up on abort) is strictly safer.
- **P3-3** — Per-entry allocations in hot paths: fresh `encoded_neighbors`
  per node on the write side, fresh `neighbors` Vec per consume on the read
  side. Reusable scratch buffers are free wins.
- **P3-4** — `retained_cursor_bytes` uses unchecked arithmetic while the rest
  of the file is checked; `stats.shard_output_spill_bytes` is assigned twice
  (stitch, then overwritten identically by the caller); BufFile struct
  overhead beyond BLCKSZ uncounted.
- **P3-5** — Hardcoded `whence = 0` in `rewind`; a named SEEK_SET constant
  would self-document.
- **P3-6** — `stitch_peak_union_len` semantics changed (multi-membership
  only); any trend series across this change is discontinuous. Doc is
  consistent with the new meaning; noting for manifest readers.
- **P3-7** — `assign_shards` computes the distance of every node to every
  centroid twice (once for `best`, once for the band test). A
  `shard_count`-sized scratch of distances halves that; minor at ≤16
  centroids.
- **P3-8** — Clippy artifact doesn't capture its command line and a clean run
  is indistinguishable from `cargo check`; echo the command into future
  captures. Manifest timestamps predate two of the artifacts they describe
  (cosmetic).

## Disposition

reads are exactly-once sequential, validation is strict, and the output graph
is provably byte-identical to the pre-change implementation. Task 179 may
build on this checkpoint. Task 163 closeout still requires the P2-3
measurements, and the P2-1 build-phase batching should be fixed (or at least
honestly reported) before any D8 memory claim is cited in a manifest.
