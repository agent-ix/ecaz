## New findings (P3)

- **P3-1 — Worst-case build-phase peak is still ~all shards' encodings
  when `threads >= shard_count`, and it remains unreported.** With
  `worker_count = min(threads, shard_count)`, channel capacity equals
  shard_count in the realistic Intel-host regime, so near-simultaneous
  completions can queue every flat encoding at once — same O as the old
  batch, though a genuinely smaller constant (flat stream vs nested
  Vec-of-Vecs) and a much shorter window (eager drain). The packet-003
  fallback ask — report the build-phase peak — was not taken: the
  NOTICE has no build-phase field. Track a queue-depth high-water ×
  encoded-size estimate in the drain loop and add one NOTICE field
  (and/or drop capacity to ~2); fold the empirical answer into the
  still-open RSS measurement gate.
- **P3-2 — Statement-cancel latency during the parallel phase is up to
  one full shard build.** The backend is interrupt-responsive (50 ms
  poll), but the cancel only reaches workers via a failed `send` after

  join blocks the unwind until then — minutes at 1M scale. Not a
  regression versus the old rayon batch, hence P3: add an
  `Arc<AtomicBool>` cancel flag set before propagating, polled between
  Vamana epochs in the worker loop.
