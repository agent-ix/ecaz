# Task 163 signoff review

No signoff yet. The sharded path is directionally good and the packets contain useful A/B evidence, but a few FR-077 closeout requirements are not yet verifiable from the current implementation and packet artifacts.

## Findings

### P2 - D8 / CON-4 peak-memory evidence does not match the implementation

FR-077-CON-4 requires stitch memory to stay within ADR-085 D8's "streamed by vec_id group" bound: peak <= one vec_id group plus prune working set (`spec/functional/index/distann/FR-077-distann-sharded-build-and-stitch.md:80`, `spec/adr/ADR-085-ec-distann-single-global-graph.md:121`). The packet claims `stitch_peak_union_len` is the peak-memory evidence (`reviews/task-163/001-m1-stitch-ab/artifacts/manifest.md:119` and `reviews/task-163/002-m1-closure-sweep/artifacts/manifest.md:106`).

The code still materializes every shard's global node list and every shard adjacency list in memory before stitching:

- `src/am/ec_distann/shard_build.rs:89` defines `ShardGraph { nodes: Vec<u32>, neighbors: Vec<Vec<u32>> }`.
- `src/am/ec_distann/shard_build.rs:148` builds `let shard_graphs = build_shard_graphs(...)`.
- `src/am/ec_distann/shard_build.rs:158` passes the full `&shard_graphs` slice into the stitch pass.
- `src/am/ec_distann/shard_build.rs:255` returns `Vec<ShardGraph>` and `src/am/ec_distann/shard_build.rs:270` collects all shard outputs.

The merge loop itself only holds one node's union at a time, but the retained shard outputs are part of the stitch working set under D8. `stitch_peak_union_len` therefore underreports peak memory and does not prove CON-4. Either stream/spill sorted shard outputs and stitch from cursors over those streams, or change the requirement/evidence to report actual retained shard-output memory plus the union/prune working set.

### P2 - Reachability repair can violate the degree bound and then fail staging

FR-077-CON-1 requires post-stitch out-degree not to exceed `graph_degree` for any node (`spec/functional/index/distann/FR-077-distann-sharded-build-and-stitch.md:77`). `repair_reachability` says it preserves the degree bound (`src/am/ec_distann/shard_build.rs:433`), but its degenerate branch explicitly appends past `graph_degree` when every existing edge is protected:

- `src/am/ec_distann/shard_build.rs:510` says "Still guarantee reachability by exceeding R by one here".
- `src/am/ec_distann/shard_build.rs:514` performs `graph.neighbors[src as usize].push(node)`.

That is not just a spec mismatch. `flush_build_state` rejects any graph with `neighbors.len() > graph_degree` before staging records (`src/am/ec_distann/ambuild.rs:470`). So a repair path that claims to recover reachability can still turn a valid build into an error after the expensive build has completed. The fix should preserve both CON-1 and CON-3: select another reached source, re-prune while protecting required repair reachability, or otherwise make the repair algorithm bounded by `R`, then add a targeted regression for the degenerate case.

### P3 - Packet 002 overstates the 50k epsilon parity result

The 100k epsilon=0.3 result supports the proposed FR-077-AC-1 interpretation for the operational band: at ef>=64 the stitched arm is above monolithic (`reviews/task-163/002-m1-closure-sweep/artifacts/manifest.md:52`). But the packet text says stitched "matches or exceeds" monolithic across the operational recall band at both 50k and 100k (`reviews/task-163/002-m1-closure-sweep/request.md:35`).

At 50k, epsilon=0.3 is below monolithic at ef=64: `0.9795` vs `0.9840`, delta `-0.0045` (`reviews/task-163/002-m1-closure-sweep/artifacts/manifest.md:46`). Please tighten the closeout wording so the 50k result is not described as "matches or exceeds" unless ef=64 is explicitly excluded from the operational band.
