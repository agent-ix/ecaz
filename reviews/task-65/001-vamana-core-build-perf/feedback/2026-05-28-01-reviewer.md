### Slice B — growing-α `robust_prune` ✅ clean (minor perf nit)

`src/am/ec_diskann/vamana.rs:372-410`. The two-pass outer loop is
gone; growing-α lives inside `robust_prune`:

```rust
let mut alpha = 1.0f32;
loop {
    let best = robust_prune_at_alpha(&candidates, alpha, max_degree, &dist);
    if best.len() >= max_degree || alpha >= max_alpha {
        return best;
    }
    alpha = (alpha * 1.2).min(max_alpha);
}
```

This matches pgvectorscale's pattern (`graph/mod.rs:413-484`) in
shape and termination condition.

**Minor perf nit (not blocking):** each α step calls
`robust_prune_at_alpha` over the FULL candidates set from scratch,
discarding the previous α's result. Pruning at higher α is strictly
more permissive than at lower α, so the lower-α result is a subset
of the higher-α one — the recomputation is mostly redundant. A
single forward pass that *relaxes* dropped candidates back in as α
grows would halve the prune work in the multi-α path. Given the
overall 8.4× speedup already achieved, this is a follow-up nit, not
a slice gate.

`pass1_extra_candidates` still wired into the new single-pass
driver via `append_candidates_for_prune` (vamana.rs:621-633). The
gate on `pass_index == 0` was removed, so extras now apply to every
pivot — that matches the new single-pass shape but means the HNSW
warm-start consumer (if any) gets a slightly different candidate
pool than before. Worth a one-line note in `build_vamana_graph_with_pass1_extra_candidates`'s
docstring; not a blocker.

### Slice D — bounded min-heap frontier ✅ clean (better than spec)

Commit `da2807c0e` is a real improvement over the spec'd
`BinaryHeap<Reverse<Candidate>>` design. The implementation now
uses **two heaps**:

- `unexpanded: BinaryHeap<Reverse<Candidate>>` — min-heap for
  popping the next expansion target. Lazy deletion via the
  `in_frontier` bitset on pop.
- `retained: BinaryHeap<Candidate>` — max-heap for tracking the
  L-best frontier so far. Worst-element peek/pop is O(log L) on
  overflow.

The previous design (commit `351987249`) had a residual
`scratch.frontier.sort_unstable()` on every overflow — the bounded
max-heap eliminates that. Cleanly thought through.

**Minor nit:** the final `frontier` Vec is rebuilt by iterating
`scratch.retained` and filtering by `in_frontier.contains(...)`
(vamana.rs:347-352). Since `push_frontier_candidate` removes a
node's `in_frontier` bit at the same time it evicts the node from
`retained`, the filter should be no-op. If that's load-bearing
defensive code, fine; if not, simplify with a debug_assert.

**Minor nit:** `GreedySearchResult { frontier, visited:
scratch.visited_order.clone() }` (vamana.rs:354) clones
`visited_order`. The build path passes `result.visited` into
`candidate_pool_for_prune` and never reads `result.frontier` —
those clones are pure waste in the build hot path. Consider
`std::mem::take(&mut scratch.visited_order)` and accepting a
re-allocation on the next call (or restructure the API to expose
borrowed slices). Not blocking; perf followup.

## Blocking issues

### B1 — `tuple_is_alive` skip in build callback is incorrect

Commit `4bd460081`, `ambuild.rs:218-228`:

```rust
unsafe extern "C-unwind" fn ec_diskann_build_callback(
    _index: pg_sys::Relation,
    tid: pg_sys::ItemPointer,
    values: *mut pg_sys::Datum,
    isnull: *mut bool,
    tuple_is_alive: bool,
    state: *mut c_void,
) {
    pg_am_callback!({
        if !tuple_is_alive {
            return;
        }
        ...
```

This is wrong for concurrent index builds and is inconsistent with
every other AM in this codebase. Evidence:

- `src/am/ec_hnsw/build.rs:110`, `src/am/ec_hnsw/build_parallel.rs:2671`,
  `src/am/ec_ivf/build.rs:103`, `src/am/ec_spire/build/tuples.rs:266` —
  all ignore the parameter with `_tuple_is_alive`.
- pgvectorscale's three callbacks at
  `pgvectorscale/src/access_method/build.rs:968,984,1012` also
  ignore it.

Why the param exists: during `CREATE INDEX CONCURRENTLY`, PG calls
the build callback for tuples that are HEAPTUPLE_RECENTLY_DEAD —
dead under the current snapshot but still visible to older
snapshots that may execute queries against the new index. These
tuples MUST be indexed; otherwise queries from those older
snapshots will see inconsistent results. PG sets `tuple_is_alive =
false` for these so that the AM can skip steps that are only valid
for live tuples (e.g. uniqueness checks, deferred constraint
recording), not skip indexing entirely.

Skipping the tuple entirely creates a sliently corrupt index under
`CREATE INDEX CONCURRENTLY` on a hot table. Per memory
`feedback_dont_defer_safety_fixes`, this must block close.

**Fix:** remove the `if !tuple_is_alive { return; }` guard. Restore
`_tuple_is_alive: bool` (matching the other AMs).

If the commit was trying to fix a real test failure, that failure
needs a different fix — describe the symptom in the next packet
and I'll help diagnose.

### B2 — `scanned_tuples` invariant relies on the now-broken assumption

`ambuild.rs:208-213` asserts:

```rust
if heap_tuples != state.scanned_tuples as f64 {
    pgrx::error!(
        "ec_diskann ambuild scanned {heap_tuples} heap tuples but observed {}",
        state.scanned_tuples
    );
}
```

When B1 is fixed and the callback stops short-circuiting, this is
fine. As currently written (B1 in place), any
HEAPTUPLE_RECENTLY_DEAD tuple in a CIC build will increment PG's
`heap_tuples` count without incrementing
`state.scanned_tuples` — and the assertion `pgrx::error!`s the
build. So today's behaviour silently corrupts the index on
non-concurrent builds AND noisily fails CIC builds. Fixing B1
fixes B2.
