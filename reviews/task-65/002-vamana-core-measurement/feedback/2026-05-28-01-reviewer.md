### Synth-10k ⚠ L=200 violates the 0.5pp gate

| L | this packet | Task 29 envelope (same L) | Δ |
|---:|---:|---:|---:|
| 64 | 0.1605 | 0.1650 | −0.45 pp |
| 128 | 0.2105 | (not reported) | — |
| 200 | 0.2500 | 0.2665 | **−1.65 pp** |

The L=200 regression of 1.65 pp exceeds the Task 65 spec's
behavioural gate ("Recall must hold within 0.5 percentage points of
current numbers"). Packet 002 acknowledges this explicitly (lines
38-41), which is the right move per memory `feedback_dont_overclaim_done`
— but acknowledgement is not a fix.

Two paths to close this:

1. **Find and fix the regression.** Likely causes worth probing
   first:
   - The growing-α `robust_prune` recomputes from scratch at each
     α step rather than relaxing. At small N the multi-α path may
     produce a *different* selection than the old two-pass driver
     for borderline candidates, which can shift recall on a small
     synthetic.
   - The `pass1_extra_candidates` extras now apply on every pivot
     in the single-pass driver (they were gated on `pass_index ==
     0` before). If the warm-start path is being exercised here
     and the extras list isn't empty, that's a behaviour change.
     The synth-10k fixture may exercise this; please confirm.
   - Random permutation derived from the same seed in a
     single-pass world produces a different node ordering than
     the two-pass world — a small recall delta from re-ordering
     is expected, but 1.65pp at L=200 is on the high side.
2. **Formally relax the gate** for synth-10k with rationale. The
   packet's argument that synth-10k is a "smoke" fixture in a
   known-low-recall envelope (0.16-0.33) is reasonable in
   isolation — at those absolute levels, 1.65pp is well within
   noise. But the task spec's 0.5pp gate didn't carve out
   synth-10k, so this requires an explicit Task 65 spec amendment
   or reviewer sign-off, not a packet-side waiver. Per memory
   `feedback_no_premature_task_close`, the reviewer does not
   override plans. Either revise the plan or fix the number.

Please pick one path and document the decision in the next packet.

## Memory / allocation evidence ⚠ substitute, not direct

The packet ships `artifacts/hot-loop-static-audit.md` instead of
heaptrack / dhat output because both were unavailable on the host.
That is acceptable as a substitute per CLAUDE.md
"`artifacts/manifest.md` should record... command used", but the
task spec specifically requested heaptrack/dhat evidence as the
memory gate. Static code audit is necessary but not sufficient: it
can confirm no `vec![false; n]` *source code* in the hot loop, but
cannot confirm no *runtime* allocations from indirect call paths
(rayon's worker setup, codec encode internals, etc.).

Recommendation, not blocking: in the next checkpoint, run a single
release-mode `dhat` or `heaptrack` measurement on a host where
they're available (Linux CI runner if local macOS keeps blocking)
and attach the rolled-up summary to a follow-on packet. The static
audit can stay; treat dhat as confirmation.

## Carried-over blocker from packet 001

**B1 from packet 001:** `tuple_is_alive` skip in
`ec_diskann_build_callback` is incorrect for concurrent index
builds and is inconsistent with every other AM in this codebase
(HNSW, IVF, SPIRE all use `_tuple_is_alive`). pgvectorscale does
the same. See packet 001 feedback for full diagnosis.

This blocker affects packet 002's standing for two reasons:
1. The measurement runs were performed against a build that
   contains this bug. The 8.44 s number is unaffected (no dead
   tuples in a fresh build), but a CIC re-validation would either
   silently corrupt the index or trip the `scanned_tuples`
   assertion. The measurement does not exercise that path.
2. The "Build callback skips dead tuples" behaviour was introduced
   in the same window as the recall measurements. If any tuples
   in the recall fixtures had `tuple_is_alive = false` (unlikely
   on a fresh COPY but worth a one-line check), the recall numbers
   would understate node coverage. Probably not the cause of the
   synth-10k regression, but worth verifying when B1 is fixed.
