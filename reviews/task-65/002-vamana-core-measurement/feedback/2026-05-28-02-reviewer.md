## B1 — visibility skip: ✅ resolved by `a8b0b8789` + loader fix

The fix has two parts and the bundling is correct:

1. **DiskANN side** (`ambuild.rs:218-228`): clean revert. The
   `if !tuple_is_alive { return; }` guard is gone. Parameter
   renamed to `_tuple_is_alive` to match every other AM
   (`src/am/ec_hnsw/build*.rs`, `src/am/ec_ivf/build.rs`,
   `src/am/ec_spire/build/tuples.rs`) and pgvectorscale. Matches
   the recommended fix in packet 001 feedback exactly.
2. **Loader side** (`crates/ecaz-cli/src/commands/corpus/load.rs`):
   the corpus loader now stages rows into a temp
   `ecaz_corpus_stage` table, then issues an `INSERT ... SELECT
   encode_to_ecvector(...)` so the final `ecvector` column is
   `NOT NULL` from the moment the row becomes visible. The old
   `COPY → UPDATE` pattern produced a brief visibility window
   where `embedding IS NULL`, which the previous tuple_is_alive
   skip was masking. Fixing the root cause is the right move and
   removes any future need for the band-aid.

The fixed-loader total (24.95 s end-to-end vs ~9 s previously) is
slower because the staging-table pattern moves encode + copy into
a single transactional INSERT instead of a streamed UPDATE. That
is a deliberate correctness trade and is explicitly called out in
the packet (lines 27-30). Acceptable.

### Synth-10k: ⚠ → ✅ — point estimate diverges but is **statistically null**

This is the change from the prior review. The new packet adds
L=800 plus the recall_ci95 columns. Reading
`recall-synth10k-…-l64-200-800.log`:

| L | Task 65 recall@10 | Task 65 95% CI | Task 29 baseline | baseline inside CI? |
|---:|---:|---|---:|---|
| 64 | 0.1605 | [0.1451, 0.1772] | 0.1650 | **yes** |
| 200 | 0.2500 | [0.2315, 0.2694] | 0.2665 | **yes** |
| 800 | 0.3315 | [0.3112, 0.3524] | 0.3260 | **yes** (slightly higher) |

At all three list sizes, the Task 29 envelope value falls inside
the Task 65 measurement's 95% CI. The L=200 "−1.65pp regression"
flagged in the prior review is a point-estimate artifact of the
200-query / 2000-trial sample, not a real recall drop. At L=800
the Task 65 number is actually *above* the Task 29 baseline.

This changes my prior call. The task spec's 0.5pp gate was
written as if the baseline were a noise-free target; on a 10k
synthetic with 200 queries the 95% CI half-width is already
±1.7pp at L=200. The 0.5pp threshold is tighter than the
measurement precision, so any measurement on this fixture is
guaranteed to fail or pass on noise alone.

**Reviewer call:** the synth-10k behavioural gate should be
considered met, and the task spec amended (or the packet annotated)
to phrase the synth-10k gate as "Task 29 envelope inside Task 65
95% CI" rather than "within 0.5pp point estimate". I recommend
the user accept this re-interpretation and close.
