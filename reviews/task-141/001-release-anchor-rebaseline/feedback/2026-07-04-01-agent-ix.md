## Finding 1 (HIGH) — `debug_install` auto-bypasses the runtime guard

`run_local_multinode_bench_suite(..., allow_debug_backend = args.debug_install)`
passes `--allow-debug-backend` to the nested suite whenever `debug_install` is
set (`spire_multicluster.rs`, nested-suite command build). So a single
`"debug_install": true` in a suite config silently disables the latency guard
for that fixture's entire nested suite, and the resulting `spire-pipeline`
latency rows in `results.jsonl` are byte-indistinguishable from release rows —
the taint survives only in `suite-manifest.json`. That separation of the number
from its provenance is precisely what produced the original Task 139
contamination. The spec sanctions a *labeled* escape hatch, not an
auto-coupled one.

Recommend: (a) stamp `build_profile` into every latency-emitting row in
`results.jsonl` (not only the manifest), so no latency number is readable
without its profile; and/or (b) require an explicit second opt-in rather than
deriving `--allow-debug-backend` from `debug_install`. This directly serves the
spec's "no stale number survives unexplained."

## Finding 2 (HIGH) — anchor captures remote transport phases only; no coordinator/routing phase or end-to-end p50

In all three cells (`release-50k-n128-b0-r2`, `release-50k-n1024-b0-r2`,
`release-100k-n1024-b0-r2`) the `production-read` rows in `results.jsonl` carry
only `phase ∈ {candidate_receive, heap_receive}` on `node_id ∈ {2,3,4}`. There
is no coordinator (`node_id 1`) row and no routing/merge/plan-walk phase, and
no end-to-end query p50. Max-phase p50 lands at 18–28 ms (50k n128), 18–20 ms
(50k n1024), 18–21 ms (100k n1024).

Two problems:
1. **Implausible headline.** ~21 ms at 100k is ~7× *below* the single-instance
   release SPIRE baseline the spec calibrates against (100k 0.9975 @ 147 ms).
   A distributed query is a superset of that work (routing + fan-out + merge on
   top of per-node scan); it cannot be 7× faster. These per-remote transport
   phases are therefore not the query p50 and must not be read as the anchor.
2. **Misses the Task 142 target.** The spec asks the distortion be decomposed
   "routing vs scan vs transport," and Task 142's entire premise is the
   coordinator O(nlists) routing tax (the ~41/137/269 ms plan-walk gap). If the
   anchor never captures the coordinator routing phase, it both understates
   distributed latency and omits the one phase 142 exists to fix — 142 would
   have no honest before/after to measure against.

Action: surface the coordinator-side routing/merge timing and an end-to-end
query p50 into the packet readout (confirm whether it already exists in
`suite-run.log` or a `latency`-kind step and just isn't in `results.jsonl`). A
distortion-factor table without the routing phase isn't decision-grade.

## Finding 3 (MEDIUM) — 1 ms timer quantization is coarse for the release regime

Every `elapsed_p50/p95/p99` and `payload_decode_p*` value is a whole
millisecond (`21.000`, `5.000`, `0.000`). At release-build latencies this is
~5–10% of signal for the transport phases and 100% quantization noise for
payload_decode. Task 142–145 chase single-digit-ms mechanism deltas; a 1 ms
timer will not resolve them. Flagging now because it affects the whole program,
not just this packet: consider microsecond resolution on the pipeline timers
before 142 measures against this anchor.

## Finding 4 (MEDIUM) — new safety property is untested

`release_guarded_step_kinds_include_latency_emitting_steps` and
`release_guard_checks_selected_pending_spire_pipeline_steps` cover kind
classification and step *detection*, but the actual new guarantee — the
per-node loop bailing when `backend_nodes[i].build_profile != "release"` — has
no unit test, nor does the `discover_postgres_socket_ports` empty-`socket_dir`
→ coordinator-only fallback. Add: (a) a debug node in `backend_nodes` triggers
the bail; (b) empty socket dir degrades to coordinator-only (documenting that
the multinode guard silently no-ops if `socket_dir` is unset — see Finding 5).

## Finding 5 (MEDIUM) — multinode guard depends on `socket_dir` discovery

`preflight_backend_nodes()` finds node ports by scanning
`socket_dir/.s.PGSQL.<port>.lock`, where `socket_dir` comes from
`config.defaults.socket_dir` or `conn.host`. If unset/misconfigured, `ports` is
empty and it falls back to a single coordinator preflight — the multinode guard
AC1 rests on becomes a no-op with no warning. Log when the fallback is taken,
or fail closed for any suite that declares a `spire-local-multinode` step.
