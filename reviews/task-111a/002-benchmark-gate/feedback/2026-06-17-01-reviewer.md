# Feedback: Task 111a — Aligned LE Typed-View Fast Path (analysis + recommendation)

**Origin:** design proposal raised in another agent's session (relayed by the
operator). This file is my reviewer analysis of whether it is sound, rewritten
as actionable feedback for the coder. Recorded against packet 002 because the
dense-block format, the zero-copy/endianness question, and the Approach B
decision all converge here.

## Bottom line

The proposal is **technically sound** and worth pursuing as a Task 111a slice,
with three caveats the original framing understates: (1) it is a **durable
dense-format change**, not just a codec tweak; (2) its alignment guarantee is
absolute, not offset-relative, so the runtime check is mandatory; and (3) on the
**adopted coalescing path it is not zero-copy** — the big zero-copy win actually
lands on the per-block (RaBitQ) path, which reframes where it pays off.

## The proposal

Keep the durable dense format little-endian, but add a zero-copy typed view of
the numeric arrays guarded by `cfg!(target_endian = "little")` + an alignment
check, falling back to `from_le_bytes` otherwise:

```rust
fn gammas_view(&self) -> Option<&[f32]> {
    let p = self.gamma_bytes.as_ptr().cast::<f32>();
    (cfg!(target_endian = "little") && p.is_aligned()).then(|| unsafe {
        // SAFETY: len is count*4 by construction; alignment checked; on LE the
        // byte order matches native and every 4-byte group is a valid f32.
        std::slice::from_raw_parts(p, self.gamma_bytes.len() / size_of::<f32>())
    })
}
```

…and reorder the on-disk dense block so typed arrays are aligned: aligned arrays
first (descending alignment), variable byte fields last:

```text
header (8-aligned) | gammas[f32] | heap_tid_offsets[u32] | heap_tid_counts[u16]
| deleted_bitmap[u8] | rerank_tids | heap_tids | payloads
```

## What is sound (confirmed)

1. **Endianness rationale.** LE matches both deployment targets — Graviton 4
   (Neoverse V2, little-endian) primary and AWS Intel (x86-64, little-endian)
   secondary — so LE-on-disk forces **no** byte swap on either. Keeping the
   durable format LE preserves the Task 42 invariant. Correct.
2. **The current cost is decode + copy, not cross-endian conversion.** On a LE
   host, `from_le_bytes` is value-identical to a native load; the real overhead
   is (a) per-element `from_le_bytes` over the gamma/offset/count arrays and (b)
   the `Vec<f32>` allocation+copy (`gammas()` / `copy_gammas_to`). Eliminating
   those on LE is a genuine saving. Correct.
3. **The reinterpret is memory-safe on LE when aligned.** `f32`, `u16`, `u32`
   have **no invalid bit patterns**, so reading arbitrary validated bytes as
   those types is never value-UB (unlike `bool`/`char`). The gamma byte slice is
   a validated subslice of the pinned page buffer (valid provenance, length =
   `count*4` by construction), so **alignment is the only remaining safety
   condition** — exactly what the guard checks. Sound.
4. **Reorder minimizes padding; storage impact is negligible.** Putting aligned
   typed arrays first and variable byte fields (bitmap, TIDs, payloads) last
   means the variable bitmap no longer pushes the typed arrays off alignment.
   Padding cost is 0..3 bytes/block (4-align) or 0..7 (8-align) — noise relative
   to the per-row payload. Correct. (Minor: keep 4-byte arrays before 2-byte
   arrays so a `u16` array can't misalign a following `u32`/`f32` array — also
   correct as stated.)
5. **Spanning-format storage risks are the real ones.** If a multi-page/packed
   format is ever pursued: per-segment metadata/headers, PG line-pointer
   overhead per segment, partial-group padding to 32, and page fragmentation are
   the actual storage costs — not the bitmap. Storing the true `count` for a
   final partial group (vs padding to 32) unless a scorer fast-path needs it and
   it benchmarks as worth it — correct guidance.

## Caveats the proposal understates (reviewer additions)

A. **This is a durable format change, not a free codec tweak.** Reordering the
   dense block to guarantee alignment changes the on-disk `0x25` layout. That
   means a new format tag/version, the same Task 42 reconciliation we already
   owe for the experimental dense tag, and a rebuild of any gated dev indexes.
   So "cheaper" is true *at runtime on target* but carries a one-time
   format-migration cost. It must be **gated on a measured win**, not adopted on
   first principles — especially since dense TQ already beat row via coalescing
   in packet 002, so the typed-view delta is on top of an already-good result.

B. **Alignment is absolute, not offset-relative.** I confirmed page tuples are
   placed at `ALIGNMENT_BYTES = 8` (`storage/page.rs`), but the alignment of an
   array *inside* the tuple also depends on `TUPLE_HEADER_BYTES` and the in-tuple
   field offsets. So the reorder is necessary but not by itself sufficient to
   *prove* alignment at every site — the runtime `is_aligned` check is
   **mandatory** as the safety net (and correctly makes the path sound even if a
   placement assumption ever breaks; it just falls back to decode). Also note
   the example's `is_aligned_to::<f32>()` isn't a real API — use
   `ptr.cast::<f32>().is_aligned()` (stable) or an explicit modulo check.

C. **The big one — interaction with the *adopted* coalescing path.** The batch
   scorer already takes `gammas: &[f32]` (`quantizer.rs:486,606`), so in
   principle a typed gamma view can feed it with no copy. **But Task 111a adopted
   Approach A (coalescing)**, which *gathers* postings across blocks into
   `IvfPostingScratchSoa.gammas: Vec<f32>` before scoring. On that path a
   per-block typed view **cannot** be passed straight to the scorer — you still
   copy into the gather buffer. So the win splits:
   - **TurboQuant (coalesced):** typed view makes the *gather* cheaper (bulk
     native copy + no per-element `from_le_bytes`) but is **not** zero-copy.
     Marginal-to-moderate.
   - **RaBitQ (per-block, `dense-old`, already width≥32):** typed view on the
     per-block path is **true zero-copy `&[f32]` → scorer**. This is plausibly
     the clean fix for the RB1 regression-vs-`dense-old` I flagged in the
     packet-002 feedback — and it would be *better* than the width-aware
     coalescing heuristic I suggested there, because it removes the side-array
     decode/copy entirely rather than just skipping the coalesce gather.

   Net: the typed view's headline "no `Vec<f32>` copy" benefit lands mainly on
   the per-block/RaBitQ path, with a smaller gather-speedup on the coalesced TQ
   path. That should shape how it's benchmarked.

## Recommendation

Treat "aligned LE typed views + dense field reorder" as the **next Task 111a
slice**, sequenced and gated as follows, rather than adopting it on argument:

1. Land the format reorder + typed-view accessors
   (`gammas_native_le() -> Option<&[f32]>`, and the `u16`/`u32` side-array
   equivalents) behind the existing `dense_posting_blocks` gate, with the
   runtime `is_aligned` guard and `from_le_bytes` fallback retained for
   tooling/tests/non-LE.
2. Wire the per-block (non-coalesced) scan path to pass the typed gamma view
   straight to the scorer; wire the coalesced gather to use native typed reads.
3. **Re-run the 50k/100k A/B** (it's cheap and already scripted) as a four-way:
   row / dense+A / dense+typed-per-block / dense+A+typed-gather. The decision to
   adopt should rest on whether typed-per-block recovers RaBitQ (vs `dense-old`)
   and whether the TQ gather speedup is non-trivial — not on first principles.
4. Keep the durable format LE; the reorder takes a new tag/version and the Task
   42 reconciliation, same as the existing `0x25` caveat. Note the migration in
   the packet manifest.

## Correction: typed views and Approach B are complementary, not alternatives

**Operator direction (2026-06-17): Approach B does NOT stay closed.** Packet
002's "reject B as dominated" recommendation — which my prior feedback endorsed —
is overridden. B is back in scope and must be built and measured, per the
original "both, equal weight" intent of Task 111a.

I had the relationship backwards in an earlier draft. Typed views are **not** a
reason to keep B closed; the two compose because they fix **different axes**:

- **Approach B (on-disk spanning/packing)** fixes **batch width + page-local
  contiguity**: a logical block spans multiple pages so it holds ≥32 postings
  contiguously and is wide *by construction*, with no scan-side gather. This is
  the fullest realization of the original Task 111 thesis — "write postings in
  the shape the scorer consumes and score them directly off the page."
- **Typed views** fix **per-element decode + copy cost**: aligned LE arrays read
  as `&[f32]`/`&[u16]`/`&[u32]` with zero copy.

They reinforce each other. A packed B span **laid out with aligned typed arrays**
gives wide batches AND zero-copy reads handed straight to the scorer — strictly
better than either alone, and it removes the scan-side coalescing gather entirely
within a span. Note the alignment/reorder design in this proposal was itself
framed "for the spanning-page format" — i.e. the typed-view layout is a
**component of doing B well**, not a substitute for it.

So the work sequences as: (a) the aligned-typed-view layout is a building block
used by both the existing one-page format and the B span format; (b) Approach B
(multi-page packing) is implemented and benchmarked as originally scoped. The
storage risks I confirmed above (per-segment metadata/headers, line-pointer
overhead, partial-group padding, fragmentation) are real B design constraints to
measure — not reasons to skip B.

Updated benchmark ask (supersedes the four-way above): row / dense+A (coalesced)
/ dense+typed-per-block / **dense+B (packed)** / **dense+B+typed**, for
TurboQuant and RaBitQ at 50k/100k, so the equal-weight A-vs-B decision rests on
measured evidence. Task 111a AC#2 is updated to require B (the early-close
escape hatch is removed).

## Approach B should be a logical-group spanning format (analysis: sound)

Further design input (other agent's session) sharpens what B should be, and I
confirm it is sound: B should be a **logical-group spanning format**, not merely
"dense block segments." The unit is a logical dense group **sized to the scorer
width** (32 or 64), and physical pages fragment that group only when needed —
i.e. stop letting PostgreSQL page capacity define SIMD batch size. This is the
durable, structural version of what Approach A's scan coalescing proved at
runtime: the win is wide scorer calls; B makes width a property of the format
instead of something a scratch buffer recovers each scan.

Must-haves (all sound, and each maps to a real risk if omitted):

- logical group id + segment index/count;
- contiguous segment visitation or explicit assembly checks;
- metadata arrays stored **once per logical group** (avoids the per-segment
  metadata-duplication storage risk);
- continuation segments are mostly payload bytes (avoids per-segment header
  overhead);
- typed LE views on aligned metadata arrays for Intel/Graviton (the Phase 2b
  building block — composes directly: assemble group → typed view → score once);
- **no per-segment scorer calls** — assemble the whole logical group, then score
  once. This is the load-bearing rule: a spanning format that scored per
  physical segment would preserve the exact small-flush regression B exists to
  fix, while adding format complexity. Confirmed critical.
- no padding a final tail up to 32/64 payloads unless a scorer fast-path needs
  it and it benchmarks as worthwhile.

Reviewer caveats to carry into the B design:

- **Keep Approach A as the baseline/gate.** It already works and is far simpler;
  B is judged against it, not assumed better. (Agreed with the source.)
- **Assembly cost is the main new complexity.** Each segment is a separate raw
  tuple/line-pointer, possibly on different pages; the scan must gather
  contiguous segments (read-stream friendly) before scoring. Budget for that and
  measure it — it partially offsets the zero-copy win.
- **Lifecycle stays with Task 114.** A per-group deleted bitmap is fine
  (metadata-once), but repack/reclaim of partially-dead spanning groups under
  churn is Task 114, not 111a.
- **Durable format change → Task 42.** Same reconciliation already owed for the
  experimental `0x25` tag; the spanning format gets its own tag/version.

So: yes, a page-spanning (logical-group) dense format is the right durable
direction to stop being bound by the single-page TurboQuant case — pursued
alongside, and consuming, the aligned-typed-view building block, with Approach A
retained as the simpler benchmark baseline.

Leaving the request open; not closing it or flipping task status.
