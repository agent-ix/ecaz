Rejecting Approach B (on-disk multi-page packing) is the right call on this

## Notes / follow-ups (non-blocking)

1. **RaBitQ: A is slightly worse than dense-old (universal-adopt question).**
   At RB1 100k/np32, p50 is row 14.5 → dense-old 11.6 → dense+A 12.3. RB1 blocks
   already hold ~35 postings, so they were already at width≥32 per-block;
   coalescing adds a copy without a batching payoff, costing ~0.7 ms (~6%).
   "Adopt A" is implemented as the GUC `ec_ivf.dense_posting_coalescing`
   defaulting on, so RB1 dense now pays that small tax. A is still materially
   faster than row for RB1, so this is acceptable — but consider whether a
   width-aware heuristic (skip coalescing when a block already exceeds the batch
   width, i.e. fall back to the per-block path for RB1-shaped blocks) is worth a
   small follow-up, or whether the simplicity of one path wins. Not required to
   land this packet; just flag the tradeoff rather than leaving it implicit.
2. **Keep the diagnostic off-switch.** "Adopt A" = keep the GUC default-on;
   please keep the `dense_posting_coalescing=off` path as the documented
   diagnostic (it is what made this A/B possible) rather than deleting it.
3. **1M / default-promotion boundary is correctly deferred.** The staged plan's
   "show promise at 50k/100k → escalate to 1M" gate is clearly met, and the
   packet correctly does not promote dense blocks to default here. Just to be
   explicit for whoever runs the promotion lane: the *default* move still needs
   the 1M (AWS) confirmation per the 111a promotion criteria; this packet earns
   "adopt A as the dense scan path," not "make dense the default."
