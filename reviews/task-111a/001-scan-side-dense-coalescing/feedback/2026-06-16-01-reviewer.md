# Feedback: Task 111a Packet 001 — Scan-Side Dense Coalescing (Approach A)

**Reviewer:** Claude (Opus 4.8)
**Date:** 2026-06-16
**Checkpoint reviewed:** `b47d5b78ccc6`

## Verdict

LGTM for the scope it claims (Phase 1 / Approach A correctness + observability).
The coalescing is implemented cleanly by reusing the existing
`IvfPostingScratchSoa` accumulator for dense postings and flushing it through the
same SoA batch scorer the row path uses — which is exactly the mechanism that
gives the row path its width≥32 batching. Correctness semantics are preserved
and the unsafe scratch lifecycle mirrors the established pattern. Not blocking;
notes below, and the actual width/latency win is correctly deferred to the
Phase 3 benchmark.

## Verified correct

- **Coalescing accumulator.** Dense postings now accumulate into a dedicated
  scan-opaque `dense_posting_coalescing_scratch` (a second `IvfPostingScratchSoa`)
  via `push_dense_posting`, which mirrors the row `push` exactly: gamma,
  recomputed `heap_tid_offset` (relative to the scratch's own heap-tid vector),
  `heap_tid_count`, heap TIDs, and payload. The new unit test
  `posting_scratch_soa_batches_dense_posting_fields_without_losing_order`
  confirms field-level correctness and ordering across non-contiguous indices.
- **Flush boundaries are complete.** Dense scratch is drained at: a row posting
  (before row handling), a dense block whose `list_id` differs from the current
  accumulation, `!can_accept(heap_tid_count)`, reaching
  `IVF_POSTING_SCRATCH_SOA_BATCH_POSTINGS`, and end-of-scan. Row scratch is
  symmetrically drained when a dense block is encountered. No accumulated
  postings can be left unscored.
- **Semantics preserved.** `is_deleted` filtering, per-list
  `consume_live_tid_budget`, heap-TID expansion, and candidate dedup (shared
  `best_by_heap_tid`) are all retained — `append_dense_posting_block_to_coalesced_scratch`
  applies the same guards the prior `process_dense_posting_block` did, just
  routing the survivors into the shared accumulator instead of scoring one block
  at a time.
- **Memory safety.** The new `dense_posting_coalescing_scratch` is a separate
  heap `Box` (disjoint from both the row scratch and the opaque struct), so
  `&mut *dense_scratch` and `&mut *opaque` do not alias — same sound pattern as
  the packet-005 scratch. Allocated once before the visitor loop, only the raw
  pointer is used inside, and it is freed in `ec_ivf_amendscan` with the matching
  `Box::from_raw` + null-replace double-free guard.
- **Observability.** Counters are correctly separated: row drains call
  `record_scratch_soa_flush`, dense drains call `record_dense_coalesced_flush`,
  both EXPLAIN-visible (property array 21→24, prime-fixture equality test
  updated). The PG18 fixtures assert dense-only scans show
  `dense_coalesced_flushes > 0` while `scratch_soa_flushes == 0`, which is the
  right way to prove the dense path is actually exercised and didn't silently
  fall back to row reshaping.

## Notes / follow-ups (non-blocking)

1. **Cross-flushing on row↔dense alternation.** The row scratch is flushed on
   *every* dense-block visit, and the dense scratch on *every* qualifying row
   posting. For the common layout (a list is all build-dense or all row/delta,
   block sequences grouped by list) this is fine. But a delta-heavy or
   per-tuple-interleaved mixed list would fragment *both* accumulators back into
   small batches — i.e. reintroduce the very width<32 problem for the mixed
   cell. Phase 3 should include a mixed dense+row cell and watch
   `Scratch SoA Flushes` vs `Dense Coalesced Flushes` widths there, not just the
   pure-dense cells.
2. **List-boundary dense flush may be stricter than needed.** The dense
   accumulator is flushed when `list_id` changes, but the batch scorer is
   list-agnostic (it scores payloads against the query; the live-TID budget is
   already consumed per-posting at append time). The row scratch does *not*
   flush at list boundaries. If Phase 3 shows small/interleaved lists fragment
   dense batches, consider letting the dense accumulator span list boundaries
   like the row path does. If there is a correctness reason for the
   list-boundary flush I've missed, please note it in the packet.
3. **`dense_posting_block_scratch` (packet 005) is now bypassed on the batch
   path.** Dense blocks in the TQ/RaBitQ scratch-SoA path now route through
   coalescing, so `process_dense_posting_block` (and its
   `IvfDensePostingBlockScratch`) is only reached by the non-batch `else` path.
   That's fine, but confirm it's intentional that the packet-005 reuse buffer is
   no longer on the hot path for the formats this task targets — and that the
   non-batch path still wants the per-block scorer.
4. **Width≥32 is not yet demonstrated (expected).** The PG fixtures are 4-row,
   so they prove the coalesced path runs but cannot show the SIMD width shift or
   the TQ latency recovery. AC#4 (flush-width counters show TurboQuant reaching
   width≥32) and the go/no-go remain on the Phase 3 benchmark — correctly run at
   50k/100k first per the staged plan, escalating to 1M only on promise.

This is a clean first checkpoint for Approach A. The correctness scaffolding to
make the benchmark meaningful is in place; the open question is purely whether
the wider batches recover TurboQuant latency without a mixed-cell regression,
which the Phase 3 run will answer. Leaving the request open.
