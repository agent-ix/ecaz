## Verdict

The Approach B core is well-built. The load-bearing rule — **assemble the whole
logical group, then score once** — is correctly and defensively enforced, the
packed codec is bounds-checked, and segment ordering/consistency is validated
loudly. Not blocking. The main finding is the answer to "why no zero-copy for
TurboQuant" and two concrete improvement levers; plus the test-coverage gap.

## Verified correct

- **Codec structure.** Separate tags for header (`0x26`) and continuation
  (`0x27`); fixed header-byte constants; `decode` validates min length, tag,
  `segment_index < segment_count`, heap-tid ranges (`checked_add`, bound vs
  `total_heap_tids`), and payload lengths. Consistent with the existing dense
  codec's defensive style.
- **Assemble-then-score-once is enforced (the critical rule).**
  `IvfDensePackedPending` accumulates `from_header` (must be segment 0) then
  `append_continuation`, and the scan only calls `drain_dense_packed_group_to_
  scratch` when `is_complete()` (`next_segment_index == segment_count`). It
  **never** scores a partial group, so a spanning group cannot reintroduce the
  small-flush regression B exists to fix.
- **Strong assembly validation.** `append_continuation` checks matching
  `list_id`/`logical_block_id`/`segment_count`, in-order `segment_index ==
  next_segment_index`, `payload_offset == payloads.len()`, and that the running
  payload length never exceeds the group total. Interleaving violations (a row
  posting or dense block "interrupting" a group, a continuation without a header,
  or a group that ends before its final continuation) all return errors rather
  than silently corrupting — fail-loud is the right call here.

## Finding 1 — why TurboQuant is not zero-copy, and how it could be (answers the open question)

The packed assembly copies payloads into an owned buffer:
`from_header` does `payloads.extend_from_slice(segment.payloads)` and
`append_continuation` concatenates each continuation. So the scorer is fed an
**assembled owned `Vec<u8>`**, not a page-resident slice.

Root cause (not endianness, not decode — it's *contiguity*): the batch scorer
needs `width` postings' payloads contiguous in memory. RaBitQ blocks already
hold ≥32 postings in one page, so the per-block path can borrow and score
zero-copy. TurboQuant's payload is ~3.5× larger (per packet 002: ~10
postings/page), so a width-32 TQ logical group **spans ~3 pages** — its payload
bytes live in three different page buffers, and assembling one contiguous batch
necessarily copies. B makes that gather *cheaper* (a few bulk per-segment
memcpies + zero-copy gammas via the typed views) but it is **not** zero-copy for
the payload, by construction.

Two levers to improve it, in increasing cost:

1. **Single-segment fast path (cheap, do this).** Today `from_header` builds
   owned Vecs even when `segment_count == 1` (the group fits one page). For that
   case, score **directly from the page-resident segment** (borrow gammas via the
   typed view + the payload slice) with no `IvfDensePackedPending` assembly. That
   restores zero-copy for every group that fits a page — all RaBitQ packed groups
   and any small TQ group — and is a localized change with no format impact.
2. **Segmented/scatter-aware batch scorer (expensive, measure first).** True
   zero-copy for a *spanning* TQ group requires a scorer that strides over N
   page-resident payload chunks and produces one set of `width` scores without
   concatenating them. That is real SIMD plumbing. Whether it beats the current
   bulk-memcpy assembly depends on whether that assembly copy is actually a hot
   cost — which the `004` benchmark (dense+B vs dense+B+typed) should show. Do
   not build it speculatively; gate it on the measured assembly cost.

So: TQ zero-copy is achievable for page-fitting groups via lever 1 now, and for
spanning groups only via lever 2 — and lever 2 may not be worth it if assembly is
cheap. Recommend implementing lever 1 and letting the benchmark decide on lever 2.

## Finding 2 — test coverage (should address)

The committed validation is unit-level (`dense_posting_packed`,
`build_state_splits_packed_dense_payloads_into_continuations`). There is **no
PG18 fixture** exercising a real multi-segment group through the scan
read-stream. The assembly correctness depends on segments being visited in
strict write order via the block sequence; the code fails loudly if not, but a
violation would make those indexes unscannable. Add a PG18 fixture that builds a
packed index whose groups span pages and asserts: correct scan results, that the
packed path engaged (counters), and that deleted/live-tid semantics hold across
segments. This is the gating correctness test before the benchmark is meaningful.

## Finding 4 — multi-page efficiency is the common case across the RaBitQ bit-width sweep

The "TurboQuant spans pages, RaBitQ doesn't" framing only holds for RaBitQ
**1-bit**. Postings-per-page falls as `quant_bits` rises: rb1 ≈ 35/page (fits
≥32), but rb2 ≈ 17, rb4 ≈ 9, rb8 ≈ 5 — and TurboQuant ≈ 10. So **every quant mode
except rb1** produces width-≥32 groups that span multiple pages and pays the
exact assembly copy from Finding 1, with the copy *growing* with bit-width. The
multi-page spanning path is therefore the common case, not a TQ corner, and its
efficiency is a primary objective.

Consequences:
- **Benchmark coverage gap:** the matrix must sweep RaBitQ `quant_bits` (at least
  {1, 4} to bracket fits-vs-spans, preferably {1, 2, 4, 8}), not just rb1 + TQ.
  Testing only rb1 hides the regime where B's assembly cost actually lands.
- **Lever priority shifts:** Finding 1's lever 1 (single-segment borrow) only
  helps groups that fit a page — i.e. rb1 and small TQ. For rb2/4/8 + TQ the
  groups span, so **lever 2 (segmented/scatter scorer) or otherwise minimizing
  the spanning assembly copy is the lever that matters across most of the quant
  spectrum.** That raises its priority above the earlier "TQ-only, measure first"
  framing — still measure, but expect spanning to dominate.
- Add a per-group **assembly/copy-bytes counter** so the benchmark can quantify
  the copy across bit-widths and decide lever 2 on evidence.
