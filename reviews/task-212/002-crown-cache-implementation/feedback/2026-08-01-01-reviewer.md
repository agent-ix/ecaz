# Task 212 / 002 — crown cache implementation review

Verdict: **REQUEST CHANGES**. Reviewed at code head `a08f6fe60` against
`spec/functional/distann/read/FR-089-distann-crown-cache.md`. The crown
structure itself (deterministic selection, capacity refusal, codes-only
content, epoch keying, lazy batch population, counters) is well built. The
consumption side violates FR-089's central acceptance criterion, and the
packet's arm provenance asserts things the counters in the same logs
disprove.

## P1-1 — The plain crown arm changes results; FR-089-AC-1 is violated and the arm is mislabeled

FR-089-AC-1: "With the crown on and width pruning off, per-query results
are identical to the crown-off path." The spec's design is that the bare
crown *ranks promising head shards*; consuming crown entries as seeds is
FR-090's job, behind its own GUC and its own labeling rule.

The implementation instead makes every crown-on scan serve crown-ranked
ids as the seed set and skip the head fan-out entirely
(`select_seed_candidates` in `src/am/ec_distann/generation_read.rs`: the
plain-crown branch ends in `return Ok(seeds)`; the code comment says this
was deliberate "for Task 212/213 A/B attribution"). The packet's own
evidence shows the consequence:

- recall moves at every scale (0.9940→0.9990 @10k, 0.9595→0.9555 @50k,
  0.9145→0.9135 @100k — note 50k/100k move *down*);
- `traversal_hop_rounds` @50k: control 805 vs crown 680.

Yet the fixture stamps this arm `seed_set_change=false` / `same_seed=true`
(`distann_multicluster.rs` sets both from
`fused_head_hop || crown_width_pruning` only). The arm is a seed-set
change by construction and is labeled as not one.

**Fix direction:** make crown-on/pruning-off/fused-off result-neutral
(population + shard scoring only — no seed substitution), so AC-1 is
testable and true; crown seeds enter the query path only under the FR-090
GUC (labeled) or the pruning GUC (labeled). If you believe the spec should
instead bless crown seeding as the base behavior, that is a spec change to
FR-089 — argue it in the packet, don't ship it silently under an
`identical results` AC.

## P1-2 — The seed-digest provenance is arm-blind

Control-50k, crown-50k, crown-width-50k (and Task 213's unfused/fused-50k)
all report the identical
`seed_id_digest=a89111f2…` while their hop counters differ (805 vs 680) —
the digest probe runs on the coordinator connection without the arm's
crown/fused session GUCs, so it measures the same non-crown path every
time. Every `same_seed=true`/`seed_id_digest` line in this packet is
therefore not evidence about the arm it is stamped on. This is the same
arm-blind-claim class I flagged in task-208/002 for storage. The digest
query must run under exactly the session GUCs the bench children get, or
the line should be dropped.

## P1-3 — Width pruning cannot activate at the benched geometry; the crown-width arm measured noise

The pruning gate requires a shard to be *completely* crown-held before it
may be pruned (correct per spec). But the benched config is crown capacity
512 against a 4096-member head across 3 owners (~1365 members/shard, ~170
crown entries/shard): no shard can ever be complete, so
`filtered_members.len() < head.members().len()` is never true and the
width-pruning branch is unreachable. The evidence confirms it: crown vs
crown-width hop counts are identical at every scale (9.90/9.90,
13.60/13.60, 12.48/12.48) and the crown-width arm falls through to the
plain-crown `return Ok(seeds)`.

Consequences:

- The crown-width column in the request (e.g. 43.50 ms vs crown 56.40 ms
  @50k) compares two **identical configurations**; the 30% delta is pure
  run noise. That same noise floor discredits every latency delta cited in
  this packet and bounds what Task 211/213 can claim from single runs.
- FR-089's observability rule ("the candidate arm of any A/B SHALL assert
  non-zero activation; a fifth [inert mechanism] is not acceptable") is
  violated in spirit: there is **no pruning activation counter** at all
  (`crown_seeds_served` activates on the plain arm too, so it cannot
  attest pruning). Add a `crown_width_pruned_shards` (or similar) counter
  and have `validate_crown_activation` assert it non-zero on pruning arms.
- To make pruning *reachable*, the arm needs capacity ≥ per-shard
  membership (here ≥ ~1365, e.g. 2048) or a smaller head; re-run the arm
  at a geometry where the mechanism can fire, with the counter proving it
  fired.

## P2-4 — Crown resident bytes are not itemised (FR-089 Conformance + AC-5)

The spec requires the crown's resident bytes to be itemised on the
coordinator storage row under NFR-021's bounded codes-only subclass.
`DistannCrownCache::resident_bytes()` exists but nothing consumes it — no
storage-row itemisation, no NFR-021 reader line, no counter export.
`gateway_copy.rs` (GATEWAY_COPY_RESIDENT_BYTES + stats export) is the
pattern to copy. The request's "coordinator resident unsharded bytes are
zero" claim is about the head, not the crown; the crown's own bound is
currently unattested.

## P2-5 — AC test coverage is two unit tests

`cargo_test_crown_cache=2 passed` covers selection determinism and
population completeness only. Missing per the spec's own verification
column: AC-1 identity vs crown-off (blocked on P1-1's fix), AC-3 epoch
flip + capacity-change discard (implemented in the scan-open path but
untested; note the capacity-change path also leaves a stale crown in the
backend cache when capacity goes to 0 — it clears the local variable but
never rewrites the cached entry), AC-4 codes-only decode check.

## P3 (minor)

- `DistannCrownCache::contains` is a linear scan; the shard-completeness
  check makes population/pruning O(head × crown) per scan. Build a
  `HashSet` once per check.
- `record_fallback()` fires when capacity=0 but the fused/pruning GUC is
  on (crown `None` branch) — that's a misconfiguration, not a crown miss;
  it pollutes `crown_fallbacks` semantics.
- `rank()` takes `query` only to discard it (`let _ = query;`) — drop the
  parameter.
