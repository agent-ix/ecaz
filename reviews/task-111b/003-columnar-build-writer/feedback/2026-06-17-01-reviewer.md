# Feedback: Task 111b Packet 003 — Gated Columnar Build Writer

**Reviewer:** Claude (Opus 4.8)
**Date:** 2026-06-17
**Checkpoint reviewed:** `e7fed64df`

## Verdict

Good structural slice — the gate, the item-aligned raw-page generation (acting on
the packet-002 note), the deterministic header refs, and the special-area raw
pages are all sound in design. **But the raw-page block-number placement
arithmetic is the load-bearing risk and it has no read-back validation in this
slice** (scan isn't wired). That's the one thing I want closed before the reader
slice builds on it. Not blocking the checkpoint, but treat finding #1 as the next
required step.

## Verified correct (by reading the code)

- **Gate.** `columnar_frozen_lists` reloption, default off, plumbed through
  `EcIvfOptions`/cost/insert; `insert.rs` forces it off so the mutable path stays
  on row postings. Existing row/dense/packed paths unchanged unless the reloption
  is set.
- **Item-aligned raw pages (addresses packet-002 note #1).** Every column —
  gamma(4), payload(payload_len), heap_tid_count(2), heap_tid_offset(4),
  heap/rerank TID(ItemPointer), bitmap(1) — is paged via the item-aligned
  chunker, so no column item splits across a page.
- **Placement arithmetic is internally consistent.** `current_block` is captured
  after the per-list `start_new_page_if_current_has_tuples()` (line ~43), so the
  current page is fresh; the small header tuple lands on `current_block`;
  `first_column_block = current_block + 1`; the post-header `start_new_page` +
  `append_empty_pages(n-1)` allocate exactly `first_column_block ..=
  last_column_block`; raw bytes are staged at `first_column_block + i`; a trailing
  `append_empty_pages(1)` separator stops the next list from appending tuples
  onto the last raw page. `checked_add` guards the block-number math. The logic
  hangs together.
- **Special-area raw pages.** Storing column bytes in the page special area
  (reserving the full area so normal tuple insertion can't reuse the page) keeps
  these as valid PostgreSQL pages (buffer manager / checksum / WAL safe) rather
  than truly raw pages — the right call.

## Finding 1 (must close next) — no read-back validation of placement

The block-number arithmetic above is *plausible* but *fragile*: it couples the
computed `first_column_block..last_column_block` to the exact page-allocation
sequence, and nothing in this slice reads the bytes back to confirm they landed
where the header says. The staging test checks the produced header/refs, not a
materialized-chain read at those blocks. A one-off-by-one in `start_new_page` /
`append_empty_pages` ordering would silently corrupt and only surface
(confusingly) inside the reader slice.

Add a focused test **now**, independent of scan:
1. stage a columnar list whose payload spans **≥2 raw pages**,
2. materialize the `DataPageChain`,
3. read the special-area bytes at `header.first_column_block ..=
   header.last_column_block`,
4. assert they equal the source column bytes (and that the separator page is
   empty / not mistaken for a column page).

This de-risks the durable placement before the reader depends on it, and doubles
as the determinism check for the same input/seed/reloptions.

## Notes (non-blocking)

2. **Reader must mirror the special-area read exactly.** The next slice has to
   read raw bytes from the special area at the header's block range and derive
   each raw page's valid byte length from the header/page_size (the last page is
   partial). Worth stating the per-page valid-length derivation in the reader
   packet so it can't drift from the writer.
3. **Separator-page storage cost.** `append_empty_pages(1)` per columnar list is
   one empty page/list (e.g. 64 pages at nlists=64 ≈ 512 KiB) plus the
   whole-item page-tail padding. Negligible at 100k+, but include both in the
   111b storage benchmark so the columnar storage win vs A is reported net of
   them.
4. **Page checksums/WAL.** Confirm these special-area pages round-trip through
   checksum + WAL like normal pages (they should, being standard page format) —
   a focused note or assertion in the read-back test would settle it.

Solid writer; the placement read-back is the gating follow-up. Leaving the
request open.
