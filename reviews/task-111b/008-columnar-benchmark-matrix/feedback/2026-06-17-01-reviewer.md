## Strategic finding — columnar storage density (matters for 111c/111d)

`summary.md` shows columnar < row but **dense-old < columnar in every cell**. The
columnar format is structurally less storage-dense than compact one-page dense
blocks, because of: per-column page-tail padding (whole-item alignment × 6
columns), the per-list separator page, the 8-byte guard, and **always-present
cold columns** (e.g. a full `rerank_tid` column even when every entry is INVALID).

Why this matters beyond storage: larger on-disk size ⇒ **more posting pages
read** ⇒ more I/O per scan. 111c removes the assembly *copy*, but it does not
shrink the bytes read. So the no-copy win has to overcome columnar's extra page
reads vs dense — the same fragmentation tension that sank Approach B, milder but
present. If columnar can't get close to dense on bytes/page-reads, score-in-place
could win on copy and lose on I/O, exactly the trap we're trying to avoid.

Concrete, do this with/before 111c (this is the "cheaper page layout" the packet
gestures at, made specific):
1. **Elide always-INVALID cold columns.** If `rerank_tid` (and any unused cold
   column) is uniformly INVALID for a list, omit it and flag its absence in the
   header — don't store 6 B/posting of nothing.
2. **Pack small columns together.** gamma(4)/count(2)/offset(4)/bitmap(1) each
   page-aligned wastes a tail per column per page; co-locating the small columns
   (or only page-aligning the *payload* column, which is the one the scatter
   scorer needs aligned) cuts most of the padding.
3. **Drop the per-list separator page** if the 8-byte guard already prevents
   tuple reuse — confirm and remove the extra empty page.
   Report bytes/row and posting-pages-read against dense after each, so the
   storage gap is closed (or bounded) before 111c's latency numbers are judged.
