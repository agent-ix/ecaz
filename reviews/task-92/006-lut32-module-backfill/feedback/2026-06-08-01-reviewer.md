## Finding — must-fix before any ISA-attributed counter evidence ships

**Counter attribution lies once a real ISA kernel ships.**

`score_lut_no_qjl_4bit_block32` now picks an ISA at dispatch time via
`current_isa()`. All non-scalar branches currently delegate to the
scalar function, so a Graviton 4 host runs scalar code but
`current_isa()` returns `Isa::Sve2`. The counter call site in
`src/am/common/candidate_batch.rs` still hardcodes
`isa: Isa::Scalar` in the `BlockKernelCounterKey`.

For this backfill that is harmless (the work is scalar regardless of
which scalar function pointer was used). But the moment Tasks 93–98 land
a real SVE2 kernel, the dispatch will route through
`sve::score_block32_sve` while the counter row still says
`isa=Scalar` — every Graviton 4 packet would then under-report
SVE2 work as Scalar, and the cross-(AM × quant × ISA) Task 99 matrix
becomes incorrect.

The fix can land in either of two natural places:

1. In the next Phase 3 / Phase III slice that wires a real kernel under
   any ISA: change the counter call site to pass the **dispatched** ISA
   (i.e., the value `score_lut_no_qjl_4bit_block32` actually used,
   threaded back from the kernel function or read from
   `current_isa()` at the same call site) into
   `BlockKernelCounterKey { isa, … }`. Packet 007's
   `record_block_kernel_score(key, …)` already takes a full key, so the
   wiring is API-clean — only the call-site value needs to become
   non-constant.

2. Land a `score_lut_no_qjl_4bit_block32` variant that returns the
   dispatched `Isa`, and let the counter call site use that returned
   value. This keeps `current_isa()` resolution single-sited.

Either way: please make sure no Graviton 4 packet ever ships an
`isa=Scalar` row for kernel-block work after a real SVE2 kernel lands.

Document the constraint in the LUT32 module-level doc comment so
Tasks 93–98 reviewers catch the regression at code-review time, not at
matrix-aggregation time.
