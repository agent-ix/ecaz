# Reviewer feedback — Task 92 Packet 003 (block kernel counter surface)

scoring-share evidence. Two correctness bugs in the elapsed-nanos
attribution and one design conflict with the locked F2 rule. The
`(surface, quant_kind, isa)` identity and SQL function shape are fine.

## Findings

### F1 (must-fix before Phase 3 SIMD evidence): elapsed_nanos is double-counted

`BlockKernelCounters::record(candidate_count, elapsed_nanos,
kernel_candidates, scalar_candidates)` currently does:

```rust
if kernel_candidates > 0 {
    self.kernel_elapsed_nanos.fetch_add(elapsed_nanos, …);
}
if scalar_candidates > 0 {
    self.scalar_elapsed_nanos.fetch_add(elapsed_nanos, …);
}
```

For a 39-candidate batch (32 kernel + 7 scalar), the same total batch
elapsed_nanos lands in **both** `kernel_elapsed_nanos` and
`scalar_elapsed_nanos`. The test even bakes that in:

> assert_eq!(block.kernel_flushes, 1);
> assert_eq!(block.scalar_flushes, 1);

Per the contract `kernel_*` and `scalar_*` are meant to be a **split** of
total batch nanos so Tasks 93–98 can compute kernel-vs-scalar speedup
ratios. Adding the full elapsed to both lanes means `kernel_elapsed_nanos
+ scalar_elapsed_nanos > elapsed_nanos`, and a `kernel / scalar` ratio is
the same regardless of how many candidates were in either lane. That
breaks the `≥2×` methodology before it ships.

Fix options for the next Phase 2 slice:

- Measure the kernel-block timing and the scalar-tail timing separately
  inside `score_turboquant_no_qjl_4bit_batch_inner` (or wherever the
  whole-block range and tail range are scored), pass two
  `elapsed_nanos` values into `record`, and add each to the matching
  field. Total = kernel + scalar.
- Or: split into two `record` calls and route the scalar tail to a
  different `(surface, quant_kind, isa=Scalar)` row (see F2 below) so
  there is never a mixed row. The total batch elapsed is then the sum
  of the two row's row-total elapsed.

Either fix is acceptable; the second is preferred because it also
resolves F2.

### F2 (must-fix before Phase 3 closes): mixed row contradicts the locked tail-attribution rule

The locked F2 convention in
`reviews/task-91/001-phase1-trait-audit/artifacts/dispatch-contract.md`
(updated in commit `4366618ad`) reads:

> Scalar tails after one or more ISA kernel blocks are attributed to
> `isa=Scalar` in Task 92 counters. Do not record tails under the
> selected ISA row's `scalar_*` fields.

The implementation records both kernel and tail under a single key with
`isa = Isa::Scalar` here (because LUT32 has no real ISA dispatch yet, so
the `isa` field happens to be `Scalar` either way) — but the **API
shape** of `record_block_kernel_score(key, …, kernel_candidates,
scalar_candidates)` invites the wrong call pattern in Phase 3 when an
SVE2 kernel block plus a scalar tail will arrive together: the obvious
extension is `key = (…, Isa::Sve2)` with both `kernel_candidates` and
`scalar_candidates > 0`, which puts the scalar tail under the SVE2 row.

Please refactor so the recording API enforces the locked rule, e.g.:

- `record_block_kernel(key=(…, Isa::Sve2), kernel_candidates, kernel_nanos)`
- `record_block_scalar_tail(surface, quant_kind, scalar_candidates, scalar_nanos)`
  which writes into the `(surface, quant_kind, Isa::Scalar)` row's
  `kernel_*`-or-`scalar_*` fields per the documented semantic for that
  row.

Or land a single typed enum on the call shape that makes the two cases
non-mixable. Whatever shape you pick, please update the Phase 2 test to
exercise the **post-Phase-3 expected** call pattern with a synthetic ISA
so reviewers can verify the rule is enforced by the API and not only
documented.

### F3 (cosmetic but worth fixing this slice): Task 87 compat aggregation drift

`candidate_batch_surface_snapshot` aggregates `lut32_*` as:

```rust
if quant_kind == QuantCodecKind::TurboQuant && snapshot.kernel_flushes > 0 {
    lut32_flushes += snapshot.flushes;
    lut32_candidates += snapshot.candidates;
}
```

This adds the **row total** (kernel + scalar) into `lut32_*` whenever any
kernel work happened. Old semantics counted the batches that used LUT32
specifically — i.e., flushes where `batch.len() >= BLOCK_WIDTH`. With the
new shape that's `kernel_flushes` / `kernel_candidates`, not the row
totals. Please change the aggregation to:

```rust
if quant_kind == QuantCodecKind::TurboQuant {
    lut32_flushes += snapshot.kernel_flushes;
    lut32_candidates += snapshot.kernel_candidates;
}
```

so Task 87 packet parsers that already exist do not see a numerical
regression when they read the old SQL function. (The Phase 2 test
happens to pass because the recorded batch fills both lanes; a batch
with `batch.len() < BLOCK_WIDTH` would currently mis-attribute scalar-only
work into `lut32_*`.)
