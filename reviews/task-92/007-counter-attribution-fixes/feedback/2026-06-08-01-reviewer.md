# Reviewer feedback — Task 92 Packet 007 (counter attribution fixes)

## Spot checks against commit `4c7c9bab8`

### F1 fixed — kernel and scalar lanes get split elapsed_nanos

`score_turboquant_no_qjl_4bit_batch_lut32` now times each kernel block
range separately (`block_started = Instant::now(); …;
timing.kernel_elapsed_nanos = timing.kernel_elapsed_nanos.saturating_add(…)`)
and times the scalar-tail span separately
(`scalar_started = Instant::now()`). The aggregate
`BatchScoringTiming { kernel_candidates, kernel_elapsed_nanos,
scalar_candidates, scalar_elapsed_nanos }` is returned to the caller,
which splits the recording across two API calls.

The test now asserts
`block.elapsed_nanos == block.kernel_elapsed_nanos + block.scalar_elapsed_nanos`,
which is exactly the additive invariant F1 needed. ✓

### F2 fixed — scalar tails routed to a separate `isa=Scalar` row

`BlockKernelCounters` now has two distinct methods:

- `record_kernel(candidate_count, elapsed_nanos)` increments only
  `kernel_*` plus the row-total.
- `record_scalar(candidate_count, elapsed_nanos)` increments only
  `scalar_*` plus the row-total.

`record_block_kernel_score` takes a full key and calls `record_kernel`.
`record_block_scalar_score` takes only `(surface, quant_kind)` and forces
`isa: Isa::Scalar` internally before calling `record_scalar`. The
recording API now structurally enforces the locked F2 rule — the caller
cannot accidentally write a scalar tail into an SVE2 row.

The new test
`block_kernel_counter_api_records_scalar_tail_under_scalar_isa`
simulates exactly the Phase 3 expected pattern with `Isa::Sve2` + scalar
tail, and asserts the SVE2 row carries only kernel fields and the Scalar
row carries only scalar-tail fields. ✓ That is the test shape the prior
F2 feedback asked for.

### F3 fixed — Task 87 compat `lut32_*` derived from kernel-only counts

`candidate_batch_surface_snapshot` now does:

```rust
if quant_kind == QuantCodecKind::TurboQuant {
    lut32_flushes += snapshot.kernel_flushes;
    lut32_candidates += snapshot.kernel_candidates;
}
```

The compat test's expected value flipped from `lut32_candidates = 39` to
`lut32_candidates = 32`, which matches the old "LUT32 work means
batch.len() >= BLOCK_WIDTH" semantics (32 of the 39 candidates went
through the kernel). ✓

### Compatibility flushes carry the higher of kernel/scalar lane

`candidate_batch_surface_snapshot` rolls TurboQuant rows up with
`snapshot.kernel_flushes.max(snapshot.scalar_flushes)` to avoid
double-counting a single batch that now writes to both kernel and
scalar lanes through two API calls. That preserves the old "one flush
per batch" invariant for the Task 87 compatibility row. Subtle but
correct given how the underlying counters changed shape.
