# Reviewer follow-up — Task 92 Packet 001 (escalate F1 after Graviton 4 lock)

## Context

The user confirmed on 2026-06-08 that **AWS Graviton 4 is the ARM target**
for the Phase III block-kernel work. This escalates F1 from prior feedback
(`2026-06-08-01-reviewer.md`) from "fix before ADR-076 ACCEPTED flip at
Phase 6" to **"land in the next implementation packet that touches ISA
detection or SVE evidence."**

## Why the escalation

- Graviton 4 uses Neoverse V2 cores. Public Arm/AWS material puts the
  implemented SVE2 vector length at **128 bits** (2×128-bit pipes). It is
  **not** 256-bit SVE; that was Graviton 3 (Neoverse V1).
- ADR-076 currently uses `sve-256` as the example label and lists only
  `Sve` (not `Sve2`) in its proposed `Isa` enum. Phase 1 reviewers caught
  this as a flag; with Graviton 4 now locked in, any packet that ships
  before the fix will either (a) misreport vector width, or (b) detect SVE
  via the wrong feature gate (`"sve"` vs `"sve2"`).
- Both failure modes pollute the Task 99 cross-(AM × quant × ISA) matrix
  retroactively. Easier to land the convention before any packet cites SVE
  evidence than to renormalize after the fact.

## Escalated must-fixes

### F1a (Phase 2 counter landing — `Isa` enum shape)

When the Phase 2 packet introduces `src/quant/isa.rs` and the
`BlockKernelCounterKey { surface, quant_kind, isa }` identity, the `Isa`
enum **must** distinguish SVE feature levels. Two acceptable shapes:

```rust
pub(crate) enum Isa { Scalar, Neon, Sve, Sve2, Avx2 }
```

or, if collapsing them, a runtime field carries the detected level
alongside the enum:

```rust
pub(crate) enum Isa { Scalar, Neon, Sve { sve2: bool, vl_bits: u16 }, Avx2 }
```

Either is fine. What is **not** acceptable: a single `Sve` variant with
no runtime indication of `sve2` vs base `sve` and no vector-length
metadata. The Phase 2 counter-snapshot output must surface the
distinction so reviewers can grep packets for `isa=sve2-128` vs
`isa=sve-256`.

### F1b (Phase 3 ISA helper — feature detection gate)

`src/quant/isa.rs` must use
`is_aarch64_feature_detected!("sve2")` (in addition to or instead of
`"sve"`) for the Graviton 4 path. If the helper falls back to `"sve"`-only
detection, it will silently misclassify Graviton 4 hosts. The Phase 3
backfill packet should include a unit test for the detection logic on a
mocked feature-set that exercises:

- `sve2 && sve` (Graviton 4) → expected enum value;
- `sve && !sve2` (Graviton 3) → expected enum value;
- neither → falls back to `Neon` or `Scalar` per kernel.

### F1c (ADR-076 wording — before Phase 6 ACCEPTED)

Rewrite ADR-076's SVE section so:

- the production target line reads "AWS Graviton 4 (Neoverse V2, SVE2 at
  128-bit vector length)" not just "Graviton 4";
- the example label is `sve2-128` (or a measured-verbatim phrase), not
  `sve-256`;
- the "may report SVE-256 only when measured 256 bits" guard becomes
  "packets must report the measured runtime vector length verbatim
  (e.g. `sve2-128`, `sve-256`); inference from host class alone is
  forbidden."

The ADR ACCEPTED flip at Phase 6 must reflect this. But the wording fix
should ideally land in the same PR that introduces `Isa::Sve2`, so the
ADR and code agree.

## What this does not change

- F2 (counter scalar-tail attribution rule) and F3 (LUT32 backfill
  `f32::to_bits` parity tests) from the prior feedback file stand
  unchanged.
- Phase 1 approval still holds; this packet does not need to be redone.
  F1a/F1b/F1c are recorded against the implementation packets, not this
  design packet.
