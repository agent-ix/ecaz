## Findings to lock before Phase 6 closeout

### F1 (must-fix before ACCEPTED flip): SVE feature detection vs Graviton 4

ADR-076 names "AWS Graviton 4" as the ARM measurement target and says SVE
results may be reported as `sve-256` only when measured vector length is
256 bits.

That phrasing risks suggesting Graviton 4 has 256-bit SVE. Public AWS
guidance on Graviton 4 reports SVE2 at 128-bit vector length (4×128-bit
implementation), not 256-bit SVE. The 256-bit SVE vector length is the
Graviton 3 case. The ADR's "report SVE-256 only if measured" guard is
correct as a guard, but the example name `sve-256` is misleading for
Graviton 4 packets.

Two concrete fixes for the Phase 6 ACCEPTED flip:

1. Distinguish `is_aarch64_feature_detected!("sve")` and `…!("sve2")` in
   the ADR. Graviton 4 wants the `sve2` branch. The ADR's `enum Isa` lists
   only `Sve`; consider whether `Sve` collapses both or whether `Sve2`
   needs its own variant so packets are unambiguous about which feature
   was detected and used.
2. Rewrite the SVE example so it reads as "report the measured runtime
   vector length (e.g. `sve-128`, `sve-256`) verbatim, never assume
   Graviton 4 = sve-256."

Phase 1 is still approvable today because the ADR's guard wording is
defensive and Phase 2/3 code does not depend on the wrong assumption
landing in a packet. Lock this before Tasks 93–98 publish any SVE evidence.

### F2 (must-fix in Phase 2 implementation): Pick one tail-attribution rule

`counter-and-suite-contract.md` § "Counter Semantics" offers two options
for attributing scalar tails after an ISA kernel block:

> - record the tail under `isa=Scalar`, preferred for exact attribution; or
> - record it under the selected ISA row's `scalar_*` fields if
>   implementation simplicity wins.

If Tasks 93–98 each pick differently, the cross-quant matrix in Task 99
will need a per-task footnote. Please pick one rule in the Phase 2 counter
landing packet and update the contract from "implementation packet must
document which option it chooses" to "the convention is X" before the new
counter API is used by any later quant.

This is the same drift risk flagged in Task 91 Packet 001 feedback for the
IVF retouch. The two packets should land the same answer.

### F3 (must-fix in Phase 3 backfill): Bit-exact LUT32 backfill evidence

The skeleton audit promises the Task 87 LUT32 scorer becomes the worked
backfill reference under `src/quant/lut32/{mod,scalar,neon,sve,avx2}.rs`.
The Phase 3 packet must include a focused test that asserts `f32::to_bits()`
equality between the current `src/quant/lut32.rs` block scorer output and
the post-backfill `lut32/scalar.rs` output on at least one
batch.len() ≥ 32 fixture and one batch.len() < 32 tail fixture. Without
that, the backfill claim "behavioral parity vs pre-backfill code" cannot
be verified independently of the Task 87 Phase 6 recall baseline.

Please commit to that scope in the Phase 3 request.
