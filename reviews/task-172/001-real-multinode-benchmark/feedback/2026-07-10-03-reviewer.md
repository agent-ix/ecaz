# P0 correction: Task 172 must benchmark the physically sharded index

The current 10k preflight is **not a sharded-index run**. It builds the complete
global graph independently on all three PostgreSQL instances and partitions only
serving ownership. The later `disjoint_shard_drill` deletes non-owned heap rows
and tombstones their already-built graph records; it does not remove the full
replicated index from each node. The current packet is useful read-path,
fanout/merge, fault-injection, and recall-oracle evidence only.

This feedback supersedes the prior Task 172 plan wording that allowed physical
disjoint storage to remain merely a blocker while the rest of the gate matrix
continued. The canonical task plan is now corrected: physical FR-078 placement
is a fail-closed prerequisite for all gate measurements.

## Required correction

1. Add a reusable `ecaz bench suite` topology that builds/stitches one logical
   global Vamana graph and publishes each graph record plus its full-precision
   vector to exactly one `hash(vec_id) mod roster` owner. This is record-level
   physical sharding of one graph, not independent per-node ANN graphs.
2. Do not use cloning plus ownership filtering, or cloning plus heap deletion /
   index tombstoning, as the sharded lane. A serving node must not retain the
   non-owned graph records at all.
3. Add a suite-driven topology audit that runs before measurement and emits
   normalized rows proving exact corpus coverage, empty pairwise record
   intersections, exactly one physical graph record per vec_id, correct hash
   owner, record/vector co-placement, no non-owner live or tombstoned residue,
   per-node record/byte counts, and FR-078's 100k balance criterion. Missing or
   failed audit fields must invalidate the run.
4. First produce a clean release 10k smoke with this audit plus non-zero remote
   expansion/materialization engagement. Only after that topology is green
   should the 10k/50k/100k recall, latency, throughput, storage, load/build,
   overhead, and capacity matrix run.
5. Keep the existing replicated lane only if useful as a separately named
   `replicated-serving-control`. Its rows must carry an explicit non-gate
   topology label and must never be promoted as Task 172 distributed latency,
   storage, or scaling evidence.

The in-progress generic latency/result-row work can remain a reusable runner
capability, but results collected with the current replicated fixture do not
count toward Task 172. Prioritize the physical placement/publish path and its
audit before spending more host time on the benchmark matrix.

## Gate status

Task 172 remains open. The committed 10k packet does not satisfy the corrected
topology prerequisite, and no 50k/100k distributed gate run should be promoted
until the physically hash-sharded lane exists and passes the audit.
