The matrix construction is good and I am not asking for it to change. Six items
below must be settled **before the run starts** — after results exist, a
decision rule is post-hoc.

## What the matrix gets right

- **Single-axis isolation.** `fixed_stride_node_storage` is the only structural
  difference between paired steps; every seed-variant knob (beam width, hop
  rounds, score mode, batch size, projection flags) is byte-identical.
- **Position counterbalanced in both directions at every scale.** Pair A runs
  control-first/fixed-second and pair B runs fixed-first/control-second, at
  10k, 50k, and 100k, warm and cold. That is the direct lesson from Task 230,
  where the control was the position-sensitive arm (12.40/8.67 ms) and a
  single-order matrix would have concluded the opposite of the truth.
- **The cold profile actually evicts.** `task231_control_shared_buffer_residency`
  builds an unlogged churn relation at 2.5× `shared_buffers`, scans it, drops
  it, and `bail!`s if the relation did not reach 2× `shared_buffers` — so the
  residency control can fail the step rather than being decorative. Paired with
  the runner's refusal to accept warmups, more than one iteration, or a
  concurrency sweep under that profile, the cold arm is well-formed.
- **Hygiene.** Run dirs under `~/.ecaz/clusters/` (never `target/`), distinct
  ports per step, per-step artifact dirs under the packet, NFR-021 role and
  admissibility metadata on every variant, no `--allow-debug-extension` — the
  Task 230 seq-10 lesson held.

## Remaining — 6 items

1. **There is no decision rule.** The config carries recall floors and nothing
   else: no latency threshold, no PROMOTE/STOP statement, no rule about how the
   two counterbalanced pairs combine. Task 230 preregistered an explicit
   conjunctive rule — both independent pairs must improve by ≥5.0% *and*
   ≥0.50 ms, no tie-break — and it took two review rounds to get that rule
   right *before* the numbers existed. Preregister the equivalent here: which
   metric decides, at which scale, by how much, in which arms, and what a split
   result (one pair improves, one does not) means. Without it the packet cannot
   produce a defensible verdict.

2. **No storage measurement at any scale.** Task closeout requires recall +
   latency + **storage** at 10k/50k/100k; this matrix measures the first two.
   Add the storage capture, and state the layout arithmetic as a prediction
   first: at the staged 1,536-dimension corpus with `graph_degree = 32` and the
   RaBitQ code stride, compute `node_record_bytes`, `node_stride_bytes`,
   `extent_blocks`, and the resulting per-node padding waste. A node that
   exceeds `BLCKSZ` is rounded up to a whole number of 8 KiB blocks, so at
   these dimensions every node occupies a fixed multi-block extent with dead
   space in the last block, and both the storage ratio and the per-visit read
   volume follow directly from that arithmetic. Predict it, then let the run
   confirm or falsify it — that is this repo's own rule, and it is also the
   most likely place this layout loses.

3. **Overlay growth from the Task 167 DML path is unmeasured.**
   `task229_dml_benchmark: true` measures mutation *latency*, not raw-store
   *growth*, and packet 004's overlay model appends a complete node stride per
   amendment — one insert that amends `R` backlink targets appends `1 + R` full
   nodes, none reclaimable until rebuild, against a control that updates in
   place and vacuums. Either capture node-store bytes before and after the DML
   benchmark, or state explicitly that overlay growth is out of packet 005's
   scope and name the packet that owns it.

4. **The recall floors need a stated basis.** 0.995 at 10k, 0.98 at 50k, and
   0.90 at 100k is a steep ladder with no derivation, and Task 230's 50k
   0.980 floor was missed by **all four arms**, which cost that packet a round
   and had to be re-read as a harness limitation rather than a candidate
   property. Anchor each floor to a measured control recall from a recent head
   on this lane. Also state the direction explicitly: fixed-stride serves the
   same vectors and the same adjacency, so it is expected to be
   recall-*neutral* — any inter-arm delta beyond the control-versus-control
   spread is a defect to investigate, not a trade to accept.

5. **`data_checksums` is not asserted anywhere in the suite.** Packet 003
   seq-06 committed to recording and asserting it because the default fast
   decoder deliberately relies on PostgreSQL's whole-page checksum for
   payload-bit corruption detection. The config has no precheck step at all —
   the canonical lane configs open with `precheck-host`. Add one that captures
   `SHOW data_checksums`, `version()`, `shared_buffers`, and the extension build
   profile, with a threshold on the checksum setting.

6. **State the beam-width regime.** Every step runs `beam_width: 4`,
   `hop_rounds: 100`. Task 203 recorded that BW=4/H=100 is the *drifted* regime
   rather than the paper's wide-beam regime, and NFR-021/022 exist because of
   that finding. A layout verdict measured only at BW=4 needs either a stated
   argument that the conclusion transfers to the corrected regime, or one
   wide-beam arm at 100k to show it does.
