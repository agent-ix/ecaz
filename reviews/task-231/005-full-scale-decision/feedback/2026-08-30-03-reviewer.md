## Remaining — 1 item

1. **Nothing verifies that the controlled-cold protocol actually evicts the
   benchmark relations.** `task231_control_shared_buffer_residency` builds an
   unlogged churn relation at 2.5× `shared_buffers`, scans it, drops it, and
   gates only on the relation's *size* (`relation_bytes >= 2 ×
   shared_buffers`). Size is a proxy for eviction, not evidence of it, and the
   mechanism named in the code comment is the wrong one: PostgreSQL's
   `initscan` switches to the `BAS_BULKREAD` strategy once a relation exceeds
   `NBuffers / 4`, so the full sequential read the comment relies on cycles
   through a 256 KiB ring and displaces almost nothing. What does most of the
   displacement is the preceding `INSERT ... SELECT`, whose pages are allocated
   through the normal clock sweep. The outcome is probably right, but the
   emitted `pass=true` asserts a residency property that is never measured, and
   12 of the 27 steps depend on it.

   Make it measured rather than inferred, either way:

   - **Simplest and airtight:** restart each node (`pg_ctl restart`) between
     the build and the timed cold arm. Shared buffers are empty by
     construction, the OS page cache stays warm, and that is exactly the
     residency level the profile name claims.
   - **Or measure it:** `CREATE EXTENSION pg_buffercache` and count buffers
     belonging to the generation relations immediately before and after the
     churn, requiring approximately zero after, with the counts in the
     `physical_benchmark_residency_control` row so `pass` reflects a
     measurement.

   Either fix also lets the code comment state the real mechanism. This does not
   touch the PROMOTE/STOP rule — the cold arms are mechanism evidence only — but
   without it those twelve steps may quietly be warm runs labelled cold.
