Reviewed code checkpoint `08075a341274f9f76df018f503af912d6d95b0e5` against
request `166062b31` and the committed artifacts. GitHub ticket: issue #97.
`be7264b5a` (fixed-stride decision-runner instrumentation) landed afterwards

The overlay model is the right shape: raw WAL append first, MVCC directory
publication second, no in-place rewrite of a Published base node, tombstones
that preserve vector/locator/code/adjacency, and full verification
(`read_node_verified`) on every mutation read plus a row-locator cross-check
against the directory row. Ordering, abort-tail reuse, and the reclaim/rollback
path all hold up. Four items below; 1 is a correctness defect and 2–3 will
decide whether Packet 005's DML numbers mean anything.

## Remaining — 4 items

1. **Ordinal allocation is snapshot-dependent and can hand two writers the same
   ordinal.** `next_fixed_stride_ordinal` derives the tail from
   `SELECT max(node_ordinal) FROM {graph_name}`. The `ShareRowExclusiveLock`
   serialises writers, but it does not fix *visibility*: under REPEATABLE READ
   or SERIALIZABLE the second writer's snapshot was taken at transaction start,
   so after it acquires the lock the `max()` still cannot see the first
   writer's committed directory row. Both allocate ordinal *N*; both pass their
   own *N* as `unpublished_tail_floor`, so `write_node` accepts both writes and
   the second overwrites the first's raw node while both directory rows stay
   `is_current` for different `vec_id`s. One vec_id then serves another's
   vector and adjacency, silently. READ COMMITTED happens to be safe because
   each statement takes a fresh snapshot — the correctness must not rest on the
   caller's isolation level.

   Allocate from physical state under the same lock instead:
   `main_fork_block_count_handle` (with the layout's packing arithmetic) or a
   tail counter in the EFM1 block are both snapshot-independent, and the raw
   relation is already the authority for what has been written. A regression
   test should run two concurrent `REPEATABLE READ` inserts.

2. **Every mutation full-scans the directory.** The only index on the graph
   relation is `UNIQUE (vec_id) WHERE is_current`, so `max(node_ordinal)` —
   which deliberately spans historical rows — is a sequential scan of the whole
   directory on each insert, replacement, tombstone, and backlink amendment. At
   100k base nodes with degree `R` backlink amendments per insert, one inserted
   vector costs `1 + R` full scans. That cost is an artifact of the allocation
   strategy, not of the fixed-stride layout, and it will dominate any Task 167
   DML measurement in Packet 005. Fixing item 1 by reading the physical tail
   removes this at the same time; if you keep an SQL-derived tail, it needs its
   own index.

3. **Overlay write amplification needs to be preregistered as a measured axis,
   not discovered in the run.** Every amendment appends a *complete* node
   stride: at 1,536 dims / degree 64 that is roughly 10 KB per amendment, and a
   single insert that amends `R` backlink targets appends `1 + R` full nodes —
   order 650 KB of raw store per inserted vector — none of it reclaimable until
   the generation is rebuilt. The graph-heap control updates its record in place
   and lets vacuum reclaim. Task closeout requires storage evidence, so Packet
   005 must measure DML-driven raw-store growth per insert alongside recall and
   latency, and the packet should state the expected growth arithmetic up front
   so the measured number can confirm or falsify it. This is the packet's
   biggest exposure and it is not mentioned in the request.

4. **Take the mutation lock once per context.** `lock_mutations` is called
   inside `append_fixed_stride_node`, so a transaction that appends `1 + R`
   overlays calls `LockRelationOid` that many times and never unlocks. The
   effect is only local lock-refcount churn, but the intent — one
   transaction-scoped lock, deliberately never released — reads better if it is
   acquired in `FixedStrideDmlContext::open` with the comment attached there.

## Reviewer-focus questions, answered

- **Raw-WAL-before-MVCC-publication ordering:** correct. The raw append is
  durable and non-transactional, the directory row is transactional, and an
  abort therefore leaves an unreachable tail ordinal that the next writer
  reuses — which is exactly what `write_node`'s floor argument permits and
  nothing else. Ready evidence is unaffected because packet 003 seq-06 made the
  packed committed digest prefix-exact; the two designs fit together.
- **Snapshot visibility after the ordinal lock:** this is item 1. The lock is
  correct; the snapshot-derived `max()` is not.
- **Abort-tail reuse:** correct, including in the packed case — the first
  truncated ordinal is `ordinal + 1`, never below the floor, so a rewind can
  only discard slots from the aborted attempt.
- **Exact-vector preservation through amendments:** correct.
  `current_graph_node_for_update` carries `Some(fixed.exact_vector)` out of the
  verified raw read, `persist_graph_node_amendment` errors rather than
  fabricating if it is absent, and the insert path passes the genuinely new
  vector. Tombstones keep vector, locator, search code, and adjacency.
- **Lock ordering across owners:** no new hazard. Each owner generation has one
  raw relation and every local writer takes that single lock, so there is no
  local ordering to get wrong; the cross-owner ordering remains the existing
  2PC handoff sequence, which this checkpoint does not change.
