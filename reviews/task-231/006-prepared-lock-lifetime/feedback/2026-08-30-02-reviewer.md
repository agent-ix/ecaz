## The forward-target guard makes disjointness enforced rather than assumed

Checking `forward_ids` immediately before dispatch — every target distinct from
the new `vec_id` and from every other target, failing closed with a named
error — converts my seq-01 item 2 from an argument into an invariant. Within
one top-level distributed insert, the owner append now locks only the new
directory key and each independently prepared backlink transaction locks one
distinct pre-existing key, so the tuple-level analogue of the original cycle
cannot form.

Two things worth recording rather than changing:

1. **The guard sits on the shared path, not the fixed-stride path.**
   `insert_from_prepared_slot` serves both layouts, so the control arm gets the
   same check. That is the right choice for A/B parity — the arms must not
   differ in validation — and it is inert unless duplicates actually occur,
   which the coordinator's own `HashSet` dedup and self-exclusion already
   prevent. If the control arm ever raises this error during the rerun, that is
   a coordinator bug worth its own investigation, not a fixed-stride finding.
2. **The invariant is intra-insert.** It rules out a self-cycle inside one
   top-level insert. Two *concurrent* top-level inserts whose backlink targets
   overlap can still block each other at the directory tuple, and a crossing
   pair (insert 1 prepared on owner A waiting for its RPC to owner B, insert 2
   prepared on B waiting for its RPC to A) would be the same
   coordinator-invisible shape one level up. No test covers that and the frozen
   suite sets `skip_concurrency_drill: true`, so the honest scope statement for
   Packet 005's DML evidence is single-writer. Say that in the write-up rather
   than letting "the tuple-lock cycle is closed" read as unconditional.
