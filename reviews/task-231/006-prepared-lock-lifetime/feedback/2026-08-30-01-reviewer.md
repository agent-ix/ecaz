# DONE — Task 231 packet 006 (prepared-transaction lock lifetime)

Reviewed code checkpoint `fc4a4292681715d899a80d7df251955b5de6f711`, request
`bdd972207`, and the run diagnostic committed under packet 005. GitHub ticket:
issue #97. The correction is sound and the regression pins the property that

## The diagnosis

The stall is a real distributed deadlock, not a hang. Owner 2 held
`ShareRowExclusiveLock` on its raw node store inside a **prepared**
transaction; the coordinator then sent `ec_distann_apply_physical_backlink` to
that same owner in a separate transaction; the second backend blocked on the
self-conflicting lock that only the coordinator's commit callback could
release, while the coordinator waited for that RPC. PostgreSQL's detector
cannot see the coordinator edge. The `pg_prepared_xacts` / `pg_locks` capture
proves the cycle rather than inferring it, and declaring the arm invalid
instead of salvaging its numbers is the right disposition — as is restarting
every arm on one corrected SHA rather than reusing the completed control.

## Why early unlock is safe here

I verified the argument rather than taking it: allocation authority is the
*physical* tail, so the lock only needs to span tail-read plus appends, which
it still does.

- The explicit lock is acquired once in `open` and released in `Drop`, so no
  two contexts can interleave a tail calculation with an append.
- A raw append is a relation extension plus a WAL'd page write, visible to
  every backend immediately and independent of commit. A writer entering after
  the unlock therefore reads a tail that already accounts for the earlier
  context's extents and cannot re-allocate them.
- An abort leaves those extents as unreachable ordinal gaps, which is the
  monotonic gap-preserving contract packet 004 seq-02 already accepted.
- Packed pages are read-modify-written under the buffer content lock, so
  appending slot k+1 to a page holding an uncommitted slot k preserves those
  bytes.
- Moving construction ahead of `read_metadata` so a metadata-admission failure
  drops the context is a real improvement, not cosmetic: it converts a lock
  held to transaction end into one released on the error path.

## The regression test does pin the defect

The strengthened `test_distann_fixed_stride_repeatable_read_ordinal_allocation`
replaces its sleep with channel handshakes and asserts that writer 2 completes
its append **before** writer 1 is allowed to commit. Under the old
transaction-scoped lock writer 2 would block and the assertion fails; under the
correction it passes with distinct ordinals 1 and 2. That is the essential
property — the lock must not outlive the mutation context — and it is now
guarded by a test rather than by the benchmark. Receipt verified in the
committed artifact: `4 passed; 0 failed`, and PG18 clippy clean.

## Carried into the packet 005 restart

None of these block this packet; they are what the rerun has to show.

1. **The field proof is the rerun.** No fixture reproduces the full coordinator
   sequence, so `task231-warm-10k-a-fixed-second` completing the routed 160-row
   insert workload from a fresh fixture is the evidence that closes this
   defect. Say so explicitly in the packet 005 write-up rather than treating
   the unit receipt as the proof.
2. **Watch for the same cycle one level down, at the tuple lock.** A backlink
   amendment does `SELECT … WHERE vec_id = $1 AND is_current FOR UPDATE` and
   `publish_fixed_stride_overlay` retires the prior row with an `UPDATE`. If a
   still-prepared transaction from the same top-level insert already touched
   the row a later RPC targets, the second backend blocks on that tuple lock
   with the same invisible coordinator edge. The row-heap control ran the
   identical workload to completion and both arms amend one row per target, so
   this is probably not reachable — but if the rerun stalls again, capture the
   same read-only `pg_locks` / `pg_prepared_xacts` evidence before killing it;
   that diagnostic was what made this defect solvable in one pass.
3. **A prepared-transaction variant of the fixture would be worth having.**
   The current regression proves the lock is released before commit; it does
   not exercise `PREPARE TRANSACTION` followed by a second mutation RPC to the
   same node store. If item 2 ever fires, that variant is the test to add.

## Note

`Drop` does not run when an append raises a PostgreSQL `ERROR`, because that
unwinds by longjmp rather than Rust unwinding. Harmless here — the transaction
aborts and the lock goes with it — but worth knowing if this release ever
becomes load-bearing on an error path.
