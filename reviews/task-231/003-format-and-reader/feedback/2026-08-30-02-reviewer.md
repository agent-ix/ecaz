## Remaining — 6 items

1. **The renamed telemetry has no consumer.**
   `generation_read.rs:432` is `let _ = telemetry;`, and
   `logical_blocks_touched` / `logical_bytes_touched` appear nowhere else in
   `src/`. Finding 4 asked for honest labelling, not for the counter to be
   dropped — as it stands Packet 005 has no extent-touch evidence at all.
   Route it into the `distann-head-attribution-benchmark` stage counters
   alongside the `ExactVectorReads` / `ExactVectorBytes` records you already
   emit there.

2. **`fixed_exact_vectors` grows without bound for the life of the scan.**
   `RetainedGenerationScan` (`generation_read.rs:1409`, inserted at 2599) keeps
   `HashMap<u64, Vec<f32>>` of every exact vector the scan has ever decoded,
   never cleared or capped, and each insert is a fresh `vector.clone()`. At
   1,536 dims that is 6 KiB per distinct node touched — a traversal covering
   20k nodes holds ~120 MB per backend, and the clone is a per-node copy on the
   measured path. The live `GenerationExpander` path does this correctly
   (`record.exact_vector.as_deref()`, batch-scoped). Scope the retained path
   the same way, or clear the map per batch once
   `local_source_vector` has consumed it.

3. **Batch dedup is O(n²) on the fixed-stride path.**
   `generation_read.rs:330-332` linear-scans `fixed_directory_entries` for every
   requested `vec_id`, where the graph-heap path uses `records.contains_key`.
   At beam width 8 × degree 64 that is ~262k comparisons per hop, purely to
   deduplicate. Use a `HashSet<u64>` (or insert a placeholder into `records`)
   so the two arms differ in storage, not in dedup complexity — otherwise the
   A/B carries an artificial handicap.

4. **With verification off, corrupt payload bytes are returned silently.**
   The default path checks magic, version, header length, flags, reserved
   bytes, and ordinal/vec_id identity, but not the node or page digest, and not
   the padding. A flipped bit inside the exact vector or neighbor codes
   therefore produces silently wrong distances. That is a defensible trade only
   if PostgreSQL page checksums are on, since they cover the whole block
   including the raw region. Please state `data_checksums` for the bench and
   fixture clusters in the packet manifest, and assert it in the PG18 fixture
   so the guarantee is pinned rather than assumed.

5. **The packed-page retry guard moved entirely into the caller.**
   `fixed_stride_store.rs:458` relaxed the check to
   `envelope.slot_count < slot_index`, so rewriting slot *k* on a page that
   already holds more slots is accepted, and `payload.resize(required, 0)` at
   line 474 then *truncates* the page to `slot_index + 1` slots and lowers
   `slot_count` — silently discarding the later slots. Today the only thing
   preventing that from dropping published nodes is the caller-supplied
   `unpublished_tail_floor`, which `handoff.rs` passes correctly and the tests
   pass as `0`. Make it fail closed at the page level: reject the write unless
   every slot being truncated is itself at or above the floor.

6. **The committed-page digest may not be stable across a retried batch.**
   `committed_page_digest` accepts `envelope.slot_count > expected_slots` on the
   final page (`fixed_stride_store.rs:413` only rejects `<`), and hashes that
   page's stored EFS1 digest, which covers the extra slots. Raw pages are not
   MVCC-rolled-back, so an aborted staging attempt that wrote past the eventual
   committed count leaves those bytes behind; if the retry re-splits batches and
   commits fewer nodes on that page, the digest differs from a clean run of the
   same generation. Either state that the digest is only ever compared within
   one attempt, or make it prefix-exact — zero the tail beyond the committed
   count, or hash the committed slot bytes instead of the whole-page digest.
