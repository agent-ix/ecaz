## Blocking

### 1. Raw pages live in a `relkind='r'` heap, and `pd_lower` makes heapam read fake line pointers

`generation_store.rs` creates the node store as
`CREATE TABLE {qualified_node} (__ecdz_raw bytea) WITH (autovacuum_enabled=false)`,
and `fixed_stride_store::set_page_lower` then advances `pd_lower` to
`data_offset + payload_len` on every page.

For heapam, `PageGetMaxOffsetNumber` is `(pd_lower - SizeOfPageHeaderData) / 4`.
An 8 KiB EFS1 page therefore presents ~2000 line pointers whose contents are
arbitrary EFS1/node bytes. Everything that reads this relation through heapam
will follow those garbage `ItemId`s:

- plain `VACUUM` / `vacuumdb` (database-wide) — `autovacuum_enabled=false` does
  not stop manual vacuum;
- anti-wraparound autovacuum — `autovacuum_enabled=false` is explicitly ignored
  once `relfrozenxid` passes `autovacuum_freeze_max_age`, and this relation
  never advances `relfrozenxid` because nothing is ever inserted through
  heapam;
- `ANALYZE` block sampling, `pg_dump`'s `COPY`, and any `SELECT` on the
  auxiliary table by the index owner or a superuser.

Every other raw-page store in this repo writes into an **index** relation's
main fork (`ec_hnsw/build.rs`, `ec_hnsw/insert.rs`, `ec_diskann/insert.rs`,
`ec_spire/page.rs`, `ec_distann/ambuild.rs`). This packet is the first to put
raw pages in a heap, and the heap is what makes the `pd_lower` trick unsafe.

The `pd_lower` reasoning itself is right — `GenericXLogRegisterBuffer` with
`GENERIC_XLOG_FULL_IMAGE` still registers `REGBUF_STANDARD`, so the
`pd_lower..pd_upper` hole is stripped from the image. Two ways out:

- **Preferred:** back the node store with an internal index relation, matching
  the rest of ecaz, so no heapam path can ever open it.
- **Minimum:** set `pd_lower == pd_upper == SizeOfPageHeaderData`. The hole is
  then zero-length so the full page is still logged, while heapam sees
  `PageIsEmpty` and zero line pointers.

Either way, please state in the packet which scanners are believed to touch the
relation and why they are safe.

### 2. Verification cost sits on the per-node read path — the arm will measure SHA-256, not layout

`read_node` does, per node:

1. `read_metadata` — pin/lock block 0, `SHA-256` over the 160-byte EFM1 record,
   plus a full `layout.validate()` re-derivation;
2. `decode_locked_page` → `FixedStridePageEnvelopeV1::decode` — `SHA-256` over
   the page header **plus the entire page payload**, i.e. all packed slots, not
   just the requested one;
3. `FixedStrideNodeV1::decode_into` — `SHA-256` over the full node stride;
4. `layout.validate()` again inside `address`, `validate_shape`, and
   `decode_into` (each re-runs `with_page_shape` from scratch).

Reading one node from a packed page hashes roughly two page-fulls, and holds
the buffer content lock while doing it. At the paper regime this task is
chasing (BW=8, ~100 hops) that is tens of MB of SHA-256 per query, on the exact
measurement this task exists to produce. Task 231 cannot produce a meaningful
10k/50k/100k A/B in this shape.

Asks: admit EFM1 once per scan/generation open and cache the admitted layout
rather than re-reading and re-deriving it per node; make the page digest cover
the slot being read (or drop it and rely on PG page checksums plus the per-node
digest); put full verification behind an off-by-default debug GUC in the
NFR-020 drill style so the default path is arithmetic plus `memcpy`. Also
please add a microbench or `perf` line to the packet showing the per-node
decode cost with verification on and off — this needs a number, not a
prediction.

### 3. Adjacency stores neighbor `vec_id`s, so every hop still pays a B-tree plus heap tuple

`FixedStrideNodeV1` carries `neighbor_vec_ids: Vec<u64>` and no neighbor
ordinals. The in-progress read path confirms the consequence: it resolves
`SELECT vec_id, node_ordinal, row_tid` from the graph relation to get an
ordinal before it can address a node. Expanding one node's `R` neighbors
therefore costs `R` index probes plus `R` heap tuple deforms — the cost the
task set out to remove. The DiskANN property being replicated is that the
neighbor's address follows from the record itself; this format does not have
that property.

I recognise the likely reason: in a distributed roster, adjacency can reference
vec_ids that are not owner-local. So the question, not an assertion: what
fraction of adjacency is owner-local under DISJOINT-SHARD? If it is most of
them, store an owner-local ordinal (u32) per neighbor with an escape/flag for
remote vec_ids, and recover `vec_id` from the visited node's own header. That
is a V1 node-format decision, so please settle it before the handoff slice
freezes the layout digest.

### 4. Telemetry is labelled physical but counts logical block touches

`FixedStrideReadTelemetry { blocks_read, bytes_read }` is computed from
`extent_blocks` / `block_size`, so a buffer-cache hit counts as a read, and the
block-0 metadata touch from `read_metadata` is not counted at all. The
`request.md` and `manifest.md` wording ("reports physical blocks and bytes
read") will over-state I/O if packet 005 cites it. Either wire it to
`pgBufferUsage` read-vs-hit counters or rename the fields to say they are
logical extent touches.

### 5. Fail-closed matrix and catalogue lifecycle are untested through the relation

`fixed_stride_store_round_trips_packed_and_multiblock_nodes` covers the happy
path, the tail retry, and one wrong-`vec_id` rejection, on a table the fixture
creates itself. Task 231 P3 requires truncated, swapped-version, bad-padding,
wrong-ordinal, and digest-corruption cases to fail closed; right now those are
only proven on in-memory byte fixtures, not against real pages. Missing at the
relation level: missing/short multi-block segment, on-page node and envelope
digest corruption, wrong generation tag, block gap rejection, metadata
mismatch, and unpublished-slot read.

Separately, nothing exercises `create_generation_relations` /
`drop_generation_relations` / `validate_replay` for `node_store_relid`, so the
catalogued lifecycle the request claims ("lifecycle drop / rebuild
propagation") has no evidence behind it.

## Non-blocking notes

1. Packed append re-hashes every prior slot on the page, so filling a page is
   `O(n^2)` in digest bytes. Bounded by `nodes_per_page`, but worth a comment.
2. `write_node` re-verifies EFM1 for every node written; same fix as item 2.
3. If `buffer.block_number() != target` after a `P_NEW` extension, the
   extension has already happened and the error leaves a zeroed block behind.
   `open_data_block_for_write` also reads the block count and then extends with
   no extension lock — fine for a single-writer build, but the invariant should
   be asserted or documented.
4. `decode_into` mutates `out` before the padding checks, so a rejected node
   leaves partially decoded state in a reused buffer. Callers must not read
   `out` on `Err`; worth stating on the method.
5. The `node_storage_layout='fixed_stride'` reloption is accepted at this HEAD
   even though the handoff writer and production read path are not landed, so a
   `CREATE INDEX` with it set fails part-way through the build. Gate it or say
   so in the packet.

## What I checked and found correct

- `with_page_shape` arithmetic, alignment rounding, and the packed /
  one-page / multi-block classification, including `nodes_per_page == 0` as the
  multi-block discriminator.
- `validate()` re-derivation as the drift gate, and its use on every decode.
- Version-first admission ordering in the layout, node, page-envelope, and
  EFM1 decoders, and rejection of unknown flag bits and non-zero reserved
  bytes.
- Digest zeroing symmetry between `encode` and `decode` for node, page, and
  metadata records; domain separation per record type.
- Page envelope binding to `block_number`, `generation_tag`, and
  `node_stride_bytes`, and the packed `base_ordinal % nodes_per_page` check.
- `read_page_region` bounds checks before the `from_raw_parts`, and the
  `content_bytes`-from-header read being bounded by page size before the digest
  is verified.
- Reloption mutual exclusion with Tasks 229/230 and the
  `distributed_control=true` requirement.
- Catalogue plumbing for `node_store_relid`: nullable with `<> 0` check,
  `UNIQUE`, replay validation that the catalogued store matches the descriptor,
  internal dependency recording, and drop ordering before the graph store.
