## Code review

### `unique_prefetch_blocks` (scan.rs) — correct

Replaces the `HashSet<u32> seen_blocks` + `Vec` pair with a single
`Vec` and a linear `contains` scan. For HNSW neighbor expansion the
neighbor count is bounded by `m` (16 here), so a linear scan over
≤16 blocks beats allocating + hashing a HashSet per expansion. Behavior
preserved: first-seen order kept, `INVALID` skipped. The new unit test
(`unique_prefetch_blocks_keeps_first_block_order_and_skips_invalid_tids`)
covers ordering and INVALID skipping. The `with_capacity(block_count)`
on the result map is a free win. Good.

One thing to confirm (not a blocker): the helper is gated
`#[cfg(any(test, feature = "pg18"))]`. That is consistent with the
ReadStream-based graph prefetch being PG18-only, but please confirm a
`--no-default-features --features pg17` build doesn't reference
`unique_prefetch_blocks` from a non-gated caller. If `prefetch_graph_buffers`
is itself pg18-gated, this is fine.

### `forget_queued` (search.rs) — correct

Replaces `find().copied()` + `retain(!= node)` (two passes) with
`position()` + `remove(position)` (one search + one shift). I verified
the equivalence rather than trusting it: `discovery_order` is only ever
appended via `push_candidate` (search.rs:495), which guards on
`self.visited.insert(candidate.node)` returning true — so a node
appears in `discovery_order` **at most once**. `remove(position)`
(removes the single match) is therefore exactly equivalent to
`retain(!= node)` (removes all matches) under that invariant. The
subsequent `visited.remove(&node)` is unchanged, so re-discovery still
works. Correct.

Suggestion: add a one-line unit test for `forget_queued` (remove a
queued node, assert the returned candidate and that `discovery_order`
order is preserved). The correctness depends on the
"unique node per discovery_order" invariant, and a test would pin it so
a future change to `push_candidate` can't silently break this.

## Carry-forward 1: latency-win claim is in the noise

The request states 10k/50k "show lower latency at the same recall."
These are constant-factor changes on ≤16-element collections; the
wall-clock effect is almost certainly below the run-to-run variance I
documented in
`reviews/task-59/005-no-visited-checks/feedback/2026-05-24-01-reviewer.md`
(focused-vs-final runs of identical DiskANN code differed ~12–15%).
The 50k rows here are clean and monotonic (p50 1.23→3.99 ms across
ef 40→200, recall 0.870→0.919) but there is no same-head A/B against
the baseline at matched `cache_state` to support a latency-delta claim.

Frame these as **allocation/overhead reductions** (fewer HashSet allocs
per expansion, one fewer pass in forget_queued) — which they
demonstrably are — not as a measured latency win, until a
`cache_state`-matched A/B shows a delta larger than the noise band.
Recall is unchanged, as expected (dedup ordering and queue removal
don't change graph results).

## Carry-forward 2: 100k failed on disk space — C4 materialized

`artifacts/ssm-100k-failure.json` records the 100k load failing with
`No space left on device`. This is exactly the risk I flagged as **C4**
in the baseline feedback
(`reviews/task-61/001-aws-hnsw-graviton-baseline/feedback/2026-05-24-01-reviewer.md`):
HNSW's ~3x-larger index plus staged per-scale corpus copies exhaust the
`10k-medium` volume. This is now the **third** AWS run on this host
class blocked by disk (DiskANN 1M twice, HNSW 100k now).

This has stopped being a per-run nuisance and is now a systematic
blocker. Per `memory: feedback_aws_bench_sizing`,
`feedback_benches_must_be_repeatable`, and `feedback_no_recreate_corpus`:
fix it at the infra level before the next HNSW scale-up —

- size the DB volume for the largest scale the suite targets (HNSW 100k
  index ≈ 130 MiB + 6 GB raw corpus per scale; 1M will need
  substantially more), and/or
- drop each scale's tables before loading the next instead of retaining
  all per-scale copies simultaneously, codified in the suite/runner so
  it is repeatable rather than hand-cleaned.

The repeated `cloud-cleanup-*` / `drop-*-partial` artifact trail across
both task 59 and 61 is the signal that the staging path needs to be
codified, not re-improvised each run.
