## Bottom line

**Baseline is usable, with one significant caveat: the recall ceiling
looks capped by the build config, not by HNSW.** Before this baseline
is used as the reference to optimize against, confirm whether `m=16`
is the intended product config or just a first-pass default — because
the recall numbers below are low for HNSW and will mislead any
"HNSW vs DiskANN/IVF" comparison if taken at face value.

## Concerns

### C1. Recall ceiling of 0.912 at ef=200 is low for HNSW — likely an m=16 artifact

HNSW at 1536-dim normally reaches 0.99+ recall@10 with adequate `m`
and `ef_search`. This baseline tops out at **0.912 at ef=200** and is
still climbing, which strongly suggests the graph is under-connected
(`m=16`) rather than that the search is saturated. For comparison on
the same corpus family:

- ec_diskann pq_fastscan 100k: 0.9865 recall@10 at list_size=800.
- ec_ivf rabitq 1M: 0.9864 at nprobe=128.
- the comparator manifest's pgvector HNSW used ef sweeps to reach
  ~0.97–0.99.

If `m=16` is a deliberate small-index choice, fine — but then the
baseline should say so and the recall deficit should be framed as a
size/recall trade, not as HNSW's achievable recall. If it's just a
default, raise `m` (e.g. 32/48) and/or extend the ef sweep until
recall plateaus before declaring this the reference curve. Otherwise
every downstream "HNSW is worse on recall" conclusion will be an
artifact of the build param.

### C2. Index is ~3x larger than DiskANN at the same scale

130.2 MiB at 100k (1365 B/row) vs ec_diskann 46.1 MiB (483 B/row).
Expected — HNSW stores full f32 vectors inline plus the graph — but
worth stating explicitly in the manifest so the size axis is on the
table next to recall/latency. This is the structural reason HNSW will
lose the storage comparison to the quantized AMs; it should be named,
not left implicit.

### C3. cache_state label present, but labeled-warm rows still carry a cold first query

Good: the latency rows carry `cache_state = post_recall_warm` (the
007 work applied here too). But the `ef=40` row has stddev 4.80 ms and
max 64.4 ms against a p50 of 1.52 ms — i.e. the first timed query was
cold despite the warm label. The label documents intent; it does not
discard the cold sample. Same warmup-discipline gap noted in the
Task 59 008 feedback and task-51/027/01 Gap B. Not a blocker for a
baseline, but the p95/p99 on the low-ef rows are inflated by it.

### C4. 100k run required manual disk cleanup (same pattern as Task 59)

The artifact trail (`cloud-cleanup-after-100k-failure`,
`drop-50k-partial`, `cloud-bench-drop-loaded-tables`,
`cloud-cleanup-restart-postgres`) shows the same hand-cleaned
disk-space dance that blocked the DiskANN 1M run. HNSW's 3x-larger
index makes this worse at scale. Before attempting 1M HNSW, codify
the staging/teardown path (volume sizing or drop-between-scales) so it
is repeatable — per `memory: feedback_benches_must_be_repeatable` and
`feedback_aws_bench_sizing`. Otherwise the 1M HNSW run will hit the
wall the DiskANN run did, only sooner.

## What's good

- Same suite shape, same reporting columns, `cache_state` present —
  consistent with the DiskANN lane, so cross-AM comparison is
  mechanically possible (subject to the m=16 caveat).
- Latency curve itself is clean and monotonic in ef, with tight
  stddev once past the cold first query (ef≥64 stddev ~0.5–0.9 ms).
- p50 latency is competitive (1.5–5.2 ms at 100k), faster than
  DiskANN at matched scale — which is the expected HNSW strength and
  the reason to keep it in the matrix.

## Asks before this is the optimization reference

1. Confirm `m=16` is intended; if not, rebuild at higher `m` and
   extend the ef sweep until recall plateaus, so the recall ceiling
   is real and not a build-param artifact (C1).
2. Add the index-size row to the manifest's headline comparison so
   the size axis is explicit (C2).
3. Codify the disk staging path before any 50k/100k/1M HNSW scale-up
   (C4).
