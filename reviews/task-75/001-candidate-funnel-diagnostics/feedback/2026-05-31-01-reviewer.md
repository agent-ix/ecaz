# Task 75 packet 001 — diagnostic surface

## Decision

**Request changes before this packet, packet 002, or packet 003 can be
accepted.** The diagnostic SQL function `ec_spire_index_scan_leaf_candidate_snapshot`
returns counts that do not vary across queries for `top_graph_search_list_size >= 32`
and that do not match the suite runner's own pipeline counters. Because
Task 75's Phase 2 decision (packet 002) and closeout (packet 003) rest on
those counts, the rest of the chain needs to be re-evaluated after the
diagnostic is fixed.

## Load-bearing finding — diagnostic SQL is query-invariant for tg >= 32

Spot-checked the funnel JSONL in
`benchmarks/task75-intel-local-routing-envelope/artifacts/`:

| tg | query 1 candidates | query 100 candidates | query 200 candidates |
| ---: | ---: | ---: | ---: |
| 16 | 12,397 | 11,952 | 13,625 |
| 32 | 16,061 | 16,061 | 16,061 |
| 64 | 16,061 | 16,061 | 16,061 |
| 96 | 16,061 | 16,061 | 16,061 |
| 128 | 16,061 | 16,061 | 16,061 |

For tg=16, the per-query counts vary naturally with the query vector,
which is what the SQL function is supposed to do.

For tg=32/64/96/128, **every single query in a 200-query run returns
exactly identical counts**: 20 routes, 16,061 candidates, 16,036
truncated, 25 retained, 10 returned. That's not how a per-query
diagnostic against a real workload should behave — different queries
route to different leaves with different per-leaf row counts.

The CLI call site looks query-dependent
(`crates/ecaz-cli/src/commands/bench/spire_pipeline.rs` calls
`query_leaf_candidate_rows(&client, &index, &query.source).await`
inside the per-query loop), and the SQL function does pass `query`
into `scan::collect_single_level_scan_placement_diagnostics`. So the
query-invariance is most likely happening inside
`collect_single_level_scan_placement_diagnostics` when the routing
draft saturates the leaf set — possibly the diagnostic enumerates the
full reachable leaf set regardless of which leaves the query would
actually score.

Until the diagnostic SQL is fixed so its counts vary per query (the way
they do at tg=16), Phase 2's "0.18% retained/candidate" reading is
measuring the diagnostic's behavior, not the production scan's
behavior.

## Cross-channel disagreement reinforces the finding

For tg128 b0 nprobe=96, the **suite runner pipeline counters** show:

- `leaf_route_sum = 3,556` over 200 queries → `17.78` routes/query average
- `candidate_sum = 2,784,952` over 200 queries → `13,924.76`
  candidates/query average

The **per-query diagnostic SQL** shows:

- `leaf_route_count = 20` every query (200 × 20 = 4,000, not 3,556)
- `candidate_count = 16,061` every query (200 × 16,061 = 3,212,200,
  not 2,784,952)

The diagnostic is reporting ~15-30% higher counts than the suite runner
counters. The suite-runner numbers are query-dependent (variation is
hidden in the sum, but the per-query average isn't 17.78 routes
identically). The diagnostic numbers are query-invariant. They're
measuring different things.

## Code-level notes (non-blocking)

### N1 — `--funnel-output` + `--production-read-only` check fires too late

In `spire_pipeline.rs` the error path

```rust
if args.production_read_only && args.funnel_output.is_some() {
    return Err(eyre!(
        "--funnel-output requires SQL-visible local pipeline diagnostics; remove --production-read-only"
    ));
}
```

is at the bottom of the function, after the per-query loop has already
run. The in-loop `if args.funnel_output.is_some() && !args.production_read_only`
silently skips the diagnostic, then the post-loop check refuses to write
output. Move the check to the start of the function so the flag combo
fails fast instead of running ~200 queries first and then refusing.

### N2 — `.expect("…")` on diagnostic counter casts will panic the backend

`src/lib.rs` does

```rust
i64::try_from(row.candidate_row_count).expect("candidate row count should fit in i64"),
```

…and similar for every counter. For diagnostic counts this will never
overflow in practice (counts of disk rows), but `.expect()` inside a
`#[pg_extern]` panics the PostgreSQL backend. For a diagnostic SQL
helper that's acceptable but loud; consider `pgrx::error!` or saturating
casts so a future caller passing an oversized object can't crash the
postmaster.

### N3 — `leaf_entry_if_routed` is unused

Defined in `scan/types.rs` but I don't see it called in the diff. If
it's planned for a follow-up, fine — otherwise drop it before clippy
catches it on a future warning gate.

## What's good

- Clean separation of the SQL function from the bench tooling — the
  diagnostic is reusable for other investigations.
- JSONL artifact format is reviewer-friendly and machine-readable.
- `--funnel-output` is opt-in and behind `--production-read-only`
  semantics; doesn't slow the default bench path.
- Per-leaf candidate distribution fields (`leaf_candidate_mean/p95/max`)
  are useful even after the per-query issue is fixed.

## Required next action

Fix the query-invariance in
`scan::collect_single_level_scan_placement_diagnostics` (or whichever
layer is collapsing per-query routing into a query-invariant
enumeration) so that for tg >= 32 the per-query funnel counts vary the
same way they do for tg = 16. Then re-run the Phase 1 measurement and
re-evaluate packets 002 and 003.
