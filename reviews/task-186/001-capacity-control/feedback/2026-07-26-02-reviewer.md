# Task 186 packet 001 — provenance: the checked-in config did not produce two of its three arms

Second-pass finding, from cross-checking every committed `SuiteConfig` against the
`config_sha256` its run manifest recorded. This is new; it is not covered by
`004-full-scale-decision/feedback/2026-07-26-01-reviewer.md` or by the packet 005
correction.

## Finding (P1)

`artifacts/task186-capacity-control-100k-suite.json` as committed hashes to:

```
edbf80d33be171e7845507dd97450fad610d148d649eaf063bbcc797ce9deba8
```

That matches `run-cap16384/suite-manifest.json` (`config_sha256`), which records
three steps: cap-4,096 `skipped`, cap-8,192 `skipped`, cap-16,384 `succeeded`.

It does **not** match `run-benchmark-feature/suite-manifest.json`, which records:

```
config_sha256 87e59b638f1572abd609d04c03aa8600014d63ee624de2a531455f0487bbdad6
config       reviews/task-186/001-capacity-control/artifacts/task186-capacity-control-100k-suite.json
steps        trained-cap-4096-control-100k    succeeded  2358789 ms
             trained-cap-8192-candidate-100k  succeeded  2461788 ms
```

Same path, different content, only two steps. So the **cap-4,096 control and the
cap-8,192 candidate — the entire capacity trend, and the pre-registered gate that
authorized running 16,384 — were produced by a config that is not in the repo.**
The file was edited in place afterwards (the 16,384 step appended) and only the
amended version was committed. Nothing in the packet reproduces the run that
generated two of its three cited rows.

The task's own conditional structure makes an amendment legitimate: cap 16,384
"runs only if the 8,192 control shows a useful monotonic recall signal", so a
second config authored after seeing the 8,192 result is the intended flow. The
defect is that the amendment silently overwrote the pre-registration rather than
being added alongside it, which is exactly what NFR-007 provenance and the
"pre-register" language exist to prevent.

## Requested change

Commit the original two-step config as a separate file (e.g.
`task186-capacity-control-100k-suite.pre16384.json`) and record both SHA-256s in
`artifacts/manifest.md`, mapping each to the run directory it produced. If the
original is no longer recoverable, say so explicitly in the manifest and mark the
4,096/8,192 rows as produced by an unrecovered config — an honest gap is fine, a
silent mismatch is not.
