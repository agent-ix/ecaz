What does not hold up:

1. `physical_benchmark_post_insert_fresh_rebuild ... distinct_recall=0.541667`
   is not decision-grade. Both arms insert exact copies of the same corpus
   rows, so every parity query vector duplicates three rows in the table; the
   `md5(source::text)` `INTERSECT` collapses those to one key while the
   denominator stays a literal `10.0`. The per-query ceiling is 8/10, which the
   artifact confirms exactly (`max_distinct_recall=0.800000`). The `0.80`
   threshold is therefore reachable only by bit-identical top-10 agreement
   between two independently built ANN graphs.
2. `append_enabled_minus_disabled=0.000000` and the identical per-arm
   `0.541667` are not a measured null result. Ids `2000000..2000023` and
   `3000000..3000023` both map to corpus source offsets 0–23, so the two arms
   query the same 24 vectors against the same index. Packet 029's claim that
   parity attributes recall separately to the two arms does not hold for this
   fixture.
3. `benchmark_parity_queries: 48` in
   `artifacts/task167-final-real-suite.json` makes the held-out corpus arm
   `LIMIT greatest(48 - 48, 0)` = 0 rows. The gate is measured entirely on the
   degenerate population from (1); no ordinary query participates.
4. Consequently the packet's own framing — that the run "failed required
   post-insert physical-vs-fresh distinct-recall parity" — is not supported.
   The run neither demonstrates nor clears incremental graph quality loss.
   `min_distinct_recall=0.300000` is worth chasing, but with recall against
   exact brute-force ground truth for both graphs, not pairwise index overlap.
   Do not use this run's `physical_benchmark_recall ... 0.9990` as the
   counter-argument: that figure is roster-vs-no-roster on the same index and
   says nothing about incremental vs fresh.
