# Packet 020 — runtime and UPDATE evidence: CHANGES REQUESTED

Reviewed `406817f15` with `artifacts/cited-results.log`, `results.jsonl`,
`update-drill.log`, `suite-manifest.json` and `task167-physical-suite.json`.
The code review that accompanies this verdict is in
`reviews/task-167/022-overload-cleanup/feedback/2026-08-12-01-reviewer.md`;
this file records only the evidence findings, by their IDs there.

The matrix did run at 10k / 50k / 100k on the three-owner physical lane with
recall, latency, storage, insert A/B and drills, and the results trace to
`results.jsonl`. Nothing here is fabricated and the provenance chain is
intact. The problem is what four of the cited lines actually measure.

1. **AC-4 parity is a blended figure, not the inserted-neighborhood parity
   (P2-8).** `task167_post_insert_fresh_rebuild_parity` averages recall over
   200 queries — 48 inserted rows plus 152 ordinary held-out queries — and the
   string `inserted_neighborhood_queries=48` in the emitted line is a hardcoded
   literal, not a measurement. The request's claim that "fresh-rebuild parity
   used 48 distinct inserted neighborhood queries" does not match the code.
   Please report the 48 separately at each scale. The 0.9525 → 0.8920 → 0.8445
   trend is exactly where P1-1 (silently dropped cross-owner back-edges) would
   surface, so this is the number that decides whether AC-4 is met.
2. **AC-2 counters measure the plan, not the work (P2-7).**
   `backlink_amendments` is recorded as `forward.len()` before any amendment is
   attempted, so it is a duplicate of `forward_neighbors_selected` and cannot
   observe a skipped or dropped back-edge. Separately, all three scales report
   `forward_neighbors_selected=48` against `inserts=48` — a mean forward degree
   of exactly 1.0 with `graph_degree=32`. Please explain or fix that before
   citing it as the bounded-work demonstration; the fixture's
   `48 <= 32*48` assertion passes either way.
3. **Latency rows are contaminated (P1-4).** `physical_owner_routes` now
   resolves a conninfo for the local route, and three read-path sites use
   `conninfo.is_some()` as the is-remote discriminator. The coordinator was
   dialling itself over libpq for its own shard during these runs. The
   `mean_ms=18.30/22.30/20.90` rows are not comparable to the Task 165
   baseline until that is reverted and the arm re-run.
4. **Build profile is unverifiable, and the throughput numbers invite the
   question (P2-9).** The manifest records the driver as
   `/home/peter/.cargo-target/debug/ecaz` while asserting a release extension
   profile. 0.185 rows/s at 100k (~5.4 s per single-row insert) and 18-24 ms
   query latency are both consistent with a debug `.so` — the trap this repo
   has hit before. Please record the installed `.so` and its profile.
   Also note `beam_width=4, hop_rounds=100` is the regime Task 203 flagged as
   drifted; say whether that is deliberate here.
5. **Coverage gaps.** The UPDATE drill checks exactly one vec_id at one
   version transition. `physical_concurrent_insert_query` is one writer against
   four readers, so it does not test AC-6's concurrent *inserts* (P2-6). There
   is no routed DELETE + VACUUM drill at any scale, and that path does not
   currently work against a participant (P1-5).
6. **Process.** The bespoke `task167-physical-suite.json` needs its
   justification stated in `manifest.md` per CLAUDE.md. The lane genuinely
   needs a non-standard config; just say so.
