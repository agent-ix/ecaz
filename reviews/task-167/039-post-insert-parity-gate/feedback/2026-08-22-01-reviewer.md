## 1. The enforced parity gate is unsatisfiable by construction (P1)

`validate_task167_post_insert_parity` (`distann_multicluster.rs:3305`) requires
mean distinct recall ≥ `0.80`. The metric it validates cannot reach `1.0`, and
in this fixture cannot exceed `0.8`.

The chain:

- `measure_task167_insert_arm` (`:2988-3002`) inserts rows whose `source` is
  copied verbatim from the corpus:
  `SELECT {id}, ..., source, encode_to_ecvector(source, 4, 42) FROM
  {physical_corpus} ORDER BY id OFFSET {source_offset} LIMIT 1`.
- The append-disabled arm writes those copies at ids `2000000+k` and the
  append-enabled arm at `3000000+k`, both into `{physical_corpus}`. So for
  every source offset `k`, the physical table holds **three rows with byte-
  identical `source`**: the original, the `2000000` copy, and the `3000000`
  copy. `encode_to_ecvector(source, 4, 42)` is deterministic, so the embeddings
  are identical too.
- The parity query set is exactly those inserted rows (`:3206-3218`), so every
  query vector is an exact duplicate of three table rows.
- Both sides key hits on `md5(hit.source::text)` (`:3221`, `:3229`) and compare
  with `INTERSECT` (`:3243-3245`). The three exact duplicates occupy the top
  three slots of every top-10 and collapse to **one** distinct key. Eight
  distinct keys is the maximum on either side.
- The denominator is a literal `/ 10.0`.

Ceiling = 8/10 = 0.8. The packet-037 artifact confirms it exactly:
`max_distinct_recall=0.800000`, and not one of the 48 queries reaches 1.0.

Because the gate compares the **mean** against 0.80 and the per-query ceiling
is 0.80, the gate passes only if every query hits the ceiling — that is, only
if the incrementally-built distributed graph and a separately built local graph
return identical distinct top-10 sets for all 48 queries. That is not a
correctness property of incremental insert; it is a demand for determinism
across two different graph constructions.

Fix: divide by the number of distinct hit keys on the fresh (reference) side,
or dedupe both hit sets before the `INTERSECT`, then re-derive the threshold
from what the corrected metric actually reads on a known-good build. Add the
duplicate count to the emitted line so the ceiling is visible in the artifact.

## 2. `append_enabled_minus_disabled` is structurally zero (P1)

`id = id_base + trial * rows_per_trial + ordinal` and
`source_offset = trial * rows_per_trial + ordinal` (`:2986-2987`). For
`id_base=2_000_000`, ids `2000000..2000023` are trial 0, ordinals 0–23, source
offsets **0–23**. For `id_base=3_000_000`, ids `3000000..3000023` are also
trial 0, ordinals 0–23, source offsets **0–23**.

The `append_disabled` and `append_enabled` arms of the parity gate therefore
query with **the same 24 vectors**, against **the same index**, in the same
session, after both arms' rows are already in the graph — the
`debug_disable_append_when_room` GUC is not re-applied for the parity queries
and could not affect an already-built graph if it were.

`append_enabled_minus_disabled = 0.000000` and
`append_disabled_recall == append_enabled_recall == 0.541667` in the artifact
are not a measured null result; they are the only values this code can emit.
Packet 029's "parity attributes recall separately to the disabled and enabled
arms" does not hold.

Fix: either drop the arm split from this line entirely (and say so in the
manifest), or give each arm its own table + index built with the arm's GUC
setting so the comparison is real.

## 3. The parity gate never touches a normal query (P1)

`:3211-3213` adds the held-out corpus arm with
`LIMIT greatest({query_count} - 48, 0)`. The committed config
(`037-final-real-matrix/artifacts/task167-final-real-suite.json`) sets
`benchmark_parity_queries: 48` at all three scales, so that limit is **0**. All
48 parity queries are the pathological duplicate-of-inserted-row population
from §1; zero `physical_queries` rows participate.

Fix: raise `benchmark_parity_queries` so held-out queries dominate, and emit
the inserted-neighborhood and held-out populations as separate recall figures.
The inserted-neighborhood subset is worth keeping — it is the one that probes
the new rows — but it cannot be the whole gate.

## 4. The `0.541667` disposition is not supported either way (P1)

Given §1–§3 the number means "two ANN graphs agreed on 5.4 of a theoretical
maximum 8 distinct keys, on 48 queries chosen to be maximally degenerate." It
is not evidence of incremental graph quality loss, and it is not evidence
against it. `min_distinct_recall=0.300000` is a real signal that something
disagrees more than tie collapse explains, and it should be chased — but with
the right instrument.

Do not cite the same run's `physical_benchmark_recall ... 0.9990` as
reassurance. `recall_sql` (`:1320-1340`) compares `roster=''` against the full
roster **on the same table and the same index**; it measures distributed-
serving parity, not ANN quality, and says nothing about incremental vs fresh.

What would settle it: exact brute-force top-10 (seqscan, no index) as ground
truth, on one query set, then recall@10 of the incrementally-built physical
graph and recall@10 of the fresh rebuild reported side by side. If both land
near the same value, there is no quality loss regardless of how much they
disagree with each other.

## 5. `ec_distann_insert_work_reset` and `ec_distann_stage_scoring_reset` are
the same function (P1, evidence integrity)

`src/lib.rs:2002` and `src/lib.rs:2007` both call
`am::ec_distann::stage_counters::reset()`, which
(`src/am/ec_distann/stage_counters.rs:641-653`) zeroes `SCANS`,
`STAGE_ELAPSED_NS`, `STAGE_SAMPLES`, all of `MATERIALIZATION_WORK` **and** all
of `INSERT_WORK`.

Packet 038 states the two surfaces are separated. They are separated in the
CLI's control flow only; in the extension they share one global store and one
reset. The fixture calls `ec_distann_stage_scoring_reset()` from six places —
`physical_concurrency_drill` at `:9865` and `:10139`, plus `:2209`, `:2302`,
`:4992`, `:5031` — and every one of them also zeroes the Task 167 insert-work
counters. Today those all run outside the A/B window so the packet-037
measurement is intact, but any reordering silently zeroes the insert-work
counters mid-window, and the now-unconditional `inserts != expected_inserts`
check (`:3132`) converts that into a hard `bail!` on a run that was otherwise
fine.

Fix: add a reset that touches only `INSERT_WORK` and point
`ec_distann_insert_work_reset()` at it. If you would rather not change the
extension, say plainly in the manifest that the two SQL names alias one global
reset and that the drill ordering is load-bearing.

Related, please confirm rather than assume: `record_insert_work` fires only in
`src/am/ec_distann/physical_dml.rs`, and the counters are per-backend statics.
The CLI resets and snapshots through the coordinator connection. If any
owner-side backlink work executes in a remote owner backend, that work is
invisible to the coordinator snapshot, and both the `graph_degree × attempts`
bound check and the append A/B amendment comparison cover only the
coordinator's share. State which in the manifest.

## 7. Reviewed and accepted, with notes

**7.1 Snapshot lifetime fix (`15f7fcf5f`) — correct, no objection.** The
previous code bound the refreshed guard to a local
(`let retry_snapshot = Some(retry_snapshot); ... self.snapshot = snapshot.as_ptr()`)
that dropped at the end of `expand_nodes_masked`, leaving later traversal
rounds dereferencing unregistered snapshot storage — a genuine use-after-free
consistent with the observed
`TransactionIdFollowsOrEquals(xid, TransactionXmin)` abort. The fix stores the
guard in `GenerationExpander.retry_snapshot`
(`generation_read.rs:6013-6019`), so it outlives every use of the pointer.
Checked and satisfied:

- `:6256-6257` assigns `self.snapshot` from the new guard **before**
  `self.retry_snapshot = Some(...)` drops the previous one, so the pointer is
  never briefly stale.
- the helper's `None` path (`:437-446`) now leaves the caller's original
  snapshot in place instead of manufacturing a `latest()` it did not need;
  `RetainedGenerationScan` (`:2103-2105`) correspondingly keeps its existing
  guard, and rederives the pointer from it at `:1790-1794` and `:1991-1993`,
  so pointer and owner stay paired.
- the short-lived expanders constructed with `retry_snapshot: None`
  (`:1808`, `:2015`, `:4840`) return owned data only, so dropping their guard
  at end of scope hands no raw snapshot pointer back to the caller.

**7.2 Two Task 167 unit tests do not test their names.**
`task167_synthetic_vectors_are_unit_normalized` (`:11494`) asserts that the
generated SQL *contains the substring*
`sqrt(sum(component * component) OVER ())`. It would pass unchanged if the
expression divided by the wrong quantity, and it never evaluates a vector.
`task167_ab_workload_uses_the_preregistered_sample_size` (`:11487`) asserts
`TASK167_AB_TRIALS == 5` etc. — it restates the constants and would still pass
if `measure_task167_insert_arm` reintroduced local `TRIALS`/`ROWS_PER_TRIAL`
constants, which **is exactly the defect packet 031 was opened to fix**. The
regression is not pinned. Assert instead that the emitted `sample_rows` equals
the number of INSERT statements the arm actually issues, and verify
normalization once against PG (`sqrt(sum(x*x)) ≈ 1`) in fixture preflight.
The four `validate_query_stage_counter_feature` /
`validate_task167_post_insert_parity` tests are fine — they exercise real
functions at real boundaries.

**7.3 `record_retry_attribution` guard — right fix, wrong enabling
condition.** `generation_read.rs:352-360` correctly stops an absent fixture
relation from turning a recoverable visibility retry into an undefined-table
abort, and fully qualifying to `public.` removes the `search_path` dependency.

production scan into a writer, and that `Spi::run` INSERT raises in a

longjmps. Repo convention for debug surfaces is an off-by-default GUC

belt.

and the writer decrements the count on its error path so a failed writer
cannot hang the scanners.

**7.5 Vector normalization (`caa8ad63f`) — accepted.** Single shared
