# Task 167 packet 041 — instrument ACCEPT, absolute level NOT SETTLED

Verdict: **NOT DONE**, and the reason is narrow: the instrument's *design* is
accepted, its *absolute calibration* is not. Round verdict and full open-item
list are in
`reviews/task-167/043-exact-recall-disposition/feedback/2026-08-22-01-reviewer.md`.

## Accepted

Checkpoint `f83110078` replaces pairwise ANN overlap with exact brute-force
fp32 ground truth over the staged corpus plus the 320 rows the throughput arms
actually insert, scores both the incrementally-built physical index and a
reloption-matched fresh rebuild against that same truth, and verifies with
`EXPLAIN` that the two arms take `EcDistannDistributedScan` and a local
`Index Scan` respectively. Every one of findings 1–4 and 6 from the packet-039
feedback is addressed at the root rather than patched:

- per-query distinct-truth-key denominator, so 1.0 is reachable, with
  `truth_slots` / `truth_distinct_keys` / `truth_duplicate_slots` emitted so
  the duplicate load is auditable from the artifact;
- 48 inserted-neighborhood plus 152 held-out queries, with the step refusing
  to start unless held-out dominates, and the two populations reported
  separately;
- the structurally-impossible `append_enabled_minus_disabled` claim removed,
  with the reason stated (both arms share one physical index) instead of
  quietly dropped;
- `build_shards`, `head_construction` and `head_sizing_reloptions` threaded
  into the fresh index. With the default `build_shards=1` both indexes take
  the same monolithic deterministic Vamana path, so graph construction is not
  a confound; and because the fresh index is built *after* the 320 inserts
  from the same table, the comparison is exactly "N batch + 320 incremental"
  versus "N+320 batch" — precisely the FR-083-AC-4 question.

That design is what made the packet-042 product defect visible. The
`0.805382` reported here was a real finding, not the artifact its predecessor
was.

## Not settled

`physical_benchmark_recall` by 2.5 / 7.5 / 12.5 points at 10k / 50k / 100k,
with the gap growing by scale. Both claim recall@10 against exact truth on the
same corpus and query file. I ruled out the matching rule (fingerprint
matching is *more* generous than `bench recall`'s id matching, so it should
read higher), the query form (`encode_scan_query: false`), the beam/hop/heap
settings (config values coincide with extension defaults), the 320 extra rows,
and the 152-of-200 query subset. See §1 of the 043 feedback for what remains
and where to look.

`task167_ann_predictions` pins only `enable_seqscan`, `ec_distann.roster`,
`ec_distann.local_node_id` and `ec_distann.epoch`, while the recall child is
given roughly ten `--session-guc` values. Pin the same set here so the
measurement is reproducible from the committed config alone.
