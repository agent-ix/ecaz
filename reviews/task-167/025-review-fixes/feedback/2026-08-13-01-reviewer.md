## P1-1 — the gate is on the wrong function

`artifacts/exact-head-fixture-saturated.log`, the pre-gate repro:

```
role=writer writer=1 iteration=1 stderr=ERROR: ec_distann physical aminsert failed:
  [EC_RECORD_MISSING] physical generation RPC failed:
  [EC_RECORD_MISSING] retained physical generation lacks owned vec_id 0x29a26c9b2f0f8b74
```

That message string exists in exactly one place —
`generation_read.rs:1716` and `:1725`, both inside
`RetainedGenerationScan::resolve_nodes`. The message emitted by
`expand_nodes_masked` is different: `"physical generation {epoch} lacks vec_id
{...}"`.

The intent gate and the bounded retry were added only to
`expand_nodes_masked`. `resolve_nodes` still does a strict single lookup plus a
strict re-check, with no gate and no retry.

This matters because `resolve_nodes` is the owner-side node resolver behind the
**materialization** path (`generation_read.rs:1826`, `:1829`), which is what
`physical_dml::materialize_remote_vectors` reaches during insert planning — and
the repro failure is an `aminsert` failing on a remote RPC. It also backs the
traversal-replica chunk export (`:2300`, `:2336`) and gateway copies
(`:5185`, `:5285`), which have the same exposure.

So the run that passes at `f0bcb06f8` passes because that run did not hit the
race, not because the race is now handled. Both the failing and the passing run
report `churn_retries=Some(0)` — see P1-2 — so there is no positive evidence
the new code path ever ran.

Fix: apply the same gate + bounded retry to `resolve_nodes`, or lift it into a
shared helper both callers use, and then reproduce. The saturated log gives you
a repro recipe that already worked once.

## P1-2 — the retry counter cannot see the retry

`record_work(TraversalFrontierRetries, 1)` fires inside
`GenerationExpander::expand_nodes_masked`, which executes in the **owner's**
backend when it serves `ec_distann_expand_physical_nodes` over the RPC. The
fixture reads the counter on the **coordinator**
(`role=frontier_retry_counter ... output=0 steady_output=0`).

Stage counters are per-backend process state. A retry on an owner node can
never appear in a coordinator-side snapshot, so `churn_retries=0` is what this
assertion will report whether or not retries happen. It is consistent with the
counter reading 0 in the failing run too.

Fix: query the counter on each owner port — the fixture already opens owner
ports for the graph-store and tombstone checks — and require `churn_retries > 0`
during the churn wave. That single assertion is what converts P1-1's fix from
"the run was clean" to "the retry fired and recovered".

## P2-3 — the gate is broader and longer-lived than it should be

`pending_remote_insert_intent` matches **any** intent row for
`(index_oid, node_id, served_epoch)` in `prepare_requested`, `prepare_acked` or
`commit_intended`. It is not scoped to the missing vec_id, nor to the owner
that lost it. Two consequences:

- Under sustained write load there is essentially always some non-terminal
  intent row, so the gate is open ~always and a genuine dangling edge costs
  8 × 5 ms before it errors. Strictness survives — it does still error — but
  the discrimination the gate was supposed to provide does not.
- Intent rows are never deleted, only advanced. A coordinator that dies between
  `prepare_requested` and resolution leaves a non-terminal row **forever**, so
  the gate stays permanently open for that `(index, node, epoch)` until the
  reaper runs.

Fix: bound on `updated_at` (the column exists) — a few seconds is generous
relative to a 2PC window — and scope by the owner of the missing vec_id if the
call site can supply it.

## P2-4 — 40 ms of `pg_sleep` inside a locked owner scan

The loop runs `Spi::run("SELECT pg_sleep(0.005)")` up to eight times inside the
expander, while the scan holds its relation guards, inside an RPC the
coordinator is timing with `call_timeout()`. Worst case is 40 ms of an owner
backend spent asleep under lock, per expansion batch that trips the gate.

Prefer waiting on the intent row leaving its non-terminal state (poll the row,
not the clock), or cut the budget substantially. A 2PC window that needs more
than a few milliseconds is a different problem and should surface as an error
rather than be absorbed.

## P2-5 — `forward_neighbors_selected` is mislabeled, and what it shows is not good

The packet says this number "counts inserted-node forward edges". It does not.
In the fixture it is `forward_neighbor_count = found.len()`
(`distann_multicluster.rs:10016`), where `found` is the set of inserted vec_ids
discovered **inside other nodes' neighbour lists** — i.e. reverse-edge
coverage.

So `forward_neighbors_selected=2` means: of the ~26 rows inserted during the
drill, **2 have a back-edge anywhere in the cluster**. Last round the same
number was 8 of 24. It has gone down, and the two that survive are precisely
the two controlled writer inserts the drill seeds.

That does not invalidate `back_edge_check=true` — the controlled invariant
genuinely passed — but it means the under-linking signal I raised as item 6 is
still open, is now measured worse, and the packet's explanation resolves it by
renaming it. Please either explain the mechanism or show the number moving on
the 10k/50k/100k run, where the append-when-room change should raise it if that
change is doing what we think.
