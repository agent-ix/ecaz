The diagnosis is correct and the fix is the minimal one.

`exact_distance` (`src/am/ec_distann/insert.rs:52`) passed raw
`-inner_product` into `robust_prune`. For unit vectors every similar pair is
negative, and `robust_prune`'s diversity test is
`alpha * d(kept, candidate) <= d(pivot, candidate)` with `alpha >= 1`.
Multiplying a negative distance by alpha makes it *smaller*, which inverts the
relaxation the parameter exists to provide — so the incremental planner was
pruning on an inequality that meant the opposite of what batch construction
meant by it. Batch Vamana has always used `max(0, 1 - ip)`
(`src/am/ec_diskann/ambuild.rs:796-805`), and the two paths were silently
disagreeing on the metric.

Checked and satisfied:

- all three `exact_distance` call sites (`insert.rs:95`, `:104`, `:145`) use
  the value only as prune input or sort key, so the monotone change is safe,
  and the `max(0, ·)` clamp now matches batch exactly;
- both incremental forward-edge selection and full backlink re-pruning route
  through the shared helper, so the two incremental paths can no longer drift
  from each other or from batch;
- degree, alpha, search width, beam width, query sample and the threshold are
  all unchanged, which is what makes the measured effect attributable to this
  one change.
