# Task 167 packet 006 review

No M5 signoff. Reusing the scan search materially improves the sampled fold
recall, but the packet does not establish rebuild parity and Task 167's core
distributed insert path remains unimplemented.

## Findings

### P0 - Task 167 still does not implement distributed `aminsert`

`ec_distann_aminsert` still writes only the bounded local delta buffer
(`src/am/ec_distann/routine.rs:80-98`). Global/include identity insert is
rejected (`src/am/ec_distann/dml.rs:290-296`), graph fold is a separate operator
function, and the remote write endpoint accepts only tombstone vec_ids. There is
no owner-routed new-record append, bounded traversal, batched remote back-edge
amendment, UPDATE tombstone-then-insert, or distributed concurrency behavior.
The request's own “remaining M5” list confirms the main acceptance criterion is
open.

### P1 - Batch fold can select an unfolded delta row that has no directory entry

`graph_insert_record` now calls `collect_distann_hits`, which appends every entry
from the still-live delta chain to its hit list
(`src/am/ec_distann/routine.rs:466-507`). During a multi-row fold, that includes
other not-yet-folded delta rows. They become exact forward candidates, but the
next step requires every selected forward vec_id to exist in the persisted
directory (`src/am/ec_distann/insert.rs:378-384`). If robust-prune selects one,
the fold errors after earlier rows may already have mutated the graph. The only
pg_test inserts and folds one row (`src/tests/ec_distann_basic.rs:1019-1068`).

Exclude non-directory delta hits from graph-placement candidates or publish a
batch-aware pending directory, then add 2-row, near-cap, retry, and failure
regressions.

### P1 - The fail-before-publish protocol still exposes dangling backlinks

The mutation order is node append, visible in-place backlink rewrites, directory
write, fault injection, then metadata publish
(`src/am/ec_distann/insert.rs:391-450`). A failed or concurrent scan can observe
an active record pointing to an unpublished vec_id. The packet-024 single-query
drill does not validate directory/adjacency closure. This needs a pending,
idempotent, crash-recoverable protocol before FR-083-AC-5/6 can pass.

### P1 - Packet 006 is not valid FR-083-AC-4 benchmark evidence

The runs use direct `ecaz bench recall`, not `ecaz bench suite`; there is no
SuiteConfig, suite manifest, `results.jsonl`, load/fold timing, throughput,
concurrency, or targeted inserted-neighborhood query set. The fresh-rebuild
baseline is reused from an earlier packet/commit rather than a same-head A/B.

The saved 10k artifact is named and contains the greedy result
`0.8610/0.9095/0.9735/0.9820/0.9930`; it does not contain the request's claimed
scan-search sweep `0.9995/1.0/...`. At 100k, scan-search is also 0.008 below the
rebuild at top_k=16 and 0.002 below at top_k=200, so “matches or beats at every
point” is false. The observed result is promising, not closeout evidence.

### P2 - The interim fold has superlinear work beyond the task's bound

Candidate robust-prune allocates an O(C^2) pairwise distance matrix
(`src/am/ec_distann/insert.rs:98-112`), the full sorted directory is read and
rewritten for every row (`src/am/ec_distann/insert.rs:308-310`,
`src/am/ec_distann/insert.rs:425-450`), and `add_backlink` silently skips a full
neighbor when any current edge vector is absent from the candidate map
(`src/am/ec_distann/insert.rs:605-629`). No counter or throughput artifact
demonstrates the required traversal-cap + R amendment bound. Batch directory
publication and an explicit bounded candidate/backlink fetch are required for
the committed surface.
