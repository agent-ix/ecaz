## 1. Two exact-truth recall numbers, 12.5 points apart (P1, blocking)

At 100k, in the same suite step, on the same extension build
(`01da3574498fcd30cef6b29e14cf4ca7f3872326/release`), against the same staged
corpus and the same `query_sha256=a7cbec6f…`:

| Instrument | 100k physical |
| --- | --- |
| `physical_benchmark_recall` (`ecaz bench recall`, k=10, 200 queries, exact truth cache) | `0.9280` |
| `physical_benchmark_post_insert_exact_recall population=heldout` (brute-force fp32, k=10, 152 queries) | `0.802632` |

10k: `0.9990` vs `0.974342`. 50k: `0.9535` vs `0.853289`. The gap tracks
scale, which is the signature of a systematic instrument difference rather
than sampling noise.

I ruled out the easy explanations so you don't have to re-walk them:

- **Not the matching rule.** `bench recall`'s `distinct_recall_summary_at_k`
  (`crates/ecaz-cli/src/commands/bench/recall.rs:1011`) matches truth to
  prediction by **raw corpus id**; the new instrument matches by **source
  fingerprint**. Fingerprint matching is strictly more generous, so it should
  read *higher*, not 12 points lower.
- **Not the query form.** `ec_distann` has `encode_scan_query: false`
  (`crates/ecaz-cli/src/profiles.rs:218`), so `bench recall` issues
  `ORDER BY embedding <#> $1::real[]` — the same shape as the new instrument's
  inline `ARRAY[...]::real[]`.
- **Not beam/hop/heap.** The config's `beam_width=4`, `hop_rounds=100`, and
  `--sweep 32` all coincide with the extension defaults
  (`ECDISTANN_DEFAULT_BEAM_WIDTH=4`, `_HOP_ROUNDS=100`,
  `_CANDIDATE_HEAP_LIMIT=32` in `src/am/ec_distann/mod.rs:262-275`), so the
  unpinned session in the new instrument lands on the same three values by
  accident.
- **Not the 320 extra rows.** They are present only for the new instrument,
  and `truth_duplicate_slots=0` on the heldout population at 10k and 100k
  confirms they are not in any heldout query's true top-10.
- **Not the query subset.** 152 of the same 200 queries cannot move a mean 12
  points.

What is left, and where I would look:

- the GUCs the recall child sets that the new instrument does not —
  `append_materialization_benchmark_guc` (`materialization_batch_size=10` for
  the physical arm), `append_sharded_head_guc`, `append_typed_locator_guc`,
  `append_packed_payload_guc`, `append_expanded_locator_guc`,
  `append_crown_gucs`, and `args.bench_session_gucs`
  (`distann_multicluster.rs:6340-6407`);
- `SET ec_distann.epoch = {epoch}` and `SET ec_distann.local_node_id = 1`,
  which the new instrument forces and the recall child does not;
- whichever ambient GUC state the long-lived `coordinator` session is carrying
  by the time the exact-recall step runs.

Until this is reconciled, the *absolute* level of the exact-recall instrument
is not trustworthy. Both of its arms share whatever operating point it is
running at, so the physical-vs-fresh **delta** is still internally valid — but
the practical significance of a `-0.014385` delta depends on whether the
index is really at 0.80 or 0.93 recall there, and the disposition question is
exactly about significance. Put the reconciliation in the manifest with the
cause named.

## 2. Removing the gate is the wrong end state (P1)

Your FR-083-AC-4 argument checks out. I read
`spec/functional/distann/lifecycle/FR-083-distann-dml-path.md:182`:

> `FR-083-AC-4 | (Tier 2) After incremental insert, distinct_recall@10 on
> queries targeting the inserted rows' neighborhoods matches a fresh rebuild
> containing the same rows | Test (bench A/B via ecaz bench suite)`

No numeric threshold. Carrying `0.002` as a labeled `reference_band` with
`disposition=outside_review` instead of a hard `bail!` is defensible, and
keeping the measurement-integrity failures (wrong plan, missing rows, unknown
id, malformed truth, insufficient held-out queries) as hard failures is the
right split.

But the sequence still reads badly: 041 introduced the gate, it failed; 042
fixed the algorithm, it still failed; 043 removed the gate and the matrix went
green. The defensible version of that move ends with a *better* gate, not with
none. As it stands, a future change that halves post-insert recall produces a
green suite and a log line nobody reads.

You have the data to set a real band. Same extension runtime
(`01da35744`), same config, 10k inserted-neighborhood: packet 042 measured
`0.945809`, packet 043 measured `0.940600` — a `0.0052` spread across two
runs, while the fresh arm returned bit-identical `0.954985` in packets 041,
042 and 043. That is a clean result in its own right: the batch build is
deterministic and the incremental/distributed path is not. Derive the band
from the physical arm's spread over a handful of repeats (3–5 runs at 10k is
cheap next to a 5.5M ms 100k step) and gate on that. Keep
`disposition=outside_review` for anything inside the band.

## 6. Packet 042's product fix — ACCEPT

This is the strongest work in the round. `exact_distance`
(`src/am/ec_distann/insert.rs:52`) fed raw `-inner_product` into
`robust_prune`. For unit vectors that is negative on every similar pair, and
`robust_prune`'s test is `alpha * d(kept, candidate) <= d(pivot, candidate)`
with `alpha >= 1` — multiplying a negative distance by alpha makes it
*smaller*, inverting the relaxation the parameter exists to provide. Batch
Vamana has always used `max(0, 1 - ip)`
(`src/am/ec_diskann/ambuild.rs:796-805`). The diagnosis is right and the fix
is the minimal one: route incremental forward-edge selection and full backlink
re-pruning through the same shared helper.

I checked all three call sites (`insert.rs:95`, `:104`, `:145`) — every use is
ordering or prune input, so the monotone change is safe, and the clamp now
matches batch exactly. Nothing else moved: degree, alpha, search width, beam
width, query sample and the threshold are all unchanged, which is what makes
`0.805382 → 0.945809` at fixed fresh reference `0.954985` attributable to this
one change. `+0.140427` from a four-line diff, and it was only visible because
finding 4 was fixed first.

One nit, pre-existing and not from this diff: the comment at `insert.rs:147`
says "A candidate that is the inserted vector itself (re-insert) is dropped",
and `rank_insert_candidates` does not drop anything. With the A/B fixture
inserting exact duplicates this comment is actively misleading — either drop
it or make it describe what the code does.
