## P1-1 — the closeout matrix ran on a pg_test build

The 10k run exercises two functions that do not exist in a production build:

- `ec_distann_debug_resolve_nodes_retry` — `#[cfg(feature = "pg_test")]`,
  `generation_read.rs:4032`.
- `ec_distann.debug_disable_append_when_room` — the GUC is registered under
  `#[cfg(feature = "pg_test")]` (`options.rs`), and `debug_disable_append_when_room()`
  is likewise gated.

The log shows both running and passing:
`role=frontier_retry_probe owner=1 ... pass=true`, and
`physical_benchmark_append_when_room_ab ... pass=true`. So the installed `.so`
was built with `pg18 pg_test`.

`release_profile_preflight status=passed ... extension_build_profile=release`
does not contradict this: it records the **cargo profile**, and a
`--release --features 'pg18 pg_test'` build is release-profile. The preflight
has no visibility into features.

That makes every cited recall, latency, storage and throughput number a
measurement of a build that carries fault-injection in the retry hot path —
`FORCED_FRONTIER_RETRY_USED` thread-local plus a GUC read on every lookup batch
in both retry helpers. This repo has already lost time to exactly this class of
problem (a `pg_test` install shadowing a release build before a latency run).

Two consequences worth stating plainly: the matrix must be re-run on the
production feature set, and the append-when-room A/B **cannot be run at all on
a production build**, because the disable side is a `pg_test`-only GUC. If that
arm is required for closeout, the toggle needs to be a normal userset GUC.

Please also extend `release_profile_preflight` to report the feature set. A
provenance check that cannot distinguish a test build from a production one is
not doing the job the packet cites it for.

## P1-2 — the head is not the code that was benched

Manifest says the production checkpoint is `cf5ad6761`. Every cited log says
`extension_git_sha=5f56390d18c09a7c3020951d0e0318fab7d9eede`. The manifest
frames the intervening commits as harness-only, and six of the seven are — but
`cf5ad6761` is not:

```
cf5ad6761 Remove sleep from bounded owner visibility retries
 src/am/ec_distann/generation_read.rs | 10 ++++------
```

It deletes `Spi::run("SELECT pg_sleep(0.001)")` from **both** retry loops. That
is a change to the mechanism this entire review round is about, and it has zero
runtime evidence — no matrix, no concurrency drill, not even the forced probe.

The change also looks wrong on its face. Both loops now run 32 iterations with
no wait between them, so the whole retry budget elapses in the time it takes to
issue 32 index lookups plus (P1-5) up to 32 gate queries — microseconds to low
milliseconds of pure spin. The window it is supposed to absorb is the interval
between the coordinator's local commit and its `COMMIT PREPARED` round trip to
each owner: a libpq connect plus a network round trip. A budget that expires
before the event it waits for is not a bounded wait, it is a busy loop that
always fails.

My P2-4 objection last round was specifically about sleeping **while holding
the owner scan's relation guards**. `lookup_graph_nodes_with_reopened_intent_retry`
already fixed that by dropping and reopening the guards per attempt. Removing
the wait from that loop solves nothing and breaks the mechanism. The other
loop (`lookup_graph_nodes_with_intent_retry`, line ~446) does hold its guards
across attempts and is the one that genuinely should not sleep — that one needs
the reopen treatment, not the sleep deletion.

Either restore a bounded wait in the reopening loop and show it working, or
show me a run at head where the natural race recovers without one.

## P1-3 — `churn_retries=3` is the forced probe, not a race

From the 10k log, in order:

```
role=frontier_retry_probe owner=1 vec_id=Some(258183856494066) scheduled=true
role=frontier_retry_probe owner=1 vec_id=Some(258183856494066) pass=true during_churn=true
...
role=frontier_retry_counter churn_retries=Some(3) churn_by_owner=[(1, Some(3), "3"), ...]
```

The probe SQL hand-inserts a synthetic intent row
(`gid='ec_distann_insert_retry_probe_1'`, `intent_state='commit_intended'`),
sets `ec_distann.debug_force_frontier_retry=true`, and calls
`ec_distann_debug_resolve_nodes_retry`. And `retry_counter_ok` in the fixture
requires `forced_retry_probe` as a conjunct.

So what is proven is: *when the test fault forces a miss and a synthetic intent
row is present, the gate admits a retry, the counter increments on the owner,
and the lookup succeeds.* That is a worthwhile self-test of the plumbing and I
am glad it exists. It is not what item 2 asked for. The open question has always
been whether the **natural** 2PC visibility gap trips this path and whether the
bounded retry actually spans it — and after P1-2 the answer is more likely to be
no than it was last round.

What would settle it: a churn arm with `debug_force_frontier_retry` off in which
`churn_retries > 0`. If the natural race never trips it at 10k, say so and
raise the write concurrency until it does; if it trips and the retry does not
recover, that is the finding and it needs the wait back.

## P1-4 — the 50k and 100k concurrency drills failed

The packet says they "stalled and were terminated" and that a large-scale
concurrency arm "is not required". The log says something more specific:

```
role=shared_target reason=seed_insert_failed
  stderr=FATAL:  terminating connection due to administrator command
       | server closed the connection unexpectedly
physical_concurrent_insert_query pass=false
  0: physical TC-043 concurrent insert/query drill failed
```

The suite step **failed**. `FATAL: terminating connection due to administrator
command` is `pg_terminate_backend` or a shutdown — the backend was killed
because it was not making progress. Two of three scales failed the concurrency
gate.

I do accept that a full concurrency arm is not needed at every scale for its own
sake. That is not the issue. The issue is that a drill which passes at 10k and
hangs at 50k and 100k is telling you the mechanism has a scale-dependent
liveness problem, and P1-6 gives a concrete candidate. Passing at the one scale
where it happens not to bite does not retire that. Diagnose the hang.

## P1-5 — the gate does not discriminate

```rust
fn visibility_retry_allowed(...) -> Result<bool, DistannExpandError> {
    if recent_remote_insert_intent(...)? { return Ok(true); }
    Ok(vec_ids.iter().any(|vec_id| {
        current_graph_tuple_exists(generation.graph_store_relid, *vec_id).unwrap_or(false)
    }))
}
```

The intent half is well scoped now — owner, epoch, exact vec_id, state,
30-second freshness. Good; that is P2-3 from last round handled.

The second half is not. It is `any()` over the **whole batch**, not over the
ids the error says are missing. In a frontier batch of 30 where 29 resolve
fine, the predicate is trivially true, so a genuinely permanent dangling edge
admits the full retry budget every time. Strictness survives — it still errors
eventually — but the discrimination the gate exists to provide does not, and
`visibility_retry_allowed` is called again inside the loop, so this runs up to
32 more times per batch. Combined with P1-2's zero-wait spin, a single dangling
edge now costs ~64 SPI round trips of pure overhead.

The doc comment above the function says "exact requested ids", which is true but
not the property you need. `DistannExpandError::OwnedRecordMissing` carries the
vec_id — thread it through and test only that id.

## P1-6 — the retry writes to the coordination row it is waiting on

Both retry helpers do this before spinning:

```rust
let _ = Spi::run(&format!(
    "UPDATE ec_distann_remote_prepared_xact_intent SET retry_count = retry_count + 1
      WHERE served_epoch = {} AND node_id IN ({}) AND tracked_vec_id IN ({}) ..."));
```

This takes row locks on exactly the rows the coordinator must update to advance
the two-phase commit (`mark_remote_physical_intent_precommit` and the resolve
path write the same rows, keyed the same way). The scanning backend holds those
locks for the rest of its serving transaction, and then spins waiting for that
same coordinator transaction's effects to become visible.

That is a lock-order inversion: the reader takes the coordination row and then
waits on the writer that needs it. It is a strong candidate for the 50k/100k
hang in P1-4, where more concurrent writers means more overlap on those rows.

The fixture's counter reset compounds it. Every reset issues, on every owner,
mid-drill:

```
ALTER TABLE ec_distann_remote_prepared_xact_intent ADD COLUMN IF NOT EXISTS retry_count ...;
ALTER TABLE ec_distann_remote_prepared_xact_intent ADD COLUMN IF NOT EXISTS tracked_vec_id ...;
```

`ADD COLUMN IF NOT EXISTS` still takes `AccessExclusiveLock` even when the
column exists. That blocks every concurrent gate query and every intent
transition on that node until it is granted — and it has to queue behind the
very row locks above. `reset_outputs=[(1, "ALTER TABLE | ALTER TABLE | UPDATE 100"), ...]`
shows this running three times per sample point. I note commit `c79b21a2a`
("avoid hot-path intent schema locks") already chased a version of this; it is
still here in the fixture.

Attribution must not be a write on the hot coordination row, and the fixture
must not run DDL against a table under concurrent load. Options: a separate
unlogged per-backend counter relation; a pid-keyed side table; or keep the
process-local `stage_counters` value and add a small owner-side endpoint the
fixture calls to read it before the backend exits. Put the columns in the
migration, not in the drill.

## P2-7 — the saturated-target case still does not assert saturation, and shows edge loss

`graph_degree=5`, and:

The target had 5 neighbours at selection, 3 by the time the wave started, and 3

```rust
shared_target_initial_neighbor_count >= args.graph_degree as usize
    && saturation_inserts_ok
    && final_neighbor_count.is_some_and(|count| count <= args.graph_degree as usize)
```

`count <= degree` cannot detect loss, so a target that dropped to zero

graph_degree` in that case, and explain where the edges went — with
append-when-room and two writers at degree 5 this should not shrink.

Related: `reverse_edge_coverage=15/24` is a real improvement over 2/26 and the
label is now honest. But it is at degree 5 where the prior number was degree 8,
