## What is right

Worth stating, because these were the hard parts and they landed cleanly:

- The transactional shape of the owner-local path is right: row tier appended
  before the graph pointer, everything in the callback transaction, so an
  error aborts the whole set. The mid-insert drill confirms it
  (`before_rows=500 after_rows=500 consistent=true`).
- Duplicate-identity safety has a real backstop, not just the application
  check: `generation_store.rs:479` creates `UNIQUE (vec_id) WHERE is_current`,
  so two racing inserts of the same stable identity cannot both become
  current.
- The retained-record model (`record_version` / `is_current`) is applied
  consistently across readers — `handoff.rs:714`, `handoff.rs:974`,
  `generation_read.rs:1253` all filter `is_current`, and
  `validate_generation_relations` was tightened to require the 5-column shape
  and a partial (`indpred IS NOT NULL`) directory. No reader was left behind.
- Packet 021's SQL hardening is correct and complete for the three endpoints:
  `SECURITY DEFINER` + fixed `search_path` + `REVOKE ... FROM PUBLIC`, matching
  the existing physical read-endpoint class.
- Packet 022's overload change is minimal and safe. Every caller I could find
  passes explicit argument lists — `PHYSICAL_EXPAND_SQL`
  (`remote_transport.rs:1163`) uses the full 8-argument `regclass` form, and the
  `ec_distann_basic` tests use the 4-argument `oid` overload, which is a
  different function. Removing the two `DEFAULT NULL`s does not orphan a caller.
- Sending a frozen packed row payload instead of a source ctid
  (`freeze_source_slot_packed` / `decode_packed_row`) is the right call; the
  owner never has to assume the coordinator's heap is mirrored.

## P1 findings

### P1-1. Cross-owner back-edges are silently dropped once the target is at full degree

`physical_dml.rs:1851-1873`, in `apply_owner_backlink`:

```rust
for neighbor in &node.neighbor_vec_ids[..usize::from(node.neighbor_count)] {
    let neighbor_owner = ...owning_node(*neighbor, ...);
    if neighbor_owner == local_owner && !remote_vectors.contains_key(neighbor) {
        return append_backlink_if_room(...);
    }
}
```

`remote_vectors` is built (line 1849) from `remote_ids`, which is by
construction *only* the neighbors **not** owned locally. So for any
locally-owned neighbor, `remote_vectors.contains_key(neighbor)` is always
false and the guard is always true. The loop therefore takes the
`append_backlink_if_room` branch whenever the target has **at least one
locally-owned neighbor** — the overwhelmingly common case — and only reaches
`amend_backlink` when every single neighbor is remote.

The doc comment says the fallback is for "a retained graph record that
references a source row no longer present in the owner row tier". The
condition tests the wrong thing entirely; it should test whether that
neighbor's row is actually unreadable (i.e. `read_current_vector` fails), not
whether it appears in a map that by definition excludes it.

Failure scenario: coordinator inserts vec_id N; N's forward set includes T,
owned by a remote participant; T already has `neighbor_count == graph_degree`
(32). `append_backlink_if_room` sees `count >= graph_degree` and returns
`Ok(())` **without writing anything and without reporting anything**. N has a
forward edge to T; T has no edge back to N. Every cross-owner backlink into a
saturated target is lost this way, silently. Since a mature graph has most
nodes at or near full degree, this degrades to "cross-owner inserts get
essentially no back-edges" — the exact reachability-over-churn property
FR-083 exists to provide.

This is consistent with the declining parity trend in packet 020
(0.9525 / 0.8920 / 0.8445 at 10k / 50k / 100k): the larger the graph, the
higher the fraction of saturated targets.

Fix: gate the fallback on an actual failed row read for that neighbor, and
make the no-room case in `append_backlink_if_room` observable (counter or
error) rather than a silent `Ok(())`.

### P1-2. A committed coordinator transaction can be rolled back on the owner

`remote_transport.rs`, `resolve_physical_insert_prepared` + the reaper.

The intent lifecycle is `prepare_requested` → `prepare_acked` →
(`commit_local` | `rollback_local`), and the transition to `commit_local` is
written **only after the remote `COMMIT PREPARED` has already succeeded**:

```rust
if client.batch_execute(&format!("{command} {gid}")).is_ok() {
    let state = if commit { "commit_local" } else { "rollback_local" };
    let _ = client.batch_execute(&format!("UPDATE {PHYSICAL_INTENT_TABLE} SET intent_state = ...
```

and the callback bails out entirely if it cannot even connect
(`let Ok(mut client) = ... else { return; }`).

So the window between "the coordinator's local transaction commits" and "the
owner's prepared transaction is committed" is not covered by any durable
record of the commit decision. If the owner is unreachable, or the
coordinator backend dies, at that moment, the intent row is still
`prepare_acked`. The reaper then does:

```rust
let commit = intent == "commit_local";
let command = if commit { "COMMIT PREPARED" } else { "ROLLBACK PREPARED" };
```

`prepare_acked` is not `commit_local`, so it **rolls back**. The coordinator's
source row is committed and visible; the owner's row-tier tuple and graph
record are gone. That is a torn write in the direction that loses data, under
precisely the single-fault condition the task Goal names ("the graph left
consistent under any single fault") and FR-083 AC-5 requires.

The commit decision has to be recorded durably *before* the local commit
completes — a `commit_intended` state written in the pre-commit callback
(`PgXactCallbackEvent::PreCommit`), so the reaper's default for an
`prepare_acked`-and-nothing-else orphan can stay rollback while a
`commit_intended` orphan is committed forward. As written, the reaper cannot
distinguish "coordinator committed, we lost the ack" from "coordinator
aborted", and resolves both the same way.

The mid-insert drill does not cover this: it injects the fault *before* the
coordinator commit, exercising only the abort direction.

### P1-3. The reaper's liveness check reads the wrong node's xid space

`remote_transport.rs`, `coordinator_xid_is_live`:

```rust
client.query_one(
    "SELECT EXISTS (SELECT 1 FROM pg_catalog.pg_stat_activity
      WHERE backend_xid::text = $1 OR backend_xmin::text = $1)", &[&xid.to_string()])
```

`client` here is the connection **to the owner**. `parts.xid` is the
*coordinator's* top transaction id, parsed out of the GID. Transaction ids
are per-cluster; comparing a coordinator xid against the owner's
`pg_stat_activity` compares unrelated counters. Two outcomes, both wrong:
usually a false negative (the guard never fires, so the reaper will happily
resolve a prepared transaction whose coordinator is still running and about
to commit it — combined with P1-2 that is an active data-loss path, not a
theoretical one); occasionally a false positive when an owner-local backend
happens to hold the same numeric xid, in which case the orphan is skipped
forever.

The check has to run against the coordinator, or the liveness signal has to
come from something that crosses the cluster boundary (a coordinator-side
heartbeat row, or the coordinator's own reconciliation pass).

Related: `NEXT_PHYSICAL_INSERT_GID` is a process-local counter restarting at 1
each backend, so GID uniqueness rests entirely on the xid component. That is
adequate today but is worth a comment, since the reaper's fencing parses that
GID.

### P1-4. Read-path regression: the coordinator now dials itself for its own shard

`generation_read.rs:818` changed `physical_owner_routes` to resolve a conninfo
for **every** route, including the local one:

```rust
- conninfo: if is_local { None } else { Some(resolve_conninfo_secret(&secret)?) },
+ conninfo: Some(super::node_registry::resolve_conninfo_secret(&secret)?),
```

But `conninfo.is_some()` is the established "this shard is remote"
discriminator across the read path, with comments saying so in as many words:

- `generation_read.rs:4548` — head shard export: `match owner.conninfo.as_deref() { Some(..) => remote_head_shard_export(..), None => { ... local export } }`, above the comment "The coordinator's own shard is exported through the local path".
- `generation_read.rs:4553` — "The coordinator is normally itself an owner, and its own route carries no conninfo. Serve that shard in-process rather than dialling ourselves".
- `generation_read.rs:5104` — gateway copies: `if route.conninfo.is_some() { remote_work.push(..); continue; }`.
- Same shape at `2382`, `5207`.

After this change every one of those takes the remote branch for the local
shard: a libpq round trip from the backend to its own cluster, during a scan,
for work it could do in process. At minimum this is a latency and
connection-count regression on the FR-080/FR-081 read path that Task 167 does
not own; it also re-enters the `ec_distann_expand_*` endpoints on a fresh
session whose roster/epoch GUC state is set from the caller, which is a
failure mode the local branch was explicitly written to avoid ("003a review,
2026-07-31 finding 3" is cited right there in the code).

If the physical DML path needs a conninfo for the local node, give it a
separate accessor (or populate `physical_owner_routes_for_owner_insert`,
which already handles this correctly by setting `None` for local). Do not
change the meaning of the shared field.

This also means the packet 019/020 latency numbers were measured with the
local shard going out over libpq. They are not comparable to the Task 165
baselines.

### P1-5. Routed tombstones to a remote owner cannot succeed

`remote_endpoint.rs`, `ec_distann_apply_physical_tombstone` resolves the
generation with:

```rust
let active = super::generation_read::active_generation_identity(index_regclass, logical_index_uuid)?
    .ok_or_else(|| "EC_GENERATION_MISSING: physical tombstone has no active epoch")?;
```

The insert endpoint immediately above it does **not** do this, and the comment
explains why:

> Participant catalogs intentionally do not advance an active pointer for a
> coordinator-published epoch. Resolve the immutable published generation by
> the coordinator's fingerprint instead.

The tombstone endpoint contradicts that contract, so on a participant owner it
fails with `EC_GENERATION_MISSING` before it does anything. `tombstone_owner_record`
compounds it: it calls `PhysicalGenerationScan::open(index_oid)` (active
pointer, and `load_head = true`, which pulls the coordinator-resident head
sample the owner does not have) rather than
`open_at_fingerprint_for_owner_insert`.

Net effect: `ambulkdelete` on a multi-owner physical generation routes a
tombstone to a remote owner and errors out — which fails the whole VACUUM
(see P3-10). Nothing in the fixture covers this: the drills exercise insert,
concurrent insert/query, and stable-vec_id UPDATE. There is no routed-DELETE
+ VACUUM drill at any scale, so this path has never been executed against a
real participant.

Please add a DELETE-then-VACUUM drill on the three-owner fixture before this
task closes; it is the only committed-scope operation with zero runtime
coverage.

## P2 findings

### P2-6. Concurrent back-edge amendments lose updates, and can resurrect a tombstone

`amend_backlink` (`physical_dml.rs:1565`), `append_backlink_if_room`
(`1662`), and `tombstone_owner_record` (`724`) all follow the same pattern:
SPI-`SELECT` the whole `graph_record`, decode, modify in memory, then
`UPDATE ... WHERE ctid = '(b,o)' AND is_current` writing the **entire**
re-encoded record.

Under READ COMMITTED, two amendments to the same target serialize on the row
lock, but the second one re-evaluates only the `WHERE` clause — it still
writes the record it computed from its pre-block snapshot. The first
amendment's back-edge is overwritten and lost. Worse, a `tombstone_owner_record`
that lands between a concurrent amendment's read and its write is undone: the
amendment writes back a node whose `tombstoned` flag is still `false`, so a
deleted node becomes live again in the published graph.

The TC-043 drill (`scanners=4, iterations=12`, one background writer) is a
reader/writer test only — it cannot observe this. FR-083 AC-6 as written is
about concurrent inserts; the evidence is concurrent *queries* against a
single inserting session.

Fix shape: `SELECT ... FOR UPDATE` on the target row (or a
read-modify-write retry loop keyed on `record_version`) so the mutation is
computed from the version it is about to replace. Then add a genuinely
concurrent multi-writer drill — two sessions inserting vectors that share a
forward neighbor.

### P2-7. The AC-2 "bounded work" counters measure intent, not work

`physical_dml.rs:332-336`:

```rust
stage_counters::record_insert_work(DistannInsertWork::ForwardNeighborsSelected, forward.len());
stage_counters::record_insert_work(DistannInsertWork::BacklinkAmendments, forward.len());
```

`BacklinkAmendments` is recorded as `forward.len()` **before any amendment is
attempted**, so it is a duplicate of `ForwardNeighborsSelected` by
construction. It cannot distinguish an amendment that happened from one that
was skipped (`amend_backlink` early-returns when the edge already exists) or
silently dropped (P1-1). Every `backlink_amendments` line in the packets is
therefore evidence about the plan, not about the graph. Please increment it at
the point of a successful `UPDATE`, and add a separate counter for the
no-room / already-present / dropped cases.

Second, the cited values need an explanation before they support AC-2. From
`020/artifacts/cited-results.log`, identically at all three scales:

```
physical_benchmark_insert_work: forward_neighbors_selected=48 backlink_amendments=48 owner_writes=48 inserts=48
```

48 inserts (3 trials × 16 rows, `measure_task167_insert_arm`), so the mean
forward degree is **exactly 1.0 neighbor per insert** with `graph_degree=32`
and a search list of `max(8*32, 64) = 256`. Either `select_insert_forward_neighbors`
is collapsing the candidate set to a single survivor (in which case every
incrementally inserted node joins the graph with one forward edge and the
insert path is not building a usable neighborhood), or the counter is not
recording what it appears to. The fixture's assertion
(`value <= graph_degree * inserts`, i.e. `48 <= 1536`) passes vacuously either
way and detects neither.

AC-2 says "per-insert work bound demonstrated by counter evidence". A counter
sitting three decimal orders below the bound is not a demonstration of the
bound; it is an unexplained anomaly. Please run one insert with the candidate
set and prune result logged, and say which of the two it is.

### P2-8. The AC-4 parity number is not the inserted-neighborhood parity

`task167_post_insert_fresh_rebuild_parity` (`distann_multicluster.rs:3001`)
builds `task167_parity_q` from 48 inserted rows **plus** `query_count - 48`
(= 152) ordinary held-out queries, then averages recall over **all 200**. The
emitted line hardcodes the string `inserted_neighborhood_queries=48` into the
format — it is a literal, not a measurement — and packet 020's request and
manifest both read that as "parity used 48 distinct inserted neighborhood
queries", which is not what the number is. The 48 inserted-neighborhood
queries are 24% of a blended average and their parity is never reported
separately.

Also note the comparison is index-vs-index (physical ANN top-10 vs
fresh-local ANN top-10), so it folds the fresh rebuild's own approximation
error into the metric; it is an agreement score, not recall against ground
truth. That is defensible as an oracle check, but the packet should say so
rather than call it `distinct_recall`.

Concretely, for AC-4 I need: the 48 inserted-neighborhood queries reported as
their own aggregate, at each scale, alongside the blended figure. If P1-1 is
what the declining 0.9525 → 0.8920 → 0.8445 trend reflects, the isolated
number is where it will show up.

### P2-9. Throughput and build provenance

`physical_benchmark_insert_throughput_ab` gives 1.255 / 0.346 / 0.185 rows/s
at 10k / 50k / 100k — about **5.4 seconds per single-row insert at 100k**, and
degrading faster than linearly in corpus size, which is the opposite of the
bounded-work claim in the Goal. `pass=true` is decided purely by the ratio
against the local control (0.59 / 0.87 / 0.94), so an absolute number this
large passes as long as the control is equally slow. Please state the absolute
target, or record explicitly that FR-083 has no absolute insert-latency gate.

- `020/artifacts/manifest.md` records the suite driver as
  `/home/peter/.cargo-target/debug/ecaz` while asserting a "release extension

  latency are both consistent with a debug `.so`. Please record the installed
  `.so` path + its build profile (or the `ecaz dev install` line that placed

- The suite runs `beam_width: 4`, `hop_rounds: 100`. Per Task 203 that is the

## P3 findings

- **P3-10. `ambulkdelete` does remote libpq RPCs from VACUUM.** `routine.rs`
  now routes tombstones inside the bulkdelete callback. If any owner is
  unreachable, `remote_physical_tombstone` errors and the entire VACUUM fails
  — repeatedly, including autovacuum, which puts the source table on a path to
  xid-wraparound pressure for a reason unrelated to the heap. Combined with
  P1-5 this is not hypothetical. Consider: collect failures and report rather
  than error; or move routed tombstones to an explicit maintenance surface and
  keep `ambulkdelete` local. Also, `ec_distann_physical_source_map` is never
  pruned for tombstoned rows, and `tombstone_dead_records` scans the whole map
  on every vacuum; and `tombstone_owner_record` re-opens the generation
  (`PhysicalGenerationScan::open`) once per dead row.
- **P3-11. Owner-side placement validation is anchored on caller-supplied
  state.** Both `ec_distann_apply_physical_*` and
  `physical_owner_routes_for_owner_insert` derive placement from
  `placement_directory_for_epoch(current_epoch())`, i.e. the roster GUC the
  coordinator itself set on that session via `roster_spec_for_routes`. The
  fingerprint check does anchor the generation, and PUBLIC execute is revoked,
  so this is not an unprivileged escalation — but the "does this vec_id belong
  to me" check is being made against the requester's own claim rather than
  against `descriptor.roster`, which is immutable, already loaded, and carries
  `node_id`. Prefer the descriptor.
- **P3-12. Asymmetric INVALID-tid guard.** The local branch guards
  `if source_tid != ItemPointer::INVALID { update_source_mapping(...) }`
  (`physical_dml.rs:572`) but the remote branch calls it unconditionally
  (`453`). `insert_from_owner_payload` passes `ItemPointer::INVALID`, so if an
  owner ever re-routes (roster disagreement), a `(0,0)` tid is written into the
  source map. Make the two branches agree.
- **P3-13. `decode_packed_row` datum lifetime.** The `ReceiveFunctionCall`
  input buffer (`input_bytes`) is a `Vec` local to each loop iteration, but the
  returned datum is stashed in the virtual slot and only materialized by
  `store_virtual_tuple()` after the loop. This is safe for receive functions
  that palloc (all the standard ones do), but it is an unsafe-FFI invariant
  resting on an assumption about every possible column type in a user's row
  tier. A comment stating the invariant, or a `pg_detoast`/copy before
  `set_datum`, would close it.
