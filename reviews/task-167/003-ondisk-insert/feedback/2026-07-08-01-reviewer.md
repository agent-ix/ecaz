# Task 167 packet 003 review

No signoff for the on-disk mutation slice. It proves a useful happy path, but the fault and retry semantics are not yet safe enough for FR-083.

## Findings

### P1 - Mid-fold failures can leave graph edges pointing at an unpublished node

Task 167 explicitly requires failed insert to leave no dangling forward edge and to keep the graph consistent under a single fault (`plan/tasks/167-ec-distann-m5-incremental-insert.md:18`, `plan/tasks/167-ec-distann-m5-incremental-insert.md:30`). The implementation appends the new node record first (`src/am/ec_distann/insert.rs:355`), then mutates backlinks on forward neighbors (`src/am/ec_distann/insert.rs:364`), and only after that rebuilds/publishes the directory and increments metadata node_count (`src/am/ec_distann/insert.rs:378`).

If any error occurs after a backlink rewrite but before the new directory/metadata is published, a visible neighbor can now return `new_vec_id` in its adjacency, while the directory still cannot resolve that vec_id. The scan path treats that as an owned-record-missing structural fault (`src/am/ec_distann/expand.rs:86`). There is no compensation step, in-progress marker, recovery pass, or mid-fault drill in the packet evidence; the test only covers the one-row happy path (`reviews/task-167/003-ondisk-insert/artifacts/test-evidence.log:4`).

This needs a fail-closed mutation protocol before the slice can satisfy NFR-020/FR-083. Options include publishing the node in a recoverable pending state before exposing backlinks, making retries idempotent by construction, or deferring all visible edges until the directory publish is durable.

### P2 - Vec_id collision / retry is not rejected before appending a node

The task scope requires insert-time vec_id collision to error (`plan/tasks/167-ec-distann-m5-incremental-insert.md:28`). `graph_insert_record` reads the current directory and then unconditionally pushes `new_vec_id` and the new TID into the rebuilt directory (`src/am/ec_distann/insert.rs:332`, `src/am/ec_distann/insert.rs:380`). There is no `directory_lookup(&directory, new_vec_id)` guard before the node append.

A duplicate fold, retry after partial progress, or future include-identity collision can therefore append a second record with the same vec_id and stage a duplicate key into the directory. The reader requires strict ascending vec_ids and will reject duplicates as a corrupt directory (`src/am/ec_distann/reader.rs:101`). Add an explicit collision check before any page mutation, and add a regression that a duplicate fold errors without changing node_count, backlinks, or directory_head.

### P2 - The packet still documents append-if-free backlinks, but the branch now has full-reprune backlinks

The request describes step 4 as append-if-free and says full-reprune is a follow-up (`reviews/task-167/003-ondisk-insert/request.md:18`). Current code has since changed to full-reprune-at-capacity in `add_backlink` (`src/am/ec_distann/insert.rs:545`). That is the right direction, but this packet's request/evidence no longer describes the reviewed code. Please add a packet update or a new packet for the full-reprune implementation, including the exact commit and tests that support it.
