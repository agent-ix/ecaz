## P1 — a missing frontier node is now silently reported as a tombstone

`generation_read.rs:226` and `generation_read.rs:5740`.

`lookup_graph_nodes` no longer errors on an absent vec_id (`return Err(missing(*vec_id))`
became `continue`), and `expand_nodes_masked` now synthesizes a tombstone
response for any requested vec_id that came back absent.

The transient case you are describing is real, and it is inherent to the
protocol as built: the owner's write becomes visible at `COMMIT PREPARED`,
which runs in the coordinator's **post-commit** callback, so two owners'
records for the same logical insert become visible at different instants. A
reader can legitimately traverse an already-amended edge into a node whose
owner tuple is not yet visible. I agree that should not fail a query.

What I cannot accept is that the *permanent* case is now indistinguishable
from it, and silent. Consequences:

- `EC_RECORD_MISSING` (`XX001` / `OwnedRecordMissing`) is the NFR-020 /
  TC-042 `missing_node_record` structural-fault class. `options.rs:696`
  states the contract in as many words — the drill exists "so the multinode
  fault-drill matrix (TC-042) can assert the scan errors rather than
  under-returning". For a physical generation, the scan now under-returns
  instead of erroring. A genuinely lost or corrupt owner record produces a
  silently short result set with no signal anywhere.
- The `missing` closure passed at `generation_read.rs:5724` is now
  constructed and never called, and the parameter is `_missing`. A reader of
  that call site will believe the path still errors. (The other caller,
  `resolve_nodes` at `1702`, re-checks and does still return
  `OwnedRecordMissing` — that one is fine.)
- Nothing counts the degradation, so no drill can assert "zero degraded
  frontier entries in steady state".

What I need instead of the blanket conversion — any one of these, or a
combination:

1. Count it. A `stage_counters` metric for degraded frontier entries, exposed
   like the insert-work counters, so the concurrency drill can assert it is
   non-zero only during churn and zero afterwards.
2. Bound it. Re-read the absent vec_ids once at the end of the round (a fresh
   snapshot is enough for the 2PC window, which closes in milliseconds) and
   only degrade the ones still absent.
3. Condition it. `ec_distann_remote_prepared_xact_intent` can answer "is there
   an in-flight prepared write for this index on that owner" cheaply; degrade
   only when there is one, error otherwise.

And either way: keep a strict physical path for the fault-drill class, or
update the NFR-020 taxonomy doc to say the physical expander under-returns by
design and retire that drill deliberately. Right now the taxonomy says one
thing and the code does another, and the only record of the change is a code
comment.

## P1 — the remote-owner materialization proof is now vacuous

`distann_multicluster.rs`, remote-owner proof. Before:

```sql
... WHERE source_id = '{source_id}'::uuid ORDER BY embedding <#> '{vector}' LIMIT 1
```
asserted `materialized_source_id == source_id`.

After: the `WHERE source_id = ...` qual is gone, `LIMIT 1` became
`LIMIT {source_count}` (i.e. every row), the result is scanned for *any* row
that exists in that owner's row tier, and the verdict is a literal
`let owner_served = true;`. The log records the outcome as

```
physical_remote_owner node=2 custom_scan=true pass=true
  expected_source_id=072b030b-... materialized_source_id=6c8349cc-...
```

— pass, with expected ≠ materialized.

Your stated reason is sound as far as it goes: approximate traversal is not
required to return a specific row. But the previous query did not rely on ANN
ranking to find the row — it **pinned it with an equality qual**. The question
raised by last round's failure (`query returned an unexpected number of rows`
at what is now this call site) is why a qualified distributed scan returned
zero rows for a row that exists. That question is still unanswered; the
assertion that asked it was removed instead.

This matters more than a fixture detail because it sits in the CustomScan qual
path, which Task 165 already had to repair once, and because the plausible
cause is the same missing-node behaviour above — in which case these two
findings are one bug, and the packet has now suppressed both its detector and
its symptom in the same checkpoint.

Please restore a pinned single-row probe (equality qual, or an exact-vector
query for the sampled row) and either show it returning the sampled row or
report the diagnosis of why it cannot. Keep the membership check as an
addition; it is a reasonable secondary assertion.

## P2 — the backlink prune swallows "not visible" as well as "absent"

`physical_dml.rs`, `amend_backlink`:

```rust
Err(error) if error.starts_with("EC_INSERT_BACKLINK: current row for vec_id") => continue,
```

`read_current_vector` emits that prefix for **two** distinct conditions:
`"... is missing"` (no current graph record — a genuinely stale retained edge,
where pruning is correct) and `"... is not visible"` (the row_tid exists but
is invisible under this snapshot — transient). The second is exactly the
in-flight-prepared-transaction case: another coordinator's prepared write on
this owner makes a live neighbour's row temporarily invisible, and this code
then **permanently deletes that neighbour's edge** while rebuilding the target.
That is edge loss under concurrency again, by a different mechanism than the
one `FOR UPDATE` closed.

Split the two error cases and prune only on genuine absence; on
not-visible, either keep the existing edge and its stored code bytes untouched
or fail the amendment and let the caller retry.

## P2 — the concurrency invariant was replaced with one the probe already proves

The blocking assertion is now `current_graph_rows == inserted_vec_ids.len()`:
every committed insert has one current graph record on its owner. The
remote-insert probe already proves that for a single row; running it 24 times
concurrently is a good liveness check but it is not the P2-6 invariant, which
is that two writers amending a **shared target** do not clobber each other.

Your reasoning — robust prune may legitimately retain no reverse edge — is
correct, and I accept that a blanket "every inserted id has a back-edge" is the
wrong assertion. The answer is a controlled case, not no case: pick a target
that currently has spare degree (with `graph_degree=8` and 100 rows there are
many), have both writers insert a near-duplicate of it, and assert both new
vec_ids are in its neighbour list afterwards. That is deterministic under
correct behaviour and fails under a lost update.

Also, read the diagnostic you kept: `forward_neighbors_selected=8` with 24
inserted rows means **16 of 24 inserted nodes have no reverse edge anywhere in
the cluster**. That is the same signal as the still-unexplained
`forward_neighbors_selected=48 / inserts=48` (mean 1.0) from packet 020. Two
independent runs now point at incrementally inserted nodes being under-linked.
Please explain that before the benchmark re-run — if inserts really are joining
the graph with ~1 forward edge and usually no reverse edge, the AC-4 parity
number will encode it and the benchmark will not tell you why.

## Scope note on the passing run

The green run is 2 owners, 100 rows, dim 4, `graph_degree=8`,
`--skip-fault-drills`, debug extension. That is a smoke test and the packet

drills have only ever run at a scale where every owner holds ~50 rows; the
behaviours at issue here (saturated degree, prune decisions, visibility
windows under load) are scale-sensitive.
