## New P1 — `commit_intended` violates the intent-table CHECK constraint

`remote_transport.rs:717` (`mark_remote_physical_intent_precommit`):

```rust
"UPDATE {PHYSICAL_INTENT_TABLE} SET intent_state = 'commit_intended', ..."
```

but the column is constrained in both schema paths, neither of which was
touched in this checkpoint:

- `sql/bootstrap.sql:511-518`
- `ecaz--0.1.1--0.1.2.sql:31-38`

```sql
intent_state text NOT NULL CHECK (
    intent_state IN ('prepare_requested','prepare_acked','commit_local','rollback_local')
),
```

Failure scenario: any coordinator INSERT that routes to a remote owner. The
owner write prepares fine; at commit time the `PreCommit` callback runs the
UPDATE, PostgreSQL rejects it with a check-constraint violation, the callback
calls `pgrx::error!`, and **the user's transaction aborts**. Every cross-owner
insert and backlink now fails at commit. The prepared transaction is then
resolved by the Abort callback, so nothing is corrupted — but the committed
write path is entirely non-functional at this head.

Fix: add `'commit_intended'` to the `CHECK` list in both files. Sequence it
between `prepare_acked` and `commit_local` for readability. Note
`ec_spire_remote_prepared_xact_intent` (`sql/bootstrap.sql:166`) carries the
same four-state list; leave it alone unless SPIRE adopts the same fence.

This is unreviewable by compilation — it needs the focused pgrx run or the
fixture. Please do not re-request review until at least one remote insert has
actually committed at this head.

## New P2 — a routed DELETE can now be silently and permanently lost

`physical_dml.rs`, `tombstone_dead_records`, remote branch:

```rust
Err(error) => {
    pgrx::warning!("ec_distann ambulkdelete could not tombstone remote vec_id ...");
    continue;
}
```

`continue` skips `delete_source_mapping`, which is right, but VACUUM proceeds
regardless: `ambulkdelete` returns success, the heap tuple is reclaimed, and
that source TID will never be reported by a future bulkdelete callback. The
map row survives as an orphan that nothing ever revisits. Net result: the
record stays live and untombstoned in the published graph forever, and its
row-tier tuple keeps answering queries for a deleted row — with only a
`WARNING` in the log.

The previous behaviour (error out, fail the VACUUM) was worse for availability
but at least retriable, which is why I raised P3-10 as a design question rather
than a defect. Trading a retriable failure for a silent permanent one is the
wrong direction.

Suggested shape: keep the warn-and-continue, but mark the map row as
`pending_tombstone` instead of leaving it indistinguishable from a healthy
mapping, and give the reaper endpoint (or a small maintenance function) a pass
that retries pending rows. Then the drill can assert the queue drains.

## New P3 — the `roster_spec_for_routes` fallback is now unreachable

With `conninfo: None` restored for the local route (correctly), the fallback
branch in `roster_spec_for_routes` — taken when the coordinator session has no
`ec_distann.roster` GUC — now hits
`"EC_NODE_DESCRIPTOR: resolved route has no conninfo"` on the local entry and
errors. Its doc comment still claims it exists precisely so remote DML works
"even when the coordinator session did not have the operator roster GUC
installed". One of the two has to change: either drop the fallback and require
the GUC explicitly, or source the local node's conninfo from the participant
binding rather than the route.

## Coverage gap still open

The two-writer concurrency drill adds real contention, but it only asserts
that no session errored and that readers see `top_k` rows. That is the same
assertion as before, run with more writers. It cannot observe the invariant
P2-6 protects: after the drill, check that **each** inserted vec_id appears in
the neighbor list of at least one of its selected forward neighbors, i.e. that
writer A's back-edge was not overwritten by writer B. Without that assertion
the drill would pass equally well against the pre-fix code.
