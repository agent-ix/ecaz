## New P1 — the two-writer back-edge assertion cannot pass

`distann_multicluster.rs`, `physical_concurrency_drill`:

```rust
let inserted_ids = (0..WRITERS).flat_map(|writer| (0..ITERATIONS).map(move |iteration| {
    900_000_i64 + base_rows as i64 + (writer * ITERATIONS + iteration) as i64
})).collect::<HashSet<_>>();
```

These are the source-table `id` column values. They are then compared against
values parsed out of `neighbor_vec_ids`:

```rust
for neighbor in neighbors.split(',').filter_map(|v| v.parse::<i64>().ok()) {
    if inserted_ids.contains(&neighbor) { found.insert(neighbor); }
}
```

`neighbor_vec_ids` holds **stable vec_ids** — 64-bit hashes of the 16-byte
source identity (`vec_id_from_source_identity` over the uuid derived from
`md5(id)`), not the small `id` integers. The two sets are disjoint by
construction, so `missing` is always the full inserted set, `back_edge_check`
is always false, and `Ok(pass && forward_neighbor_check)` always returns false.
The drill can never pass, no matter how correct the code under test is.

The fixture already has the right pattern for this: the routed DELETE drill
maps id → vec_id via `ec_distann_list_directory` joined to `dm` on
`t.ctid = ('(' || d.heap_block || ',' || d.heap_offset || ')')::tid`. The
coordinator source map (`ec_distann_physical_source_map` joined to `dm` on
`ctid = source_tid`) is an even more direct lookup and is what the new
remote-insert probe already uses. Resolve the 24 inserted ids to vec_ids first,
then intersect.

While you are in there: the assertion as written requires each inserted vec_id
to appear in *some* neighbor list anywhere on any owner. That is the right
smoke test, but it is not quite the P2-6 invariant. The lost-update symptom is
specifically that writer A's back-edge on a *shared target* is overwritten by
writer B. Consider also asserting per-target: for each target that both
writers selected, both new vec_ids are present (or the target is at full
degree and the prune result is stable). Not blocking; the domain fix is.

## Hypothesis worth testing first for the concurrent backlink failure (P2)

Before assuming a logic bug: the prepared-transaction protocol holds owner-side
row locks from `PREPARE TRANSACTION` until the coordinator's **post-commit**
callback runs `COMMIT PREPARED`. Round 2 added `SELECT ... FOR UPDATE` to
`amend_backlink` / `append_backlink_if_room` / `tombstone_owner_record` (the
correct P2-6 fix). Combine the two: two coordinator sessions inserting
concurrently, whose forward sets share a backlink target on the same owner,
now block on that target row across the whole remote round trip. If each holds
a prepared transaction the other is waiting behind, neither cluster's deadlock
detector can see the cycle — it is split across two nodes — so it resolves only
when `call_timeout()` fires, surfacing as exactly this kind of opaque remote
error.

If that is what is happening, the fix is a protocol-level ordering rule, not a
lock tweak: amend backlinks in a deterministic global order (e.g. ascending
target vec_id) so two writers can never hold-and-wait in opposite order, and/or
use `SELECT ... FOR UPDATE NOWAIT` / a bounded lock timeout on the owner and
let the coordinator retry. Worth checking `pg_locks` on the owner during a
reproduction before choosing.
