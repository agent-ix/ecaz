# Packet 021 — endpoint hardening: ACCEPT (scoped)

Reviewed `48195c196` in isolation.

The SQL boundary change is correct and complete for what it claims. All three
physical DML endpoints get `SECURITY DEFINER`, the fixed
`pg_catalog, @extschema@, pg_temp` search path, and `PUBLIC EXECUTE` revoked,
matching the existing `ec_distann_expand_physical_nodes` /
`ec_distann_materialize_*` hardening class. The signatures in the `ALTER` /
`REVOKE` statements match the `#[pg_extern]` definitions in
`remote_endpoint.rs`. `ec_distann_remote_prepared_xact_intent` and
`ec_distann_physical_source_map` also carry `REVOKE ALL ... FROM PUBLIC` in
both `sql/bootstrap.sql` and the `0.1.1--0.1.2` upgrade path.

**ACCEPT for the SQL-boundary change.** Two qualifications:

1. This closes the *ACL* half of AC-5. It does not close AC-5, which is a
   single-fault consistency criterion. See P1-2 and P1-5 in
   `reviews/task-167/022-overload-cleanup/feedback/2026-08-12-01-reviewer.md`:
   a committed coordinator transaction can still be rolled back on the owner,
   and the routed tombstone endpoint cannot execute on a participant at all.
   The acceptance-matrix edit pointing AC-5 at this packet claims more than the
   packet delivers.
2. `SECURITY DEFINER` on a write endpoint raises the stakes on the endpoint's
   own authorization check. The placement check inside these three functions is
   evaluated against the roster GUC the *caller* installed on the session
   (P3-11 in the same file), not against the immutable
   `descriptor.roster`. Worth tightening now that the functions run as the
   extension owner.

Full task-level review, including four P1 findings that block closeout, is in
packet 022's feedback.
