### P1 - Task 167's required M5 surface is not implemented

The task goal is that `aminsert` performs distributed self-insertion with bounded insert work and single-fault consistency (`plan/tasks/167-ec-distann-m5-incremental-insert.md:16`). The committed AM insert path still only spools to the D5 delta buffer (`src/am/ec_distann/routine.rs:79`), and graph folding is a separate maintenance SQL function (`src/am/ec_distann/insert.rs:396`). The code comment also says multi-node routing through the FR-083 write endpoint is a later wire-up (`src/am/ec_distann/insert.rs:399`), while the current write endpoint only accepts tombstone vec_ids (`src/am/ec_distann/remote_endpoint.rs:114`).

That means the completed branch has a local/operator-triggered fold, not distributed `aminsert` self-insertion. It also leaves `source_identity='include'` insert routing unsupported in the delta path (`src/am/ec_distann/dml.rs:291`). This may be a useful research milestone, but it is not the committed Task 167 scope.

### P1 - Required closeout evidence is missing

Task 167 requires TC-043, insert-then-query distinct_recall parity vs fresh rebuild via `ecaz bench suite`, insert throughput A/B, NFR-020 mid-insert drill logs, and per-insert work-bound counter evidence (`plan/tasks/167-ec-distann-m5-incremental-insert.md:35`, `plan/tasks/167-ec-distann-m5-incremental-insert.md:45`). Do not close Task 167 until those artifacts exist packet-locally. The current evidence supports “folded rows are queryable and full-reprune improves recall slightly,” not FR-083-AC-4/5/6.

### P2 - Fold recall remains materially below full rebuild

The original packet measured A_full recall@10 0.9560 vs B_fold 0.8900 (`reviews/task-167/004-fold-recall/artifacts/fold-recall.log:7`). The kept full-reprune backlink change improved B_fold to 0.8980, but the residual gap is still about 0.058 recall@10 (`reviews/task-167/004-fold-recall/artifacts/fold-recall.log:27`). That is not “insert-then-query distinct_recall parity vs fresh rebuild” as required by the task (`plan/tasks/167-ec-distann-m5-incremental-insert.md:37`).

The improvement is worth keeping, but the acceptance state should be “quality gap remains; REINDEX restores parity,” not “M5 delivered.”

### P2 - Per-insert work is not bounded by traversal cap + graph_degree amendments

The acceptance criteria require per-insert work-bound evidence (`plan/tasks/167-ec-distann-m5-incremental-insert.md:49`), and the task goal says insert cost is bounded by traversal cap plus `graph_degree` back-edge amendments (`plan/tasks/167-ec-distann-m5-incremental-insert.md:18`). Current `graph_insert_record` reads the full directory (`src/am/ec_distann/insert.rs:332`) and rebuilds/writes the entire sorted directory for every folded row (`src/am/ec_distann/insert.rs:378`). Folding a batch loops this per delta entry (`src/am/ec_distann/insert.rs:423`).

That is O(N) directory rewrite work per folded row, before considering I/O. It can be acceptable as a temporary research fold, but it is not the bounded insert surface described by Task 167. Either move to an insert-tail directory / batch directory rewrite, or document the descope and provide throughput evidence showing where this interim path is allowed.
