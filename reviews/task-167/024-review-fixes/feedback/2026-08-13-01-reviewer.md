## Confirmed fixed

- **Strict `EC_RECORD_MISSING` restored, with a bounded retry.**
  `lookup_graph_nodes` errors again, the `_missing` parameter is live, and
  `expand_nodes_masked` re-reads the whole frontier exactly once under
  `RegisteredSnapshotGuard::latest()` before failing. A second miss is a hard
  `OwnedRecordMissing`. This is option 2 from my list and it is the right
  shape. Two improvements over the prior code worth noting: the physical path
  now raises the **typed** `OwnedRecordMissing` (`XX001` / `EC_RECORD_MISSING`)
  rather than `Internal` with an `EC_RECORD_MISSING` text prefix, so it lands
  in the NFR-020 taxonomy properly for the first time; and the retry re-reads
  the complete frontier rather than just the missing ids, so a partially
  advanced snapshot cannot produce a mixed record set within one batch.
- **Missing vs not-visible split.** `is_current_vector_missing` now requires
  both the prefix and the `" is missing"` suffix, so only a genuinely absent
  current graph record prunes the edge; `" is not visible"` propagates.
  `apply_owner_backlink` was tightened the same way — a non-missing read error
  now returns instead of silently falling back to append-if-room. That is
  further than I asked and it is correct.
- **The code-copy source bug.** `&candidate.node.neighbor_codes[...]` →
  `&original_node.neighbor_codes[...]`. This is a real defect that I did not
  catch when I reviewed the round-2 `FOR UPDATE` change: `old_slot` was being
  computed against the re-read record while the code bytes were copied out of
  the stale planning-time record, so any target whose neighbour list had
  changed between planning and locking would have had its retained neighbours'
  quantized codes taken from the wrong slots — silently wrong scoring, no
  error, invisible except as recall loss. Good find.
- **Shared-target concurrency drill.** The construction is right: seed a node,
  find a target with at least three spare slots that is a neighbour of that
  seed, seed a near-duplicate of the target's own vector, then have both
  writers insert that exact vector on iteration 0 behind a `tokio::sync::Barrier`,
  and require both writers' vec_ids in the target's neighbour list afterwards.
  The barrier is what makes it an actual race rather than a sequence. This is
  the lost-update invariant, and it will fail if a writer's amendment is
  clobbered.
- **Pinned owner probe restored as instrumentation.** The equality-qualified
  coordinator query is back and its outcome is classified
  (`returned_sample` / `zero_rows` / `error_or_unexpected_row`) and logged with
  the raw output, while the gate is the owner-side exact probe. I accept that
  split — see the note below.

## Note on the zero-row question, which I think is now answerable

Having looked at it again with the qual restored: a zero-row result from
`WHERE source_id = X ORDER BY embedding <#> v LIMIT 1` is most likely **not** a
defect. If the qual is applied as a filter after the distributed ANN scan
produces its top-k, a row outside that top-k is filtered away and the query
correctly returns nothing. That is ordinary ANN-with-filter semantics, and it
means the original fixture assertion was unsound rather than the code being
broken — my round-4 objection was to the question going unanswered, not to the
widening itself.

So: keep the instrumentation, and when the next run lands, read the
`pinned_probe=` field. If it reports `zero_rows` consistently, record that
conclusion in the fixture comment and in the packet, and the matter is closed
properly. If it reports `error_or_unexpected_row`, that is a different signal
and worth chasing.

## Open, non-blocking, but they need the run to resolve

1. **The retry may not actually absorb the window it targets.** The transient
   gap is the interval between the coordinator's commit and its post-commit
   `COMMIT PREPARED` calls — a libpq connect plus a round trip per owner, so
   milliseconds. The retry is an immediate re-read; it is likely to land inside
   that same window. Restoring strictness is correct, but the practical
   consequence may be that the concurrency drill now fails with a hard
   `EC_RECORD_MISSING` where it previously passed by degrading. That is the
   single highest-risk item in this checkpoint and it is exactly what the
   un-run drill would tell you. If it does fail, the precise fix is the third
   option from last round: consult `ec_distann_remote_prepared_xact_intent`
   for an in-flight prepared write on that index/owner and degrade only then,
   which is timing-independent. A small bounded wait would also work but is
   less honest.
2. **No counter on the retry.** I asked for observability and got bounding
   instead, which is fine on its own, but a `stage_counters` metric for
   frontier retries would let the drill assert "retries occur only during
   churn" rather than leaving the behaviour invisible in steady state. Cheap
   to add while the counters are already being re-run.
3. **`amend_backlink` now appends when the target has spare degree instead of
   robust-pruning the union.** I think this change is right — it is closer to
   DiskANN Algorithm 2, which prunes only when the neighbour set exceeds R —
   and it is plausibly the fix for the "16 of 24 inserted nodes have no reverse
   edge" observation from the last run, since a below-degree target could
   previously prune the new edge away. But it is a **graph-construction change
   made to make a drill deterministic**, and per the repo's A/B rule it needs
   its own attribution in the 10k/50k/100k run rather than riding along with
   everything else. Please report the back-edge counters before and after this
   change, or gate it so the arms are separable.
4. **The full-degree contention path is still unasserted.** The shared-target
   drill deliberately picks a target with spare slots, so it exercises the new
   append path, not robust prune under two concurrent writers. That is the
   right first assertion; a second case at a saturated target would cover the
   path where the two writers' amendments genuinely compete for slots.
5. **The forward-side under-linking is still unexplained.** The reverse-edge
   half now has a plausible mechanism (item 3). The
   `forward_neighbors_selected=48 / inserts=48` mean of 1.0 from packet 020 is
   about the inserted node's *own* forward edges, which nothing in this
   checkpoint touches. Please read that counter on the re-run and explain it
   before citing AC-2.
