`pgvectorscale` is ~3.5× faster than `ec_diskann` at matched recall,
and builds ~6.6× faster on the same M5 fixture. At `list_size=200`,
`pgvectorscale` hits perfect 1.0000 recall in 1.37 ms mean while
`ec_diskann` hits 0.9970 in 2.79 ms mean.

This is the publishable post-M5 finding and the packet does not lie
about it — but the request.md, manifest, and (eventual)
`docs/benchmarks.md` update should state this gap explicitly rather
than burying it in a per-engine table. The honest read is: M5 DiskANN
is competitive on recall, not on latency or build time, vs the
external `pgvectorscale` baseline.

### Note 2 — Memory HWM column is all zeros

`latency-diskann-real10k-final-table.log` shows
`rss_peak_kb=0, hwm_peak_kb=0, memory_samples=0` for every list_size
row. The packet schema lists `memory_hwm_kb` as an expected metric,
but the bench surface didn't sample it on this run. Two options:

1. Drop the memory_hwm column from this packet's published claims
   and note the instrumentation gap in the manifest. The headline
   recall/latency/build/storage numbers still stand.
2. Re-run with whatever flag is needed to enable RSS sampling on
   the M5 benchmark surface. (Looking at the all-zero `memory_samples`
   field, the sampler simply didn't fire — likely a missing CLI flag
   on the `bench latency` invocation rather than a code gap.)

Either is fine. Don't silently leave the zero rows in `results.jsonl`
without a note — a downstream reader could mistakenly publish
"0 KB memory" as a real claim.

### Note 3 — Build-time / index-size symmetry

The packet captures `ec_diskann` build time (9.84s from `load-diskann`)
and pgvectorscale build time + index size (from the compare log:
1.48s, 5,136,384 B). It does not appear to extract `ec_diskann`'s
own `pg_relation_size` into a top-level result line, nor capture
`ec_hnsw` build time in a directly-comparable row.

The cross-engine table in `docs/benchmarks.md` will want a single
row per engine with `(recall@best, mean_ms@best, build_s, index_bytes)`.
Make sure `artifacts/results.jsonl` carries the parsed build time
and index size as `kind=storage` and `kind=load` rows for **all
three** engines, not just for the ones the underlying tool emitted
naturally.
