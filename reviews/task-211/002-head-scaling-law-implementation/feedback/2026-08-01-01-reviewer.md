# Task 211 / 002 — head scaling law implementation review

Verdict: **ACCEPT with notes**. Reviewed at code head `a08f6fe60` against
`spec/functional/distann/read/FR-088-distann-head-scaling-law.md`.

## What conforms

- **Law arithmetic (AC-1).** `DistannHeadSizingAttestation::resolve`
  (`src/am/ec_distann/generation_descriptor.rs`) is exactly the pinned
  sequence the spec demands: one f64 multiply of the reloption rate by N,
  `ceil`, clamp to [floor, ceiling]. Deterministic across replays/ISAs.
- **v3 attestation (AC-2).** The v3 build-options subrecord carries all
  seven attested fields (resolved C, sample_count, rate bits, floor,
  ceiling, N, law-active), is validated on both encode and decode
  (`options.encode()?` round-trip inside `decode`), and byte-size math
  checks out (65 + 37 = 102). Because build options are digest-bound in the
  build spec/manifest chain, tampering breaks the chain; the unit test
  demonstrates a tampered rate refuses to encode.
- **Precedence and validation (AC-3).** Rate 0 → `head_sizing: None`,
  explicit cap governs, encoded as v1/v2 → decodes law-inactive, which
  matches the spec's decode rule for pre-law epochs. `EC_HEAD_SIZING` fires
  on non-finite/negative rate, floor > ceiling, out-of-domain bounds, and
  `validate_head_sizing_inputs` is called at the top of `build_epoch`
  before capture-adjacent work.
- **Trained-policy reconciliation (AC-4).** Both the rate-0 path
  (explicit ≠ 4096) and the law path (resolved ≠ 4096) fail with
  `EC_HEAD_TRAINING`, and `DistannBuildOptions::encode` re-checks it, so an
  inconsistent combination cannot be attested.
- **Honest outcome (AC-5 + verification scope).** The 0.02 law arms
  resolved 200/1000/2000 as predicted, hop counters were reported, no
  consistent win appeared, and the packet keeps the fixed-cap default —
  precisely the "law implemented, default unchanged, re-sweep at 1M+"
  outcome the spec pre-authorizes. This is the right call on this evidence.
- Fixture/suite plumbing (`--head-sampling-rate/--head-cap-floor/
  --head-cap-ceiling` through `distann_multicluster` and the suite step)
  validates bounds at every layer and stamps law provenance into the
  `physical_benchmark_*` result lines.

## Notes (non-blocking)

1. **Decode error text is stale.** The length-mismatch error in
   `DistannBuildOptions::decode` still says "expected {V1} or {V2}" bytes;
   a 102-byte v3 record is now also legal. Cosmetic, worth fixing next
   touch.
2. **`law_active` is vestigial as encoded.** `validate()` rejects
   `law_active == false`, and rate-0 builds encode v1/v2 with no
   attestation at all, so the flag is always `true` in any v3 record. Fine
   under the spec's decode rule, but the field can never carry information;
   a one-line comment saying so would prevent someone "fixing" it later.
3. **Reloption registration ranges are wide open**
   (`head_cap_floor`/`head_cap_ceiling` registered with
   `i32::MIN..i32::MAX`, rate with ±1e308). Acceptable because
   `EC_HEAD_SIZING` enforces the real domain at T2, but tightening the
   reloption ranges would fail faster at `CREATE INDEX` time.
4. **Latency deltas in this packet are inside run noise.** The Task 212
   counter run shows a 30% swing (56.4 vs 43.5 ms @50k) between two arms I
   verified execute identical paths (see my Task 212 feedback), so the
   +2.5 ms @100k law-arm regression here is not a measured fact either
   direction. This does not threaten the packet's decision — keeping the
   fixed-cap default is the conservative branch — but do not later cite
   these latency columns as a measured law penalty.
5. **Curiosity, not a blocker:** at 10k the law arm (C=200, a 20× smaller
   head) matched fixed-cap recall and *lowered* mean hops (11.90 → 11.60).
   Smaller heads should seed worse. Plausibly the smaller head's graph is
   denser per landmark; if the 1M+ re-sweep happens, this inversion is
   worth a counter-level look.
