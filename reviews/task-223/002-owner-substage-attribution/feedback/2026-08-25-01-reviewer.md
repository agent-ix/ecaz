   `reviews/task-222/004-full-scale-decision/artifacts/run/100k/distann-multinode-summary.log`
   the `variant=projected-candidate` rows read
   `mean_ms=11.60` (`physical_benchmark_latency`, `count=50`, `cache=warm`,

   `extension_build_profile=release`) and
   `stage=materialize_owner_payload_sql_work ... mean_ms=0.514999`.
   `projected-candidate` is the accepted production default, so the
   denominator and the bucket come from the same retained path.

2. **The arithmetic holds.** 0.514999 / 11.600000 = 4.439647%; the 5% gate is
   0.580000 ms; the shortfalls are 0.065001 ms and 0.485001 ms. Both registered
   gates fail.

3. **The timer scope claim is true in code, not just in prose.** In
   `src/am/ec_distann/generation_read.rs`, `payload_sql_started` is taken
   immediately before `qualified_relation_name` / payload-SQL construction
   (~line 2406) and `payload_sql_ns` is stamped after the `nodes.zip(payloads)`
   response assembly (~line 2629). The enclosed span therefore covers relation
   name and SQL build, TID argument construction, `client.select` SPI
   execution, PostgreSQL array construction, the `payload_nulls` /
   `payload_values` Rust decode and byte flattening, and ordered row assembly —
   exactly the mechanisms a direct row-tier tuple path would replace. Nothing
   Task 223 could remove sits outside it.

4. **The excluded remainder really is non-addressable by this candidate.**
   `owner_endpoint_work` (0.817929) decomposes as
   `open_validate` 0.022598 + `node_lookup` 0.278229 + `payload_sql` 0.514999
   = 0.815826, which reconciles to the parent within 0.002 ms. `node_lookup_ns`
   is `resolve_nodes` — the graph-to-row TID resolution a direct tuple fetch
   still has to perform to get a TID at all. Scoping it out is correct, not
   convenient. (It is addressable by a *different* mechanism — the
   `expanded_locator` arm, which is Task 221 and already review-closed as a
   regression — so it is not silently orphaned either.)

5. **The bound is more conservative than the packet claims.** The owner stages
   are recorded at `samples=100` over `scans=50`, i.e. summed across owners,
   while `materialize_owner_endpoint_critical` (the per-scan max) is 0.428234
   ms. Owner work overlaps across the three owners, so the *end-to-end* saving
   from deleting the entire payload-SQL bucket is smaller than 0.514999 ms, not
   equal to it. The stated 4.439647% is an over-estimate of the ceiling and the
   STOP is stronger than argued.

  satisfied. The criterion asks for a decision from a measurable ceiling, not

  re-derive a number already bounded above.
