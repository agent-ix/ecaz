## Blocking before closeout (not blocking further iteration)

### B1. The latency numbers are scalar-vs-SIMD and must not decide the gate

TQ+ scoring is **scalar-only**. `score_tqplus_4bit_from_parts` /
`score_tqplus_no_qjl_4bit_unrenormalized_with_qjl` is a plain per-dimension LUT
gather:

```rust
for dim_index in 0..self.original_dim {
    let centroid_index = mse_index_at(mse_packed, dim_index, bits_per_index) as usize;
    score += prepared.lut[dim_index * num_centroids + centroid_index];
}
```

There is **no `score_tqplus_*_avx2` / `_neon` variant** (confirmed by grep).
Baseline TurboQuant, by contrast, scores through the SIMD tiled-LUT path
(`PreparedTiledLutNoQjl4BitQuery`, `score_ip_from_parts_{avx2,neon}`) on the
1536-dim DBPedia tile, and through SIMD `score_ip_from_parts_*` on the generic
768-dim path.

So the reported 3× (1536) / 4.8× (768) p50 gaps are largely measuring
"TQ+ has no vectorized kernel yet," not the intrinsic cost of calibration —
calibration folds entirely into the LUT and the per-candidate bias, so a tiled
TQ+ scorer should land within noise of baseline. **The closeout must not cite
these latency numbers as evidence against TQ+.** Before the promote/defer
decision, either:

- (a) add a tiled/SIMD TQ+ scorer so latency is apples-to-apples; or
- (b) explicitly mark latency as **non-comparable** in the closeout and decide
  on recall / score-error / storage alone.

The good news for the decision: even setting latency aside, recall is neutral or
slightly negative across 10k/50k/100k and on the projected-QJL lane. So the
evidence still points at **defer / keep-experimental** — but the *stated reason*
should be "no recall/quality win on DBPedia," not "3× slower," because the
latter is an implementation gap, not a property of TQ+.

### B2. Cross-corpus is still required by the task and the ADR

Every DBPedia cell is one embedding distribution. ADR-081's measurement
commitments and the task's Phase 5 both require ≥1 non-DBPedia corpus before any
promote/defer is final. The coder lists this as open — just confirming it's a
hard gate, not optional, even for a "defer" outcome (a defer should show the
boundary isn't DBPedia-specific).

## Non-blocking notes

- **N1. ADR-081 is `status: PROPOSED`.** Treat this review as approval of the
  *experimental* direction and the reloption name. Flip it to `ACCEPTED` (it's
  the Phase-1 gate) once you're past iteration, and add the cross-corpus
  requirement to its "Measurement Commitments" as a non-waivable item.
- **N2. Calibration persistence reuses the `IvfPqCodebookTuple` chain /
  `pq_codebook_head`.** Fine for an experimental IVF-only profile, but the
  diagnostic/metadata labels still read as "PQ codebook." If TQ+ ever graduates
  out of experimental, rename to a TurboQuant-calibration label (the ADR-072
  lineage concern). Note it as a graduation precondition; don't churn now.
- **N3. `unsafe fn tqplus_model_for_scan<'a>(...) -> Result<&'a IvfTqPlusModel>`**
  returns a borrow tied to the scan opaque and is correctly `unsafe fn` with a
  lifetime/validity doc — consistent with the anti-pattern-B rule. Just
  double-check `'a` is derived from the `opaque` borrow (not synthesized) when
  you next touch it; looks right as written.
- **N4. Scope.** Re-doing IVF here (rather than treating Task 86's reverted IVF
  result as "already validated") is the correct call — the Task 86 TQ+ code was
  reverted and tag-4 is now `coarse_rerank`, so re-landing on current main under
  the experimental profile is necessary groundwork. SPIRE/HNSW/DiskANN stay
  correctly gated behind the IVF promotion decision.

## Bottom line

The engineering and the evidence discipline here are good, and the honest
negative result is genuinely useful. The one thing that would make the eventual
closeout unsound is leaning on the latency delta — fix that comparability (B1)
and add cross-corpus (B2) before writing the promote/defer decision. Everything
through packet 005 is approvable as iteration toward that closeout.
