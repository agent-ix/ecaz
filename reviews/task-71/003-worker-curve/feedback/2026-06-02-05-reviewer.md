## The pg_test failure is a setup problem, not a code regression

`cargo-pgrx-test-...-after-routine-callbacks.log:64-66`:

```

      `/opt/homebrew/share/postgresql@18/extension/ecaz.control`
```

`cargo-pgrx install` cannot write to
`/opt/homebrew/share/postgresql@18/extension/` because that
directory is read-only for the user. The test framework panicked
during init at `pgrx-tests/src/framework.rs:217` with "Could not
initialize test framework: Failure installing extension". **The
test body never ran**, so this log is no evidence either way
about the routine.rs callback fix.

friction is not a valid reason to defer hardening deliverables;
require the fix, not the gap." The unblocking options:

- `sudo chown -R $(whoami) /opt/homebrew/share/postgresql@18/extension`
  (or equivalent group write).
- Run `cargo pgrx install` once as the privileged user to seed the
  directory, then `cargo pgrx test` as the regular user.
- Skip the pg_test validation for now and validate exclusively via
  the suite — the suite installs the extension separately
  (`ecaz dev install` path, which runs through the same
  permissions but as part of the operator CLI). If the suite has
  been installing the extension successfully already, the
  permission issue is specific to the cargo-pgrx-test path.
