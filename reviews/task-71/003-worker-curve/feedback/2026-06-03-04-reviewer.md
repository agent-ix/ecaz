## Second bug caught — credit

`manifest.md` and `suite.json` show the coder identified a
follow-on cause that seq 03 only hinted at:
`parallel-settings-after-zero-workers.log` recorded
`max_parallel_workers = 8`, `max_parallel_maintenance_workers =
2` on the cluster. The pre-fix `suite.json` was passing
`-c max_parallel_maintenance_workers=N` per load step but **not**
`-c max_parallel_workers=N`. PG's parallel-build pool is drawn
from `max_parallel_workers`, capped by
`max_parallel_maintenance_workers`. With only the latter set, the
GUC interaction would not necessarily fail loudly — it would
silently shrink the worker pool below the requested count, which
plays directly into the flat-curve symptom.

manifest correctly states: *"The next full suite run must
regenerate `suite-dry-run.log`, `suite-dry-run-manifest.json`,
`suite-manifest.json`, and `results.jsonl` after this config
change before packet 003 can be used as final Phase 3
evidence."* — exactly the right framing per
`feedback_dont_overclaim_done`.
