heap-ingest scaling, leader-side bottleneck as predicted.

## Verdict — Stop Condition, cleanly

Task §"Exit Criteria" says "multi-× build-time win at workers
≥ 2". **Not met.** Best observed is 1.30× at 100k.

Task §"Stop Conditions" says: "Stop if Phase 1 design shows
the per-worker overhead is comparable to the heap-scan
speedup at M5 corpus sizes (i.e. parallel build is a wash on
local hardware)."

This is **the soft-wash case**:
- Heap-scan phase parallelizes correctly (3.2× at w=8 on 100k).
- Total build wall time is dominated by leader-side work
  (PQ-FastScan training, centroid assignment, posting flush)
  that Option A explicitly chose NOT to parallelize.
- Result: real gain at the heap-ingest phase, capped at the
  Amdahl ceiling for total wall time.

This is a clean Stop Condition closeout. The implementation
is **correct and useful** — `amcanbuildparallel = true` is
honest, the parallel-build callbacks are wired, and on
larger fixtures or different hardware (Graviton) the parallel
share may dominate differently. The flag stays.

## Anomaly — `parallel_workers_delta` in suite-manifest is always 0

Every load step in `suite-manifest.json` records:

```
"parallel_workers_before": 0
"parallel_workers_after":  0
"parallel_workers_delta":  0
```

This contradicts the loader's own `workers_launched=N`
counter, which is correctly non-zero per cell. The
suite-runner's bracket capture using
`pg_stat_get_db_parallel_workers_launched(oid)` is **not
reading what we think it's reading**. Likely cause:

- The capture runs in a separate `psql` / `ecaz dev sql` child
  connection from the load step's own connection. PG's stat
  function returns a session-cumulative value that depends on
  where you call it from, OR
- The function semantics in PG18 differ from what was
  assumed.

**This is not a Phase 3 blocker** — the loader's `[loader]
ec_ivf build timing: workers_launched=N` line is the
authoritative ground truth and it's correct. But the suite
runner's `capture_parallel_workers` plumbing
(commits f19382afa, 39d66d13b) should be flagged for a future
fix or removed, because right now it's misleading: it tells a
casual reader "no workers spawned" while the actual heap-ingest
parallelism is happening fine.

**Recommendation**: log a follow-up to either (a) replace the
bracket query with parsing the loader-timing line into the
`StepRecord` fields (already half-done via
`parse_ec_ivf_build_timing_line` from the uncommitted suite.rs
diff), or (b) just remove the bracket capture since the
loader-timing line covers it. Option (a) keeps FR-038 alignment.
