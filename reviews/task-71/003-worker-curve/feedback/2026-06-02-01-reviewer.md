# Phase 3 Worker-Curve Review — BLOCK

## Verdict

**BLOCK.** The packet honestly frames itself as setup-only, and
the runner/CLI changes are sound. The partial data that did land
already exposes the load-bearing problem: **no measured speedup at
any worker count, and zero positive evidence that PG launched any
parallel workers.** This packet cannot close Phase 3, and the
underlying numbers cross into Task §"Stop Conditions" territory
for the Phase 2 implementation itself.

`suite-manifest.json` shows 25 of 50 steps are still `pending` —
everything from `load-real50k-w1` onward. Phase 3 explicitly
includes 50k and 100k fixtures.

## Suite runner conformance — OK

Driven by `ecaz bench suite` with checked-in `suite.json`. No
shell-glue. The new `pgoptions` / `table_reloptions` / explicit
`load_log` / `recall_log` / `storage_log` / `truth_path` fields in
`crates/ecaz-cli/src/commands/bench/suite.rs` and the
`table_reloptions` plumbing in `crates/ecaz-cli/src/commands/corpus/load.rs`
have unit-test coverage (`cargo-test-ecaz-cli-suite-table-reloptions.log`,
etc.). FR-038 compliance is preserved.

## Numerical results — speedup is absent

Build wall times (`built …_idx in N.NNs`):

| corpus | w=1 | w=2 | w=4 | w=8 |
|---|---|---|---|---|
| 10k | 13.62s | 13.30s | 16.38s | 13.16s |
| 25k | 24.26s | 23.03s | 22.68s | 23.54s |

This is a wash. w=4 on 10k is slower than w=1. The Exit Criterion
"multi-× build-time win at workers ≥ 2" is **unmet** by an order
of magnitude in the cells that did run, and matches the
empirically-flat curve the Phase 1 packet was supposed to predict
via an Amdahl bound (see feedback on packet 001).

## Worker-launch verification — FAILS

`parallel-workers-before.log` shows
`pg_stat_get_db_parallel_workers_launched = 0`. There is no
`parallel-workers-after.log` artifact. There is zero positive
evidence that PG ever launched a parallel worker during these
builds. The flat build-time curve is consistent with workers
never being spawned at all.

This is the load-bearing missing piece. Task 71's whole premise
(`amcanbuildparallel = true`) cannot be claimed validated without
a non-zero `workers_launched` delta per build.

## Determinism / index size

Reported totals (from suite output, not in `manifest.md`):

- real10k: 2.9 MiB at w=1/2/4/8
- real25k: 5.9 MiB at w=1/2/4/8

Byte-equal at the corpus level for the cells that ran. But:

- `manifest.md` does **not** record per-worker storage results
  per the CLAUDE.md "manifest.md should record … key result
  lines that `request.md` cites" rule.
- "Total index MiB" is a coarse equivalence proxy. Per Task
  §"Exit Criteria", structural equivalence should be a per-page
  digest or `pg_relation_size` parity at minimum.
- 50k/100k size invariance is not exercised at all.

## Recall

10k: 1.0000 at all worker counts at nprobe=48, rerank_width=750.
25k: 0.9990 at all worker counts. The `1.0000` saturation on 10k
is suspicious — the sweep is hiding any worker-driven drift the
exit criterion is designed to catch. Also:

- `request.md` does **not** cite the Task 31 baseline numbers it
  claims to be within 0.5 pp of.
- The loader prints
  `manifest verification failed for …prefix="ec_hnsw_real_10k"
  (expected "task71_real10k_w1")` and the suite sets
  `allow_manifest_mismatch: true`. Comparing recall against a
  Task 31 baseline while bypassing manifest equality needs an
  explicit "same vectors, different naming" justification, not
  a silent bypass flag.

## Memory HWM

`sample_backend_memory: true` is in suite defaults but no HWM is
reported. Per packet 002 feedback, the leader's `worker_tuples`
holds a full second copy of the heap. Either capture the value
or mark `not_measured` per CLAUDE.md and the Task 33 packet 002
gap rule.

## Blocking items before Phase 3 can close

1. **Re-run the full suite to completion** for real50k and
   real100k at workers 1/2/4/8.
2. **Confirm `workers_launched > 0`.** Emit
   `parallel-workers-after.log` and add a per-build

3. **If workers_launched stays 0 or speedup stays flat**, do
   **not** retry. File the Stop-Condition finding — this is a
   Phase 2 implementation regression / a wash on M5 hardware,
   either of which is a stop condition explicitly named in the
   task plan. Defer to Graviton/cloud-class fixture instead.
4. **Per-cell rows in `manifest.md`** with build-time, recall,
   `pg_relation_size(idx)`, `workers_launched` delta, and the
   suite step status.
5. **Cite Task 31 baseline recall numbers explicitly** in
   `request.md` with the file paths they come from.
6. **Justify or remove** `allow_manifest_mismatch: true`. If the
   real10k/real25k corpora are byte-identical to Task 31's despite
   the manifest-prefix change, say so. If they are not, the
   recall comparison is suspect.
7. **Add per-build `workers_launched` capture** inside the suite
   runner itself (this is an `ecaz bench suite` gap if the
   counter has to be read outside the suite to be trusted).
