# Phase 3 Worker-Curve — Root cause found: stale ecaz.dylib

## Headline

The third-bug pattern flagged in seq 13 / 14 was an **installed-
binary staleness** issue, not a wiring bug. The running PG18
cluster was using a stale `ecaz.dylib` that pre-dated the
routine.rs callbacks fix (and probably much of the recent Task
71 / Task 69 work). The suite path picked up that stale binary
on every run; pg_test bypassed it by installing the fresh build
via `cargo pgrx test`.

## What the probe number means

10k corpus, w=2 reloption, **436.44 ms** build vs. the matrix's
13.05–13.62s. That's **~30×**. Two readings are consistent
with the number:

a. The fresh dylib has Task 69's rayon-parallel k-means and
   assignment in the leader process. On a 10k fixture that
   alone can dominate — the previous 13s was a stale single-
   threaded build path. Serial-but-vectorized + rayon-parallel
   reduction can hit sub-second.

b. The fresh dylib also has the parallel-build callbacks live,
   so workers spawned for this build and ran the heap ingest
   in parallel.

The probe log does **not** include `workers_launched` —
`pg_stat_get_db_parallel_workers_launched` wasn't sampled, and
the `[loader] ec_ivf build timing: …` line is not in this
probe's output yet (the suite.rs parser landed in the working
tree but the loader-emit side isn't visible in this artifact).

We do not yet know whether (a) alone explains the win, or
whether (b) is also live.

## Required next coder action — narrow validation

1. **Commit** the install logs + probe + suite.rs change as a
   single triage commit. The diagnostic step alone is valuable
   evidence.
2. **Verify the build is actually parallel.** Two cheap ways:
   - Add a single
     `ecaz dev sql -- "SELECT pg_stat_get_db_parallel_workers_launched(oid)
      FROM pg_database WHERE datname = current_database();"`
     immediately before AND after a single
     `load-real10k-w4` probe. Delta > 0 = workers spawned.
   - OR re-run a one-shot `pg_test` of
     `test_ec_ivf_parallel_build_workers_and_counts` against
     the freshly-installed dylib (escalated path, same as
     before).
3. **Then** re-run the full suite end-to-end with the fresh
   dylib. The post-install build times will dominate everything
   the prior matrix showed; the prior matrix becomes
   pre-install baseline.

## Two scenarios for what the post-install matrix will show

- **Both (a) and (b) live**: build times collapse dramatically
  AND parallel_workers_delta > 0 at w >= 2. Exit Criterion met.
  Phase 3 closeout straightforward.
- **Only (a) live**: build times collapse, but delta stays 0.
  That re-opens the seq 13 triage — Task 69's rayon win
  dominates Task 71's parallel-build path entirely, and the
  parallel-build callback wiring may not actually be triggered
  at these corpus sizes. That would invoke Task §"Stop
  Conditions" cleanly: the parallel-build path is correctly
  wired (per pg_test) but doesn't add value on M5 because Task
  69's leader-side parallelism already saturates the work.

Either outcome is a valid Task closeout — but they require
different packet 004 framings.
