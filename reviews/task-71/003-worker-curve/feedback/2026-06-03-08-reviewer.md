## What's the same and what's different (pg_test vs suite)

Both paths:
- Set `max_parallel_workers=N` and
  `max_parallel_maintenance_workers=N`
- Set the table's `parallel_workers=N` reloption
- Have the `amestimateparallelscan` / `aminitparallelscan` /
  `amparallelrescan` callbacks wired (20d4db545)
- Use `amcanbuildparallel = true`

Differences worth triaging:

1. **Connection-vs-session for the GUC.** pg_test runs `SET
   max_parallel_workers = 4` via Spi inside the test
   transaction. The suite passes `-c max_parallel_workers=N`
   via PGOPTIONS. Verify PGOPTIONS actually applies to the
   `ecaz corpus load` child connection — quick test: add a
   `SHOW max_parallel_workers` to the load log output, or do a
   one-shot
   `ecaz dev sql -- "SHOW max_parallel_workers"` with the same
   PGOPTIONS to confirm.

2. **Table size threshold in `compute_parallel_worker`.**
   PG's planner uses `min_parallel_table_scan_size` (default
   8MB) as a floor. The pg_test corpus is 128 rows — way under
   8MB — but works because `parallel_workers` reloption on the
   table is **forced** when explicitly set, bypassing the size
   floor. Verify the suite's table actually has the reloption
   set: `\d+ task71_real10k_w4_corpus` should show
   `parallel_workers=4` in the storage parameters. If not,
   `--table-reloption parallel_workers=N` isn't being applied
   by the load step.

3. **The CREATE INDEX reloption list omits parallel_workers.**
   The load log shows the index is created with
   `reloptions=[storage_format=pq_fastscan, pq_group_size=8,
   nlists=64, nprobe=48, rerank=heap_f32, rerank_width=750]` —
   no `parallel_workers`. That's correct for the **index**
   (IVF doesn't take a `parallel_workers` reloption), but is
   the **table** reloption actually live? If
   `--table-reloption parallel_workers=N` runs as a CREATE
   TABLE WITH clause AFTER the table was already loaded, the
   ALTER would need to fire — verify in the loader.

4. **`amestimateparallelscan` returning small estimates.**
   The shared-state estimator might be returning an
   underestimate that's causing PG's planner to not allocate
   workers. Worth a `RAISE NOTICE` inside that callback during
   suite run to confirm it's called and what it returns.

5. **The `parallel_workers_before/after` capture query**.
   Quick sanity: confirm the query
   `pg_stat_get_db_parallel_workers_launched(oid)` actually
   increments inside the pg_test session — if it does in
   pg_test but not in suite, that narrows the gap to PGOPTIONS
   propagation or table reloption application.
