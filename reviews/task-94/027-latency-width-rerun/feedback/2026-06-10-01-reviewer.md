# Reviewer feedback — Task 94 Packet 027 (latency/width rerun follow-up)

## Verdict

**Width-histogram and provenance findings: closed.** The catalog diagnosis
was correct, the width buckets are present end-to-end, and the healthy
two-step cells are good evidence.

**Latency mystery: root cause found.** I completed the diagnosis the packet
left open. The slow profile is a **debug-built `ecaz.so`** being silently
installed into the shared pgrx tree by `#[pg_test]` runs. The cache-state
names were a red herring — pure ordering correlation. Full evidence chain
below; it is verifiable on the bench host right now.

## Root cause: pg_test runs install the debug backend over the release one

`cargo test --lib grouped_pq` includes the PG18 `#[pg_test]`. The pgrx test
framework builds the extension in the **debug profile** and installs it
into `/home/peter/.pgrx/18.3/pgrx-install/lib/postgresql/ecaz.so` — the
same tree the benchmark PostgreSQL (socket `/home/peter/.pgrx`, port 28818)
loads `ecaz.so` from on every new backend connection. Any benchmark run
after a pg_test run, without re-running `ecaz dev install`, measures a
debug build: a deterministic, constant-factor ~8–19× slowdown of all
per-tuple scoring work — which is exactly why **batch-off cells and DiskANN
cells were equally slow** and why the numbers reproduced so precisely.

### Evidence chain (all verifiable on the bench host)

1. **The installed backend is the debug artifact right now.**
   `sha256(/home/peter/.pgrx/18.3/pgrx-install/lib/postgresql/ecaz.so)` =
   `sha256(target/debug/libecaz.so)` = `141835bef9d4...` (273 MB).
   `target/release/libecaz.so` is `d5d0a6009e2b...` (27 MB) — exactly the
   SHA this packet's manifest recorded from `ecaz dev install` at 16:17.

2. **The overwrite timestamp lands inside the pg_test run.**
   `target/debug/libecaz.so` mtime = 16:22:29.89; installed `ecaz.so`
   mtime = 16:22:30.69. `cargo-test-grouped-pq.log` (packet 101/003, the
   set with the PG18 pg_test) started 16:22:11.

3. **Fast and slow runs bracket the overwrite perfectly.**
   - 16:17:49 release build + install (SHA asserted) →
     16:21:35 healthy two-step run: **2.70 ms / 15.3 ms** (release backend).
   - 16:22:30 debug overwrite →
     16:24:32 diagnostic full rerun: **41.1 ms / …** (debug backend).

4. **The identical pattern preceded packet 026.** The packet-001 cargo
   test logs were captured 13:02:51–13:03:32 (grouped_pq with its pg_test
   at 13:02:57); the packet-026 suite started 13:04:32 — every cell ran on
   a debug backend. Packet 025 (Jun 9) ran with a release backend → fast.

5. **The slowdown is deterministic, not load.** Per-step durations of
   packet 026 vs this packet's diagnostic rerun match within 1–3%
   (10k-off 56.7 s vs 55.1 s; 25k-off 122.0 vs 119.5; 100k-off 427.9 vs
   422.0). Concurrent-load interference cannot reproduce that; a build
   profile does.

6. **Cache-state names are inert.** `--cache-state` is an operator label
   recorded with each row (`crates/ecaz-cli/src/commands/bench/latency.rs:85-87`);
   it controls nothing. The correlation existed because the
   original-names full rerun happened to run after the debug overwrite
   and the fresh-names two-step before it.

## Remediation

### Immediate (unblocks AC5)

Run `ecaz dev install ecaz-pg-test --pg 18`, then the full matrix suite,
with **no cargo test invocations between install and bench**. Expect
numbers in packet-025 territory. The healthy two-step cells already hint
AC5 will pass with headroom: IVF 10k batch-on 2.70/4.10 ms vs packet 025's
2.90/4.63 ms, and DiskANN 50k forced grouped-PQ 15.3/15.5 ms vs 22.3/18.7 ms
— the coverage win (4% → 100% kernel attribution) is showing up as real
end-to-end latency improvement on a release backend.

### Systemic (per the FR-038 extend-the-runner rule, not ad hoc glue)

This failure mode will recur — focused pg_tests are part of the normal
checkpoint loop. Make it impossible to hit silently:

1. Add a SQL-visible build-profile marker to the extension, e.g.
   `ecaz_build_profile()` returning `'release'`/`'debug'` from
   `cfg!(debug_assertions)`. PG-side truth — immune to stale `target/`
   artifacts and to .so-on-disk vs loaded-.so skew.
2. Teach `ecaz bench suite run` a preflight: query the profile (and record
   the installed backend sha256) into `suite-manifest.json` before step 1,
   and **refuse latency/recall steps on a debug backend** unless an
   explicit `--allow-debug-backend` flag is passed.
3. Land that as its own commit before the AC5 rerun, so the rerun manifest
   itself carries the proof.

Item 1+2 should be considered part of closing this finding; the AC5 rerun
packet should cite the recorded profile line.
