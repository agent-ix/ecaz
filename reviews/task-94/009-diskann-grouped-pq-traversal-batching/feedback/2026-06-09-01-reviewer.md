# Reviewer feedback — Task 94 Packet 009 (DiskANN traversal batching)

## Verdict

**Approve.** This is the highest-value packet in the Phase 6 series:
it moves the block kernel from "registered at the codec surface" to
"reachable from the production DiskANN traversal", with the sign
convention and profiling counters preserved. The `VamanaPrefilter`
trait design is the right shape.

Reviewed against commit `bc0133f4b`.

## Spot checks

### Trait design

- `VamanaPrefilter { score, score_batch }` with a default scalar
  `score_batch`, plus a blanket impl for `Fn(&VamanaNodeTuple) -> f32`
  — every existing closure caller compiles unchanged with scalar
  behavior. Zero-risk migration path. ✓
- `vamana_scan{,_with,_with_frontier_profile}` and
  `greedy_descent{,_with,_with_frontier_profile}` bounds switched from
  `Fn` to `VamanaPrefilter`. ✓

### Greedy-descent batching

Both descent variants now collect an expansion's deduplicated
neighbors (`!in_frontier` filtered), read their tuples, then score the
whole expansion through `score_batch` before frontier insertion.
Ordering of frontier pushes is preserved (same iteration order as the
old interleaved loop), so traversal behavior is unchanged when scores
are bit-identical — and they are (see below). Memory per expansion is
bounded by graph degree. ✓

### Sign convention

`score_diskann_prepared_prefilter_batch` scores the grouped-PQ batch
as positive inner product via `score_grouped_pq_batch_for`, then
negates in place — matching the scalar
`DiskannPreparedPrefilter::score` convention. The test asserts batch
score bits == `-grouped_pq_score_f32` bits == scalar `score()` bits
per tuple. Bit-exact equivalence of old and new traversal scoring. ✓
Non-grouped-PQ prefilter variants fall back to the per-tuple scalar
loop, behavior unchanged. ✓

### Call-site coverage

- Normal scan path (`routine.rs:827`): passes `prefilter` directly. ✓
- Insert planning (`aminsert`, routine.rs:379): passes `&prefilter`
  (second impl for `&DiskannPreparedPrefilter` covers this). ✓
- Profiled scan: `ProfiledDiskannPrefilter` wraps both methods;
  `prefilter_count += tuples.len()` keeps per-candidate counting
  consistent with the old per-call counting. ✓

### Tests

- `greedy_descent_uses_batch_prefilter_for_neighbor_expansions` proves
  structurally that descent calls the batch override (counting
  prefilter). ✓
- Prepared-prefilter batch test asserts bit-exact negated scores plus
  `(diskann, grouped_pq)` counter attribution 32 kernel / 7 scalar. ✓

## Non-blocking notes

### N1 — Expansion batches are degree-bound; sub-32 expansions score scalar

A greedy-descent expansion batch is at most the node's neighbor count
after dedup. With typical Vamana degree near 32–64, many expansions
will be sub-32 and take the scalar path (correctly recorded as scalar
rows). This is inherent to per-expansion batching, not a defect — but
the closeout's scoring-share evidence should report the
kernel-vs-scalar candidate split from the counters on a real graph so
the actual kernel utilization is visible, not assumed.

### N2 — Insert-time scoring now feeds the same counters

`aminsert` traversal batches now record under `surface=diskann` too.
For benchmark packets, counter snapshots should be taken around the
query phase (the bench CLI already resets/samples per sweep), so this
won't pollute attribution — flagging so closeout artifacts note that
counter rows include any concurrent insert traffic if present.
