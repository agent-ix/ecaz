### VL-agnostic assembly

`core::arch::global_asm!` ecaz_grouped_pq_sve_accumulate_f32 (sve.rs:8-37):

```asm
mov x3, #0
1:
  whilelt p0.s, x3, x2          ; predicate for lanes x3..x3+VL bounded by x2=32
  b.none 2f
  ld1w z0.s, p0/z, [x0, x3, lsl #2]  ; out[x3..]
  ld1w z1.s, p0/z, [x1, x3, lsl #2]  ; values[x3..]
  fadd z0.s, z0.s, z1.s
  st1w z0.s, p0, [x0, x3, lsl #2]
  incw x3                       ; advance by VL
  b 1b
```

`incw` advances by runtime VL words; `whilelt` predicates the tail.
Vector-length-agnostic. ✓ Works for VL = 128/256/512+ bits. Graviton 4
SVE2-128 will iterate the loop 8 times for BLOCK_WIDTH=32.

### Bit-exact accumulation order

`score_block32_sve_impl` (sve.rs:118-140) outer loop is `group_index`,
inner scalar-gathers into `[f32; 32] values`, then `ecaz_...accumulate_f32`
adds `values` into `out_scores` element-wise.

Per-lane sum order: `out[lane] = 0` initially, then for each group g
`out[lane] += values_g[lane]`. Identical to scalar `(0..G).map().sum()`
left-fold from 0.0. Bit-exact parity holds per lane. ✓

The scalar gather + SVE-add pattern doesn't yet exploit SVE for the
gather itself — this is acceptable per Phase 1 N1 (SVE2 TBL repack is a
follow-up if Graviton 4 measurements show gather stalls dominating). No
parity correctness concerns.

### Runtime vector-lane helper

`runtime_vector_lanes()` (sve.rs:106-115) gates on `sve` (not `sve2`)
and calls `ecaz_grouped_pq_sve_cntw` which executes `cntw x0`.
`cntw` is base-SVE, so the `sve` gate is correct (SVE2 implies SVE).
✓ Ready for Graviton 4 evidence packet to report measured lanes verbatim.

### N3 — Bit-exact across VL widths

The per-lane sum order is unaffected by VL because each
`ecaz_grouped_pq_sve_accumulate_f32` call adds `values_g` to `out` lane-
wise in one logical operation regardless of how many SVE chunks the
inner loop takes. Bit-exact parity is therefore VL-independent. ✓ No
need for a "sve-256 vs sve-128 parity" gate.
