## Finding (non-blocking)

### F1 — HNSW traversal does not form candidate batches; disposition must be explicit in closeout

The HNSW scan loop still scores grouped-PQ candidates one at a time:
`score_grouped_search_code_result` (src/am/ec_hnsw/scan.rs:2902) calls
`QuantCodec::score_ip_candidate` per search code, and nothing in the
HNSW traversal calls `score_ip_batch` outside unit tests.

Phase 1 Q3 was approved as: register where the scan loop exposes a
natural candidate batch; **otherwise document scalar-only HNSW** with
the missing-boundary reason. The codec-level registration shipped here
is fine and useful (it makes HNSW kernel-capable the moment a batch
boundary exists), but the readiness matrices currently say "registers
existing HNSW grouped-PQ scan codec batch path", which a measurement
reader could mistake for traversal-level batching.

Required for the Phase 7 closeout (no new code needed):

1. State explicitly that HNSW grouped-PQ traversal remains
   per-candidate scalar scoring; `surface=hnsw, quant=grouped_pq`
   kernel counter rows will NOT appear in production scans.
2. Name the missing batch boundary (greedy search expands neighbors
   through the exact/score-result path one tuple at a time).
3. If HNSW traversal batching is wanted later, it is follow-up-task
   scope, mirroring how DiskANN traversal batching got its own packet
   (009).

Compare DiskANN: packet 007's Evidence Limits flagged the same gap for
DiskANN and packet 009 closed it. HNSW needs either the same treatment
or the explicit scalar-only documentation. Documentation is acceptable
per the Phase 1 approval.
