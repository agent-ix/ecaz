## Findings (closeout scope)

### F1 — Batch path bypasses suffix-max min-bound pruning; name the trade explicitly

The legacy per-posting path scores through
`score_ip_from_parts_with_min_bound`, which uses the prepared query's
`suffix_max` table to early-terminate candidates that cannot beat the
running top-k (scan.rs:1555-1569, quantizer.rs:336-364). The new batch
path scores every posting in the scratch with no cutoff, then inserts.

This is why the latency table is mixed instead of a clean win: the
baseline is *pruned* scalar, not naive scalar, so the AVX2 kernel's
throughput gain is partially spent re-scoring candidates the old path
skipped. Correctness is unaffected (pruning only skips candidates that
cannot enter the top-k, and recall parity confirms it), but the
closeout must state this trade explicitly rather than letting readers
attribute the flat latency to kernel overhead. Two follow-ons:

1. EXPLAIN counter semantics shift: `posting_pruned_by_bound` will read
   0 with batch-on. Worth one line in the closeout so dashboard
   consumers aren't surprised.
2. If a future packet wants the win at small nprobe too, a hybrid
   (cutoff-aware block skip, or pruning before batch formation using
   the suffix-max bound on the block max) is follow-up scope — not
   Task 94.

### F2 — Kernel path is opt-in behind a default-off experimental GUC

`ec_ivf.scratch_soa_batch_decode` is documented as "Task 51 diagnostic
mode; disabled by default." After this packet, that GUC is the only
switch standing between production IVF PqFastScan scans and the
grouped-PQ kernel. The closeout must either (a) flip the default with
supporting evidence, or (b) explicitly document that Task 94's IVF
kernel path ships opt-in and name the GUC. Leaving a completed task's
headline feature behind an undocumented diagnostic flag would be a
deployment surprise.
