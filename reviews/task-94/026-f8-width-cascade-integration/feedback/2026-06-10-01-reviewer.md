## F8 kernel review (`src/quant/grouped_pq_block/avx2.rs`)

Correct. Specifics I checked:

- The two-permute-plus-blend selection (`_mm256_permutevar8x32_ps` on the
  low and high 8-entry LUT halves, `_mm256_cmpgt_epi32(index, 7)` mask,
  `_mm256_blendv_ps`) implements a 16-entry f32 LUT lookup exactly;
  nibble-decoded centroid indexes are always 0..=15, and the signed compare
  is safe in that range.
- The `lut_offset + 8` half-load stays in bounds for the last group because
  `validate_lut_shape` pins `lut.len() == group_count * GROUPED_PQ_CENTROIDS`
  (= 16) on every entry path before dispatch.
- Bit-exactness against the scalar reference is asserted across shapes
  (`grouped_pq_block32_matches_scalar_reference_bits_across_shapes`,
  AVX2-specific sibling), and the test fixture's `& 0x0F` code generator
  exercises the high LUT half, so the blend path is genuinely covered.
- `score_grouped_pq_partial` pads with `codes[0]` (a validated live code),
  scores into a stack block, and copies back only live lanes — no
  out-of-bounds reads, no partial writes to caller state on any path.
- The updated 39-candidate AM counter tests (DiskANN quantizer ×2, HNSW
  scan) correctly branch on host class: 39 kernel / 0 scalar on SIMD hosts,
  32 / 7 on scalar-only hosts, matching the driver's
  `scalar_block_counts_as_kernel` semantics.

One scalar-host caveat on the padded partial path is recorded as finding 3
in the Task 101 packet 001 feedback (dead-lane work and elapsed-time
attribution on scalar-only hosts).

## Measurement evidence

### 1. (must-fix) Unexplained ~8–19× latency shift vs packet 025 invalidates the latency table

I compared `results.jsonl` cell-by-cell against packet 025 (identical suite
config — I diffed the two JSONs; only artifact paths differ; same fixtures,
prefixes, host class, socket):

| Cell | 025 p50 | 026 p50 |
| --- | ---: | ---: |
| IVF 10k batch-off nprobe=32 | 2.87 ms | 41.6 ms |
| IVF 100k batch-off nprobe=64 | 34.8 ms | 568.0 ms |
| DiskANN 100k grouped-PQ list=128 | 34.3 ms | 364.7 ms |

Every cell — including **batch-off** cells the code change does not touch,
and the DiskANN forced runs — shifted by roughly an order of magnitude.
This is environmental or build-related, not the code under review. Until
the cause is identified, no latency claim from this run is usable in either
direction: not for AC5 ("no regression beyond noise"), and not the packet's
batch-on-slower-than-batch-off observation either (in packet 025's healthy
environment, batch-on ≈ batch-off within noise; here it reads 15–22%
slower — that delta may be an artifact of whatever degraded the run).

Likely suspects to check before rerunning: a debug-profile extension or
stale/debug tooling in the measurement loop, host load/thermal state, or a
PG config difference. Note the extension itself demonstrably ran the new
code (counter rows below), and `ecaz dev install` builds `--release` and
asserts the installed `.so` hash — but this packet's manifest records **no
install step at all**, so build provenance for the measured extension is
unverifiable from the packet. Please add the install/build evidence line to
measurement manifests going forward.

Action: diagnose, rerun the latency cells in a healthy environment, and
state the cause in the next manifest. Recall and counter steps do not need
a rerun.
