# Task 74 Intel profiler baseline — acceptance

## Decision

**Accept the Intel-local packet as satisfying Task 74's profiler gate.**
The reviewer-side push for "M5 samply" was based on a stale assumption about
the characterization host; the operator confirmed Intel desktop is the current
local bench host, and `perf record` + `cargo-flamegraph` is the right tool on
Linux. An M5 rerun is not required.

**Accept the no-Phase-2-slice closeout direction.** Identifiable
SPIRE-specific orchestration above the scoring kernel is ~4.9% of samples,
well below the task's 10% stop-condition floor. Editing
`scan/{routing,candidates,leaf_rows,snapshot,callbacks}.rs` against that
profile would be optimizing tail noise.

Task 74 may move from `pending profiler evidence and reviewer approval` to
`complete` once these notes are recorded.

## What's solid

- Real profile artifacts: `intel-spire-nprobe96.perf.data` + flamegraph SVG +

  host-dependent — reproduces consistently.

## Caveats to record (non-blocking)

### C1 — Self-time interpretation depends on unsymbolized frame attribution

The SPIRE perf report has several 1-4% entries as bare hex addresses
(`0x048d4837…`, `0x0605040302…`, `0x0000000000000000` with non-zero children).
Combined, these unsymbolized frames are several percent of samples. The
"~4.9% orchestration" estimate counts only the named SPIRE symbols; if some
of the unsymbolized frames live inside SPIRE callbacks rather than the PG
executor or scoring inlines, real orchestration could be modestly higher.
Still likely below 10%, but the closeout shouldn't treat 4.9% as a precise
floor.

### C2 — Rerank-width asymmetry between SPIRE and IVF surfaces

SPIRE runs at `rerank_width=25`, IVF at `rerank_width=500`. That's the same
asymmetry as Task 73's matched-recall comparison, so it's not new — but it
shows up in the profile as IVF's `randomize_mem` taking 30.96% self-time
(likely allocator activity around the larger rerank buffer). The 3.65x p50
ratio embeds that asymmetry; it isn't a pure leaf-scan-orchestration
comparison. Worth one line in the closeout so the next reader doesn't
re-discover it.

### C3 — Callback-boundary split is partial

The reviewer ask for a clean split between `pg_am_callback!`-bounded code
and `scan/routing.rs` recursive draft consumption is only partially
answered. The SPIRE Rust symbols are present and visible; the executor and
callback shim frames are not symbolized cleanly enough to allocate the
last ~20% of self-time precisely. The packet says so explicitly — accepted
as a Linux-perf-on-PG limitation rather than a packet shortfall.
