# Review follow-up: packet 002 — relabel (cheap) vs rerun; the clean IVF A/B already exists

Follow-up to the seq-1 blocking finding (IVF `kernel_off` steps did not force
`ec_ivf.scratch_soa_batch_decode=off` after the Phase 1 default flip). This
note resolves the relabel-vs-rerun choice with verified evidence.

## Key fact verified: Task 99's 100k IVF A/B is clean

The canonical IVF kernel differential already exists and is valid at 100k.
Against head `7b7870af5`, `reviews/task-99/008-g4-lane/artifacts/profile-run/
suite-config.json` carries both `ivf_scratch_soa_batch_decode: true` and
`false` cells. Task 99 ran **before** the Phase 1 default flip landed in Task
105 (`db1c4b373` flipped `src/am/ec_ivf/options.rs` to default-true), so at
Task 99 time `false`/absent genuinely ran the default-off path. That makes
Task 99's 100k IVF on/off pair a real A/B — not a same-config noise pair.

The defect is therefore Task-105-specific: only after the default flipped did
`false` become equivalent to absent-and-on, which is why the Task 105 IVF
"off" cells at 10k/50k/1M all inherited batch-decode on.

## Resolution

**Preferred — relabel (doc/config-only, no rerun):**

1. Amend `artifacts/gen_t105_sweep.py` and the generated configs so the IVF
   `kernel_off` cells are no longer presented as the diagnostic A/B column —
   either drop the IVF off arm from the Task 105 sweep, or force
   `ec_ivf.scratch_soa_batch_decode=off` explicitly *and* note it was not
   measured this run.
2. Amend `request.md` (and confirm packet 006's already-present caveat) so the
   IVF kernel differential is explicitly delegated to **Task 99's clean 100k
   A/B**, and the Task 105 IVF off cells at 10k/50k/1M are marked
   "same-config, not A/B."

This is the recommended path: the differential the off arm was meant to
provide already exists clean at 100k, so re-measuring is not required for
correctness — only the labels are wrong.

**Alternative — rerun (only if a multi-scale IVF differential is required):**

If a fresh IVF on/off A/B is genuinely wanted at 10k/50k/1M (not just 100k),
that data does not exist and must be measured: snapshot-restore the corpus
base and rerun the IVF arm with the GUC forced off via `ecaz bench suite`
(per NFR/workflow — no bash sweeper). Packet 006 already notes this is "one
snapshot-restore away." Recommend against unless the multi-scale IVF curve is
a stated deliverable.

Note: the suite runner treats `false` the same as absent (only appends
`--ivf-scratch-soa-batch-decode` / emits `SET ... = on` when true). If the
relabel path keeps an explicit off arm, that runner gap must be closed first
(extend `crates/ecaz-cli/src/commands/bench/suite.rs` to emit an explicit
`SET ec_ivf.scratch_soa_batch_decode = off` for the false case) and landed as
its own commit before regenerating — otherwise a relabeled "off" still runs on.
