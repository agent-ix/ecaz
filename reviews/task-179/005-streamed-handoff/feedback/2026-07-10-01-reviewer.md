# Review feedback — Task 179 Packet 005 streamed handoff

Reviewed `c36aada77` and the Packet 005 request/artifacts at packet HEAD
`6a270d13d`. I inspected the source-capture/spool/workspace path, owner router,
wire/hash formats, generation catalog updates, participant stage/seal code,
SECURITY DEFINER wrappers, FR-078, Task 179, and the focused tests. The checked-in
logs support the stated commands/results. I did not rerun the already packeted
5+ minute PG18 installation/test lane.

## Findings

### P1-1 — Participant binary receive executes caller-controlled domain checks as the extension owner

`ec_distann_stage_epoch_batch` and `ec_distann_seal_epoch_handoff` are SECURITY
DEFINER (`src/lib.rs:516-527`). The row schema accepts any locally resolvable
type/binary-I/O identity (`src/am/ec_distann/row_schema.rs:52-168,171-247`), and
stage resolves the type's receive function then invokes `ReceiveFunctionCall`
without changing security context (`src/am/ec_distann/handoff.rs:265-358`).

That is unsafe for domains even when base-type binary I/O is trusted. PostgreSQL's
domain receive path evaluates the domain's CHECK expressions. A control/row-schema
owner can define a domain whose CHECK calls an invoker-rights PL/pgSQL function;
when stage receives the value, that function runs with the SECURITY DEFINER's
effective extension-owner privileges. This crosses the exact privilege boundary
that the endpoint ACL/search-path hardening is intended to create. Seal repeats
binary send under the same definer context (`handoff.rs:534-612`), so arbitrary
user-owned type support also needs a deliberate execution policy there.

Fix before accepting this checkpoint. Either execute all type I/O/domain
validation under the authenticated control owner (with a carefully scoped
`SetUserIdAndSecContext` guard that restores on every exit), or reject types whose
receive/send/domain execution chain is not extension-owned/trusted. Add a live
role-switch regression using a user-owned domain CHECK that attempts an operation
available to the extension owner but not the control owner; stage must not confer
the privilege. Merely comparing qualified function names in the schema fingerprint
does not address execution privilege.

### P1-2 — The router's peak memory exceeds the normative `8 MiB × roster_count` handoff bound

Each owner buffer retains decoded `DistannHandoffEntry` values, including all row
payload vectors (`src/am/ec_distann/handoff_router.rs:37-43,138-143`). On flush it
then:

1. clones the complete entry vector into a `DistannHandoffBatch`
   (`handoff_router.rs:148-159`);
2. encodes every entry into a second `Vec<Vec<u8>>`
   (`handoff_wire.rs:319-330`);
3. allocates the canonical batch and copies every encoded entry into it
   (`handoff_wire.rs:331-354`); and
4. retains the original decoded owner buffer until the remote acknowledgement has
   been validated (`handoff_router.rs:162-205`).

`push` also fully encodes the incoming entry solely to measure it before retaining
the decoded copy (`handoff_router.rs:105-143`). Thus, near the 8 MiB boundary, one
flushing owner can transiently hold several full-batch copies in addition to the
other owners' nearly-full buffers. The current router test asserts only final wire
length (`handoff_router.rs:264-319`); it does not measure retained or peak bytes.
This does not prove, and structurally cannot satisfy, FR-078-CON-5 / Task 179's
hard handoff peak bound.

Buffer canonical encoded entries (or a single canonical batch builder) rather than
decoded payload trees, finalize into at most one encoded batch, and retain that
exact encoded batch while it is unacknowledged. Hash/count state should advance
only after its exact acknowledgement as today. Add instrumented tests at
8 MiB-minus/exact/plus boundaries with multiple simultaneously non-empty owners
that account for capacity, not just logical length.

### P1-3 — Source capture bypasses the specified index-build callback and makes its mismatch check tautological

FR-078 lines 209-220 and Task 179 lines 223-227 require the physical lane to use
the index-build callback's `tuple_is_alive` classification, exclude callback-dead
rows, and exact-refetch each callback-live TID before accepting the callback
vector/identity. The implementation instead starts a separate `heap_beginscan`
and reads the key/identity from that scan slot (`src/am/ec_distann/ambuild.rs:
600-664`), then refetches the same scan TID under the same snapshot and compares
those two reads (`ambuild.rs:812-910`). It never invokes `table_index_build_scan`,
never observes `tuple_is_alive`, and never processes actual callback datums.

For an ordinary heap and an undisturbed snapshot this independent scan normally
produces the desired live-row set, but it is not the specified correctness path:
the exact-refetch comparison is between two reads selected by the same custom scan,
so the test cannot prove rejection of a callback/slot disagreement, and the
recently-dead callback rule is unimplemented rather than tested. The focused PG18
case only deletes before the snapshot and asserts that the row is absent
(`src/tests/ec_distann_basic.rs:2295-2395`).

Wire physical capture through `table_index_build_scan` (or revise the normative
spec first if an independent heap scan is intentionally the new design), preserve
the one registered snapshot, reject `tuple_is_alive = false` before datum access,
and add deterministic fault injection for absent exact TID, vector disagreement,
and identity disagreement. Add a genuine recently-dead callback case, not only a
row deleted before snapshot acquisition.

### P2-1 — Packet tests do not cover the required zero-mutation stage/seal matrix

The stage integration test proves exact replay, conflicting acknowledged replay,
and a sequence gap; the seal test proves one wrong expectation and successful/
empty replay (`src/tests/ec_distann_basic.rs:1984-2292`). It does not exercise the
implemented wrong-owner, duplicate-existing, malformed inner entry, schema/codec
mismatch, non-canonical binary receive, unsupported schema, oversize, corrupted
persisted hash state, missing physical row/directory, or participant-restart paths.
It also asserts row counts after two early failures but does not snapshot and
compare graph/row/directory physical bytes and catalog progress for the full
FR-078-AC-7 matrix.

These are security- and storage-sensitive validators, not optional breadth. Add
focused per-category tests proving no catalog/count/digest/physical-byte change,
plus at least one failure after complete decode/preparation but before insertion.
Participant restart/resend may remain in TC-042 if Packet 006 owns the real
transport, but Packet 005 should expose and unit-test the restart state needed by
that fixture.

## Verified good

- The owner-stream hash state is pinned, independently decoded, endian-checked,
  and represented in the compatibility matrix; the format evidence supports the
  Packet 005 claim.
- Stage verifies the outer digest before descriptor-driven inner decode, locks in
  control-relation then generation-row order, validates all decoded entries before
  physical writes, and journals/progresses in the same PostgreSQL transaction.
- Exact acknowledged replay is intentionally digest-plus-length identity, matching
  FR-078's collision-resistance contract; it does not duplicate physical rows.
- Seal independently walks physical graph rows in unsigned vec-id order,
  reconstructs locator-free entries, checks row locators/owners/identities, derives
  the three receipt digests, and performs Building→Ready as its final mutation.
- The source payload itself is transaction/resource-owner scoped in a PostgreSQL
  `BufFile`; random-access locator validation and complete row payload capture cover
  NULL, generated, toasted, dropped, and deleted-before-snapshot data.
- Packet artifacts are compact, packet-local, and consistent with the request;
  no benchmark-closeout claim is made.

## Disposition

**Changes required.** P1-1 is a privilege-escalation boundary, P1-2 violates an
explicit hard memory invariant, and P1-3 does not implement the normative MVCC
callback contract. Packet 005 should not be treated as approved until all three
are corrected and the focused negative matrix is expanded. Publication/recovery,
physical generation reads, true multi-instance topology, and 10k/50k/100k gates
remain correctly outside this packet and open.
