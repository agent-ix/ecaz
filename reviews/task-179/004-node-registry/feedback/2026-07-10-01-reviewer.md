## P2

- **P2-1 — Published/retained build bindings are only procedurally
  protected: no FK stops deleting `ec_distann_build_registration` out
  from under an active epoch.** `ec_distann_build_participant_binding`
  FKs to `build_registration` with ON DELETE CASCADE, and
  `ec_distann_active_epoch` FKs to `ec_distann_publish_decision` — but
  `publish_decision` has **no FK to `build_registration`**. Deleting a
  registration row cascades away the private bindings while the decision
  and active pointer still reference that `build_id`; the packet's own
  basic test does exactly this (`DELETE FROM {build_catalog}` at the end
  of `test_distann_node_registration_provenance_and_guards`) and
  succeeds. FR-078 ("bindings remain until their last epoch is
  reclaimed") and NFR-014 §13 (routing SHALL resolve the private
  binding) are currently enforced by nothing structural — unregister is
  carefully guarded, registration deletion is not. Fix: add
  `FOREIGN KEY (index_oid, logical_index_uuid, build_id)` from
  `ec_distann_publish_decision` to `ec_distann_build_registration`
  (RESTRICT), so a Pending/Applied decision pins its registration and
  bindings until reclaim removes the decision first. Land before
  checkpoint 006 (publication).

## P3

- **P3-1** — The compatibility digest omits vector dimensionality when
  the indexed column is untyped `ecvector` (typmod −1): the control
  constructor never sets `metadata.dimensions`, and dims are otherwise
  bound only via the source column typmod inside the row-schema
  fingerprint. Two controls of different intended dimensionality then
  digest identically and register as compatible; failure defers to
  build-spec/handoff. Impl matches the FR-078 digest spec exactly, so
  this is a spec+impl v2 item: reject `distributed_control=true` on an
  untyped vector column at ambuild, or add dims/typmod to compatibility
  v2.
- **P3-2** — Server-canonical locator uses `format('%I.%I')`, which
  quotes reserved keywords (a schema named `user`, `select`, …); the
  quoted form then fails `validate_canonical_index_locator`
  (`node_registry.rs:57-73`), making a grammar-conformant relation name
  unregistrable. Fail-closed, so cosmetic — note in FR-078 or accept
  `quote_ident(x) = x OR x matches grammar`.
- **P3-3** — `validate_roster` (`generation_descriptor.rs:88-95`) echoes
  the rejected endpoint value in its "malformed, duplicate, or
  secret-bearing endpoint identity {:?}" error. Unreachable with secrets
  in the register path today (grammar validation runs first), but the
  same function validates decoded descriptor rosters; if a
  secret-bearing string ever reaches it via a future path, that branch
  prints the secret. Don't echo the value.
- **P3-4** — No negative test where the participant's source-table
  *shape* drifts (extra/differently-typed payload column) and
  registration is rejected via the row-schema-fingerprint component of
  the digest — the positive loopback test passes precisely because the
  remote table byte-matches the fixture. Add one shape-drift rejection
  to close the fingerprint leg.
- **P3-5** — Coordinator self-registration is not rejected: nothing
  forbids `participant_logical_index_uuid` equaling the coordinator's
  own UUID (the digest deliberately excludes the UUID), so the
  coordinator's control index can be registered as its own `is_local`
  participant. FR-078-AC-12 supports coordinator-in-roster, presumably
  via a distinct shard control, not the control index itself. Reject the
  self-UUID or state in FR-078 that it is legal.
- **P3-6** — `increment_registry_revision`'s concurrent-change branch
  (`node_registry.rs:167-169`) is dead under the SRE+row-lock discipline
  and raises XX000 if ever live; comment it as unreachable defense or
  map to 40001.

## Verified GOOD (decision-grade)

- **Lock retention:** `retain_lock_until_transaction_end()` sets
  close-lockmode to `NoLock`, so the `ShareRowExclusiveLock` from
  `index_open` genuinely survives to transaction end; all three ops use
  relation-lock → registry-row `FOR UPDATE` in consistent order.
- **Deadlock fix proven:** under the old early-unlock behavior the
  two-backend fixture is a textbook ABBA (waiter holds granted SRE
  blocking winner's re-request; `deadlock_timeout=100ms` would fail the
  test); with retention the waiter blocks on the relation lock (gated
  via `pg_blocking_pids`) and observes the committed roster. Real
  independent loopback backends, not mocks.
- **40001 and revision accounting:** stale RR transaction's
  `SELECT ... FOR UPDATE` on the twice-updated registry row raises
  native serialization failure; exact SQLSTATE asserted; committed
  replacement survives. Revision is conditional-incremented under the
  self-conflicting SRE — cannot regress or skip; the basic test's final
  revision of 6 matches exactly six committed mutations.
- **Security surface:** all eight definer endpoints have
  `search_path TO pg_catalog, @extschema@, pg_temp` (explicit, last) +

  attacker fixture creates a real NOLOGIN role, asserts endpoint and
  catalog denial, plants an attacker-schema spoof of

- **Grammars:** endpoint/secret-ref/locator character classes are

  (injective); `=`, space, and `:` are outside all alphabets, excluding

- **Compatibility digest:** domain-separated, versioned, golden-pinned;
  binds reloptions, extension-namespace-pinned opclass identity,
  key/identity attnums, identity base type + NOT NULL, index
  valid/ready/live preconditions, and an OID-free row-schema fingerprint
  (typmod, collation, dropped slots, generated kind, send/receive
  identity).
- **Roster vs bindings:** desired-roster edits cannot touch bindings
  (bindings key on `build_id`, cascade only from `build_registration`);
  unregister's single CTE atomically distinguishes
  absent / in-progress-captured / concurrently-changed, with

  fingerprint→build resolution; catalog cleanup respects FK-safe delete
