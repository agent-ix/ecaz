# Packet 034 — cancelled-generation recovery (outside review)

**Status: APPROVED — closes packet-033 P1-2; one P2.** This is a real,
well-built audited reclaim path for the Ready / Published-but-never-active
participant generation left durable by a Cancelled decision, and it
reconciles the FR-082-AC-17 over-claim I flagged (the reclaim remedy is
now split out to a new AC-18 that matches the implementation).

Verified:
- **Audit/tombstone preserved** — the reclaim tombstone
  (bootstrap.sql:893-917) is inserted before drop_generation_relations +
  the generation DELETE, in one transaction.
- **Covering-successor='Applied' safely bypassed** — reclaim does NOT go
  through ec_distann_retire_decision; it is an independent audited path.
  No route to a live generation: both participant
  (participant_lifecycle.rs:1039-1058) and coordinator
  (build_coordinator.rs:2593-2612) check ec_distann_active_epoch and
  reject the active generation (EC_PUBLISH_CANCEL); eligibility is
  restricted to Ready/Published; Published targets must match the audit
  fingerprint+manifest against the persisted catalog.
- **Only genuinely-Cancelled** — the coordinator entry
  (recover_cancelled_publish) reads decision_state FOR UPDATE and errors
  unless 'Cancelled', then re-verifies audit digest + coordinator
  identity + build_id; recover_epoch_publish on a cancelled decision
  fails EC_PUBLISH_CANCEL (tested).
- **Idempotent replay** — cancellation_reclaimed_at short-circuit +
  tombstone-equality replay (Ok on exact match, error on conflict);
  driven twice in the test.
- **New-hole checks pass** — future rebuild cannot reference the reclaimed
  generation (only non-active eligible; rebuild advances epoch/build_id);
  the FK chain permits the DELETE (batch CASCADE, tombstone has no back-FK);
  consistent with the burned-ordinal behavior (packet-033 N-1; test build
  advances 11→12).

- **P2-1 — recover_cancelled_publish lacks the decision-xmin commit-
  boundary guard.** Unlike its siblings recover_epoch_publish
  (build_coordinator.rs:2982) and recover_epoch_retire, it has no
  TransactionIdIsCurrentTransactionId check, so recovery of a Cancelled
  decision written in the same uncommitted transaction would proceed.
  Narrow (recovery is a separate operator call; cancel commits first) but
  it is exactly the guard the other recovery paths carry and that
  packet-028 P2-1 established as the pattern. Add it.
