# Packet 036 — bounded remote transport (outside review)

**Status: CHANGES REQUIRED — the fix introduces a new P1.** The packet
genuinely bounds the transport (connect_timeout, remote statement_timeout
refreshed per pooled session, per-call client deadline, CHECK_FOR_INTERRUPTS
around awaits, SQLSTATE-preserving/redacting error classification, all
PG18-tested), addressing most of packet-025 P2 — but the interrupt check
it adds creates a backend-poisoning bug.

- **P1-1 (new) — interrupt longjmp leaks the transport-state RefCell
  borrow, FATAL-ing the backend's next distributed query.**
  maybe_check_for_interrupts() → check_for_interrupts!() ereport(ERROR)
  longjmps to the executor's PG_TRY on a pending cancel. That check now
  fires inside runtime.block_on(...), which runs inside
  DISTANN_TRANSPORT_STATE.borrow_mut() (with_transport_state,
  remote_transport.rs:736-744). The longjmp skips Rust destructors, so the
  RefMut is never dropped and the thread-local RefCell stays permanently
  borrowed; there is no xact-abort/resowner reset hook. The next transport
  call in the same backend hits "already borrowed: BorrowMutError" → panic
  → FATAL. So the interrupt-safety this packet adds converts a
  hung-but-alive backend into one that cancels once and then FATALs on its
  next distributed query — and it is untested (the PG18 test exercises only
  the server-side statement_timeout clean-unwind path, not the client
  interrupt longjmp). Fix: drive the interrupt check OUTSIDE the
  borrow_mut/block_on scope (a bounded poll loop returning a normal Err so
  Rust unwinds cleanly, or wrap block_on so the state guard is dropped on
  longjmp), and add a cancel-mid-connect/mid-await test.
- **P2-1 (carried, packet-029 P2-2) — physical owner fan-out still
  serial.** PhysicalMultiOwnerExpander::expand_nodes and the materialize
  path iterate owners with a for-loop, each block_on-ing one RPC; latency
  is Σ per-owner RTT, not max, regressing FR-081. Correctly out of this
  packet's claimed scope, but it means multi-owner distributed latency
  numbers still measure the serial regression, not the target design — so
  a distributed multi-owner latency benchmark is NOT yet design-
  representative even with the 035 cache. Parallelizing likely needs a
  multi-thread runtime or per-owner spawn + join_all (and interacts with
  the P1 borrow-held state).
- **P3 — interrupt observation is only at await boundaries on a parked
  current-thread runtime**, so cancel latency ≈ the client deadline
  (statement_timeout+5s), not prompt. The SRE lock is held up to that
  bound, not indefinitely (an improvement), but not released promptly on
  Ctrl-C.

Verified good: connect timeout + remote statement_timeout + client
deadline all present and PG18-proven (10 ms budget cancels a 1 s remote
sleep within 2 s); TimedOut → distinct non-torn Internal error, retryable
SQLSTATEs preserved; conninfo redaction retained; connect-failure aborts
the driver task. The one exception to clean cleanup is the P1 longjmp
path.
