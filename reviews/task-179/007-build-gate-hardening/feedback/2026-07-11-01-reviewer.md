## New findings

- **P2-A — the utility hook locks named relations with no permission
  check, and over-locks.** `RangeVarGetRelidExtended(..., lockmode,
  RVR_MISSING_OK, None, null)` (`build_gate.rs:351-364` + callers
  `:418-557`) acquires the escalated lock with a NULL callback, where
  stock PostgreSQL passes `RangeVarCallbackForDropRelation`/`ForTruncate`
  etc. precisely so ownership is checked *before* locking. Any
  unprivileged user can transiently `AccessExclusiveLock` any nameable
  table (including catalogs) via failing DROP/ALTER/TRUNCATE/CLUSTER
  statements — a queue-poisoning DoS stock PG deliberately prevents.
  Separately the hook takes AEL for every `ALTER TABLE` (stock lock level
  is often ShareUpdateExclusive) and for `REINDEX ... CONCURRENTLY`
  (stock SUE), holding to transaction end — partially defeating
  CONCURRENTLY database-wide. Fix: resolve at `NoLock` (the mask's
  OID+UUID+IndexGetRelation revalidation already bounds stale-OID
  damage), or supply per-statement permission callbacks plus the true
  `AlterTableGetLockLevel` lockmode.
- **P2-B — ATTACH PARTITION bypasses the durable gate.** Begin-build
  rejects inherited sources, but post-registration
  `ALTER TABLE parent ATTACH PARTITION gated_source ...` names only the
  parent, so the AlterTable arm checks the wrong OID; routed leaf
  partitions also do not appear in `resultRelations`, so
  `INSERT INTO parent` then writes through in the dead-coordinator
  durable window — exactly the window the gate exists for. Gate
  `AT_AttachPartition` subcommands against the attached relation.
