## P1-1 (spec + frozen schema) — Pending-decision successor loss wedges the logical index forever

The abandon override exists only for **predecessor** bindings of an
**Activated** decision (FR-082:361-362). If a **successor-roster** participant
is permanently destroyed after the durable publish decision commits but before
it acknowledges publication, the decision is stuck `Pending` forever:

- `EC_PUBLISH_PENDING` retains the commit-only decision for retry (FR-082:697);
- the coordinator keeps the old active pointer until all participants
  acknowledge (FR-082:582-585);
- recovery SHALL NOT reinterpret the generation as aborted (FR-082:580-581)
  and abort must refuse a generation named by a durable publish decision;
- begin-build is rejected while any publish decision is `Pending` or
  `Activated` (FR-078:265-268) — already implemented in
  `ensure_build_slot_available` (build_coordinator.rs:520-536).

Outcome identical to the resolved P1: no future epoch can ever be built; only
remedy is DROP + full rebuild. This matters **now** because 54d09c177 freezes
`decision_state IN ('Pending','Activated','Applied')` (bootstrap.sql:565-567),
the `one_recovery_active` partial index over `('Pending','Activated')`
(bootstrap.sql:624-626), and the retire-decision FK pinned to the
`decision_state`-bearing unique — exactly the "expensive to re-freeze" surface
the prior review used to justify fixing the first wedge pre-code.

Fix shape: an audited operator **decision-cancellation** valid only in
`Pending` (pointer never swapped, so predecessor-active state is untouched);
cancelled decisions keep blocking their fingerprint via the
committed-decision registration check (FR-082:373-378), and successor
participants' Published-but-never-active generations become auditable
force-retirable orphans. Add the `Cancelled` (or equivalent terminal) state to
the schema **before more lifecycle code stacks on the current enum** — or make
the spec explicitly argue that pre-activation successor loss is
DROP-and-rebuild territory. The argument must be made in the spec, not by
omission.

## P2-1 (sql/bootstrap.sql:1244-1269) — SECURITY DEFINER event trigger pins search_path without `pg_temp`

`ec_distann_catalog_drop_index_cleanup_event()` is
`SECURITY DEFINER SET search_path = pg_catalog, @extschema@`
(bootstrap.sql:1247-1248). Without `pg_temp` listed, the session's temp schema
is implicitly searched **first** for relations. The body reads
`SELECT 1 FROM ec_distann_registry_state WHERE index_oid = ...`
(bootstrap.sql:1261-1264): an unprivileged user who creates
`CREATE TEMP TABLE ec_distann_registry_state(index_oid oid)` and drops any
index they own makes the definer-privileged cleanup run for an object with no
genuine registry row. Concrete damage today is bounded, but it is the classic
SECURITY DEFINER pg_temp hazard and inconsistent with every Rust bridge in the
same commit (all use `pg_catalog, @extschema@, pg_temp`, src/lib.rs:556-579).
One-line fix; apply to the SPIRE twin at bootstrap.sql:1221 for uniformity.

## P2-2 (sequencing) — begin-build is SQL-reachable but the durable gate enforcement it depends on does not exist at 54d09c177

FR-078:233-240 (added by this very amendment): durable DML/utility-hook
enforcement SHALL cover the interval between top-level abort and
reacquisition; the task file adds begin-build must not be promoted
independently of that enforcement. At 54d09c177 the only thing blocking source
DML is the session ShareLock; after a top-level abort nothing consults the
durable gate rows. The request declares "DML/utility gate hooks" as a later
checkpoint — honest, but per the contract's own SHALL this must be recorded as
a **blocking precondition** for the next checkpoint (any build that captures a
snapshot), not a generic "remaining." (The follow-up commit 28b99f151 attempts
this; it has its own CHANGES REQUIRED — see `2026-07-11-05-reviewer.md`.)
