# Task 179 packet 006 — outside review of the publication/retention contract

**Status: CHANGES REQUIRED — one P1 and two P2 spec amendments before
packet-006 lifecycle code lands.** The amendment (`d27cc4ce5`) genuinely
closes the gaps it claims and — verified clause by clause — does **not**
violate any previously frozen FR-082 invariant: the retirement fence
remains exactly one lock keyed by `(database_oid, logical_index_uuid)`
(fence IDs are allocated per that pair, not per fingerprint, so the
packet-001 NEW-P2-A race is not reintroduced); zero per-query participant
RPC/WAL work is preserved; the fence is held through decision commit and
released before reclaim RPCs; `EC_RETENTION_ACTIVE` creates no decision;
participants never reclaim autonomously. T4a's swap + `Activated` record
+ gate clear are one atomic transaction with a CAS against the recorded
predecessor; session-lock cleanup direction is correct (abort releases
newly acquired, subcommit promotes, releases scheduled post-commit);
descriptor v2 is a coherent rebuild-only migration with TC-050 golden and
matrix obligations. But the new clauses interact to create one
availability flaw the internal approval did not probe.

## P1

- **P1-1 — A permanently lost predecessor owner wedges the logical index
  forever; no override path exists.** FR-078:252-256 rejects begin-build
  while any publish decision is `Pending` or `Activated`; FR-082:317-326
  reaches `Applied` only when *every* predecessor private binding reports
  the exact Retired activation digest; an unavailable predecessor yields
  `EC_PREDECESSOR_RETIRE_PENDING` with retry (FR-082:470-473, 578). The
  removed-owner retirement feature (FR-082:284-287, 307-311) exists
  precisely for node decommissioning — and decommissioned nodes get
  destroyed. If a predecessor-roster owner is permanently gone before T4b
  completes: the decision is stuck `Activated` forever, begin-build is
  rejected forever, and no future epoch can ever be built.
  `ec_distann_force_retire_epoch` does not help — it targets a non-active
  Retired fingerprint, still needs reclaim RPCs to the dead node, and
  nothing advances the successor decision to `Applied`. The only remedy
  is DROP + full rebuild: a total-loss outcome for a designed-for
  scenario. Fix before lifecycle code (this changes the `Applied`
  predicate and decision-row schema, which is expensive to re-freeze
  later): specify an audited coordinator-side **abandon-binding**
  override, ceremonially parallel to force-retire — audit record with
  binding identity/caller/reason, marks the binding forfeited so the
  decision can reach `Applied`, and the abandoned node (if it ever
  returns) fails closed via its stale coordinator-UUID/activation
  validation.

## P2

- **P2-1 — `ec_distann_retire_epoch` is not gated on the successor
  decision being `Applied`, producing a reachable dead-end.** While the
  decision is `Activated`, predecessor participants are a mix of
  `Published, non-active` and `Retired` (FR-082:67-68). Nothing stops the
  coordinator committing a retire decision (fence held, zero count) while
  some participant is still unmarked; `apply_epoch_retire` on that
  participant then hits Published→Reclaimed — a transition absent from
  the state table — and errors `EC_EPOCH_STATE` with zero mutation. The
  committed retire decision meanwhile blocks all new registrations of the
  fingerprint (FR-082:373-378), and `recover_epoch_retire` has no stated
  authority to issue T4b marks. One sentence fixes it: normal and forced
  retirement of a predecessor fingerprint SHALL require its covering
  successor decision to be `Applied` (or: retire-apply on a
  `Published, non-active` generation with a matching activation binding
  subsumes the mark). Add the axis to TC-042's retire/reclaim row
  (spec/tests.md:662).
- **P2-2 — Fence-map capacity is monotonic per postmaster lifetime, so
  index churn bricks scan registration on healthy indexes.**
  FR-082:414-416: fence IDs are never recycled during one postmaster
  lifetime and capacity counts every distinct database/UUID pair since
  startup (default 4,096; FR-082:391-393). Every DROP+CREATE and every
  destructive REINDEX (which mints a new UUID) permanently consumes a
  slot; a long-lived server with churn — a CI/test host is exactly this —
  eventually fails registration with `EC_EPOCH_PIN_CAPACITY` until
  restart. Either permit removal of a fence entry whose UUID is provably
  dropped and whose heavyweight lock has no holders/waiters (safe: v4
  UUIDs never recur, so collision-freedom for live UUIDs is preserved),
  or explicitly specify the restart remedy and make the exhaustion state
  operator-observable. TC-042's registry row tests max+1 but not
  churn-to-exhaustion of fences.

## P3

- **P3-1** — "Backend-start generation" (FR-082:397-398) is not a
  PostgreSQL-native concept; define the liveness predicate normatively
  (e.g. stored PID + PGPROC match for that ProcNumber under the LWLock,
  or an extension-maintained per-ProcNumber generation counter) or two
  implementations will disagree on when a token is dead.
- **P3-2** — `EC_EPOCH_PIN_CAPACITY`'s "evict and mutate nothing"
  (FR-082:573) contradicts the mandated dead-entry reaping at
  registration (FR-082:399-402). Say "evict no live token; dead-entry
  reaping is permitted before failing."
