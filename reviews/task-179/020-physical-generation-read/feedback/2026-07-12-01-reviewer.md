# Packet 020 — Published physical-generation read (outside review)

**Status: CHANGES REQUIRED — one P1.** Correctness of the read design is
strong (see VERIFIED GOOD); the blockers are operational.

- **P1-1 — Scan token leaks on any query ERROR/cancel** (violates
  FR-082:526-529 / AC-13). The ScanTokenGuard lives in
  PhysicalGenerationScan, palloc0 + ptr::write in the CustomScan exec
  state (custom_scan.rs:554-556), dropped only in end_custom_scan
  (:1288-1294). On elog(ERROR)/timeout/cancel PostgreSQL never calls
  EndCustomScan and resets the memory context without running Rust Drop.
  The reaper only reaps dead backends, so a pooled backend that errors
  mid-scan strands the token for its lifetime → normal retirement of
  that fingerprint returns EC_RETENTION_ACTIVE forever; only exit is
  audited force-retire. Errors after registration are very reachable
  (any remote-transport hiccup raises; bench-harness timeouts cancel).
  Fix: register tokens in a backend-local list released by an
  xact-abort callback (the codebase already uses this pattern for the
  retirement fence), with EndCustomScan deregistering normally. This
  must land before any benchmark campaign — harness cancels will wedge
  inter-epoch cleanup.
- **P2-1 — No epoch-mismatch restart on the physical path**
  (FR-082-AC-2): run_scan_attempt_with_restart wraps only the legacy
  path; the physical open() race raises EC_EPOCH_MISMATCH straight to
  the user, and the comment claiming "executor-level restart can resolve
  the successor" (generation_read.rs:96-99) is false — no such restart
  exists. Loop once (drop stale guard, reopen) and classify remote
  fingerprint rejections as EpochMismatch.
- **P2-2 — Underlying physical endpoints keep default PUBLIC EXECUTE**:
  the revoked SQL wrappers are decorative because
  ec_distann_expand_physical_nodes /
  ec_distann_materialize_physical_row_payloads are in no REVOKE block
  (same finding as packet 029 P1; fix together).
- **P2-3 — Hot-path costs will make latency benchmarks measure overhead,
  not design**: (a) per-query Vamana head-graph CONSTRUCTION in open()
  (load_head_sample + build_vamana + repair_reachability per scan);
  (b) per-hop fresh Spi::connect with format!-assembled SQL, no prepared
  plans, full record copies; (c) ~6 catalog SPI round-trips per open.
  Land head-index caching/persistence + prepared-plan reuse (or a
  direct heap-read expander) before citing physical-path latency. This
  is almost certainly the packet-032 probe's 10.7s-vs-1.0s delta,
  together with the per-scan candidate verification (packet 031
  feedback P2).

P3s: registration retire-decision check is MVCC-snapshot-stale under

entry or read with a fresh snapshot); open() never cross-checks
generation.epoch_fingerprint == active.fingerprint; READ COMMITTED
mid-statement publish can surface the hard "disappeared" error;
ExecClearTuple precedes the null-relation guard.

Correctness/recall through this path is trustworthy; latency is not yet.
