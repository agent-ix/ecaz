## P1 — resolve in a spec revision before the affected checkpoint

- **P1-1 — `placement_hash` v1 is never algorithmically defined.**
  FR-078:180 gives only `placement_hash(vec_id, hash_version) mod
  roster_count` plus a version field. This is the one function that
  determines physical placement, that participants must independently
  recompute to enforce `EC_WRONG_OWNER`/derive their ordinal, and that
  FR-078-AC-1 asserts is identical on coordinator and participants — yet a
  spec that pins byte layouts and digest domain strings everywhere leaves it
  unspecified. Name a concrete function for `hash_version = 1` (e.g.
  SipHash-2-4 with a fixed published key over `u64_le(vec_id)`, or
  `SHA-256("ec_distann_placement_v1\0" || u64_le(vec_id))` truncated — pick
  one and add golden test vectors under TC-050). Blocks checkpoint 001
  (format-and-control).

- **P1-2 — `build_options` canonical encoding contradicts between FR-078 and
  FR-082, inside digested formats.** FR-078:322 defines the build-spec field
  as exactly `build_list_size u16, alpha f32_le, seed u64, closure_epsilon
  f32_le, head_index_cap u32, build_shards u32` (no graph degree). FR-082:94
  defines the manifest field as "canonical graph degree, build width, alpha,
  seed, closure, and head-cap values" — includes graph degree, omits
  build_shards, renames build_list_size, and gives no byte layout. Since the
  manifest is SHA-256-digested into the fingerprint, `manifest_digest` is not
  deterministically derivable from the spec. Same gap for the manifest's
  `codec_parameters` (FR-082:93 — "canonical codec kind and shape", no
  layout; contrast the fully specified `codec_artifact` in FR-078:148-156).
  Either reference FR-078's encodings by name or restate them byte-for-byte.
  Blocks checkpoint 001 (`manifest_v2.rs`).

- **P1-3 — per-scan durable pins on every participant are an unbudgeted
  read-path tax that will dominate the first detailed benchmarks.**
  FR-082 Scan Pins requires, per scan attempt: a fresh UUID token, a pin RPC
  to *every* roster participant before the first expansion, a durable
  (restart-surviving, i.e. WAL-flushed) ledger write per participant, and a
  matching unpin pass at completion. That is 2 × roster_count extra round
  trips plus 2 × roster_count synchronous commits per query, serialized ahead
  of any useful work — on a path whose whole design goal (ADR-085 D11,
  NFR-019) is H round-trips of useful expansion. NFR-017's latency gate
  nowhere accounts for this. The retention problem being solved (participant
  restart must not reclaim a generation pinned by a live coordinator scan) is
  real but does not require per-scan durable writes; retirement is rare and
  operator-adjacent, so make *retirement* expensive instead of *scans*.
  Alternatives, roughly in order of preference:
  1. **Coordinator-side in-flight registry + retire handshake:** participants
     never reclaim unilaterally; `ec_distann_retire_epoch` (coordinator-run)
     checks the coordinator's local in-flight scan table, then instructs
     participants. Participant restart is safe because reclaim only ever
     happens on explicit coordinator instruction. Zero per-scan remote work.
  2. **Leased epoch pins per (backend, fingerprint), not per attempt:** a
     backend pins once, renews on a coarse interval, unpins at backend exit;
     thousands of scans amortize one pin. Wedged leases expire by TTL instead
     of requiring force-retire.
  3. **Lazy pin-on-first-contact:** piggyback the pin on the first expansion
     call each participant actually receives in the attempt, dropping the
     up-front barrier and pinning only touched participants (materialization
     already touches every owner in the k-prefix, but expansion may not).
  If the durable per-scan pin is retained deliberately, the spec must say so
  with a measured justification, and NFR-017 must include pin overhead in the
  gate. Blocks checkpoint 004/005 (publication-and-pins, read path) — not
  checkpoints 001-003.

## P2 — fix in the same revision; does not block starting checkpoint 001

- **P2-1 — Build-gate durability contradicts the one-transaction
  build-to-Ready, and mid-build coordinator death leaves undiscoverable
  remote orphans.** FR-078:89-98 requires the durable gate be persisted
  "before returning Ready" while also requiring build-to-Ready to be "one
  coordinator transaction" — state written inside that still-open transaction
  is not durable until the return itself, and if the coordinator dies
  mid-build the gate never existed, the registry snapshot and build id were
  never durably recorded, and participants are left holding Building
  generations that no coordinator-side record names (`ec_distann_epoch_build_status`
  requires knowing the build id). Require a small separately-committed build
  registration (build id, epoch, roster snapshot, gate) *before the first
  remote `begin`*, and state that participant-side Building generations from
  vanished builds are discoverable/abortable via a local listing.
- **P2-2 — Scan-triggered publish recovery needs single-flight and a
  privilege model.** FR-082:267-273 makes any reader that observes a pending
  decision invoke recovery — remote publishes and a pointer swap performed
  from an arbitrary user backend. Two concurrent readers racing the
  swap-"exactly once", and the required privileges, are unspecified. Require
  an advisory-lock single-flight with non-blocking fallback to the prior
  active fingerprint (the fallback text already exists), and state who may
  execute recovery.
- **P2-3 — A wedged pin on the ACTIVE epoch has no cleanup path short of
  retiring the epoch.** FR-082:234-237 says only force-retire may clear
  wedged tokens, but force-retire retires the generation. A coordinator crash
  that wedges tokens on the *current* active epoch permanently blocks its
  future normal retirement with no remedy that doesn't take the epoch down.
  Add an audited `force_unpin` (or lease TTL per P1-3 option 2).
- **P2-4 — `EC_HANDOFF_TOO_LARGE` for a single >8 MiB entry is a permanent
  corpus rejection discovered mid-handoff.** A single wide TOASTed source row
  can exceed 8 MiB on its own (FR-078:393), failing the build after the full
  stitch has run. Require a preflight at snapshot capture (max encoded row
  payload check) so the failure is immediate and classified, or specify
  entry chunking. State explicitly that this is a documented corpus
  constraint if it stays.
- **P2-5 — NFR-018's numerator includes the logical control index but the
  specified measurement excludes it.** NFR-018:19-22 sums the control index
  into the ≤4× numerator; FR-078:366-367 mandates topology byte counts
  exclude it. The specified audit cannot produce the specified numerator.
  Pick one (recommend: keep it in the numerator, add a control-index bytes
  column or a separate suite-storage source).
- **P2-6 — `logical_index_uuid` has no provenance.** The roster carries it,
  participants must match on it, but `ec_distann_register_node_descriptor`
  takes no UUID and no operation returns a participant's UUID. Specify how
  the coordinator learns/verifies it (e.g. registration-time remote identity
  query, or an explicit argument validated at begin).
- **P2-7 — The one-owner `distributed_control` build is ambiguous between
  the "single-node degenerate deployment" (base-table TIDs allowed,
  FR-078:248-249) and the distributed contract (frozen row tier required).**
  tests.md requires a one-node degenerate roster cell; FR-075 defines
  multinode as roster > 1. State that `distributed_control=true` always
  freezes a row tier regardless of roster size (recommended — one code path,
  and TC-040's one-owner cell becomes implementable), reserving the
  base-table path for `distributed_control=false` only. The plan's §1 already
  leans this way; the spec should say it.
- **P2-8 — "Generation" is used at per-participant and cluster scope without
  definition** (FR-078:47 "one Building generation per roster participant"
  vs FR-082:18 "each physical graph generation" = cluster). Add a one-line
  definition (e.g. "generation = one participant's physical shard of an
  epoch; the epoch is the cluster-wide unit") and sweep usages.
- **P2-9 — The packet's `traceability-audit.log` is self-attested key=value
  output with no captured command.** The claims survived independent
  re-verification this round, but the artifact is not reproducible evidence
  per the manifest convention. Land the audit as a script/command whose
  invocation and raw output are captured, like the quire log.
