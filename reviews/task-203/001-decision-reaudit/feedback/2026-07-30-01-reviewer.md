# Task 203 / 001 — the founding finding is intact in the spec layer and orphaned in the task layer

This is a program-integrity re-read, not a re-audit of the matrix. The question
asked was whether the reason this audit started — **ec_distann had stopped being
sharded** — survived into the tasks that were written and the work that was done.

Answer: it survived in the **requirements**, and it did not survive as an
**owner**. Four threads that carry the sharding intent have no task assigned to
them, and one of them is the shipped default.

## What did survive, and is worth protecting

- `StR-008`'s conformance precondition states the intent exactly: "A
  configuration that meets the p50 criterion by ceasing to distribute the index
  does not satisfy this need — **it abandons it**." That sentence is the audit's
  founding finding in normative form.
- `NFR-021` (distribution invariant) and `NFR-022` (control validity) landed with
  this packet and are now machine-checked by Task 208.
- The ledger records `TRAV-28` as **SCOPE DRIFT** and `TRAV-30` as **ACTIVE — the
  NFR-021-conforming direction ... Reinstated as the successor direction to the
  withdrawn replica**.
- Task 204 removed the measurement blindness that let the loss of sharding pass a
  gate, and Task 208 turned the invariant into a per-arm verdict.

## P1 — `TRAV-30` is reinstated in the ledger and imported by no task

`TRAV-30` ("routing-only gateway copies without full graph replication") is the
one candidate from Task 190's family 1 that preserved sharding, was dropped at
that task's narrowing step, and was explicitly reinstated by this audit.

`grep TRAV-30 plan/tasks/*.md` returns only Task 187 and Task 194, both of which
say it "belongs to Task 190" — and Task 190 is closed with an **INVALID** verdict
in this packet's own matrix. Tasks 204–209 do not import it. The status vocabulary
at the top of the roadmap defines **active** as "assigned to the next executable
task"; `TRAV-30` is marked active and is assigned to nothing.

The corrective program is sequenced **pushdown → regime → head** — three latency
and recall levers. The distribution direction that the audit reinstated is not in
that sequence.

## P1 — FR-084's disposition is a non-goal everywhere, and the replica is still the preferred path

This packet's recommendation 6 says "Do not delete FR-084 or the replica. Its
disposition ... is an operator decision." Task 204 non-goals: "Deciding FR-084's
disposition." Tasks 205, 206, 207, and 209 each list "Reviving the traversal
replica" as a non-goal.

Every task correctly refuses to *revive* it. No task owns *retiring* it, and no
operator decision is recorded anywhere in `plan/` or `reviews/`.

Meanwhile it is not dormant. `generation_read.rs:2523` opens
`ReadyTraversalReplica` unconditionally on the normal read path and prefers it
whenever a Ready image exists — there is no production GUC gating it, which is
exactly what Task 199 promoted. The 204/205 benchmark arms read as sharded
because the fixture is run with `traversal_replica=false`; that is an arm
setting, not the default.

So the literal statement the audit was founded on — *we are not actually
sharding* — is still true of the shipped preferred configuration, ten tasks
later. Whatever the operator decides (retire, re-scope to the bounded top-layer
`TRAV-28` as written, or waive explicitly as a labeled non-conforming
accelerator), it needs an owning task rather than a non-goal in six.

## P2 — sharding the head is written as optional

`plan/tasks/207-...md` Phase 3: "Distribute head storage/search across the roster
per §2.2. Required for NFR-021 if the cap ever becomes a function of N;
**optional while the cap is constant**, so this phase is measured on its own
merits (coordinator CPU, not storage)."

The head is 25,280,512 bytes of full-precision f32 landmarks plus a ~0.6 MB graph
— constant across 10k/50k/100k, ~1% of cluster bytes at 100k. A storage argument
will therefore always conclude "leave it central," and a coordinator-CPU
argument probably will too at BW=4. §2.2 makes it a *sharded* index and §4.1
scales it by *replicas*; neither is conditioned on its size.

If the intent is "shard everything the paper shards," this phase should be
unconditional and the NFR-021 clause that permits a constant-cap
coordinator-resident head should be tightened to a recorded, time-boxed
divergence rather than a standing permission.

## P2 — per-partition construction has no enabling task

Task 207 Phase 1 requires building the head "from the union of per-owner /
per-partition top layers." Its own Why notes `build_shards = 1` is the default,
"so the common case has no partitions at all." No task owns changing that. The
primary candidate of the head task depends on a build-side change that is
described as context rather than tasked.

## P3 — the head is invisible to the gate that now enforces distribution

`distann_multicluster.rs:5381` emits the coordinator's
`physical_benchmark_storage_node` row with `graph_bytes=0 directory_bytes=0
control_bytes=0`, carrying only the traversal-replica derived relation. The head's
25.9 MB goes to a separate `physical_benchmark_head` row that the Task 208
conformance check does not consume.

The one structure that is not sharded is the one structure the distribution gate
cannot see. Folding coordinator-resident index relations into the per-node row is
a small emitter change and belongs with 208's gates.

## Suggested shape

The audit's four defects were framed as *paper conformance*, and the follow-on
program inherited that framing — it is organised by lever (pushdown, regime,
head), not by the property that was lost. That framing is why sharding work
ended up as a phase inside a recall task and a reinstated ledger row with no
owner. One task owning "restore and enforce distribution" — `TRAV-30`, FR-084's
disposition, unconditional head sharding, per-partition build, and the
coordinator storage row — would put the founding finding back in the execution
path instead of only in the requirements.
