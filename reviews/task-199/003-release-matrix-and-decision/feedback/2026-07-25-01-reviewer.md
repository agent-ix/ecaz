### P1-B is properly closed — I checked the mechanism, not the label

`active_ready_replica_at_snapshot` and `ready_replica_may_exist_at_snapshot`
both route through `pg_sys::SPI_execute_snapshot(plan, NULL, NULL, snapshot,
NULL, /*read_only=*/true, /*fire_triggers=*/false, 1)` with a snapshot from
`RegisteredSnapshotGuard::latest()` (`RegisterSnapshot(GetLatestSnapshot())`).
`read_only = true` with an explicit snapshot is the one SPI path that does
**not** substitute `GetTransactionSnapshot()`, which was the entire defect. The
guard owns the matching `UnregisterSnapshot` on drop. `ActiveSnapshotGuard`
is no longer used at this call site, so the misleading no-op is gone. That is
ask #1 from seq 03, implemented as asked, including the
`ready_replica_may_exist` half I flagged as needing the same treatment.

**And the drill can now fail.** `stronger_isolation_mutation_fenced` does
exactly the discriminator I specified: retire + reclaim so no Ready exists →
`BEGIN ISOLATION LEVEL {RR,SERIALIZABLE}` → `INSERT INTO
task199_isolation_xid_probe` (assigns the XID and fixes the transaction
snapshot) → a **second connection** builds Ready → `INSERT` into the corpus
must return `40001` / `EC_REPLICA_INVALIDATED` with the image `Stale` and zero
rows inserted. Under the pre-`8b6a00e9f` code this returns
`EC_GENERATION_MISSING` with the image still `Ready`. Both isolation levels
run, with a rebuild between cases. Result line:
`stronger_isolation_mutation_fenced pass=true ... stale_snapshot=true
xid_assigned_before_ready=true ready_committed_after_snapshot=true
sqlstate=40001 ... inserted_rows=0`. This is the drill this finding needed.

### P2-G is properly closed

The `data` arm requires a marker line with
`op=write|pwrite|pwrite64|pwritev|fsync|fdatasync` **and** the tablespace path,
so it cannot be satisfied by the create-time `open` fault the first arm uses.
Zero catalog residue, zero relation residue, cluster health and owner-fallback
identity are all queried, not asserted by literal, and the recovery build
returns to `Ready`. `enospc_midcopy_cleanup pass=true sqlstate=53100 ...
eligible_partial_images=0 catalog_residue=0 relation_residue=0` is earned.

#### P2-K — re-verify the negative cache now that it sits in front of a fresh-snapshot lookup

`0c4bf83f0` reinstates `if READY_REPLICA_PRESENCE == 1 { return; }` *before*
`RegisteredSnapshotGuard::latest()`, which is correct for performance and is
the right call — but it means the cached negative, not the fresh snapshot, is
what most mutations actually consult. `2a4a70b23` correctly stops
`guard_source_traversal_replicas` from *populating* that cache through ordinary
SPI, which was the sharp edge.

I traced the remaining argument and believe it holds: a stale `1` can only
survive into a mutation if the backend acquired no new relation lock mode since
caching, and a backend already holding a conflicting lock on the index has by
that fact prevented the Ready commit. Both `ready_replica_may_exist()` callers
that write the cache through ordinary SPI (`active_ready_replica`,
`ReadyTraversalReplica::open`) are now reachable only at READ COMMITTED, where
`GetTransactionSnapshot()` is fresh per command.

That is three independent mechanisms holding up one invariant, and it is
currently argued in a doc comment on `ready_replica_may_exist_at_snapshot`. No
action needed if you agree with the trace — but this is the part of Task 199
most likely to be broken by a future refactor, and P3-O's unit tests are the
cheapest insurance available.
