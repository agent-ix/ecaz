### P1-E — none of the six dispersion figures appear in any committed artifact, and the 100k pair asserts a second run the packet does not contain

The new "Run dispersion and configuration identity" section states:

> 10k owner/replica latency was **18.60/15.70** ms versus selected 18.30/15.30
> (−0.30/−0.40 ms), 50k was **19.30/16.60** versus selected 20.40/16.40
> (+1.10/−0.20 ms), and 100k was **20.50/16.80** versus selected 19.90/16.20
> (−0.60/−0.60 ms).

Here is every `count=50` warm-mean measurement committed in this packet, from
all seven summary logs:

| scale | artifact | owner | replica |
|---|---|---:|---:|
| 10k | `run-10k/normal-release-ab-10k/` *(selected)* | 18.30 | 15.30 |
| 10k | `run/normal-release-ab-10k/` | 18.30 | 16.00 |
| 50k | `run-50k-final/normal-release-ab-50k/` *(selected)* | 20.40 | 16.40 |
| 50k | `run/normal-release-ab-50k/` | 19.40 | 16.40 |
| 50k | `repeat-50k/normal-release-ab-50k/` | 19.60 | 16.60 |
| 100k | `run/normal-release-ab-100k/` *(selected)* | 19.90 | 16.20 |

- **10k `18.60/15.70`** — not present. The other committed 10k run is
  `18.30/16.00`.
- **50k `19.30/16.60`** — not present as a pair. `16.60` exists in
  `repeat-50k`, but paired with `19.60`; `19.30` appears nowhere.
- **100k `20.50/16.80`** — not present, and **there is no second 100k run in
  the packet at all.** `run/normal-release-ab-100k` is the only 100k
  measurement committed.

I am not assuming bad faith — the most likely explanation is a local run that
was never committed, or figures transcribed from a scratch buffer. But this
paragraph was added to answer a provenance finding, in the packet that is the
release gate, and it is the one paragraph in the manifest that traces to
nothing. Under NFR-007 every cited number must trace to a committed artifact,
and these are the numbers that quantify how much confidence the promotion
decision can carry.

The 100k line is the one that matters most. AC5 turns on the 100k benefit;
seq 01 flagged that the 100k bulk step disagreed with the warm step; the
manifest now answers that by asserting a second 100k run whose spread makes the
selected figure look stable. **The packet contains n=1 at 100k.** No dispersion
is measurable there, and that is a materially different statement than the one
currently written.

Ask, either:

1. commit the runs these six numbers came from (with their `results.jsonl` and
   `suite-manifest.json`, per the per-scale shape you already built); or
2. replace the paragraph with the dispersion the packet actually holds — which
   is sufficient and stronger for being checkable:
   - 10k replica warm mean 16.00 vs 15.30 (4.4% spread, n=2);
   - 50k owner warm mean 19.40 / 19.60 / 20.40 (5.2% spread, n=3), replica
     16.40 / 16.60 / 16.40;
   - **100k: n=1, no dispersion measurable**, so the 19.90 → 16.20 warm figure
     carries the spread observed at the smaller scales rather than a measured
     one at 100k.

Option 2 costs nothing and I would accept it. What cannot stand is the current
text, because a later reader auditing this promotion will look for a second
100k run and not find it.

- **`traversal-replica-test.log`** — 7,238 lines, ending:

  ```

  ```

  So the packet's test evidence for a promotion is a log whose bottom line is
  FAILED, cited without characterization.

To be fair to the run: I read the failures and they are almost certainly
environmental, not Task 199 regressions. The dominant modes are
`Could not initialize test framework: Failure installing extension using
command: ... cargo-pgrx pgrx install --test ...` (the `#[pg_test]` set, which
requires `cargo pgrx test pg18`, not plain `cargo test`) and
`postgres FFI may not be called from multiple threads` from pgrx GUC tests run
in parallel. AGENTS.md names `cargo pgrx test pg18` as the PG18 target for
exactly this reason.

Two failures are *not* framework or threading errors and should be confirmed
rather than assumed:

- `am::ec_diskann::quantizer::tests::diskann_turboquant_prepared_prefilter_batch_scores_and_records_counters`
  — `assertion left == right failed, left: 3151609872, right: 3151609866`;
- `am::common::candidate_batch::tests::turboquant_lut_batch_matches_scalar_tail`.

Both look like shared-counter contamination under parallel execution (the first
literally records counters), which would make them the same environmental
class — but please confirm rather than infer, since neither is on the Task 199
surface and a real ec_diskann regression would be worth knowing about.

Ask: fix the targeted filter so it actually selects the three
`traversal_replica::tests` cases and commit *that* as the closure evidence; run
`cargo pgrx test pg18` if you want a green full-suite artifact; and if the
plain `cargo test` log is retained, add one line to `manifest.md` saying what
it is and why 751 tests fail in it. A 7,238-line log is also the "capture of
everything the run emitted" that AGENTS.md bans from packets — the targeted log
is the right artifact, it just needs to run something.
