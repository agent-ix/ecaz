## What is right

These are load-bearing and should not be "simplified" later:

- **F2's fence is genuinely coherent, and the redundancy is required.**
  `build_traversal_replica` takes `ShareRowExclusiveLock` on the control index
  and calls `retain_lock_until_transaction_end()`
  (`src/am/ec_distann/traversal_replica.rs:519-528`), which conflicts with the
  `RowExclusiveLock` the executor takes on the index. The ExecutorStart guard
  alone would *not* be sufficient: a DML statement can pass
  `guard_planned_result_relations` while the replica is still `Building`, then
  block in `ExecOpenIndices`, then proceed after the build commits `Ready`. The
  per-tuple `guard_traversal_replica_mutation` in `ec_distann_aminsert`
  (`routine.rs:94`) is what closes that window. Please add a code comment
  saying so — it currently reads as removable duplication.
- **F3 holds.** `ec_distann_mark_traversal_replica_stale` takes a plain
  `pg_sys::Oid`, never a `PgRelation`, does only catalog work, and the loopback
  config sets `statement_timeout=5000 lock_timeout=5000 connect_timeout=5s`
  (`traversal_replica.rs:1061-1128`). The 44 ms queued-`AccessExclusiveLock`
  drill is a fair demonstration of the no-inversion property.
- **F4 is wired to the real publish path.** `recover_epoch_publish` is the only
  T4a endpoint, so the two `retire_superseded_replicas` call sites in
  `build_coordinator/t4a.rs` cover both normal publish and replay; the epoch
  turnover drill shows `reason=epoch_superseded`, `reclaimed=true`,
  `relation_residue=0`.
- **P3 item 3 (privileges) is closed structurally, not by checklist.** The
  class-wide `ec_distann\_%` closure in `src/lib.rs` gives every new endpoint
  SECURITY DEFINER + fixed `search_path` + `REVOKE ... FROM PUBLIC` without a
  new signature entry, and `require_index_owner` correctly reads
  `GetOuterUserId()`.
- **The total-order early-exit is strictly more conservative than before.**
  `(dist, vec_id) >= (kth.exact_dist, kth.vec_id)` cannot exit in any case the
  old bare `>=` did not, so it cannot introduce a new truncation; both new unit
  tests cover the exit and the no-exit direction.
- The two partial unique indexes
  (`ec_distann_traversal_replica_one_active`, `..._one_local_authority`) put
  single-authority in the catalog rather than in Rust. Good.

## P1 findings

### P1-1 — REPEATABLE READ / SERIALIZABLE *reads* fail instead of falling back to the owner path

`ReadyTraversalReplica::open` calls `require_read_committed` after it has
confirmed the row is `Ready` (`traversal_replica.rs:1867`), and
`generation_read.rs` re-raises that class instead of falling back:

```rust
Err(error) if error.starts_with("EC_TRANSACTION_ISOLATION:") => {
    return Err(error);
}
```

Consequence: once an operator builds a replica, **every** RR/SERIALIZABLE read
of that index errors. `BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT ...
ORDER BY v <-> $1 LIMIT k;` no longer works. Any RR reporting transaction,
consistent multi-statement read, or application that runs SERIALIZABLE loses
access to the index as a side effect of an operator building a performance
object. Packet 002 confirms this is the shipped behavior, not a drill artifact:
`scenario=repeatable_read_rejected_without_demotion pass=true
token=EC_TRANSACTION_ISOLATION`.

F5 asks that RR/SERIALIZABLE **cannot select** an invalidated replica. Not
selecting and using owner traversal satisfies that; erroring the query does
not. The owner path itself has no READ COMMITTED requirement — the
pre-Task-199 read path runs under any isolation level today.

Ask: treat non-READ-COMMITTED as `Ok(None)` (owner fallback), and drop the
`EC_TRANSACTION_ISOLATION` re-raise arm. If you believe the owner path is also
unsafe under RR here, that is a much larger claim than this task carries —
state it explicitly with the reasoning and put it in the AC4 disclosure.

### P1-2 — RR/SERIALIZABLE *writes* fail with an isolation error, not the disclosed single `40001`

`guard_traversal_replica_mutation` calls `require_read_committed` and
`pgrx::error!`s on failure (`traversal_replica.rs:1230`). So with a Ready
replica present, DML inside an RR/SERIALIZABLE transaction returns
`EC_TRANSACTION_ISOLATION`, not the disclosed "exactly one retryable `40001`".

Rejecting the *mutation* is defensible — an RR snapshot could miss a replica
that turned `Ready` after the snapshot, and skipping invalidation there would
be silently incoherent. What is not acceptable is that this is undisclosed.
Combined with P1-1, building a replica removes RR/SERIALIZABLE usability from
the whole table in both directions, and the task's "read-mostly, single
authority" restriction says nothing about isolation levels.

Ask: fix P1-1 (reads fall back), keep the write rejection, and add the
isolation restriction to AC4's disclosed envelope and the operator
documentation, with the exact SQLSTATE and token an application will see.

## P2 findings

### P2-1 — the replica lookup is on the hot path with no negative cache

- `ReadyTraversalReplica::open` runs a 3-table join plus a `LEFT JOIN`
  aggregate over SPI on **every** `PhysicalGenerationScan` search, including on
  indexes that have never had a replica built.
- `active_ready_replica` runs **two** SPI queries (`extension_owner()` plus the
  active-epoch/candidate join) and is called from `ec_distann_aminsert`
  **per inserted tuple**, from `ec_distann_ambulkdelete`, and from
  `guard_source_traversal_replicas` for every result relation of every DML
  statement in the database.

Compare `reject_if_gated` in the same file: it has `extension_is_installed()`
plus the `NO_ACTIVE_GATE` thread-local negative cache specifically so that
ordinary DML in an unrelated database pays nothing. `guard_source_traversal_replicas`
has neither, and `ec_distann_indexes_for_source` issues its
`pg_index`/`pg_class`/`pg_am` join unconditionally.

This is exactly the class of change this repo's rules say must not be closed on
prediction. Ask: (a) add a backend-local negative cache with a correct
invalidation source (relcache/shared invalidation keyed on the replica
catalog, or the same statement-trigger pattern the build gate already uses),
and (b) packet 003 must include a **no-replica** before/after arm across the
Task 199 commit boundary — read latency at 10k/50k/100k *and* an
insert/load-throughput A/B. AC5's "material end-to-end benefit" must not be
funded by a regression on the default deployment that never builds a replica.

### P2-2 — `ambulkdelete` turns routine autovacuum into an ERROR

`guard_traversal_replica_mutation` in `ec_distann_ambulkdelete`
(`routine.rs:123`) means the first VACUUM with dead index tuples aborts with
`40001` and a message telling the caller to "retry the mutation on the owner
path". For autovacuum there is no such caller; the worker logs the error, and
routine table maintenance has silently destroyed a replica that cost 52 s of
build and ~1.9 GB of WAL at 100k. It self-heals on the next pass only because
the image is now `Stale`.

Ask: give the vacuum path its own disposition — invalidate and continue
without raising — or, if raising is deliberate, disclose in AC4 that any
autovacuum of the source table retires the replica, and say what an operator is
expected to do about it on a read-mostly-but-not-read-only table.

### P2-3 — the "retry on the owner path" message does not match measured behavior

Packet 002: `real_insert_durable_invalidation ... first_sqlstate=40001
token=EC_REPLICA_INVALIDATED state_after_error=Stale
retry_token=EC_GENERATION_MISSING retry_inserted_rows=0`.

The retry does not succeed. On the published physical epoch it hits the
pre-existing Task 167 fail-closed posture. The guard's error text
("retry the mutation on the owner path") and Task 199 AC3 ("retry through
owners") both describe something the evidence shows does not happen. You
flagged the separation honestly in the packet 002 request — now fix the
artifacts that assert otherwise: correct the guard message to name the real
posture, and correct AC3 (or show a mutation front door where the retry
actually commits).

### P2-4 — post-invalidation rebuild is a dead end with an unactionable error

`existing_ready_digest` errors for any non-`Ready` row carrying the same
`build_id`: `"existing replica is not a complete Ready replay (Stale)"`. After
the first mutation invalidates the replica, a same-epoch rebuild is impossible
until the operator runs retire + reclaim — which the error never mentions, and
which AC2's "idempotent" construction implies should not be necessary.

Ask: either auto-retire the same-`build_id` `Stale` row inside
`build_traversal_replica` (it already holds the authoritative fence), or make
the error name `ec_distann_retire_traversal_replica` +
`ec_distann_reclaim_traversal_replica` explicitly.

### P2-5 — a demotion failure can escalate a fallback into a failed read

`handle_ready_replica_failure` returns `Err` when both the side transaction and
the in-transaction local demotion fail, and `generation_read.rs` propagates it
with `?`. That turns a replica problem into a failed user query, which is the
precise outcome F7 exists to prevent. The local fallback also performs a
catalog `UPDATE` inside what the user issued as a `SELECT`, so it fails outright
in a `SET TRANSACTION READ ONLY` block or on a hot standby.

Ask: on any demotion failure, `warning!` and continue to owner traversal.
Availability of the owner path must never depend on being able to write the
replica catalog.

## P3 findings

### P3-1 — the guard is fail-closed on *lookup* errors, database-wide

`guard_traversal_replica_mutation` calls `pgrx::error!` on any error from
`active_ready_replica`, so a transient failure reading
`ec_distann_traversal_replica` fails all DML on every ec_distann-indexed table,
including indexes that have never had a replica. Fail-closed is defensible for
coherence; confirm it is intended for the never-had-a-replica case and put it
in the AC4 disclosure.

### P3-2 — confirm the intended query role for the new revoked-catalog reads

`ReadyTraversalReplica::open` reads `ec_distann_traversal_replica` and
`ec_distann_traversal_replica_owner` with a bare `Spi::connect` in the querying
backend. Both tables are `REVOKE ALL ... FROM PUBLIC`, and unlike
`active_ready_replica` this call is *not* wrapped in
`with_restricted_type_io_owner`. Pre-existing reads in the same path
(`active_generation_identity` on `ec_distann_active_epoch`) have the same
shape, so this may be an accepted deployment assumption — but this change puts
two more revoked-catalog reads on the normal read path. Please state the
intended query role; if it is not the extension owner, wrap this lookup the way
`active_ready_replica` already does.
