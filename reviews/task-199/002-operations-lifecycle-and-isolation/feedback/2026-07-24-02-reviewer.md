## New P2 findings

### P2-E — the write-side READ COMMITTED requirement is broader than the hazard requires, and the lock fence already covers it

`guard_traversal_replica_mutation` now calls `require_read_committed` **before**
the Ready lookup, so every RR/SERIALIZABLE write through any ec_distann index
fails with `25001` — on indexes that have never had a replica, in databases
where no replica has ever been built, forever. The stated justification is that
"a stronger-isolation snapshot cannot safely prove that no Ready replica was
concurrently committed".

That justification is about the *snapshot*, but the coherence property is
actually supplied by the *lock*, and the lock does not care about isolation
level:

1. `ExecOpenIndices` takes `RowExclusiveLock` on the ec_distann index before the
   first `aminsert`;
2. `build_traversal_replica` takes `ShareRowExclusiveLock` on that same index
   and holds it to transaction end;
3. therefore no build can commit `Ready` for that index while a mutating
   statement is between `ExecOpenIndices` and its last tuple, at **any**
   isolation level.

So a lookup performed in the post-lock per-tuple guard under a fresh snapshot
(`PushActiveSnapshot(GetLatestSnapshot())` around the SPI, popped after) is
authoritative for the remainder of the statement regardless of `XactIsoLevel`.
This is the same reasoning `b242c748a` already relies on for the blocking-fence
case, just applied one step further. The ExecutorStart guard can stay a
pre-lock best-effort check, exactly as it is today.

The cost of not doing this is not small: it removes RR and SERIALIZABLE writes
from every table with an ec_distann index, as a permanent property of the
access method, in exchange for a hazard the fence already closes. That is a
larger production restriction than a per-index optional acceleration object
should be able to impose.

Ask: either implement the fresh-snapshot lookup in the post-lock guard and drop
the write-side isolation requirement, or keep the restriction and answer this
lock-based counter-argument explicitly in `FR-084` — the current spec text
argues only the snapshot side.

### P2-F — a broken control connection is now available but unbounded and non-self-healing

`1b3de943c` is correct (P2-5 closed), but it leaves the image `Ready` when the
side transaction cannot commit. There is no backend-local suppression, so every
subsequent scan of that index repeats the whole sequence: presence lookup →
full replica catalog join → validation/search failure → a **fresh loopback
connection attempt** with `connect_timeout(Duration::from_secs(5))` and
`statement_timeout=5000` → `warning!` → owner restart.

`loopback_connection_config` builds a new `postgres::Config` and connects per
call; nothing is cached. With the control path down (bad auth, missing password
file, socket dir change, `max_connections` exhausted) that is up to ~5 s added
to **every query** on the index, plus a warning per query in the server log,
indefinitely — until an operator notices and runs
`ec_distann_recover_traversal_replica_invalidation`. F7 asks for a
*self-healing* fallback; this is a healing fallback that never heals and whose
degraded mode is far more expensive than owner traversal.

The `control_auth_failure_recovery` drill proves availability under this
condition. It does not measure its cost, and the packet does not disclose it.

Ask: add a backend-local "do not select this `build_id` again this session"
suppression — the `READY_REPLICA_PRESENCE` cache already has the right
invalidation source and lifetime — so a broken control path degrades to plain
owner traversal instead of owner traversal plus a 5 s connect timeout. Then
either measure the degraded-mode read latency in packet 003 or disclose the
bound in the runbook.

## New P3 findings

### P3-A — `require_read_committed` also rejects READ UNCOMMITTED

`lifecycle_guard.rs:9` tests `XactIsoLevel != XACT_READ_COMMITTED`. PostgreSQL's
`XACT_READ_UNCOMMITTED` is `0`, and PostgreSQL implements READ UNCOMMITTED
*as* READ COMMITTED — it takes a fresh snapshot per statement and has exactly
the visibility property this guard needs. So
`BEGIN ISOLATION LEVEL READ UNCOMMITTED; INSERT ...` now fails with `25001`,
and a read at that level needlessly declines a healthy replica.

The correct predicate is the one PostgreSQL uses for this question itself,
`IsolationUsesXactSnapshot()`, i.e. `XactIsoLevel >= XACT_REPEATABLE_READ`.
This is pre-existing in `lifecycle_guard.rs`, but Task 199 is what puts it on
the front door of every ec_distann write, so it should be fixed here. Low
severity only because `READ UNCOMMITTED` is rare.

### P3-B — `25001` is a slightly wrong SQLSTATE for "isolation level too strong"

`ERRCODE_ACTIVE_SQL_TRANSACTION` (`25001`) means "cannot be executed within a
transaction block" in every other PostgreSQL use; client retry middleware and
ORMs key on it accordingly. "Your transaction's isolation level is too strong"
is closer to `25000` `invalid_transaction_state` (or `0A000`
`feature_not_supported`). The `EC_TRANSACTION_ISOLATION` token makes it
workable either way and the choice is now written into the task, FR-084, and
the runbook — so if it is deliberate, say so and leave it. Flagging only
because it is cheap to change now and expensive once documented downstream.

## Two notes, not findings

**The presence cache's correctness argument should be written down.** I traced
it and believe it holds, but only via a chain that a future refactor will not
see: a stale-negative `READY_REPLICA_PRESENCE` can only survive into a mutation
if the backend acquired no new relation lock mode since caching, and
`LockRelationOid` calls `AcceptInvalidationMessages()` on any acquisition that
is not `LOCKACQUIRE_ALREADY_HELD`; a backend that *does* already hold a
conflicting lock on the index has, by that same fact, prevented the build from
committing `Ready`. Both halves are load-bearing. Please put that in a comment
above `ready_replica_may_exist`, the way `routine.rs` now explains the
redundant per-tuple guard.

**State the DELETE invariant explicitly.** `INSERT` has two guards (pre-lock
ExecutorStart plus post-lock per-tuple); `DELETE` has only the pre-lock one,
because ec_distann has no per-tuple delete callback. So a build that commits
`Ready` in the window between the DELETE's source-table lock and
`ExecOpenIndices` can be missed. I believe this is benign — a missed DELETE
invalidation leaves the replica exactly as stale as the owner index, and heap
MVCC filters the row from both — whereas a missed INSERT would make the replica
*incomplete*, which is why the per-tuple backstop exists there. That asymmetry
is a deliberate and correct design, but it is currently unstated; a reader will
otherwise see it as a missing guard. Put the invariant in `FR-084` or the
guard's doc comment.
