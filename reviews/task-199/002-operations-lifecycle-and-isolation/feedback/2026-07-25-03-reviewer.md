### P2-C crash arm — closed

`scenario=crash_after_control_commit pass=true backend_pid=153291
backend_terminated=true state=Stale inserted_rows=0

### P2-F — closed, and the fix is better than what I asked for

`2dd24b6dc` + `6bf805bdb` do close this, and the drill genuinely discriminates —
I checked, because the assertion looked tautological at first read. The sequence
in `task199_auth_failure_recovery_drill` repairs the password file *before* the

would find Ready, fail validation, successfully demote, and leave `Stale`. The

Two things I got wrong in seq 02 that the fix caught: `build_id` is the

`ReadyTraversalReplica::open` also means the degraded path skips the presence
query and the catalog join, not just the 5 s connect. Good.

### Empty-catalog fix — correct

`fcfc529e5` is right: `Spi::get_one` errors on a zero-row result, which is the
ordinary pre-first-build state that `6bf805bdb` had just introduced a path into.
The `EXISTS(...)` + `(SELECT tableoid … LIMIT 1)` single-row form keeps the
presence semantics and the catalog-OID learning in one snapshot, and the r19 run
exercises the empty catalog on every pre-build scan. The invariant is preserved.
The near-miss (a regression introduced and fixed inside one review round, caught
only by a full three-node run) is the argument for P3-F.

## P1 finding

### P1-B — the post-lock guard does **not** get a fresh snapshot; the RR/SERIALIZABLE write invariant in FR-084 is unsound as implemented

`guard_traversal_replica_mutation` now wraps the Ready lookup in
`ActiveSnapshotGuard::latest()` and both `traversal_replica.rs` and FR-084 state
that this makes the lookup authoritative at any isolation level. It does not,
because SPI overrides the pushed snapshot:

1. pgrx executes `client.select(...)` as
   `SPI_execute(cmd, Spi::is_xact_still_immutable(), limit)`
   (`pgrx-0.17.0/src/spi/query.rs:80`), and
   `is_xact_still_immutable()` is `GetCurrentTransactionIdIfAny() == InvalidTransactionId`
   (`pgrx-0.17.0/src/spi.rs:212`).
2. By the time `aminsert` runs, `heap_insert` has already assigned an XID, so
   `read_only = false`.
3. `_SPI_execute_plan` with `snapshot == InvalidSnapshot && !read_only &&
   !allow_nonatomic` executes
   `PopActiveSnapshot(); PushActiveSnapshot(GetTransactionSnapshot());`
   (`src/backend/executor/spi.c:2608-2612` in 18.3) — it discards the guard's
   pushed snapshot.
4. `GetTransactionSnapshot()` returns the fixed `CurrentSnapshot` whenever
   `IsolationUsesXactSnapshot()`. So at RR/SERIALIZABLE the catalog lookup runs
   under the **transaction** snapshot, exactly the condition the removed
   `require_read_committed` check existed to prevent.

This also explains why the old design was self-consistent: at READ COMMITTED,
`GetTransactionSnapshot()` returns a brand-new snapshot per SPI command, so the
RC path was always effectively fresh and remains correct today. Only RR and
SERIALIZABLE are affected.

Failure scenario (guard silently does not fire):

```
-- B: BEGIN ISOLATION LEVEL REPEATABLE READ;
--    INSERT INTO scratch VALUES (1);        -- assigns an XID, fixes the snapshot
-- A: SELECT ec_distann_build_traversal_replica('dm_idx');   -- commits Ready
-- B: INSERT INTO corpus VALUES (...);       -- ExecutorStart guard: txn snapshot, Ready invisible
--                                           -- aminsert guard:      txn snapshot, Ready invisible
```

The lock argument I made in seq 02 P2-E is still correct on its own terms —
`RowExclusiveLock` does prevent a build from committing Ready *during* the
statement — but it never covered a build that committed **before**
`ExecOpenIndices` and **after** the transaction snapshot. Closing that window was
the entire job of the fresh snapshot, and the fresh snapshot is not reaching the
query. My P2-E ask is therefore not satisfied by this implementation; I am
reopening it at higher severity rather than pretending the argument landed.

**Current blast radius is small, and the reason matters.** For a
distributed-control index `ec_distann_aminsert` unconditionally raises
`EC_GENERATION_MISSING` immediately after the guard (`routine.rs:105-109`), so a
missed invalidation cannot actually let a row into the owner generation today.
The two endpoints that do mutate owner state — `ec_distann_apply_record_writes`
(`remote_endpoint.rs:238`) and `ec_distann_fold_delta_into_graph`
(`insert.rs:488`) — still call `require_read_committed` themselves. And the
missed-DELETE case is the benign asymmetry now documented in FR-084. So this is a
latent defect masked by the Task 167 fail-closed posture, not a live data-loss
bug. It stops being latent the moment M5 incremental distributed insert removes
that fail-close, which is precisely when nobody will be re-deriving this proof.

The drill cannot detect any of this. `stronger_isolation_mutation_fenced` opens
`BEGIN ISOLATION LEVEL {RR,SERIALIZABLE}` and immediately inserts, so the
transaction has no XID yet at `ExecutorStart`, `read_only` is *true* there, the
Ready row was committed before the transaction began, and the guard fires from
the pre-lock check. The drill never reaches the post-lock guard and never tests a
Ready row committed after the transaction snapshot. `sqlstate=40001` in the r19
log is real but proves a different property than the one FR-084 claims.

Ask, in order of preference:

1. Make the lookup actually snapshot-fresh: run the presence and identity
   queries through `pg_sys::SPI_execute_snapshot(..., GetLatestSnapshot(),
   InvalidSnapshot, /*read_only=*/true, ...)`, or replace the SPI call with a
   `systable_beginscan` under an explicit snapshot. `ActiveSnapshotGuard::latest`
   then becomes redundant for this call site and should be dropped rather than
   left as a misleading no-op. Note that `ready_replica_may_exist` has the same
   defect and needs the same treatment — a stale-negative presence answer
   short-circuits before the identity query ever runs.
2. Or restore the write-side READ COMMITTED requirement (keeping the P3-A
   `>= XACT_REPEATABLE_READ` predicate) and revert the FR-084 / task-file /
   runbook text to match. This is safe and honest; it is simply the restriction I
   argued against, and I would rather have it than an invariant that is written
   down but not implemented.

Either way the drill needs a variant that can fail: have the RR transaction write
to a scratch table first, *then* let a second session commit Ready, then insert
into the corpus. Today that returns `EC_GENERATION_MISSING` (XX000) with the
image still `Ready` instead of `40001` / `Stale` — a clean discriminator that
will keep working after M5 lands.

## P2 finding

### P2-G — the ENOSPC arm only exercises relation *creation*, so `eligible_partial_images=0` is close to vacuous

The armed run is real and I am not disputing it: the fault provider is
`LD_PRELOAD`ed into node 1's postmaster, the arm file is created only around
`ec_distann_build_traversal_replica`, and the run reports
`sqlstate=53100 provider_fault_events=1 errno=28 eligible_partial_images=0
catalog_residue=0 relation_residue=0 cluster_healthy=true
owner_fallback_identity=true` with a successful Ready recovery build. The
mechanism is sound too: `tablespace_clause` (`generation_store.rs:336-354`) puts
the replica heap and directory index in the *index's* tablespace, so
`ALTER INDEX dm_idx SET TABLESPACE task199_replica_enospc` does route them under
`pg_tblspc/`, and the provider only faults `open*` calls carrying `O_CREAT`
(`ldpreload_provider.c:171-251`), so ordinary reads of `dm_idx` cannot trip it.

But `ECAZ_FAULT_PROVIDER_AFTER=1` faults the **first** creating open under
`pg_tblspc/`, which is the replica heap's file inside
`create_traversal_replica_relations` — before the `Building` catalog row is
inserted (`traversal_replica.rs:678-724`) and before a single record is copied.
So the drill proves that a build failing at its earliest possible point rolls
back cleanly, which single-transaction DDL already guarantees. It does not
exercise the case AC2 is actually about: relations created, rows partially
copied, `Building` row present, then ENOSPC. That is also the only case that
would exercise the `pwrite`/`pwritev`/`fsync` interception `a4a8c3aa2` was
written for — as run, the new `pwritev` hook is covered by its unit test and by
nothing else.

Ask: add a second arm with `ECAZ_FAULT_PROVIDER_AFTER` set past the create
(or matching the replica relfilenode and faulting a write) so the failure lands
mid-copy, and assert the same zero-residue and no-eligible-image posture from
there. Keep the create-time arm; it is cheap and it is the one that proves
`53100` propagates.

## P3 findings

- **P3-C — the ENOSPC drill does not assert its own SQLSTATE.** The bail
  condition (`distann_multicluster.rs:1671-1683`) checks
  `provider_faults`, residue, health and owner fallback, but `sqlstate` is only
  *reported*. A build that failed for an unrelated reason while one stray
  provider fault line existed would still print `pass=true` with a different
  sqlstate. Add `sqlstate != "53100"` to the bail.
- **P3-D — the provider marker is not packet-local.** `provider_fault_events=1`
  is the drill's derived count; the raw witness (`fault=1 … op=… errno=28
  target=…/pg_tblspc/…`) lives in the ephemeral run dir and is not in
  `artifacts/`. Per AGENTS.md the raw output backing a cited result belongs in
  the packet. It is a handful of lines — copy it in, or quote the fault line in
  `manifest.md`. It would also settle P2-G's "which file failed" question by
  inspection rather than by code reading.
- **P3-E — say that the manifest hashes are of committed blobs.** Two logs hash
  differently on disk than in git because of `core.autocrlf=input`. One line in
  `manifest.md` naming the verification command
  (`git cat-file blob HEAD:<path> | sha256sum`) stops the next reviewer from
  re-opening `c058e4c99`.
- **P3-F — no unit coverage for the suppression / presence-cache logic.**
  `suppress_ready_replica`, `ready_replica_is_suppressed` and the OID-matched
  clear in `invalidate_ready_replica_presence_cache` are pure backend-local state
  with no test; `traversal_replica.rs`'s test module still covers only the
  content hasher and the state machine. The `6bf805bdb` → `fcfc529e5` empty-catalog
  regression was caught by a 6-minute three-node run, which is not a repeatable
  gate. A `pg_test` over "empty catalog → no Ready", "suppress → declined",
  "catalog transition → re-eligible" is cheap and would also pin P1-B's fix.
- **P3-G — suppression survives a full relcache reset.** On sinval overflow
  PostgreSQL invokes relcache callbacks with `InvalidOid`, so
  `catalog_oid != 0 && catalog_oid == relation_oid` is false, the presence cache
  clears but `SUPPRESSED_READY_REPLICAS` does not. That backend then declines a
  repaired image for the rest of its session. Availability-safe (it degrades to
  owner traversal), but the conservative branch is to clear the set when
  `relation_oid == InvalidOid` as well.
- **P3-H — `ec_distann_guard_traversal_replica_mutation` should be
  `parallel_unsafe`.** It is labelled `parallel_restricted`, which promises it is
  safe in the leader under parallel mode; it now reaches `GetLatestSnapshot()`,
  which does `elog(ERROR, "cannot update SecondarySnapshot during a parallel
  operation")` when `IsInParallelMode()` (`snapmgr.c:353-361`). Narrow — a SELECT
  containing a Gather elsewhere in the plan — and it disappears if P1-B is fixed
  by dropping the guard, but the label is wrong either way. The `aminsert` and
  `ExecutorStart` call sites are not exposed: PG18 still requires
  `commandType == CMD_SELECT` for `parallelModeOK` (`planner.c:368-383`), so DML
  never enters parallel mode.
- **P3-I — the ENOSPC drill leaves global fixture state changed.** `dm_idx` stays
  in `task199_replica_enospc` and the tablespace is never dropped, so every later
  step in the run (storage, head, engagement) measures against a relocated index.
  Same filesystem here, so the r19 numbers are unaffected — but the drill runs
  near the end by luck of ordering, not by construction, and the disarmed
  provider is still loaded. Restore the tablespace at the end of the drill.
