## P1 finding

### P1-A — the fence drill does not exercise the ordering hazard it needs to

`scenario=concurrent_build_mutation_fenced ... build_lock=ShareRowExclusiveLock
mutation_sqlstate=55P03 inserted_rows=0`. `55P03` is `lock_not_available`, so
the mutation used a NOWAIT-style acquisition. That proves the two lock modes
conflict — which was never in doubt — and it skips the case F2 actually has to
survive:

1. build starts, replica row is `Building`, control index held
   `ShareRowExclusiveLock`;
2. a **blocking** INSERT reaches `ExecutorStart`, `guard_planned_result_relations`
   sees no `Ready` replica and returns cleanly;
3. the INSERT blocks in `ExecOpenIndices` behind the build's lock;
4. the build commits `Ready` and releases;
5. the INSERT proceeds and mutates the owner generation.

The design does survive this — the per-tuple `aminsert` guard fires at step 5 —
but nothing in this packet demonstrates it, and the ExecutorStart guard alone
would not. Add a drill with a waiting (non-NOWAIT) INSERT and assert either
`40001` at step 5 with the image left `Stale`, or the row present in the
replica. Without it, F2 is argued rather than shown, and a future
"remove the redundant aminsert guard" cleanup has no test standing in its way.

## P2 findings

### P2-A — the no-replica owner-path regression arm is missing everywhere

Every arm in this run is either replica-selected or the owner control inside the
same post-Task-199 binary. What is measured nowhere is what Task 199 costs a
deployment that never builds a replica: an extra SPI catalog join per scan, two
SPI queries per `aminsert` tuple, and one per DML statement (see packet 001
P2-1). Under this repo's A/B-per-change rule that is a required cell, not an
extra: packet 003 needs a before/after arm across the Task 199 commit boundary
for read latency at 10k/50k/100k and an insert/load-throughput comparison.

### P2-B — F1 is not closed, and the new drills are not yet in a packet

The packet correctly reports that actual DELETE and participant-tombstone
front-door evidence is missing. `f0f58e869` ("exercise delete mutation front
doors") and `a3932f6e4` ("inspect participant tombstone generation") land after
this packet's head SHA and are not represented in `manifest.md` or
`results.jsonl`. F1 stays open until those drills run on a normal release build
and their result lines are cited in a packet manifest.

### P2-C — two phase-3 cases have no evidence at all

Disk exhaustion during build and crash-after-control-commit are named in the
task's phase 3 and in AC3, and neither appears in this run. Neither is
substitutable by static reasoning: the first decides whether a failed build can
leave an eligible partial image (AC2), and the second decides whether the
durable `Stale` transition survives a coordinator crash between the control
commit and the caller's `40001`.

### P2-D — heterogeneous-ISA ordered identity needs a decision, not a deferral

Correctly reported as not establishable on a same-host three-node run. Graviton 4
is a named target for this project, so this cannot quietly disappear at
closeout: either run the ordered-identity check across ISAs, or record an
explicit stakeholder waiver in `plan/tasks/199-*.md` naming what is untested.
