# Task 222 packet 002 — contract and correctness: NOT DONE (4 P1, 3 P2)

Verdict: **NOT DONE.**

Scope of this review: the requested checkpoint `f088021ea`, plus the
uncommitted follow-on work in the branch working tree (`custom_scan.rs`,
`options.rs`, `payload_projection.rs`, `ec_distann_physical_lifecycle.rs`,
`bench/suite.rs`, `dev/distann_multicluster.rs`) and the ten untracked
`artifacts/pg18-focused-*.log` runs. Reviewing the committed SHA alone would
have reported "one focused test passes" and missed the eight crashed runs that
followed it. Where a finding is specific to one of the two states I say which.

The typed-API shape and the plan-time/begin-time split asked for by packet 001
are right and are done. The unresolved problem is the one the eight failing
logs are circling: **the payload mask and the target list the executor
actually evaluates are derived from two different trees, and nothing left in
the working tree guarantees they agree.**

## P1 — blocking

### 1. The working tree elides against a tree PG18 does not promise is final, and hard-errors instead of failing closed

`plan_custom_path` now calls `elide_ordering_only_target(tlist, ...)`
(`custom_scan.rs`, working tree) and raises `pgrx::error!` when the callback
`tlist` does not contain exactly one match. Both halves are wrong.

- The callback `tlist` is **not** the tree the executor evaluates. PG18
  `create_projection_plan` recurses into a projection-capable subpath with
  `CP_IGNORE_TLIST` (`createplan.c:2057`), `create_scan_plan` then sets
  `tlist = NULL` (`createplan.c:638`), and the caller **replaces**
  `plan->targetlist` after `PlanCustomPath` returns. Our path is
  projection-capable (`custom_scan.rs:527`,
  `is_projection_capable_path` → `createplan.c:7411`), so this is a live
  shape, not a hypothetical. The task file's own P1 bullet pre-registers
  exactly this fact — the working tree contradicts the contract that packet
  001 accepted.
- On any mismatch the code kills the query. Fail-closed for this contract
  means *include the vector in `Exact` and evaluate normally*; it never means
  `ERROR`. A planner shape variation must degrade to a wider payload, not to
  a failed user query.

Also note `create_customscan_plan` runs `replace_nestloop_params` over
`custom_exprs` **after** `PlanCustomPath` returns, while `build_path_tlist`
has already rewritten the tlist operand. At plan time the two sides of the
`pg_sys::equal(planned_value, query_value)` comparison in
`is_ordering_only_target` are therefore not guaranteed to be in the same
representation; at `BeginCustomScan` they are. This is the mechanical reason
the plan-time placement keeps producing "no match" on parameterized shapes,
and it is what finding 4 below was worked around rather than fixed.

**Required:** apply the exemption to the tree the executor will evaluate, and
make a non-match return `Exact(with vector)` / `AllColumns(...)`, never an
error.

### 2. Nothing re-establishes "vector omitted from the mask ⟺ nothing evaluates it"

`f088021ea` had this invariant: Begin derived the mask, and if the mask
omitted the ordering attnum it elided the projection or raised. The working
tree deletes that block and moves elision to plan time, where it fires
unconditionally on the proof and independently of the derived mask. There is
now no single point that holds both facts.

The consequence is already in the packet's own artifacts: eight runs, all
`SIGSEGV`, all with `DETAIL: Failed process was running: SELECT
pg_catalog.uuid_send(source_id)` — an *execution*, not an `EXPLAIN`
(`pg18-focused-external-elision-failed.log:56`,
`pg18-focused-forced-generic-failed.log:56`,
`pg18-focused-bound-param-proof-failed.log`). A distance `OpExpr` evaluated
against a payload attribute that was never shipped is the expected shape of
that crash. `pg18-focused-rescan.log` (16:48, newest) is a truncated compile
log, so there is no passing run of the current tree in the packet at all.

**Required:** one derivation point that owns both the mask and the projection
change, and a test that **executes** (not just `EXPLAIN`s) each covered shape,
including a second execution of the same cached plan and a run under
`plan_cache_mode = force_generic_plan`.

### 3. Both placements mutate a plan tree that is not ours to mutate

`elide_ordering_only_target` writes `entry.expr` in place. In `f088021ea`
that target was `(*custom_scan).scan.plan.targetlist` at `BeginCustomScan` —
i.e. the tree owned by the plan cache. A generic cached plan is re-entered on
every `EXECUTE`: the second Begin sees an entry that is already `NULL::real`,
`is_ordering_only_target` no longer matches it (it is a `Const`, not the
`OpExpr`), `elide` returns false, and the guard raises
`"exact mask omitted ordering attribute without one elidable projection"`.
Plan trees are read-only during execution; the plan-time placement in the
working tree only moves the mutation, it does not remove it (the entry is
still shared with the finished plan).

**Recommended shape:** `copyObject` the final target list into the
`CustomScanState`, rewrite the copy, and build the projection from the copy —
`plan->targetlist` is never written. That also removes the "stale ExprState"
problem cited in the working-tree comment, because the copy is made before
projection is assigned, not after.

### 4. Dropping PARAM_EXEC support removes a shipped capability to dodge the proof

Working tree, `is_query_value`: a `Param` is now only a query value when
`paramkind == PARAM_EXTERN`, and `custom_scan_candidate_index` additionally
bails on `rowMarks`/`hasForUpdate`. The new test asserts the resulting
fallback:

    "correlated PARAM_EXEC rescans must fall back instead of entering the
     unsupported distributed payload path"

That is a scope reduction, not a payload mask. Correlated LATERAL was an
explicitly designed-for shape — `DistannCustomScanExecState::query_expr_state`
carries the comment "evaluated lazily per (re)scan — a correlated LATERAL
Param is only bound per outer row" — and Task 222 P2 lists correlated LATERAL
and changed-Param rescan as **cases to exercise**, not to remove. A correlated
LATERAL query silently stops using the distributed path, which changes results
availability for remote-owned rows, not just latency.

If the ordering exemption cannot be proved per-rescan, the fail-closed answer
for those plans is "retain the vector / `AllColumns`", not "no CustomPath".
Land the exemption behind that, and keep the test asserting
`EcDistannDistributedScan` **is** used for LATERAL with correct per-rescan
results.

## P2 — must be resolved before the 100k A/B is meaningful

### 5. The benchmark control arm is not the control

`payload_projection_enabled()` is consulted only in
`payload_mask_for_custom_scan` (Begin). With
`ec_distann.benchmark_payload_projection = off`, the plan-time proof and
elision still run, so `all-columns-control` in
`reviews/task-222/003-isolated-100k/artifacts/task222-payload-projection-100k.json`
executes a plan whose ORDER BY projection is `NULL::real` — which is not the
pre-222 production behavior the entry gate names as the control. Either gate
the elision on the same GUC, or state the deviation in the packet
`manifest.md` before the run.

### 6. `Ordering Projection: elided|retained` can lie

`explain_custom_scan` derives that label from whether the mask omits the
ordering attnum, not from what happened to the target entry. In the working
tree the "ordering operand in qual" shape gets a plan-time elision (the proof
depends only on Query shape) while the mask retains attnum 2 — EXPLAIN will
print `retained` for a plan whose ordering entry is a typed NULL. Since this
line is the evidence P1 asks you to cite in the packet, derive it from the
actual target entry.

### 7. `FOR UPDATE` moved from hard error to silent fallback, undocumented

The new `rowMarks`/`hasForUpdate` early-out means a row-locking query now
plans as an ordinary scan instead of raising `EC_UNSUPPORTED_PROJECTION`. That
may well be the better behavior, but the task file Goal still says system
columns "keep the existing plan-time `EC_UNSUPPORTED_PROJECTION` error", and
packet 001 finding 2 made that taxonomy binding. Record the change in the task
file, or revert it. (The two existing system-column tests — `ctid` projection
and `xmin` qual — still assert the error and still pass; they carry no
rowmark.)
