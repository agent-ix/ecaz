## Required

### 1. Pre-register the ordering-operand (junk sort key) rule — it decides the headline

The plan's premise is "the standard latency query projects only `id`". That is
true at the SQL level and almost certainly false at the executor-plan level.
For `SELECT id FROM t ORDER BY embedding <-> $q LIMIT k`, the ORDER BY operand
enters the rel's `reltarget`/scanjoin target as a junk requirement, and
`plan_custom_path` receives that tlist and installs it verbatim
(`custom_scan.scan.plan.targetlist = tlist`, `custom_scan.rs:515`;
`CUSTOMPATH_SUPPORT_PROJECTION` is set at `custom_scan.rs:455`, so the planner
hands the real tlist, not just the visible projection). A mask derived from
"target list + quals + rechecks" as scoped will therefore prove `embedding`
(and plausibly `source real[]`, if referenced) as *required* and ship it —
leaving the dominant vector bytes of the 123,076.8 B/scan in place. The
task's own P0 rationale (4 columns → id-only) is unreachable under the plan's
stated derivation without an additional, explicitly argued rule.

Required plan additions:

- **P1 must open by capturing the actual executor tlist** for the standard
  latency query (EXPLAIN VERBOSE + the emitted attnum evidence) so the
  contract is written against the real trees, not the SQL text.
- **Pre-register whether attributes referenced *only* by resjunk sort entries
  are excluded**, with the proof obligation stated: the entry is resjunk, its
  ordering is already claimed by the scan's pathkeys
  (`custom_path.path.pathkeys = sort_pathkeys`, `custom_scan.rs:454`), and no
  Sort/MergeAppend/upper consumer reads it. If that proof cannot be made
  mechanical, the honest outcome is a mask of `{id, embedding}` and the plan's
  expected win shrinks to the non-vector columns — say so in Why/Goal.
- If the exclusion is adopted, **add the adversarial correctness cases it
  creates**: `SELECT id, embedding <-> $q FROM ...` (distance is a visible
  output, vector must ship), `ORDER BY` operand also referenced by a qual, and
  rescan with a changed correlated param.

Without this section, P2/P3 risk measuring a mask that differs from control by
one small column and reporting a null result that says nothing about MAT-28/29.

### 2. System-column "fallback" contradicts landed fail-closed behavior

Goal and P1 say system-column shapes "fall back to the current all-column
behavior". Landed code **errors** instead: `reject_unsupported_system_columns`
raises `EC_UNSUPPORTED_PROJECTION` at both path time (`custom_scan.rs:426`)
and plan time (`custom_scan.rs:498`), precisely because all-column shipping
cannot reconstruct a remote row's `ctid`/`xmin` — a fallback would evaluate
them against a NULL virtual-slot field (the hazard documented at
`custom_scan.rs:268-274`). As written, the plan would *regress* a hard error
into silently wrong answers. Revise the fail-closed taxonomy:

- whole-row Var (`varattno == 0`) and any unproved shape → all-column
  fallback (correct: the scan slot uses the relation descriptor, so a
  whole-row datum composes correctly from a fully shipped row);
- system columns (`varattno < 0`) → **keep the existing plan-time error**.

### 3. Name the concrete derivation inputs, and where derivation runs

"Target lists, executor quals, recheck expressions, and other executor-visible
expressions" is not yet a contract. This scan has exactly three trees:
`plan.targetlist`, `plan.qual` (both installed at `custom_scan.rs:515-516`;
`custom_scan_tlist` is NULL and `scanrelid` is set, so Vars keep base-rel
attnos after setrefs), and `custom_exprs[0]` (the ORDER BY query-value
expression, Const/Param only — the contract should *assert* it contains no
relation Var and fail closed if it ever does). There is no separate recheck
tree: EPQ re-evaluates `plan.qual`, and the multi-window qual-rejection path
(011/020-P1) consumes the same quals. Pre-register that enumeration, and state
**where the mask is derived** — plan time in `plan_custom_path` (where
`root`/`parse` context exists for the rule in item 1) versus
`begin_custom_scan` — since the choice constrains what item 1 can prove.

### 4. Define the mask's exported shape — Tasks 223/229 consume it as an API

Task 223 encodes "Task 222's proven attribute mask" into its payload contract;
Task 229 selects the sidecar "only when every required attribute is covered"
and must distinguish *proved-exact* masks from *fail-closed all-column* masks
— an all-column fallback and a genuinely wide query are the same attnum set
but must behave differently downstream. P1 currently promises only
benchmark-only log lines. Add to the pre-registered contract a typed, reusable
surface — e.g. `Exact(attnums)` vs `AllColumns(FallbackReason)` — as the
deliverable, not logic inlined into `build_payload_metadata`
(`custom_scan.rs:836`). With that, 222 is a sound gate for 223 and 229; the
sequencing itself (223 re-attributes against the refreshed denominator, 229
consumes the mask, both gated on 222's disposition) is correct and I have no
ordering findings.
