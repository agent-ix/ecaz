# Reviewer feedback: Task 67 packet 037 (cloud bench SIMD env propagation)

## Verdict

Accept with follow-up. The narrow runner fix is correct and directly
addresses the byte-identical-suites root cause flagged in packet 036
finding #2: `ECAZ_SIMD` is now exported into the remote `ecaz bench
suite` process, not just into PostgreSQL's systemd environment. The
unit test pins both surfaces. Diff is scoped to
`crates/ecaz-cloud/src/commands/bench.rs` only — no drift.

The follow-ups below do not block this packet but should be addressed
in the rerun packet that supersedes 036's scalar/auto numbers.

## Findings

### 1. Root-cause fix is correct (OK)

`remote_suite_script` now prepends `export ECAZ_SIMD=<mode>;` to the
remote `ecaz bench suite run` command line when `--simd-mode` is set
(crates/ecaz-cloud/src/commands/bench.rs:197-205). Together with the
pre-existing PostgreSQL systemd `set-environment ECAZ_SIMD` block at
line 227, both the in-process sidecar-rerank kernel selection (CLI
process) and any in-PG kernel selection (PostgreSQL process) now see
the same mode. This is what packet 036 finding #2 needed.

### 2. Shell-escape is reused for env value (OK on injection)

The forwarded value goes through `shell_escape` (line 199), the same
single-quote escaping helper used for paths elsewhere in this file.
Injection surface is no worse than the rest of the SSM script.

### 3. Test coverage is narrow and load-bearing (OK)

`remote_suite_script_exports_simd_for_cli_and_postgres` asserts both:

- `sudo systemctl set-environment ECAZ_SIMD='scalar'` (PG side), and
- `export ECAZ_SIMD='\''scalar'\''` immediately before the
  `ecaz bench suite run` invocation (CLI side).

That second assertion is exactly the bit that was missing before
this change, so the test would have failed on the pre-fix code. Good
regression guard.

### 4. Per-suite control is still env-only, not in `SuiteConfig` (MEDIUM, follow-up)

The review focus asked whether the SIMD mode is "in-band, recorded
in SuiteConfig JSON, not just env." It is not. `--simd-mode` is a
flag on `ecaz cloud bench` that injects `ECAZ_SIMD` into the remote
shell; the `SuiteConfig` JSON itself has no field that records which
kernel mode was selected. Consequence: the resulting
`suite-manifest.json` checked into a packet will not on its own
disclose whether scalar or auto was used — that has to be inferred
from the wrapping cloud-bench invocation in the manifest's re-run
section.

This is the same class of issue as `feedback_access_method_naming`
(naming the access method explicitly in baselines). Suggest, as a
follow-up (not a blocker on this packet):

- have `bench suite run` capture `ECAZ_SIMD` (or the resolved kernel
  family) into `suite-manifest.json` at run time so downstream
  auditors do not have to read the cloud-bench shell to know which
  kernel ran; and/or
- accept `simd_mode` as a top-level `SuiteConfig` field so the JSON
  config is self-describing.

Either route lets a packet's `artifacts/manifest.md` cite a single
canonical source for the kernel mode.

### 5. No validation of `--simd-mode` value (LOW)

`simd_mode: Option<String>` is forwarded verbatim into `ECAZ_SIMD`
with no allow-list check (e.g. `scalar` | `auto` | `avx2` | `neon`).
A typo like `--simd-mode scaler` will silently run whatever the
default fallback resolves to on the remote host, and the packet
evidence (only `artifacts/manifest.md` says `scalar`) will not catch
it. Cheap fix: parse into an enum or assert against a known set
before exporting. Not a blocker, but worth doing before the 036
rerun lands so a typo cannot quietly invalidate another scalar/auto
comparison.

### 6. Re-run section is reproducible (OK)

`artifacts/manifest.md` includes a concrete `ecaz cloud bench
--simd-mode <mode> --config ... --suite ...` template for both
scalar and auto. That satisfies `feedback_benches_must_be_repeatable`
for this packet. Note for the rerun packet: those `<packet>` and
`<scalar-suite-name>` placeholders must be filled in with the actual
checked-in config paths when used.

### 7. NFR-007 manifest fields present (OK)

`artifacts/manifest.md` records head SHA, timestamp, task bucket,
lane, and validation commands with results. The "not a benchmark
run" disclaimer is appropriate — this is a runner fix, not a
measurement. The two validation logs under `artifacts/` are the
cited evidence and they match the claimed results.

### 8. No drift outside cloud bench (OK)

`git show --stat bcd8e29c6` is a single-file change to
`crates/ecaz-cloud/src/commands/bench.rs`. No other crate touched,
no `src/quant/**` collateral, no spec/test drift.

### 9. Packet 036 scalar/auto numbers must be marked superseded (follow-up)

The packet correctly states under "Follow-up" that packet 036's
100k scalar/auto numbers should be replaced. When the rerun packet
lands, also drop a note into packet 036's manifest or a feedback
file pointing at the new packet, so a future auditor walking the
036 artifacts is not misled by the original (byte-identical)
numbers.

## What is needed to clear this packet

Nothing blocking. Land the rerun in a new packet that:

1. Uses this fixed `ecaz cloud bench --simd-mode {scalar,auto}` wrapper.
2. Cites `ECAZ_SIMD` value in the manifest alongside per-host CPU
   attestation (finding 036 #6).
3. Updates packet 036's record so the superseded numbers are not
   silently treated as Task 67 evidence.

Items #4 and #5 above (record `simd_mode` in `SuiteConfig` JSON,
validate the flag value) are nice-to-have hardening for the next
runner change, not gates on this packet.
