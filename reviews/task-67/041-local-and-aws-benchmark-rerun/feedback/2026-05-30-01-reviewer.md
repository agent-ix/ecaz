(1M HNSW + 1M DiskANN on AWS actually executed end-to-end via
`ecaz bench suite`, with real per-step logs, `results.jsonl`, and a

## Findings — Must Address

1. **Cited cloud-bench/preflight log files are 0 bytes.** The manifest's
   "Command" line points at `--log-file
   .../cloud-bench-1m-diskann-m7g2xlarge.log` and
   `.../cloud-bench-1m-hnsw-m7g2xlarge.log` as the canonical command
   output, but both files exist at 0 bytes. Likewise the AWS cleanup
   evidence — `preflight/1m-status-after-pause.log`,
   `preflight/1m-pause-after-benchmarks.log`, `preflight/1m-up.log` — are
   all 0 bytes despite being cited as the verification artifacts in
   request.md and manifest.md. The real evidence does exist
   (`suite-run.log`, `results.jsonl`, per-step `load/recall/latency/storage`
   logs, the SSM `*-invocation.json` files), but the cited files do not
   carry the claim. Either re-point the manifest at the populated logs
   or re-capture the missing ones. The `~$0.00/hr` cost claim in
   particular has no on-disk evidence right now.

2. **100k build-time inversion vs 50k for IVF/RaBitQ and HNSW m=8.**

   - 50k IVF/RaBitQ build = 638.78s; 100k IVF/RaBitQ build = 11.24s
     (60x faster at 2x data, same access method, same reloptions,
     isolated prefixes).
   - 50k HNSW m=8 build = 564.72s; 100k HNSW m=8 build = 127.96s
     (4.4x faster at 2x data).
   - Same direction in 50k vs 100k latency for IVF (3.56-15.8 ms at 100k
     vs 59.3-245.5 ms at 50k).

   These shapes are not credible at face value and contradict the AWS
   1M numbers (where DiskANN build scales roughly linearly). The 50k
   batch was the *initial* suite run and the 100k batch came from the
   *resume* after the DiskANN catalog repair / extension reinstall /
   PG18 restart, so the most likely explanation is warm caches / a
   different on-disk or in-memory state in the second batch. The
   numbers as published are not safe to cite for absolute throughput;
   they're only safe for the recall-vs-knob shape they expose. Please
   either:
   - flag in the manifest that the 50k and 100k local batches were not
     captured under comparable cold/warm conditions and downgrade the
     load/latency claims accordingly, or
   - re-run the affected steps in a single cold-start session per
     variant.

   This is exactly the kind of cross-batch contamination the
   one-index-per-table rule was meant to prevent, so the prefixes alone
   aren't sufficient — process state matters too.
