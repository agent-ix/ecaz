# Verdict: Approve

The AVX-512 bits=1 mask-decode kernel is correctness-safe. Bit-to-mask
packing preserves the scalar `(code[d/8] >> (d%8)) & 1` semantics exactly,
`_mm512_mask_blend_ps` argument order encodes the RaBitQ sign convention
correctly (bit=1 -> `lut[1]` / pos, bit=0 -> `lut[0]` / neg), the
`target_feature` gate is now tight (`avx512f` only, matching
`has_avx512_bits1()` after the simd.rs change), tail handling is unchanged
and exercised, and the differential test still passes against the scalar
reference. AWS Intel measurement shows identical recall scalar vs auto at
all nprobe values, which is strong empirical confirmation. Latency gate
miss is acknowledged in the request and is not a correctness issue.

## Findings

### F1 (verified) — Packet 006 F1 gate concern is resolved

Prior feedback observed the bits=1 kernel was gated on
`avx512f,avx512vpopcntdq` even though no VPOPCNTDQ intrinsic was used.
This packet tightens the gate at two layers:

- Kernel `target_feature` now `avx512f` only
  (`9989a1d87:src/quant/rabitq.rs:2714`, `:2874`).
- `has_avx512_bits1()` now just `self.avx512f`
  (`src/quant/simd.rs:156-158`).

Skylake-X / Cascade Lake hosts with plain AVX-512F will now select the
SIMD path instead of falling back to scalar. The dispatch precondition
`ctx.bits1_byte_lut.is_some()` is unchanged
(`9989a1d87:src/quant/rabitq.rs:1789, 1817`); note the body no longer
reads `byte_lut` (parameter renamed to `_byte_lut`), so the
`is_some()` guard is now strictly a vestigial cheap presence check.
Harmless, but if a follow-up wants to fully decouple bits=1 SIMD from
`bits1_byte_lut` construction it could drop that condition.

### F2 (verified) — Sign convention preserved

`_mm512_mask_blend_ps(k, a, b)` returns lane = `b` where mask bit set,
`a` where clear. Call sites are
`_mm512_mask_blend_ps(mask, neg_v, pos_v)`
(`9989a1d87:src/quant/rabitq.rs:2761-2762, 2890-2893`) with
`neg_v = lut[0]`, `pos_v = lut[1]`. So lane = `lut[1]` when mask bit set,
`lut[0]` when clear. The scalar tail at 2796-2799 does
`if bit == 1 { pos } else { neg }`. Convention matches. The scalar
reference `sum_query_dequant_scalar` uses `(code[i/8] >> (i%8)) & 1`
to index `dequant_lut` (where `lut[1] = +sqrt(d)/256`,
`lut[0] = -sqrt(d)/256`), so production behavior is preserved.

### F3 (verified) — Bit-to-mask packing matches `(code[d/8] >> (d%8)) & 1`

For a 16-lane chunk covering dims `[base*8 .. base*8+16]`:

- `mask0 = u16::from_le_bytes([code[base], code[base+1]])`
  (`9989a1d87:src/quant/rabitq.rs:2745-2748`).
- `from_le_bytes` places `code[base]` in low byte and `code[base+1]`
  in high byte, so u16 bit `i` (for `i in 0..8`) is bit `i` of
  `code[base]`, and bit `i` (for `i in 8..16`) is bit `i-8` of
  `code[base+1]`.
- `__mmask16` bit `i` controls lane `i` of `_mm512_mask_blend_ps`,
  and `q0` lane `i` is loaded from `query_rotated[dim_index + i]`
  where `dim_index = base*8`.
- Therefore lane `i` mask bit = `(code[(dim_index+i)/8] >> ((dim_index+i)%8)) & 1`.
  Exact match with scalar.

The pair kernel applies the same packing per code stream
(`9989a1d87:src/quant/rabitq.rs:2867-2880`).

### F4 (verified) — Tail handling

Main loop processes 32 dims per iteration; remainder (`dim < 32` or
`dim % 32 != 0`) is handled by the scalar tail loop
(`9989a1d87:src/quant/rabitq.rs:2793-2799, 2912-2919`). The
differential test covers
`{1, 7, 8, 15, 16, 31, 32, 33, 64, 95, 96, 1536}`
(see `git show 9989a1d87:src/quant/rabitq.rs` test at 6146..),
exercising tail-only, aligned-boundary, tail+body, and large
multi-iter shapes. Pair test covers
`{1, 7, 8, 15, 16, 31, 32, 33, 64, 95, 96, 1536}` similarly.

### F5 (verified) — No regression to bits=4 / bits=8 / bf16 paths

The diff for `9989a1d87` is bits=1-scoped: removes the
`bits1_query_byte_sums` plumbing (constructor, struct field, dispatch
branches, batch dispatch, scalar fallback, dedicated unit test), and
swaps only the AVX-512 bits=1 single + pair kernel bodies. The AVX2
bits=1 kernel still reads `byte_lut`. bits=4 / bits=8 /
bf16 kernels and gating helpers (`has_avx512_bits4`,
`has_avx512_bits8`, `has_avx512_bits4_bf16`) are untouched
(`src/quant/simd.rs:161-169`). Differential tests for bits=4 and
bits=8 remain in place.

### F6 (verified) — Empirical correctness on real Intel host

`artifacts/manifest.md` records identical recall@10 across scalar and
auto at all measured nprobe values (16/32/64) on the 10k real corpus.
Local `cargo test -p ecaz quant::rabitq` reports 46 passed / 0 failed
(`artifacts/preflight/validation.log`). Suite audits pass for both
configs. This is good independent evidence the mask-decode kernel
produces the same scores as the scalar reference on production
fixture geometry.

### F7 (observation, non-blocking) — Performance gate

Mean latency on Intel 10k: scalar 2.59 / 4.04 / 7.00 ms vs auto
1.48 / 1.95 / 2.80 ms, i.e. 1.75x / 2.07x / 2.50x. The Task 67 primary
bits=1 speed gate is still not satisfied; the request explicitly
flags this and does not claim completion. No correctness implication.
The post-packet revert chain (47fed5ba2 sign-flips, 5c51abfc8 revert,
12ed902df restore byte LUT) shows the coder is actively iterating on
this; that is out of scope for this packet's review.

### F8 (minor, nit) — `_byte_lut` parameter now unused in AVX-512 kernels

`sum_query_dequant_avx512_bits1` and `..._pair` now accept `_byte_lut`
but do not read it
(`9989a1d87:src/quant/rabitq.rs:2718, 2877`). Production callers still
hold and pass the table because the AVX2 path needs it, so the
signature is justifiable. If the mask-decode approach sticks, a
follow-up could drop the parameter from the AVX-512 entry points to
reduce noise. Non-blocking.
