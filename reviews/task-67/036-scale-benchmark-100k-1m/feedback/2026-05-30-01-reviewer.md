# Reviewer feedback: Task 67 packet 036 (scale benchmark 100k/1m)

## Verdict

Request as stated (configs staged, no results claimed) is broadly fine,
but the on-disk artifacts contradict it and the scalar-vs-auto pair is
not a real comparison. Block on the questions below before treating
the 100k numbers as Task 67 evidence; the 1M coverage is not delivered.

## Findings

### 1. request.md misstates packet state (HIGH)

`request.md` says "Configs are staged for audit and execution. No AWS
benchmark result is claimed yet in this packet." But the packet
contains executed `suite-run.log`, `suite-manifest.json` (dry_run:
false), and 17-line `results.jsonl` files for both 100k-scalar and
100k-auto. If those runs are review-relevant, request.md must say so
and cite the headline numbers; if they are not, they should not be
checked in here. Right now the reviewer has to guess which.

### 2. "scalar" vs "auto" suites are byte-identical at the kernel layer (HIGH)

The two suite JSONs differ only in `name`, `artifact_dir`, and the
load/sidecar `prefix`. No `ecaz.simd_mode` (or equivalent) GUC, env
var, or CLI flag is set anywhere in either config to force the scalar
path. `suite-run.log` confirms the emitted commands are otherwise
identical. The matching results bear this out:

- scalar `sidecar_score_p50`: 0.022-0.023 ms
- auto   `sidecar_score_p50`: 0.022-0.026 ms

These are within run-to-run jitter. The "scalar vs auto" framing is
not measured by this packet. Either:
- wire a kernel-mode selector through `corpus load`/`bench
  sidecar-rerank` and into `SuiteConfig` (extend the suite runner per
  CLAUDE.md, do not script around it), then re-run; or
- drop the "scalar" suite and keep only one 100k baseline.

### 3. Suite default `bits: 4` vs variants `rabitq8*` (MEDIUM)

`defaults.bits = 4` while the sidecar `variants` are bits8 family
(`rabitq8`, `rabitq8ls`, `rabitq8c3`, `rabitq8c4`) and the index
reloption is `quant_bits=1`. Three different "bits" values in one
config is confusing for an auditor. Document in manifest.md what each
controls (IVF storage quant vs sidecar rerank kernel width vs load
codepath) or set `bits` to match the surface under test (8).

### 4. 1M coverage not delivered (HIGH for the stated scope)

- `artifacts/1m-hnsw/cloud-bench-1m-hnsw-on-10k-intel.log` is 0 bytes.
- `artifacts/1m-diskann/` contains only `suite-dry-run-*`.
- `preflight/1m-up.log` failed on `--confirm-cost`.
- `preflight/1m-up-confirmed.log` failed terraform apply (likely the
  VPC limit referenced by the empty `1m-down-after-vpc-limit.log`).

No 1M run produced data. The packet should explicitly state this in
request.md and manifest.md ("1M runs blocked on VPC limit; configs
staged only") rather than listing the 1M JSONs as scope items without
calling out that they did not run. As-is this fails
NFR-007 honesty about evidence.

The original review focus — does the SQL-headline flatness change at
1M, does bits8 reach 4x at scale — is therefore unanswered. State that
explicitly so the gate can be evaluated correctly.

### 5. manifest.md missing required NFR-007 fields (HIGH)

`artifacts/manifest.md` has:
- head SHA: pending
- timestamp: pending
- no command lines
- no host attestation (this matters: `/var/run/postgresql` could be
  the AWS Intel host or the dev box; the auditor cannot tell from the
  packet)
- no key result lines extracted for request.md to cite
- no rerun/repro section

CLAUDE.md "Review, Test, Benchmark, and Artifact Logs" lists head SHA,
command, timestamp, isolation, and key result lines as required. None
of them are present. The 100k runs already exist; backfill them.

### 6. Host attestation per `feedback_access_method_naming` (MEDIUM)

Nothing in the packet pins the host or CPU family. The 100k-scalar
and 100k-auto suite manifests just record `host: /var/run/postgresql`.
For Task 67 SIMD work this is the load-bearing detail (Intel vs
Graviton selects different kernels). Record `cpuid`/`uname -m` and
the cloud profile name (`10k-intel`) in manifest.md alongside the run.

### 7. Per `feedback_benches_must_be_repeatable` (MEDIUM)

No "How to re-run" section in manifest.md. For each of the four
suites, the exact `ecaz bench suite ...` invocation, the
`--confirm-cost` value, and any pre-conditions (corpus snapshot
identifier, kernel-mode env) should be in the manifest so an outside
reviewer can reproduce without scrollback.

### 8. Index-isolation rule satisfied (OK)

Each suite uses a unique `prefix` (`task67_r8head_100k_scalar` vs
`_auto`), so the per-variant tables are not shared across suites.
This satisfies `feedback_index_isolation_rule`. Note for the auditor:
within a single suite, the four sidecar variants share the same IVF
candidate table (which is the intended Task 67 sidecar comparison
shape), so this is fine.

### 9. SQL-headline flatness confirmed at 100k (OK, informational)

Across all 24 100k rows, `sidecar_score_p50` is 0.022-0.026 ms while
`candidate_sql_p50` is 11.9-21.6 ms — scoring is 0.1-0.2% of total
bound. This is consistent with the packet 027 10k finding: SQL
headline drowns the SIMD score path. Whether this still holds at 1M
remains unmeasured (finding 4). Until 1M data lands, the gate cannot
honestly be evaluated at scale.

### 10. Comparators

No vchord/pgvectorscale runs were attempted in this packet, which is
correct per `feedback_no_unchanged_comparator_runs`.

## What is needed to clear this packet

1. Fix request.md to accurately describe what ran and what did not.
2. Either implement and verify the kernel-mode selector so
   scalar-vs-auto is a real comparison, or drop the "scalar" suite.
3. Backfill manifest.md with head SHA, timestamp, host/CPU
   attestation, exact commands, isolation note, key result lines, and
   a re-run section.
4. State 1M-blocked-on-VPC-limit honestly, or land actual 1M
   results.
5. Reconcile the three "bits" values in the 100k configs.
