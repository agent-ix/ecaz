# Reviewer Feedback — Task 67 x86 bits=4 batch

**Verdict:** Approve with one test-coverage gap noted.

## Scope and dispatch

- Dispatch wiring is correct and narrow: `estimate_ip_batch_impl`
  routes `Avx512Bits4` -> `estimate_ip_batch_avx512_bits4`
  (src/quant/rabitq.rs:4145-4157) and `Avx2Bits4` ->
  `estimate_ip_batch_avx2_bits4` (src/quant/rabitq.rs:4158-4171),
  both under `cfg(target_arch = "x86_64")`. Existing bits=1,
  bits=8, NEON arms are unchanged. `Avx512Bf16Bits4` is
  intentionally not wired into batch and falls through to
  scalar — same pattern as prior packets; out of scope here.
- Public batch API shape (slab in, code_len, &mut [f32] out)
  matches the Task 66 Slice D contract used by NEON
  bits=1/bits=8 batched paths and the AVX-512/AVX2 bits=1
  and bits=8 batched paths landed earlier in this task.
- Task 66 Slice D itself does not specify a NEON bits=4
  batched kernel (only bits=1 and bits=8), so there is no
  NEON bits=4 batched counterpart to drift from. The packet
  correctly matches the *API shape*, not a NEON bits=4 sibling.

## Nibble-unpack correctness in pair kernels

- AVX-512 pair (src/quant/rabitq.rs:3353-3450): per loop step
  processes 16 dims from 8 code bytes per candidate, unpacking
  low nibble then high nibble. Decode order
  (`lut[b & 0x0F]`, `lut[b >> 4]`) matches the scalar
  `read_level(code, dim_index, 4)` convention and matches the
  single-candidate AVX-512 bits=4 kernel
  (src/quant/rabitq.rs:3176-3193) byte-for-byte.
- AVX2 pair (src/quant/rabitq.rs:3458-3556): same per-step
  cardinality (16 dims) with two 8-lane FMA accumulators per
  candidate, sharing the two query loads q0/q1 across code0
  and code1. Matches single-candidate AVX2 bits=4 ordering
  (src/quant/rabitq.rs:3302-3331) exactly.
- Tail loop in both pair kernels uses
  `read_level(code, dim_index, 4)` (src/quant/rabitq.rs:3438,
  3548), so partial-stride tails preserve scalar decode order
  for both candidates.

## Partial-batch tail handling

- Both `estimate_ip_batch_avx512_bits4` and
  `estimate_ip_batch_avx2_bits4` consume pairs via
  `chunks_exact_mut(2)` and handle an odd-count remainder by
  calling the existing single-candidate kernel and
  `finish_scalar_only_estimate`. This is the same scalar
  fallback used by the bits=8 and bits=1 batch arms — correct.

## Unsafe / target_feature boundary

- New `_pair` kernels carry
  `target_feature(enable = "avx512f,avx512bw")` and
  `target_feature(enable = "avx2,fma")`. Outer batch wrappers
  inherit the same feature gates. Runtime detection occurs in
  `select_query_dequant_kernel` / `select_x86_query_dequant_kernel`
  before reaching the unsafe call; SAFETY comments at the call
  sites cite the runtime gate (src/quant/rabitq.rs:4146,
  4160).
- `get_unchecked` reads are bounded by the
  `dim_index + 16 <= dimensions` loop guard and the
  caller-asserted `ceil(dimensions * 4 / 8)` code length
  documented on the `# Safety` clauses; consistent with the
  single-candidate kernels.

## Test coverage — one gap

- `bits4_batch_estimator_matches_scalar_order`
  (src/quant/rabitq.rs:4650) uses 6 candidates with dim=33.
  - dim=33 = 32 (two pair iterations of 16) + 1, so the
    scalar tail inside each pair kernel *is* exercised.
  - 6 candidates is even, so `chunks_exact_mut(2)` produces
    3 pairs and an empty remainder. The
    `out_chunks.into_remainder().first_mut()` odd-candidate
    fallback at src/quant/rabitq.rs:3884-3888 and 3916-3920
    is **not** covered by the new test, even though the
    request lists "odd-cardinality fallback" as a review
    focus item.
  - This is non-blocking — the fallback path simply
    delegates to the already-tested single-candidate kernels
    + `finish_scalar_only_estimate`. Suggest adding (in a
    follow-up if convenient) either an odd `candidates.len()`
    in this test or a sibling test exercising 3 or 5
    candidates to lock the dispatch shape.
- Existing single-candidate AVX-512/AVX2 bits=4 differential
  tests (src/quant/rabitq.rs:5944, 5957) cover decode
  correctness, which is what the pair kernels reuse, so the
  gap above is bounded.
