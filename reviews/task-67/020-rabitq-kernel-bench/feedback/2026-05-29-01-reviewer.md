# Review: Task 67 packet 020 — RaBitQ kernel bench command

Commit under review: `2edbb887c Add RaBitQ kernel bench command`
(`crates/ecaz-cli/src/commands/bench/rabitq_kernel.rs` +
`crates/ecaz-cli/src/commands/bench/mod.rs`)

Verdict: **changes requested — block**. The bench, as written, does not
exercise the x86 SIMD single-shot scoring kernels at all; the packet has
no `request.md` / `artifacts/manifest.md`; no AVX-512 host evidence is
attached (local host is AVX2-only i9-10900K, the configured `auto/` and
`scalar/` artifact directories are empty, and the preflight cloud-install
log is zero-byte).

## Blocking findings

### B1. "single" rows measure scalar — not SIMD

`crates/ecaz-cli/src/commands/bench/rabitq_kernel.rs:113` and `:122` call
`prepared.estimate_ip_scalar_only(...)` inside `bench_single`. That
function (`src/quant/rabitq.rs:911 estimate_ip_scalar_only` →
`estimate_ip_scalar_only_impl`) is explicitly the scalar reference path
and bypasses the SIMD dispatcher in `estimate_ip_batch_impl`
(`src/quant/rabitq.rs:4098`). Consequence: with `backend=avx2+fma`
recorded in `artifacts/local/rabitq-kernel-auto-local.log:1`, every
`single` row in that log is still running the scalar kernel, identical to
the `backend=scalar` run.

This is visible in the data: AVX2 `bits1 single` ≈ 9.34 µs vs scalar
`bits1 single` ≈ 3.27 µs (`rabitq-kernel-auto-local.log:6` vs
`rabitq-kernel-scalar-local.log:6`). They differ only because input
generation / RNG seeding differs across runs, not because SIMD ran.
A SIMD bench whose AVX2 row is 3x slower than scalar for bits1 is, by
inspection, not measuring SIMD.

The bench is purported to be a "RaBitQ kernel bench" for the x86 SIMD
work in 001–019 of this bucket. As written, only the `batch` rows
(`bench_batch` → `estimate_ip_batch`) reach the SIMD dispatcher. Single-
score callers (the hot rerank path in `ec_diskann/ec_ivf`) are not
covered at all.

Fix: drive `bench_single` through whatever single-shot entrypoint
actually dispatches to SIMD (`PreparedEstimator::estimate_ip` /
`estimate_ip`, see `src/quant/rabitq.rs:551` / `:890`), and keep a
labeled `scalar` variant that explicitly calls `estimate_ip_scalar_only`
for comparison. Don't silently substitute the scalar path for the SIMD
path.

### B2. bits4 batch is silently skipped

`rabitq_kernel.rs:69`: `if matches!(variant.bits, 1 | 8)` excludes the
bits4 batch. But the dispatcher has both `estimate_ip_batch_avx512_bits4`
(`src/quant/rabitq.rs:3867`) and `estimate_ip_batch_avx2_bits4`
(`:3899`). The packet bucket spans bits1/4/8 work (packets 002–007);
bits4 is the one that hardens the AVX-512 / AVX2 routes, and is missing
from coverage. Either include it or document why it is excluded; the
current implementation just drops bits4 batch silently.

### B3. Per-backend isolation is by env mutation, not separate binaries

There are two suite JSONs (`task67-rabitq-kernel-auto-suite.json`,
`task67-rabitq-kernel-scalar-suite.json`) but they invoke the same
`bench rabitq-kernel` command with no flag to force backend. The scalar
log reports `backend=scalar` (`rabitq-kernel-scalar-local.log:1`), which
means the runner is relying on an out-of-band env var (e.g.
`ECAZ_FORCE_SIMD_BACKEND` or similar) that is neither captured in the
suite JSON nor in the packet docs. Per
`feedback_benches_must_be_repeatable`, the re-run recipe must be
self-contained. Either:

- add an explicit `--backend {auto,scalar,avx2,avx512}` flag to
  `bench rabitq-kernel` and put it in the suite JSON, or
- record the exact env var name + value in the suite JSON's `env`
  field and in a packet-root manifest.

As written, an outside reviewer reading only the packet cannot reproduce
the scalar lane.

### B4. Per-backend (AVX-512 vs AVX2) split is not exercised

`backend=avx2+fma` in the auto log is the runtime dispatch result on
the AVX2-only host (`artifacts/local/cpu-features.log:25`, i9-10900K,
no `avx512f` flag). There is no AVX-512 run in this packet. Without an
AVX-512 run the packet cannot claim to cover the AVX-512 batch kernels
(`estimate_ip_batch_avx512_bits1/4/8`, `src/quant/rabitq.rs:3784/3867/
3931`) added in this bucket. The configured `artifacts/auto/` and
`artifacts/scalar/` directories (per the suite JSONs) are empty. The
intended Intel cloud run (packets 015–017) does not appear to have
produced output yet — `artifacts/preflight/cloud-install-2edbb887c.log`
and `artifacts/preflight/cloud-resume.log` are both zero-byte.

The packet needs at least one Intel AVX-512 host run before the kernel
bench can serve as evidence for the bits1/bits4/bits8 AVX-512 work.

### B5. Packet hygiene: no `request.md`, no `artifacts/manifest.md`

Per `CLAUDE.md`:

> Feedback Files / Review, Test, Benchmark, and Artifact Logs ...
> Measurement packets must include `artifacts/manifest.md` as the
> packet-local source of truth for artifact metadata.

This packet has neither `request.md` nor `artifacts/manifest.md`. There
is no head SHA, no command record, no isolation note, no statement of
what `request.md` would cite. Reviewers had to dig out the commit SHA
from `git log`. Add both before re-requesting.

## Non-blocking observations

- N1. **Mixed code+measurement scope** — the packet is a code commit
  (the bench tool itself) plus measurement runs against it. Per
  NFR-007, that mix stays under `reviews/task-67/...` (this packet) and
  should cite a `benchmarks/<topic>/` packet for the pure measurement
  evidence. Once Intel runs land, copy/move the kernel measurement
  matrix into `benchmarks/rabitq-kernel/` and reference it from
  `request.md`.
- N2. **Runner reproducibility** — both suites use `bench rabitq-kernel
  --dim 1536 --candidates 1000 --iterations 1000`. With the `time_loop`
  warmup being `iterations.clamp(1, 64)` (`:110`) / `clamp(1, 16)`
  (`:140`), warmup scales with `iterations` only up to a low ceiling.
  For 1000 iterations the warmup is fine; for tiny `--iterations` the
  warmup floor is 1, which may include cold dispatch cost. Document the
  warmup behavior or pin the warmup independently of `--iterations`.
- N3. **No host capture in log** — the log preamble records `backend`,
  `dim`, `candidates`, `iterations`, but not host CPU model, kernel,
  `RUSTC_BOOTSTRAP`, build profile, or `CARGO_PROFILE_RELEASE_*`
  overrides. For cross-host comparison the log should include enough
  metadata to re-derive the run; right now the host attribution lives
  only in `cpu-features.log`.
- N4. **Checksum is per-row, not per-variant determinism check** —
  `checksum` accumulates a running sum unique to each row. That is fine
  as a `black_box` anchor but does not provide a cross-backend
  equivalence check. A separate "scalar reference checksum" column would
  catch silent SIMD divergence (e.g. the AVX-512 bits1 sign-flip / mask-
  decode work from packets 018–019).
- N5. **`bench_api::PreparedEstimator` exposure** — verify the path
  `ecaz::bench_api::{PreparedEstimator, ProdQuantizer, Quantizer,
  RaBitQQuantizer}` is actually exported with the build features used
  here. The build log
  `artifacts/local/cargo-build-ecaz-cli.log` should show no warnings; I
  did not see explicit feature flags asserted in the suite JSON.
- N6. **No `--sample-size 30 + nice + sleep` cadence** is needed here
  because this is an in-process µbench (no SSM), so the small-vCPU host
  rule from memory does not apply. Noted only to confirm I checked.
