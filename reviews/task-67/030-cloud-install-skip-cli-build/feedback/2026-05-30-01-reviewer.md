## Findings

### Skip semantics are explicit, not invariant-checked (intentional)

The new `--skip-cli-build` is a pure operator-asserted opt-in. There is no
version/sha check between the remote `/usr/local/bin/ecaz` and the
extension build that just landed. This is consistent with how the rest of
`ecaz cloud install` already trusts operator inputs (`--git-ref`,
`--extension-features`, `--skip-extension-recreate`), and the doc comment
on the flag is honest about its intent ("Use this when only extension
build features are being changed and the existing remote CLI is already
suitable for the follow-up command."). Fine for a bench-iteration flag,
but worth keeping in mind if this surface is ever reused outside the
bench workflow — a future caller might silently run an older CLI against
a newer extension. Not a blocker for this packet.

### Default path is byte-stable

With `skip_cli_build=false` the rendered script keeps the same two lines
that used to be hardcoded:

- inside the `sudo -u postgres bash -lc '...'` block:
  `  cargo build --release -p ecaz-cli`
- outside the block:
  `sudo install -Dm755 /var/lib/pgsql/build/ecaz/target/release/ecaz /usr/local/bin/ecaz`

The `install_script_omits_feature_flag_by_default` test now asserts both
of those lines are present, which locks the default path against
accidental regression. Good.

### Skip path is clean under `set -eux`

With `skip_cli_build=true`, line 144's `{cli_build}` expansion is empty,
which leaves a blank line inside the `sudo -u postgres bash -lc '...'`
heredoc just before the closing `'`. Line 146's `{cli_install}` is also
empty, which makes that line render as just
`sudo systemctl restart postgresql`. Both are inert under
`set -euxo pipefail`. No corruption risk on re-run; the skip path is
idempotent in the same sense the non-skip path is (next invocation just
runs `cargo pgrx install` again).

### Test coverage matches the behavior change

Three install-script unit tests now exercise:

1. default (no features, CLI rebuild present),
2. features on, CLI rebuild present (the previous test, updated for the
   new arg),
3. features on, CLI rebuild skipped — and explicitly asserts the
   `cargo build` and `install -Dm755` lines are absent while the
   extension SQL check and `systemctl restart postgresql` remain.

That is the right shape for a script-rendering change. Logs in
`artifacts/local/cargo-test-ecaz-cloud-install-script.log` confirm 3
passed.

### Flag naming

`--skip-cli-build` parallels the existing `--skip-extension-recreate`
boolean and the boolean field on `InstallArgs`. Naming is consistent.

### Scope

Change is confined to `install.rs`. No drift into other cloud commands,
the CLI surface, or the benchmark runner. Matches the "don't add features
beyond what the task requires" rule — this is the minimum needed to
unblock the bf16-on extension reinstall after the disk-full failure in
packet 029, not a speculative knob.

## Nits (non-blocking)

- The `--skip-cli-build` doc comment could mention that PostgreSQL is
  still restarted and the extension SQL state is still verified, so a
  reader doesn't conflate "skip CLI build" with "skip post-install
  verification". Optional.
- If this flag survives past the bf16 validation, a future packet could
  add a version-check warning (compare extension version vs.
  `/usr/local/bin/ecaz --version`) so silent skew is logged. Out of
  scope for this packet.

## Result

Approve. No required changes. Safe to land for the Slice I bf16 AWS
follow-up.
