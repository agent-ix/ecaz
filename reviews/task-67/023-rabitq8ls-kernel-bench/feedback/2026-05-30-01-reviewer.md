# Reviewer Feedback: Packet 023 (rabitq8ls kernel bench)

## Verdict

ACCEPT. The packet credibly isolates the `rabitq8ls` kernel and the AVX-512
results clear the Task 67 5x per-kernel target (6.69x). No code drift outside
the bench harness, no scoring math change.

## What I verified

- Code change at `c72003b7b` is narrow: 44 lines added to
  `crates/ecaz-cli/src/commands/bench/rabitq_kernel.rs` only. No
  `src/quant/rabitq.rs` change. Verified via `git show c72003b7b --stat`.
- The new `bench_single_least_squares` invokes
  `prepared.estimate_ip_least_squares_scalar_only(...)`, which despite its name
  is **not** scalar-pinned: it calls `estimate_ip_least_squares_scalar_only_impl`
  (rabitq.rs:4367), which in turn calls `sum_query_dequant_with_bf16` →
  `sum_query_dequant_dispatch` (rabitq.rs:1547,1577). On AVX-512 the dispatcher
  resolves to the SIMD bits=8 kernel. This is the real `rabitq8ls` sidecar
  scoring path: `crates/ecaz-cli/.../sidecar_rerank.rs:1059` routes
  `SidecarVariant::Rabitq8ls` through the same entrypoint.
- The bench structure (warmup, `time_loop`, `black_box`, checksum print)
  mirrors `bench_single_dispatch` and `bench_single_scalar`. No dead-code
  elimination risk; the checksum is consumed by `print_row`.
- Packet 020 finding ("bench_single calls scalar") does **not** repeat here:
  `single-least-squares` uses the same dispatch wrapper pattern as the existing
  `single-dispatch` row, and the scalar/auto log backend lines confirm the
  expected backends.
- Raw logs reproduce manifest values:
  - scalar log: `backend=scalar`, `bits8ls single-least-squares ... 807.72`
  - auto log: `backend=avx512f+vpopcntdq+bw+bf16`, `bits8ls ... 120.74`
  - 807.72 / 120.74 = 6.69x, matches the request table.
  - Checksums 2.446483 (scalar) vs 2.446484 (auto) — agree to fp noise,
    confirming both paths compute the same score.

## Cross-reference with packet 017 finding

My packet 017 finding flagged that the bits=8 sidecar score kernel appeared
flat ~1.0x against the 4x target. Packets 020 and 023 together now show that
at the **prepared-estimator kernel layer** the bits=8 family (`bits8`,
`bits8ls`, `bits8c3`, `bits8c4`) is in fact SIMD-bound:

- bits8 single-dispatch: 6.25x
- bits8ls single-least-squares: 6.69x
- bits8c3 single-dispatch: 6.04x
- bits8c4 single-dispatch: 6.31x

So the kernel layer is healthy. The 017 flatness must live above the kernel
(SQL wall-time path, scan setup, IO, plan-time overhead). The packet correctly
limits its claim to the kernel row and explicitly defers the SQL interpretation
to packets 017, 021, 022 — that scoping is right.

## Minor observations (non-blocking)

1. The function name `estimate_ip_least_squares_scalar_only` is misleading —
   the underlying impl dispatches through `sum_query_dequant_with_bf16` and
   reaches SIMD kernels. The bench row label `single-least-squares` is fine,
   but a future tidy could either:
   - rename the API function to drop `_scalar_only` (it isn't), or
   - add a comment at rabitq.rs:933 noting that `_scalar_only` refers
     historically to the outer arithmetic, not the inner dequant sum.
   Not in scope for this packet; flagging for future cleanup.

2. The bench only emits `bits8ls` for `variant.name == "bits8"`. That's
   correct given the least-squares path only applies to bits=8 in the
   sidecar, but a tiny comment on the gate would help a future reader.

3. Smoke run header shows `backend=avx2+fma` locally and the AWS auto row is
   `avx512f+vpopcntdq+bw+bf16`. Both are real dispatches; no issue. Worth
   noting that the request only claims the AWS AVX-512 5x clearance, not a
   local AVX2 number. Scoping is correct.
