# Review: Task 67 Packet 017 Intel Measurement Final

## Verdict

**Accept as evidence, with caveats.** The packet is well-organized, uses
`ecaz bench suite` end-to-end, isolates per-variant tables, names the access
method explicitly in load logs, and includes a complete manifest with
reproducible commands and S3 provenance. Recall is preserved and a 1.88x-2.54x
primary speedup is real. However, the headline framing of the sidecar speedup
is misleading, the Slice J performance gates are not met, and there is no
runtime telemetry confirming AVX-512/BF16 kernels actually engaged on the auto
side (we rely solely on the `ECAZ_SIMD=auto` systemd env). Recommend the
packet is recorded as Slice J evidence-of-progress with the interpretation
section corrected before closeout. Do not close Task 67's performance gate on
this evidence.

## Findings

### F1 (high). Sidecar speedup is attributed to the wrong kernel.

`request.md:12` and `request.md:79-91` claim "Auto-SIMD improves `rabitq8*`
sidecar total-bound p50 by about 2.0x across all four variants." The
underlying numbers tell a different story:

- scalar sidecar `sidecar_score_p50` ≈ 0.025-0.027 ms
  (`artifacts/scalar-sidecar/sidecar-10k-rabitq8-variants-scalar.log:4-10`)
- auto sidecar `sidecar_score_p50` ≈ 0.024-0.027 ms
  (`artifacts/auto-sidecar/sidecar-10k-rabitq8-variants-auto.log:4-10`)
- scalar `candidate_sql_p50` = 7.733 ms vs auto = 3.719 ms

The 2.0x total-bound improvement comes entirely from the bits=1 batched
candidate scan (`candidate_sql_p50` halving), not from the `rabitq8*` sidecar
scoring kernels — those are flat. For Slice J this matters: the request reads
as if both the bits=1 and bits=8 SIMD paths are improving, but the bits=8
scoring kernels show no measurable auto-SIMD lift at this scale. Reword the
sidecar table heading or add a column to separate `candidate_sql` (improving)
from `sidecar_score` (flat).

### F2 (high). No direct evidence x86 SIMD kernels actually engaged.

The only "auto-SIMD on" signal is `ECAZ_SIMD=auto` in systemd env
(`artifacts/preflight/validation.log:57-63`). No log line shows kernel
selection (e.g., "selected AVX-512 BF16 bits1 batch kernel"). The 1.88x-2.54x
latency delta is consistent with SIMD being active, but a confirmation log
line (or a `pg_settings`/`ecaz dev` probe captured in preflight) would make
the evidence non-circumstantial. Memory rule `feedback_benches_must_be_repeatable`
implies an outside reviewer should be able to verify SIMD engaged without
re-running. Add a kernel-selection capture step in the next packet shape.

### F3 (high). Slice J headline gates are not met.

`request.md:13` correctly states this: bits=1 batched path target is at least
3x and bits=8 variant target is at least 4x; observed is 1.88x-2.54x and
~1.0x (sidecar score itself, per F1). Verdict on closing Task 67 performance:
**not closed**. Packet accurately reports this; no concealment.

### F4 (medium). `quant_bits` reloption rejected as unknown.

`artifacts/auto/load-10k-rabitq1-auto.log:1` and
`artifacts/scalar/load-10k-rabitq1-scalar.log` (same line) log:

    [loader] warning: profile "ec_ivf" does not list quant_bits as known
    reloption; passing through verbatim. Known reloptions: nlists, nprobe,
    rerank_width, training_sample_rows, seed, pq_group_size, storage_format,
    quantizer, rerank

`quant_bits=1` is passed through verbatim. The index then logs
`storage_format=rabitq` so it presumably reaches `ec_ivf`'s rabitq plumbing,
but the loader's known-reloption list is out of date. This is not a packet
defect, it is an `ecaz-cli`/profile-table inconsistency; flag for a separate
follow-up so future readers do not mistake the warning for a misconfiguration.

### F5 (medium). Access method naming: good for load, weaker for results tables.

Per memory rule `feedback_access_method_naming`, access method must be named
explicitly. The load logs do this well — `ec_ivf` is printed at
`artifacts/auto/load-10k-rabitq1-auto.log:10,15,21`. However, the result
tables in `request.md:43-91` are titled "Primary Bits=1 Results" and "Sidecar
rabitq8* Results" without naming the access method anywhere in the table or
its caption. Add "Access method: `ec_ivf`, storage_format: `rabitq`" in the
section headers so the request stands alone without the reader cross-checking
the load log.

### F6 (low). Comparator runs correctly omitted.

Per memory rule `feedback_no_unchanged_comparator_runs`, no vchord or
pgvectorscale runs appear. Hardware (m7i.2xlarge) is new for this lane, but
the scope here is intra-ecaz scalar-vs-auto, not a paired baseline rerun.
This is correct. The pinned paired baseline (94c02c682) is unaffected.

### F7 (low). Per-variant table isolation: confirmed.

`artifacts/auto/load-10k-rabitq1-auto.log:6,9` show distinct
`task67_intel_10k_rabitq1_auto_corpus` and `..._queries` tables per variant
prefix; same for scalar (`..._scalar_*`). Manifest line 12 attests four
distinct prefixes. Memory rule `feedback_index_isolation_rule` satisfied.

### F8 (low). Suite runner usage: clean.

All four sweeps drive through `ecaz cloud bench --config ... --suite ...`
(`artifacts/preflight/validation.log:81-91`) with `suite audit` run on every
config (`validation.log:66-77`). No ad-hoc shell glue. CLAUDE.md
"`ecaz bench suite` Only" requirement satisfied.

### F9 (low). Superseded artifact retained with rationale.

`artifacts/scalar/cloud-bench-scalar.log` retained with reason documented in
`manifest.md:106-109`. Good provenance hygiene.

### F10 (low). Next-step suggestion partially redundant with Task 66.

`request.md:97-100` proposes "add a per-kernel RaBitQ microbench" as one
next-step option. Task 66 packet 001
(`reviews/task-66/001-m5-neon-rabitq/artifacts/manifest.md`) is exactly that
on NEON. Clarify the suggestion is to **port** the Criterion `quant_score`
bench to the x86 lane (or run it on this Intel host) — that is genuinely new
evidence and would isolate the bits=8 flatness in F1 from candidate-scan
plumbing. As-written it reads like the author is unaware Task 66 already
landed a microbench.

## Answers to request questions

1. **Split primary-vs-sidecar suite shape acceptable for Slice J?** Yes,
   technically. The split is well-justified (sidecar-rerank needs
   `rerank=off`) and each side is independently audited and reproducible.
   The split does not invalidate the evidence; however, see F1 — the sidecar
   numbers must be presented in a way that does not conflate
   `candidate_sql` improvement with `sidecar_score` improvement.

2. **Performance-gate interpretation correct?** Yes for bits=1 (1.88x-2.54x <
   3x, gate not met). For bits=8, "2.0x speedup" is technically true on
   total-bound but the kernel itself shows no measurable speedup — the gate
   on the bits=8 *kernel* (which is what Slice J's 4x target was about) is
   not just unmet, it is currently 1.0x and that should be stated bluntly.

3. **Next step: per-kernel microbench vs more kernel optimization?** Per-
   kernel microbench first (port the Task 66 Criterion bench to Intel).
   Until F2 is addressed and F1's sidecar story is isolated, optimization
   work risks chasing the wrong hot path. A per-kernel run on this same
   m7i.2xlarge would tell us whether the bits=8 AVX-512 BF16 kernel is even
   being selected; if it is and still flat versus scalar, the optimization
   target shifts. If it is not being selected, F2 becomes a bug, not a
   review-evidence gap.
