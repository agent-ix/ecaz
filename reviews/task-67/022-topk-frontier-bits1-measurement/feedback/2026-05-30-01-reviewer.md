## Correctness Analysis

The `score` argument to `record_scored_posting_candidates` is **not** an
estimated upper bound on a still-to-be-computed score: it is the same scalar
(`-ip`) that would otherwise be stored in both `best_by_heap_tid` and
`running_top` (see callsites at lines 1486-1493 and 1514-1521). So
`would_reject_score` compares like-for-like against the current worst score in
the pre-rerank top-K heap. This is the correct invariant: "skip work whose
contribution would itself be pruned downstream."

Ordering direction was verified:

- `candidate_cmp` (line 1128) sorts ascending by `score.total_cmp` (lower
  score = better; `score = -ip`).
- `CandidateTopK.retained` is a `BinaryHeap<CandidateHeapEntry>` (max-heap by
  `candidate_cmp`), so `peek()` returns the worst retained candidate. `score >
  worst_score` therefore means strictly worse than the k-th best, which
  matches the intent.

Tie handling: rejection uses `>` (strict), so equal scores still flow through
the dedup map and heap. This preserves the existing deterministic
heap-TID tie-break in `candidate_cmp` / `candidate_heap_tid_cmp`. The unit
test `candidate_top_k_rejects_only_scores_worse_than_full_worst` covers the
strict/equal/empty cases for `would_reject_score`.

### Interaction with the dedup map

A subtle pre-existing quirk: the `Occupied` branch in
`record_scored_posting_candidates` updates `best_by_heap_tid` but does **not**
push the improved candidate to `running_top`. That means `running_top` could
already hold stale worse scores for revisited heap_tids in the pre-patch code.
The patch makes this slightly tighter, not looser:

- Pre-patch: first sighting of heap_tid X at a bad score occupies a `running_top`
  slot (later improved scores only update dedup, not `running_top`).
- Post-patch: a bad first sighting that exceeds the current worst frontier is
  dropped entirely; a later better sighting takes the Vacant branch and is
  pushed to `running_top` with its true (better) score.

The final ranked candidates come from `best_by_heap_tid.values()` at
line 1428, then re-ranked by `collect_ranked_probe_candidates`. Any candidate
the patch skips would, in the pre-patch path, have either (a) been pruned by
the final `collect_ranked_probe_candidates` top-K because its score exceeds
the live frontier worst, or (b) been later replaced in dedup by a better
sighting. Case (a) is the dominant case; case (b) is the only behavioral
delta, and it strictly improves the tightness of the `min_ip_to_keep` bound
fed to `score_ip_from_parts_with_min_bound` at lines 1500-1503 / 1397-1400 —
i.e., it can only prune more, never less.

## Findings

### Non-blocking

1. **Document the dedup/top_k asymmetry.** The pre-patch behavior where
   `Occupied` updates dedup but not `running_top` is load-bearing for the
   correctness argument here. Consider an inline comment near the new
   `would_reject_score` check (or near the `Occupied` branch) explaining that
   the rejection is safe because `running_top` is only a pruning hint and the
   authoritative candidate pool is `best_by_heap_tid`. This will save the next
   reader the same investigation.

2. **Differential parity test for the scan path.** The unit test exercises
   `CandidateTopK::would_reject_score` in isolation but does not exercise
   `record_scored_posting_candidates` end-to-end with and without the
   optimization toggled. The recall@10 evidence is reassuring, but a focused
   test that feeds two posting lists into the function and asserts identical
   `best_by_heap_tid.values()` plus identical `running_top` worst-score with
   and without the early return would harden the invariant against future
   refactors. Optional — current measurement evidence is sufficient.

3. **Headline gate framing.** The 3x gate is met only at nprobe=64 against
   the packet 017 scalar baseline (2.11x / 2.52x / 3.07x). The request
   already flags this, and the interpretation paragraph asks the right
   question (kernel-throughput vs total SQL wall-time). Suggest closing this
   packet on its narrow merits (the scan-path pruning is independently sound)
   and tracking the SQL-level 3x decision in the higher-level Task 67 thread
   rather than re-opening it here.
