## Findings

### AMI lookup is architecture-correct (positive)

`infra/cloud/terraform/main.tf` lines 269-285 replace the hard-coded
`al2023_arm64` lookup with a parameterized `data.aws_ami.al2023` that filters
on both `name = al2023-ami-2023.*-${var.instance_architecture}` and
`architecture = var.instance_architecture`. `most_recent = true` plus
`owners = ["amazon"]` is the canonical AWS pattern, so the lookup will resolve
to a current, supported AL2023 image at plan time rather than pinning a stale
AMI ID into Terraform — that is the right call (avoids drift, no hand-curated
AMI list to refresh).

### Architecture matches Intel lane (positive)

`infra/cloud/terraform/profiles/10k-intel.tfvars` line 5 sets
`instance_architecture = "x86_64"` for `m7i.2xlarge` / `c7i.large`. The Intel
dry-run in `artifacts/validation.log` lines 38-50 confirms the resolved AMI
(`ami-029a761f237195c2c`) is attached to both `m7i.2xlarge` (DB) and
`c7i.large` (loader). Architecture mismatch (Graviton AMI on Intel) — the
stated failure mode of the previous plan — is fixed.

`{arm64, x86_64}`. The Graviton dry-run in `artifacts/validation.log` lines
62-75 confirms the existing `10k` profile still resolves to an arm64 AL2023
AMI (`ami-0a2a049c945b84826`) attached to `m8g.large` / `c8g.medium`. No
regression for existing Graviton profiles.
