## Findings / notes (non-blocking)

1. **Cross-link to packet 022 top-K frontier reasoning is implicit.**
   The interpretation in `request.md` correctly identifies the likely
   cause (growth/allocator overhead) but doesn't explicitly tie the
   negative result back to the packet-022 finding that the top-K
   frontier already prunes the candidate set aggressively. With the
   frontier active, the dedup map's effective working set is bounded
   far below `candidate_bound`, so a tighter initial reservation
   wouldn't typically save allocation — it would just force the
   hashmap to grow as the frontier pulls in more rerank candidates
   than the inline-tid cap predicted. Calling that out explicitly
   in `request.md` would help future bits=1 work avoid re-running
   this experiment under a different name.

2. **No `latency_ms` ratio analyzed against scalar within this packet.**
   The packet-026 scalar mean (1.33 ms @ nprobe 16) is itself faster
   than packet-017's 2.28 ms scalar mean. Some of that is host
   variation between runs, but it suggests the cap may have had a
   mild positive effect on the scalar path and a negative one on the
   SIMD path. Not actionable inside this packet — it's reverted — but
   worth flagging if any future bits=1 work revisits the dedup map.

3. **Manifest lists `load-10k-rabitq1-dedup-reserve-{scalar,auto}.log`
   under Artifact Inventory but `request.md` omits them.** Cosmetic;
   both files exist on disk.
