# Verdict: Accept

The bits=4 AVX-512 and AVX2 single-candidate kernels in commit `497d2890e` are
correct, runtime-gated consistently with their `target_feature` annotations,
and shape-aligned with `sum_query_dequant_neon_bits4`. The differential test
covers tails. No drift into shared bodies, bits=1, or bits=8.

## Confirmations

- **Nibble order matches encoding** (`src/quant/rabitq.rs:1380-1384`,
  `1393-1400`). `write_level`/`read_level` for `bits=4` put the level for
  even `i` in the low nibble (`& 0x0F`) and odd `i` in the high nibble
  (`>> 4`). Both AVX-512 (`2640-2657`) and AVX2 (`2768-2785`) unpacks emit
  `lut[b & 0x0F]` at lane `2k` and `lut[b >> 4]` at lane `2k+1`, matching
  NEON (`2366-2383`).

- **Runtime gating consistent**. Selector requires
  `features.has_avx512_bits4()` = `avx512f && avx512bw`
  (`src/quant/simd.rs:100-102`) for `Avx512Bits4`, and `avx2 && fma` for
  `Avx2Bits4` (`src/quant/rabitq.rs:1802-1808`). Kernel `target_feature`s
  declare `"avx512f,avx512bw"` (`2620`) and `"avx2,fma"` (`2746`)
  respectively. Test gate (`4831-4856`) mirrors both.

- **Dispatch wired correctly**. `sum_query_dequant_dispatch`
  (`1652-1672`) routes `Avx512Bits4` and `Avx2Bits4` to their new kernels
  inside `unsafe`; bits=1 slots still fall through to scalar fallback;
  bf16 slot untouched. `select_x86_query_dequant_kernel` (`1799-1804`)
  now passes the bits=4 slot through instead of degrading to `Scalar`.

- **Scalar tail covers non-multiple-of-16 dims** (`2599-2603`,
  `2790-2794`) via `read_level(code, dim_index, 4)`, exercised by test
  dims `{1,7,8,15,16,31,32,64,256,1536}`.

- **`unsafe` hygiene**. `get_unchecked` on code bytes is bounded by
  `dim_index + 16 <= dimensions` and the caller's `code.len() >=
  ceil(dim*4/8)` invariant; `_mm512_loadu_ps` / `_mm256_loadu_ps` over
  `query_rotated` are unaligned and within the same bound; horizontal
  reduction via `_mm512_storeu_ps`/`_mm256_storeu_ps` into a 16/8-lane
  stack array is sound.

## Observations (non-blocking)

1. **`avx512bw` is gated for but unused in the kernel body.** The
   request.md teases "nibble-unpack via `_mm512_srli_epi16` + mask",
   but the implementation does scalar nibble unpack into a 16-f32
   stack array before a single `_mm512_loadu_ps`. That's fine for
   correctness and matches the NEON shape. If a later slice keeps
   the scalar unpack permanently, the `avx512bw` requirement could
   be relaxed to `avx512f` only (and `has_avx512_bits4()` adjusted),
   which would let Cascade Lake / Skylake-X parts with AVX-512F but
   not BW run this path. Not required for this packet.

2. **AVX-512 uses 1 accumulator chain; AVX2 uses 2; NEON uses 4.**
   Correctness-fine. Single AVX-512 chain may bottleneck on FMA
   latency (~4c) on Intel server parts. Worth revisiting in the
   later bits=4 batched/perf slice (scope item 5+); not blocking
   for the single-candidate slot.

3. **No 8-wide intermediate tail.** NEON has `+= 8` mid-tail then
   scalar; x86 paths jump straight from 16-wide to scalar. Correct
   in both cases; just a shape divergence.

4. **Validation is compile-only.** Per `request.md`, runtime unit
   execution is blocked locally by the `LockBuffer` pgrx link.
   Differential test asserts will fire on the next CI/AWS run where
   AVX-512F+BW or AVX2+FMA is present.

## Scope discipline
