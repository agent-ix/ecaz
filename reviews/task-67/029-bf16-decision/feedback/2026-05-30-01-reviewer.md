## Findings

### F1. Decision is explicit and measurement-justified (PASS)

`comparison.md` and `request.md` record the decision verbatim: "Do not
enable `rabitq-bf16` by default for this Task 67 SQL lane. It preserves
recall but regresses p50 and mean latency at every tested nprobe value."
Each nprobe row is cited (1.08x–1.17x slower at p50). This satisfies the
Slice I null-result requirement.

### F2. Honest bf16 ON vs OFF comparison (PASS)

Both runs use identical fixture (`ec_real_10k`, 200 queries),
`storage_format=rabitq`, `quant_bits=4`, `rerank=heap_f32`,
`rerank_width=100`, nprobe sweep `{16, 32, 64}`, and ran on the same AWS
Intel `10k-intel` lane with `ECAZ_SIMD=auto`, PG18. The only varying axis
is the `--extension-feature rabitq-bf16` build flag (visible in the bf16-on
install command in `manifest.md`).

### F3. Access method named explicitly (PASS, per `feedback_access_method_naming`)

Both `suite-manifest.json` files invoke `--profile ec_ivf`. The
`comparison.md` header states "`ec_ivf`" directly. The corpus prefix
(`task67_bf16{on,off}_10k_rabitq4`) is not used to infer access method.

### F4. Index isolation (PASS, per `feedback_index_isolation_rule`)

Distinct prefixes per variant: `task67_bf16off_10k_rabitq4` vs
`task67_bf16on_10k_rabitq4`, each on its own replicated corpus table. No
shared-table comparison.

### F5. Recall parity within tolerance (PASS)

Recall@k matches exactly at every nprobe:

- nprobe 16: 0.9985 vs 0.9985 (both have identical CI95 `[0.9956, 0.9995]`
  and identical worst-case 0.8000)
- nprobe 32 / 64: 1.0000 vs 1.0000

No recall delta to flag. bf16 cost is purely latency, justifying the
opt-in decision.

### F6. Pause status not a data-incompleteness flag (PASS)

Commit `28cb0fb20` records `state: paused`, which is normal post-bench AWS
teardown after the successful bf16-on run captured in
`cloud-status-after-bf16-on-success.log` (state: stopping, $0.00/hr
running). Both measurement runs completed cleanly before the pause; the
pause is not a midway abort, and the request does not lean on incomplete
data. Multiple preflight failures (out-of-disk during CLI rebuild,
git-index lock, missing corpus after `cargo clean`) are transparently
disclosed in `request.md` Notes and `manifest.md` Recovery section, and
recovery commits/packets (030-032) are flagged.

### F7. NFR-007 manifest completeness (PASS)

`manifest.md` includes head SHA (c4ebcbca2…), task bucket and packet path,
lane, fixture, storage format / rerank mode, isolated surface prefixes,
exact `ecaz cloud bench` and `ecaz cloud install` commands, S3 run URIs
for both runs, suite-config audit results, and key result lines that
match the latency/recall logs exactly.
