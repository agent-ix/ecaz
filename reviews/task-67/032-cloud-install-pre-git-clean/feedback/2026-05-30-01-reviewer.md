# Reviewer feedback: Task 67 packet 032 — clean target before git reset

## Verdict

APPROVE. Small, well-scoped reorder that addresses a real failure mode
observed in packet 029. Behaviorally a no-op for the default path; the
clean-on path now frees disk before any git write, which is exactly what
the request claims.

## Findings

### F1 — Reorder is correct and minimal

Single-template move of `{pre_git_clean_target}` from just-before
`cargo pgrx install` to just-after `cd /var/lib/pgsql/build/ecaz` and
just-before `git reset --hard`. Variable was renamed
`clean_target` -> `pre_git_clean_target`, which is a useful tell at the
call site. Happy path is preserved: clone-or-cd, then (optional) clean,
then full git reset/fetch/checkout sequence, then pgrx install, then
optional CLI build.

### F2 — Default (no-clean) byte-stability: behaviorally identical, not byte-identical

Note for the record: with `--clean-cargo-target` off, the placeholder
expands to the empty string, which still emits a bare blank line in the
script. In packet 031's layout that blank line sat just before
`cargo pgrx install`; after this commit it sits just before
`git reset --hard`. Bash ignores both, and `set -x` trace output is
unchanged in any meaningful way, so this is not a correctness concern.
It just means the default install script is not byte-for-byte stable
across 031 -> 032. The change is small, the rationale is in the request,
and no consumer keys off exact script bytes, so flagging only — no action
required.

### F3 — Test coverage updated for the new ordering

`install_script_can_clean_cargo_target_before_build` now asserts
`clean_pos < reset_pos < build_pos` (via the existing `clean_pos < build_pos`
plus the new `clean_pos < reset_pos`). This is the right invariant: it
locks in the "clean before git reset" ordering that the request is
selling. The other three install_script_* tests are unaffected and
continue to cover default, features, and skip-cli-build shapes.

### F4 — Idempotency preserved

`cargo clean` is idempotent. Running it before `git reset --hard` /
`git clean -fd` is safe — git's reset/clean do not touch `target/`, so
the cargo clean is not undone, and a subsequent re-run on a clean tree
is a no-op. The first-time clone branch (`if [ ! -d .../.git ]`) is
unaffected; in that path there is no stale `target/` yet, so the
pre-git clean is harmless.

### F5 — Disk-pressure rationale lines up with packet 029

Packet 029 failed at `.git/index.lock` write, which happens during
`git reset --hard` / `git fetch`. Moving `cargo clean` ahead of those
git ops is the right fix; reclaiming the multi-GB `target/` before any
git plumbing tries to write index/pack files is what unblocks the
sequence on a full disk.

### F6 — Scope discipline

Only `crates/ecaz-cloud/src/commands/install.rs` is touched (one
template reorder + variable rename + one extra test assertion). No
drift into other crates, no Cargo.toml churn, no benchmark or runner
changes. Matches "support checkpoint" framing.

## Nits (non-blocking)

- Consider tightening the test to assert all three positions in one
  chained inequality (`clean_pos < reset_pos && reset_pos < build_pos`)
  to make the intended ordering self-documenting; current pair of
  asserts is fine.
- If a future packet wants the default path to be byte-stable, the
  ordering could be expressed without the trailing newline in the
  empty-case (e.g. emit `"  cargo clean\n"` or `""` and drop the
  template newline). Not worth doing now.
