# Reviewer feedback — Task 67 x86 bits=8 kernels (commit 434a2da56)

## Verdict

Approve. The AVX-512F and AVX2+FMA bits=8 scoring kernels are correct,
properly gated, and aligned with the NEON bits=8 reference. No changes
requested for this slice.

## Findings

### Correctness — arithmetic-dequant chain (PASS)

- `sum_query_dequant_avx512_bits8` at `src/quant/rabitq.rs:2558-2598` computes
  the same `acc += code_byte * query_scale + query_offset` accumulation as the
  scalar fallback and the NEON reference at `src/quant/rabitq.rs:2400-2459`.
  Widening order `_mm_loadu_si128 → _mm512_cvtepu8_epi32 → _mm512_cvtepi32_ps`
  preserves unsigned byte semantics (matches NEON `vmovl_u8 → vmovl_u16 →
  vcvtq_f32_u32`). 16-lane main loop + scalar tail mirrors NEON's
  16-element stride.
- `sum_query_dequant_avx2_bits8` at `src/quant/rabitq.rs:2606-2654` splits the
  16 bytes into two 8-lane halves via `_mm_srli_si128(code_bytes, 8)` and uses
  two independent accumulators (`acc0`, `acc1`). The dual-accumulator pattern
  matches NEON's a0..a3 fan-out and improves ILP. Scalar tail is identical.
- Both kernels pair the FMA result with an outer add into the accumulator
  (`acc = add(acc, fmadd(code, scale, offset))`), matching NEON
  (`vaddq_f32(acc, vfmaq_f32(o, c, s))`). Arithmetic shape is bit-for-bit
  equivalent at the FMA level; only floating-point reduction order differs,
  which is bounded by the 1e-4 relative tolerance used by the differential
  test.

### Runtime gating & target_feature alignment (PASS)

- AVX-512 kernel declares `#[target_feature(enable = "avx512f")]` at
  `src/quant/rabitq.rs:2554` and the selector `select_x86_query_dequant_slot`
  reaches `Avx512Bits8` only when `features.has_avx512_bits8()` is true, which
  is `self.avx512f` (`src/quant/simd.rs:104-106`). Match.
- AVX2 kernel declares `#[target_feature(enable = "avx2,fma")]` at
  `src/quant/rabitq.rs:2604` and the selector requires
  `features.avx2 && features.fma` (`src/quant/rabitq.rs:1814-1820`). Match.
- Upstream `detect_x86_features` (`src/quant/simd.rs:34-39`) populates these
  flags via `is_x86_feature_detected!`, so the production dispatch path is
  guarded end-to-end.

### Unsafe boundary hygiene (PASS, minor style nit)

- Both `unsafe fn` bodies are entered only through the
  `sum_query_dequant_dispatch` arms at `src/quant/rabitq.rs:1629-1652`, whose
  SAFETY comments correctly cite (a) runtime feature confirmation and
  (b) bits=8 precompute length checks, both established by
  `select_x86_query_dequant_slot` at `src/quant/rabitq.rs:1810-1820` which
  verifies `bits8_query_scale.len() == ctx.dimensions` and
  `bits8_query_offset.len() == ctx.dimensions` before yielding the kernel
  slot.
- Style nit (non-blocking): the AVX-512 kernel wraps loads in an inner
  `unsafe { ... }` block (rabitq.rs:2570-2576) but `_mm512_cvtepu8_epi32`
  /`_mm512_cvtepi32_ps`/`_mm512_fmadd_ps` are intrinsics that are also
  `unsafe` and sit outside any inner block. The AVX2 kernel does the same.
  Both compile because the enclosing `unsafe fn` is itself an unsafe context;
  the inner `unsafe { }` blocks are decorative under current Rust editions.
  Consistent with the existing NEON kernel style. Leaving as-is is fine.

### Differential test registration (PASS)

- `x86_sum_query_dequant_bits8_matches_scalar_when_available`
  (`src/quant/rabitq.rs:4383-4427`) exercises dims 1, 7, 8, 15, 16, 31, 32, 64,
  256, 1536, hitting the 16-lane main loop, the scalar tail at multiple
  remainders, and dims smaller than one vector. It is gated by
  `is_x86_feature_detected!("avx512f")` and `("avx2") && ("fma")`, matching the
  kernels' `target_feature` requirements. Tolerance `1e-4 * max(|scalar|, 1.0)`
  is appropriate given the FMA reorder.
- The test is registered alongside the existing NEON differential tests and
  uses `build_bits8_query_precompute` (the Task 66 Slice C entry point),
  confirming the kernel/scalar pair consume the same precompute shape.

### Variant coverage (PASS)

- The bits=8 slot dispatched by `select_x86_query_dequant_slot` is shared by
  every variant whose `bits_per_dim == 8`, i.e. `rabitq8`, `rabitq8ls`,
  `rabitq8c3`, `rabitq8c4` — the variant fan-out lives upstream of the
  selector and does not require per-variant kernels. Coverage matches the
  stated scope.

### Out-of-scope drift (PASS)

- Diff touches only the bits=8 dispatch arms, the bits=8 slot pass-through in
  `select_x86_query_dequant_kernel`, two new x86 kernel bodies, and one new
  test. bits=1 and bits=4 x86 slots remain scalar; bf16 slot unchanged.
- The deferred bits=1 VPOPCNTDQ decision documented in `request.md` (current
  bits=1 scorer is query-weighted via byte LUT, not Hamming) is the right
  call — a popcount kernel here would change the scoring math. Defer to a
  future slice that reconciles encoding.

## Suggestions for follow-up slices (non-blocking)

1. A batched/pair x86 bits=8 kernel analogous to
   `sum_query_dequant_neon_bits8_pair` (rabitq.rs:2467-2547) is the obvious
   next slice — amortizes the byte load and the scale/offset broadcasts.
2. Consider extending the differential test to also assert AVX-512 vs AVX2
   results agree with each other (cross-kernel rather than just kernel vs
   scalar) on hosts that have both. Not required.
