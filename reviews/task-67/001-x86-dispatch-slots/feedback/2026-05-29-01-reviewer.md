# Task 67 Slice A — x86 dispatch slots

Verdict: **approve-with-nits**

Commit `19715a204e16a4b8142f2ad2ed95ebe3dc752647` lands a plumbing-only Slice A
that (a) adds AVX-512 feature detection, (b) carves a `SimdBackend::Avx512`
variant carrying `vpopcntdq` / `bw` / `bf16` capability bits, (c) reserves
seven `QueryDequantKernel::{Avx512Bits1, Avx512Bits4, Avx512Bits8,
Avx512Bf16Bits4, Avx2Bits1, Avx2Bits4, Avx2Bits8}` slots, and
(d) routes existing AVX-512-capable Intel hosts through the existing AVX2/FMA
paths in `hadamard.rs` / `prod.rs`. All of this is the right shape for Slices
B-H to attach `target_feature` kernel bodies one slot at a time without
restructuring.

## Answers to the review-focus questions

1. **`SimdBackend::Avx512` shape** — yes, acceptable. Carrying `vpopcntdq`,
   `bw`, and `bf16` as capability bits on the variant lets the kernel
   selector pick bits1 / bits4 / bf16 paths off `backend()` alone. `avx512f`
   itself is implicit on the variant (only emitted when one of bits1/bits4/bits8
   detectors fires, all of which require `avx512f`).

2. **Slot map coverage** — yes, the seven slot variants line up 1:1 with
   Task 67 scope items 1-6 + 8 (`plan/tasks/67-rabitq-intel-avx-optimization.md`
   lines 40-66). Item 7 (batched scoring) will need additional slot variants
   when Slice D-equivalent batched kernels land; current shape composes
   naturally — add `Avx512Bits1Pair`, `Avx2Bits4Pair`, etc. alongside the
   single-kernel slots without touching `sum_query_dequant_dispatch`. No
   shared estimate body changed.

3. **AVX-512 hosts via AVX2/FMA non-RaBitQ paths** — yes, acceptable. Every
   AVX-512-capable Intel CPU has AVX2+FMA, so the
   `SimdBackend::Avx512 { .. } | SimdBackend::Avx2Fma =>` collapses at
   `src/quant/hadamard.rs:17` and `src/quant/prod.rs:512` and
   `src/quant/prod.rs:781` are safe. Hadamard / ProdQuantizer get the same
   behavior they had before this commit on AVX-512 hosts.

## Nits / follow-ups (non-blocking)

- **`backend_name()` drops `bf16` for partial-feature hosts**
  (`src/quant/simd.rs:147-178`). The match arm for
  `vpopcntdq: true, bw: false, bf16: _` returns `"avx512f+vpopcntdq"` and
  similarly the `vpopcntdq: false, bw: true, bf16: _` and
  `vpopcntdq: false, bw: false, bf16: _` arms ignore bf16. That makes
  `backend_name()` lossy on hypothetical `avx512f+vpopcntdq+bf16` /
  `avx512f+bw+bf16` / `avx512f+bf16` hosts. Not a correctness issue (selection
  uses the struct, not the name), but please make the printable name
  exhaustive — concat from a small `Vec<&str>` instead of a fanned-out match
  would be simpler and avoids missing combinations.

- **`ECAZ_SIMD=avx512` env override hardcodes `bf16: false`**
  (`src/quant/simd.rs:139-144`). When the env override is used on a real
  bf16-capable host, the override path will deliberately disable bf16 even
  if the host supports it. Probably fine for forcing the non-bf16 AVX-512
  lane in benches, but Slice F (bf16 kernel) will want either
  `ECAZ_SIMD=avx512_bf16` or a separate env knob. Note it in the Slice F
  request when you get there.

- **`select_x86_query_dequant_slot` arm order is correct but subtle**
  (`src/quant/rabitq.rs:1783-1827`). The `1 if features.has_avx512_bits1() &&
  bits1_byte_lut.is_some()` arm sits above the `4 =>` and `8 if ...` arms,
  with the AVX2 `1 if ...` arm after them. Rust top-down match guarantees
  this works (`bits == 4 | 8` never matches the `1 if` guards), but an
  inline comment grouping arms by `bits` value would help future Slice
  authors avoid an "obvious" reorder that breaks fall-through.

- **No `*_for_test` placeholder entries yet for the differential-test
  scaffold** (Task 67 scope item 9). The new `x86_query_dequant_slots_cover_
  task67_kernels` test exercises slot selection but does not yet plumb
  `bench_api::sum_query_dequant_avx512_*_for_test` / `..._avx2_*_for_test`
  exports through `tests/simd_diff.rs`. Acceptable for Slice A since no
  kernel exists to expose, but the request claims "differential-test
  scaffold registration" — strictly the registration is deferred until
  Slice B lands the first kernel body. Recommend explicitly calling that
  out in Slice B's request so a reviewer doesn't expect simd_diff coverage
  before kernels land.

- **Runtime validation gap** (`reviews/task-67/001-x86-dispatch-slots/
  artifacts/validation.log`). `cargo test -p ecaz quant::simd` failed at
  binary startup on `undefined symbol: LockBuffer` (pgrx dynsym issue), so
  the new `x86_feature_slots_model_task67_kernel_requirements` and
  `x86_query_dequant_slots_cover_task67_kernels` test bodies never executed.
  These are pure-Rust tests with no pg18 dependency — if there is a way to
  run them through the in-process `cargo pgrx test pg18` lane or via a
  binary fixture that resolves pgrx symbols, please attach a passing run
  before Slice B starts. The compile + slot-coverage logic looks correct on
  inspection, but Slice A's whole purpose is the seam, and a green run on
  the seam tests would be cheap reassurance.

## Structural concerns: none

Nothing in this commit forces a structural change to Task 66's dispatch
shape. The `select_query_dequant_kernel` dispatcher at
`src/quant/rabitq.rs:1745` still matches `SimdBackend` once and delegates
per-arch; the x86 branch goes through the new `select_x86_query_dequant_
kernel` helper without touching the aarch64 branch or the shared
`QueryDequantContext` / `sum_query_dequant_dispatch` signature. Slices B-H
can flip `Scalar` -> real kernel by replacing the collapser body in
`select_x86_query_dequant_kernel` and filling in the matching
`sum_query_dequant_dispatch` arms one slot at a time.
