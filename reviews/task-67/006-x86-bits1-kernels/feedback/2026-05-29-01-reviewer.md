# Verdict: Approve with observations

Bits=1 x86 kernels correctly mirror the NEON byte-LUT FMA shape and are
correctness-safe to land. Differential coverage against scalar is present
and parameterized across tail and aligned dimensions. No drift outside the
bits=1 slot. Findings below are non-blocking observations about scope
framing and gating, not correctness defects.

## Findings

### F1 (observation, non-blocking) — Kernel does not use VPOPCNTDQ but is gated on it

The AVX-512 kernel `sum_query_dequant_avx512_bits1`
(src/quant/rabitq.rs:2603) is `#[target_feature(enable =
"avx512f,avx512vpopcntdq")]` and is selected via
`features.has_avx512_bits1()` which requires `avx512vpopcntdq`
(src/quant/simd.rs:96-98). However, the body uses only `_mm512_loadu_ps`
and `_mm512_fmadd_ps` over a per-query byte LUT — it never invokes
`_mm512_popcnt_epi64` or any VPOPCNTDQ intrinsic. The gate is therefore
unnecessarily restrictive: a Skylake-X / Cascade Lake host with AVX-512F
but no VPOPCNTDQ will fall back to scalar even though plain AVX-512F is
sufficient for the implemented kernel.

This is consistent with the scope note in `request.md` (the bits=1 path
remains weighted byte-LUT, not XOR+popcount sign-IP), and the prior slot
reservation pre-dates this slice. Recommend tightening the gate (or
splitting `has_avx512_bits1` into a popcount-required flag vs a plain
F flag) in a follow-up slice — ideally either when a true popcount kernel
lands or as a standalone Sandy Bridge-Server fix-up.

### F2 (observation, non-blocking) — Scope deviates from task text, request acknowledges

Task 67 scope items 1-2 describe a sign-popcount inner product
(`dim - 2*popcount(xor)`). The implementation preserves the weighted
byte-LUT estimator instead. The request explicitly flags this in "Scope
Notes" and motivates it by the production code path. Accepting per the
request, but the divergence should be tracked so that the bits=1 fast path
described in the task is either implemented in a later slice or the task
text is amended.

### F3 (verified) — Byte/bit order matches NEON

AVX-512 kernel stitches `byte_lut[b0][0..7]` followed by `byte_lut[b1][0..7]`
into `dq0` (lines 2620-2638), and reads `query_rotated[dim_index..+16]`.
This matches NEON's row-pair loads at 2166-2196 and the scalar tail's
`(code[i/8] >> (i%8)) & 1` semantics (2682-2686, 2746-2750).

AVX2 kernel loads `byte_lut.as_ptr().add(b0).cast::<f32>()` directly as 8
f32s (2719-2722). Row layout `[[f32;8];256]` is contiguous so an unaligned
256-bit load reads exactly one row. Correct.

### F4 (verified) — Feature gating

- AVX-512 kernel: `target_feature(enable = "avx512f,avx512vpopcntdq")`
  matches dispatch precondition `has_avx512_bits1()`.
- AVX2 kernel: `target_feature(enable = "avx2,fma")` matches dispatch
  precondition `features.avx2 && features.fma`.
- Dispatch SAFETY comments at 1672-1675 and 1689-1692 correctly cite both
  the runtime CPUID check and the `byte_lut` presence invariant.

### F5 (verified) — Differential test

`x86_sum_query_dequant_bits1_matches_scalar_when_available` (5301-5346)
covers dims {1, 7, 8, 15, 16, 31, 32, 33, 64, 95, 96, 1536} which
exercises tail-only (1, 7), aligned-boundary (8, 16, 32), tail+body
(15, 33, 95), and large multi-iter (1536). Both AVX-512 and AVX2 paths
run only when CPUID confirms the matching feature, with a relative
tolerance `1e-4 * max(|scalar|, 1)`. Good.

### F6 (minor, nit) — Inner unsafe blocks redundant inside `#[target_feature]` fn

Inside `sum_query_dequant_avx512_bits1` and `sum_query_dequant_avx2_bits1`,
the `unsafe { ... }` wrappers around the `_mm512_loadu_ps` /
`_mm256_loadu_ps` calls (e.g. 2641-2648, 2725-2734) are inside an `unsafe
fn`. Harmless and conforms to current `unsafe_op_in_unsafe_fn` lint
practice. No action needed.

### F7 (minor, nit) — Reduction style

AVX-512 reduce uses a 16-lane store + scalar `.iter().sum()` (2666-2671).
`_mm512_reduce_add_ps` would be one intrinsic call with the same result.
Functionally equivalent; either is fine.
