# Feedback: Task 67 Packet 028 — Cloud Install Extension Features

## Verdict

Approve. The slice is narrow, the default install path is byte-identical to
before, and the feature plumbing reaches `cargo pgrx install` via the
established shell-escape helper. Tests cover both the omitted-feature and
appended-feature shapes.

## Findings

### Correctness / safety

- Shell-injection surface is sound. `extension_features` get joined with a
  space, then passed through the existing `shell_escape` (single-quote +
  `'\''` escape) just like `git_url` / `git_ref`. A malicious feature string
  ends up quoted inside the remote `sudo -u postgres bash -lc '...'` block,
  not interpreted. Reasonable trust model: this is an operator-typed flag
  on a build matrix the operator already controls.
- Default path is preserved. `extension_features.is_empty()` produces an
  empty `extension_features_arg`, so the emitted line is exactly
  `cargo pgrx install --sudo --release --pg-config /usr/bin/pg_config`
  with no trailing whitespace, matching the prior script. The
  `install_script_omits_feature_flag_by_default` test pins this against
  the trailing newline, which is the right assertion.
- Multi-feature join is correct for Cargo. `cargo pgrx install --features
  'a b'` accepts space-separated features inside one arg, so a repeated
  `--extension-feature a --extension-feature b` collapses to a single
  `--features 'a b'` token — consistent with how
  `crates/ecaz-cli/src/commands/dev/install.rs` already invokes
  `--features` with a space-separated `"pg{} pg_test"`.

### Pathing / artifacts

- No change to `target/release` artifact resolution or the
  `sudo install -Dm755 ... /usr/local/bin/ecaz` step. The build still runs
  in `/var/lib/pgsql/build/ecaz`, and the `cargo build --release -p
  ecaz-cli` line is untouched. Good — `--extension-feature` intentionally
  only affects the extension (`cargo pgrx install`) build, not the CLI
  binary build.

### Hardcoding / extensibility

- No hardcoded feature allow-list. `Vec<String>` accepts any feature the
  package exposes (`rabitq-bf16` today, future flags tomorrow) without
  touching this file again. Matches the packet's stated intent.

### CLI naming

- The flag is `--extension-feature` (singular, repeatable), distinct from
  Cargo's own `--features`. That's deliberate disambiguation: the cloud
  install command itself doesn't take a Cargo `--features` today, and
  scoping the name to "extension" makes it clear the flag does NOT
  influence the `cargo build --release -p ecaz-cli` step. Recommend
  keeping the name as-is. If a future packet also needs CLI-binary
  features, a parallel `--cli-feature` is the right shape.

### Drift

- Diff is confined to `crates/ecaz-cloud/src/commands/install.rs`. No
  cross-crate edits, no shared helper refactor, no changes outside the
  cloud install command. Matches the request scope.

### Tests

- Two `#[cfg(test)]` unit tests cover the empty-features and
  single-feature paths. They assert against the literal emitted script
  fragment, which is the right granularity for a string-builder.
- Optional follow-up (not blocking): a third case with two features
  (e.g., `&[String::from("rabitq-bf16"), String::from("other")]`)
  asserting the joined `--features 'rabitq-bf16 other'` shape would lock
  in the join semantics. Today the multi-feature behavior is only implied
  by the join + escape code, not pinned by a test.
- Optional follow-up (not blocking): a feature containing a single quote
  (`String::from("a'b")`) would document the shell-escape contract for
  the feature axis. Low-priority since the operator controls the input.

## Recommendation

Ship as-is. Use this on the Intel bf16 lane per the packet rationale; no
changes required before that run.
