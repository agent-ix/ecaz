## Findings

### F1. Stub additions actually link the symbols, not mask them — accept

The new symbols in `standalone_pg_backend_stubs.c` split cleanly into two
categories with appropriate semantics:

- **Loader-only state** (real definitions so the dynamic linker resolves
  them): `NBuffers`, `NLocBuffer` (lines 95–96 of the post-patch file),
  `errstart_cold`, `errmsg_internal`, `pg_re_throw`, `palloc`, `format_type_be`.
  These are needed just to get the cdylib loaded; they do not pretend to do
  backend work.
- **Backend-only panic stubs** routed through `tqvector_backend_only*` —
  e.g. `LockBuffer`, `ReadBufferExtended`, `UnlockReleaseBuffer`,
  `index_open`/`relation_open`/`table_open`, `BuildIndexInfo`,
  `RelationGetIndexList`, `GetActiveSnapshot`, `InputFunctionCall`,
  `ExecInitExpr`, SPI/Tuple/Array helpers, `read_stream_*`. These panic at
  call time, so any plain-Rust test that wandered into real backend
  execution would fail loudly rather than silently succeed.

This is the correct fix for the LockBuffer symbol blocker from packets 012/013:
it resolves the link, and it preserves the "plain Rust tests must not fake
SPI/heap/catalog/executor/buffer behavior" contract called out in `request.md`.
Notably `LockBuffer` (line ~ in the new section) is a panic stub, not a no-op
— good.

Minor observations (non-blocking):

- `palloc` and `palloc0` both `malloc` and `abort` on OOM rather than going
  through `tqvector_*`. Fine for tests but inconsistent in style. Leave.
- `GetDatabaseEncoding` returns the hardcoded literal `6` (UTF8). This is a
  real value rather than a panic stub. Acceptable because the surrounding
  `getTypeInputInfo`/`getTypeOutputInfo` return zeros, so any caller relying
  on the encoding to drive real IO will hit a panic stub immediately after.
- `list_free`, `CacheRegisterRelcacheCallback`, `fmgr_info`,
  `pg_detoast_datum*`, `DecrTupleDescRefCount`, `ExplainProperty*`,
  `getBaseType`, `get_array_type`, `get_index_am_oid`, `exprType` are silent
  no-ops/identities rather than panic stubs. These are pure metadata or
  callback-registration helpers; making them no-ops keeps the test binary
  importable without faking backend behavior. Acceptable.

### F2. `estimate_ip_batch` bits=4 gate change is correct — accept

`src/quant/rabitq.rs:962` widens the gate from `bits_per_dim != 1 && != 8` to
`!matches!(self.bits_per_dim, 1 | 4 | 8)`. The downstream call path
(`estimate_ip_batch_checked` at line 987 → `estimate_ip_batch_impl` at line
1019) already passes `bits: self.bits_per_dim as usize` through `QueryDequantContext`,
and the bits=4 kernels are wired in `sum_query_dequant_*_bits4` (NEON, AVX2,
AVX-512, plus bf16 mirrors and pair variants — see lines 1601, 1659, 1666,
1713, 3155, 3280, 3354, 3459, and the SoA batch path at 3867
`estimate_ip_batch_avx512_bits4`). So this is **unblocking an already-landed
bits=4 implementation**, not adding new behavior. That matches what packets
b4757c347 ("Batch RaBitQ x86 bits1 scoring") and the prior bits=4 batch
commits already reviewed in this lane established.

The `code_len_for(self.dimensions, self.bits_per_dim)` branch in
`estimate_ip_batch_checked` (line 998) handles bits=4 sizing correctly via
the same `if self.bits_per_dim == 1` short-circuit it used before.

The compatibility wrapper `estimate_ip_bits1_batch` (line 972) keeps its
strict `bits_per_dim != 1` check, so no caller that asks specifically for the
bits=1 entry point is silently broadened.

### F3. target_feature detection unchanged — accept

This packet does not touch SIMD dispatch, `is_x86_feature_detected!`, or the
`PgRaBitqFeatures` gating. The test lane uses the same runtime feature probe
as production: the AVX2+FMA host runs the AVX2 path, and the `_when_available`
test naming (e.g. `x86_sum_query_dequant_bits4_matches_scalar_when_available`,
`x86_sum_query_dequant_bits1_pair_matches_scalar_when_available`) preserves
the existing pattern of feature-conditional kernels falling back to scalar
when the feature is absent. AVX-512 kernels remain untested here, as
acknowledged in `manifest.md` §Limitations.
