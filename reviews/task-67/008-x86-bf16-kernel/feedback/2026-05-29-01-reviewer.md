# Reviewer Feedback: Task 67 x86 AVX-512 BF16 bits=4 Kernel

## Verdict

Approve as a readiness slice. The kernel is correctly lane-aligned, gating is
sound, and scope is contained to bf16 bits=4. The unresolved feature-enabled
`cargo check`/`cargo test --features rabitq-bf16` build remains a follow-up that
must run on an Intel host before claiming Intel bf16 readiness, but the slice
itself reads correctly and does not change default behavior.

## Findings

### Correct: `_mm512_dpbf16_ps` lane grouping

`_mm512_dpbf16_ps(acc, a, b)` reduces 32 bf16 pairs into 16 f32 accumulator
lanes via `acc[i] += a[2i]*b[2i] + a[2i+1]*b[2i+1]`.

- Query side: `query_bf16` is loaded sequentially from `dim_index`, so lane
  `2k`/`2k+1` carry dims `dim_index + 2k` / `dim_index + 2k+1`.
- Dequant side: `write_level`/`read_level` for bits=4 (`src/quant/rabitq.rs:1381`,
  `src/quant/rabitq.rs:1398`) put dim `2k` in the **low nibble** of byte `k`
  and dim `2k+1` in the **high nibble**. The kernel builds
  `dq[2*idx] = lut_bf16[byte & 0x0F]` (`src/quant/rabitq.rs:2640-2670`) and
  `dq[2*idx + 1] = lut_bf16[byte >> 4]`, which matches the encoded ordering.

Pair alignment is consistent. 32 bf16 → 16 f32 reduction is correct.

### Correct: bf16 truncation matches encode path

`f32_to_bf16_bits` (`src/quant/rabitq.rs:1410-1412`) is pure top-16-bit
truncation (no round-to-nearest-even). The scalar tail at
`src/quant/rabitq.rs:2698-2702` reconstructs floats from the already-truncated
bf16 bits via `(bits as u32) << 16`, so the tail consumes exactly what
`prepare_bf16_state` produced. No semantic skew between SIMD body and scalar
tail, and the differential test
(`x86_sum_query_dequant_bf16_bits4_matches_bf16_scalar_when_available`,
`src/quant/rabitq.rs:6342`) compares against bf16-rounded scalar math — not raw
f32 — so a passing test reflects kernel correctness, not encode fidelity.

### Correct: `target_feature` and runtime gating

- The kernel is `#[target_feature(enable = "avx512f,avx512bf16")]`
  (`src/quant/rabitq.rs:2613`).
- Slot selection requires `features.has_avx512_bf16()`, which is
  `avx512f && avx512bf16` (`src/quant/simd.rs:168-170`).
- Dispatch is reachable only via `select_x86_query_dequant_slot`
  (`src/quant/rabitq.rs:1795-1801`) and `select_x86_query_dequant_kernel`
  which now passes the slot through instead of demoting to Scalar
  (`src/quant/rabitq.rs:1846-1847`).
- All call sites are `#[cfg(all(target_arch = "x86_64", feature = "rabitq-bf16"))]`,
  so the bf16 kernel is fully feature-gated and runtime-gated.

### Correct: bf16 mirror length guard

The new `ctx.query_bf16.is_some_and(|q| q.len() == ctx.dimensions)` check at
`src/quant/rabitq.rs:1798` ensures the SIMD body's `query_bf16.as_ptr().add(dim_index)`
loads of 32 u16 starting at `dim_index` stay within `q.len() >= dimensions`.
Combined with the `dim_index + 32 <= dimensions` loop guard
(`src/quant/rabitq.rs:2630`), this is sound. The exact-equality is slightly
stricter than the `>=` form some callers might expect, but it matches the
mirror's actual length (`prepare_bf16_state` collects exactly one bf16 per
input element, `src/quant/rabitq.rs:1422-1426`), so equality is the right
invariant.

### Acceptable: validation gap

Default-feature focused build (`--no-run`) and the standalone bf16 intrinsic
`rustc` probe both completed. The feature-enabled `cargo check --features
rabitq-bf16` could not be brought to a result locally due to a stalled cargo
process. Since the bf16 path is gated behind a non-default feature and a
non-default runtime check, this is acceptable for the readiness slice as the
packet itself acknowledges. A follow-up on an Intel host that exercises:

- `cargo check -p ecaz --features rabitq-bf16 --lib`
- runtime `x86_sum_query_dequant_bf16_bits4_matches_bf16_scalar_when_available`
- the Intel benchmark/recall gates required by Task 67

is the correct next step before declaring Intel bf16 performance.

### Scope

`git show f909b16ded2b276a10c952aab1516e00c1759b56` touches only
`src/quant/rabitq.rs` (+152/-2). No drift outside the bits=4 bf16 path: bits=1
and bits=8 selection, encode paths, and the NEON kernel are unchanged.

## Nits (optional, non-blocking)

- The `unsafe { ... }` around the two `_mm512_loadu_si512` + transmute
  expressions in `src/quant/rabitq.rs:2671-2680` is technically redundant inside
  an `unsafe fn`, but it makes the intent explicit and matches the comment.
  Fine as-is.
- The `dq` stack array is built scalar-by-scalar (32 nibble lookups per
  iteration). NEON uses the same approach. A future optimization could
  pre-vectorize the nibble unpack, but this is correctness-first and out of
  scope for the readiness slice.
