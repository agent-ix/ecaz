# Task 67 Packet 011 — x86 differential-test scaffold

Verdict: **approve-with-nits**

Commit `a22677eb8` adds a `#[cfg(test)] pub(crate) mod bench_api` inside
`src/quant/rabitq.rs` (lines 4441-4717) that exposes a `*_for_test`
registry over the existing scalar + x86 `sum_query_dequant_*` kernel

(`task67_sum_query_dequant_for_test_scaffold_registers_expected_kernels`,
`task67_sum_query_dequant_for_test_scaffold_matches_scalar_when_available`).
This closes the deferred scaffold nit from packet 001 feedback (item

dequant surface. No kernel bodies were touched.

## Review focus answers

1. **x86 entries registered for bits=1/4/8 and bf16** — yes.
   `SUM_QUERY_DEQUANT_KERNELS_FOR_TEST` at `src/quant/rabitq.rs:4472`
   registers `scalar_bits{1,4,8}`, `avx512_bits{1,4,8}`,
   `avx2_bits{1,4,8}`, and `avx512_bf16_bits4` (gated on
   `feature = "rabitq-bf16"`). Slot-to-kernel coverage matches the
   seven `QueryDequantKernel::Avx*` slots reserved in Slice A
   (`src/quant/rabitq.rs:1718-1731`), plus the bf16 entry. The
   compile-time assertions in
   `task67_sum_query_dequant_for_test_scaffold_registers_expected_kernels`
   (rabitq.rs:4774-4790) enforce the registry shape.

2. **`*_for_test` paths actually invoke the target kernel under
   feature detection, not scalar fallback** — yes. Each x86 wrapper
   carries the matching `#[target_feature(enable = …)]` and calls
   directly into the production `sum_query_dequant_avx512_bits1`,
   `sum_query_dequant_avx2_bits1`, `sum_query_dequant_avx512_bits4`,
   `sum_query_dequant_avx2_bits4`, `sum_query_dequant_avx512_bits8`,
   `sum_query_dequant_avx2_bits8`, and
   `sum_query_dequant_avx512_bf16_bits4` bodies at
   `src/quant/rabitq.rs:2617`, `2715`, `2810`, `3107`, `3155`,
   `3226`, `3280`. Signatures line up exactly with the fixture
   field plumbing (`query_rotated`, `bits1_byte_lut`,
   `bits8_query_scale`/`offset`, `query_bf16` + `dequant_lut_bf16`).
   The driver
   (`task67_sum_query_dequant_for_test_scaffold_matches_scalar_when_available`,
   rabitq.rs:4793-4845) only `unsafe { (kernel.invoke)(&fixture) }`
   after `task67_kernel_features_available` (rabitq.rs:4685-4700)
   confirms the host actually exposes the declared features, so on
   AVX-512-less hosts the AVX-512 entries are skipped, not silently
   downgraded.

3. **Differential test driver picks up new entries** — yes, but
   in-module only (see Nit 1 below). The in-module test iterates
   `bench_api::sum_query_dequant_kernels_for_test()` filtered by
   `kernel.bits == bits` and tolerance `1e-4 * max(|scalar|, 1.0)`.
   That checks scalar / AVX-512 / AVX-2 paths on bits 1, 4, 8 at
   `dim ∈ {33, 96}`. bf16 entries are correctly skipped by the
   match because `query_bf16 = None` / `dequant_lut_bf16 = None`
   make the wrapper return `None` via `?`, which the driver tolerates
   with `let Some(actual) = … else { continue }`.

4. **`target_feature` / `unsafe` boundary hygiene** — clean.
   Each x86 wrapper is `unsafe fn` with
   `#[target_feature(enable = "…")]` matching its kernel's
   intrinsic requirements (rabitq.rs:4565, 4589, 4613, 4635, 4657,
   4679, 4702). The call-site `unsafe` block is preceded by a
   feature check (rabitq.rs:4831-4834) plus a SAFETY comment
   covering both feature availability and fixture sizing
   (rabitq.rs:4836-4838). Fixture buffer sizes (`code` is
   `packed_bytes + RABITQ_SCALAR_LEN`, `query` has length `dim`,
   `bits8_query_scale/offset` filled only for `bits == 8`) match
   what the kernels read.

5. **No drift into kernel bodies** — confirmed. `git show
   --stat a22677eb8` shows a single file changed (308 insertions,
   0 deletions). Diff is entirely additive inside `rabitq.rs`,
   appended after `sign_words_from_byte_slice` and integrated
   into the existing `#[cfg(test)] mod tests`. No production
   kernels, dispatch tables, or `SimdBackend` plumbing were
   modified.

## Nits / follow-ups (non-blocking)

1. **Scaffold is in-module only; `tests/simd_diff.rs` is not yet
   wired.** The new `bench_api` is `pub(crate) mod bench_api` at
   `src/quant/rabitq.rs:4441`, distinct from the top-level public
   `pub mod bench_api` at `src/lib.rs:95` that
   `tests/simd_diff.rs:9` consumes. The NEON `*_for_test` precedent
   (`fwht_in_place_neon_for_test`,
   `hnsw_source_inner_product_neon_for_test`,
   `score_ip_from_parts_neon_for_test`) re-exports through
   `src/lib.rs::bench_api` so `tests/simd_diff.rs` can call them
   under `feature = "bench"`. The current packet keeps the
   differential in `mod tests` inside `rabitq.rs` instead, which
   satisfies the registry-shape aspect of packet 001's deferred
   nit but does **not** yet land the `simd_diff` integration-test
   coverage the original Task 67 scope item 9 implies. Either is
   defensible — the in-module path is simpler and avoids
   `feature = "bench"` gating — but the request copy
   ("future tests and benchmark audits can enumerate the optimized
   kernels") should be calibrated: today only same-crate tests can,
   because `pub(crate)` does not cross the integration-test crate
   boundary. If a later slice still wants `simd_diff.rs` coverage,
   re-export the registry through `src/lib.rs::bench_api` under
   `#[cfg(feature = "bench")]` and add a NEON sibling for symmetry.

2. **`avx512_bits4` target feature declares `avx512bw` even though
   the kernel uses only avx512f intrinsics.** The wrapper at
   `src/quant/rabitq.rs:4612-4614` declares
   `#[target_feature(enable = "avx512f,avx512bw")]`, and the
   registry entry at `4506-4512` declares
   `required_features = &["avx512f", "avx512bw"]`. The kernel body
   `sum_query_dequant_avx512_bits4` at `rabitq.rs:3155` uses only
   `_mm512_fmadd_ps` / `_mm512_loadu_ps` / `_mm512_setzero_ps` /
   `_mm512_storeu_ps` — none of which require `avx512bw`. This
   intentionally mirrors the slot gating at
   `src/quant/simd.rs:160-162` (`has_avx512_bits4 = avx512f && bw`),
   so the differential test fires exactly when production would
   dispatch. That's defensible and probably what you want, but
   worth a one-line comment in the wrapper to head off the
   "looks over-declared" question.

3. **No runtime acceptance attached.** `artifacts/validation.log`
   only cites `--no-run` compile passes plus `cargo fmt` and
   `git diff --check`. The packet is up-front about this
   (request.md lines 37-40), and on a non-AVX-512 WSL host
   `task67_sum_query_dequant_for_test_scaffold_matches_scalar_when_available`
   would only really exercise the scalar entries even if the
   `LockBuffer` symbol issue were resolved (AVX-2 entries would
   run if the host has AVX-2; AVX-512 entries would be skipped
   by `task67_kernel_features_available`). Keep the existing
   "AVX-512 runtime acceptance remains pending on suitable Intel
   hardware" note attached when packet 015/016/017 (Intel cloud
   profile + measurement) folds this scaffold into a runtime run.
