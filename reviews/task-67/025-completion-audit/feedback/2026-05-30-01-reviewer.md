# Reviewer feedback — Task 67 packet 025 completion audit

## Verdict

**Do not close Task 67 on the kernel-throughput reading.** The audit is
well-organized, the evidence pointers are accurate, and the honest split
of "kernel layer pass / SQL wall-time below 3x at nprobe ≤ 32" is exactly
what I want to see in a closeout audit. But the requested interpretation

## Gate 4 interpretation: end-to-end means end-to-end

The audit (request.md lines 9–20) argues Task 67 can close on the
"kernel-throughput" reading because the task wording says "end-to-end
RaBitQ scoring throughput". I read the same sentence the opposite way:

- Gate 4 verbatim: "On the Intel benchmark host, end-to-end RaBitQ
  scoring throughput is at least 4× current scalar across the four
  bits=8 variants, and at least 3× on the bits=1 batched path. Numbers
  published in **Slice J's measurement packet**."
- Slice J is defined as: "Re-run Task 66 Slice H's bench harness on the
  Intel host with these kernels. … Per-kernel throughput, recall delta,
  **headline wall time pre/post**."
- Per-kernel throughput and headline wall time are explicitly listed as
  separate deliverables in Slice J. The gate then says "end-to-end …
  throughput", which in this task's vocabulary is the headline wall-time
  pre/post line, not the per-kernel microbench.

Mapping that to landed evidence:

- bits=1 batched path, 3× gate, headline wall time: packet 022 reaches
  3.07× only at `nprobe=64` (`reviews/task-67/022-topk-frontier-bits1-measurement/`).
  At `nprobe=16` and `nprobe=32` the best landed result is 2.11× and
  2.52× vs packet 017 scalar. The gate is not yet met across the
  measured `nprobe` set.
- bits=8 variants, 4× gate, headline wall time: I do not have a Slice J
  end-to-end SQL measurement for the four `rabitq8*` variants at all.
  Packet 017 covered the bits=1 SQL story; packets 020 and 023 are
  per-kernel microbenches, not the Slice J headline. The 4× bits=8
  gate is unmeasured at the SQL level. The audit's "Complete" row for
  this gate rests entirely on the microbench, which is the
  per-kernel line in Slice J, not the headline line.

Closing Task 67 on the kernel-throughput reading would require Slice J
itself to be redefined — the task as written does not support that.

## Concrete remaining work to close Task 67

1. **Slice J headline bits=8 SQL measurement.** Run the Task 66 Slice H
   bench harness on `10k-intel` for `rabitq8`, `rabitq8ls`, `rabitq8c3`,
   `rabitq8c4` at the same `nprobe` set used in packet 017. Publish
   headline wall-time pre/post vs scalar. Drive via `ecaz bench suite`
   per the repo rule. Without this, gate 4 has no bits=8 evidence at
   the level the task requires.
2. **Slice J headline bits=1 SQL gate at nprobe ≤ 32.** Either land a
   further `ec_ivf` scan-path optimization above the RaBitQ kernel
   (the audit itself names this as the residual work), or get explicit
   user sign-off to scope the headline gate to "≥ 3× at the recall-
   preserving operating point" with `nprobe=64` as that point. The
   latter is a scope amendment to the task file, not a reviewer call.
3. **Slice I bf16 decision packet.** Publish the on-host bf16 vs
   non-bf16 measurement and document the gate-flip decision (or the
   explicit "no win, gate stays off" finding). Even a short packet
   under `reviews/task-67/` is fine.
4. **AVX2-only Intel coverage** (Slices C, E, G). Either measure on an
   AVX2-only host or amend Task 67 to scope AVX2 fallbacks as
   "differential-tested, no on-host bench gate". The task as written
   gives AVX2 fallbacks explicit per-slice bench targets (≥ 3× for
   bits=1, ≥ 5× for bits=4/8 at the slice level), and those have not
   been measured.
5. **AC4 regression acknowledgement.** A short note that DiskANN /
   HNSW / IVF scan tests did not regress (link the relevant test runs
   or state explicitly that no behavioral changes were made outside the
   RaBitQ scoring path) belongs in the closeout audit.

If items 2 and 4 above prefer a scope amendment over more measurement,
that's the user's call — but the amendment has to land in
`plan/tasks/67-rabitq-intel-avx-optimization.md` first, not in a
reviewer feedback file.
