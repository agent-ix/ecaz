## Findings

### F1 — Allowance choice is reasonable, but worth pinning rationale (non-blocking)

The packet picks `#![allow(clippy::incompatible_msrv)]` instead of bumping
the crate MSRV. This is the right call given that the offending intrinsics
(`_mm512_popcnt_epi64`, `_mm512_dpbf16_ps`, etc.) are reachable only via
runtime `is_x86_feature_detected!` dispatch on x86_64 hosts, so they
never execute on a host built with a too-old toolchain. Clippy's
`incompatible_msrv` does not model the dispatch and reports a false
positive. The allowance is module-scoped, not crate-wide, which keeps
the suppression near the code that needs it.

Suggestion (future packet, not blocking): add a brief in-module comment
above the new `#![allow(...)]` explaining why it is there
("AVX-512 intrinsics gated behind runtime feature detection; clippy
cannot see the dispatch") so a later reader does not silently widen the
allowance or paper over a genuine MSRV regression.

### F2 — Local clippy log does not exercise the lint that failed (non-blocking, acknowledged)

`artifacts/cargo-clippy-local.log` was produced on macOS/aarch64. The
failing surface is x86_64 Linux CI's clippy step where AVX-512 intrinsics
are visible to the MSRV checker. The packet explicitly acknowledges this
and points at the authoritative CI rerun. That is acceptable for an
unblocker. If you want defense-in-depth on a future similar fix, an
`x86_64-unknown-linux-gnu` clippy run (via Docker, devcontainer, or a
remote builder) would let us verify locally instead of round-tripping
through CI.

### F3 — Local rustfmt disagrees with CI rustfmt; checked-in formatting follows CI

`artifacts/cargo-fmt-check.log` shows local `rustfmt 1.9.0` preferring the
multi-line wrap while CI's Rust 1.95 rustfmt wants the single-line form.
The committed code matches the CI form (correct choice for CI green).
This is a toolchain pinning gap that is out of scope for this packet but
worth a future ADR: either pin `rustfmt` via `rust-toolchain.toml` so
local matches CI, or wire `cargo fmt` to a toolchain-pinned wrapper.

### F4 — Process: packet code landed bundled into the Task 33 commit (advisory)

The MSRV/fmt change landed inside `d551c40c6` "Task 33 HNSW M5 reference
refresh" (50 files changed, +12801 lines), bundled with unrelated Task 33
packets, an ADR, and large fixture/log/json artifacts. CLAUDE.md
"Coder Workflow" expects narrow, testable slices and "Commit each
reviewed code checkpoint." For a CI unblocker that touches only two files
and has its own review packet, a standalone commit
(e.g. "Allow incompatible_msrv on RaBitQ AVX-512 module + CI rustfmt")
would have made bisect, revert, and review-of-just-this-packet trivial.
The bundling does not change the correctness of the change, but it
should be avoided next time. Flag for coder note in next checkpoint.

### F5 — Process: ordinal collision with `040-local-and-aws-benchmark-rerun` (advisory, non-blocking)

There are two `040-...` packet directories under `reviews/task-67/`:

- `040-msrv-clippy-avx512-rabitq/` (this packet, has `request.md`)
- `040-local-and-aws-benchmark-rerun/` (no `request.md`, looks WIP)

CLAUDE.md "Packet Ordering" says "Prefix every packet directory with the
next task-local ordinal." Duplicate ordinals break chronological sort
and ambiguity-resolution by ordinal alone. Since the other `040` packet
has no `request.md` yet, the cheapest fix is to rename it to `041-...`
when its request is opened (or earlier if the coder is comfortable). No
action required for this packet's content.
