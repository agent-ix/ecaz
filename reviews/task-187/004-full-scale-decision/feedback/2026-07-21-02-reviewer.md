## Refinement for the follow-up: the materialization "wait" is already
## attributed — it is owner-side compute, not wire transport

Re-reading the packet 001 stage counters, the materialization path is less
opaque than the STOP framing (and my own round-1 F2 wording, "16 ms of remote
request waiting") suggests. Per scan (2 owner requests, run concurrently):

- `materialize_owner_endpoint_work` 15.360 ms =
  `owner_open_validate_work` 6.722 + `owner_payload_sql_work` 8.340 +
  `owner_node_lookup_work` 0.292;
- `materialize_request_roundtrip_work` 17.044 ms, so wire + encode + decode
  is only ~1.68 ms/scan of the materialization path;
- coordinator blocking wait `materialize_request_wait` 9.991 ms ≈ the
  concurrent critical path `owner_endpoint_critical` 8.992 ms.

So of the 10.018 ms `remote_materialize` stage, roughly 90% is owner-side
endpoint work that the existing counters already split into two concrete,
bounded targets:

1. **Per-request open/validate: ~3.36 ms per owner request (6.72 ms/scan).**
   Re-validating epoch/relation state on every materialization request is
   amortizable session state, not per-row work.
2. **Payload SQL: ~1.26 ms per returned row (8.34 ms/scan for ~6.64 rows).**
   That per-row cost points at per-candidate statement execution rather than
   one set-returning fetch per owner window.

Traversal's ~4.6 ms/query transport overhead remains genuinely
un-decomposed and still needs the nine-way counters before any traversal
candidate. But the materialization targets above need no new
instrumentation — they satisfy Task 187's "demonstrated causal target" bar
today.
