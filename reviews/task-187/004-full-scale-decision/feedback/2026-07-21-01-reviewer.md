## Findings

**F1 (P2, process — Phase 1 delivered 3 of 9 contracted components).** The
task's Phase 1 contract requires a non-overlapping 9-way split: frontier/
partitioning, connection/session state, request encode + bytes, owner reads/
decode, owner scoring, response encode + bytes, transport wait + per-owner
straggler distribution, coordinator decode/insert, and hop/batch/cache work
counters — explicitly "feature-gated and reset after warmups," i.e. building
that instrumentation was in-scope. What ran is a 3-way split (local expand,
remote expand, derived remainder) from pre-existing Task 183/191 counters.
The STOP rationale — "the dominant remote transport path is not decomposed
finely enough to attribute a change safely" — is therefore a consequence of
not building the in-scope counters, not an external blocker. I still accept
the STOP: it is honest (a candidate advanced on this evidence would violate
the task's own attribution gate), the task file's Decision section records
the gap plainly, and instrumentation-as-code arguably deserves its own
reviewed slice. But the follow-up transport task MUST inherit the full 9-way
Phase 1 contract (the per-owner encode/wait/decode/straggler counters named
in packet 004) rather than a diluted "add some counters" scope — and per
operator convention, that task is a proposal until the stakeholder confirms
its creation.

**F2 (P3, missed derivation that strengthens the STOP).** The existing
counters already bound the transport share, and the packets should say so:
remote_expand is 6.174 ms over 493 samples (~9.9 remote expansions/query,
0.626 ms each); local_expand is 1.230 ms over 398 samples (~8.0/query,
0.155 ms each). Taking local expansion as the proxy for owner-side graph
read + RaBitQ scoring work, ~0.47 ms per remote expansion (~4.6 ms/query,
~75% of remote_expand) is transport/encode/wait overhead rather than owner
compute. Combined with materialize_request_wait (9.991 of the 10.018 ms
materialization stage), roughly 16 of the 22.40 ms warm mean is remote
request wait. That is the quantitative frame the follow-up task should
open with; worth a sentence in packets 002/004 when the F3 fix is committed.

**F3 (P3, manifest typo).** Packet 001 `manifest.md` records
`run/suite-manifest.json` SHA256 as `1a6cff49f2f4c3c6…`; the committed
file hashes to `1a6cff49f4f2c3c6…` (two hex pairs transposed). The other
three digests match exactly, so this is a transcription slip, not a
provenance problem. Fix in a one-line docs commit.
