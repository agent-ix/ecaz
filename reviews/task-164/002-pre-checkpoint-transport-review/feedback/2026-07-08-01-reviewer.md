# Task 164 transport pre-checkpoint review

No signoff for the in-progress transport slice. The compile check passes, but there are blocking architecture and runtime issues before this should be wired into scans.

## Findings

### P1 - Remote hits cannot be materialized through the current AM scan contract

`remote_expand_nodes` converts every remote response into a `DistannExpandedNode` with `heap_tid: ItemPointer::INVALID` (`src/am/ec_distann/remote_transport.rs:187`). That matches the FR-079 wire shape, but the current orchestration and AM result path still carry a heap TID in every `DistannScanHit` (`src/am/ec_distann/scan.rs:83`) and `amgettuple` returns that TID to PostgreSQL with `set_scan_heap_tid` (`src/am/ec_distann/routine.rs:403`).

Once `RemoteNodeExpander` is wired, any remote-owned top-k hit will therefore try to return an invalid local heap TID. The scan may find the right remote exact distances, but it cannot produce valid SQL rows. Before wiring the transport, the task needs a materialization design for remote results: for example a coordinator-visible frozen vector/result tier keyed by vec_id, a separate remote materialization endpoint, or a changed scan contract that does not feed invalid local TIDs into `amgettuple`.

### P1 - The remote SQL binds an index name as `regclass`, not text

The transport carries `index_regclass` as a string, but the SQL uses `$1::regclass::oid` (`src/am/ec_distann/remote_transport.rs:102`) and passes `&request.index_regclass` (`src/am/ec_distann/remote_transport.rs:161`). With tokio-postgres this makes the parameter type `regclass`; the established async call sites cast string parameters as text first, for example `$1::text::regclass::oid` in SPIRE (`src/am/ec_spire/coordinator/remote_candidates/write_payload.rs:180`).

As written, the remote call is expected to fail during parameter encoding or prepare/bind instead of reaching `ec_distann_expand_nodes`. Change this to `$1::text::regclass::oid` or resolve with `to_regclass($1)` and add a loopback transport test that actually crosses tokio-postgres.

### P2 - Per-node remote expansion is sequential, not parallel

FR-081 says each hop round issues per-node expansion calls in parallel over the pooled transport (`spec/functional/index/distann/FR-081-distann-query-orchestration.md:28`). `RemoteNodeExpander::expand_nodes` iterates buckets and blocks on each `remote_expand_nodes` call before starting the next one (`src/am/ec_distann/remote_transport.rs:237`, `src/am/ec_distann/remote_transport.rs:253`).

That turns a multi-node hop into roughly the sum of remote RTTs instead of the max remote RTT. It will undercut the H x RTT measurement and does not satisfy the orchestration contract beyond the two-node case. Build a per-round set of remote futures and drive them concurrently on the runtime, then merge responses after all owners complete or fail.

### P2 - Session setup SQL is built by string interpolation

The loopback setup emits raw SQL with the entire roster spec inside a quoted literal (`src/am/ec_distann/remote_transport.rs:248`). Roster conninfo strings can contain spaces and `=`, and in practice can also contain credentials or application names that include quotes. A single quote in the roster breaks the statement; worse, this is a SQL injection surface because the string is run through `batch_execute`.

Use parameterized `set_config` calls, for example `SELECT set_config('ec_distann.roster', $1, false), set_config('ec_distann.local_node_id', $2, false), ...`, or a proper literal-quoting helper that is covered by tests.

### P2 - Transport still cannot classify retryable endpoint errors

The transport wraps any remote SQL error into a string (`src/am/ec_distann/remote_transport.rs:174`). Even if the endpoint later emits stable categories, this layer must preserve SQLSTATE/detail or map it into a typed enum so the coordinator can implement the FR-082 restart rule instead of substring matching.

It exited 0, but the log shows 14 unused-import warnings from `src/am/ec_distann/remote_transport.rs` (`reviews/task-164/002-pre-checkpoint-transport-review/artifacts/cargo-check-lib.log:3`). That will not survive the repo's `-D warnings` posture; clean the leftover scaffold imports before requesting a checkpoint.

### P3 - Reassembly collapses duplicate requested vec_ids

`RemoteNodeExpander` stores responses in `HashMap<u64, DistannExpandedNode>` and removes by vec_id while rebuilding request order (`src/am/ec_distann/remote_transport.rs:236`, `src/am/ec_distann/remote_transport.rs:263`, `src/am/ec_distann/remote_transport.rs:269`). FR-081 currently dedupes expansions upstream, so this may be unreachable in the scan path, but the `DistannNodeExpander` trait itself says one response per requested vec_id in request order, not one per unique vec_id (`src/am/ec_distann/scan.rs:46`).

Either make uniqueness an explicit precondition with an assertion/test at the seam, or reassemble by original positions so the remote implementation matches the local expander contract for duplicate inputs too.

## What was done well

- The transport keeps the existing `DistannNodeExpander` seam, so the orchestration loop does not need to know about placement buckets.
- Pooling is per backend/per conninfo and follows the same broad current-thread runtime shape as the existing SPIRE transport.
- Local and remote batches are split by the FR-078 placement helper, and local ids still use the in-process `LocalNodeExpander`.
