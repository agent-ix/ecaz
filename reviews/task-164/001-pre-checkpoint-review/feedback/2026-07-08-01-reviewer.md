## Findings

### P1 - Epoch fingerprint does not bind the build-time record/vector tier

FR-082 says the epoch fingerprint attests to the roster, placement, format version, build-time record set, and vector tier, and that every participant resolves the same manifest/placement/head sample/vector tier for that fingerprint (`spec/functional/index/distann/FR-082-distann-epoch-lifecycle.md:29`, `:53`). The implementation documents the same intent (`src/am/ec_distann/epoch.rs:6`), but `DistannEpochIdentity` only hashes epoch, format version, placement hash version, roster node ids, `node_count`, dimensions, graph degree, neighbor codec kind, and build seed (`src/am/ec_distann/epoch.rs:34`, `src/am/ec_distann/epoch.rs:125`). `local_epoch_identity` builds the same coarse identity from metadata only (`src/am/ec_distann/roster.rs:185`).

Two different published graphs can therefore have identical fingerprints if they share row count, dimensions, seed, codec, degree, epoch, and roster. That includes a stale remote node serving a different vec_id set, adjacency, head sample, codebooks, or exact vector tier with the same metadata. The remote endpoint then accepts the fingerprint and serves inconsistent records instead of triggering the FR-082 restart path.

Fix: compute and persist a deterministic epoch content digest during build/publish, then include that digest in `DistannEpochIdentity`. It should cover at least the sorted vec_id set, node-record bytes/adjacency, head sample identity, quantizer/codebook identity, and the co-placed vector-tier digest. Add a regression with two same-count indexes that differ by one source identity/vector/edge and prove their fingerprints differ.

### P2 - The SQL endpoints are declared immutable and parallel-safe while reading relations, GUCs, and snapshots

The uncommitted endpoint declares both `ec_distann_expand_nodes` and `ec_distann_epoch_fingerprint` as `#[pg_extern(immutable, parallel_safe)]` (`src/am/ec_distann/remote_endpoint.rs:52`, `src/am/ec_distann/remote_endpoint.rs:86`). Both functions read relation metadata, placement/epoch GUCs, cached index contents, heap rows, and the active snapshot (`src/am/ec_distann/remote_endpoint.rs:91`, `:136`, `:173`, `:178`, `:186`).

That is not immutable in PostgreSQL's volatility contract and should not be marked parallel-safe. The planner is allowed to treat immutable functions as independent of database state and GUC state; for this endpoint, that is exactly the state the call is validating. Mark these functions volatile and parallel-unsafe or parallel-restricted, matching the actual relation/snapshot access pattern.

### P2 - Endpoint error classes are collapsed into one generic SQL error

FR-079/FR-082 need the coordinator to distinguish a retriable epoch mismatch from non-retriable placement and structural faults. The endpoint currently returns `Result<_, String>` internally and maps every error through `pgrx::error!("{e}")` (`src/am/ec_distann/remote_endpoint.rs:77`, `src/am/ec_distann/remote_endpoint.rs:88`). The new pg tests assert substrings, but a remote coordinator should not parse human text to decide whether to restart a whole scan.

Add a typed error enum and map it to stable SQLSTATEs or a stable machine-readable error field/category. At minimum, epoch mismatch must be programmatically distinct from placement error, owned-record-missing structural fault, co-placed-vector-missing structural fault, and ordinary bad-input errors.

### P2 - The grouping helper loses original request positions needed for FR-079 order

FR-079 requires response rows to preserve request order (`spec/functional/index/distann/FR-079-distann-remote-expansion-protocol.md:44`). `group_by_owning_node` returns only `Vec<Vec<u64>>` (`src/am/ec_distann/placement.rs:78`) and the comment claims the caller can stitch buckets back into request order (`src/am/ec_distann/placement.rs:75`). Once the request is split into per-node buckets, the original positions are gone unless every caller separately retains a side map.

Make the grouping helper return original positions, for example `Vec<Vec<(usize, u64)>>`, or introduce a request-plan type that owns both per-node batches and the output reassembly order. Then test an interleaved request across two owners where the remote responses complete/concatenate in node order but the final rows still match the original input order.

### P3 - Invalid zero-node placement is silently normalized in the low-level helper

`owning_node` documents `node_count >= 1`, but in release builds it silently uses `node_count.max(1)` (`src/am/ec_distann/placement.rs:63`, `src/am/ec_distann/placement.rs:68`). `group_by_owning_node` does the same for bucket allocation (`src/am/ec_distann/placement.rs:83`). A bad empty published roster should be rejected as manifest/config corruption, not treated as a single-node epoch below the validation layer. Keep the single-node fallback in `current_placement_directory`; make the lower-level hash helper return `Result` or panic only behind an already-validated directory.
