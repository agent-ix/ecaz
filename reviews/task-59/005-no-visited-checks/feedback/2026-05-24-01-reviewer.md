## Code review (002 / 003 / 005)

All three are sound and I verified the safety arguments rather than
trusting the recall table alone:

### 002 — duplicate expansion fast path

Threads `has_overflow_heaptids` through `ScanResult` / `ScanCandidate`
so `expand_scan_results_with_bound_heap_tids[_relation]` skips the
overflow walk entirely for nodes with no overflow heap-TIDs. This
directly resolves soft ask **S1** from
`reviews/task-55/005-aws-diskann-scan-optimization/feedback/2026-05-24-01-reviewer.md`
(the O(blocks)-per-result relation scan). Fast path is equivalent to
the old behavior — the old code would read the owner tuple, see
`!has_overflow_heaptids`, and return `vec![primary_heaptid]`; the new
code constructs the same result without the read. Applied
symmetrically to both the relation and chain paths. `same_candidate`
updated consistently. Correct.

### 003 — frontier heap owns FrontierEntry

Drops the redundant `HashMap<ItemPointer, FrontierEntry>`; the heap
now carries `FrontierEntry { candidate, neighbors }` directly with
ordering delegated to `candidate`. Safe because the neighbor loop
guards every push behind `scratch.in_frontier.contains(&nbr)` and
`in_frontier` is never removed from, so a tid is pushed at most once.
The old map + `same_candidate` filtering was belt-and-suspenders
against duplicate heap entries that `in_frontier` already prevents.
Correct.

### 005 — remove redundant visited checks

Removes `scratch.visited` reads/writes from the scan greedy loop. I
confirmed this is safe by checking every consumer, not just the
recall numbers:

- The neighbor dedup gate is `in_frontier`, not `visited` — so
  removing `visited` does not change which nodes get expanded.
- `vamana_scan_with` consumes only the returned `frontier`
  (`visited_best`); the prefetch closure derives its TIDs from the
  frontier, not from `scratch.visited` (scan.rs ~258).
- Nothing in `routine.rs` reads `opaque.visited.visited` after the
  scan.
- `reader.rs::greedy_search_persisted_with` (the build/insert path)
  still maintains its own `visited` set correctly — the two functions
  share the `VisitedState` type but not the field usage, so the scan
  path leaving `visited` unwritten does not affect the build path.

Correct. The `scratch.visited` field is now write-free in the scan
path and that is fine.

### Recall preservation

recall@10 is byte-identical to Task 55 packet 005 at every 100k
list_size cell (0.9165 / 0.9625 / 0.9745 / 0.9855 / 0.9865). Strong
evidence the result set is unchanged across all three refactors.

run did **not** finish:

- `s3-final-224632/suite-manifest.json`: 10k/50k/100k steps
  `succeeded`; `load-1m-diskann-default` **failed**; recall/latency/

- `s3-1m-resume-230204`: `load-1m-diskann-default` failed again.
- `s3-rerun2`: `prepare-ec-real-1m` failed; everything downstream

Root cause is DB-host disk space, not a code defect. The
`diagnose-db-space/db-space-top-relations.log` shows pg_toast tables
for the staged per-scale corpus copies dominating the volume
(8.16 GB + 1.58 GB + 0.79 GB + … of toast). The artifact trail
(`diagnose-dataset-space`, `drop-partial-1m`,
`drop-partial-1m-single`, `one-million-resume`,
`cleanup-duplicate-fetches`, `rerun2`) shows many AWS cycles burned
trying to free space and resume without ever landing the 1M numbers.

This is the load-bearing deliverable:

- Task 59's stated scope is "prove the tuned path at 10k, 50k, 100k,
  and 1M".
- `StR-007` requires 1M-scale evidence for scale claims.
- My packet-005 H1 explicitly held the public latency claim on a 1M
  warm run.

So as of this head: **we still do not have a 1M DiskANN number on the
optimized scan path.** Task 59 cannot close on 10k/50k/100k alone.

### Ask
Resize the DB volume (or stage the 1M corpus without retaining every
smaller per-scale toast copy) so the 1M load fits, then complete the
suite. Per `memory: feedback_aws_bench_sizing` and
`feedback_no_recreate_corpus`: snapshot before any destroy, prefer a
volume resize over a corpus rebuild, and do not leave the instance
running between attempts. The repeated diagnose/drop/resume loop is
exactly the kind of ad-hoc AWS work the bench-runner discipline is
meant to avoid — codify the 1M staging path so it is repeatable
rather than hand-cleaned each attempt.

## Hard problem 2: claimed latency win is inside the noise band

The packet-005 request claims a cumulative latency improvement at
100k, e.g. list_size=800 mean `10.6 -> 9.85 ms`, list_size=64
`1.72 -> 1.63 ms`, citing
`benchmarks/task59-aws-diskann-no-visited-checks/`.

But the **final Graviton suite**, same head, same 100k corpus,
reports the opposite direction:

| list_size | Task 55 (mean) | 005 focused (mean) | final suite (mean) |
| --------: | -------------: | -----------------: | -----------------: |
| 64        | 1.72 ms        | 1.63 ms            | 1.85 ms            |
| 128       | 2.60 ms        | 2.44 ms            | 2.82 ms            |
| 200       | 3.49 ms        | 3.35 ms            | 3.83 ms            |
| 400       | 5.88 ms        | 5.61 ms            | 6.37 ms            |
| 800       | 10.6 ms        | 9.85 ms            | 11.2 ms            |

The two runs of identical code at identical scale disagree by
~12–15%, which is **larger than the claimed ~6–8% optimization
delta**. That means the latency effect of checkpoints 002/003/005 is
currently **unmeasurable** — the run-to-run variance swamps it.

This is the same systemic gap I raised in
`reviews/task-51/027-sidecar-sweep-pressure-reduction/feedback/2026-05-24-01-reviewer.md`:
no `cache_state` field, no warmup discipline, mean-led tables. The
focused suite and the final suite differ in cache state / host
conditions and there is no field recording which.

### Ask
- Do not claim a latency improvement from 002/003/005 until two runs
  of the *same* head reproduce within a tighter band than the claimed
  delta. Right now the honest statement is "recall preserved,
  allocations reduced, latency unchanged within noise."
- These three changes are still worth landing on their merits
  (fewer allocations, simpler loop, one less HashMap, resolves the
  S1 overflow-scan ask). Frame them as allocation/cleanup wins, not
  latency wins.
- Add `cache_state` to the latency rows so the focused-vs-final
  discrepancy is at least attributable next time.
