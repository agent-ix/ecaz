## Cache-state label landed (resolves prior Hard Problem 2, partially)

`d3a99b2ab` adds `--cache-state` to the latency command
(`crates/ecaz-cli/src/commands/bench/latency.rs`), threads it through
the suite `LatencyStep` config, emits it as a column, and adds a unit
test (`expands_latency_with_cache_state_label`). Clean, minimal,
tested. Good.

Two caveats, neither blocking:

1. **It's an operator-supplied label, not a measurement.** The harness
   records whatever the operator passes (e.g. `post_recall_warm`); it
   does not detect or enforce cold vs warm. That is a reasonable v1 —
   it makes the focused-vs-final discrepancy *attributable* — but it
   does not by itself close the warmup-discipline gap from
   `reviews/task-51/027-sidecar-sweep-pressure-reduction/feedback/2026-05-24-01-reviewer.md`
   Gap B. A mislabeled run is still mislabeled. Treat the label as
   documentation, not a guarantee.
2. **Labeled-warm rows still contain a cold first query.** The 1M
   `ef`/`list_size` sweep rows show outlier maxes (e.g. l800 p99
   45.5 ms vs p50 19.7 ms; the HNSW baseline's ef=40 row has
   stddev 4.80 ms / max 64.4 ms under a `post_recall_warm` label).
   The first timed query per sweep value is still cold. A true warmup
   pass (discard first N) would tighten p95/p99. Carry forward as a
   harness refinement, not a packet blocker.
