### Slice 002 follow-up (`d81097686`) — `visit_ivf_posting_refs_for_block_sequence` safe fn

**Verdict**: ✓ sound, but borderline anti-pattern A flag.

The function signature `pub(super) fn visit_ivf_posting_refs_for_block_sequence(index_relation: pg_sys::Relation, ...)` is a **safe `fn` taking a raw `*mut RelationData`**.

Per `feedback_anti_pattern_b_unbounded_lifetime`, the analogous
anti-pattern B prohibits safe `fn(*mut T) -> &'a T` (where caller
gets a reference back). This case is anti-pattern A
(safe `fn(*mut T)` with unsafe deref inside) — not explicitly
covered by the memory rule, but in the same family.

**Why it's sound in practice**:

1. The function body doesn't deref `index_relation` directly. It
   passes it to `crate::am::stream::visit_relation_block_sequence_read_stream`
   (pg18 path, also safe `fn`) or to
   `visit_all_ivf_posting_refs_for_block` (pg17 path, safe `fn`
   that calls `ivf_relation_nonnull(index_relation, ...)` to
   validate before use).
2. The eventual deref is gated by `NonNull::new(...).unwrap_or_else(error!)`
   inside `ivf_relation_nonnull`, which is the safety boundary.
3. PostgreSQL's AM callback contract guarantees `pg_sys::Relation`
   is non-null at all callback entry points, so the runtime check
   is defensive but never fires in practice.

**Why it's borderline**:

A safer signature would be:

```rust
pub(super) fn visit_ivf_posting_refs_for_block_sequence(
    index: IvfPageRelation,   // already a typed handle
    block_numbers: &[pg_sys::BlockNumber],
    payload_len: usize,
    visitor: F,
) -> Result<(), String>
```

That pushes the null check up to the call site (which is what
`flush_build_plan` does in slice 002 — pattern is well-established).
The chosen signature keeps the raw pointer in the safe surface;
sound but stylistically weaker.

**Recommendation**: file as a follow-up cleanup. Not blocking
close.

### Slice 004 (`fb75a23d4`) — `fn → unsafe fn` promotion, METRIC-GAMING with real safety-doc gap

**Verdict**: ✓ sound (no new UB), ⚠ metric gaming, ⚠ doc gap.

The slice strategy is: take helpers that are `safe fn(...)` with
internal `unsafe { ... }` blocks, promote them to `unsafe fn`, and
drop the now-redundant inner unsafe blocks. The unsafe-block count
goes down by 1 per promotion. The safety boundary moves outward
(caller now needs `unsafe { fn_call() }`).

**Where the technique is honest**:

- `set_scan_heap_tid(scan: pg_sys::IndexScanDesc, ...)`: takes a
  raw scan-desc pointer, derefs `(*scan).xs_heaptid`. Promoting to
  `unsafe fn` correctly reflects that the function is intrinsically
  unsafe (caller must provide a live scan).
- `debug_am_begin_scan`: wraps `ec_ivf_ambeginscan` which is
  `unsafe extern "C-unwind" fn`. Promotion honest.
- `configure_heap_rerank_state` consolidation (3 → 1 block): pure
  consolidation, real cleanup.

**Where the technique is metric-gaming**:

- `free_scan_prepared_query(opaque: &mut EcIvfScanOpaque)`: takes a
  safe Rust reference. The internal `Box::from_raw(opaque.prepared_query)`
  IS unsafe (caller asserts pointer provenance), but the function
  COULD be refactored to use `Option<Box<T>>` semantics with `take()`
  to be properly safe. Promoting to `unsafe fn` is the path of
  least resistance, not the path of best safety.
- `free_pq_fastscan_model`, `free_scan_query_prep`,
  `free_candidate_dedup`, `free_posting_scratch_soa` (per commit
  msg): same shape — all should arguably be `Option<Box<T>>::take`
  + `drop`.

**Real safety-doc gap** introduced or amplified by the promotions:

```
$ grep -cE "^[ \t]*(pub(\(.*\))?\s+)?unsafe fn" src/am/ec_ivf/scan.rs
55
$ grep -c "/// # Safety" src/am/ec_ivf/scan.rs
31
→ 24 unsafe fn declarations missing /// # Safety doc

$ grep -cE "^[ \t]*(pub(\(.*\))?\s+)?unsafe fn" src/am/ec_ivf/vacuum.rs
6
$ grep -c "/// # Safety" src/am/ec_ivf/vacuum.rs
2
→ 4 missing
```

**24 + 4 = 28 promoted `unsafe fn` declarations lack `/// # Safety`
documentation.** Per Rust API guidelines (and clippy
`missing_safety_doc` lint), every `unsafe fn` should document the
caller's safety contract.

By shifting safety responsibility outward without documenting it,
slice 004 makes the codebase **less locally-auditable**. A future
reviewer reading a call site `unsafe { set_scan_heap_tid(scan,
tid) }` cannot reason about what invariants the call asserts
without spelunking through git history to find the original
`fn → unsafe fn` promotion commit.

This is a real safety regression at the documentation level, even
though no new UB is introduced.
