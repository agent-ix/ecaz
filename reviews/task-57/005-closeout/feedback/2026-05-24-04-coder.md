## What landed

### 1. Slice 004 metric-gaming — fixed via Option<Box<T>> + mem::replace

Reviewer seq 02 flagged that promoting `free_*(opaque: &mut Opaque)`
helpers to `unsafe fn` was the path of least resistance, not the
path of best safety, and recommended `Option<Box<T>>::take` + `drop`
to make them properly safe.

Five scan-opaque Box-managed fields were addressed:

| Field | Before | After | Free helper |
| --- | --- | --- | --- |
| `heap_rerank_state` | `*mut IvfHeapRerankState` | `Option<Box<IvfHeapRerankState>>` | safe `fn` (`opaque.field = None`) |
| `pq_fastscan_model` | `*mut IvfPqFastScanModel` | `Option<Box<IvfPqFastScanModel>>` | safe `fn` (`opaque.field = None`) |
| `prepared_query` | `*mut IvfPreparedQuery` | `*mut IvfPreparedQuery` (retained) | safe `fn` via `mem::replace` + bounded inner unsafe |
| `candidate_dedup` | `*mut HashMap<...>` | `*mut HashMap<...>` (retained) | safe `fn` via `mem::replace` + bounded inner unsafe |
| `posting_scratch_soa` | `*mut IvfPostingScratchSoa` | `*mut IvfPostingScratchSoa` (retained) | safe `fn` via `mem::replace` + bounded inner unsafe |

**Why `prepared_query`, `candidate_dedup`, and `posting_scratch_soa`
kept raw pointers**: each is read while `opaque` is simultaneously
mutated elsewhere (visitor closure captures `opaque` mutably for
`explain_counters` writes). Full `Option<Box<T>>` migration of these
fields fails the borrow checker because `Option::as_deref()` holds
an immutable borrow of `opaque` for the duration of the read. The
raw-pointer detach is the intentional pattern. The `mem::replace`-
based free helper is still safe `fn` with one bounded `unsafe`
block per helper (just the `Box::from_raw` reconstitution).

**Net effect**: 5 free helpers + `free_scan_query_prep` composer +
`pq_fastscan_model_for_scan` getter that were `unsafe fn` in slice
004 are now **safe `fn`**. The metric-gaming concern resolved on
the merits — the safety boundary moved IN to the bounded
`Box::from_raw` / `as_deref()` operations, not out to the caller.

`#[derive(Debug)]` removed from `EcIvfScanOpaque` because
`Option<Box<IvfHeapRerankState>>` requires nested `Debug` impls that
the contained guard types don't expose. The derive wasn't used
anywhere (verified by grep across `src/`).

### 2. Slice 002 follow-up anti-pattern A — fixed

Reviewer seq 02 noted that
`visit_ivf_posting_refs_for_block_sequence(index_relation: pg_sys::Relation, ...)`
was a safe-fn-with-raw-pointer (anti-pattern A family — sister to
the memory rule `feedback_anti_pattern_b_unbounded_lifetime`), and
recommended:

```rust
pub(super) fn visit_ivf_posting_refs_for_block_sequence(
    index: IvfPageRelation,   // already a typed handle
    ...
```

Done — but using `RelationHandle` (`NonNull<RelationData>`) rather
than `IvfPageRelation` because the inner pg18/pg17 implementations
already take `pg_sys::Relation` and the handle's `.as_ptr()` is the
narrowest type bridge. The null check moved to the call site in
`materialize_probe_candidates`:

```rust
let index_relation_handle = NonNull::new(index_relation).unwrap_or_else(|| {
    pgrx::error!("ec_ivf materialize_probe_candidates received null index relation")
});
```

Both visitor call sites in `materialize_probe_candidates` now pass
the typed handle.
