## Bottom line

**Well-scoped. Endorse as written, with three additions.** The plan
respects the index-isolation rule, gates decisions on measured
evidence, promotes one slice at a time, and carries the right stop
conditions. The additions below close gaps that already bit earlier
lanes.

## Strengths

- Both storage formats (`turboquant` + `pq_fastscan`) on **isolated
  surfaces** so the planner can't pick a sibling index — matches the
  index-isolation rule and avoids the cost-model trap.
- Recall-comparable `ef_search` sweep across both formats.
- Gate 1 (general vs PqFastScan-specific) and Gate 2 (portable vs
  Graviton-specific) are both evidence-gated, with a one-slice-at-a-time
  promotion rule.
- Host precheck row (CPU/memory/storage/PG settings/extension SHA/
  config hash) directly addresses the host-parity reporting gap I
  raised in task-51/027/01. Good.
- 1M stop-condition on storage feasibility is exactly right given the
  disk-space failures below.

## Additions

### A1. Require `cache_state` on every latency row

The harness now emits `--cache-state` (commit `d3a99b2ab`). The
required latency rows here should carry it so the focused-vs-final
variance problem (documented in task-59/005/01) is attributable for
HNSW too. Add `cache_state` to the "latency mean/p50/p95/p99" line in
the Required Baseline Matrix.

### A2. The 1M disk-space blocker is inherited, not new — fix it at infra level first

Task 62's 1M stop-condition is good, but the root cause is already
known: the `10k-medium` volume cannot hold staged per-scale corpus
copies plus indexes. This blocked DiskANN 1M (twice) and HNSW 100k
(task-61/002 C4), and HNSW's ~3x-larger index makes it worse. Don't
rediscover this at 1M — size the volume or drop-between-scales in the
suite/runner **before** the matrix runs, and record the chosen staging
path in the packet so it's repeatable rather than hand-cleaned. Per
`memory: feedback_aws_bench_sizing`, `feedback_benches_must_be_repeatable`.

### A3. Comparator rows must assert host parity, not just cite numbers

The acceptance criterion "compare HNSW rows against pgvector HNSW,
pgvectorscale DiskANN, vchord RaBitQ, and ecaz IVF/RaBitQ" inherits the
unresolved cross-packet host-parity gap (task-51/027/01 Gap C). Those
comparator numbers were taken on a possibly-different host. Either
re-run the comparators on the same Graviton profile in-suite, or state
the host delta explicitly per row — don't present a cross-host
comparison as head-to-head.

## Net

Endorse. Fold A1–A3 into the packet before the matrix runs; A2 is the
one that will actually block 1M if not handled up front.
