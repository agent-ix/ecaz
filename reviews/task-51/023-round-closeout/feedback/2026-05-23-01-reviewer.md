## Two real concerns in the AWS sidecar tails

The Pareto cells have a serious tail problem worth flagging before
the product follow-up starts:

| Cell | sidecar p50 | sidecar p95 | sidecar p99 |
| --- | ---: | ---: | ---: |
| f16 random-id c1 | 18.76 ms | **324.07 ms** | **529.69 ms** |
| f16 TID-sorted c1 | 0.52 ms | 0.79 ms | 1.92 ms |
| rabitq8 TID-sorted c4 | 1.12 ms | 1.72 ms | **334.87 ms** |

Two failure modes visible:

1. **Random-id has catastrophic tails** (p99 ~530 ms while p50 is
   18.8 ms — ~28× tail blowup). That's not a normal sidecar I/O
   distribution; it looks like queue stalls or cache-miss cascades.
   Closeout calls random-id a Pareto point for completeness, but
   the tail makes it unshippable as-is.
2. **rabitq8 TID-sorted under c=4 has a p99 of 335 ms** while p50
   is 1.1 ms (~300× tail blowup). c1 was clean (p99=0.5 ms). So
   concurrency introduces tail blowup even in the tid-sorted path
   — exactly the concern I flagged in 022 feedback about the c=1→c=4
   ratio compression carrying additional risk.

Neither tail is a blocker for closing Task 51 — they're follow-up #1
problems. But they need to be in follow-up #1's brief, not buried
in the closeout's appendix.
