# Reviewer Feedback: IVF Scratch SoA Batch Decode (packet 015, plan Exp 3)

Scope: `reviews/task-51/015-ivf-scratch-soa-batch-decode`, code
commit `a22ca8453` "Add opt-in IVF scratch SoA batch decode."

## What works

- Honest negative result: 2.2% local p50 improvement (603.7 → 590.5 ms)
  against a 20% candidates/sec gate is correctly reported as a
  non-promotion. Self-rejection on the gate is the right call.
- Recall byte-equivalence holds across paths (`0.9750 / p10=0.9000 /
  NDCG=0.9986` on both). That's the load-bearing safety property —
  whatever the scratch-SoA path does, it doesn't drift results.
- Opt-in via GUC, isolated per-variant table, identical work counters
  (posting pages 5192, postings scored 138476). Methodology is clean.

## The 2% number probably doesn't mean what it looks like

Look at what the commit actually changed:

> Copies tuple fields into SoA buffers, then reuses existing scalar
> scoring (not true vectorized kernel).

That's a **memory-layout-only** change. The scratch SoA prototype in
the plan §3 explicitly describes "score the batch through a chunked
bits=1 path" — the win was always supposed to come from the
*scoring loop*, not from where the bytes sit before scoring.

Reading 2.2% on this implementation tells us:
- Scratch buffer reuse is bounded and not allocating per-candidate ✓
- The memory-layout transform is roughly free (no regression)
- Whether the chunked bits=1 SIMD path would win is **not yet
  measured** — that experiment hasn't actually run

So I would not yet conclude that Exp 3 is dead. The current measurement
rules out *the SoA copy alone* as a win, which was always the expected
result (you're paying for a copy and getting no scoring benefit from
it). The actual Exp 3 question — does chunked bits=1 scoring over the
SoA layout move the needle — is still open.

## Asks before declaring Exp 3 done

1. **Wire the SoA path to a chunked bits=1 scorer**, not the existing
   scalar one. The NEON byte-LUT work from packet 003 already
   exercises chunked bits=1; the scoring kernel is in `bench_api`. If
   the chunked path can be reached from the SoA buffer without
   another copy, that's the actual experiment.
2. **Then re-measure candidates/sec**, not just wall-clock p50.
   Candidates/sec isolates the scoring kernel from posting iter cost
   and is the metric the plan's promotion gate names. The current
   packet reports p50 only.
3. If the chunked path *also* fails the 20% gate, that's evidence
   the bits=1 scalar path is already close to the kernel floor on
   this CPU, and the plan's "scratch SoA → Layout v2" gate can be
   honestly closed. Land that finding as a round-level note.
4. **Local PG18/WSL2 is the wrong host for the kernel question.**
   The byte-LUT win is NEON-specific. A local kernel "no win" is
   ambiguous on WSL2; a Graviton "no win" is conclusive. If the
   chunked path looks plausible locally, the next step is one AWS
   Graviton cell (single nprobe, q=200 is fine for a microbench)
   before any further investment.

## Lower priority

- The runtime-blocked posting-scratch test (`pg_re_throw` symbol)
  is the existing pgrx-test backend issue; not introduced by this
  packet. Skip — benchmark runtime evidence is sufficient.
- Opt-in default-off is correct for an exploratory path. If a future
  variant wins, the on-by-default decision is separate.

## Recommendation

**Do not close Exp 3 yet.** The packet correctly rules out
SoA-layout-only as a win, but the experiment Exp 3 actually proposed
(chunked bits=1 scoring over SoA) hasn't been run. Wire the chunked
path, measure candidates/sec, then either promote or close the
experiment with evidence. Until then this packet is one of two halves
of the Exp 3 measurement.
