## Concern — the harness does not measure what its name implies

The fundamental issue: this is a **"source access is free"
measurement**, not a "sidecar storage" measurement.

`build_sidecars` loads the full corpus source column into an
`Array2<f32>` in process memory before reranking, then scores the
candidate frontier against that in-memory array. There is no second
I/O on the sidecar side — `sidecar_p50 = 1.5 ms` for f32 at
candidate_k=50 is essentially "score 50 candidates against a vector
already in L2/L3."

That makes the harness an upper-bound oracle, not a measurement of
any of the storage shapes the plan talks about:

1. **In-index inline** (vchord-style — source bytes packed into the
   same pages as the candidate codes). Source access is on the same
   I/O stream as the scan. The harness's "free" assumption is roughly
   correct here by construction.
2. **Sidecar table, random id lookup.** Source bytes live in a
   separate table keyed by id. Cost is ~the existing heap-rerank
   fetch pattern, minus the toast-detoast on `real[]`. The harness
   does **not** model this.
3. **Sidecar table, TID-sorted with prefetch and a packed fixed-width
   layout.** Can approach in-index, but only with deliberate
   engineering. The harness does not model this either.

`plan/tasks/51` Non-Goals explicitly rejects (1) as a product
direction ("Do not make inline source-vector sidecars the default
product direction"). So the realistic product target is (2) or (3) —
exactly the cases the harness doesn't measure.

Practical risk: a sidecar product decision driven by these numbers
could ship something that lands much closer to today's heap+toast
cost than the harness suggests.

### What the harness can and cannot answer

- **Can answer:** the recall ceiling of each rerank format at a
  given candidate_k (f32/f16 preserve, rabitq8 loses ~0.045 at
  width=50). Useful — closes the recall-quality question.
- **Can answer:** the pure scoring CPU cost of each format
  (~1.1–2.6 ms at k=50). Useful — confirms scoring is not the
  bottleneck.
- **Cannot answer:** end-to-end p50 of a real sidecar read path
  on Graviton.
- **Cannot answer:** whether (2) recovers any of the projected
  win from the Pareto table, or whether only (1)/(3) do.

### Suggested next slice (in priority order)

1. **Document the harness's "free I/O" assumption in
   `request.md` and `manifest.md` of this packet.** Without that
   note, downstream readers will treat the `total_bound_p50` column
   as a real-product latency forecast, which it is not.
2. **Add a real-I/O sidecar microbenchmark variant** to the same
   harness, before any product decision:
   - Build a per-id sidecar table (fixed-width bytes, no `real[]`,
     no toast) for the f16 and bits=8 variants on the same isolated
     prefix.
   - Run two read modes per variant: (a) random id lookup,
     (b) TID-sorted batch fetch with prefetch.
   - Report `sidecar_io_p50` separately from `sidecar_score_p50`,
     so the I/O vs CPU split is visible.
3. **Then re-evaluate** the Pareto table in `plan/tasks/51` against
   the real-I/O numbers. The middle Pareto cells (f16, bits=8) may
   collapse toward existing heap cost under naive sidecar I/O, or
   may stay close to the upper bound with TID-sorted layout. Either
   answer is a load-bearing input to the round's exit decision.
4. **Defer the f32 sidecar variant** until (1)–(3) are done. The
   f32 "upper bound" is only meaningful as an in-index inline
   ceiling, and the Non-Goals already rule that out as a product
   path. Carrying f32 forward without an in-index storage path
   blurs the analysis.

## Lower-priority items

- `recall_p10 = 0.9000` at nprobe=32 across all variants — the
  width=50 candidate frontier is the floor; f32 and f16 cannot
  recover what wasn't in the candidate set. Worth a one-line note
  in `manifest.md` so the f16/f32 "matched-recall" claim isn't
  overread.
- `candidate_sql_p50 ≈ 107 ms` at 50k nprobe=64 is the
  `rerank=off` IVF scan returning the full candidate set. Confirm
  in the manifest whether this is candidate_k=50 truncated at the
  client or the full posting frontier — the cost shapes differ.
- q=200 is documented as a local-screen waiver; that is correct
  per the recommendation flow in 006/002 feedback.

## Recommendation

The harness is good infrastructure and the recall-quality answer
it produces is reusable. Do **not** treat the `total_bound_p50`
column as a sidecar-product latency forecast. Land the real-I/O
sidecar variant before any product decision; until then, the
harness is an oracle, not a measurement of the shapes the plan
actually proposes shipping.
