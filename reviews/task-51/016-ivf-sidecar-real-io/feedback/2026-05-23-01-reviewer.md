# Reviewer Feedback: IVF Sidecar Real-I/O (packet 016)

Scope: `reviews/task-51/016-ivf-sidecar-real-io`, code commit
`0b359e5dd` "Add real-I/O sidecar rerank modes," benchmark packet at
`benchmarks/task51-local-ivf-rabitq-sidecar` (extended). Directly
responsive to feedback at
`reviews/task-51/008-ivf-rabitq-sidecar-rerank-bench/feedback/2026-05-23-01-reviewer.md`.

## This is the missing measurement. Good packet.

The 008 feedback's core ask was: separate `sidecar_io_p50` from
`sidecar_score_p50` and run **real** sidecar reads, not in-memory
oracle. This packet does both, with the right two read modes
(random-id and TID-sorted), against an unlogged fixed-width `bytea`
PLAIN-storage sidecar table that avoids both `real[]` and toast.

The numbers are the load-bearing answer to "is a separate-table
sidecar a viable product path":

| Read mode | I/O p50 (50 candidates) |
| --- | ---: |
| `free` (in-memory oracle) | ~0 ms |
| `random-id` | ~17–18 ms |
| `tid-sorted` | ~0.9–1.4 ms |

That's the whole picture in three rows. Random-id sidecar would
absorb most of the projected sidecar win (it's in the same ballpark
as today's heap+toast cost); TID-sorted preserves it. The
"sidecar vs in-index inline" question now has a real answer:
**TID-sorted sidecar can plausibly realize the upper bound, random-id
cannot.**

## The product-question this opens

TID-sorted reads require candidate IDs to be available in physical
order at scan time. The current IVF approximate frontier comes out
sorted by approximate score, not by TID. So the product question is
no longer "sidecar vs inline" — it's **"can we keep TID-sorted
sidecar fetches under realistic workload conditions?"** That has
several sub-questions:

1. **Sort cost.** Sorting the candidate frontier by TID before the
   sidecar fetch is O(k log k) on a small k (50–256). Tiny — probably
   irrelevant. The harness already pays this for the `tid-sorted`
   mode; cost should be visible in the numbers (it isn't called out).
2. **Concurrent inserts / churn.** TID locality of the sidecar table
   depends on insert order matching corpus insert order. After
   updates/deletes, TIDs scatter. The harness builds the sidecar
   from a static corpus snapshot; that's the optimistic case.
3. **Page cache reuse.** The 1.4 ms TID-sorted result on a 50k
   fixture almost certainly fits the whole sidecar in OS cache
   (~293 MiB for f32, ~146 MiB for f16, ~74 MiB for rabitq8). At 1M
   on Graviton with realistic working sets, this number will be
   different. Probably still much better than random-id, but not
   1.4 ms.
4. **Concurrent query interference.** Single-thread harness. Under
   concurrency, sidecar table cache hit-rate behavior is its own
   measurement.

## Asks

1. **Document the TID-sorted assumptions in the packet manifest:**
   static corpus, single-thread, 50k fits in cache, sidecar built
   in-order. These are loadbearing for the result and need to be
   visible to anyone reading the Pareto table.
2. **One Graviton 1m cell** for each of f16 random-id, f16
   tid-sorted, bits=8 random-id, bits=8 tid-sorted. q=200 latency
   is enough — this is a microbench, not a product gate. Same suite
   config, same isolation, snapshot it. That answers "does the
   tid-sorted advantage hold at 1m on Graviton" — the only question
   the local 50k cannot answer.
3. **Defer the f32 variant on AWS** — Non-Goals already rules out
   f32 as a product direction. Reading the f32 numbers locally is
   fine as an upper bound check; spending Graviton time on it is
   not.
4. **One concurrency cell** (c=4 or c=8, single nprobe) once the
   Graviton numbers exist. Sidecar cache-hit behavior under
   contention is a real product question and the harness can
   answer it cheaply.
5. **Surface candidate frontier TID-sort cost** in the metric set
   (`sidecar_sort_p50` or fold into `sidecar_io_p50` with a note).
   At k=50 it's negligible, but for honesty in the Pareto table.

## What this changes about the round

Before 016, the open product question was "in-index inline vs
sidecar," with a strong implicit assumption that sidecar would lose.
This packet says: sidecar can win **if access pattern is
TID-sorted**. That's a real product path that doesn't require
Posting Layout v2 / format bump / forced rebuild.

The product follow-up task (whatever it ends up being called) should
be scoped around "TID-sorted sidecar fetch path during IVF rerank,"
not around "in-index inline storage." Saves a large category of
work from being premature.

## Recommendation

Accept the packet — it cleanly closes the 008 feedback and shifts
the round's product question in a productive direction. Land the
manifest assumption notes (ask 1) before promoting any conclusion
to AWS. Schedule one Graviton 1m microbench (asks 2 + 4) before
the round writes its final recommendation. Do not promote f32
beyond the upper-bound role.
