# Reviewer Feedback: Bench Harness And Spec Cannot Answer Head-To-Head Questions

Scope: this is **not** feedback on the 027 code change itself (the
one-variant-at-a-time pressure reduction is fine — local tests pass,
no behavior regression). This is feedback on the bench harness and the
bench spec it implements, both of which produced the AWS sidecar
results in `benchmarks/task51-aws-rabitq8-sidecar-full-sweep/` and the
prior `benchmarks/task51-aws-ivf-rabitq-current-head-final-gate/`.

I am writing this under packet 027 because it is the most recent
sidecar harness change and is the right inbox slot for the coder to
pick up the harness/spec issues called out below.

## What I tried to use the benches for

A user asked, in effect, "is ecaz IVF+RaBitQ faster than vchord at
1M on AWS, and at what recall, on what hardware?" Using only landed
packet evidence, I cannot answer that question. Specifically:

- `task51-aws-rabitq8-sidecar-full-sweep` reports a `candidate_sql_p50`
  of **1759.5 ms** for the IVF candidate scan at nprobe=128.
- `task51-aws-ivf-rabitq-current-head-final-gate` reports
  `latency-1m-rabitq1-rerank` at nprobe=128 of **34.6 ms p50** for the
  same access method on the same DB shape and head.
- vchord baseline in `benchmarks/comparators-50k-100k-1m/` is
  **80.4 ms p50 at 1M**.

Pick the wrong ecaz row and you conclude "ecaz is 22× slower than
vchord". Pick the other and you conclude "ecaz is 2.3× faster than
vchord". The bench evidence supports both readings. That is a
benchmark process failure, not a "missing detail in one packet".

## What the bench harness is missing — process, not one-off

These are structural gaps in `crates/ecaz-cli/src/commands/bench/*`
and the result rows it emits. Fixes belong in the harness and in the
bench spec, not in any individual packet manifest.

### 1. No warmup discipline

`sidecar_rerank::collect_candidates` starts the per-query
`Instant::now()` timer on query #1 (`sidecar_rerank.rs:467`). On a
freshly-restored EBS snapshot or a fresh PG restart the first many
queries are dominated by EBS lazy-load + shared-buffer cold-misses
and have nothing to do with steady-state index performance. There is
no `--warmup-queries N` flag, no auto-detection of cold cache, and no
separate cold-vs-warm reporting. This is the most likely cause of the
1759 ms vs 35 ms discrepancy above.

**Required harness behavior**:
- A first-class `warmup_queries: usize` field on every bench step
  config that runs SQL, executed against the live query set, whose
  timings are *excluded* from p50/p95/p99.
- A `cache_state: cold|warm` column in every `results.jsonl` row that
  records which regime the row represents.
- An option to run both phases in one step (`cold_n + warm_n`) and
  emit both rows.

### 2. No host parity metadata on rows

`results.jsonl` rows for sidecar, latency, recall, and storage do not
carry the AWS instance type, EBS volume type/IOPS/throughput, or
PostgreSQL `shared_buffers`/`effective_cache_size`. The comparator
manifest documents these in prose; per-row JSON does not. That makes
cross-packet comparisons (ecaz head vs vchord baseline) impossible to
machine-verify and reliant on operator memory of which packet was on
which host.

**Required harness behavior**:
- Add `host.instance_type`, `host.cpu_arch`, `host.db_volume_type`,
  `host.db_volume_iops`, `host.db_volume_throughput`,
  `host.shared_buffers`, `host.effective_cache_size`,
  `host.maintenance_work_mem` (whatever Postgres exposes via
  `current_setting`) to every emitted row.
- Suite manifest already records environment in prose — promote those
  fields into the structured row schema.

### 3. No same-host comparator step

There is no FR-038 step kind that runs vchord (or pgvectorscale, or
pgvector) inside the same suite execution as the ecaz rows being
claimed against. Comparator rows live in older, separately-scheduled
packets on what may be a different host. Per
`memory: feedback_no_unchanged_comparator_runs`, unchanged comparator
versions on unchanged hardware do not need rerun — but the harness has
no way to *assert* host equality between the current ecaz run and the
pinned comparator packet it cites. Today the bench cannot answer
"head-to-head on this hardware", only "ecaz on host A vs vchord on
host B, trust me they were the same shape".

**Required harness behavior**:
- A `comparator` step kind in `ecaz bench suite` that runs a pinned
  vchord/pgvectorscale/pgvector benchmark inside the same suite,
  producing rows in the same schema. Gated by a
  `--skip-unchanged-comparators` flag that requires the suite to
  point at a baseline packet AND assert (via the host-parity fields
  above) that the current host matches it; otherwise the comparator
  step runs.
- If we choose not to add the step kind, the spec needs to mandate
  that any head-to-head claim include a structured host-equality
  assertion row in `results.jsonl`.

### 4. Recall and latency cannot be joined to the same sweep tuple

`latency` rows and `recall` rows are emitted as separate `kind`s with
no `(nprobe, candidate_k)` join key on the recall side. So when the
final-gate packet reports "p50 34.6 ms at nprobe=128" there is no
machine way to say "and the recall at that nprobe was X". A reviewer
has to read prose. That is exactly the path that lets latency wins
masquerade as wins at lower recall.

**Required harness behavior**:
- Every `kind: latency`, `kind: recall`, `kind: explain`, and
  `kind: sidecar-rerank` row MUST carry the full sweep tuple
  (`access_method`, `storage_format`, `rerank_mode`, `nprobe`,
  `candidate_k`, `k`, `concurrency`, `read_mode`, ...) so rows from
  the same suite can be joined by sweep identity.
- Today many of these are blank on `latency` rows
  (`task51-aws-ivf-rabitq-current-head-final-gate/results.jsonl`
  latency rows have empty `access method`, `index`, etc.).

### 5. No build-time / build-cost step kind

`StR-006` and the comparator manifest both track build time as a
first-class claim (vchord 3.6 min, pgvectorscale DiskANN 72 min, etc.
at 1M). FR-038-AC-2 only requires `load, recall, latency, storage,
explain, raw`. There is no `kind: build` row in any Task 51 packet,
so the comparator's "vchord builds in 3.6 min, what does ecaz do?"
question is unanswerable from `results.jsonl`. The build wall-time
exists in some commit messages and prose manifests but not in
structured form.

**Required harness behavior**:
- Add a `build` step kind that runs `CREATE INDEX`, captures wall
  time, peak `pg_stat_progress_create_index` memory, final
  `pg_relation_size`, and emits a `kind: build` row carrying the
  same identity fields as latency/recall.

### 6. Candidate SQL timing duplicated across variants

`task51-aws-rabitq8-sidecar-full-sweep` emits identical
`candidate_sql_p50 = 1759.456 ms` on all four variant rows. The
sidecar bench shares the candidate frontier across variants (per the
027 commit message), but the duplicated number obscures that and
inflates noise. Worse, the variant rows do not carry a
`shared_candidate_run_id` so a reviewer cannot tell at a glance
whether the candidate column is per-variant or shared.

**Required harness behavior**:
- Emit one `kind: candidate-frontier` row per (nprobe, candidate_k)
  sweep value, and have each `kind: sidecar-rerank` row reference it
  by id. Stop duplicating the same number across variant rows.

### 7. Sidecar size is a formatted string, not numeric

`sidecar_size: "1.43 GiB"` is a presentation string in `values.*`,
not a number. Cannot be summed, compared, or thresholded
programmatically. Same goes for `sidecar_bytes_per_vector` (it is
numeric here but inconsistent across other rows).

**Required harness behavior**:
- All sizes in `results.jsonl` SHALL be raw bytes (`u64`); pretty
  strings may appear alongside but never as the primary field.

## Spec gaps that allowed the harness to ship this way

The spec already gestures at most of these requirements but does not
enforce them at the row level, which is why the harness can comply
on paper while producing rows that don't answer the questions.

### Gap A — NFR-015 §4 requires "cache state" only in reports, not rows

`NFR-015 §4` says latency reports SHALL include "iteration count,
cache state, p50, p95, p99, mean, and whether the planner path was
forced or natural." The harness satisfies this by allowing the
operator to write `cache_state` into the prose `manifest.md`. There
is no acceptance criterion saying the structured `results.jsonl`
row MUST carry it.

**Spec fix**: add an AC under NFR-015 (or a new FR derived from
FR-038) requiring `cache_state` and `warmup_queries` as mandatory
fields on every `kind: latency`, `kind: recall`, and
`kind: sidecar-rerank` row produced by `ecaz bench suite`.

### Gap B — No requirement for warmup discipline anywhere

There is no FR or NFR that says benchmark steps measuring steady-state
behavior SHALL exclude warmup queries from percentile aggregation.
Without that, the harness is free to (and currently does) include
cold-cache pages in p50.

**Spec fix**: add an NFR (or extend NFR-015) requiring that any
steady-state latency claim defines its warmup policy in the suite
config and that the harness honors it. Cold-cache numbers may still
be reported but MUST be tagged `cache_state: cold` and MUST NOT be
the basis of a steady-state comparison.

### Gap C — No host-parity requirement for cross-packet comparisons

`NFR-007` covers provenance per-packet but does not require host
equality for head-to-head comparisons across packets. `NFR-015 §8`
requires hardware identification only for "product benchmark reports",
leaving non-product comparisons (Task 51 review packets vs the pinned
comparator packet) unbound.

**Spec fix**: extend NFR-015 §8 (or add NFR-016) so that any
review-class comparison claim ("ecaz beats vchord at 1M") requires
either (a) a same-suite comparator step or (b) a per-row host-parity
assertion against the cited comparator packet. Without one of those,
the claim is inadmissible.

### Gap D — FR-038 step kinds do not include `build`, `comparator`, or `candidate-frontier`

FR-038-AC-2 fixes the step set at `load, recall, latency, storage,
explain, raw`. This is why the harness has no build-time row, no
in-suite comparator, and no shared-frontier abstraction — they are
literally not in the spec.

**Spec fix**: extend FR-038-AC-2 to add `build`, `comparator`, and
`candidate-frontier` step kinds, with behavior bullets for each in
the FR-038 Behavior section.

### Gap E — No required join schema across `kind`s from one suite

`NFR-015 §1` lists identity fields ("access method, opclass, storage
or quantizer format, format-specific options, AM reloptions, session
GUC overrides, rerank mode") but does not say these fields MUST be
present on EVERY emitted row regardless of kind. So `latency` rows
can be emitted with blank identity (and currently are), making the
recall/latency join impossible.

**Spec fix**: tighten NFR-015 §1 to "Every row emitted to
`results.jsonl`, regardless of `kind`, SHALL carry the full identity
tuple."

### Gap F — StR-007 cloud benches have no anti-cold-snapshot procedure

`StR-007` describes the provision→install→load→bench→tear-down cycle
and emphasizes preserving corpus via snapshots, but says nothing
about warming the snapshot before the bench. Pause/resume from EBS
snapshot is the *default* path for repeatability, and on EBS it is
also the worst case for cold-cache reads. The spec should require
the cloud bench cycle to include an explicit warmup phase after
snapshot restore, before the timed suite begins, with the warmup
treated as part of provisioning, not measurement.

**Spec fix**: add a Success Criterion to StR-007 that
`ecaz cloud bench` performs a documented warmup pass after
snapshot/resume before timed measurements, and that this is recorded
in the suite manifest as a provenance line.

## Minimum bar to re-enable head-to-head latency claims

Before any Task 51 packet is allowed to make an ecaz-vs-vchord
latency claim:

1. Harness emits `cache_state` on every latency-shaped row (Gap A,
   harness item 1).
2. Harness emits host-parity fields on every row (harness item 2).
3. Cloud bench includes a warmup pass after snapshot restore
   (Gap F).
4. Comparator step kind exists OR per-row host-parity assertion
   against the cited comparator packet is mandatory (Gap C +
   harness item 3).
5. Latency and recall rows for the same sweep can be joined by a
   stable key (Gap E + harness item 4).

Without these, I cannot sign off on a comparator claim out of any
future Task 51 final-gate packet, and the round closeout should not
claim ecaz beats vchord on AWS.
