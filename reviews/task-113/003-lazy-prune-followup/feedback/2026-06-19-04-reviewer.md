# 113/003 — Deep audit follow-up: dense-prune verdict has not been implemented

Reviewed current branch source plus the committed Task 113 benchmark feedback and
shared benchmark artifacts. Static/read-only review only; no new tests or benchmarks
run.

## Findings

### P2 — The measured dense-path slowdown is still enabled by default

The committed benchmark feedback concludes that posting-bound prune is a row-path win
but a dense-path loss: dense/coarse_rerank prune-on measured `7.22 / 13.3 ms` versus
prune-off `6.98 / 13.1 ms` at nprobe `64 / 200`, with equal recall, and recommends
gating prune to the row path (`feedback/2026-06-19-01-reviewer.md:24-43`;
also summarized in `benchmarks/ivf-111g-115-attribution/FINDINGS.md:137-146`).

The code has not applied that recommendation. `ec_ivf.posting_bound_prune` still
defaults on globally (`src/am/ec_ivf/options.rs:49-56`), and the scan initializes a
single `running_top` for every non-residual RaBitQ scan before it knows whether the
selected path will be row, dense direct, or dense coalesced
(`src/am/ec_ivf/scan.rs:1497-1511`). The dense direct path still calls
`posting_prune_cutoff` and records bound-pruned postings
(`src/am/ec_ivf/scan.rs:2095-2124`).

Please either gate the bound-prune work to the row/SoA path where it measured as a
win, or explicitly document that the project is accepting the measured dense-path
overhead. As written, the default-on setting preserves a benchmarked slowdown in the
dense/coarse_rerank path.

### P2 — The benchmark suite still does not surface the prune-work counter

The earlier feedback said the `postings_pruned_by_bound` counter should be exposed in
`results.jsonl` (`feedback/2026-06-19-01-reviewer.md:42-43`). The follow-up response
only fixed artifact/manifest provenance (`feedback/2026-06-19-03-reviewer.md:14-19`);
it did not add the counter to the benchmark output.

The counter exists in the scan debug snapshot (`src/am/ec_ivf/scan.rs:3495-3554`) and
the EXPLAIN counter plumbing exists, but the committed dense/row prune JSONL artifacts
do not carry `postings_pruned_by_bound`. Without that per-run counter, the +4% row
win is a latency observation but the packet still cannot prove how much actual prune
work occurred in each cell. Please extend `ecaz bench suite` / latency result parsing
to capture the counter before treating prune-work attribution as closed.
