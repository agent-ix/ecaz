# 113/003 — Benchmark: posting-prune is recall-safe; +4% on row path, inert on dense path (codex P2 answered)

Evidence: `benchmarks/ivf-111g-115-attribution/` (FINDINGS.md, `head-prune-ab`
+ `head-dense-prune-ab`), fixed `.so` 67e1534c, A/B via
`ec_ivf.posting_bound_prune` off vs on, 100k, sweep `[8,16,32,64,128,200]`.

## Measured

**Row path (storage_format=rabitq):**

| | recall np64 / np200 | p50 np64 / np200 |
|---|---|---|
| prune off | 0.9655 / 0.9990 | 17.4 / 45.5 ms |
| prune on  | 0.9655 / 0.9990 | 16.7 / 43.6 ms |

**Dense path (storage_format=coarse_rerank — codex P2):**

| | recall np64 / np200 | p50 np64 / np200 |
|---|---|---|
| prune off | 0.9650 / 0.9985 | 6.98 / 13.1 ms |
| prune on  | 0.9650 / 0.9985 | 7.22 / 13.3 ms |

## Verdict

- **Recall-safe on both paths** (off == on, byte-identical) — confirms the
  pruned==unpruned invariant by end-to-end measurement, including the dense path
  codex P2 flagged as untested.
- **Row path: ~4% latency win** at matched recall — the lane's one real,
  measured latency improvement. Keep (default-on is fine).
- **Dense path: no win, ~3% slower** — confirms codex P2's other point: the dense
  / coarse_rerank direct-scan does not pre-prune (only at retention), so the
  cutoff is pure bookkeeping there. **Recommend gating the prune to the row path**
  (or accept it as recall-neutral overhead on dense).
- The pruned-by-bound counter is not surfaced in `results.jsonl`; expose it so the
  prune impact is visible per run.
