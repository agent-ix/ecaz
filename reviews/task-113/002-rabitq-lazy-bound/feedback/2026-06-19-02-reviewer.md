# 113/002 — Follow-up review: lazy-bound activation and dense-prune evidence gaps

Reviewed current `main` at `0a195764a`, the 113/002 request, manifest, and the
carried Task 112 feedback. Static review only; no new tests or benchmarks run.

## Findings

### P1 before enabling skips — the exact-score trap is still present at the lazy call site

113 correctly rewrites `RaBitQLazyBound` as a bound on exact score error rather
than estimate-space cutoff, and the default bound still disables all skips. That
part is recall-safe today.

The activation seam is still not correct, though. The 113/002 packet says
`scan.rs` feeds the candidates' "true approximate frontier scores" so
`worst_kept` becomes finite (`request.md:38-42`). But `worst_kept` is the driver's
exact-score floor by contract (`src/am/ec_ivf/lazy.rs:288-312`). Current
`scan.rs` passes the approximate score vector as the `fetch_exact` closure
(`scan.rs:2239-2259`), so a future finite `RaBitQLazyBound` plus k-cap would stop
against an approximate floor while proving against an exact floor.

This is not a current recall regression because `RaBitQLazyBound::default()` and
`min_kept = rerank_len` make skips impossible. It is a blocker for the advertised
"live seam" becoming active. The fix belongs with the future k-cap/per-candidate
bound work: exact rescoring has to happen on demand inside the lazy driver, or the
proof/driver contract must be rewritten and tested for approximate/exact
divergence.

### P2 — Packet claims dense posting-prune coverage that the committed evidence does not show

The packet says `ec_ivf.posting_bound_prune` is threaded through row, SoA scalar
fallback, and dense-block direct scan (`request.md:75-83`), and calls
`test_ec_ivf_posting_bound_prune_equals_unpruned` the row/dense-path
recall-safety proof. The manifest cites only one PG test for pruning:
`cargo pgrx test pg18 posting_bound_prune` with 1 passed
(`artifacts/manifest.md:16-24`, `:29-34`).

That test builds:

```sql
WITH (nlists = 4, nprobe = 4, training_sample_rows = rows_len, quantizer = 'rabitq')
```

in `src/tests/ec_ivf.rs:3893-3910`, without `dense_posting_blocks = 1` or
`dense_posting_typed_layout = 1`. I do not see packet-local evidence that the
dense-block direct path, typed dense layout, or coalesced dense path was exercised
under prune on/off. The scalar row/SoA proof may be fine, but the packet should
either add dense-specific A/B tests or narrow the coverage claim to the path the
test actually builds.
