## The exact-score-vs-estimate trap (your main finding)

You are correct: the lazy stop compares `lower_bound(a)` against `worst_kept`,
which is an **exact** heap-f32 neg-IP, so the bound must be a sound lower bound
on the **exact** score `e = -⟨q, o⟩`, not on the estimate. My initial doc cited
"surface (1)" (the estimate-space Cauchy-Schwarz posting-prune cutoff) as the
derivation — that is the wrong reference and, if anyone implemented `slack` from
it, a recall bug.

Fix (commit `b93e536b4`): the `RaBitQLazyBound` derivation now uses exactly the
residual bound you constructed:

```text
⟨q, o⟩ = ⟨q, x_dec⟩ + ⟨q, o − x_dec⟩
|⟨q, o − x_dec⟩| ≤ ||q|| · ||o − x_dec||
||o − x_dec||² = ||o||² − 2·o_dot·||o||·||x_dec|| + ||x_dec||²
```

so `|e − a|` is bounded per-candidate by `||q|| · ||o − x_dec||`, all
recoverable from the stored scalars — distinct from both the estimate cutoff and
the probabilistic ε-envelope. The affine `a - slack` code shape is unchanged;
only the contract for what `slack` must bound is corrected (the residual budget).
Module docs, the struct/field docs, the `rabitq.rs` cross-reference, and
`scan.rs` are all aligned to this.

On tightness (your open question): a *global* deterministic `slack` (sup of
`||q||·||o − x_dec||`) is sound but loose — at 1-bit RaBitQ `||o − x_dec||` is
large, so the stop fires rarely/never. That is now documented as the honest
finding, and the genuinely tight + sound path (carry the per-candidate residual
bound on the frontier candidate) is recorded as remaining Phase 4 work. I did
**not** force the probabilistic envelope (Non-Goal honored).
