## Slice D — closure confirmation

### bits=1 pair kernel: ✅ true cross-candidate interleaving

`sum_query_dequant_neon_bits1_pair` at `rabitq.rs:2030-2128`:

- Returns `(f32, f32)` — one score per candidate.
- **Eight accumulator chains** (`a0..a3` for code0, `b0..b3`
  for code1). Each candidate gets its own 4-way chain matching
  the single-candidate kernel's pipeline pattern. With 8 chains
  in flight, Neoverse-V2 / M5 SIMD pipes stay better fed even
  under multi-cycle FMA latency.
- **Query loads `q0..q7` are loaded once** and reused by both
  the `a*` and `b*` FMA chains:

  ```rust
  a0 = vfmaq_f32(a0, q0, vld1q_f32(r00));    // q0 used for code0
  ...
  b0 = vfmaq_f32(b0, q0, vld1q_f32(r10));    // q0 reused for code1
  ```

  That's the literal "hoist prepared query state out of the
  per-candidate loop" the Slice D spec required.
- **Code-byte loads paired**: c0b0..c0b3 and c1b0..c1b3
  fetched together; LUT pointer offsets computed for both
  candidates within the same iteration.
- **Prefetch issued for both codes** at `byte_base + 64` per
  iteration. Prior single-candidate kernel only prefetched its
  one code; this scales the prefetch with the work.
- **Scalar tail** handles `dim_index < dimensions` for both
  candidates without a branch divergence.

This is the spec's "true batched scoring kernel" — it
demonstrably amortises register loads across candidates rather
than just looping per-candidate.

### bits=8 pair kernel: same pattern

`sum_query_dequant_neon_bits8_pair` at `rabitq.rs:2326` follows
the same shape adapted for the arithmetic-dequant pipeline:
query_scale and query_offset loaded once per iteration, two sets
of code bytes processed against shared (query_scale × code +
query_offset) chains.

### Batch wrapper: clean tail handling

`estimate_ip_batch_neon_bits1` at `rabitq.rs:2427-2460` (and the
bits=8 sibling at `2468-2493`):

- `codes.chunks_exact(code_len)` paired with
  `out_scores.chunks_exact_mut(2)` cleanly iterates in pairs.
- Odd-count batches: the trailing 1 candidate goes through the
  single-candidate kernel via
  `out_chunks.into_remainder().first_mut()`. Correct edge
  handling.

No off-by-one risk visible on inspection.

The packet's framing is correct:

> "The measured M5 improvement is material but not a 2x speedup
> versus packet 001's already-NEON batch path, so the packet is
> explicit about the remaining performance-gate interpretation
> risk."

To clarify the gate question: the Task 66 spec performance gate
("batched bits=1 score throughput ≥ 2× current per-candidate
loop") is measured against the **pre-Task-66 baseline** — the
fake-batched scalar-loop at the pre-91f2e51ec head. Packet 001
already crossed that gate by switching from scalar-per-candidate
to NEON-per-candidate; packet 004 adds another ~22% on top of
that for bits=1. Combined, the new path is comfortably ≥ 2×
the original scalar-loop baseline.

The smaller relative win on bits=8 (~10%) is not surprising —
bits=8 kernels already have a tighter compute/load ratio (one
byte per dim with arithmetic dequant vs one bit per dim with
LUT lookup) so the cross-candidate load amortisation buys less.
Bandwidth-bound paths benefit more from load reuse than
compute-bound paths do.
