## Slice-by-slice findings

### Slice A — dispatch seam: ✅ clean, real seam

`rabitq.rs:1561-1664`. The shape:

- `QueryDequantContext<'a>` — owned-borrow struct carrying all
  prepared query state.
- `QueryDequantKernel` enum — `Scalar | NeonBits1 | NeonBits4 |
  NeonBits8 | NeonBf16Bits4` with `#[cfg(target_arch = "...")]`
  guards on the NEON variants.
- `select_query_dequant_kernel(ctx)` — top-level selector
  dispatching on `crate::quant::simd::backend()` (the existing
  `OnceLock<SimdBackend>` with `SimdBackend = { Scalar | Avx2Fma
  | Neon }`).
- `select_neon_query_dequant_kernel(ctx)` — NEON-arm sub-selector
  by `ctx.bits`.
- `sum_query_dequant_dispatch(ctx, code)` — matches on the
  selected kernel and calls the right `unsafe` NEON fn.

For Task 67: the `Avx2Fma` arm at `rabitq.rs:1647-1652` is the
explicit slot. Task 67 will need to add `Avx2Bits{1,4,8}`,
`Avx512Bits{1,4,8}` variants to `QueryDequantKernel` and a paired
`select_x86_query_dequant_kernel` helper. That's "the slot
mechanism" — touching `rabitq.rs`'s dispatch surface but not the
shared scoring fan-out, which is what Task 67's "MUST NOT need
to touch `rabitq.rs` outside the slot mechanism" allows.

The `sum_query_dequant_with_bf16` body collapses to a thin
context-builder shim (`rabitq.rs:1532-1558`) so Task 67 doesn't
need to touch it.

One structural call-out: `estimate_ip_batch_impl` does its own
match on `QueryDequantKernel` (`rabitq.rs:2693-728` in current
HEAD line numbering). So Task 67 will need to extend two match
sites, not one. Worth noting in Task 67's plan but not a Task 66
blocker.

### Slice B — NEON bits=8 arithmetic-dequant kernel: ✅ clean

`sum_query_dequant_neon_bits8` at `rabitq.rs:2147` follows the
arithmetic-dequant plan from the task spec:

- No `dequant_lut` gather — `query_scale` and `query_offset`
  precomputes are passed in as `&[f32]` slices.
- 4-way unroll (`acc0..acc3`) matching the bits=1 / bits=4
  kernel pattern.
- `vld1q_u8 → vmovl_u8 → vmovl_u16 → vcvtq_f32_u32` widen
  chain, then `vfmaq_f32` of `query_offset + code_f32 *
  query_scale` (the precompute already folded the scale + query
  pairwise).

`# Safety` doc names the precondition (NEON availability +
slice lengths). ✓

Covers all four IVF bits=8 variants (`rabitq8`, `rabitq8ls`,
`rabitq8c3`, `rabitq8c4`) because they share the same bits=8
code byte layout — the dispatch goes through the same
`select_query_dequant_kernel(ctx)` regardless of which c-clip
variant the prepared state encodes.

### Slice C — query-side precompute: ✅ clean

`bits8_dequant_linear_params(dimensions, quant_clip) → (scale,
offset)` (`rabitq.rs:1452-1478`) returns the linear-dequant

(`rabitq.rs:864-871`), so they're built once per query and
reused across candidates.

`bits1_byte_lut` is also stored on `PreparedEstimator` already
(`Option<Box<[[f32; 8]; 256]>>`) — pre-existing, not a regression.
The per-query allocation concern I flagged in the task spec
turned out to be already-owned state; nothing to move.

## Blocking issues

### B1 — "batched" NEON kernels are loop-of-single-candidate

`rabitq.rs:2261-2280` (`estimate_ip_batch_neon_bits1`):

```rust
unsafe fn estimate_ip_batch_neon_bits1(...) {
    for (out, code) in out_scores.iter_mut().zip(codes.chunks_exact(code_len)) {
        let sum = unsafe {
            sum_query_dequant_neon_bits1(query_rotated, dimensions, byte_lut, lut, code)
        };
        *out = finish_scalar_only_estimate(dimensions, 1, sum, code);
    }
}
```

Same shape for `estimate_ip_batch_neon_bits8`
(`rabitq.rs:2282-2304`).

The Task 66 spec for Slice D was:

> Slice D — true batched scoring kernel that hoists prepared
> query state out of the per-candidate loop, replaces the
> fake-batched `estimate_ip_bits1_batch` loop-of-scalar at
> `rabitq.rs:933-973`.

What landed:
- ✓ Hoists the **dispatch** decision out (one
  `select_query_dequant_kernel` call per batch instead of per
  candidate).
- ✓ Uses NEON kernels per candidate instead of scalar.
- ✗ Does NOT hoist the prepared query state into a kernel-level
  outer loop. Each candidate iteration re-enters
  `sum_query_dequant_neon_bits1` / `_bits8` and re-issues the
  same query-state loads.

The improvement is real (no per-call scalar→NEON crossing tax,
no per-call dispatch tax), but it's a loop-of-NEON, not a
cross-candidate-interleaved SIMD batch. The Criterion log
(`artifacts/criterion-rabitq-neon.log`) shows single-score
numbers but no batched-throughput delta, so we can't yet
measure how much the missing cross-candidate interleaving
costs.

**Two paths to close:**

1. Land a true cross-candidate kernel — process 2-4 candidates
   per outer NEON iteration, reusing `query_scale` / `query_rotated`
   register loads across them. This is the FastScan-style
   amortization the spec language described.
2. Formally amend Slice D's scope to "API-level batched dispatch
   over a NEON per-candidate kernel" and update the Task 66
   spec text accordingly. The current implementation satisfies
   that weaker statement.

Either is acceptable. Path 1 is technical work; path 2 is a
spec amendment. Don't paper over the divergence by closing the
slice with the current implementation under the original spec
language.

### B2 — Slice H is missing the recall delta

Packet 001's "Review Notes" line 40 explicitly defers recall
evidence:

> Recall/SQL suite evidence is not included in this first packet
> because these changes are scoring-kernel equivalent and
> covered by scalar/NEON differential tests; follow-up full IVF
> sidecar suites can reuse the new Criterion group and
> sidecar-rerank batch path.

The Task 66 spec validation gate says:

> Recall must hold within 0.5 pp on whatever fixtures exercise
> bits=8 IVF-RaBitQ scoring.

The differential tests (`neon_sum_query_dequant_matches_scalar_bits{1,4,8}`
at `rabitq.rs:3744`, `3829`, `3862`) are necessary but not
sufficient. They prove the NEON kernel agrees with the scalar
kernel within float tolerance on synthetic inputs. They do NOT
prove the IVF-RaBitQ scan path produces the same recall numbers
end-to-end, because the path includes the prepared-query
precompute, the IVF posting traversal, the rerank pipeline, and
any threshold/budget interactions.

Per memory `feedback_dont_overclaim_done` — the task isn't
done until both exit-criteria bullets AND the documented
validation gate are met.

**To close:** run the existing IVF-RaBitQ sidecar bench suite
(or the recall harness used by `task51-local-rabitq8-sidecar-recall-sweep`)
on the four bits=8 variants and report Δrecall@10 vs the
pre-Task-66 head at L=64,128,200 (or whatever list-size shape
the existing baselines use). Within 0.5 pp = pass.

Acceptable substitute if running the full sweep is heavy: a
1-fixture smoke (e.g. `m5_diskann_real10k` or the synth fixture
used by the differential tests) showing identical recall to the
scalar-fallback path, plus a written argument that the kernel
equivalence test transitively guarantees recall parity. The
latter requires confirming no IVF-side budget heuristic that
might react differently to identical scores — I'd accept the
argument with that caveat documented.

## Safety scan

Per memory `feedback_dont_defer_safety_fixes` and
`feedback_anti_pattern_b_unbounded_lifetime`:

- **Every new `unsafe fn` has a substantive `# Safety` doc.**
  Confirmed by inspection at `rabitq.rs:2138` (bits=8 kernel),
  `2210` (prefetch), `2256` (batch bits=1), `2275` (batch
  bits=8). Each doc names the runtime feature precondition
  and slice-length contracts. ✓
- **No `fn(*mut T) -> &'a T` lifetime-laundering.** `grep -E
  "fn .* \*mut .* -> &"` on the new code returns no matches.
- **Runtime feature detection paired with SAFETY comments at
  call sites.** All `unsafe { sum_query_dequant_neon_* }`
  call sites in `sum_query_dequant_dispatch`
  (`rabitq.rs:1578-1626`) are inside `#[cfg(target_arch =
  "aarch64")]` arms of a match guarded by
  `select_neon_query_dequant_kernel`, which itself gates on
  `crate::quant::simd::backend() == SimdBackend::Neon`. The
  backend detector at `src/quant/simd.rs:20-42` runs
  `std::arch::is_aarch64_feature_detected!("neon")` before
  returning `Neon`. So the chain is: runtime detection → cached
  backend → match arm → unsafe call. That's correct, and the
  pre-existing `// SAFETY: NEON feature confirmed at runtime`
  comments are preserved by the refactor.
- **No new unsafe outside `target_feature` kernel bodies.** The
  only non-`target_feature` unsafe added is `prefetch_read_l1`,
  which uses `core::arch::asm!` for `prfm pldl1keep` — that's
  legitimate inline asm, and its `# Safety` doc correctly notes
  the instruction is non-faulting. Acceptable.

No safety blockers.
