## Verdict

**Approve the architecture; request one change to the scalar parity contract
before Phase 2 implementation.** The module shape, counter contract, width
gating, SIMD staging, and safety boundary are all sound and match the Task 92 /
ADR-076 / LUT32 conventions verbatim. One pinned acceptance gate — strict
`f32::to_bits()` scalar parity — is, as written, **not achievable on the dev or
bench hosts** and must be redefined before code lands, or Phase 2 will either
fail CI or get the gate silently relaxed under schedule pressure.

## REQUEST CHANGES — Finding 1 (must fix before Phase 2)

**Strict `f32::to_bits()` parity against `estimate_ip_scalar_only` /
`estimate_ip_bits1_batch` is unachievable on aarch64 or x86_64 SIMD hosts.**

The design (request line 42; design lines 146, 169–174) pins the Phase-2 scalar
gate as direct `f32::to_bits()` equality of the new scalar block kernel — modeled
on `sum_query_dequant_bits1_byte_lut_scalar` (`rabitq.rs:1976`) — against the
pre-kernel scorers. But neither reference scorer runs the byte-LUT scalar path on
a SIMD host:

- `estimate_ip_scalar_only` → `sum_query_dequant_with_bf16` →
  `sum_query_dequant_dispatch` (`rabitq.rs:1624`). On aarch64, bits=1 with the
  byte LUT present **always** selects `QueryDequantKernel::NeonBits1`
  (`select_neon_query_dequant_kernel`, `rabitq.rs:1904`) — never the scalar
  fallback. On x86_64 it selects `Avx2Bits1` whenever `avx2 && fma`
  (`rabitq.rs:1864`).
- `estimate_ip_bits1_batch` → `estimate_ip_batch_checked` →
  `estimate_ip_batch_impl` (`rabitq.rs:4145`) dispatches the same way
  (`Avx2Bits1` / `NeonBits1` / AVX-512), again not the scalar loop.

The dispatched NEON kernel `sum_query_dequant_neon_bits1` (`rabitq.rs:2184`)
uses `vfmaq_f32` (fused multiply-add, single rounding) across four accumulators
on a 32-dim stride, then a tree reduction `((acc0+acc1)+(acc2+acc3))` followed
by `lanes[0]+..+lanes[3]`. The scalar byte-LUT reference does separate `*` then
`+` (two roundings) accumulated sequentially in 8-wide groups. **These produce
different f32 bit patterns in general** (FMA fusion + a different summation tree
both change rounding). So a byte-LUT scalar kernel will be `to_bits()`-equal to
the dispatched reference only on a scalar-only host — which is neither this dev
host (darwin/aarch64) nor the Graviton/Intel bench hosts.

Pick one and write it into the packet before Phase 2:

1. **(Recommended)** Anchor the scalar kernel's strict `to_bits()` gate to
   `sum_query_dequant_scalar_fallback` (the forced-scalar path), and grade the
   new kernel against the *production dispatched* `estimate_ip_scalar_only` /
   `estimate_ip_bits1_batch` under the same ≤4-ULP / 1e-6-relative tolerance you
   already apply to the SIMD variants. This keeps a real bit-exact anchor while
   being honest that the dispatched scorer is FMA-based on every host that ships.
2. Make the scalar block kernel mirror, per arch, the exact reduction order of
   the dispatched kernel (fragile; couples the "scalar" kernel to NEON/AVX2
   internals — not recommended).
3. Drop strict `to_bits()` entirely and use ULP tolerance for the scalar kernel
   too — acceptable but loses a deterministic anchor.

## Finding 2 (must resolve as part of Finding 1)

The design asserts the **same** scalar kernel is `to_bits()`-equal to **both**
`estimate_ip_scalar_only` (per-candidate) **and** `estimate_ip_bits1_batch`
(batch) (design lines 170–173). Those two references dispatch to *distinct*
per-candidate vs batch kernels (`sum_query_dequant_neon_bits1` vs the batch
`estimate_ip_batch_*_bits1` family) with their own blocking and reduction. Before
asserting a third implementation equals both, add a one-shot test that confirms
the existing scalar and batch references already agree bit-for-bit with each
other on the target host. If they don't, no single kernel can satisfy both gates
and the tolerance framing from Finding 1 is mandatory, not optional.

Note also: the weighted-sum decomposition in design §SIMD lines 189–200
(`neg*Σq + (pos-neg)*Σ_{bit=1} q[i]`) is algebraically correct but is yet another
op order — keep it out of whatever path you designate as the bit-exact anchor.

## Finding 3 (recommendation, non-blocking)

**Add the `Diskann` variant to `CandidateBatchScoringSurface` in Phase 2, not
Phase 6.** Routing DiskANN through `Unknown` in the interim (design line 271)
pollutes the shared `unknown` counter namespace during exactly the measurement
window the closeout matrix draws from, and the design already concedes the enum
value is "likely cleaner." Landing it up front is a one-line enum + match-arm
change (the surface already has a stable `index()` mapping at
`candidate_batch.rs:110`) and removes a re-attribution step later. Your call, but
flag it explicitly in the packet either way.
