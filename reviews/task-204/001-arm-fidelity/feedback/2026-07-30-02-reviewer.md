# Task 204 / 001-arm-fidelity — do not wire the NFR-021 `≤ 2.0` gate yet

Short addendum to `2026-07-30-01-reviewer.md`, narrowing one instruction in it.

My seq-01 "Open item 1" asked for two things under Phase 3: a computed
cross-scale growth row, and a gate that fails the run on breach. After reading
DistributedANN (arXiv:2509.06046) directly, I want to split those
apart. Full reasoning and citations are in
`reviews/task-205/003-ab/feedback/2026-07-30-02-reviewer.md` and
`reviews/task-205/003-ab/artifacts/paper-algorithm-citations.md`.

**Build the row. Do not build the gate.**

The paper does not contain the invariant NFR-021's Measurement table states. It
accepts ~10× space amplification by design (§2.2, eq. 1), reports 780 TiB against
a conventional index's 270 TiB and calls that the cost of the approach (Table 1),
and scales by spreading across "over a thousand machines." The only thing it
bounds independent of N is the orchestration service's own state — `H_R` of size
`k` and `H_C` of size `L` (§2.4).

On a roster fixed at three nodes, per-node bytes must grow ~linearly with N. The
10.79 that Task 205 measured is the correct answer for a properly sharded index,
not a breach. A `≤ 2.0` hard failure wired into every distann gate run would halt
Tasks 205 through 209 on their first run, including runs of exactly the
architecture NFR-021 exists to bless.

So for Phase 3/4:

1. **Emit the growth row.** Still worth having — it is real data, and Task 205
   had to hand-compute it into a markdown sidecar, which is the pattern Task 204
   exists to end. Emit it as a measurement, unjudged.
2. **Hold the gate** until NFR-021's Measurement row is resolved by its owner.
   The two candidate resolutions are: scale the roster with N so the ratio
   measures distribution rather than corpus size, or restate the metric as
   coordinator-resident / non-owned bytes.
3. **Consider gating on the second metric instead**, which this packet already
   emits and which needs no cross-scale ratio at all: the coordinator's own
   `physical_benchmark_storage_node` row. Owner-control reports
   `graph_side_bytes=0`; the coordinator-replica arm reports `1,659,518,976`.
   That single-scale comparison is the paper-faithful test of "does any node hold
   index state it does not own," it discriminates correctly between the two arms
   measured here, and it would not have blocked the Task 205 A/B.

Everything else in seq-01 stands unchanged, including the ACCEPT.
