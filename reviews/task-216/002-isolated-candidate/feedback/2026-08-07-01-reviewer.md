# Task 216 / 002-isolated-candidate — CHANGES REQUESTED

The STOP is the right call. The recorded *reason* for it is wrong, and if it
goes into the roadmap as written it closes the `MAT-15` family on evidence
that does not support that closure. Two methodology defects also need fixing
before `MAT-21` or any other candidate runs in this lane.

Verified first, so it is clear what I am not disputing: both suite manifests
report `status=succeeded`; the cited latency, recall, storage, and topology
lines match `results.jsonl` and the packet-local summary logs; the control and
candidate worktrees were source-clean at `e8f15ab0c` / `6662b302f`; no Task
215 defaults, MAT-21, or traversal changes are stacked into either arm. The
regression itself is real and reproducible from the artifacts.

## P1 — the 45 ms regression is 100% in one stage, and that stage is not the one MAT-15 addresses

The end-to-end delta decomposes cleanly:

| stage (per scan unless noted) | control | candidate | delta |
|---|---:|---:|---:|
| `custom_scan_total` | 38.34 ms | 83.78 ms | +45.44 |
| `materialize_owner_payload_sql_work` (owner-summed, samples=100) | 40.376 ms | 118.422 ms | +78.05 |
| `materialize_coordinator_decode` | 0.076 ms | 0.096 ms | +0.02 |
| `traversal_total` | 8.57 ms | 10.21 ms | +1.64 |
| `payload_bytes_returned` | 576,576 B | 576,945 B | +0.06% |

Every millisecond of the regression is inside the owner's payload SQL. Nothing
moved on the wire (bytes are flat to 0.06%) and nothing moved on the
coordinator.

The leading hypothesis is `build_payload_sql` in
`src/am/ec_distann/remote_endpoint.rs`. The change moves the projection into a
`LEFT JOIN LATERAL (SELECT <CASE…send(col)…> AS payload_value_N) AS payload ON
true` and then references those aliases from two places: the cumulative offset
array and the `||` concat chain. For the `k` projected columns, the offset
array alone contains `k(k+1)/2` `octet_length(payload.payload_value_j)`
references. This bench projects 4 columns (`payload_columns_requested`
124.88/scan ÷ `remote_candidates_requested` 31.22/scan), so the SQL holds 10
offset references plus 4 concat references — **14 references to the send
expressions where the control had 4**.

A single-row `SELECT` with no `FROM` is a subquery-pull-up candidate, so those
references very plausibly inline back into 14 evaluations of the `CASE
WHEN … THEN ''::bytea ELSE typsend(heap.col) END` expressions per row rather
than 4. At ~18.5 KB of payload per row (576,576 B ÷ 31.2 rows), re-detoasting
and re-`typsend`-ing the wide column several extra times per row, plus the
`k-1` growing intermediate concatenations, is the right order of magnitude for
a 2.93× move in exactly this stage and nothing else.

Cheap way to confirm or kill this before anything else: run `EXPLAIN (VERBOSE)`
on the string `build_payload_sql` emits for a 4-column projection and count how
many times the send expressions appear in the final plan's target lists. If
they appear once each, my hypothesis is wrong and the cost is the concat chain
alone; either way you get the answer in minutes without a rebuild.

**The consequence for the packet:** the packet measured *packing performed
inside the owner's payload SQL* — the stage attribution in packet 001 named as
already dominant. It did not measure "packed payload buffers." A conforming
MAT-15 builds the packed buffer in Rust in `materialize_row_payloads_impl`
after the existing `bytea[]` comes back, or evaluates each send exactly once
(CTE `AS MATERIALIZED`, or offsets derived Rust-side from the array lengths).
Nothing in this evidence says packing is slow; it says this SQL is slow.

## P1 — but do not re-run MAT-15 either: its ceiling was 0.19%, and that was knowable from packet 001

The stronger argument, and the one that should carry the STOP: MAT-15's
addressable cost is coordinator-side decode allocation, which control measures
at **0.076 ms per scan against a 40.60 ms scan — 0.19%**. Even a flawless
implementation that drove that to zero would be invisible. Response bytes were
already effectively unchanged, so there is no wire win to bank either.

Packet 001 screened `MAT-15` first because
`materialize_owner_payload_sql_work` (~39 ms) was dominant. That stage's cost
is heap access plus `typsend` on wide columns — MAT-15 does not touch either.
The screen mapped the candidate onto a stage it cannot move. I accepted that
screen in `001-attribution/feedback/2026-08-06-02-reviewer.md`; that acceptance
was wrong on this point, and the correction belongs in this lane's record.

So: keep the STOP, replace the rationale. "MAT-15 has a 0.19% ceiling on the
measured profile" closes the family correctly and permanently. "Our MAT-15 was
2.1× slower" closes it on an implementation artifact and invites someone to
reopen it later with a better implementation for a win that cannot exceed
0.19%.

## P1 — the two arms are not the same index, and that is why identity moved

A payload *representation* change cannot alter which rows are returned. Recall
moved (0.9275 → 0.9295), the ordered predictions differ in 2/200 rows, and the
persisted head seed digests differ (`d25e8d4d…` vs `0e623a8d…`). Those three
facts together are not an unexplained identity anomaly — they are proof that
each arm built its own generation and the two generations are not identical.

The packet is right that the difference is not MAT-15-caused, and right to
refuse to launder it. But it stops one step short: the cause is the lane
design, not an open mystery. `task216-mat15-100k.json` runs
`distann-local-multinode` with `skip_install: false` per arm, so each arm
provisions a fresh cluster and a fresh build.

Fix for the next candidate: **build the generation once and swap only the
extension binary between arms**, or pin whatever input is drifting so two
fresh generations from one config are bit-identical. Until one of those holds,
no A/B in this lane can assert ordered-result identity, and every recall
comparison carries generation noise. This is a lane-blocking item — it will
hit MAT-21 exactly the same way.

The latency conclusion survives this defect, for the record: `traversal_hop_rounds`
(584) and `ranked_candidates` (2336) are identical across arms, so the two
generations imposed near-identical traversal work and the +78 ms sits in a
stage the generation difference does not plausibly reach.
