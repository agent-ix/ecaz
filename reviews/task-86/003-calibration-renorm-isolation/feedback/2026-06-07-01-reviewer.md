# Packet 003 — Calibration / Renorm Isolation — APPROVE

## Verdict

**APPROVE as a clean orthogonality probe.** The packet does
exactly what its name says — isolates the renorm-scaling
contribution from the rest of TQ+ — and reports the result
honestly.

## What landed

Commit `84c4ff340` — +39/−4 LOC, refactor-only in
`src/quant/prod.rs`:

- Split the scoring path:
  `score_..._from_prepared_unrenormalized_for_test` returns
  `score + bias`; the renormalized wrapper just multiplies by
  `encoded.renorm`. Encoder is unchanged, only the scorer
  applies/skips the per-vector scalar.
- Test now reports `tqplus_unrenorm_mae/rmse` alongside
  `tqplus_mae/rmse` plus `renorm_mean/min/max` distribution
  stats.

## Result

Same synthetic 1536-d fixture as packet 002:

| variant | MAE |
|---|---|
| baseline | 0.0264 |
| TQ+ renormalized | 0.00344 |
| TQ+ **unrenormalized** | **0.00311** |

renorm distribution: mean=1.008, [0.989, 1.037].

**Unrenormalized BEATS renormalized on the IP-normalized
lane.** Per-vector renorm is not the value driver on this
lane; per-coordinate calibration is.

## Why this is a clean isolation

- Same encoder, same calibration, identical packed bytes.
- Only the final `* renorm` differs.
- Both columns in the same log file, same harness, same
  fixture, same SHA.
- This is exactly what "renorm isolation" should mean.

The request frames the result honestly — does not claim "TQ+
is faster" or "renorm is dead", claims only that "renorm is
not carrying the gain on the normalized/IP lane."

## Safety bar

not the **storage** side. Removing the field is a structural
change that belongs in a different slice if/when the field
is judged dead.
