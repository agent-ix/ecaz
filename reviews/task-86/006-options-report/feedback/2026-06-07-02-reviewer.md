# Packet 006 — Escalation: no measured speedup yet

## Verdict change

Seq 01 said APPROVE with a tightening request for Exit-
Criteria mapping. **The verdict was too soft for an
optimization task.** Escalating: the Options Report must
explicitly state "zero production speedup measured to date"
and pre-condition every downstream recommendation on a real-
corpus `ecaz bench suite` measurement on the production scan
path.

## The miss

Task 86 is a TurboQuant **optimization** investigation. The
Options Report consolidates findings from packets 001-005
and makes "next task" recommendations:

1. SPIRE suite via `ecaz bench suite` first
2. Calibration-only TQ+ prototype on a single index
3. Cross-index extension only after one index proves out
4. Deprioritize byte-pair LUTs
5. Defer renorm

What's missing from these recommendations: every one of them
can be acted on **without ever running a benchmark on the
production scan path against the existing baseline.** And
that's exactly what happened — packets 005 + 007 were
written, and neither shipped a before/after measurement on a
real fixture.

The report does name TurboVec's claimed wins (87% MAE drop
on synthetic, etc.) but it does not state, anywhere in
either the request or the analysis document, the fact that
**zero packets in 001-005 measured a production speedup at
any fixture**. A reader walking from this report into next-
slice planning would not learn this from the document.

## What the report should say

Insert near the top of the analysis document, before any
recommendation:

> ### Measurement status as of 2026-06-07
>
> **No production speedup has been measured by any packet
> in this task.** The TQ+ calibration result (002, 003) is
> a score-MAE reduction on a 192-train / 96-candidate /
> 16-query synthetic 1536-d anisotropic fixture; it is not
> a recall or latency number on a real corpus. The byte-LUT
> kernel result (004) is a 0.82× negative result vs the
> existing dim-LUT scorer at debug build. The SPIRE LUT
> integration (005) ships a scoring-path code change with
> no benchmark; packet 007 attempted the suite but is
> BLOCKED on missing baseline. **Every "next task"
> recommendation below is conditional on running an
> `ecaz bench suite` cell on real corpus with the
> production lane both before and after the change.**

Plus: the Exit-Criteria mapping requested in seq 01 must
explicitly mark every criterion that depends on a measured
speedup as "not yet evidenced" rather than "in progress."

## Pre-condition for downstream packets

Per `feedback_dont_overclaim_done`, no code-change packet in
this task may ship without:

1. An `ecaz bench suite` `suite.json` checked into the
   packet, AND
2. A side-by-side baseline run on a real fixture (real10k+),
   AND
3. The change-on column on the same fixture, AND
4. Recall@10 + p50/p95/p99 latency + storage rows in
   `manifest.md` citing the deltas.

Anything else is a refactor or a test-only commit, not an
optimization commit, and the task's Exit Criteria do not
treat it as one.
