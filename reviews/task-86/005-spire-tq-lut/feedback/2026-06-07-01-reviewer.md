## Correctness — minor concern

When the LUT path is taken, the caller-supplied `gamma` is
silently ignored. This is **mathematically correct** because
the existing `score_ip_from_split_parts_no_qjl_4bit`
(`src/quant/prod.rs:795-825`) also ignores gamma in the
no_qjl_4bit lane — both compute the identical sum
`Σ codebook[idx[d]] * rotated[d]`.

But it's not obvious from the call sites. **Add a one-line
comment or debug-assert** at the SPIRE LUT branch noting
that gamma is intentionally dropped because no_qjl_4bit is
gamma-independent. Otherwise a future reader who sees
`gamma` threaded through `score_ip_from_parts` and silently
discarded in the LUT branch may try to "fix" the omission.

## Test quality — the flag

The added test computes the expected value by calling
`score_ip_from_parts_lut_no_qjl_4bit` directly, then asserts
the SPIRE scorer matches. This is **circular** — it proves
the SPIRE scorer routes through the LUT path (already
covered by the separate `no_qjl_4bit_lut.is_some()` assert)
but does not independently prove parity against the prior
generic `score_ip_from_parts` path.

The mathematical-equivalence claim ("LUT and non-LUT paths
produce identical sums modulo float ordering") is the
load-bearing correctness invariant. Lock it in with a parity
test:

```rust
let expected = score_ip_from_parts(prepared, gamma, payload);
let actual = SpirePreparedAssignmentScorer::TurboQuant {...}.score(...);
assert!((actual - expected).abs() < 1e-6);
```

…where `prepared` is the **non-LUT** prepared query. This
gates the LUT path against silent divergence.

## Storage format — unchanged

No payload bytes, no page layout, no on-disk SPIRE struct

## Determinism

The LUT and non-LUT scorers compute the same f32 sum in the
same order on the same codebook — bit-identical modulo
compiler reorder, which is identical on the same build.
Determinism preserved.
