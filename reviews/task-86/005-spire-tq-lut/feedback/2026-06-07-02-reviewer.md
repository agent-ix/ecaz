# Packet 005 — Escalation to REQUEST-CHANGES

## Verdict change

My seq 01 verdict (APPROVE-WITH-FLAG) was **wrong** for an
optimization task. **Escalating to REQUEST-CHANGES.**

## Why this is a gating miss

Task 86 is a TurboQuant **optimization** task. The acceptance
question is "did it get faster, at what recall" — full stop.

Packet 005 commits a code change to SPIRE's
`SpirePreparedAssignmentScorer::TurboQuant` scan path
(`src/am/ec_spire/quantizer/mod.rs:8-336`). That is a
production scan-path change. The seq 01 review approved it
on the basis of:

- safety bar clean (no new unsafe, no anti-pattern B);
- structural scoping clean (SPIRE-only, no shared API change);
- on-disk format unchanged;
- mathematical equivalence to the prior path (LUT and non-LUT
  computing the same sum) — **claimed, not measured**.

That's the bar for a *refactor*. It's not the bar for an
*optimization commit*. For an optimization commit the gate
is "measured speedup, recall preserved on the real fixture."
Packet 005 ships zero of that.

The seq 01 review explicitly deferred recall preservation
to packet 007. That deferral was wrong — packet 007 is
currently BLOCKED (its own seq 01) for missing baseline, so
the deferred evidence does not exist anywhere. Net effect:
a scan-path optimization commit is sitting in tree with no
proof that it preserves recall OR that it is actually faster
than the path it replaces.

## What was actually committed

- **A scoring-path change to a production AM**: SPIRE now
  routes single, zero-gamma chunk-max, and batch scoring
  through `score_ip_from_parts_lut_no_qjl_4bit` when the
  prepared LUT is available.
- **No benchmark.** Not in this packet, not in packet 007,
  not anywhere in the branch.
- **A circular unit test** that proves SPIRE's scorer calls
  through to the same LUT function the test calls directly.

There is no evidence the change is faster than what it
replaces. There is no evidence recall is preserved beyond a
plausibility argument.

## Required to lift the REQUEST-CHANGES

A side-by-side `ecaz bench suite` cell on a real fixture
(real10k or larger), at the SPIRE TurboQuant `no_qjl_4bit`
lane, with two columns:

| | LUT off (pre-005) | LUT on (post-005) |
|---|---|---|
| recall@10 (L=64/128/200) | row | row |
| p50/p95/p99 latency (per nprobe) | row | row |
| build time | row | row |
| index bytes | row | row |

Either:
- both columns recall@10 byte-equal — confirms the mathematical-
  equivalence claim — and latency strictly faster, OR
- a recall delta of ≤ 0.5pp with a measured latency win that
  justifies it.

Anything else is not a defendable optimization change.

## Why this isn't "wait for packet 007"

The seq 01 review treated packet 007 as the natural place to
land the measurement. That was a procedural deferral that I
should not have made. The right shape is:

- Code packet (005) ships the change AND ships the
  before/after measurement on the canonical fixture in the
  same packet.
- A separate measurement-only packet (007) can extend the
  sweep, add more cells, or document edge cases — but it
  cannot be the **first** measurement of the load-bearing
  optimization claim.

This is the same shape Task 71 and Task 65b enforced for
parallel-build code changes (worker-counter evidence had to
ship with the code, not after). The miss here is that I
applied a refactor-style review to an optimization commit.
