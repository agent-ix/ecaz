# Packet 004 — Byte LUT Kernel Probe — APPROVE (negative result)

## Verdict

**APPROVE as a negative-result probe.** Code is test/bench-
gated, no production surface changed, no safety regression.
The probe's own measurement supports its stated conclusion
("deprioritize byte-pair LUT") — byte LUT is 1.71× faster than
direct scalar but only 0.82× of the existing dim-LUT scorer.

## What landed

Commit `462ece1df`. All new code in `src/quant/prod.rs`
gated `#[cfg(any(test, feature = "bench"))]`:

- `build_byte_pair_lut_no_qjl_4bit` (lines 1805–1832):
  build per-byte (`mse_code_len * 256`) f32 LUT from existing
  per-dim 16-entry LUT.
- New scorer:
  `for (byte_index, &packed) in mse_packed.iter().enumerate() {
   sum += lut[byte_index * 256 + packed as usize]; }`
  (lines 925–936).
- Golden equality test asserts `|delta| < 1e-6` vs direct
  scalar and dim-LUT scorer on 16 candidates (lines
  2625–2635).

## Kernel shape

- **Scalar reference, not SIMD.** No intrinsics, no
  `target_feature`, no `unsafe`. Anti-pattern B not
  applicable (no raw pointer surface).
- LUT layout: per-byte (`mse_code_len * 256`) f32, indexed by
  full packed byte (one lookup per byte).
- Inner loop: one LUT read per packed byte (two nibbles per
  byte = two original dims).
- Accumulator: f32.

## Safety bar

- **Zero new unsafe.** SIMD safety rules vacuously satisfied.
- LUT length contracts asserted via `debug_assert_eq!` at
  `:929`.
- Branch-free; odd `dim` handled at LUT-build time via
  zero-padding the missing high nibble (`:1815-1827`).
- Index bounded by `mse_packed.len() * 256 == lut.len()`.
- Visibility of `PreparedByteLutNoQjl4BitQuery` re-exported
  only under the same cfg gate in `src/lib.rs:104-105`.

## Determinism

- Golden equality vs direct scalar + dim-LUT, `|delta| < 1e-6`.
  Adequate for probe; if promoted, tighten to **exact
  equality on byte-pair sums** (this kernel is bit-exact by
  construction — same two f32 adds in the same order as the
  reference).
- Encode-side nibble order (`pack_mse_indices_4bit`,
  `:1972-1983`): low nibble = first index. Byte-LUT builder
  (`:1814-1817`) reads `packed & 0x0F` → low_dim, `packed >>
  4` → high_dim. **Endianness agrees end-to-end.**
- Single-fixture only (dim=1536, seed=42). No proptest, no
  sweep over multiple dims/seeds, no explicit non-power-of-2
  dim. The LUT-build path *does* handle odd dim via guards
  but no test exercises them.

## Measurement evidence

One log: `direct=9356 ns, dim_lut=4449 ns, byte_lut=5459 ns`
per score at dim=1536, 16384 scores. Byte LUT is:
- **1.71× faster than direct** (positive)
- **0.82× of dim-LUT** (negative — slower than existing)

Run is debug-ish (`cargo test` without `--release`) so absolute
ns numbers are not benchmark-grade. The request acknowledges
this; the relative ordering across three kernels in the same
harness is robust to debug overhead, which is what supports
the negative-result conclusion.

## Architecture coverage

Pure scalar. No arch-specific paths added. Existing AVX2/NEON
dispatch for QJL-enabled scoring (`:776-792`) untouched. No
regression to runtime feature detection.

## Per-query LUT memory at promotion

If this kernel ever promotes, note the per-query LUT memory:
at dim=1536 with mse_code_len ≈ dim/2, the LUT is
`(dim/2) * 256 * 4 = 786 KiB`. That's a meaningful L2 working
set inflation that downstream AMs would need to budget for.
Probably the third reason (after the 0.82× speed and the
duplicate kernel maintenance cost) to leave this as deprio.

## Verdict

**APPROVE as negative-result probe.** The packet does what a
deprioritization probe should: lands a clean reference
implementation, measures it against existing alternatives,
reports the result honestly, and concludes against
promotion. The kernel itself is test-bench-only and stays
that way unless future work flips the call (e.g., if the
TurboVec-style blocked-slab approach lands and changes the
per-byte LUT economics).

Non-blocking notes for any future promotion attempt:
- Tighten the golden tolerance from `1e-6` to exact equality.
- Add coverage for odd `dim` (LUT builder has dead-code
  branches currently unexercised).
- Real `ecaz bench suite` measurement under release before
  citing speedup as production-relevant.
- Memory accounting: 786 KiB per-query LUT at dim=1536.
