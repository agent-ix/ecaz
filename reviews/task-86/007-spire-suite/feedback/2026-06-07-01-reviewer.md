# Packet 007 — SPIRE Suite Evidence — BLOCK

## Verdict

**BLOCK.** The suite is FR-038-clean and demonstrates that
the SPIRE TurboQuant LUT path builds and scans under PG18.
But the measurement is **necessary but not sufficient** for
the Task 86 §Required Evidence / §Gates: no baseline cell,
synthetic 256-row corpus far below the canonical fixture
surface, and recall@10=0.5813 at nprobe=4 is well below any
meaningful floor.

## Why BLOCK

### B-1. No baseline cell

There is no pre-LUT row at the same fixture to diff against.
Without it:
- Recall parity claim (LUT vs non-LUT) cannot be verified
  from this packet alone.
- Latency improvement claim (LUT vs non-LUT) cannot be
  verified.

The request acknowledges this ("does not prove an end-to-end
speedup by itself"). Honest framing helps, but the missing
column is the load-bearing one for closeout.

### B-2. Fixture is undersized

256 rows / 32 queries is well below the canonical SPIRE
corpus surface (real10k+). Task plan §Required Evidence
specifies real-corpus rows for index-level claims.

Recall@10 = 0.5813 at nprobe=4 is below any meaningful
recall floor for a real workload — at this fixture size the
nearest-neighbor structure is sparse enough that nprobe=4
covers only ~50% of the centroid mass. This is not a recall
the packet can hold up as evidence of preservation.

The request notes the canonical corpus was not present in
this checkout. Per `feedback_no_setup_deferral` (HARD RULE),
"setup/tooling/loader friction is not a valid reason to
defer hardening deliverables; require the fix, not the gap."
Either re-stage the canonical corpus or generate a
deterministic stream fixture at meaningful scale (10k+).

### B-3. Build evidence is good but closeout-critical signal is recall delta

Build time `9.85 ms` shows the LUT integration doesn't add
build overhead — useful but unsurprising (the LUT is built
at query prepare time, not index build time). The
closeout-load-bearing signal is **scan-path recall + latency
delta vs pre-LUT**, which this packet does not measure.

## Required to lift the BLOCK

Rerun the same suite at HEAD (with LUT) **and** at a pre-LUT
SHA (or with a config flag toggling LUT off), on the same
canonical SPIRE corpus, side-by-side, in the same packet.
Report:

- recall@10 delta per nprobe cell
- p50 / p95 / p99 delta per nprobe cell
- per-vector stored bytes (should be unchanged — verify)
- build_index delta (should be unchanged — verify)

If recall is bit-equal (which is the mathematical expectation
per the equivalence in packet 005's review), document that
explicitly. If recall diverges anywhere, the LUT integration
needs investigation before it can ship.

## Non-blocking observations

  0.9187) is the right shape (more probes → more recall).
  Useful sanity that the SPIRE scan logic is intact under
  the LUT path.
- The 1312 B/row storage is consistent with the existing
  TurboQuant on-disk format. No format change detected,
  which matches packet 005's structural review.

2. Baseline cell with LUT off, same fixture.
3. Recall + latency delta vs baseline per nprobe.
4. Cite the equivalence claim from packet 005's review

With those four, the SPIRE LUT change becomes a defendable
closeout claim. Without them, the suite is build-only
infrastructure evidence and the Exit Criterion remains
