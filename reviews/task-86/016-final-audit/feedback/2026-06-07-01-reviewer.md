## Architectural review

### What actually shipped

Two distinct things, in different layers:

1. **SPIRE TurboQuant LUT routing** (packets 005 + 008 + 009)
   — SPIRE's `SpirePreparedAssignmentScorer::TurboQuant` now
   routes scoring through the same
   `score_ip_from_parts_lut_no_qjl_4bit` kernel that HNSW
   and IVF were already using. Cross-AM consistency on the
   no-QJL 4-bit lane. ~3-5% latency improvement at unchanged
   recall and storage. **No format change.**

2. **TQ+ as a new IVF quantizer variant** (packets 011 + 012
   + 016) — new `StorageFormat::TurboQuantTqPlus = 4`
   reloption on IVF. Per-coordinate `(shift, scale)`
   calibration trained from a deterministic sample, packed
   4-bit codes, calibrated LUT scoring. **New on-disk format
   tag, opt-in via reloption.**

These are architecturally orthogonal: SPIRE's change is a
shared-kernel routing fix; IVF's TQ+ is a new quantizer
variant with its own encoder + scorer + format tag. Both
are scoped cleanly to their respective AMs.

### Design choices that look right

- **TQ+ as a separate StorageFormat tag (4)**, not a
  modification of the existing TurboQuant tag (1). Means
  pre-TQ+ binaries reject tag 4 cleanly rather than
  misinterpreting bytes. Backwards-compat preserved.
- **Opt-in via reloption** (`turboquant_tqplus` /
  `tqplus`). No silent migration. Operators choose to use it.
- **Deterministic calibration sample** via
  `training::deterministic_sample_indices(seed)`. Index
  rebuilds at fixed seed produce identical calibration.
- **Cross-AM scope discipline**: TQ+ references are confined
  to `src/am/ec_ivf/*` + `src/quant/prod.rs`. SPIRE / HNSW /
  DiskANN unaffected. Per Task 86 §"Use our TurboQuant
  baseline only" — measured TurboQuant vs TurboQuant
  comparison on the same AM, not against another quantizer
  family.
- **`prepare_ip_query` / `encode_source` error on TQ+
  profile** instead of silently falling back to non-TQ+
  scoring. Loud failure mode on misuse.

### Design choices to flag

- **Calibration storage reuses `IvfPqCodebookTuple` chain**
  (shift→scale via `next_tid`, anchored at
  `metadata.pq_codebook_head` with `pq_group_size = 0`).
  Acknowledged in the format plan. The calibration data is
  not really a PQ codebook — it's two `Vec<f32>` of length
  `dim`. Opportunistic reuse keeps the on-disk page
  vocabulary small, but couples TQ+ to PQ-FastScan's
  storage primitive. If future PQ work changes
  `IvfPqCodebookTuple` semantics, TQ+'s storage breaks.
  Not blocking; flag for the persist-layer next-task work.

- **TQ+ scoring bypasses the shared LUT kernel**
  (`score_ip_from_parts_lut_no_qjl_4bit`). TQ+ has its own
  calibrated LUT and scorer (`score_tqplus_no_qjl_4bit_*`).
  This means the SPIRE LUT routing optimization and the TQ+
  quantizer don't compose at the kernel level. **Task 87**
  (candidate batching) needs to support TQ+ as a first-class
  quant type from day 1 — TQ+ is now production on IVF, not
  just a prototype. I'll update Task 87's quantizer scope to
  reflect this.

- **Two new `unsafe fn` declarations** on the branch:
  `load_tqplus_model` (quantizer.rs:656) and
  `tqplus_model_for_scan<'a>` (scan.rs:834). Both are
  legitimate per the IVF callback-surface convention — they
  take `pg_sys::Relation` and produce typed views — and
  `tqplus_model_for_scan` returns `&'a IvfTqPlusModel` from
  `unsafe fn`, so anti-pattern B does **not** apply (that
  rule targets safe fns smuggling pointer→borrow lifetimes).
  But — see Flag F-1 below — `load_tqplus_model` is missing
  its `/// # Safety` doc block. The sibling
  `load_pq_fastscan_model` is also missing one; pre-existing
  technical debt that Task 86 replicated.

near-neutral storage. The optimization gate is met.

## Flags to address before merge

### F-1. Missing `/// # Safety` doc on `load_tqplus_model`

`src/am/ec_ivf/quantizer.rs:656`:
`pub(super) unsafe fn load_tqplus_model(...)` — has no
`/// # Safety` doc block. Per the auto-memory
`feedback_dont_defer_safety_fixes` (HARD RULE), every unsafe
fn must document its safety contract on the item itself.

The sibling `load_pq_fastscan_model` at line 602 is also
missing one — pre-existing technical debt that Task 86
replicated rather than introduced. Either:

- Add `# Safety` to `load_tqplus_model` only (Task-86 scope).
- Add `# Safety` to both (close the pre-existing gap too).

The second option is cleaner and the cost is trivial
(~3 lines of doc-comment each). Recommend doing both as
a single narrow commit.

### F-2. No CI gate for added `unsafe { ... }` blocks

The unsafe-add-and-remove cycle (`e0ae9fe7d` adds 2 blocks
inside an already-`unsafe fn`, packet 016 catches it and
`d58ff8716` removes them) was caught by coder self-audit
~2h22m after the addition. No CI / reviewer / lint gate
flagged it. Final state is clean, but the next safety-
sensitive task could be less lucky.

Recommend landing a narrow CI ratchet (either a clippy
`unused_unsafe` deny, or a `git diff` check against
`origin/main` for added `unsafe { ... }` lines) before the
next safety-sensitive feature. This isn't a Task 86 merge
blocker — it's the structural fix that prevents recurrence.

A `clippy::unused_unsafe` deny would have caught **exactly**
this case (redundant `unsafe { ... }` inside an
`unsafe fn`). It's the most narrowly-scoped fix that
addresses the actual miss without overreaching.

### F-3. Pre-PR checklist for deterministic gates

The TQ+ scope expansion broke three deterministic, cheap-to-
run gates that landed as three separate cleanup packets
(013 clippy, 014 hardening compile, 015 coverage delta).
These are all gates that should fail loudly **before** a
"coder-complete" claim, not after.

The coder workflow's "Run tests only when... static review
is not sufficient" allowance is right for expensive PG
runtime tests, but coverage + clippy + hardening compile
are cheap. Recommend a `make pre-pr` target (or equivalent
checklist) that runs these three before any "coder-complete"
claim on production code surfaces. Not a Task 86 merge
blocker, but worth landing alongside F-2 as the structural
process improvement.
