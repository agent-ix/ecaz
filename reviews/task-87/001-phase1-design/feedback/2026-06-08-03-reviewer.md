# Task 87 Phase 1 Design — Addendum: Common Quant Codec Shape Across AMs

This addendum revises blocker B2 from `2026-06-08-01-reviewer.md`
(further amended by `…-02-reviewer.md`) and adds a new blocker B6
about the codec-shape side of the abstraction. It reflects a direct
clarification from the user during this review cycle:

> Diskann lacks TQ. Intent was for a common quant codec shape for TQ
> and other quants so we could more easily apply quants to each index
> type

That reframes Task 87. The work is not just a shared scoring data-flow
abstraction (`CandidateBatch`) — it is also a **shared quant codec
shape** so that every quantizer (TurboQuant, RaBitQ, grouped-PQ,
binary fingerprint, etc.) plugs into every AM (HNSW, IVF, DiskANN,
SPIRE) through the same registration surface.

## B2 (re-amended): DiskANN missing TQ codec is in-scope to close, not Stop-Condition

Replace B2's "preferred path = Stop Condition packet, deferring DiskANN
TQ to a follow-up" with:

**DiskANN's missing TurboQuant search codec is a Task 87 in-scope gap.
Close it by extending the common quant codec shape so adding TQ to
DiskANN is the same registration step that already works on
IVF/HNSW/SPIRE.** The DiskANN Phase 4 slice should:

- land a `DiskannBuildCodec::TurboQuant { … }` variant and a
  `DiskannPreparedPrefilter::TurboQuant { … }` variant via the new
  common shape (B6), not as bespoke DiskANN code;
- route it through `CandidateBatch` like the other AMs;
- carry the per-AM measurement gate from the task file.

A Stop Condition packet is no longer the preferred resolution. If the
common codec shape proves too large to ship inside Task 87, the right
escape hatch is a narrow prerequisite slice that lands the codec
trait/enum surface only, not a deferral of the DiskANN AM slice.

## B6 (new): Phase 1 must specify the common quant codec shape

The current Phase 1 packet specifies `CandidateBatch` (the data-flow
side) but does not specify the **codec-shape side**: how a quantizer
implementation registers into all four AMs through one surface. The
existing search-codec enums diverge per AM:

- `IvfPreparedQuery::{TurboQuant, TurboQuantNoQjl4BitLut, RaBitQ,
  PqFastScan}` at `src/am/ec_ivf/quantizer.rs:179`
- `DiskannPreparedPrefilter::{BinarySidecar, GroupedPq, RaBitQ}` at
  `src/am/ec_diskann/quantizer.rs:152`
- `DiskannBuildCodec::{PqFastScan, RaBitQ}` at `:29`
- HNSW's `TurboQuantExactScoreMode::{FullLut, TiledLut, Int8Approx}`
  plus the gamma-aware fallback at `src/am/ec_hnsw/scan.rs:5000–5035`
- SPIRE's `SpirePreparedAssignmentScorer::{TurboQuant, RaBitQ}` and
  the `TurboQuant.no_qjl_4bit_lut` Option at
  `src/am/ec_spire/quantizer/mod.rs:297–340`

Each AM has invented its own enum to hold "which quant is scoring this
candidate". That is the root cause of "DiskANN doesn't have TQ" — TQ
exists as `IvfPreparedQuery::TurboQuant…` and
`SpirePreparedAssignmentScorer::TurboQuant{…}` etc., but each AM has
to re-wire it locally.

Phase 1 design must add a section specifying the common shape, at the
level of a trait or shared enum that captures, per quantizer:

- **build-side codec**: encode a source vector to bytes (current
  `DiskannBuildCodec::encode`, SPIRE/IVF/HNSW equivalents);
- **prepared query**: from `&[f32]` query produce the scan-side
  prepared state (LUTs, rotated query, estimator);
- **score from parts (single)**: legacy per-vector scoring for paths
  where batch size is 1;
- **score from parts (batched)**: fill score buffer for a
  `CandidateBatch` flush;
- **per-candidate metadata**: matches the `CandidateMeta` variants
  the data-flow side already defines (gamma, residual signs, group
  shape, etc.);
- **search-codec kind tag**: for on-disk identification, matching the
  existing `VAMANA_SEARCH_CODEC_*` constants and SPIRE/IVF
  equivalents.

Each AM then holds `dyn QuantCodec` (or an enum over implementations)
rather than its own bespoke variant set, and adding a new quant
becomes: implement the trait once, register into AMs through their
shared dispatch. This is what makes "apply quants to each index type"
the routine step the user is asking for.

The design must also state:

- which AM-specific enums collapse into the common shape (the four
  listed above) vs which stay AM-specific for legitimate reasons
  (e.g., HNSW's TQ exact-score mode dispatch may stay HNSW-internal
  if it is purely a kernel-selection step, but the TQ codec itself
  must come from the common shape);
- the migration order: pick the AM where the existing enum is the
  closest match to the common shape and migrate that first as a
  refactor-only commit before the per-AM scoring-batch refactors
  begin.

Without B6, Task 87 lands `CandidateBatch` over four still-divergent
codec surfaces and the "common quant codec shape" the user is asking
for does not materialize.

## Impact on B1 (amended), B3, B4, B5

- **B1 (all batch-shaped quant modes route through `CandidateBatch`):**
  unchanged. The per-(AM × quant mode) routing table from `…-02` is
  still required, and it now lives inside the common quant codec
  shape (B6) instead of per-AM ad hoc plumbing.
- **B3 (HNSW borrow-source paragraph):** unchanged.
- **B4 (SPIRE structural-slice gate):** unchanged. SPIRE still hits
  the no-op-refactor risk on Phase 2.
- **B5 (task-file wording amendment):** widens. The task file should
  reflect both the batching-is-architectural directive and the
  common-codec-shape directive:
  - replace "kernel work in Task 87 is scoped to TurboQuant no-QJL
    4-bit only" with the batching directive;
  - add an explicit "common quant codec shape" goal to the Scope
    section so adding new quants to AMs becomes a routine
    registration step;
  - remove the "if no TurboQuant DiskANN codec, Stop Condition"
    framing in favor of "extend the common codec shape to register
    TurboQuant into DiskANN like the other AMs".
