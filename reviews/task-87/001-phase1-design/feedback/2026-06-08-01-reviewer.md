# Task 87 Phase 1 Design — Reviewer Feedback

Scope: `reviews/task-87/001-phase1-design/` at head `68a01f056`
(documentation-only packet; verified citations against the working tree).

## Verdict

**Conditional approve on the abstraction shape; resolve the four blockers
below before Phase 2 starts.** The contract direction (borrowed payload
view + typed `CandidateMeta` enum, AM-owned ids and frontier/top-k) is
right, the source-scoring-map citations check out, and the
quantizer-walkthrough exercise demonstrably shows no TurboQuant-only
assumption baked into the batch type. The deferral of the 32-vector u8
nibble LUT kernel is also the right risk call — agreed, do not freeze a
flat-slab layout before HNSW and DiskANN expose their real per-step batch
sizes.

The blockers below are about per-AM mapping completeness and the lifetime
contract on the worst-case AM, not about the abstraction shape itself.

## Blockers

### B1. HNSW exposes three TurboQuant exact-score modes, not one

The design and source-scoring map both speak as if HNSW's TQ no-QJL 4-bit
path is a single LUT branch
(`src/am/ec_hnsw/scan.rs:5007` → `score_ip_from_parts_lut_no_qjl_4bit`).
The actual scoring site at `scan.rs:5000–5028` dispatches on
`TurboQuantExactScoreMode` with three live branches:

- `FullLut` → `score_ip_from_parts_lut_no_qjl_4bit`
- `TiledLut` → `score_ip_from_parts_tiled_lut_no_qjl_4bit`
- `Int8Approx` → `score_ip_from_parts_int8_approx_no_qjl_4bit`

All three are no-QJL 4-bit shaped. Phase 1 must decide:

a) does the Phase 5 HNSW slice route **all three** modes through
   `CandidateBatch`, or
b) only the `FullLut` mode, with `TiledLut` / `Int8Approx` left on the
   inline path until a follow-up?

Either is defensible, but the per-AM validation gate ("HNSW TQ no-QJL
4-bit recall byte-equal at every cell") and the no-regression clause for
non-batched paths both become ambiguous unless the design names which
modes are in scope. The Phase 5 slice gate should also state which
`TurboQuantExactScoreMode` the recall byte-equality is asserted under.

### B2. DiskANN scope question must be answered now, not deferred to Phase 4

The design correctly observes that the working-tree DiskANN exposes only
`PqFastScan` (grouped-PQ) and `RaBitQ` search codecs
(`ec_diskann/quantizer.rs:29–34`, `:111`, `:152–169`) and that there is
no TurboQuant no-QJL prefilter branch to route. Marking this as
"reviewer should decide between prerequisite slice, Stop Condition, or
wording adjustment" is the right framing, but Phase 1 is the right place
to land the decision so Phase 2–5 sequencing is unambiguous.

Reviewer position:

- **Do not** silently route grouped-PQ or RaBitQ DiskANN through a
  TQ-only validation gate. The acceptance criteria are explicit that
  "kernel work in Task 87 is scoped to TurboQuant no-QJL 4-bit only",
  and the Stop Conditions block ad hoc broadening of that scope.
- **Preferred path:** treat Phase 4 as a Stop Condition packet up front
  ("DiskANN has no TurboQuant search codec on this branch; deferring
  the DiskANN slice to a follow-up that enables a TurboQuant DiskANN
  search codec, scoped separately from Task 87"). That packet should
  cite the Task 86 packet 006 grouped-PQ/RaBitQ decision and the
  task-87 acceptance language as evidence.
- The follow-up task should be opened **before** Phase 2 starts, not as
  closeout cleanup, so Task 87's "all four AMs" gate is not a moving
  target.
- The alternative (in-Task-87 codec-enablement prerequisite slice) is
  acceptable only if the coder can show that adding a TurboQuant no-QJL
  4-bit DiskANN search codec is a narrow on-disk-format-neutral change
  (e.g., adds a `VAMANA_SEARCH_CODEC_TURBOQUANT` variant + encode/decode
  + prefilter scorer without rewriting tuple layout). If it grows past
  that, push it out and use the Stop Condition route.

This decision needs to land before Phase 2 because it changes Task 87's
acceptance-criteria interpretation (per-AM completion non-negotiable
clause).

### B3. `CandidateBatch<'a>` lifetime is fine for SPIRE/IVF but not yet shown for HNSW

The design's batch type holds `code: &'a [u8]` payload borrows with a
single lifetime `'a`. On SPIRE/IVF this is sound because the source
storage is contiguous column or posting-list memory that outlives the
batch flush. On HNSW it is less obvious:

`load_successor_candidates_for_layer_with_storage`
(`graph.rs:1261–1290`) re-enters `load_exact_graph_element` for **each
neighbor**, inside the per-neighbor loop. Each `GraphElement` load
acquires storage on a per-tuple basis. Currently each neighbor is scored
and dropped before the next neighbor loads, so the lifetimes don't have
to compose. With batched scoring, the design implicitly requires either
(a) all neighbor codes for one expansion to be kept live until the batch
flushes, or (b) the batch to copy code bytes into an owned scratch.

Phase 1 design picks (a) ("does not copy payload bytes unless a later AM
proves its source storage cannot keep borrows alive through scoring")
but does not show how `load_exact_graph_element` is changed to support
holding multiple neighbor element backings live concurrently.

Action: Phase 1 design needs one paragraph that names the HNSW
borrow-source change — either "expand load to return owned code Vec for
each neighbor" or "batch holds page buffer guards as an additional
sidecar field" or "fall back to copying into a fixed-size owned scratch
buffer for HNSW only, accepting the copy overhead as part of the Phase 5
≥2× scoring-share target". Pick one and write the contract down.

Without this, Phase 5 will discover the lifetime gap mid-slice and
either widen `CandidateBatch` retroactively (breaking the abstraction
the other AMs landed) or quietly fall back to inline scoring.

### B4. SPIRE Phase 2 has a no-op refactor risk

`SpirePreparedAssignmentScorer::score_batch_ip` at
`src/am/ec_spire/quantizer/mod.rs:297–340` is **already a chunked batch
scorer** that loops `payload_stride`-sized chunks over the TQ no-QJL
4-bit LUT scorer per chunk. The SPIRE Phase 2 work is mostly
"re-express the existing SPIRE batch loop as a shared `CandidateBatch`
flush" with the same per-candidate LUT scorer kernel. The Phase 1 design
acknowledges this ("The initial implementation may use the current
per-candidate LUT scorer inside that batch entry point").

That means SPIRE's measured scoring-share win on the Phase 2 slice is
likely small or zero (within noise), and could trigger the Stop
Condition "if measured scoring-share speedup is < 5 % after the
refactor, back the AM out and document". A "back out SPIRE" outcome on
Phase 2 would be wrong because:

- the abstraction value on SPIRE is structural (it unblocks the shared
  block kernel that lands later), not perf;
- backing it out breaks Task 87's cross-AM applicability premise.

Phase 1 should either:

a) explicitly mark SPIRE Phase 2 as a "structural slice" whose Stop
   Condition is recall byte-equality + no end-to-end regression rather
   than ≥ 2× scoring-share, with the perf win deferred to the kernel
   landing in the follow-up; or
b) commit to landing a real new SPIRE batch kernel (the 32-block u8
   nibble LUT or another measured win) **within** Task 87 so Phase 2 can
   actually clear the ≥ 2× gate.

The current design picks neither explicitly. Recommend (a) and write
that into both Phase 1's kernel-decision section and the Phase 2 gate
language.

## Non-blocking observations

- **Streaming compose contract (Task 88) reads correctly.** Keeping
  `CandidateBatch` out of cursor/snapshot/scan-descriptor ownership is
  the right call; the resort buffer sits above it cleanly.
- **Measurement methodology** (DBPedia real10k/50k/100k × source-install
  baseline vs change, isolated one-index-per-table, recall byte-equal
  gate, suite-driven per FR-038) matches the Task 86 packet 008 shape
  and `feedback_index_isolation_rule`. Good.
- **Source-scoring-map citations** I spot-checked all line numbers
  against the working tree at head `68a01f056` (SPIRE 2445/2447/2457,
  SPIRE quantizer 297/331/336/340, IVF 164/179/181/237/253/261, DiskANN
  29/111/152/153/157/163/169, HNSW graph 1261/1275/1279/1284/1285/1288,
  HNSW scan 5005/5007/5035). All present and accurately described. The
  HNSW scan citation is correct but incomplete per blocker B1.
- **Quantizer scope walkthrough** exercises TQ 2-bit, TQ QJL, RaBitQ,
  binary, PQ/grouped-PQ against the contract and shows each fits. This
  satisfies the Task 87 Phase 1 explicit requirement.
- The proposed `CandidateMeta` enum's `RaBitQ` variant is empty —
  consider whether it should hold the residual-sign or rotation
  metadata the task wording calls out
  ("RaBitQ carries rotation metadata"). On the current code path RaBitQ
  metadata is already inside `PreparedEstimator` so the empty variant
  is defensible; flag it as a comment in the design so a future RaBitQ
  block kernel reviewer doesn't re-litigate.
