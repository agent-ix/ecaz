# Task 87 Phase 1 Design — Addendum: Batching Is Architectural, Not TQ-Only

This addendum amends blocker B1 in `2026-06-08-01-reviewer.md` and adds
a new blocker B5 against the task wording. It reflects a direct
clarification from the user during this review cycle:

> All quant modes should be in scope if they make sense to batch
> process. Batching is considered a key architectural design choice to
> improve processing.

That overrides the "kernel work in Task 87 is scoped to TurboQuant
no-QJL 4-bit only" language currently in
`plan/tasks/87-candidate-batched-scoring-across-ams.md` and the
matching "other quant paths stay on inline scoring" framing in the
Phase 1 design's per-AM mapping section.

## B1 (amended): all batch-shaped quant modes route through `CandidateBatch`

Replace B1's "pick which HNSW modes are in scope" question with:

**Every quant mode whose kernel benefits from batching must route
through `CandidateBatch` in its AM slice.** The Phase 1 design must
add a per-(AM × quant mode) routing table that names, for each cell:

- routed-through-batch (yes / no)
- if no, the specific reason (e.g. "f32 raw: per-vector SIMD already
  saturates throughput; batch adds copy overhead with no kernel win",
  or "batch size lower bound is 1 by traversal shape: HNSW level-N
  entry probe")
- the expected batch-size distribution from the AM's traversal pattern
  for that cell

Concrete cells the addendum requires the design to address (this is
not exhaustive):

- HNSW × {TQ FullLut, TQ TiledLut, TQ Int8Approx, RaBitQ if present,
  generic gamma-aware fallback}
- IVF × {TQ no-QJL 4-bit LUT, generic TQ, RaBitQ, grouped-PQ /
  PqFastScan}
- SPIRE × {TQ no-QJL 4-bit, generic TQ gamma-aware, RaBitQ assignment}
- DiskANN × {grouped-PQ prefilter, RaBitQ prefilter, binary-sidecar
  Hamming, plus any TurboQuant codec landed under B2's resolution}

The default position is **route through batch**. A "no" cell must come
with measured or structurally-evident justification, not "scoped out
by the task wording".

The original B1 (HNSW exposes three TQ exact-score modes) collapses
into this: all three modes route, the per-AM Phase 5 validation gate
asserts recall byte-equality on all three under their respective
prepared-query branches.

## B5 (new): Task file wording is now stale and must be amended

`plan/tasks/87-candidate-batched-scoring-across-ams.md` currently says:

> **kernel work in Task 87 is scoped to TurboQuant no-QJL 4-bit only.**
> Other quant types stay on their current inline scoring paths until
> follow-up tasks land their block kernels.

and the Quantizer Scope table marks every non-TQ-no-QJL-4-bit entry as
"follow-up". That is no longer the directive. The task file should be
updated to reflect:

- the abstraction is quantizer-agnostic (unchanged);
- **every quant mode routes through the abstraction where batching
  benefits processing**, with non-routing cells justified per the per-
  AM × quant-mode routing table;
- new SIMD block kernel landings can still be staged into follow-ups
  per quant mode, but **plumbing through `CandidateBatch` is in
  scope for Task 87**.

This wording change is a prerequisite for Phase 2 because the per-AM
validation gates ("non-batched paths show no regression") and the Stop
Conditions ("if measured scoring-share speedup is < 5 % after the
refactor, back the AM out") are written for the narrower scope and
would misfire on the broader scope without an update.

Coder should land the task-file amendment in the same packet
(`reviews/task-87/002-phase1-design-revision`) that addresses B1–B4.

## Impact on B2, B3, B4

- **B2 (DiskANN scope):** broadens. The DiskANN slice now also covers
  routing grouped-PQ and RaBitQ prefilter scoring through
  `CandidateBatch` where the per-expanded-node neighbor set is the
  natural batch boundary. The Stop Condition still applies to the
  *TurboQuant no-QJL 4-bit codec* specifically (since no such codec
  exists on this branch), but DiskANN is no longer scope-blocked by
  the missing TQ codec — the grouped-PQ and RaBitQ paths give it real
  Task 87 in-scope work.
- **B3 (HNSW borrow lifetime):** widens slightly. The lifetime
  contract must now hold for whichever per-neighbor backing each of
  HNSW's quant modes uses (graph-element decoded code for TQ paths,
  whatever sidecar for RaBitQ if/when added). The recommended fix
  (name the borrow-source change in Phase 1 design) is unchanged.
- **B4 (SPIRE structural-slice gate):** unchanged. SPIRE's
  `score_batch_ip` already-chunked nature still puts Phase 2 at risk
  of a near-zero scoring-share delta; the structural-slice gate
  language is still the right resolution.
