## What I verified independently

- **Scoring identity is correct.** `⟨q,o⟩ = ⟨q,c⟩ + ⟨q,o−c⟩`, with `⟨q,c⟩` exact
  per probed list and `⟨q,o−c⟩` estimated by the **unchanged** RaBitQ estimator
  on a code that encodes `r = o−c`. The linearity argument
  (`sign(rot(o−c)) = sign(rot(o)−rot(c))`, query rotated once) is sound — the
  estimator is generic over "the encoded vector," so no query-side change / no new
  kernel is needed. Elegant.
- **`encode_code_residual(v, c)` = `encode_code(v − c)`** with dim asserts on both
  inputs — confirmed in code. The residual scalars (`||r||`, `r_dot`, `||x_dec||`)
  are therefore computed correctly by the existing encoder for `r`, automatically.
- **`combine_residual_estimate(centroid_ip, residual_estimate)` = `centroid_ip +
  residual_estimate`** — the identity in one shared place. Good.
- **Tolerance test references the true exact IP.** `residual_scoring_matches_exact
  _within_tolerance` compares `combine(...)` against `exact_inner_product(q,o)`
  with `rel_err = |combined−exact| / (||q||·||o−c||)` and a bit-dependent tol —
  the residual-scale denominator is the right call (the full sum can be ~0 for a
  random q/centroid, which would make an absolute-error tolerance meaningless).
  `residual_estimate_recovers_exact_residual_term` (bit-identical to
  `encode_code(o−c)`) anchors correctness; `residual_beats_absolute_on_
  concentrated_lists` demonstrates the expected error reduction at bits=1.
- **Stop condition correctly does not fire.** The residual code is byte-identical
  in shape to the plain code (`⌈D·bits/8⌉` + 12-byte scalar tail); the scalars now
  describe `r` instead of `o`; the exact centroid term is per-list, not stored
  per-posting → **zero extra per-posting metadata, identical index size.** That is
  the ideal compact-index outcome and the right basis for the recall-per-probe
  thesis (smaller residual dynamic range → lower quant error).

## The Task 113 coordination is reasoned correctly — hold yourself to it in the scan slice

You identified the right hazard and the right fix: 113's posting-prune cutoff
`||o||·||q||/o_dot` upper-bounds the estimate of `⟨q,o⟩` for **plain** payloads;
under residual encoding the estimate is `⟨q,o−c⟩`, so the sound full-score upper
bound shifts to `⟨q,c⟩ + ||r||·||q||/r_dot`. Since the scan sites don't carry the
centroid term today, gating the (default-on) 113 prune **off in residual mode**
(byte-identical to unpruned) is the correct conservative call, with the shifted
cutoff as a documented follow-up. **Required in the scan slice:** the residual-mode
`pruned==unpruned` recall-safety test you promised — do not let the default-on
prune run on residual payloads with the plain-derived cutoff under any code path.

## For the build/insert/scan slices (carry these)

1. **Centroid consistency (build = insert = scan).** Correctness hinges on the
   *same* centroid bytes being used to encode a posting (build/insert) and to add
   `⟨q,c⟩` at scan. A posting is scored when its assigned list is probed, so the
   probed-list centroid is the right per-posting term — but assert/guarantee no
   centroid drift or requantization between build, insert, and scan (Non-Goal:
   don't change centroid training, so they should be frozen — just don't let a
   refresh/rebuild path desync them). A test that a residual posting scores
   identically whether inserted at build or via later INSERT would pin this.
2. **heap-f32 rerank must stay untouched.** Rerank scores the exact source vector
   `o` from the heap/sidecar, independent of how the posting *code* was encoded, so
   residual mode should not touch the rerank path at all. Confirm that explicitly
   (a residual-mode index whose rerank output is bit-identical to plain-mode
   rerank on the same vectors).
3. **Mode gating + flag.** Default stays plain RaBitQ (Non-Goal: no default change
   without bench-backed promotion). The metadata/mode flag distinguishing plain
   vs residual is a current-mode selector, not old-version compat — keep it a clean
   two-mode switch.
