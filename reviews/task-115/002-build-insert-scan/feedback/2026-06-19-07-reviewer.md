# 115/002 — Deep audit follow-up: residual metadata is under-documented

Reviewed current branch source, Task 115 packets, and the current on-disk-format
docs/fixtures. Static/read-only review only; no new tests or benchmarks run.

## Findings

### P2 — The residual flag was a persisted metadata semantic change and needs explicit version-policy accounting

Task 115 stores `rabitq_residual` in IVF metadata byte 35
(`request.md:15-21`; `src/am/ec_ivf/page.rs:617-622`,
`src/am/ec_ivf/page.rs:667-692`, `src/am/ec_ivf/page.rs:769-779`). That is a
persisted field/meaning change, not just an in-memory reloption. Per the version
policy in `docs/on-disk-format.md:73-86`, incompatible field additions or
reinterpretations must update the format tag, layout assertions, fixtures, and matrix.

The current branch later moved IVF to v4 for the 92-byte sidecar-directory layout, so
the final reader now rejects old v3 metadata by version. That avoids an immediate
runtime ambiguity in the current checkout. But the Task 115 packet itself describes
the byte-35 field as "clean two-mode current-build switch, not old-version compat"
without recording the required format-policy dependency on the v4 clean break. Please
update the Task 115 request/manifest or a follow-up note to say that residual mode is
part of the current IVF v4 metadata contract and is not version-neutral.

### P2 — Current on-disk docs and fixture assertions omit byte 35

The current on-disk docs describe IVF v4 as 92 bytes and document the sidecar head at
80..86 and directory head at 86..92, but they omit the residual flag at byte 35
(`docs/on-disk-format.md:88-111`). The upgrade matrix row likewise mentions only the
sidecar and directory heads (`fixtures/upgrade/matrix.csv:7`). Task 42 is also stale:
it still says IVF metadata is v3/86 bytes and points at the old v3 fixture/assertions
(`plan/tasks/42-on-disk-format-invariants.md:10-36`).

The tests have partial coverage but not enough registry coverage for this field:
`tests/on_disk_fixtures.rs::ivf_metadata_v4_fixture_decodes` asserts quant bits and
sidecar heads but not `rabitq_residual == false`
(`tests/on_disk_fixtures.rs:508-554`), and `tests/size_of_assertions.rs` pins many IVF
metadata offsets but not `EC_IVF_METADATA_RABITQ_RESIDUAL_OFFSET`
(`tests/size_of_assertions.rs:120-142`). Please document byte 35 in
`docs/on-disk-format.md` and the matrix, refresh the stale Task 42 update, and pin the
field in the v4 fixture/size assertions so future metadata changes cannot silently
drop or reinterpret the residual flag.

### P3 — Do not close residual from exact-rerank benches alone

The committed HEAD benchmark correctly found residual mode gives no recall-per-probe
benefit under exact heap-f32 rerank and is slower, and the latest response already
notes the needed `rerank=off` follow-up (`feedback/2026-06-19-06-reviewer.md:18-19`).
Keep that limitation visible: exact rerank masks coarse-side scoring differences, so
Task 115 is not fully answered until the coarse-only/matched-recall lane is measured.
