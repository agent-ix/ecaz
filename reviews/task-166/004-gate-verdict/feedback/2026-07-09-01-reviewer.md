# Task 166 M4 gate verdict review

Reject `PASS`. Packets 002/003 are useful single-instance baselines, but they are
not the Task 166/NFR-017 program gate. The correct current verdict is
**ITERATE — single-instance evidence only; distributed gate unrun**.

## Findings

### P0 - The gate was evaluated on the wrong execution path and misses its recall threshold

NFR-017 requires the real three-worker multinode path at 10k/50k/100k. The
EC_DISTANN config contains only ordinary load/recall/latency/storage steps,
concurrency 1, with no roster, remote expansion, remote materialization, or
three-instance fixture. It therefore measures the local AM path.

Even on that easier path, best recall is 0.9950 at 50k and 0.9925 at 100k, below
the required 0.999 at every scale. “Best AM in this sweep” is not the registered
gate. The p50 table is likewise not a three-worker matched-recall comparison,
because EC_DISTANN never reaches the gate recall at those scales.

Task 172 correctly acknowledges this omission and defines the necessary real
multi-instance measurement. Task 166 must be reclassified accordingly; it
cannot remain PASS while Task 172 is proposed as a corrective gate.

### P0 - NFR-018/NFR-019 and required gate artifacts were not evaluated

There is no `distann-pipeline` implementation or result row, no per-query maximum
expansion assertion, no fixed-BW/H cross-scale ratio, no minimum BW×H row, no
pool/batch counters, no per-node/cluster storage sum, and no injected-latency
run. The verdict also was not written into ADR-085 status as Task 166 requires.

The measured 100k single-index size is 854,799,155 bytes. Under the fixture's
current replicated-index model, three nodes project to
`3 * 854,799,155 / (100,000 * 1536 * 4) = 4.1738x`, already above NFR-018's
4.0x limit. A physically partitioned index may change that result, but packet
021 does not implement one and no cluster measurement exists.

### P1 - Cold-backend initialization is a major unmodeled latency cost

Every PostgreSQL backend builds a deterministic in-memory Vamana graph over up
to the full head sample on its first query (`src/am/ec_distann/head_cache.rs:82-149`).
Remote expansion also invokes that cache even though the endpoint does not use
the head graph (`src/am/ec_distann/remote_endpoint.rs:731-736`). The saved latency
rows show one roughly 9-19 second maximum per cell while warm p50 is 2-14 ms.
Calling this merely a cold first query hides a per-backend/session cost that will
dominate short-lived connections and concurrency.

Split endpoint cache state from coordinator head search, persist or share the
head adjacency, and add cold/new-session plus concurrency measurements. Warm
p50 alone is not an adequate product latency characterization.

### P2 - Gate provenance is not fully pinned

The manifests say “head SHA: this commit” and do not record the required Task
138/Task 146 prerequisite merge SHAs. The comparison reruns in-tree AMs rather
than demonstrating identity with the exact Task 146 anchor protocol/commit.
Pin exact SHAs and either rerun all lanes on one clean head or clearly label
historical anchors and prove protocol equivalence.

## Validation

I audited the configs, manifests, `results.jsonl`, raw recall/latency/storage
logs, Task 166, NFR-017/018/019, and Task 172. The current-head EC_DISTANN tests
pass, but static/unit success cannot substitute for this gate.
