# Task 77 packet 002 — Phase 1 no-slice closeout

## Decision

**Accept with one substantive note** about the object-read cost the
closeout doesn't address. The no-slice direction is sound for
materialize + heap_append, but those two are not the only
candidate-cost classes the task spec named.

## What's solid

- Per-phase numbers are internally consistent: at tg96/nprobe96, the
  attribution summary gives score 103.2 ms/query, materialize 2.65
  ms/query, heap_append 1.92 ms/query, object_read 18.0 ms/query
  (total ~126 ms attributable). Task 76's measured p50 at the same
  setting is 146.7 ms. The ~20 ms gap is unaccounted-for (routing
  draft, top-graph traversal, rerank, return path) but doesn't
  invalidate the score-dominance read.
- Score share at 82-83% is independently confirmed by Task 74's
  Intel profiler (75% in `ProdQuantizer::score_ip_from_split_parts`).
  Two unrelated measurement methods agreeing is strong evidence.
- Fixed-candidate microbench at 77,531 candidates is the right shape
  for a successor task to pick up scoring-kernel work without
  re-deriving the cost split.
- The shelve reasoning ("even eliminating materialize+heap entirely
  wouldn't clear the 10% gate") is correct arithmetic: 4.6 ms / 146.7
  ms = 3.1%, well below 10%.
- Honest about the 100k tg128 result — `candidates = 100,000` exactly,
  min = max, meaning at tg128/nprobe128 on a 100k corpus the high-recall
  ceiling collapses to a full scan. That's important context the body
  doesn't quite spell out, but the data makes it visible.
- Task 78 successor filed for scoring-kernel/storage-format work, which
  matches the task's allowed no-slice-with-handoff branch.

## Substantive note — object reads weren't evaluated for slicing

The Task 77 spec lists five candidate-cost classes:

1. leaf route/object reads
2. candidate row decode/materialization
3. approximate quantized scoring
4. heap-retained candidate maintenance
5. final rerank/top-k handoff

The closeout's shelve argument addresses (2) + (4) — materialize +
heap_append, total 4.6 ms/query at tg96. It excludes (3) per scope. It
does not address (1) object reads.

Object reads at tg96/nprobe96 cost **18.0 ms/query** = **12.3% of
Task 76's p50 (146.7 ms)**. That clears the task's 10% p50 gate as a
target, if a defensible slice exists. The closeout doesn't explain
whether object-read optimization is in scope, out of scope (storage
layer), or considered and rejected.

Two acceptable responses:

- **Add one paragraph to the closeout** explaining why object reads
  are out of scope (e.g. "object reads are shared storage-layer work
  and Task 78 picks up the broader storage-format question") or why a
  slice isn't safe (e.g. "object reads are already pipelined and
  further reduction needs storage redesign"). Then close cleanly.
- **Or reopen briefly** to evaluate one object-read slice (e.g.
  read-coalescing, batch decode, prefetch tuning) before closing. The
  attribution data supports it.

Without one of those, the no-slice decision is incomplete relative to
the task's own scope.

buggy. The query variation now lives in `candidates` and the timing
fields, which is correct.
