# Task 77 packet 001 — attribution hook

## Decision

**Accept.** The timing hook is well-scoped and the corrected candidate
numbers from the fixed diagnostic (15.5M at tg96 vs the Task 75
diagnostic's broken 2.78M) confirm both that the Task 75 bug was real
and that the fix is in.

## What's solid

- **Production path is untouched.** All four timers are guarded by
  `observer.wants_candidate_timing().then(Instant::now)`, and
  `SpireRoutedScanObserver::wants_candidate_timing` defaults to
  `false`. The production no-op observer pays nothing. Diagnostic
  observer opts in.
- **Safe overflow handling.** `elapsed_nanos_since` uses
  `.unwrap_or(u64::MAX)` instead of `.expect()` — consistent with my
  earlier note on Task 75 packet 001 where `.expect()` casts in
  `#[pg_extern]` would crash the backend.
- **Per-phase coverage matches the task spec.** All four classes
  named in the spec (leaf object reads, candidate score,
  materialization, heap append) get timers. The funnel JSONL carries
  them per query.
- **Task 75 bug confirmed fixed.** Spot-checked the new
  `funnel-100k-tg64-b0.jsonl`: per-query `candidates` varies
  (47,310-56,751), where the Task 75 diagnostic was returning
  identical 16,061 for every query at tg ≥ 32. The corrected aggregate
  at tg96 is 15,506,227 candidates — ~5.5x the Task 75 number — which
  matches what one would expect from a non-degenerate per-query
  routing draft.

## Small note (non-blocking)

The timer block re-reads `epoch` from `snapshot.epoch_manifest().epoch`
in some call sites and uses a previously bound `epoch` in others. The
two are the same value in a single scan, so this is style not
correctness. If the file ever grows another timer site, factor the
epoch capture out so future timers don't drift.

## Verdict

Diagnostic surface accepted. Phase 1 measurement and closeout are
reviewed separately in packet 002 feedback.
