# Task 81 packet 002 — local 100k block-summary gate

## Decision

**Accept as local gate pass + diagnostics validation.** The packet does what
it claims: shows the current SPIRE block-summary mechanism (V4 multi-rep
summaries + deferred decode) clears all three Task 81 local gates at 100k,
and proves the new packet 001 diagnostic counters report consistent
attribution. However, this is essentially a re-measurement of Task 79
packet 044 under the ADR-074 vocabulary, **not** the new persisted
block-summary format work that Task 81 ultimately needs. That's fine for a
gate-clearing checkpoint, but reviewers should be clear about what this
packet does and does not establish.

## Critical context: what this packet does NOT establish

The headline numbers (3,673,383 candidates, recall 0.9940) are
**byte-identical** to Task 79 packet 044's `global1152` row. That is not a
coincidence: Task 79 already implemented the V4 multi-rep summary +
deferred-decode mechanism, and packet 001 just added new counters without
changing behavior. So this packet:

- **Does** prove the new diagnostics infrastructure is correct and
  consistent.
- **Does** prove the existing V4 + deferred-decode path still passes the
  Task 81 local gates after the packet 001 diagnostics slice landed (no
  regression).
- **Does NOT** prove any new pruning mechanism. Task 81's actual scope
  (per spec: "persist compact scoreable summaries for deterministic row
  blocks inside each SPIRE leaf … include an explicit format/version
  plan") has not been exercised by this packet. The leaf format is
  unchanged from Task 79.

That's not a defect — it's the right checkpoint shape: confirm the
diagnostic infrastructure, get a clean local row, then proceed to the
actual format/mechanism work. But the AWS 1M gate is the real test, and
the Task 80 review showed that at 1M with the *current* mechanism, the
cap-1152 candidate count collapses to the old tg96 baseline (18,428/q
identical), so this local gate pass does not predict an AWS 1M gate pass.

## What the diagnostic split tells the next slice

The 44/56 summary-vs-row CPU split, and the 11.6 vs 63.2 MB/q I/O split,
are useful steering signals for whatever the actual Task 81 mechanism
slice ends up being:

- **Per-query summary I/O is small (11.6 MB)** — adding more summaries
  (more reps, finer block granularity) has headroom before summary I/O
  becomes the bottleneck.
- **Per-query row I/O is 5.4× larger** — the per-candidate read cost
  dominates, and at 1M this scales further. This matches the Task 80
  finding that the latency gap at matched candidates is per-candidate
  I/O, not candidate count.
- **Row scoring CPU (56%) > summary scoring CPU (44%)** — reducing rows
  is more valuable than making summary scoring cheaper per unit.

If the next slice targets a finer block size (8 rows? 4 rows?) with more
summary representatives, that would attack the right axis: fewer rows
admitted per selected block while keeping summary discrimination strong.

## Non-blocking notes

1. **Diagnostic rerun (`suite-run-diagnostics-rerun.log`)** is present in
   the artifacts list but not described in the manifest. Worth a one-line
   manifest entry explaining why a rerun was needed.
2. **The block-size declaration isn't shown in the result row** — the
   16-row block size is implicit. Would help future cross-packet review
   if `leaf_block_rows` is recorded in the result row metadata alongside
   `max_global_blocks`.
3. **AWS 1M follow-up gate**: per Task 81 spec, AWS 1M only runs after
   "a local row clears the Task 80 candidate and latency gate shape".
   This packet clears the local gate, so AWS 1M is unblocked. But the
   Task 80 review evidence strongly suggests the AWS 1M run with this
   unchanged mechanism will fail again. Worth considering whether to
   land an actual mechanism change first (finer block size? richer
   summaries? cold/hot payload split per ADR-074?) before re-burning
   AWS budget.

## Verdict

Accept. Local gate passes cleanly, diagnostic counters validated, no
behavior regression from packet 001. The headline result is the same as
Task 79 044 by design — the new evidence is in the counter attribution,
not the bench numbers. AWS 1M gate is now formally unblocked but the
mechanism work needed to make AWS 1M pass remains ahead.

Recommend the next slice either (a) lands an actual format/mechanism
change before re-running AWS 1M, or (b) explicitly runs AWS 1M as a
"reconfirm the gap" measurement with a clear hypothesis for what the
deeper format change should target.
