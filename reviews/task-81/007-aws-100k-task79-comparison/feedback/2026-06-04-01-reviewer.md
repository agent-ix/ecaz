# Task 81 packet 007 — AWS 100k Task 79 comparison (re-framed bar)

## Decision

**Accept the comparison as honest, but flag two important caveats**:
(1) the 3.2ms p50 delta is at the edge of run-to-run variance for a
single q200 row, and (2) the re-framed acceptance bar is a substantial
scope reduction from the original Task 81 charter and deserves explicit
acknowledgment.

The headline numbers (Task 81 32.023ms vs Task 79 35.199ms p50 at
identical 3,672,619 cands / 0.9945 recall) are real data points on a
clean, comparable surface. Whether they justify Task 81 closure depends
on what scope the task is now expected to deliver — and that has moved.

## Caveat 1: 3.2ms delta on a single q200 row is measurement variance

The claim is "9.02% p50 improvement". On a single 200-query measurement
at AWS Graviton with retained surface, 3ms variation is well within
run-to-run noise:

- **No mechanism change.** Packet 001 was diagnostics-only (counters
  + timing splits, no scan/storage behavior change — I confirmed this
  in the packet 001 review). There is no Task 81 code path that would
  systematically make scoring faster than Task 79's path.
- **The p95 and p99 deltas are also small** (Task 79 36.20/36.59 ms vs
  Task 81 32.94/33.32 ms = 3.3/3.3 ms deltas). All three percentiles
  move together by ~3 ms, consistent with a single run sample
  centered ~3ms lower than the Task 79 sample. That's a shift in the
  measurement noise floor, not a structural latency win.
- **Without an N-run repeat** (e.g. 3-5 runs of each row with
  variance estimated) it's not possible to distinguish "9% systematic
  improvement" from "single sample drawn from a distribution that
  overlaps Task 79's by ±5ms".

For the headline framing, I'd recommend either:

a. running the comparison 3 times each (Task 79 surface, Task 81
   branch code) and reporting median + range, or
b. lowering the claim from "9% improvement" to "within run-to-run
   variance of Task 79 — no regression from the diagnostics slice."

Option (b) is honest and supports closure of the no-regression check.
Option (a) is needed if you want to claim Task 81 actually delivered a
latency improvement.

## Caveat 2: the re-framed bar is a substantial scope reduction

The original Task 81 spec (`plan/tasks/81-spire-leaf-block-summary-format.md`)
says:

> AWS 1M accepted rows must improve recall over the old tg96 row
> without increasing the candidate surface relative to the old
> 9,213,846 q500 shape.

This bar requires moving 1M recall above 0.9832 while keeping
candidates ≤9.2M. Packets 003 and 005 demonstrated that the current
mechanism cannot do this. Packet 006 attempted to diagnose why and
hit tooling limits.

Packet 007 re-frames the bar to: "reduce latency at the same
recall/candidate point as Task 79 at AWS 100k". That's a different
goal:

- The original bar targets **1M scale recall improvement**.
- The re-framed bar targets **100k scale latency at matched recall**.

The user explicitly clarified the re-framing, so it's a legitimate
scope change — but it should be recorded as such in the Task 81 spec
status, not slid in via a packet result. Two paths forward:

1. **Update the Task 81 spec** to formally narrow the AWS gate to
   "100k matched-recall latency parity or improvement", and explicitly
   defer the 1M recall problem to a successor task (probably an
   ADR-074 format implementation under a new Task 82 number).
2. **Keep the original spec** and close packet 007 as "Task 81 partial
   close: no regression at 100k under the re-framed bar; 1M recall
   bar remains unmet and is deferred". Then file Task 82 for the
   actual format work.

Either is fine procedurally. Conflating the two — accepting packet
007 as full Task 81 closure under a bar the spec doesn't define — is
the thing to avoid.

## Verdict

Accept as honest no-regression evidence at the AWS 100k matched-recall
point, **with the caveat that the 9% claim should be downgraded to
"within run-to-run variance"** unless an N-run repeat is added.

The Task 81 closure decision is properly the user's, not mine, but
flagging that:

- **Closing on packet 007's bar** = closing Task 81 with the 1M
  recall problem deferred. The spec needs an explicit amendment
  acknowledging this, and Task 82 (or equivalent) should be filed
  for the actual ADR-074 format work.
- **Closing on packet 007's bar without spec amendment** = quietly
  redefining the task's success criteria, which would damage
  cross-task evidence consistency.

Recommend: amend Task 81 spec to record the bar pivot + defer 1M
recall work to a successor task, then accept packet 007 as the
closeout under the amended bar.
