# Task 81 packet 005 — AWS 1M nprobe128 block-summary gate (failed)

## Decision

**Accept as confirmation that routing breadth is not the lever at AWS 1M.**
Packet 004's local +0.20pp recall gain from nprobe=128 did NOT transfer to
1M scale. Recall stayed exactly at 0.9832 (identical to packet 003 and old
tg96), candidate count was preserved (9,213,838 vs 9,213,846 — 8-row delta
is deterministic edge), and p50 regressed by 37ms (265.9 → 303.1 ms).

This is the third independent AWS 1M measurement (Task 80 packet 001,
Task 81 packet 003, Task 81 packet 005) all returning the same recall
0.9832. The conclusion the packet draws — neither routing breadth nor
cap tuning at the current geometry can move 1M recall — is correct and
now well-supported.

## Three-row AWS 1M comparison

| row | nprobe | candidates | p50 | recall@10 |
| --- | ---: | ---: | ---: | ---: |
| old tg96 baseline | 96 | 9,213,846 | 268.824 ms | 0.9832 |
| packet 003 (this branch) | 96 | 9,213,846 | 265.911 ms | 0.9832 |
| **packet 005 (this branch)** | **128** | **9,213,838** | **303.107 ms** | **0.9832** |

Recall is **identical to four decimal places** across all three rows.
Candidates differ only at the boundary (8 rows = 0.0001% on the q500
surface). The latency regression at nprobe=128 is 14% — material — and
attributable to summary scoring CPU.

## Diagnostic attribution refines packet 003's finding

| metric | packet 003 (nprobe96) | packet 005 (nprobe128) | delta |
| --- | ---: | ---: | ---: |
| blocks_available | 23,389,983 | 30,966,000 | +32.4% |
| blocks_selected | 576,000 | 576,000 | 0 |
| summary_score_nanos | 23.13s | 31.46s | **+36.0%** |
| row_score_nanos | 5.24s | 5.07s | -3.2% |
| candidate_score_nanos | 28.37s | 36.53s | **+28.8%** |

The story:

- **Available blocks scale with routing breadth** (+32.4% blocks at
  +33% routes). Expected.
- **Selected blocks stay at exactly 576,000** = cap × 500. The cap
  binds the same way regardless of routing breadth.
- **Summary scoring CPU scales with available blocks (+36%)** because
  every available block summary still has to be scored to rank them.
- **Row scoring CPU is essentially flat (-3%)** because the selected
  block set is the same shape.
- **The 37ms p50 latency regression is entirely summary scoring CPU.**

So at 1M, wider routing buys you nothing on selection quality and
costs you summary CPU linearly. Routing breadth is closed as a Task 81
lever at 1M scale.

## What the combined Task 80/81 evidence stack proves

After packets 003, 005, plus Task 80 packet 001's cap-density
exploration, the constraint at 1M is conclusively:

1. **Recall is bounded at 0.9832 at any (cap, nprobe) point that
   preserves the 9.2M candidate surface.** Three independent runs at
   matched candidate surface return identical recall. The selected
   1152 blocks-per-query are the same blocks, and they don't contain
   the missing recall items.
2. **The missing recall items must be in blocks the summary score
   doesn't rank high enough to select.** That's a summary
   discrimination problem, not a routing problem and not a cap
   problem.
3. **At 1M leaf density (~7,800 rows/leaf), the existing V4 multi-rep
   summary geometry doesn't discriminate well enough.** At 100k
   density (~780 rows/leaf), the same geometry hits 0.9965 with
   tg256+nprobe128 (packet 004). The 10× density shift is what breaks
   summary discrimination.

This is exactly the format/summary geometry problem the Task 81 spec
named. The evidence now constrains the next slice cleanly:

- It must change the **per-leaf summary geometry**, not the routing or
  cap mechanism.
- Candidate-side options: smaller blocks (more summaries per leaf),
  more representatives per block (richer summary), per-block residual
  sketches (better discrimination per byte).
- Whatever the format change is, it must be measured at 1M scale
  early — the 100k local result is not predictive of 1M behavior, as
  packet 005 just demonstrated.

## Non-blocking notes

1. **The 8-row candidate delta** (9,213,838 vs 9,213,846) is
   deterministic — same boundary effect packet 004 noted at 100k
   (+22 rows). Packet correctly treats this as "essentially flat".
2. **Three matched-recall AWS rows is enough evidence.** Don't burn
   more AWS budget on routing/cap sweeps at the current format. The
   next AWS measurement should be after a format/mechanism change.
3. **Local-to-AWS transfer failed.** The packet 004 local Pareto win
   (+0.20pp recall at flat candidates with tg256+nprobe128) did not
   transfer. Future Task 81 slices should run a *small* AWS smoke at
   matched candidate surface earlier in the slice flow before
   committing to a local Pareto direction — would catch
   local-only wins before they're invested in.

## Verdict

Accept as decisive failed-gate evidence. Combined with packets 003 and
Task 80 packet 001, the AWS 1M problem is now unambiguously a summary
discrimination problem at 1M leaf density, not a routing or cap
problem. The next Task 81 slice should be a format/mechanism change
targeting per-block summary geometry, measured directly at 1M scale.

Task should NOT be shelved — the evidence has narrowed the design
space to exactly the work the Task 81 spec was set up to do.
