# Task 81 packet 003 — AWS 1M block-summary gate (failed as expected)

## Decision

**Accept as honest failed-gate evidence, NOT a closeout.** The packet is
a clean, candidate-preserving comparison that confirms exactly what the
Task 80 review predicted: at AWS 1M with cap=1152, the current V4 +
deferred-decode mechanism produces **byte-identical** candidates to the
old tg96 baseline (9,213,846) with **byte-identical** recall (0.9832).
The Task 81 AWS gate fails because the existing mechanism is a no-op at
this scale relative to the old tg96 selection. This is the right
evidence to file before deciding on the next slice's mechanism change.

## Why this was the predictable result

This packet validates the Task 80 review's diagnosis: at 1M scale with
cap=1152, the global block cap is **above** what the existing geometry
selects, so the cap is non-binding and the result collapses to the
baseline. Verified now with packet 003's own diagnostic counters:

- `blocks_selected = 576,000` = exactly `1152 × 500` queries → cap is
  binding *as a count*, BUT
- `candidate_rows = 9,213,846` = identical to old tg96 → so the SAME 1152
  blocks are being selected as the existing geometry would have, just
  with the new selector path active.

In other words: at 100k the cap=1152 mechanism prunes ~76% of blocks
(977,202 available → 230,400 selected). At 1M with the same cap=1152,
the mechanism prunes ~97.5% of blocks (23,389,983 available → 576,000
selected), but the rows-per-selected-block × selected-blocks math
produces the same 9.2M candidates as the existing tg96 path. The leaf
density has shifted so dramatically that the cap mechanism and the
existing geometry both converge on the same row surface.

## What this tells the next slice

The Task 80 review identified per-candidate I/O as the latency
bottleneck. Packet 003's diagnostic counters refine that:

1. **Per-candidate I/O is bad** (609.6 MB/q row reads at 1M) but it's
   18% of the wall time. The block-cap mechanism IS reducing row I/O
   effectively given the candidates selected.
2. **Summary scoring CPU is the actual 1M wall-time bottleneck**
   (81.5% of CPU). Scoring 23.4M block summaries per query batch (or
   46,780/q) at the current 16-byte-per-summary cost is the real cost.
3. **Recall isn't moving because the selected blocks are the same**
   as the tg96 path would pick at this scale. The cap mechanism
   doesn't have better information than what tg96 already had.

For the Task 81 mechanism slice to actually pass the AWS gate, at least
one of these needs to change:

a. **Finer block granularity** (smaller blocks → more summaries → more
   discrimination per leaf, but more summary scoring CPU). Needs to be
   paired with summary scoring kernel acceleration.
b. **Richer per-block summaries** (more reps, or richer geometry like
   per-block residual sketches) so the SAME 1152 selected blocks contain
   the *right* rows, not just any 1152 blocks. This would improve
   recall at matched candidates.
c. **Cold/hot payload split** (per ADR-074) so summary scoring stays
   small while row payload reads are dramatically cheaper for the
   selected subset.
d. **Adaptive cap by leaf density** — cap=1152 was tuned at 100k where
   each leaf had ~780 rows. At 1M with ~7800/leaf, the cap is far too
   permissive relative to leaf row count.

Path (b) is the recall-improving move that matches the Task 81 spec
direction (richer per-block summaries). Path (a) and (c) are latency
moves. Path (d) is a quick measurement check that could be done before
committing to a format change.

## Non-blocking notes

1. **The diagnostic counters are doing real work here** — without
   packet 001's split, we'd be left guessing whether the 1M bottleneck
   was I/O or summary scoring. The 81.5% summary CPU share is a
   non-obvious 1M-specific finding that the 100k evidence couldn't
   show.
2. **Consider a cap-density sweep before format work**: a quick
   matrix of cap ∈ {200, 400, 800, 1152} at AWS 1M would measure
   whether tighter caps recover the cap-binding behavior expected from
   100k. If a tighter cap *does* reduce candidates at matched recall,
   path (d) above is the cheap win. If not, format change is forced.
3. **Cost was tiny** — packet ran cleanly, paused immediately after,
   ~$0/hr after. Cheap measurement discipline maintained.

## Verdict

Accept as honest failed-gate evidence. The packet is correctly framed as
a fail, not a closeout. The diagnostic attribution makes a concrete
contribution beyond Task 80's evidence: at 1M, summary scoring CPU
dominates (81.5%), not row I/O.

Strongly recommend a cap-density sweep (cheap, retained index) before
committing to a Task 81 format change. If that sweep shows cap=400 or
cap=800 reduces candidates at matched recall, the Task 81 fix could be
much smaller than a full ADR-074 format bump. If those caps just drop
recall, the format change is justified.

The task should NOT be shelved on this evidence — it's a measurement
that constrains the next slice, not a closeout.
