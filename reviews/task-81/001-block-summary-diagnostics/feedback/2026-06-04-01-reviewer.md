# Task 81 packet 001 — block-summary diagnostics + ADR-074 contract

**Accept.** Clean diagnostics-only slice; no behavior change to scan

## Code review (commit `9fa1fc505`)

### Behavior preservation (clean)

- Scan selector logic unchanged: `select_leaf_block_row_ranges()` and
  sampled/global pruning paths add only observational calls
  (`leaf_block_selection()`, `leaf_summary_score_time()`); all conditional
  returns and scoring remain identical.
- All fallback paths covered: empty summaries, non-RaBitQ formats, disabled
  pruning (`max_blocks >= summaries.len()`), and V2-only fallback routes all
  explicitly call `leaf_block_selection(epoch, placement, summaries.len(),
  summaries.len())` to record full-leaf fallback.
- Storage decode path untouched: `row_segment_bytes_total()` extracts
  diagnostic metadata only; no changes to segment read or validation logic.

### Diagnostic correctness (clean)

- **Summary bytes**: sourced from explicit V3/V4 metadata
  (`leaf_object.meta.summary_bytes_total`, validated during decode). Not
  heuristic.
- **Row bytes**: `row_segment_bytes_total()` uses checked subtraction
  (header + meta + summary from total) with proper underflow error handling
  (`ec_spire leaf V3 row segment byte length underflow`). Correct
  derivation, no estimation.
- **Block selection semantics**: `selected_blocks = min(selected_blocks,
  available_blocks)` prevents overflow; skipped count derived as
  `available - selected`. Registered in both placement and leaf-level
  diagnostics.

### Timing split (clean — and worth explaining for downstream review)

`leaf_summary_score_time()` and `leaf_row_score_time()` route through
separate fields (`leaf_summary_score_nanos`, `leaf_row_score_nanos`) AND
contribute to the broader `candidate_score_nanos` aggregate. This is
intentional: the leaf timers are sub-components, not duplicates. The
aggregate is computed as `summary + row`, so totals stay consistent with
the existing candidate-score timer.

For Task 81 closeout evidence, this is exactly the split needed: you can
attribute latency between summary-scoring work (cheap when summaries
discriminate well) and row-scoring work (the cost block-pruning aims to
avoid).

### SQL surface (clean)

7 new fields added to `ec_spire_index_scan_leaf_candidate_snapshot`:
5 block counts/bytes + 2 timers. Uses `i64` coercion with `.expect()` on
usize/u64 conversions, matching the existing extension pattern. Acceptable
because these conversions are in the marshalling layer, not on the scan
hot path.

### Safety (clean)

- No new unsafe blocks.
- `.expect()` calls limited to SQL marshalling (i64 coercion).
- No panics or unwraps on the scan hot path.
- V3/V4 readers reused, not duplicated.

### ADR-074 alignment (clean)

The ADR update now correctly records:
- V2 = row-payload-only fallback (no summaries)
- V3 = single-representative block summaries
- V4 = multi-representative block summaries (k=3 in current builds)

This matches the implementation and gives Task 81 a stable format-version
ground truth before the actual pruning slice changes scan behavior.

   available` valid in every diagnostic context.
