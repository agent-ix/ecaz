# Task 81 packet 006 — AWS 1M block-rank attribution (abandoned)

## Decision

**Accept as honest negative diagnostic provenance.** The attempt to
diagnose WHY recall stays at 0.9832 across packets 003/005 by computing
per-query missed-winner ranks didn't work in the available time/tooling.
The packet correctly stops, files the tooling gap, and recommends a
pivot. That's the right call.

## What was attempted and what failed

The goal was a per-query rank-attribution diagnostic: for each query
where recall@10 is incomplete, find the rank of the missed winner's
block in the global summary score ordering. That would tell us whether
the cap=1152 is cutting off the right blocks (missed by 100s of ranks)
or the wrong ones (missed by 10s).

Three approaches were tried:

1. **q500 truth cache sliced to q50**: failed descriptor validation
   because the query hash no longer matches a q50 prefix of the q500
   query set. Correct guard behavior — the truth cache shouldn't be
   usable against a different query set. This is a tooling limitation,
   not a code defect.
2. **Uncached q50 with full corpus stream**: would compute exact truth
   by scanning 1M rows. Cancelled because q50 progress probe showed it
   would take longer than the SSM window.
3. **Raw SQL fallback**: also too slow as a diagnostic query, cancelled.

## One useful diagnostic preserved

The q1 offset probe (`ssm-rank-offset-probe-q1-rerun-final4.json`)
confirms `truth_id + 1` is the correct mapping for this retained SPIRE
surface, and q1 has all 10 exact neighbors selected under cap=1152.

That's a single data point but it's useful: it rules out a global
selection failure on q1. The recall miss has to be unevenly distributed
across other queries — i.e., some queries get all 10 winners selected,
others miss multiple. Without the q50 rank distribution we can't see the
miss-rank shape.

## Tooling gap correctly identified

The packet recommends not spending more Task 81 time on this path until
the suite runner has first-class support for either:

- reusing a validated q500 truth cache for a limited prefix of queries
  (cache slice with descriptor mode that re-hashes prefix), or
- emitting per-query rank diagnostics without recomputing exact truth.

That's a legitimate tooling deferral. Per the FR-038 / no-shell-sweeper
rule, this should be filed as an `ecaz bench suite` extension ticket,
not a one-off shell hack.

## Pivot to packet 007 is reasonable

The packet recommends pivoting Task 81's acceptance bar to the Task 79
optimized comparison rather than the old full-leaf 15.5M row. That's a
significant scope re-framing (see packet 007 review), but the user
clarified it directly, so the pivot itself is well-grounded. Packet 007

## Verdict

Accept as honest abandoned-attempt evidence. The tooling gap is real
and worth a small `ecaz bench suite` extension ticket. The pivot to
packet 007's re-framed bar is reasonable given the user's clarification.

The rank-attribution diagnostic remains valuable future work if the
tooling lands — it's still the cleanest way to attribute "where does
the missing recall come from" at 1M scale, and that question matters
for any future SPIRE format work targeting >0.9832 recall at the
9.2M candidate surface.
