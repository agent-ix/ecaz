## P1-1 — `ec_distann.fused_head_hop` is behaviorally inert; the A/B compared a configuration with itself

In `select_seed_candidates` (`src/am/ec_distann/generation_read.rs`), the
fused branch and the plain-crown branch return the identical value:

- fused on: rank crown → `record_fused_head_hop()` → `return Ok(seeds)`;
- fused off (crown on, pruning off): rank crown → `return Ok(seeds)`.

The only difference the GUC makes is incrementing a counter. Both arms
feed the same crown-ranked ids into the same first expansion; neither
performs the dedicated head fan-out. The packet's own artifacts prove the
paths are identical: unfused-50k and fused-50k report the same
`traversal_hop_rounds` (680 = 680, likewise at 10k/100k, and equal to
Task 212's plain-crown arm), the same per-scale recall to four digits, and
the same hop means (9.90/13.60/12.48 in both packets' validation logs).

Consequences:

- **FR-090-AC-5 is not met.** The AC requires "hop/RTT counter deltas" so
  the mechanism (one fewer round trip) is visible in evidence. The
  measured delta is exactly zero — because no round trip was removed;
  the unfused arm had already skipped the head fan-out. The latency
  deltas in the request (e.g. 44.20 → 41.10 @100k) are run noise between
  identical configurations (Task 212's logs show 30% noise between
  provably-identical arms at 50k).
- **This is the inert-mechanism failure mode the spec names.** FR-089's
  observability clause exists because four Task 210 mechanisms ran inert
  inside green suites and "a fifth is not acceptable." `fused_head_hops`
  being non-zero satisfied the letter of the activation check while the
  activation changed nothing — the counter attests the branch was taken,
  not that the mechanism did work. This is the fifth.

## P1-2 — The unfused two-phase path is unreachable with a populated crown, inverting the spec's arm definitions

FR-090: "When the crown is off, unpopulated, or misses, the scan SHALL use
the unfused two-phase path (dedicated head fan-out, then traversal)…" and
the fused behavior is opt-in via this FR. As implemented, *any* populated
crown hijacks seeding, so crown-on + fused-off — the exact "unfused"
control arm the task file specifies ("both with crown on, so the delta
attributes to fusion alone") — never runs the two-phase path.

**Fix direction** (shared with Task 212 P1-1): crown-on + fused-off must
run the dedicated FR-080 head fan-out with the crown unused for seeding;
`fused_head_hop=on` must be the one switch that replaces that fan-out with
crown-ranked ids in the first FR-079 expansion. Then re-run the 10k/50k/
100k A/B — if fusion works, the fused arm shows a per-query round-trip
reduction in counters, not just a mean-latency wiggle. Note the current
per-hit `dist` flowing from `crown.rank` is the quantized code distance;
that is fine for beam ordering (the beam is code-ordered anyway) and seeds
get exact distances from their first expansion, so the fix is confined to
path selection, not distance handling.

## P2-3 — Seed-set-change labeling is asserted, not evidenced

The fused arms are labeled `seed_set_change=true` (correct by construction
at capacity 512 < sample_count 4096 — the exact policy is structurally
unclaimable, matching the spec). But the `seed_id_digest` lines that would
*evidence* the change are arm-blind: fused, unfused, and even the Task 212
control all report the same digest because the digest probe runs without
the arm's session GUCs (details in Task 212 feedback P1-2). After the
digest probe is fixed, the fused arm's digest should demonstrably differ
from the unfused arm's.

## P2-4 — FR-090-AC-1/AC-2 have no tests

The positional contract (one response row per requested id, request order,
across owners) and the threshold/batch-limit equivalence are listed as
Test-verified ACs. The implementation inherits both by construction (the
fused first request is an ordinary expansion batch), which is the right
design — but "inherited by construction" was the argument for the four
Task 210 inert mechanisms too. After the P1 rework, one focused test that
a fused first round with seeds spanning ≥2 owners returns positionally
correct rows, and one asserting the fused round requests ≤ `seed_count`
ids, would close these.

## P2-5 — Mid-request failure semantics unimplemented or unevidenced

FR-090 requires an epoch-mismatch refresh-retry to re-enter via the
**unfused** path with all crown-derived candidate state discarded. I could
not find that handling, and nothing in the packet exercises it. Today it
is moot (fused ≡ unfused), but it becomes real the moment P1-1 is fixed —
either implement it in the retry path or cite where the existing refresh
logic already guarantees it.
