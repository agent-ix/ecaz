## Verdict

The equivalence test and counters are solid and close my packet-001 gaps. But the
EXPLAIN A/B in this packet is the headline, and it is a **red flag for the
score-in-place thesis, not a win**: zero-copy page scatter is **~2.4× slower**
than the copy fallback (51.2 ms vs 21.4 ms) despite copying zero payload bytes.
That deserves a hard decision gate before more 111c kernel work. Detail below. Not
blocking the checkpoint — the code is correct — but the direction needs a call.

## The strategic finding — scatter is slower than copy, and the cause is locality

| path | bytes copied | scan µs | exec ms |
| --- | ---: | ---: | ---: |
| page scatter (`on`) | 0 | 46,983 | **51.2** |
| copy fallback (`off`) | 18.89 MB | 17,244 | **21.4** |

The copy fallback copies ~19 MB and is still **2.4× faster**. This is the
contiguous-access lesson, measured: the fallback does a cheap bulk memcpy into a
contiguous slab and then the SIMD transpose reads it **sequentially**
(prefetch-friendly, cache-optimal). The scatter path reads payloads through
per-posting borrowed refs scattered across pages — losing sequential locality and
paying per-posting page/offset lookups + generic batch construction. **The copy
was never the bottleneck; the scattered read pattern is.**

This directly challenges the premise behind 111b/111c ("read each byte once, no
copy = the floor"). On this evidence, *copy-once-then-read-sequentially* beats
*read-scattered-once*. dense-a (Approach A) also copies into a contiguous scratch
and then reads sequentially — so scatter is currently losing to A for the same
reason.

## Recommendation — gate the rest of 111c

1. **Set a hard gate: page scatter must beat dense-a, or 111c pivots/stops.** Do
   not fan out the scatter kernel to RaBitQ{1,2,4,8} × SVE2/NEON until the TQ
   reference path is at least competitive on the same host. Fanning out a path
   that's 2.4× slower multiplies the kernel-matrix cost against a losing design.
2. **The one lever worth trying first: exploit intra-page payload contiguity.**
   Payloads *within* one page are contiguous; only page boundaries break
   sequentiality. If the scatter path currently gathers per-posting refs even
   within a page, restructure it to score each page's postings as a contiguous
   sub-run and only "jump" at page boundaries (process per-page runs, accumulate
   the batch across pages). That recovers most of the lost locality without a
   copy. Packet 003's heap-tid fix is in this spirit but doesn't address the
   payload access pattern.
3. **If, after the per-page-run rework, scatter still trails the
   copy/dense-a path,** that is strong evidence the contiguous-copy approach
   (dense-a, or 111b-copy) is simply the better design for this workload — which
   would be a legitimate, evidence-backed outcome to record (copy is cheap;
   locality is king), and 111d (pre-transpose) would not rescue it because it
   doesn't change the scattered read.

The honest read: this packet does its job (correctness + observability), and the
A/B it records is exactly the kind of early signal that should redirect effort.
Leaving the request open.
