# Feedback: Task 111c Packet 004 — Page-Run Payload Refs

**Reviewer:** Claude (Opus 4.8)
**Date:** 2026-06-17
**Checkpoint reviewed:** `f642231d6`

## Verdict

The lever is correctly implemented, and the result is decisive: **it is an
exhausted/insufficient lever.** This was the main optimization I recommended in
packet 002, and applying it moved page scatter only 35.8 → 34.5 ms while the
copy fallback is ~23 ms — scatter still loses by ~49%. To the coder's explicit
question: **yes, record this and pivot — do not fan scatter out across
codecs/ISAs.** Reasoning below.

## Code — correct

- `payload_page_runs` is the right reader boundary: it exposes contiguous
  borrowed payload runs (`start_index`, `item_count`, slice) split on page
  boundaries, with checked offset/end arithmetic. The scan pushes payload refs
  per run instead of a `single_page_slice` per posting.
- Ordering / live-tid budget / delete-skipping / cross-page batch accumulation
  are preserved (metadata still per-posting via `push_columnar_metadata`;
  payloads per-run), and the dense flush count stays 109 — same as the copy
  fallback, confirming width is unchanged. Equivalence test still green, so the
  refactor is a true no-op on results.

So the per-posting payload-lookup overhead is genuinely gone; what's left is the
irreducible part.

## Why this is the end of the scatter line (answering the gate)

The gap is now structural, not micro-optimizable:

- **The remaining cost is the scattered read itself**, plus the fact that copy's
  slab is *more compact* than the page-resident layout (no page headers/gaps
  between the batch's payloads, L1-resident after the write). Page-run refs
  recover intra-page sequentiality but cannot make the cross-page working set as
  dense or as prefetchable as a freshly-written contiguous slab. 003 removed the
  heap-tid allocation; 004 removed the per-posting payload lookup; the residual
  ~49% is the locality ceiling I flagged, and there is no per-posting overhead
  left to chase.
- **It's a pigeonhole, not a missing optimization.** For a large payload you
  cannot have a width-≥32 batch that is *both* contiguous in memory *and*
  zero-copy — the postings don't fit one page, so you either copy them
  contiguous (copy / Approach A) or read them scattered (this). The bench shows,
  repeatedly, that cheap-bulk-copy + sequential read beats scattered zero-copy.
- **111d will not rescue it.** Pre-transpose removes the scan-time transpose, but
  that helps copy and scatter *equally* and does nothing about the scattered read
  — so it cannot flip scatter ahead of copy. 111d is moot for this purpose.

This is the "build it, optimize it, measure it, and let the evidence decide"
outcome applied to score-in-place — the same rigor that settled A-vs-B in 111a.
The best design was genuinely pursued (format 111b, zero-copy scatter 111c/001,
equivalence + counters 002, heap-tid 003, page-run 004) and it lost to
contiguous-copy on real hardware. That's a complete, durable answer, not a
premature stop.

## Recommendation

1. **Pivot: stop the 111c scatter fan-out.** Don't build RaBitQ{1,2,4,8} /
   grouped-PQ × SVE2/NEON scatter kernels — that multiplies the kernel matrix
   against a path that's ~49% slower with no remaining lever.
2. **Record a 111c closeout** (like 111a/008 and 111b/009): score-in-place
   scatter is dominated by contiguous-copy; mark 111d won't-pursue (orthogonal,
   can't rescue) and 111e moot.
3. **The durable answer to Task 111's latency goal stands from 111a:** compact
   dense blocks + Approach A coalescing + typed views. 111b columnar stays
   complete-but-not-promoted — without the scatter win it is ≈ A on a
   larger-storage format, so it's dominated by dense-a; keep it gated/off.
4. Keep the `columnar_page_scatter` GUC + the 111b columnar format in-tree as the
   measured negative result / diagnostic, but off by default.

Strong, honest slice — and the right place to call it. Leaving the request open
for an outside decision; not closing it or flipping status.
