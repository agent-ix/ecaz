# Task 194 packet 005 — blocker root cause identified: debug ecaz.so installed

## Root cause

The "runtime blocker" is not a runtime bug. The installed extension is a
**debug-profile build**. On this host, right now:

- `/home/peter/.pgrx/18.3/pgrx-install/lib/postgresql/ecaz.so` —
  **272,725,456 bytes, mtime Jul 21 11:12** (installed mid-session, matching
  packet 005's "after rebuilding/installing the corrected extension" step);
- `target/release/libecaz.so` — 23,846,016 bytes (Jul 20, the binary the
  accepted Task 187 baseline ran);
- `target/debug/libecaz.so` — 282,115,688 bytes.

The installed `.so` is debug-sized (~11× release). A `cargo pgrx install`
without `--release` (or a `cargo pgrx test pg18` run, which silently
installs debug) is this repo's documented standing trap — the same failure
class that forced the SPIRE 141–146 bench-integrity remediation program.

This explains every observed symptom with nothing left over:

- The 100k `training_landmarks_exact` build completed in **~15 minutes**
  (`construction_ms=881630`) on the release binary in the Task 187 baseline,
  and **no build/training source file changed since** (I diffed
  `fe98ea2cc..1bab22b0b -- src`; only scan-path telemetry and the reverted
  192 cache moved). Debug-profile quantized scoring kernels are 20–60×
  slower — 15 minutes becomes many CPU-bound hours, which is exactly a
  backend pinned at ~96.8% CPU in `ec_distann_build_epoch_with_training`
  with no wait event, no error, and no phase output, deterministically, on
  all four attempts. The earlier "futex stall after ~13 minutes" was almost
  certainly the same thing: not stalled, just glacially progressing.

## Unblock steps

1. Reinstall the release extension **with the measurement feature** from the
   branch head (the 187 baseline precedent is release + stage-counter
   feature), e.g. `cargo pgrx install --release` with
   `pg18,distann-head-attribution-benchmark`, or the repo-standard
   `ecaz dev install` release path.
2. Verify before running — this is the check the memory rule mandates after
   any pg_test: installed
   `~/.pgrx/18.3/pgrx-install/lib/postgresql/ecaz.so` size/mtime must match
   `target/release/libecaz.so` (≈24 MB), not ≈272 MB.
3. Re-run `task194-suite.json` as already configured (50/10, provenance
   rows). Expect the build phase to complete in roughly the baseline's
   ~15 minutes; if it does not on a verified release binary, that becomes a
   real finding — but measure it with `extension_build_profile=release` in
   the log.
4. Keep ~20 GB free; the checkpoint pressure noted in attempts 2–3 was real
   but secondary.

## Prevention (small follow-up slice, recommended)

The fixture prints `extension_build_profile` only in provenance rows *after*
the build completes — too late to catch this. Add a preflight to the
`distann-local-multinode` fixture (and ideally `ecaz bench suite`
generally): resolve the installed `ecaz.so`, fail fast before building if
the profile is not `release` unless an explicit `--allow-debug` flag is
passed. This is the second program-level incident of this exact class; a
five-line guard ends it permanently.
