## F1 (P0): the retained run likely measured the reverted Task 192 cache,
## and nothing in the packet can tell us

`materialize_owner_open_validate_work` is 6.722 ms/scan (3.36 ms/request)
in the accepted Task 187 baseline and **0.026 ms/scan** in this packet's
retained run — a ~260× drop in the exact quantity Task 192's
schema-resolution cache (`33f9fed42`) removes from the hot path. That
commit was reverted in `43fe9656c` (09:07); the run artifacts were
committed at 09:50 from a separate worktree, and the direct log contains
**no `physical_benchmark_provenance` rows** — no extension git SHA, no
build profile, no head/seed digests. The binary cannot be identified. The
overwhelmingly likely reading: the measured extension was built from the
pre-revert tree, so the "unmeasured, unsafe" Task 192 candidate was in fact
measured — request wait fell 9.99 → 7.79 ms/scan and `remote_materialize`
10.02 → 7.83 ms/scan — and then discarded, while its accidental measurement
is being retained as the Task 194 "fresh attribution."

Either way this is disqualifying for the packet as filed: a
decision-bearing counter moved by 260× against the accepted baseline and no
packet text acknowledges it. Required: rebuild from the branch head
(post-revert), rerun through `task194-suite.json` (which correctly pins
50 iterations / 10 warmups and emits provenance), and reconcile
`owner_open_validate_work` against the 6.722 ms baseline value. If it stays
collapsed on a verified post-revert binary, that itself is a finding that
rewrites Tasks 192's premise — but it must be measured with provenance, not
inferred.

## F2 (P0): the "owner" traversal timers measure the local path, and
## "transport wait" duplicates an existing timer

From `f6711910b`:

- `TraversalOwnerGraphRead` / `TraversalOwnerScore` are recorded inside
  `GenerationExpander::expand` — the **coordinator-local** expander. The
  log proves it: `traversal_owner_graph_read` has samples=85, exactly
  `local_expand`'s sample count, while `remote_expand` has 101. Remote
  owner-side graph reads, decode, and scoring — components 4 and 5 of the
  nine-way contract, the entire point of the task — are unmeasured. The
  attribution summary's "Owner graph read 0.914 ms; owner scoring
  0.057 ms" invites exactly the wrong subtraction (6.87 − 0.97 ≈ "5.9 ms
  wire overhead"); those numbers are local-expansion sub-steps.
- `TraversalTransportWait` starts from the same `remote_started` instant
  as `RemoteExpand` and records the same elapsed interval
  (6.870165 vs 6.870773 ms — identical modulo record ordering). It adds
  zero information; it is not a wait/service split.

Delivered vs contract: partition (1), request encode without bytes (3,
partial), coordinator decode+placement (8), and the work-counter family (9)
are real. Missing: connection/session state (2), request/response bytes
(3/6), remote owner reads/decode/scoring (4/5), transport wait separated
from owner service time (7a), and per-owner straggler distribution (7b —
nothing per-owner is recorded at all). The right mechanism already exists
in this codebase: the materialization path ships `owner_*` timers back in
the response sideband. Do the same for expansion responses, then compute
wait = coordinator-observed wall − owner-reported service, and straggler
spread = per-hop max−min across engaged owners.
