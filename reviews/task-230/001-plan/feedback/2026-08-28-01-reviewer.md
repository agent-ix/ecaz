## What must change before packet 002 is authorized

### 1. The hot tier as specified does not remove the exact-vector TOAST fetch

This is the item that matters most, because it is the plan's whole premise.

`sql/bootstrap.sql:67-76` declares `ecvector` with `STORAGE = external`. That
makes EXTERNAL the attribute's default storage class in any heap that holds an
`ecvector` column. A 1,536-dimension value is roughly 6 KB, far above the
~2 KB TOAST tuple threshold, so PostgreSQL moves it out of line — uncompressed,
by definition of EXTERNAL — in *any* relation that stores it as a plain column.

The plan's hot heap (§2) is `vec_id | tombstone | exact vector | scalars`,
created — per the plan's own "compact physical columns" wording — as an ordinary
table. Section 4's acceptance invariant is "zero cold work for
expansion/rerank-only calls", and that will hold. But the cost it is trying to
remove is not cold-relation work. An exact-vector read today is: fetch the row
heap tuple by TID, then detoast the vector via the row heap's TOAST index and
chunk heap. Under the plan it becomes: fetch the *hot* heap tuple by TID, then
detoast the vector via the *hot* heap's TOAST index and chunk heap. Same number
of index descents, same number of chunk fetches, same bytes moved. What the
split removes is the pointer-arithmetic walk past two other attributes in
`slot_getattr` — and PostgreSQL never detoasts an attribute it does not
dereference, so that walk is already close to free.

`generation_store.rs:477-480` creates the current row tier with a bare
`CREATE TABLE {qualified_row} ({row_columns}){tablespace}` — no storage class,
no fillfactor. The plan proposes the same for the hot heap. Task 229, by
contrast, explicitly set `WITH (fillfactor=100)` and
`ALTER TABLE ... ALTER COLUMN payload SET STORAGE PLAIN`
(`generation_store.rs:507-517`), and pinned it with an `attstorage = 'p'`
assertion (`src/tests/ec_distann_physical_lifecycle.rs:5878`). That is exactly
the lever Task 230 needs and does not name.

Required before packet 002:

- State the hot-tier vector storage class explicitly (`PLAIN` or `MAIN`) and the
  hot-tier fillfactor, in the plan, as part of the format contract — not as an
  implementation detail.
- State the mechanism the win is expected to come from in one sentence, so
  packet 004 can test it. If it is "the hot tuple is inline, so an exact-vector
  read is one heap page fetch instead of a heap fetch plus a TOAST index descent
  plus N chunk fetches", say that. That is a testable claim; "reads only the hot
  surface" is not.
- Bound the supported dimension. `PLAIN` cannot store a tuple larger than a
  page, so it caps the hot tier at roughly 2,000 float32 dimensions; `MAIN`
  silently falls back to out-of-line when the tuple does not fit, which would
  reintroduce the current cost without any error. Say which is used, what the
  maximum descriptor dimension is under it, and what happens at the boundary —
  a build-time rejection is fine, a silent fallback is not.
- Note the storage consequence and preregister it: at 1,536 dimensions a `PLAIN`
  hot tuple of ~6.2 KB yields one row per 8 KB page, roughly 30% hot-tier
  amplification. That may still be the right trade, but it must be in §6's
  expectation rather than discovered in packet 004.

### 2. §2 and §3 disagree on whether the hot tuple stores the cold TID

§2 fixes the hot heap as `vec_id | tombstone | exact vector | selected scalar
values` — no cold locator column. §3 says the participant "inserts cold first,
records its TID in hot, then records the hot TID in graph."

Both cannot be true. The two readings differ in the persisted hot tuple shape,
in the §3 hot content digest (which folds vec_id, tombstone, vector bytes, NULL
shape, and hot scalar bytes — and no cold TID, agreeing with §2), and in the
§6 per-row overhead bound. If the graph record V2 pair `{hot_tid, cold_tid}` is
the sole locator authority, then §3's clause is a write-ordering statement
mis-worded as a storage statement, and should read "inserts cold first, then
hot, then records both TIDs in the graph record." If instead the hot tuple does
carry `cold_tid`, then there are two locator authorities that can disagree, and
the plan owes a rule for which one wins on mismatch.

Pick one and make §2, §3, and §6 agree.

### 3. §2 and §4 disagree on the visibility authority

§2: "The hot tuple's MVCC header is the visibility authority."
§4: "cold-only requests batch-fetch cold and never open hot on the success
path."

A cold-only read that never opens hot cannot consult the stated visibility
authority. This is not hypothetical: §5 has delete update the graph tombstone
and the hot tombstone and explicitly "never rewrite or fetch cold payload", so a
deleted row's cold tuple remains live and visible in the cold heap indefinitely.
The only thing standing between a cold-only projection and a deleted row's
payload is the graph record — which means the graph `is_current`/tombstone state
is the visibility gate, and the hot MVCC header and hot tombstone byte are
corroborating echoes.

That is a defensible design. State it that way, and say what the hot tombstone
byte is *for* if it is not the gate, since §6 pays a byte per row for it.

### 4. A legal, supported configuration cannot build a hot/cold generation

`ambuild.rs:646` requires `distributed_control=true` to carry
`source_identity='include'` with "exactly one UUID or bytea(16) INCLUDE column",
and `ambuild.rs:1385` repeats it. **bytea(16) is a first-class supported source
identity.**

§1 requires that the source identity "must appear explicitly" in
`hot_payload_attnums`, and in the same paragraph rejects "variable-width" types
as hot scalars. `bytea` is variable-width and is not in the allowlist —
`payload_sidecar.rs:41-50` maps `bool/int2/int4/int8/float4/float8/uuid/date/
time/timestamp/timestamptz` and returns `None` for everything else, with
`fixed_binary_width("pg_catalog", "text") == None` pinned at
`payload_sidecar.rs:606`.

So every index whose identity is `bytea(16)` — a configuration main supports
today — cannot express a legal `hot_payload_attnums`. Resolve it explicitly:
either widen the hot allowlist to admit the fixed-16-byte identity `bytea` as a
special case, or drop the "identity must be listed explicitly" rule and treat
identity like the vector (implicitly hot, not nameable in the reloption). The
second is more consistent — the plan already argues the vector is implicit
because it is mandatory, and the identity is equally mandatory. The DDL-
visibility argument for listing it does not survive the fact that it makes half
the supported identity types unbuildable.

### 5. Graph record V2's header growth invalidates compile-time offsets

§2 says the V2 record's "fixed header grows by one six-byte TID." The header is
not private to the codec. `tuple.rs:42-50` exposes
`DISTANN_NODE_HEADER_BYTES = 20`, `DISTANN_NODE_HEAP_TID_OFFSET = 12`,
`DISTANN_NODE_NEIGHBOR_COUNT_OFFSET = 18`, and
`DISTANN_NODE_SEARCH_CODE_OFFSET = DISTANN_NODE_HEADER_BYTES` as plain
constants, and `DistannNodeTuple::encoded_len` (`tuple.rs:76-79`) computes
record size from them. They are consumed as raw byte offsets outside the codec:

- `insert.rs:625` and `insert.rs:651` read neighbor count at
  `DISTANN_NODE_NEIGHBOR_COUNT_OFFSET`
- `remote_endpoint.rs:93,107` computes a minimum length and decodes the TID
- `dml.rs:91,107` does the same
- `routine.rs:535-536` decodes the TID
- both are re-exported through `am/mod.rs:60-61` and `lib.rs:473-474`

Under V2, `NEIGHBOR_COUNT_OFFSET` and `SEARCH_CODE_OFFSET` become 24 and 26
while remaining 18 and 20 for V1, so every one of those sites reads the wrong
bytes for a V2 record unless it becomes version-parameterized. The plan should
say the offsets become `const fn(version)` (or that the six-byte cold TID is
appended after the neighbor arrays so the existing header offsets are
unchanged — which is cheaper and worth considering, at the cost of a
variable-position field).

Also note `generation_descriptor.rs:493` currently hard-pins
`graph_record_version != DISTANN_GRAPH_RECORD_VERSION` (constant 1) as a
validation failure. The plan's V1/V2 admission rule requires changing that
predicate; name the site so packet 002 does not have to rediscover it.

Task 231 owns fixed-stride graph-node extents. A header-length change is
directly in its path. Say which task lands first, or the two will collide on
these same constants.

## Required before packet 004 preregistration, not before packet 002

### 6. The 258-byte and 96-byte bounds are derived from the wrong layout

Both bounds are computed from Task 229's *canonical binary wire widths*, but
Task 230 stores hot scalars as real heap columns, where tuple layout — not wire
width — decides bytes.

- "Sixteen 16-byte values plus a two-byte NULL bitmap gives a hard 258-byte
  scalar-value bound" ignores alignment padding. `uuid` is char-aligned,
  `int8`/`float8`/`timestamp` are double-aligned; a `bool` followed by an `int8`
  costs 8 bytes, not 1. The bound is not hard.
- The NULL bitmap is sized by the hot tuple's total attribute count — vec_id,
  tombstone, vector, and up to 16 scalars is 19 attributes, so 3 bytes, not 2.
- The 96-byte per-row overhead enumeration omits the cold tuple's line pointer
  and, more significantly, that the split creates a *second* TOAST relation and
  TOAST index pair for the generation, each with its own pages and its own
  index descents.

None of this changes the disposition; the amplification is still low against two
1,536-float values. But the descriptor records "maximum scalar bytes" as a
persisted field, so the number needs to be the heap number, not the wire number.

### 7. Carry Task 229's measured result into the preregistration

Task 229 is the closest available prior and the plan cites only its
disposition, not its finding. The measured result
(`reviews/task-229/004-full-scale-decision/`, reviewer seq-13): a narrow,
`PLAIN`-storage, TID-indexed sidecar lookup replacing row-tier payload SQL
**regressed 13.49% and 55.04% mean at 100k** across two independent
same-generation pairs, recall-neutral, with no added remote round trip. One
extra narrow relation lookup on the materialization path cost that much.

Task 230 makes cold-only and mixed projections a *two*-relation fetch on that
same path. The honest prior is that those shapes regress. That does not argue
against running the task — §4's hot-only exact-vector path is a genuinely
different mechanism and is worth measuring — but §6 currently lists twelve
metrics and names no primary gate, deferring all thresholds to packet 004.
Before that preregistration, state per projection shape (id-only, hot-scalar,
exact-vector, cold-scalar, mixed, `SELECT *`) which direction is expected and
which single shape is the primary gate. Preregistering after 229's result is
known, without naming which shape carries the decision, leaves room to select
the favorable shape post hoc.
