## Remaining

### 1. The hot `tombstone` byte is not justified by any failure vec_id misses, and it is expensive

§2 demotes the hot tombstone to a "corroborating integrity echo" that "detects
graph/hot partial mutation or misaddressed locator state". Take those two cases
separately against §4's own validation order.

*Misaddressed locator.* §4 already validates the `vec_id` echo on every hot read.
A `hot_tid` that lands on a different live row fails the vec_id check. A
`hot_tid` that lands on a predecessor version of the *same* vec_id is excluded
earlier by graph `is_current` and `record_version`, and in any case a
replacement does not tombstone its predecessor, so the byte would read the same
value there. vec_id strictly dominates the byte on this case.

*Partial mutation.* The only mutation that can leave graph and hot disagreeing
is the one §5 introduces to maintain the byte. Without the byte, delete touches
graph alone — which is what main does today — and there is no partial state to
detect. The check exists to catch a hazard the checked thing creates.

The cost of keeping it is not marginal. §5 already works out the consequence
honestly: flipping one byte inside a ~6.2 KiB `PLAIN` tuple is an UPDATE, at
`fillfactor=100` with one row per page it can never be a HOT update, so every
delete allocates a fresh 8 KiB page, and the resulting TID change forces a graph
V2 locator rewrite under the intent/current-version check. That converts a
metadata flip into a page-sized write plus a second mutation plus a new
cross-structure invariant that retry, forwarded-mutation, fault, and recovery
paths all have to hold. §5 defers the cost to packet 003, which is the right
instinct for a cost, but this is a format decision — the column, the §3 hot
digest that folds it, the delete path, and the locator-rewrite logic all get
written in packet 002.

Close this either way:

- **Remove it.** Hot heap becomes `vec_id | exact vector | selected scalars`,
  §3's hot digest drops the tombstone field, and §5's delete returns to a graph
  tombstone flip with no hot write and no locator churn. This is the design I
  would land.
- **Keep it, and state the failure mode.** One sentence naming a state that the
  byte catches and `vec_id` + graph `is_current` + `record_version` do not. If
  such a state exists I have not found it, and naming it closes the item.

Either answer is DONE. What is not acceptable is carrying the byte into packet
002 on the current justification, because the current justification is circular.

### 2. The V2 length gate rejects V2 before the version is read, and the "all named raw consumers" list is missing the site where it breaks

§2's compatibility argument is right and the trailing-append design is the good
call. But `tuple.rs:248-261` orders the checks the wrong way for it:

```
fn decode_into_version(input, graph_degree_r, code_len, expected_version, out) {
    let expected = Self::encoded_len(graph_degree_r, code_len);
    if input.len() != expected { return Err("... length mismatch ...") }
    if let Some(expected_version) = expected_version { /* reads offset 0 */ }
```

`encoded_len` takes no version, and for a given `(graph_degree_r, code_len)` the
length is exactly what distinguishes V1 from V2 — V2 is six bytes longer. So a
V2 record fails the length check and returns a length-mismatch error before
control ever reaches the version dispatch. The version lives at offset 0 and is
readable before the length is known; the decode order has to invert — bounds-check
two bytes, read and admit the version, then compute the version-sized expected
length and compare.

§2 names `insert.rs`, `remote_endpoint.rs`, `dml.rs`, and `routine.rs` as the raw
consumers to dispatch. Those four are correctly identified and, having checked
them, they are also the least affected: `remote_endpoint.rs:93,107`,
`dml.rs:91,107`, and `routine.rs:535` only touch `DISTANN_NODE_HEAP_TID_OFFSET`
at byte 12 and `DISTANN_NODE_FLAGS_OFFSET`, and `insert.rs:625,651` only touches
`DISTANN_NODE_NEIGHBOR_COUNT_OFFSET` at 18 — every one of which the trailing
append leaves in place. The site that actually breaks is the codec's own length
gate, and it is not in the list. `tuple.rs:184`, `tuple.rs:204`, and
`insert.rs:867` also compute or assert against `encoded_len` and need the version
threaded through.

Add `tuple.rs:248-261` to §2's list with the decode-order inversion stated, and
say that `encoded_len`'s existing call sites take the version rather than
defaulting to V1.

## Accepted, and not reopening

**Finding 1, exact-vector TOAST.** Fully resolved and the strongest part of the
revision. `STORAGE PLAIN` on the hot vector column with an `attstorage = 'p'`
validation pin, `fillfactor=100`, a hard 1,536-dimension V1 cap with build
rejection at 1,537 and explicitly no `MAIN`/`EXTERNAL` fallback, and §6's
mechanism stated in falsifiable form — one hot-heap page fetch replacing a
row-heap fetch plus a TOAST-index descent plus multiple chunk fetches. §4's
acceptance invariant correctly grew to "zero cold work **and zero vector TOAST
fetches**", which is the thing that actually needs to be counted. The precedent
holds: Task 229 set `attstorage='p'` on a `bytea` column whose type default is
extended (`generation_store.rs:507-517`, pinned at
`ec_distann_physical_lifecycle.rs:5878`), so PLAIN overriding the type's
`STORAGE = external` is proven in this codebase, not assumed.

The 1,536 cap is conservative in the right direction. `MaxHeapTupleSize` is 8160;
a 1,536-dimension datum at roughly 6.2 KiB plus a 32-byte header/bitmap, the
vec_id, the identity, and a full sixteen aligned scalars still lands near 6.4 KiB,
leaving well over a kilobyte of headroom. §2 is right that a later version may
widen it, and right not to do so now.

§6's ~30% hot-page amplification is the correct figure and correctly labelled a
deliberately paid cost. For what it is worth the comparison holds arithmetically:
TOAST chunks pack about four per page at ~97% efficiency, so the control stores
the same vector in roughly 6.3 KiB against the candidate's full 8 KiB page.

**Finding 2, cold locator.** Resolved. §2 line 121 and §3 line 155 agree: the hot

the §3 hot digest field list matches the §2 tuple shape.

`bytea` is varlena, so the §1 maximal-tuple estimator needs the identity's
contribution defined as the 16-byte value plus its short varlena header rather

**Finding 5, graph offsets.** Resolved in design by appending `cold_tid` after
