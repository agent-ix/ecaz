## Blocking

### 1. `maximum_hot_tuple_bytes` is an unconstrained caller parameter, not a computed bound

`resolve_hot_cold_layout` takes `maximum_hot_tuple_bytes: u32` as an argument
(`row_layout.rs:433`) and checks it only against the constant ceiling
(`row_layout.rs:451-455`, and again in `validate` at `row_layout.rs:169-170`).
Nothing relates it to `exact_vector_dimensions`, to the identity width, or to
the hot scalar widths — the two bounds are validated independently.

So this descriptor is valid today:

```
exact_vector_dimensions  = 1536      // ~6,148 bytes of vector datum
maximum_hot_tuple_bytes  = 1         // "the hot tuple fits in one byte"
```

It passes `validate()`, passes `validate_row_schema()`, encodes, decodes, and
produces a stable digest. The tests never catch it because every call site
passes a hand-chosen `6_400` (`row_layout.rs:632, 659, 681, 697, 716`), a magic
number with no derivation shown.

This matters more than an ordinary missing check because of what the field *is*.
The packet-001 contract §1 makes the descriptor "the authority, never a later
reloption read" and says the descriptor "binds that versioned computed
hot-tuple bound". Later slices — relation creation, the maximal-tuple preflight,
the `PLAIN` insert path — are supposed to trust this number. A self-inconsistent
value that validates now becomes a descriptor already frozen in persisted bytes
by the time the real preflight computes the true width and disagrees. Fail-closed
has to happen at the point the value is admitted.

I accept that the *native* preflight needs PG catalog access and belongs with
relation creation, which this slice explicitly defers. But a lower bound is
computable from the descriptor alone, with no catalog: the vector datum from
`exact_vector_dimensions`, the internal `vec_id`, the identity from
`identity_maximum_inline_bytes`, the sum of `hot_scalars[].binary_width`, plus
the tuple header and null bitmap over `DISTANN_HOT_INTERNAL_COLUMNS +
placements-in-hot`. Require `maximum_hot_tuple_bytes` to be at least that.
The catalog-exact figure can still tighten it later; what must not survive this
slice is a bound that is arithmetically impossible for its own declared vector.

### 2. The `bytea(16)` short-varlena accounting is computed and thrown away

`identity_maximum_inline_bytes` (`row_layout.rs:24-35`) correctly returns 16 for
`uuid` and 17 for `bytea` — value bytes plus the one-byte short-varlena header,
which is exactly the seq-03 carry-in. But its return value is discarded at the
only call site:

```rust
identity_maximum_inline_bytes(identity).ok_or_else(|| {
    "EC_SCHEMA_MISMATCH: source identity is not UUID or bytea(16)".to_owned()
})?;                                              // row_layout.rs:303-305
```

`Option::ok_or_else(..)?` here is a type gate. The 16-versus-17 distinction —
the entire content of the carry-in — reaches nothing. The request's scope bullet
claims it as delivered ("the `bytea(16)` identity contribution defined as 16
value bytes plus its one-byte short-varlena header rather than `attlen=-1`") and
the review request asks me to review "bytea short-varlena accounting", but there
is no accounting, only a type check that happens to be spelled with a width
function.

The test that appears to cover it does not:

```rust
assert_eq!(identity_maximum_inline_bytes(&bytea_schema.attributes[1]), Some(17));
                                                  // row_layout.rs:688-691
```

That calls the private helper directly and asserts the constant the helper is
written from. It cannot fail while the helper compiles, and it would still pass
if every consumer ignored the value — which is the current state. It pins a
literal, not a behavior.

Findings 1 and 2 have one fix between them: make the minimum-width check consume
`identity_maximum_inline_bytes`. Then the helper has a purpose, the 17-byte case
becomes observable through `resolve_hot_cold_layout` rejecting a too-small bound
for a `bytea` identity that it would accept for a `uuid` identity, and the test
can assert that difference instead of the constant.
