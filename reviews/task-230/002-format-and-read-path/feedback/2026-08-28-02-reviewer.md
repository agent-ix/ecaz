## Blocking findings — closed

**1. `maximum_hot_tuple_bytes` is now a checked bound.** `minimum_hot_tuple_bytes`
(`row_layout.rs:41-70`) derives a floor from the MAXALIGN'd heap header plus null
bitmap, the internal `vec_id`, the vector datum, the persisted identity width,
and the declared hot scalar widths, and `validate()` rejects anything below it
(`row_layout.rs:222-235`). The 1,536-dimension / one-byte descriptor I described
now fails, and the test asserts that through `validate()` rather than by
construction (`row_layout.rs:841-847`).

Two details I checked rather than assumed:

- The `+ 2` in `hot_attribute_count` (`row_layout.rs:46`) hardcodes vector and
  identity, and the function runs *before* the placement loop that proves the hot
  tier contains exactly vector, identity, and the declared scalars. The ordering
  is safe: if that correspondence does not hold, `validate()` fails later on its
  own checks and the width result is never relied on.
- `vector_datum_bytes = dim * 4 + 4` (`row_layout.rs:54-57`) is not an
  approximation. `pack_raw_f32` (`lib.rs:1324-1337`) emits exactly `dim * 4` raw
  little-endian bytes with no dimension header, and pgrx wraps the `Vec<u8>`
  return in a four-byte varlena header. At 1,536 dimensions that is 6,148 bytes,
  which is right.

`DISTANN_HOT_TUPLE_MAX_BYTES = 8_160` is also correct as PG18's
`MaxHeapTupleSize` — `8192 - MAXALIGN(24) - MAXALIGN(4)`.

**2. The `bytea(16)` identity accounting is now consumed and observable.** The
width is persisted as `source_identity_maximum_inline_bytes`
(`row_layout.rs:192`), constrained by `validate()` to exactly 16 or 17
(`row_layout.rs:214-221`) so pure decode is self-contained, cross-checked against
the frozen schema's actual identity type (`row_layout.rs:381-389`), and consumed
by the minimum-width calculation.

The test is no longer tautological. `row_layout.rs:849-858` asserts
`bytea_bound == uuid_bound + 1` and then — the part that matters — that a
UUID-derived bound is *rejected* for a `bytea` identity through
`resolve_hot_cold_layout` while the bytea-derived bound is accepted. The
16-versus-17 distinction now changes observable behavior at a public entry point.
This is exactly the fix I asked for, including the collapse of findings 1 and 2
into one change.

## Carry into the next slice — not conditions on this verdict

**The field is named `maximum_` but the tests now set it to the `minimum_`.**
Every call site passes `derived_hot_tuple_bound(...)`, which returns
`minimum_hot_tuple_bytes` exactly (`row_layout.rs:751-777`). That is fine for
unit tests of the floor check, but the packet-001 contract has the build
preflight bind the *catalog-exact maximum* here, and a real formed tuple can
exceed the derived minimum: `minimum_hot_tuple_bytes` sums
`scalar.binary_width` with no inter-attribute alignment padding, and always
charges a null bitmap PostgreSQL omits when no NULLs are present. For the
packet's own fixture the two happen to coincide — hot column order is
`vec_id, id, source_id, embedding`, which needs no padding, so the minimum lands
exactly on 6,204 bytes — but that is a property of this schema, not of the
formula. When the preflight lands, set the field from the maximal formed tuple
the contract already calls for, not from this floor.

**The vector type check is name-only.** `vector.type_name != "ecvector"` does not
pin `type_namespace`, `send_function`, or `receive_function`, while hot scalars
pin all of them via `matches_schema` (`row_layout.rs:125-138`). A user-defined
`ecvector` in another schema would pass. The extension schema is not fixed, so
hardcoding a namespace is wrong, but pinning the send/receive function identity
the way hot scalars do would close it. This matters at the slice where the vector
is actually deformed and scored, not here.

**Two new `validate_row_schema` branches are untested:** rejection of a generated
identity (`row_layout.rs:383-385`) and of a persisted inline width that disagrees
with the schema (`row_layout.rs:386-392`). The bytea/uuid path is covered through
`resolve_hot_cold_layout`, but descriptor-versus-schema drift on those two fields
is not. Fold them into the corrupt-fixture coverage the packet still owes.

**`maximum_hot_scalar_count`** still persists a field whose only legal value is
the compile-time 16. Unchanged from seq-01 and still harmless.

The five pre-existing clippy errors remain repository-wide. Now that they are
recorded in a packet manifest they are at least visible; someone should own them
