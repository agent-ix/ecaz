## The bytea correction is right, and my seq-02 acceptance was wrong

seq-02 introduced `bytea(16)` at 17 bytes — 16 value bytes plus a one-byte
short-varlena header — and I accepted it. This slice changes it to 20
(`row_layout.rs:33-36`) on the grounds that "the hot relation pins
`attstorage='p'`, so bytea cannot be converted to PostgreSQL's one-byte
short-varlena representation."

That is correct. PostgreSQL only packs a varlena into a short header when
`ATT_IS_PACKABLE`, which is `attlen == -1 && attstorage != TYPSTORAGE_PLAIN`.
Under PLAIN the value keeps its four-byte header *and* takes full nominal
alignment to `bytea`'s typalign of 4. So 4 + 16 = 20, at alignment 4. I should
have checked that interaction when I accepted 17; I did not, and the coder
caught it.

I verified the consequence arithmetically. For the packet's fixture schema
(`id int8` hot scalar at attnum 1, identity at 2, `ecvector` at 4), the hot
tuple is header 23 + 1 bitmap byte → MAXALIGN 24, + `vec_id` 8 = 32; then
attnum 1 at align 8 → 40; then the identity; then the vector at align 4.

- uuid: align 1, width 16 → 56, then vector → **6204**
- bytea: align 4, width 20 → 60, then vector → **6208**

which is exactly the `bytea_bound == uuid_bound + 4` the test now asserts
(`row_layout.rs:945`). The frozen `distann_row_tier_layout_v1.hex` value of 84
for a dimension-8 uuid layout checks out the same way: 24 + 8 + 16 + 36 = 84.

## The bug the PG18 test found

This is the part of the slice I most wanted to see. `1407d4504` adds
`test_distann_begin_build_binds_hot_cold_row_layout`, a real `#[pg_test]` that
creates hot/cold coordinator and participant indexes, registers a participant,
begins the epoch build, and asserts the registration digest is stable across
exact replay. It exposed that `metadata.dimensions` is legitimately zero for an
unbuilt distributed-control index, so the layout was being resolved with
dimension 0.

The fix sources the dimension from the indexed vector's frozen `typmod`
(`build_coordinator/mod.rs:86-98`). I verified that is the right source in this
codebase rather than assuming: `ecvector_typmod_in` (`lib.rs:1510-1528`) returns
the dimension directly, and `validate_ecvector_dim` (`lib.rs:1024`) compares
`dim != typmod as usize`. A dimensionless `ecvector` column yields typmod −1 and
fails closed with a clear message. Correct.

This is the second time on this task that a real callback test has found
something static review would not have. Worth continuing.

## Carry into the relation-creation slice

**1. The 20-byte figure depends on DDL that does not exist yet.** The comment
asserts "the hot relation pins `attstorage='p'`", but this slice creates no
relation, and the accepted packet-001 contract promises `STORAGE PLAIN` only for
the *exact-vector* column. Nothing currently verifies the identity column's
storage class — the `!=` equality check compares the stored field against a
recomputation from the same inputs, so it proves internal consistency, not
agreement with PostgreSQL.

The direction is safe: PLAIN sizing is always ≥ packed sizing, so a frozen 20
can only over-reserve. But when relation creation lands it must either set
`attstorage='p'` on the identity column and assert it — exactly as Task 229 did
for its sidecar payload, pinned at `ec_distann_physical_lifecycle.rs:5878` — or
the figure returns to 17. Packet-001 §1's requirement to "form and inspect a
maximal tuple to pin the estimator against PostgreSQL" is the check that will
actually settle this; do not let it slip.

**2. The V4 golden fixture never exercises a cold placement.** The
`sample_row_schema()` it is emitted from puts both live attributes in the hot
tier, so the frozen bytes pin only `tier = Hot(1)`. Unit tests cover Cold
placements and a corrupted tier byte, but a golden fixture exists to freeze
bytes, and this one cannot catch a regression that mis-encoded the Cold
discriminant. Add a cold attribute to the fixture schema when the tier relations
land.

**3. `POSTGRES_VARLENA_HEADER_BYTES` is used as an alignment value** for both the
vector and the bytea identity (`row_layout.rs:110-124`). Both quantities are 4,
so it is correct today, but a byte-exact sizing function should not spell
"int alignment" as "varlena header size". Give the alignment its own constant.

**4. Two redundant `align_up(.., 8)` calls** open `maximum_hot_tuple_bytes`
(`row_layout.rs:126-129`) on an already-MAXALIGN'd header, and `vec_id` is added
without an explicit alignment step, relying on the header being 8-aligned. Both
are correct now and both would silently stop being correct if the header
computation changed.

**5. `pg_test` reinstalled a debug `.so`.** The PG18 log shows
`PGRX_BUILD_PROFILE="dev"`. That is fine for a correctness test, but the
installed extension is now a debug build; reinstall the release build before any
packet-004 latency measurement, or the numbers are meaningless.
