## The three conditions, closed

**1. NULL coverage — done, and done the right way.** The fixture builder marks
NULL positions in the wire bitmap and omits them from the ordered value stream,
so the row travels the real wire → handoff → seal → read path. The request
explains why it was built that way rather than mutating a published row: a
post-publication mutation would invalidate the Graph V2 CTIDs. That reasoning is
correct and it is the difference between a test that exercises the format and
one that exercises a fixture.

The assertions are precise about the thing that actually breaks. For a mixed
`1,2,4,5` projection over a row whose cold payload and generated payload are
both NULL:

```rust
assert_eq!(nulls, vec![false, true, false, true]);
assert_eq!(offsets[1], offsets[0]);          // NULL must not advance the cursor
assert_eq!(offsets[3], offsets[2]);
assert_eq!(usize::try_from(offsets[3]).unwrap(), values.len());
```

The two offset-equality assertions are the check that matters — a NULL that
wrongly advances the value cursor would silently shift every subsequent
attribute, and nothing else in the suite would catch it. The terminal offset
pinning `values.len()` closes the other end. Cold-only reconstruction is
separately asserted to preserve NULL shape with no payload bytes.

**2. Scope reconciliation — written down, not dropped.** Restart and
owner-failure read coverage move to packet 003's lifecycle matrix, with the
request stating explicitly that packet 003 "must restate and dynamically
exercise both; they are not waived." That is exactly what I asked for. Packet
003's request must carry both items forward, and I will check for them there.

**3. TOAST attribution — decided, and the choice is sound.** Packet 004 will
capture pre/post `pg_statio_all_tables` deltas per isolated arm and query shape,
covering heap, TOAST heap, and TOAST index reads and hits, with the
shared-buffer hit ratio derived from the same deltas.

This is the right call. `pg_statio_all_tables` exposes
`heap_blks_read`/`hit`, `toast_blks_read`/`hit`, and `tidx_blks_read`/`hit` per
relation, so the control arm's TOAST traffic and the candidate's absence of it
become directly comparable, and the buffer-ratio metric I asked for falls out of
the same measurement instead of needing a second one. It also avoids adding
detoast instrumentation to production paths, which is the correct trade for a
measurement that only has to hold during a benchmark.

One practical note for the harness: these counters are cumulative and the delta
is only meaningful once the backend's stats are visible. PG18 keeps them in
shared memory so the lag is small, but take the post-reading after an explicit
`pg_stat_force_next_flush()` rather than assuming immediate visibility, and take
both readings from the same session that ran the queries.
