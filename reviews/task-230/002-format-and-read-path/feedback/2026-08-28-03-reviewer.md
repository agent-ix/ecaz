## Blocking

### 1. The "V1 cannot silently discard a cold locator" guarantee has no test

The request states it as a scope deliverable: "Existing legacy and physical-V1
writers must carry `cold_tid=None`; V1 cannot silently discard a cold locator."
Two guards implement it —

```rust
if self.cold_tid.is_some() {                                    // tuple.rs:172
    return Err("distann V1 physical node record unexpectedly has a cold-tier TID"...)
```
```rust
None => {
    self.validate(graph_degree_r, code_len)?;
    if self.cold_tid.is_some() {                                // tuple.rs:257
        return Err("legacy distann node record unexpectedly has a cold-tier TID"...)
```

— and neither is reached by any test. Grepping the whole test module, `cold_tid`
is only ever set to `Some` at `tuple.rs:785` and `819` (both V2 encodes) and to
`Some(ItemPointer::INVALID)` at `833`. Nothing constructs a tuple with a *valid*
`cold_tid` and calls `encode_physical_v1` or the legacy `encode`. Both guards
could be deleted and the suite would stay green.

This is the same shape as the seq-01 finding I blocked on: a behavior the
request claims as delivered, with no test that could observe its absence. The
difference is that here the code is live and correct — it just isn't pinned. Two
assertions close it:

```rust
let mut v1_with_cold = sample();
v1_with_cold.cold_tid = Some(ItemPointer { block_number: 29, offset_number: 7 });
assert!(v1_with_cold.encode_physical_v1(R, CODE_LEN).is_err());
assert!(v1_with_cold.encode(R, CODE_LEN).is_err());   // legacy path
```

### 2. `decode_into_physical_version` is new public API with zero exercise

`tuple.rs:358-366` adds the pooled V2 decode entry point. Nothing calls it — not
production code (no caller is switched to V2 yet, correctly), and not any test.
The existing `distann_node_decode_into_reuses_pooled_buffers` (`tuple.rs:886`)
covers only the legacy `decode_into`.

That leaves the pooled-reuse path untested at exactly the place it matters.
`decode_into_version` resets `out.cold_tid = None` in the common body
(`tuple.rs:445`) before the version match repopulates it (`tuple.rs:472-475`).
I traced it and the ordering is correct — a pooled tuple that held a V2 record
and is then reused for a V1 decode does get its `cold_tid` cleared rather than
carrying a stale locator. But pooled decode is the traversal hot path, a stale
locator is precisely the class of bug that survives unit tests into a benchmark,
and right now the invariant rests on my reading rather than on a test.

Add a pooled test that decodes V2 into a reused buffer, asserts the `cold_tid`,
then decodes V1 into the *same* buffer and asserts `cold_tid == None`.

## What is correct — verified, not assumed

**V1 byte preservation.** `distann_node_cold_tid_offset` is
`encoded_len(r, code_len)` (`tuple.rs:64-66`), so the trailer lands strictly past
every V1 byte and offsets 12, 18, and 20 are untouched. I decoded both fixtures
by hand rather than trusting the test:

```
v1: 0100 0000 8877665544332211 09000000 0300 0200 a1a2 <4×u64> <8 code bytes>
v2: 0200 ... identical ...                                              1d000000 0700
```

62 bytes and 68 bytes, matching `encoded_len(4,2) = 20+2+32+8` and that plus six.
Everything from byte 2 through byte 62 is byte-identical between the two
fixtures, and the trailer decodes to block 29 / offset 7. The unit test
(`tuple.rs:794`) and the fixture test (`on_disk_fixtures.rs:369`) both assert
`v2[2..v1.len()] == v1[2..]`, which is the right invariant stated the right way.

**The golden fixture is genuinely independent.** `on_disk_fixtures.rs:347-368`
walks every field with a separate reader and explicit expected values, then
`finish()`es to reject trailing bytes. It does not round-trip through
`DistannNodeTuple`, so a codec change that broke the format would fail it. That
is what a frozen fixture is supposed to do, and it is emitted from the same base
tuple as the V1 fixture (`manifest_v2.rs:1386-1393`), which is why the byte
comparison is meaningful.

**Version-before-length dispatch.** `decode_into_version` now bounds-checks two
bytes, reads and admits the version, and only then computes the version-sized
expected length (`tuple.rs:375-396`). This is the ordering inversion I asked for
in packet-001 seq-02, and `distann_physical_node_version_is_admitted_before_
version_sized_length` (`tuple.rs:817`) pins it in the way that actually proves
it: a V2-length record with a corrupted version, decoded as V1, must produce a
version error and **not** a length error. Asserting the absence of
`"length mismatch"` is the detail that makes that test meaningful.

**The legacy branch is correctly scoped out.** The `None` arm keeps its
V1-sized length check and its tag/reserved check (`tuple.rs:396-409`), so
`decode`, `decode_into`, and the tag-guarded `expand.rs`, `reader.rs`, and
`insert.rs:433` paths are untouched — exactly the separation packet-001 seq-03
required. Every existing writer got `cold_tid: None` in its struct literal
(`ambuild.rs:1589`, `handoff.rs:570`, `insert.rs:288`, `physical_dml.rs:552`)
rather than a defaulted field, so the compiler forced each site to be considered.

**MSRV.** `clippy.toml` sets `msrv = "1.75"`; `Option::is_none_or` stabilized in
1.82, so `incompatible_msrv` firing was a real catch and `map_or(true, ..)` is
the correct 1.75-compatible form. Clippy does not turn around and suggest
`is_none_or` back, because that lint is MSRV-aware.

**Clippy gate.** I ran
`cargo clippy --all-targets --no-default-features --features pg18 -- -D warnings`
and got the same five pre-existing errors as the last two cycles —
`ambuild.rs:139`, `generation_descriptor.rs:798`, `head_sample.rs:1818`,
`remote_endpoint.rs:1069`, `ec_distann_physical_lifecycle.rs:7951` — and nothing
in a touched file.

## Notes, not conditions

- `distann_node_cold_tid_offset` is exported through `bench_api` and returns a
  valid offset only for V2 records; for a V1 record it points one past the end.
  The name does not say so. Consider `..._v2_offset`, or have it take the version
  the way `encoded_len_for_version` does.
- `validate_physical_v2` (`tuple.rs:189`) duplicates the adjacency-padding block
  from `validate_physical_v1` verbatim. It cannot call `validate_physical_v1`
  because that one rejects a present `cold_tid`, but the padding check could be
  factored into a shared helper.
- Two version namespaces now exist and must agree:
  `DISTANN_NODE_HOT_COLD_FORMAT_VERSION = 2` in `tuple.rs`, and
  `DISTANN_GRAPH_RECORD_VERSION = 1` in `generation_descriptor.rs`, which has no
  V2 counterpart yet. When the next slice replaces the V1-only predicate at
  `generation_descriptor.rs:493` with the admission matrix, have the descriptor
  field take the `tuple.rs` constant rather than a second literal.
- Carried unchanged from seq-02 and still owed: the preflight must set
  `maximum_hot_tuple_bytes` from the catalog-exact maximal formed tuple rather
  than the padding-free `minimum_hot_tuple_bytes`; the indexed-vector check is
  name-only and should pin send/receive identity; and the two
  `validate_row_schema` drift branches need corrupt-fixture coverage.
