## Notes

**1. The maximal-tuple assertion's exactness is coincidental at this width.**
The inserted row has no NULLs, so PostgreSQL omits the null bitmap and
`t_hoff = MAXALIGN(23) = 24`. The estimator always charges a bitmap:
`MAXALIGN(23 + 1) = 24`. They agree only because 23 + 1 is already MAXALIGNed.
At nine or more hot attributes — legal, up to sixteen scalars plus vector and
identity — the estimator gives `MAXALIGN(23 + 2) = 32` while a non-NULL row
still forms at 24, and this `assert_eq!` would fail on a correct estimator.

The estimator is right: a maximum must include the bitmap, since any hot column
other than `vec_id` may be NULL. It is the test that will need widening. When a
wider hot cover is exercised, either insert a NULL-bearing row so the bitmap is
actually present, or assert `formed_bytes <= maximum_hot_tuple_bytes` with the
equality case restricted to ≤ 8 hot attributes.

**2. No clippy artifact in this packet.** seq-02, seq-04, and seq-05 each
recorded a `clippy-seq-NN.log`; seq-06 records five artifacts and none of them is
the clippy gate. I ran it and it passes with only the five known pre-existing
errors, so this is a provenance gap rather than an unverified claim — but per
CLAUDE.md my terminal output is not durable packet evidence. Add
`clippy-seq-06.log` and its manifest entry before packet 002 closes.

**3. Bootstrap and migration create differently-named constraints.**
`sql/bootstrap.sql` uses an anonymous table-level `CHECK` and `UNIQUE
(cold_tier_relid)`; the migration uses the named
`ec_distann_generation_cold_sidecar_exclusion_check` and a separately named
`ec_distann_generation_cold_tier_relid_unique` index. Semantically identical, but
the two install paths end up with different catalog object names. Cosmetic given
this repo takes no backward-compatibility obligation, and worth one line only if
anything ever introspects constraint names.
