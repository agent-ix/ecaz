## The join does not weaken the proof

This was the claim worth checking rather than accepting. Before:

```sql
SELECT source_id::text || '|' || source::text FROM <row_relation> ORDER BY source_id LIMIT 1
```

After:

```sql
SELECT internal.a_2::text || '|' || corpus.source::text
  FROM <row_relation> internal
  JOIN dm corpus ON corpus.source_id = internal.a_2
 ORDER BY internal.a_2 LIMIT 1
```

The ownership assertion is "this owner's generation relation contains this
identity", and that is unchanged: the row is still selected `FROM` the internal
generation relation and ordered by the internal identity column. The join only
decorates it with the raw query vector, which is not a hot column and genuinely
cannot come from the compact tier.

The two ways a join could have weakened it both fail to apply. An inner join that
dropped rows would change *which* owned row is sampled, not whether it is owned —
and if `dm` matched nothing at all the query returns empty and fails closed. A
non-unique `dm.source_id` could pair an identity with another row's vector, but
identity determines `vec_id` under `source_identity='include'`, so duplicate
identities would be a broken fixture rather than a weakness introduced here.

All three internal-relation probes now use the selected column — the sample
query, the pinned-owner probe, and the returned-candidate ownership count — which
was the specific thing the request asked me to confirm. The helper is pinned by a
test asserting both mappings.
