## The offsets contract, settled at the encoder

I checked the production encoder rather than taking either assertion's word for
it. `remote_endpoint.rs:847-855`:

```rust
let mut payload_offsets = Vec::with_capacity(payload_values.len());
let mut payload_buffer = Vec::new();
for value in payload_values {
    payload_buffer.extend_from_slice(&value);
    payload_offsets.push(i64::try_from(payload_buffer.len())?);
}
```

One cumulative **end** offset per requested attribute, no terminal N+1 entry. So
`ec_distann_materialize_physical_row_payloads` returns *n* offsets for *n*
attnums, the packet-002 seq-10 pgrx assertions were correct, and the CLI's
`= 3` for `ARRAY[1,3]` was the wrong one. The fix to `= 2` is right.

The whole contract is coherent once you see that `payload_values` carries one
entry per requested attribute with NULLs contributing zero bytes — which is
exactly why seq-10's `offsets[1] == offsets[0]` and `offsets[3] == offsets[2]`
hold for a projection with two NULLs, and why `offsets.len()` is 4 there rather
than 2. Both suites now assert the same encoding.

Worth noting this landed as a one-character correction to a test assertion, not a
change to production behaviour. The encoder was always right; the harness was
checking it against the wrong arity, which would have failed the retained-read
arm at runtime with a misleading "offsets_valid=false" rather than surfacing a
real defect.

## CLI lint gate

`cargo clippy -p ecaz-cli --all-targets` is now a packet receipt, exiting 0
against the pre-existing warning baseline (77 in the binary target, 78 in the
test target) with nothing at the seq-09 change. Recording the baseline rather
than applying `-D warnings` is the right call for now, since that crate's
dependencies — `ecaz-cloud`'s `too_many_arguments` plus the two known `ecaz` lib

**One suggestion to make the receipt load-bearing.** A 77-warning baseline is
too large to eyeball. A new warning introduced by a future checkpoint would sit
in the middle of that list and nobody would notice. Record the baseline *count*
in the manifest and compare it each run — if the count grows, investigate; if it
shrinks, update the baseline. That turns the receipt from an artifact anyone can
file into a check that can actually fail. Cheap, and packet 004 will be adding
more CLI code.
