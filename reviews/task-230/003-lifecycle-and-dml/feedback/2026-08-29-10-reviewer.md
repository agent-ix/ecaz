## Must change for packet 004: drop `--allow-debug-extension`

Both steps pass `--allow-debug-extension`, and both preflights report
`debug_override=true`.

Here it did no harm — the extension was genuinely built `--release` (the install
log shows `Finished \`release\` profile [optimized]`), so the override was
unnecessary. But it disables the one guard that would catch a debug `.so`, and
`pg_test` has silently reinstalled a debug build four times over this task's
history. For a fault matrix that is irrelevant; for packet 004's latency numbers
it is the difference between a measurement and a fiction.

Packet 004 must run **without** that flag so the release-profile preflight is
load-bearing rather than advisory. The guard demonstrably works — it correctly
reported `extension_build_profile=release` here — so this costs nothing but
removing a flag.

## One framing note for the record

This evidence ran at `--rows 2000 --dim 16`. That is right for a fault and
lifecycle matrix, and every invariant it proves — cold-pair balance across 2PC
recovery, retained-predecessor reconstruction, four-relation lifecycle accounting
— is dimension-independent.

But at dimension 16 the hot tuple is roughly a hundred bytes and would be inline
whether or not `attstorage='p'` were set, so **packet 003 is not evidence about
the storage regime**. The PLAIN-inline mechanism at 1,536 dimensions is pinned by
packet-002 seq-06's maximal-formed-tuple test (6,204 bytes, `pg_column_size`
against the frozen descriptor). Worth stating so nobody later cites packet 003 as
mechanism evidence.
