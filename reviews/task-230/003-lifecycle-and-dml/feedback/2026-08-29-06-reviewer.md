## Blocking: the `cold-only` shape reads the hot relation by construction

For `ColdOnly` in the hot/cold arm, the physical attribution issues **two**
queries (`distann_multicluster.rs:10108-10148`):

```sql
SELECT a_4 FROM <hot_relation>  LIMIT k   -- a_4 is the embedding: HOT tier
SELECT a_5 FROM <cold_relation> LIMIT k
```

and the control arm projects `embedding, payload_note` from the row relation.

Three consequences, in increasing order of seriousness:

**1. It contradicts a property already pinned by test.** Packet-002 seq-09
asserts, with counters, that a cold-only projection satisfies
`HotTierRelationOpens == 0` and `HotTierTupleReads == 0`. Packet 004 will publish
an I/O table where the row labelled `cold-only` shows non-zero hot heap and TOAST
reads — because the harness explicitly issues a hot-relation read for it. A
reader holding both artifacts gets a direct contradiction about the same named
shape, and no way to tell which is authoritative.

**2. It does not measure what §6 predicted.** Packet-001 §6 pre-committed that
cold-scalar projection would "regress, because it adds a cold relation lookup."
That is a claim about projecting a cold attribute. Reading a 6 KiB vector plus a
cold payload measures something else, and it inflates the candidate's apparent
cost on that shape — two relations and a large inline value versus the control's
single tuple.

**3. The rule is not stated, and is applied inconsistently.** Across the six
shapes the hot-side physical projection is: `IdOnly → a_1, a_4`,
`HotScalar → a_1`, `ExactVector → a_4`, `ColdOnly → a_4`, `Mixed → a_1, a_4`,
`SelectAll → *`. Meanwhile the end-to-end projections are `id`, `id`,
`embedding`, `payload_note`, `id, payload_note`, and all columns.

So `a_4` appears in the physical arm for three shapes that do not project the
vector end-to-end. There is a defensible reading — traversal reads the exact
vector on every query, so attributing it to every shape is honest. But under that
reading `ColdOnly` should also read `a_1` the way `IdOnly` and `Mixed` do, and it
does not. Under the other reading — the physical query mirrors the shape's own
projection — `a_4` should not appear in `IdOnly`, `ColdOnly`, or `Mixed` at all.
Neither rule is currently followed.

**What DONE looks like:** state in one sentence what the physical attribution
query represents — the engine's actual per-shape touches, or a mirror of the
shape's projection — and make all six shapes follow it. If the answer is
"mirror the projection," `ColdOnly` becomes `a_5` alone and the control becomes
`payload_note` alone. If the answer is "what the engine touches," `ColdOnly`
gains `a_1`. Either is fine; the current mixture is not, because packet 004
cannot label the resulting numbers honestly.

I would take the mirror reading: traversal I/O is already attributed by the
id-only arm, and keeping each shape's attribution equal to its own projection is
what makes the six rows comparable to the six §6 predictions.
