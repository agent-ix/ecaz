## The attribution is right

All six counters are captured — `heap_blks_read`/`hit`, `toast_blks_read`/`hit`,
`tidx_blks_read`/`hit` — per relation, as pre/post deltas, on every owner, in the
same backend session that performed the attributed reads. That is the method
fixed at packet-002 closure, implemented in full.

Three details I want to credit specifically:

**`pg_stat_clear_snapshot()` alongside `pg_stat_force_next_flush()`.** I only
asked for the flush. The clear matters just as much: `pg_statio_*` views are
snapshot-stable within a transaction, so without clearing, the "post" read can
return the same cached tuple as the "pre" read and every delta comes back zero —
a failure that looks like a clean result. Catching that is the difference between
a measurement and a plausible-looking artifact.

**`checked_sub` for the delta, failing closed on counter reset.** A `pg_stat_reset`
between snapshots makes post < pre. Saturating would report zero I/O, which is
indistinguishable from a perfect cache hit and would read as evidence *for* the
candidate. Returning an error instead is the correct direction, and it is tested
(`task230_io_counter_delta_covers_heap_toast_and_tidx`, "counter reset must fail
closed").

**One query shape per fresh fixture, reuse rejected.** `pg_statio` is cumulative
and cache state is sticky, so running several shapes against one fixture would
let earlier shapes warm later ones and silently compress the deltas. Forcing
isolation per shape is the right call and it is enforced rather than documented.

The emitted log lines carry their own provenance —
`stats_pre_post_same_session=true`, `query_session_same_stats_session=true`,
`post_force_flush=true`, `isolated_shape=true`,
`attribution_surface=direct_generation_relation`. A packet-004 reviewer can check
the methodology from the artifact itself instead of trusting manifest prose.
