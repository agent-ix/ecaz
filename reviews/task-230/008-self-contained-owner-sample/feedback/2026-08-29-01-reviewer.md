## This one is partly my miss

Packet 007 broke a working path, and I accepted it. My verdict there considered
exactly this failure mode and waved it through:

> An inner join that dropped rows would change *which* owned row is sampled, not
> whether it is owned — and if `dm` matched nothing at all the query returns
> empty and fails closed.

It did fail closed. But "fails closed" at the owner-proof phase of a 20-step
decision run **is** the harm — it costs a full restart. I treated a
liveness failure as benign because it was not a correctness failure, and in a
benchmark harness that distinction does not hold.

The larger miss is that I answered only the question the request asked me —
"does the join weaken the ownership proof?" — and never asked the more basic one:
**why change the row-heap query at all?** Packet 007 rewrote a proven, working
path in order to fix a hot/cold problem. The minimal fix was always to branch on
layout and leave row-heap untouched. That instinct should have been mine to
supply and was not.

Packet 008 is that minimal fix, arrived at the expensive way.

## The correction is right

- **Row heap returns to its exact pre-007 query.** Restoring a proven path rather
  than fixing forward is the correct move when the change that broke it bought
  nothing for that layout.
- **Hot/cold is self-contained**: `a_2::text || '|' || (a_4::real[])::text` from
  one owned generation tuple, no `dm`, no join, no dependency on the logical
  source relation at a phase whose durable contract is the internal relation.
- **The test forbids `JOIN dm` in hot/cold**, which is a negative assertion
  against the specific mistake rather than only a positive assertion of the new
  shape. That is what stops the regression class returning.

Two things I checked rather than assumed:

**The cast exists.** `CREATE CAST (ecvector AS real[])` at `sql/bootstrap.sql:127`,
so `a_4::real[]` is valid rather than a fourth failure waiting at runtime.

**Both layouts sample a numerically identical query vector.** This matters
because the probe runs a search with it, so if the two arms sampled different
vectors their ownership proofs would not be equivalent. `ecvector` stores raw
little-endian f32s with no dimension header (`pack_raw_f32`), so
`real[] → ecvector → real[]` is lossless, and `(a_4::real[])::text` yields the
same array literal as row-heap's `source::text`.

## The smoke is correctly scoped and correctly placed

One step, `hot_cold_row_tier=true`, real-10k, release-guarded with no
`allow_debug_extension` key so the preflight stays armed, `run_dir` under
`~/.ecaz/clusters`, id-only I/O shape, and — the important part — **stage-counter
only, explicitly not producing decision evidence**. A smoke that emitted
decision-eligible numbers would contaminate the preregistration; this one cannot.

It exercises precisely the phases that have failed three times: build, topology,
serving, both remote-owner proofs, the 62-row attribution contract, and cleanup.

Keeping it in the packet's `artifacts/` rather than `crates/ecaz-cli/suites/` is
also right — it is a one-off diagnostic, not a standard lane config, and it
should not be mistakable for one.

## For the record: three failures, three different classes

1. **Packet 005** — a stale row-count constant, from adding counters without

2. **Packet 007** — logical column names hardcoded against a compact relation,
