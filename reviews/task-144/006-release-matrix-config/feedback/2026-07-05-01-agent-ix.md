# Review: Task 144 Packet 006 — Release Matrix Suite Config

## Verdict

**CHANGES REQUESTED before spending the 50k/100k run. The matrix *shape* is sound
for per-mechanism attribution, but it is under-sampled on the two axes that
matter — the ratio-pruning band and the closure ε — and the 10k pilot (007) has
already shown the single ratio value it carries (1.25) catastrophically
overprunes.** Fix the ratio axis (and add a truth-cache prereq step) before
scaling, or the long run burns hours to reconfirm a known dead point.

## Matrix shape — attribution is clean (good)

Config is `{single, fixed_b2, closure_e010_b8} × {fixed, ratio125, adaptive}`
across 10k/50k/100k = 46 steps (1 precheck + 9 load + 9 storage + 27
spire-pipeline), driven by the canonical `ecaz bench suite` runner (audit passes,
dry-run 46 steps). This **does** satisfy CLAUDE.md per-mechanism attribution:
the assignment axis (single vs fixed-count b2 vs closure-ε) and the query axis
(fixed vs ratio vs adaptive) are each isolated, not stacked. No bespoke bash
sweeper, no nonexistent subcommand. Storage step present per variant (mandatory —
replication is a storage trade). Good.

## Finding F1 (blocking for closeout) — ratio axis is a single point, and it is the wrong point

Only `probe_distance_ratio=1.25` is configured. Packet 007 shows 1.25 collapses
recall to 0.76 (single) / 0.915 (fixed_b2) / 0.768 (closure) with recall *flat
across the whole nprobe sweep* — i.e. the band, not nprobe, is binding, and it
saturates at a low ceiling (the ADR-084 surrogate collapse). A one-point ratio
axis cannot locate the recall/scan knee; it can only reconfirm the dead point at
three scales. Add looser ratios (e.g. **1.25 / 2.0 / 4.0 / 8.0**) so the matrix
can actually trace where pruning starts holding ≥0.99 recall — or, better, gate
the run on a norm-robust surrogate (ADR-084's deferred cosine) so ratio 1.25
means a real 25% metric band. As-is, the ratio arm of the 50k/100k run is
predetermined to fail.

## Finding F2 (should-fix) — single closure ε; report replicas, not just bytes

Only `closure_epsilon=0.10` is exercised, and 007 shows ε=0.10 adds just +3.4%
index (barely replicates under the collapsing surrogate). Consider a second ε
(e.g. 0.25/0.50) so the closure axis spans more than a near-no-op, and have the
suite emit **mean replicas/vector + tail**, not only index size — the task Scope
requires the replication factor explicitly.

## Finding F3 (should-fix) — truth-cache prereq (already surfaced by 007)

007 found `spire-pipeline --include-recall` needs `--truth-cache-file` to
pre-exist; the pilot worked around it with a manual `ecaz bench recall` and (per
AGENTS.md) did not commit the cache. Before 50k/100k, add the first-class
truth-cache step / runner support the 007 packet promises, so a clean artifact
dir runs end-to-end without manual glue. Land that as its own `ecaz-cli` commit
per the "extend the suite runner, don't fork it" rule.

## Finding F4 (nit) — sweep deviates from the registered default; state it

The config sweeps `[8,16,32,64,96]`, not the registered `ec_spire` default
`[8,16,24,32]`. That is a justified deviation (you need higher nprobe to reach
0.99 on this corpus), but CLAUDE.md's Standard Sweep rule says a bespoke grid
must state its reason in `manifest.md`. Add that note.

## Bottom line

Ship the config once the ratio axis is a sweep (F1), the closure axis and
replica reporting are broadened (F2), and the truth-cache prereq is first-class
(F3). The scale/variant/attribution skeleton is correct; the sampling density on
the two experimental knobs is not yet decision-grade.
