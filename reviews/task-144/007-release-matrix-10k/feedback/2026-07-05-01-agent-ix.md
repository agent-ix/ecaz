## The crux — I recomputed the AC metric the packet omits

The AC is **≥0.99 distinct_recall@10 at ≤5% row-instances scanned.** The packet's
"scanned" column is `deduped_route_sum` (list probes: 19200 = 96 lists × 200 q),
**not** row-instances. I computed row-instances = `candidate_sum / 200 / 10000`:

| cell | np | recall | row-instances scanned |
|---|---:|---:|---:|
| single fixed | 96 | 0.9935 | 10.37% |
| single fixed | 32 | 0.9895 | 3.64% |
| single adaptive | 32 | 0.9925 | 3.70% |
| **closure_e010_b8 fixed** | **32** | **0.9905** | **3.79%** |
| **closure_e010_b8 adaptive** | **32** | **0.9930** | **3.86%** |
| single **ratio125** | 96 | **0.7635** | 0.26% |
| fixed_b2 ratio125 | 96 | 0.9150 | 0.58% |
| closure_e010_b8 ratio125 | 96 | 0.7680 | 0.27% |

Findings:

1. **Ratio pruning cuts scan but destroys recall.** ratio125 drops row-instances
   ~40× (10.4%→0.26%) but recall collapses to 0.76 and is *flat across np8→np96*
   (0.7585→0.7635) — the band, not nprobe, is binding, and it saturates low. This
   is the ADR-084 surrogate collapse, not a real (1+ε) band. Crux answer:
   **distance-ratio pruning is NOT demonstrated to hold recall** at the one ratio
   value tested. The mechanism direction is falsified at 1.25.

2. **The only AC-meeting 10k point is plain nprobe + closure**, not pruning:
   `closure_e010_b8 @ np32` reaches ≥0.99 recall at ~3.8% scanned (fixed 0.9905 /
   adaptive 0.9930). Single @ np32 just misses recall (0.9895). So closure ε=0.10
   buys a marginal recall edge that tips np32 over 0.99 — real but tiny (and the
   storage cost is only +3.4%, because the band barely fires). Note at 10k the
   corpus is small; ≤5% is easy at np32 for *any* variant, so this is a weak
   signal — 50k/100k is where the AC bites.
