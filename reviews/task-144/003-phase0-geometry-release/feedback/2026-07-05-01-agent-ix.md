## The key steer for Phase 1/2 (read this before building)

The request frames "single-assignment true top-10 already spans ~5.5 leaves,
above the 1–4 target" as discouraging. That conflates two different metrics the
task carries — the aspirational **1–4 probe count** (from "Why") and the actual
**acceptance criterion ≤5% row-instances scanned** (Goal / AC). On the AC metric
the geometry is comfortable, not dead:

- 50k: 5.505 leaves × 48.8 mean rows/leaf ≈ **268 rows ≈ 0.54%** of 50k to
  cover the true top-10. p90 (8 leaves) ≈ 0.78%; the worst case (10 leaves) ≈
  1.0%. All well under the 5% budget.
- 100k: 5.615 × 97.7 ≈ **549 rows ≈ 0.55%**. Same picture.

So the true-neighbor cover *fits the ≤5% row budget with ~5× headroom*. The
binding constraint is **not** geometry — it is query-side **routing precision**:
can a query identify those ~5.5 covering lists from query→centroid distances
without opening 20–30? That is exactly what Phase 2 `probe_distance_ratio` +
closure must jointly buy, and it is **not measured here**. Phase 0 bounds the
floor (you must probe ≥ the cover); it does not predict the achievable point.
Please state this reframing in the Phase 1 plan so the effort targets routing
precision, not a doomed hunt for a 1–4-list cover.

Corollary confirmed by the data: closure *grows* the cover (ε0.20 → 16 leaves /
27 rows), it does not shrink it. Closure's payoff is only realized when paired
with query-time ratio pruning — closure alone is a storage cost with no probe
win, precisely the Task 139 failure mode the task Why-section calls out. Do not
land closure without the pruning half in the same measurement arc.
