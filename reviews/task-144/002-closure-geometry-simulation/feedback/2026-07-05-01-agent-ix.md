# Review: Task 144 Packet 002 — Closure Geometry Simulation

## Verdict

**Sound directional groundwork with one methodology caveat to pin down before
Phase 1 builds anything — proceed, but define the closure distance surrogate in
an ADR first.** The closure simulation is read-only, invokes real code paths
(no fabricated CLI surface, no ADR-0004-style taint), and the record math is
correct. The caveat is about the *distance proxy*, not the plumbing: the ε-band
is applied to a floored inner-product surrogate whose semantics must be locked
to whatever Phase 1's build-side closure will use, or the simulated ε will not
map to the built ε.

## What is SIMULATED vs MEASURED

- **Measured on the real index:** nothing new in this packet beyond 001's
  single-assignment surface. This packet only adds the *simulated* rows.
- **Simulated (read-only, not built):** the closure rows
  (`mode="closure_simulated_ip_distance_ratio"`). For each exact-truth vector,
  the code re-scores it against the live leaf centroids
  (`ec_spire_index_routing_centroid_snapshot`) and keeps leaves within
  `(1+ε)·dist_nearest`. No index is replicated; build/scan/recall are unchanged.
  The manifest and request state this plainly — good, the SIMULATED/MEASURED
  boundary is honest.

## Findings

### F1 (medium — resolve before Phase 1): pin the closure distance surrogate; it is a floored IP, not a metric
`closure_leaf_pids_for_vector` uses `distance = (1 - dot(vector, centroid)).max(0.0)`
and keeps leaves with `distance ≤ best_distance·(1+ε)`.

- **Ranking is metric-consistent** with the real router: SPIRE routing ranks by
  `inner_product` (`rank_centroid_routes_by_ip`,
  `src/am/ec_spire/build/routing_plan.rs:127,242,281`), and ranking ascending by
  `1-ip` is the same order. So the ε→0 nearest leaf reproduces the real primary
  assignment. That part is fine.
- **The ratio threshold is not robust.** Neither the router nor this proxy
  normalizes vectors (`inner_product` is a plain dot). For a non-normalized
  vector, `dot` can exceed 1, so `1-ip` goes negative and is **floored to 0**.
  When `best_distance = 0`, `threshold = 0·(1+ε) = 0`, and only exact-tie leaves
  survive — the closure band **collapses to single-assignment** for those
  queries regardless of ε. This biases the simulated replication factor
  *downward* for high-norm truth vectors and makes ε geometrically
  non-uniform across the distance scale (a multiplicative band on a
  shifted-then-floored quantity means a fixed ε buys a very different absolute
  width near a centroid vs. far from it). The modest ε=0.05 delta observed in
  003 (mean assignment rows 10 → 11.42) may partly be this collapse rather than
  true geometry.
- **Ask:** before Phase 1, define the closure distance surrogate in an ADR
  (normalize first, or use a norm-robust surrogate) and make the build-side
  `closure_epsilon` and this diagnostic use the *same* definition. Otherwise the
  simulated ε and the built ε are different knobs and the Phase 0→Phase 1
  hand-off loses its predictive value. A cheap validation to add: assert the
  proxy's ε→0 nearest leaf equals the recorded
  `ec_spire_index_leaf_target_assignment_snapshot` primary for each truth id —
  if that holds on real data, the ranking half is confirmed; the threshold half
  still needs the normalization decision.

### F2 (low): the diagnostic measures cover, not probe count
Closure concentration answers "under ε-closure, how many lists *hold* the true
top-k." It does **not** model the query-side quantity that actually gates the
≤5%-scanned target: how many lists a *query* opens under Phase 2 ratio pruning
(that depends on query→centroid distances, not truth→centroid distances, and on
the pruning rule, none of which is simulated here). This is acceptable for Phase
0 scope, but the packet should not let the closure-ε rows be read as a probe/scan
prediction. State explicitly that Phase 2 probe-count remains unmodeled. (Fuller
treatment in the 003 feedback.)

### F3 (nit): closure sim emits no per-truth leaf ids
Because only aggregate counts are emitted, F1's ε→0-vs-real-assignment check
cannot be done from the JSONL alone. Consider emitting the per-truth chosen leaf
(or at least a `closure_matches_single_primary` bool) so the sim's fidelity to
real assignment is auditable from the artifact.
