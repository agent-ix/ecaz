## What is NOT resolved — the crux items still owed by the RUN

(dry-run only), so items 1, 3, 4, 5 are structurally unanswerable here:

1. **Surrogate collapse / does ratio pruning cut %-scanned while holding
   recall — STILL OPEN.** `ip_score_distance_proxy` is *unchanged*:
   `src/am/ec_spire/scan/routing.rs:1656` is still `(1.0 - score).max(0.0)`,
   last touched by packet 004's `a7b94ca0b`. The coder took the ratio-SWEEP path
   (my explicitly-offered alternative), **not** the norm-robust surrogate. That is
   an acceptable choice, but note the residual analytical risk: a wider ratio only
   helps queries whose `best_distance > 0`. For any query whose nearest route
   score floors to ≥1.0 (proxy → *exactly* 0), `threshold = 0 × ratio = 0` at
   **every** ratio, so those queries stay pinned to ~1 route and 2.0/4.0/8.0 do
   not rescue them. If the 007 collapse at 1.25 was driven by exact-0 flooring,
   recall will NOT rise monotonically with the ratio. The run must show recall
   varying sensibly with the ratio and pruning cutting %-scanned *while holding
   ≥0.99* — if it doesn't, that is the definitive signal to either adopt the
   deferred norm-robust surrogate or take the ADR-051/060 escalate/shelve
   decision.
2. **50k/100k on the 143 baseline — NOT RUN.** The config is prepared for
   10k/50k/100k (5 load × 3 scales, matching truth-cache/storage), and it *will*
   sit on 143. But prior evidence is still 10k-only; the AC bites at 50k/100k
   where ≤5% is not free. This is the primary remaining deliverable.
